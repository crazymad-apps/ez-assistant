# Goal 模式设计讨论总结

- 记录日期：2026-08-17
- 状态：设计讨论结论（待纳入版本功能设计）
- 来源：与用户的设计讨论 + 对 `~/github/opencode`、`~/github/hermes-agent`、`~/github/DeepSeek-Reasonix` 三仓库的调研
- 目标：为 ez-assistant 的 Goal 模式提供一份经用户逐点确认的设计基线

---

## 一、调研结论：Goal 模式是什么

**Goal 模式 = 目标驱动的持久自动循环（Ralph loop）**：给 Agent 一个目标，它一轮一轮自动干活，直到目标达成。核心三件套：持久目标、完成判定、自动续跑。与 Plan 模式（先想清楚再动手）本质不同——Goal 是"不达目标不罢休"的无人值守推进。

| 仓库 | Goal 模式 | Todo 列表 | 完成判定 |
| --- | --- | --- | --- |
| opencode | ❌ 无（只有 plan 模式） | ✅ `todowrite`（全量覆盖、session 级、两级可选、平铺） | 无（模型自管） |
| hermes-agent | ✅ `/goal` + kanban `--goal` | 无独立 todo | 独立 judge 模型每轮判定，fail-open，轮次预算兜底 |
| DeepSeek-Reasonix | ✅ `/goal` + kanban goal_mode | ✅ `todo_write` + `complete_step`（两级、证据签收） | 模型自报 `update_goal` + 独立 evaluator 兜底（fail-closed）+ 证据账本 readiness + 预算/无进展门禁 |

**调研结论**：Reasonix 是三家里工程最重的（证据账本 + 裁判 + 状态机防篡改），hermes 居中（裁判每轮跑、较费 token），opencode 最轻（只有 todo，无循环）。

## 二、我们明确不采纳的部分（防过度设计）

经讨论确认，以下重机制**不进入本设计**：

- ❌ 证据账本（Ledger/Receipt）：宿主逐条记录工具执行回执做证据校验——写死点多，本版不做；
- ❌ 独立裁判模型（goaleval/judge）：额外模型调用花 token，且语义判断本身也不可靠——不做；
- ❌ 完成合约五字段（outcome/verification/constraints/boundaries/stop_when）：schema 过重——不做；
- ❌ complete_step 证据签收 + 防篡改状态机：不做；
- ❌ 事后 review 体系：不做。

**采纳的核心**：todo 常驻 + 自报循环 + 控制器刹车（预算/中断/无进展）。

## 三、消息模型

### 3.1 kind 二分为 `user | runtime`

```text
kind: "user"      → 用户真实输入，UI 正常展示，唯一能打断/重定向的来源
kind: "runtime"   → 系统注入（goal 初始化、续跑指令），UI 默认不可见，可审计展开
```

- runtime 消息默认用户不可见，允许按需（审计/调试）展开查看；
- 续跑指令是特殊的 runtime 消息：**明确标记 + 不打断用户输入语义**。

### 3.2 续跑指令内容

```text
[Continuing toward your standing goal]
Goal: <控制器持有的 goal_text>
Current todos:
  [x] ...（completed 前缀）
  [>] ...（当前 in_progress）
  [ ] ...
Next: <上一轮 LLM 报告的 next_action 或缺失项清单>
```

- 目标 + todo 快照通过 user message 注入（不动 system prompt → 保 prompt 缓存、可审计）；
- todo 快照每轮由控制器从权威状态读取注入，不依赖模型记忆（防压缩丢失）。

## 四、输入队列模型（双模式）

| 模式 | 输入队列消费 | 输入源 |
| --- | --- | --- |
| 非 goal（普通会话） | **自动消费**（现有机制不变） | 用户输入按队列序执行 |
| goal 模式 | **挂起自动消费** | 只有 runtime 注入（goal/todo/续跑指令） |

- 用户输入在 goal 模式下照常入队（不丢、UI 可见），但**不被自动消费**；
- goal 循环的三个路径都不消费队列：
  1. 续跑：runtime 消息注入，不消费队列；
  2. blocked：停等，不自动消费队列；
  3. 中断：paused，不自动消费队列，恢复只靠用户显式发送新消息或 `/goal resume`；
- **排队内容与 blocked 的问题无对应关系，自动消费必然时序错乱**——这是禁止自动消费的原因；
- 队列定位：非破坏性暂存区，防止用户"无效时刻的尝试"丢失，不参与自动流转。

## 五、Goal 状态机

```text
running
  ├─ LLM 报 complete          → done
  ├─ LLM 报 blocked           → waiting_user   // 停等，预算冻结
  ├─ 预算/无进展耗尽           → paused(budget)
  ├─ 用户显式中断（epoch++）    → paused(user)
  └─ runtime 续跑             → 不消费输入队列

waiting_user / paused(user)
  └─ 唯一恢复途径：用户显式发送新消息 或 /goal resume
       → running（新消息作为输入，LLM 自主判断是否更新 goal/todo）
```

- **没有任何自动消费分支**：blocked 不消费、中断不消费、续跑不消费；
- 恢复只靠用户显式动作，无隐式触发。

## 六、手动中断与竞态防护（防 bug 关键）

### 6.1 两种"用户输入"语义严格分离

| 输入 | 入口 | 处理 | 经 LLM？ |
| --- | --- | --- | --- |
| 显式中断 | `/goal stop`、UI 停止按钮 | 控制器立即刹车 | ❌ 绝不 |
| 重定向 | 普通聊天消息 | 作为输入进入下一轮，LLM 消化 | ✅ |

显式中断是控制信号，不是输入，走独立通道，控制器同步处理。

### 6.2 中断竞态矩阵

```text
1. 无 Run 在跑、队列空        → 直接置 stopped/paused
2. 有 Run 在跑、队列空        → 置 stopped；正在跑的 Run 自然收尾，报告被拒
3. 有 Run 在跑、队列有续跑 Run → 置 stopped + 清除队列中的续跑 Run；正在跑的收尾
4. 无 Run 在跑、队列有续跑 Run → 置 stopped + 清除队列
```

- 正在跑的 Run 不硬杀（避免半成品写盘），自然结束后其报告被 epoch 拒绝；
- 中断默认 `paused(cause=user)`（可恢复，保留 goal/todo/预算），`clear` 才彻底清除。

### 6.3 三个必写死的防 bug 机制

1. **世代号（epoch）拒绝迟到报告**：stop/clear/替换 goal 时 `epoch++`；所有 `update_goal` 报告和 Run 回调携带 epoch，对不上直接丢弃——防"用户停止后模型 continue 又续跑"；
2. **队列清理**：停止时清除队列中所有 `kind=runtime` 的续跑 Run，只放行正在执行的一个自然收尾；
3. **中断状态默认 paused 可恢复**：误触停止不丢状态，也不会自动恢复（恢复唯一入口 = 用户显式动作）。

## 七、Goal 模式如何进入

**结论：用户手动指令开启为主 + LLM 提议必须用户确认。**

- hermes / Reasonix 均为显式命令开启，无一让 LLM 自主进入自动模式；
- goal 模式是执行语义级切换（自动续跑 + 预算 + 输入队列挂起），授权必须显式——LLM 自主进入等于自我授权（自我授权倒挂）；
- 开启路径只有一条：用户显式确认
  - 用户直接发指令：`/goal <目标>`（含预算，可选）；
  - LLM 提议：模型在回复中建议"此任务适合 goal 模式"，给出目标总结 + 默认预算 → **用户确认才生效**。

## 八、Goal 与 Todo 的关系（已确认）

**Todo 常驻、不归属 Goal；Goal 复用并推进 Todo。**

| 维度 | Goal | Todo |
| --- | --- | --- |
| 本质 | 执行语义：自动续跑、预算、队列挂起、目标声明 | 工作清单：步骤、进度、过程可见性 |
| 生命周期 | 明确周期：开启 → 完成/中断/清除 | 常驻：随会话存在，跨 goal 存活 |
| 归属 | 拥有目标文本 + 预算 + 状态 | 不归属 goal（goal 结束 todo 保留） |
| 依赖 | 依赖 todo（续跑时注入 todo 快照） | 不依赖 goal（非 goal 也可用） |

已确认的两个细节：

1. **goal 开启时 todo 处理：复用当前 TodoList + 模型自主调整**（goal 确认后的第一轮，模型基于目标增删改 todo），不强制清空重建；
2. **goal 完成判定与 todo 耦合度：第一版模型自报 complete、不拦**；todo 只作上下文（续跑注入快照、UI 进度），不作门禁。以后按实测假完成率决定是否加"todo 未全完成时 complete 声明被拦"的轻量校验。

## 九、职责划分（控制器 vs LLM）

| 职责 | 归属 |
| --- | --- |
| 判断完成 / 阻塞 / 停等用户 | LLM（update_goal 报告） |
| 判断目标是否变化、更新 goal/todo | LLM（update_goal.goal_text / todo_write） |
| 注入 runtime 消息（最新 goal + todo 快照） | GoalController |
| 存权威 goal/todo/kind 状态 | GoalController |
| 预算（轮次/token）、无进展、中断兜底 | GoalController |

LLM 管"语义决策"，控制器管"注入 + 存储 + 刹车"。控制器 = 决策表 + 消息构造器 + 状态读写，写死面极小。

## 十、已确认决策清单（用户拍板项）

- [x] kind 简化为 `user | runtime` 两种；runtime 默认不可见、可审计展开；
- [x] 允许 LLM 自主判断是否需要停下来等待用户输入确认（blocked 语义）；
- [x] 用户新输入后，LLM 自主判断是否需要更新 goal 目标和 todo list；
- [x] 暂时不考虑输出过程中的插话：输出中用户输入统一为队列性质（排队、不打断）；
- [x] 只有 blocked、中断情况下可以输入（输入生效窗口）；
- [x] goal 模式续跑不消费输入队列；block 和中断也不自动消费队列（恢复只靠显式输入）；
- [x] 非 goal 模式输入队列自动消费（现有机制），与 goal 模式是两套行为；
- [x] 用户手动中断必须显式处理：epoch 拒迟到报告 + 清续跑队列 + 正在跑的 Run 自然收尾；
- [x] goal 模式进入：用户手动指令开启为主 + LLM 提议需用户确认；
- [x] todo 常驻、不归属 goal、跨 goal 存活；
- [x] goal 开启时复用当前 todo + 模型自主调整；
- [x] 完成判定第一版：模型自报 complete、不拦（不引入证据账本/裁判/合约）。

## 十一、遗留 / 待后续决定

1. `update_goal` 工具需要支持 `goal_text` 可选字段（LLM 更新目标的入口）——具体协议定义待技术方案；
2. 完成核查（todo 未全完成时拦 complete）作为可选增强，按实测假完成率决定；
3. UI 展示：runtime 消息默认隐藏 + 可展开；队列状态可见（"已排队，将在本轮暂停后处理"）；goal/todo 进度展示；
4. 预算上限的默认值 / 用户配置入口；
5. 本设计进入版本功能设计前的评估：纳入哪个版本、与现有 Run 调度/持久化如何衔接。
