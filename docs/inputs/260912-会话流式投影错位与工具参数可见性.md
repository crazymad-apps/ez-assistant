## 一、问题现象

### 1.1 单轮会话较长时流式输出错位

- 历史工具调用记录堆积在最新 step 后面；
- 多轮 step 挤在同一个 reasoning 窗口里输出；
- **会话结束后由权威快照渲染则完全正常**——问题只出在"输出中"的 live 投影。

### 1.2 工具参数不可见

- 权限审批时界面看不到工具的实际参数；
- 工具调用结束前，界面看不到工具的实际参数。

### 1.3 已撤回的需求

工具调用改为"reasoning 之后、正文之前"显示——已确认**不做**，理由见 §5.1。

## 二、现状链路（事实基线）

### 2.1 Runtime 事件与投影

- `agent-core` 每个模型 turn 发 `StepStarted{step}`、`text_delta`/`reasoning_delta{step, part_id}`、
  `tool_*{step, call_id}`；`step` 是 Run 全局单调编号（`crates/agent-core/src/engine.rs:127-179`、`337-343`）。
- `part_id` 由 provider 解码器**每个请求内重新编号**（`part_1`、`part_2`…），因此**跨 step 必然重号**
  （`crates/agent-openai-compatible/src/chat/decode/stream.rs:226-286`）。
- 每个 step 的 assistant 消息在工具批次提交时落账，同一提交点连发
  `ConversationCommitted` + `StepCommitted{step}`
  （`crates/assistant-runtime/src/run/recorder.rs:215-227`）。
- `RunRecord.tools` 整轮累积、从不按 step 清理（`crates/assistant-runtime/src/run.rs:55`）；
  `RunRecord.reasoning/text` 在切换 step 时清空，只保留 active step 的流式文本（`run.rs:194-213`）。

### 2.2 desktop 双源渲染

- **live 尾部**：`LiveExecutionStore` 按 `run_id + step` 分桶累积事件
  （`apps/desktop/src/stores/LiveExecutionStore.ts:193-346`）。
- **权威历史**：`AssistantTurn` 渲染可靠 messages；每个 step 提交后经 80ms debounce 刷新会话视图
  （`apps/desktop/src/stores/RuntimeLifecycleCoordinator.ts:440-455`）。
- 80ms 不是轮询，是"提交类事件到达后合并成一次快照拉取"的合并窗口，作用是完成
  live → 权威的"接力棒交接"。

## 三、根因

### D1 提交水位靠"分页 items 反推"，窗口只有 30 条

- `DEFAULT_PAGE_SIZE = 30`（`crates/assistant-runtime/src/runtime/product.rs:48`），单位是
  **可显示消息条数**（`crates/assistant-runtime/src/storage/conversation.rs:155`），
  约等于「1 条 user + 每 step 1 条 assistant + 少量上下文摘要/控制结果」。
- desktop 用 items 里 `assistant.step` 拼 `committed_steps`（`LiveExecutionStore.ts:97-110`），
  且只统计 `run_id` 存在且 `step` 非空的项。
- 长轮里早期 step 滚出窗口 → 反推不到 → 该 step 不会被删除。窗口跨 run 共享，
  所以"当前会话尾部 30 条里还剩几个 step 水位"才是真正的触发条件。

### D2 补回依据是"整轮全量 tools"，删/补范围不对称

- `#reconcileRunSnapshot` 用
  `snapshot.tools.filter(tool => tool.step === undefined || !committed_steps.has(tool.step))`
  决定把工具补回哪个 step（`LiveExecutionStore.ts:365-366`）。
- 由于 D1 反推不到早期 step，这些 step 的工具**每次对账都被重新补回**。
- 即：**删除依据被分页截断，补回依据是全量的**——两者不对称是错位的直接来源。

### D3 重建只 append，不排序

- `ensureStep` 对不存在的 step 直接追加到数组末尾（`apps/desktop/src/stores/liveExecutionProjection.ts:84-89`），
  `LiveSteps` 按数组顺序渲染（`apps/desktop/src/features/conversation/ConversationView/ToolSegments.tsx:63-91`）。
- 于是被复活的旧 step 出现在最新 step 之后 → 「历史工具堆积在最新 step 后面」。
- 又因为 part_id 跨 step 重号（§2.1），一旦 step 桶被复用/合并，多轮内容会拼进同一个
  reasoning 段 → 「多轮 step 挤在一个 reasoning 窗口」。

### D4 快照兜底重建的粒度不匹配

- 本地没有该 run 时，`#reconcileRunSnapshot` 把 `snapshot.reasoning` / `snapshot.text`
  各当作**一段**使用（`LiveExecutionStore.ts:387-409`）；而这两个字段在 Runtime 侧
  只是当前 active step 的流式文本（`run.rs:194-213`），在 `hydrate()` 恢复路径下
  又是"最后一条 assistant 消息全部 reasoning part 的拼接"（`run.rs:110-132`）。

### D5 已有缺口检测没有接到 live

- `RuntimeProjectionStore.acceptEvent` 已用全局 `RuntimeEventEnvelope.sequence` 检测缺口，
  不连续即返回 `"gap"`（`apps/desktop/src/stores/RuntimeProjectionStore.ts:203-213`）。
- 但 coordinator 在 gap 时**直接 return、不送入 live**（`RuntimeLifecycleCoordinator.ts:396-400`），
  `#handleStreamGap` 也只刷新权威投影与会话视图（同文件 `459+`）→ live 会跨越缺口继续累积。

### D6 补丁痕迹（佐证"多轮打补丁"）

- `removeCommittedTools` 定义并导出，但全仓库无调用点（`liveExecutionProjection.ts:177-193`）：
  曾有一版"按工具粒度对账"，后被"整 step 删除"取代。
- 现存回归用例正是为"已提交工具被重新加回"打的补丁，但它只在 step 仍在 30 条窗口内时成立
  （`apps/desktop/tests/unit/live-execution-store.test.ts:375`）；另一条用例记录了
  "part id 按 step 隔离"的既有约束（同文件 `:184`）。
- `retain_terminal_error`、`status !== "accepted"` 等特例条件
  （`LiveExecutionStore.ts:113-121`）属补偿式判断，而非领域不变式。

## 四、开源实现调研结论

### 4.1 三家做法对照

| 维度 | opencode | hermes | kimi-code |
|---|---|---|---|
| 顺序依据 | 单调可排序 id + 排序 | turn 内序列 + 封口 segment | turn/step/frame 分层 id |
| 变更语义 | part 整段 upsert | 缓冲 + 权威全文覆盖 | 幂等 upsert + 唯一 append |
| live 尾部界定 | 最新且 `!time.completed` 的消息 | 当前 turn 的缓冲区 | 未被 reset 覆盖的操作流 |
| 缺口处理 | `durable(after: seq)` 增量追赶 | `already_streamed` 去重 | `append.offset` → `gap` → reset |
| 旧对象 | 封口后**永不**复活 | 封口 segment 不重写 | upsert 覆盖 |
| 是否重排展示顺序 | 否 | 否（只做过程块合并） | 否 |

### 4.2 要点

- **opencode**：`step.started` 时先把上一条未完成的 assistant 消息写上 `time.completed` 封口、
  再新建一条，注释明确「never resume an older assistant projection」
  （`packages/core/src/session/message-updater.ts:22-23`、`186-208`）；
  投影器按 part id `onConflictDoUpdate` 整段替换（`packages/core/src/session/projector.ts:270-305`）；
  `durable({aggregateID, after: seq})` 先读历史再挂 live 订阅
  （`packages/core/src/event.ts:134`、`585-600`）；
  客户端用 `preserveUnfetched` / `touched` 规则合并分页快照与在途事件、并按 id 排序
  （`packages/app/src/context/server-session.ts:154-185`）。
- **hermes**：delta 累积 + interim 同步 + complete 用权威全文按已显示段落去重收敛
  （`ui-tui/src/app/turnController.ts:558-582`、`669-713`）；
  「思考」与「工具」视为同一类过程信息合并成 shelf，**正文是硬边界**
  （`ui-tui/src/lib/liveProgress.ts:19-38`、`53-79`；测试 `ui-tui/src/lib/liveProgress.test.ts:83-106`）；
  出站投递用显式状态机、对歧义崩溃诚实做 at-least-once
  （`gateway/delivery_ledger.py:1-30`）。
- **kimi-code**：操作流 + 纯函数折叠（`packages/transcript/src/ops/apply.ts:24-70`），
  几乎全部 op 是幂等 upsert，**唯一非幂等的 `append` 自带 offset 并返回 `gap`**
  （`packages/transcript/src/ops/operation.ts:46`）；粒度分级 `off/turn/block/delta`
  与「粒度升级必须由 reset 快照重建」（`packages/transcript/src/granularity/grade.ts`）。

### 4.3 可照搬 / 不适用

可照搬：

1. 给 step/消息一个单调可排序身份，**渲染按身份排序**而非数组位置；
2. "未完成"是对象自身状态，不靠外部快照推断；
3. **封口即不回头**：已提交对象不再接受增量；
4. 结束时用**权威内容覆盖**本地累积；
5. 缺口用已有信号检测后**作废重来**，而不是硬补。

不适用：

- opencode 的 `durable(after: seq)` 需要可重放事件日志，我们的事件流不可重放，成本高（可作二期）；
- kimi 的 per-chunk offset、`gap` 对象、粒度分级、`reset-on-transition` 是为"多订阅者 + 可重放日志"
  设计的，我们不具备也不需要该复杂度；
- hermes 的文本级 `finalTail` 去重适用于单一文本流的终端 UI，我们是结构化 segments，
  更适合"整段覆盖"路线。

## 五、已确认的设计决策

### 5.1 展示顺序维持原样，不做重排也不做聚合折叠

理由：

- 模型发出 `tool_calls` 即结束该 turn（看不到工具结果），因此**工具块必在 step 末尾**，
  "正文 → 工具 → 正文"在物理上不可能；
- 但 **reasoning ↔ 正文交错真实存在**（推理模型边想边说），一刀切重排会在
  `[R1, T1, R2, G]` 上产生语义失真；
- opencode / hermes / kimi 三家**均不重排**；hermes 只做"过程信息合并 + 正文边界"。

### 5.2 `StepCommitted` 到达即自动封口

低于/等于该水位的 step 不再接受任何事件，迟到事件直接丢弃。

### 5.3 一期只做"稳定投影 + 参数可见"

不改展示语义、不改数据顺序语义。

## 六、一期范围（待落实）

## 2026-09-16 补充：历史分页被全局实时事件打断

- 状态：已定位并纳入 `v0.27.0` C05；2026-09-21 功能/技术设计及开发计划已确认，M0 与循环验收已获用户确认，待提交。
- 目标版本：`v0.27.0`，见[总体设计](../versions/v0.27.0/总体设计.md)；以下保留最初反馈和核查结论。
- 来源：用户向上滚动自动加载历史消息时的截图及后续讨论。

### 现象与已核查原因

- 向上加载更早消息时，界面显示 `runtime state is changing; retry the snapshot`。
- `Runtime::list_conversation_page` 比较读取前后的 Runtime 全局事件序号；连续 4 次
  读取期间序号都发生变化后，返回 `snapshot_busy`。
- 每条已发布事件的序号本身固定，变化的是 Runtime 最新发布事件的序号。当前会话的
  文字、思考输出，以及其他会话的事件，都可能使检查失败，即使所读取的旧历史页没有变化。
- 前端 `RootStore::loadPreviousConversationPage` 只特殊处理 `snapshot_stale`，
  未处理暂时繁忙的 `snapshot_busy`，因此将后端英文错误直接显示为历史加载错误。

### 已确认的处理原则

用户明确：“历史消息就是历史消息。”

- 历史分页不应要求整个 Runtime 在读取期间没有新事件。
- 新消息、思考输出、工具进度及其他会话活动，不应仅因推进全局事件序号而使旧历史页失效。
- 只有历史本身被清空、重写等实际影响分页有效性的变化，才应要求重新加载。
- 后续修复应收窄后端一致性校验范围，同时保证分页读取一致、前端滚动位置稳定。
- 前端对暂时繁忙的有限重试仅作为补充，不能替代后端校验范围的修正。

### 后续验证重点

- 当前会话持续流式输出、其他会话并发运行时，仍能正常向上分页读取旧历史。
- 历史被清空或重写、游标实际失效时，正确拒绝旧游标并恢复展示。
- 加载或重试后无消息重复、遗漏或滚动位置跳变。

本次只记录问题与处理原则，未修改代码或推进版本计划。
