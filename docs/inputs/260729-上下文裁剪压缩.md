## 2026-09-18 真实会话诊断：重复压缩由旧 usage 触发

对“基于草图的密集架与设备布置及墙厚标注”本地会话只读核查后确认：

- 模型窗口 `256000`、阈值 `204800`；压缩前父模型结果为 `205421` token，第一次压缩正常触发。
- 第一次摘要成功后，replacement 保留的最近 Assistant Result 仍带有压缩前 usage；窗口判断立即
  再次判定超限。
- 第二次请求只是在重新摘要第一次摘要；旧 usage 仍未失效，最终达到两次自动恢复上限并失败。
- UI 的 `1912K Token` 是子任务多次请求的累计消耗，不是父上下文或单次请求大小。
- 两次摘要请求均未命中输入缓存，而压缩前正常请求有大量缓存命中。后续旁路摘要不得先改变原
  上下文或清空影响缓存前缀的工具定义，应在原模型上下文末尾追加压缩指令。

由此调整优先级：先解决压缩后的 usage 权威边界和旁路请求缓存前缀，再构造专门的单轮大上下文
用例。只有修复后仍出现 protected tail 真实超限，才重新评估轮内拆分或剪枝。

以下保留历史反馈与裁剪方案讨论。历史章节中“已确认的数据存储方向”等表述描述当时的裁剪
候选方案约束，不代表本版必须采用裁剪或某种具体 replacement 形状；当前范围以上述最新方向
和版本总体设计为准。文件路径保持原名，以保留既有引用。

## 问题定义

长会话中旧 Tool Result、日志、文件内容和 Shell 输出可能占用大量上下文。裁剪压缩
不使用模型重写整段历史，而是把较旧、低价值且已经闭合的内容替换为有明确语义的
精简表示。

裁剪压缩与 Rolling Summary 的区别：

- 裁剪压缩主要减少大体积内容，通常无需额外模型调用，确定性较高但压缩能力有限；
- Rolling Summary 使用模型重新表达较早历史，压缩能力更强，但存在费用、延迟和
  摘要遗漏风险。

## 已确认的数据存储方向

- Runtime Conversation History 继续保存完整原始消息，不修改、不删除，也不在原始
  Message List 上写入裁剪策略标记；
- 裁剪结果写入新的 `ContextCheckpoint.replacement` 派生副本；
- replacement 保留原 `MessageId`、`ToolCallId`、Tool Result 状态和消息顺序，只替换
  被选中 Tool Result 的大体积内容；
- replacement 必须使用可识别的派生裁剪表示，不能用普通 error ToolResult 冒充；
- Provider 投影仍必须包含完整配对的 Assistant Tool Call 与 ToolMessage；
- 原始内容继续可通过 Conversation History 中的消息/调用标识定位；
- Checkpoint 仍只保存完整 replacement，不增加 `covers_through`、父 Checkpoint 或
  额外位置字段。

未来可评估类似以下 provider-neutral 表达，具体类型由对应版本技术方案决定：

```text
ToolResultContent::Compacted {
  summary_or_notice,
  omitted_size
}
```

## 在现有压缩架构中的接入方式

裁剪压缩不得新增另一套调用链。它作为新的 Compression Strategy 接入 Runtime 唯一
`compact_context` 入口，复用：

- 同会话串行；
- 最新有效 projection 读取；
- 闭合历史块与 protected tail；
- replacement 完整性和 Tool Call/Result 配对校验；
- Strategy Candidate/NoOp 结果和候选有效性校验；
- Context Checkpoint 原子提交；
- Compacted/NoOp/Failed 结果；
- 自动交接与用户主动压缩的既有调用封装。

未来可以增加：

- `ToolResultPruning`：只裁剪符合条件的旧 Tool Result；
- `HybridCompression`：按策略组合裁剪和 Rolling Summary，但最终只生成一个
  replacement、只提交一次 Checkpoint。

## 2026-09-17 历史补充：单轮 Run 上下文耗尽，提前规划剪枝

- 来源：用户实际使用反馈。
- 状态：历史观察与候选方向；已被 2026-09-18 真实会话诊断修正，不再作为
  C02 直接实现剪枝的依据。

### 原始反馈与影响

> 现在出现了单轮run里面就占用了过多的上下文窗口, 导致即便压缩后, 也无法继续进行的地步, 需要提前考虑加入剪枝策略, 标记一下优先级

当时该现象被判断为单轮 Run 内容量耗尽，因此候选方案要求覆盖同一 Run 多次模型与
工具交互产生的上下文增长。2026-09-18 核查后已确认，该样本的直接原因是旧 usage 未失效，
因此下列剪枝内容只保留为历史候选，不表示真实轮内空间不足已被证实。

### 当时的候选处理方向（已暂缓）

- 将轮内剪枝纳入优先设计范围：评估在下一次模型请求前，裁剪当前 Run 中较早且已闭合的
  大体积 Tool Result、日志、文件内容和 Shell 输出；不能只处理前几轮历史。
- 核查 protected tail 的保护粒度，避免当前轮所有内容都不可裁剪，导致压缩无法释放有效空间。
- 沿用已有压缩入口和派生 projection，保留原始历史及可回查标识；保持工具调用与结果配对，
  保护未完成交互、必要 Provider 状态、当前任务约束和记忆变更。
- 明确继续请求所需的空间及有效回收判定；裁剪或摘要仍不足时，应有界停止并提供原因，
  避免反复执行无效压缩。具体阈值、候选规则和单条超大结果的处理由技术方案确定。

### 当时的候选验收重点（已暂缓）

- 单轮 Run 多次工具调用积累大量上下文时，可通过轮内剪枝释放空间并继续执行。
- 已执行工具不因剪枝被重放，原始结果可追溯，连续剪枝与摘要后任务约束及记忆变更仍保留。
- 对确实无法释放足够空间的输入有明确、有界的失败结果，不进入压缩与失败循环。

## 2026-09-28 补充：服务端历史续接与切换模型自动重建

- 状态：已纳入 `v0.29.0` [总体设计](../versions/v0.29.0/总体设计.md) F06；用户授权优先设计，[功能设计](../versions/v0.29.0/features/F06-服务端历史续接与上下文重建/功能设计.md)与[技术方案](../versions/v0.29.0/features/F06-服务端历史续接与上下文重建/技术方案.md)草稿待确认，未实现。
- 用户明确要求：切换模型时自动重建上下文，无需用户手动清理状态或新建会话。

### 已明确的行为

- 切换模型后，在下一次模型请求前从本地有效上下文自动重建输入，不沿用旧模型的
  `previous_response_id` 或远端会话绑定；同一服务商内切换模型也适用。
- 重建使用当前指令、已有压缩摘要、保留的近期消息及必要工具调用与结果；不恢复已被
  摘要替换的全部原始历史，不重新执行历史工具，不改变用户会话身份。
- 目标接口支持且启用了服务端续接时，用重建后的完整有效上下文建立新链，再使用增量
  续接；不支持或未启用时，按无状态接口发送完整有效上下文。切回原模型也重新建立，
  不恢复可能已落后于当前会话的旧链。
- Provider 专属状态只在目标接口明确兼容时使用，不能跨服务商直接搬运不透明状态；
  重建输入仍须满足目标模型的上下文限制及工具交换配对规则。

### 待正式设计的配置与生命周期

- 区分接口是否支持响应存储／历史续接，以及具体服务商连接是否启用续接；不能只凭
  支持 Responses 格式或接受 `store` 参数推断支持历史续接。
- 当前讨论建议由服务商身份与协议提供能力默认值，具体连接提供启用策略，自定义接口
  按需覆盖；配置归属、字段和默认值尚未最终确认。
- 本地上下文保持为可独立重建的权威事实。压缩提交、连接或协议切换、续接失效时的
  重建统一复用该事实；续接 ID 属于执行状态，不属于模型配置。
- 进行中的调用与模型切换如何衔接、重建失败处理及状态提交边界在技术方案中明确，
  不从本输入推导中断当前 Run 或自动重试工具副作用。

### 本轮补充确认：重启恢复续接

- 2026-09-28 用户否定“仅内存保存续接 ID、重启后直接重建”的取舍；助手撤回后，用户确认继续按恢复方案设计。
- 响应 ID 及对应连接、模型、身份和本地上下文边界须可靠保存；重启本身不使其失效。
- 恢复后一致就继续增量续接；压缩、模型切换、真实绑定变化或服务端明确拒绝旧 ID 时才重建。

### 使用反馈与目标

用户反馈现有滚动压缩限制较大，经常出现压缩后窗口占用仍超过 50% 的情况，要求后续改进。
该比例是用户使用反馈，尚未对本次样本核查真实有效上下文、usage 口径及各部分占用；不能直接
归因于最近完整 User Turn 的保护粒度，也不能认定为已定位的计量错误。

目标是改善长任务的实际可用空间与连续执行能力，评估解除现有 Rolling Summary 对当前轮的
容量限制；不把“任何任务压缩后必须低于 50%”或某个固定压缩比直接设为已确认验收标准。

### 已确认方向与后续设计约束

- 统一上下文管理入口，按显式装配的能力与策略选择本地滚动摘要或服务端自动压缩；上下层
  调用方只处理可继续、上下文更新、占用已知/估算/未知及恢复等统一语义，不选择具体 Provider API。
  优先复用现有装配、ProviderState、Checkpoint 和恢复机制，不预设新增公共 trait 或第二份可变历史。
- 同一路径只保留一个自动压缩负责人。服务端自动模式下不再由本地阈值抢先触发 Rolling Summary；
  本地继续承担原始历史保存、状态可靠提交和有界失败恢复。通用本地压缩仍服务未支持该能力的路由。
- 首先面向 OpenAI Responses 的 `context_management` / `compact_threshold` 核查真实支持，不能由
  Responses 兼容格式或历史续接能力推断自动压缩能力。独立 `/responses/compact` 作为受控压缩
  候选保留，是否纳入首版由正式设计决定。
- 将调用 token 消耗与有效上下文占用分开表达。发生服务端压缩后，不能直接把该次
  `usage.total_tokens` 当作压缩后窗口大小，也不能按密文字节数或压缩调用用量推算剩余占用。
  优先评估 `/responses/input_tokens` 对下一次真实输入的计量，并验证 compaction item 与
  `previous_response_id` 的计数行为；测量须绑定实际请求、模型路由及上下文版本。
- 窗口展示采用“有效输入 token / 模型窗口”，另计输出预留与必要余量；失效测量须重新校准。
  无法可靠计量时明确标为估算或未知，不沿用压缩前百分比，不扣除缓存命中 token 来虚减占用。
- 原始产品历史与有效模型输入分开投影。加密 compaction item 按 Provider 原生状态保留和回传，
  不伪装成普通文本摘要；响应完整成功并校验后再与可靠链头一起提交，取消或失败不污染旧检查点。
  模型切换、重启、远端链失效及不兼容 opaque state 的恢复来源与额度须在正式设计中明确。
- 正式设计须显式修订当前“Provider 不在原执行内隐藏压缩”和以最近响应总 usage 作为窗口基数
  的相关架构约束，形成可观察的能力及生命周期；本输入不直接改变现行模块规则。

## 2026-10-14 补充 自动与手动压缩请求参数统一

- 状态：待修复，目标版本待定；用户要求记录本次问题。
- 范围：本地 Rolling Summary 的请求构造与失败诊断；服务端原生 compact 不属于本次案例。

### 已确认的问题

自动压缩复制正常生成请求，保留工具定义并设置 `tool_choice: none`；手动压缩先清空工具列表，
Responses 编码器因此同时省略 `tools` 与 `tool_choice`。两条入口虽然复用摘要策略，实际发送
的请求参数仍不一致。

真实调用对照中，历史输入、系统提示词及其他参数相同，带工具定义和 `tool_choice: none` 的
自动摘要请求返回 HTTP 400 `invalid_request_error`，不带这两个字段的随后摘要请求成功。
现有证据高度指向工具参数组合的上游兼容问题；上游仅返回泛化错误，尚未单独定位到某个字段。

压缩服务已装配现有有限重试器，但该 400 被归类为 `ModelError::Provider`，不满足瞬态错误
重试条件。Runtime 随后以 `context_compaction_failed (reason=threshold_reached)` 结束 Run。
未重试是当前分类规则的结果，修复重点应放在请求构造差异。

### 修正方向

- 自动与手动本地压缩统一采用无工具的摘要请求构造，复用现有入口与策略，避免再次形成两套参数规则。
- 历史工具调用与结果继续完整配对保留；清空当前请求的可用工具定义不等于删除历史工具交换。
- 本方向调整了 2026-09-18 为缓存前缀保留工具定义的取舍；实施时明确缓存影响，兼容性与可继续执行优先。
- 保留现有瞬态错误的有限重试，不把所有 HTTP 400 改成自动重试，也不重放已执行工具或整个 Run。
- 压缩失败诊断应保留可展示的错误类别与 HTTP 状态，便于区分请求拒绝、传输失败和摘要无效。

### 后续验收关注点

同一上下文和模型配置下，自动、手动摘要请求除必要调用关联信息外保持一致；覆盖当前请求不带
工具、历史工具交换与图片保留、真实 Responses 路由兼容、瞬态错误重试及普通 400 有界失败。
摘要成功后继续沿用既有可靠提交与续跑，不重复执行历史工具副作用。
