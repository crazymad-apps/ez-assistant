# 插件应用界面与消息卡片机制讨论

- 记录日期：2026-10-15。
- 状态：已纳入 `v0.33.0`，版本待启动，具体设计继续深化。
- 来源：用户关于插件通信协议、控制协议、渲染方式和卡片发布入口的会话讨论。
- 目标版本：`v0.33.0`；2026-10-15 用户明确安排到下一版本，见[版本路线](../版本管理.md#runtime-阶段版本路线)。

本次确认版本归属，不改变当前 `v0.32.0` 范围；尚未开始正式功能设计、开发计划或代码实现。

本文保留讨论中已确认的职责边界、卡片发布方向和最新快照恢复机制，并区分候选方案与待定问题。示例中的字段、
协议名称和返回结构是讨论草案，不代表已实现或已冻结的产品契约。

## 一、原始目标与用户约束

深化插件机制，使插件能够提供可直接使用的应用界面，包括：

- 直接放入消息流的交互卡片。
- 可以从侧边资源栏打开的插件应用页面。
- 消息流卡片与侧栏应用之间的打开、定位、消息传递和其他联动。

讨论重点是通信协议、控制协议和渲染机制，不能仅停留在卡片与页面的表现形式。

用户明确要求：Agent 本体不要过多干预插件的业务组织，插件卡片和应用页面如何通信、业务如何
组织，由插件自己决定。Agent Core 专注 LLM ReAct 循环；宿主提供通用承载与协议转发能力。

## 二、已确认的职责边界

| 层次 | 职责 |
| --- | --- |
| Agent Core | 保持现有模型调用、工具调用、结果反馈与 ReAct 循环，不增加插件业务分支 |
| Runtime／Runtime Host | 按现有工具执行机制承接发布请求，管理必要的身份、权限、持久化与传输 |
| 客户端宿主 | 承载卡片和应用容器，负责界面加载、消息路由、尺寸、焦点与生命周期 |
| 插件 | 定义业务数据、卡片参数、界面内容、内部通信、状态同步和业务持久化方式 |

- 宿主可以理解插件身份、入口、通信端点与请求关联，但不解释报价、天气、图纸等业务字段。
- 插件业务对象、版本、订阅、状态机和数据源不应被强制纳入统一的宿主业务模型。
- 通用路由、界面挂载与权限边界属于宿主，不进入 Agent Core 的推理循环。
- 业务插件源码、Skill、前端资源和打包继续归独立插件仓库维护；本仓库负责通用契约及宿主接入。

## 三、已确认的卡片发布方向：统一走工具调用

提供稳定内置工具 `publish_card`，由 LLM 按普通工具调用流程主动请求发布卡片。

用户确认两条路径可以结合使用：

```text
MCP／其他工具组织业务结果和卡片参数
    → 普通工具结果告知 LLM 下一步可调用 publish_card
    → LLM 将所需参数传给 publish_card
    → 宿主发布卡片

Skill 说明卡片用途、参数结构和组织方式
    → LLM 获取必要信息并组织参数
    → LLM 调用 publish_card
    → 宿主发布卡片
```

### 3.1 MCP／其他工具路径

插件工具可以在普通工具结果中给出卡片标识、参数以及下一步调用建议，例如：

```json
{
  "summary": "报价已生成，共 12 个项目。",
  "suggested_action": {
    "tool": "publish_card",
    "arguments": {
      "card": "quotation.summary",
      "input": {
        "quote_ref": "quote-123"
      }
    }
  }
}
```

`suggested_action` 只是示意，不是宿主必须识别的新协议字段。LLM 读取普通工具结果后决定并调用
`publish_card`；宿主不解析该字段自动执行，Agent Core 不为它增加特殊逻辑。调用仍遵循现有
工具授权和执行规则。

### 3.2 Skill 路径

对于天气查询等轻量功能，Skill 可以说明可用卡片标识、适用条件、输入结构、示例以及如何取得
和组织所需数据。LLM 按 Skill 指导调用 `publish_card`，不要求为了卡片展示单独建立 MCP Server。

卡片也可以只接收初始化参数，再由插件自行取数；具体选择属于插件。若模型只获知卡片已发布，
而没有获取天气等业务结果，就不能把发布回执当作实际业务查询结果。

插件清单中的入口和参数 schema 供宿主加载、校验；Skill 与工具结果指导模型使用。首版不必因此
另建卡片搜索或发现工具，是否需要集中目录和渐进披露留待真实规模评估。

### 3.3 模型上下文与冗余信息

- 卡片调用参数会经过 LLM，这是本次确认的工具链组织方式；不能宣称这些参数完全不占模型上下文。
- HTML、JS、组件结构、样式等渲染实现来自插件包，不需要模型生成或在工具结果间转传。
- 小型展示数据可以直接放入参数；较大数据可以使用插件定义的引用，由插件界面读取。
- `publish_card` 只返回简短发布回执，不再次返回整份输入或卡片内容。
- 发布后的最新快照由卡片通过界面桥接上报，直接供宿主保存与恢复，不经过 LLM。

这一区分取代早期“所有卡片数据均通过模型不可见旁路交付”的设想。

## 四、publish_card 契约草案

输入采用稳定外层、插件自定义内层：

```json
{
  "card": "quotation.summary",
  "input": {
    "quote_ref": "quote-123"
  }
}
```

- `card`：已安装插件声明的卡片标识，具备可消歧的插件归属。
- `input`：插件定义的初始化参数，宿主按入口声明进行校验、保存和投递，不解释业务含义。
- 会话、Run 和调用来源由工具执行上下文绑定，不交给模型自由指定。
- 界面入口、固定标题、图标和资源位置优先来自插件声明，不要求模型提交任意代码或页面地址。

成功返回示意：

```json
{
  "status": "published",
  "card_id": "card-456"
}
```

讨论中的成功语义是：宿主已经保存发布记录，可通知客户端展示；不表示客户端已加载完成、
插件取数成功或业务操作已完成。`card_id` 表示持久发布引用，不是前端组件实例。

失败应提供模型可理解、可修正的简短错误，例如入口不可用或缺少参数。错误具体使用既有工具
错误结构还是业务返回字段，待技术方案确定，不预建第二套错误机制。前端加载失败与工具发布
失败应区分，不能因后续渲染失败自动重复发布卡片。

工具注册与实现、产品持久化和客户端展示需要扩展；“不改核心逻辑”指复用现有 Agent 工具调用
与 ReAct 机制，不代表整个产品零改动。

## 五、消息流展示位置与生命周期：当前讨论倾向

卡片显示在回复正文区域，作为独立内容块，默认放在本轮正文之后，不嵌套在工具执行卡片内部。
工具记录仍用于展示调用过程、参数与诊断；卡片可以关联来源调用，但展示位置绑定所属回复轮次。

```text
助手本轮回复
├─ 执行过程（可折叠）
│  └─ 工具调用记录
├─ 回复正文
└─ 插件卡片
```

曾讨论卡片可以在正文完成前先出现，后续正文在其上方更新，卡片保持在该轮尾部。多张卡片排序、
流式滚动稳定性，以及多次 Assistant 消息、子任务与回复轮次的具体映射尚未定稿。

挂载和销毁的候选原则：

- 客户端按可视范围和资源预算挂载，离屏后允许销毁或有限缓存，避免所有历史卡片长期运行。
- 重新挂载时交付初始参数与最新已保存快照，由卡片恢复展示与交互状态，不重放历史业务操作。
- 销毁界面释放通信端点，不删除历史卡片记录，也不默认取消插件后端已接纳的业务任务。
- 插件不能依赖界面永远存在；需保留的业务结果由插件自己保存。

具体缓存规模、卸载通知、未提交输入恢复与流式阶段挂载时机仍待设计。

## 六、交互与侧栏应用

卡片内部的按钮、表单、图表等交互由插件实现。宿主可提供通用能力：

- 调用插件后端或向同插件其他端点传递消息。
- 打开已声明的插件应用入口，在侧边资源栏打开或复用标签页。
- 传递插件自定义初始化、定位和选中参数。
- 上报本卡片的最新快照，由宿主持久保存，并在重新挂载时交回卡片。
- 请求容器尺寸变化，以及在明确需要时通过现有会话输入机制请求 Agent 参与。

卡片打开侧栏应用只表达“入口 + 插件参数”；宿主不解释参数中的业务对象。打开容器与插件业务
加载成功是不同结果。卡片和页面可以直接通过宿主路由通信，也可以共同连接插件后端；宿主不
强制采用共享状态或资源订阅模型。

同一 View 改变展示容器，与打开另一个可同时存在的 View，是两种不同操作。复用键、页面归属、
关闭行为和具体桥接方法尚未确定。

## 七、已确认的最新快照与恢复机制

2026-10-15 用户明确：需要维护的是卡片最新的交互与展示数据快照，用于恢复渲染。例如确认按钮
已经完成操作，重新加载后不能回到可再次点击的初始状态。快照由卡片自己上报，宿主保存。

本节替换此前关于发布时历史快照、不可变业务版本及静态／实时卡片分类的讨论；不为这一需求
建立通用业务历史版本机制。

### 7.1 保存内容与完整链路

```text
LLM 调用 publish_card
    → 宿主创建卡片发布记录，保存入口和初始参数
    → 卡片加载、取数或交互后，上报最新快照
    → Runtime 持久保存，替换该卡片上一份快照
    → 重新挂载时，宿主交付初始参数和最新已保存快照
    → 卡片自行恢复内容与交互状态
```

| 内容 | 职责 |
| --- | --- |
| 卡片入口、初始参数与消息位置 | 宿主随发布记录保存，作为首次初始化与恢复定位的依据 |
| 最新快照 | 卡片自行组织并上报，宿主原样保存，用于恢复最后一次已保存状态 |
| 界面代码 | 随插件包提供，不在每条消息重复保存 |
| 业务数据与实际操作结果 | 仍由插件管理，卡片快照不替代业务持久化或执行核验 |

每张卡片只维护最新一份快照，每次成功上报替换上一份，不默认保存快照历史。快照可以包含当前
展示数据、按钮状态、业务结果摘要，以及插件认为需要恢复的其他界面状态；宿主不解释这些字段。

`publish_card` 即使只传业务引用，也不要求引用指向不可变版本。卡片可以按引用自行加载，并将
恢复需要的状态上报为快照；重新挂载优先按已保存快照恢复，是否继续取数或同步由插件决定。
尚无快照时按初始参数初始化，不把未上报或未保存的状态宣称为已恢复。

### 7.2 上报与恢复契约方向

界面桥接可提供类似 `await card.saveSnapshot(snapshot)` 的能力，方法名称和具体 wire 结构待定。

- 成功响应表示 Runtime 已持久保存，不仅是客户端内存更新或消息已发出。
- 卡片身份由宿主绑定，上报只更新所属卡片，组件不能自行指定其他卡片作为写入目标。
- 重新挂载时提供 `initialInput` 和 `snapshot`，由插件解释快照并恢复渲染；字段名仅为示意。
- 快照更新不经过 LLM，不产生新的 `publish_card` 调用，不追加会话消息，也不改变卡片位置。
- 保存失败不能反馈为成功；未完成的保存与异常恢复需要明确处理。
- 迟到或已销毁实例发出的旧快照不能覆盖较新状态；具体排序与并发控制方式留待技术设计。

卡片发布继续统一走工具调用；快照上报属于界面状态保存，两者职责不同，均无需修改 Agent Core
的 ReAct 逻辑。

### 7.3 确认按钮示例

确认完成后，卡片可上报：

```json
{
  "state": "confirmed",
  "result": {
    "message": "已确认"
  }
}
```

重新挂载时，插件据此展示“已确认”并禁用按钮。宿主不理解 `confirmed` 的业务含义。

对于存在异步操作的卡片，可采用“待确认 → 处理中 → 已确认”的插件内部状态：先保存“处理中”，
再执行操作，完成后保存最终状态。若重载时仍为“处理中”，保持不可重复点击，由插件核对实际
执行结果再更新快照。该状态与执行核验由插件实现，不成为宿主统一业务状态机；实际业务防重复
执行也仍由插件负责。

快照大小限制、上报时机与频率、保存失败处理、多实例更新顺序，以及插件升级后的格式兼容和
不可用展示，属于后续需要细化的技术问题；最新快照由卡片上报、宿主持久保存并交回恢复的方向
已获用户确认。

## 八、通信与渲染候选，不作为本次选型结论

前期讨论考察过 MCP Apps、JSON-RPC／postMessage 桥接和隔离 HTML 界面，可作为后续参考。
目前未确认必须采用 MCP Apps，也不能让 MCP 成为卡片发布或轻量插件的前置条件。

通信的方向性原则是外层管理路由、关联、身份和生命周期，内层承载插件自定义载荷。插件可自行
选择业务通信方式，宿主不强制统一报价对象、资源版本、同步事件或增量补丁。

渲染候选倾向插件提供构建好的 HTML/CSS/JS，由宿主隔离承载并提供桥接。iframe、不同源资源加载、
CSP、桌面与 Web 的一致性、大资源传输等仍需验证；不能仅因加入 iframe 就宣称完成隔离。

## 九、后续讨论入口

1. 细化最新快照上报、持久保存回执、挂载恢复和迟到更新隔离的最小契约。
2. 明确正文尾部展示在现有消息、Run 和子任务结构中的归属、排序与流式行为。
3. 细化卡片挂载、销毁、交互恢复与插件升级后的展示策略。
4. 确定插件界面与宿主桥接、打开侧栏页面和端点路由的最小契约。
5. 评估隔离渲染与资源加载方式，再确定是否采用 MCP Apps 的相关部分。
6. `v0.33.0` 启动设计时，按开发流程形成设计与计划；本次版本安排不构成实施授权。
