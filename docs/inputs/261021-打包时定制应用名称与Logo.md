# 打包时定制应用名称、Logo 与默认数据目录

日期：2026-10-21。目标版本：**v0.32.2**，状态：**待启动**；用户已确认纳入本版计划，
本文保留为需求输入与候选方向，尚未进入正式设计或实现。

## 一、用户需求

为了方便首次交付，打包时需要灵活定制应用名称、安装包名称、Logo 和默认数据目录，
无需为每次交付逐处修改源码。

2026-10-21 用户已明确的要求如下：

| 项目 | 要求 |
| --- | --- |
| 应用名称 | 可在打包时指定，安装后的应用名称使用定制名称 |
| 安装包名称 | 随应用名称统一定制，按平台文件命名规则处理字符并附加版本、平台、架构等必要信息 |
| Logo | 可在打包时提供，覆盖系统应用图标与应用内品牌标识 |
| 品牌关键词 | 用户可见的 `ez-assistant`、`EZ Assistant` 等品牌名称统一使用定制名称；内部标识不做全局文本替换 |
| 默认数据目录 | 纳入打包定制，例如将用户主目录下的 `.ez-assistant` 改为 `.acme-assistant`；目录名独立于应用显示名称配置 |
| 应用身份 | 沿用同一应用身份、覆盖安装和升级，不要求不同品牌在同一台电脑上共存 |
| 数据迁移 | 主要面向首次交付，暂不做旧数据迁移，不搬移、合并或清理旧目录 |

默认数据目录的最新要求取代前期“保持现有数据位置”的候选约束；
沿用应用身份不再意味着默认数据路径必须保持 `.ez-assistant`。
后续章节中的具体实现建议与待明确事项不视为已经确认的完整技术方案。
本项与企业中心多机构租户同属 v0.32.2，排在 v0.32.1 之后、v0.33.0 之前，
版本范围见[版本管理](../版本管理.md)。当前 v0.32.1 的 Feature 与实施门禁保持。

## 二、现有实现核查

- `apps/desktop/src-tauri/tauri.conf.json` 固定配置 `productName`、应用标识和窗口标题；
  macOS、Windows 平台配置也各自定义窗口标题和图标路径。
- `apps/desktop/scripts/generate-macos-icon.mjs`、`generate-windows-icon.mjs` 和
  `generate-macos-tray-icon.mjs` 已有源 SVG 到平台图标的生成能力，可优先复用。
- 登录布局和会话导航直接导入 `apps/desktop/app-icon.svg`；登录布局、HTML 标题、托盘提示及
  部分通知仍使用固定产品名称，只改安装包配置不能覆盖这些展示。
- macOS 发布脚本从基础 Tauri 配置读取产品名以定位产物；Windows 发布脚本还固定使用
  `EZ-Assistant` 作为最终安装包文件名前缀。发布流程须与最终生效的品牌配置一致。
- Host 构建通过 `EZ_ASSISTANT_WEB_DIST` 内嵌前端资源；定制构建需要让 Desktop 与随包 Host
  使用同一次品牌构建的资源，避免桌面界面和浏览器入口显示不同品牌。
- Desktop 的 `apps/desktop/src-tauri/src/runtime_bootstrap.rs` 与 Host 的
  `apps/runtime-host/src/config.rs` 分别解析默认 Runtime Home，目前正式默认目录均为
  用户主目录下的 `.ez-assistant`；已有 `EZ_ASSISTANT_RUNTIME_HOME` 环境变量覆盖，
  Host 另支持 `--runtime-home` 参数。定制默认值需要统一这两处入口。
- `.ez-assistant/skills` 还出现在 Skill 扫描及打开目录等逻辑中；正式设计须核对实际 Runtime Home
  派生路径与工作区 Skill 目录约定的区别，不能通过全局替换目录字符串实现本需求。

以上为当前工作树源码事实，不代表定制能力已经实现或安装包已经验证。

## 三、建议的使用方式与范围

建议由现有打包入口接收一份交付配置，指定应用名称、Logo 源文件和默认数据目录名；
不传配置时沿用现有默认品牌与目录。
应用名称与安装包文件名共用一个名称来源，不增加独立的安装包品牌名字段。
同一份配置用于安装名称、快捷方式、窗口／页面标题、登录与导航标识、托盘提示和交付文件命名。
系统应用图标由源文件自动生成，macOS 托盘可单独提供适配模板图标的素材。

默认数据目录名单独配置，按当前操作系统用户的主目录解析，不在包内写入某台机器的绝对路径。
例如应用显示名称为“示例助手”，目录名可以固定为 `.acme-assistant`，两者无需相同。
Desktop 启动、发现和管理 Host，以及 Host 自身读取配置与存储数据时，必须使用同一个解析结果；
显式环境变量和 Host 启动参数继续按现有优先级覆盖打包默认值。
同一交付品牌后续升级时保持目录名稳定，不能仅因显示名称变化而切换数据目录。

优先沿现有 Tauri 配置合并、前端构建和图标生成脚本实现，不逐处手改品牌常量，不手改生成图标。
构建 A 品牌后再构建 B 品牌或默认品牌时，须避免遗留素材、名称、默认目录、前端资源和产物互相污染；
校验输入应在耗时构建前完成，图标、名称和默认目录应在平台签名之前确定。
真实交付客户的名称、素材、目录配置按仓库私有资料规则保存，不写入公开示例或锁文件。

此需求暂不包含企业中心中的在线品牌编辑、机构管理员上传安装包或运行期间切换品牌。
与[多机构租户初步规划](261021-企业中心多机构租户初步规划.md)中的平台统一分发边界一致：
打包定制由构建／交付流程承载，不给机构管理员新增安装包生成、上传、发布或品牌配置权限。
正式设计时共同核对安装、更新与兼容边界，不默认新增按机构或品牌划分的发行渠道。

## 四、已确认边界与待明确事项

1. **应用身份已确认**：沿用原应用标识、安装与升级身份；默认数据目录可独立定制。
   不同品牌包仍是同一应用，遵守原有版本比较和安装规则；不承诺相同版本一定能够覆盖安装。
   不新增品牌隔离或独立 Runtime 实例机制。
2. **首次交付与数据边界已确认**：全新环境按定制默认目录初始化，暂不实现旧数据迁移。
   如将原默认目录改为新目录，新目录不会自动获得旧目录的会话和配置；不增加旧目录自动探测、
   回退读取、复制或合并机制，不删除旧数据。不同目录不代表支持两个品牌应用并行运行。
3. **内部关键词边界**：默认数据目录属于本次明确可定制项；Rust crate／npm 包名、
   环境变量名、内部可执行文件名、应用标识及协议产品标识暂保持，避免把品牌定制扩展为全仓重命名。
4. **首批平台与素材**：macOS／Windows 的实际交付范围，以及接受的 Logo 输入格式；
   平台专用图标与托盘素材能否作为可选覆盖项，在正式方案中确定。
5. **更新与版本归属**：目标版本已确认为 v0.32.2。沿用原应用升级机制，不因显示名称变化改写现有清单中的
   `ez-assistant` 产品身份。升级后展示取决于新包中的品牌资源；需要持续保留定制品牌时，
   后续升级包也必须使用对应品牌构建。现有分发入口如何提供对应升级包仍待正式设计明确，
   不据此新增按品牌划分的发布渠道，也不承诺安装默认品牌更新包后仍保留定制品牌。

## 五、正式设计应覆盖的验收点

- 应用名称、安装包品牌名称及用户可见品牌文案一致，系统图标与应用内 Logo 使用定制素材。
- 全新环境按定制默认目录初始化，Desktop 与随包 Host 对同一 Runtime Home 完成启动、发现和访问。
- 既有显式路径覆盖继续生效；目录名不从显示名称自动推导。
- 旧默认目录存在时，不迁移、合并、清理其数据，也不静默回退到旧目录。
- 两组品牌连续构建及恢复默认构建时，名称、素材、前端资源与默认目录均无串用。
- 无效输入在耗时构建前失败；平台安装展示与应用内展示一致。
- 同一应用身份下的安装／升级遵循现有规则；使用相同交付配置升级后，品牌与默认目录保持稳定。

验收点在正式方案中细化验证入口，当前仅整理需求，不代表已执行构建、安装或数据操作。
