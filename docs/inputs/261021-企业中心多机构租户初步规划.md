## 一、当前实现与改造原因

以下为当前工作树的源码事实，未据此认定线上数据库状态。

| 当前事实 | 多机构下需要改变的边界 | 实现依据 |
| --- | --- | --- |
| 用户名全中心唯一，账号只有 admin/user 角色和超级管理员标记 | 账号须有机构归属，管理员权限须限定管理范围 | `src/users/entity.ts`、`src/users/repository.ts` |
| Token 只绑定 userId，LLM key 关联该 Token | 认证结果须提供可信机构上下文，不能信任客户端自报机构 | `src/identity/service.ts` |
| 服务商、固定参数没有机构归属，默认模型为 singleton；现有企业契约只下发单默认模型 | 每个机构维护可用模型、默认模型及自主选择策略；企业用户可另配个人模型 | `src/models/entity.ts`、`src/models/repository.ts`、`apps/runtime-host/src/resources/model/managed.rs` |
| 调用录制策略为 singleton，调用索引与正文通过既有服务读取 | 策略、记录、正文读取和清理都须按机构约束 | `src/llm/entity.ts` |
| Agent、插件及包按名称等全中心标识维护 | 机构之间可以维护同名资源，引用和下载不能串机构 | `src/agents/entity.ts`、`src/plugins/entity.ts` |
| 设备登记和用户授权没有机构字段 | 登记、审批、分配和桥接须核对同一机构 | `src/host-devices/entity.ts` |
| Host 用户域以 center_id + user_id 区分 | 租户身份须进入访问校验；保留原 ID 时不必机械迁移本地目录 | `apps/runtime-host/src/access/enterprise/mod.rs` |

表中 `src/` 路径相对 `apps/enterprise-center/`。中心已经有认证、事务、审计、配置分发和文件读取机制，
改造应沿这些机制补全机构归属，避免另建租户服务进程、第二套登录体系或配置分发链路。
机构有独立身份、配置所有权和启停生命周期，现有用户角色与中心身份不能直接代替机构实体。

## 二、建议的首版产品规则

1. **机构是业务隔离边界**：有稳定 ID、唯一机构编码、名称和启停状态；编码用于登录定位，名称用于展示。
2. **一个账号归属一个机构**：保留全中心不可复用的用户 ID，用户名改为机构内唯一。
   同一个人确需使用两个机构时，首版使用两个独立账号；不立即增加全局账号和成员关系表。
3. **登录明确机构**：普通用户使用机构编码、用户名和密码；管理员可提供带机构编码的登录入口，减少手工输入。
   服务端校验机构与账号后绑定 Token，LLM key 沿用同一归属；修改请求参数不能切换 Token 的机构。
4. **区分平台管理与机构管理**：平台管理员创建、启停机构并初始化机构管理员；机构管理员只管理本机构的插件、智能体和模型。
   用户与机构归属、设备审批和授权等管理入口暂由平台集中维护，不因机构隔离而自动授予机构管理员。
   现有 `is_super_admin` 的全中心权限须在正式设计中明确转换方式，不能直接当作每个机构的管理员绕过条件。
   平台管理员访问机构数据须显式进入目标机构并记录操作人、目标机构及动作，默认不把业务正文作为平台首页数据。
5. **机构独立配置**：新机构初始无模型、无业务资源，由机构管理员配置；配置不完整时明确提示。
   不自动继承其他机构的 Provider 密钥、默认模型、Agent 或私有插件。
6. **机构停用立即限制访问**：拒绝登录、代理和设备访问，撤销该机构凭据并按既有 owner 机制结束受控连接；
   已发送的上游请求不能承诺没有费用。本地历史与文件保留，不因中心停用机构而删除。
7. **安装包平台统一管理**：Desktop/Client 的安装包、版本说明、发布、撤回和兼容要求由平台维护；
   各机构共用产品发行体系，客户端仍按平台、架构和兼容要求选择更新。
   机构管理员不上传、发布或撤回客户端安装包，也不提供机构侧在线生成或配置品牌安装包的入口。
   同版纳入的打包交付定制由构建流程承载，不默认增加按机构或品牌划分的独立版本渠道。
8. **机构模型按策略选择**：机构管理员配置可用模型集合、其中的默认模型，以及是否开放用户自主选择。
   开放时用户可以在本机构可用范围内按会话选择；关闭时机构模型仅使用机构默认模型。
   中心保存的完整目录不等于普通用户可用范围，代理须校验实际机构策略。
9. **企业用户可配置个人模型**：在当前 Runtime 的登录用户域内维护个人服务商、密钥与模型配置，
   复用现有个人模型管理能力；个人配置只对本人可用，不写入机构共享配置、不上传中心真实密钥。
   模型列表以“机构模型”和“个人模型”分组，并显示所属服务商；模型来源随会话选择保存。

### 机构模型与个人模型的配合规则

- 用户自主选择开关控制机构模型范围内的选择，不额外增加禁止个人模型的开关；关闭机构自主选择后，
  机构来源仅提供默认模型，用户仍可配置和选择个人来源。若后续需要企业统一禁用个人来源，另行确认产品规则。
- 无显式会话选择时跟随机构默认模型；显式选择属于当前会话，不改写机构默认值或其他会话。
  沿用既有活动 Run 与排队期间的模型切换限制，不在一次执行中动态换模型。
- 机构模型经中心代理调用，中心只下发允许使用的模型及有效参数，真实 Provider 密钥留在中心。
  个人模型由当前 Host 使用用户自己的配置连接服务商，既有企业登录和用户域授权仍有效；个人来源不赋予机构资源权限。
- 个人模型请求通常不经过中心，因此不能将中心调用记录、用量或快照宣称为包含全部个人调用。
  个人密钥由实际承载该用户域的 Host 保管，不落前端存储，也不自动跨设备同步或导入其他账号的数据。
- 机构与个人来源即使服务商、模型名称相同也不得混用；配置同步只更新机构来源，不能覆盖个人配置或会话显式选择。
  切换来源时不能复用另一服务商或主体的续接状态。
- 已选模型被移出可用范围、机构关闭自主选择，或个人配置删除时，须在执行前重验并明确提示；
  不静默切换到另一来源、其他模型或付费凭据。具体在途请求、排队和旧会话处理在正式方案中确定。

### 管理权限范围

| 管理范围 | 平台管理员 | 机构管理员 |
| --- | --- | --- |
| 机构、用户归属及机构管理员配置 | 集中管理 | 首版不开放 |
| 客户端安装包、版本发布、官网及公共配置 | 统一管理 | 首版不开放 |
| 本机构插件、智能体、服务商、可用模型、默认模型及自主选择策略 | 在显式机构上下文中管理 | 管理本机构 |
| 设备审批与用户授权 | 按机构维护，禁止跨机构授权 | 首版不开放 |
| 调用录制策略、调用记录与正文、管理审计及反馈处理 | 保留平台管理入口，敏感内容读取范围待正式设计明确 | 首版不开放 |

个人查看身份、改密、反馈提交和已授权设备使用继续沿既有普通用户能力处理，
并新增本人的个人模型配置入口；个人模型属于普通用户配置能力，不授予机构管理权限。
机构数据仍须隔离，管理入口归平台不等于数据可跨机构混用。

首版不开放机构自助注册、机构删除、账号跨机构转移、跨机构设备共享、部门层级、计费套餐、SSO 或细粒度权限矩阵。
这些能力各有独立规则，不作为解决配置共用问题的前置建设。

## 三、数据和配置归属

| 范围 | 建议归属与行为 |
| --- | --- |
| 用户、机构管理员 | 账号有机构归属，由平台维护；最后启用管理员保护按机构计算；机构管理员仅有三类配置管理权限 |
| 机构 Provider、密钥、目录、固定参数、可用模型、默认模型和自主选择策略 | 机构所有；配置下发及代理按可信机构、可用范围与选择策略校验 |
| 企业用户的个人 Provider、密钥、目录与固定参数 | 当前 Host 的登录用户域所有，不属于机构共享配置；同 Host 不同账号与不同设备之间不自动共享 |
| 会话模型选择 | Runtime 会话所有，记录机构／个人来源与实际服务商、模型引用；未显式选择时跟随机构默认模型 |
| Agent、私有插件、插件发布和包下载 | 机构所有；名称唯一约束和引用解析限定机构；首版不引入平台共享插件市场或共享覆盖层 |
| 调用录制策略、调用索引、用量、正文快照 | 按机构保存和授权，管理入口留在平台；详情、统计、文件读取、保留期与清理均跟随机构；全局资源限额由平台约束 |
| 管理审计、反馈 | 记录明确机构，管理入口留在平台；删除用户后仍保留历史机构归属，不靠当前用户关联推导历史权限 |
| 设备、用户授权、在线通知、HTTP/SSE/WS 桥接和桌面信令 | 归属机构，平台按机构审批和分配；申请、连接与访问两端都须同机构，管理员身份不隐含设备使用权 |
| 中心稳定身份、软件协议、公开地址、官网、公开安装包 | 平台统一维护和分发，各机构共用；一个 center_id 继续代表同一个中心，不按机构复制中心身份或安装包发布记录 |
| 模型能力模板、进程资源上限、数据库及存储根目录 | 平台级基础设施；机构不能修改全局模板文件或任意指定服务器存储路径 |
| Session、Run、用户文件和本地记忆 | 继续由目标 Runtime 用户域持有，不迁入企业中心 |

`model_settings` 当前混合默认模型与公开代理地址，改造时须拆清归属：默认模型按机构，
公共访问地址保持平台配置。不能把现有 singleton 表机械复制后就允许机构改变中心地址。

建议首版继续复用一个 PostgreSQL、`public` schema、单实例中心和显式 SQL 迁移。
业务对象通过机构归属与受约束引用实现逻辑隔离，不为每个机构复制部署、数据库或整套表结构。
这是共享基础设施下的逻辑隔离，不承诺独立数据库或故障域；有物理隔离要求时再独立评估部署方式。

具体字段、组合唯一约束、外键和索引在技术方案确定。可以从父资源可靠推导归属的子表，
先评估复用关系；只有隔离约束或实际查询确需时才冗余机构字段。
历史调用、反馈和审计则必须能独立保留机构事实，不能依赖可能被删除的用户或 Provider。

## 四、贯穿所有入口的隔离要求

- **鉴权与查询**：在现有认证入口解析机构，业务查询、详情 ID、写入、关联资源和分页统计都核对机构；
  不把前端隐藏菜单、URL 前缀或单个列表的过滤条件当作完整隔离。平台跨机构操作采用明确的管理入口。
- **配置与代理**：可用模型、默认模型与选择策略读取、发送前重验、配置绑定和 Responses 续接链包含可信机构作用域；
  中心不能继续以“请求必须等于默认模型”代替可用范围校验。配置失效只影响相应机构，
  不能按同名模型误伤其他机构或个人配置，也不能复用其他来源的连接与续接状态。
- **文件与后台任务**：插件包和快照必须先验证资源归属再取文件；
  缓存、下载 owner、订阅、异步回调和清理任务同样有明确机构范围。
  内容寻址文件是否共享物理字节可复用既有实现，但不能因此共享下载权限或误删仍被引用的文件。
- **界面切换**：后台持续展示当前机构；平台管理员切换机构时卸载页面、关闭草稿并拒绝旧响应覆盖新机构。
  已经发出的写入始终绑定原机构，取消等待不代表回滚，不自动重发。
- **Host 接入**：首版建议一个 Host 的设备登记归属一个机构，跨机构并用同一 Host 后置。
  更换机构须显式解除旧登记和授权、结束受控连接，再建立新归属；不按新登录用户静默重绑设备。
  Host 仍按既有用户域隔离历史；是否需要扩展本地身份键及路径，由全中心用户 ID 不变这一事实决定。
- **兼容**：中心、后台、Host、Desktop/Web 的登录与身份契约需配套更新，并评估 Client 入口。
  建议通过现有企业协议门禁明确拒绝不支持机构的旧客户端，不提供静默落入默认机构的长期回退。
  具体协议下限、升级顺序和旧版处理方式进入正式方案后确认。

## 五、候选实施顺序

以下为 v0.32.2 的初步实施顺序，不是已批准的开发计划；正式设计时再确定 Feature 划分和里程碑。

| 步骤 | 主要工作 | 形成的可验收结果 |
| --- | --- | --- |
| 1 方向与契约设计 | 确定账号归属、平台权限、资源矩阵、设备规则和兼容方式；核对实际接口读写链路 | 多机构总体方向、迁移归属和最终验收边界清楚 |
| 2 机构与身份边界 | 机构管理、机构登录、可信 Token 作用域、机构管理员保护及后台机构上下文 | 两个机构的同名账号可以独立登录，管理权限互不越界 |
| 3 业务资源完整隔离 | 可用模型、默认模型与自主选择策略、配置下发与代理、Agent/插件、调用/快照/用量、反馈/审计及清理任务 | 机构配置互不影响，用户只能调用策略允许的机构模型 |
| 4 客户端与设备闭环 | Host 身份、双来源模型装配、个人模型配置、按会话选择与来源分组、配置同步、设备授权及桥接 | 用户能按规则使用机构／个人模型，凭据与历史不混用，设备撤权有效 |
| 5 迁移与整体验收 | 隔离库演练、旧数据默认机构归属、配套升级与恢复演练 | 历史可读、引用完整，旧客户端不会绕过机构边界 |

第 2—4 步为依赖顺序，不代表可以在尚有全中心业务入口时对外开放多机构。
公开启用前必须完成全部现有业务入口的租户审查，以及跨机构的整体验收。
每个正式里程碑仍按仓库流程完成后汇报并等待用户确认。

## 六、现有数据迁移方向

建议先建立一个默认机构，将现有用户、配置、设备、调用、反馈和资源整体归入该机构，
不自动按用户名、角色或历史调用猜测并拆分机构。保留 `center_id`、用户 ID、资源 ID 及现有文件引用，
尽量维持 Host 本地历史路径。现有超级管理员的转换及默认机构首位管理员须明确指定，
不能把平台与机构权限静默混为一体。

这里的旧数据归入默认机构与同版打包定制中的“默认数据目录改名”是两项不同范围：
前者仍须设计和演练企业中心历史数据迁移；后者主要面向首次交付，暂不迁移旧 Runtime Home。

先在项目 `.runtime-test/` 新建的一次性场景演练。正式迁移前须核实真实主机、端口、数据库、
实际读取表、文件存储及影响范围，取得用户明确确认，停写并结束在途传输，建立独立备份且验证可读取、
关键表精确数量及恢复可行性。现有自动升级开关不能替代生产迁移确认。

迁移尽量以事务完成；涉及数据库外文件或不可回滚步骤时，执行前说明恢复办法。
回退须使用匹配的程序、数据库备份和文件状态，不能让旧程序忽略机构字段后继续读取新库。
完成后按表核对归属、数量、关键引用，并通过实际登录、配置、代理、文件读取和设备接口确认结果。

## 七、正式验收重点

1. 两个机构使用同名账号、Agent、插件及相同模型 ID，数据、配置和引用均互不串用。
2. 使用机构 A 凭据携带机构 B 的资源 ID、下载定位、调用 ID 或设备 ID，读取和写入均被拒绝；
   列表总数、统计与错误返回也不泄露另一机构的数据。
3. 修改 A 的默认模型、密钥、配置或录制策略，B 的新请求、在途请求和续接链不被误改或撤销。
4. 停用机构、账号或撤销设备授权后，相关凭据、等待准入、长连接和迟到响应不能恢复访问。
5. 清理 A 的过期记录和文件不影响 B；删除账号后历史仍归属于正确机构。
6. 迁移后默认机构保留原历史与资源，其他新机构初始为空；不兼容的旧客户端得到明确升级提示。
7. 机构管理员只能管理本机构的插件、智能体和模型；直接调用安装包发布、用户管理、设备管理等接口仍被拒绝。
   各机构从同一平台发行体系发现和下载符合兼容要求的客户端版本。
8. 机构默认模型属于可用集合；开放自主选择时不同会话可使用不同机构模型，关闭时仅提供机构默认模型。
   伪造未授权模型请求被中心拒绝，旧配置不能绕过新策略。
9. 企业用户能维护和使用个人模型，列表按机构／个人分组，同名模型与密钥不混用；
   机构配置刷新不覆盖个人配置，其他用户无法读取个人密钥，个人请求不被误记为中心代理调用。
10. 会话保存实际模型来源；重新打开和切换来源后仍能正确解析，执行与排队期间沿用冻结约束，
    配置撤销、删除或策略变化时明确报告，不跨来源静默回退，也不复用旧来源续接状态。

## 八、进入正式设计前需要确定的选择

- **账号模型**：是否接受首版账号只归属一个机构；若要求同一账号加入多个机构，需改为全局身份与成员关系，
  并重新设计机构切换、角色、Token 和本地数据域，不能只加一个用户机构字段。
- **资源共享**：首版是否接受各机构独立维护 Provider 与私有插件；若要平台提供公共模型或插件，
  须另定授权、分发及覆盖规则，不能默认共享现有密钥。
- **平台权限细节**：机构管理员范围已收敛为插件、智能体和模型；继续明确平台查看业务正文的范围与审计要求。
- **交付安排**：目标版本已确定为 v0.32.2；继续明确机构编码入口及配套升级窗口，再形成正式设计和开发计划。

机构多模型与个人模型的产品范围已由用户确认；双来源装配、会话引用、策略变更与旧数据处理等实现细节留待正式设计，
不将当前版本的单默认模型限制继续作为 v0.32.2 的目标边界。

本轮完成范围为源码边界核对与初步规划；未修改业务代码，未连接或操作数据库，未变更线上配置。
