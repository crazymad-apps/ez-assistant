# 模型列表拉取风暴、在线目录缓存与卡死会话（诊断记录）

- 记录日期：260912
- 状态：已在 `v0.26.0` 完成，2026-09-17 用户确认验收并归档。
- 来源：用户会话（2026-09-12 00:35 左右）
- 目标版本：`v0.26.0`；正式范围见 [归档功能设计](../versions/v0.26.0/功能设计.md)。

## 一、原始内容

> 为什么 kimi 的模型总是非常不稳定，经常拉不到模型列表，导致会话终端（中断），另外你也看下为什么
> 平台老是跑获取不到模型列表的问题，到底是哪里在频繁触发计划外的拉取动作。
>
> 考虑一下是否增加模型列表缓存机制，避免高频触发这个刷新动作，建议直接把显示刷新放到模型管理页面，
> 模型选择默认使用缓存。
>
> 而且还有一个 bug，像最新的那个 kimi 模型的会话就卡住了，删也删不掉，顺便还把页面初始化也卡慢了
> （不知道是 runtime 阻塞了还是怎么回事）。

用户后续补充的口径（2026-09-12）：

> 如果获取列表失败，则继续使用缓存；不需要 TTL，只要不触发刷新，就一直用缓存；
> 出现模型不可用的情况，让用户自己来手动处理。

> 这里需要做个决策：缓存是否需要存文件或落库，不然 runtime 重启就失效了；另外还要决策，
> 如果不存在缓存的情况下，模型选择器是否自动执行刷新动作。

> 尽量降低系统复杂度。

## 三、诊断结论

四个独立成因叠加，才形成用户观察到的全部症状：

| 编号 | 成因 | 直接症状 |
| --- | --- | --- |
| C1 | 在线目录没有缓存／去重／合并，且被挂在**非用户动作**的高频路径上 | 计划外拉取次数极多 |
| C2 | 目录发现沿用模型推理的 300s 预算 | 单次挂起让会话视图／Run 装配最长卡 5 分钟 |
| C3 | Run 在“准备模型”阶段失败时，已接纳的 Input 永久留在 `queued` | 会话永久不空闲 → 删／归档／清空／换模型全部被拒 |
| C4 | 中断 Run 的恢复只挂在 `SessionLoader::prepare`，`load` 路径不恢复 | 进程被杀留下的 Run 永远“运行中”，会话删不掉 |

供应商侧（kimi `/models` 约 1/9 概率无响应挂死）是**外部事实，不能修**，但正因为它不可控，
更不能被放在会话视图、Run 装配这类关键路径上。

一句话链条：

```text
用户展开/发送/切换会话
→ prepare_model 无固定记录 → 每次新建 client 同步 GET /models
→ 供应商约 1/9 概率挂死，而预算 300s
→ 会话视图与 Run 装配被拖着走（页面卡、会话中断）
→ 准备失败的 Run 不把 Input 置 committed（且 load 路径不恢复中断 Run）
→ 会话永久非空闲 → 删不掉
```

## 四、证据

### 4.1 在线目录没有任何缓存、去重或合并

- `crates/assistant-runtime/src/config/managed_model.rs::prepare_model`：只有
  `store.get_model_fixed_config` 命中时才完全不联网；**无固定记录时一律先联网**
  `discover_models`，仅仅为了拿 metadata 去补模板参数。
- `crates/assistant-runtime/src/runtime/model_management.rs::discover_provider`：每次调用都
  新建 reqwest Client，直接 `GET <endpoint>/models`；模块注释与
  `docs/modules/assistant-runtime.md` 明确写有“不缓存在线目录／无目录缓存”，
  说明这是**已确认的设计选择**，不是实现疏漏。

### 4.2 联网点被挂在会话与 Run 的高频路径上

`prepare_model` 的实际调用方（共用同一份“无固定记录就联网”逻辑）：

| 调用方 | 触发时机 | 是否用户显式动作 |
| --- | --- | --- |
| `runtime/product.rs::composer_capabilities`（经 `get_session_view`） | 每次打开／切换会话视图；Desktop 在 `run_started`、`run_finished`、`conversation_committed`、`session_changed`、`config_changed` 等事件后 80ms 防抖刷新 | 否 |
| `runtime/model.rs::compile_run_agent` | 每一条用户消息的 Run 装配 | 否 |
| `runtime/materialization.rs::materialize_session` | 草稿首次发送 | 否 |
| `runtime.rs::create_session`、`runtime/session_management.rs::set_session_model` | 新建会话带模型选择、会话内换模型 | 半显式 |
| `runtime/model_management.rs::save_model_selection` | 保存默认模型／辅助识图模型 | 是 |
| `runtime/connection_validation.rs` | 连接验证 | 是 |

另外 `get_model_configuration` 在无固定记录且 `origin=online` 时同样联网，被
`apps/desktop/src/features/composer/ComposerDock/useDraftModelEfforts.ts`（打开 Composer
模型设置菜单）与固定参数页调用。只有 `list_provider_models`（模型选择器展开服务商、
模型管理页）属于用户预期的“计划内”拉取。

现成可复用但未被使用的同义能力：
- `config/domain.rs::configured_model`：只读固定配置、不联网。
- 会话自身已接纳的 `model_binding`：`runtime/model.rs::resolve_session_model` 已经用它服务
  标题、手动压缩等路径，**唯独会话视图没用**。

### 4.3 供应商 `/models` 确有偶发挂死

同一个 key 连续 `GET https://api.kimi.com/coding/v1/models`：

- 正常：200，约 0.18–0.24s，1582B，返回 4 个模型（`kimi-for-coding`、
  `kimi-for-coding-highspeed`、`k3`、`k3-256k`）。
- 抽样 18 次中 **2 次无任何响应**，直到被 10s 超时中断（另有 1 次 1.2s）；约 **1/9** 概率挂住。
- 同 key 同路径其余请求全部 200，排除鉴权与路径问题。

### 4.4 “拉不到模型列表导致会话中断”的直接证据

`~/.ez-assistant/data/runtime.sqlite3`，会话 `s_DPVlBo7K12vT`（标题即本次提问，
model `k3-256k`，`message_count = 0`）：

```text
run_id        = r_L6Y9py2kCrIf
status        = failed
error_code    = invalid_request
error_message = 获取在线模型列表失败，请重试或编辑已有固定配置。
```

该文案来自 `config/managed_model.rs` 的 `prepare_model` 取目录失败分支，即用户观感中的
“会话起了个头就中断”。

### 4.5 会话删不掉：两处独立成因

**(a) 启动前失败的 Run 把已接纳的 Input 永久留在 `queued`。**
`runtime/input/mod.rs::fail_before_start` 结算 Run 为 Failed 时只把 Input 从内存队列弹出，
**没有把 `input.state` 置为 `committed`**（正常路径在 `commit_user_message` 之后同事务置位）。
而 `session.rs::ensure_idle` 把“存在 `queued` Input”判定为不空闲，于是
`delete_session`、`clear_session`、`archive_session`、`set_session_model` 等全部以
`SessionNotIdle` 拒绝。

本机现存 5 条残留 Input，分布在 4 个会话：

```text
i_qe5ZvaG8GFoh / i_vyzNNt7xBlGc → s_zJ42eELaH54Y（k3-256k）
i_qdA8sFTKkLRI                    → s_4zcXAPxjBLrd（k3-256k）
i_l1BN0UYIeNtr                    → s_cg03SyZNdVom（gpt-5.6-sol）
i_1yiK-eeXKJMF                    → s_DPVlBo7K12vT（k3-256k）
```

**(b) 中断 Run 的恢复只在 `SessionLoader::prepare` 里执行。**
`runtime/session_loading.rs` 中，恢复（`recovery::prepare_interrupted_run_settlements`）只挂在
`prepare()`；`load()` 只加载不恢复，而 `AssistantRuntime::session()` 走的正是 `load()`。
`get_session_view`、`delete_session`、`archive_session`、`rename_session` 都走 `session()`，
只有发消息与队列命令走 `prepare()`。进程被杀留下的 `status=running` Run 因此一直显示
“运行中”且无法删除。本机现存 1 条：

```text
r_2bmrgQYi5kbB  session_id=s_R2SW0iG1JiSx  status=running
started_at_ms=1788743660218（2026-09-07 09:14）
```

（当前会话 `s_w8ecYbal2dDe` 的 `r_n0wMBJ9R6ji8` 属于正在执行的 Run，不是残留。）

### 4.6 页面初始化变慢

`get_application_snapshot` 本身只读本地数据；但客户端连上后必然
`loadApplication → selectInitialSession → loadSession → get_session_view`。
本机 13 个带模型引用的会话中有 **7 个没有固定记录**（涵盖全部 `k3-256k` 与 `gpt-5.6-sol`
会话），因此这一步要等一次 `/models`，挂死时最长 5 分钟。所以用户看到的“初始化卡慢”
不是 Runtime 全局阻塞，而是初始化链上串了一次不可控的外网调用。

## 五、用户已确认的口径（2026-09-12）

1. **不做复杂缓存**：不设 TTL、不做定时或自动重新校验、不做后台预热。
   “只要不触发刷新，就一直用缓存”。
2. **刷新只由模型管理页显式触发**：模型选择器默认使用缓存，自身不触发任何拉取。
3. **拉取失败继续使用缓存**：刷新失败不破坏已有列表，保留上次结果。
4. **模型不可用由用户手动处理**：不自动回退、不自动清理、不自动重选；Runtime 只给出明确
   失败原因，由用户自行刷新列表或重新选择模型。

## 六、助手建议（已获用户口头认可，待纳入版本时正式确认）

### D1 目录快照持久化，加在 `providers` 表

- 结论：**落库**（Runtime 重启必须保留）。`providers` 增加两个可空字段
  `discovered_models_json`、`discovered_at_ms`；`NULL` 表示“从未刷新过”。
- 理由：快照生命周期与 provider 实例完全一致（删除 provider 必须一并消失），放在同一行可复用
  现有 `ON DELETE` 语义；内存侧直接复用现有聚合 `ManagedModels.providers`
  （`BTreeMap<ProviderInstanceId, Arc<StoredProvider>>`），会话视图、Run 装配、选择器**已经在读
  这份数据**，等于零新增读取路径、零新增失效机制（`ensure_provider_current` 的 Arc 身份校验
  天然覆盖“刷新后旧绑定失效”）。
- 改动面已核实：`StoredProvider` 只有 3 个字段、全仓 4 处构造点；SQL 为显式列名；
  迁移框架已有 `v0_25_2` 这类按版本追加的既有形态。
- 否决“新增快照表”：只换来 `providers` 表不掺派生数据，却多一张表、一次 join 和一套级联。
- 否决“Runtime Home 下的 JSON 文件”：SQLite 已是运行事实的唯一权威存储，再加一份文件会引入
  第二套原子写、损坏检测与启动恢复。
- 配套口径：
  - `discovered_models_json` 反序列化失败必须降级为“无快照”，**不得阻断 provider 加载**。
  - 连接（endpoint／方言）被修改时按用户规则**保留**快照、不自动拉取；管理页提示“连接已修改，
    建议刷新”，并始终展示快照获取时间供用户判断。
  - 新增可空列向后兼容，旧库升级后快照为空正好等于“从未刷新”的新语义，不回填、不写兼容分支。

### D2 无快照时模型选择器不自动刷新

- 结论：**不自动刷新**。该服务商下显示“尚未获取模型列表”并给出「去模型管理页刷新」入口；
  已保存的固定记录（纯本地 `list_fixed_model_configs`）照常列出并可选。
- 理由：选择器展开是高频且无意识的动作，若此时自动拉取等于给“刷新”开了第二个入口，
  C1/C2 会原样复现（实测约 1/9 概率挂死）。无快照不等于不可用——本地固定记录仍可选，
  这正是“模型选择默认使用缓存”的完整含义。
- 配套口径：无快照且无固定记录时的执行失败文案必须给出可执行的下一步
  （指路“设置 → 模型与服务商 → 刷新在线模型列表”），不能只报“获取模型列表失败”。

### S1 会话视图与 Run 装配彻底不再联网（治本项）

缓存只能解决“次数”，解决不了“关键路径串外网”，因此必须同时做：

- `composer_capabilities` 改为只读**会话已接纳的 `model_binding`**（`resolve_session_model`
  已有该逻辑），无绑定时退回 `configured_model`（只读固定配置），都不可用就返回 unavailable
  而不阻塞视图——**不联网**。
- `compile_run_agent` 不再隐式联网：“无固定记录才在线确认身份”只保留在**用户显式选择模型**
  的那一刻（选择、保存固定配置、管理页刷新），Run 装配只消费已确认结果。
- `get_model_configuration` 同理：只读固定记录／快照，不触发发现。

### S2 目录发现使用独立短超时

目录发现（15s 量级）与模型推理的 300s 预算解耦；失败快速返回并保留上次快照。
具体数值与配置项归技术方案。

### S3 两个“会话不可删除”缺陷的修复方向

- (a) `fail_before_start` 在结算后必须让该 Input 进入终态（置 `committed` 或引入明确的已终结
  语义），保证 `ensure_idle` 能收敛。
- (b) 把中断 Run 的恢复从 `prepare` 抽到共用装载路径，或让会话视图／删除／归档命令也走带恢复的
  装载路径。

### S4 前端配套

- `ModelPicker` 默认读“本地固定记录 + 目录快照”，不再一展开就联网。
- 模型管理页保留显式“刷新在线模型列表”，并展示快照获取时间与刷新失败提示
  （“刷新失败，仍在使用上次结果（获取于 …）”）。
- `config_changed`／`run_*` 等事件刷新不再连带触发模型目录读取（S1 落地后自然成立）。
- `SessionManagementController` 对 `pending_session_action` 期间的静默拒绝给出明确反馈，
  避免用户观感为“点了没反应”。

### S5 现阶段的权宜处置（不涉及代码）

Runtime 正在运行，**不能在运行期直接改库**（内存状态会与库不一致）。可用的临时手段：

- **4.5(b) 的会话**：在该会话里发一条消息或点“重试”会走 `prepare()`，即可恢复并把中断 Run
  结算为 interrupted，之后可正常删除。
- **4.5(a) 的 4 个会话**：`fail_before_start` 不置 `committed`，任何客户端动作都不会自动清掉，
  只能等 S3(a) 修复，或停掉 Runtime 后按根 `AGENTS.md` 第七节做受控数据收敛
  （独立备份 + 事务 + 逐表核验，5 条 `inputs` 置为 `committed`）。

### 取舍自检（按最小新增原则必答）

把本方案新增的机制全部删掉后，现有事实是否已经足够？

- 只做 S1 + S2 + S3：C1/C2 的**关键路径卡顿与会话中断**已消除，但每次“首次使用某个无固定记录
  的模型”仍需一次真实联网，且无快照时行为分散在各处——**不足以**满足用户“拉取失败继续用缓存、
  刷新只在管理页”的明确口径。
- 因此保留 D1（持久化快照，1 个迁移 + 2 个可空列 + 复用现有聚合）与 D2（选择器不自动刷新）。
  两者都不新增实体、表、DTO、缓存层或第二份权威状态，是达到该口径的最小机制集。
