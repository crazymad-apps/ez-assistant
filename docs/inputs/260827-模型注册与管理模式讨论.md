## 当前方向（2026-09-08 用户修订，优先于下方历史讨论）

- 采用多服务商模式，用户管理服务商连接，不再逐个注册模型。
- 各服务商的模型列表直接通过在线接口获取，不再与本地逐模型注册清单取交集。
- 模型选择保留所属服务商实例；不同服务商下的同名模型仍彼此独立。
- 同一服务商的协议方言统一配置，其下所有模型共用，不给每个模型重复配置方言或维护独立的
  适配方案。模型自身能力元数据与服务商方言分开；具体协议选择规则继续在服务商层讨论。
- 用户在模型选择配置中只设置一个默认模型，从多个服务商提供的模型中选择。
  默认选择需要同时明确服务商实例和该服务商的模型 ID，避免仅凭同名模型产生歧义。
- 默认模型保存在数据库中，不写入 `config.toml`；选择默认模型不把整个应用绑定为单服务商模式。
- 服务商连接配置也保存在数据库中，由设置页统一管理。
- 在线模型列表仅使用本次获取结果，获取失败就显示失败，不保留或回退上次结果，也不将列表
  写入数据库。已保存的默认／会话选择是用户配置，与在线列表分开，不因获取失败而删除。
- 模型能力、上下文窗口和输出上限等参数从服务商接口获取；服务商返回的特殊字段在测试联调时
  核查并由服务商适配处理；后续真实测试发现参数不全，用户已改为允许编辑并固定运行参数。
- 辅助识图能力保留，旧辅助识图选择直接废弃，不做历史配置转换，用户从在线列表手动重新选择。
- 原先“模板复制出逐模型用户配置，再取在线交集”的流程不再作为当前方案。
  不再以静态目录自动补齐参数作为默认方案，不再沿用逐模型方言配置。
- 服务商不返回必要参数、接口协议选择和默认模型失效时的具体执行反馈留到设计／联调核查；
  参数来源现已修订为在线预填＋用户固定，不能假定所有服务商接口都提供相同字段。旧配置与旧会话选择
  的废弃规则、数据库初始版本已按下文明确，本轮不执行数据库操作。

### 真实接口测试后的追加修订（2026-09-08，当前优先）

- 用户明确要求查阅厂商文档，并允许编辑在线模型列表中的上下文及相关设置，固定保存到数据库。
- 设置采用三级页面：模型与服务商 → 服务商详情／在线列表 → 模型配置；快速选择仍为服务商 → 模型。
- 固定配置按服务商实例和 model_id 保存，显式保存整份标准化参数；刷新不覆盖。重置就是物理删除
  固定记录，不清模型选择或历史。来源优先固定记录，否则在线获取；未知值不伪造。
- 新建固定记录从在线模型进入，已有记录可独立管理，不建立任意 ID 注册入口或失败目录缓存。
  方言仍归服务商，旧 TOML 配置仍废弃，不自动转换为新固定配置。
- 已同步功能／技术／交互／开发计划；[厂商参数核查](../resources/v0.25.1-服务商参数文档核查.md)
  区分文档最大值、接口默认值、套餐范围和用户运行限制。本轮为方案修订，未执行数据库操作。

### 核查事项的用户结论

1. **服务商连接保存位置。** 用户确认存数据库，统一由设置页管理；凭据保护方式归技术方案。
2. **在线模型如何获得可运行参数。** 当前
   [当前模型编译器](../../crates/assistant-runtime/src/config/managed_model.rs)仍要求上下文窗口和输出上限；
   用户确认方言归服务商、模型参数由元数据提供，并进一步指定元数据从服务商接口获取。
   测试阶段核对是否需要处理特殊字段；缺字段时如无法满足现有执行要求，报告实测缺口，
   不伪造参数或自行恢复静态目录／手工注册方案。服务商协议选择与非对话模型的展示规则由设计明确。
3. **在线目录获取失败。** 用户否定保留上次结果的建议：失败直接显示失败，旧结果不保留、不回退，
   在线列表不入库。当前成功结果仅作为本次获取与展示的数据，刷新、失败和切换服务商不能继续
   展示上次结果充当当前成功。获取失败不代表删除数据库中的服务商或用户选择。
4. **辅助识图模型。** 保留识图能力及从统一在线列表选择的入口；旧辅助识图配置直接废弃，
   不做兼容转换，用户手动重选，不自动继承旧选择或套用普通默认模型。

添加／修改服务商后的获取时机、删除服务商与默认失效的反馈可在功能设计中形成具体规则，
不再把已确认的存储、失败处理与参数来源列为待定。

## 兼容与增量演进（2026-09-08）

用户最终明确：**废弃字段不再保留在系统中；旧会话的原模型配置直接废弃，允许用户重新选择
或使用默认模型；旧配置不能导致软件异常退出或崩溃。** 新字段仍尽量增量加入，但这不表示
保留旧列、旧 DTO 或旧配置分支。以下作为正式技术方案的约束，不代表已执行数据迁移。

### 已核查的源码事实

- [配置输入](../../crates/assistant-runtime/src/config/schema.rs)中 `default_model` 是必填字符串，
  `models` 是按旧 key 组织的配置；顶层启用 `deny_unknown_fields`。因此停用旧配置需要同时处理
  缺失、旧字段残留和版本解释，不能只删除字段定义导致原配置整体解析失败。
- 原 TOML 配置编辑器（v0.25.1 已删除）当前将默认模型、模型 CRUD 和
  辅助识图模型写回 TOML；新管理入口必须退出这条旧写入路径。
- [数据库 schema](../../apps/runtime-host/src/storage/schema.rs)中 `sessions.model_key` 为
  `TEXT NOT NULL`，会话创建、物化、Fork、切换和查询使用该字段；
  [历史加载](../../apps/runtime-host/src/storage/engine.rs)与
  [列表加载](../../apps/runtime-host/src/storage/session_loading.rs)都会解析为旧 `ModelKey`。
- [应用命令](../../crates/assistant-protocol/src/command.rs)、快照和配置投影均引用旧 `ModelKey`；
  需要一并核查 Desktop/Web、子 Agent、代理会话、恢复、默认识图与诊断消费方。

本次只读源码，未打开或查询用户数据库；以上是代码结构事实，不是对用户数据内容的验证。

### 当前演进原则

1. **新旧语义分开。** 新增明确表达服务商实例和模型 ID 的选择字段及数据库默认选择；
   不把旧 `model_key` 或旧 `provider` 字段原地改成另一种含义。已有表能承载的事实优先增列，
   只有独立服务商实体等明确需要独立所有权的内容才新增表；不重建逐模型注册表。
2. **彻底移除废弃字段。** 从当前数据库 schema、配置输出、领域类型、应用协议与 UI 中删除
   已废弃模型字段和对应读写路径，不保留旧列、旧值影子、字段别名或双写。旧格式只在升级入口
   做必要识别与清理，处理后统一进入新格式，不形成第二套运行时配置系统；独立备份不参与运行。
3. **废弃旧模型选择，不做映射迁移。** 不再根据旧模型配置还原服务商或转换旧会话引用。
   历史消息和会话本身保留，旧模型选择清除后允许用户手动重选或采用有效全局默认模型。
   建议选择顺序为“新格式的会话显式选择 → 有效全局默认 → 提示选择／配置模型”；
   不能因缺少模型阻止启动、设置页或历史消息查看，没有有效模型时只阻止需要模型的执行。
4. **清除旧约束及调用方依赖。** 删除 `sessions.model_key` 时同时调整 INSERT、SELECT、
   Fork、恢复和切换逻辑，不能留下 NOT NULL 依赖或伪造占位 key。能直接增删列则直接处理；
   如 schema 限制必须局部重建表，在方案中说明最小范围、完整性检查与恢复方式。
5. **兼容已发布数据，明确客户端边界。** 沿用 Host/Desktop 同版本交付约定，不自动增加旧客户端
   兼容层。新 JSON 字段的缺省值与可空语义需覆盖历史记录，不能让历史快照因缺新字段无法读取；
   新记录缺少有效选择也不能被静默当成可执行。更换模型后的历史投影复用正式切换边界，
   不把旧 Provider 私有状态发送给不匹配的新服务商／协议；不为此恢复旧模型配置。
6. **升级错误可处理。** 旧 TOML 残留、旧模型字段的非法值、缺新字段、没有默认模型和在线获取
   失败均不得传播成 panic、进程退出或空白界面。升级逻辑识别并移除已废弃字段，保留其他有效
   配置；无法安全解析或升级失败时给出可见诊断和修复入口，不盲目覆盖文件或继续有风险的写入。
   升级可重复执行，不能在第二次启动清除已经保存的新选择；配置清理与数据库变更需可中断恢复。
7. **验证后交付自动升级。** 最小验证覆盖旧版本升级、新安装、新会话创建、历史查看与继续、
   Fork／切换／重启、默认与辅助模型引用、重复升级、缺失和冲突、失败恢复。配置文件和数据库
   无法共享一个事务，方案必须说明执行顺序与中断恢复。实际数据库操作前按根 AGENTS.md
   核对目标、取得写入确认、创建并验证独立备份。用户随后明确要求正式产品启动时自动升级，
   该产品机制按下节设计，不在每次启动增加人工 SQL 确认；本轮仍不直接操作用户实际数据库。
   兼容验收重点是旧配置不致崩溃、历史消息仍可查看、重选或设默认后能继续使用，以及废弃字段
   确实已从新系统读写契约移除，不再要求保留旧模型选择。

## 按软件版本自动升级数据库（2026-09-08，本版新增范围）

用户要求本版本建立正式机制：数据库中新增表记录数据库版本，版本号与软件版本一致；
每次启动检查版本，未对齐时自动按顺序执行中间版本的数据库变更 SQL。

### 现状和职责

[StorageEngine 初始化](../../apps/runtime-host/src/storage/engine.rs)已经调用
[schema::initialize](../../apps/runtime-host/src/storage/schema.rs)，后者使用事务执行建表、
`ensure_column` 补列和部分数据处理，但没有按软件发布版本记录升级历史；它还混合了
Recall 重建中断恢复等每次启动都需要执行的动作。应在现有 Host 存储初始化入口中收敛，
不另建迁移服务或让 Desktop/Web 直接执行 SQL。

用户已明确自动升级目标，并确定 **v0.25.1 为首个数据库版本和固定迁移起点**；
具体表名与 SQL 文件路径仍在技术方案中确定，不再识别或补记 v0.25.1 以前的数据库版本。

### 版本与迁移记录

- 数据库版本以当前 Runtime Host 软件版本为目标，与 workspace 产品版本同源；远程 Desktop
  不能用自己的版本修改远端库。统一比较语义版本，不按字符串排序，也不新增独立数字 schema 版本体系。
- 建议一张迁移记录表（暂名 `schema_migrations`），每个完成版本记录 `version` 和 `applied_at`；
  当前版本由已提交记录中的最高语义版本得出，不额外保存第二份可变“当前版本”状态。
- 每个正式软件版本登记一个有序迁移入口，SQL 随产品发布；无数据库变更的版本登记空迁移，
  成功后照样写入版本记录，保证最终数据库版本与软件版本对齐。
- 已发布迁移不可原地修改，后续修正进入新版本。未发布版本的设计调整直接统一，不为中间状态
  维护长期兼容分支；开发验收使用隔离库，防止同版本号掩盖已经执行过的不同 SQL。
- 不扫描和执行用户目录中的任意 SQL；执行集必须来自当前软件携带的版本迁移清单。

### 启动执行路径

1. Host 取得对应 Runtime Home 的独占所有权，在会话加载、Run 恢复和业务命令开放前检查数据库。
2. 读取版本记录；空库、无版本表或没有已提交版本记录的库统一从 v0.25.1 SQL 开始执行。
   有有效记录则从下一版本继续；记录损坏或自相矛盾按错误处理，不能当成无版本库重新初始化。
3. 版本相同则不重复执行迁移；数据库较旧则先校验完整升级链，再备份并实际验证备份可读、
   关键表数量有效，然后按版本顺序执行全部待执行步骤。缺少迁移链不能直接跳到目标版本。
4. 每个版本的 SQL、必要数据调整、结构／关键数据验证和成功版本记录放在同一事务中提交。
   SQL 失败或验证不符时回滚当前版本，立即停止后续步骤；成功标记绝不能提前写入。
5. 所有版本对齐且最终结构核验通过后，再进行每次启动的恢复操作并开放正常业务。
   不把 Recall 中断恢复等日常操作放进只执行一次的版本迁移。

示例：数据库没有版本记录、软件 `v0.25.3`，依次执行 `v0.25.1 → v0.25.2 → v0.25.3`；
数据库已记为 `v0.25.1` 时，只执行 `v0.25.2 → v0.25.3`。
若 `v0.25.2` 失败，库保留在已提交的 `v0.25.1`；本次不继续执行，恢复后从首个未完成版本开始。
每版本事务不等于整个升级链可一次回退；回退旧软件需恢复升级前经验证的独立备份，不执行猜测的逆向 SQL。

### 首次接入与失败边界

- 新安装和所有无版本记录的旧库统一执行 v0.25.1 初始化／迁移入口，不推断旧软件版本，
  不补录历史版本，也不直接标记成功。该入口需兼容空库和已有表，保留会话正文等有效数据，
  完成当前结构初始化与废弃模型字段清理后，才在同一事务中登记 v0.25.1。
- v0.25.1 入口内部允许为安全执行 SQL 检查表／列是否存在，但这些检查不用于猜历史版本或
  选择多个历史迁移起点；无版本旧库不等于可清空重建的空库。执行或验证失败按统一失败流程处理。
- 后续软件启动无版本库也始终从固定 v0.25.1 起点执行，再依次升级到软件版本，不能把
  “当前版本”解释为每次安装时直接从最新版本的 SQL 开始。
- 用户已确认：数据库版本高于软件版本时，不自动降级，不允许旧程序按旧结构继续读写；进入可见的版本不匹配
  状态，引导使用匹配或更新的软件，不能表现为崩溃或无限重启。
- SQL 失败、磁盘满、备份失败、结构异常、缺迁移入口和版本记录异常时，都停止正常数据库业务，
  Desktop/Web 启动界面仍需给出失败步骤与可执行的恢复提示。诊断通道与业务就绪分开，
  具体接入方式由技术方案基于现有启动流程确定，不承诺在不兼容 schema 上继续读取历史。
- 表结构变更与版本记账自动完成；备份核验或迁移失败不得自动扩大范围、自行删除数据或循环补救。
- SQL 迁移不执行无法纳入事务的外部文件副作用；涉及 TOML 清理与数据库的组合升级，需要另行
  明确执行顺序和中断恢复，不把文件变更伪装成已被数据库事务回滚。
