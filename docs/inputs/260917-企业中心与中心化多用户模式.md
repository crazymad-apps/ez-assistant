# 企业中心与中心化多用户模式

- 记录日期：2026-09-17
- 状态：已纳入 `v0.27.0` 总体设计初稿，设计待确认、未实现
- 来源：用户关于企业交付、中心化管理、多用户本地隔离、模型转发和版本分发的会话讨论
- 目标版本：Runtime 套件 `v0.27.0`；Center 软件版本独立确定

> 2026-09-18 已进入 [v0.27.0 总体设计](../versions/v0.27.0/总体设计.md)。本文保留原始需求、
> 已确认取舍和前期候选；具体范围与循环边界由总体设计收敛，不授权开始实现。

## 一、原始意图

项目后续需交付到企业内部使用，并在尽量复用现有 Desktop、Web 和 Runtime Host
成果的前提下，增加以下能力：

1. 企业中心统一管理并分发模型配置；
2. LLM 请求由企业中心转发，真实 Provider 凭证不下发到 Runtime；
3. 企业中心记录企业使用所需的日志；
4. 同一台运行 Runtime Host 的电脑可由多个用户共享，各用户数据在应用层
   逻辑隔离，不要求容器、虚拟机或独立操作系统账号等物理隔离；
5. 个人版与企业版共享主代码并持续演进，同时允许两个产品线按不同节奏
   交错发布和跳版发布。

## 二、已确认的产品形态

### 2.1 普通 Runtime Host 电脑即可作为多用户主机

- 不额外定义“工作站”产品、设备或业务实体。
- 任何普通个人电脑都可运行现有 Runtime Host；开启非本机访问后，其他终端
  可以通过网络访问。
- 企业中心暂不维护工作站登记、设备审批或 Host 路由关系。日志如何区分
  Host 来源留待日志与审计设计，但不因此引入需注册管理的工作站实体。

### 2.2 企业用户登录与本地数据

- 企业用户由企业中心统一认证。
- 某个用户首次成功登录某台 Host 时，Host 自动创建该用户的本地数据库或等价
  的本地数据域，不需要管理员提前登记用户与工作站的绑定。
- 同一 Host 进程可以为多个企业用户服务，会话、Run、配置投影和持久化数据
  必须按已认证用户逻辑隔离。
- 同一企业用户在不同 Host 上的本地数据相互独立；本阶段不由企业中心同步
  用户的本地会话和工作数据。
- 这是应用层逻辑隔离，不应在 UI 或文档中宣称为强安全沙箱。特别是 Shell 以
  Host 所属操作系统用户权限运行，可能绕过应用层文件边界；企业模式下 Shell
  的默认开关、授权和审计策略尚待确定。

## 三、企业模型管理与配置分发

### 3.1 企业中心保留完整模型管理

- 企业中心后台的模型管理模式与当前客户端保持一致，而不是另建一套简化模型或
  映射模型。
- 中心维护完整的 Provider 实例、Provider endpoint、真实凭证、模型目录、
  `model_id`、固定模型参数、默认模型等信息，并沿用现有
  `ProviderInstance` 和 `(provider_instance_id, model_id)` 的身份关系。
- 不引入额外的模型别名或中间映射表；Runtime 仍使用真实 `model_id`。

### 3.2 Runtime 只接收当前生效配置

- 企业中心虽然管理完整模型目录，但登录后只向 Runtime 下发当前企业默认
  模型的有效配置，不下发全部可用模型。
- 下发信息继续保留现有 Runtime 需要的 `endpoint`、凭证 `key`、真实
  `model_id` 及固定模型参数，以尽量复用已有模型配置与调用链路。
- `endpoint` 固定指向企业中心的 LLM 转发地址，并在 URL 路径中携带中心内部
  Provider 实例 ID，例如：

  ```text
  https://center.example.com/api/llm/providers/{provider-id}/v1
  ```

- Provider 实例 ID 已在 endpoint 路径中表达，不再作为独立字段下发给
  Runtime。Runtime 将该 endpoint 视为不透明的 Provider 访问地址。
- Runtime 内部如因现有存储结构需要 Provider ID，可使用固定的企业托管标识；
  该标识只是 Runtime 内部适配细节，不是中心 Provider ID 的第二份传输。
- 企业模式下默认不允许用户切换模型。客户端屏蔽模型管理和模型切换入口，
  Runtime 服务端同时拒绝相关命令，不只依赖 UI 隐藏。
- 不为该动态配置增加 `revision`、`policy_version` 或其他每次修改递增的版本号。

登录响应所需信息可概括为下列形状，但字段命名和最终 DTO 仍需在技术方案
中确定：

```json
{
  "endpoint": "https://center.example.com/api/llm/providers/provider-123/v1",
  "credential": "<temporary-key>",
  "model": {
    "model_id": "qwen-max",
    "parameters": {}
  }
}
```

### 3.3 临时凭证与中心转发

- 下发的 `key` 是由企业中心签发的临时访问凭证，不是 Provider 真实 API Key。
- 每次用户成功登录都签发新的临时凭证；该凭证在所属登录态登出前一直
  有效，登出时撤销。
- Runtime 使用该 endpoint 和临时凭证请求企业中心；中心根据 endpoint 路径中的
  Provider ID 查找真实 Provider endpoint 和 API Key，再向上游发起请求。
- 临时凭证只应允许访问企业中心的 LLM 转发入口，不与企业中心管理员会话或
  Runtime 普通业务会话混用。

临时凭证不再单独设置短时过期与续期机制，以避免给后台长任务增加额外续期
状态。同一用户多次登录时是否允许多个登录态并存，由后续统一登录策略确定；
不在 LLM 凭证层另建一套并发会话规则。

### 3.4 LLM 透明转发

- 企业中心采用透明转发，不再建立统一模型请求协议或在 Node.js 中重复实现
  现有 Rust Provider Adapter。
- Runtime 继续按现有 Provider 协议构造请求。中心只进行临时凭证校验、当前默认
  Provider／模型校验、真实上游地址查找与认证凭证替换，然后透传请求和流式响应。
- 中心不重复执行 Runtime 已持有的固定模型参数上限校验，不为同一约束保存第二份
  执行逻辑。

### 3.5 后台默认模型变更时拒绝旧配置

- 中心收到 LLM 请求后，使用 endpoint 路径中的 Provider ID 和请求体中的
  `model_id` 与当前企业默认模型比较。
- 如果管理员已修改默认 Provider 或默认模型，而 Runtime 尚未刷新，中心直接拒绝
  旧请求，不在服务端静默切换模型。
- 中心必须返回固定、可机器识别的配置过期错误，以便 Runtime 主动刷新。当前
  建议使用 HTTP `409`、错误码 `managed_model_configuration_stale`，提示
  “企业模型配置已更新，请刷新配置后重试。”；具体 HTTP 状态和字段待技术方案确定。
- Runtime 识别该稳定错误后主动刷新企业配置。并发请求的合并刷新、当前
  Run 是否自动重试等执行细节尚待确定。
- 仅修改中心保存的真实 Provider endpoint 或 API Key 时，Runtime 无需刷新，因为
  Runtime 始终请求企业中心。
- 在 Provider ID 和 `model_id` 均不变的情况下修改固定模型参数时，已登录
  Runtime 不立即获得新参数，中心也不额外执行参数上限校验。新参数在 Runtime
  下次获取配置后生效；是否除重新登录外提供显式刷新入口，留待后续功能设计确定。

## 四、代码、分支与发布管理

### 4.1 单仓库与单主干

- 个人版与企业版继续放在同一代码仓库。
- 只保留一条长期主干 `main`，不建立长期 `personal`、`enterprise` 或类似产品
  分支。
- 普通功能分支保持短生命周期，完成后合并回 `main`。
- 产品差异通过明确的产品配置和能力边界表达，不依靠两条长期分支保存两份
  实现。

### 4.2 个人版与企业版可交错发布

- Runtime 产品套件（Desktop、Client、Runtime Host）继续使用统一软件版本。
- 个人版和企业 Runtime 可按各自产品重点交错发布，也可跳过不适用于自身的
  中间版本。两个渠道分别记录最新可发布版本，不要求每个 Runtime 版本都同时
  发布两个产品形态。
- 企业中心使用独立软件版本和独立发布节奏，不随企业 Runtime 安装包捆绑发布。
  当中心自身实现和兼容协议未变时，可以跳过若干 Runtime 版本而不发布新中心。
- Runtime 与企业中心是否可以协作，由双方声明的当前协议能力和最小兼容要求
  双向判定，不要求两者软件版本一致。具体兼容字段和比较规则留待技术方案确定。

### 4.3 Hotfix 分支保留

- 需要对已发布版本进行紧急修复时，允许在对应支持线继续发布补丁版本，不强制
  所有修复都通过新主版本或次版本交付。
- Hotfix 分支不在第一次修复后删除；在该版本支持期内持续保留，以便继续修复。
- 每个 hotfix 修复完成后都必须同步合并或前向移植到最新 `main`，避免修复在后续
  版本中丢失。
- 对应版本结束支持后，hotfix 分支停止更新但保留历史，不因暂时没有新修复
  就删除。

## 五、企业中心技术栈方向

### 5.1 已确认的技术选择边界

- 企业中心不继续使用 Rust 作为主要 B/S 业务开发技术栈。
- 中心优先选择适合传统 B/S 管理后台、权限、数据库与前后端开发的生态。
- LLM 转发需要良好支持 SSE／流式响应、取消、超时、背压和连接断开传播，
  但这不构成必须选择 Rust 或排除 Java 的理由。
- 中心数据库使用 PostgreSQL；原先“不使用 ORM”的要求已于 2026-09-18 改为采用 TypeORM。库表管理参考现有 Runtime Host 的模式，
  使用显式 SQL、有序升级和事务执行，不在生产启动时由工具自动同步 Schema。
- 2026-09-18 补充确认：PostgreSQL 16.14，node-pg-migrate 执行版本化升级 SQL，不逐字段比对；
  升级与业务只使用一个数据库账号，不临时提权。CENTER_DATABASE_AUTO_UPGRADE 默认 true，
  关闭时启动只读检查，需要升级则退出；可显式执行 db:upgrade。
- 初始化直接写入首个 SQL：创建中心身份、超级管理员 admin / 123456（仅存预生成摘要）及
  初始化审计，与建表同事务。由框架保证只执行一次，不另设初始化代码或配置，重启不重置密码；
  公开默认密码应在正式使用前修改。

### 5.2 当前候选

Node.js 经初步讨论可以承载企业中心和 LLM 流式转发。当前建议候选为：

- Node.js LTS + TypeScript；
- NestJS + Fastify Adapter；
- PostgreSQL + TypeORM（pg 驱动）+ node-pg-migrate 显式升级 SQL（2026-09-18 最新确认）；
- React + TypeScript + Vite 管理端；
- 首版采用模块化单体和单一部署单元，在代码中独立 `llm-proxy` 模块边界，
  有实际负载或故障域需求时再考虑拆分。

上述组合是已验证可行性的建议方向，不视为已最终确认的依赖清单。Java 不是
因为需要转发 LLM 就技术上不可用，但在本项目首版中，Node.js 在流式代理、
前后端 TypeScript 一致性和开发迭代速度上是当前更优的候选。

## 六、企业中心的已知责任

企业中心至少承担以下责任：

| 责任 | 当前边界 |
| --- | --- |
| 用户身份 | 管理后台和 Runtime 共用同一套用户、登录和会话机制，通过权限决定可访问功能 |
| 模型管理 | 维护完整 Provider、模型目录、固定配置和企业默认模型 |
| 配置分发 | 登录成功后向 Runtime 下发当前有效默认模型配置和临时凭证 |
| LLM 转发 | 验证临时凭证和当前默认模型，注入真实 Provider 凭证并流式转发 |
| 企业日志 | 记录企业内部使用所需的审计和调用日志；字段、脱敏、保留期待定 |
| 管理后台 | 管理用户、模型和企业级策略；首版具体权限粒度待定 |

企业中心不持有 Runtime 的 Session、Run 或本地工作数据的第二份权威状态，
也不因为提供认证和 LLM 转发就升级为 Runtime 任务调度中心。
临时 LLM key 是从已登录会话签发的限定用途凭证，不是第二套用户登录态。

2026-09-18 补充确认：普通用户在本机 Runtime 的 Desktop/Web 入口登录、退出、查询本人身份及修改本人密码，不进入企业后台；后台仅供管理员使用，仍复用同一套中心认证与会话机制。个人改密必须输入原密码；管理员在用户管理中可直接重置任意用户（包括自己）的密码，无需原密码。两者是不同性质的操作，不能按目标是否为自己合并处理。

2026-09-18 补充确认：用户表需要增加超级管理员的数据库字段标记；该用户禁止删除，默认具有所有权限，默认具有管理员角色。是否禁止停用或调整角色、如何授予和撤销该标记尚未明确。

### 6.1 请求与返回内容快照

企业中心是 LLM 请求的必经路径，技术上可以同步保留请求和返回内容快照。
这对内部审计、问题追溯和成本对账有价值，但会中可能包含用户隐私、文件内容、
系统提示词和工具参数，不应与普通运行日志默认等同。

内容快照保持透明代理边界，并由企业中心后台服务负责落盘：

- 运行元数据和操作审计始终记录；
- 完整请求／返回内容快照是独立的企业策略开关，具体默认值待确认；
- 开启后保存代理实际看到的原始请求体和上游响应体，不为日志再建立一套
  Provider 统一响应模型；
- 上游响应结束后，后台服务再将该次请求和完整返回内容统一写入本地文本
  快照文件，不将内容正文直接存入 PostgreSQL；
- PostgreSQL 只记录调用标识、用户、Provider／模型、时间、结果状态和快照文件定位
  等必要的检索字段；具体字段由后续功能设计收敛；
- 保留期、本地根目录、文件格式与命名、查看权限、脱敏、大小限制以及中断时
  是否保留部分快照仍需在功能设计中确定。

## 七、当前明确不做

- 不为工作站建立登记、审批和路由系统。
- 不在首次使用前由管理员预创建每个用户的 Host 本地数据库。
- 不为企业模型管理另建一套模型映射、别名或虚拟默认模型。
- 不向 Runtime 下发完整企业模型目录和真实 Provider 凭证。
- 不用递增配置版本管理动态模型配置。
- 不在企业中心重复实现 Provider Adapter 或 Runtime 已执行的固定模型参数校验。
- 不为管理员和普通 Runtime 用户建立两套登录与会话机制。
- 不使用 ORM 自动同步表结构或维护第二套升级账本；允许 TypeORM 处理业务数据访问。
- 不将 LLM 请求与返回内容正文直接存入 PostgreSQL。
- 不强制企业中心与 Runtime 使用相同软件版本或同步发布。
- 不建立个人版和企业版两条长期产品分支。
- 首版不默认引入微服务、Redis、Kafka、Elasticsearch 或 Kubernetes；只在已确认
  的容量、性能或运维要求下重新评估。

## 八、待后续确认的核心选择

1. **多端登录策略**：同一用户多次登录时是否允许登录态并存，以及管理员停用账号
   时如何统一撤销已登录会话和所属 LLM key。
2. **内容快照策略**：是否默认保存 LLM 完整请求与返回内容，以及本地快照
   的保留期、根目录、文件格式与命名、查看权限、脱敏、大小上限和中断处理。
3. **企业工具权限**：在逻辑隔离前提下，Shell、文件系统和其他本地工具的默认能力、
   授权和审计策略。
4. **最终开发框架**：是否正式确认 Node.js + TypeScript + NestJS/Fastify 组合，以及中心
   的工程边界、部署形式和发布产物。

## 九、后续进入版本时的评估要求

2026-09-18 按更新后的流程在 `v0.27.0` 统一版本号下划分实现循环，先确认总体设计，
再逐循环编写功能设计和技术方案。需要重点核对：

- 现有单用户 Runtime 权威状态如何最小化改造为按已认证用户分区；
- 现有模型管理、会话默认模型与 Run 配置冻结语义如何直接复用；
- 企业模式下仅隐藏 UI 不足以形成权限边界，哪些命令必须由 Runtime 服务端拒绝；
- 临时凭证、企业日志和 Provider 真实凭证的存储、脱敏和泄漏边界；
- LLM 流式转发在断连、取消、超时、限流、上游错误和客户端重试下的确定语义；
- Runtime 与企业中心独立升级、降级和跳版发布时的双向兼容验证。

## 2026-09-18 登录机制简化确认

- 前端负责保存和清除凭据，后端统一 Bearer 鉴权，不设置或清除 Cookie。
- 不建设 Session 实体、会话 ID 或会话表；允许同一用户多个 Token，哪个 Token 登出就废弃哪个。
- Token 直接存进程内存 Map<token,userId>，不入库、不做 Token 哈希；用户密码仍使用摘要保存。
- 无定时过期，中心单实例关闭/重启后全部 Token 和关联 LLM key 失效，需要重新登录。
- 替代此前持久化登录态/会话机制的表述；不改变用户、中心稳定身份和管理审计的持久化职责。

## 2026-09-18 超级管理员补充确认

不提供新增超级管理员或清除标记的管理接口，禁止 API 停用/降权；允许修改资料和管理重置密码。允许按数据库安全规则直接在库中给其他用户赋予超级管理员标记，代码必须按 is_super_admin 判定，不得绑定默认账号名或固定用户 ID。
