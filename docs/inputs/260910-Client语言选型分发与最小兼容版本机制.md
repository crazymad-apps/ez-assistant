## 一、原始意图

用户希望 Client 使用 TypeScript 编写，作为与 Desktop 同级的产品，各自分发包内置 Runtime
Host。同时安装 Client 与 Desktop 时，需要解决 Host 实例冲突和版本兼容问题。

讨论最初提出版本不一致时提示启动失败，随后用户明确修订为：每个版本声明最小兼容版本，
每次连接 Host 初始化时双向比较。Client、Desktop、Host 同一发布版本的应用协议最小兼容
版本应一致，因为它只表达应用协议层的兼容性。

用户进一步要求数据库也维护独立的最小兼容版本，避免低版本 Host 启动后破坏数据库。

后续功能讨论中，用户收敛 Client 定位：主要管理本机 Host，Agent 功能大多数通过随包 Web
使用，因此当前 Client 基本没有直接管理远端 Host 的需要。该收敛针对本版 Client 功能，
不改变 Host 提供远程 Web 访问及 Desktop 既有远端连接能力。

本文保存以上讨论结果与待定项，不作为完整技术方案，也不授权启动开发或操作用户数据库。

## 二、Client 语言与分发

- Client 使用 TypeScript，运行时使用 Node.js；用户明确不使用 Bun，关注其兼容性风险。
  Host／Runtime 继续使用 Rust。
- Client 与 Desktop 为同级产品，均可独立安装，也可以同机共存；Client 不限定为服务器专用。
- 两个产品的分发包各自内置 Runtime Host，Host 作为共有运行组件提供 Web，不单独作为第三种产品分发。
- Client 通过既有应用协议连接 Runtime，负责命令、连接和交互；会话、Run、调度及持久化权威状态仍归 Runtime。
- 同一用户、同一 Runtime Home 默认共用一个运行实例，优先发现并连接已有 Host；无实例时可启动自身随包 Host。
- 同时启动时复用 Host 单实例锁，未取得锁的一端重新发现并校验已有实例；退出任一客户端不停止 Host 和任务。

用户进一步明确 Client 必须能够独立演进：以后更换技术架构也不能影响 Host／Desktop 的正常使用。
各方通过共享应用协议和 Host 本机管理契约协作；Host／Desktop 不依赖 Client 的框架、源码、
构建脚本、随包 Node 或运行状态。共享协议生成和自启服务亦须独立于 Client 实现，
Client 内部改造不要求提高兼容下限或迁移共享数据。具体约束与验证见技术方案 3.3 和验收 A23。

### 本版功能定位补充

Client 聚焦本机 Host 管理。先前提出的终端会话、Agent 交互、模型管理及直接连接远端 Host
不作为本版主线；Agent 使用主要交给随包 Web。服务器部署场景下，在服务器上执行当地 Client
管理 Host，用户通过浏览器访问该 Host 的 Web。

用户进一步明确：Client 的 Agent／Session 会话能力可以放到后续版本建设，保留为后续产品
方向；本版专注本机 Host 管理。后续版本号、具体会话功能与交互形式待定，不因本版定位收敛
将 Client 永久限定为 Host 管理工具，也不提前实现会话入口或扩展框架。

用户在技术方案评审中明确，智能终端与 Host 的版本兼容不纳入 v0.25.2，需要本项目与智能终端
项目同步开展。后续共同设计版本声明、设备握手、失败处理并联合验收，版本号未定。
本次选中的 WS Open 行实际属于 Desktop／Web 的 Shell（PTY）终端，技术稿已明确区分它与
智能终端 Device Gateway；本版不单方面改造智能终端协议或要求另一项目同步升级。

功能讨论先收敛为以下分组，具体入口和交付细节以主功能设计为准：

| 分组 | 候选内容 |
| --- | --- |
| Host 生命周期 | 启动、停止、重启、发现并复用本机已有实例 |
| 运行与访问配置 | Runtime Home、监听配置、密码和本机 Host 远程访问开关 |
| 状态与诊断 | 运行及初始化状态、版本与兼容信息、启动失败原因和日志 |
| Web 入口 | 展示访问地址；具备浏览器环境时打开 Web，无图形环境下输出地址 |
| 自启服务配置 | 已确认纳入：配置形式、默认关闭，主要面向 Linux 服务器；具体服务方式待方案 |

本机 Host 允许其他设备访问，与 Client 主动管理另一台 Host 是两个范围。本版不需要由 Client
维护远端目标列表和登录凭据；本版应用协议双向兼容规则覆盖 Client／Desktop／Web 的实际连接入口，
不延伸至智能终端设备连接。

JavaScript 运行时已确定为 Node.js。随包携带 Node runtime 作为后续分发方案的验证方向，
具体 Node 版本、终端交互库、安装渠道和打包方式尚未确定。Desktop 分发包是否额外附带 CLI 入口也待定。

### config 交互入口（2026-09-10 补充）

用户明确 `config` 入口采用交互方式，用于配置本机 Host 访问设置。这一选择不表示已经采用
无参数常驻管理菜单；其他管理命令、默认入口行为及终端交互库仍待设计。

正式功能设计评审中，用户补充自启服务应以配置形式存在，默认不开启，主要面向 Linux 服务器；
本版据此纳入自启配置，替代初稿暂不纳入系统服务的建议。主功能设计将其放入 config 的启动设置，
区分自启策略与当前 Host 启停；具体平台服务、权限及崩溃拉起策略不从这条确认自动推导。

用户已进一步确认：Host 未启动时也能使用交互式 `config`，支持首次配置和启动前修正访问
设置；配置能力不以先启动 Host 为前提，保存的设置供下次启动使用。

基于现有 Host 访问设置，交互配置项包括：

| 配置项 | 现有范围与交互方向 |
| --- | --- |
| 访问密码 | 设置或修改；展示是否已设置，输入时隐藏内容，不回显已有密码 |
| 非本地访问 | 是否允许其他设备连接本机 Host；未设置密码时不能开启 |
| 监听端口 | 本机与非本机访问共用同一端口，默认 7240 |
| 访问协议 | HTTP／HTTPS |
| HTTPS 证书与私钥 | 选择 HTTPS 时填写 Host 上的文件路径 |
| 允许的域名 | 可选域名列表；通过 IP 访问时无需填写 |

具体界面采用菜单或分步向导尚未确定。建议进入时展示当前设置，由用户选择修改项，明确保存
及取消；访问密码沿用独立修改操作，避免将密码和其他配置的多次写入误报为一次原子保存。

现有保存与生效规则：密码修改会使已有普通登录失效；访问开关和域名更新无需重启，端口、
协议和证书修改需显式重启 Host。已开放非本地访问时，先关闭它再修改监听配置；监听变更保存
并重启后，才能重新开启非本地访问。交互必须明确区分“已保存”和“当前已生效”，不自动重启。

现有依据：[Host 访问契约](../../crates/assistant-protocol/src/host_access.rs)与
[访问配置处理](../../apps/runtime-host/src/access/mod.rs)。运行中的 Host 应复用现有配置入口与
校验，不能由 Client 绕过 Host 并行覆盖配置。Host 未启动时的离线配置能力已确认，具体保存、
校验、密码处理及与并发启动的协调路径由技术方案确定；已运行但处于启动诊断状态的 Host
仍需按实际状态处理，不能误认为离线并直接覆盖。当前仅记录需求，尚未实现。

## 三、应用协议最小兼容版本

Client、Desktop、Host 都携带：

| 信息 | 含义 |
| --- | --- |
| 当前版本 | 当前组件的软件发布版本号，例如 0.25.2 |
| 最小兼容版本 | 本版本应用协议允许连接的最低对端软件版本号，例如 0.25.2 |

用户在技术方案评审中再次明确“使用软件版本号”。两项均使用同一软件版本体系，
不另外维护协议版本号；技术稿中保留并提升协议整数的建议已移除。

同一发布版本的三个组件应使用同一份最小兼容版本定义，避免分别维护产生差异。协议仍兼容时
下限可保持不变；协议发生破坏兼容的变化时提高下限，不因 UI 或内部实现变化直接提高。

每次客户端连接 Host 初始化时，必须同时满足：

```text
客户端当前版本 >= Host 声明的最小兼容版本
Host 当前版本 >= 客户端声明的最小兼容版本
```

Desktop 按相同客户端规则处理；Client 与 Desktop 无需直接互相比版本。本机、远端直连、
断线后重新初始化，以及并发启动后发现的实例，都执行该检查。

任一方向不满足时，提示当前客户端启动／连接失败，说明实际版本及未满足的最低要求。
已有 Host 和任务保持运行，不自动停止、替换、升级、降级或另开实例。不同软件版本只要
满足双向兼容条件即可连接，早先“必须完全同版本”的讨论不再作为最终规则。

## 四、数据库最小兼容版本

数据库独立持久保存“允许安全读写本库的最低 Host 软件版本”。它与应用协议的最小兼容版本
含义不同，数值无需一致；Client 和 Desktop 不直接决定数据库兼容性。

Host 使用数据库的必要条件为：

```text
Host 当前版本 >= 数据库记录的最小兼容 Host 版本
```

保护方向：

- Host 先取得 Runtime Home 实例锁，再只读核实数据库兼容信息；通过前不得执行迁移、业务写入、数据修复、索引初始化或持久日志模式变更。
- 不兼容时存储初始化失败，不开放业务服务，保留原数据并报告原因；不自动降级、清理或重建数据库。
- 达到下限只是必要条件，仍需执行现有完整性、迁移路径和目标数据校验。
- 下限由表结构、字段语义及持久化格式的安全读写要求决定，不能只检查是否发生 DDL。
- 破坏存储兼容的迁移应将数据变更与下限提升在同一事务提交；兼容变更不因 Host 升级自动提高下限。
- 启动时不能用当前安装包中的值覆盖数据库已有下限，也不能由旧 Host 降低要求；迁移前保留独立备份及实际内容验证要求。

数据库实际完成的迁移版本与最小兼容 Host 版本是不同事实。现有迁移账本的职责仍需保留，
不能以一个兼容下限替代迁移历史或跳过数据检查。

## 五、已有基础与待明确事项

本轮仅阅读源码，未启动 Host、连接数据库或修改业务数据。

- Desktop 已有 [TypeScript Runtime Client](../../apps/desktop/src/runtime-client/RuntimeClient.ts)
  和生成的协议类型；仅按本机 Host 管理的实际需要评估复用范围，并处理浏览器及桌面 bootstrap
  依赖，不从语言一致推导必须抽取完整会话或事件流客户端。
- Host 已有[按 Runtime Home 加锁及发布发现信息](../../apps/runtime-host/src/endpoint.rs)的机制；
  [Desktop bootstrap](../../apps/desktop/src-tauri/src/runtime_bootstrap.rs)已优先发现已有实例。
- [数据库迁移入口](../../apps/runtime-host/src/storage/migrations/mod.rs)目前已拒绝高版本库，
  尚无独立最小兼容下限；新规则必须与该保护及迁移账本校验统一，不能只加字段就放开旧 Host。

以下事项已转入技术方案，按开发计划实施和验证：

1. 三个组件共享版本定义的落点、生成方式、首个兼容下限，以及版本信息交换与比较方法。
2. 统一使用软件版本比较并移除现有 `protocol_version`；能力检查继续按实际入口需要执行。
3. 数据库兼容信息的落点、旧库缺少信息时的识别／迁移、信息损坏时的处理及必要验收。
4. 已发布旧程序不会自动执行新增检查；需要核查这些程序的现有拒绝行为，不能承诺任意历史 Host 均受新机制保护。
5. 双产品共存时的 Host 重启来源、显式停止／升级影响及卸载后的启动路径；具体运行环境与分发装配另行确定。

本文中的比较表达只说明语义；字段名称、数据库表结构和协议形状以技术方案为准。
