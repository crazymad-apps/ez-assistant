## UI-006 正文与 reasoning 输出跟随及自由滚动

- 反馈日期：2026-09-16。
- 状态：已纳入 `v0.27.0` C05；2026-09-21 功能/技术设计及开发计划已确认，M0 与循环验收已获用户确认，2026-09-22 随版本归档。
- 目标版本：`v0.27.0`，见[总体设计](../versions/v0.27.0/总体设计.md)。

### 原始反馈

> 现在reasoning和text正文, 都不能随输出自动滚动到底部, 因为最新行输出后可能就导致程序判断当前已经不是在最底部了, 但是我希望能维持用户自由滚动的能力, 避免一直被锁定在底部

### 问题与初查

- 正文所属消息列表已有底部跟随状态，但每次 scroll 都按当前底部距离重新赋值；需要核查
  内容增长、程序滚动及布局变化触发的事件，避免误当作用户主动离开底部。
- reasoning 使用最高 180px 的独立滚动区域，目前没有对应的输出自动跟随逻辑。
- 正文所涉位置：`apps/desktop/src/features/conversation/ConversationView/index.tsx`；
  reasoning 所涉位置：同目录 `ToolSegments.tsx` 的 `ReasoningBox` 及 `index.module.scss`。

### 期望行为与后续验证

- 用户原本处于底部跟随状态时，新增正文或 reasoning 后继续滚动到对应区域底部；不能仅因
  新内容把底部推远，就取消跟随。
- 用户主动向上滚动查看已有内容时暂停跟随，后续输出不得抢回视口；仍允许正常滚轮、触控板、
  键盘及滚动条操作，不持续锁定到底部。
- 用户主动回到底部，或点击消息列表现有的“回到底部”按钮后恢复跟随。
- 消息列表和 reasoning 内部区域分别维护跟随意图，嵌套滚动不能误切换另一层的跟随状态。
- 验证连续换行、大块增量、布局变化及程序滚动时的事件顺序，并覆盖用户上滚后继续输出、
  回底恢复、reasoning 展开收起、切换会话和加载更早消息的滚动位置保持。

本条先保留问题和交互目标，具体修复与版本归属另行安排。

## UI-012 运行中上下文窗口与累计 Token 统计串值

- 反馈日期：2026-09-22。
- 状态：已在 v0.28.1 F01 完成核查与旧 step 覆盖快照问题修复，随版本按实际结果验收归档；未逐项记录的人工场景仍为已知限制。
- 目标版本：v0.28.1 F01；见[开发计划](../versions/v0.28.1/features/F01-LLM请求异常恢复/开发计划.md)。
- 补充材料：用户会话附图。

### 原始反馈

> 这个累计数值明显算错了，怎么可能窗口 token 等于总量呢，记一下这个 bug

### 现象与正确口径

- 附图中的运行状态栏同时显示“上下文 129K Token / 1050K Token（12.2%）”和
  “累计 128K Token”；当前上下文占用与会话累计消耗几乎相等，明显存在统计口径串用、
  聚合遗漏或投影更新异常的可能。
- “上下文”应表示当前请求实际携带的有效上下文窗口占用，会受历史压缩、替换及当前轮新增内容影响；
  “累计”应表示会话历次模型调用产生的累计 Token 消耗。两者必须独立计算和更新，不能直接复用同一数值。
- 后续修复需核查运行中临时 usage 与持久化会话 usage 的合并逻辑、压缩前后数值，以及输入、输出、
  缓存 Token 是否按各自口径计入；不能仅通过改文案或显示取整掩盖错误。
- 验证至少覆盖多轮会话、发生上下文压缩后的会话和运行中增量更新，确认当前窗口占用可以下降或重算，
  而累计消耗保持单调累加且不会被窗口值覆盖。

2026-09-27 核查结论：live usage 是最近完整 step，并非累计 Run；数值接近本身不足以证明串值。已复现旧 step 的较高用量通过前端 max 合并覆盖较小的新上下文快照，删除该合并后直接消费 Runtime 权威窗口占用，累计消耗保持独立。原截图无法单独重建历史请求，人工复测沿上述正确口径进行。
