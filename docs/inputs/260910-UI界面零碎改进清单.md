## UI-006 正文与 reasoning 输出跟随及自由滚动

- 反馈日期：2026-09-16。
- 状态：已纳入 `v0.27.0` C05；2026-09-21 功能/技术设计及开发计划已确认，M0 与循环验收已获用户确认，2026-09-22 随版本归档。
- 目标版本：`v0.27.0`，见[总体设计](../versions/v0.27.0/总体设计.md)。

### 原始反馈

> 现在reasoning和text正文, 都不能随输出自动滚动到底部, 因为最新行输出后可能就导致程序判断当前已经不是在最底部了, 但是我希望能维持用户自由滚动的能力, 避免一直被锁定在底部

### 问题与初查

- 正文所属消息列表已有底部跟随状态，但每次 scroll 都按当前底部距离重新赋值；需要核查
  内容增长、程序滚动及布局变化触发的事件，避免误当作用户主动离开底部。
- reasoning 使用最高 180px 的独立滚动区域，目前没有对应的输出自动跟随逻辑。
- 正文所涉位置：`apps/desktop/src/features/conversation/ConversationView/index.tsx`；
  reasoning 所涉位置：同目录 `ToolSegments.tsx` 的 `ReasoningBox` 及 `index.module.scss`。

### 期望行为与后续验证

- 用户原本处于底部跟随状态时，新增正文或 reasoning 后继续滚动到对应区域底部；不能仅因
  新内容把底部推远，就取消跟随。
- 用户主动向上滚动查看已有内容时暂停跟随，后续输出不得抢回视口；仍允许正常滚轮、触控板、
  键盘及滚动条操作，不持续锁定到底部。
- 用户主动回到底部，或点击消息列表现有的“回到底部”按钮后恢复跟随。
- 消息列表和 reasoning 内部区域分别维护跟随意图，嵌套滚动不能误切换另一层的跟随状态。
- 验证连续换行、大块增量、布局变化及程序滚动时的事件顺序，并覆盖用户上滚后继续输出、
  回底恢复、reasoning 展开收起、切换会话和加载更早消息的滚动位置保持。

本条先保留问题和交互目标，具体修复与版本归属另行安排。

## UI-012 运行中上下文窗口与累计 Token 统计串值

- 反馈日期：2026-09-22。
- 状态：已在 v0.28.1 F01 完成核查与旧 step 覆盖快照问题修复，随版本按实际结果验收归档；未逐项记录的人工场景仍为已知限制。
- 目标版本：v0.28.1 F01；见[开发计划](../versions/v0.28.1/features/F01-LLM请求异常恢复/开发计划.md)。
- 补充材料：用户会话附图。

### 原始反馈

> 这个累计数值明显算错了，怎么可能窗口 token 等于总量呢，记一下这个 bug

### 现象与正确口径

- 附图中的运行状态栏同时显示“上下文 129K Token / 1050K Token（12.2%）”和
  “累计 128K Token”；当前上下文占用与会话累计消耗几乎相等，明显存在统计口径串用、
  聚合遗漏或投影更新异常的可能。
- “上下文”应表示当前请求实际携带的有效上下文窗口占用，会受历史压缩、替换及当前轮新增内容影响；
  “累计”应表示会话历次模型调用产生的累计 Token 消耗。两者必须独立计算和更新，不能直接复用同一数值。
- 后续修复需核查运行中临时 usage 与持久化会话 usage 的合并逻辑、压缩前后数值，以及输入、输出、
  缓存 Token 是否按各自口径计入；不能仅通过改文案或显示取整掩盖错误。
- 验证至少覆盖多轮会话、发生上下文压缩后的会话和运行中增量更新，确认当前窗口占用可以下降或重算，
  而累计消耗保持单调累加且不会被窗口值覆盖。

2026-09-27 核查结论：live usage 是最近完整 step，并非累计 Run；数值接近本身不足以证明串值。已复现旧 step 的较高用量通过前端 max 合并覆盖较小的新上下文快照，删除该合并后直接消费 Runtime 权威窗口占用，累计消耗保持独立。原截图无法单独重建历史请求，人工复测沿上述正确口径进行。

### 现象与只读定位

- 用户进一步澄清：“不是，我的意思是默认出来的终端类型和/bin/sh不一样”。核心问题是
  默认交互 Shell 与显式 `/bin/sh` 是不同的启动选择，而当前下拉目录没有表达默认 Shell，

- [`SelectionPopover`](../../apps/desktop/src/components/SelectionPopover/index.tsx) 将
  未匹配的选中索引用 `Math.max(0, findIndex(...))` 回退到 0，并使用该项标签渲染，

- 默认 Shell 显示“系统默认 Shell”，有可靠的实际类型信息时可补充名称，不能猜测为 zsh
  或回退显示第一个不相关选项。
- 交互终端提供返回系统默认 Shell 的入口，目录按所连接 Host 的平台与实际支持能力展示，
  不按 Desktop 所在操作系统推断远端 Shell；系统默认 Shell 入口同样应有可用的实际启动来源。
- 不把 Agent 非交互 Shell 的类型限制直接当作用户交互终端的完整可选目录。
- 检查公共选择器未匹配选中值的展示与键盘焦点逻辑，不能用修正焦点索引冒充选中状态。
- 与 UI-014 协调，先确保真实 Shell、标签和选择一致，再适配提示符；不将 macOS 默认终端
  强制改成 `/bin/sh`。具体目录和协议调整留正式设计，不预先增加类型或持久化状态。

将连续工具调用合并成默认收起的工具组，组头显示执行状态、数量及当前工具；展开后保留
原顺序和单次参数/结果入口。中间正文或 reasoning 出现时结束当前分组，不跨内容重排；
失败和待审批需保持可见。这是内层工具展示建议，不改变已经确认的外层处理过程展开规则。

### 设计时需明确的边界

- 区分新消息到达与同一消息的流式增量；用户手动收起后，不能擅自把每个增量都当成
  新消息强制展开。真正新消息到达时的展开触发范围在正式设计中明确。
- 分别维护外层处理过程与内层 reasoning 的展开语义；summary 流式更新与原文模式切换
  不重复渲染、不丢失最新文本。
- 核对正常完成、失败、取消、等待反馈与审批时的折叠及时间表现，待办入口不能因折叠而无法访问。
- 保持用户自由滚动、历史分页和重连后的稳定投影；最新 reasoning 行的滚动不抢占主列表视口。
- 本项是新的展示范围，取代历史版本“不做过程聚合折叠”的后置安排，不改写已归档版本结论。

本轮仅记录交互需求与参考图，未修改消息投影或前端实现。


## UI-021 跨会话的待审批与待回答感知

- 反馈日期：2026-09-29。
- 状态：2026-09-29 用户已确认纳入 `v0.29.0` F03；范围已同步总体设计与版本台账，独立设计已形成，应用内提醒待后续里程碑实现。
- 目标版本：`v0.29.0` F03；跨会话应用内通知与点击定位处理入口，侧栏保持原状。

### 原始反馈

> 发现一个实际问题，不知道是因为在不同会话里面还是因为通知没触发，用户无法感知到会话阻塞了

用户随后明确这里的阻塞指 **工具审批 / 用户问答**；尚未确认发生时应用处于前台还是后台。

### 已核实的现状

- [通知投递](../../apps/desktop/src/features/notifications/NotificationStore.ts)在应用前台时跳过所有业务系统通知，并将该事项消费，不区分当前阅读会话；切到后台后不补发。已有单元测试明确覆盖审批及问答的这一行为，因此不能仅凭没有横幅判断事件未触发。
- [侧栏会话列表](../../apps/desktop/src/features/sessions/SessionSidebar/WorkspaceGroup.tsx)只依据活动 Run 显示“正在运行”，没有使用待审批或待回答事实显示区别；用户在其他会话时可能无法发现任务已经等待处理。
- 系统通知开关默认关闭，后台显示还受权限和系统设置影响；本次未复现用户实际运行环境的系统横幅，不宣称具体通知投递故障已定位。

### 用户确认与交付边界

2026-09-29 用户明确要求：

> 侧栏状态不需要变更了保持原状，跨会话应用内提醒需要做一下，可以做成应用内通知机制以及点击点位处理入口；纳入 F03

- 侧栏状态、转圈和时间显示保持原状；不将之前提出的侧栏等待标记纳入本项。
- 建立应用内通知机制，首版覆盖其他会话的工具审批和用户问答，沿用现有通知目标、去重、身份隔离及点击定位能力。
- 当前正在阅读来源会话时，已有审批/问答入口必须明显可达；阅读其他会话时，需要可点击定位来源会话的应用内提示。
- 会话所在项目收起、侧栏隐藏或来源为助理会话时，应用内通知仍应可见，并能点击进入对应处理入口。
- 应用在后台时沿用既有系统通知权限、开关、去重与点击定位；应用内的待处理展示不依赖系统通知是否开启或横幅是否显示。
- 点击通知先复核当前身份与事项，定位来源会话及审批/问答入口；子任务审批仍定位父会话唯一审批区。已处理或失效时展示最新状态，不打开过期操作。
- 尚未处理事项的应用内可达性在重连后恢复；不重放历史弹出提醒或旧系统通知。解决/取消后依据 Runtime 权威事实消除对应待处理提示，不另建一套执行阻塞状态。
- F03 独立设计时细化通知外观、聚合与保留方式；本次范围确认不提前实现 F03，也不推进 F06 的下一里程碑。
