# v0.11.0 Workspace 与附件讨论

- 记录日期：2026-08-10
- 状态：已纳入并随 v0.11.0 完成归档
- 来源：v0.11.0 用户会话讨论；Hermes Agent、OpenCode 当前实现只读调研
- 目标版本：v0.11.0

> 本文保留进入功能设计前的阶段性讨论。已确认结论以
> [`v0.11.0 功能设计`](../versions/v0.11.0/功能设计.md) 为准；其中“附件与消息作为一个原子提交”
> 等早期方案已被后续确认的“先上传文件、再提交消息，成功附件不回滚”取代。

## 原始目标

v0.11.0 围绕 Workspace、附件和 System Context 建立下一阶段 Runtime 能力。当前先讨论并确认
业务概念和使用边界，不直接编写功能设计，不提前确定字段、表结构、软链接等技术实现。

本版本允许在隔离验证环境中先完全放行 Agent 的实际文件能力，正式的 Plan / Build、Ask / Auto、
权限作用域、审批和审计仍属于 v0.12.0。Runtime 内部数据的完整性约束不因验证环境放行而取消。

## 已确认的 Workspace 关系

- Workspace 是独立、可持久化的业务对象，可以被多个 Session 复用；
- 一个 Session 最多绑定一个 Workspace，也允许创建不绑定 Workspace 的普通会话；
- Session 创建后不直接更换所绑定的 Workspace；需要切换时创建新 Session，未来也可以通过显式
  Fork 形成新会话；
- Workspace 对应用户已有工作目录，Runtime 不复制整个项目；
- Session 继续拥有 Runtime 管理的临时目录，临时目录与用户 Workspace 是两个概念；
- Workspace 中的文件是可以被 Agent 持续读取和修改的普通工作文件。

## Artifact 结论

v0.11.0 不引入 Artifact 业务对象。

- Agent 写入 Session 临时目录的文件仍是临时文件；
- Agent 写入 Workspace 的文件仍是普通工作文件；
- 不增加 Artifact 注册、发布、版本、不可变快照或独立生命周期；
- 后续桌面端如果确实需要产物卡片、交付文件或长期保存语义，再根据实际交互重新定义。

调研发现，OpenCode 的 Agent 输出文件主要仍是工作目录中的普通文件；Hermes 在部分临时任务中
把明确声明的结果文件复制出即将清理的 scratch workspace，其主要作用也是保留临时目录中的结果。
ez-assistant 已经拥有 Session 临时目录，因此当前没有必要为同类问题增加 Artifact 概念。

## 附件定义

附件是用户交给 Agent 参考的 Session 私有、静态文件：

- 用户选择的原始文件在提交时复制到 Runtime 管理的存储，不长期引用用户原始路径；
- 上传完成后的附件内容不可通过产品流程修改或覆盖；原始文件后来变化不影响附件；
- 附件正文不自动注入模型上下文；模型只看到必要的附件引用信息，需要时自行调用工具读取；
- 附件是 Session 资源，可以被同一 Session 的多条 User Message 引用；
- 具体消息引用哪些附件，直接记录在 User Message Parts 中，顺带供 Agent 和 UI 展示；
- 数据库不维护消息级附件引用次数，历史重新输入或消息尾段销毁也不更新这类计数；
- Session 归档时附件继续保留，恢复后仍然可读。

## 数据管理方向

- SQLite 管理附件的业务元数据和生命周期，附件二进制正文保存在文件系统中；
- 附件记录与 Session 关联，至少需要保留附件标识、原始名称、内容类型、大小、Blob Hash、Runtime
  内部物理位置、状态和时间信息；具体字段等到技术方案确认；
- Message Parts 通过附件标识建立引用，不把 Runtime 内部物理路径作为持久协议标识；
- 原始文件名和内容都相同时可根据 Blob Hash 复用同一份物理内容；同内容不同名不复用，但各 Session 仍拥有独立、不可越权访问的业务附件；
- 引用只按 Session 层级理解：同一物理内容被多少个不同 Session 持有。一个附件出现在同一
  Session 的多少条消息中不影响该引用关系；
- 是否持久化物理内容的 Session 引用计数尚不作为功能事实。当前可以根据相同 Hash 的 Session
  附件关系统计；如果未来为了清理效率引入独立 Blob 元数据，再决定是否缓存计数；
- Session 私有附件目录是 Agent 可读取的逻辑视图，数据库附件记录和物理内容才是权威数据；该视图
  应当可以从数据库重建。

## 文件工具接入方向

优先复用现有文件读取能力，使 Agent 能像读取普通文件一样按需读取附件。可以评估在 Session 私有
附件目录中为物理内容建立软链接或其他只读映射，但目前只确认能力目标，不把软链接确定为跨平台
产品契约。

现有本地文件 Adapter 会跟随软链接读取，同时 Write / Edit 也会跟随软链接修改目标。因此必须满足：

- 附件目录不属于 Agent 可修改的 Workspace 或 Session 临时目录；
- 即使 v0.11.0 验证环境对 Workspace 文件能力完全放行，也不能把附件修改解释为受支持行为；
- 若技术方案采用软链接，需要明确 Read 与 Write / Edit / Delete 的边界，并处理 Shell 不是操作
  系统沙箱、可能绕过应用层文件规则的已知限制；
- Hash 除内容寻址和复用外，也用于识别附件内容是否发生了非预期变化；
- Windows 等平台是否使用软链接、复制、只读映射或其他方式，由技术方案基于平台能力确定。

## 文件上传与消息提交

交互层可以把选文件和发送消息表现为一次操作，但传输与业务事实明确分为两步：

1. 用户点击发送后，客户端先把每个文件上传到当前 Session；
2. 文件上传成功就立即形成 Session Attachment 事实，不需要先属于某条 Message；
3. 任一文件上传失败时，客户端不继续提交 User Message；
4. 全部文件上传成功后，客户端使用 Attachment ID 列表提交文本和 File References Part；
5. Message 提交失败不回滚已成功的 Attachment，客户端可直接复用这些 ID 重试；
6. 输入继续使用既有幂等 Key；附件不再引入单独 Key，同一 Session 通过“原始文件名 + 文件字节”得到的 Blob Hash 去重，
   同名同内容返回首次 Attachment。不同 Session 仍建立独立 Attachment 并可复用同名同内容的物理正文。

因此合法状态包含“已属于 Session、但尚未被任何 Message 引用”的 Attachment。
它不是 staging 或异常数据，本版本不自动回收。

## 传输方向

- Runtime Host 统一使用 HTTP：默认只启用本地 loopback HTTP；后续可选远程 HTTPS
  默认关闭，如显式启用则共用同一套 Command、SSE 和 Streaming Upload API；
- 附件通过独立 HTTP 路由流式传输文件字节，不在 Command 中传 Base64、字节数组
  或客户端本地源路径；
- 项目尚未对外稳定发布，v0.11.0 不保留 Unix Socket 与 HTTP 双轨。

## 明确遗留与非目标

- 定时清理未提交暂存文件、已删除 Session 的附件和无 Session 引用的物理内容，本版本暂不实现，
  作为后续遗留项；
- v0.11.0 不因为消息裁剪或历史重新输入而自动清理 Session 附件；
- v0.11.0 不建立正式的通用权限模型、审批流程或 Shell 沙箱；
- 附件不直接作为多模态内容发送给模型；文本、图片、音频等均按“模型通过工具按需读取”处理；
- 不实现 Artifact、产物卡片或产物版本历史。

## 讨论收口

上述已确认功能语义进入归档的 [`v0.11.0 功能设计`](../versions/v0.11.0/功能设计.md)；数据表、
Blob/稳定视图、HTTP 通信、上传一致性和正式 Host 验证进入
[`v0.11.0 技术方案`](../versions/v0.11.0/技术方案.md)。Workspace Instructions 自动注入、格式专用

待补的设计空缺。
