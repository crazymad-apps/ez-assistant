# shell 后台进程存活机制调研（detached 为何被回收）

- 记录日期：260826
- 状态：待评估
- 来源：在本地排查「shell 工具以 detached 方式启动 Godot 编辑器，工具调用结束后编辑器进程仍被回收」问题；对 `ez-assistant` 本地实现（`crates/agent-tools-local`）的只读源码调研
- 目标版本：待定

## 一、原始内容

### 1.1 问题现象

用 shell 工具启动一个长驻 GUI 应用（Godot 编辑器），希望它在工具调用返回后保持运行：

- 用默认（`managed`）模式：进程随工具调用结束立即被回收；
- 改用 `detached` 模式 + 后台化（`nohup ... >日志 2>&1 &`）：进程仍在工具调用结束时被回收；
- 再把后台进程的标准输入/输出/错误全部指向 `/dev/null`（`</dev/null >/dev/null 2>&1 &`）：依然被回收。

### 1.2 关键疑惑

`detached` 从字面和 Schema 描述（"后代允许脱离工具生命周期"）上看应当能存活，但实际不行。需要定位 ez-assistant 内部到底是如何管理"进程树生命周期"的，以及 `detached` 是否真正实现"脱离"。

## 二、调研结论（源码实锤）

结论一句话：**`detached` 并非真正脱离进程组；只要后台进程仍持有 shell 的 stdout/stderr 管道，就会在输出结算超时（`TimedOut`）分支被 `terminate_and_wait` 连同整个进程树一起清掉。**

### 2.1 包装层：`crates/agent-tools-local/src/process.rs`

| 模式 | 入口 | 关键差异 |
| --- | --- | --- |
| `Managed` | `spawn()` | `KillOnDrop` + `ProcessGroup::leader()`（unix）/ `JobObject`（win） |
| `Detached` | `spawn_detachable()` | **去掉 `KillOnDrop`**，但仍建立 `ProcessGroup::leader()` |

实现：

```rust
fn spawn_wrapped(command: Command, kill_on_drop: bool) -> std::io::Result<ManagedChild> {
    let mut command = CommandWrap::from(command);
    if kill_on_drop {
        command.wrap(KillOnDrop);
    }
    #[cfg(unix)]
    command.wrap(ProcessGroup::leader());
    #[cfg(windows)]
    command.wrap(JobObject);
    command.spawn()
}
```

> 注意：`detached` 去掉的仅是 `KillOnDrop`（drop 时不主动杀），**并没有脱离进程组**。子进程仍在同一个 `ProcessGroup` 里，这是后续能被"整组清理"的前提。

### 2.2 执行层：`crates/agent-tools-local/src/shell.rs` 的 `run()`

父进程（`/bin/sh`）退出后的分支：

```rust
match process_completion {
    ProcessCompletion::Exited(status) => {
        if request.process_mode == ShellProcessMode::Managed {
            process::terminate_and_wait(&mut child)   // Managed：清理整棵树
        }
        let output_completion = settle_output_until(   // 等待 stdout/stderr 管道 EOF
            stdout_task, stderr_task, output_task, deadline, &cancellation
        ).await?;
        match output_completion {
            OutputCompletion::Complete(output) => { drop(child); Ok(...) }   // 正常交接
            OutputCompletion::TimedOut(output) => {
                process::terminate_and_wait(&mut child)  // 关键：超时 → 杀进程树！
                Err(ShellToolError::TimedOut { ... })
            }
            OutputCompletion::Cancelled => { process::terminate_and_wait(&mut child); ... }
        }
    }
    ...
}
```

- **Managed**：父进程一退出就 `terminate_and_wait`，后台后代必死。
- **Detached（正常路径）**：父进程退出后**不杀**，转去 `settle_output_until` 等待输出管道读到 EOF；若读到 EOF 则 `drop(child)`，此时进程组被释放，后台后代可存活。
- **Detached（超时路径）**：若输出管道在 `deadline` 内**没有 EOF**，`settle_output_until` 返回 `TimedOut`，随后**仍会执行 `terminate_and_wait(&mut child)` 清掉整个进程组**，并向上报 `timeout` 错误。

### 2.3 输出结算：`crates/agent-tools-local/src/shell/output.rs`

`settle_output_until` 带有 `deadline`，带 `biased` 的 `tokio::select!`：

```rust
tokio::select! {
    biased;
    _ = cancellation.cancelled() => { ...; Ok(OutputCompletion::Cancelled) }
    _ = sleep_until(deadline) => { ...; Ok(OutputCompletion::TimedOut(...)) }
    output = &mut settle => output.map(OutputCompletion::Complete),
}
```

即：**只要输出管道未在 deadline 内关闭（EOF），必然落入 `TimedOut`**。

### 2.4 为什么 `nohup ... >日志 2>&1 &` 救不了

即使显式把后台进程的 stdout/stderr 重定向到日志文件，后台进程（尤其像 Godot 这种 GUI 程序）**fork 出的后代进程仍可能继承原 shell 的 stdout/stderr 管道句柄**。只要管道还有一个写端未关闭，`settle_output_until` 就读不到 EOF；等 `deadline` 一到，回到 `TimedOut` 分支 → `terminate_and_wait` 把整个 `ProcessGroup`（含 Godot）杀掉。

> 关键点：**`detached` 是否存活，取决于输出管道能否在 deadline 内关闭，而不是取决于是否用 `nohup` / 是否重定向到日志。**

### 2.5 真正能存活的做法

让后台进程**完全不进入当前 shell 的进程组**，从而使工具的清理逻辑够不到它。

在 macOS 上最可靠的方法是用 `open` 把 `.app` 交给 **LaunchServices / launchd** 独立派发：

```bash
open -n -a "/Applications/Godot4.7.app" --args --editor --path /path/to/project
```

实证结果：`open` 返回 0（无超时），在工具调用结束多个轮次后，Godot 编辑器进程仍存活（`ps` 可见），不再被回收。

## 三、对 ez-assistant 的影响与建议

### 3.1 语义澄清

当前 `detached` 的语义（"后代允许脱离工具生命周期"）与实际行为存在落差：

- **字面/Schema 表述**：似乎只要 `detached` 就会脱离。
- **实际行为**：`detached` 只在"父进程退出且输出管道顺利 EOF"时才真正交接（`drop(child)`）；一旦输出结算超时或取消，依旧整组清理。

建议在文档/注释中把 `detached` 的语义表述收敛为：**"detached = drop 时不主动 kill-on-drop，且输出管道在 deadline 内 EOF 时才交接给 OS；否则仍会整组清理"**。

### 3.2 能否让 `TimedOut` 分支对 `detached` 不清树？

一个可讨论的选项：在 `OutputCompletion::TimedOut` / `Cancelled` 分支，若 `process_mode == Detached`，**不对整个进程组执行 `terminate_and_wait`**，而是仅清理 shell 父进程并中止管道读取，将仍存活的后代留给 OS。

这需要权衡：
- 优点：`detached` 真正实现"脱离"，长驻进程（GUI、服务）在超时后仍存活。
- 风险：超时会吞掉本应被清理的孤儿进程；stdout/stderr 管道因仍有写端而无法关闭，输出任务需 `abort`，可能产生悬挂的管道读取任务。

### 3.3 与"长任务机制"既有输入的衔接
