## 四、架构与范围边界

### 4.1 依赖方向

- `agent-memory` 只依赖 Provider-neutral 基础类型和通用第三方库，不依赖 Tool、Core、
  Runtime、Provider 或应用。
- `agent-tools` 依赖 `agent-memory`，提供五个标准工具壳；`agent-core` 仍只运行普通 Tool
  Loop，不识别记忆工具名称或类型。
- `memory-demo` 是顶层验证宿主，私有持有 JSON Store、JSON RecallSource、Session、Journal
  和 Provider 装配，不存在 `agent-memory-local`。
- `assistant-runtime` 的源码和直接 manifest 没有变化。由于它依赖 `agent-core`，依赖树会经
  `agent-core -> agent-tools -> agent-memory` 包含 `agent-memory`；这是公共工具能力带来的
  预期传递依赖，不代表 Runtime 建立了 Memory SPI、存储或编排逻辑。
- `assistant-protocol` 与 Desktop 没有代码或直接依赖变更，Demo 私有 DTO 未进入产品协议。

### 4.2 明确排除项

以下能力没有进入 v0.5.0：

- 正式 Runtime 和桌面应用的 Session、存储、权限、调度或 UI 接线；
- 内置本地 Memory Adapter 或可复用的 Demo 文件格式；
- 自动观察、自动提炼、自动写入、后台整合、自动淘汰；
- Embedding、向量数据库、复杂检索规划或动态工具定义；
- 跨进程 Store writer 协调和产品级数据迁移契约。

### 5.4 Memory Demo 真实 Provider 闭环

M6 在系统临时数据目录执行真实 `memory-demo chat`，实际完成：

1. 从默认 `demo_records` 召回并展示稳定来源 reference；
2. 调用标准 Pinned 工具写入本地 `pinned-memory.json`；
3. `/state` 对照旧 Session 的冻结 Prompt 与最新 Store；
4. `/new` 创建 Session 并读取最新 Store；
5. 退出进程后使用 `--session` 恢复旧 Session，继续使用原 Prompt 快照；
6. 本地 `sessions/<id>.json` 与 `recall-records.json` 可直接审阅。

用户已实际启动并验证 Demo，确认功能无问题。完整记忆正文和 credential 未写入本文。

## 六、代码审查与实现偏差

- 审查 Pinned Store 与 Demo Journal 的原子提交点、取消边界和锁持有范围，失败不会把未落盘
  状态发布为成功状态。
- 审查 XML/JSON 转义、显式容量、错误脱敏、Source 超时、确定排序、去重、截断和部分失败；
  未发现 blocker 或 major。
- 五个标准工具均使用固定 Schema、模型显式 `limit`、resolved arguments、通用授权事实和
  既有 Dispatcher；没有增加 Memory 专用授权器或旁路。
- 开发计划原“正式 Runtime、Protocol 和 Desktop 的代码及依赖无变化”在验收时精确化为
  “源码与直接依赖无变化”。Runtime 的预期传递依赖已在 4.1 明示，不改变功能范围。
- Demo JSON Store 只保证单进程单 writer；这是已确认边界，不提升为公共 Adapter 或产品契约。
