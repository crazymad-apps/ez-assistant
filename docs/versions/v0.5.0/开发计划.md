## 二、实施原则

1. M0 → M7 严格顺序实施。每个里程碑完成实现和验证后标记为 `🟨 待确认`并停止，获得
   用户明确确认后才进入下一里程碑。
2. 开发计划确认只授权开始 M0，不授权连续执行后续里程碑。
3. 先建立 workspace、依赖和长期模块约束，再迁移公共 Prompt API；公共契约改动必须在
   所属里程碑同步迁移全部生产者、消费者和测试，不保留新旧并行字段。
4. Core 不增加 Memory SPI、召回阶段或专用状态机；Pinned 与 Recall 都通过既有 System
   Prompt 和普通 Tool Loop 工作。
5. `agent-memory` 只承载实现无关的领域类型、能力契约、快照渲染和协调逻辑，不访问本地
   文件、数据库、远程服务或 Runtime。
6. 不创建 `agent-memory-local`。JSON Store、JSON RecallSource、Session 文件和原子写入
   全部留在 `tools/memory-demo` 私有实现，未来 Runtime/应用层自行选择正式 Adapter。
7. Pinned Memory 的所有容量限制显式配置；超限明确失败，不自动观察、提炼、整合、摘要、
   淘汰或写入。
8. `recall_memory` 保持固定 Schema；Source 可见性由 System Prompt/Skill 表达，多来源选择、
   超时、去重、排序和降级由工具背后的具体实现承担。
9. 自动测试使用 fake model、受控 Source 和 tempfile，不访问用户真实目录、应用数据库或
   网络，不记录完整敏感记忆。
10. 真实 Provider 人工验证只在 M6/M7 明确执行；credential 只在 `chat` 入口加载，不进入
    配置展示、日志、错误或测试 fixture。
11. `assistant-runtime`、`assistant-protocol` 和 `apps/desktop` 保持零代码、零依赖变化；
    只允许同步长期模块职责文档。
12. 每个里程碑开始前重新核对工作树和对应 Rust/module 规范；发现技术方案与真实实现不符
    时停止扩大改动，先修订设计并重新确认。
13. 每个里程碑完成后提供精简导读，只挑选影响公共契约、核心语义、依赖边界、安全性或后续
    实现的代码与偏差供用户 Review；若本阶段没有重要 Review 点，必须直接说明，不为流程完整
    人为制造确认问题。用户确认里程碑后才继续下一阶段。

### 前置依赖

M0 已确认。

  快照构造压缩请求。
- 机械迁移 agent-core、agent-context、agent-provider、agent-testkit、runtime-harness、

- Rolling Summary 压缩请求与正常请求使用同一完整 system 前缀。

## 七、M2：Pinned Memory 领域、Store 契约与 XML 快照

### 目标

在 `agent-memory` 建立实现无关的置顶记忆领域、显式容量规则、最小 Store trait 和确定性
System Prompt Part 渲染，不实现任何本地持久化。

### 前置依赖

M1 已确认。

### 实施内容

- 实现 PinnedMemoryId、PinnedMemoryCategory、MemoryPropertyValue、Entry、Draft 和 Patch。
- 字符串/数字属性使用 BTreeMap；拒绝空白、控制字符、非法数字、非法 Patch 和超限输入。
- 实现必传 `PinnedMemoryLimits`，覆盖条目、正文、Category、属性和最终快照字节上限；
  library 不注入隐藏默认。
- 定义 boxed-future `PinnedMemoryStore` 的 list/pin/update/unpin 契约及稳定错误分类。
- 定义 `PinnedMemorySnapshotInput` 与只保存最终字符串的 `PinnedMemorySnapshot`。
- 使用 quick-xml Writer 输出固定 `<pinned_memories>` 结构；Entry 按 `(category, id)` 排序，
  property 按键排序，字符串和 attribute 全部安全转义。
- 属性以 `<property name type>` 元素表达，不把业务属性键当作 XML name。
- Snapshot 不提供反向解析为 Entry 的 API，也不包含 store revision、Slot、selector 或配置。

### 自动测试或人工核对

- 所有 ID、Category、正文、属性值、属性键和 limits 边界可逐项验证。
- 属性只接受字符串或 JSON number，拒绝 boolean、object、array 和 null。
- pin Draft 无 ID；Patch 至少修改一项，空 attributes 与未提供语义不同。
- Store trait 可由 mini fake 实现，错误能区分 NotFound、CapacityExceeded、Corrupt、Io、
  InvalidInput 和 Cancelled。
- 相同输入始终产生字节相同 XML；输入顺序变化不影响排序结果。
- `<>&\"'`、Unicode、空 entries/properties 和快照超限均有测试。
- `agent-memory` 不访问文件系统，不依赖 Tool/Core/Runtime。

### 验证

```bash
cargo test -p agent-memory pinned
cargo test -p agent-memory snapshot
cargo test -p agent-memory
cargo clippy -p agent-memory --all-targets --all-features -- -D warnings
cargo fmt --all --check
```

### 完成判定

- Pinned Memory 的领域、Store 替换边界和 XML 快照可独立使用；
- Snapshot 只保存成品文本，Store trait 不绑定本地实现；
- 尚未注册模型工具或创建 Demo 文件。

## 八、M3：Memory Recall、RecallSource 与协调实现

### 目标

建立实现无关的召回请求、来源结果、错误、RecallSource 和统一 MemoryRecall 能力，并完成
一个确定、可取消、可部分降级的具体多 Source 协调实现。

### 前置依赖

M2 已确认。

### 实施内容

- 实现 RecallSourceId、MemoryRecallRequest/Response、RecallSourceRequest/Response、
  RecallItem、Origin、Failure 和稳定错误分类。
- 定义 boxed-future `RecallSource` 和 `MemoryRecall` trait；Source 只暴露稳定 ID，不持有
  模型可见性、Prompt、Skill、Session 或授权对象。
- 实现 `CoordinatedMemoryRecall`，构造时校验 Source ID 唯一、默认 Source 存在和所有
  timeout/数量/字节配置。
- sources 省略时使用显式默认集合；指定未知 Source 明确失败，不回退默认 Source。
- 并发调用选中 Source，与取消和单 Source timeout 竞争；按构造顺序收集，消除完成顺序
  不确定性。
- 按 Source 内部排名轮转合并；对正文与 attributes 完全相同的项合并 origins，不进行
  主观语义合并或跨 Source score 归一。
- 部分失败返回 items + failures；全部失败返回结构化 AllSourcesFailed；至少一个 Source
  成功但没有匹配是正常空结果。
- Source 输出统一由协调器附加 source_id，Source 不能伪造其他来源。

### 自动测试或人工核对

- 默认、显式、未知、重复、空 Source 和最大 Source 数分别覆盖。
- 并发快慢顺序变化不影响最终 items 顺序。
- 精确重复合并全部 origins，属性不同不误合并。
- limit 截断、truncated、单条超限和 Source 违反契约均有稳定结果。
- 单个失败、多个失败、全部失败、timeout 和 cancellation 可确定性验证，不使用 sleep
  猜测顺序。
- 无 Source 时由上层不注册工具；Coordinator 构造不产生隐藏 No-op。
- `agent-memory` 仍不依赖 Tool/Core/Runtime 或具体数据源。

### 验证

```bash
cargo test -p agent-memory recall
cargo test -p agent-memory coordinator
cargo test -p agent-memory
cargo clippy -p agent-memory --all-targets --all-features -- -D warnings
cargo fmt --all --check
```

### 完成判定

- 单 Source 替换边界和多 Source 协调行为均可独立验证；
- 结果天然携带来源，部分失败不破坏其他有效结果；
- 尚未提供模型工具或 Demo Source。

## 九、M4：五个标准记忆工具壳与 Agent Loop 契约验证

### 目标

把 Pinned Memory 和 Memory Recall 接入既有类型化工具体系，证明 Core 无需任何 Memory
专用分支即可完成增删改查、召回、授权、Recorder 和多轮继续。

### 前置依赖

M3 已确认。

### 实施内容

- `agent-tools` 增加对 `agent-memory` 的依赖和 `standard::pinned_memory/recall_memory`。
- 实现 `pin_memory`、`update_pinned_memory`、`unpin_memory`、
  `list_pinned_memories` 四个固定标准工具壳。
- 工具描述明确 Store 修改只影响未来 Session，当前会话使用 Tool Result；list 返回最新
  Store，不宣称等于当前 Prompt 快照。
- 实现固定 `recall_memory`：query 非空、limit 必传且无默认、sources 可选；maximum 进入
  模型可见描述，不动态枚举 Source。
- resolve 只做结构、limits、ID 和 Patch 校验，不访问 Store/Source；execute 委托能力。
- Pinned/Recall 错误映射到稳定 ToolError；部分失败返回成功 JSON，全部失败使用结构化
  Execution details。
- 五个工具使用现有 GeneralAuthorizationFacts、Registry、Dispatcher、Guardrail、
  Authorizer 和 Recorder 顺序，不新增 Core 类型或 AgentEvent。
- `agent-testkit` 增加 FakePinnedMemoryStore、ScriptedRecallSource/MemoryRecall 和确定性
  观察能力；`agent-tools` 自身单测继续使用 crate 内 mini fake，避免依赖环。
- 增加 Engine Harness 场景，证明模型调用标准记忆工具后通过普通 Tool Result 继续回答。

### 自动测试或人工核对

- 五个名称、描述、Schema 和 Tool Result JSON 稳定，Registry 重名仍拒绝。
- recall limit 必传、没有 schema default；超 maximum、空 query 和重复 sources resolve 失败。
- pin/update/unpin/list 的参数、空 Patch、NotFound、CapacityExceeded 和取消正确映射。
- resolve 阶段不调用任何能力方法；授权拒绝时 Store/Source 无副作用。
- Pinned 修改成功后，同一 ExecutionSpec 的 system_prompt 字节保持不变。
- list 返回 fake Store 最新状态；Recall 结果不会调用 Pinned Store 或自动写入。
- 部分 Source 失败仍是成功 Tool Result，全部失败是错误 Tool Result，call ID 配对正确。
- Core 源码和事件中没有 Memory 专用分支。

### 验证

```bash
cargo test -p agent-tools memory
cargo test -p agent-testkit memory
cargo test -p agent-core -p agent-tools -p agent-testkit
cargo clippy -p agent-core -p agent-tools -p agent-testkit \
  --all-targets --all-features -- -D warnings
cargo fmt --all --check
```

### 完成判定

- 五个标准工具通过唯一类型化 resolve/execute 路径工作；
- 普通 Agent Loop 完成记忆工具多轮闭环，Core 不感知 Memory；
- 尚未实现任何真实文件 Store、RecallSource 或 Session。

## 十、M5：Memory Demo 私有文件能力与 Session 快照生命周期

### 目标

在 Memory Demo 内私有实现真实、可重启验证的 JSON Pinned Store、JSON RecallSource、
Session 文件和 Journal，先验证数据与快照生命周期，不建设 CLI Agent 对话。

### 前置依赖

M4 已确认。

### 实施内容

- 在 `tools/memory-demo` 私有实现 atomic_json、DemoPinnedMemoryStore、DemoRecallSource、
  SessionRecord 和 Journal；这些类型不从 binary 导出。
- Pinned 文件使用版本、next_id 和 entries；不存在时为空，损坏、重复 ID、版本不兼容或
  超限时构造失败且不覆盖原文件。
- pin/update/unpin 在进程内 Tokio Mutex 中串行；在副本上修改并校验，通过同目录
  NamedTempFile write/flush/sync/persist 成功后才替换内存状态。
- ID 使用持久化单调序号，删除不回收；同一文件只允许一个 Demo writer 实例。
- Recall 文件使用版本化 records；每次 recall 重新读取，按 query term 命中数和 reference
  确定排序，输出受控模型可读记录。
- Session 文件保存完整 SystemPromptSnapshot 和 ConversationSnapshot；创建先读取 Store、
  渲染 Pinned Part、组合说明并原子持久化，恢复只读取 Session 成品快照。
- Demo 私有 Recorder 保持 pending/completed Tool Exchange 顺序，Session 文件不暴露未配对
  Tool Call/Result。
- 为 Session create/restore/new/branch/continuation 提供私有函数；branch/continuation 复制
  原 Prompt，只有 create/new 读取最新 Store。

### 自动测试或人工核对

- Pinned 文件不存在、首次写入、正常重启、损坏 JSON、错误版本、重复 ID 和超限。
- pin/update/unpin/list、稳定 ID、不回收序号和并发调用串行。
- 注入 write/persist 失败后旧内存状态和旧文件仍可读取。
- DemoRecallSource term 匹配、attributes 匹配、稳定排序、每次重读、空结果和 InvalidData。
- 新 Session 使用最新 Store；Store 修改不改变现有 Session 快照；新 Session 看到最新状态。
- 销毁并重建 Demo 对象后恢复原 Session 快照，不读取最新 Store 重建。
- branch/continuation 继承原快照；缺失、损坏或不兼容 Session 明确失败。
- 所有文件测试只使用 tempfile，不访问用户目录。

## 十一、M6：Memory Demo CLI 与真实 Agent 记忆闭环

### 目标

完成独立 CLI 验证宿主，装配真实 Provider、五个标准工具、默认/失败 Source、私有 Journal
和 Session，供开发者人工验证模型对两类记忆的理解。

### 前置依赖

M5 已确认。

### 实施内容

- 实现 `memory-demo chat --data-dir <DIR> [--session <ID>]`，只有 chat 加载 `.env` 和
  OpenAI-compatible/DeepSeek 配置。
- 未指定 ID 创建并先持久化新 Session；指定 ID 恢复成品快照和规范对话。
- 首次数据目录初始化创建带少量可审阅记录的 recall 文件，已存在文件绝不覆盖。
- 固定装配 `demo_records` 默认 Source 与受控 `failing_demo`；System Prompt 说明 Source ID
  和用途，工具 Schema 不动态变化。
- 注册四个 Pinned 工具和 `recall_memory`；使用显式 AllowAllAuthorizer 仅表示 Demo
  选择，不改变 Core 授权机制。
- 实现一次只运行一个 AgentExecution 的 CLI 循环；用户消息先落 Journal，Core 最终消息由
  Demo 追加，Tool Exchange 使用私有 Recorder。
- 实现 `/state`、`/new`、`/cancel`、`/quit`；活动 Run 中拒绝 `/new`，quit 先取消并等待
  Core 收敛。
- `/state` 展示 Session ID、创建/恢复来源、Prompt Parts、快照 Pinned 文本和最新 Store，

- 默认 Source、显式 `demo_records`、显式 `failing_demo` 和两者组合结果均可观察来源与失败。
- Recall Tool Result 不自动进入 Pinned Store；Pinned 内容不需要重复 recall。
- `/cancel`、`/quit` 和 Recorder 失败均保持 Tool Call/Result 配对与唯一终态。
- `--help` 和全部自动测试不加载 credential、不访问网络。

## 十五、实施顺序结论

实施顺序固定为：

```text
M0 工程与长期边界
→ M1 冻结 Prompt
→ M2 Pinned 领域与快照
→ M3 Recall 与 Source
→ M4 标准工具闭环
→ M5 Demo 私有持久化与 Session
→ M6 CLI 真实 Agent 闭环
→ M7 全量回归与验收准备
```

该顺序先固定底层依赖和 Prompt 生命周期，再实现两个记忆子域，随后通过工具接入 Core，最后
在 Demo 上增加私有存储和应用编排。任何阶段发现必须修改正式 Runtime、引入产品数据库、
改变 Core 执行状态机或增加自动学习链路时，立即停止当前里程碑并回到设计阶段重新确认。
