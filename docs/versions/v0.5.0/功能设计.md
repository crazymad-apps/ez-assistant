## 二、背景与版本目标

ez-assistant 面向通用桌面 AI 助手，记忆能力不能只等同于编程项目指令或历史会话搜索。
少量、长期有效的信息需要稳定地伴随新会话；大量历史和外部信息则应在需要时临时召回，
不能全部常驻于模型上下文。

本版本建立两个语义独立的记忆子域：

- **Pinned Memory**：保存少量置顶记忆，在新建会话时冻结为 System Prompt 的固定部分。
- **Memory Recall**：通过普通工具按需检索历史或外部信息，并将结果临时带入当前上下文。

版本目标如下：

1. 建立 Pinned Memory 的持久化、会话快照和模型工具闭环。
2. 区分新建会话与恢复会话，统一 instructions 与 Pinned Memory 的冻结生命周期。
3. 以 `recall_memory` 普通工具作为 Memory Recall 的模型入口。
4. 允许工具背后接入一个或多个 RecallSource，并隔离数据源差异与协调复杂度。
5. 通过独立 Memory Demo 验证上述能力，不在本版本接入正式 Runtime 和应用层。

## 三、版本边界

### 3.1 本版本包含

- Pinned Memory 的条目语义、持久化边界、确定性渲染和内置工具。
- 新建、恢复、继续、压缩续接、分支以及重置会话时的 Prompt 快照语义。
- `recall_memory` 工具及其背后的统一召回能力。
- 可替换 RecallSource 和多来源协调的最小边界。
- 独立 Memory Demo 及确定性测试支持。

### 3.2 本版本不包含

- 正式 `assistant-runtime`、`assistant-protocol` 和桌面应用接入。
- 正式 Runtime 的 Session、Run、持久化或迁移契约。
- 特定数据库、向量库、Embedding 服务或远程记忆供应商绑定。
- 当前会话 Prompt 的热更新。
- 自动观察对话、自动提炼记忆、后台整合和淘汰等学习机制。
- 自动将召回结果、历史消息或工具结果写入 Pinned Memory。
- 为尚无替换需求的协调算法建立公共 Orchestrator 抽象。

Demo 可以私有实现最小 Session 和持久化流程，但这些 DTO 与交互语义不构成产品契约。

## 四、Pinned Memory

### 4.1 定位

Pinned Memory 保存数量较少、长期有效、值得在每个新会话中直接提供给模型的信息，例如
用户偏好、稳定约束和重要背景。它不是一个需要检索才能获得的历史资料库。

Pinned Memory 在 System Prompt 中使用独立、明确的区域，说明以下语义：

- 其中的信息已经提供给模型，不需要再次召回。
- 当前对话中的明确更正优先于旧的置顶记忆。
- 当前会话内的 Pinned Memory 快照保持不变。
- 对置顶记忆的修改只影响未来新建会话。

### 4.2 持久状态与会话快照

Pinned Memory 区分三个责任阶段：

1. 持久 Store 保存当前最新的置顶记忆，供工具读写和未来的新会话读取。
2. 新建会话使用结构化初始化数据生成完整的 System Prompt Part。
3. 会话只保存并使用确定性渲染后的最终快照，不在恢复时根据最新 Store 重新生成。

每条置顶记忆具有稳定标识、开放字符串形式的归类、正文和可扩展属性。属性用于帮助模型
理解记忆的业务含义以及可能关联的外部工具，只允许字符串或数字值；Core 不解释属性的
业务语义，也不把属性作为授权依据。

快照包含由上层宿主提供的整体说明。该说明描述整个 Pinned Memory 区域的模型语义，不是
普通记忆条目，不能通过置顶记忆工具修改。条目、属性和整体说明必须以稳定顺序正确转义，
保证相同输入得到相同 Prompt 内容。

### 4.3 模型工具

Pinned Memory 使用语义明确的普通工具：

- `pin_memory`：保存一条以后新会话始终可见的信息。
- `update_pinned_memory`：修改一条已经置顶的信息。
- `unpin_memory`：取消一条置顶信息。
- `list_pinned_memories`：查看持久 Store 中最新的置顶信息。

工具修改持久 Store，但不修改当前会话快照。工具调用和结果已经存在于当前上下文，因此
模型可以在本次会话继续使用刚刚变更的信息。`list_pinned_memories` 返回 Store 的最新状态，
同样不会刷新当前快照。

置顶工具沿用普通工具的注册、策略和审计机制，不建立绕过 v0.4.0 安全边界的特殊通道。
外部可检索数据源若支持写入，应提供符合自身业务语义的工具，不复用置顶记忆工具。

## 五、Memory Recall

### 5.1 定位与入口

Memory Recall 用于从历史会话、用户笔记、项目资料或远程服务等大量信息中按需查找与当前
任务相关的少量内容。召回结果只作为当前工具调用产生的临时上下文，不会自动变成 Pinned
Memory，也不会修改会话 Prompt 快照。

Memory Recall 通过固定、简单的 `recall_memory` 普通工具进入 Agent Loop。Core 只看到
标准 Tool Call 和 Tool Result，不增加召回专用阶段、状态机或执行路径。

### 5.2 RecallSource

`RecallSource` 表示一个可检索数据源的适配器，例如历史会话、本地笔记、项目资料或远程
记忆服务。它负责把具体数据源的搜索能力转换为统一的召回语义，但不要求直接拥有数据。

采用 `RecallSource` 命名，避免与项目已有的 Model Provider 混淆。同一个 Source 可以查询
一个数据源中的多类数据，多个 Source 也可以针对同一底层存储提供不同的业务检索能力。

### 5.3 Source 对模型的可见性

RecallSource 始终存在于实现侧。LLM 是否知道某个 Source、是否能在 Tool Call 中指定它，
取决于当前应用的 System Prompt 或已注入 Skill 是否提供了该 Source 的标识和用途。

`recall_memory` 不为不同 Source 动态重建工具定义，也不增加独立的工具装配阶段。工具保持
固定语义：模型可以省略 Source，让背后的实现选择默认数据源；模型也可以指定当前 Prompt
或 Skill 已告知的 Source。未知、未启用或不可用的 Source 必须返回明确结果，不能被静默
替换成其他数据源。

Source 的模型可见性与实际访问授权相互独立。模型知道一个 Source 存在，不代表调用一定
获得授权。

### 5.4 背后的实现责任

`recall_memory` 只负责表达模型的检索意图并返回统一结果。以下复杂度属于工具背后的具体
召回实现：

- 管理已接入的 RecallSource 和默认数据源；
- 调用一个或多个 Source；
- 合并、去重、排序和截断结果；
- 隔离单个 Source 的失败；
- 在可以返回有效部分结果时，不因个别 Source 失败而破坏 Agent 主循环。

所有召回结果必须天然携带安全、可理解的来源信息，使模型能够判断内容来自哪里。来源内部
的数据库表名、文件路径、服务地址或认证信息不因此暴露。

首期不引入职责重叠的 Memory Service，也不把多来源协调器抽象为公共 trait。工具背后只需
一个统一召回能力；是否使用单一 Source 或具体的多来源协调实现，对 Core 和工具调用方透明。

## 六、会话 Prompt 生命周期

Pinned Memory 快照与现有 instructions 具有相同生命周期：两者都是创建会话时确定、恢复
会话时原样加载的持久 Prompt 数据。Core 只消费最终的冻结状态，不负责判断当前是在新建
还是恢复会话，也不持有产品层 Session ID。

不同会话操作遵循以下原则：

| 场景 | Prompt 状态来源 | 是否读取最新 Pinned Memory Store |
| --- | --- | --- |
| 新建会话 | 使用当前 instructions 和当前 Store 生成并持久化 | 是 |
| 恢复或进程重启后重建会话 | 加载原会话保存的精确 Prompt 状态 | 否 |
| 同一会话继续执行 | 继续使用原 Prompt 状态 | 否 |
| 上下文压缩后的 continuation | 继承原 Prompt 状态 | 否 |
| 会话分支或 fork | 继承源会话 Prompt 状态 | 否 |
| 用户明确新建或重置 Session | 生成新的 Prompt 状态 | 是 |

上层宿主应明确区分“使用结构化输入创建新状态”和“使用持久化状态恢复”两条路径，不能依靠
可选字段猜测调用语义。创建会话时应先得到并持久化完整 Prompt 状态，再开始首个 Run。

恢复时如果快照缺失、损坏或版本不兼容，应返回明确错误或走显式迁移，不能静默读取最新
Store 重建，否则会改变历史会话语义。具体序列化与迁移方式留到技术方案及正式 Runtime
设计中确定。

## 七、Core 与上层边界

- Core 消费冻结的 Prompt 状态，通过既有工具循环执行置顶记忆和召回工具。
- Core 不直接读写 Pinned Memory Store，不管理 RecallSource，也不创建或恢复产品 Session。
- Pinned Memory 的持久化和快照生成属于记忆能力及其上层宿主的责任。
- RecallSource 的接入、多来源协调和容错属于 `recall_memory` 背后的实现责任。
- 正式 Runtime 未来负责产品会话 Prompt 状态的创建、持久化和恢复，本版本不修改它。
- 独立 Memory Demo 可以组织临时会话和真实记忆实现，但不建立正式应用契约。

## 八、对照项目结论

OpenCode 当前主要提供会话历史、压缩、项目或用户 instructions 和扩展 Hook，没有一套独立
的一等长期记忆系统。其做法适合作为编程 Agent 的上下文参考，但不足以覆盖通用桌面助手的
持久用户记忆目标。

Hermes 的分层方案说明：少量人工维护的常驻信息可以在会话初始化时冻结进 System Prompt；
大量信息则应通过外部检索、会话搜索或后台整理按需进入上下文。本版本采用这种分层原则，
但不照搬其具体 Provider、文件格式、字符串协议或 Runtime 耦合方式。

## 九、当前已确认的设计结论

1. Pinned Memory 与 Memory Recall 是两个语义独立的子域。
2. Pinned Memory 是固定 System Prompt Part，需要真实持久化并冻结到会话。
3. 置顶记忆修改不改变当前会话快照，只影响未来新建会话。
4. `list_pinned_memories` 查看最新 Store，但不刷新当前快照。
5. 置顶记忆保留稳定标识、开放归类、正文和字符串或数字扩展属性。
6. 初始化阶段保留结构化条目，最终快照只保存精确渲染文本及整体说明。
7. instructions 与 Pinned Memory 一样属于会话冻结 Prompt 状态。
8. 新建会话读取最新 Store；恢复、继续、压缩续接和分支继承原快照。
9. Memory Recall 只通过普通 `recall_memory` 工具进入 Core。
10. `RecallSource` 表示可检索数据源的适配器，避免使用 Memory Provider 命名。
11. Source 是否对 LLM 可见、可指定，由 System Prompt 或 Skill 决定。
12. `recall_memory` 保持固定、简单，不增加动态工具定义或独立装配阶段。
13. 多来源选择、合并和失败降级属于工具背后的实现。
14. 所有召回结果必须携带来源信息，且不会自动进入 Pinned Memory。
15. 当前不引入 Memory Service 和公共 Orchestrator trait。
16. 本版本不改正式 Runtime 和应用层，可以使用独立 Demo 验证。

## 十、技术方案约束

技术方案必须基于真实仓库和依赖核查落实以下要求，不得改变本功能设计的能力语义：

- Memory Demo 私有实现能够跨进程重启保存数据的真实本地 Pinned Store；修改必须具备明确
  的原子性和并发语义，失败时不能留下被当作成功状态读取的部分结果。正式实现由未来
  Runtime 或应用层决定，本版本不提供内置本地 Adapter。
- Pinned Memory 的容量限制必须显式配置；超过限制时返回明确错误，本版本不自动淘汰、
  摘要或合并已有记忆。
- Pinned Memory 快照采用确定性、安全转义的标记结构；相同输入必须产生相同内容，缺失、
  损坏或不兼容的快照必须明确失败，不能静默使用最新 Store 重建。
- `recall_memory` 使用固定工具定义，并要求模型显式给出返回数量；实现不得使用模型不可见
  的默认结果数量制造无法预期的大段 Tool Result。
- 默认 Source 集合由上层显式配置；模型指定未知、未启用或不可用的 Source 时必须返回明确
  结果，不能自动改查其他 Source。
- 多来源召回必须保留每条结果的来源，并允许成功结果与个别 Source 的失败信息同时返回；
  排序、去重、截断、超时和取消规则必须确定且可测试。
- Memory Demo 至少装配一个可真实查询的本地 RecallSource 和一个可控制失败的 RecallSource，
  用于验证默认召回、显式 Source、来源追溯和部分失败；不接入正式远程产品服务。
- 技术方案必须核查现有 `ExecutionSpec.instructions`、System Prompt 组装、Tool SPI、策略、
  Recorder 和上下文压缩路径，给出兼容演进方式并保持已有调用方与测试可迁移。
- 公共类型、请求与结果契约、crate 归属、持久化格式和 Demo 交互只在技术方案中确定；
  它们必须服务于本文已经确认的行为，不扩大版本范围。

## 十一、风险与兼容性

- **Prompt 稳定性**：错误地刷新或重建 Pinned Memory 会改变历史会话语义并破坏缓存；以
  冻结成品快照、恢复时原样加载和明确失败保证一致性。
- **敏感信息访问**：置顶记忆和 RecallSource 可能包含用户隐私；继续通过普通工具策略控制
  调用，Source 可见性不替代实际授权，结果不暴露实现路径、服务地址或认证信息。
- **上下文噪声与膨胀**：召回结果过多会降低模型可用性；返回数量由模型显式请求，背后实现
  按确定规则排序、去重和截断，不进行无界返回。
- **外部来源不稳定**：单个 Source 可能超时或失败；保留来源级失败并继续返回其他有效结果，
  不把部分失败升级为 Agent Loop 整体失败。
- **既有 Core 契约兼容**：Prompt 状态会影响现有 instructions 和上下文组装；技术方案必须
  提供明确迁移路径，并用现有回归场景证明工具循环、压缩和 Provider 往返未被破坏。
- **产品持久化兼容**：正式 Runtime 尚未接入，本版本不承诺产品数据库和历史 Session 的迁移
  格式；Demo 私有持久化契约不得被视为正式产品契约。

## 十二、验收标准

开发计划必须覆盖以下可观察行为：

1. 新建会话读取当前 Pinned Memory Store；同一会话内修改置顶记忆后，快照保持不变。
2. 新建另一个会话可以看到 Store 的最新结果。
3. 旧会话可以列出最新 Store，但其 System Prompt 不发生变化。
4. 进程重启后恢复会话仍使用原始 Prompt 状态，而不是最新 Store。
5. Pinned Memory 的归类和扩展属性能以稳定、正确转义的形式提供给模型。
6. 模型能够通过普通 `recall_memory` 工具从默认或已知 Source 召回信息。
7. 召回结果携带来源，单个 Source 失败时其他有效结果仍可使用。
8. 召回结果只进入当前工具上下文，不改变 Pinned Memory 或会话 Prompt 快照。
9. Core 不产生记忆专用执行阶段，workspace 不产生正式 Runtime、Protocol 或桌面行为变更。
