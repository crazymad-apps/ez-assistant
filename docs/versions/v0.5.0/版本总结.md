## 三、形成的核心能力

- `SystemPromptSnapshot` 把有序 System Prompt Parts 提升为共享、可序列化的冻结值；Core、
  Context 和 Provider 全链路使用同一快照，压缩与多轮模型调用不会重新读取最新记忆。
- `agent-memory` 提供 Pinned Entry、显式容量限制、Store trait、确定性 XML 渲染、
  MemoryRecall、RecallSource 和具体多来源协调实现，不依赖 Core、Runtime、Provider 或应用。
- Pinned Memory 的新增、修改、取消置顶和查看，以及 `recall_memory`，均作为普通标准工具
  经过既有 Registry、resolve、Authorizer、Dispatcher、Recorder 和 Tool Result 流程。
- Recall 结果天然携带可信来源；协调器支持确定排序、精确去重、截断、超时、取消和 Source
  部分失败，不把单个数据源故障升级为整个 Agent Loop 故障。
- Memory Demo 以可直接审阅的本地 JSON 文件验证 Store、RecallSource、Session 和 Journal；
  修改 Store 不刷新当前 Session，恢复路径不按最新 Store 重建冻结 Prompt。

## 四、偏差与边界

- 正式 `assistant-runtime`、`assistant-protocol` 和 Desktop 源码与直接依赖没有变化，也未
  接入记忆存储、Session 或工具编排。Runtime 会经 `agent-core -> agent-tools ->
  agent-memory` 获得预期传递依赖，但不存在 Memory 专用运行阶段或 Runtime 耦合。
- 没有创建 `agent-memory-local`；Demo 的 JSON Store、RecallSource、Session、Journal、
  文件格式和 CLI 均为宿主私有实现，不是产品兼容契约。
- 自动观察、自动提炼、自动写入、后台整合、自动淘汰、Embedding、向量数据库、复杂检索
  规划和跨进程 writer 协调均未进入本版本。
- Provider crate 中独立的联网 ignored smoke 没有重复执行；真实 Memory Demo 已完成包含
  标准记忆工具的 Provider 端到端联调。Desktop/Tauri 未构建，因为产品代码与直接 manifest
  未修改。

## 五、遗留与后续入口

- `v0.6.0` 进入扩展性与可靠性主题；启动设计时重新评估 Provider、Tool、Memory Adapter
  边界，以及错误模型、背压、重试、事件一致性、并发安全、录制回放与故障测试。
- 正式 Runtime 如何装配 Pinned Store、RecallSource、权限和产品持久化，仍应在 Runtime
  版本中结合真实应用需求单独设计，不能直接提升 Demo 私有实现。
- 若未来引入自动学习、Embedding 或跨来源检索规划，应形成新的明确功能设计，不能扩张
  当前普通工具和数据源协调契约的职责。
- 归档没有执行 `git add`、`git commit` 或 `git push`；提交准备等待用户另行授权。
