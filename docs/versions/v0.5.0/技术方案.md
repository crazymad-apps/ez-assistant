## 二、现状核查

本方案基于 2026-08-03 当前仓库、`cargo metadata --format-version 1 --no-deps`、
`cargo tree -p agent-core --depth 2`、`cargo tree -p agent-tools --depth 2` 以及实际源码搜索
形成，不沿用尚未落地的历史设想。

### 2.1 System Prompt 与上下文

- `agent-core::ExecutionSpec.instructions` 当前是 `Vec<String>`；Engine 在每个 Model Step
  直接克隆到 `ModelRequest.system`。
- `agent-model::ModelRequest.system` 同样是裸 `Vec<String>`。OpenAI-compatible Adapter
  按顺序把每一项编码成独立 system message，已经具备固定 Part 的协议基础。
- `agent-context::CompactionInput.instructions` 又复制了一份相同语义；滚动摘要要求压缩请求
  继续使用原 system 前缀，但类型层面无法区分“当前配置重新生成的 instructions”和“原会话
  冻结的完整 Prompt”。
- 当前没有产品 Session Prompt 类型或持久化实现。正式 Runtime 尚未进入该阶段，适合先把
  Core、Context 和 Demo 共同需要的不可变 Prompt 语义收敛为 Provider-neutral 类型。

### 2.2 工具层

- `agent-tools::Tool` 已具备 `Input → resolve → ResolvedInput → execute` 两阶段契约；
  Registry 在注册时冻结工具名、描述、JSON Schema 和模型可见默认值。
- 标准文件与 Shell 工具已经证明“能力 trait + 标准工具壳”的分层可以避免 Core 绑定具体
  实现。Memory 沿用这一边界，但本版本的本地文件实现只属于 Demo，不新增内置本地 Adapter。
- `ToolError` 已能表达输入错误、执行错误和受控结构化错误 details；`ToolContext` 已提供取消
  信号；普通工具可直接使用通用授权事实。
- 工具定义在 `ToolSetSnapshot` 中冻结，执行期不可变。因此 `recall_memory` 应保持固定
  Schema，Source 信息通过会话 System Prompt 或 Skill 提供，不能在执行期间修改工具定义。

### 2.3 Memory 现状

- workspace 中没有 Memory 类型、trait、Store、工具或真实 Adapter。
- [`Agent 系统技术架构`](../../modules/agent-system.md)和
  [`agent-core 模块约束`](../../modules/agent-core.md)仍保留早期的 `MemoryService`、
  `MemoryPlugin`、`observe`、`consolidate` 与 Memory 专用 Core 接缝，但代码从未实现。
- 该旧设想与已确认的“Pinned Memory 冻结进 Prompt、Memory Recall 只走普通工具”冲突。
  本版本应直接修订长期架构文档，不能为了兼容未落地文档而实现无调用方抽象。

### 2.4 依赖与验证宿主

- workspace 使用 Rust edition 2024、resolver 3、`unsafe_code = "forbid"`，异步 trait
  沿用手写 boxed future，不引入 `async-trait`。
- `quick-xml 0.41.0` 已存在于当前 `Cargo.lock`，但只由 Tauri 间接引入；记忆 crate
  需要把它提升为 workspace direct dependency，以安全、确定地生成 XML。
- `tempfile 3.27.0` 已是 workspace dependency，可用于同目录临时文件与覆盖持久化。
- `runtime-harness` 专用于 v0.2/v0.3 累计验证，`safety-demo` 专用于 v0.4 安全闭环；
  v0.5 新建独立 `memory-demo`，不继续膨胀已有宿主。

### 2.5 结论

实现分成四条技术链：

1. 将有序 system parts 提升为共享、可序列化的冻结 `SystemPromptSnapshot`；
2. 在新 `agent-memory` 中建立 Pinned Memory、Memory Recall、RecallSource 和具体协调实现；
3. 在 `agent-tools` 提供五个固定标准工具壳，在 Memory Demo 内私有实现真实本地 Store
   与本地 RecallSource；
4. 在独立 CLI Demo 中私有实现会话创建、恢复、Journal 和真实 Provider 装配，验证快照
   冻结与普通工具召回闭环。

## 四、冻结 System Prompt

### 4.1 共享快照类型

在 `agent-model` 定义 Provider-neutral 的透明新类型：

```rust
#[derive(Clone, Debug, Default, Eq, PartialEq, Serialize, Deserialize)]
#[serde(transparent)]
pub struct SystemPromptSnapshot {
    parts: Vec<String>,
}
```

- 新类型只表达“有序、已经完成渲染的 system parts”，不保存 instructions、Memory Entry
  或构建配置。
- 保持透明数组序列化，使现有调试 JSON 和 Provider request 形状不发生无意义变化。
- 提供 `new`、`parts`、`into_parts` 和 `is_empty`；不提供执行期间原地修改接口。
- 空快照继续合法，保持最小 Agent 能力。

`ModelRequest.system` 改为 `SystemPromptSnapshot`。OpenAI-compatible Adapter 只把原来的
数组遍历改为 `parts()`，system message 顺序和线上 JSON 不变。

### 4.2 Core 与 Context 迁移

`ExecutionSpec.instructions` 改为：

```rust
pub system_prompt: SystemPromptSnapshot
```

Engine 每个 Model Step 直接克隆同一快照进入 `ModelRequest`，不在 Core 中追加 Pinned
Memory、Source 说明或其他动态文本。

`agent-context::CompactionInput.instructions` 同步改为
`system_prompt: SystemPromptSnapshot`。滚动摘要请求复用完整快照，因此 Pinned Memory 和
Source/Skill 说明与正常 Agent 请求保持相同前缀，不因压缩重新渲染或读取 Store。

所有现有 `ExecutionSpec`、`ModelRequest` 和 `CompactionInput` 调用点机械迁移；
Provider Codec 的既有 system 顺序测试升级为快照测试，证明协议内容没有变化。

### 4.3 创建与恢复责任

Core 不增加 `CreateSessionParams` 或 `RestoreSessionParams`。正式 Session 属于 Runtime，
本版本只在 Demo 私有层验证两条清晰路径：

```text
创建：当前 instructions + 当前 Pinned Store
   → PinnedMemorySnapshotInput
   → PinnedMemorySnapshot
   → SystemPromptSnapshot
   → 先持久化 Session，再开始首个 Run

恢复：读取 Session 中原样保存的 SystemPromptSnapshot
   → 不读取 Pinned Store，不重新渲染
   → 开始后续 Run
```

分支、continuation 和同会话继续执行均复制原 `SystemPromptSnapshot`。用户显式创建新 Session
才重新读取 Store。快照文件缺失、损坏或版本不支持时明确失败，不回退到最新 Store。

## 五、`agent-memory`：Pinned Memory

### 5.1 领域类型

Pinned Memory 使用下列稳定领域类型，字段名延续功能设计，不引入 Slot：

```rust
pub struct PinnedMemoryEntry {
    pub id: PinnedMemoryId,
    pub category: PinnedMemoryCategory,
    pub content: String,
    pub attributes: BTreeMap<String, MemoryPropertyValue>,
}

#[serde(untagged)]
pub enum MemoryPropertyValue {
    String(String),
    Number(serde_json::Number),
}
```

- ID、Category 和 RecallSourceId 使用校验过的字符串 newtype；空白和控制字符在 newtype
  构造边界拒绝，可配置的超长值在携带必传 Limits 的领域输入校验边界拒绝，不引入隐藏
  固定上限。
- `MemoryPropertyValue` 只接受 JSON 字符串或有限数字；布尔、数组、对象和 null 拒绝。
- `BTreeMap` 固定属性顺序；属性键是模型语义名称，不作为 XML 元素名，也不承担授权。
- 添加使用不带 ID 的 Draft；修改使用带可选 category/content/attributes 的 Patch，并要求
  至少修改一项。显式空 attributes 表示清空，未提供表示保留。

具体字节上限统一由必传 `PinnedMemoryLimits` 配置，至少覆盖条目数、单条正文、Category、
属性数量、属性键/字符串值和最终快照字节数。所有 Demo 数值显式写在装配处，不放隐藏默认。

### 5.2 Store 契约

`PinnedMemoryStore` 是 Pinned 工具背后的最小持久能力：

```rust
pub trait PinnedMemoryStore: Send + Sync {
    fn list(&self, cancellation: CancellationToken) -> PinnedMemoryFuture<Vec<PinnedMemoryEntry>>;
    fn pin(&self, draft: PinnedMemoryDraft, cancellation: CancellationToken)
        -> PinnedMemoryFuture<PinnedMemoryEntry>;
    fn update(&self, id: PinnedMemoryId, patch: PinnedMemoryPatch,
        cancellation: CancellationToken) -> PinnedMemoryFuture<PinnedMemoryEntry>;
    fn unpin(&self, id: PinnedMemoryId, cancellation: CancellationToken)
        -> PinnedMemoryFuture<PinnedMemoryEntry>;
}
```

- `pin` 由 Store 原子分配 ID，并返回已保存的完整条目。
- `update` 和 `unpin` 对不存在 ID 返回稳定 `NotFound`，不静默成功。
- 错误分类固定为 InvalidInput、NotFound、CapacityExceeded、Corrupt、Io 和 Cancelled。
- Store 不暴露 `store_revision`；本地实现的单实例串行和原子替换已经满足本版本并发契约。
- trait 不提供通用 CRUD、selector、Slot 配置、自动合并或淘汰入口。

### 5.3 快照输入与确定渲染

```rust
pub struct PinnedMemorySnapshotInput {
    pub description: String,
    pub entries: Vec<PinnedMemoryEntry>,
}

pub struct PinnedMemorySnapshot {
    content: String,
}
```

`PinnedMemorySnapshot` 只保留最终 XML 字符串。渲染规则固定为：

```xml
<pinned_memories>
  <description>...</description>
  <entries>
    <memory id="..." category="...">
      <properties>
        <property name="..." type="string">...</property>
        <property name="..." type="number">...</property>
      </properties>
      <content>...</content>
    </memory>
  </entries>
</pinned_memories>
```

- Entry 按 `category + id` 稳定排序，属性按 BTreeMap 键排序。
- `quick-xml::Writer` 负责元素、文本和 attribute escaping，不拼接未经转义的 XML。
- 属性以 `<property>` 表达，避免业务属性键成为不合法 XML name 或覆盖 `id/category`。
- 空 entries 和空 properties 仍输出固定容器，使结构稳定。
- description、entry 和 limits 校验成功后一次生成；超过最大快照字节数返回明确错误。
- `PinnedMemorySnapshot` 可作为 `SystemPromptSnapshot` 的一个完整 Part，但不能反向解析回
  Entry。创建新 Session 需要结构化输入时重新读取 Store；恢复 Session 只加载成品 Part。

## 六、`agent-memory`：Memory Recall

### 6.1 两层能力

`MemoryRecall` 是 `recall_memory` 工具依赖的统一能力，`RecallSource` 是单一数据源 Adapter：

```rust
pub trait MemoryRecall: Send + Sync {
    fn recall(&self, request: MemoryRecallRequest, cancellation: CancellationToken)
        -> MemoryRecallFuture<MemoryRecallResponse>;
}

pub trait RecallSource: Send + Sync {
    fn id(&self) -> &RecallSourceId;
    fn recall(&self, request: RecallSourceRequest, cancellation: CancellationToken)
        -> RecallSourceFuture<RecallSourceResponse>;
}
```

- `MemoryRecallRequest` 包含非空 query、显式非零 limit 和可选 Source ID 列表。
- `RecallSourceRequest` 只包含 Source 真正需要的 query 与候选上限，不向 Source 泄露 Tool
  Call ID、Session ID、Prompt 或授权对象。
- RecallSource 返回已经按自身相关性排序的模型可读条目；协调器不要求不同 Source 提供
  可比较分数，也不向 LLM 暴露内部评分。
- Source trait 只暴露稳定 ID，不携带“是否对模型可见”或模型说明。可见 Source 说明属于
  System Prompt/Skill，已获准接入的 Source 集合属于上层构造参数。

### 6.2 统一结果与来源

协调后的结果包含：

- `items`：正文、非空 origins 和字符串/数字 attributes；
- `origins`：每个来源的 `source_id` 与可选稳定 reference；
- `failures`：Source ID、稳定失败类别和脱敏消息；
- `truncated`：是否还有候选因显式 limit 未返回。

每个 Source 原始条目由协调器附加自身 Source ID，Source 实现不能伪造其他来源。完全相同的
正文与 attributes 视为重复项，保留首次排序位置并合并 origins；属性不同的内容不做主观
语义合并。

Source 错误分类固定为 Unavailable、Timeout、Io、InvalidData、Cancelled 和 Internal。
部分 Source 失败时返回成功 items 与 failures；全部 Source 失败时返回
`AllSourcesFailed` 执行错误及结构化失败明细；至少一个 Source 成功但无匹配属于正常空结果。

### 6.3 具体协调实现

`CoordinatedMemoryRecall` 是 `MemoryRecall` 的具体实现，不再抽象公共 Orchestrator trait。
构造时注入：

- ID 不重复的 RecallSource 列表；
- 显式默认 Source ID 列表；
- 单 Source 超时、最大 Source 数和单条结果字节上限等配置。

执行顺序为：

```text
校验 query / limit / Source ID
→ sources 省略时选择显式默认集合
→ 并发调用选中的 Source，并与取消、单 Source 超时竞争
→ 按构造时 Source 顺序收集结果，消除并发完成顺序的不确定性
→ 按 Source 内部排名轮转合并
→ 精确去重并合并 origins
→ 按请求 limit 截断
→ 返回 items + failures + truncated
```

- 指定未知 Source 直接返回 InvalidInput，不改查默认 Source。
- 已知 Source 执行时不可用形成该 Source 的 failure。
- 协调器只接入上层已经允许访问的 Source；v0.5 不增加 Source 级二次审批 SPI。普通工具
  Authorizer 仍在执行前控制 `recall_memory` 整体调用。
- 取消优先收敛为 Cancelled；所有已启动 Source future 必须观察同一取消令牌。
- 无 Source 时不注册 `recall_memory`，而不是装配一个隐藏 No-op。

## 七、`agent-tools`：标准记忆工具壳

### 7.1 Pinned Memory 工具

在 `agent-tools::standard` 增加：

| 工具 | 能力依赖 | 关键输入 | 结果 |
| --- | --- | --- | --- |
| `pin_memory` | `PinnedMemoryStore` | category、content、attributes | 已保存完整条目 |
| `update_pinned_memory` | `PinnedMemoryStore` | id 与至少一项修改 | 修改后的完整条目 |
| `unpin_memory` | `PinnedMemoryStore` | id | 被移除的完整条目 |
| `list_pinned_memories` | `PinnedMemoryStore` | 无 | 最新 Store 全量条目 |

- 工具描述明确说明修改只影响未来新 Session，当前会话继续依赖 Tool Result。
- Store 已有显式总容量，因此 `list_pinned_memories` 不另做隐藏分页。
- resolve 只执行 schema、字符串、Patch 和 ID 校验，不读 Store；I/O 全部在 execute。
- 四个工具使用通用授权事实，现有按工具名策略即可区分读、写、更新和删除。

### 7.2 Recall 工具

`recall_memory` 使用固定输入语义：非空 query、必传非零 limit、可选 Source ID 列表。

- limit 没有默认值；工具实例只配置允许的 maximum，并把 maximum 写入固定工具描述。
- sources 省略时由 `MemoryRecall` 使用显式默认 Source；提供时只查询指定 Source。
- 工具描述只解释参数语义，不动态枚举 Source。可用 Source ID 与用途由 System Prompt 或
  Skill 告知模型。
- resolve 校验 limit 上限、Source ID 格式与重复 ID；execute 委托 `MemoryRecall`。
- 统一响应直接作为 JSON Tool Result。部分失败保持成功状态并携带 failures；全部失败映射
  为带结构化 details 的 `ToolError::Execution`。

五个工具继续走 Registry、resolved invocation、Guardrail、Authorizer、Recorder 和
Dispatcher 的既有顺序。Core 不增加 Memory 分支或特殊 AgentEvent。

## 八、Memory Demo 私有本地能力

本节的文件格式和实现全部位于 `tools/memory-demo`，只用于验证 `agent-memory` 的可替换
契约。它们不进入正式 Memory crate，也不代表未来 Runtime 或应用层必须使用本地 JSON。

### 8.1 Demo JSON Pinned Store

Demo 私有的 `DemoPinnedMemoryStore` 使用版本化文件：

```json
{
  "version": 1,
  "next_id": 1,
  "entries": []
}
```

- 文件不存在时以内存空状态启动，首次成功修改才创建文件。
- 构造时完整读取、反序列化并校验版本、next_id、重复 ID、条目与容量；任何损坏都使构造
  失败，禁止覆盖原文件“修复”。
- ID 格式为持久化单调序号，例如 `pinned_0000000001`；删除不回收序号。
- 一个 Store 实例内部用 Tokio Mutex 串行所有读写；同一数据文件只允许由宿主创建一个
  writer 实例。本版本单进程架构不承诺跨进程多 writer。
- 每次修改先克隆当前状态并在副本上校验；随后在 `spawn_blocking` 中使用目标同目录
  `NamedTempFile` 写入 JSON、flush、`sync_all` 并 `persist` 覆盖；成功后才替换内存状态。
- 写入失败时继续保留旧内存状态和旧权威文件，不把部分修改暴露给后续 list/snapshot。
- JSON 使用稳定字段和 entries ID 顺序输出，但该文件只是 Demo 私有契约，不进入正式
  Memory API、Runtime 数据库或应用协议。

### 8.2 Demo JSON RecallSource

Demo 私有的 `DemoRecallSource` 是只读、可真实查询的本地参考 Source。版本化文件包含稳定
reference、content 和 attributes。每次 recall 在阻塞文件任务中重新读取文件，使开发者
修改样例数据后无需重启 Demo。

搜索算法明确保持简单：

1. query 按 Unicode 空白切分并做小写归一；
2. 在 content、reference 和可字符串化 attributes 中匹配；
3. 至少命中一个 term 的记录成为候选；
4. 按命中 term 数降序、reference 升序返回 Source 内部排名；
5. 单条记录超过配置上限或文件损坏时返回 InvalidData，不截断成不可追溯的半条记录。

该实现只用于验证 RecallSource 可替换边界，不宣称具备生产级语义搜索能力。未来 Runtime
或应用层可以选择 SQLite、向量、远程或混合实现，只需实现同一 RecallSource，不改变工具
和 Core。

## 九、Memory Demo

### 9.1 形态与入口

`tools/memory-demo` 使用 CLI，不新增 Web server、静态页面或前端工程。入口为：

```bash
cargo run -p memory-demo -- chat --data-dir <DIR>
cargo run -p memory-demo -- chat --data-dir <DIR> --session <SESSION_ID>
```

- 未提供 Session ID 时创建新 Session，并打印稳定 ID；提供时恢复该 Session。
- `chat` 才加载 `.env` 和 DeepSeek/OpenAI-compatible credential；默认测试完全离线。
- 交互命令只提供 `/state`、`/new`、`/cancel` 和 `/quit`；记忆增删改查及召回必须由模型
  调用正式标准工具，不在 CLI 复制第二套业务入口。
- stdin 继续放在专用线程，不阻塞 Tokio worker。

### 9.2 私有持久化

Demo 数据目录固定为：

```text
<data-dir>/
├── pinned-memory.json
├── recall-records.json
└── sessions/
    └── <session-id>.json
```

Session 文件是版本化私有记录，至少保存完整 `SystemPromptSnapshot` 和规范
`ConversationSnapshot`。新 Session 创建顺序固定为：

```text
读取 Pinned Store
→ 渲染 PinnedMemorySnapshot
→ 组合 Demo instructions、RecallSource/Skill 说明和 Pinned Part
→ 原子保存 Session 文件
→ 才允许启动 AgentExecution
```

恢复顺序固定为：

```text
读取并校验 Session 文件
→ 原样使用 SystemPromptSnapshot 与 ConversationSnapshot
→ 不读取 Pinned Store 构建 Prompt
```

Demo 的私有 Recorder 在副作用前保存 pending Assistant Tool Call，并在工具完成后原子提交
Tool Result；最终 AssistantMessage 由 Demo 追加。Session 文件使用与本地 Store 相同的
同目录临时文件覆盖策略。`/new` 只在无活动 Run 时创建使用最新 Store 的新 Session。

### 9.3 RecallSource 装配

Demo 固定装配：

- `demo_records`：读取 `recall-records.json` 的私有 `DemoRecallSource`，作为默认 Source；
- `failing_demo`：始终返回受控 Unavailable 的私有 Source，只用于验证部分失败。

首次初始化数据目录时创建带少量可审阅示例记录的版本化 Recall 文件；已存在文件绝不覆盖。
Demo System Prompt 固定说明两个 Source 的用途，便于人工要求模型执行默认、显式单 Source
和显式多 Source 召回。

### 9.4 状态观察

`/state` 展示当前 Session ID、System Prompt Part 数量、会话创建/恢复来源、快照中的
Pinned Memory 文本和当前 Store 条目列表，并明确两者可能不同。它不修改状态，也不把 Demo
Session/Run 类型升级为正式 Runtime 契约。

## 十二、安全、兼容与排除项

- Pinned 和 Recall 内容都可能敏感；库错误不记录正文，Demo `/state` 只在开发者显式命令下
  输出当前测试数据，正式日志和调试事件不增加记忆正文。
- `recall_memory` 使用普通 Authorizer；Source 集合由上层在构造协调器前完成访问资格筛选，
  Source ID 的模型可见性不等于权限。
- XML、JSON 和工具输入全部经过大小、类型和转义校验；损坏持久文件只报错，不自动修复或
  覆盖。
- Demo Store 只承诺单进程、单实例 writer；不承诺网络文件系统、跨进程锁或数据库事务。
- DemoRecallSource 是线性扫描验证实现，不作为大型语料、语义相关度或生产性能方案。
- 本版本不实现自动观察、候选记忆、后台整合、自动淘汰、自动写入、Embedding、向量搜索、
  远程产品服务、Source 动态加载或正式 Runtime/应用接入。
- Memory Demo 的 Session ID、文件格式、命令和 Journal 均为验证私有契约，不进入
  `assistant-protocol`，未来正式 Runtime 不直接复制。
