## 二、背景与版本目标

`v0.18.0` 已建立持久 Goal、WorkPlan 和同一 Runtime Run 跨执行段自动续跑基线。
Skills 的关键不是再建一套 Agent Loop，而是让可审阅的本地指令包以稳定、可发现、
可诊断且可恢复的方式进入现有 Runtime 与 Conversation。

本版本目标是形成一个完整的本地 Skills 产品闭环：

1. 兼容 Agent Skills 目录包并按确定性来源规则发现本地 Skill；
2. 把可用名称和描述以可持久 Catalog Snapshot 告知模型；
3. 支持 Agent 自主激活与用户显式激活，且在 Runtime 再次校验调用资格；
4. 激活正文进入规范 Conversation，跨压缩、重启、恢复和同 Run 续段保持有效；
5. Desktop 能发现、选择和诊断 Skill，并能看懂当前 Session 实际绑定了什么；
6. Skill 只提供指令，不绕过现有 Plan/Build、Ask/Auto、权限、审批和审计边界。
7. 所有内插式消息通过统一边界机制进入模型上下文，并保证实时消息、
   可靠 Conversation 和 Desktop 重连/重建后的 reasoning、正文与 Tool Call 顺序一致。

成功标准不只是“模型读到 `SKILL.md`”，而是用户能回答以下问题：

- 哪些 Skills 被发现，哪一份候选实际生效？
- 为什么某个 Skill 不可用或被覆盖？
- 当前 Session 看到的 Catalog 是哪个 revision？
- 本次输入是否显式激活了 Skill，Agent 又自主加载了哪些？
- 修改本地文件或名称启停状态后，为什么只影响后续新 Session？
- 一条 Runtime Hidden UserMessage 或 Provider 临时 user-role 投影是否只改变
  模型上下文，而不会把后续 reasoning 和工具显示到错误位置？

## 三、明确非目标

`v0.19.0` 已确认只处理本地 Skills，不同时建设完整扩展平台。
本版本不包含：

- MCP Server 发现、连接、工具发布或 OAuth；
- Plugin ABI、插件市场、Hub/Tap、远程 URL 安装和自动更新；
- Agent 自主创建、编辑、删除或下载 Skill；
- Skill 专属模型、推理强度、子 Agent Profile、`runAs=subagent` 或嵌套 Skill；
- Flow、参数模板、自动调度、后台执行或把 Skill 当成可执行任务；
- 文件 watcher 向已有 Session 静默发布变更；
- 把 `allowed-tools` 解释为越过 ez-assistant 权限系统的预授权；
- 为尚不存在的远程来源预建通用 Provider Registry。

## 四、术语与缺失的状态模型

前期讨论已覆盖扫描、优先级和激活，但尚未把“安装了”、“被发现”、“可调用”、
“已激活”分成稳定产品事实。`v0.19.0` 需要先固定以下概念：

- **Skill Package**：一个至少包含 `SKILL.md` 的本地目录包。
- **Candidate**：某个来源中扫描到的具体包，即使无效、被覆盖或禁用也是诊断事实。
- **Winner**：同名候选按确定性规则选出的当前有效定义。
- **Catalog Snapshot**：某个 Session 已持久发布给模型的完整可用目录，包含 revision。
- **Activation**：把某个 Catalog revision 中 Skill 的精确指令正文注入规范 Conversation。
- **Active Skill**：已进入当前 Conversation 且仍应对后续执行生效的 Skill 版本。
- **Diagnostic**：格式错误、不可读、越界资源、同级冲突、被覆盖、过大、不兼容或
  按名称禁用等可观察事实。

建议的状态链是：

```text
目录包
→ 扫描为 Candidate
→ 解析/校验
→ 按 Skill name 查询全局启停状态
→ 同名优先级选择 Winner
→ 生成 Session Catalog Snapshot
→ 用户或 Agent Activation
→ Conversation 中的 Active Skill
```

这条链必须在 Runtime 中有单一权威语义；Desktop 只展示快照和发送用户意图。

## 五、已形成的设计方向

### 5.1 包格式与调用资格

- 只支持 `<skill-root>/<skill-name>/SKILL.md` 目录包，按 Agent Skills 标准解析
  `name`、`description`、`license`、`compatibility`、`metadata`、`allowed-tools`。
- 保留 `scripts/`、`references/`、`assets/` 与其他相对资源，发现时不读取正文资源、
  不自动执行脚本。
- 兼容 `disable-model-invocation` 和 `user-invocable` 客户端扩展，Runtime 归一为
  `model_invocable` 与 `user_invocable` 两个布尔事实。
- 两者都不可调用的包不进入任何调用目录，但保留为诊断项。
- `allowed-tools` 可解析和展示兼容性信息，不改变工具授权结果。

### 5.2 本地来源与确定性覆盖

只扫描四个固定 Skill Root，优先级已确认为：

```text
<workspace>/.ez-assistant/skills
→ <workspace>/.agents/skills
→ ~/.ez-assistant/skills
→ ~/.agents/skills
```

- 不沿 Workspace 祖先目录继续查找，不扫描这四个固定目录之外的任何来源。
- 高优先级层只覆盖同名 Skill，不丢弃低优先级层的其他名称。
- 不依赖文件系统返回顺序；完全相同优先级的冲突不静默选择。
- Catalog 不向模型暴露绝对路径；用户可在桌面诊断中查看来源位置。
- 启用/禁用以通过格式校验的 Skill `name` 字段值直接作为 SQLite 唯一键，不把来源、层级、
  locator 或 digest 纳入键。没有存储记录的新名称默认启用。
- 名称被禁用时，该名称的所有来源候选都不进入 Winner 和 Catalog，
  不因当前 Winner 被禁用而让下层同名包候补；重新启用后再按正常来源
  优先级选出 Winner。所有候选仍保留为诊断事实。

### 5.3 Session Catalog 冻结周期

- Session 使用已持久的完整 Catalog Snapshot，不在每个 Model Step 扫描文件系统。
- 创建 Session 时扫描四个固定 Skill Root，应用 SQLite 名称启停状态，
  生成并持久化一份完整 Catalog Snapshot；未发现有效 Skill 时持久化空 Catalog。
- Catalog 在 Session 生命周期内不变，不提供任何重新扫描或替换当前
  Session Catalog 的入口。
- `SKILL.md` 新增、修改、删除和 SQLite 名称启停变化只影响变更后新建的 Session；
  已有 Session、已 accepted Input 和活动 AgentExecution 始终使用原冻结 Catalog 定义。
- Skill 普通资源仍位于四个共享 Root，不复制到 Session；执行时按冻结源目录读取当前文件，
  文件缺失或变化由对应工具按正常资源错误处理，不改写已经落账的指令正文。
- Catalog 变化不影响稳定注册的 `load_skill` 工具定义或其 schema。

### 5.4 Agent 激活与同 Run 续段

- Agent 使用专用 `load_skill` 工具按名称激活，不直接从 Catalog 绝对路径读文件。
- `load_skill` 作为稳定网关工具始终进入冻结 ToolSet；即使当前没有可用技能，
  也不动态移除或更改工具定义。
- `name` 使用稳定字符串参数，不根据当前技能列表编译为动态 enum；Runtime
  在执行时按当前 Session Catalog revision 重新校验名称和 `model_invocable` 资格。
- `load_skill` 只返回简短结构化状态，不把整篇正文放入 Tool Result。
- `load_skill` 使用普通串行工具语义，不改变同批其他工具既有的串行/并行调度；当前 Tool Batch
  仍完整结算，Skill 指令只对可靠提交后的下一执行段生效。
- 完整 Tool Call/Result 批次先落账，成功激活的正文再作为 Runtime Hidden Injected
  User Part 持久化。
- 多个成功激活按原 Tool Call 顺序合并落账；至少一个成功时才进入 Skill
  continuation，全部失败则以普通错误 Tool Result 继续当前 AgentExecution。
- 当前 AgentExecution 以通用 continuation 终态结束，Runtime 在同一 `RunId` 内
  启动下一执行段。
- 一个 Run 对用户仍只有一次 accepted/started/finished，step、usage、budget、
  guardrail 和取消跨段累计。

### 5.5 用户显式激活

- 用户选中的 Skill 在首次模型请求前随该次规范 UserMessage 一起持久化，
  不为此先运行一个空 `load_skill`。
- Composer 草稿同时最多只保留一个技能选择；再次选择直接替换草稿中
  当前技能，不追加第二个。发送成功后清空 Composer 的技能标签，
  不清理已落账的 Conversation Activation。
- 用户显式调用技能的流程始终保留，不依赖模型是否主动调用 `load_skill`，
  也不因当前技能列表变化而删除入口。
- Desktop 只从 Session Catalog Snapshot 展示 `user_invocable` 候选；Runtime 必须
  在提交时对同一份冻结 Snapshot 重新校验名称、revision 和调用资格，不读取
  当前文件或 SQLite 启停状态改写它。
- 显式激活和 Agent 自主激活最终使用同一 Activation 领域事实，仅 trigger 不同。

### 5.6 安全与权限

- Skill 是指令来源，不是权限授予来源。
- Skill 本身不设独立的来源信任或权限门禁。只要该名称在当前冻结 Catalog
  中可用，并符合 `user_invocable` / `model_invocable` 调用资格，Runtime 就允许
  激活，不再按来源或目录层级二次判断。
- 文件、Shell、网络、记忆和未来 MCP 能力继续通过现有 Authorizer、审批与审计。
- Skill 内容、资源列表、文件路径和参数需确定性编码，不能破坏消息包装边界。
- 资源读取必须限定在成功激活的 Skill 根中，需防止 `..`、符号链接和别名越界。

## 六、建议的产品与交互闭环

本节收口功能层的交互要求；具体页面结构、状态、焦点和中文文案已经形成独立的
[`v0.19.0 界面交互设计指导`](界面交互设计指导.md)。

### 6.1 统一中文界面文案

桌面端面向用户的导航、标题、按钮、标签、状态、帮助和错误文案统一使用
中文，不在同一信息层级混用中英文产品概念。这是本版本已确认的交互要求，
不再作为待选方案。用户可见术语统一映射为：

| 内部/技术术语 | 界面统一文案 |
| --- | --- |
| Runtime | 运行时 |
| Skills / Skill | 技能 |
| Agent | 智能体 |
| Workspace | 工作区 |
| Session | 会话 |
| Run | 运行 |
| Candidate / Winner | 候选项 / 当前生效项 |
| Activation / Active Skill | 激活 / 已激活技能 |
| Tag | 标签 |

不强行翻译用户安装的技能原始名称、模型名、服务商名、`SKILL.md`、
`load_skill`、`/skill` 等文件名或稳定标识符；它们只在必要的技术详情、路径或
输入语法中保留原文。界面主文案应先给出中文语义，不直接显示
`winner`、`revision`、`user_invocable` 等内部字段名。
斜杠命令列表中使用“选择技能”作为主标题，`/skill` 只作为次要快捷语法显示。

### 6.2 设置中的“技能”页

建议在现有“运行时 / 模型 / 记忆 / 权限”设置导航中增加“技能”，承担全局发现与
诊断，不把管理列表塞入输入区。

建议首版提供：

- 按名称排序的当前生效技能列表，显示名称、描述、来源层级、“用户可用 /
  智能体可用”资格和健康状态；
- 诊断列表，能查看无效、冲突、被覆盖和不可读候选项的原因；
- 详情页标题只显示技能名称；摘要放入“描述”字段，并展示当前来源的
  `SKILL.md` 正文、状态、调用资格和覆盖诊断；
- 每个技能名称提供明确的“已启用 / 已禁用”开关，并说明禁用将屏蔽
  所有同名来源，不会启用下层候补；
- “打开来源目录”菜单，可分别打开四个固定 Skill Root；
- 空状态明确给出可放置目录和 `SKILL.md` 最小格式，不引导到尚不存在的市场。

启停状态由 Runtime 以 Skill `name` 为唯一键持久化到 SQLite，设置页不保存
第二份本地状态。切换成功后持续显示“对新会话生效”；已有 Session 保留
原 Catalog binding，不因开关变更被中途改写。

### 6.3 输入区中的显式激活

建议不在首版动态注册大量 `/<skill-name>` 顶层命令，而是复用现有斜杠命令
与草稿标签交互：

```text
输入 /skill
→ 打开可搜索的技能选择器
→ 选择后移除命令字面量
→ 在草稿区显示可移除的技能标签
→ 与正文/附件一起提交
```

理由：

- 不与 `/goal`、`/model`、`/mode` 等内建命令发生名称冲突；
- 大量技能不会淹没一级命令列表；
- 选中后用户仍能看见待提交事实，提交失败时与正文、附件一起保留；
- 未来如增加 `$skill-name` 或 `/<skill-name>` 快捷别名，仍可归一到同一运行时意图。

已确认首版按以下契约实现：

1. **Composer 只保留一个技能**：技能选择器是单选。草稿已有技能时再次选择，
   直接替换当前选中项，不追加新标签。标签始终显示技能名称并可手动移除。
2. **技能标签不是任务**：没有正文、附件或 Goal objective 时不允许只提交
   技能标签，发送入口保持不可用并提示“请输入要使用该技能完成的任务”。
3. **发出后保留审计标签**：用户消息显示弱化技能标签，只展示冻结技能名称，
   不向用户暴露 Catalog revision 或注入正文。
   发送成功后清空 Composer 中的技能选择；消息上的审计标签和已落账
   Activation 不受影响。发送失败则与正文、附件一起保留。
4. **选择器只展示用户可用项**：列表展示技能原始名称、中文资格说明、描述和来源；
   兼容性声明作为非阻断警告。“仅智能体可用”项只在设置诊断中展示，
   不进入输入区选择器。
5. **草稿使用 Session Catalog**：选择器和提交校验均使用当前 Session 的冻结
   Catalog；草稿期间的文件或全局启停变化不会让已选标签过期或静默换版。

### 6.4 技能变更何时生效

技能文件和启停变化不修改已有 Session。设置页中的文件路径说明和启停操作均
明确标注“对新会话生效”。用户需要使用变更后的 Skill 时新建会话；旧会话
继续使用原冻结 Catalog，界面不增加其他变更状态或操作。

### 6.5 当前上下文与消息时间线

建议在右侧“当前上下文”增加紧凑的“技能”分区，具体只展示：

- **已激活技能**：每项显示技能名称和“用户激活 /
  智能体激活”，按 Conversation 中的规范 Activation 顺序投影；
- **诊断入口**：显示错误/警告数量，点击后进入设置的“技能”页并定位诊断列表。

该分区不展示 Catalog revision、可选技能数量、全量 Candidate、覆盖链、路径和启停开关，
避免把内部冻结身份或选择器数据误解成用户需要管理的状态，也不复制设置页的管理职责。

消息时间线建议：

- 用户显式激活：用户消息显示弱化的技能标签，隐藏正文注入部分；
- 智能体自主激活：沿用一行工具事件“加载技能 · <技能名>”，详情展示结果和诊断，
  不显示 Catalog revision、路径或整篇正文；
- 同一运行内续段：不新建用户气泡、不重启运行动画、不让步骤编号回退。
- 模型服务兼容投影为图片结果临时生成的 user-role 信封不进入产品时间线；
  桌面端不得因此重开用户回合或把后续段落归到前一步骤。

### 6.6 响应式、焦点与可访问性

- 技能选择器复用输入区浮层根节点，与待办/执行设置/模型设置同时只有一个前台浮层。
- 支持键盘搜索、上下选择、Enter/Tab 确认、Esc 返回，关闭后焦点回到输入框。
- 选项的名称、描述、可调用模式和禁用原因不依赖颜色或悬浮提示才能理解。
- `720px` 及更窄宽度不新增输入区底栏常驻按钮；技能通过斜杠命令与标签
  进入，避免破坏 `v0.18.0` 已收口的五项底栏。
- 长描述、大量候选、150% 缩放、中文输入法和“减少动态效果”必须进入交互验收。

## 七、本次整理新发现的遗漏议题

以下内容在原调研中未覆盖或只有一句提示，现已随功能设计一并收口。

### 7.1 技能启停与工具权限边界

本版本不引入 Workspace Skill 来源信任、安全级别或额外权限开关。
技能是否可以进入 Catalog 和被激活，只由名称启停状态、当前冻结 Catalog
及 `user_invocable` / `model_invocable` 调用资格决定。

已确认契约如下：

1. **名称是唯一启停键**：Runtime 以通过格式校验的 Skill `name` 字段值直接作为 SQLite 主键
   持久化 enabled/disabled 事实，不按来源、目录层级或候选路径分别存储。
2. **禁用不产生同名候补**：禁用一个名称后，所有同名候选都从 Winner
   和 Catalog 中排除，但仍保留在设置诊断中；重新启用后才恢复正常覆盖选择。
3. **默认启用**：未在 SQLite 中存在启停记录的新名称按已启用处理；
   只在用户明确切换后写入或更新记录。
4. **启用即放行 Skill**：不对 Workspace Skill 或其他来源另做信任、权限、
   风险等级或审批判断。Skill 一旦通过启停和调用资格校验就可注入模型上下文。
5. **实际操作按工具授权**：Skill 后续要求文件、Shell、网络、记忆或未来 MCP
   操作时，只由对应工具的 Authorizer、审批和审计决定；不因 Skill 启用而预授权，
   也不因 Skill 来源而附加二次授权。
6. **冻结执行不被开关改写**：启停变更只影响变更后新建 Session 的初始
   Catalog；已有 Session、已 accepted Input、活动 AgentExecution 和历史 Activation
   继续以各自冻结数据为准，不中途删除、替换或重新解析。

### 7.2 严格规范与宽容兼容的边界

Agent Skills 格式规范对名称、目录匹配、长度和 YAML 有严格限制，客户端实现指南
同时允许客户端对不影响识别和激活的字段做宽容处理。本版本已确认
采用“能确定性缺省就缺省，无法安全处理就报错并跳过”的两级策略，
不为强行加载引入第二套修复解析器或启发式改写。

- 缺少 `license`、`compatibility`、`metadata`、`allowed-tools` 等可选字段时，
  使用明确缺省值，不产生错误；
- 缺少客户端调用扩展字段时，按已确认规则缺省为
  `model_invocable = true` 和 `user_invocable = true`；
- 可选字段存在但类型不符时，如可直接忽略且不影响包身份，则按缺省值
  加载并产生 warning；不做字符串拼接、自动引号或其他原文修补；
- YAML 无法解析、缺少或无法解析必要的 `name` / `description`、
  `name` 无法形成稳定唯一键、正文或资源边界无法安全确定时，记录 error
  并跳过该 Candidate；
- `compatibility` 是作者声明而非 Runtime 已验证能力；字段有效时原样展示，
  缺失或可忽略的类型异常不阻断加载。

### 7.3 已激活 Skill 的去重、更新与压缩保护

本版本采用以下可观察契约：

- 同一 `name + definition digest` 在当前 Conversation 中已激活时，返回
  `already_active` 结构化结果，不重复注入正文；
- 本地 Skill 出现新 digest 后，只进入变更后新建 Session 的 Catalog；已有
  Session 继续使用旧定义，且其已激活正文不被改写。新 Session 中只有用户或
  Agent 显式激活后，新定义才进入该 Conversation；
- 同名新 digest 激活后，新 Activation 对后续执行取代旧版本，但旧消息仍作为
  不可变历史保留；不同名称的 Skill 可在 Conversation 中同时保持已激活状态。
  这与 Composer 每份草稿只能选一个 Skill 不冲突；
- 压缩必须保护每个名称当前生效的 Activation 正文和替换关系，不能无声丢失；
  已被同名新版取代的旧正文可进入历史压缩，不需永久全文保护；
- Fork、导出/导入和重启均以规范 Activation 及替换关系恢复，不通过当前文件
  重建历史指令。具体内容去重与压缩布局算法归技术方案。

### 7.4 Catalog Snapshot 与文件变化竞态

Catalog 冻结后、激活前，`SKILL.md` 可能被修改或删除。可选语义为：

1. Catalog Snapshot 同时保存可激活的精确正文，后续不依赖原文件；
2. Catalog 只保存 locator + digest，激活时再读文件；如 digest 不符则失败并要求新建 Session。

本稿选择第 1 种，但只冻结 Catalog 中的 `SKILL.md` 定义事实，不复制 Skill 包：
Catalog revision 必须能从 SQLite 恢复精确激活正文和共享源目录；用户显式调用在
Input accepted 时进一步冻结该定义的身份和正文。普通资源继续由四个共享 Root 持有，
不进入 Session 私有目录、Catalog revision 或资源索引。已发布 revision 不能静默加载
新的 `SKILL.md` 正文，但按需读取的普通资源允许反映共享目录当前状态。

### 7.5 支持资源的访问、列表与脚本语义

本版本按 Agent Skills 通用的三级渐进加载方案处理，不新建另一套资源执行系统：

1. **发现阶段**：只解析名称、描述和其他有界元数据，不读取资源正文，
   不运行脚本。
2. **激活阶段**：加载 Catalog 中已冻结的 `SKILL.md` 指令正文，并告知对应的
   共享 Skill 根目录；不递归枚举或预读 `scripts/`、`references/`、`assets/`。
3. **执行阶段**：指令引用某个资源时才按需读取。文本与二进制文件继续
   使用现有文件/图片等工具，不为 Skill 绕过工具能力和输出上限。
4. **相对路径**：Skill 中的文件引用均相对该 Skill Root 解析；解析后必须仍在
   已激活 Skill Root 内，拒绝 `..`、符号链接、别名或规范化后的越界。
5. **脚本显式执行**：`scripts/` 在发现和激活阶段绝不自动运行。Skill
   可指示 Agent 通过现有 Shell 工具显式执行相对脚本路径；完整命令、工作目录、
   权限、审批、流式输出、超时、取消和审计均沿用普通 Shell 契约。

普通资源的大小、输出和执行限制复用实际文件、图片、Shell 等工具契约，不新增
Skill 专属资源索引、Session 容量预算或包复制生命周期。

### 7.6 扫描和上下文规模上限

技术方案需根据真实扫描和上下文成本确定四个固定 Skill Root 下的候选目录数、
扫描深度/时间、Catalog Skill 数与 Token/字节预算、每 Run 激活/continuation 数，
以及诊断分页上限。功能层固定以下超限语义：

- 单个 Candidate 的 `SKILL.md` 正文或字段超限时，只对该 Candidate 记录 error 并跳过，
  其他有效 Skill 继续处理；
- 如果触发根数、扫描时间或总目录数等全局上限，导致 Runtime 无法证明扫描完整，
  则该 Session 的 Skills Catalog 初始化整体失败，不发布伪装完整的部分 Snapshot；
  Runtime 持久化明确的 Catalog 不可用诊断，Session 的其他能力仍可使用；
- Catalog 投影或激活正文超过上下文预算时，产生结构化失败和可操作诊断，
  不静默截断指令或资源列表；
- 每 Run 的激活或 continuation 达到上限后，后续请求返回稳定错误，
  不影响已落账 Activation、Tool Result 和 Run 累计用量。

### 7.7 Session 生命周期与 Catalog 所有权

这些不是新建一套 Skill 专属 Session 机制，而是因为 Catalog Snapshot 绑定 Session、
Activation 进入 Conversation，所以必须说明它们如何复用现有创建、Fork、归档和恢复语义。

1. **新会话使用当前状态**：在 Session 创建时扫描四个固定
   Skill Root，按来源优先级和当时的 SQLite 名称启停状态生成初始完整 Catalog。
2. **Session 全程冻结**：Catalog 创建成功后不再扫描或替换；文件和启停状态变化
   只影响后续新建 Session。Runtime 重启从持久化 Snapshot 恢复，不重新扫描。
3. **Fork 继承冻结事实**：Fork 继承分支点的精确 Catalog revision 和 Conversation
   Activation，不重新扫描、不换成当前 Winner，且在其生命周期内保持冻结。
4. **归档与恢复不改写**：归档 Session 保留原 Catalog；恢复后仍使用同一份冻结
   Snapshot。需要使用最新 Skill 时新建 Session。

### 7.8 兼容性与可调用性的用户语义

`compatibility` 是作者文本声明，不是 Runtime 已验证能力。首版只在
设置详情和技能选择器中作为非阻断说明展示，不因声明内容自动禁用 Skill。
当前 Plan/Build、Ask/Auto 或工具环境与声明不匹配时，由真实工具能力、授权和执行结果反馈。

“仅智能体可用”的 Skill 在设置页可见但不进入 Composer；“仅用户可用”
不进入模型 Catalog。两者都使用中文资格说明，不暴露内部字段名。

### 7.9 `load_skill` 的稳定注册与手动调用

官方客户端实现指南建议在无可用 Skill 时不注册激活工具，并可以把名称参数限定为
当前可用名称枚举。本项已确认不采用该动态方案：

- `load_skill` 始终作为稳定网关工具注册；
- `name` 是普通字符串，不编译当前名称 enum；
- Skill 文件与启停状态变化只影响后续新建 Session，不重建已有 Session 的
  Catalog Snapshot 或 ToolSet Snapshot；
- 模型调用按 `model_invocable` 校验，用户显式调用按 `user_invocable` 校验，
  两条流程共用当前 Catalog revision 和 Activation 落账契约，但互不依赖；
- 列表为空、名称不存在或调用资格不匹配时，Runtime 返回结构化
  失败，不通过修改工具 schema 或移除用户入口预防调用。

技术方案只需回证稳定 schema、prompt cache 和冻结 ToolSet 装配符合上述已确认口径，
不再比较动态注册或动态 enum 方案。

### 7.10 子 Agent 与委派边界

当前产品已有父 Run 内的单层 child conversation。即使 `v0.19.0` 不支持 `runAs=subagent`，
已激活 Skill 仍可以指示父 Agent 使用现有 `delegate_task`，所以只需补齐
Catalog/Activation 在现有父子 Conversation 边界中的所有权，不新建 Skill 专属子 Agent。

- child 继承父 Run 创建子任务时已冻结的 Catalog revision，不自行扫描文件；
- child 可以针对该继承 Catalog 独立调用 `load_skill`，仍按 `model_invocable`
  调用资格校验，不用当前文件或后来的启停状态改写父 Run 已冻结事实；
- 父 Conversation 已激活的正文不自动注入 child，继续遵守“child 只接收
  自包含任务和显式背景”的现有边界；
- child 自主产生的 Activation 只写入 child conversation，在子任务详情和用量中
  按 child owner 展示，不回写父 Conversation；
- 父 Run 取消、child 独立取消、压缩和重启恢复沿用现有父子任务所有权，
  Skill continuation 只通过统一内部消息边界附着到其所属 child，不跨 owner 恢复。

### 7.11 Queue、Goal 与 Skill 草稿事实

用户可以在存在活动 Run 或 Goal 时提交新输入。如果输入携带技能标签，
本稿建议采用“接受输入时完整冻结，之后任何状态变化都不改写输入”的语义。

建议契约如下：

1. **接受时原子冻结**：Runtime 在 Input accepted 前按该 Session 的冻结 Catalog
   校验名称存在且符合 `user_invocable`，不重新读取当前 SQLite 启停状态；并将
   单个 name、revision、
   definition digest、trigger 和精确 activation snapshot 与 Input 原子持久化。
   任一项失败则整个输入不接受，
   Desktop 保留正文、附件与技能标签。
2. **启动时不重新选 winner**：输入排队后发生同名技能更新、全局启停变化、
   原文件修改或删除，都不得把该 Input 静默切换到新定义。执行时直接使用
   已冻结的 activation snapshot。
3. **冻结事实永不改写**：已接受 Input 的用户正文、附件、单个技能选择、
   revision、digest 和 activation snapshot 均不可变。后续发生的启停状态或
   原文件变化或删除都不得修改、删减、重新解析或替换其内容。
   具体工具调用在执行时仍正常进入各自权限与审批流程，但工具授权不改写 Input。
4. **Queue 完整保留事实**：Queue 以中文技能标签显示冻结名称，不展示 Catalog revision。
   置顶不改变技能选择和冻结事实；取消连同未提交 Activation 一起删除；
   重启恢复和 Goal held input 完整恢复它们。
5. **Goal 与 Skill 正交**：允许 `/goal` 与技能标签同时提交。Goal objective 只冻结
   用户真实输入和附件事实，不把技能注入文本混入 objective；技能作为规范
   Conversation 中的执行上下文，供 Goal 续跑的后续 Run 继续使用，不每次重复激活。

这一方案保证用户意图不被排队时间或任何后续状态改写，
并使 Queue、Goal 与普通 Input 复用同一份冻结 Activation 契约。具体存储去重、
阻塞状态 DTO 和恢复事务归技术方案。

### 7.12 Catalog 与 Activation 的规范消息表示

技术方案将两类冻结事实区分处理：

- **Catalog Snapshot** 是 Session 创建事实，其结构化内容和确定性渲染成品与
  Session 一起持久化，模型投影使用冻结 `SystemPromptSnapshot` 的独立版本化 Part；
  不向 Conversation 追加可替换的 SystemMessage 或 Hidden UserMessage。
- **Activation** 是 Conversation 中的执行上下文：用户显式激活作为该次可见
  UserMessage 的结构化内部 Part 落账；Agent 通过 `load_skill` 激活时，作为
  Runtime-origin 且产品隐藏的内部 UserMessage 与工具结果原子落账。
- 两种 Activation 复用同一 `InternalContext` 载荷格式，注入 Markdown 正文与
  结构化 name、catalog revision、digest、trigger 和共享源目录，不把用户启停
  等客户端控制字段当成 Skill 指令。
- Catalog、Activation 和普通 UserMessage 的投影顺序由 Provider-neutral 请求组装
  与统一内插边界确定；Chat Completions、Responses、DeepSeek thinking 与压缩
  replacement 使用同一冻结身份进行校验。

这一区分保证该落库的 Catalog/Activation 事实全部落库，同时不为不会
变更的 Session Catalog 额外制造 Conversation replacement 消息。

### 7.13 所有内插式消息的统一边界与时间线一致性

该问题不局限于 `read_image`。当前与未来会改变模型上下文、但不应被当成
新用户回合的内插来源至少包括：

- `read_image` 等图片 Tool Result 在部分 Provider 上生成的 request-only user-role 信封；
- `load_skill` 成功后落账的 Skill Activation 与同 Run 续段；
- Goal 启动、自动续跑和恢复上下文；
- WorkPlan、Plan/Build 模式、上下文续接/压缩和委派输入中的 Injected Part 或
  Runtime Hidden UserMessage；
- 未来其他需要在同一用户意图或同一 Run 内切换 AgentExecution 的内部控制消息。

这些消息的业务来源、是否进入规范 Conversation 和是否需要持久化并不相同，
但它们必须通过同一个 Provider-neutral 的“内部消息边界”抽象封装顺序、
执行段和产品投影语义。功能模块只提供原因、指令载荷和所需持久化策略，
不得自行拼接 Hidden UserMessage、重置 step 或直接操作 Desktop 时间线。
边界一旦产生，必须先冻结其权威事实，再派生模型请求和界面事件；
应进入规范 Conversation 或影响恢复的消息、控制事实必须落库，并通过
`run_id` 与稳定的 message/boundary 身份、执行段序号和前后续关系串联。

`read_image` 的规范 Tool Result 可以持久化图片引用，但部分 Chat Completions /
Responses Provider 不能在原生 Tool Result 中承载图片。当 Adapter 使用
`AggregatedUserInput` 兼容投影时，会在完整 Tool Result 批次后向模型请求
内插一条 user-role 图片信封。该信封是 request-only 投影，不是用户输入，
也不应写入规范 Conversation 或显示为用户气泡。

2026-08-23 已对本机三条包含 `read_image` 的存量会话做脱敏只读核对：

- 只提取 role、message/part/call ID、工具名和顺序，未读取或复制用户正文、
  图片内容和工具参数；
- Conversation JSONL 中的 Assistant/Tool 顺序完整，request-only user-role
  图片信封没有被错误持久化；
- SQLite `runs` / `run_message_refs` 证明图片工具前后的 AssistantMessage 仍属于
  同一 Run；
- 正在运行的 Runtime `get_session_view` 产品快照仍按规范 Assistant parts
  顺序投影 reasoning、text 和 Tool Group。

因此当前证据不支持“持久化消息已写乱”，而是把问题收窄到实时事件投影、
正在运行的 step 归属与可靠快照对账边界。当前 Runtime 的 reasoning/text delta
在模型流中即时发布，Tool Proposed 则在完整 AssistantMessage 结束并可靠落账后
才发布；Desktop 仅按事件到达先后追加段落，并以已投影 AssistantMessage
数量推断已提交 step。这两个接缝都需用确定性事件夹具进一步复现，
在技术方案确认前不预设只修 Desktop 或只改 Runtime 协议。

统一抽象至少必须封装以下事实：

1. **稳定边界身份**：为每次内部插入或执行段切换生成稳定身份，并明确其
   owner、`run_id`、段序号、前置可靠消息和后续 AgentExecution；
2. **冻结事实权威**：边界载荷、存储策略、可见性、所属 Run 和执行段在
   接受或提交时冻结；后续模型请求、实时事件和产品快照只能从它派生，
   不得通过到达顺序或当前 Catalog 重新解析；
3. **显式存储与可见性策略**：区分“规范且可见”、“规范但产品隐藏”和
   “仅 Provider 请求投影、不持久化”。前两者及其恢复关系必须落库；
   最后一种只能由已冻结的规范事实确定性生成，不用某个工具名猜测策略；
4. **Run 内全局单调 step**：同一 Run 内的 continuation 不得因新
   AgentExecution 重新从 step 1 计数；内插消息不分配、重置或隐藏 step；
   实时事件、可靠 AssistantMessage、用量和 Desktop 全部使用同一 `run_id + step`；
5. **原子边界提交**：需持久化的工具结果、内插消息、Activation 和 continuation
   控制事实按一个可恢复边界提交，不出现“工具显示成功但指令未落账”的半状态；
6. **统一产品投影**：桌面端只消费权威 `run_id + step` 和可靠消息，不通过当前窗口
   Assistant 数量、事件到达顺序、隐藏消息数量或工具名推断归属；
7. **统一恢复与对账**：落账、分页、SSE 断线、Session 产品快照重读、Runtime 重启和压缩后，
   均按同一边界身份收敛，不重复、不丢失、不跨段移动 reasoning、text 或工具。

修复还必须遵守以下产品口径：

- Provider request-only user-role 投影与 Runtime Hidden UserMessage 是两种事实，
  复现和测试必须分开覆盖；
- 规范 Conversation 仍是可靠顺序与重连后显示的权威，不为了修 UI 而持久化
  Provider 兼容信封；
- 实时 UI 可以在正文落账前显示增量，但一旦可靠 AssistantMessage 可见，
  必须按其有序 parts 无闪烁、无重复地收敛；
- 修复不得特判 `read_image`、`load_skill`、Goal、WorkPlan 或其他来源；新增任何
  内插消息的功能都必须接入同一抽象，不得新建平行的消息拼接与前端对账逻辑；
- 从真实数据只提取最小结构夹具，不把用户正文、图片或绝对路径提交入库。

## 八、模块边界与契约影响

### 8.1 `assistant-runtime`

- 持有 Skill 领域、候选与诊断、优先级、以名称为键的 SQLite 启停状态、
  Session Catalog binding、Activation ledger 与同 Run continuation 的权威状态。
- 负责用户与模型调用资格再校验，并把 Skill 指令与工具权限严格分开。
- 负责跨执行段累计预算、可观察事件、取消、重启恢复与终态结算。
- 持有 Provider-neutral 的“内部消息边界”协调器，统一生成边界身份、
  Run 内执行段序号、存储/可见性策略和原子提交事实；需恢复的事实以
  冻结记录为权威，通过 `run_id`、稳定边界身份与执行段序号串联。Goal、WorkPlan、
  Skill Activation 等功能模块只提供来源、载荷和策略，不各自实现续段机制。
- 负责让每个模型 step 的实时段落与已落账 AssistantMessage 按边界身份
  确定性对账，不让 Provider 投影专有的临时 user-role 信封泄漏到产品语义。

### 8.2 Runtime Host

- 实现本地 Skill Root 解析、有界扫描、`SKILL.md` 读取与 digest；普通资源继续由
  既有文件、图片和 Shell 工具按共享源目录访问。
- Host 是基础设施 Adapter，不保存第二份 Session Catalog 或 Activation 权威状态。

### 8.3 `agent-core`、`agent-tools`、`agent-context` 与 Provider Adapter

- Core 只理解通用 Tool Batch 屏障、执行段续接契约、可信 continuation 终态和
  本段已消费预算，不依赖 Skill、Session 或 RunId，也不为 `load_skill`
  定义专属分支。Run 内的权威段序号与存储边界仍由 Runtime 管理。
- `load_skill` 的定义与领域执行可由 Runtime 装配；如需 post-tool control 契约，
  必须是能被压缩等真实后继动作共用的最小通用能力。
- Context 必须保证激活指令不在压缩后无声失效，但不读取 Skill Store 或扫描文件。
- Provider Adapter 可以把规范 Tool Result 投影为 request-only user-role
  兼容信封，但该信封必须从已冻结、已落库的规范 Tool Result 及其
  `run_id`/边界/执行段关系确定性派生。Adapter 不取代应有的规范落库，
  也不额外创建产品消息、step 身份或第二份持久化事实。

### 8.4 `assistant-protocol`

- 只公开 Desktop 必需的 Skill 摘要、来源层级、调用资格、名称启停状态、
  诊断、Catalog revision、Active Skill 和用户激活意图。
- 不公开 Runtime 内部 locator、扫描器、digest 实现、存储 effect 或续段内部结构。
- 本地 Desktop 的技能设置详情可按名称读取当前来源的正文；打开四个固定来源目录
  仍通过来源枚举和 WorkspaceId 解析，不向 WebView 或 Catalog 投影暴露绝对路径。
- 实时与可靠段落统一使用最小、Provider-neutral 的 `run_id + step + part/call ID`
  契约；step 在同一 Run 内全局单调，执行段只供 Runtime 内部恢复和诊断，
  不向 Desktop 暴露；
  该契约覆盖全部
  内插来源，不按 `read_image`、`load_skill` 或 Goal 增加来源专用协议变体，
  也不公开 Responses `output_index` 等线路细节。

### 8.5 Desktop

- Settings 负责全量发现与诊断，Composer 负责本次用户显式激活，Context Panel 负责
  当前 Session 绑定和已激活事实，三者不复制权威状态。
- Desktop 不根据本地文件、Tool Result 文本或前端缓存猜测 winner/revision/active。
- 所有成功操作在 Runtime 确认后重读快照，失败保留草稿与当前有效状态。
- Composer 只投影一个待提交技能标签，再次选择执行替换；只在发送成功后
  清空该草稿标签，不把清空操作投影成 Conversation Activation 删除。
- 实时段落不以“事件到达先后”或“当前窗口内 Assistant 数量”代替权威
  step/段落身份；快照对账后不重复、不丢失、不跨 step 移动 reasoning 或工具。
- 所有内插来源共用一条实时投影、可靠快照对账与重连恢复路径；
  Desktop 不按工具名、隐藏消息类型或功能模块保留专项补丁。

## 九、可验收能力草案

1. 一个符合 Agent Skills 规范的本地目录包可被发现，同名来源严格按
   “工作区 `.ez-assistant/skills` > 工作区 `.agents/skills` > 用户根目录
   `.ez-assistant/skills` > 用户根目录 `.agents/skills`”使用确定性 Winner，
   Desktop 可查看被覆盖候选与原因；
   不扫描这四个固定 Skill Root 之外的位置。
2. 可选字段缺失或可安全忽略的类型异常使用缺省值并在需要时产生 warning；
   无效 YAML、缺少必要的 `name` / `description`、同级冲突、不可读和
   无法安全处理的定义超限产生 error 并跳过对应 Candidate，
   不自动修复原文或强行加载。
3. Session 创建时持有完整 Catalog revision 和精确 `SKILL.md` 定义，生命周期内保持不变；
   定义与名称启停变化只影响后续新建 Session，不改写已有 Session 或活动 AgentExecution。
   普通资源保留在共享 Root，按需读取当前内容。
4. 用户可从输入区查找并显式激活一个 `user_invocable` Skill；
   Composer 再次选择时替换当前技能，始终只显示一个包含技能名称的标签。
   该手动调用入口不依赖模型调用，技能标签不能脱离任务单独提交；
   发送成功后清空 Composer 标签，提交失败时保留正文、附件与标签。
5. Agent 只能加载当前 Catalog 中 `model_invocable` Skill；`load_skill` 的稳定字符串
   schema 不随列表变化，空列表、未知名称和资格不匹配以结构化 Tool Result 返回。
6. 成功激活在完整 Tool Result 批次后原子持久化，并在同一 Runtime Run 中续段；
   UI 不产生新 Run 或隐藏用户气泡。
7. 崩溃和重启不会出现“Tool Result 表示已加载，但正文未落账”的半状态，也不会重放
   历史工具副作用。
8. 已激活 Skill 在正常压缩、断线恢复和同 Run continuation 后仍生效，重复激活不无界
   复制正文。
9. Skill 按“元数据 → 指令正文 → 按需资源”渐进加载；资源不复制到 Session，使用相对
   共享 Skill Root 的路径并拒绝越界。脚本不自动执行，只能由 Agent 通过现有
   Shell 工具显式运行，并完整经过工具权限、审批、审计、超时与取消链路。
10. 设置、输入区、当前上下文和消息时间线在标准宽度、`720px`、150% 缩放、
    键盘与中文输入法下可完成完整操作；用户可见主文案使用中文，
    不直接显示 `winner`、`revision`、`user_invocable` 等内部字段。
11. 携带 Skill 的输入在 accepted 时原子冻结单个 Activation，经 Queue、
    Goal held input、重启和置顶后不丢失或改变选择；名称启停变更和
    原文件变化均不修改冻结 Input。Goal objective 不混入技能注入文本；child 中的 Catalog 与
    Activation 不越过已确定的父子 Conversation 所有权。
12. 从脱敏真实结构构造的 `read_image -> Tool Result image -> request-only
    user-role envelope -> reasoning / Tool Call` 夹具能在修复前稳定复现错位；
    修复后与 `load_skill` 激活续段、Goal、WorkPlan、Plan/Build、上下文续接/
    压缩及委派输入的结构夹具共用同一边界机制并稳定通过。
13. 运行中渐进显示、AssistantMessage 落账、Session 快照对账、SSE 断线重连和
    Runtime 重启后，reasoning、text 与 Tool Group 的顺序一致，不闪烁或重复。
14. 相同 part ID 在不同 model step 中重用、一个 Run 中多次或不同类型的
    内插边界连续出现、并行 Tool Call、分页从 Run 中部开始，均不会破坏归属。
15. Runtime Hidden UserMessage 不显示用户气泡，Provider request-only user-role
    信封不进入规范 Conversation，两者前后的可靠消息边界都可恢复；
    全部内插来源复用同一测试矩阵，不存在功能专用对账分支。
16. 所有规范消息与可恢复控制事实按策略完整落库，并能由 `run_id`、
    稳定边界身份和执行段序号还原唯一顺序；模型请求、实时事件和
    Desktop 快照均与冻结记录一致，request-only 信封可由其重建而不单独落库。
17. 技能启停以通过格式校验的 `name` 字段值直接作为 SQLite 唯一键，同名候选不按来源或层级
    分别存储开关。禁用后所有同名候选均不进入 Catalog，不产生下层候补；
    启用后不做技能级来源信任或权限审批，具体操作仍由各工具授权；开关变化
    只影响后续新建 Session。
18. 新 Session 使用当前四个固定 Skill Root 和启停状态建立初始 Catalog；Fork
    继承分支点的精确 Catalog/Activation；归档、恢复和 Runtime 重启均不重新扫描。
19. child 继承父 Run 冻结 Catalog 但不自动继承父 Conversation 的 Activation 正文；
    child 可独立激活技能，产生的规范消息、用量和续段只属于 child owner。
