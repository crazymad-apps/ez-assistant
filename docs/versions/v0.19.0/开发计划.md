- 功能基线：[`v0.19.0 功能设计`](功能设计.md)

## 二、台账与实施原则

1. 按 M0—M7 顺序实施。本计划获得确认后只开始 M0；每个里程碑完成实现与
   最小有效验证后标记为 `🟨 待确认`，获得用户确认后才进入下一里程碑。
2. 开始 M0 前将 [`版本管理`](../../版本管理.md) 从 `计划中` 更新为 `开发中`；
   计划整体确认不授权连续实施后续里程碑。
3. M0 必须先让脱敏结构夹具在旧逻辑下稳定复现 `read_image` 后的归属错位，
   记录失败形状后才修改生产契约；不先写修复再反推一个无法证明的用例。
4. 同一 Run 的 step 由 Core 从 Runtime 一次性传入的起始值直接单调递增；
   Desktop 只消费 `run_id + step`，不获得 segment、不做 offset 或 Assistant 数量映射。
5. Runtime 始终是 Skill Catalog、Activation、Input/Run、内部边界和恢复的唯一业务权威者；
   Host 只实现文件、SQLite 与传输 Adapter，Desktop 只提交意图和展示快照。
6. Skill 启用不是工具授权。不新增 Skill 级信任、权限或审批链；真实操作继续由文件、
   Shell 等具体工具的 Authorizer 和审批决定。
7. Conversation 历史只追加。旧 `Injected` Part、旧协议事件和旧 SQLite 行必须安全读取；
   不批量重写用户历史，不扫描旧 JSONL 猜测 step 或 Activation。
8. 所有 SQLite migration、故障注入、恢复和共享资源访问验证只使用 `TempDir`、内存 Store
   或隔离 Runtime Home。本计划不授权打开、迁移或写入用户实际 Runtime Home 数据库。
9. 四个 Skill Root 之外的路径、远程安装、市场、watcher、刷新当前 Session、多技能草稿、
   MCP 和跨 Session 资源去重均不得在里程碑中顺手实现。
10. 实时事件是可丢失观察，规范 Conversation、Run Snapshot、Session Catalog 和
    Activation ledger 才是恢复基线；测试不能只断言 UI 或内存状态。
11. 真实 Provider 测试保持 `#[ignore]`，只在用户明确同意产生网络请求后执行；
    不输出 credential、用户正文、reasoning、图片或私有绝对路径。
12. 不主动执行 Git commit/push；每个里程碑开始前重新核对工作树、授权、
    对应语言规范和模块约束。

## 四、里程碑明细

### M0：确定性复现与 Run step 时间线修复

前置依赖：本开发计划已确认；版本状态已更新为 `开发中`。

目标：先把 `read_image` 后 reasoning / Tool Call 串位变成可稳定失败的脱敏自动化夹具，
再以同 Run 全局单调 step 修正 Core、Runtime、可靠消息和 Desktop 的唯一归属契约。

交付范围：

- 从已完成脱敏核对的真实结构中只提取伪 Run/message/part/call ID、相对顺序、
  事件序号和 commit 时点，不进入用户正文、图片、工具参数或绝对路径；
- 先证明旧 Desktop 在缺失 `StepStarted`、相同 PartId 跨 step、可靠快照插入和分页窗口下
  可稳定串位，并记录 Chat/Responses 图片信封的正确 request-only 位置；
- 为 Core 增加可一次性注入起始值的 step 序列，所有 delta、usage 和工具事件直接携带
  最终 Run step；所有终态返回可靠 `ExecutionConsumption`；
- Runtime 只在创建 AgentExecution 时传入 `next_step`，不按事件改写 step；
  内插、压缩、Provider retry 和新 AgentExecution 均符合已确认序号语义；
- 为可靠 Assistant/Tool 消息、RunSnapshot、`run_message_refs` 和事件增加必要 step，
  并在每个可靠 step 提交后发布 `ConversationCommitted` / `StepCommitted`；
- Desktop 以 `(run_id, step)` 为唯一分组，以 `(run_id, step, call_id)` 定位工具，
  删除按 Assistant 数量、当前 active step 或文本相等的对账分支；
- 覆盖主 Run、child、多 AgentExecution、事件丢失、断线、重启、分页和旧行缺失 step 的兼容读取。

验证入口：

```bash
cargo test -p agent-core
cargo test -p agent-testkit
cargo test -p agent-openai-compatible
cargo test -p assistant-protocol
cargo test -p assistant-runtime
cargo test -p assistant-runtime-host
cargo run -p assistant-protocol --example export_typescript -- --check
cd apps/desktop
npm run test
npm run build
```

完成判定：修复前失败夹具可复查；修复后丢失 `StepStarted` 也不会串位，
任意实时事件都能仅依据 `run_id + step` 自定位，内插前后 step 严格单调且
图片信封不进入 Conversation。

Review 重点：是否真正先观察到修复前失败；Core 是否直接发最终 step；
`StepStarted` 丢失是否仍可恢复；旧历史是否被误回填或重写。

### M1：统一内插边界

前置依赖：M0 已确认。

目标：建立一套同时覆盖规范内部消息和 Provider request-only 投影的插入计划，
让 Skill、Goal、WorkPlan、压缩和委派不再各自拼装隐藏消息或时间线。

交付范围：

- 增加 Provider-neutral `ContextInsertionPlan` 与规范且产品隐藏的 `InternalContext` Part，
  保留旧 `Injected` Part 的安全反序列化；
- 建立 Runtime `InternalBoundaryCoordinator`，统一 boundary 身份、owner、存储/可见性、
  retention key 和前后可靠消息；
- Chat/Responses 从规范 Tool Results 产生 `RequestOnly` 插入计划，不按 `read_image`
  工具名创建产品消息或 Runtime boundary；
- 让 Goal、WorkPlan、压缩 continuation、Plan/Build 与委派输入通过协调器构造新消息，
  保留各自领域状态机；
- 对需恢复的工具结果、内部消息和 continuation 边界实施原子落账，
  落账失败时 fail-closed；
- 建立 Tool Result Image、Goal、WorkPlan、压缩和委派的共享测试矩阵，
  不保留功能专用 Desktop 对账分支。

验证入口：

```bash
cargo test -p agent-types
cargo test -p agent-model
cargo test -p agent-context
cargo test -p agent-openai-compatible
cargo test -p assistant-runtime
cargo test -p assistant-runtime-host
cargo clippy -p agent-types -p agent-model -p agent-context -p agent-openai-compatible \
  -p assistant-runtime -p assistant-runtime-host --all-targets --all-features -- -D warnings
```

完成判定：新产生的内部消息不再由功能模块自行拼装；该落库的规范事实均可恢复，
request-only 信封可由规范事实重建且从不落库；旧 Conversation 无需重写仍能读取。

Review 重点：公共抽象是否只承载真实共性；Provider Adapter 是否倒向依赖 Runtime；
原子边界是否存在“工具显示成功但内部消息未落账”的半状态。

### M2：Skill 发现、诊断与名称启停

前置依赖：M1 已确认。

目标：在 Runtime 领域与 Host 基础设施边界内建立完整、确定性、有界的本地 Skill 发现，
并以校验后的 `name` 作为唯一 SQLite 启停键。

交付范围：

- 在 Runtime Host 增加已确认的反序列化专用 YAML 依赖，实现 frontmatter 与正文边界；
- 只扫描工作区 `.ez-assistant/skills`、工作区 `.agents/skills`、
  用户根目录 `.ez-assistant/skills` 和用户根目录 `.agents/skills`；
- 实现来源优先级、同名 Winner、同级冲突、可缺省字段、跳过错误候选项和确定性诊断；
- 实施候选数、`SKILL.md`/frontmatter 大小、候选路径、特殊文件和不完整扫描上限；发现阶段只保留
  源目录，不枚举或读取普通资源，也不执行脚本；
- 增加默认启用的全局 `skill_name_states`，只以 `name` 为键；禁用所有同名来源且不回退下层；
- 建立 Runtime 领域、Volatile Store、Host SQLite Store 和隔离迁移/恢复测试；
- 扫描和启停均不进入 Skill 级权限判断，`allowed-tools` 不写入 Authorizer。

验证入口：

```bash
cargo test -p assistant-runtime
cargo test -p assistant-runtime-host
cargo clippy -p assistant-runtime -p assistant-runtime-host \
  --all-targets --all-features -- -D warnings
```

另用 `TempDir` 精确覆盖四 Root 优先级、缺失/不可读 Root、同级冲突、候选特殊文件、
发现阶段上限、普通资源不影响候选事实、单一名称开关、事务回滚和旧 schema 升级。

完成判定：给定相同四 Root 和名称开关时必然产生相同 Winner/诊断；
无效候选项可定位但不进入 Catalog；禁用名称不产生下层候补；未触碰用户实际数据库。

Review 重点：是否多扫了目录；目录顺序是否准确；可缺省与应跳过边界是否过度复杂；
名称开关是否被错设计成来源开关或权限门禁。

### M3：Session Catalog 冻结与共享源绑定

前置依赖：M2 已确认。

目标：让新 Session 在创建边界一次生成完整 Catalog 和模型目录投影，冻结 Winner 的
`SKILL.md` 定义事实并绑定共享源目录；之后的执行、重启、Fork、归档恢复和 child 均不重扫
当前技能定义，也不在 Session 下复制 Skill 包。

交付范围：

- 实现 Catalog Winner 定义快照、确定性 revision、ready/empty/unavailable 与结构化诊断；
- 把模型可见目录作为冻结 `SystemPromptSnapshot` Part 持久化，空目录也保留稳定形状；
- Catalog 只持久化 Winner 的精确 `SKILL.md` 正文、digest、来源和共享源目录；普通资源
  不在发现或建会话阶段枚举、读取、索引或复制，后续按 Skill 指令通过既有文件/Shell 工具访问；
- Session/Runtime Home 不创建 `private/skills`、暂存目录或其他 Skill 包副本；
- 扩展正式/易失 Session Store，并为旧 Session 提供 `legacy unavailable` 缺省；
- Fork 复制源 Session 的精确 Catalog 结构化事实而不重扫、不改写路径、不复制文件；
  归档恢复和 Runtime 重启不改写 Catalog；
- child 继承创建时的 Catalog，不继承父 Conversation 的 Active Skill；
- Session 永久删除只删除 Session 自有数据，绝不删除四个共享 Skill Root 中的文件。

验证入口：

```bash
cargo test -p agent-model
cargo test -p assistant-runtime
cargo test -p assistant-runtime-host
cargo clippy -p agent-model -p assistant-runtime -p assistant-runtime-host \
  --all-targets --all-features -- -D warnings
```

完成判定：Session 创建后修改 `SKILL.md`、切换名称开关、重启 Runtime 或 Fork，均不改变
已冻结 Catalog 定义；普通资源始终从共享源读取，文件变化会反映到后续工具访问，文件缺失则
由具体工具正常报错；旧 Session 不获得升级时的当前技能，且任何 Session 目录都没有 Skill 副本。

Review 重点：是否在每个 Model Step 重扫；文件与 SQLite 是否存在“数据库已引用、
定义未冻结”的半状态；创建、恢复、Fork 和删除是否误建、复制或删除共享 Skill 文件。

### M4：用户显式激活与应用协议

前置依赖：M3 已确认。

目标：让用户选择的单个 Skill 与完整 Input 在 accepted 边界原子冻结，
并为 Desktop 提供管理、选择、Queue、消息和当前上下文所需的最小协议。

交付范围：

- 为提交意图增加可缺省的单个 `skill_name`，Runtime 只从目标 Session 冻结 Catalog
  校验 `user_invocable`，不重读当前文件或名称开关；
- 在 Input accepted 事务中同时保存可见 UserMessage 内部 Part、结构化激活身份、
  queued Input、首次 Run 和用户 Activation ledger；
- `/goal` 与技能正交，Goal objective 只读取真实用户正文/附件；排队、置顶、取消、
  held input 和重启使用同一冻结事实；
- 增加管理列表/名称启停命令、Session Catalog、Active Skill、诊断、Queue 和
  UserMessage 单标签 DTO、稳定错误与 TypeScript 导出；
- 打通正式 HTTP Command、SSE 失效提示和 SessionView/ConversationPage 生产消费点，
  Host 不复制 Skill 状态机；
- 用正式 Host + fake Provider 验证普通输入、Goal + Skill、Queue、重启、Fork 和旧协议缺省。

验证入口：

```bash
cargo test -p assistant-protocol
cargo test -p assistant-runtime
cargo test -p assistant-runtime-host
cargo run -p assistant-protocol --example export_typescript -- --check
cargo clippy -p assistant-protocol -p assistant-runtime -p assistant-runtime-host \
  --all-targets --all-features -- -D warnings
cd apps/desktop
npm run build
```

完成判定：客户端只提交名称也能得到精确冻结 Activation；排队时间、文件变化、
开关变化和重启都不替换已 accepted Input；所有 Desktop 所需事实可从正式协议快照恢复。

Review 重点：是否由 Desktop 提交 digest/正文/路径；相同名称是否被当成多来源开关；
Goal objective 是否混入 Skill 指令；协议是否泄漏共享 Skill 源的绝对路径。

### M5：Agent `load_skill` 与同 Run continuation

前置依赖：M4 已确认。

目标：让模型和用户手动调用流程互不依赖，并让 Agent 成功加载 Skill 后使用
已落账 Activation 在同一 Run 的下一全局 step 继续，不特化 Core Agent Loop。

交付范围：

- 稳定注册 `load_skill`，`name` 使用普通字符串，无 Catalog 时也不移除工具或生成动态 enum；
- 执行时只按继承的 Session Catalog 校验 `model_invocable`，不增加 Skill 权限审批；
- `load_skill` 复用普通 `Serial` 调度，不改变同批其他工具既有的串行/并行行为；
- 以 ToolCallId 暂存成功 Activation，在 Recorder 完成整批 results 时原子落账
  Tool Results、hidden InternalContext、boundary 和 Activation ledger；
- Core 只返回通用 ContextChanged continuation 终态及可靠 consumption，Runtime 使用
  下一全局 step 建立新 AgentExecution；
- 实现 unknown、not invocable、already active、批次多调用、Store 失败、取消、压缩保留、
  child 独立激活和重启恢复；
- 确保用户显式 Activation 不另跑空 `load_skill`，Agent Activation 不伪装用户输入。

验证入口：

```bash
cargo test -p agent-tools
cargo test -p agent-core
cargo test -p agent-testkit
cargo test -p agent-context
cargo test -p assistant-runtime
cargo test -p assistant-runtime-host
cargo clippy -p agent-tools -p agent-core -p agent-testkit -p agent-context \
  -p assistant-runtime -p assistant-runtime-host --all-targets --all-features -- -D warnings
```

完成判定：成功 `load_skill` 只在完整 Tool Exchange 可靠提交后生效；存储失败不发布
伪成功工具终态；后续 AgentExecution 仍使用原 RunId 和下一全局 step；用户手动流程仍可独立使用。

Review 重点：工具 schema 是否被 Catalog 变动破坏；同批其他 Tool Call 的调度是否被无故改变；
Activation 是否在 Recorder 前提前落账；Core 是否渗入 Skill/Run 领域。

### M6：中文 Desktop 技能闭环

前置依赖：M5 已确认。

目标：依据交互指导在现有 Settings/Composer/Queue/Conversation/Context Panel 上
完成统一中文的 Skill 管理、单选激活和可恢复展示。

交付范围：

- 设置导航收口为“运行时 / 模型 / 记忆 / 权限 / 技能”，实现工作区范围、
  当前技能/诊断、名称开关、详情、覆盖关系和四 Root 目录操作；
- 设置页没有刷新按钮或 watcher；每次重新进入“技能”页和切换工作区范围时读取最新
  管理投影，切换开关使用 Runtime 命令返回的投影更新，并持续说明“对新会话生效”；
- 实现 `/skill` 搜索单选器、原始名称标签、再次选择替换、移除、
  Session 切换清空、提交成功清空和失败完整保留；
- 标签不能单独发送；Goal 与技能可同时出现但技能始终只有一个；
- Queue 技能标签位于条目右侧操作区左边，用户消息标签、“加载技能”工具行和右侧
  “技能”分区只使用协议快照，不解析注入文本、Tool Result 或当前文件列表；
- 对本版本触达的设置、Composer、Context Panel、时间线、帮助和错误做中文审计，
  将 Runtime、Workspace、System Context、Slash Command、Build/Plan、Ask/Auto 等固定产品文案收口为中文；
- 覆盖键盘、焦点返回、中文输入法、长文本、大列表、减少动态效果、
  `720px` 及更窄宽度和 100% / 125% / 150% 缩放。

验证入口：

```bash
cd apps/desktop
npm run lint
npm run test
npm run build
npm run test:e2e
```

完成判定：用户可从设置诊断到会话选择、提交、Queue、消息和当前上下文完成全链操作；

开关是否本地乐观伪造；技术字段或英文固定文案是否直接泄漏给用户。
