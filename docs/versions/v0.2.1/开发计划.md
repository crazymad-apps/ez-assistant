# v0.2.1 开发计划：版本验证 Runtime Harness

## 一、计划信息

- 版本：`v0.2.1`
- 状态：✅ 已完成并归档（2026-07-28）
- 关联文档：
  - [`功能设计`](功能设计.md)（✅ 已确认 2026-07-28）
  - [`技术方案`](技术方案.md)（✅ 已确认 2026-07-28）
- 界面交互设计指导：只在既有 debug-viewer 增加轻量通道筛选和时间线，不改变
  页面主结构，按规范跳过独立交互指导。
- 前置条件：v0.2.0 已归档；本版本功能设计和技术方案已确认。

本计划只新增独立开发工具并扩展 debug-viewer，不修改正式
`assistant-runtime`、桌面应用或后续 Core 能力。

## 二、实施原则

1. M0 → M6 严格顺序实施；每个里程碑完成验证后标记 `🟨 待确认`并停止。
2. 先稳定 workspace 和 viewer 消费端，再实现 Runtime、离线场景与真实 chat。
3. `verify v0.2` 必须完全离线；真实 DeepSeek 调用执行前单独取得用户确认。
4. Harness 自己实现内存 JournalRecorder；testkit 只提供 scripted 能力。
5. viewer 始终接收 `llm` / `agent` / `runtime`；推送选择只影响 producer。
6. 产品 crate 不依赖 runtime-harness，Core/Provider 不依赖 viewer。
7. 临时 Harness 类型不上提到 `assistant-protocol`，也不成为正式 Runtime API。

## 六、M1：debug-viewer 三通道与强类型 Agent 事件

### 目标

让一个 viewer 实例同时接收并展示模型、Agent 和 Runtime 三层事件。

### 前置依赖

M0 已确认。

### 实施内容

- `debug-viewer` 新增 `agent-core` 依赖。
- `DebugChannel` 改为 `Llm / Agent / Runtime`，移除未使用的 `Sched`。
- `DebugPayload` 新增强类型 `AgentEvent` 和 `{name,data}` RuntimeEvent。
- `DebugClient` 新增 `post_on`；现有 `post` 保持 Llm 默认兼容。
- 页面顶部保留 Session 单选，左侧固定模型输出，右侧使用三通道单选 Tab 并展示
  Agent/Runtime 轻量时间线；LLM 原始事件直接展示，Agent/Runtime 原始 JSON 可展开；
  静态资源禁用缓存以保证开发刷新生效。
- Agent/Runtime 条目不得改变模型 Turn 卡片的 open/close 生命周期。
- 同步 `docs/modules/debug-viewer.md`。

### 自动测试

- 三通道和新增 payload serde 往返。
- 旧 LLM payload 与 `post` 行为兼容。
- `post_on` 保留 channel，多通道共享 seq/correlation。
- viewer 不响应时非阻塞自静音。
- POST → SSE 广播新增 payload。

### 人工核对

启动 viewer 并注入三通道样例，确认筛选只影响展示，模型卡片不被事件时间线破坏。

### 验证

```bash
cargo test -p debug-viewer
cargo clippy -p debug-viewer --all-targets --all-features -- -D warnings
cargo fmt --all --check
```

### 完成判定

viewer 可同时接收三通道，旧 provider chat example 继续工作，代码与当前文档不再
残留 `Sched` 旧称。

## 七、M2：Harness CLI、Run 与内存 Journal

### 目标

形成不依赖真实 Provider 的临时 Runtime 状态基础。

### 前置依赖

M1 已确认。

### 实施内容

- `cli.rs`：
  - `list` / `verify v0.2` / `chat` / `--help`；
  - `--debug` 与 `DEBUG_URL` 优先级；
  - `--debug-layer provider|agent|both`，默认 both；
  - 配置错误和退出码。
- `runtime.rs`：
  - 私有 SessionId/RunId；
  - `Pending → Running → Completed|Failed|Cancelled`；
  - 单活动 Run、单调 run counter、wall-clock + monotonic 耗时。
- `journal.rs`：
  - completed messages、pending、snapshot；
  - `HarnessRecorder` 两阶段 begin/complete；
  - receipt 绑定 Run、原子 completed 投影、pending 隔离；
  - 锁中毒受控映射，运行路径不用 unwrap/expect。
- `output.rs`：事件、终态、roles 和 `/state` 控制台投影。
- `main.rs`：Tokio current-thread 入口、HarnessError 与退出码。
- 本里程碑只要求 `list` 可运行；verify/chat 可返回“尚未接入”的受控错误。

### 自动测试

- CLI 合法/非法组合、默认值和环境优先级。
- ID 不复用、状态非法转换拒绝、单活动 Run。
- begin 后 snapshot 不可见，complete 后整批可见。
- 未知 receipt、pending 阻止新 Run、reset 清理但不复用 run ID。
- Completed 追加最终 Assistant；Failed/Cancelled 不合成消息。
- `/state` 不展示 credential 或默认展开正文。

### 验证

```bash
cargo test -p runtime-harness
cargo clippy -p runtime-harness --all-targets --all-features -- -D warnings
cargo run -p runtime-harness -- list
cargo fmt --all --check
```

### 完成判定

CLI、Run 与 Journal 可独立测试，尚未接真实网络、stdin 线程或 debug 推送。

## 八、M3：v0.2 离线版本场景

### 目标

提供可直接运行且完全离线的 v0.2 累计能力验证入口。

### 前置依赖

M2 已确认。

### 实施内容

- 建立 VersionEntry / ScenarioDefinition 注册表，`list` 登记 v0.1/v0.2。
- 实现六类场景：
  - `plain_text`
  - `single_tool_loop`
  - `allow_deny_batch`
  - `controlled_failure`
  - `cancelled`
  - `observation_disconnect`
- 复用 testkit scripted model/tool/authorizer/gate；只有模型流挂起桩就近私有实现。
- `verify v0.2` 每场景使用全新 Runtime，输出 Run、事件摘要、终态、Journal roles、
  pending 和最终汇总。
- 场景失败返回 Result，全部场景跑完后统一非零退出，不用 panic 控制 CLI。

### 自动测试

- 注册表与 list 一致。
- 六类场景的关键断言。
- 单场景失败不掩盖后续报告。
- binary `verify v0.2` 退出码为 0。
- 即使环境存在哨兵 API Key，verify 也不加载 `.env` 或联网。

### 验证

```bash
cargo test -p runtime-harness
cargo run -p runtime-harness -- list
cargo run -p runtime-harness -- verify v0.2
cargo clippy -p runtime-harness --all-targets --all-features -- -D warnings
cargo fmt --all --check
```

### 完成判定

离线命令可读地证明 v0.2 代表能力，无凭据、网络、用户文件、数据库和真实 Shell。

## 九、M4：真实 DeepSeek Chat 与交互控制

### 目标

装配真实 Provider、Agent Engine、演示工具与多轮内存 Journal。

### 前置依赖

M3 已确认。

### 实施内容

- 类型化无副作用 `lookup_weather` demo tool。
- stdin 专用阻塞线程 + 容量 16 Tokio channel，Ctrl-D 等价 `/quit`。
- `chat` 仅在本模式加载 `.env`，读取 DeepSeek key/base URL/model。
- 构造 OpenAiCompatibleService，显式 `max_steps=8` / `max_tool_calls=8` 和
  AllowAll authorizer。
- 完成多轮 User → tool exchanges → final Assistant Journal。
- 支持 `/state`、`/reset`、`/cancel`、`/quit`。
- 活动 Run 中普通文本/reset 明确拒绝；quit 先 cancel 并等待清理和唯一终态。
- debug 参数可以解析，但实际推送留 M5。

### 自动测试

- demo tool schema、输入校验和输出。
- 缺 key 快速返回脱敏配置错误。
- stdin 命令分类和活动 Run 约束。
- scripted model 替代真实 Provider，验证两轮用户输入共享 Journal。
- cancel/reset/quit 的状态和 Journal 结果。

### 真实联调

真实 DeepSeek 调用可能产生费用，执行前再次向用户确认。获授权后核对真实模型触发
tool call、结果回喂、最终文本、下一轮上下文和交互命令；未授权时记录离线替代证据。

### 验证

```bash

cargo clippy -p runtime-harness --all-targets --all-features -- -D warnings
cargo fmt --all --check
```

### 完成判定

真实 chat 路径实现完整，离线替代测试通过；外部实测状态明确记录。

## 十、M5：Runtime 分层调试推送与端到端联调

### 目标

由 Runtime 选择 provider、Agent 和 Runtime 事件，并在 viewer 中按同一 Run 关联。

### 前置依赖

M4 已确认。

### 实施内容

- `DebugLayerSelection::{Provider,Agent,Both}`。
- 每 Run 一个共享 DebugClient，correlation 为 `<session>/<run>`。
- `ObservedModelService` 观察 request、建立结果和 ModelEvent。
- Agent 事件消费器发送强类型 AgentEvent。
- Runtime 发送 run start/cancel/terminal/journal updated。
- 装配规则：
  - provider → Llm；
  - agent → Agent + Runtime；
  - both → 全部，默认；
  - 无 debug URL → 不创建 client/decorator。
- viewer 失败、队列满或发送失败不得改变 execution outcome。
- 同步运行手册。

### 自动测试

- decorator 不修改请求、事件、建立错误、取消或终态。
- 三种选择不向未选择通道发送。
- 多通道 correlation/seq 一致。
- DebugClient 静音不影响 Run。
- 使用本地 viewer router 完成 Harness POST → SSE 三通道端到端测试。

### 人工核对

```bash
cargo run -p debug-viewer
cargo run -p runtime-harness -- chat \
  --debug http://localhost:7331 \
  --debug-layer both
```

确认同一 correlation 可切换三通道，provider-only/agent-only/both 符合选择，viewer
关闭后 chat 继续。真实 Provider 联调仍需单独授权。

### 验证

```bash
cargo test -p debug-viewer -p runtime-harness
cargo clippy -p debug-viewer -p runtime-harness \
  --all-targets --all-features -- -D warnings
cargo fmt --all --check
```

### 完成判定

三层事件可关联，Runtime 可选推送层，调试故障不影响执行。

- 代码审查：Journal 原子性、cancel/quit 清理、DebugClient 背压、decorator 透明性、
  credential 边界、CLI 退出码。
- 创建 v0.2.1 代码审查记录，修复发现并重新验证。

## 十四、实施顺序结论

M0 建立边界，M1 先稳定多通道消费端；M2 建立 Runtime/Journal，M3 给出离线可运行
成果；M4 再接真实 Provider，M5 完成分层调试；M6 只做审计、审查和收口。这样从
M3 起已有不依赖外部条件的验证入口，真实网络和调试接线不会反向干扰基础状态语义。
