# v0.2.1 功能设计：版本验证 Runtime Harness

## 一、设计信息

- 版本：`v0.2.1`
- 状态：✅ 已确认并归档（2026-07-28）
- 影响模块：
  - 新增 `tools/runtime-harness`
  - 复用 `agent-core`、`agent-model`、`agent-provider-openai-compatible`、
    `agent-testkit`、`agent-tools`、`agent-types`
  - 扩展 `tools/debug-viewer` 的 Runtime/Agent 调试事件展示能力
  - 不实现正式 `assistant-runtime`
- 需求来源：2026-07-28 用户会话结论——在继续 Core 后续版本前，先提供一个临时
  Runtime，用于直观看到并持续验证各版本已完成能力。

## 二、背景与目标

v0.1.0 已提供直接调用真实 Provider 的命令行 chat demo；v0.2.0 已提供基于
scripted model/tool 的离线 Engine example 和完整 Harness。两者分别证明模型 Adapter
和 Agent Engine，但缺少一个位于应用装配层、能够把 Provider、Core、工具、Run、
内存对话与调试事件串起来的可运行宿主。

正式 `assistant-runtime` 未来需要承担 Session、Run、调度、配置、持久化、权限和
恢复等产品职责。现在为了人工验证而直接填充它，会把临时交互和未确认的产品语义
固化进正式模块。因此本版本新增独立开发工具 `runtime-harness`：

1. 以 Runtime 视角装配真实或 scripted 模型、工具、Recorder 和 Authorizer。
2. 提供完全离线的版本场景验证，作为自动测试之外的可观察集成证据。
3. 提供真实 DeepSeek 交互模式，验证用户输入经过 Agent Engine、多轮工具循环后
   得到最终回答的实际效果。
4. 在 Harness Runtime 层关联本地 Session/Run，并统一把模型与 Agent 调试事件推送
   给 debug-viewer。
5. 后续每个 Core 版本在此增加一组代表性场景，形成累计验证入口。

成功标准不是取代 workspace 自动测试，而是让开发者可以用一个稳定入口回答：
“当前 checkout 已经能实际运行哪些版本能力，事件、对话投影和终态是什么样子？”

## 三、非目标

- 不实现正式 `assistant-runtime` 的公共 API，也不把 Harness 类型导出给产品代码。
- 不接 Tauri、WebView、桌面 command、托盘或窗口生命周期。
- 不接数据库、Repository、持久化迁移、重启恢复或 Scheduler。
- 不实现多 Session 并发、同 Session 排队、全局限流或后台常驻任务。
- 不实现真实 FileSystem/Shell；真实工具的路径、权限、审计和进程清理仍留正式
  Runtime/Adapter 版本。
- 不提前实现 v0.3.0 上下文系统、v0.4.0 Approval/Guardrail 或后续记忆能力。
- 不把 debug-viewer 线格式移入 `assistant-protocol`。
- 不保证在一个新 checkout 上复现旧版本二进制；历史实现仍由 Git commit/tag
  复现，Harness 的版本场景用于验证当前代码对既有能力的累计兼容。

## 四、工具定位与生命周期

### 4.1 代码落位

新增 workspace 开发工具：

```text
tools/runtime-harness/
```

它是独立可执行程序，不属于桌面产品进程，也不是 sidecar、daemon 或本地服务。
只有开发者显式运行命令时才启动，退出后不保留进程状态。

产品 crate 不依赖 `runtime-harness`。Harness 可以向下依赖真实 Agent crate、
`agent-testkit` 和 debug-viewer 客户端，因为它本身就是开发验证宿主，不进入产品
依赖闭包。

### 4.2 临时性

Harness 在正式 Runtime 与桌面端能够覆盖同等累计验证能力之前持续维护。达到以下
条件后可以删除，或收敛为纯端到端 smoke 工具：

- 正式 Runtime 已能装配真实 Provider 与工具；
- Session/Run/Journal 和事件关联已经有稳定实现；
- 桌面端或正式 CLI 已有等价的人工验证入口；
- 版本场景已有其他长期宿主承接。

## 五、使用路径

### 5.1 查看可验证版本

```bash
cargo run -p runtime-harness -- list
```

输出当前 Harness 支持的版本场景、验证模式和必要条件。v0.2.1 首期至少登记
`v0.1`（真实 Provider 单轮能力）与 `v0.2`（Agent Engine 与工具循环）。

### 5.2 离线验证

```bash
cargo run -p runtime-harness -- verify v0.2
```

该命令不读取 API Key、不访问网络、用户文件或数据库。它使用 scripted model/tool
运行代表性场景，并输出：

- 场景名称与通过/失败结论；
- Runtime Session/Run 标识；
- Agent 事件摘要与唯一终态；
- Recorder completed/pending 状态；
- 最终 Conversation Journal 投影；
- 失败时的可操作错误和非零退出码。

首期 v0.2 代表性场景包括：

1. 纯文本完成；
2. 单工具两轮闭环；
3. 同轮多工具，包含 Allow 与 Deny；
4. 模型或工具失败后的受控结果；
5. 模型流、授权等待或工具执行中的取消代表场景；
6. 普通事件拥塞或订阅断开不影响可靠终态。

该命令验证实际装配效果；精细边界矩阵仍由现有 25 个 Engine Harness 测试承担，
不在命令行场景中复制全部测试实现。

### 5.3 真实交互

```bash
cargo run -p runtime-harness -- chat
```

真实模式沿用现有 DeepSeek 配置：

- `DEEPSEEK_API_KEY`：必需；
- `DEEPSEEK_BASE_URL`：可选；
- `DEEPSEEK_MODEL`：可选。

凭据只用于构造 Provider service，不进入请求 DTO、事件、错误、日志或
debug-viewer payload。

交互模式至少支持：

- 多轮用户输入；
- reasoning 与文本增量展示；
- 一个安全的内存演示工具，用于观察真实模型触发的工具循环；
- `/state`：查看当前内存 Session、最近 Run、Journal 条目和 pending exchange
  数量；
- `/reset`：清空当前内存会话；
- `/cancel`：取消当前 Run 并等待 Core 受控收敛；
- `/quit` 或 Ctrl-D：退出。

真实 Provider 调用可能产生费用，不进入默认自动验证；执行结果必须在验收记录中
明确区分“已运行”“未运行”和原因。

### 5.4 调试查看器

```bash
cargo run -p debug-viewer
cargo run -p runtime-harness -- chat \
  --debug http://localhost:7331 \
  --debug-layer both
```

事件推送在 Harness Runtime 层执行：

- 模型 service decorator 观察 `ModelRequest`、建立结果和原始 `ModelEvent`；
- Harness 消费 `AgentExecution.events`，观察 `AgentEvent`；
- Harness 为两类事件附加同一 Session/Run correlation，再交给
  `DebugClient` 非阻塞推送；
- Core、Provider Codec 和工具实现都不直接依赖或调用 debug-viewer。

debug-viewer 仍是独立进程，Harness 只建立出向连接。viewer 未启动、队列满或发送
失败不得影响 Agent 执行。

viewer server 不按启动项绑定某一层，而是始终同时接收所有调试通道；浏览器按
`llm`、`agent`、`runtime` 筛选展示。推送方决定发送层级：

- `--debug-layer provider`：只发送 `llm` 通道的规范 `ModelRequest` /
  `ModelEvent`；
- `--debug-layer agent`：发送 `agent` 通道的 `AgentEvent` 和 `runtime` 通道的
  Run 生命周期；
- `--debug-layer both`：同时发送上述全部通道，作为默认值。

现有 Provider chat example 可以继续直接向 `llm` 通道推送；当 Provider 被
Runtime Harness 装配时，由 Runtime 的 ModelService decorator 推送同类事件，
Provider 库本身不持有 viewer 客户端。这里的 “provider” 指 Adapter 解码后的
Provider-neutral `ModelEvent`，不包含原始 SSE frame、HTTP header 或 credential。

## 六、Harness Runtime 的状态边界

### 6.1 本地标识

Harness 在应用层生成仅用于当前进程的 `SessionId` 与 `RunId`，用于控制台输出和
调试关联。这些标识不传入 `agent-core`，也不进入 `AgentEvent`。

它们是开发工具内部类型，不上提到 `assistant-protocol`，不承诺与未来正式 Runtime
标识完全一致。

### 6.2 内存 Conversation Journal

Harness 持有当前会话的内存 Journal，并为每次 Run 创建绑定该 Journal 的 Recorder：

```text
当前 ConversationSnapshot + 新 UserMessage
→ AgentExecution
→ completed tool exchanges
→ 最终 AssistantMessage / 受控失败或取消
→ 更新并展示内存 Journal
```

Journal 必须保证：

- 只有 completed tool exchange 进入规范投影；
- Assistant Tool Call 与整批 Tool Result 保持配对和顺序；
- 最终 AssistantMessage 在 Run 完成后进入后续轮次上下文；
- pending exchange 可见于 `/state`，但不进入下一次模型请求；
- reset 后旧会话状态不再进入新请求。

这些语义用于验证 Core 契约，不定义正式 Runtime 的数据库事务、失败恢复或保留策略。

### 6.3 Run 生命周期

同一进程首期只允许一个活动 Run。Run 至少具有：

- `Pending` / `Running` / `Completed` / `Failed` / `Cancelled` 状态；
- 创建时间、结束时间和唯一终态；
- `ExecutionControl` 取消句柄；
- Agent 事件消费任务；
- 与调试事件共用的 correlation。

终端输入、事件订阅或 debug-viewer 断开不得隐式取消 Run；只有 `/cancel`、进程退出
或执行自身终态会结束当前 Run。

## 七、跨层边界

### `runtime-harness`

- 拥有 CLI、临时 Session/Run、内存 Journal、装配、事件关联和输出。
- 选择 scripted 或真实 Provider。
- 执行 debug-viewer 推送。
- 不向产品 crate 提供公共依赖。

### `agent-core`

- 继续只负责一次 `AgentExecution`。
- 不增加 Session/Run ID，不感知 CLI、环境变量或 debug-viewer。

### `agent-testkit`

- 提供离线 scripted model/tool、Recorder、Authorizer 和确定性 gate。
- 不承担 CLI 或真实 Provider 配置。

### `agent-provider-openai-compatible`

- 继续只负责 Provider 协议与传输。
- 现有 chat example 可在 Harness 真实模式覆盖后保留为 Adapter 最小示例；本版本
  不要求删除。

### `debug-viewer`

- 继续拥有调试线格式、接收服务与前端展示。
- 可以新增 Runtime/Agent 事件 payload 和展示，但不进入产品协议层。
- 可以直接依赖 `agent-core` 并在调试 payload 中承载强类型 `AgentEvent`；
  debug-viewer 是位于 Core 上层的独立开发工具，不会形成产品依赖反转。

### `assistant-runtime`

- 本版本不修改其实现。
- Harness 形成的交互语义不自动成为正式 Runtime 设计；未来只能按已确认的
  Runtime 功能设计选择性吸收。

## 八、验收标准

1. `tools/runtime-harness` 可作为独立 workspace binary 构建和运行，产品 crate
   不依赖它。
2. `list` 能明确展示当前支持的版本场景和离线/真实运行条件。
3. `verify v0.2` 完全离线运行，代表性场景全部通过时退出码为 0，任一失败时非 0。
4. 离线输出能直接核对事件顺序、唯一终态、Recorder pending/completed 状态和最终
   Journal 投影。
5. `chat` 能以真实 DeepSeek 驱动至少一次多轮工具循环，最终 AssistantMessage
   进入下一轮上下文；未配置凭据时给出脱敏且可操作的错误。
6. `/state`、`/reset`、`/cancel`、`/quit` 行为可预测；取消收敛为唯一 Cancelled
   终态且不暴露未配对 Tool Call/Result。
7. 开启 `--debug` 后，viewer 能同时接收并按通道筛选模型层事件和 Agent/Run
   层事件；Runtime 可通过 `provider` / `agent` / `both` 选择推送层级，同一 Run
   的多通道事件共享 correlation；viewer 不可用不影响主流程。
8. credential 不进入控制台、错误、Agent/Model 事件或 debug payload。
9. 默认测试和 `verify` 不访问网络、数据库、用户文件或真实 Shell，不依赖 sleep
   判断并发顺序。
10. `cargo fmt --all --check`、workspace Clippy `-D warnings` 和
    `cargo test --workspace` 全部通过；运行手册说明离线验证、真实 chat、viewer
    联调和后续版本如何增加场景。

## 九、风险、兼容性与待确认项

### 风险与控制

- **临时代码反向塑造正式 Runtime**：Harness 类型保持工具内部私有，文档明确其
  非产品契约，正式 Runtime 仍走独立版本设计。
- **与现有 Harness 测试重复**：命令行只保留代表性集成场景，细粒度边界继续由
  crate tests 承担。
- **真实模型行为不确定**：真实 chat 用于人工效果验证；版本完成门槛以离线场景
  和自动测试为主，真实结果单独记录。
- **调试信息包含正文**：仅向用户显式指定的 loopback viewer 推送，继续禁止
  credential 和请求 header。
- **历史版本语义混淆**：`verify v0.2` 表示当前 checkout 仍满足 v0.2 能力基线，
  不表示运行归档时的旧二进制。

### 兼容性

- 本版本只新增开发工具和 debug-viewer 调试 payload，不改变 Agent Core、
  Provider、Runtime 或应用协议的既有公共语义；debug-viewer 新增对
  `agent-core` 的单向开发工具依赖。
- 后续版本新增场景时保留已经登记的版本场景，除非对应能力被明确废弃并记录迁移。

### 待确认项

无。以下技术细节均已在技术方案与对应开发里程碑中确认：

- CLI 子命令与内部模块划分；
- ModelService 调试 decorator 的流生命周期与背压；
- Runtime/Agent 调试 payload 的具体线格式；
- 内存 Journal 在失败、取消和 pending exchange 下的精确更新算法；
- `/cancel` 与 stdin/event 输出的并发实现。
