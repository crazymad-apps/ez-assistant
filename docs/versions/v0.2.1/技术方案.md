## 二、现状核查

基于 2026-07-28 当前仓库实际代码：

- `assistant-runtime` 只有 `session` / `run` / `scheduler` / `config` 空模块注释；
  现在写入临时交互语义会与正式 Runtime 的 Session、调度、持久化和恢复设计混杂。
- `AgentExecution::start` 已返回独立的 `events`、`completion`、`control`：
  - 普通 `AgentEvent` 走有界可丢弃流；
  - 唯一终态可靠且最后交付；
  - `ExecutionControl::cancel()` 幂等；
  - Core 不持有 `RunId` / `SessionId`。
- Core 的 `ExecutionRecorder` 已是 `begin_tool_exchange` /
  `complete_tool_exchange` 两阶段协议；最终无工具 AssistantMessage 只通过
  `ExecutionOutcome::Completed` 交给 Runtime。
- Core 每个模型 step 调用 `Arc<dyn ModelService>`；因此可以在装配期使用一个
  `ModelService` decorator 观察请求、建立结果和返回流，无需修改 Engine 或具体
  Provider。
- `OpenAiCompatibleService` 构造时绑定 base URL、credential、model 和
  `Profile::deepseek()`；credential 不进入 `ModelRequest`、事件和错误。
- `agent-testkit` 已提供 `ScriptedModelService`、`ScriptedTool`、
  `ScriptedAuthorizer`、可控 gate 和能力 fake；但现行模块文档只允许它出现在其他
  crate 的 dev-dependencies。
- debug-viewer 当前只有 `llm` / 尚未使用的 `sched` 两个通道，payload 只覆盖
  `ModelRequest`、模型建立和 `ModelEvent`；`DebugClient::post` 固定发送 `llm`。
  本版本把语义过窄且尚无生产者的 `sched` 更名为 `runtime`。
- debug-viewer 浏览器以 `correlation_id` 分 tab；`seq` 在一个 DebugClient 内
  单调递增；客户端有界、非阻塞、失败自静音。
- debug-viewer 当前只依赖 `agent-model` / `agent-types`。本版本可直接增加
  `agent-core` 依赖以承载强类型 `AgentEvent`；debug-viewer 是上层开发工具，
  Core 不依赖 viewer，因此不会形成循环或产品依赖反转。
- 当前 Tokio workspace features 足以运行 current-thread runtime、sync、time；
  stdin 可使用标准阻塞线程 + bounded Tokio channel，不需要新增异步终端依赖。

结论：新增独立 workspace binary，并对现有 SPI 做应用层装配即可；除
debug-viewer 新增对 Core 类型的只读消费外，不需要修改 `agent-core`、
`agent-model`、Provider Adapter、`assistant-runtime` 或
`assistant-protocol`。

## 四、CLI 与进程入口

### 4.1 参数模型

不引入 `clap`。`cli.rs` 使用 `std::env::args_os` 解析为私有 enum：

```rust
enum Command {
    List,
    Verify { version: VersionBaseline },
    Chat {
        debug_url: Option<String>,
        debug_layer: DebugLayerSelection,
    },
}

enum VersionBaseline {
    V0_2,
}

enum DebugLayerSelection {
    Provider,
    Agent,
    Both,
}
```

支持：

```text
runtime-harness list
runtime-harness verify v0.2
runtime-harness chat
  [--debug <url> | --debug=<url>]
  [--debug-layer provider|agent|both]
runtime-harness --help
```

- 缺少子命令、未知版本、重复参数或缺失 `--debug` 值返回配置错误和非零退出码。
- `DEBUG_URL` 作为 `--debug` 的次级来源；显式 CLI 参数优先。
- `--debug-layer` 缺省为 `both`；未启用 debug URL 时允许解析但不产生推送。
- `list` / `verify` 不加载 `.env`，确保离线模式不会意外读取 credential。
- 只有 `chat` 调用 `dotenvy::dotenv()` 并读取 DeepSeek 配置。

### 4.2 错误与退出码

私有 `HarnessError` 使用 `thiserror`，至少区分：

- `Cli`
- `Config`
- `Provider`
- `ToolRegistration`
- `Journal`
- `Execution`
- `ScenarioFailed`
- `Io`

错误展示只输出可操作的分类和脱敏文本。建议退出码：

- `0`：成功；
- `2`：CLI/配置错误；
- `1`：运行、场景或 I/O 失败。

不把 API Key、Authorization header、完整环境变量或 HTTP 请求正文放入错误链。

## 五、Harness Runtime 与 Journal

### 5.1 内部标识与状态

定义工具私有 newtype：

```rust
struct HarnessSessionId(String);
struct HarnessRunId(String);

enum RunStatus {
    Pending,
    Running,
    Completed,
    Failed,
    Cancelled,
}
```

- 进程启动生成一个 session ID：`session_<pid>_<start_unix_ms>`。
- Run ID 为 session 内单调序号：`run_1`、`run_2`……
- correlation 使用 `<session_id>/<run_id>`。
- 标识不进入 Core、Provider 请求或 `assistant-protocol`。

`HarnessRun` 保存：

- ID、状态；
- `SystemTime` 开始/结束时刻与 `Instant` 单调耗时；
- `ExecutionControl`；
- 唯一 `ExecutionOutcome`；
- 本 Run 观察到的 Agent 事件摘要和丢弃计数。

同一时刻最多一个活动 Run。状态转换只允许：

```text
Pending → Running → Completed | Failed | Cancelled
```

### 5.2 Journal 状态

```rust
struct JournalState {
    messages: Vec<ConversationMessage>,
    pending: Vec<PendingExchange>,
    next_exchange: u64,
}

struct PendingExchange {
    receipt: ExchangeReceipt,
    assistant: AssistantMessage,
}
```

`HarnessJournal` 内部使用 `std::sync::Mutex<JournalState>`：

- 锁只保护纯内存克隆与 Vec 更新；
- `ExecutionRecorder` 返回立即就绪的 boxed future；
- 不持锁 `.await`；
- 不发生文件、网络或数据库 I/O。
- 锁中毒转换为 `RecordError` / `HarnessError`，运行路径不使用 `unwrap` /
  `expect`。

### 5.3 Recorder 算法

`HarnessRecorder` 持有 `Arc<HarnessJournal>` 和当前 `HarnessRunId`。

`begin_tool_exchange`：

1. 锁定 Journal；
2. 生成 `<run_id>_exchange_<n>` receipt；
3. 把完整 AssistantMessage 加入 pending；
4. 释放锁并返回 receipt。

`complete_tool_exchange`：

1. 锁定 Journal；
2. 精确找到 receipt；不存在返回 `RecordError`；
3. 先在临时 Vec 中组装 Assistant + 全批 ToolMessage；
4. 一次性追加到 `messages`；
5. 删除 pending 并释放锁。

结果批次为空或 call/result 配对异常不由 Recorder 重新解释；Core 已负责执行语义。
Recorder 只保证 receipt、原子可见性和 pending 隔离。

### 5.4 每次 Run 的 Journal 更新

启动前：

1. pending 非空时拒绝新 Run，提示 `/state` 后 `/reset`；v0.2.1 不实现恢复算法。
2. 从当前 completed messages 创建 `ConversationSnapshot`。
3. 生成 run-prefixed User `MessageId` / `PartId`。
4. 把 UserMessage 追加到 Journal，同时作为 `ExecutionInput.user_input`。

执行中：

- tool exchange 由绑定当前 Run 的 Recorder 直接原子追加；
- pending 永不进入 `snapshot()`。

终态：

- `Completed(message)`：把最终 AssistantMessage 追加到 Journal；
- `Failed` / `Cancelled`：不合成虚假 AssistantMessage，保留已经确认的 User 和
  completed exchange；
- 任一终态后更新 Run 状态和结束时间。

下一次 Run 只消费 completed messages。若上次失败/取消后没有 pending，允许继续；
这是 Harness 的演示策略，不上升为正式 Runtime 持久化或恢复契约。

### 5.5 `/state` 与 `/reset`

`/state` 输出不可变快照：

- Session ID；
- 当前/最近 Run ID、状态和耗时；
- completed message 数与角色顺序；
- pending receipt 数和对应 AssistantMessage ID；
- 最近终态与 `dropped_events`。

不输出 credential。消息正文默认不在 `/state` 展开，详细正文通过显式 debug 模式
或 viewer 查看。

`/reset` 只在无活动 Run 时允许；它原子清空 completed/pending Journal 和最近
Run，保留进程 session ID 与单调 run counter，避免同一进程内复用 correlation。

## 六、真实 Chat 装配

### 6.1 Provider 配置

沿用现有环境变量：

```text
DEEPSEEK_API_KEY       # 必需
DEEPSEEK_BASE_URL      # 缺省 https://api.deepseek.com
DEEPSEEK_MODEL         # 缺省沿用当前 chat example
DEBUG_URL              # 可选
```

创建：

```rust
OpenAiCompatibleService::new(
    base_url,
    BearerCredential::new(api_key),
    model,
    Profile::deepseek(),
    TransportTimeouts::default(),
)
```

v0.2 Engine 当前机械构造默认 `GenerationConfig` / `ProviderOptions`；Harness 不修改
Core 以注入 DeepSeek thinking 开关。真实模式验证的是当前 Core + Provider 的实际
默认装配能力，reasoning 仅在 Provider 实际返回时展示。

### 6.2 演示工具

`demo_tool.rs` 实现一个类型化 `lookup_weather`：

- 输入：`{ city: String }`，`Deserialize + JsonSchema`；
- 输出：固定、明确标记为 demo 的 JSON 天气结果；
- 无网络、文件和系统副作用；
- 描述要求模型在回答天气问题前调用该工具。

`chat` 的 `ExecutionSpec` 使用：

- 固定系统 instructions：说明演示工具与回答纪律；
- 已绑定的真实 ModelService（可选 debug decorator）；
- 只含 `lookup_weather` 的 `ToolSetSnapshot`；
- `max_steps = 8`、`max_tool_calls = 8`，避免人工模式无限消耗；
- `AllowAllAuthorizer`。

这些上限是 Harness 显式规格，不是 Core 隐藏默认值。

### 6.3 stdin 与活动 Run

使用一个标准阻塞线程读取 stdin，每行通过容量 16 的
`tokio::sync::mpsc::Sender::blocking_send` 送到 current-thread Tokio 主循环。
阻塞只发生在专用输入线程，不阻塞模型/工具任务。

无活动 Run：

- 普通非空文本启动新 Run；
- `/state`、`/reset`、`/quit` 立即处理；
- `/cancel` 提示当前无活动 Run。

有活动 Run：

- `/cancel` 调用 `ExecutionControl::cancel()`，状态保持 Running，直到 Core
  收敛到 Cancelled；
- `/state` 可读取快照；
- `/quit` 先请求取消并等待终态/清理，再退出；
- `/reset` 与新的普通用户文本明确拒绝，不静默排队。

Ctrl-D 等价 `/quit`。输出与输入提示可能交错，但每条事件保持完整行；本版本不引入
终端 UI 库。

### 6.4 执行消费

每个 `AgentExecution` 拆成：

- 事件消费任务：打印 AgentEvent，并推送 agent debug channel；
- completion future：决定 Run 终态和 Journal 最终更新；
- control：留在活动 Run 接收 `/cancel`。

主循环必须等待事件消费任务结束后再宣布 Run 完成，保证可靠终态已经被观察。
事件订阅 drop 或 viewer 失败不改变 completion 结果。

## 七、调试事件方案

### 7.1 线格式

viewer server 始终接受全部通道，不通过启动参数把实例固定成 provider-only 或
agent-only。`POST /ingest`、SSE `/events` 和一个浏览器页面承载混合事件流，
`DebugEnvelope.ch` 负责区分来源层。

扩展 `DebugChannel`：

```rust
enum DebugChannel {
    Llm,
    Agent,
    Runtime,
}
```

扩展 `DebugPayload`：

```rust
AgentEvent {
    event: agent_core::AgentEvent,
}
RuntimeEvent {
    name: String,
    data: serde_json::Value,
}
```

- `AgentEvent` 直接使用 `agent_core::AgentEvent`，由 Rust 类型和 serde 测试保证
  线格式与 Core 事件同步，不增加中间转换层。
- `RuntimeEvent` 的 `name` 首期包括 `user_message_appended`、`run_started`、`cancel_requested`、
  `run_completed`、`run_failed`、`run_cancelled`、`journal_updated`。
- `user_message_appended` 在 Runtime 接受输入并写入 Journal 后发送一次；Viewer
  将其渲染为独立用户消息。Provider `TurnRequested` 只展示请求快照，不再作为用户
  消息来源，避免一个 Run 的多个模型 Step 重复展示同一输入。
- `data` 只放 Session/Run 标识、状态、耗时、计数和脱敏错误；不放 credential。
- 现有 payload 和 JSON tag 保持不变，旧 chat example 与 viewer 继续兼容。
- `llm` 中的 provider 事件是 Adapter 解码后的 Provider-neutral
  `ModelRequest` / `ModelEvent`，不增加原始 SSE frame、HTTP header 或 credential
  payload。

### 7.2 推送层选择

Runtime Harness 的 `DebugLayerSelection` 控制装配，而不是控制 viewer：

| 选择 | `llm` | `agent` | `runtime` |
| --- | --- | --- | --- |
| `provider` | ✅ ModelRequest / ModelEvent | — | — |
| `agent` | — | ✅ AgentEvent | ✅ Run/Journal 事件 |
| `both`（默认） | ✅ | ✅ | ✅ |

- `provider`：给真实 ModelService 套 `ObservedModelService`，但 Agent 事件只输出到
  控制台。
- `agent`：直接装配真实 ModelService，不创建模型观察 decorator；Agent 与 Run
  事件推送 viewer。
- `both`：模型、Agent 和 Run 三路事件共用同一个 DebugClient。
- 未配置 debug URL：不创建 DebugClient，也不创建仅为调试存在的 decorator。
- 现有 `agent-provider-openai-compatible/examples/chat.rs` 仍可作为独立推送方发送
  `llm` 事件；Provider 库实现本身不依赖 debug-viewer。

### 7.3 DebugClient

新增通用方法：

```rust
pub fn post_on(&self, channel: DebugChannel, payload: DebugPayload);
```

现有 `post(payload)` 保留，内部等价 `post_on(DebugChannel::Llm, payload)`。
同一个 Run 共用一个 `Arc<DebugClient>`，因此三个通道共享：

- correlation `<session>/<run>`；
- 全局单调 `seq`；
- 同一有界队列和失败自静音状态。

### 7.4 ModelService decorator

`ObservedModelService`：

```rust
struct ObservedModelService {
    inner: Arc<dyn ModelService>,
    debug: Arc<DebugClient>,
    endpoint: String,
    configured_model: String,
}
```

`stream` 顺序：

1. clone 并推送 `TurnRequested`；
2. 记录 `Instant`，调用 inner `stream`；
3. `Err` 时推送 `EstablishmentFailed`，原错误返回；
4. `Ok(stream)` 时推送 `TurnEstablished`；
5. 用 `StreamExt::inspect` 对每个 `ModelEvent` clone 后非阻塞推送；
6. 原事件流和生命周期原样交回 Core。

decorator 不修改 request、context、取消、事件顺序或错误。调试序列化/入队失败只告警
并静音，不得转换为模型错误。

### 7.5 浏览器展示

`app.js` 保留现有模型 Turn 卡片逻辑，并新增轻量时间线条目：

- `agent_event`：显示事件 `type`、tool call ID、step 或终态；
- `runtime_event`：显示 Run 状态和 Journal 计数；
- `ch` 使用不同 badge；
- 页面顶部按 correlation 的 session 部分聚合 Session 单选，同一会话的多个 Run
  只产生一个 Tab，模型流卡片状态仍按完整 correlation 隔离；左侧固定展示模型输出，右侧放置 Agent/Runtime 时间线
  与通道选择，`llm` / `agent` / `runtime` 使用单选 Tab 切换查看；LLM 展示原始事件，
  Agent/Runtime 可展开完整原始 JSON。筛选只影响展示，不影响 server 接收或 SSE 广播；
- 静态资源响应使用 `Cache-Control: no-store`，保证开发期间普通刷新即可读取当前
  HTML/CSS/JS；
- 完整原始 JSON 仍进入 raw 面板。

Agent/Runtime 事件不得改变 `openCard`，避免与模型流卡片生命周期互相干扰。

## 八、离线版本场景

### 8.1 注册表

```rust
struct VersionEntry {
    version: &'static str,
    capabilities: &'static [&'static str],
    offline_verify: Option<VersionBaseline>,
    manual_modes: &'static [&'static str],
}

struct ScenarioDefinition {
    name: &'static str,
    baseline: VersionBaseline,
    run: fn() -> ScenarioFuture,
}

struct ScenarioReport {
    name: &'static str,
    status: ScenarioStatus,
    run_id: HarnessRunId,
    terminal: RunStatus,
    event_summary: Vec<String>,
    journal_roles: Vec<&'static str>,
    pending_count: usize,
}
```

`list` 从 `VersionEntry` 与场景注册表生成输出，避免帮助文本与实际场景漂移。
首期 `v0.1` 登记真实 Provider 单 Turn 能力及 `chat` 人工入口；`v0.2` 额外登记
离线场景和 Agent 工具循环能力。`verify v0.2` 顺序执行全部 v0.2 场景，每个场景
使用全新 HarnessRuntime 和确定性 ID。

### 8.2 v0.2 代表场景

| 场景 | 装配 | 核对重点 |
| --- | --- | --- |
| `plain_text` | scripted final text，无工具 | 唯一 Completed、User + final Assistant |
| `single_tool_loop` | 两个 model scripts + 成功工具 | 两个 step、两阶段 Recorder、完整 Journal |
| `allow_deny_batch` | 同批两工具 + scripted authorizer | Allow 执行、Deny 错误回喂、循环继续 |
| `controlled_failure` | 建立前模型失败与工具错误子用例 | Failed 或错误 ToolResult 路径可见 |
| `cancelled` | 本地 pausable model / AuthorizeGate / hanging tool 子用例 | `/cancel` 等价 control 路径、清理后唯一 Cancelled |
| `observation_disconnect` | drop 事件消费者或制造普通事件拥塞 | completion 与可靠终态不受影响 |

已有公共 testkit 无法表达的“模型流挂起”只在 `scenario/v0_2.rs` 定义一个私有
`PausableModel`；不因单一消费点扩展 testkit 公共 API。

每个场景做少量关键断言并生成可读报告；25 个 Engine Harness 的完整预算、Recorder
失败和事件矩阵继续是权威自动测试。

### 8.3 场景失败

- 场景断言不使用 `panic!` 控制 CLI 结果，返回 `Result<ScenarioReport, HarnessError>`。
- `verify` 运行全部场景后汇总，避免第一个失败掩盖后续状态。
- 任一失败最终返回 `ScenarioFailed` 和非零退出码。
- 测试代码内部仍可使用 `assert!` / `expect`。

- 场景注册表和 list 输出。

集成测试：

- 启动 binary 执行 `list`；
- 启动 binary 执行 `verify v0.2`，断言退出码 0、全部场景和 summary；
- 缺凭据的 `chat` 快速失败且不泄漏环境值；
- 未知子命令/版本返回配置退出码。

### 9.2 debug-viewer

- 三种 `DebugChannel` 与新增 payload serde 往返；
- `post` 仍默认为 Llm，`post_on` 保留指定 channel；
- 多通道共用 seq/correlation；
- provider-only、agent-only、both 三种装配不会向未选择通道推送；
- POST → SSE e2e 接收新增 payload；
- viewer 不可响应时主流程不阻塞；
- 浏览器人工核对模型卡片与 Agent/Run 时间线不会互相覆盖。

## 十一、风险、兼容与排除项

### 风险

- `agent-testkit` 成为 binary 普通依赖：通过“仅开发工具例外 + 无产品反向依赖 +
  cargo tree 审计”控制。
- stdin 线程与流式输出交错：以完整行输出和 bounded channel 控制，不引入终端 UI。
- Run 取消时直接退出可能遗留工具资源：`/quit` 必须先 cancel 并等待 Core 完成清理。
- debug-viewer 事件量扩大：继续使用容量 256 的 fire-and-forget 队列，丢失只影响
  观察；seq gap 可见。
- Journal 的失败/取消策略与正式 Runtime 不同：类型私有、文档显式标注，不向
  产品层传播。
- Core 的 ToolMessage ID 是执行内序号，跨 Run 可能重复；Harness 不篡改 Core
  产物，当前 `ConversationSnapshot` 不要求 MessageId 全局唯一。真实 Runtime
  设计时需重新核对持久化主键与协议 ID 的关系。

### 兼容性

- `DebugClient::post` 和全部既有 payload 保持兼容；
- 新 channel/payload 对旧前端至少仍可在 raw 面板显示，更新后的前端提供专门视图；
- Agent Core、模型和工具公共 API 无变更；
- 原 provider chat example 与 agent-testkit engine demo 保留。

### 排除项

- 不新增数据库或文件写入；
- 不实现真实文件/Shell；
- 不实现正式 Runtime 恢复、重试、调度和并发；
- 不把 Harness ID 或调试 payload 放入 `assistant-protocol`；
- 不为未来 Provider 提前抽象通用配置注册表；
- 不修改 v0.3.0 及后续 Core 能力范围。
