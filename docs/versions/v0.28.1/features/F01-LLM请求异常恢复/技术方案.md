# v0.28.1 F01 技术方案：LLM 请求异常恢复

- 状态：已实现并通过自主验收，待人工测试；2026-09-27。
- 功能与验收依据：[版本总体与功能设计](../../总体设计.md)。
- 实施步骤：[开发计划](开发计划.md)。

## 现状与复用

- `crates/agent-model/src/retry.rs` 已有有限重试、错误分类、退避、Retry-After 与取消；`retry_tests.rs` 已有边界测试。
- `crates/assistant-runtime/src/runtime/model.rs` 装配重试服务，`run/model_diagnostics.rs` 接收请求尝试事件。先补齐现有链路，不在 UI 或 Host 再套重试循环。
- 原 `apps/desktop/src/stores/contextUsage.ts` 合并快照与活动用量；已沿 UI-012 的生产者核对“最近 step”与“累计 Run”来源，并删除会覆盖权威快照的旧合并，结论见下文。

## 实施方案

1. 既有显式重试配置优先；未配置时由 Runtime 显式装配产品默认值：最多重试 5 次（含首次请求共 6 次尝试），间隔 1/2/4/8/16 秒，Retry-After 上限 30 秒。`[runtime.model_retry] enabled=false` 可关闭；原有完整策略表缺少 enabled 仍启用。只对连接、超时、限流、暂时不可用错误重试，认证、参数、取消等错误直接收口。
2. 自动重试限于模型请求建立失败；流已建立后中断、部分输出或执行结果未知时，本版默认不自动重放，明确展示失败。重试不重新提交用户输入、不重启整个 Run、不重复执行工具。
3. 使用现有尝试事件更新客户端原有执行状态行；RunSnapshot 仅新增可选 `model_request` 观察投影，引用同一 RunModelDiagnostics 状态，断线后从快照恢复。请求进度不落库，取消、建流和终态清除；失败继续沿用现有持久 Run 错误摘要，页面刷新后从最新 Run 恢复。父模型观察器不再用于 child 或压缩调用，它们共享无父观察器的模型服务与同一重试策略，不相互污染。
4. UI-012 核查确认 live usage 来自最近完整 step，未把累计 Run 值误当单步值；但前端 `max(快照占用, 旧 step 用量)` 会让旧 step 覆盖较小的新快照。删除该合并，Composer/ContextPanel 直接消费 Runtime SessionView.context；已有 UsageUpdated/ConversationCommitted/压缩事件触发快照刷新。累计消耗保持独立存储口径。

## 修改边界与验证

- 主范围：`agent-model`、Runtime 模型装配与诊断、客户端运行状态和用量展示；协议只补现有投影无法表达的必要信息。
- 与 F03：重试本身不依赖通知；最终状态供 F03 消费，同一事件只在一处解释。
- 定向验证请求次数、退避取消、不可重试错误、流中断和工具只执行一次；用量测试使用不同 step 与压缩前后数据，防止累计值冒充窗口占用。
- 风险：Provider 对超时的结果可能未知，不承诺服务端请求绝对只执行一次。协议改动需核对 Rust/TS 全部生产者、消费者和持久化影响。

## 实施核对结论

- 复用 RetryingModelService，不改变 agent-model/Core 的重试边界；没有新增表、迁移、持久请求状态或消息。
- 新增 `ModelRequestStatus` 是 Run 既有易失请求进度的跨层投影，由 Runtime 与 Desktop 两处消费；无独立身份或生命周期。删除这一字段将无法在重连时恢复等待状态，因此只保留此必要协议增量。
- 旧 Run JSON 缺少可选 model_request 按空读取；已有错误持久化形状不变，客户端只识别 Runtime 固定脱敏摘要，不展示 Provider 原文。配置缺省变化明确记录，显式策略继续优先，运行中配置仍冻结。
- timeout 的服务端结果可能未知，自动重试只保证不重复本地用户输入和已提交工具，不承诺 Provider 计费或服务端生成恰好一次。
