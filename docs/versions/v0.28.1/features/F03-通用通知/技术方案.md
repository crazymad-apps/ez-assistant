# v0.28.1 F03 技术方案：通用系统通知

- 状态：2026-09-27 用户确认 F03 验收通过；完成范围与后续 F04/版本联合验收边界见开发计划。
- 功能与验收依据：[版本总体与功能设计](../../总体设计.md)。
- 实施步骤：[开发计划](开发计划.md)。

## 现状与复用

- 用户明确要求 Windows、macOS 桌面端和 Chrome 浏览器三种场景的系统通知。`AppMessage` 是应用内操作反馈，不能承担本项的系统通知验收。
- `crates/assistant-protocol/src/event.rs` 已有执行与审批事件；客户端已有 Runtime 投影与会话定位能力。复用这些业务事实，不复制 Run、审批或待反馈状态。
- 当前检查的 Desktop 依赖与 native-bridge 中未发现系统通知适配。新增窄的平台通知接口有实际的原生与浏览器两个实现边界；不为此建立新的通知业务数据库。

## 实施方案

1. **统一来源入口**：turn 结束、交互反馈、审批等来源提供稳定事项标识、类型、简短标题/摘要与目标身份（Runtime、用户、会话及具体事项）。业务来源不判断操作系统，由通知适配层完成权限检查、发送和点击回调。普通“保存成功”等操作仍使用已有 AppMessage。
2. **Windows/macOS**：官方插件的 Actions 仅保证移动端，因此采用窄的原生适配：macOS 使用 `mac-usernotifications` 的安全异步接口调用 UNUserNotificationCenter；Windows 使用现有 `windows` crate 的 Toast API 和 Activated 回调。原生事件经 Tauri Channel 返回主窗口，复用既有唤起逻辑，再由客户端重读事项。命令只暴露给主 WebView，参数有界且不接受业务动作；等待属于可取消的 command future，设有数量与时长上限，页面重载会取消旧句柄。不增加仓库 unsafe 代码。Windows 安装包的应用身份与实际激活仍需实机验证，API 交叉编译不等于验收。
3. **Chrome**：使用标准 Notifications API 发送浏览器承载的系统通知，不依赖 Tauri；点击时聚焦对应页面并定位原事项。显式检测安全上下文、API 和通知权限，用户点击“启用通知”后才请求授权。内网普通 HTTP 地址不满足安全上下文要求，验收使用受信任 HTTPS；localhost 的本机例外不能推广到内网 IP。不得要求用户关闭浏览器安全限制。
4. **权限与展示**：提供启用/关闭、权限状态与测试通知入口。拒绝或撤销权限后不反复请求，提供系统/浏览器设置指引并保留应用内待处理入口；未获得权限、发送失败或系统免打扰时不宣称用户已收到。通知只带必要摘要，不携带凭据、完整对话或文件内容。

   Windows Win32 应用首次发送前，`ToastNotifier.Setting` 可能返回 `ERROR_NOT_FOUND`；此时参照 Windows Community Toolkit 初始化通知身份：发送禁止弹窗、静音且短时过期的临时通知，立即按应用身份、独立分组与 tag 移除，再读取系统实际设置。仅处理这一错误，不把其他失败当作授权，也不改写系统通知开关。已初始化身份直接查询，权限验证不得依赖用户先成功发送测试通知。
5. **去重与定位**：使用原有事项身份，在当前 Runtime/用户范围去重；同源多标签页协调单次发送，桌面与浏览器分别按自身通知开关投递。重连恢复未处理事项，不把历史事件全部重发为系统通知；点击时重新核对权限与事项状态。关闭通知不等于审批、回答或终止任务，切换用户不能打开旧账号事项。
6. **生命周期**：本次实现覆盖桌面进程运行时的前台、最小化和隐藏窗口，以及 Chrome 页面仍存活、事件连接有效时的前台/后台标签页。通知接收不能只挂在当前会话组件上。网页冻结/丢弃、关闭所有页面或桌面进程退出后，不能靠原有页面 SSE 保证新通知；本次不提供进程退出或关闭页面后的推送。若后续纳入，需要另行评估 Web Push、Service Worker 与投递服务。macOS 主窗口显式关闭后台节流；该 WebView 配置由 macOS 14+ 支持，较旧系统的隐藏窗口接收不作保证，实际隐藏/托盘行为仍须实包验证。

实现落点为 `features/notifications`、`native-bridge/systemNotifications.ts` 与原生 `system_notification` 模块。RootStore 从已通过事件水位校验的全局事件接入，快照不会触发提醒；浏览器通过 Web Locks 与有限的 SHA-256 投递回执协调标签页，回执不保存会话正文或待办状态。点击期间发生账号、Runtime 或导航变化时丢弃旧请求。

返回位置按来源处理：turn 返回原会话（含已归档会话）；审批返回父会话的审批区，展开并选中对应 `approval_id`，子任务审批也使用这一唯一入口；已处理审批只展示最新会话并提示状态。子任务内容目标使用既有子任务视图，反馈问题通过 F04 的业务导航回调定位。连续点击以最后一次为准，窗口聚焦或旧读取迟到不能覆盖新目标；成功切换时关闭设置并清除旧引用定位。通知点击本身不执行审批或回答，测试通知仅聚焦应用。

## F04 ask_user 接入契约

该接入口是本版必需实现，供 `wait` 和 `end_turn` 共用；F03 定义通知适配接口，F04 提供待反馈事实与定位目标。先落实接口再并行开发，不能只预留空方法而遗漏最终接入。

| 接入时点 | F04 提供的事实 | F03 行为 |
| --- | --- | --- |
| 问题成功发布 | 已登记且可查询的待反馈请求身份、用户/Runtime/会话/owner 归属、简短提示 | 经统一策略触发一次待反馈系统通知；一组 questions 只发一条 |
| 回答、取消或失效 | 同一请求的最新业务状态 | 标记通知目标不再待处理；平台支持时移除对应系统通知，旧通知被点击时仍重新核验 |
| 通知被点击 | 原请求对应的会话与问题定位目标 | 唤起/聚焦客户端并打开该问题；已处理显示结果，失效提示状态，不重新创建等待 |
| 客户端重连/快照恢复 | 当前待反馈快照 | 恢复处理入口，不把恢复快照当作新的问题重复提醒 |

- 身份复用 Runtime 现有请求及归属标识，作为去重和定位依据；不要求模型传通知 ID、渠道或 `notify` 参数，不再建立一份等待状态。
- 工具输入校验失败、登记失败或尚不可查询时不通知；end_turn 的待反馈发布与执行终态需协调，仅发待反馈通知，不重复发任务完成通知。
- 来源适配位于客户端全局事件/快照消费处，不绑定问答组件是否挂载或当前选中会话；`ask_user` 工具不直接调用 Windows/macOS/Chrome API。
- 通知关闭、发送失败或授权拒绝均不能回填答案、取消请求或阻塞问题发布；用户仍可在应用内回答。发送采用受控的非阻塞调用，等待用户的业务流程不等待通知送达。
- 已提供 `feedbackPublished(target)`、`resolved(target)` 和 `registerFeedbackNavigator(callback)`；target 包含当前 scope、owner、run_id、request_id。F04 必须在可靠登记之后调用发布，在重连恢复时不调用发布；点击回调负责重读并定位最新问题。
- 同一 Run 的轮后反馈发布会抑制其后到达的普通完成通知；终态 `awaiting_feedback` 也能覆盖客户端错过发布事件的情况。轮内回答后的正常完成仍可通知，失败不被此去重隐藏；不可用通知发送失败来改变等待状态。
- 契约样例已覆盖一组一条、完成通知抑制、解决后的移除与失败隔离。F04 已接入真实来源并完成两模式本地与 Chrome 联调；Windows/macOS 原生反馈通知及三端完整场景保留联合验收，样例不替代最终验收。

## 修改边界与验证

- 主范围：客户端来源适配与导航、native-bridge、Tauri 通知依赖/权限和原生激活、Chrome 通知与权限设置；Runtime 保持业务权威状态，不向远端 Host 所在机器误发用户桌面通知。
- 向 F04 提供同一系统通知入口。普通气泡反馈保留原职责，不强制所有短时交互都发系统通知。
- 本地 Chrome 自动化使用 localhost 安全上下文与真实 Notifications API/Host/SSE，覆盖投递、点击路由、审批过期、权限撤销和跨标签协调。它不证明操作系统横幅已出现；受信任 HTTPS、Windows/macOS 实机点击及后台场景保留人工验收。
- 三端分别实测 turn 结束、审批、反馈请求，授权/拒绝/撤销、后台接收、点击回到正确事项、重复事件、多标签页与断线恢复；Windows 用安装包，macOS 用实际应用包，Chrome 在 Windows/macOS 上核对表现。
- 系统通知到达由操作系统/浏览器策略决定；权限拒绝和免打扰是受限场景，应用应正确说明。三端正常授权场景必须看到真实系统通知，应用内兜底不能代替通过。

## 平台依据

- [Tauri 通知插件](https://v2.tauri.app/plugin/notification/)：支持 Windows/macOS；Windows 有安装形态要求，Actions API 标注为移动端能力。
- [Notifications 标准](https://notifications.spec.whatwg.org/)：安全上下文、通知权限、点击与关闭语义。
- [Chrome 团队 Web Push 概览](https://web.dev/articles/push-notifications-overview)：系统通知展示与后台 Push 是两种能力；关闭页面后的接收需要额外的推送链路。
