# v0.28.1 总体设计与功能设计：执行可靠性、资源交付与用户交互闭环

## 一、设计信息与需求依据

- 目标版本：`v0.28.1`。
- 状态：已完成并归档；2026-09-27 用户确认按实际结果通过整体验收。未取得完整实测结论的原生及跨 Feature 场景作为已知限制保留，不记作已执行。
- 需求来源：2026-09-27 用户提出的 LLM request 异常重试、用户期望产物列表、通用系统通知（Windows、macOS、Chrome）、两种模式的阻塞反馈工具；Windows 测试中发现的产物图片预览失败、右栏预览/下载失效和 Finder 文案不匹配；[UI-012 运行中用量口径待核查](../../inputs/260910-UI界面零碎改进清单.md)。
- 本版组织方式：用户确认把各 Feature 的功能设计集中写在这一份版本文件中；Feature 目录只保留简化技术方案与开发计划，引用这里的行为和验收，不再各写一份功能设计。此安排仅适用于 `v0.28.1`，不改变其他版本的流程。
- 2026-09-27 新增需求：用户要求纳入企业中心 Token 用量统计及调用正文“未采集”问题，登记为 F06；服务商与模型合并为一个维度。F06 已实现、完成隔离验证并部署到本地 7320 测试环境，不改变 F01—F05 的已有完成边界。

## 二、版本背景与最终目标

当前 Runtime 已有可配置的有限模型请求重试、工具文件引用、Run 事件和审批入口，但它们尚不足以共同回答用户在执行过程中的四个问题：请求异常后会怎样继续、任务最终交付了什么、何时需要关注任务、Agent 等待反馈时回复会如何进入对话。Windows 测试还发现产物图片预览和右栏文件预览、下载存在故障；这些基础操作必须可靠，正式产物列表才能交付可用结果。

本版目标是让执行过程在异常和等待状态下保持可理解、可恢复，并让用户直接看到真正要求交付的产物。通知和反馈应作为可供不同任务来源复用的产品能力，而不是分别写在某个页面或业务流程中的特殊分支。

版本完成时，用户应能：

1. 在可安全恢复的 LLM 请求异常后看到有限自动重试的结果；无法安全重试或重试耗尽时，得到明确状态和下一步操作，不产生重复工具副作用。
2. 查看任务的正式产物列表，清楚区分用户期望交付的文件与中间脚本、缓存、临时资源；列表中的产物能打开或定位，失效项不会冒充可交付结果。
3. 在 Windows、macOS 桌面端和 Chrome 浏览器收到系统通知，获知 turn 结束、需要交互反馈、等待审批等重要事件；点击通知能唤起/聚焦对应客户端并回到原会话或待处理事项。
4. 回答 Agent 主动提出的阻塞问题；轮内反馈作为当前工具调用的结果继续执行，轮后反馈作为新的 user message 开始后续 turn，两者在界面和对话记录中都可辨认。
5. 在 Windows 桌面端和通过 Windows Host 访问的 Web 端预览产物图片、在右栏预览及下载文件；Windows 上与文件位置有关的文案使用“资源管理器”。
6. 在企业中心按个人/全部、小时/天/月和模型查看经过中心代理的 Token 用量，能追溯到调用明细，并理解、配置和核查真实请求/响应正文的采集状态。

## 三、范围与非目标

| 候选 Feature | 本版应形成的能力结果 | 与其他项的关系 |
| --- | --- | --- |
| F01 LLM 请求异常恢复 | 在现有有限重试能力上完善可重试分类、执行边界、进度反馈和失败收口；核查运行中上下文窗口与累计 Token 的展示口径，复现问题后修复 | 为通知提供可观察的重试与终态，但不依赖通知才能正确执行 |
| F02 正式产物列表 | 对任务明确记录和展示“要交给用户的产物”；中间处理文件仍可在资源工作区查看，但不自动混入正式产物 | 复用现有文件引用和资源能力，具体声明与更新方式在简化技术方案中确定 |
| F03 通用系统通知 | 提供与通知来源解耦的机制接口，兼容 Windows/macOS 原生通知和 Chrome 浏览器系统通知，首批接入 turn 结束、反馈请求和审批请求 | F04 的待反馈提醒接入此机制；不为每种来源单建通知体系 |
| F04 阻塞反馈工具 | 提供轮内与轮后两种明确模式、等待状态和用户回复入口，并正确衔接各自的对话语义 | 复用 F03 的通知入口；等待及恢复实现边界在简化技术方案中确定 |
| F05 跨平台资源预览与下载修复 | 修复产物图片预览、Windows 桌面与 Web 端右栏预览/下载；按实际运行平台显示文件管理器文案，失败时给出可见反馈 | 与 F02 的正式产物打开/下载验收共同验证；先核对消息图片、Host 路径、右栏、Native 和 HTTP 调用链，再确定最小修复范围 |
| F06 企业中心用量统计与调用采集修复 | 以中心代理调用为依据统计 Token，支持个人/全部、小时/天/月、“服务商 / 模型”联合维度筛选；明确正文采集状态并修复经核实的采集或展示缺陷 | Center 持有用量事实，Admin 查询展示；与 F01 联合核对重试请求的消耗，不以 Runtime 累计数再次入账 |

上述编号仅标识 `v0.28.1` 内的 Feature，不是开发顺序或已经确认的技术方案。F05 是本版新增的缺陷修复边界，不预设故障一定发生在前端或 Host。UI-012 先作为 F01 的展示口径核查项；数值接近本身不构成故障结论。

本版不把所有工具输出、资源文件或执行脚本重新定义为正式产物；不把所有模型错误无条件自动重发；不将轮后反馈伪装成旧工具结果；不以通知机制取代会话、Run、审批和消息各自的权威业务状态。Windows、macOS 和 Chrome 的系统通知是本版必需能力；邮件、第三方 IM 不在本版范围。关闭所有网页或退出桌面进程后继续接收通知的生命周期范围，在 F03 实施前落实，不从系统通知支持自动推导后台推送能力。

### 各 Feature 的功能行为

| Feature | 用户使用路径与关键行为 | 异常与边界 |
| --- | --- | --- |
| F01 | 用户发送消息后，遇到可安全重试的 LLM 请求异常时，当前执行自动有限重试并显示重试状态；最终成功则继续原任务，失败则显示原因与可行的后续操作 | 用户取消立即停止后续重试；部分输出或结果未知时不能把已执行工具或用户输入重复提交。运行中窗口占用与累计消耗分别展示，UI-012 需先复现再确定修复范围 |
| F02 | 任务执行过程中明确形成要交给用户的文件清单；用户在正式产物列表查看、打开或下载这些文件，仍可在资源工作区查看中间资料 | 中间脚本、缓存和临时文件不因存在于目录中自动成为正式产物；文件不存在或已失效时给出明确状态，不显示为可下载的成果。声明方式由简化技术方案确定 |
| F03 | 用户启用系统通知并授权；turn 结束、需要反馈、等待审批等来源通过同一接口触发所在设备的系统通知，点击后回到对应会话或处理入口 | Windows、macOS、Chrome 均需实测；权限拒绝或浏览器非安全来源时明确说明；多会话、重复事件及断线重连不串扰，关闭通知不代表已处理 |
| F04 | Agent 提出需要用户回答的问题后，界面显示等待状态和明确的回复入口；轮内回复回填为当前工具结果并继续执行，轮后回复作为新的 user message 进入后续 turn | 普通新消息不能无提示地冒充待反馈答案；离开页面、取消、重连和重复提交均保持两种模式原有语义 |
| F05 | 用户在消息中预览产物图片，在右栏打开文件并下载；Windows 桌面和连接 Windows Host 的 Web 端均可完成；Windows 的文件定位操作显示“资源管理器” | 路径无效、文件缺失或下载失败时显示可见错误；资源只从所属 Host 的受控读取入口获取，不能把 Host 文件当成客户端本机文件 |
| F06 | 管理员按全部或指定用户查看用量趋势、“服务商 / 模型”分布和调用明细；在调用记录中了解正文是否启用采集，启用后可查看新调用的真实请求和响应 | 用量统计不依赖正文保存开关；上游未返回用量、流中断和历史无数据均明确展示，不能作为 0 或完整统计；历史未保存正文不能补造 |

本版允许并行准备 Feature 方案。实现时按实际修改文件、协议、状态和验证环境划清归属：F03 的通知入口先形成可供 F04 接入的稳定契约；F02 与 F05 共享资源展示链路，需要协调修改和联合回归；其余可独立推进的部分不互相等待。并行不取消每项自己的验收和版本整体验收。

### F06 用量统计与调用采集细则（方向已确认）

- **范围与权限**：首期按企业管理后台场景设计，“个人”指管理员筛选指定用户，“全部”指当前企业中心全部用户；身份依据中心鉴权后的用户 ID。同一用户跨设备/Host 合并统计，绕过中心的个人直连模型不计入。首期不新增普通成员自助入口，不开放现有管理员调用记录接口。
- **统计维度**：用户、时间范围及小时/天/月粒度、“服务商 / 模型”联合维度为必需；同时支持调用类型（业务代理/配置测试）及转发结果。“服务商 / 模型”使用一个选择器和一种分组，内部以服务商实例 ID 与模型 ID 联合标识，不提供两个独立统计维度，也不自动合并跨服务商同名模型；模型/用户改名或停用不能使历史记录丢失。时间固定按 Asia/Shanghai 分桶，以调用开始时间归桶，范围采用左闭右开；未结束调用标明进行中。
- **统计指标**：展示输入、输出、总 Token、调用次数，以及可获得的缓存命中输入明细；推理输出作为输出子项仍按上游字段采集，但不在首期用量页面展示。缓存与推理不再次加到总量。供应商语义不一致的字段不能强行相加，缺失子项不伪造为 0。沿用现有转发结果及耗时展示，不把 HTTP 2xx 或转发完成等同于模型任务成功。
- **来源与完整性**：从上游实际响应中的 usage 提取，覆盖 Chat Completions/Responses 和流式/非流式；支持的字段映射在技术方案中核实。正文采集关闭或快照超限时仍独立提取用量；无 usage、解析失败、不支持的编码、流中断分别保留原因，展示已知用量及统计覆盖情况。代理经过请求不保证一定拿到完整 usage，不按字符估算冒充真实数据。
- **请求粒度与重试**：每次实际代理尝试独立记录，有上游用量即计入，包括失败/取消前已报告的用量；缺失用量的尝试仍计入请求次数并标明未知。重复的终态 usage 不重复相加，不能把重试的真实消耗去重掉，也不叠加客户端累计上报。配置测试单列，默认业务视图排除测试并明确筛选范围。
- **查看路径**：统计视图提供汇总、时间趋势、用户或“服务商 / 模型”分组，沿用后台主题与控件；点击统计项进入带相同用户、时间、服务商实例与模型 ID、调用类型及结果条件的调用列表，明细展示该次 usage 和来源状态。查询在服务端聚合全部符合条件的记录，不对当前列表分页求和。
- **“未采集”核查结论**：迁移 `002-models-and-calls.sql` 将正文采集默认设为关闭；请求开始时依照策略将快照标记为 disabled。7320 测试环境已核实策略、修复快照目录，并在开启后用新代理请求验证请求和响应正文均可读取。旧记录未采集的正文无法恢复，统计用量与正文开关独立。
- **采集修复范围**：将 disabled 明确展示为“当时未启用正文采集”，列表显示当前策略及入口；启用后用新请求核验请求与响应两侧真实正文。保存失败、截断、文件缺失、过期和编码不支持分别展示原因，不能统一称为未采集。仍显示 disabled 时核查请求开始时策略、实际连接的中心和记录时间；已启用却不能读取正文时沿快照写入/读取链修复。不自动改变既有部署的采集策略，也不声称能够恢复此前未采集的数据。
- **存储与保留**：优先扩展现有调用记录承载每次 usage，不另建第二套调用生命周期；正文文件和统计数值分开管理。现有正文/索引默认保留 7/90 天，索引清理会限制可查历史；统计页必须展示有效数据范围，超出保留范围不呈现为零消耗。首期沿用现有可配置索引保留期（默认 90 天，最多 3650 天），月粒度不意味着无限期保留；管理员可通过现有策略延长未来留存，但已删除数据不会恢复。不引入独立汇总表或后台任务；升级前无 usage 的历史调用保留未知，不从无正文记录推算。
- **非目标与默认策略**：首期不默认纳入费用结算、预算/限额、告警、部门/项目归属或独立计费系统；这些需要价格和组织归属等额外事实。首期管理员查询、沿用现有索引保留期、正文继续默认关闭；本轮文档设计不修改现有环境配置。

影响模块为 `apps/enterprise-center`（代理观察、调用持久化、聚合与权限）和 `apps/enterprise-admin`（统计及调用展示），涉及数据库字段与 OpenAPI/生成 SDK；正式 Host 目前 Chat 流式请求已设置 `stream_options.include_usage=true`，优先复用。[F06 技术方案](features/F06-企业中心用量统计与调用采集修复/技术方案.md)明确有界流式解析、数值范围、幂等结算、既有数据与升级影响、保留策略和定向验证；不得为提取 usage 静默改写透传请求或中断原有转发。F06 与 F01 只增加联合验收，不重开已完成实现。

### F04 问答交互细则

F04 的模型参数、参考实现与消息格式见 [F04 技术方案](features/F04-阻塞反馈工具/技术方案.md)。本节集中记录用户行为，供 Desktop/Web 共用。

- **工具与模式**：一个 `ask_user` 工具，默认 `mode=wait`；用户回答后继续当前执行。`mode=end_turn` 用于提交阶段性结果、等待后续反馈，当前执行结束，答案成为下一轮用户消息。界面使用“等待你回答”“等待你的回复”等自然文案，不向普通用户显示 tool result、Run 或模式枚举。
- **问题组织**：优先一个问题，最多四个有关联的问题；有选项时每题 2—4 项，支持单选或多选。无选项就是文本输入，是否题使用普通两个选项。每题始终可填写自由文本，选中答案后也能补充说明；不默认勾选推荐项。
- **呈现位置**：消息流展示提问记录，当前会话问答面板与审批组件一样抢占输入区，等待期间隐藏普通输入框，两者引用同一待反馈状态。等待只阻塞对应任务，不使用阻止全应用操作的强制弹窗；用户仍可看资料、滚动记录和切换会话。ask_user 两种模式均接入 F03：问题成功发布后按通知设置发出系统通知，一组问题只提醒一次；点击后定位到该面板，通知内不直接完成审批或提交答案。通知失败不影响等待或回答。
- **多问题操作**：一个问题直接展开；多个问题通过短标题/序号及“上一题/下一题”切换，标记完成情况，切换不丢已有填写。当前题有选择或非空文字后可进入下一题；最后一题若仍有遗漏，主按钮定位未答题，全部填写后才允许一次提交整组答案。用户可回答“暂不确定”，系统不能替用户推断答案。选中选项本身不触发执行，避免尚未补充说明或尚有其他题时提前继续。导航与状态合并为一行，选项采用轻量行式布局，可选说明以弱化文字跟随名称、空间不足时自然换行，清除选择放在选项提示旁；选项下明确标注可选补充说明。
- **提交**：最后一步轮内主按钮“回复并继续”，轮后为“发送回复”；均使用现有标准按钮。提交中禁用重复发送，服务端成功接收后才清理草稿；失败保留填写并允许重试。键盘可访问选项和按钮，自由输入支持多行，Ctrl/Cmd+Enter 执行当前主按钮的下一题、定位未答题或提交动作，中文输入法组词期间及重复按键不触发；切题后焦点进入当前题，普通输入不抢焦点。
- **取消等待**：面板不提供收起或最小化，只有提交回答或明确“取消”才释放当前输入区；切换会话不取消等待；“取消”终止本次等待，轮内同时停止当前执行，轮后不创建新消息。两种情况均不伪造答案。已回答、已取消或重启后失效的历史卡片只读，迟到回复有明确提示。
- **普通输入与草稿**：提问出现时保留原输入框文字和附件。问答草稿按用户、Runtime、会话和请求隔离；页面仍在时切换会话及网络重连保留填写。回复入口明确关联问题；用户若改发其他新指令，先取消等待，待取消确认后恢复普通输入框，再手动发送，不把普通消息无提示地解释为某题答案。页面刷新后至少恢复已发布问题与已提交答案，未提交草稿是否跨刷新保留沿现有草稿能力核实，不因此把敏感内容另存全局缓存。
- **消息呈现**：轮内回答显示在工具问答记录内，不额外生成用户消息；轮后回答作为正常用户消息显示，再开始新一轮执行。结束本轮等待反馈时只提示待反馈，不同时发送“任务已完成”通知。等待无默认自动超时，拒绝系统通知不影响手动回答。

单题示意（2026-09-27 按用户要求抢占输入区、禁止收起；复用审批面板配色与容器、现有字段和按钮）：

```text

```

## 四、共同产品与架构边界

- Runtime 继续持有会话、Run、等待事项与业务结果的权威状态；桌面和 Web 端负责展示与提交用户意图。断线重连后应能从权威状态恢复仍需处理的事项，不能只依靠一次性前端弹窗。
- LLM 重试只针对能够判定安全的请求边界；不得因重试复制已提交的工具调用或用户消息。部分流式输出、响应结果未知、取消与超时的具体判定留给 F01 设计，但必须在实施前明确。
- 正式产物是面向用户的交付事实，不等同于目录扫描结果或“工具曾引用过的文件”。产物缺失、被移动或失效时，展示必须与实际文件状态相符。
- 资源引用解析必须匹配文件实际所在的 Host 操作系统，同时保持现有本地文件访问边界；图片预览、右栏预览与下载不能因 Windows 盘符或路径分隔符而静默失效。
- 系统通知通过统一来源接口对接 Windows/macOS 原生与 Chrome 浏览器适配；运行在用户正在使用的客户端设备上，不在远端 Host 机器上替用户弹窗。AppMessage 继续负责应用内短时反馈，不能替代系统通知验收。通知引用原有会话、Run 和待处理状态，重复、延迟和已处理通知不能导致重复操作。
- Chrome 通知需要安全上下文与用户授权；内网普通 HTTP 访问必须明确告知限制，使用受信任 HTTPS 验证系统通知。权限申请由用户操作触发，拒绝后保留应用内待处理入口。
- 反馈问题必须关联发起它的会话和执行上下文。轮内模式保持工具调用与结果配对；轮后模式结束当前 turn，用户回复进入新的 user message，不回填旧工具结果。取消、离开页面、重连与恢复不能悄悄改变这两种模式。
- 企业中心以实际经过本中心的代理调用持有统计事实，客户端只查询展示；Token 提取与正文留存分别控制，不能因关闭正文采集而停止统计。统计扩展不改变透明代理、不在中心增加模型重试，不以猜测填补缺失用量。

## 五、版本整体验收

1. **异常恢复与用量口径**：覆盖可重试、不可重试、重试耗尽、用户取消和流式输出中断等场景；结果与请求次数可核对，工具副作用不重复，用户能辨识当前状态。复核多轮、压缩后及运行中窗口占用与累计消耗；若复现 UI-012，修复后两者按各自口径更新。
2. **产物识别**：一个同时生成正式图纸、辅助脚本与临时文件的任务只在正式产物列表列出图纸等明确交付项；可打开的产物确实存在，失效项有明确反馈。
3. **三端系统通知**：Windows 安装包、macOS 应用包和 Chrome 浏览器分别验证 turn 结束、反馈请求及审批请求的真实系统通知，点击能唤起/聚焦并定位正确事项。覆盖前台/后台、授权/拒绝/撤销、多会话、多标签页、重复事件、断线重连及事项已处理场景；Chrome 在受信任 HTTPS 下验证，并核对 Windows/macOS 表现。应用内提示不能替代任一端验收，系统免打扰不被误报为通知已读。
4. **反馈语义与可用性**：轮内回复成为对应工具结果并继续当前执行；轮后回复形成新的 user message 和后续 turn。覆盖纯文本、单选、多选、组合问题、补充文字、中文输入法及标准按钮；选择不自动提交。两种模式的等待、取消、重复提交、断线恢复及排队输入行为可区分，提交失败不丢输入。通过代表性模型调用核对工具描述、参数生成与模式选择，不仅测试 JSON 是否合法。
5. **跨 Feature 闭环**：出现模型异常后需要用户介入的任务，能通过正确通知回到原会话；用户反馈后继续执行并最终看到正式产物。验收基于实际 Runtime 与客户端组合，不以单项 Feature 通过代替版本整体验收。
6. **跨平台资源交付**：在 Windows 桌面端和连接同一 Windows Host 的 Web 端，分别验证消息内产物图片预览、右栏图片/文档预览及下载；失败时显示具体反馈。Windows 的定位操作显示“资源管理器”，macOS 仍使用对应平台文案；原有 macOS 资源操作回归通过。
7. **企业中心统计与调用采集**：覆盖个人/全部、跨小时/天/月边界、“服务商 / 模型”联合维度与同名模型隔离、配置测试排除、流式/非流式两协议、重复 usage、缺失 usage、取消与重试；聚合与调用明细一致，缓存/推理不重复计数，用户权限不能越界。关闭正文采集时仍有已知用量；启用后新请求的两侧正文可实际读取，历史 disabled 不被误标成功，快照失败及保留期外数据有明确反馈。与 F01 联合核对多次代理尝试消耗；验证统计观察不改变原始转发内容和取消行为。

2026-09-27 版本验收检查：Rust 全量测试、协议兼容、Desktop/Client/Center/Admin 构建与定向检查通过；F01、F02、F03、F04、F05 的隔离正式 Host 浏览器链路通过，Desktop no-bundle Release 构建通过。F06 的隔离库验证与 7320 测试环境真实代理、用量及双侧正文快照已核验。此前与视口滚动规范冲突的旧测试断言已修正并通过定向回归。

已知限制：Windows 原生保存对话框、Windows/macOS 原生问答与系统横幅、Chrome 受信任 HTTPS 后台通知尚无完整实测结论；模型异常后经通知、反馈到正式产物的单条跨 Feature 任务，以及正式 Runtime 重试经 Center 代理后的逐次用量，尚未单独完成端到端验证。用户确认按这些限制验收，不能据此将第 3、5、6、7 项未执行部分写作已逐项通过；本版未公开发布。
