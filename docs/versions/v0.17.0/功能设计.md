# v0.17.0 功能设计：工具图片回流与 Responses API

## 一、设计信息

- 版本：`v0.17.0`
- 状态：已完成（2026-08-20）
- 版本主题：可恢复的工具图片产物与 `openai_responses` 独立模型协议
- 影响模块：`crates/agent-types`、`crates/agent-model`、`crates/agent-core`、
  `crates/agent-tools`、`crates/agent-tools-local`、`crates/agent-context`、
  `crates/agent-openai-compatible`、`crates/assistant-runtime`、
  `crates/assistant-protocol`、`apps/runtime-host`、`apps/desktop`
- 需求来源：[`Agent 工具图片回传与 Responses API`](../../inputs/260819-Agent工具图片回传与Responses-API.md)；
  `v0.16.0` 已归档的图片附件、原生视觉与辅助识图基线；2026-08-19 用户会话确认

本文档固化本版本已经确认的工具图片文件回流与 Responses API 首版边界。输入记录中的
开放设想若未被本文档明确吸收，仍不构成功能契约。后续开发计划和实现只在本设计范围内
推进，不自动引入浏览器操作、远端 Responses 状态或其他 Provider 内建工具。

## 二、背景与问题

`v0.16.0` 已经让用户附件图片可以通过稳定文件引用进入原生视觉模型或辅助视觉模型，
但工具结果目前只能保存文本或 JSON。当 Agent 需要在执行过程中读取本地图片时，
现有契约无法把图片作为一等 Tool Result 内容回传给后续模型调用。

只返回原始本地路径会使恢复、重试和迁移依赖一个可能已经变化或消失的外部文件；
把 Base64 直接写入 Conversation、SQLite 或 Journal 又会显著放大文本持久化、读写和迁移成本。
本版本因此先建立一条最小、可靠的图片文件回流链路，并用通用 `read_image` 工具完成
首个真实生产与消费闭环。

## 三、版本目标与成功标准

### 3.1 工具图片目标

1. 让工具结果能以 Provider-neutral 的有序 Image Part 表达图片，不在规范 Conversation
   中保存图片 Base64、Data URL、Provider URL 或 Provider file ID。
2. 新增单图 `read_image(path)` 工具，把通过授权和内容校验的图片物化为当前 Session
   的稳定工具图片，再以 Image Part 返回。
3. 同一份图片字节在同一 Session 内只保存一份；Agent 重复读取或并发读取时可以
   产生独立工具调用记录，但不产生重复图片文件。
4. 根据当前主模型和协议能力，将规范图片结果投影为原生多模态 Tool Result 或兼容图片输入；
   文本主模型继续通过已有 `inspect_images` 工具获得辅助视觉模型返回的文本 Tool Result。
5. 让图片引用和字节随 Conversation 恢复、上下文选择、Run 重试、Session Fork、
   Runtime Home 整体迁移与 Session 删除共同遵守明确生命周期。

### 3.2 Responses API 目标

1. 新增明确的 `openai_responses` 协议，与 `openai_chat_completions` 并存；Provider 差异继续
   作为同一协议下的方言处理，不为 DeepSeek、Qwen、GLM 或 Kimi 创建伪协议名。
2. 首版统一使用 `store: false` 和本地完整历史回放。规范 Conversation 是唯一权威来源，
   不依赖 `previous_response_id`、远端 Conversation 或 Responses 查询/删除接口。
3. 覆盖普通文本、图片输入、函数调用、函数结果、reasoning、usage、明确终态和恢复所需的
   最小 input/output item 与流式事件集合。
4. 将 reasoning 中不可解释但必须回传的内容作为 ProviderState 保真持久化，并按精确模型路由
   隔离；没有加密状态的方言不伪造该字段。
5. 保持规范 Tool Call/Result 批次的原始顺序和原子边界，在协议不能把图片直接放进
   `function_call_output` 时，确定性构建请求级兼容图片输入，不制造新的业务用户消息。
6. 只有文档契约与真实连接测试均通过的精确 `(provider, protocol, model_id)` 才默认启用；
   未知 OpenAI-compatible 端点不自动升级，也不在失败后静默回退到 Chat Completions。

### 3.3 总体成功标准

- `read_image` 读取受支持图片后，当轮模型能通过已选投影路径实际理解图片，
  不会只收到文件路径或一条虚假的“已读取”文本。
- Conversation 只保存工具图片相对路径和实际 MIME；图片正文、Base64 和外部源路径
  不进入 Conversation、SQLite 文本列、Journal 或普通调试事件。
- 重复读取相同字节的图片，`tool-images/` 内文件数不增加；不引入全局缓存、
  跨 Session 引用计数或逐引用 GC。
- Runtime 重启后仍可从规范 Tool Result 重建图片模型输入；Session 迁移时只需保留
  会话目录相对布局，无需重写 Conversation 中的物理路径。
- 工具图片默认不进入附件栏或产物栏；Desktop 仅在对应工具详情中展示有界预览与
  不可用状态。
- 历史工具图片缺失、损坏或 MIME 不一致时明确失败，不按已经可能变化的原始外部
  路径自动重读，也不静默省略图片后继续请求。
- Responses 会话在 Runtime 重启后只依赖本地 Conversation 和会话文件恢复，不要求远端
  response ID 仍然存在；使用 Chat Completions 的既有模型配置和会话行为不发生隐式变化。
- 多函数调用、图片工具结果、reasoning 状态、上下文压缩与所有终态均有离线 fixture，首批
  启用路由还有真实连接证据，且 wire 顺序不受工具实际完成顺序影响。

## 四、明确非目标

本版本不包含：

- 浏览器打开、页面导航、DOM 查询、CDP、Playwright、无头渲染、computer-use 或屏幕控制；
- 为浏览器截图、computer-use 截图或图片生成器集成具体生产工具；未来工具可以复用
  本版本的 Image Part 契约，但不是当前验收项；
- 把所有普通工具文件都自动转换为模型上下文内容；非图片文件仍只保留既有路径、
  工具详情或产物投影；
- 通用 `SessionFileReference`、媒体资源 `scope`、全局内容寻址存储、跨 Session 去重、
  引用计数或独立图片 GC；
- 图片编辑、生成、搜索、视觉定位框、分割、像素级测量、自研 OCR 或本地视觉模型；
- 将工具图片自动提升为用户附件、工作区文件或用户显式保存的产物；
- 新增单 Session 可恢复归档的导入/导出协议；现有 Markdown 导出仍只是人可读展示；
- 用操作系统文件权限宣称形成强沙箱；Shell 继续以当前用户权限运行，可以绕过
  结构化文件工具的目录限制；
- Responses 内建的 Web Search、Code Interpreter、MCP、computer-use、文件/PDF/OCR、
  图片生成、音频、视频或其他托管工具；
- `previous_response_id`、远端 Conversations、Responses GET/DELETE、background mode、
  远端生命周期管理、Responses Compact 接口或手工 Prompt Cache 管理；
- Structured Outputs 等未列入首版边界的高级响应形态；
- 对任意 OpenAI-compatible 端点进行运行时协议探测、试错式降级或 Chat/Responses 隐式切换；
- 把 `inspect_images` 识别文本另存为派生缓存、由 `read_image` 隐式调用辅助模型，或对
  Agent 显式重复发起的辅助识图调用自动免除计费。

## 五、工具图片产物契约

### 5.1 规范 Tool Result 内容

Tool Result 从单个 Text/JSON 值扩展为保持顺序的 Part 列表。本版本确认三种语义 Part：

- Text：模型可见文本；
- JSON：需要保持结构的 JSON 值；
- Image：指向当前 Session 工具图片目录的稳定图片引用。

Image Part 的持久化逻辑形态为：

```json
{
  "type": "image",
  "relative_path": "<sha256>.<ext>",
  "media_type": "image/png"
}
```

契约约束：

- `relative_path` 虽使用相对路径名称，本版本只允许单层合法文件名
  `<sha256>.<ext>`；禁止绝对路径、路径分隔符、`.`、`..` 和其他越界形态。
- Runtime 始终以当前 Session 目录下的固定 `tool-images/` 为根目录解析，
  Conversation 不保存 Runtime Home、Session 绝对路径或资源 `scope`。
- `<sha256>` 是已验证原图字节的内容哈希，只用于当前 Session 内稳定命名与去重；
  不构成全局 Blob 身份。
- `<ext>` 与 `media_type` 来自 Runtime 对实际字节的嗅探和校验，不信任输入路径的扩展名。
- 不增加图片宽高、原始源路径、原始文件名、Attachment ID、哈希字段、可见性
  `scope`、Base64、Provider URL 或 Provider file ID。
- Part 顺序是规范 Conversation 事实。协议 Adapter 可以为目标协议重建 wire 表达，
  但不能改写或丢失规范顺序。

旧 Text/JSON Tool Result 必须继续可读。具体 Rust 类型形态、Serde 兼容策略与数据迁移是
后续技术方案的必须项，本文档不预定类型名。

### 5.2 `read_image` 工具

`read_image` 是本版本唯一新增的具体图片产物工具：

```text
read_image(path: string) -> one Image Part
```

- 一次只读取一张图片；多图由 Agent 显式发起多次工具调用，不在工具内扫描目录。
- `path` 使用现有 Session/Workspace 可读文件语义解析，并经过普通工具解析、授权、
  取消、超时和审计链路；知道路径不等于获得访问权。
- 来源可以是 Session 附件、Session/Workspace 中的可读图片或授权允许的其他本地图片；
  无论来源是否已稳定，成功结果都统一物化到当前 Session 的 `tool-images/`。
- Runtime 按实际字节判定是否为受支持静态图片，不根据扩展名或模型声称猜测。
  损坏、超限、动画或不支持的内容返回稳定错误 Tool Result，不产生 Image Part。
- 只有当图片文件已经原子提交到 `tool-images/` 后，才能持久化成功 Tool Result；
  避免 Conversation 指向尚未存在或只存在于临时路径的文件。
- 工具错误继续使用现有错误 Tool Result 语义；失败时不把部分图片、临时路径或
  原始外部路径作为成功内容保存。

## 六、会话内存储、去重与生命周期

### 6.1 目录与所有权

工具图片使用 Session 自有、Runtime 管理的独立目录：

```text
data/sessions/<session-id>/
  attachments/
  tool-images/
    <sha256>.<ext>
  private/
```

- `tool-images/` 与 `attachments/`、`private/` 同级，不放入 Agent 可写的 `private/`。
- Runtime 负责创建、校验、物化和清理该目录；结构化文件写入、编辑、移动和删除工具
  必须拒绝以该目录为目标。
- 已提交文件使用只读文件权限作为防误操作措施，但不宣称这能限制以当前用户
  权限运行的 Shell。
- Agent 不使用 `tool-images/` 内部物理路径作为日常文件工作区；Runtime 只在模型投影、
  工具详情和恢复链路中解析 Image Part。

### 6.2 会话内去重

1. Runtime 读取并验证源图字节，计算 SHA-256，并从实际 MIME 选择规范扩展名。
2. 候选文件先在同一 Session 目录范围内暂存，再通过原子、不覆盖提交到
   `tool-images/<sha256>.<ext>`。
3. 目标已存在时校验它与期望内容一致并直接复用；重复和并发读取不覆盖稳定文件。
4. 每次工具调用仍保存自己的 Tool Call/Result、权限、时间和状态；去重只复用图片
   正文，不合并审计事实。

不为了阻止 Agent 重复调用而引入隐式调用拦截器。工具描述可以告知模型已读取的图片无需
重复读取，但正确性依靠幂等物化，不依赖模型一定遵守提示。

### 6.3 恢复、Fork、迁移与清理

- 每次从 Conversation 恢复或构建模型请求时，Runtime 都使用当前 Session 目录的
  `tool-images/` 与 `relative_path` 拼接，不依赖创建时的 Runtime Home 绝对路径。
- Context Layout 可以随所属 Tool Message 整体选入或裁剪 Image Part；文件不因暂时离开
  模型上下文而提前删除。
- Fork 创建新 Session 时，把已进入分支 Conversation 的工具图片复制到新 Session
  自有的 `tool-images/`；可保留同一相对文件名，不建立跨 Session 共享引用或计数。
- Runtime Home 整体迁移时必须同时携带 SQLite 与 `data/sessions/`；因 Image Part
  只保存 Session 内相对路径，不改写 Conversation 即可在新根目录恢复。
- 现有 Markdown 导出仅是人可读展示，不是可恢复会话包；本版不新增单 Session
  归档导入/导出协议。
- Session 存活期内不做逐引用 GC。删除 Session 时随整个 Session 目录一并删除
  `tool-images/`；继续沿用现有 Session 删除的分阶段和恢复语义。
- 图片文件缺失、不可读、哈希或 MIME 校验失败时，Image Part 标记为不可用并形成
  可诊断错误；不回到 `read_image` 最初的源路径自动重建。

## 七、后续模型调用的三条识图路径

前两条路径以 Image Part 作为规范 Conversation 事实，并根据当前 Model Route 构造请求视图；
第三条沿用 `v0.16.0` 的普通辅助识图工具，不把二者混成隐藏的自动转换。切换模型或协议不改写
历史 Tool Result。能力依据继续来自精确 `(provider, protocol, model_id)` 目录与用户 override，
不按模型名称猜测，也不在请求失败后静默改走另一路径。

### 7.1 原生多模态 Tool Result

当主模型支持图片，且当前协议允许图片作为 Tool Result Part 时：

- Runtime 从 Image Part 解析稳定原图，复用 `v0.16.0` 的公共图片预处理器；
- Adapter 把有序文本、JSON 与图片编码为协议原生多模态 Tool Result；
- 这是无损且优先的路径，不额外调用辅助视觉模型。

### 7.2 Chat/Responses 兼容图片输入

当主模型支持图片，但当前 Chat Completions 或 Responses 方言不接受图片 Tool Result 时：

- 保留与原 Tool Call 配对的可靠 Tool Result 表达；
- 在完整 Tool Result 批次之后生成至多一条只存在于当次模型请求视图的内部图片输入，
  使用同一批 Image Part 和公共预处理结果；
- 内部图片输入不是用户新提交的业务消息，不单独写入 Conversation，不出现在
  Desktop 用户消息列表；其文字只标明图片对应的 `call_id` 和 Part 序号，不表达新用户意图；
- 每次回放都由规范 Image Part 确定性重建；没有图片时不生成内部图片输入。

具体兼容消息角色和 wire 形态必须由后续技术方案以协议 fixture 和真实连接测试固定。
未通过验证的方言不开启该能力，不通过改变排序或静默省略图片试错。

### 7.3 辅助识图工具路径

当主模型不支持图片，但已配置有效辅助视觉模型时：

- 不向该模型暴露 `read_image`；继续暴露已有 `inspect_images`，由 Agent 显式调用；
- `inspect_images.image_paths` 与 `read_image.path` 使用同一套 Session 路径解析和文件 Read
  权限：既支持相对工作目录路径，也支持绝对路径，不再限制为附件 Registry 路径。多图调用逐条
  授权，全部路径获准后才执行，任一路径的 Deny/Ask 都不能被其他路径的 Allow 掩盖；
- `inspect_images` 使用配置的辅助视觉模型，直接返回普通 Text Tool Result。该文本随
  Tool Result 正常持久化，历史恢复和回放只使用已保存结果，不重新调用辅助模型；
- 授权后的本地图片只做本次辅助模型请求的瞬时预处理，不复制到 `tool-images/`，不新增附件、
  Tool Image Part 或其他图片产物；
- 不增加“辅助识图文本缓存”字段、派生 observation 或惰性识别机制；`read_image` 也不
  自动转调 `inspect_images`；
- Agent 后续再次显式调用 `inspect_images` 是一次新的真实工具调用，继续产生对应 usage，
  不以文件哈希自动拦截或复用旧调用结果。

无有效辅助视觉模型时，不向文本主模型暴露识图工具，并明确表示当前路由不能识图；
不伪造识别内容，也不在失败后自动切换 Provider。

### 7.4 多工具批次的规范顺序

无论使用 Chat Completions 还是 Responses，规范 Conversation 均保持以下边界：

1. Assistant Message 中的多个 Tool Call 按模型原始 `output_index` 顺序保存。
2. 工具可以按既有并行资格并发执行，但 Core 等待整批调用都进入终态；每个调用恰好形成一个
   成功或错误 Tool Result，再按原 Tool Call 顺序原子结算完整批次。
3. 原生多模态方言把每张图片保留在对应 `call_id` 的 Tool Result 中。兼容方言先编码整批
   Tool Result，再追加至多一条聚合的内部图片输入；图片按 Tool Call 顺序、再按该结果的 Part
   顺序排列并标注来源。
4. 禁止按工具完成时间排序，也禁止编码为“结果 A → 内部图片 A → 结果 B → 内部图片 B”。
   重复或缺失 `call_id`、无法解析图片或批次不完整时，在发起后续模型请求前明确失败。
5. Context Layout 把同一 Assistant Tool Call 与整批 Tool Result 视为不可拆分的交换边界，
   不裁出缺结果的调用或与调用脱离的内部图片投影。

## 八、Desktop 与产物展示

- 工具图片是为了恢复模型上下文而持久化的内部会话资源，不等同于用户附件或 Agent
  明确交付的文件产物。
- Desktop 不把 `read_image` 产生的 Image Part 加入附件栏、Context Panel 资源列表或通用
  产物栏，避免 Agent 重复读图时制造大量用户可见项。
- 现有工具卡片可以显示工具名、源文件脱敏摘要、状态和一个有界缩略图；同一 Image
  Part 被多次引用不创建多份 Desktop 资源记录。
- 预览继续通过 Runtime 受控资源路由读取，Desktop 不直接拼接 Runtime Home，不保存
  Base64 副本。
- 文件缺失时工具调用和文本历史仍可查看，预览显示不可用；不因预览失败删除
  Tool Result 或其他 Conversation 内容。

## 九、模块边界与契约影响

### 9.1 `agent-types`、`agent-core` 与 `agent-context`

- `agent-types` 承载 Provider-neutral 的有序 Tool Result Part 和最小 Image Part 引用；
  不包含 Session ID、绝对路径、Attachment ID 或 Provider 字段。
- `agent-core` 只保持 Tool Call/Result 配对、Part 顺序、工具执行与 Recorder 语义；
  不读取图片文件，不决定投影路径。
- `agent-context` 把 Image Part 作为所属 Tool Message 的内容处理，确保压缩、裁剪和配对校验
  不生成孤立图片或无对应 Tool Call 的 Tool Result。
- `agent-context` 还必须允许已经被摘要覆盖的旧轮次及其 ProviderState 离开后续活动模型上下文，
  同时保持摘要边界之后的近期 ProviderState 和未完成 Tool Exchange 原样；不因历史上曾出现
  ProviderState 而永久禁止长期会话继续压缩。

### 9.2 `agent-tools` 与 `agent-tools-local`

- `agent-tools` 定义 `read_image` 的稳定名称、单路径 Schema 与输出契约，不访问本地文件系统。
- 本地文件读取、路径解析、取消、大小上限和字节流属于可替换的本地能力；
  Session 目录选择、物化、去重和生命周期由 Runtime/Host 装配，不下沉为 Core 文件 I/O。

### 9.3 `agent-model` 与协议 Adapter

- `agent-model` 分别承载目标模型能否接收图片输入、目标方言能否接收多模态 Tool Result、
  是否需要不透明 ProviderState 等显式能力事实；不把 `image_input` 与
  `multimodal_tool_result` 合成一个布尔值，也不根据错误响应临时学习或改写能力。
- 模型请求准备层解析 Image Part，复用公共图片预处理能力；Adapter 只把已准备的有序
  Part 编码为具体 wire，不读取本地路径或 Runtime Home。
- `agent-openai-compatible` 同时承载 Chat Completions 与 Responses 两种 OpenAI-compatible
  协议实现，但使用独立 Codec/Service 路径；共享传输、图片准备结果和 Provider 方言配置，
  不把两种 wire 状态机塞入同一分支密集编码器。

### 9.4 `assistant-runtime`、`runtime-host` 与应用协议

- `assistant-runtime` 持有 Session 目录、Conversation、Run、工具图片生命周期和投影选择的
  权威业务事实；Responses 也只使用本地 Conversation 驱动后续调用，不把远端 response 或
  conversation 变成第二份权威状态。
- `runtime-host` 提供会话目录建立、原子文件 I/O、图片内容校验、公共预处理实现和
  受控预览路由；不持有第二份 Session/Run 状态。
- `assistant-protocol` 只在 Desktop 需要展示工具预览时投影最小资源身份和不可用状态；
  不把内部 Conversation Image Part、绝对路径或图片字节直接暴露为公共命令 DTO。
- 新增协议字段必须核对 Runtime 生产、Host 转发、Desktop 消费、持久化与旧客户端兼容。

## 十、Responses API 首版边界

### 10.1 协议选择与本地权威

- 新增 `openai_responses` 协议；既有 `openai_chat_completions` 保持独立可选，不做配置迁移、
  自动升级或失败回退。两者共享 Provider-neutral 模型契约，但 wire item、流式状态机和方言
  编解码相互隔离。
- 与 Chat Completions 一样，OpenAI、DeepSeek、DashScope 等差异使用协议内方言兼容；
  `provider` 仍表示实际服务/网关，不能只根据相同模型名称跨网关复用能力结论。
- 所有首版 Responses 请求显式使用 `store: false`。Runtime 每次从本地规范 Conversation
  构造完整有效历史；不发送 `previous_response_id`，不创建远端 Conversation，也不实现
  Responses GET/DELETE。远端响应过期或服务商清理状态不影响本地 Session 恢复。
- 响应 ID 可以作为当次请求诊断元数据，但不是 Conversation 连续性、重试或恢复的必要字段。

### 10.2 首版 item、流与终态

首版请求覆盖：文本消息、图片输入、`function_call_output`、工具定义，以及当前路由继续推理
所需的 reasoning/ProviderState。首版响应覆盖：Assistant 文本与 refusal、`function_call`、
reasoning 摘要/状态和 usage。

流式解码至少识别并验证以下语义事件族；Provider 的具体事件名由方言 Codec 映射：

- response created/queued/in-progress；
- output item added/done；
- content/output text delta/done 与 refusal；
- function arguments delta/done；
- reasoning summary delta/done；
- response completed、incomplete、failed、cancelled 与 error。

`completed`、`incomplete`、`failed`、`cancelled` 必须形成互斥且唯一的模型调用终态。usage 至少
映射 input、output、total token；Provider 返回 cached input 或 reasoning token 时继续保留，
未返回时不伪造。遇到未知但会影响执行的 output item、缺失终态、重复终态或不完整函数参数时
明确失败；`queued` 只作为非终态接受，不代表本版本支持 background mode。仅有诊断意义且已列入
白名单的扩展字段可以忽略。

### 10.3 Reasoning 与 ProviderState

- Opaque ProviderState 的唯一作用，是在 `store: false` 的本地权威模式下，为同一
  精确 Provider 路由保真回放无法规范化的已完成 reasoning item。它不是
  思维正文、Prompt Cache、response ID、远程会话句柄或压缩锁。
- Reasoning 摘要是模型可解释内容；`encrypted_content` 等字段是不透明的 ProviderState。
  二者可以同时出现，但语义和可见性不能合并。
- OpenAI 官方无服务端存储的 reasoning 路径按能力需要请求
  `include: ["reasoning.encrypted_content"]`，并把返回值作为不透明状态保真持久化和回传。
  Adapter/Runtime 不解密、不摘要、不索引，也不写入普通日志或 Desktop。
- 本地真实连接验证中，DeepSeek `deepseek-v4-flash` 与 `deepseek-v4-pro` 即使没有显式
  `include` 也返回非空 `encrypted_content`，同时返回 `reasoning_text`；两者都必须按原 item
  保真持久化，不能沿用“DeepSeek 没有加密状态”的旧假设。
- Qwen `qwen3.8-max` 与 Kimi `k3` 返回 reasoning summary，`encrypted_content` 为 `null`；
  它们只持久化实际返回的 summary/item 字段，不创建空的或伪造的加密状态。是否存在
  ProviderState 是精确路由事实，不是 Responses 协议的全局必选项。
- ProviderState 只能回放给与其绑定的 provider、protocol、endpoint/route 和 model 相容的
  请求。具体路由指纹与兼容判定由技术方案固定；切换到不相容路由时绝不透传旧状态。

### 10.4 ProviderState 与上下文压缩

ProviderState 不能从 reasoning 文本或 summary 重新生成，但这不意味着从最早出现状态的轮次起
必须永久保护全部历史。功能语义区分“活动模型上下文”与“旧 Conversation generation/checkpoint”：

1. 压缩候选只取完整且已经结算的旧轮次；当前未完成 Tool Exchange 和受保护近期尾部不拆分。
2. 使用同一相容路由生成摘要时，候选旧轮次的 ProviderState 可按该方言要求随压缩请求回放
   最后一次；压缩成功后，后续普通模型请求以摘要替代这段旧轮次，不再携带其中的状态。
3. 压缩调用自身产生的 ProviderState 属于临时摘要请求上下文，不拼接进主 Conversation 尾部。
   摘要边界之后的新普通响应会自然产生并持久化新的 ProviderState。
4. 旧轮次是否仍存在于归档 generation/checkpoint，沿用既有替换与恢复生命周期；本版本不要求
   为了压缩额外物理删除。功能验收关注它们不再进入活动模型上下文且不会阻塞后续压缩。

ProviderState 不进入摘要正文、Recall、Memory、全文索引、UI 或普通日志。技术方案必须消除当前
“从最早 ProviderState 起整体保护”的长期增长行为，同时保持近期状态和完整 Tool Exchange。

### 10.5 工具图片在 Responses 中的表达

- OpenAI 官方方言若允许 `function_call_output.output` 使用有序的文本、图片或文件 Part，
  直接把每个 Tool Result 的 Image Part 编码在其对应 `call_id` 下。
- Kimi `k3` 真实连接已验证单次和双调用的图片型 `function_call_output.output`，两张图片均能
  被正确识别；该精确路由可以使用原生多模态函数结果投影。
- 当前 Qwen 方言的 `function_call_output.output` 只按字符串能力启用；它虽支持独立
  `input_image`，但这不等于允许把图片塞进函数结果。Qwen 使用第 7.2 节的批次兼容投影：
  先发送全部 `function_call_output`，再发送至多一条聚合内部图片输入。真实连接中直接发送
  图片数组虽返回 HTTP 200，却把火箭图标识别为苹果，因此必须视为能力不支持而不是成功。
- Chat Completions 的兼容路径遵守相同的批次原则：先完整 Tool Result 批次，后至多一条
  聚合内部图片输入，不把每张图片伪装成一次真实用户追加消息。
- Qwen 与 Kimi 的多函数调用均已验证“整批函数结果后一个聚合图片输入”；Qwen 还验证了
  一成功一错误且只有成功结果附图的批次。离线 fixture 仍必须固定该顺序，后续服务行为变化时
  关闭对应能力，不静默改成逐结果穿插图片或丢图继续。

## 十一、验收标准

### 11.1 工具图片

- [x] `read_image` 在单图成功时返回一个规范 Image Part；非图片、损坏、动画、超限、
  越界、无权限、取消与超时均返回稳定错误，不留半成品成功引用。
- [x] Tool Result 可以按顺序持久化、恢复和投影 Text、JSON 与 Image Part；旧 Text/JSON
  Conversation 无需人工修改即可读取。
- [x] 同一 Session 内串行重复读取和并发重复读取都只生成一份
  `tool-images/<sha256>.<ext>`，不丢失各自的 Tool Call/Result 审计记录。
- [x] Image Part、Tool Result 正文、SQLite 非 Tool Call 字段、Runtime 事件、普通日志和
  调试事件不复制图片 Base64、Data URL 或原始外路径；规范 Tool Call 仍保留
  `read_image(path)` 参数以支持审计。
- [x] 原生多模态 Tool Result 和 Chat/Responses 兼容图片输入都从同一规范 Image Part 构建；
  文本主模型继续通过 `inspect_images` 获得普通持久化 Text Tool Result，不新增派生缓存。
- [x] 图片从原始路径物化后，修改或删除原始文件不改变已保存 Tool Result；Runtime
  重启后仍能重建模型输入。
- [x] Fork 后新 Session 使用自有图片副本和相同相对文件名；Runtime Home
  整体迁移保留相对布局；删除 Session 会清理它自己的 `tool-images/`，
  不需要全局引用计数。
- [x] 结构化文件工具不能修改或删除 `tool-images/`；文档与 UI 不把该约束表述为
  可限制 Shell 的操作系统强沙箱。
- [x] Desktop 能在工具详情中展示单个有界预览或不可用占位，不把该图片加入附件栏、
  Context Panel 或通用产物栏。
- [x] 历史图片缺失或损坏时保留 Tool Call/Result 文本事实并显式报错，不从原始外部
  路径自动重建，不在省略图片后继续模型请求。

### 11.2 Responses API

- [x] `openai_responses` 只能通过明确配置和能力目录选择；现有 Chat Completions 配置、请求
  fixture 和真实调用保持不变，不发生自动升级、失败回退或跨协议 ProviderState 泄漏。
- [x] DeepSeek、DashScope/Qwen 与 Kimi 的首批精确路由补齐离线 fixture，并保持已有显式真实
  连接验证；OpenAI 在取得项目凭据后补真实连接验证。未通过的模型不进入默认启用目录。
- [x] 普通文本流能够完成 created/queued/in-progress、增量、usage 和唯一终态闭环；completed、
  incomplete、failed、cancelled 互斥，未知可执行 output item 与畸形流明确失败。
- [x] 单个与多个 `function_call` 都能完整往返；工具可并发执行，但下一请求中的结果始终按
  原始 Tool Call 顺序编码，每个 `call_id` 恰好一个成功或错误结果。
- [x] 批次图片至少覆盖“两调用一图一文本”“两调用各一图”“单调用两图”“一成功一错误”；
  OpenAI 验证原生函数结果图片，Qwen 验证“整批函数结果后一个聚合图片输入”，Chat 兼容路径
  验证同样的非穿插顺序。
- [x] 所有请求实际使用 `store: false`，不要求 `previous_response_id` 或远端 Conversation；
  Runtime 重启后只用本地 Conversation、ProviderState 和会话图片恢复后续调用。
- [x] OpenAI 与 DeepSeek 的非空加密 ProviderState 能在相容路由上跨轮和重启保真回放，且不
  进入 UI、Recall、Memory、摘要正文或普通日志；Qwen/Kimi 不产生伪造的加密状态。
- [x] 上下文压缩能用摘要替代含旧 ProviderState 的已结算头部，后续请求不再回放该头部状态；
  摘要后的近期 ProviderState、未完成 Tool Exchange 和批次原子性保持不变。
- [x] 图片解析失败、缺失/重复 `call_id`、批次未结算或方言不支持所需投影时，在发起下一次
  Provider 请求前失败，不按完成时间重排、不静默省略内容，也不临时切换协议。
- [x] Chat/Responses 兼容图片输入只存在于 Provider 请求视图；消息查询、计数、
  Runtime 事件、UI、重试和恢复均不把它暴露为用户输入。

## 十二、风险与兼容性

### 12.1 图片文件与持久化

- 稳定文件在 SQLite Conversation 之外，数据完整性依赖“先提交文件，后提交 Tool Result”的
  顺序。技术方案必须定义进程崩溃时临时文件和未引用稳定文件的恢复扫描，但不因此引入
  引用计数。
- 按原图字节去重会保留大图；公共预处理仍需限制解码尺寸、像素、单图输出和
  请求总量，不允许 `read_image` 绕过 `v0.16.0` 的图片安全边界。
- 图片 MIME 可能因解码库升级而发生识别差异；已持久的 `media_type` 用于稳定投影，
  但每次读取仍必须校验字节，不把字段当成跳过安全检查的信任标记。

### 12.2 投影兼容

- 不同 Chat/Responses-compatible 服务对工具结果、图片输入的角色、排序和内容限制可能
  不同。未通过 fixture 和真实连接验证的组合不开启该能力；Provider 更新行为后也需重新回证。
- 辅助识图会增加调用成本，且识别文本会损失视觉细节。产品不能把该路径标记为与
  原生视觉等价，也不能隐藏实际调用的辅助模型和 usage。
- 聚合内部图片输入是兼容投影，不是规范 Conversation 消息。若实现层误将它落盘，可能造成
  恢复重复、UI 伪用户消息和上下文乱序，必须用请求快照与恢复测试同时约束。

### 12.3 Responses 状态与方言风险

- `encrypted_content` 虽不解释正文，仍可能携带敏感上下文，必须按 Conversation 敏感数据处理；
  Trace 如需记录只能沿用高敏 Full Trace 边界，普通诊断不得输出。
- ProviderState 路由绑定过宽会把状态发送给错误服务，绑定过窄又会在正常恢复时丢失连续性。
  技术方案必须根据现有 Model Route 实际字段确定稳定指纹、迁移和错误语义。
- 当前 Context Layout 对含 ProviderState 的尾部保护过宽。修改压缩边界时必须证明旧状态能离开
  活动上下文，又不能拆坏 Tool Exchange、近期 reasoning 或已提交摘要的恢复语义。
- Provider 官方文档与实际兼容端点可能存在差异。能力目录只接受可复现的真实连接证据，不能把
  “SDK 支持”“同名模型在另一网关可用”或一次 404 以外的猜测写成全局能力。

### 12.4 技术方案必须收口的事项

- Tool Result Part 的具体 Rust/Serde 兼容形态、SQLite 迁移和旧 Conversation 读取策略；
- `tool-images/` 的原子写入、崩溃残留扫描、只读防误操作、Fork/整体迁移与删除顺序；
- Chat 与各 Responses 方言的确切 wire fixture、聚合内部图片消息角色和上下文 token 计量；
- Responses 流式状态机、ProviderState 路由指纹、压缩 generation/checkpoint 替换过程；
- 首批模型的真实测试入口、凭据脱敏、显式运行方式和能力目录启用门禁。

## 十三、后续设计文档判断

本版本必须继续编写独立技术方案，因为它涉及规范 Tool Result、Provider Codec、模型能力、
Conversation 兼容、Context Layout、Session 目录、原子文件 I/O、持久化恢复、Fork、整体迁移和
Responses API。技术方案必须基于当时真实源码确定公共类型、Serde/SQLite 迁移、错误分类、
