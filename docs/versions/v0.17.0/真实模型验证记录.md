# v0.17.0 真实模型验证记录

## 一、验证信息

- 日期：2026-08-19
- 目的：在编写技术方案前，用本地已有模型配置验证 Responses API 方言、reasoning、
  function call、图片输入与工具图片回流方案
- 配置来源：本机 `~/.ez-assistant/config.toml`
- 安全边界：只读取模型路由和凭据用于当次 HTTPS 请求；不打印、复制或写入 API Key，
  不记录完整 response ID、call ID、reasoning 正文或用户私有图片路径
- 验证方式：先以独立的最小 HTTPS 探针隔离 Provider 行为，再复跑正式 Runtime Host 的
  `v0_16_real_multimodal` 真实测试验证现有 Chat/辅助识图基线

本记录只证明验证日期与本地账户下的精确路由行为。Provider 后续变更仍需重新验证；
HTTP 200 也不自动等于某项内容能力可用。

## 三、文本、流式与本地历史

### 3.1 基础请求

DeepSeek 两个模型、Qwen 和 Kimi 均接受：

```json
{
  "model": "<exact-model-id>",
  "input": "<short-text>",
  "store": false
}
```

四条路由都返回 `object: response`、`status: completed`、reasoning/message output item 和
input/output/total usage。GLM 两个已知官方 Base URL 均没有 Responses 路由。

### 3.2 流式状态机

四条可用路由均观察到：

- `response.created`、`response.in_progress`；
- `response.output_item.added/done`；
- 文本或 reasoning 的 delta/done；
- `response.completed` 或 `response.incomplete`；
- 终态事件内 usage。

低 `max_output_tokens` 下 DeepSeek/Kimi 可在 reasoning 阶段形成可靠 `response.incomplete`；
提高上限后同一路由形成 `response.completed` 和最终 message。Qwen 还返回 `x_details` usage
扩展。实现必须把 `incomplete` 当正常模型终态处理，不能等到传输 EOF 后猜测。

### 3.3 `store: false` 与完整历史回放

四条可用路由均完成以下两轮验证：

1. 第一轮用 `store: false` 让模型记住随机代号；
2. 第二轮不使用 `previous_response_id`，显式回传第一轮 user input 和完整 output item，
   再询问代号。

四个模型都正确返回代号，证明首版“本地 Conversation 唯一权威、完整 item 回放”可行。
Qwen 官方文档同时明确 `store: false` 时响应不能再通过 `previous_response_id` 引用。

## 四、Reasoning 与不透明状态

| 路由 | 实际 reasoning item | `encrypted_content` |
| --- | --- | --- |
| DeepSeek Flash/Pro | `content: reasoning_text`，summary 为空 | 未请求 `include` 时也返回非空字符串 |
| Qwen `qwen3.8-max` | `summary: summary_text` | `null` |
| Kimi `k3` | `summary: summary_text` | `null` |

结论：

- “DeepSeek 没有加密状态”的先验不成立。Responses Adapter 必须保真保存 DeepSeek 返回的
  完整 reasoning item 和非空 `encrypted_content`。
- Qwen/Kimi 不需要伪造 ProviderState；只保存实际 summary/item 字段。
- DeepSeek 的一次工具续接实验即使移除 reasoning item 仍返回 200，但这不能证明所有复杂
  reasoning/tool 链都可安全丢弃。规范实现仍按原 item 保真回放，再由上下文压缩边界淘汰旧轮次。
- `reasoning.effort` 实测：DeepSeek `high`、Qwen `low`、Kimi `low` 均接受；Qwen 会在响应根部
  回显 effort，Kimi 不回显。能力目录不能靠响应是否回显判断参数是否生效。

## 五、Function Call

### 5.1 ToolChoice 方言

DeepSeek、Qwen、Kimi 的 thinking 路由都拒绝 `tool_choice: required`：

- DeepSeek 明确返回 thinking mode 不支持该 ToolChoice；
- Qwen 明确返回 thinking mode 不支持 `required` 或对象模式；
- Kimi 返回通用 `invalid_request_error`。

改用 `tool_choice: auto` 后，四条路由均成功完成单函数调用和结果续接。因此技术方案必须让
ToolChoice 支持集成为精确路由能力，不能把 OpenAI Responses 的完整枚举全量下发。

### 5.2 单调用与双调用批次

DeepSeek Flash/Pro、Qwen、Kimi 均完成：

- 单个 `function_call` → 字符串 `function_call_output` → 最终 message；
- 同一 Assistant output 中两个有序 `function_call`；
- 等待两个结果后按原 call 顺序连续发送两个 `function_call_output`；
- 最终回答同时包含两个不同的确定性 marker。

实际服务接受“reasoning、call A、call B、output A、output B”的完整历史。工具是否并行执行
不应改变 wire 顺序。

为确认规范类型不需要额外保存 Responses 的 function output item `id`，又补做了
最小回放验证：第二轮只从规范 `ToolCall` 重建 `type/call_id/name/arguments`，
明确省略 Provider 的 function item `id`。DeepSeek Flash/Pro、Qwen 与 Kimi 均完成
续接并正确返回工具 marker。因此 function item `id` 不进入规范 Conversation；
`call_id` 仍是工具配对的唯一权威身份。

Qwen/Kimi 还通过了“只使用 `ReasoningPart` 可重建的
`type/id/summary`”续接，省略 `status/content/encrypted_content` 后仍能正常完成工具链。
这进一步确认两条路由不需为 `null` 加密内容创建 ProviderState。

## 六、图片能力与工具结果投影

验证图片包括一个中央为火箭的应用图标和一个帆船缩略图；图片字节只存在于请求内，
没有写入本记录。

### 6.1 普通 `input_image`

| 路由 | 结果 |
| --- | --- |
| Qwen `qwen3.8-max` | 正确识别火箭 |
| Kimi `k3` | 正确识别火箭 |
| DeepSeek Flash/Pro | 有图与无图都返回 `NO_IMAGE`；HTTP 均为 200 |

DeepSeek 证明了图片能力不能通过“请求不报错”探测；必须由精确目录声明并以内容断言验证。

### 6.2 原生多模态 `function_call_output`

使用 OpenAI 的数组形态把 `input_text` 与 `input_image` 直接放入对应 `call_id` 的
`function_call_output.output`：

| 路由 | 单图 | 双调用各一图 | 结论 |
| --- | --- | --- | --- |
| Kimi `k3` | 正确识别火箭 | 正确识别火箭和帆船 | 精确路由可启用原生多模态 Tool Result |
| Qwen `qwen3.8-max` | HTTP 200，但把火箭识别为苹果 | 未继续作为能力验证 | 视为不支持；不能因 HTTP 200 启用 |
| DeepSeek Flash/Pro | HTTP 200，回答 `NO_IMAGE` | 不适用 | 模型没有图片输入能力 |

### 6.3 聚合兼容图片输入

Qwen 与 Kimi 均通过以下顺序：

```text
reasoning / function_call A / function_call B
function_call_output A / function_call_output B
one internal user image envelope(image A, image B)
```

两个模型都按 call/path 顺序正确识别火箭和帆船。Qwen 还通过“一调用返回 not_found、另一调用
成功并附一张图”的批次，最终回答同时保留错误和正确图片结果。

因此：

- Qwen 必须使用字符串 `function_call_output` 加一个批次级内部图片输入；
- Kimi 可以优先使用原生多模态 Tool Result，兼容投影可作为离线对照而不是运行时失败回退；
- 内部图片输入只存在于请求视图，不得写入 Conversation 或 UI；
- 不允许逐结果穿插图片，也不允许 Provider 返回 200 后再根据自然语言答案动态学习能力。

### 6.4 Chat Completions 聚合兼容回证

Qwen 与 Kimi 另以现有 Chat Completions 协议执行两个 function call：先按
call 顺序发送两条 tool message，再发送一条包含两张图的 user image message。
两条路由均在答案中保留两个工具文本标记，并正确识别火箭图。

因此 Chat 兼容投影与 Responses 遵守同一批次原则，但分别由各自 Codec
产生协议原生的 tool/user wire 形状，不共用已序列化 JSON。

## 八、技术方案输入结论

1. Responses 使用独立 Codec/Service，但沿用 provider 方言；首批实现精确覆盖 DeepSeek
   Flash/Pro、Qwen `qwen3.8-max`、Kimi `k3`，GLM 暂不启用。
2. 必须拆分 Responses 协议选择、`image_input`、`multimodal_tool_result`、
   reasoning item 形态和 ToolChoice 支持集，不能用一个“OpenAI-compatible”
   布尔值概括。
3. DeepSeek ProviderState 必须保真；Qwen/Kimi 的 null `encrypted_content` 不物化为空状态。
4. Qwen 工具图片固定走批次聚合兼容投影；Kimi 固定走原生多模态 Tool Result。运行时不根据
   失败或自然语言结果切换路径。
5. 流式 Decoder 必须覆盖 reasoning text、reasoning summary、文本、函数参数、completed 与
   incomplete；未知可执行 item 明确失败。
6. OpenAI 官方路线目前只有官方文档契约，没有本地项目凭据真实连接证据；实现可完成离线
   fixture，但进入默认能力目录前仍需单独真实验证。
7. 四条可用路由都接受 Responses 根级 `instructions`，并在最小指令断言中给出精确结果；
   技术方案可以把冻结 `SystemPromptSnapshot` 确定性合并到该字段，无需为四家方言
   分别伪造 system input item。

```text
cargo test -p assistant-runtime-host --test v0_17_real_responses -- --ignored --nocapture
```

最终 4 项全部通过：DeepSeek Flash/Pro 均完成 function call、字符串 function output、最终回答和
下一轮本地 reasoning 历史回放；Qwen 通过批次聚合工具图片识别纯红图片；Kimi 通过原生

首次复验暴露并修正两项之前最小探针未覆盖的差异：

- DeepSeek 在 `reasoning_text` delta 前后发送通用 `response.content_part.added/done`，Decoder 需将
  part type 路由到 reasoning 状态，而不能只按 message text 处理；
- DashScope 会拒绝缺少显式 `properties` 的空对象工具参数 Schema；公共 OpenAI-compatible
  Schema 降级器现对该合法空对象补 `{ "properties": {} }`。

修正后分别重跑失败路由并通过；临时诊断探针已删除，仓库只保留可重复执行的正式忽略测试。
