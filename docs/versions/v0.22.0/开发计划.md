扩大改动，先回写对应设计并重新确认。

## 二、台账与实施原则

1. 按 M0—M8 顺序实施。开发计划确认后，开始 M0 前才把版本状态从 `计划中` 更新为 `开发中`。
2. 每个里程碑执行“核查 → 实现 → 最小有效验证 → 记录实际结果 → 标记 `🟨 待确认` → 汇报 → 等待
   用户确认”；未确认不得开始下一里程碑。
3. 每个里程碑开始前重新读取涉及语言规范、模块约束和 `Agent 系统技术架构`，核对当前工作树与用户已有
   改动；不主动 commit/push，不清理无关文件。
4. Desktop 只持有新会话草稿、selection、选区焦点、动画和布局等客户端状态；Runtime 继续持有 Session、
   Conversation、Run、Workspace 与持久化权威事实。
5. 新会话首次发送只通过已确认的窄 materialization 入口实现，不落持久 Draft、Provisional Session、
   通用上传租约或事务协调器。
6. 标题自动与 `/title` 只传不同 trigger，由同一机制读取调用时最新 Conversation Snapshot；不得增加
   title revision、调用方内容装配或空闲门禁。普通 Run/Compaction 后续提交不使标题快照失效。
7. Workspace 编辑只更新当前 Workspace 元数据；任何既有 Session 的 System Prompt、System Context、
   主目录和附加目录快照都不得被重建或改写。
8. 图片粘贴、文件选择器附件和首次 materialization 共用 selection/上传/预览语义；剪贴板图片不得以
   Base64、Object URL 或 Web `File` 作为长期草稿事实。
9. 引用点击只更新 Desktop 草稿；纯文本 `exact`、每侧最多 128 个 Unicode 字符的前后文和直接来源范围在发送时进入
   UserMessage，不签发 recall reference。发送起始同步清理 `TransientFocusTarget`，不能出现无法回收
   的 DOM 高亮状态。
10. 动效只控制视觉生命周期，业务清理不等待动画。分栏保存 preferred width，不把响应式显隐结果写回。
11. 所有 schema migration、失败注入、恢复和文件清理测试只操作 `TempDir`、内存 Store 或隔离 Runtime
    Home；本计划不授权读取、迁移、覆盖或删除用户实际数据库和附件目录。
12. 默认模型验证使用 fake/deterministic ModelService。真实 Provider 调用可能产生网络请求和费用，只有在
    版本验收阶段获得用户明确授权后执行，并使用隔离 Runtime Home 与脱敏日志。

## 四、里程碑明细

### M0：共享契约与迁移基线

前置依赖：本开发计划已确认；版本状态已更新为 `开发中`。

目标：先建立后续能力共同依赖的 provider-neutral 消息、单轮模型执行、兼容持久化和生成类型基线，保证
旧 Runtime Home 可在隔离测试中升级，但不提前改变 Desktop 新建会话、Workspace 或标题行为。

交付范围：

- 在 `agent-model` 提供经过 `LifecycleValidator` 的无领域单轮 stream 收集 helper，并让现有 Rolling
  Summary 改用该 helper，压缩策略和结果不变；
- 在 `agent-types` 增加结构化 `QuotedText` UserPart，并完成 OpenAI-compatible Chat/Responses 投影、
  XML/文本转义和序列化往返；
- 增加 Workspace label/附加目录、Session 冻结附加目录、materialization key、自动标题 pending 和旁路
  usage 的兼容 schema migration、Stored 类型与 Volatile Store 对应字段；
- 旧 Workspace 使用 basename 标签和空附加目录，旧 Session 使用空附加目录且不自动生成历史标题；
- 增加后续里程碑所需的 additive DTO/事件基础类型和 TypeScript 生成，但不发布无法处理的 RuntimeCommand；
- 覆盖旧 schema、重复迁移、损坏 JSON、默认值、Provider 投影和单轮流异常测试。

验证入口：

```bash
cargo test -p agent-model -p agent-context -p agent-types -p agent-openai-compatible
cargo test -p assistant-protocol -p assistant-runtime -p assistant-runtime-host
cargo run -p assistant-protocol --example export_typescript -- --check
cargo clippy -p agent-model -p agent-context -p agent-types -p agent-openai-compatible \
  -p assistant-protocol -p assistant-runtime -p assistant-runtime-host \
  --all-targets --all-features -- -D warnings
```

完成判定：旧数据可无损加载并得到设计默认值；新类型可序列化恢复；Chat/Responses 始终保留引用 exact 且
不暴露裸来源 identity；压缩回归通过；没有新用户入口、半实现命令或第二套模型任务框架。

Review 重点：helper 是否混入标题/Session 语义；schema 是否增加不必要表或 revision；新增 UserPart 是否
污染应用协议；迁移是否触碰真实用户数据。

### M1：Workspace 标签与多目录闭环

前置依赖：M0 已确认。

目标：完成 Workspace 当前元数据、多目录 Session 冻结和统一编辑入口的端到端闭环，同时证明编辑
Workspace 不会热更新既有 Session 的执行上下文。

交付范围：

- 实现 Workspace 注册/更新的 label、主目录、有序附加目录校验、canonicalize、移除/恢复和事件投影；
- 扩展 Session execution environment、System Prompt/System Context 和 Session Resources 的冻结目录；
- 相对文件路径和 Shell cwd 继续使用主目录，附加目录通过明确绝对路径访问；Runtime 根据 Session
  冻结的全部 Workspace 根提供结构化文件缺省能力，显式 Ask/Deny 优先，目录编辑不维护权限文件；
- 按主目录、附加目录顺序读取根 `AGENTS.md`，并按根序号完成 Workspace Skill 发现、去重与冲突诊断；
- Controller 管理投影返回当前 Workspace label 和目录摘要；正式 Session Context 返回当前 label 与冻结目录；
- Desktop 左栏与新会话菜单使用 label，左栏菜单和右侧 Workspace Section 打开同一编辑弹窗；
- 弹窗在同一表单中编辑名称、主目录、附加目录、主目录切换与排序，不新增全局设置页；
- 覆盖更新前后既有 Session Prompt/Context/目录逐字不变、新 Session 使用新目录的测试与交互回归。

验证入口：

```bash
cargo test -p assistant-protocol -p assistant-runtime -p assistant-runtime-host
cargo run -p assistant-protocol --example export_typescript -- --check
cargo clippy -p assistant-protocol -p assistant-runtime -p assistant-runtime-host \
  --all-targets --all-features -- -D warnings
cd apps/desktop
npm run build
npm run test
npm run tauri -- build --no-bundle
```

完成判定：用户能从两个入口用同一弹窗编辑 Workspace 名称与目录；新 Session 得到正确有序多目录；既有
Session 的 System Prompt、System Context、cwd 和冻结目录完全不变；Agent/Controller 可识别 label。

Review 重点：Workspace 当前投影与 Session 冻结事实是否混淆；是否把多目录误作强沙盒；Skill/AGENTS
顺序是否稳定；缺省权限是否只依赖冻结目录且不写入权限文件；是否为了编辑表单引入 revision、目录实体
或设置页。

### M2：首次发送物化后端

前置依赖：M1 已确认。

目标：在不改变当前 Desktop 新建路径的前提下，完成可由隔离 Host 调用的首次发送窄物化入口，使
Session、附件、首条消息、Input 和 Run 在用户可观察层面一次可靠出现。

交付范围：

- 增加 `session_materialization` Host capability、multipart manifest/result 和专用 HTTP route；
- 复用现有 Streaming Upload 的大小、哈希、媒体嗅探、Blob 和稳定视图逻辑；
- Runtime 复用 Session 创建与 Input 接受校验，构造冻结环境、System Prompt、附件引用、兜底标题和首个 Run；
- Store 新增单一 `materialize_session` 业务方法，在文件准备后用一个 SQLite 事务提交全部可见业务事实；
- 通过 nullable unique materialization key 处理响应丢失重试，内容不同的同 key 返回 conflict；
- Store 成功后再安装内存 Session/权限/队列并发布事件；重连 Snapshot 可恢复已提交但未发布事件的结果；
- 增加 staging、Blob、稳定视图、数据库提交、事件发布和进程中断的失败注入与孤儿清理测试；
- 保留旧 `create_session`、单 Session upload 与 `submit_input`，验证新 Host 兼容旧 Desktop。

验证入口：

```bash
cargo test -p assistant-protocol -p assistant-runtime -p assistant-runtime-host
cargo run -p assistant-protocol --example export_typescript -- --check
cargo clippy -p assistant-protocol -p assistant-runtime -p assistant-runtime-host \
  --all-targets --all-features -- -D warnings
```

完成判定：无附件、多附件、Skill/Goal 和结构化引用载荷都只生成一组 Session/Input/Run；提交前失败不
产生可见 Session；提交后响应丢失用同 key 返回原结果；文件/数据库恢复不依赖 Provisional Session。

Review 重点：Store 是否演进为通用事务框架；文件准备和 SQLite 可见性顺序是否正确；幂等是否把不同
manifest 合并；旧 Desktop 与 Controller 创建路径是否回归。

### M3：新会话草稿与首次发送 UI

前置依赖：M2 已确认。

目标：把 Desktop 新建会话切换到按 Workspace 隔离的进程内草稿，并正式使用 M2 materialization；只有
首次发送可靠接受后才出现 Session 列表行。

交付范围：

- 新增 `NewSessionDraftStore`，按 `WorkspaceId | unbound` 保存文本、selection、引用占位、模型与执行设置、
  Skill/Goal 意图和 materialization 重试状态；
- Navigation 支持“选中草稿但没有 selected_session_id”，新建菜单、Workspace 行 `/new` 复用同一草稿；
- 草稿 Header、空状态和右栏只展示真实草稿/Workspace 信息，不伪造 Session、Run 或附件历史；
- Tauri 增加首次 materialization 批量桥接，流式读取现有 selection 并提交 manifest；
- 明确失败使用新 key、响应不确定沿用原 key/manifest，成功才释放 selection、清空草稿并切换 Session；
- 新 Desktop 检查 Host capability，旧 Host 缺少入口时明确提示更新/重启，不回退为空 Session 流程；
- Workspace 移除、草稿清空、Session 导航、WebView/进程退出和多草稿切换按设计释放或保留资源；
- 覆盖每 Workspace/unbound 隔离、列表无草稿、失败保留、响应丢失、仅附件首发和应用重启不恢复。

验证入口：

```bash
cargo test -p assistant-protocol -p assistant-runtime -p assistant-runtime-host
cd apps/desktop
npm run build
npm run test
npm run tauri -- build --no-bundle
```

完成判定：点击任意新会话入口不改变 Runtime Session 数；多 Workspace 草稿互不覆盖；首次发送成功只
出现一个正式 Session，失败和不确定重试不丢草稿、不重复创建；进程重启后草稿完全消失。

Review 重点：Desktop 是否保存第二份 Session 权威状态；草稿是否写入偏好/localStorage；selection 是否因
切换 Session 被错误释放；旧 Host 是否被静默降级。

### M4：自动标题与 `/title`

前置依赖：M3 已确认。

目标：在保留确定性兜底标题的基础上，完成首轮异步自动标题与手动 `/title`，两者只由 trigger 区分，
不阻塞主 Run 和 Composer。

交付范围：

- Runtime title 模块内部读取调用时最新稳定 Conversation Snapshot，自行选择有界可见内容并构造请求；
- 新普通/Fork Session 使用单一 `automatic_title_pending`，旧 Session/Controller 不补生成；失败 Run 不提前
  耗尽资格，首次成功回复后至多执行一次；
- 自动与手动调用使用同一个结构化输出路径、输出清理和提交函数；只暴露一个不执行的
  标题函数契约，Runtime 只接受唯一匹配 ToolCall，并记录旁路 usage 聚合；
- 同 Session 新 trigger、直接改名、clear、删除取消旧标题调用；普通 Run/Compaction 后续提交不触发
  title generation/revision guard；
- 自动结果只在现有 generated title 仍有效时写入；手动 `/title` 可替换任何调用前标题并关闭自动资格；
- 增加 command、transient View、SSE 开始/完成事件和恢复检查；不创建 UserMessage/Input/Run/Queue；
- Desktop Slash Menu、状态行、失败重试和标题淡入反馈落地，活动 Run/Queue/Approval/Compaction 不禁用；
- Session clear 改为统一保留当前标题，并覆盖自动/手动/直接编辑竞态和重启恢复测试。

验证入口：

```bash

cargo test -p assistant-protocol -p assistant-runtime -p assistant-runtime-host
cargo run -p assistant-protocol --example export_typescript -- --check

  -p assistant-runtime-host --all-targets --all-features -- -D warnings

```

完成判定：首轮回复先可见、标题后更新；失败保留兜底；精确 `/title` 在所有允许状态下使用同一 Snapshot
机制且不进入主执行队列；直接改名和 clear 不被迟到结果覆盖；不存在标题专属 revision 或输入装配分支。

Review 重点：调用方是否偷偷传首轮/近期消息；是否复用了视觉模型设置；title task 是否占用 Session 长锁；
clear 是否重新按标题来源分支；事件缺口后 View 是否能收敛。

前置依赖：M4 已确认。

目标：完成附件 Tag 详情和剪贴板图片到普通附件的受控登记，使文件选择、paste、新会话草稿和已有
Session 发送共用一条 selection 生命周期。

交付范围：

- Composer 建立有序 Context Item 基础，附件 Tag 主体打开详情、独立按钮移除，Skill/Goal 仍分区展示；
- 本地 selection 详情支持受控图片/文本预览、名称、大小、媒体类型和状态，不暴露物理路径；
- textarea paste 只处理本次 `kind=file && type=image/*`，纯文字保持原生行为，混合粘贴按当前选区保留
  文字和图片；
- Tauri `stage_clipboard_image` 使用 raw `Uint8Array` IPC、magic-byte sniff 和匿名临时文件；
- `SelectedAttachment` 支持 external path/owned handle reader，覆盖 upload、preview、release 和 TTL；
- 落实单图 `32 MiB`、每 Composer 32 项、全进程 256 selection/256 MiB clipboard temp 上限与整批回滚；
- 支持图片-only 发送；paste 不提前创建 Session 或上传，失败保留草稿，成功/移除/TTL/退出释放 owned handle；
- 覆盖单图、多图、纯文字、混合、伪 MIME、超限、批次中途失败和多 Workspace 草稿共存。

### M6：会话文本引用闭环

前置依赖：M5 已确认。

目标：按开源 Agent 常见的“来源身份 + 选区范围 + 冻结内容”模式，完成从同一消息跨渲染元素选区到
结构化 UserMessage、详情和一次性来源定位的完整闭环。

交付范围：

- 删除第一版 `prepare_text_quote` command、`text_quote` capability、HMAC 签发/解析链路和 quote
  `recall_reference`，不保留未发布方案的兼容分支；
- Desktop 以消息正文根容器为边界，允许 Selection 跨文本节点、行内代码、链接和强调；跨消息、工具块
  或交互控件拒绝。用消息可引用文本投影计算规范化 `text_start_utf16/text_end_utf16`、exact 和 Unicode
  有界 prefix/suffix，不再匹配 raw Markdown occurrence；Runtime 不用 UTF-16 range 切 UTF-8 字符串；
- 跨渲染元素统一投影为可见纯文本 exact；行内代码、链接和强调不反向转换成 Markdown，来源定位只使用
  可见文本范围；
- 浮动气泡调用纯前端 quote draft 动作；点击后立即生成 Tag，不发送 Host/Runtime command。消息正文
  不拦截右键或 `Shift+F10`，复制等操作继续使用 WebView 原生 Context Menu；
- SubmitInput 与首次 materialization 在发送时携带结构化引用。Runtime 只校验数量、大小和结构；来源
  locator 不属于目标 Session 或已 stale 时降级为 unavailable，不损坏冻结内容；
- Provider 投影始终包含一次冻结 exact 和每侧最多 128 个 Unicode 字符的 prefix/suffix，排除 quote ID、owner、generation、
  message identity 与 text range，也不提示调用引用专属 Recall 工具；
- Composer Context Item 加入 quote，按加入顺序与附件共同展示；发送失败保留，成功清空；
- 引用详情展示冻结正文、前后文和来源状态，内部 Message ID/generation/range 不进入产品文案；
- `TransientFocusStore` 和 owner resolver 完成导航、滚动与一次性高亮；发送起始、关闭、滚动、切换、
  超时、失败和卸载统一清理；
- “查看来源”直接使用持久 locator 和现有 Conversation 投影/普通历史分页，不新增引用专属 resolve API；
- 覆盖一词/重复短句、跨行内元素、列表/链接/代码/CJK/emoji、128 字符边界、子任务来源、来源 stale、
  点击无网络请求、刷新恢复和高亮快速切换测试。

### M7：统一动效与可调分栏

前置依赖：M6 已确认。

目标：在所有主要业务浮层和 Context Item 已稳定后，统一 enter/exit 生命周期并完成左右分栏用户偏好，
不让视觉动画改变业务状态或焦点语义。

交付范围：

- 提供无第三方依赖的 Presence 生命周期和 motion token，覆盖进入、退出、快速反向、父级卸载和 fallback；
- Dialog 退出期间 inert/aria-hidden 且继续锁定背景，退出完成后恢复 opener 焦点；
- 迁移 Dropdown、SelectionPopover、Context Menu、Slash Menu、Skill Picker、Composer 上拉菜单和产品 Dialog；
- Collapse 使用自然布局过渡包装，展开态不锁定像素高度，嵌套内容直接撑开父容器；Workspace 移除及脏表单确认替换 `window.confirm`；
- `prefers-reduced-motion` 使用同一清理路径，不依赖 transitionend 才完成业务收敛；
- AppShell 增加左右 `SidebarResizeHandle`、pointer capture、键盘步长、双击复位和拖拽清理；
- preferred/effective visibility 分离，右栏支持到 `800px`；侧栏始终使用用户偏好宽度，不做窗口
  响应式压缩。三栏不足时先隐藏右栏，左栏与 `500px` 中栏仍不足时再隐藏左栏；
- AppShell 横向骨架使用不换行 Flex，避免旧断点 Grid 与拖拽柄数量不一致时产生隐式下一行；
- 当前上下文展开/收起按钮固定在会话标题栏“更多会话操作”右侧，不随右栏宽度移动；
- 右侧 ContextPanel 按自身容器宽度在单列与两条独立纵向列之间切换，列间不做同行高度对齐；
- Tauri Desktop Preferences 保存 `286px/326px` 默认与用户宽度，兼容缺失/损坏/越界旧数据；
- 覆盖焦点陷阱、不可见交互层、减弱动效、长会话流式输出和窗口缩放回归。

## 六、计划风险与调整规则

- M0 只建立后续已确认能力需要的共享基线；若出现没有第二个真实调用方的公共抽象，留在领域模块内。
- M1—M7 任一里程碑发现需要新增持久实体、改变 Session/Run 权威边界、开放裸 Message ID、热更新既有
  Session System Context 或引入第三方动画框架时，视为设计偏差并停止实施。
- M2 的文件系统补偿经失败注入证明不足时，只能先记录失败证据并回到技术方案，不得自行扩展为通用事务。
- M5 的 raw IPC 上限若在真实截图验收中不足，先提供样本大小、内存峰值和失败证据，再调整单图/总量边界。
- 里程碑内部的小修正服务于当前完成判定时直接纳入；明显扩大版本目标、改变依赖顺序或破坏后续交付节奏
  的事项先回写设计并重新确认计划。
