## 二、背景与问题

### 2.1 “新会话”目前过早成为持久业务记录

Desktop 当前点击“新对话”就立即请求 Runtime 创建空 Session。用户只是切换 Workspace、比较
模型或暂时输入几句话，也会在会话列表中留下空记录。Composer 草稿又是组件局部状态，切换会话
时直接丢失，导致“先建记录、后决定是否真的发送”的产品顺序与用户意图相反。

新会话应先是 Desktop 内的临时草稿，只有用户真正发送第一条消息且 Runtime 可靠接受后，才成为
产品 Session。草稿不能伪装成会话列表记录，也不能让 Runtime 持有第二份未完成会话状态。

### 2.2 标题截断可用，但不足以表达会话主题

Runtime 当前在首个 Input 接受时取第一条非空文本并截断为标题。它保证了可靠兜底，却经常把长
指令、日志或上下文前缀直接显示成标题。外部 Agent 实现普遍在首轮回复结束后，由宿主发起一次
独立模型调用；这条调用不属于主 Agent Tool Loop，也不阻塞用户看到回复。

本版本需要保留现有确定性兜底，同时在首轮可靠结束后生成更能概括意图的标题，并增加精确
`/title` Slash Command，让用户可以基于当前最新 Conversation 主动重新生成标题。自动触发与
Slash 触发必须进入同一条标题旁路推理，调用方只传入不同 `trigger`；标题机制内部统一读取调用
时最新的 Conversation Snapshot，并自行决定使用哪些内容进行推理。

### 2.3 Workspace 缺少稳定可读身份，单目录也限制真实项目组织

Workspace 当前只有不透明 `WorkspaceId`、一个用户目录和一个 Workspace 私有目录。Desktop
主要通过目录 basename 展示；主控 Agent 查询受管会话时只能看到 `workspace_id`，容易把会话
委派到错误项目。一个实际工作空间也可能同时需要主仓库、文档库或多个相邻仓库，单目录模型无法
表达这种关系。

本版本需要为 Workspace 建立固定、用户可编辑的标签，并把用户目录扩展为有序多根目录。Session
仍最多绑定一个 Workspace，不引入 Workspace 之间的继承或嵌套。

### 2.4 复制粘贴会丢失引用身份和来源定位

用户目前只能把历史文本复制进 Composer。模型能够看到文本，却不知道它来自哪条消息；Desktop
也无法打开来源或定位原文。渲染后的 Markdown 还会把一段可见文字拆到多个 DOM 元素中，如果按单个
元素或回查原始 Markdown 的字符串 occurrence 处理，跨行内代码、链接、强调等元素的正常选区会失败。

本版本采用开源 Agent 常见的“稳定来源身份 + 选区范围 + 冻结内容”模式：Desktop 在一条消息正文内
直接读取浏览器 Selection，允许选区跨越多个行内渲染元素，并把可见纯文本、每侧最多 128 个 Unicode
字符的前后文和来源定位一起暂存在 Composer。点击“引用”不请求 Runtime，也不签发 capability token；
发送时再作为结构化引用提交。来源定位只服务产品 UI，不成为模型读取任意消息的授权入口。

### 2.5 旁路模型调用已经存在，但概念边界尚未统一

上下文压缩会读取当前 Session Conversation 并产出 Context Summary；自动标题也将读取当前
会话首轮内容并回写标题。这两者属于“从当前 Session 派生、由领域所有者提交结果”的旁路推理。

辅助识图虽然也是独立模型调用，但它只读取工具目标和图片，不继承当前 Conversation；它属于
独立辅助推理。若把两者都称为旁路会话，容易错误引入第二类持久 Session、错误共享 Conversation
或让视觉模型读取无关历史。本版本必须先统一生命周期协议，再明确两类调用不能合并领域语义。

### 2.6 Desktop 浮层与分栏交互缺少统一完成态

Desktop 已有弹窗、下拉/上拉菜单、Popover、二级抽屉和多种 Collapse，但不同组件的出现、关闭和
内容展开反馈不一致，部分浮层直接挂载或卸载，用户难以感知层级变化。应用的左右侧栏也只有固定
宽度和展开/收起状态，长 Workspace 名称、目录或上下文内容无法由用户主动分配空间。

本版本需要建立克制、可中断、遵循减弱动态效果偏好的统一过渡规则；同时为左侧会话栏与右侧
上下文栏提供独立拖拽宽度、键盘调整和设备本地持久化，且任何调整都不能挤破中间会话区的最低
可用宽度。

### 2.7 剪贴板图片没有进入现有附件链路

Composer 已支持通过文件选择器添加附件，但用户从截图工具、浏览器或其他应用复制图片后，仍需先
保存到磁盘再选择文件。WebView 的粘贴事件可以直接提供图片文件项，却不能让这些字节绕过现有附件
限制、原生资源生命周期或首次发送物化边界。

本版本需要在 Composer 获得焦点时把剪贴板中的图片文件项自动登记为普通图片附件。普通文本粘贴
保持原行为；同一次粘贴同时包含文字和图片时，两者都应保留。图片一旦登记成功，预览、移除、发送、
失败重试和新会话草稿语义全部复用附件能力，不建立“剪贴板图片”第二套消息类型。

## 三、版本目标与成功标准

`v0.22.0` 形成七个相互协同的优化闭环：

1. 新会话先成为按 Workspace 隔离的临时草稿，首次发送可靠接受后才物化 Session；
2. 首轮可靠回复后异步触发标题生成，并允许用户通过 `/title` 手动触发；两者只传入不同 trigger，
   由同一机制读取最新 Conversation Snapshot，失败时保留现有标题；
3. Workspace 具有固定标签和有序多目录，并让 Desktop、Runtime 与 Agent 使用同一关联事实；
4. 用户可以选择会话文本形成结构化引用，在 Composer 查看、移除、发送并按需返回来源；
5. 用户把图片粘贴进 Composer 后，图片自动成为普通待发送附件，并与同次粘贴的文字共同保留；
6. Runtime 建立统一的旁路推理生命周期，整合自动标题与既有上下文压缩，同时把辅助识图明确
   保持为不继承当前会话的独立辅助推理；
7. Desktop 的弹窗、菜单和折叠组件使用统一过渡动画，左右分栏宽度可调且能够跨应用重启恢复。

成功标准是用户能够完成以下路径：

- 连续打开多个 Workspace 的“新会话”页面并输入草稿，会话列表始终不出现空记录；
- 每个 Workspace 保留自己的一份临时草稿，未绑定 Workspace 也有独立一份，切换回来能够继续；
- 退出应用或刷新 WebView 后临时草稿不恢复，也不会在 Runtime 留下草稿或空 Session；
- 首次发送成功后，只创建一条 Session 和一条用户输入；失败重试不会创建重复 Session；
- 首轮回复可靠结束后标题在后台更新，不阻塞回复，模型失败时仍有可用标题；
- 输入精确 `/title` 可以在 Session 运行或空闲时触发同一标题旁路机制，不产生普通消息或 Run；
- 自动触发与手动触发都由标题机制自行读取调用时最新的 Conversation Snapshot，调用方不分别
  装配首轮、近期消息或 Context Summary；
- 为 Workspace 设置稳定标签、增加和排序多个目录，Agent 能可靠识别会话所属项目及可用目录；
- 在一个 Workspace 内跨多个登记目录读取或修改文件时，仍受现有 Plan/Build 与权限规则约束；
- 选择一段短文本后可以引用，模型始终看到选中的原文，并可按来源引用召回消息内或消息周边内容；
- 在 Composer 粘贴截图或复制的图片后立即出现图片附件 Tag；只粘贴普通文字不会生成附件；
- 同一次粘贴同时含文字和图片时，文字插入原光标选区，图片进入上下文区；图片登记失败不丢文字；
- 新会话可以只粘贴图片后发送，图片随首次物化提交；发送失败后图片仍留在对应 Workspace 草稿；
- 点击 Composer 顶部附件或引用 Tag 能打开详情，点击移除只移除该项；
- 点击引用来源可以一次性定位并高亮原消息，发送、关闭、滚动、切换会话或定位失败后绝不残留高亮；
- 自动标题、手动/自动上下文压缩和辅助识图的用途、上下文来源、持久化结果与失败影响均可区分，
  且系统中不出现第二类持久 Session。
- 打开或关闭弹窗、下拉/上拉菜单、Popover、抽屉与 Collapse 时具有一致、短促且可中断的过渡，
  开启减弱动态效果后不依赖动画也能完整操作；
- 独立拖拽左、右侧栏到需要的宽度，收起再展开或重启应用后仍恢复用户宽度，窄窗口下中间会话区
  不会被挤到不可用。

## 四、明确非目标

本版本不包含：

- 把新会话草稿同步到 Runtime、数据库、云端或应用重启后的本地持久恢复；
- 在会话列表、搜索结果、最近使用或主控工具中展示草稿记录；
- 自动保存任意历史 Session 的 Composer 草稿；本版本只处理“新会话”临时草稿；
- 为标题生成向主 Agent 装配设置标题工具，或让主 Agent 自主决定何时生成标题；
  标题旁路内部仅用于结构化输出的函数契约不属于主 Agent 工具；
- 自动重写用户手动标题、批量重命名既有 Session 或重新生成全部历史标题；
- 把 `/title <文本>` 解释为直接命名；显式文字标题继续使用现有标题编辑入口，`/title` 只执行
  基于 Conversation 的模型生成；
- Workspace 嵌套、Workspace 之间继承、远程文件系统、容器挂载或 Git 仓库管理；
- 每个目录独立的 Workspace 私有目录、独立 Workspace 权限文档或读写角色系统；
- 允许 Session 在创建后重新绑定 Workspace，或跟随 Workspace 后续目录变更静默改变冻结执行环境；
- 跨 Session、跨 Workspace 或跨应用选择文本后直接引用；首版只引用当前 Session 内当前可见的
  主 Conversation 或其子任务正文；
- 用引用替代 Conversation Recall、复制完整消息树，或默认把整条来源消息及相邻消息全部塞入模型上下文；
- 将来源 `message_id` 暴露给 Provider、把它设计成模型工具参数，或增加引用专属消息读取工具；
- 持久化来源高亮、修改消息正文 DOM 标记，或承诺来源删除后仍能定位；
- 主动读取系统剪贴板历史、监听 Composer 之外的全局粘贴，或把非图片文件、HTML、远程图片 URL、
  Base64 文本和普通文字自动解释为图片附件；
- 为旁路推理创建 `SideSession`、第二份 Conversation、普通 UserMessage、Input、Run、Queue 或工具循环；
- 把辅助识图改为继承当前 Session Conversation，或把视觉模型配置复用为通用文本辅助模型配置；
- 在本版本实现新的上下文裁剪算法；上下文压缩继续使用现有 `agent-context` 唯一路径；
- 为原生文件选择器、系统菜单、系统窗口动画或第三方 WebView 内核界面强行增加应用内动画；
- 保存每个 Workspace、Session 或窗口实例各自的分栏宽度；本版本保存一组设备本地 Desktop 偏好。

## 五、核心概念与生命周期

| 概念 | 权威所有者 | 是否持久化 | 是否进入会话列表 | 是否继承当前 Conversation |
| --- | --- | --- | --- | --- |
| 产品 Session | Runtime | 是 | 是 | 是 |
| 新会话草稿 | Desktop 当前进程 | 否 | 否 | 否；首次发送时才创建 Session |
| 旁路推理 | Runtime 领域操作 | 仅持久化领域结果与必要状态 | 否 | 是，读取冻结的有界快照 |
| 独立辅助推理 | 具体工具或诊断领域 | 按调用方既有规则 | 否 | 否 |
| 文本引用 | 引用所在 UserMessage | 是 | 作为消息内容展示 | 携带冻结纯文本选区、有界上下文与直接来源定位 |
| 来源瞬时焦点 | Desktop | 否 | 否 | 不适用 |

### 5.1 产品 Session

Session 仍是 Runtime 持有的正式会话身份，拥有 Conversation、Input、Run、Queue、Workspace
绑定、模型设置和持久化事实。没有 Runtime 接受结果就没有 Session；Desktop 不预分配业务
Session ID，也不维护一份可与 Runtime 冲突的权威会话。

### 5.2 新会话草稿

新会话草稿是当前 Desktop 进程内的临时编辑状态。它可以包含文本、待上传文件、引用、Workspace、
模型和执行设置，但没有 Session ID、Conversation generation、Input 或 Run。草稿只为用户导航
期间保留编辑连续性，不承诺跨应用重启恢复。

### 5.3 旁路推理

本文所称“旁路会话”在产品和技术语义上统一命名为**旁路推理**：它是某个已有 Session 领域
操作发起的一次有界模型交换，不是产品 Session。自动标题和上下文压缩属于旁路推理；
标题可暴露一个只用于结构化返回值的函数契约，但 Runtime 不执行它，也不进入 Agent Tool Loop。

### 5.4 独立辅助推理

独立辅助推理不继承当前 Conversation。辅助识图由工具目标和图片构造自己的请求，即使将来与
旁路推理复用薄的模型请求执行能力，也不能共享 Session 快照、标题/压缩提交规则或生命周期状态。

### 5.5 文本引用与来源焦点

文本引用是随 UserMessage 持久化的结构化用户内容；来源焦点只是 Desktop 为“查看来源”建立的
一次性视觉状态。两者必须分离，不能因为高亮失效而损坏已经发送的引用，也不能把视觉高亮写回
消息状态。

## 六、新会话临时草稿与首次发送物化

### 6.1 草稿分区

- Desktop 为每个 active Workspace 保留至多一份新会话草稿，并为“未绑定 Workspace”保留
  一份独立草稿。
- 草稿 key 是 `WorkspaceId | unbound`，不是 Workspace 标签或目录路径；修改标签或目录不能
  造成草稿串位。
- 点击“新对话”只选择对应草稿，不调用 `create_session`。如果目标没有草稿，就按当前默认配置
  建立一份空的内存状态。
- 在新会话与已有 Session 之间导航时，草稿继续保留在当前 Desktop 进程；应用退出、WebView
  刷新或进程重建后全部丢弃，不写磁盘恢复文件。
- Workspace 被移除时，对应未发送草稿立即失去可发送资格；Desktop 提示用户切换 Workspace
  或放弃草稿，不把它静默迁移到其他 Workspace。

### 6.2 草稿内容

每份草稿至少保存：

- 正文文本；
- 待上传附件的原生选择句柄、名称、大小和本地状态；其中包括文件选择器登记和剪贴板图片登记；
- 尚未发送的结构化文本引用；
- Workspace 选择；
- 模型、reasoning effort、Agent 变体和审批模式；
- 已选择的用户 Skill 与 Goal 提交意图等当前 Composer 可发送设置。

草稿中的 Workspace、模型和执行设置只是首次发送意图。Session 创建成功后，Runtime 才按照
正式规则冻结或持久化对应事实。

### 6.3 首次发送是单一物化边界

用户点击发送后，Desktop 发起“创建 Session 并接受首条输入”的统一意图。对用户和业务事实而言，
以下内容必须一起可靠成立：

1. Session 使用草稿当前 Workspace、模型和执行设置创建；
2. 待上传附件成为该 Session 的正式附件引用；
3. 文本、引用、附件、Skill/Goal 意图形成首个 Input 与 UserMessage；
4. 首个 Run 被接受并进入该 Session 的串行执行路径；
5. Session 出现在列表并成为当前选中会话。

附件字节如何在 Session 尚不存在时校验和提交，由技术方案基于现有上传链路选择最小物理步骤；
不能以“先创建可见空 Session、上传失败后再清理”代替用户可观察结果的一致性。

> **简化设计标记**：上述“一起可靠成立”描述的是用户可观察的业务结果，不预设必须实现一个
> 覆盖 Session、附件和 Input 的通用分布式事务，也不授权提前建设持久 Draft、通用上传租约服务、
> Provisional Session 状态机或独立事务协调器。技术方案必须先评估复用现有 `create_session`、
> 附件上传和 `accept_input` 链路，通过一个窄的首次提交入口、短生命周期进程内暂存或延迟列表
> 可见性满足要求；只有失败注入和重启幂等验证证明这些最小方案不足时，才增加范围受限的暂存标识。
> 无论采用哪种物理步骤，Desktop 都不能持有第二份 Session 权威状态，Runtime 也不能留下最终
> 可见的空会话记录。

### 6.4 失败、重试与清理

- 首次发送在可靠接受前失败：不创建可见 Session，保留该 Workspace 草稿的正文、附件、引用和
  设置供用户重试。
- Runtime 已接受但客户端未收到响应：相同幂等键重试必须返回同一 Session/Input/Run，不能创建
  第二条 Session。
- 首次发送可靠接受：Desktop 切换到正式 Session，并清空原草稿中的正文、附件 Tag、引用 Tag、
  Skill/Goal 临时状态和原生文件选择句柄。
- 普通已有 Session 发送继续沿用“失败保留、成功清空”的规则。
- 点击发送时，无论最终成功或失败，都立即清除浏览器文本选区、引用气泡、来源定位和瞬时高亮；
  发送失败可以保留引用 Tag 供重试，但不得恢复高亮。

## 七、自动标题

### 7.1 两阶段标题

- 首次输入可靠接受时，Runtime 继续用第一条非空用户文本截断生成**确定性兜底标题**，确保列表
  立即可读且不依赖模型成功。
- 首个用户来源 Run 可靠完成并产生最终 Assistant 文本后，Runtime 异步发起一次标题旁路推理。
- 自动调用方只提交“自动触发”意图，不装配首轮用户/Assistant 片段。标题机制在真正执行时读取
  最新 Conversation Snapshot，并按统一规则自行选取有界、适合生成标题的内容；该规则同样服务
  手动 `/title`，不因 trigger 分叉。
- 标题机制不得把 reasoning、完整工具详情、附件字节或隐藏凭据作为标题输入；具体取用
  User/Assistant、Context Summary 等哪些规范部分，由后续技术方案在统一机制内部固定。
- 标题生成不阻塞主回复、不创建普通 Run、不装配业务工具、不写入 Conversation。
- 标题旁路只暴露一个输出契约函数，要求模型在 `title` 参数中返回结果。Runtime
  只解析唯一的对应调用，不执行工具、不回传 Tool Result；普通文本、错误函数或多次调用
  一律视为失败，不得作为标题。
- 有效 `title` 必须去除多余引号、换行和标记，并服从统一标题长度与空值校验；
  无效结果等同失败。

### 7.2 手动 `/title`

- 精确 `/title` 是 Session 上下文控制命令，与 `/compact` 同类：它不形成普通 UserMessage、Input、
  Run 或 Queue 项，也不写入规范 Conversation。
- `/title` 调用方只提交“手动触发”意图；标题机制与自动触发完全相同地读取调用时最新的
  Conversation Snapshot、选择输入、调用模型、校验格式并写回标题。
- Session 无论处于空闲、运行、排队、审批或压缩状态都可以手动触发；Snapshot 之后继续产生的
  消息不属于本次生成输入，也不影响当前 Run。
- 附件、引用、Goal、Skill 等 Composer 临时状态不参与标题生成，也不构成调用门禁；新会话草稿
  尚未物化 Session、没有 Conversation Snapshot，因此只能在首次发送创建 Session 后使用。
- 手动触发可以更新兜底、自动生成或直接编辑的当前标题。并发、重复调用和写回顺序统一由标题
  机制处理，不按 trigger 设计不同提交路径，也不为本需求新增 title revision 状态。
- 生成成功后更新标题并显示轻量完成反馈；失败、取消或输出无效时保留触发前标题并显示可重试提示。
- Controller Session 保持固定产品身份，不执行自动标题或手动 `/title`。

### 7.3 模型路由与失败

- v0.22.0 默认使用该 Session 冻结的模型执行标题生成，不新增或复用“辅助视觉模型”配置。
- 旁路推理公共生命周期允许未来按任务类型选择轻量文本模型，但本版本不为尚未确认的模型路由
  增加用户设置。
- 模型不可用、超时、取消、输出无效或首轮 Run 未成功产生回复时，保留兜底标题，不影响 Session
  与主 Run 终态。
- 普通模型失败只结束本会话纪元的本次自动标题尝试，不在后台无限重试；异常重启恢复可以根据
  持久资格状态幂等补做尚未真正发起或尚未可靠结算的一次任务。

### 7.4 标题优先级与生命周期

- 首轮自动触发继续尊重现有用户直接编辑标题优先语义；用户主动执行 `/title` 则明确要求重新生成，
  可以更新当前标题。除此之外不增加新的标题来源层级或 revision 状态。
- Session clear 统一保留当前标题，不区分它来自兜底、自动生成、`/title` 或直接编辑；clear 不因
  标题来源重新生成、重置或分支处理标题。
- Fork 保留现有可解释的副本标题；只有用户在 Fork 中提交第一条新输入并完成回复后，才允许针对
  Fork 的新工作生成一次标题，不能仅根据继承的旧历史静默改名。
- Controller Session 的固定产品身份不参与普通自动标题生成。

## 八、Workspace 固定标签与多目录

### 8.1 固定标签

- Workspace 增加稳定的用户可读标签。字段对外统一称为 `label`，避免与 Session `title` 混淆。
- 新登记 Workspace 默认使用主目录 basename 作为标签，用户可以在登记时或之后显式修改。
- “固定”表示标签属于 Workspace 自身，不随 Session 标题、当前目录、对话内容或自动标题变化；
  不表示用户永远不能重命名。
- 标签允许重复，稳定身份仍是 `WorkspaceId`。Desktop 和 Agent 在可能歧义的位置同时展示标签与
  目录摘要，不能把标签当成唯一键或路由键。

### 8.2 有序目录集合

- 一个 Workspace 拥有一个主目录和零个或多个附加目录，组成非空、有序、去重的 canonical
  目录集合。
- 主目录决定默认 Shell 工作目录、默认标签、Workspace 主要展示路径和无歧义时的简写。
- 用户可以增加、移除附加目录和调整顺序；更换主目录属于明确操作，不能由排序副作用隐式完成。
- 同一 canonical 目录不能在同一 Workspace 重复登记；目录不存在、不可访问或与现有登记存在
  不安全重叠时应给出可解释诊断，具体校验规则由技术方案固定。
- Workspace 仍只有一个 Runtime Home 下的 `workspace_private_directory`，不为每个用户目录复制
  私有目录。

### 8.3 Agent 执行环境

- 新 Session 创建时冻结 Workspace 当时的 `WorkspaceId`、标签快照、主目录和有序目录集合。
- 结构化文件能力将全部冻结目录视为该 Session 的 Workspace 用户区域；实际读写仍受 Agent
  变体、权限规则、审批和工具能力约束。
- Shell 默认 `cwd` 为主目录。Shell 仍以当前用户权限执行、不是强沙盒；多目录列表不能被宣传为
  Shell 的操作系统级隔离边界。
- System Context 和主控受管会话查询必须向 Agent 提供 Workspace 标签、主目录及附加目录，
  使其能用可读事实选择项目，而不是猜测 `WorkspaceId`。
- Workspace 权限文档仍是每个 Workspace 一份，并作用于全部登记目录；精确路径规则继续基于
  canonical 绝对路径判断，不因标签或目录顺序改变含义。

### 8.4 Instructions 与 Skills

- 每个冻结用户目录都可以提供其根级 Instructions 和 Workspace Skills；来源必须带目录身份，
  不能把多个根拼成无法判断适用范围的一段匿名文本。
- 根级 Instructions 只约束对应根目录下的文件与工作；跨根的共同用户意图仍由 Session 请求和
  Workspace 级上下文表达。
- 同名 Workspace Skill 冲突时，主目录优先，其余按冻结目录顺序选择第一项；被遮蔽项必须可诊断，
  不能随文件系统枚举顺序随机变化。
- Global、User、Workspace、Built-in 之间的既有优先级不变；多目录只细化 Workspace 来源内部
  的稳定次序。

### 8.5 Workspace 修改与既有 Session

- 修改 Workspace 标签后，列表与 Agent 的 Workspace 识别信息使用当前标签；Session 的目录和
  权限执行环境仍保持创建时冻结事实。名称更新只是 Workspace 元数据变化，不能因此重建、替换或
  修改既有 Session 已冻结的 System Prompt 与 System Context。
- 增加、移除或重排目录只影响之后创建的 Session 和尚未物化的新会话草稿；既有 Session 不静默
  获得或失去目录访问范围，也不触发 System Prompt/Context reload。
- Desktop 必须提示“目录变化仅对新会话生效”，并允许用户从该 Workspace 新建草稿继续工作。
- 移除 Workspace 继续沿用软移除与既有 Session 可解释恢复规则，不因多目录化直接删除用户文件。

## 九、会话文本引用与 Composer 上下文区

### 9.1 引用入口

- 用户在当前 Session 的主 Conversation 或当前打开的子任务正文中选择非空文本后，Desktop 显示
  轻量浮动气泡，主操作为“引用”。
- 消息正文不劫持右键 Context Menu；复制等操作沿用 WebView 原生菜单，引用只保留浮动气泡入口，
  避免两套浮层竞争。
- 选区可以跨越同一消息正文内的文本、行内代码、链接、强调等渲染元素；只在跨越多条消息、工具块、
  交互控件或超出合理大小时拒绝。首版不把多个来源自动合并成一条引用。
- 点击引用只读取当前 Conversation 投影并更新 Desktop Composer 草稿，不调用 Host/Runtime；因此旧
  Runtime、网络错误或模型状态都不能影响引用 Tag 的创建。
- 引用只加入当前 Session Composer。跨 Session 或跨 Workspace 引用留待后续版本。

### 9.2 结构化引用

每条引用至少包含以下语义：

- `exact`：浏览器 Selection 产生的冻结可见文本，始终是引用预览和模型输入的核心内容；
- `prefix` / `suffix`：同一消息“可见文本投影”中选区前后的有界纯文本，每侧最多 128 个 Unicode
  字符，用于短文本和重复文本消歧；
- 来源所有者、Conversation generation、规范 Message 身份，以及相对于可见文本投影的起止范围；
- 来源角色、时间和可读预览等展示元数据。

引用作为 UserMessage 的结构化内容随 Input 持久化，不简单拼接进用户 Markdown 正文，也不建立
独立 Quote 表或可变镜像。来源定位字段是应用内导航元数据，不进入 Provider 投影；Provider 只看到
冻结纯文本和有界上下文。行内代码、链接、强调等渲染结构不反向转换为 Markdown，也不参与证明来源身份。

### 9.3 短选区与来源定位

- 即使用户只选择一个词，模型也会直接看到 `exact` 和有界 `prefix/suffix`，不需要通过 Message ID
  或引用专属工具找回原文。
- 来源定位优先使用 `owner + generation + message identity + visible range`；范围直接区分同一消息中的
  重复短句，不再通过 `exact/prefix/suffix` 反向搜索 raw Markdown occurrence。
- 该直接 locator 只供 Desktop 打开已有 Conversation、滚动和高亮。它不是 capability token，不能作为
  Provider 参数，也不开放读取其他 Session 消息的接口；既有 Conversation Recall 机制不与引用绑定。
- 来源被 clear、删除、generation 变化或定位失败时，`exact/prefix/suffix` 冻结快照仍可用，
  只有“查看来源”降级为不可用；产品不能搜索相似文本冒充原来源。

### 9.4 Composer 图片粘贴与顶部附件/引用区

- Composer textarea 只在实际 `paste` 事件中检查剪贴板文件项；`kind=file` 且 MIME 声明为
  `image/*` 的项按剪贴板顺序登记为待发送附件。
- 没有图片文件项时完全保留浏览器普通文字粘贴行为。图片与 `text/plain` 同时存在时，文字替换当前
  选区并把光标移动到插入内容之后，图片同时进入附件区；不能因为处理图片吞掉文字。
- 剪贴板图片沿用附件数量、单文件大小、真实媒体类型校验和失败反馈。登记失败只回滚本次新增图片，
  已插入文字和原有附件/引用保持不变。
- 图片登记成功后不再保留 Web `File` 作为另一份长期草稿数据，而是取得和文件选择器一致的进程内
  原生选择句柄；新会话按 Workspace 草稿保存该句柄，已有 Session 也在发送时走现有附件上传。
- 没有正文时，只要存在有效附件也允许发送；该规则同时适用于文件选择器附件和粘贴图片。

- Composer 顶部使用统一的上下文 Tag 区展示待发送附件和引用；两者视觉可区分，但交互遵循同一模式。
- 点击 Tag 主体打开详情弹窗：附件展示名称、大小、类型、上传状态和可用预览；引用展示完整 `exact`、
  有界前后文、来源角色和来源状态。
- Tag 的移除按钮只移除该附件或引用，不打开详情；上传或其他不可中断阶段按既有取消语义处理。
- 引用详情中的“查看来源”仅在来源仍可解析时启用；不可解析时保留冻结预览并解释原因。
- 已发送 UserMessage 继续展示其引用摘要；查看详情读取持久引用内容，不依赖 Composer 草稿。

### 9.5 来源定位与瞬时高亮

- 来源定位由独立的 `TransientFocusTarget` 类状态驱动，通过可扩展 resolver 解析主消息或子任务
  来源；消息组件不保存持久 `highlighted` 标记，也不修改正文内容。
- 定位成功后滚动到来源并进行一次性高亮；同一时刻只允许一个瞬时焦点，新目标会先清理旧目标。
- 超时、关闭详情弹窗、点击发送、切换会话、滚动、组件卸载、来源解析失败都必须清理选区、焦点和高亮。
- **点击发送即强制清理瞬时高亮**。发送成功后再清空引用与附件 Tag；发送失败保留 Tag 供重试，
  但高亮不会自动恢复。
- resolver 遵循开闭原则：新增来源类型通过注册解析器扩展，不能在各消息组件中增加无法统一回收
  的高亮分支。任何异常路径都只能退化为“显示冻结预览”，不能留下不可恢复的视觉状态。

## 十、旁路推理机制

### 10.1 统一生命周期，不统一领域结果

Runtime 为旁路推理建立统一生命周期语义：

1. 领域所有者在明确节点创建任务，并冻结有界输入快照、任务类型和调用 Session；只有压缩等确实依赖
   body generation 的领域才同时记录 generation；
2. 任务选择模型路由、超时、取消与输出上限，不装配 Agent 工具；
3. 模型请求独立执行，不占用主 Agent Tool Loop，也不向 Conversation 写中间消息；
4. 领域所有者在提交前只校验自身需要的条件：标题校验当前任务身份与用户改名，压缩校验 generation；
5. 只持久化领域结果、结算状态和必要用量，不持久化第二份 Conversation；
6. 失败只影响对应辅助结果，不改变主 Run 已有终态。

公共能力仅承载模型请求、超时/取消、用量、错误归类和提交前 guard 所需的最小契约。标题格式、
Context Summary、压缩 generation 切换等仍由各自领域所有，不建立可以任意读写 Session 的万能
“辅助任务服务”。

### 10.2 自动标题

标题生成功能是旁路推理的新调用方，具有首轮可靠结束的自动 trigger 和精确 `/title` 的手动
trigger。两个调用方都只把 Session 与 trigger 交给同一个标题生成用例；用例内部读取调用时最新
Conversation Snapshot、统一选择内容、调用模型、校验并写回。trigger 只用于记录调用来源和决定
是否由生命周期自动发起，不改变推理装配、模型路由、输出格式或持久化机制。

### 10.3 上下文压缩

- 自动压缩和 `/compact` 继续由 Runtime 的上下文压缩领域触发，使用 `agent-context` 的既有滚动
  摘要策略和当前 Session 模型。
- 压缩读取当前 Conversation 的稳定快照，输出 Context Summary 候选；只有 generation 和压缩
  操作仍匹配时才能提交。
- 手动压缩仍不是普通 UserMessage、Input 或 Run；取消、失败和 no-op 继续保留现有产品语义。
- 本版本收敛其模型调用生命周期与可观测性，不另建压缩算法或旁路 Session。

### 10.4 辅助识图明确不是旁路会话

- 辅助识图不继承当前 Conversation，只读取工具调用目标与待识别图片，因此归为独立辅助推理。
- 它继续使用明确配置的辅助视觉模型，并把结果作为原工具调用的 Tool Result 回到主 Run。
- 它可以复用 provider-neutral 单次模型执行、超时、取消和用量记录等薄能力，但不能复用旁路推理
  的 Session 快照、conversation generation 或标题/压缩提交规则。
- 该区分以“输入是否继承当前 Conversation、结果由谁提交”为准，而不是以“是否调用了第二次模型”判断。

### 10.5 可观测性与恢复

- 每次旁路或独立辅助推理都应记录任务类型、模型键、开始/结束状态、脱敏错误和 usage；不得伪装
  为主 Run token 使用或 Context Window 占用。
- Session 相关旁路任务可以计入 Session 的辅助用量汇总，但必须与主 Agent Run 使用量可区分。
- Runtime 关闭、Session 删除、clear、generation 变化或领域资格消失时，应取消任务或让迟到结果
  在提交 guard 处稳定失效。
- 恢复只重建仍有持久业务必要的资格与领域结果，不恢复模型流或第二份隐藏聊天记录。

## 十一、Desktop 统一动效与可调分栏

### 11.1 统一过渡范围

本版本统一覆盖 Desktop 自有的以下组件：

- 模态弹窗及其遮罩；
- 下拉菜单、上拉选择器、Context Menu、Popover、Tooltip 之外的操作浮层及级联菜单；
- Composer 二级抽屉、思考过程、Workspace/会话分组、消息详情等 Collapse；
- 左右侧栏的展开与收起。

Tooltip 继续以即时可读为优先，只允许极短淡入；Toast、加载旋转和持续流式状态沿用各自语义，
不为“统一”强制套用弹窗动画。

### 11.2 动效语言

- 动效继续遵循“克制、清晰、紧凑、安静”的设计语言。常规过渡使用约 `100–160ms`，大型弹窗
  最长不超过约 `180ms`；最终分级和 easing 在界面交互设计指导中统一固定。
- 弹窗使用遮罩透明度与内容轻微透明度/位移或缩放；菜单沿实际展开方向做短距离位移和淡入；
  Collapse 使用内容尺寸、透明度与箭头旋转表达层级变化，不使用弹跳或夸张缩放。
- 打开和关闭都必须有对应过渡。组件可以在退出动画结束后卸载，但业务状态、焦点陷阱和背景
  `inert` 不能因延迟卸载而出现可交互泄漏。
- 快速连续开关、Esc、点击外部、路由切换或父组件卸载都必须可中断并收敛到最后一次状态，不能
  残留透明遮罩、不可点击页面、错位 Popover 或未恢复焦点。
- 动画只表达界面状态，不延迟 Runtime 命令、危险确认、审批决定或发送行为。用户动作被可靠接受
  后立即更新业务状态，再让视觉层完成退出过渡。
- 优先使用 `opacity`、`transform` 等低成本属性；需要真实尺寸的 Collapse 和侧栏宽度变化必须在
  流式消息与低性能设备上验证，不允许造成消息列表持续抖动或输入延迟。

### 11.3 无障碍与减弱动态效果

- 全部过渡遵循 `prefers-reduced-motion: reduce`。减弱模式关闭非必要位移、缩放和尺寸动画，保留
  即时状态切换或极短淡入，不影响内容、焦点、键盘路径和完成反馈。
- 动画期间语义状态必须已经正确：打开组件可被辅助技术识别，关闭组件不再进入 Tab 顺序。
- 菜单、弹窗和 Collapse 继续满足既有 Enter、Space、方向键、Esc、焦点返回与 `aria-expanded`
  语义；动画不能成为判断状态的唯一线索。
- 自动化测试可以稳定跳过或等待过渡，不依赖任意 sleep 猜测组件何时可操作。

### 11.4 左右分栏拖拽

- 左侧会话栏与中间会话区之间、右侧上下文栏与中间会话区之间各提供一个独立拖拽分隔条。
- 分隔条在 Hover、键盘聚焦和拖拽时显示清晰反馈，鼠标指针表达横向调整；默认状态保持克制，
  不增加持续抢眼的粗边框。
- 两侧栏只在展开时允许调整。拖动一侧只改变该侧宽度，不按比例联动另一侧。
- 左、右栏各有设计规定的最小值、默认值和最大值；中间会话区继续保有不低于现有设计基线的
  最小可用宽度。接近边界时宽度稳定 clamp，不允许侧栏覆盖 Composer、弹窗或另一侧栏。
- 窗口暂时变窄时可以压缩实际展示宽度或沿用既有响应式收起策略，但不能覆盖用户保存的偏好值；
  窗口重新变宽后恢复用户偏好。
- 拖拽期间禁止误选页面文本，不触发会话导航；结束、取消、窗口失焦和组件卸载都必须释放指针捕获
  与拖拽状态。

### 11.5 键盘、恢复默认与持久化

- 分隔条使用可访问的 separator 语义并可聚焦；方向键按固定步长调整，较大步长和到达边界的
  快捷方式由界面交互设计指导统一确定。
- 现有“恢复默认布局”同时恢复左栏 `286px`、右栏 `326px` 的设计默认宽度及默认展开状态；
  收起后再展开则恢复用户最近保存宽度，而不是强制回到默认值。
- 左右宽度与现有侧栏开关一起保存在 Desktop 设备偏好中，作用于整个应用，不按 Workspace、
  Session 或 Conversation 分叉。
- 拖拽过程只更新内存投影，结束时或受控 debounce 后持久化，不能每移动一个像素都同步写文件。
- 应用正常重启后恢复宽度；偏好缺失、旧版本没有宽度字段、数值损坏或超出新边界时安全回退或
  clamp 到设计默认。该持久化语义与“不跨重启恢复新会话草稿”互不冲突。

## 十二、模块职责

### 12.1 Desktop

- 持有按 Workspace 隔离的新会话内存草稿、原生文件/剪贴板图片选择句柄和瞬时来源焦点；
- 提供新会话、Workspace 标签/目录管理、图片粘贴、选区引用、Tag 详情与来源定位交互；
- 从同一消息正文内的浏览器 Range 生成可见文本范围、冻结纯文本和有界上下文；引用加入 Composer
  时不调用 Runtime，也不反向匹配 raw Markdown；
- 首次发送只表达统一物化意图，不预创建 Session 或自行拼装权威消息历史；
- 发送成功清理草稿，发送失败保留可重试内容；所有发送尝试立即清理选区和瞬时高亮；
- 统一浮层/Collapse 过渡状态与可调分栏，持有实时宽度并通过既有 Desktop 偏好入口保存。

### 12.2 assistant-protocol

- 承载 Workspace 标签/目录、首次提交、结构化引用及必要旁路状态的跨层 DTO；
- 保持 provider-neutral、UI-neutral，不包含 DOM Range、浏览器 Selection 或本机私有文件句柄；
- 引用来源使用规范消息身份和可见文本范围；这些字段只用于应用内来源导航，不作为授权凭据或
  Provider 可调用参数。

### 12.3 Runtime Host

- 继续只负责 loopback HTTP Command、SSE、Streaming Upload 和 Desktop/Runtime 传输适配；
- 为首次提交的附件暂存提供受控传输生命周期时，不持有第二份 Session 或草稿权威状态；
- 断线、重复请求和上传中断必须保留幂等与清理边界。

### 12.4 assistant-runtime

- 持有 Session 首次物化、标题状态、Workspace 标签/目录、引用提交校验与旁路推理编排的权威状态；
- 冻结 Session 的多目录执行环境，装配文件、Shell、权限、Instructions、Skills 与 Agent 可见信息；
- 在发送时校验引用数量、大小和结构并持久化冻结内容；不签发引用 token，不新增引用专属 Message ID
  查询或 Recall 工具；
- 保证首次提交的幂等、标题当前任务/用户改名保护和压缩 generation guard 各自成立；标题自动/手动
  trigger 不形成两套提交机制，也不增加 title generation/revision guard。

### 12.5 Agent crates

- `agent-context` 继续拥有上下文布局、判断与压缩策略，不承担产品 Session 生命周期；
- `agent-model` 提供 provider-neutral 单次模型调用能力，不知道标题、Workspace 或 UI 草稿；
- `agent-types` 只在规范模型消息确实需要表达结构化引用时承载最小通用类型；
- `agent-tools` 与 `agent-tools-local` 按 Runtime 冻结的多目录能力工作，不自行读取 Workspace 存储；
- Agent Core 仍只执行单次 AgentExecution，不调度标题、草稿或产品会话。

## 十三、兼容与迁移

- 存量 Workspace 迁移为“basename 默认标签 + 原 `user_directory` 作为唯一主目录”；Workspace ID、
  agent directory、生命周期和 Session 绑定不变。
- 存量 Session 继续使用恢复出的冻结单目录执行环境，不因 Workspace 迁移自动获得新目录。
- 存量标题保持原值和来源，不批量调用模型；Session clear 统一保留当时的当前标题。
- 已存在的空 Session 不自动删除或隐藏；“不创建空记录”只约束 v0.22.0 之后的新会话入口。
- 旧消息没有结构化引用，继续按原投影显示；新引用不能改变旧 Message ID 或附件引用语义。
- 现有 Context Summary、手动 `/compact`、辅助识图 Tool Result 和 Session usage 必须可迁移并保持
  既有含义；新增分类只能补充可观测性，不能重写历史。
- 旧 Desktop 偏好没有分栏宽度时使用 `286px / 326px`；既有左右栏开关和 Workspace 展开状态
  保持不变。损坏偏好继续使用设计默认值，不能阻止应用启动。
- 跨层协议变化必须同步检查所有生产者、消费者、生成 TypeScript、Host body 上限、序列化兼容和
  持久化恢复；旧 Desktop 与新 Host 的兼容策略由技术方案明确。

## 十四、验收标准

1. 点击任意 Workspace 或未绑定入口的“新对话”后，Runtime Session 数量与会话列表均不变化。
2. 同一 Desktop 进程内，每个 Workspace 与 unbound 各保留一份独立草稿，来回切换互不覆盖。
3. 应用重启或 WebView 刷新后草稿不恢复，Runtime 中也不存在草稿 Session。
4. 首次发送成功时只产生一个 Session、一个 UserMessage、一个 Input 和一个 Run，并自动选中该 Session。
5. 首次发送在附件暂存、请求断线或 Runtime 拒绝时不留下可见空 Session，草稿可重试。
6. 使用同一幂等键重试已接受的首次发送，只返回原 Session/Input/Run。
7. 首次发送接受时立即出现确定性兜底标题；首轮回复结束后标题异步更新且不延迟回复。
8. 标题模型失败、超时、输出为空或首轮 Run 失败时保留兜底标题，Session 仍正常可用。
9. 首轮自动触发与精确 `/title` 只传入不同 trigger，标题机制对两者都自行读取调用时最新
   Conversation Snapshot 并走同一内容选择、模型调用、校验和写回路径。
10. 精确 `/title` 在标准 Session 空闲、运行、排队、审批或压缩时都可以触发，不产生 UserMessage、
    Input、Run 或 Queue，也不要求先移除附件、引用、Goal 或 Skill。
11. `/title` 失败保留原标题；Session clear 对所有来源的当前标题统一保留，不新增 title revision
    或按标题来源分支的 clear 规则；fork 行为符合 7.4。
12. 存量 Workspace 迁移后标签和单一主目录正确，Workspace ID 与既有 Session 绑定不变。
13. 用户可修改标签、增加/移除/排序附加目录；重复或不可用目录得到稳定诊断。
14. 新 Session 冻结全部有序目录；Workspace 后续名称或目录修改不改变既有 Session 的执行范围、
    System Prompt 或冻结 System Context。
15. 文件工具能在各冻结目录内按权限工作，Shell 默认 cwd 始终是冻结主目录。
16. 主控查询 Session 时能得到 Workspace 标签和目录摘要，不再只能看到不透明 Workspace ID。
17. 多目录 Instructions 和 Skills 的来源、作用范围与冲突顺序稳定且可诊断。
18. 选择当前 Session 的可用文本后，浮动气泡生成结构化引用；同一消息内跨行内代码、链接、强调等
    元素的选区仍能成功，跨消息选择被拒绝，右键保持 WebView 原生行为。
19. 点击引用不产生 Host/Runtime 请求；一词短选区发送后模型只看到一次纯文本 `exact` 和每侧最多
    128 个 Unicode 字符的前后文。
20. 来源使用直接消息定位和可见文本范围；来源过期或定位失败时冻结预览仍可读，来源字段不进入
    Provider，也不能用来读取其他 Session 的消息。
21. 点击附件或引用 Tag 打开详情，移除按钮只删除对应项；发送失败保留 Tag，成功后全部清除。
22. Composer 粘贴一个或多个图片文件项后按原顺序生成普通图片附件；只粘贴文字不生成附件。
23. 同次粘贴含文字和图片时两者都保留；登记失败不丢文字或原有上下文，图片-only 输入也能发送。
24. 粘贴图片在新会话草稿切换、首次发送失败、移除、成功和应用退出时与文件选择器附件遵循同一
    句柄与清理生命周期，不泄漏长期临时文件。
25. 查看来源产生的高亮在发送、超时、关闭、滚动、切换、卸载和失败路径均能完全恢复。
26. 自动标题、手动 `/title` 和上下文压缩不创建 UserMessage、Input、Run、Queue 或第二类
    Session；标题输出契约的模型 ToolCall 只在单轮结果中解析，不执行、不持久化、不回传。
27. 辅助识图请求不包含当前 Conversation，结果仍通过原 Tool Result 返回主 Run。
28. 标题被新 trigger、直接改名、clear 或删除取消后不能提交迟到结果；普通 Run/Compaction 的后续提交
    不使调用时快照失效。上下文压缩继续遵守自己的 generation 提交 guard，失败不改变主 Run 终态。
29. Desktop 自有弹窗、下拉/上拉菜单、Context Menu、Popover、二级抽屉与 Collapse 均有统一的
    打开/关闭过渡，没有只动画打开却瞬间消失的组件。
30. 快速连续开关、Esc、点击外部和路由切换后不残留遮罩、焦点陷阱、错误 `inert` 或不可见浮层。
31. `prefers-reduced-motion` 下关闭非必要位移/尺寸动画，所有鼠标、键盘和辅助技术路径仍完整可用。
32. 左右分隔条可独立用鼠标和键盘调整，始终遵守侧栏边界与中间会话区最低可用宽度。
33. 收起再展开、窗口缩小再恢复时保留用户偏好；应用重启后恢复最近保存的左右宽度。
34. 旧版、缺失、损坏或越界宽度偏好安全使用默认值或 clamp，“恢复默认布局”恢复设计默认宽度。
35. 文档、协议、Runtime 单测、Desktop 交互测试、正式 Host 集成验证和必要的真实模型验证均通过，
    且不回归现有会话、附件、压缩、召回、权限、Skills 和多终端能力。

## 十五、风险与取舍

### 15.1 首次发送跨附件上传与持久化，原子边界复杂

“不留下空 Session”不能只靠 Desktop 隐藏列表项，否则重启后会暴露孤儿记录。技术方案需要把
附件暂存、Session 创建和首个 Input 接受设计成可回收、可幂等的业务边界，并验证进程中断；
实现必须遵循 6.3 的简化设计标记，优先收窄和复用现有链路，不能直接演进成通用草稿或事务系统。

### 15.2 多目录扩大了文件与指令作用范围

多目录不是简单把多个路径拼进提示词。权限判断、Shell cwd、Instructions/Skills 冲突、Session
冻结与 Workspace 后续编辑都必须一致；任何一层仍按单目录假设工作，都可能造成越权或误操作。

### 15.3 引用快照与来源可能分离

冻结 `exact` 保证已发送消息可解释，但来源 clear、删除或 generation 变化后不再保证定位。产品
必须明确展示“内容仍有效、来源不可用”，不能自动搜索一个相似文本并冒充原来源。

### 15.4 旁路生命周期统一不等于提前抽象所有模型调用

自动标题与压缩共享 Session 派生、单轮收集、提交 guard 等稳定事实；压缩仍是无工具
文本输出，标题使用不执行的输出契约函数。辅助识图只共享更薄的模型执行能力。本版本按已存在
调用方抽取，禁止为了未来摘要、翻译等假想任务建立万能公共框架。

### 15.5 自动标题会增加模型调用与费用

标题调用必须有严格输入/输出上限、超时和 usage 记录。自动 trigger 每个 Session 首轮至多发起
一次，用户可以按需再次执行 `/title`；两者沿用同一旁路调用和通用请求可靠性，不增加标题专属
并发状态机。确定性兜底确保用户可在禁用或失败环境下继续使用；本版本不增加复杂的轻量模型设置界面。

### 15.6 退出动画会延长组件物理存活时间

若只延迟卸载而不分离视觉状态与交互状态，透明弹窗仍可能截获点击或困住焦点。实现必须统一
enter/exit 状态机与清理协议，并对快速反转和父组件卸载单独验证。

### 15.7 分栏偏好与响应式实际宽度需要分离

把窄窗口 clamp 后的实际宽度写回偏好，会永久丢失用户原本设置；完全不 clamp 又会挤破中间区。
因此必须区分“用户偏好宽度”和“当前窗口实际宽度”，只在用户主动调整后更新偏好。

### 15.8 剪贴板图片字节需要受控暂存

剪贴板图片没有可长期复用的本地路径，若把 Web `File`、Base64 或 Object URL 直接留在多个组件状态中，
会造成大对象复制、刷新失效和清理不一致。Desktop 必须在一次 paste 事件内把有限图片字节登记到既有
原生选择池，并在移除、成功、TTL 和退出路径删除 owned 临时文件；Runtime 仍执行最终媒体嗅探和附件限制。

## 十六、设计结论与后续阶段

本版功能设计确认以下核心决策：

- 新会话草稿完全由 Desktop 当前进程持有，每个 Workspace 一份外加一份 unbound，不跨重启恢复；
- 首次发送是 Session、附件、首条消息、Input 与 Run 的统一物化边界；
- 自动标题在首轮可靠回复后触发，现有文本截断保留为即时兜底；精确 `/title` 只是同一机制的
  手动 trigger，机制内部统一读取调用时最新 Conversation Snapshot，不新增专用输入装配或 revision；
- Session clear 统一保留当前标题，不按兜底、自动生成、`/title` 或直接编辑来源分支处理；
- Workspace 使用 `label` 与“主目录 + 有序附加目录”，既有 Session 冻结目录不随 Workspace 编辑变化；
- 文本引用由 Desktop 从同一消息内的浏览器选区直接生成，冻结纯文本 `exact` 与每侧最多 128 个 Unicode
  字符的 `prefix/suffix`，使用消息身份和可见文本范围定位来源；点击时不调用 Runtime、不签发 recall reference；
- Composer 粘贴图片后把它登记为普通附件；同次文字继续插入，图片-only 可发送，失败与清理复用附件链路；
- 附件与引用共用 Composer 顶部上下文区，点击 Tag 查看详情；来源高亮是一次性可统一清理的瞬时状态，
  点击发送必须强制清除；
- 自动标题与上下文压缩属于继承当前 Session 快照的旁路推理；辅助识图不继承当前 Conversation，
  属于独立辅助推理；系统不建立第二类持久 Session；
- Desktop 自有弹窗、菜单、Popover、抽屉、Collapse 与侧栏收起使用统一短促动效，完整支持
  `prefers-reduced-motion` 和中断清理；
- 左右侧栏可独立拖拽与键盘调整，保存一组设备本地应用偏好；响应式 clamp 不覆盖用户偏好。
