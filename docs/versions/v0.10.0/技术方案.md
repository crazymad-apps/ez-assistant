# v0.10.0 技术方案：可靠会话与持久化执行

## 一、方案信息

- 版本：`v0.10.0`
- 状态：已确认（2026-08-07）
- 影响模块：`assistant-runtime`、`assistant-protocol`、`apps/runtime-host`、`agent-core`
- 关联功能设计：[`v0.10.0 功能设计`](功能设计.md)
- 核查依据：2026-08-07 实际源码、`cargo metadata --no-deps`、
  `cargo tree -p assistant-runtime -e normal` 与
  `cargo tree -p assistant-runtime-host -e normal`

本文只承接实现级内容：存储边界、SQLite 表、Conversation 文件格式、提交与恢复顺序、运行时

## 二、现状核查

### 2.1 当前权威状态全部位于内存

当前执行链是：

```text
AssistantRuntime.sessions: BTreeMap<SessionId, SessionController>
    └── SessionState
        ├── InMemoryJournal.completed
        ├── InMemoryJournal.pending
        ├── BTreeMap<RunId, RunRecord>
        └── ActiveRun
```

- `SessionController` 冻结 `model_key` 和 `SystemPromptSnapshot`，其余状态由同步 `Mutex` 保护。
- `InMemoryJournal` 把完整 Conversation 与单个 pending tool exchange 放在内存中；pending 不进入
  `ConversationSnapshot`。
- `start_run` 仅接受空闲 Session，在同一个内存临界区追加 User Message、创建 Run 并登记活动
  Run；已有活动 Run 时返回 `SessionBusy`。
- `RuntimeRecorder` 在工具副作用前调用 `begin_tool_exchange`，结果齐备后调用
  `complete_tool_exchange`，但两个阶段都没有落盘。
- `RunRecord` 的 reasoning、text 和工具 stdout/stderr 来自可丢的实时事件；终态正文由最终
  `AssistantMessage` 校准。
- Session ID、Run ID 和 Message ID 均为随机不透明标识，本身不表达顺序。

因此不能直接给现有结构增加一次“退出时保存”：退出前可能已经崩溃，且 SQLite、Conversation
文件、工具副作用和 Run 终态之间需要明确的提交边界。

### 2.2 已有恢复相关基础

- `ConversationMessage`、`SystemPromptSnapshot` 及其嵌套规范类型已经支持 Serde。
- `ConversationSnapshot::validate_tool_exchange_pairs` 能校验 Tool Call/Result 的唯一性、顺序和
  完整配对。
- Runtime 关闭已有等待上限，超时后会中止 supervisor 并强制结算活动 Run。
- Host 已显式观察 connection writer/event task 的 `JoinError`，不再静默吞掉 panic。
- Host 已通过实例锁保证同一 Runtime endpoint 只有一个产品进程；v0.10.0 将该约束扩展为同一
  Runtime Home 只有一个存储写入者。

仍需在本版本修复的是 `agent-core/src/execution.rs`：engine task 的 `JoinHandle` 被丢弃，
`CompletionFuture` 通过 oneshot 的 `expect` 取结果。engine panic 会让 completion 再次 panic，
而不是形成稳定的 `ExecutionOutcome`。

### 2.3 依赖核查

当前 workspace 没有 SQLite 依赖。方案选择
[`rusqlite`](https://docs.rs/rusqlite/latest/rusqlite/struct.Connection.html)，并由 Host 的专用
阻塞 worker 独占一个 `Connection`：它直接映射本版本所需的 SQLite 事务和约束，不引入 ORM、
连接池或异步 SQL 运行时。`rusqlite::Connection` 可以在线程间转移，但不作为并发共享对象使用；
M0 已通过 `cargo add` 将版本固定为 `rusqlite 0.40.1`，只启用 `bundled` feature 并关闭默认
feature；最终解析结果以 workspace `Cargo.lock` 为准。

SQLite 采用单连接、rollback journal 和完整同步。
[SQLite 事务](https://www.sqlite.org/transactional.html)保证单库事务的原子提交，但这种原子性
不自动覆盖外部 JSONL 文件，因此文件与数据库之间仍需要下面定义的 staged append 协议。

## 三、目标架构与依赖

### 3.1 所有权与依赖方向

```text
apps/runtime-host
├── Runtime Home / instance lock
├── storage::LocalRuntimeStore
│   ├── dedicated blocking worker
│   ├── rusqlite::Connection
│   └── per-Session Conversation JSONL
└── AssistantRuntime::open(RuntimeStore, ...)
          │
          ├── Session registry / queue driver / Run supervisor
          ├── PersistentJournal
          └── RuntimeStore port
                    │
                    └── agent-core::AgentExecution
```

- `assistant-runtime` 定义业务语义和 `RuntimeStore` 端口，不依赖 `rusqlite`、本地路径或文件句柄。
- `apps/runtime-host/src/storage/` 实现 SQLite 与文件提交协议；按模块地图、engine、worker、schema、
  filesystem、conversation、recovery、run_state 和 tests 分责，不把存储代码堆入 `main.rs` 或
  `server.rs`。
- `assistant-protocol` 只增加跨进程意图、状态和脱敏错误，不暴露表名、文件名、offset、generation
  或 staged operation。
- `agent-core` 只修正自身任务退出契约，不依赖 RuntimeStore。

不新增存储 crate。当前本地存储只有 Runtime Host 一个真实调用方，拆成新 crate 只会扩大公共
API；若以后出现第二个稳定宿主，再评估上提。

### 3.2 RuntimeStore 端口

端口按业务原子操作定义，不暴露通用 SQL CRUD：

```rust
pub trait RuntimeStore: Send + Sync {
    fn load_runtime(&self) -> StoreFuture<'_, RecoveredRuntime>;
    fn create_session(&self, session: NewStoredSession) -> StoreFuture<'_, StoredSession>;
    fn accept_input(&self, input: NewStoredInput) -> StoreFuture<'_, AcceptedInput>;
    fn commit_user_message(&self, start: UserMessageCommit) -> StoreFuture<'_, ()>;
    fn begin_tool_exchange(&self, pending: PendingToolExchange) -> StoreFuture<'_, ()>;
    fn complete_tool_exchange(&self, completed: CompletedToolExchange) -> StoreFuture<'_, ()>;
    fn settle_run(&self, settlement: StoredRunSettlement) -> StoreFuture<'_, ()>;
    fn rewrite_from_user(&self, rewrite: ConversationRewrite) -> StoreFuture<'_, RewriteResult>;
    fn set_session_archive(&self, change: ArchiveChange) -> StoreFuture<'_, ()>;
    fn set_session_model(&self, change: ModelChange) -> StoreFuture<'_, ()>;
    fn load_conversation(&self, session_id: &SessionId) -> StoreFuture<'_, ConversationSnapshot>;
}
```

以上是职责形态，不提前冻结最终 Rust 签名。实现时可把同一职责下的参数合并为经过校验的 command
类型，但禁止退化成 `execute_sql(String)`、通用键值接口或让 Runtime 自己拼接路径。

所有 store future 都由 Host worker 的有界命令队列与 oneshot 结果驱动。worker 独占数据库连接
和阻塞文件 I/O；Tokio worker 不直接执行 `rusqlite` 或 `std::fs`。队列满时业务命令等待，不丢弃；
Runtime 关闭时停止接收新命令，flush 已接受操作并观察 worker 退出。

### 3.3 Runtime 内存状态

`SessionController` 不再把内存视为最终权威，而是保存持久化状态的工作集：

```text
SessionController
├── immutable id / created_at / frozen System Prompt
├── mutable title / model_key / archive state
├── ConversationCache = Unloaded | Loaded(PersistentJournal) | Unavailable
├── Run projections and active execution handle
├── recovered queue summary
└── per-Session mutation gate
```

- 启动只加载 Session、Run 和排队输入的结构化投影，不遍历加载所有历史 Conversation。
- 第一次查询 Conversation、开始执行或历史重新输入时，按 Session 读取一次正文、完成规范校验并
  缓存在 controller；同一会话后续不反复查表、查文件重建上下文。
- 每 Session 使用一个异步 mutation gate 串行化需要跨 store await 的业务变更；持有该 gate 时
  不同时持有同步 state lock，也不调用 Provider 或工具。
- 不为历史 Session 创建永久 actor 或线程。提交输入时按需启动一个受 RuntimeTasks 所有的 queue
  driver；队列耗尽、暂停或阻塞后任务退出。

## 四、本地数据布局与格式

### 4.1 Runtime Home 布局

```text
~/.ez-assistant/
├── config.toml
├── run/
│   ├── runtime.sock
│   └── runtime.lock
└── data/
    ├── runtime.sqlite3
    └── sessions/
        └── <session-id>/
            ├── conversation.1.jsonl
            └── conversation.<generation>.jsonl
```

- `data/` 在 Host 初始化时创建；沿用 Runtime Home 当前用户私有的目录约定。
- Unix 下新建目录和文件分别按当前用户私有的 `0700`/`0600` 初始化；这是初始化约定，不把正文
  文件设计成只读，也不在每次读取时重复做配置文件级安全检查。
- Session ID 由 Runtime 生成并经过现有 ID 校验，可安全作为目录名；任何外部路径仍由 Host 从
  Runtime Home 和 ID 组合，客户端不能提交相对路径或绝对路径。
- `generation` 是文件原子替换的存储提交标识，不是 Message 顺序，也不进入应用协议。

正常追加继续写当前 generation。只有历史重新输入这类正文截断操作才写一个完整的新 generation，
SQLite 提交切换后旧 generation 失去权威性并尝试删除。这里的“销毁尾段”表示产品历史中不再可见、
不可恢复为分支，不承诺闪存级安全擦除；崩溃遗留文件的集中清理不属于本版本。

### 4.2 Conversation JSONL

每一行直接序列化一个现有 `ConversationMessage`：

```json
{"role":"user","turn":{"id":"m_...","parts":[{"type":"text","data":{"id":"p_...","text":"hello"}}]}}
{"role":"assistant","turn":{"id":"m_...","model":{"provider":"deepseek","model":"deepseek-chat"},"parts":[{"type":"tool_call","data":{"id":"call_...","name":"read_file","arguments":{"path":"README.md"}}}],"finish_reason":{"type":"tool_calls"},"usage":null}}
{"role":"tool","turn":{"id":"m_...","result":{"call_id":"call_...","status":"success","content":{"type":"text","value":"..."}}}}
```

规则：

- UTF-8；每条记录使用紧凑 JSON 并以单个 `\n` 结束；空 Conversation 是零字节文件。
- 行的物理顺序就是 Message 顺序。文件中不增加 `sequence`、Run ID、segment header 或 manifest。
- Message ID 只表达身份；Tool Result 继续通过 Tool Call ID 配对，不内嵌到 Tool Call。
- 一个 Assistant Message 的 reasoning、text、Tool Call 和 Provider State 保持现有 parts 顺序。
- reader 逐行反序列化，建立 Message ID 到物理位置的内存索引并拒绝重复 Message ID，随后对完整
  快照调用 `validate_tool_exchange_pairs`；无法反序列化或违反领域不变量时返回该 Session 的读取
  错误，不创建空 Conversation 覆盖原文件。
- 流式 token、工具 stdout/stderr 分片、RuntimeEvent 和 pending exchange 不进入正文。

### 4.3 SQLite schema

SQLite 只保存结构化关系、状态和短生命周期提交事实。首版表如下；精确 `CHECK` 文本可在实现时
按 Rust enum 的 wire 值生成，但不得改变本节关系：

```sql
CREATE TABLE sessions (
    session_id          TEXT PRIMARY KEY,
    title               TEXT NOT NULL,
    model_key           TEXT NOT NULL,
    system_prompt_json  TEXT NOT NULL,
    lifecycle           TEXT NOT NULL CHECK (lifecycle IN ('active', 'archived')),
    body_generation     INTEGER NOT NULL CHECK (body_generation > 0),
    message_count       INTEGER NOT NULL CHECK (message_count >= 0),
    created_at_ms       INTEGER NOT NULL,
    updated_at_ms       INTEGER NOT NULL,
    archived_at_ms      INTEGER
);

CREATE TABLE inputs (
    queue_order         INTEGER PRIMARY KEY AUTOINCREMENT,
    input_id            TEXT NOT NULL UNIQUE,
    session_id          TEXT NOT NULL REFERENCES sessions(session_id) ON DELETE CASCADE,
    idempotency_key     TEXT,
    user_message_id     TEXT NOT NULL UNIQUE,
    state               TEXT NOT NULL CHECK (state IN ('queued', 'committed')),
    queued_message_json TEXT,
    accepted_at_ms      INTEGER NOT NULL,
    UNIQUE (session_id, idempotency_key)
);

CREATE TABLE runs (
    run_id              TEXT PRIMARY KEY,
    session_id          TEXT NOT NULL REFERENCES sessions(session_id) ON DELETE CASCADE,
    input_id            TEXT NOT NULL REFERENCES inputs(input_id) ON DELETE CASCADE,
    attempt             INTEGER NOT NULL CHECK (attempt > 0),
    status              TEXT NOT NULL,
    cancel_requested    INTEGER NOT NULL CHECK (cancel_requested IN (0, 1)),
    error_code          TEXT,
    error_message       TEXT,
    created_at_ms       INTEGER NOT NULL,
    started_at_ms       INTEGER,
    finished_at_ms      INTEGER,
    UNIQUE (input_id, attempt)
);

CREATE TABLE run_message_refs (
    run_id              TEXT NOT NULL REFERENCES runs(run_id) ON DELETE CASCADE,
    message_id          TEXT NOT NULL,
    PRIMARY KEY (run_id, message_id)
);

CREATE TABLE pending_tool_exchanges (
    receipt_id          TEXT PRIMARY KEY,
    session_id          TEXT NOT NULL REFERENCES sessions(session_id) ON DELETE CASCADE,
    run_id              TEXT NOT NULL UNIQUE REFERENCES runs(run_id) ON DELETE CASCADE,
    assistant_json      TEXT NOT NULL,
    results_json        TEXT,
    state               TEXT NOT NULL CHECK (state IN ('begun', 'ready')),
    created_at_ms       INTEGER NOT NULL
);

CREATE TABLE body_appends (
    operation_id        TEXT PRIMARY KEY,
    session_id          TEXT NOT NULL UNIQUE REFERENCES sessions(session_id) ON DELETE CASCADE,
    run_id              TEXT NOT NULL REFERENCES runs(run_id) ON DELETE CASCADE,
    body_generation     INTEGER NOT NULL,
    base_byte_length    INTEGER NOT NULL CHECK (base_byte_length >= 0),
    kind                TEXT NOT NULL,
    payload             BLOB NOT NULL,
    message_count_delta INTEGER NOT NULL CHECK (message_count_delta > 0),
    created_at_ms       INTEGER NOT NULL
);
```

补充约束：

- `queue_order` 只定义尚未进入 Conversation 的输入接收顺序，不是 Message sequence，也不写入
  JSONL 或协议。
- `message_count` 是 Session 列表使用的派生投影，不是正文权威；普通正文提交时按新增消息数原子
  增加，generation 切换时用新正文的消息总数覆盖，不在正文加载时额外比较或触发修复流程。
- `run_message_refs` 只保存 Run 与 Message ID 的关联，不保存消息内容或顺序。Run 查询按正文
  物理顺序筛选这些 ID，因此不会出现 Message 表或 Part 表。
- `queued_message_json` 只在输入排队期间保存尚未进入正文的 User Message；提交到 JSONL 后置空，
  不长期复制 User Message。
- `pending_tool_exchanges` 是工具副作用边界使用的持久化临时区，`body_appends` 是跨 SQLite 与正文
  文件提交使用的持久化临时区；两者都不是正式 Conversation 或长期事件日志，完成对应正文提交
  后立即删除。
- 外键必须在连接建立后显式 `PRAGMA foreign_keys = ON`，不能依赖
  [SQLite 默认值](https://www.sqlite.org/foreignkeys.html#fk_enable)。

### 4.4 SQLite 运行参数

本版本只有一个 Host、一个 storage worker 和一个连接，不从 WAL 的并发读写获益，因此使用：

```text
journal_mode = DELETE
synchronous = FULL
foreign_keys = ON
busy_timeout = bounded bootstrap value
```

所有写入使用显式事务；跨 Session 也由 worker 顺序执行。`SQLITE_BUSY` 在短上限后作为存储错误
返回，不进行无界重试。v0.10.0 不执行 `VACUUM`、自动迁移、`integrity_check` 或备份操作。

## 五、提交、一致性与恢复

### 5.1 为什么需要 staged append

SQLite 事务只能原子覆盖 SQLite 文件，不能与独立 JSONL 组成一个文件系统事务。正常 append
必须满足：Runtime 报告成功后正文已经 fsync；崩溃留下半行或“文件已写、数据库未更新”时，下次
启动可以确定完成或回退，而不是猜测。

每次稳定 append 采用：

```text
1. 把整个消息批次编码为确定的 JSONL bytes
2. 在 SQLite 事务中插入 body_appends，记录当前 generation、原文件长度和完整 payload bytes
3. 从 base_byte_length 校验并写入正文，flush + sync_data
4. 在 SQLite 事务中应用结构化状态转换、增加 message_count、写 run_message_refs
5. 删除 body_appends 并提交
6. 更新 Session 内存投影，之后才发布成功/终态
```

同一 Session 同时最多一条 `body_appends`。恢复时比较当前文件：

- 长度等于 base：重新追加完整 bytes；
- base 后内容与完整 bytes 完全相同：文件已写完，直接完成第 4 步；
- base 后内容是完整 bytes 的前缀：截断回 base 后重新追加；
- 出现其他内容、generation 不符或文件短于 base：该 Session 标记 unavailable，不猜测覆盖。

这使物理文件在进程崩溃瞬间可能存在未完成尾行，但 Runtime 在完成恢复前不开放该 Session；任何
对外可见的 Conversation 始终通过完整配对校验。

### 5.2 输入接受与同 Session 排队

创建 Session 先在新的 Session 目录写入并同步空的 `conversation.1.jsonl`，再用 SQLite 事务插入
Session 行。文件创建失败时不产生 Session；SQLite 提交前崩溃最多留下无引用目录，不能出现已入库
但正文文件尚不存在的 Session。

`StartRun` 的现有含义会变成“提交后必定立刻执行”，不再适合排队。协议改为 `SubmitInput`：

1. 校验 Session 为 active、文本非空和 Runtime 正在运行。
2. 分配 Input ID、User Message/Part ID 和首次 Run ID。
3. SQLite 单事务插入 `inputs(state=queued, queued_message_json=...)` 与
   `runs(status=accepted, attempt=1)`。
4. 事务提交后才返回 accepted 投影并发布事实事件。
5. 正常同进程运行时唤醒该 Session 的 queue driver；重启恢复出的队列默认不唤醒。

相同 Session 和非空 `idempotency_key` 命中已有 input 时，直接返回该 input 的首次 Run，不创建
新记录。key 是请求身份，重复请求中的 message 不再参与第二次解释；调用方若要提交不同输入必须
使用新 key。历史重新输入销毁对应 input 后，该 key 不再占用。

driver 只领取最小 `queue_order` 的 queued input：

- 先按 Session 当前 model key 和最新有效配置编译 Run Agent；失败时把本次 Run 结算为 failed、
  保留该 queued input 并暂停后续队列，等待用户对该 Run 显式重试，避免跳过中间输入。driver 只
  领取“最早 queued input 的最新 attempt 为 accepted”的工作，不会反复领取已失败 attempt。
- 编译成功后 staged append User Message；最终事务将 input 置为 committed，并把 Run 转入实际
  启动态。
- supervisor 完成终态持久化后才领取下一条。
- 取消 queued input 会删除尚未提交正文的 input，并通过外键删除其 accepted Run；活动 Run 仍走
  `CancelRun`，两者不共用命令。

### 5.3 工具交换

`PersistentJournal` 保留现有两阶段 Recorder 语义：

```text
begin_tool_exchange
→ SQLite 写 pending_tool_exchanges(state=begun, assistant_json)
→ commit
→ 返回 receipt，Core 才能执行工具副作用

complete_tool_exchange
→ SQLite 补 results_json 并置 ready
→ staged append [AssistantMessage, ToolMessage...]
→ 完成正文与 run_message_refs
→ 删除 pending_tool_exchanges
→ 返回 Core
```

`pending_tool_exchanges` 只在一次工具交换尚未正式进入 Conversation 时存在。它虽然需要落盘以
跨越进程崩溃，但不进入 `ConversationSnapshot`，也不作为历史长期保留；只有正文、结构化关联与
派生计数全部提交成功后才能删除。一次 Assistant Message 包含多个 Tool Call 时，以完整批次为
单位暂存、提交和清理，不能让其中一部分结果先进入正文。

恢复规则：

- `ready` 表示完整结果已经在 SQLite 暂存；按原消息完成或确认 staged append。
- `begun` 表示工具可能尚未执行，也可能已经产生副作用但结果未可靠返回。Runtime 为每个 Tool
  Call 生成 `ToolResultStatus::Error` 的 Tool Message，内容固定表达“Runtime 重启，执行结果未知”，
  再把 Assistant Tool Call 与全部结果作为一个完整批次提交。
- 完整批次正式提交后删除对应 pending 记录，随后原 Run 结算为 `interrupted`。Runtime 不自动再次
  调用这些工具。

因此恢复后的正文不会出现孤立 Tool Call 或 Tool Result，也不会把未知副作用伪装成未发生。

### 5.4 Run 终态

- Completed：先 staged append 最终 Assistant Message，再在最终事务把 Run 标为 completed；文件
  提交失败时不能先返回 completed。
- Failed、Cancelled、CompactionRequired：在确认 Journal 没有 pending exchange 后用 SQLite
  事务直接结算；此前已经完整提交的工具交换保留。
- Runtime 启动恢复：`running`、`cancelling`，以及 User Message 已 committed 但仍为 `accepted`
  的 Run 统一变为新增终态 `interrupted`。
- 纯 queued 的 `accepted` Run 保持 accepted，但所在 Session 标记 `resume_required`，不会自动
  启动。客户端显式 `ResumeSession` 后才唤醒 driver。
- 用户对 interrupted Run 选择再次执行时创建同一 input 的下一 `attempt` Run，不改写旧 Run，
  也不重复追加 User Message；新的 AgentExecution 使用当前完整 Conversation 继续。queued input
  在 Agent 构造阶段失败时，同样通过下一 attempt 重试，但 User Message 仍要等真正开始执行时
  才进入正文。

Run 的 reasoning、text 和 tool 活动在运行中仍是内存实时投影，不持久化流式分片。重启后查询
终态 Run 时，Runtime 通过 `run_message_refs` 从已缓存正文恢复最终 Assistant 内容与工具完成状态；
无法从规范 Tool Result 推导的 stdout/stderr 保持为空，不伪造历史流。

### 5.5 历史 User Message 重新输入

该操作要求 Session active、完全空闲、无 pending exchange、无 queued input。提交顺序是：

1. 加载并校验当前 Conversation，按 Message ID 定位目标 User Message。
2. 保留目标之前的消息；收集目标及尾段涉及的 User Message ID、Input、Run 和 Message 引用。
3. 在破坏旧历史前校验新文本、模型配置并构造 Run Agent。
4. 分配新 Input/User Message/Run ID，生成“前缀 + 新 User Message”的完整新 generation 文件，
   flush、sync_data，并同步 Session 目录。
5. SQLite 单事务用当前 generation 作 CAS：切换 generation/message_count，删除目标及尾段 Inputs；
   由外键删除 Runs 和 refs；插入新 committed Input 与首次 Run。
6. 提交后替换内存缓存并启动新 Run；旧 generation 尝试删除。

新 generation 在 SQLite 切换前只是无引用文件；崩溃不会让半文件成为权威。SQLite 提交后若尚未
启动 Agent，重启会把该 Run 识别为 interrupted，而不会恢复被销毁尾段。

### 5.6 归档、恢复与模型切换

- Archive：mutation gate 内再次确认无活动 Run、pending exchange 和 queued input，再用 SQLite
  事务把 lifecycle 改为 archived；不修改正文。
- archived Session 仍允许列表过滤、详情、Conversation 和 Run 只读查询；所有改变会话的命令
  返回稳定 `SessionArchived` 错误。
- Restore：把 lifecycle 改回 active，正文、Run 和模型 key 不变；不会自动开始任何工作。
- SetSessionModel：只允许 active 且完全空闲的 Session；先用当前配置验证目标 model key，再
  更新 SQLite 和内存。System Prompt 与历史消息不变。

### 5.7 启动顺序

Host 在开始 accept 客户端连接前完成：

```text
取得 Runtime Home instance lock
→ 启动 LocalRuntimeStore worker，打开/初始化空库
→ 恢复全部 body_appends
→ 结算 pending_tool_exchanges
→ 将不确定活动 Run 置为 interrupted
→ 加载 Session / Run / queue 结构化投影
→ AssistantRuntime 建立 registry（Conversation 保持 lazy）
→ reload config
→ 开始监听客户端
```

单个 Session 的正文无法读取时，保留其摘要并标为 unavailable；只读或修改该 Session 返回脱敏
存储错误，其他 Session 继续可用。数据库自身无法打开或 schema 不满足本版本时 Host 启动失败，
不创建第二个空库覆盖原路径。

## 六、Runtime、Core 与 Host 改造

### 6.1 Assistant Runtime

建议按职责拆分：

```text
assistant-runtime/src/
├── runtime.rs                 # 生命周期与公共入口
├── runtime/
│   ├── input.rs               # Submit/Cancel/Resume/Retry
│   ├── session_lifecycle.rs   # archive/restore/model change/re-entry
│   ├── recovery.rs            # RecoveredRuntime 到 controller
│   ├── tasks.rs
│   └── ...
├── session.rs                 # Controller 与短内存状态
├── session/
│   └── queue.rs               # 按需 queue driver
├── journal.rs                 # PersistentJournal 领域不变量
├── run.rs
├── run/
│   ├── recorder.rs
│   ├── settlement.rs
│   └── supervisor.rs
└── storage/
    ├── mod.rs                 # RuntimeStore port
    └── model.rs               # store command/result DTO
```

创建 Session、提交输入、Conversation 查询、归档、恢复、重新输入和模型切换都涉及 I/O，公共入口
改为 async。Host dispatch 只做 await 和 DTO 路由，不承载第二份状态机。

### 6.2 Agent Core 任务结果

`AgentExecution::start` 创建 execution-owned observer 持有 engine `JoinHandle`。engine 正常结果、
受控取消与 task panic/JoinError 分开收敛：

- 新增不包含 panic payload 的 `ExecutionError::Internal` 稳定分类。
- observer await `JoinHandle` 并通过 completion oneshot 交付结果；JoinError 映射为
  `ExecutionOutcome::Failed(Internal)`，不得 panic。drop CompletionFuture 不取消 observer 或 engine。
- wrapper 保证异常退出时尽力发送对应终态事件；Runtime 仍以 completion 为唯一可靠结果。
- 测试故意让 engine 依赖 panic，验证 CompletionFuture 返回 Failed、Runtime Run 终态为 failed，
  且不泄漏 panic payload。

Runtime 现有 completion `catch_unwind` 可保留为跨 crate 最后防线，但不再承担 Core 正常契约。

### 6.3 Host 本地存储

`LocalRuntimeStore` 在 Host 中装配；新增 `rusqlite` 的 bundled SQLite feature，以避免正式桌面包
依赖目标机器预装兼容 SQLite。连接由一个命名阻塞线程从打开到关闭全程持有，worker panic、命令
channel 关闭和 shutdown 超时都映射为 Host/Runtime 可观察错误。

Host 当前 connection task 观察和 Runtime shutdown 上限已满足本版本目标，只补存储 worker 的
同级所有权、关闭顺序及回归测试，不重写 server 并发模型。

## 七、应用协议调整

项目仍处早期阶段，`PROTOCOL_VERSION` 保持 `1`，不建立所谓 V2 或并行兼容协议。Runtime Host
与客户端按同一版本同步更新。

### 7.1 标识、状态与投影

- 新增 `InputId` 和有长度限制的非空 `IdempotencyKey`。
- `RunStatus` 新增终态 `Interrupted`；`Accepted` 明确表示已持久化但尚未开始。
- `SessionSummary` 增加 `lifecycle: Active | Archived`、`queued_input_count` 和
  `resume_required`；`active_run_id` 继续只表示当前执行。
- `RunSnapshot` 增加 Input ID 与 attempt；终态错误继续使用脱敏 `RuntimeErrorInfo`。
- `RuntimeErrorCode` 增加 InputNotFound、SessionArchived、SessionNotIdle、RunNotRetryable 和
  StorageUnavailable 等调用方可采取不同行动的分类。

### 7.2 命令

新增或替换为：

```text
SubmitInput(session_id, message, idempotency_key?)
CancelQueuedInput(session_id, input_id)
ResumeSession(session_id)
RetryRun(session_id, run_id)
ListRuns(session_id)
ArchiveSession(session_id)
RestoreSession(session_id)
SetSessionModel(session_id, model_key)
ReenterFromUserMessage(session_id, message_id, message, idempotency_key?)
```

既有 GetSession、GetRun、CancelRun 保留。ListSessions 增加 active/archived/all 过滤，缺省只返回
active。旧 `StartRun` 由 `SubmitInput` 替代，避免“返回 Accepted 但实际排队”造成语义误导。

完整规范 Conversation 暂不提升为 `assistant-protocol` 公共 DTO：本版本没有正式桌面会话页面，
Runtime library 继续返回 `ConversationSnapshot`，Host 私有验证命令用于端到端验收。未来桌面消费
时单独设计应用层展示投影，不能直接把 Agent 内部类型变成长期 UI 协议。

RuntimeEvent 继续是可丢实时观察，不增加 sequence 或 cursor。持久化先成功、事件后发布；重连
通过 Session/Run 查询和 Conversation 验证入口重新获取权威状态。

## 八、测试与验证

### 8.1 存储单元与集成测试

所有测试使用 `tempfile` 隔离目录和测试数据库，不读取 `~/.ez-assistant`：

- 空库初始化、外键开启、约束与事务回滚。
- ConversationMessage JSONL round-trip、物理顺序、Provider State 和工具配对校验。
- staged append 在“仅建记录、部分写、完整写未 finalize、finalize 完成”四个中断点重开恢复。
- pending tool exchange 的 begun/ready 两种恢复，确认最终正文始终完整配对。
- User Message 提交、最终 Assistant 提交与 Run 状态不出现先成功后缺正文。
- 新 generation 写入前失败、SQLite 切换前失败和切换后重开，确认旧或新正文始终有且仅有一个
  权威版本。
- 单 Session 正文损坏不阻断其他 Session；不自动用空文件覆盖。
- 相同幂等 key 只产生一个 Input/首次 Run；queue_order 只影响未提交输入。

### 8.2 Runtime 行为测试

- 同 Session 多输入按接收顺序执行，不同 Session 保持并发。
- 正常同进程提交会自动唤醒；模拟重启后 queued input 保留且 `resume_required=true`，未调用
  ResumeSession 前不执行。
- running/cancelling/accepted+committed 重启后变为 interrupted，Provider 与工具调用计数不增加。
- RetryRun 对 interrupted Run 创建新 attempt 且不重复 User Message；对尚未提交 User Message
  的构造失败 Run 创建新 attempt，并继续占据原队列位置。
- queued input 取消与 active Run 取消严格分离。
- archive 前置条件、归档只读查询、归档拒绝变更和 restore 后继续使用。
- 历史重新输入删除目标及尾段的正文、Input、Run 和 refs，不产生隐式分支。
- model key 只在 active/idle/no-queue 时改变，System Prompt 不变。

### 8.3 Core、Host 与协议测试

- Core engine task panic/JoinError 转成 Failed(Internal)，CompletionFuture 不 panic。
- Runtime storage worker 与 supervisor 都有所有者、取消、等待和 panic 观察测试。
- Host 启动在开放 socket 前完成恢复；客户端断开不取消 Run。
- 新 ID、状态、命令、结果与错误做 Serde round-trip 和 JSON 快照。
- Runtime/Host 的错误和日志不包含 API Key、System Prompt、Conversation 正文、Provider 原始错误
  或 panic payload。

文档确认并形成开发计划后，各里程碑执行最小验证，版本完成前执行：

```bash
cargo fmt --all --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace
```

本版本涉及数据库实现，但开发与测试只创建隔离临时库；任何针对用户真实 Runtime Home 的迁移、
覆盖、恢复或批量修改都不在计划内。

## 九、风险、兼容与排除项

### 9.1 主要风险

- **跨文件原子性**：通过 staged append、base length 和启动恢复收敛；不能用“先写一个再尽快写
  另一个”替代。
- **正文增长导致加载和截断成本上升**：按 Session lazy load，普通消息 append；只有显式历史
  重新输入才重写完整正文。压缩策略由既有 Context 能力或后续版本处理。
- **派生 message_count 更新失败**：只允许在 staged append 的最终 SQLite 事务中同步增加，generation
  切换时按新正文覆盖；正文提交尚未完成时不得提前更新或向客户端报告成功。
- **工具副作用不确定**：begin 必须先入 SQLite；恢复生成未知结果并中断 Run，禁止自动重放。
- **单 worker 头阻塞**：首版以正确性和可恢复性优先；大正文重写是显式低频操作。真实性能数据
  证明不足后再评估读写分离，不能提前引入连接池和多写者。
- **协议扩大**：只加入当前 Runtime 能力必需的结构化意图；完整 Conversation 展示 DTO 留到真实
  桌面消费者出现时设计。

### 9.2 兼容性

- `v0.9.0` 没有正式持久化 Session 数据，首次启动创建空数据集，不迁移 demo/harness 私有文件。
- 现有 `config.toml` 及其兼容层不受本方案影响；数据库不保存 API Key 或完整模型配置。
- 当前应用协议随 Host 和客户端同步演进，保持 `PROTOCOL_VERSION = 1`，不维护并行协议代际。
- 持久化 DTO 与领域类型显式转换；不能因为现有领域类型支持 Serde 就把任意内部状态直接落盘。

### 9.3 明确排除

- schema migration 框架、备份恢复、便携导入导出、`integrity_check`、修复工具和孤立文件清理。
- WAL、多连接池、多 Runtime Host 共享同一 Runtime Home。
- Message/Part 关系表、Message sequence、segment/manifest 和存储专用 ToolExchange。
- 持久事件游标、RuntimeEvent 重放、token/tool output 分片持久化。
- 正式桌面会话管理页面及其 Conversation 展示 DTO。

### 9.4 版本验收入口

- 人工验收复用 `apps/runtime-host` 现有私有 Ratatui Demo。它只通过 Host 私有协议发送意图和读取
  快照，不持有 Session、Run、队列或持久化的第二份权威状态。
- 不新建独立 Demo、验证 Runtime 或新的数据格式。自动化验收场景同样只作为私有协议客户端驱动
  正式 Runtime Host，不复制 Runtime 业务实现。
- 离线场景启动临时 loopback OpenAI-compatible fake Provider，并在隔离 Runtime Home 中生成仅供
  本次验收使用的配置；正式 Host 仍走实际配置、Provider Adapter、Store 和进程启动路径，不增加
  产品 fake 模式，也不连接真实 Provider。
- 重启验证必须启动两次真实 Host 进程并复用同一个隔离 Runtime Home；只在同一进程内重建
  `AssistantRuntime` 不能作为进程重启证据。场景结束后由临时目录生命周期统一回收数据。
- Ratatui Demo 用于人工观察和交互，自动化场景用于可重复断言；二者共享同一 Host 契约，但互不
  将私有 wire 或完整 Conversation 查询提升为公共应用协议。

## 十、重点 Review 项

1. SQLite 保存 `message_count` 作为列表派生投影，但正文及其物理顺序仍只以 JSONL 为权威；是否
   接受这一个受控冗余值。
2. 幂等 key 只表示请求身份：重复 key 直接返回首次结果，不长期复制 User Message 用于比较重试
   payload；不同输入必须使用新 key。
3. pending tool exchange 是工具交换进入规范 Conversation 前的持久化临时状态：正常提交后立即
   清空；重启恢复时补齐 outcome unknown 的 Tool Result、整批提交正文后再清空，既不留下孤立
   调用，也不谎称工具未执行。
4. 普通正文使用 staged append，历史重新输入使用 generation 切换；generation 与 queue_order 都
   是存储提交/排队标识，不是 Message sequence。
5. 完整 Conversation 继续是 Runtime library 与 Host 私有验证能力，不在没有正式桌面消费者时
   提前固化新的公共展示 DTO。
