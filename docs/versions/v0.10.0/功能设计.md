# v0.10.0 功能设计：可靠会话与持久化执行

## 一、设计信息

- 版本：`v0.10.0`
- 状态：已确认（2026-08-07）
- 影响模块：`assistant-runtime`、`assistant-protocol`、`apps/runtime-host`、`agent-core`
- 需求来源：Runtime 阶段路线、既有持久化遗留、运行可靠性审查，以及 2026-08-07 的存储讨论

本版本涉及持久化、恢复和跨模块执行契约，需要在功能设计确认后单独形成技术方案。
本版本不建设正式桌面页面，不单独形成界面交互设计指导。

## 二、背景与目标

`v0.8.0` 和 `v0.9.0` 已建立正式 Runtime、Session/Run 执行、应用协议、Runtime Home 和模型
配置，但 Session、Conversation、Run 与 Journal 仍只存在于内存中。Runtime 一旦退出，用户
会话和运行事实全部丢失；客户端重试也缺少稳定的幂等与排队语义。

`v0.10.0` 的目标是形成第一个可靠的本地会话与持久化执行闭环：

1. Session、规范 Conversation、Run 和已接收用户输入可以跨 Runtime 重启保存和恢复。
2. 用户输入先成为持久化事实，再进入同 Session 串行执行；客户端重试不会重复追加或执行。
3. Runtime 能区分尚未开始、正在执行、已完成、失败、取消和被重启中断的工作，不把不确定
   状态伪装成成功。
4. Conversation 正文适合顺序加载、上下文组装、压缩和裁剪，不因关系化存储被拆成大量查询。
5. Tool Call、Tool Result、最终 Assistant Message 与 Run 终态保持既有规范语义和恢复完整性。
6. 用户可以从历史 User Message 重新输入并继续当前会话；被替换位置及其后续内容不保留隐式
   修改历史。
7. Session 可以归档、只读查看并恢复，归档不会隐式删除会话数据。
8. Runtime、Core 和 Host 显式观察执行任务的正常完成、取消和异常退出，避免任务 panic 或失联
   被吞掉。

## 三、非目标

以下内容不进入 `v0.10.0`：

- 正式桌面会话页面、历史记录管理界面、恢复提示和数据管理界面。
- 任意历史消息编辑；只有从历史 User Message 重新输入的明确操作。
- 隐式对话分支、自动保留旧回答和通用 undo。未来分支只通过用户显式 Fork 创建独立会话。
- Fork 的正文复制、共享前缀或文件快照实现。
- Workspace、附件、Artifact 和二进制内容管理；这些进入 `v0.11.0`。
- Plan/Build、Ask/Auto、正式文件与 Shell 权限、审批和审计；这些进入 `v0.12.0`。
- 历史会话语义检索、记忆提取、云同步、多用户共享或跨设备合并。
- 新的上下文压缩、Tool Result 裁剪或摘要算法；本版本只保证既有规范消息和摘要可以可靠保存。
- 把模型流式 token、普通 UI 增量或完整 Provider Trace 当作 Conversation 恢复来源。
- Runtime 崩溃后自动重试已经开始的模型调用或工具副作用。
- 多个 Runtime Host 同时写入同一个 Runtime Home。
- 备份恢复、便携 Session 导入导出、数据迁移、完整性检查、损坏修复、孤立数据清理等扩展型
  数据管理能力。
- 持久事件游标、断线事件补取和流式事件重放；客户端重连以重新获取权威快照为准。

## 四、功能范围与使用路径

### 4.1 本地数据与权威边界

Runtime Home 继续作为当前用户的本地数据根目录。结构化索引和会话正文采用不同的存储形态：

- SQLite 保存 Session、Run、持久化输入、归档状态和其他需要结构化查询或跨实体关联的数据。
- 每个 Session 使用独立的顺序正文文件保存规范 Conversation。
- Conversation 中消息的先后由正文中的物理顺序表达，不在 SQLite 中重复维护消息顺序。
- SQLite 不重复保存完整会话正文；正文文件也不复制 Session 和 Run 的结构化状态。
- 两类存储共同组成一份 Runtime 数据集，Runtime 负责一致写入和启动恢复。

正文文件直接保存现有 Provider-neutral Conversation 结构。Tool Call 和 Tool Result 继续作为
不同规范消息，通过既有调用 ID 配对；本版本不为持久化增加 `ToolExchange`、可变 Tool Call
或其他第二套消息模型。文件名、目录层级、SQLite 表结构、JSON 字段和写入算法由技术方案定义。

### 4.2 Session 生命周期

Runtime 创建 Session 后立即持久化其稳定身份、创建时间、模型 key、冻结的 System Prompt 和
Conversation。Runtime 重启后可以列出、查询并继续既有 Session，不要求客户端保存第二份状态。

Session 支持归档和恢复归档。归档只改变会话的可用状态，不删除正文或运行历史；归档 Session
仍可只读查询其元数据、Conversation 和 Run 历史，但不能提交新输入、开始或恢复 Run、从历史
User Message 重新输入，或者切换模型。恢复归档后重新允许这些操作。

只有处于空闲状态，且没有活动 Run、待结算工具交换或排队输入的 Session 才能归档；不通过归档
操作隐式取消运行、丢弃输入或等待任务结束。永久删除与物理回收策略不在本版本提供普通产品入口。

Session 空闲且没有待执行输入时，可以显式切换 model key。切换只影响之后创建的 Run，不重建
冻结的 System Prompt，也不改变历史消息记录的模型身份。活动或仍有排队输入时拒绝切换。

### 4.3 输入准入、幂等与同会话排队

客户端提交用户输入时，Runtime 先可靠记录“已接收”事实，再唤醒对应 Session。提交方可以提供
不透明幂等标识；相同 Session 下重复提交同一标识，只返回已有结果，不重复创建 User Message、
Run 或工具副作用。

同一 Session 的多个已接收输入按照接收顺序串行处理，不再以 `SessionBusy` 拒绝后续输入；不同
Session 仍可并发。Runtime 重启后保留尚未开始的排队输入，但不自动执行；Session 恢复为空闲
且待用户显式继续。已经开始但没有可靠终态的 Run 恢复为中断状态，不自动重新调用模型或工具；
用户决定再次执行时创建新的 Run，不续用被中断的 Run。

取消排队输入与取消活动 Run 是不同意图：前者不产生模型执行，后者等待当前执行按既有取消契约
完成结算。精确状态机和并发控制由技术方案定义。

### 4.4 Conversation 与工具交换

规范 Conversation 是模型上下文和会话恢复的正文事实源，流式事件不是正文。运行过程遵守：

- User Message 在对应工作执行前可靠进入 Conversation。
- 未完成的模型流式增量不进入 Conversation。
- 完整 Tool Call 在工具副作用前形成可恢复的 pending 事实，但 pending 不暴露给规范快照。
- 完整 Tool Result 批次结算后，Assistant Tool Call 与对应 Tool Result 才作为完整配对进入
  Conversation。
- 已完整结算的工具交换在 Run 后续失败或取消时仍保留；未配对 Tool Call、孤立 Tool Result
  和部分结果不得出现在可恢复快照中。
- 没有工具调用的最终 Assistant Message 与 Run 成功终态保持一致，不能一边成功、一边永久
  缺失正文。

普通文本、reasoning、Provider State、Tool Call、Tool Result 和 Context Summary 均按现有规范
类型保存。流式 token、工具输出分片和 UI 进度只用于实时观察；是否保留独立诊断记录不改变
Conversation 权威性。

### 4.5 从历史 User Message 重新输入

本版本只允许选择历史 User Message 作为重新输入点，不提供任意消息编辑。重新输入时：

- 保留目标 User Message 之前的 Conversation；
- 销毁原目标 User Message 及其之后的当前会话内容；
- 新输入创建新的 User Message 和 Run；
- 即使文本没有变化，也视为新的用户输入；
- 不保留修改历史，不自动创建分支，不复用被销毁消息的 ID；
- 如果未来需要同时保留两个方向，用户必须显式 Fork 后再继续。

被销毁尾段关联的排队输入、活动 Run、已完成 Run、事件和缓存必须形成一致结果，不能让已从
Conversation 移除的执行在稍后重新提交消息。具体清理和物理回收方式由技术方案定义。

### 4.6 重启恢复与异常收敛

Runtime 启动时读取持久化数据，并恢复 Session、排队输入和 Run 状态：

- 已完成的 Conversation 和 Run 保持原结果；
- 尚未开始的持久化输入继续保留，但等待用户显式继续后才恢复执行；
- 崩溃时正在执行的 Run 标记为中断，不自动重复执行；
- 遗留 pending tool exchange 必须结算为明确的中断或未知结果，不能暴露未配对快照；
- 无法读取的 Session 返回明确错误，不以静默丢消息或创建空会话覆盖原数据；
- 单个 Session 损坏时尽量隔离影响，不让无关 Session 一起失效。

Runtime 和 Core 必须显式观察执行任务的退出。内部 panic、JoinError、连接 writer/event task
异常和受控取消使用不同结果收敛；应用层 Completion 不因内部 task panic 再次 panic，Host 不
静默吞掉意外子任务异常。

### 4.7 快照与客户端重连

Session、Conversation 和 Run 快照是客户端恢复展示的权威来源。客户端断线重连后重新获取
快照，不依赖历史事件重放还原业务状态。

模型 token、工具输出分片和普通 UI 增量只服务实时观察，断线期间允许丢失。本版本不定义持久
事件游标、事件保留范围或流式事件重放。

### 4.8 数据能力边界

本版本只完成 Session、Conversation、Run 和输入队列的核心持久化闭环，以及 Session 归档与
恢复。备份恢复、便携导入导出、格式迁移、完整性检查、损坏修复、孤立数据清理和持久事件日志
均留待后续版本按实际产品需求单独设计，不在本版本提前冻结能力或验收口径。

## 五、模块边界与契约影响

- `assistant-runtime`：成为 Session、Conversation、持久化输入、Run、恢复和归档
  的唯一业务权威；持有同 Session 串行协调与持久化 Journal。
- `apps/runtime-host`：负责 Runtime Home、具体存储基础设施和进程/连接任务观察；不保存第二份
  Session 或 Run 业务状态。
- `assistant-protocol`：增加输入幂等、排队状态、恢复结果、归档、重新输入和模型切换所需的稳定
  意图与投影；不暴露数据库、文件路径或内部 Journal 类型。
- `agent-core`：继续只负责单次 AgentExecution，不知道 Session、Run、队列或存储；本版本只收紧
  内部任务退出的观察契约，不把 Runtime 恢复状态机下推给 Core。
- Agent Context 和 Provider Adapter：继续消费经过校验的 `ConversationSnapshot`；不读取 SQLite、
  会话正文文件或 pending 恢复记录。

具体 Repository、存储组件、协议 DTO、错误类型、任务句柄和持久化一致性实现统一由技术方案定义。

## 六、关键取舍

### 6.1 结构化索引与会话正文分层

会话正文主要按顺序恢复和组装上下文，不为关系化查询拆成 Message/Part 表；SQLite 聚焦结构化
关系、运行状态和跨会话查询。两者由 Runtime 统一维护，不能成为互相覆盖的双重权威。

### 6.2 落盘结构复用规范 Conversation

正文直接保存现有 Conversation Message 结构，不为存储合并 Tool Call/Result，也不采用
Provider 原生消息作为产品格式。这样领域类型、内存快照和正文格式保持一致，Provider 差异继续
由 Adapter 处理。

### 6.3 ID 表达身份，文件位置表达顺序

Message ID 负责身份、引用和幂等；正文中的物理位置负责消息顺序。不再保存与该顺序重复的
Message sequence 或数据库排序字段。必要的文件定位与恢复信息属于存储实现，不提升为领域字段。

### 6.4 重新输入是破坏性替换，不是隐式分支

普通操作不保存旧回答树。只有未来显式 Fork 才建立独立会话；当前重新输入直接销毁目标位置及
尾段，避免在首个持久化版本中引入不可见分支和复杂历史选择。

### 6.5 已开始的副作用不自动重试

重启恢复优先保证事实可信，而不是追求自动继续。尚未开始的输入保留但暂停，等待用户显式继续；
已开始且结果不确定的 Run 显式中断，由用户决定是否创建新的 Run 再次执行。

### 6.6 重连只依赖权威快照

Conversation 和 Run 快照承担恢复。高频流式增量不进入长期恢复承诺，也不通过持久事件日志
形成第二份正文。

## 七、验收标准

1. Runtime 重启后可以列出并查询此前创建的 Session、Conversation 和 Run，模型所需的规范消息
   内容、顺序、reasoning、Provider State 和 Tool Call/Result 配对保持不变。
2. SQLite 只保存结构化关系与状态，会话正文从对应 Session 文件顺序恢复；不存在两份可独立
   修改的完整 Conversation。
3. 重复提交同一幂等输入不会重复创建 User Message、Run 或工具副作用；不同输入按同 Session
   接收顺序串行执行，不同 Session 仍可并发。
4. Runtime 退出后，未开始的持久化输入仍然存在但不会自动执行；活动 Run 恢复为明确中断且不
   自动重复调用 Provider 或工具。用户显式继续后才能处理队列，重新执行中断工作会创建新 Run。
5. 任意恢复快照都不存在孤立 Tool Result、未配对 Tool Call 或部分 Tool Result 批次；完整结算
   的工具交换在后续失败、取消和重启后仍可恢复。
6. Run 成功与最终 Assistant Message 保持一致；持久化失败不能先向客户端报告成功。
7. 从历史 User Message 重新输入后，只保留其之前的内容并创建新输入；原消息和尾段不再出现在
   当前 Conversation，也不会被旧 Run 稍后重新提交。
8. 本版本不存在任意消息编辑、隐式分支、旧回答选择或通用 undo；未来 Fork 不受当前正文格式
   强制绑定。
9. 只有空闲且没有活动 Run、待结算工具交换或排队输入的 Session 可以归档；归档后不出现在默认
   活动列表，仍可只读查询元数据、Conversation 和 Run 历史，但不能执行会改变状态的会话操作；
   恢复归档后正文和 Run 历史不变，并可再次开始工作。
10. Session 只有在空闲且无排队输入时才能切换 model key；历史消息和冻结 System Prompt 不被
    改写，下一 Run 使用新 key 的当前有效配置。
11. 客户端断线后可以通过 Session、Conversation 和 Run 快照恢复当前状态；不依赖流式 token、
    工具输出分片或历史事件重放恢复 Conversation。
12. 正文文件缺失、内容无法读取或单 Session 恢复失败时返回明确且脱敏的错误，不静默创建空
    会话覆盖原数据。
13. Core task panic/JoinError、Runtime 取消和 Host 连接子任务异常均被显式观察并转换成稳定结果，
    不让 CompletionFuture 再次 panic，也不让 Host 无限等待或静默吞掉异常。
14. 自动化测试覆盖正常运行、并发输入、幂等重试、取消、重新输入、归档与恢复、进程中断点恢复
    和基础读取失败；测试只使用隔离目录，不读写用户真实 Runtime Home。

## 八、风险与兼容性

### 8.1 风险与缓解

- **SQLite 与正文文件不一致**：Runtime 统一管理两者的提交和恢复；遇到无法确认的一致性状态时
  停止修改受影响 Session 并返回明确错误。
- **正文重写失败**：重新输入等破坏性操作必须保证失败前后至少有一份完整可恢复正文，不允许
  原文件与新文件同时处于半完成状态。
- **工具副作用状态不确定**：副作用前保留 pending 事实；崩溃后显式结算中断或未知，禁止自动
  重放。
- **数据格式过早固化**：功能设计只冻结本版本业务语义，不冻结表和字段；格式演进和迁移能力在
  后续存在实际兼容对象时再单独设计。

### 8.2 兼容性

- `v0.9.0` 及以前没有正式持久化 Session 数据，因此首次启用不需要迁移历史会话；现有配置文件
  继续由其配置兼容层负责。
- 当前项目仍处早期阶段，应用协议在现有契约上演进，不建立并行协议代际；字段和状态变更必须
  同步 Runtime、Host 和所有客户端。
- 现有 `ConversationMessage`、两阶段 Recorder 和 Provider Codec 是正文格式的语义基础；技术
  方案必须核对其序列化方式与 Message ID 唯一性。
- `runtime-harness`、`memory-demo`、`reliability-demo` 和 `core-demo` 的 JSON/JSONL Store 仍是私有
  验证实现，不能直接复制成产品格式。

### 8.3 已确认范围

本轮已经确认存储分层、消息顺序、Tool Call/Result 形态、重新输入、重启恢复和归档语义。备份、
导入导出、迁移、完整性治理和事件重放等扩展能力暂不进入本版本。SQLite 表、正文编码、文件
一致性算法和协议字段进入技术方案，不在功能设计中展开。
