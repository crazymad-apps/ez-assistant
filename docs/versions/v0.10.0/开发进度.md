### M0：可恢复的本地存储底座

- 目标：建立隔离可测的 SQLite、Conversation JSONL 和跨文件恢复底座。
- 影响模块：`assistant-runtime`、`apps/runtime-host`
- 状态：✅ 已完成
- 实际结果：
  - 新增 RuntimeStore 最小业务端口、恢复/Session DTO、稳定存储错误分类和显式 shutdown 契约；
  - Host 新增单一命名阻塞 worker、有界命令队列、bundled SQLite schema 和私有 Runtime Home
    数据布局；`rusqlite 0.40.1` 关闭默认 feature，只启用 `bundled`；
  - Conversation JSONL 直接往返规范消息，覆盖 reasoning、Provider State、Tool Call/Result、重复
    Message ID、完整行和配对校验；
  - staged append 覆盖仅落 staged、部分文件、完整文件未 finalize 和已 finalize 四个中断点；
    generation 切换覆盖 SQLite 提交前旧正文权威、提交后新正文权威及旧正文清理；
  - 冲突尾段只把目标 Session 标记 unavailable，其他 Session 仍可读取；
  - 临时数据库精确核验 6 张业务表，成功恢复后 `body_appends = 0`、对应

### M1：Runtime 持久化启动与会话恢复

- 目标：让 Session、Conversation 和 Run 由 Runtime 持久化并跨重启恢复。
- 影响模块：`assistant-runtime`、`assistant-protocol`、`apps/runtime-host`
- 状态：✅ 已完成
- 实际结果：
  - `AssistantRuntime::open` 在进入 Running 前加载 `RecoveredRuntime`，以恢复的 Session/Run 建立
    唯一 registry；正式 Host 不再使用易失构造路径；
  - Session 创建、User Message 与 Run 起始、Run 终态均先通过 RuntimeStore 可靠提交，再更新内存
    投影和发布事实事件；Store 失败后目标 Session fail-closed，不以内存空状态继续修改；
  - Conversation 采用每 Session 首次查询/执行 lazy load；损坏正文只隔离目标 Session，重复查询
    保持 `StorageUnavailable`，不会覆盖成空正文；
  - Store 恢复 Session、Run、Run-Message 引用和派生 `message_count`；终态 Run 可从规范正文恢复最终
    reasoning/text，accepted/running/cancelling 在启动时统一转为 `Interrupted` 且不调用 Provider；
  - `CreateSession`、Run 查询/取消与完整 Conversation 查询完成 async 化；全局 operation gate 和
    每 Session mutation gate 固化 Store await 边界及 shutdown 竞态；M1 当时的提交入口已由 M2
    统一替换为 `SubmitInput`；
  - Host 在 accept loop 前打开 Store、完成 Runtime 恢复和配置加载；Runtime 关闭顺序为停止新业务、
    结算 Run、flush/join Store worker，bootstrap 失败也显式关闭 worker；
  - 协议增加 `InputId`、`RunStatus::Interrupted` 和 `StorageUnavailable` 稳定分类，协议版本仍为 1；
  - 新增真实 LocalRuntimeStore 跨重启回归，覆盖 Session、2 条规范消息、completed Run、引用和终态
    文本恢复；另覆盖 staged Run 起始/终态恢复、非终态 Run 中断收敛与损坏正文不被空状态替换。
- 验证：

    Host 54/54、Doc-tests 0；
  - `cargo test -p assistant-protocol`：通过，19/19、Doc-tests 0；
  - `cargo clippy -p assistant-runtime -p assistant-runtime-host -p assistant-protocol --all-targets
    --all-features -- -D warnings`：通过；
  - `cargo fmt --all --check`：通过；
  - `git diff --check`：通过。
- 当前步骤：已完成。

### M2：可靠输入、幂等排队与串行执行

- 目标：形成输入先落账、同 Session 串行、重启后显式恢复的执行路径。
- 影响模块：`assistant-runtime`、`assistant-protocol`、`apps/runtime-host`
- 状态：✅ 已完成
- 实际结果：
  - 公共协议以 `SubmitInput`、`CancelQueuedInput`、`ResumeSession` 和 `RetryRun` 统一替换旧
    `StartRun`，新增有界 opaque `IdempotencyKey`、Run 的 `input_id`/`attempt` 以及 Session 的
    `queued_input_count`/`resume_required` 投影，协议版本保持 1；
  - RuntimeStore 与 LocalRuntimeStore 原子持久化 Input 和首次 `Accepted` Run；幂等只按同一
    Session 的 key 命中首次 Input/Run，不比较重复请求正文，queue order 只在 SQLite 保存；
  - 每个 Session 由一个 Runtime-owned 队列执行器按持久接收顺序领取；领取前提交 User Message 与
    Run 起始，终态结算后才领取下一项，不同 Session 仍可并发且避免 missed wakeup/双 start；
  - 排队取消只删除尚未进入 Conversation 的 Input；失败或中断 Run 重试创建递增 attempt 并复用
    原 Input，已经提交的 User Message 不重复写入；
  - 重启后纯 queued Input 保持 `Accepted` 并置 `resume_required`，显式 `ResumeSession` 前不执行；
    `RetryRun` 只放行目标 interrupted Input，不会顺带启动其后的恢复队列；
  - Demo 只在 `RunStarted` 后设置活动 Run，不再把排队中的 `Accepted` 错投影为活动状态；Runtime
    输入命令/队列执行器及 Host Input/Run 存储状态已按职责拆分；
  - 所有新增存储回归均使用 `tempfile` 隔离 Runtime Home，没有读取或修改真实
    `~/.ez-assistant`，也没有调用真实 Provider。
- 验证：
  - `cargo test -p assistant-runtime -p assistant-protocol -p assistant-runtime-host --all-features`：
    通过，Protocol 20/20、Runtime 47/47、Host 56/56、Doc-tests 0；
  - `cargo clippy -p assistant-runtime -p assistant-protocol -p assistant-runtime-host --all-targets
    --all-features -- -D warnings`：通过；
  - `cargo fmt --all --check`：通过。
- 当前步骤：已完成并获得用户确认。
- 续作点：M3 实现 pending tool exchange 与异常任务收敛。
- 里程碑确认：2026-08-07 用户确认通过
- 遗留/风险：M2 只持久化完整规范消息，不按流式 chunk 落正文；工具副作用前的
  `pending_tool_exchanges`、Core task panic/JoinError 和 Host 异常任务完整收敛仍按计划归 M3。

### M3：工具交换与异常任务收敛

- 目标：持久化临时工具交换并显式观察 Core、Runtime 和 Host 异步任务终态。
- 影响模块：`agent-core`、`assistant-runtime`、`assistant-protocol`、`apps/runtime-host`
- 状态：✅ 已完成
- 实际结果：
  - RuntimeStore 增加 begun/complete 两个业务原子操作；RuntimeRecorder 在工具副作用前先持久化
    完整 Assistant Tool Call 批次，结果齐备后才把整批 Tool Result 交给 Store；Store await 全程
    受 Session mutation gate 保护，失败后 Session fail-closed；
  - Host 新增独立 `storage/tool_exchange.rs`，begun 与 ready 均只存在于短生命周期临时表；complete
    先可靠保存 results，再通过既有 staged append 一次提交 Assistant + 全部 Tool Message、refs 与
    message_count，并在同一 SQLite 最终事务清除 pending；
  - 启动先恢复 body_appends，再处理剩余 pending：ready 使用原结果，begun 为每个 Tool Call 补充
    outcome unknown 错误结果；完整批次进入正文后原 Run 转为 interrupted，从不调用 Provider 或工具；
  - Agent Core 增加 `ExecutionError::Internal`，execution-owned observer 显式 await engine JoinHandle；
    engine panic/JoinError 同时收敛为 Failed(Internal) completion 与脱敏失败终态，drop completion 仍不
    取消执行或异常观察；
  - RuntimeTasks 捕获队列/supervisor task panic 并执行领域收敛；强制关闭遇到持久 pending 时保留
    恢复事实而非伪造 Failed。Host storage worker panic/channel 关闭/join 失败可观察，既有 connection
    子任务 JoinError 回归继续通过；
  - Review 后补齐 Runtime task panic 的 fail-closed 边界：当前 Run 结算后冻结目标 Session，不在旧
    Core 执行退出尚未重新观察时唤醒剩余队列；故障 Session 的新提交、取消队列、恢复和重试均被拒绝；
  - 关闭编排下沉到独立模块，supervisor 等待、强制结算和 Store shutdown 均有等待上限；强制结算
    失败仍尝试关闭 Store，Host worker 只在 Shutdown 命令成功入队后关闭准入；
  - 新增 begun/ready 重启修复、正常整批提交清理、storage worker panic、Core engine panic、Runtime
    task panic 与脱敏 Runtime 终态测试；测试均使用 `tempfile`，未访问真实 Runtime Home 或 Provider。
- 验证：

## 本地决策与提醒

- `v0.10.0` 以可靠会话与持久化执行为主题，范围已由本归档中的功能设计确认并完成验收。
- 已确认结构化关系使用 SQLite、每 Session 使用独立顺序正文文件；Message 顺序由正文物理
  顺序表达，Tool Call/Result 继续使用现有规范结构，不为落盘增加第二套消息模型。
- 只考虑从历史 User Message 重新输入并销毁尾段，不提供任意消息编辑、隐式分支或通用 undo。
- Runtime 重启后保留排队输入但不自动执行，活动 Run 标记为中断；用户显式继续后才恢复工作。
- `pending_tool_exchanges` 是持久化临时状态，只保存完整 Tool Call 与结果；正常正文提交或重启
  一致性修复完成后立即清空，不持久化 reasoning、text 或工具输出流式分片。
- v0.10.0 M5 复用 Runtime Host 现有私有 Ratatui Demo 作为人工验收客户端，不新增独立 Demo；
