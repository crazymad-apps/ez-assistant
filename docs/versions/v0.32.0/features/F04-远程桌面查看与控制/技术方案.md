### 2.1 已完成的最小验证

本机隔离原型采用两个独立 Rust 进程代表目标和本机 Host，媒体及输入跨两段 WebRTC，未接入正式 Host／企业授权。已验证能力如下：

| 能力 | 已有结论与范围 |
| --- | --- |
| 编码视频转交 | 合成 H.264 通过原生进程传输并转交 Chromium／原生 WKWebView 解码，无本机二次编码 |
| 实际键鼠与文本 | Chromium 经双段 WebRTC 到 CoreGraphics，原生窗口确认点击、右键／双击／拖动／滚轮、英文键、方向／删除、Command／Shift 组合键、中文／emoji 文本提交生效 |
| 输入停止 | 实验只读门禁、失焦／停止松键、转发进程中断后的短心跳看门狗释放通过；不代表 F01 企业撤销已接通 |
| 实时画面反馈 | ScreenCaptureKit → VideoToolbox 硬件 H.264 → 双段 WebRTC → Chromium；实际点击和文字在解码画面得到核对 |
| 整屏与双屏切换 | 两块实际显示器的整屏采集、选择器往返切换、不同原点／尺寸／比例下坐标命中、留白无输入、切屏松键、旧绑定拒绝和新屏只读通过；测试窗口覆盖显示器，未保存其他应用画面 |

**结论：原生双段 WebRTC、H.264 转交与 macOS 本机整屏操控具有局部可行性，不要求本机再次编码。** 原型已停止，未操作用户文件或数据库。真实采集与输入闭环使用 Chromium；WKWebView 只验证合成视频及消息链路。负坐标、混合 DPI、旋转／热插拔、多查看者、正式授权、跨机器／NAT、弱网及持续负载仍在第九节待办中。本机少量点击到解码帧测量不替代正式性能分位数或跨机器延迟。

采用 `webrtc`／`rtc` 0.21.1 做这次探针，已检查其 Tokio、编码样本发送和 RTP 转发 API，并在当前 macOS nightly 工具链构建运行。其 MIT／Apache-2.0 许可见上游；声明版本不能代替完整依赖、MSRV、目标平台和分发核查。设计期未验证 Rust 1.89。M0 实编已确认该声明不成立：WebRTC 依赖使用较新的标准库接口，Host 原有 SQLite 依赖也不能通过 1.89。用户明确允许调整构建工具链；正式 Host 声明改为 Rust 1.98，以稳定版验证，软件版本 0.32.0 与应用／存储兼容下限不变。`webrtc`／`rtc` 固定为 0.21.1，关闭默认 feature，启用 Tokio／aws-lc；Host 保留显式 TLS provider 初始化，允许工作区中其他依赖合并 ring。传递依赖许可证声明已核对，包含 MIT／Apache、BSD／ISC、Unicode 等，发布时继续带所需声明；M0 不包含最终安装包体积与公证验收。

### 2.2 候选比较

| 路线 | 判断 |
| --- | --- |
| `webrtc-rs` + 平台采集编码 | 当前优先；与 Tokio 装配直接，实验验证了编码样本和 RTP 转交；库不替代编码器，也不能自动解决两段拥塞反馈 |
| `str0m` + 平台采集编码 | 保留为选型失败时的评估项；Sans-I/O 可由 Host 控制 I/O 和生命周期，本轮未编译／运行，不预建第二栈 |
| libwebrtc 原生封装 | 能力完整但增加原生构建、绑定与随包成本；本轮不引入 |
| 原 Demo RFB／noVNC | 可复用平台经验，但原始像素方案不直接满足目标；不作为静默降级或长期双栈 |

删除新增机制后的判断：现有授权、控制连接、右栏足够承载身份与入口；现有 HTTP／WS 字节代理缺少视频分包、拥塞、反馈和原生编码能力，仍需一个 Host 私有桌面 owner 及具体媒体／平台适配。无需新 Runtime 实体、通用媒体框架或独立持久化平台。

## 三、拓扑、信任与状态

```text
Desktop WebView <── loopback WebRTC ──> 本机 Runtime Host
                                            ║
                               WebRTC / ICE 直连（视频、输入）
                                            ║
                                      目标 Runtime Host
                                            │ 私有受管平台调用／IPC
                                      采集、H.264 编码、输入

控制：Desktop → 本机 Host ⇄ 已有中心 WS/WSS ⇄ 目标 Host
```

- 目标 Host 私有桌面模块持有查看者、唯一远程控制占用及共享采集资源；本机 Host 持有两段 PeerConnection 和转交任务。Session／Run 不参与媒体状态。
- 平台原生辅助程序是 Host 管理的能力子进程，按 OS 交互会话运行，无业务数据库、不监听公开网络、不拥有企业授权；不增加常驻 Worker 或会话级进程。
- 保留现有唯一 HTTP／HTTPS 应用监听。ICE 需要短生命周期 UDP 媒体 socket，不能误称“只用 TCP 7240 就能打通”；本地播放段只绑定／接受 loopback，跨设备段使用可用网络候选。
- Host—中心信令与本地协商 API 复用现有认证／版本检查、Origin 和本机来源规则；UI 不拿到跨设备 ICE、中心 Token 或设备秘密。本地 WebRTC 自有 ICE 凭据只在当前内存协商使用。
- SDP 指纹与 ICE 信息绑定当前 access_id、可信用户和目标设备；拒绝已关闭访问、错误来源、迟到协商和任意目标地址代理。不能把 DataChannel 打开当作已获控制权。
- WebRTC 使用原生 DTLS-SRTP／SCTP 安全。现有中心允许 WS、WSS 可选的约定不变；未加密信令不提供抗主动中间人替换 SDP 的保障，不能宣称所有部署均具备可验证的端到端身份安全。需要该保证的部署使用 WSS 并验证证书，本版不另造签名／加密协议。

## 四、连接与权限消费

1. 本机客户端发出打开桌面意图，Host 通过 F01 创建 `desktop_view` 访问。目标同时完成系统能力核查，再创建内存查看资源；访问成功、媒体连通、首帧就绪分别表达。
2. 信令沿 F01／F02 同一控制 owner 路由，中心核对活跃访问及收发设备，转发有界 SDP／ICE；不解析媒体正文，不创建新连接数据库。
3. 本机 Host 先与 WebView 完成本地 offer／answer，得到实际接受的 H.264 参数，再与目标编码能力求交集；目标创建跨设备 offer、本机 Host 回答。只有两段 profile／level／packetization-mode 兼容才启动采集；能力不兼容返回明确错误，不自动转码。
4. 两端 Host 执行 ICE 检查；只使用 host／srflx／prflx 候选，不配置 TURN、不接受 relay 作为成功路径。STUN 地址由部署配置提供，不硬编码未经确认的公共服务。没有 STUN 时只保证尝试现有直接可达地址，不承诺公网 NAT 穿透。
5. 本地媒体连接只接受 loopback 候选；WebView 只接收本机 Host 的编码视频，并经本机 Host 转送输入。两段连通且 WebView 确认收到首个可解码帧后进入查看就绪，才允许申请控制。
6. 控制操作另消费 `desktop_control` 许可，绑定现有查看者；停止控制关闭控制访问，查看访问可以继续。只读和控制撤销分别处理，目标再次验证关联用户、设备、查看者及原生权限。
7. F01 的目标访问准备流程须提供窄的 owner 消费点，把已核验身份、能力、取消与到期传给桌面资源；不扩大公开可变 Session，不从中心 JSON 另建授权缓存。F02 接入时共同核对，修改前重新验证 F01 相关边界。

连接与控制消息使用现有请求关联和随机 access_id，不新增持久 revision／generation。切屏先使旧显示绑定不可输入、释放远程按键并停止控制，再建立新绑定；旧连接不能继续注入新屏幕。新屏首帧就绪后仍只读，不能把旧控制权、排队输入或旧几何信息移交新绑定。目标显示器列表由原生适配枚举，当前引用和显示名称分离，列表序号不作为采集标识；拔除、分辨率／布局变化使旧映射失效时停止控制并重新核查。UI 结果按原访问与标签 owner 关联，取消后的结果直接回收。

### 4.1 访问身份与最小接口

每次查看使用独立 `desktop_view access_id`，它同时作为该次显示绑定身份。切屏关闭旧查看／控制访问并创建新查看访问，不保留一个会被原地改写目标屏幕的访问；新建失败时旧访问也不恢复。显示器枚举由目标在已授权查看准备阶段返回，不消耗额外媒体连接。`desktop_control access_id` 单独绑定同一用户、来源设备、目标设备和活跃查看访问；目标原子检查整机唯一控制占用，失败即关闭这次控制访问。

现有 `OpenAccess` 只有设备和能力，没有查看父级或显示器字段。F04 在 Host 私有的桌面准备／控制绑定请求中关联两次已核验访问，目标从 F01 活跃许可取身份并比对，拒绝跨用户、跨设备或已关闭父级；不能把浏览器提供的两个 ID 直接当作授权证明。当前目标 `Offer` 尚无来源设备字段，需由中心从已有访问事实补充可信来源设备／连接关联，再传给目标消费点；这属于 F04 对既有控制消息的最小扩展，必须补验 F01 兼容与撤销，不能假设现有 DTO 已提供该身份。查看关闭级联控制关闭，控制关闭不撤销仍有效的查看许可。

以下为语义契约，正式字段命名及路由在实施时沿既有分发入口确定，不预建未使用的公共实体：

| 意图／投影 | 必需内容与结果 | 所有者 |
| --- | --- | --- |
| 打开／切换查看 | 可信目标设备、目标显示器引用或首次主屏选择；返回当前查看 access_id、显示器列表、绑定几何和阶段 | Desktop 发送意图；本机 Host 装配，目标准入 |
| 本地播放协商 | 当前查看 ID 与仅本地 SDP／ICE；终止或超时回收两个 peer | 本机 Host 的桌面适配，不进入 Runtime Session |
| 开启／停止控制 | 当前查看 ID；返回控制 access_id 或占用／权限错误，停止幂等 | 目标桌面 owner 原子授予／释放 |
| 状态查询／事件 | 关联查看 ID，查看阶段、所选屏幕、是否持有控制及结构化错误 | 复用 Host 本地事件入口；不把每帧／每键放入 SSE |
| 关闭查看 | 当前查看 ID；立即进入不可输入状态，取消待协商资源及所属控制 | 两端 owner 幂等收尾 |

UI 拥有标签及焦点事实，Host 拥有访问和连接事实；事件只更新匹配访问的标签。控制已执行但响应丢失时先查询当前访问，不重复申请占用；点击、按键、文本不以网络重试实现“至少一次”。

### 4.2 信令与准入预算

- 跨设备 SDP／ICE 走 F01 同一控制连接的桌面专用消息，由中心按当前访问、两端连接和允许方向路由；复用 F02 的有界调度入口，不借用普通文件／终端流传输媒体，也不要求 F02 预建媒体字段。
- 目标是跨设备 offer 发起方，本机 Host 是本地 offer 发起方；每次访问只允许一轮初始协商，避免双端同时发 offer。连接失败或切屏新建访问，首版不做原访问内的自动 ICE restart／无缝迁移。
- 沿用当前控制消息 16 KiB 边界，草案预算为单 SDP 8 KiB、单 ICE 候选 1 KiB、每方向至多 64 个信令候选；应用正文和消息封装均检查字节上限。使用 trickle ICE，候选只加入对应访问的当前 peer；超限或过期拒绝并关闭该次协商，不无限排队。
- 设备授权与媒体协商分开计时：已有 OpenAccess 等待预算不被“15 秒建连”覆盖；15 秒指授权准备完成后的媒体协商总预算。局域网首帧目标从该阶段起计，UI 分别显示核验与连接，取消对两个阶段均有效。
- 本地 peer 显式绑定 loopback，验证远端候选及选中路径确为 loopback，拒绝 relay 或非本地候选；仅配置 `iceServers: []` 不足以实现本地网络隔离。跨设备 peer 不配置 TURN，中心不可作为媒体候选。

## 五、视频与本地转交

- 目标编码一次，H.264 低延迟、无 B 帧；优先平台硬件编码，可用性以实际创建编码会话为准。macOS 使用 VideoToolbox；Windows 枚举 Media Foundation 硬件 MFT，失败时评估系统软件编码的受控降档。不能因 API 存在宣称任意设备支持硬编。
- 建议默认最高 1080p／30fps、按带宽降码率／帧率；需要与实际 SDP level 上限一致。合成视频与整屏实验验证到 720p 范围，不能将 `42e01f` 固定用于所有 1080p 请求；高分辨率显示器按比例降采样，保留输入到真实坐标的映射。多屏实测发现仅固定最大宽度会使较高比例的画面超出当前 H.264 level 的帧尺寸预算并导致编码初始化失败。必须同时约束宽、高及该 level 的宏块／帧率预算，按编码器要求对齐尺寸；切屏按新比例重建编码配置并核对协商能力，不拉伸画面或沿用旧屏尺寸。
- 本机接收 RTP 后按本地会话映射 SSRC、payload type、扩展编号、时间与序列语义，编码载荷保持不变。两段 DTLS／SRTP 分别终止，既不是密文直接复制，也不是解码再编码。
- 反馈不可盲目照搬：本地段 NACK 由本地发送缓存处理，跨设备段 NACK 由其发送端处理；WebView 的 PLI／FIR 经本机 Host 映射并限频通知目标编码器产生新 IDR，同时补齐 SPS／PPS。拥塞估计属于各自链路，目标必须消费跨设备预算并调码率，本地慢消费不能形成无限缓存。
- 帧队列有界，保留最新待编码原始帧；编码流若需丢弃，应在可解码边界丢帧并请求关键帧，不能随机丢 NAL 后继续宣称实时。
- 同显示器、同编码规格共享采集编码；每个查看者独立 PeerConnection／发送预算。首版每显示器仅一个活动编码规格，首个查看者在约定上限内建立它；新查看者须接受该规格，不因其加入静默改变其他人的画质。不为慢查看者另建转码器；其预算不足时关闭该查看者，明确提示网络不足，不能仅丢包后声称已单独降档。只有所有活跃查看者预算支持时才调整共享码率／帧率；需要改变 profile 或画面尺寸时重建相应查看绑定并停止控制。多显示器独立采集，切屏不修改共享采集器的目标。
- 光标建议首版直接绘入视频，避免再建立光标媒体协议；缩放后的光标与系统坐标共同验收。

## 六、输入与存活

- 首版使用可靠有序 DataChannel 承载关键输入；移动事件在发送前合并，不合并按钮、按键、滚轮或文本提交。首版不引入两条无跨通道顺序保证的输入流。
- 点击携带当前显示绑定和归一化坐标：先按实际视频内容区域计算位置，排除适应窗口的留白，再由目标映射至所选显示器的系统全局输入坐标。显示器原点、系统逻辑尺寸、采集像素、编码尺寸和 WebView CSS 尺寸分别处理，不能直接把编码像素当系统坐标，也不能无条件再乘 backing scale／DPI。超出范围直接拒绝，避免把错误点击吸附到屏幕边缘；按键记录由目标输入 owner 持有。重复 key-down、未知释放、控制已失效等情况有明确拒绝／幂等语义。
- 区分物理按键与已提交文本：物理键受目标键盘布局和输入法影响，不能保证与控制端字符一一对应。探针在英文布局验证物理键，在独立文本意图验证中文／emoji；中文组合过程及跨平台快捷键映射仍须验证。正式产品不得为让测试通过而静默切换用户输入法，不把 Unicode 提交称为目标输入法组合已通过。
- 每条输入消息包含当前查看 ID、控制 ID、该控制连接内递增序号及明确意图；目标先核验两项活跃许可与关联，再调用原生输入。心跳、释放、文本同样绑定控制 ID，旧心跳不能恢复已停止的控制。序号只用于有界消费确认和防重复，不持久化。
- 一条输入消息不超过 4 KiB；完整文本提交上限 16 KiB UTF-8，按字符边界拆分，每个控制连接最多组装一个未完成文本提交，起止序号关联分段，超限／超时清空未提交缓冲；完整提交校验后才依次注入。目标报告已接收／已处理序号和错误，表示系统接口结果，不代表应用执行或保存成功；响应未知不重发文本。
- 发送侧草案预算为累计 64 KiB 或最旧待处理输入 250 ms，触限立即禁止新输入、关闭控制并经控制面撤销；不能仅将 stop 排在已堵塞的 DataChannel 末尾。目标通过独立消费确认／存活超时使旧控制 ID 失效；在途输入无法撤回，停止预算还受检测和撤销传输影响，不把 250 ms 队列阈值宣称为跨网绝对延迟保证。
- 输入 owner 记录当前远程控制者注入的键和按钮，原生执行器缓存执行集合用于 IPC EOF／超时释放；该缓存不授予控制权。关闭／失焦／撤销只释放本控制者注入的集合。普通 key-down 的 repeat 必须明确，不把未知重复消息重复执行；未知 key-up 幂等处理。本地物理按键与远程同键同时操作时的 OS 合并行为仍须实机验证。
- 活跃控制需独立的短存活检测，建议每 250 ms 更新、超过 1 秒停止输入并释放按键；心跳必须绑定当前控制连接，不能用设备心跳替代。原生辅助程序也应在 IPC EOF／Host 消失后松键退出，避免 Host 崩溃遗留按键。
- 使用当前 F01 取消：显式控制连接断开立即取消；静默故障不得超过许可到期继续访问，最迟窗口沿现有 45 秒约束。媒体存活不能续企业授权，系统休眠唤醒后先检查到期再处理输入。

上述时限与缓冲为待确认设计预算，需要在真实设备弱网验证后校准。macOS 输入探针已验证实验只读门禁与短心跳看门狗释放；尚未接入正式控制授权、F01 撤销、排队限额或休眠生命周期，不能据此宣称正式权限闭环通过。

### 6.1 控制状态与文字提交

| 状态／事件 | 目标侧约束 | UI 结果 |
| --- | --- | --- |
| 查看准备／无首帧 | 不准入控制；输入全部拒绝 | 连接中，可取消 |
| 查看就绪 | 没有控制许可 | 只读，可申请控制 |
| 控制就绪、画面获焦 | 双许可有效且本连接持有整机占用；执行普通键鼠 | 控制中 |
| 本桌面工具栏／文本弹层获焦 | 先释放已按下键鼠，保留许可与短心跳；仅允许该绑定的显式文本意图 | 输入已暂停，普通按键用于本地 UI |
| 切离桌面标签／客户端窗口失焦 | 关闭控制许可并释放占用，仍有查看许可可保留画面 | 只读，需重新开启控制 |
| 切屏／关闭／撤销／控制心跳过期 | 旧控制 ID 进入终态，不被迟到输入或心跳复活 | 清理或重新连接，新连接只读 |

焦点是 UI 提供的交互门禁，不能替代目标许可校验。文本弹层是明确的本地输入控件，其打开时固定查看和控制 ID；提交时再次核验两者，不从当前侧栏设备推断目标。组合输入期间不发送远程物理字符，收到 composition-end 后由用户显式提交；不同时发送按键字符和已提交文字，避免双重输入。首版不对目标输入法做远程切换，也不自动改写 Command／Control 语义。

静止桌面可能没有新视频帧，不能用“连续多久没变化”独立判断断流。媒体 peer、编码器／采集健康及输入消费状态共同判断可用性；检测到媒体故障就停止控制并遮罩画面，持续画面冻结的诊断通过平台原型校准。失焦或媒体异常后恢复不能自动重获控制。

## 七、平台适配与分发

| 平台 | 首选路径 | 需验收的限制 |
| --- | --- | --- |
| macOS | ScreenCaptureKit → VideoToolbox H.264；CoreGraphics／辅助功能输入；由 Host 管理签名的原生 helper | 屏幕录制／辅助功能权限分别检查；正式签名身份稳定；多屏 Retina／负坐标、锁屏、休眠、权限撤回与 helper 崩溃 |
| Windows | DXGI Desktop Duplication → D3D11 像素转换／Media Foundation H.264 MFT；SendInput | GPU／驱动／硬编能力枚举，显示旋转与 DPI，设备丢失后的重建；锁屏／安全桌面不可用；输入受 UIPI 限制 |
| Linux | 返回被控不支持 | 不启动临时采集程序，不把编译通过当作桌面可用 |

Windows 以显示器捕获为目标，DXGI 路线与当前功能一致；Windows.Graphics.Capture 是后续原生验证若暴露阻塞时的候选，不同时引入双后端。`SendInput` 只能注入相同或较低完整性级别进程，且失败返回不能可靠辨认 UIPI 原因，产品错误需表达实际输入失败，不伪造精确诊断。

两平台采用 Host 私有的受管原生 helper，隔离采集编码故障并保留平台适配边界：macOS 使用 Swift，Windows M0 使用现有 MSVC／Windows SDK 编译 C++ helper，直接调用 DXGI／D3D11 和 Media Foundation，不新增 Rust unsafe 或绑定 crate。采集 helper 按活动显示器／编码规格创建并共享，输入 helper 只为唯一远程控制者创建；按四查看者／两活动显示器预算，最多两个采集进程和一个输入进程，无闲置常驻池。它们属于 Host 的能力子进程，不增加独立产品状态或 Runtime Session。

启动参数绑定工作模式与受信目标，命令经父子私有管道传递；不监听公开端口。输入控制与编码二进制数据使用独立管道，避免视频写阻塞松键消息；帧有明确长度、尺寸和时间戳上限，原始帧和编码队列有界。采集进程故障只结束引用它的查看者；输入进程故障立即撤销控制，查看可保留。

Host 退出时先停止控制并等待释放，随后关闭媒体、停止采集并回收子进程；IPC EOF 使输入 helper 自行松键。输入 helper 单独崩溃时，Host 保留该控制已确认与在途的按下集合，撤销旧控制后通过平台适配补发释放；不得重放其他输入。双方同时被系统强制终止时不能由已消失进程保证补发，异常终止结果和 OS 键态须作为实机验收限制说明。

随包资源按平台编译，正式签名身份、TCC／辅助功能权限绑定和 Client 安装布局统一验证，不能沿用临时探针获得的权限作正式验收。新的 Rust FFI 在实施前列清函数、线程／COM、句柄／纹理所有权和局部 unsafe 例外，不能继承旧文件例外自动扩大范围。

Desktop 与 Client 各自随包携带 Host 所需原生资源；不能依赖 Demo、用户安装 FFmpeg、系统 VNC 或随包 Node。探针用 FFmpeg 产生测试编码文件，不构成产品依赖。Client 的 Host 若作为无交互桌面的服务运行，应返回图形会话不可用；本版不增加服务到用户桌面代理或提权守护程序。

## 八、并发、关闭与错误

- 每个查看者 owner 管理信令、跨设备 peer、本地 peer、反馈、输入和取消任务，采用有界队列。关闭时先禁止输入并松键，再结束媒体与访问，等待任务及平台资源回收；超时才强制终止自己拥有的 helper。
- 用户、设备、中心身份变化，查看权限撤销或任一必要连接结束，均由 owner 统一进入终态；不靠 UI 清理保证安全。
- 采集按显示器共享，引用计数只表达使用者数量，不复制第二份系统桌面事实。唯一控制占用由目标串行处理，失败或控制许可取消时释放，不持锁执行平台调用。
- 错误至少区分：未授权／控制占用、目标离线、无图形会话、权限缺失、编码不可用、协商不兼容、无法直连、媒体中断及资源繁忙。未知副作用不重放，重试创建新访问。
- 仅记录访问关联、状态、耗时、候选类型和汇总流量；不记录视频、输入文本、完整 SDP／ICE 凭据或用户屏幕内容。

建议验收预算：在约定参考设备、局域网及 1080p 动态画面下目标 30fps；首帧 P95 不超过 3 秒，实际输入至屏幕反馈 P95 不超过 200 ms，单流码率先按 2—8 Mbit/s 调优。弱网下优先保证有界延迟和输入停止，允许降画质／帧率；授权准备完成后的跨 NAT 媒体协商建议总等待不超过 15 秒。端到端延迟以可识别帧／受控目标应用测量；CPU、GPU、内存与持续运行增长在平台原型后形成可验证预算，当前不虚填承诺。

能力、错误和少量意图进入 `assistant-protocol` 并生成 TypeScript；SDP／ICE 封装留在 Host／中心传输适配。无需桌面数据库迁移或修改既有 Session 数据。新增软件 capability／企业信令后检查旧客户端严格解析、同版准入与降级行为，再决定兼容下限；探针不提前提升发布版本。

正式依赖已在 M0 固定，剩余待办仍限制完整平台支持与 Feature 完成结论。双平台采集基础通过不等于远程桌面端到端可用。

## 十、主要依据

- [WebRTC 信令与 ICE](https://webrtc.org/getting-started/peer-connections)：信令由应用提供；STUN／TURN 角色不同。
- [TURN](https://webrtc.org/getting-started/turn-server)：中继实际承担媒体流量，本版明确禁用。
- [webrtc 0.21.1 API](https://docs.rs/webrtc/0.21.1/webrtc/)及[上游示例](https://github.com/webrtc-rs/webrtc/tree/master/examples)：编码样本和 RTP 转交；实验锁定具体版本，不按浮动文档认定稳定 API。
- [str0m](https://github.com/algesten/str0m)：Sans-I/O 候选，本轮未验证。
- [Apple ScreenCaptureKit](https://developer.apple.com/documentation/screencapturekit)、[VideoToolbox](https://developer.apple.com/documentation/videotoolbox/vtcompressionsession)：平台入口，具体行为以原生验证为准。
- [Microsoft Desktop Duplication](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/desktop-dup-api)、[H.264 Encoder](https://learn.microsoft.com/en-us/windows/win32/medfound/h-264-video-encoder)、[SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)：Windows 候选的官方能力及限制。

### M0 实施补充（2026-10-16）

- 采集基础归 `apps/runtime-host/src/desktop_media/` 与 `native/desktop/`。原生 helper 与 Host 同目录，固定名 `ez-assistant-desktop-capture`（Windows 为 `.exe`）；私有 stdin 控制／stdout 编码帧／stderr 状态，不开放网络监听，不触碰用户数据库。隐藏的本机 `desktop-media` 诊断仅枚举或短时采集计数，不保存画面，不构成远程授权入口。
- 原生输出是有界 Annex-B H.264 access unit，包含微秒时间戳和关键帧标志；Host 检查长度、编码配置及单调时间，取消部分读取后只能关闭该进程。macOS 最多两帧在途，满时在编码前丢原始帧；Windows 单线程采集／编码／输出，无待处理帧队列。控制 EOF 与视频输出独立，Host 显式等待退出，原生进程保留有界异常退出兜底。
- macOS helper 最低系统要求为 macOS 13，使用 ScreenCaptureKit／VideoToolbox 硬编，最大 1920×1080／30fps、Baseline Level 4.0，保持比例和偶数尺寸。权限不足或硬编初始化失败明确报错。本阶段权限验证来自开发启动环境，不能替代 M3 正式签名与 TCC 验收。
- Windows 当前明确使用 Media Foundation 软件编码，报告 `hardware=false`，降档上限为 1280×720／15fps、Baseline Level 3.1；不是已达成的帧率承诺。硬编路径、目标性能及旋转显示支持尚未完成，须在 M3 收口；当前旋转显示明确拒绝。软件编码使用 CBR、低复杂度与单工作线程低延迟配置，避免默认参数导致低更新率画面首帧积压；真实受控窗口已验证可解码输出。采集要求当前用户的交互会话，Session 0 不绕过系统边界。
- 最小构建入口为 `apps/runtime-host/scripts/build-desktop-capture.mjs`；Desktop 构建／sidecar 随包与 Client macOS 平台包复制同一结果。macOS helper 标识固定为 `com.ez-assistant.desktop.capture`，正式构建使用显式 Developer ID，开发构建仅 ad-hoc；不将临时签名当成正式分发完成。
- M0 只验证 macOS arm64、Windows x64；其他架构、真实 WebView 播放、远程鉴权／信令、跨 NAT 与控制输入仍按后续里程碑进行。

### M1 实施补充（2026-10-16）

- 桌面查看复用现有 `DesktopView` 许可、撤销、续期和源登录；中心为本次访问附加可信连接标识，只路由有界 `desktop_signal`。普通访问兼容旧中心缺少该字段的情况；桌面访问必须具备该绑定。中心无视频正文转发，无新数据库表。
- 本机认证监听增加 `/desktop-view/socket`，校验真实 loopback 来源、原登录和兼容信息；首消息携带 `DesktopViewOpenRequest`，Token 不放 URL。UI 只连接本机 Host，中心与跨设备 SDP／ICE 留在 Host 内。WebView 首帧实际解码后才报告就绪。
- 两段固定 H.264 Baseline Level 3.1、packetization-mode 1，当前主屏保持比例降至最高 1280×720／15fps。目标编码一次，本机转交 RTP 时重建本段 SSRC／负载类型／头扩展及填充，不重复编码。已连接路径通过 ICE transport 核验，本地段两端必须 loopback，跨设备段拒绝 relay；接收端在轨道建立后、转交任何载荷前检查路径。
- `EZ_ASSISTANT_DESKTOP_STUN` 为显式逗号分隔的 STUN URL 配置，最多四项、默认空；不接受 TURN。LAN 两平台互看已验证；跨 NAT 和不可穿透条件的实测仍是 M3 完成前门槛。
- Host Supervisor 拥有查看任务，两段 peer 均显式关闭；取消、许可撤销、中心失联和退出结束任务，目标等待采集 helper 退出。当前最多八个本机查看 socket、四个目标查看，信令、RTP 与反馈队列均有界。NACK 在各段处理；关键帧请求与编码码率反馈合并、限频，取跨设备与下游反馈中更严格的码率。
- 右栏桌面绑定打开时的设备与用户，同设备所有会话／草稿复用同一标签与 `DesktopController`；控制器归设备的资源 Store，普通资源仍归会话／草稿组。页面 key 不包含会话组 ID，切换同设备会话不重挂载视频。入口统一由右栏“＋”提供并传入查看／控制权限，设备选择菜单不承担打开桌面的动作。提供取消、断开、显式重连、适应窗口／原始大小及全屏；M1 只读，桌面连接不写入本地恢复快照，显示器偏好恢复留在 M3。
- 两台真实机器上，正式 Host 与正式桌面组件分别通过 WKWebView、WebView2 完成真实屏幕播放；权限撤销、拒绝重连、关闭／提前取消、中心断开和采集退出已核验。该验证未覆盖整套安装版客户端、跨 NAT、弱网、多屏、输入及持续性能，不替代 M2／M3。Windows 防火墙需允许 Host 的直连 UDP；受阻时明确连接失败，不自动修改系统规则或回退中继。


### M2 人工测试反馈：高清分辨率（2026-10-16）

用户明确先解决画质／分辨率，锁屏唤醒与系统服务方案搁置。以下规格取代 M0／M1 的临时 720p 降档，不改变软件版本或数据库：

- 保持源屏比例，仅缩小不放大，长边上限 1920、短边上限 1440，向下对齐偶数像素。16:9 为 1920×1080、16:10 为 1920×1200、4:3 为 1920×1440；更小屏幕保留原尺寸，超宽屏按长边等比缩小。尺寸预算支持宽高交换，Windows 旋转显示的原有限制仍待 M3 实现。
- macOS 按显示模式的物理像素计算 Retina 采集尺寸，继续 VideoToolbox 硬编、最高 30fps。Windows 继续 Media Foundation 软件编码，保留最高 15fps，采用双线性缩小与 2×2 色度平均、中等编码复杂度及低延迟切片线程；本项不宣称已完成硬编或持续性能验收。
- 两段 H.264 统一 Baseline Level 5.0／packetization-mode 1，覆盖 1920×1440 的宏块预算。WebView 接收适配先查询横／竖规格的 WebRTC 解码能力，再在接收 answer 中声明该档位；不支持时明确提示，不直接把默认 Level 3.1 当高清能力。本机 Host 完成该协商后才允许目标启动采集，不转码。
- 起始码率与拥塞控制预算统一 8Mbps，上限 8Mbps，继续取两段反馈中的较小值。Windows 编码器的工作缓冲上限与实际编码帧上限分开：工作缓冲最多一张最大 BGRA 帧，输出到 Host 的实际单帧仍最多 4MiB。
- 同一在途版本的私有媒体规格需两端 Host 与查看端 UI 配套更新；不新增持久化、协议版本或旧试验档位的兼容分支。原始尺寸居中修复继续保留。

### M2 人工测试反馈：可变帧率时间戳（2026-10-16）

桌面静止与重新变化会产生非固定采集间隔。Host 复用 H.264 RTP 分包器，以每帧原生 PTS 直接映射 90kHz 时间戳，保留随机起点、序号和 MTU；不得把上一帧间隔作为 `Sample.duration`，该接口在当前帧分包后才推进下一帧时间。该修正不调整分辨率、码率或采集上限，不代表端到端性能验收已完成。

### M2 人工测试反馈：发送预算一致性（2026-10-16）

两段媒体连接的发送限速器必须显式使用与编码器、GCC 相同的初始 8Mbps 预算。当前库的拥塞配置函数会安装默认 1Mbps 限速器，而 GCC 只有估计值变化才通知其调整；估计维持初始值时会持续积压高清数据。在现有 Registry 的 Pacer 位置替换配置即可，保留拥塞反馈、重传和动态降速，不增加第二个限速器或媒体路径。隔离双段 WebRTC 播放已复现并验证该修正；真实安装版双向连接仍需更新后验证。

### M3 实施补充（2026-10-16）

- 显示器目录随既有 offer 返回，中心继续转发已有信令，不增加目录接口或数据库状态。UI 以平台原生显示器 ID 选择，物理尺寸仅作展示；Host 将 ID 与当前位置、尺寸及旋转绑定，原生采集和输入均校验。布局变化结束旧绑定，用户重新选择或重连，不静默切换到其他屏幕。
- 目标 Host 的既有 Supervisor 按显示器持有共享采集，最多同时两块屏幕、四名查看者；同屏只编码一次，各查看者独立连接、反馈和有界帧订阅。最后一名查看者离开后停止并回收 helper；后来加入者请求关键帧。Mac 静态桌面按关键帧请求重新编码最近原始画面，时间戳保持单调。
- 共享编码维持既定高清规格和初始预算；各查看者的两段拥塞反馈独立。持续无法承载实际编码流、订阅积压或发送堵塞时仅结束该查看者，不用最慢查看者降低所有人的编码质量，不保留无界历史帧。真实弱网行为和持续性能尚需实测，不将预算当成已达成指标。
- 显示器选择复用现有下拉组件。切屏结束旧访问，新访问默认只读；本地恢复只保留设备、显示器和布局，不保存许可或媒体连接，不自动重连或恢复控制。
- Windows 增加旋转后的像素映射；两平台原生采集、Mac 真实共享采集及组件交互检查通过。当前实机均只有一块显示器，真实多屏、旋转、热插拔、跨 NAT 及弱网组合验证仍未完成；这不构成 F04 完整验收结论。唤醒、锁屏和系统服务继续搁置。
