# v0.32.0 F05 接入方案：OpenCode

## 一、状态与目标

- 所属版本：v0.32.0；依据[总体设计](../../总体设计.md)与[版本开发台账](../../开发计划.md)。
- 状态：2026-10-16 用户明确开始 F05，按本方案与计划完成 M0—M2 实现及自动化验证，真实账号与人工验收待进行；用户随后授权自主开发测试，最后统一人工测试。
- 用户方向（2026-10-15）：OpenCode 复用现有方言机制；企业端与客户端本地具备一致的模型配置能力；原生协议和会话请求头由执行会话的本机 Runtime 处理，企业端仅转发。本次授权编制方案并纳入版本计划。
- 目标：个人直连和企业配置两种来源都能使用 OpenCode 的 OpenAI-compatible 模型，解决模型发现与推理前缀不同、会话请求头缺失和协议选择不明确的问题。

本文合并本 Feature 的功能边界、技术方案与现有表单调整说明；实施步骤见[开发计划](开发计划.md)。不为同一范围重复建立功能或交互文档。

“本机 Runtime”指真正执行该会话的 Runtime Host。在跨设备使用场景中，它是目标设备的 Runtime，不能由仅显示界面的设备生成另一份模型会话身份。

## 二、已核查事实与复用依据

| 事实 | 源码入口（仓库根相对路径） | 方案影响 |
| --- | --- | --- |
| 模型发现支持 `models_path` 同源绝对路径，替换基础地址的整个 path | `apps/runtime-host/src/resources/model/discovery.rs`、`apps/enterprise-center/src/models/discovery.ts` | 直接复用，不增加独立 models URL 或第二套发现服务 |
| Provider 身份、协议偏好、端点、目录与固定参数已有统一模型 | `crates/assistant-protocol/src/model_management.rs`、`apps/enterprise-center/src/contracts/models.ts` | 本地与企业配置使用同一语义，只补 OpenCode 身份与相应校验 |
| Host 按显式 Provider 身份装配 Chat／Responses 方言 | `apps/runtime-host/src/resources/model.rs` | 在现有具名方言和装配分支接入；不新增 crate、Agent Loop 或独立 OpenCode SDK |
| 模型工厂没有稳定会话路由参数；调用 trace 仅供诊断，不可编码进 HTTP | `crates/assistant-runtime/src/factory.rs`、`crates/agent-model/src/context.rs`、`crates/agent-openai-compatible/src/shared/transport.rs` | 补最小构造参数，不能借用 trace、Run ID 或历史续接绑定 |
| 企业配置下发保留实际 `provider_type`，endpoint 替换为中心代理地址 | `apps/enterprise-center/src/models/service.ts`、`apps/runtime-host/src/access/enterprise/client/models.rs` | 保留 OpenCode 身份，使本机即使访问中心 URL 也选择正确方言 |
| 中心模型 HTTP 代理已转发原始正文，但上游请求头由固定列表重新构造 | `apps/enterprise-center/src/llm/transport.ts` | 扩充受限头透传；不在中心补造 OpenCode 标识或请求体 |
| 中心管理测试当前会自行拼装原生模型请求 | `apps/enterprise-center/src/llm/management.ts` | OpenCode 推理验证必须使用本机 Runtime 的正式适配器，不能复制这条编码路径 |

删除新增机制后，现有事实是否足够：端点、发现、参数和 HTTP 转发均足够，继续复用；显式 OpenCode 方言身份与跨 Run 稳定的会话路由参数目前缺失，需在现有类型中最小补充。无需新会话表、会话映射服务、目录缓存或通用任意请求头配置平台。

## 三、配置能力与外部接口

### 3.1 本地与企业端配置一致

在既有 Provider 类型中增加 `opencode`，本地设置与企业后台都提供 OpenCode 入口，并支持相同的：

- 服务商名称、推理基础地址、API Key、模型列表路径和显式推理协议。
- 刷新在线目录、手动模型、固定参数、模板补全、默认模型及已有能力设置。
- 保存、编辑、删除、凭据保持／替换以及连接变化后的目录失效提示。

沿用现有权限与来源规则：个人配置归 Runtime，企业配置归中心；企业用户客户端消费中心下发的有效配置，不维护另一份可写企业配置。API Key 在企业模式留在中心，本机使用既有中心模型凭据。

Go 订阅与普通按量入口用表单预设填充现有 endpoint／models_path；不新增套餐业务实体或持久化套餐枚举。选择预设时明确展示将更新的地址，编辑已有自定义值不得静默覆盖。

### 3.2 地址与协议

2026-10-15 官方 Inference API 与路由源码提供以下接入依据；基础地址后由现有协议服务追加 `chat/completions` 或 `responses`：

| 入口 | 推理基础地址 | 模型列表路径 | 证据状态 |
| --- | --- | --- | --- |
| 普通按量 | `https://opencode.ai/inference/openai/v1` | `/inference/v1/models` | 推理来自官方 API 文档；列表已只读核对 |
| Go 订阅 | `https://opencode.ai/inference/go/openai/v1` | `/inference/go/v1/models` | 推理按官方代理源码映射推导；列表已只读核对，订阅推理待实测 |

官方模型／Go 页面与专门的 Inference API 页面仍存在路径描述差异，旧 `/zen/...` 入口也仍有代理映射。实现 M0 固定预设前重新核对路由；不通过推理失败后切换地址、切换套餐或切换协议来试探。当前事实不能表述为账号鉴权、额度或真实推理已通过。

`models_path` 必须填写含前缀的同源绝对路径，不能填完整 URL；留空继续使用既有默认拼接行为。两端表单展示最终发现地址及推理地址，让前缀差异可见，不额外持久化派生 URL。

OpenCode 实例明确选择 Chat Completions 或 Responses；新建默认显式 Chat Completions，表单不提供含糊的“自动”，后端对 OpenCode 的 `auto` 配置明确拒绝并提示选择协议。其他 Provider 的既有规则保持其原契约。同一账号需要两种协议时，使用现有机制建立两个实例，不在本 Feature 引入模型级协议覆盖。

在线目录只证明模型被列出，不证明该模型适用于所选协议、账号可用或能力参数完整；原始模型 ID 保持服务端返回值，不加 `opencode/` 或 `opencode-go/` 客户端选择前缀。模型能力继续按已核实模板和固定参数处理，不能根据名称继承上游厂商方言。Messages、Gemini、System One 的新协议适配不在本 Feature 范围内。

## 四、本机方言与稳定会话路由

### 4.1 唯一处理位置

```text
个人：Runtime → 本机 OpenCode Adapter → OpenCode
企业：中心配置下发 → Runtime → 本机 OpenCode Adapter → 中心模型代理 → OpenCode
```

两条路径复用 `agent-openai-compatible` 的 Chat／Responses Service、Codec、Decoder 和 Transport。
OpenCode 的具名构造声明已核实的 wire 差异与请求头策略；会话标识值作为 Service 的不可变构造输入，不能放入全局 Adapter 单例。通用编码规则继续复用，未核实的差异不得复制 DeepSeek、Kimi 或 OpenAI 官方特有行为。

Runtime 依据会话事实提供通用 `conversation_routing_id`（工作名称，实施时在现有模型工厂输入中明确），Host 将它交给具体模型 Service。优先扩充 `ModelServiceFactoryRequest` 并沿既有装配调用传递，不让 Agent Core 引用 `SessionId`、企业协议或 OpenCode 头名，也不为此建立新的通用上下文框架。复用已有服务实例的调用方必须核对 owner 一致，不能跨会话共用可变 header 状态。

由本机 OpenCode Service 在编码后的出站请求中写入：

- `x-opencode-session`：当前 owner 的稳定、不透明路由标识。
- `User-Agent`：真实产品标识 `ez-assistant/<版本>`。

头注入覆盖 Chat 与 Responses。仅当配置明确为 OpenCode 时启用此策略，不能按 URL 包含某个字符串猜测方言。企业 endpoint 是中心地址也必须生效。Session ID 不进入 prompt、模型参数、工具结果或对话正文。

### 4.2 标识生命周期

| 场景 | 路由身份 |
| --- | --- |
| 主会话多轮、工具继续、建流重试、压缩后续跑、正常重启恢复 | 同一稳定 owner 标识 |
| 不同主会话、Fork 新会话 | 不同标识 |
| 子任务 | 从其 SessionId 与 ChildTaskId 构成独立 owner；子任务多步与恢复保持稳定 |
| 标题、本地摘要、辅助识图等旁路调用 | 沿所属会话／子任务 owner 传递；其无状态／历史隔离规则仍独立成立 |
| 无持久会话的本机连接测试 | 每次测试生成临时标识，该次重试复用，后续测试重新生成；不建立业务会话 |

优先由现有唯一 SessionId／ChildTaskId 加固定用途域派生哈希，不保存新的映射表或在每次 Run 分配新 UUID；派生规则不包含软件版本、登录 Token、Run ID、attempt 或历史配置周期。相同 Session 的清空上下文仍沿用会话路由标识；服务端历史失效与 `previous_response_id`、原生压缩绑定继续由原机制处理。该路由头不表示启用远端历史存储，也不是鉴权凭据。

## 五、企业配置、下发与透明转发

### 5.1 配置与下发

企业后台和中心 API 完整接纳 OpenCode 的类型、路径、协议及参数，复用已有存储、校验、审计、模型发现与固定参数机制。中心做配置解析和协议准入不等于执行 Provider 方言；实际原生编码仍由本机 Adapter 完成。

配置下发沿现有 `provider_type`／`protocol`／`parameters` 投影保留 OpenCode 身份，endpoint 仍是中心受信代理地址。不能把 Provider 类型改成普通 OpenAI，也不能要求 Host 根据隐藏的上游 URL 猜测方言。配置变更、凭据失效与有效配置绑定沿已有机制处理。

### 5.2 请求转发

中心接收本机已编码的正文和已生成的会话头，复用现有 HTTP 原字节转发：

- 在通用代理的受限透传列表中允许 `x-opencode-session` 与 `User-Agent`，校验单值、长度和非法换行后保留值；不开放任意头透传。
- 中心不生成、改写或兜底补齐会话标识，不根据 OpenCode 类型添加 User-Agent，也不执行 OpenCode 的 thinking／reasoning／工具调用编码。
- Authorization 继续由中心依据已准入的配置替换为上游 API Key；中心私有控制／绑定头和逐跳头仍按现有规则处理，不能透传用户 Cookie 或中心认证材料。
- 路径按配置与已选协议映射，正文原字节、流式响应、错误、取消和背压沿现有行为；中心不新增自动重试、模型替换或跨协议回退。
- 请求头缺失造成的上游错误如实返回，修复发生在本机生产请求的一侧，不在中心补造成功条件。

OpenCode 首批验证 HTTP/SSE。已有其他服务商的 WebSocket 协议转写能力继续沿其原边界；不能据此推定 OpenCode 支持 WS、服务端续接、原生 compact 或精确计量。这些能力须有对应路由证据才可声明，未验证时保持关闭／未知；若后续纳入协议转写，仍须透传本机身份，不能将方言编码迁到中心。

### 5.3 配置测试的明确边界

中心现有 `model-configuration/test` 会合成原生 body，不能作为 OpenCode 方言的另一实现。本 Feature 的 OpenCode 推理测试通过已接入企业的客户端／Runtime 执行，使用正式模型配置和同一适配器；本地模式也使用此路径。

后台仍可保存完整配置、刷新目录和检查参数；OpenCode 的配置测试位置明确说明需在客户端验证，后端不得让这类请求落入现有中心合成 body 的测试分支。目录成功不能标成推理成功。本 Feature 不为测试新增远端 Host 调度、浏览器直连本机或中心模型执行器；其他 Provider 的既有测试范围不借机重构。此交互限制需在计划审阅时明确，并以 M2 验收核对。

## 六、兼容与实现影响

- 修改范围：共享 Provider 类型／TS 投影、Runtime 配置编译与模型装配、Host Adapter、桌面表单、中心配置 DTO／下发／代理、管理后台及必要模板。模型发现复用现有实现。
- 预期不新增数据库表或持久化会话字段。实施前核查 SQLite 类型解码、中心 JSON／约束及模板枚举；若确需迁移，先明确实际存储影响与回滚，不把新增 Provider 类型等同于无需兼容评估。
- 旧通用 OpenAI 配置不自动改为 OpenCode；用户显式修改后启用方言。旧 Host 不认识新 Provider 时明确不兼容，禁止降级成通用 OpenAI 后继续调用。M0 核查发现旧 TS 客户端不做运行时 Provider 枚举校验，应用最低兼容版本统一提升为 `0.32.0`，阻止旧客户端读取无法正确展示的新类型。企业协议保持 3；旧 Host 解码未知 Provider 时失败，不降级。SQLite 表结构和存储下限保持原值，旧正式 Host 已由未知 v0.32.0 迁移账本拒绝原地降级。版本门禁针对已发布旧版，不能区分此前同为 0.32.0 的在途测试包；测试包须按本次完整源码配套更新，不能以同版本号认定已具备 OpenCode 能力。
- Core、规范消息和 Journal 无新增 OpenCode 字段；不持久化 API 请求头。应用层会话类型不会进入底层模型 crate。
- 非 OpenCode 路由不携带该会话头。既有本地／企业其他服务商、鉴权替换、错误分类与取消须定向回归。

## 七、验收条件

1. 本地和企业后台均可保存／编辑 OpenCode，模型目录与固定参数遵循相同语义，配置下发保留方言身份。
2. 推理前缀含 `openai` 而列表路径不含时，发现与推理命中各自正确路由；不靠失败后盲试。
3. Chat／Responses 均在本机完成编码和头注入；代理前后正文一致、会话头与产品标识值一致，只有已明确的鉴权／传输头变化。
4. 同会话跨 Run、工具轮次、重试和重启稳定；不同会话／子任务隔离，并发不串头；标题／摘要／辅助调用及临时测试覆盖明确。
5. 中心不存在新增 OpenCode 编码分支或 session 生成逻辑；后台仍具备完整配置能力，目录测试与推理测试状态区分清楚。
6. 配置来源切换、未知 Provider、缺失会话参数、无效 header、授权失效和上游失败可诊断，不静默换协议或改套餐。
7. 正式隔离 Host 覆盖直连与经中心两条路径；真实订阅验证按届时明确的测试账号、模型及额度范围执行。未执行的真实路由明确保留，公开 GET 或模拟网关不能冒充订阅可用。
