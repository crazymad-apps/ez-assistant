## 二、结论

当前不建议确认 M1，也不建议进入 M2。

M1 的类型化 Tool、类型擦除、Registry、不可变快照和单次 Dispatcher 主链路已经实现，计划内验证及 workspace 回归均通过；但本次审查发现：

- 3 个高优先级方案问题；
- 2 个中优先级 M1 公共契约问题；
- 1 个中优先级文档一致性问题。

其中 Registry 重名不变量和 schema 同步保证属于 M1 当前实现范围；授权批次语义、预算检查位置和取消后的 Tool Call/Result 配对属于后续 M3/M4 实施前必须解决的方案问题。处理并重新验证前，不满足当前里程碑确认条件。

## 三、审查发现

### 3.1 高：同批工具的授权与执行顺序互相矛盾

#### 证据

- 功能设计 §4.7 规定：批次内每个 Tool Call 独立过闸，**全部放行后才开始执行**。
- 技术方案 §4.2 与开发计划 M4 描述为：逐个 `authorize`，Allow 后立即 `dispatch`，然后继续处理下一调用。
- `docs/modules/agent-core.md` 只规定逐 Tool Call 的 `record → authorize → execute`，没有消除上述批次级歧义。

#### 影响

假设同批有调用 A、B：

1. A 获得 Allow 并产生副作用；
2. B 随后被 Deny、等待审批或在等待时取消；
3. 此时已经违反“全部放行后才开始执行”的功能设计语义。

该差异还会影响用户审批体验、取消边界、共享顺序日志以及同批多工具 Harness 的预期结果。

#### 建议

在 M4 前明确选择并统一一种语义：

- 先完成整个批次的授权，再顺序执行已获授权的调用；或
- 明确改为每个调用独立 `authorize → execute`，同步修改功能设计和验收标准。

Harness 至少补充：

- 同批 `Allow + Deny`；
- 第一个 Allow、第二个授权挂起后取消；
- 断言任何副作用是否允许发生在整个批次授权完成之前。

### 3.2 高：预算检查位置晚于工具副作用

#### 证据

- 技术方案将 `max_tool_calls` 定义为“实际 dispatch 的工具调用数上限”。
- 功能设计要求显式 `max_steps` / `max_tool_calls` 到达即受控终止。
- 技术方案和开发计划的状态机描述把预算检查放在 `dispatch`、ToolResult 记录之后。

#### 影响

- `max_tool_calls = 0` 时可能仍先执行一个工具再报告超限。
- 只剩 1 次额度、同批请求 2 个工具时，可能先执行 2 个工具再检查预算。
- `max_steps` 若只在轮次结束后检查，也无法阻止超过上限的下一次模型调用。

这会让资源预算失去“副作用前硬边界”的意义。

#### 建议

- 在模型调用前预检 `max_steps`。
- 在每次工具 dispatch 前预检 `max_tool_calls`。
- 明确同批调用超过剩余额度时，未执行调用如何形成配对的错误 ToolResult。
- 增加 0、刚好等于上限、同批跨越上限和 `None` 不限制四类边界测试。

### 3.3 高：取消可能在权威记录中留下未配对的 Tool Call

#### 证据

- 方案要求在任何工具副作用前先通过 Recorder 记录完整 AssistantMessage。
- 授权等待和工具执行中均可取消，取消统一收敛为 `ExecutionCancelled`。
- 当前方案没有规定取消后如何结算已经记录、但尚未产生 ToolResult 的调用。
- Agent 系统架构同时要求 Tool Call/Result 保持 ID 配对与顺序，未完成调用不得记录成成功。

#### 影响

授权等待或工具执行期间取消后，Conversation Journal 可能已经包含带 Tool Call 的 AssistantMessage，却缺少对应 ToolResult。后续若直接投影为模型请求，可能违反 Provider 的消息配对要求并导致请求失败。

同批多工具执行到一半时，问题更复杂：部分调用已有副作用或结果，剩余调用仍处于未结算状态。

#### 建议

在 M4 前明确唯一责任方和恢复语义：

- Core 在取消收敛前为未完成调用记录 interrupted/cancelled 错误 ToolResult；或
- Runtime/Journal 投影时统一结算未完成调用，并明确 ExecutionInput 不会携带未结算配对。

至少覆盖：

- AssistantMessage 记录后、授权完成前取消；
- 单工具执行中取消；
- 同批第二个工具执行中取消；
- 取消后生成的新 ConversationSnapshot 仍满足 Tool Call/Result 配对。

### 3.4 中：Registry 没有真正保证重名拒绝和名称索引稳定

#### 证据

`ToolRegistry::register_erased` 在注册时调用一次 `definition()` 取得名称并检查重复；`snapshot()` 随后再次调用每个工具的 `definition()` 生成定义列表和名称索引。

`ErasedTool` 是公共 trait，`register_erased` 是公共注册入口，因此实现方可以返回动态或带内部可变状态的 ToolDefinition。

#### 影响

如果两次 `definition()` 返回不同名称：

- 注册阶段的重名检查可能被绕过；
- 快照中可能出现重复定义；
- `by_name` 后写覆盖前写，导致部分工具无法派发；
- 模型可见定义与实际派发索引不再满足 Registry 契约。

现有测试仅使用定义恒定的 mini tool，没有覆盖这一公共 SPI 边界。

#### 建议

- 注册时只读取一次 ToolDefinition，并将其与工具句柄共同冻结。
- 快照直接消费已冻结定义，不再次调用工具的 `definition()`。
- 增加定义发生变化时仍不能破坏重名和索引不变量的回归测试。

### 3.5 中：schema 与输入类型“恒同步”没有被 API 强制

#### 证据

- `Tool::definition()` 有 schemars 派生 schema 的默认实现，但实现方可以覆盖该方法。
- `TypedToolErasure::definition()` 直接信任 `Tool::definition()` 返回值。
- 公共 `ErasedTool` 实现也可以完全自行提供 ToolDefinition。
- 文档和 M1 实际结果却将 schema 与 `Input` 类型“恒同步”描述为强保证。

#### 影响

工具实现可以提供与 `Input` serde 反序列化规则不一致的 schema：模型按公开 schema 生成参数后，运行时仍可能拒绝；反之也可能隐藏真实接受的字段。现有测试只验证默认派生结果含 `a`、`b` 字段，不能证明公共 API 强制了该不变量。

#### 建议

二选一：

- 由类型擦除层固定使用 `T::Input` 生成 schema，Tool 实现只提供名称和描述；或
- 明确允许覆盖，将文档承诺改为“默认实现保持同步”，并定义自定义 ErasedTool 的责任边界。

### 3.6 中：`ExecutionPlan.context` 的共享事实不一致

#### 证据

- 功能设计仍将 ExecutionPlan 描述为含 `context` 的五字段结构。
- 技术方案正文和开发计划采用不含 `context` 的四字段结构。
- 技术方案顶部状态说明该偏差已经于 2026-07-26 确认，但风险章节仍写为“待用户确认的偏差”。
- `docs/inputs/260726-长任务机制参考（opencode调研）.md` 还出现“四字段 plan 的 `context` 字段”这一自相矛盾表述。

#### 影响

功能设计、技术方案、开发计划和输入记录对公共执行契约给出不同答案。进入 M3 后，实施者无法仅根据已确认文档判断 `ExecutionPlan` 的最终字段，也不符合共享范围变化应同步功能设计的流程约束。

#### 建议

- 将功能设计统一为已确认的四字段结论。
- 删除技术方案风险章节中的“待用户确认”状态。
- 修正输入记录中的矛盾表述。
- 同步核对版本台账、开发计划和本地进度，但不改变当前里程碑状态。

## 六、M5 集成收口复审（2026-07-28）

### 6.1 结论

M1 审查的六项发现均已在后续里程碑处理；M5 对 v0.2.0 完整实现复审后未发现
阻断版本验收的问题。依赖方向、公共 API、默认测试离线性、文档与功能设计验收
标准已经对齐，M5 可以提交确认。

### 6.2 审查范围

- `crates/agent-tools/`：Tool SPI、Registry/Dispatcher、FileSystem/Shell 能力与桥接。
- `crates/agent-core/`：执行契约、两阶段 Recorder、事件通道与 Agent Engine。
- `crates/agent-testkit/`：能力 fake、Engine Harness 与离线 example。
- v0.2.0 功能设计、技术方案、开发计划、模块约束、版本台账和本地开发进度。

### 6.3 发现与处理

1. `agent-tools` 的 `futures-core` 没有生产调用，已删除。
2. `agent-core` 的 `serde_json` 只用于单元测试，已从生产依赖移到
   `dev-dependencies`。
3. `AgentEventSender`、事件通道构造器和容量常量只属于 Engine 内部管道，外部
   无调用方且不应允许伪造 Core 事件，已收回为 crate 内可见。
4. `ToolBehavior` 被 `ScriptedTool` 的三个公共构造器完全封装，外部无调用方，
   已改为私有类型并移除重导出。
5. Registry 模块注释残留 `ExecutionPlan` 旧称、功能设计仍把已解决项列为开放
   风险、技术方案验收矩阵误用模型 `EventCollector` 描述 Agent 事件测试，均已
   按当前实现修正。

### 6.4 审计结论

- 直接依赖保持单向：
  - `agent-tools → agent-types`；
  - `agent-core → agent-model / agent-tools / agent-types`；
  - `agent-testkit → agent-core / agent-model / agent-tools / agent-types`。
- `agent-tools` 不依赖模型、Engine、Runtime 或 Tauri；`agent-core` 不依赖
  Runtime、Tauri、数据库或具体 Provider。
- 三个 crate 的生产依赖通过 `unused_crate_dependencies` 严格检查。
- 保留的公共项均属于稳定 SPI、公共返回类型、执行入口或 testkit fake；内部事件
  发送管道不再暴露。
- 默认测试不访问真实网络、文件系统、数据库或凭据，不使用 sleep 判断并发顺序；
  testkit 中的 DeepSeek URL 只是 recorded request 数据。唯一真实 API smoke test
  位于 Provider Adapter 且显式 ignored。
- 功能设计验收标准 1–10 均有对应实现和确定性测试。
