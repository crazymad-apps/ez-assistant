# v0.2.0 功能设计：Agent Engine 与工具循环

## 一、设计信息

- 版本：v0.2.0
- 状态：✅ 已确认（2026-07-26；2026-07-28 M4 审查修订同步验收语义）
- 影响模块：`crates/agent-core`（主）、`crates/agent-tools`（新增 crate）、`crates/agent-testkit`（扩展）；`crates/agent-types`、`crates/agent-model` 仅作为依赖消费，本版本不改；`docs/modules/agent-system.md`、`docs/modules/agent-core.md` 同步修正，新增 `docs/modules/agent-tools.md`
- 需求来源：路线图 `v0.2.0` 条目（[`docs/版本管理.md`](../../版本管理.md)）、[`Agent 系统技术架构`](../../modules/agent-system.md) §5/§6/§8/§11、v0.1.0 遗留事项（本版本重新归属）、2026-07-26 用户会话结论（含 opencode 工具形态对比结论）

## 二、背景与目标

v0.1.0 已建立 Provider-neutral 规范类型（`agent-types`）、单次模型调用 SPI（`agent-model`）、OpenAI-compatible/DeepSeek Adapter 与确定性 testkit；`agent-core` 目前仅有空占位模块。本版本在其上建立 Agent 执行引擎：把"一次模型 Turn"组织成"带工具循环的一次完整 Agent 执行"。

本版本要形成的能力闭环：

1. 调用方（未来的 Runtime）以一份不可变执行规格 + 执行输入 + 已绑定的能力服务（模型、工具、Recorder、Authorizer）启动一次 Agent 执行，获得事件流、完成结果与取消控制。
2. 引擎在 Agent Loop 内显式驱动多轮工具状态机：模型 Turn → 组装完整 AssistantMessage → 记录确认 → 授权 → 工具执行 → 记录 ToolResult → 下一轮，直到完成、失败或取消。
3. 定义文件与 Shell 能力契约及其内置桥接工具；真实实现归 Runtime/Adapter，本版本以 fake 验证。
4. 全程不依赖 Tauri、数据库、真实文件系统和真实网络即可完成确定性验证。

成功标准为路线图完成门槛（fake model/tool 覆盖纯文本、单工具、多工具、多轮工具、失败和取消；工具副作用前完成规范 AssistantMessage 记录）加上本设计第七节验收标准。

## 三、非目标

- 不做 Runtime/桌面端接入：无 Tauri command、无持久化实现、无 UI。模型层 tracing 埋点、Runtime `DebugSink`、`DebugChannel::Sched` 调度通道从 v0.1.0 遗留归属调整为 Runtime 接入版本。
- 不定义 Memory/Safety/Guardrail 的任何类型。本版本原则：**`agent-core` 只实现 Agent Loop 必要的接口，记忆等二级业务功能不进入**。
- 不实现真实文件系统与 Shell 执行（仅契约 + fake 验证）；不实现权限策略与审批交互（仅预留授权接缝）。
- 不做上下文组装之外的上下文工程：压缩、token 预算裁剪、Provider overflow 恢复归 v0.3.0。
- 除 `agent-tools` 外不拆更多新 crate；不建立 Core 对外稳定 API 承诺（v0.7.0 才评估候选稳定）。

## 四、功能范围与使用路径

### 4.1 最小可执行 Agent（声明）

- **最小可执行 Agent 不含任何工具**：空工具集是合法的一等执行形态（纯模型循环，纯文本结束）。
- 工具集是装配输入：Core 内的文件/Shell 工具是 **内置工具贡献**（能力契约 + 桥接实现），是否进入某次执行完全由 Runtime 装配决定；引擎不预设任何工具必然存在。
- 引擎对工具来源（内置、Runtime 自定义、未来的记忆/MCP 工具）无差别对待；内置工具在引擎内没有任何特权。

### 4.2 执行契约

- `ExecutionSpec`：Runtime 编译完成的不可变执行事实源，仅含 `instructions`、`model`、`tools`（工具集快照，可为空）、`budget`（全 `Option`）四字段。不含 memory/safety 字段；`context`（上下文策略）经核查本版本无任何真实策略字段，v0.3.0 随上下文工程引入。"不可变"指：所有配置来源（默认、偏好、模板、会话覆盖）在执行开始前已由 Runtime 合并、校验、解析为最终答案，执行期间规格不再改变——Core 不再维护默认值与覆盖关系，配置中途修改只影响下一次执行。命名为 Spec（规格）而非 Plan，避免与后续 plan 模式的任务规划产物歧义。
- `ExecutionInput`：规范对话快照 + 用户输入（只含影响模型语义的输入）。
- `ExecutionContext`：控制面与已绑定能力——`cancellation`、`recorder`、`authorizer`。
- `AgentExecution`：启动返回的独立句柄，含事件流、完成结果与取消控制；不分配业务 ID，不携带 `RunId`/`SessionId`。

### 4.3 执行循环

状态机（语义层）：`Preparing → BuildingContext → StreamingModel →（无工具调用 → Completed）→ RecordingAssistantMessage → Authorizing → ExecutingTools → RecordingToolResults → BuildingContext …`，终态为 Completed / Failed / Cancelled 之一且唯一。

- **副作用前顺序**：完整 AssistantMessage 记录确认 → 授权决策 → 工具执行；ToolResult 记录确认后才进入下一轮。
- **Recorder 失败**：阻止后续一切副作用，受控终止。
- **取消**：模型流中、工具执行中、授权等待中均可取消；取消产生唯一受控终态。
- **预算**：引擎尊重显式 `max_steps` / `max_tool_calls`；`None` 表示不设限，Core 不注入隐藏上限。

### 4.4 工具能力

- 类型化 Tool：输入经 schema/类型校验后才进入实现；输出映射为规范 `ToolResult`；稳定错误以 `ToolResult{status: Error}` 回喂模型，循环继续。
- Registry 快照：执行期间模型可见工具集不变；未知工具名调用返回错误 `ToolResult`。
- Dispatcher：一次只处理一个规范 Tool Call；同批调用逐个过授权闸后执行；本版本顺序执行，不引入并行策略。

### 4.5 文件能力契约与内置工具

- 能力契约六个操作：`read` / `list` / `search` / `write` / `delete` / `edit`。
  - `edit` 为字符串精确替换语义：唯一匹配要求 + `replace_all` 选项；fuzzy 匹配等增强归 Runtime 实现版本。
  - `read` 支持 `offset`/`limit` 分页，输出带行号，结果带显式截断标记。
  - `search` 承载按名与按内容两类搜索语义；`rg` 仅可作为内部实现后端。
- 模型可见的内置桥接工具：`read`、`list` 各自独立；`search` 桥接为"按名查找 + 按内容搜索"两个工具；`write`/`edit`/`delete` 是否暴露给模型由 Runtime 装配决定，能力契约不预设。
- 工具描述文本承担行为纪律（工具分工与优先顺序），随 Registry 快照原样下发模型。
- 路径越界等安全约束不在能力契约中硬编码，统一经授权接缝处理（本版本恒 Allow）。

### 4.6 Shell 能力契约与内置工具

- Shell 为独立一等工具：输入为完整命令字符串、超时、工作目录；stdin 封闭，不支持后台任务。
- 流式 stdout/stderr 事件给 UI/审计；返回给模型的最终结果是一次性聚合输出，超限保留尾部并带截断标记。
- 执行可被取消打断；敏感环境变量默认不传递（真实实现归 Runtime/Adapter）。

### 4.7 权限预留（授权接缝）

- 状态机固定 `Authorizing` 位置：每个 tool call 独立过闸，逐 call `authorize → Allow 即执行`，再处理下一调用；Core 不设"整批放行才执行"的规则。
- 审批编排归 Runtime：串行询问、攒批询问或规则自动放行都是 Runtime authorizer 实现的选择；Core 在 authorize 时提供本轮批次上下文（同轮全部 tool call），批次审批交互由 Runtime 借此自行实现。
- 决策类型仅 `Allow` / `Deny{reason}`；**Deny 在授权闸处转换为错误 `ToolResult`**，对应工具不执行——回喂模型、驱动循环继续的唯一载体是 error `ToolResult`，对模型与循环不存在"被拒绝"类别；reason 文本是模型唯一可见信息，措辞归 Runtime。
- Authorizer 必须显式装配（本版本提供 `AllowAll` 实现）；Core 无隐藏默认放行策略。
- Ask（审批）不进入 Core 词汇表：审批由 Runtime 的 authorizer 实现内部挂起并代理到应用端；引擎侧的授权等待取消 race 已覆盖该场景。
- Recorder delta 顺序 + 事件流构成审计底座；决策落账（含"某调用是被拒绝的"）归 Runtime。

## 五、模块边界与契约影响

- `agent-tools`（新增 crate）：类型化 Tool SPI（含类型擦除）、Registry、Dispatcher、FileSystem/Shell 能力契约与内置桥接工具；只依赖 `agent-types`，不依赖 `agent-model` 与引擎。Runtime/Adapter 实现真实文件/Shell 能力时只需依赖本 crate。
- `agent-core`：执行契约、状态机、Recorder/Authorizer SPI、事件与预算；重组现有空占位模块（`agent.rs`/`model.rs`/`tool.rs`）；新增对 `agent-types`、`agent-model`、`agent-tools` 的依赖边（方向与既有依赖规则一致）。
- `agent-testkit`：扩展 fake tool、内存 Recorder、scripted authorizer；`ScriptedModelService` 支持多轮脚本。
- `agent-types` / `agent-model`：本版本不改；如实施中发现确需增补，须先回到本设计确认范围。
- `docs/modules/agent-system.md` 同步修正三处：
  1. 状态机 `Deny → Controlled Failure` 改为 Deny 回喂（记录 ToolResult 后回到 BuildingContext）。
  2. `AwaitingApproval` 移出 Core 状态机（审批等待发生在 Authorizing 内部，由 Runtime 代理）。
  3. §10.4 `ApprovalService` 归属从 Core 改为 Runtime 侧接口。
- `docs/modules/agent-core.md` 同步：最小可执行 Agent 声明、权限预留边界、引擎不内嵌工具实现；新增 `docs/modules/agent-tools.md`（Tool SPI、能力契约六方法（含 `edit`）、内置桥接工具边界），根 `AGENTS.md` 项目结构与依赖方向同步登记。
- 依赖方向保持 `desktop → assistant-runtime → agent-core → agent-tools → agent-types`；本版本不触动 `assistant-runtime`、`assistant-protocol`、`apps/desktop`。

## 六、关键取舍

1. **纯引擎版本边界**：Runtime 接线与 v0.1.0 遗留的可观测性事项改归后续版本，与完成门槛（fake 验证）保持一致。
2. **Core 只实现 loop 必要接口**：`ExecutionSpec` 裁剪为四字段，memory/safety 类型不提前定义；Core API 在 v0.7.0 前允许渐进扩展，不为假想需求提前抽象。
3. **权限只固定接缝**：位置、顺序、取消、Allow/Deny 语义 + fake 测试本版本定型；策略词汇、审批交互、决策落账全部推迟，Ask 由 Runtime 内部挂起代理，Core 永不感知。
4. **Deny 转换为错误结果而非终止执行**：回喂模型、驱动循环继续的唯一载体是 error ToolResult，模型可换路恢复；确需终止的场景由 v0.4.0 Guardrail 兜底。
5. **能力契约与模型工具分离**：能力层六方法正交完整（含 `delete`），模型侧粒度按模型工学桥接（`search` 拆两个工具；`delete` 暴露归装配）。
6. **`edit` 进入契约**：字符串替换是 coding agent 最高频的修改方式，契约阶段补齐成本极低；fuzzy 匹配、截断落盘、not-found 建议等实现增强留 Runtime 版本。
7. **最小可执行 Agent 无工具**：内置工具是可选贡献，非执行固有组成。
8. **拆出 `agent-tools` 独立 crate**：能力契约与工具 SPI 的稳定调用方（Runtime/Adapter 的真实文件/Shell 实现）独立于引擎存在，且 `agent-tools` 只需 `agent-types`、无需模型抽象，满足架构 §13 的拆 crate 条件；引擎只依赖 SPI/Registry/Dispatcher 机制，"内置工具无引擎内特权"由物理边界保证；recording、safety 等其余逻辑组件不拆。

## 七、验收标准

以下每条均可逐条核对；Harness 全部确定性、离线、无 sleep 竞态。

1. fake model/tool 覆盖：纯文本完成（空工具集）、单工具、多工具（同批）、多轮工具、模型失败、工具失败、取消（模型流中 / 工具执行中 / 授权等待中）。
2. 副作用前顺序断言：`recorder.begin_tool_exchange(AssistantMessage)` → `authorizer.authorize` → `tool.execute` → `recorder.complete_tool_exchange(batch)`；begin 失败时无任何工具执行，complete 失败时保留可恢复 pending exchange 且规范快照不暴露未配对消息。
3. Deny 路径：scripted authorizer 拒绝后，对应工具未执行、错误 `ToolResult` 回喂模型、循环继续。
4. 未知工具名调用返回错误 `ToolResult`；空工具集下模型幻觉 tool call 同样返回错误 `ToolResult`。
5. 工具输入 schema 校验失败不进入实现，错误回喂模型。
6. 多轮工具循环后 Tool Call/Result 配对与规范对话投影保持完整（含 reasoning / ProviderState 保真）；取消与预算超额时，未产生结果的调用由 Core 结算错误 `ToolResult`；工具取消必须在资源清理完成后收敛，Recorder pending exchange 不进入规范快照。
7. 预算语义：显式 `max_steps` / `max_tool_calls` 为副作用前硬边界（分别在模型调用前、dispatch 前预检），到达即受控终止；`None` 不限制。
8. 文件/Shell 能力契约以 fake 实现验证：`read` 分页/行号/截断标记、`edit` 唯一匹配语义、`search` 两类搜索、Shell 流式事件 + 尾部截断聚合 + 取消。
9. 事件流顺序可断言；普通观察事件可按背压策略丢弃，唯一终态始终可靠且最后交付；事件订阅断开不影响规范对话与执行结果。
10. `cargo fmt --all --check`、`cargo clippy --workspace --all-targets --all-features -- -D warnings`、`cargo test --workspace` 全部通过；默认测试集合完全离线、无凭据、无仓库外 I/O。

## 八、风险、兼容性与待确认项

- 技术方案阶段的开放项已收敛：类型化 Tool 使用泛型 + 类型擦除，JSON Schema
  使用 `schemars` 从输入类型派生，普通事件采用有界队列且唯一终态使用独立
  oneshot，`agent-core` 按执行职责拆分内部模块；`ScriptedModelService` 的既有
  顺序脚本能力可直接覆盖多轮调用。
- 风险：状态机与 Recorder/Authorizer 的顺序约束复杂——已用 scripted
  authorizer、两阶段 Recorder、共享调用日志与取消清理信号的确定性测试压制。
- 兼容性：`agent-core` 新增依赖边方向与既有规则一致；`assistant-protocol`、`assistant-runtime`、`apps/desktop` 不受影响。
- 架构与模块文档已同步两阶段 Recorder、逐 call 授权、预算预检、取消结算和
  可靠终态语义；当前无待确认的设计开放项。
