## 四、分模块实现方案

### 4.1 `agent-tools`

**Tool SPI（`tool.rs`）**

```rust
pub trait Tool: Send + Sync {
    type Input: DeserializeOwned + JsonSchema;
    type Output: Serialize;
    fn definition(&self) -> ToolDefinition;
    fn execute<'a>(
        &'a self,
        input: Self::Input,
        context: ToolContext,
    ) -> Pin<Box<dyn Future<Output = Result<Self::Output, ToolError>> + Send + 'a>>;
}
```

- 对象安全擦除：`ErasedTool::execute_json(&self, arguments: Value, context) -> BoxFuture<ToolResult>`，内部步骤固定为 **serde 反序列化校验（失败即"类型校验失败"，错误模型可读）→ 类型化 execute → 序列化输出 → `ToolResult`**；注册表持有 `Arc<dyn ErasedTool>`。
- `input_schema` 由 `schemars` 派生产生，与 `Input` 类型恒同步。**不引入 `jsonschema` 校验器 crate**：serde 反序列化即类型校验（`deny_unknown_fields` 等由类型作者自决）；完整 JSON Schema 约束校验（pattern/minimum 等）待真实需求再评估。
- `ToolContext`：`cancellation: CancellationToken` + `ToolOutputSink`（流式输出回调，引擎桥接为 `AgentEvent::ToolOutput`）。
- `ToolError`：`InvalidInput { message }`（校验/参数失败）/ `Execution { message }`（执行失败）——均转为错误 `ToolResult` 回喂模型；**取消不是 ToolError**，由 `ToolContext.cancellation` 与引擎观察处理。

**Registry 与 Dispatcher（`registry.rs`、`dispatch.rs`）**

- `ToolRegistry`（构建期注册，重名拒绝；定义注册时冻结）→ `ToolSetSnapshot`（不可变：`Vec<ToolDefinition>` + 名称索引），随 `ExecutionSpec` 进入执行，执行期间不变。
- `Dispatcher::dispatch(&snapshot, call: &ToolCall, context) -> ToolResult`：一次只处理一个规范 Tool Call；未知名 → 错误 `ToolResult`；其余失败路径见上。Dispatcher 不负责模型请求与继续循环。

**文件能力契约（`capability/fs.rs`）**

- `FileSystemTool` trait（boxed futures）：`read`/`list`/`search`/`write`/`delete`/`edit`。
- 请求/响应要点：
  - `ReadFileRequest{path, offset, limit}` → `ReadFileResult{content, truncated}`；**`content` 带 1 起始行号是能力契约语义**（桥接零格式化，fake 与真实实现同构）。
  - `SearchFilesRequest{query, path, kind: ByName | ByContent, max_results}` → 匹配列表；`rg` 仅作内部后端。
  - `EditFileRequest{path, old_string, new_string, replace_all}`：精确替换 + 唯一匹配；`old == new`、文件不存在、多处匹配均为稳定错误。
  - `FileToolError`：`NotFound` / `InvalidInput` / `Io { message }` 等稳定分类。
- 路径越界、审批等安全约束**不在契约内**（经授权接缝处理）。

**Shell 能力契约（`capability/shell.rs`）**

- `ShellTool::exec(request, sink, cancellation) -> ShellOutcome`：`ShellRequest{command, workdir, timeout}`；`ShellOutputSink` 按 chunk 流式回调（stdout/stderr 分离）；`ShellOutcome{exit_code, timed_out, aggregated}`，`aggregated` 为超限尾部保留 + 截断标记。
- 契约注释固化义务：stdin 封闭、无后台任务、完整命令原样进审计、敏感环境变量默认不传递、进程树清理（实现侧，归 Runtime/Adapter）。

**内置桥接工具（`builtin/`）**

- 八个模型可见工具：`read_file`、`list_directory`、`find_files`（按名）、`search_content`（按内容）、`write_file`、`edit_file`、`delete_file`、`shell`——由能力句柄构造（`FsReadTool::new(Arc<dyn FileSystemTool>)` 等），**是否注册由 Runtime 装配决定**。
- 描述文本承担行为纪律：局部修改优先 `edit_file`、文件/搜索/读操作不要用 `shell`、读大文件用分页等；随快照原样下发。
- 截断上限为桥接构造参数（read 默认行数、search 默认条数、shell 聚合字节数），Runtime 装配时给定。

### 4.2 `agent-core`

**执行契约（`spec.rs`、`input.rs`、`context.rs`）**

```rust
pub struct ExecutionSpec {
    pub instructions: Vec<String>,        // 直接映射 ModelRequest.system
    pub model: Arc<dyn ModelService>,     // 已绑定服务实例（构造期含 endpoint/credential/model）
    pub tools: ToolSetSnapshot,           // 可为空
    pub budget: ExecutionBudget,          // 全 Option
}
pub struct ExecutionBudget {
    pub max_steps: Option<u32>,           // 模型 Turn 数上限（模型调用前预检）
    pub max_tool_calls: Option<u32>,      // 实际 dispatch 的工具调用数上限（dispatch 前预检）
}
```

- 本版本为四字段（无 `context`，2026-07-26 已确认）：`context` 经核查在本版本**没有任何真实策略字段**——BuildingContext 是纯机械组装（instructions→system、投影+新输入→conversation、快照→tools），token 预算/裁剪/压缩全是 v0.3.0；工具输出截断由桥接工具负责，不需引擎策略。按"不为假想需求提前抽象"，v0.3.0 再引入 `context`。
- 命名 `ExecutionSpec`（规格）而非 Plan（2026-07-27 定名）：避免与后续 plan 模式的任务规划产物产生歧义。
- `ExecutionInput`：`{ conversation: ConversationSnapshot, user_input: UserMessage }`。
- `ExecutionContext`：`{ cancellation: CancellationToken, recorder: Arc<dyn ExecutionRecorder>, authorizer: Arc<dyn ToolAuthorizer> }`——**必传字段，类型层面杜绝"无授权闸"的隐藏默认**。

**Recorder（`recorder.rs`）**

- Recorder 使用两阶段 tool exchange，避免 Assistant 已落账而 ToolResult 中途失败时把未配对消息暴露为规范对话：
  - `begin_tool_exchange(assistant) -> BoxFuture<Result<ExchangeReceipt, RecordError>>`：工具副作用前持久化 pending exchange；
  - `complete_tool_exchange(receipt, results: Vec<ToolMessage>) -> BoxFuture<Result<(), RecordError>>`：整批结果原子落账并把 exchange 转为 completed。
- `ExchangeReceipt` 是 Recorder 生成并返回 Core 的不透明 exchange 标识；Core 只原样回传，不感知 Run/Session/事务。
- pending exchange 是恢复事实而不是规范对话：Runtime 构建 `ConversationSnapshot` 时只投影 completed exchange；恢复 pending 时为未完成调用生成 interrupted/unknown 错误结果后原子完成，任何快照都不得暴露未配对 Tool Call。
- `ConversationDelta` 保留为 completed exchange 的规范投影视图（Assistant + 有序 ToolMessage）；用户输入仍由 Runtime 自行落账。
- `RecordError{message}`：begin 失败阻止后续副作用；complete 失败受控终止并保留可恢复 pending exchange，不形成部分 ToolResult。

**Authorizer（`authorizer.rs`）**

- `ToolAuthorizer::authorize(call: &ToolCall, batch: &[ToolCall]) -> BoxFuture<ToolAuthorization>`：`batch` 为本轮全部 tool call（含 `call` 自身）。Core 只保证逐 call 独立过闸；审批编排（串行询问、攒批询问、规则自动放行）由 Runtime 实现借批次上下文自行完成。
- `ToolAuthorization`：`Allow` / `Deny { reason: String }`。
- `AllowAllAuthorizer`：显式装配用实现；`Deny` 在授权闸处转换为错误 `ToolResult`（reason 是模型唯一可见信息，措辞归 Runtime），对应工具不执行，循环继续——对模型与循环不存在"被拒绝"类别。

**事件（`event.rs`）**

- `AgentEvent`：`ExecutionStarted` / `StepStarted { step }` / `TextDelta { id, delta }` / `ReasoningDelta { id, delta }` / `ToolProposed { call }` / `ToolStarted { call_id }` / `ToolOutput { call_id, channel: Stdout | Stderr, chunk }` / `ToolCompleted { call_id, status }` / `ExecutionCompleted { message, dropped_events }` / `ExecutionFailed { error, dropped_events }` / `ExecutionCancelled { dropped_events }`。
- **背压策略（满足规范 §五）**：普通观察事件使用 bounded `tokio::sync::mpsc`（容量常量 256）+ `try_send`，满了丢弃并计数；唯一终态使用独立 oneshot，排在已入队普通事件之后可靠交付，不与普通队列竞争容量。三种终态都携带 `dropped_events`。订阅断开不阻塞执行。

**执行句柄与状态机（`execution.rs`、`engine.rs`）**

- `AgentExecution { events: AgentEventStream, completion: CompletionFuture, control: ExecutionControl }`；`start(spec, input, context)` 后由单一 tokio 任务驱动状态机，无后台辅助任务。
- 循环：
  1. 回到循环起点先预检 `max_steps`（到达即 `ExecutionFailed{BudgetExceeded}`）；组装 `ModelRequest`（instructions→system、投影 + `user_input`→conversation、快照→tools、`ToolChoice::Auto`、默认 generation）；
  2. `model.stream`（`ModelCallContext` 携取消令牌），出流套 `LifecycleValidator`；delta 转发为事件；
  3. `TurnFinished` → 无 tool calls → `ExecutionCompleted`；
  4. 有 tool calls → `recorder.begin_tool_exchange(Assistant)`（Err → `ExecutionFailed{Record}`）→ **逐 call 独立过闸**：`authorizer.authorize(call, batch)`（`tokio::select!` 与取消 race）→ Allow → dispatch 前预检 `max_tool_calls`（到达 → 本调用及批次内剩余调用结算错误 `ToolResult`，整批 complete 后受控终止 `BudgetExceeded`）→ `dispatch`（流式输出桥接为 `ToolOutput` 事件）；Deny → 转换为错误 `ToolResult`，对应工具不执行；整批结算完聚合为 `Vec<ToolMessage>` → `recorder.complete_tool_exchange` 原子完成 → step + 1 → 回到 1；
  5. 取消：模型流内由 `ModelCallContext`、授权等待由 race、工具执行由 `ToolContext.cancellation`；工具取消后 Engine 继续等待 dispatch future 完成资源清理，不直接 drop；收敛为 `ExecutionCancelled` 唯一终态**之前**，Core 为批次内尚未产生结果的调用补记 interrupted 错误 `ToolResult` 并原子完成 pending exchange。complete 失败收敛为 `ExecutionFailed{Record}`，pending exchange 留给 Runtime 恢复。
- 对话投影：执行内维护 `Vec<ConversationMessage>`；`ToolMessage.id` 由执行内确定性序号生成（如 `toolmsg_{n}`）——无 uuid 依赖，测试可断言。
- `ExecutionError`：`Model(ModelError)` / `Record(RecordError)` / `BudgetExceeded { kind, limit }`；工具失败与 Deny **不是**执行错误（error `ToolResult` 回喂模型）；预算是副作用前硬边界：`max_steps` 在模型调用前预检、`max_tool_calls` 在每次 dispatch 前预检，到达即受控终止（`ExecutionFailed{BudgetExceeded}`），未执行调用先结算错误 `ToolResult` 保证配对。

### 4.3 `agent-testkit`

- `ScriptedTool`：脚本化成功/失败结果、调用记录、取消与清理观察；与 recorder/authorizer 共享顺序日志以断言 `begin → authorize → execute/cleanup → complete` 严格顺序。
- `InMemoryRecorder`：pending/completed exchange、completed delta 投影、可注入“第 N 次 begin/complete 调用失败”。
- `ScriptedAuthorizer`：脚本化决策序列、调用记录、可挂起等待（验证授权等待中的取消 race）。
- `FakeFileSystemTool`：内存文件树，完整支持六方法契约语义（read 分页/行号/截断、edit 唯一匹配、search 两类）。
- `FakeShellTool`：脚本化 stdout/stderr chunk 流 + 退出码 + 超时/取消行为。
- `ScriptedModelService` **不改动**（顺序脚本 + `take_requests` 已覆盖多轮编排与断言）。

## 七、风险、兼容与排除项

- **已确认偏差与定名**：`ExecutionSpec` 不含 `context` 字段（2026-07-26 确认，v0.3.0 引入）；`ExecutionPlan` 更名 `ExecutionSpec`（2026-07-27，避免与 plan 模式歧义）；授权语义定为逐 call 独立过闸、审批编排归 Runtime（2026-07-27，见 4.2）。

- 事件背压丢弃：语义上可丢弃（非事实源 + 快照恢复 + 终态计数），Runtime 接入版本如需更强保证再评估。
- 兼容：`agent-types`/`agent-model` 公共 API 不变；如实施中发现确需增补，先回功能设计确认范围。
- 排除项：并行工具执行、真实 fs/shell 实现、`jsonschema` 完整校验器、tracing 埋点、Runtime/桌面端接入。
