本文承接实现级内容：配置字段、校验规则、内部状态、协议 DTO、装配链、并发顺序、

## 二、现状核查

### 2.1 当前构造链

实际代码的启动和执行链如下：

```text
runtime-host main
→ dotenvy::dotenv
→ ServeConfig 从 CLI/环境变量解析唯一 DeepSeek 目标
→ HostResources 读取 API Key 并构造唯一 ModelService
→ HostAgentFactory 冻结 ModelService / System Prompt / Context / Tools
→ AssistantRuntime::create_session 为 Session 构造一个 Agent
→ SessionController 在整个 Session 生命周期持有 Arc<Agent>
```

对应代码事实：

- `crates/assistant-runtime/src/config.rs` 的 `RuntimeConfig` 只有事件通道容量。
- `crates/assistant-runtime/src/factory.rs` 的 `SessionAgentFactory` 只能无参数构造冻结 Agent。
- `crates/assistant-runtime/src/session.rs` 的 `SessionController` 持有 `Arc<Agent>`，尚无 model key
  和 Session 的 System Prompt 字段。
- `AssistantRuntime::start_run` 当前先向 Journal 写入 UserMessage，再调用 Session Agent。
- `apps/runtime-host/src/config.rs` 支持 `--base-url`、`--model`、`--context-window`、
  `--api-key-env` 和对应 DeepSeek 环境变量。
- `apps/runtime-host/src/main.rs` 调用 `dotenvy::dotenv()`；`resources.rs` 缺少 credential
  时会在 Runtime 建立前失败。
- `assistant-protocol` 当前 `PROTOCOL_VERSION = 1`，只有 Session/Run/关闭命令。

### 2.2 已有可复用契约

- `agent-model::GenerationConfig` 已支持 temperature、top-p、最大输出 token 和 stop。
- `agent-core::ExecutionBudget` 已支持最大 Model Step 数和最大工具调用数；两者缺省均表示
  不注入隐藏上限。
- `agent-model::ModelRetryPolicy` 和 `RetryingModelService` 已实现建流前有限重试。
- `agent-provider-openai-compatible::TransportTimeouts` 已实现连接与整体请求超时。
- `AgentBuilder` 已能从 ModelService、System Prompt、ContextWindowEvaluator、Tools、
  `ModelRequestConfig` 和 `ExecutionBudget` 构造冻结 Agent。
- `Profile::deepseek()` 已实现 thinking-enabled 方言和工具回放约束；
  `Profile::openai_compatible(...)` 已实现标准 Chat Completions 方言，并保留调用方传入的
  实际 Provider 标识。

因此本版本不建立新的 Model Request、Retry、Transport 或 Budget 参数体系，只增加应用
配置形式、运行时所有权和到现有契约的编译。

## 三、目标架构与依赖

### 3.1 权威状态与注入边界

```text
本地 config.toml
    │
    ▼
Host RuntimeConfigSource ──原始字节/文件安全结果──▶ assistant-runtime
                                                               │
                                          解析、校验、快照、诊断、默认解析
                                                               │
Session.model_key + Session.system_prompt                      │
                  │                                            │
                  └── Run 前编译 ◀──当前 ConfigSnapshot ───────┘
                                   │
                        Host ModelServiceFactory
                                   │
                  OpenAI-compatible Adapter + Retry wrapper
                                   │
                  共享 ContextWindowEvaluator + AgentBuilder
                                   │
                           冻结 Run Agent
```

所有权分配：

| 对象 | 权威所有者 | 说明 |
| --- | --- | --- |
| Runtime Home 路径、文件读取和 Unix 权限检查 | `runtime-host` | 平台与文件系统适配，不保存第二份配置状态 |
| schema、配置快照、默认模型、诊断与 reload | `assistant-runtime` | Runtime 是业务权威层 |
| Provider Profile 和具体 ModelService 构造 | `runtime-host` | 通过工厂注入，Runtime 不依赖具体 Adapter |
| Session 的 model key、System Prompt、Conversation 和 Run | `assistant-runtime` | System Prompt 与 model key 分别冻结 |
| 单次 Run 的 `ExecutionSpec` | Run 开始前由 `assistant-runtime` 编译 | Core 只消费编译结果 |
| 跨进程脱敏投影 | `assistant-protocol` | 不传输 raw config 和 credential |

`assistant-runtime` 新增两个真实可替换边界：

- `RuntimeConfigSource`：异步读取配置文档及文件安全结果。生产实现在 Host，测试实现使用
  内存文档；Runtime 不直接访问用户真实目录。
- `ModelServiceFactory`：从已校验的模型目标与 Runtime transport 策略构造
  `Arc<dyn ModelService>`。生产实现位于 Host，离线测试使用 fake。

System Prompt 来源保留为独立的 `SystemPromptFactory` 注入边界；本版本 Host 实现只生成当前
固定 System Prompt，但 Runtime 必须在创建 Session 时调用并保存结果，不在每个 Run 重新渲染。

### 3.2 依赖调整

- `assistant-runtime` 将 `agent-context`、`agent-model`、`serde` 和 TOML/URL 解析库调整为
  直接依赖：前两者用于 Run 编译和 Retry 包装，后两者只用于应用配置解析与静态校验。
- `runtime-host` 保留具体 OpenAI-compatible Adapter 依赖，新增用户主目录解析
  依赖，并为 Tokio 开启文件 I/O 所需 feature。
- `runtime-host` 移除生产路径的 `dotenvy` 依赖和调用；Provider 独立 example/真实测试
  仍可在 Adapter crate 自己的开发入口使用 `.env`，不属于产品 Runtime 凭据来源。
- `assistant-protocol` 仍只依赖 `serde` 和 `thiserror`，不引入 TOML、URL、Provider
  或 Runtime 实现类型。
- `TransportTimeouts` 不上提到 provider-neutral crate。Runtime 内部使用自己的通信策略值，
  Host factory 在 Adapter 边界编译为 `TransportTimeouts`，避免下层 Provider 类型反向泄漏。

新增第三方依赖的精确版本在开发计划的首个依赖里程碑中经过实际 `cargo add`/
Cargo.lock 与许可证核查后固定；不在设计文档猜测版本号。

## 四、配置与 Runtime Home

### 4.1 路径与运行参数

默认 Runtime Home 使用当前用户主目录下单一、可见的数据根。[Hermes Agent 配置文档](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/configuration.md)
使用 `HERMES_HOME`（默认 `~/.hermes`）集中配置和运行数据；[OpenCode 配置文档](https://github.com/anomalyco/opencode/blob/dev/packages/web/src/content/docs/config.mdx)
则按 XDG 将全局配置放在 `~/.config/opencode`，并将运行状态分开放置。本项目当前只有一个
Runtime Home 权威根，因此采用前一种单根目录形态，但保留自己的目录名：

```text
~/.ez-assistant/
├── config.toml
└── run/
    ├── runtime.sock
    └── runtime.lock
```

规则：

- Host 使用当前用户主目录把 `~/.ez-assistant` 解析为绝对路径；无法取得用户主目录时启动
  失败，并提示使用显式 `--runtime-home`。业务代码不保存或传播未展开的 `~`。
- `serve --runtime-home <ABSOLUTE_PATH>` 为测试、开发和未来桌面启动器提供整体覆盖。
- `serve --socket <ABSOLUTE_PATH>` 保留为 Unix Socket 单独覆盖，也用于默认路径超过 Unix
  domain socket `sun_path` 长度时的可操作恢复。Host 在 bind 前显式检查字节长度。
- 私有 Demo 客户端只需 `--runtime-home`/显式 `--socket`，不接收任何模型或 credential
  参数。
- 移除产品 `serve` 的 `--base-url`、`--model`、`--context-window`、`--api-key-env`
  以及 `DEEPSEEK_*` 回退。`--event-capacity` 保留为 Runtime 建立前生效的非敏感 bootstrap
  参数，默认值继续为 `256`；它不进入可 reload 配置。
- Runtime Home 无法创建、无法以安全权限使用，或 endpoint/lock 无法建立时，Host
  返回进程级启动错误。配置文件自身的缺失或错误不属于该类失败。
- 早期开发阶段曾使用 macOS Application Support 路径；当前版本尚未发布，不建立旧路径回退或
  双配置源。已有本地开发文件由开发者显式复制到新目录，旧目录不由程序自动删除。

### 4.2 Unix/macOS 文件安全

- Host 在初始化时创建或收紧 Runtime Home 和 `run/` 为 `0700`；权限修改通过已打开的目录
  句柄完成，无法收紧、路径是符号链接或不是目录时，在绑定 endpoint 前失败。
- Runtime 不自动创建空 `config.toml`，也不修改配置内容。存在且是普通文件时，Host 在读取
  内容前通过已打开的文件句柄将 mode 收紧为 `0600`。`0600` 表示当前用户可读写，不是只读。
- 配置文件无法收紧权限、是符号链接、不是普通文件或超过 1 MiB 时，Host 不向 Runtime
  交付文件内容；Runtime 记录脱敏的配置源安全错误并 fail-closed 所有新 Run。
- 任何错误都不输出原始文本、API Key、包含 userinfo/query 的 endpoint 或 TOML 解析片段。

本文明确将 `config.toml` 分类为 **显式承载 secret 的用户私有配置**，不是普通可共享
配置。`docs/specs/Rust编程规范.md` 已同步为：禁止凭据进入普通、可共享或可导出配置；
只有经版本设计明确分类的用户私有敏感文件可承载，且必须满足权限、脱敏和禁止
协议/日志/Shell 泄漏约束。

### 4.3 `config.toml` schema version 1

完整字段形式：

```toml
schema_version = 1
default_model = "deepseek-chat"

[runtime.model_transport]
connect_timeout_ms = 10000
request_timeout_ms = 300000

# 整个表缺失时不做隐藏重试
[runtime.model_retry]
retry_on = ["connection", "timeout", "rate_limited", "unavailable"]
delays_ms = [500, 1000, 2000]
max_retry_after_ms = 10000

[agent.defaults.generation]
max_output_tokens = 4096
stop = []
# 标准兼容 Profile 需要时可增加；DeepSeek thinking Profile 不支持这两项
# temperature = 0.7
# top_p = 0.9

[agent.defaults.execution_limits]
max_steps = 40
max_tool_calls = 100

[models.deepseek-chat]
display_name = "DeepSeek Chat"
protocol = "chat_completions"
provider = "deepseek"
endpoint = "https://api.deepseek.com"
model = "deepseek-chat"
api_key = "replace-with-user-secret"
context_window_tokens = 128000
max_output_tokens = 8192

[models.local-qwen]
display_name = "Local Qwen"
protocol = "chat_completions"
provider = "local"
endpoint = "http://127.0.0.1:8080/v1"
model = "qwen-local"
api_key = "replace-with-user-secret"
context_window_tokens = 32768
max_output_tokens = 4096
```

表和字段规则：

| 位置 | 必填/缺省 | 校验与编译 |
| --- | --- | --- |
| `schema_version` | 必填 | 只接受整数 `1`；其他值为顶层不兼容 |
| `default_model` | 必填 | 必须是合法 model key；可指向当前无效模型，但此时无法默认创建 Session |
| transport 两个超时 | 分别缺省 `10000`/`300000` ms | 正整数，request 不小于 connect；Host 映射为 `TransportTimeouts` |
| `runtime.model_retry` | 整表可缺失 | 缺失表示无重试；存在时 `retry_on` 和 `delays_ms` 均不得为空，枚举直接映射 `ModelRetryReason`，毫秒值不溢出 `Duration` |
| generation | 各字段可缺失 | 缺失保持 Provider 默认；temperature 必须有限且非负，top-p 在 `(0, 1]`，最大输出为正 `u32`，stop 元素不得为空 |
| execution limits | 两字段可缺失 | 缺失表示不注入隐藏上限；存在时为正 `u32` |
| `models.<key>` | 至少可解析为空 map | key 是用户输入的稳定业务 key，形式为 `[A-Za-z0-9][A-Za-z0-9_-]{0,63}`；不另存内部 ID |
| `display_name` | 可缺失 | 缺失时安全投影使用 model key；存在时 trim 后不得为空 |
| `protocol` | 必填 | version 1 只接受 `chat_completions`；它表达 wire API 契约，不表达供应商 |
| `provider` | 必填 | 实际供应商 key，形式为 `[a-z0-9][a-z0-9_-]{0,63}`；不使用 `generic` 代指方言 |
| `endpoint` | 必填 | 绝对且可追加 path，禁止 userinfo、query 和 fragment；既有 Adapter 构造时再校验一次 |
| `model` | 必填 | 不修改原值，trim 后不得为空 |
| `api_key` | 必填 | 不修改原值，不得为空或带首尾空白；不参与跨模型校验 |
| 模型两个 token 上限 | 必填 | context window 为正 `u64`，输出上限为正 `u32` 且不大于 context window |

未知顶层表、未知字段和重复字段都显式失败，不静默忽略拼写错误。为了保留
“单模型无效不拖垮其他模型”语义，解析分两层完成：顶层 serde 类型使用
`deny_unknown_fields`，但 `models` 先保留为按 key 的 TOML value map；之后再对每个 value
单独反序列化为使用 `deny_unknown_fields` 的 RawModelConfig。单模型的类型/未知字段错误
因此只形成该 key 的 issue；TOML 语法、重复字段和全局表错误仍是顶层 Invalid。数字范围与
跨字段关系在第二阶段语义编译中校验。

schema 演进以“新程序读取旧配置时能否保持原有含义和默认行为”为升版标准：兼容性新增继续
沿用当前 schema version；只有字段结构、类型、含义或旧默认行为发生破坏性变化时才提升版本。
发生升版后，在配置编译入口增加历史 RawConfig 到当前统一配置的内存兼容层，Runtime 后续只
消费当前 `ResolvedConfig`，不维护多套执行语义。兼容读取不自动改写用户文件；具体支持哪些
历史版本、无法无损转换时的诊断，以及是否在用户通过桌面模型管理界面显式编辑并保存时原子
覆盖为最新格式，留到 `v0.14.0` Runtime CRUD、冲突处理和 UI 保存流程中共同决定。v0.9.0
只有 schema version 1，不提前实现空迁移框架。

### 4.4 Provider、protocol 与内部 Profile

- 配置只暴露供应商 `provider` 与 wire 契约 `protocol`，不暴露独立 `profile` 字段。
  `provider` 原值进入 `ProviderId`，用于模型身份、Provider Options 命名空间和后续装配；
  `protocol = "chat_completions"` 选择 OpenAI-compatible Adapter。
- Runtime 按 provider 推导内部 Profile。`deepseek` 映射 `Profile::deepseek()`；其他合法
  provider key 映射 `Profile::openai_compatible(ProviderId)` 的标准兼容 Profile。该默认规则
  允许用户如实填写 `local`、`openrouter` 等供应商，而不是把方言伪装成 `generic` provider。
- DeepSeek Run 业务编译器固定使用 `ToolChoice::Auto`，
  并注入 `deepseek` 命名空间的 `thinking.type = enabled`；不向用户暴露 reasoning
  enabled 或 tool choice 静态字段。
- `deepseek` Profile 不支持 temperature、top-p 和规范 reasoning effort。如果 Agent 全局
  generation 显式设置 temperature/top-p，该 DeepSeek 模型形成“组合无效”诊断，
  不静默丢弃字段；其他有效模型仍可使用。
- 标准兼容 Profile 使用 `ToolChoice::Auto`，reasoning 为 `None`。用户不能经 provider
  options 穿透任意 wire 字段。
- v0.9 schema 不暴露 reasoning effort 和 provider options。原因不是下层契约缺失，而是当前
  Profile 没有可由用户静态通用配置的安全交集：DeepSeek 的 thinking 由业务流程强制，
  且不支持规范 effort；标准兼容 Profile 不声明 reasoning。

每个模型的有效输出上限在配置编译时计算：

```text
effective_max_output_tokens =
    min(model.max_output_tokens,
        agent.defaults.generation.max_output_tokens
            .unwrap_or(model.max_output_tokens))
```

计算结果写入本次 Run 的 `GenerationConfig.max_output_tokens`；模型 context window 原值写入
ModelService 并用于本次 Run 的 `ContextWindowEvaluator`。两者不与 `ExecutionBudget`
相互推导。ContextWindowEvaluator 的压缩阈值本版本继续沿用现有 Host 常量 `0.8`，
不新增用户字段。

## 五、配置状态与编译流程

### 5.1 内部表示

`assistant-runtime` 内部按三层表示配置：

1. `RawConfig`：只用于 serde/TOML 反序列化，不作为运行时业务类型。
2. `ResolvedConfig`：已编译的 Runtime/Agent 全局策略、默认 model key、有效模型 map
   和逐模型诊断。
3. `ConfigProjection`：只包含应用协议允许展示的脱敏值。

API Key 使用不实现 `Serialize` 且 `Debug` 固定输出 `<redacted>` 的私有 secret wrapper。
Raw/Resolved 类型不整体 derive `Debug` 或 `Serialize`，不把内部配置直接投影到协议。本版本
不承诺进程内存的硬件级立即清零；只限制 secret 的拷贝边界并在快照/Run 释放后正常 drop。

Runtime 保存：

```text
ConfigRegistry {
  state: Missing | Invalid | Degraded | Ready,
  active: Option<Arc<ResolvedConfig>>,
  issues: safe issues,
}
```

- `Missing`：文件不存在，`active = None`。
- `Invalid`：配置源不安全/不可读、TOML 无法解析、schema version 不支持或顶层结构
  无法解释，`active = None`。
- `Degraded`：已形成新 `ResolvedConfig`，但存在无效模型、无有效模型或默认模型不可用。
  显式选择其他有效 key 仍可工作。
- `Ready`：已形成新 `ResolvedConfig`，默认模型可用，且没有逐模型错误。

配置 issue 使用稳定 code，至少覆盖配置源不安全、读取失败、语法错误、版本不支持、
未知字段、无效 key、必填值缺失、未知 protocol、无效 provider key、无效 endpoint、凭据缺失、上限无效、
策略无效、Profile 组合不支持、默认 key 缺失/无效。issue 只保存安全 message 和可选
model key，不保存原始 TOML 片段。

### 5.2 启动与 reload

启动顺序：

```text
解析 Runtime Home 和 endpoint
→ 安全建立目录/lock/socket
→ 构造不依赖有效模型的 AssistantRuntime
→ 调用 RuntimeConfigSource 进行首次 load
→ 将结果编译并交换到 ConfigRegistry
→ Host 进入客户端可连接状态
```

reload 使用与首次 load 相同的唯一编译函数：

1. 在不持有 `ConfigRegistry` 锁的情况下异步读取文件。
2. 解析为 RawConfig，编译全局策略和逐模型结果。
3. 一次短 `RwLock` 写入原子替换 registry，不在锁内 `.await`。
4. 顶层失败时将 `active` 替换为 `None`，不保留旧快照供新 Run 使用。
5. 已经取得旧 `Arc<ResolvedConfig>` 并构造完服务的活动 Run 继续执行；registry 不主动
   取消它们。

Runtime 不保存配置 revision，不向文件写回任何值。reload 同时发生时由 Runtime 内部的
单个 reload gate 串行，避免较早的读取结果覆盖较晚的 reload。

## 六、Session、Run 与连接验证

### 6.1 SessionController 调整

`SessionController` 从“持有长期 Agent”调整为持有：

- `SessionId` 与 title；
- `ModelKey`；
- 已渲染的 `SystemPromptSnapshot`；
- 现有 Journal、Run map、active run 和 faulted 状态。

删除 Session 字段 `Arc<Agent>` 和现有无参数 `SessionAgentFactory`。每个 Run 的 Agent 由 Runtime
在开始前使用 `AgentBuilder` 构造。Session 摘要增加 model key，便于客户端和诊断展示当前
选择；不增加模型配置副本。

### 6.2 CreateSession

```text
检查 Runtime Running
→ 取得当前 ConfigSnapshot
→ 解析显式 model key 或 default_model
→ 校验 key 当前有效
→ SystemPromptFactory 渲染并冻结 System Prompt
→ 创建只持有 key + System Prompt + 空 Journal 的 Session
```

配置 reload 可以在解析 key 与 Session 入库之间发生。创建使用已获取的同一份
`Arc<ResolvedConfig>` 完成选择；因此成功的 Session 存储的 key 必然在创建时快照中有效。
后续是否仍有效由每个 Run 重新解析。

### 6.3 StartRun 顺序与并发

`start_run` 必须保证所有配置/模型编译失败发生在 UserMessage 写入前：

```text
1. 读 Runtime lifecycle，校验用户文本
2. 取 Session，快速检查当前空闲
3. 取得当前 Arc<ResolvedConfig>，用 Session.model_key 解析模型
4. 编译 Runtime transport/retry、Agent generation/budget 与业务 tool/reasoning 决策
5. ModelServiceFactory 构造基础服务；Runtime 按需包装 RetryingModelService
6. 复用 Runtime 按现有阈值构造的 Evaluator 与 Session 的 System Prompt/Tools 构造 Agent；
   context window 由本次 ModelService 报告给 Evaluator
7. 重新锁定 Session 并校验仍空闲
8. 原子写入 UserMessage、RunRecord 和 ActiveRun
9. 启动 AgentExecution 并交给现有 supervisor
```

第 2 步是避免无意义构造，第 7 步是真正的同 Session 串行门禁。两个并发请求可能都完成
无副作用的 Agent 构造，但只有一个能在第 7–8 步登记 Run；失败的请求不写入消息。
任何锁都不跨文件 I/O、模型构造、网络或 `.await`。

Run 在第 3 步取得配置快照，并在第 5–6 步将 endpoint、API Key、model、Profile、上限和
请求策略冻结进 Agent/ModelService。之后 reload 不会改变该 Run。

### 6.4 连接验证

连接验证直接使用 `ModelService`，不构造 Agent、Session、RunRecord 或 Journal：

```text
解析当前 model key
→ 使用与 Run 相同的 Profile/transport/retry 编译链构造 ModelService
→ 构造固定最小 ModelRequest
→ 完整消费流直到唯一终态
→ 投影成结构化脱敏结果
```

最小请求约定：

- 空 `SystemPromptSnapshot`，只含固定 UserMessage `Reply with OK.`；
- 空工具定义，`ToolChoice::Auto`；DeepSeek 仍使用业务编译器注入的 thinking-enabled
  Provider Options；标准兼容 Profile 的 reasoning 为 `None`；
- 不使用 Agent 全局 temperature/top-p/stop，避免验证用的可选采样配置影响连接判断；
  最大输出使用模型硬上限与固定小值的较小者。
- 只有得到符合 `LifecycleValidator` 契约的 `TurnFinished` 才成功；不要求回复文本必须等于
  `OK`，不保存响应正文。

验证失败映射为 `configuration`、`connection`、`timeout`、`authentication`、
`model_unavailable`、`rate_limited`、`service_unavailable`、`provider_rejected` 或 `protocol`。
其中已经过本地编码校验的固定请求如被 Provider 以 400/404 拒绝，归为 `model_unavailable`；
其他未能稳定分类的 4xx 保留为 `provider_rejected`，不根据原始 body 字符串猜测。

连接验证请求使用 Runtime 子取消令牌和已配置 request timeout。受控关闭时取消尚未完成
的验证；不将验证任务写入 Session Run Registry。

### 6.5 有界受控关闭与任务故障

Runtime 关闭顺序固定为：

```text
Running → ShuttingDown
→ 停止登记新 Session/Run/验证
→ 关闭 Run supervisor registry 并传播 root cancellation
→ 在 RuntimeConfig.shutdown_timeout 内等待 supervisor
→ 超时则终止仍登记的 supervisor
→ 将仍为活动态的 Run 结算为 Failed/Internal 并清除 Session busy
→ Stopped
```

`shutdown_timeout` 是 Host 装配 Runtime 时提供的进程级保护参数，默认 10 秒；它不是
`config.toml` 的模型、Transport 或 Agent 配置，也不进入应用协议。正常完成或响应取消的 Run
沿用原有结算结果；只有等待上限后仍未退出的活动 Run 才使用脱敏内部失败兜底。强制结算不得
追加 AssistantMessage，也不得让 Session 保持 busy。

Runtime 显式登记每个 supervisor 的终止句柄。终止 supervisor 只解决正式 Runtime 的业务状态
和 Host 退出上限；如果 Core 内部模型/工具任务违反取消契约，它可能继续存活到 Tokio Runtime
或进程结束。Core 对内部 task 的正常结果、取消和 panic/JoinError 进行完整观察属于 v0.10.0，
本版本不扩大 `AgentExecution` 公共契约。

Host 对连接 writer/event 子任务和信号任务都必须 await 并检查 `JoinError`：预期取消作为正常
清理，panic 或异常结束映射为稳定 Host 错误，不能使用 `let _ = handle.await` 吞掉。

## 七、应用协议方案

### 7.1 当前协议与稳定类型

- 项目仍处早期阶段，`PROTOCOL_VERSION` 保持 `1`，现有 DTO 直接演进；不划分协议代际，也不为
  尚未稳定发布的旧 DTO 建立并行兼容层。Host 继续在 handshake 阶段拒绝任意版本不匹配客户端。
- `assistant-protocol` 新增 `ModelKey` newtype，使用与配置编译器相同的形式约束，
  避免跨层传播裸 `String`。它仍是用户输入 key，不是 Runtime 生成 ID。
- `CreateSessionRequest` 增加可选 `model_key`；`SessionSummary` 增加必填 `model_key`。

### 7.2 命令与 DTO

| 命令 | 请求字段 | 成功结果 |
| --- | --- | --- |
| `get_config_status` | 空 | 配置状态、安全路径、schema version、默认 key、全局安全 issue |
| `list_models` | 空 | 按 model key 确定性排序的脱敏模型摘要 |
| `get_model` | `model_key` | 指定模型的脱敏详情、有效性、issue 和有效输出上限 |
| `reload_config` | 空 | reload 后的配置状态投影；文件内容无效是正常结果，不使用 Internal 代替诊断 |
| `validate_model_connection` | `model_key` | `succeeded` 或带稳定 failure kind 和脱敏 message 的 `failed` |

模型摘要/详情可包含：`model_key`、`display_name`、`protocol`、`provider`、
`endpoint`、Provider 模型名、context window、模型输出上限、Agent 输出请求值、有效输出上限、
`is_default`、`is_valid` 和 `api_key_configured`。`api_key_configured` 只表示非空配置通过本地校验，
不表示 Provider 已验证凭据。

新增安全错误码：

- `configuration_unavailable`：顶层配置当前不可用；
- `model_not_found`：key 不存在；
- `model_unavailable`：key 存在但当前配置或组合无效；
- `model_build_failed`：已通过静态编译，但工厂/Agent 构造在 Run 前失败。

连接验证的可预期 Provider 失败使用命令成功结果中的 failure kind，不混入 `RuntimeErrorCode`。
协议层的 `ConfigIssue` 与 `ConnectionValidationFailure` 都是稳定、脱敏的应用枚举，
不直接序列化 `toml`/`reqwest`/`ModelError` 类型。

### 7.3 事件与私有 wire

v0.9 不增加配置文件自动监视，因此不增加异步 `ConfigChanged` 事件。reload 和连接验证结果
由对应命令响应返回。Session/Run 事件保持现有语义，`SessionCreated` 中的摘要自然带 model key。

Host 私有 `HostCommand` 继续包装 `RuntimeCommand`，Demo 的命令分发和 exhaustive match 必须同步新增
variant。不增加返回 raw config 或 secret 的私有调试命令。

## 八、实现分层

### 8.1 `assistant-runtime`

建议按领域拆分为：

- `config/source.rs`：`RuntimeConfigSource`、加载结果和安全错误分类；
- `config/schema.rs`：Raw serde 类型；
- `config/compile.rs`：跨字段校验、Profile 组合检查、有效上限和脱敏 issue；
- `config/registry.rs`：快照、状态投影和串行 reload；
- `model_factory.rs`：Provider-neutral 的工厂请求、secret wrapper 与错误；
- `execution_compiler.rs`：从 Session + ConfigSnapshot + 业务决策构造 Run Agent；
- `connection_validation.rs`：最小 ModelRequest、流消费与错误投影。

文件名以实现时代码体量为准，不为单个类机械建文件。`AssistantRuntime` 增加配置 registry、
config source、model service factory、prompt factory 和现有 tools/authorizer 等注入资源。

### 8.2 `runtime-host`

- `config.rs` 改为只解析 Runtime Home、socket 和 Demo 连接参数。
- 新增 Runtime Home resolver 和 LocalConfigSource，实现目录/文件权限检查与异步读取。
- `resources.rs` 不再读取环境变量或保存唯一 ModelService，而是实现
  `ModelServiceFactory` 和 `SystemPromptFactory`，同时继续提供 ToolSet 与 Authorizer。
- `main.rs` 先建立 Runtime Home/endpoint，再构造 Runtime 并执行首次配置 load；不调用
  `dotenvy::dotenv()`。
- `server.rs` 补充新命令分发、受控关闭时验证任务取消和当前协议测试。
- Demo 只增加必要的文本菜单/命令以手工查询、reload 和验证，不建设正式配置 UI。

### 8.3 下层 crate

- `agent-core`、`agent-sdk`、`agent-context` 不新增配置文件类型；现有构造契约如能完成
  Run 编译就不修改。
- `agent-model` 不为应用配置新建平行类型；Runtime 直接编译到现有 Generation/Retry
  类型。
- OpenAI-compatible Adapter 原则上无功能改动；如实现时需要共享 endpoint 静态校验，
  只可提取无 secret 的小型校验 API，不将 `TransportTimeouts` 或 Profile 内部类型提升到 Runtime。

## 十、风险、兼容与排除项

- **敏感配置边界**：用户已确认 API Key 直接位于模型配置，长期 Rust 规范已按 4.2
  同步。实现与验收必须按敏感文件而不是普通配置检查权限和泄漏。
- **明文 secret 复制**：ResolvedConfig 需为每个 Run 构造 ModelService，因此进程内会有有限复制。
  不通过缓存跨 Run ModelService 改变冻结语义；以私有 wrapper、约束 Debug/Serialize 和快照
  drop 缩小泄漏面。
- **全局 generation 与 Profile 冲突**：冲突按单模型组合无效处理，不静默丢弃值。
  如用户需要 DeepSeek thinking Profile，temperature/top-p 应保持缺失。
- **配置与 start 竞争**：Run 以取得的单一 `Arc<ResolvedConfig>` 为编译事实；reload 不回溯
  改变已开始编译的 Run。
- **UDS 路径长度**：默认 Runtime Home 路径可能因用户根路径过长超限。Host 在 bind 前失败并
  提示使用绝对 `--socket`，不在本版本引入第二个运行目录规则。
- **v1 客户端不兼容**：本项目尚未发布稳定外部客户端，采用明确 handshake 拒绝，
  不建设 v1 命令适配层。
- **不在本版本实现**：CRUD/revision、文件 watcher、Session model key 切换、Provider 列表探测、
  自定义 Profile、开关 reasoning 或控制 reasoning 展示的 UI/配置。

实现完成时必须同步修订 `docs/modules/agent-system.md`、`assistant-runtime.md`、
`runtime-host.md`、`assistant-protocol.md`、`agent-provider-openai-compatible.md`、受影响的
Agent SDK 导读和版本文档，并复核已同步的 Rust 规范与重要决策记录，保证“一个
Agent 是 Session 长期冻结事实”的旧描述不再与按 Run 编译语义并存。
