- 当前阶段：M0–M5 和版本验收均已完成
- 功能范围：[`v0.9.0 功能设计`](功能设计.md)

## 二、台账原则

1. M0 至 M5 顺序推进；前一里程碑完成实现和验证后先标记 `🟨 待确认`，用户明确
   确认后才改为 `✅ 已完成`并进入下一里程碑。
2. `assistant-runtime` 始终持有配置、Session 和 Run 权威状态；Host 只实现平台读取、
   Provider 装配和传输，Protocol 只承载脱敏跨层契约。
3. 每个里程碑均保持 workspace 可编译、已有测试不倒退；不为拆分里程碑引入将在下一步
   删除的产品配置双轨或临时 credential 来源。
4. M0–M4 的自动测试使用临时目录、假 secret、fake ModelService 和离线 fixture，
   不读写用户真实 Runtime Home，不访问真实 Provider。
5. 真实 Provider 只在 M5 通过显式人工入口验证；执行前提示可能费用，不记录 credential、
   完整 prompt 或响应正文。
6. 任何实际代码与已确认设计的不一致，先停止扩大改动并更新设计，不在实现中静默
   改变配置、冻结、fail-closed 或协议语义。
7. 实际产出、命令结果、偏差、遗留和风险写入 `docs/开发进度.md`；本计划只更新
   里程碑状态。
8. 不主动执行 Git 暂存、提交或推送。

## 四、里程碑台账

### M0：配置领域、schema 与编译基础

- 前置：`v0.9.0` 功能设计、技术方案和本开发计划均已确认。
- 目标：建立不依赖具体 Provider Adapter 的配置解析、语义编译、脱敏投影和安全 secret
  边界，为 Runtime 接管配置提供可独立测试的基础。
- 交付范围：
  - 配置解析与两阶段逐模型编译；
  - 用户 model key、配置状态、issue 与脱敏投影的领域表示；
  - Runtime、Agent 和模型静态配置到现有 Generation、Retry、Budget 契约的编译；
  - 有效输出上限、Provider 到内部 Profile 的推导和 DeepSeek 组合校验；
  - 必要的 workspace 依赖登记与单元测试。
- 验证入口：

  ```bash
  cargo test -p assistant-runtime -p assistant-protocol
  cargo clippy -p assistant-runtime -p assistant-protocol --all-targets --all-features -- -D warnings
  cargo fmt --all --check
  ```

- 完成判定：完整样例、缺省值、顶层错误、逐模型错误、Profile 组合、输出上限与
  secret 脱敏均有确定性测试；未引入平行的下层参数体系。
- Review 重点：顶层/单模型错误边界、用户 key 而非内部 ID、API Key 无 Debug/Serialize 泄漏、
  配置维度归属。
- 技术依据：技术方案第四、五节。

### M1：Runtime/Host 配置所有权与按 Run 模型装配

- 前置：M0 已确认。
- 目标：一次性用 Runtime Home 下的敏感配置取代产品 Host 的 CLI/环境模型配置，并将
  Session 长期 Agent 改为 Session 冻结 model key/System Prompt、Run 前编译完整 Agent。
- 交付范围：
  - Runtime Home 解析、目录与配置文件安全读取、显式覆盖与 endpoint 长度检查；
  - Runtime 配置源、快照 registry、首次 load 和串行 reload 内部能力；
  - Host 的 `ModelServiceFactory`/`SystemPromptFactory` 与 Runtime 的执行编译边界；
  - Session model key、System Prompt 冻结和 Run 前 Agent/ModelService 构造；
  - 模型配置失败在 UserMessage 写入前返回、reload 不影响活动 Run；
  - 移除产品 Host 的 `.env`、`DEEPSEEK_*` 和模型/credential CLI 来源；
  - 为现有 Session 协议增加 model key 并同步当前 handshake 契约；项目仍处早期阶段，
    `PROTOCOL_VERSION` 保持 `1`，不建立并行协议代际。
- 验证入口：

  ```bash
  cargo test -p assistant-runtime -p assistant-runtime-host --all-features
  cargo test -p assistant-protocol
  cargo clippy -p assistant-runtime -p assistant-runtime-host -p assistant-protocol --all-targets --all-features -- -D warnings
  cargo fmt --all --check
  ```

- 完成判定：Runtime 在配置缺失/无效时可建立；有效配置可按显式或默认 key 创建
  Session 并执行；同 key reload 只改变下一 Run；无旧 credential 回退，也无临时双轨配置。
- Review 重点：Runtime/Host 所有权、System Prompt 与 model key 冻结粒度、Run 构造顺序、同 Session
  串行、配置与 start 竞争、credential 生命周期。
- 技术依据：技术方案第三、五、六、八节。

### M2：配置查询、诊断与显式 reload

- 前置：M1 已确认。
- 目标：将 Runtime 已有的配置状态、模型脱敏投影和 reload 能力通过稳定应用协议暴露，
  使无有效模型的 Runtime 也能被客户端完整诊断。
- 交付范围：
  - 配置总体状态、模型列表、单模型详情、issue 和安全错误的协议契约；
  - 查询与 reload 命令、Host 分发、私有 wire 与 Demo 最小调用入口；
  - 当前协议的 serde round-trip、exhaustive match 和任意 handshake 版本不匹配路径；
  - 无效 reload 结果、顶层 fail-closed 和逐模型局部可用性的跨进程回证；
  - 所有查询、响应、错误和 Host 输出的 secret 泄漏测试。
- 验证入口：

  ```bash
  cargo test -p assistant-protocol
  cargo test -p assistant-runtime -p assistant-runtime-host --all-features
  cargo clippy -p assistant-protocol -p assistant-runtime -p assistant-runtime-host --all-targets --all-features -- -D warnings
  cargo fmt --all --check
  ```

- 完成判定：客户端可区分 Missing/Invalid/Degraded/Ready，定位全局或指定 model key 错误，
  并显式 reload；任何协议和调试路径不含 API Key、认证 header 或原始 TOML。
- Review 重点：Protocol 是安全投影而非内部配置序列化，reload 失败是可诊断业务结果，
  Host 不建立第二份配置状态。
- 技术依据：技术方案第五、七节。

### M3：显式模型连接验证

- 前置：M2 已确认。
- 目标：实现不产生 Session/Run/Conversation 事实的最小真实模型请求能力，并向未来
  客户端提供稳定的连接结果分类。
- 交付范围：
  - Runtime 的连接验证请求构造、ModelService 调用、流终态消费与取消；
  - 连接验证命令、脱敏结果与失败分类；
  - DeepSeek/标准兼容 Profile 的最小请求编译，不携带 System Prompt、工具或用户数据；
  - fake/fixture 成功、配置、认证、连接、超时、限流、服务不可用、Provider 拒绝与协议
    异常路径；
  - 验证任务与受控关闭的取消回归。
- 验证入口：

  ```bash
  cargo test -p assistant-runtime -p assistant-protocol -p assistant-runtime-host --all-features
  cargo test -p agent-model -p agent-provider-openai-compatible
  cargo clippy -p assistant-runtime -p assistant-protocol -p assistant-runtime-host --all-targets --all-features -- -D warnings
  cargo fmt --all --check
  ```

- 完成判定：离线测试证明验证请求只使用固定最小内容，唯有规范 `TurnFinished` 成功，
  全部失败脱敏且不产生 Session/Run/Journal 副作用。
- Review 重点：验证不是 Agent Run、不使用 `/models` 作为唯一依据、错误分类只基于稳定结构事实、
  自动测试不访问真实 Provider。
- 技术依据：技术方案第六、七节。

### M4：安全、并发、私有 Demo 与长期文档收口

- 前置：M3 已确认。
- 目标：将分里程碑能力收口为一条可重复验证的私有 Host/Demo 路径，补齐 secret、文件、
  reload/start 竞争和现有 Runtime 可靠性回归，并使长期模块文档与实现一致。
- 交付范围：
  - Runtime Home mode、symlink、非普通文件、大小上限、socket 长度与错误脱敏回归；
  - 用唯一假 secret 扫描协议、事件、错误、Host 输出和调试观察路径；
  - 同 Session 双 start、跨 Session 并发、reload/start 竞争、取消、断线和受控关闭回归；
  - 为 Runtime 受控关闭定义明确等待上限与超时后强制终止语义，确保不响应取消的
    ModelService、Tool 或 Recorder 不会无期阻塞 Host 退出；
  - Host 显式观察连接 writer/event 子任务结果，区分正常取消与意外 panic，不静默
    吞掉连接任务故障；
  - 私有 Demo 的配置查询、reload、模型选择和手动连接验证路径，不建设正式 UI；
  - `agent-system.md`、相关模块约束、Agent SDK 导读、重要决策与版本文档的一致性修订。
- 验证入口：

  ```bash
  cargo test -p assistant-runtime -p assistant-runtime-host --all-features
  cargo test -p assistant-protocol -p agent-sdk -p agent-core
  cargo clippy -p assistant-runtime -p assistant-runtime-host -p assistant-protocol --all-targets --all-features -- -D warnings
  cargo doc --workspace --no-deps
  cargo fmt --all --check
  ```

- 人工核对：使用临时 Runtime Home 完成缺失/无效配置诊断、成功 reload、Session 选择与
  无网络的本地验证路径，不使用真实 credential。
- 完成判定：私有 Demo 可端到端操作本版本全部 Runtime 能力；重要竞争和泄漏路径有确定性
  测试；长期文档不再保留 Session 长期冻结完整 Agent 的旧语义。
- Review 重点：安全边界是真实检查而非只有文档声明，并发测试不依赖 sleep，Demo 不成为
  第二业务实现。
- 技术依据：技术方案第八、九、十节。

### M5：真实 Provider 联调、全量回归与验收准备

- 前置：M4 已确认。
- 目标：用真实使用路径验证 Runtime Home、配置诊断、按 key 装配、reload 边界和连接验证，
  完成全 workspace 回归与版本验收证据准备。
- 交付范围：
  - 使用独立 Runtime Home 的真实 DeepSeek 配置、诊断、reload 和显式连接验证；
  - 显式/默认 model key、多轮、`echo_text`、双 Session、取消、断线重连和受控关闭；
  - 同 key API Key 或调用目标变更对下一 Run 生效、活动 Run 不变的人工回证；
  - workspace 格式、严格 Clippy、全量测试、Rustdoc、依赖方向和文档一致性检查；
  - 将功能设计验收点映射到实际自动/人工证据，记录未执行项、偏差与遗留。
- 验证入口：

  ```bash
  cargo fmt --all --check
  cargo clippy --workspace --all-targets --all-features -- -D warnings
  cargo test --workspace
  cargo doc --workspace --no-deps
  cargo metadata --format-version 1 --no-deps
  ```

- 人工核对：按已确认功能设计的首次配置、Session 执行、同 key reload、失败 reload 和
  显式连接验证路径执行；真实 Provider 请求前再次确认凭据来源、可能费用和脱敏记录方式。
- 完成判定：功能设计的全部验收标准均有实际证据，workspace 回归通过，未执行项、
  偏差、遗留和风险已明确记录，可进入正式版本验收。
- Review 重点：真实路径是否与冻结/reload 语义一致，是否存在 secret 泄漏，验收证据是否
  区分自动测试、文件系统状态、Runtime 状态和真实 Provider 结果。
- 技术依据：技术方案第九、十节与功能设计第七节。
