## 二、目标与边界

用户能够在同一 Host 用户域中安装、配置和使用插件，选择本地或中心智能体，在首次发送时生成带有冻结配置的会话。
个人上传与企业市场获取复用安装机制；ZIP/TAR.GZ、多平台完整包、名称依赖、完整提示词和来源隔离沿用 C01 契约。
Core 不认识插件市场或配置来源，不新增执行引擎、智能体专属权限白名单、插件多版本并行或安装后联网补依赖机制。

## 三、管理入口与启用规则

| 入口 | 管理内容与操作 |
| --- | --- |
| 既有 Skill / MCP 设置 | 只管理独立添加的能力，沿用原编辑、启停和删除方式 |
| 设置 → 插件 | 管理安装、配置、整体启停、更新和卸载；企业模式含“已安装 / 市场”，个人模式提供上传 |
| 插件详情 | 展示包内 Skill/MCP、状态和诊断，不允许单独删除、编辑包内正文/启动声明或单项启停；仅对确需 Host 装配的连接参数提供表单，插件自有配置文件供高级用户按说明导入 |
| 设置 → 智能体 | 个人模式创建、编辑和删除；企业模式查看中心配置与依赖，编辑在管理后台完成 |
| 新会话选项行 | 选择工作空间与智能体，默认不使用自定义智能体，提供管理入口；复用 C02 草稿与冲突处理 |

插件首次安装后默认整体启用，对同一用户所有会话可用；运行配置在首次调用时由插件按需初始化，不以预填软件路径作为启用条件。不跨用户、不绕过既有审批或权限。
手动安装和智能体引导安装使用相同规则。用户明确禁用后，智能体只能提示用户启用，不能静默恢复。
安装、启用和实际调用分别展示；启用不代表立即执行工具，Skill 仍按需加载，MCP 沿用现有运行机制。
智能体默认能力用于依赖准备，提示词可以强调特定插件；不限定只能使用这些能力。
切换或删除智能体不卸载、停用已经安装的插件，不因旧准备请求完成而覆盖当前草稿选择。

新会话快捷入口在客户端本机配置文件中声明，现有本机模板仅保留“快速生成 CAD 图纸”和“售后咨询”，分别选择企业售前、售后工程师助理并预填可编辑中文模板。模板文件不纳入版本控制，正式包默认不包含，只有用户要求时才显式打入；缺少文件时显示零个快捷入口。入口可以按需声明智能体、技能、MCP 与模板的组合；Composer 只解析当前 Host 可用目录并写入既有草稿字段，不包含固定业务流程，也不自动发送。已有正文或能力选择冲突时先确认，缺少配置所指能力时保持草稿不变。

同名冲突沿用总体设计：展示实际来源，不自动覆盖或改名；明确引用插件的能力不能由其他来源冒充。
管理入口分开不等于建立第二套 Registry/Catalog 或将同一能力重复登记。整体启停如何接入现有开关在技术方案中细化。

## 四、依赖准备与首次发送

### 4.1 确认与下载弹窗

1. 选择智能体后由 Host 检查依赖；已安装且满足条件的直接复用，不重复下载。
2. 对可从中心取得的缺失插件，弹窗列出待安装项、版本和可取得的大小信息；用户确认后自动下载、校验、解包和安装。
3. 弹窗展示真实下载进度与后续处理阶段，不将下载 100% 当作安装完成；不知道总量时显示已下载量与进行状态。
4. 执行中不允许关闭按钮、Esc 或遮罩关闭；提供“取消下载/取消安装”。取消先停止工作并处理未生效临时内容，进入已取消终态后才允许关闭，不能以关闭弹窗代替取消。
5. 成功、失败、已取消均为可关闭终态，确认前也可放弃；失败展示具体原因和重试入口，不把用户困在不可关闭的错误窗口。
6. 已成功安装的其他插件保留，不因后续项失败或取消而批量卸载；弹窗如实显示各项结果，取消不破坏已有生效版本。
7. 下载和安装仍由 Host 持有；客户端意外断开后的状态重读、取消与清理边界由技术方案细化，不能仅依赖前端禁用关闭按钮保证一致性。

个人模式没有包源时提示上传对应包；中心已下架、无兼容包或鉴权失败不能声称可以自动下载。
插件首次被调用时自行读取或创建原生配置，发现并校验专业软件路径；自动发现失败、确实未安装软件、需要用户凭证或显式启用时才给出具体处理入口。安装本身不要求普通用户预填专业软件路径，不自动执行清单中的安装命令。
插件环境缺失不阻止按所选智能体发送：缺少配置、外部软件、能力或连接不可用只作提示，智能体可利用现有工具检查、解决或绕过问题。缺包、显式禁用及来源冲突仍需先处理，不隐式安装、启用或替换来源。全过程保留草稿，安装/配置完成不自动发送消息。

### 4.2 配置变化自动处理

首次发送前，Host 自动核对并采用当前有效智能体配置、重新检查实际依赖，不要求用户手工刷新选择或确认单纯的提示词变化。
若配置变化没有引入缺包、显式禁用或来源冲突，继续本次发送，原子确定本次采用的配置并冻结到会话；不能在检查后又换成未经检查的另一份配置。
若出现新的缺失插件，进入上述安装确认弹窗；新增下载授权、用户凭证或插件首次调用时确实无法自动解决的外部依赖不能用自动刷新代替。
配置被删除、来源无效或所需插件包无法取得时显示可处理原因，保留草稿，不偷偷切换其他智能体或本地来源。
中心普通刷新失败沿用总体设计的最后有效目录规则；从未取得有效配置或身份明确失效时不可选择，不以缓存绕过授权。
创建成功后冻结完整提示词和默认配置；编辑、删除中心/本地源不改写旧会话，Fork/恢复沿用既有语义。

## 五、故障、更新和卸载

- 单个 MCP 连接失败不禁用其他正常能力；“已安装”“已启用”和各能力是否可用分别展示。依赖可用性用于诊断，不把环境缺失作为会话发送门槛。
- 插件页读取中心目录时自动检查在架插件的新版本，用户也可显式重查；发现版本更高且 SHA 不同的中心包后自动开始更新并展示进度，否则不重复安装或降级。新版本移除智能体所需能力时标示缺项，不改写智能体配置或自动降级。
- 有活动使用时更新/卸载提示稍后重试，更新失败保留旧版及用户配置。整体禁用对正在执行调用的具体生效边界由技术方案细化，不能热删除正在使用的文件。
- 卸载默认移除受管包和能力接入，保留用户配置与运行数据；提供“同时清除用户配置与运行数据”选项，不删除用户工作空间产物、其他插件或独立添加的能力。
- 保留数据不表示插件仍已安装/启用。重新安装时必须核对原来源和配置声明，同名其他来源不得静默取得遗留凭证。
- 中心下架只影响对应市场来源，已安装项可用可删；网络错误不等于下架，删除后不能从已下架来源补装。

## 六、用户配置归属与候选布局

已核查代码事实：`apps/runtime-host/src/host_layout.rs` 的个人根为 `users/_personal/`；
`apps/runtime-host/src/user_domain/mod.rs` 的企业根为 `users/<center_uuid>_<user_id>/`；
`user_domain/services.rs` 把该用户根交给 `LocalMcpConfigSource`，独立 MCP 配置位于用户根 `mcp.json`。

候选布局以既有用户根 `<user-root>` 为基准，所有路径在所连接 Host 上：

```text
<user-root>/
├── mcp.json                         # 既有独立 MCP 配置
└── plugins/<plugin-name>/
    ├── config/                      # 插件自行定义文件名、格式和结构，可包含多个文件
    ├── data/                        # 该插件拥有的持久运行数据
    └── packages/<sha256>/           # 校验后的不可变包内容
```

物理目录为方案建议，不代表目录已创建或存储实现已完成。插件配置由插件自己定义，可使用 TOML、YAML、JSON、
INI 或程序原生格式，也可包含多个文件；Host 不强制统一配置结构或通用序列化文件。
配置须跨包版本和默认卸载保留，因而与不可变包分开；不把插件配置混入手工 `mcp.json`。
Host 管理安装来源、整体开关和目录归属，不能把这些管理事实强塞进插件自定义配置文件。外部软件路径属于插件自身配置：插件按自己的格式写入 `config/`，首次调用时尽量自动发现、生成和校验；移动或失效后由插件重新检查，不由 Host 另存一份通用路径。
C01 清单中的用户输入字段和 MCP 占位符是当前实现事实，不等于插件自身配置文件格式；其中 `${software.*}` 依赖 Host 预填路径，与首次调用自行初始化冲突，技术方案须调整包启动契约及 C01 校验，而不能只隐藏输入框。
不向数据库、`mcp.json` 和插件配置重复持久化同一份秘密，也不假定 Host 能解析或重写任意格式。

Host 提供隔离、持久的目录和生命周期管理；插件负责自身配置内容的解释。由 Host 写入的文件复用私有文件校验及
原子替换，Unix 私有目录 0700、配置文件 0600，其他平台复用已有保护机制并实际验证。
秘密脱敏投影，不进入系统提示词、Skill 正文或通用 Shell 环境。配置目录按可能含秘密处理，需接入现有 `UserPaths`
保护规则，不依赖识别特定后缀；不得因此阻止所属插件读取自己的配置。应用级保护不是操作系统强沙盒或已实现的加密存储。

技术方案还需核定：插件整体启停与安装记录的唯一存储事实、包切换和取消恢复顺序、自定义配置/运行数据路径如何通过现有包契约交给程序，以及必要的配置操作入口。
不擅自增加 C01 未定义的占位符、可执行安装钩子或把包内 cwd 当可变数据目录；必要契约变化先说明 C01 影响再确认。

## 七、验收口径与后续

| 范围 | 可观察结果 |
| --- | --- |
| 管理隔离 | 独立能力可单独维护；插件内部不可直接编辑/删除，整体开关对当前用户有效 |
| 依赖准备 | 确认后真实下载，阶段/进度可见，执行中不可关闭，取消或失败可结束，无伪安装成功 |
| 草稿与配置 | 切换保留输入；配置自动核对；新增依赖仍确认安装；首次发送只冻结实际检查通过的配置 |
| 更新与卸载 | 活动使用受保护，失败保留旧版，默认保留用户数据，清除范围明确且不串来源/用户 |
| 真实运行 | 代表性完整运行时包在目标平台可用；缺专业软件与连接故障诊断准确 |
| 兼容与恢复 | 消费 C01 已实现接口及 C02 物化恢复契约；旧中心、旧会话和前序数据影响在技术方案中明确 |

代表性插件包须具备自包含运行时，不能以中心上传成功代替 Host 安装与实际执行验证。
本稿不包含实现计划或验证结果。[技术方案](技术方案.md)已形成草案，其中更新失败范围和活动使用保护边界待评审确认；已按用户要求先编制开发计划草案，实施前补齐交互指导并确认设计基线。
