## 二、背景、现状与目标

中心已有身份、用户管理、模型管理、调用记录、管理审计及正式 Admin 页面。
目前没有企业 Agent 配置、插件包发布和面向 Host 的插件分发能力；不能将现有模型配置或模型代理用作插件运行通道。

| 已有基础 | 核查入口 | 本循环复用方式 |
| --- | --- | --- |
| 身份与服务端权限 | [security.ts](../../../../../apps/enterprise-center/src/security.ts)、[IdentityService](../../../../../apps/enterprise-center/src/identity/service.ts) | 管理员管理，登录用户读取；沿用 Bearer 身份，不新增市场登录 |
| 管理页面路由与导航 | [routes.tsx](../../../../../apps/enterprise-admin/src/app/routes.tsx)、[导航菜单](../../../../../apps/enterprise-admin/src/app/PageLayout/NavigationMenu/index.tsx) | 在既有管理台加入 Agent 管理、插件管理，复用离开拦截和请求状态 |
| OpenAPI 与兼容信息 | [app.ts](../../../../../apps/enterprise-center/src/app.ts)、[CenterInfo](../../../../../apps/enterprise-center/src/contracts/info.ts) | 声明实际实现的新能力，Admin 继续由 OpenAPI 生成请求代码 |
| 数据与审计 | [DataSource](../../../../../apps/enterprise-center/src/database/source.ts)、[管理审计](../../../../../apps/enterprise-center/src/audit/service.ts) | 沿用唯一业务池、显式迁移及管理审计，不建第二份身份/发布账本 |

完整使用路径：管理员上传插件包并上架 → 创建含完整提示词和默认 Skill/MCP 的 Agent → 登录用户能够读取 Agent 配置、按目标平台发现并下载插件 → 管理员发布新版本或下架 → 调用方准确识别可更新或已废弃。

本循环的独立结果是中心业务和分发闭环。通过真实管理页面及授权 API 可以验证，不需要提前建设 Host 安装器。
上传成功只证明包已被中心接纳并可分发，目标平台上的实际安装、运行和 Agent 执行由 C03 验证。

## 三、范围与非目标

纳入：Agent 管理及读取、插件信息与版本完整包管理、受保护的市场发现和下载、下架及状态查询、管理审计、中心数据与包文件的一致性、正式后台入口。

不纳入：

- Host 安装、用户插件配置与凭证、MCP 连接、Skill 扫描、Agent 执行和客户端市场页面，均归 C03。
- 个人上传到 Host 的具体传输和安装实现；C01 定义同一种包，C03 复用。
- Desktop 布局、置顶和工作空间，归 C02。
- 普通用户发布、投稿审批、多市场聚合、评论评分、付费、推荐算法和自动依赖版本求解。
- 中心运行上传的 MCP、脚本或语言运行时；中心不替发布方安装依赖或构建各平台制品。
- Agent 独立模型配置、工具授权策略、会话管理、记忆和定时任务。
- 包内文件在线编辑、中心自动打包、自动向 Host 推送或强制安装更新。

## 四、功能范围与使用路径

### 4.1 管理入口与信息组织

既有管理后台增加“Agent 管理”“插件管理”两个导航入口，保留用户、模型、调用记录和审计。
普通企业用户通过后续 Host 客户端使用分发能力，不进入管理员页面；服务端仍独立验证权限。

| 页面 | 用户看到的内容 | 主要操作 |
| --- | --- | --- |
| Agent 列表 | 名称、描述、默认 Skill/MCP 摘要及中心能够判断的依赖问题 | 新建、搜索、编辑、删除 |
| Agent 编辑 | 基础信息、完整长文本提示词、默认 Skill/MCP 选择及所属插件名称 | 保存、取消；未保存离开沿用现有拦截 |
| 插件列表 | 一个插件一条记录，名称、描述、上架情况及版本概况 | 上传插件包、搜索、进入详情、上架/下架 |
| 插件详情 | 插件说明、包内 Skill/MCP 名称、版本列表及每版当前完整包和支持平台 | 编辑说明、上传新版本或替换同版本包、下载已允许的包、上架/下架 |
| 上传反馈 | 进度、解析出的插件/版本/平台、校验结果与失败原因 | 提交、取消、失败后重新选择/上传 |

搜索和状态筛选满足管理需要，不为新列表默认增加分页与总量统计机制；确有数据规模依据时再在技术方案提出。
插件顶层不按架构拆分。每个版本只展示一个当前完整包及其包内声明的平台范围，普通用户无需选择架构。

### 4.2 Agent 配置管理

1. 新建时填写名称、描述和提示词。提示词是完整长文本，可以包含角色、工作方式、约束和能力用法；不拆成固定模板字段，不通过摘要替换保存内容。
2. 默认 Skill/MCP 列表可以为空，允许仅提示词的 Agent。选择多项时展示名称及所属插件，引用均按名称保存，不绑定上传记录 ID。
3. 中心已知插件内容可用于选择；同名内容必须显示来源，由管理员明确对应插件，不自动猜测。保留对 Host 既有独立 Skill/MCP 的名称引用方式，但标明“需要在目标 Host 核对”，不伪造中心已经验证其可用。
4. 名称必填且在本中心 Agent 列表内唯一；提示词不能全空。非法名称、重复列表项、无法解释的依赖声明在保存前指出问题。
5. 本稿采用简单的名称规则：正常编辑保留已有名称，可编辑描述、提示词和默认项；需要换引用名称时创建新条目，删除旧条目由管理员显式操作。不建立名称别名或自动改写他人引用。
6. 保存后，新读取的中心配置使用最新内容；不推送改写 Host 已有会话。删除只让该 Agent 从后续中心配置中消失，不卸载插件，不删除会话或改写历史。
7. 所有已保存的有效 Agent 都进入企业配置列表，不再增加 Agent 草稿、审批发布、分组权限或第二个上架流程。

中心不以本机安装状态判断 Agent 就绪。插件下架、所需名称缺失和未覆盖的平台可以由中心提示；用户密钥、专业软件、用户禁用项等仍由 Host 判断。
保存 Agent 的引用不锁住插件生命周期：依赖后来下架时保留名称并显示问题，不悄悄删除默认项或替换为另一个插件。

### 4.3 插件名称、版本与多平台完整包

插件名称用于长期引用，版本用于区分发布内容；每个版本在中心当前只对应一个 ZIP 或 TAR.GZ 完整归档。归档内的 `plugin.json` 权威声明该版本支持的操作系统/架构，上传页面不再手动勾选平台，也不允许为同一版本分别补传平台包。

- 首个有效包建立对应插件和版本；本稿默认新插件先处于未上架状态，管理员检查详情后显式上架，不新增发布审批流程。
- 已有插件上传新版本，归入同一插件条目；包内可以声明一个或多个平台，版本详情直接展示该完整包的支持范围。
- 正常编辑不直接修改插件引用名称，可以修改插件说明。不同版本可以改变能力、配置和平台范围，每个版本必须完整自描述。
- 重复提交同 SHA 的相同包不产生变化；同名同版本但 SHA 不同的完整包允许替换当前归档，以支持测试阶段频繁修订。替换前必须完整校验新包，失败保留原包。
- 同版本替换不会触发客户端同版本更新、重装或通知；已经下载或安装的旧内容不受中心追改。上传者需自行判断该版本是否已经实际分发，正式交付后仍建议用新版本号表达更新，但中心不强制阻止。
- 已上架插件上传新版本或替换同版本包后，新的当前完整包可被后续发现和下载；这不代表已安装 Host 被自动更新。上传中和校验失败的包不可供发现或下载。

本循环管理发布状态和包，不能得知所有 Host 已安装数量，也不增加设备上报或安装统计来模拟影响范围。

### 4.3.1 包内平台差异与整体解析

上传包不是只登记一个文件名，而是要解包解析后再决定是否接纳。中心对单个 ZIP/TAR.GZ 完整校验清单、目录、共享 Skill/MCP、每个声明平台的入口、运行时和内容摘要；不再进行多包对比。包内不同平台可以拥有不同的二进制、运行时目录、启动参数、权限、资源及平台专属外部软件指引，但对外 Skill/MCP 名称和用户配置声明只定义一次，不能按平台变化。

归档格式、路径、限额、清单或任一声明平台入口无效时，整个包拒绝，不做部分平台接纳。不同版本允许改变能力、配置和平台范围，但 Host 选包时必须确认该版本同时支持当前平台、Host 版本并包含 Agent 所需名称。中心保存该版本当前原始包、SHA 和解析结果，C03 下载后仍独立复核；同版本被替换后不要求客户端识别内容变化。

### 4.4 上传、检查与运行环境责任

上传操作先验证管理员身份，接收完整包后检查是否符合本版插件交付契约，包括名称、版本、平台、Skill/MCP 入口、运行环境关联、外部软件要求及内容完整性。
上传进度、校验完成、已经可分发是不同结果，页面按实际结果展示。未知结果可重新读取插件详情确认，不凭前端进度到达末尾宣称成功。

插件需携带本地脚本/MCP 实际运行所需的语言运行时、库和程序，不依赖用户系统预装或安装后再执行 npm/pip。
纯 Skill、远程 MCP 没有本地程序时不强制包含无用运行时。Blender 等专业软件单独声明，并提供可供 Host 判断和解释的要求及指引。

中心只解析数据和包结构，不执行包内代码来“测试安全”或安装依赖。结构校验不能证明所有目标平台的实际运行情况，管理页面不能把“已通过包校验”写成“运行已验证”。

- 用户密钥、账号令牌和个人路径不是发布内容；包只声明需要填写哪些配置及哪些属于敏感项。
- 包内路径必须能在安装后定位；损坏包、入口缺失或不能遵循约定的路径明确拒绝。压缩与路径处理细节由技术方案确定。
- 大包传输、取消、断连、磁盘不足与中心关闭均需明确失败或未发布结果；不残留可以误下载的半包。
- 首个包上传失败不产生可用插件；已有插件的新包失败保留原版本和状态。临时文件清理不能删除已发布包。
- 同一包的文件与元数据均达到发布条件后才返回成功；审计写入失败不能伪造管理操作成功。

### 4.5 上架、下架与重新上架

| 动作/状态 | 管理端行为 | 分发与已安装端语义 |
| --- | --- | --- |
| 上架 | 至少存在一个完整有效版本包，管理员显式操作 | 授权用户可发现和下载支持目标平台的完整包 |
| 下架 | 显示中心可确定的 Agent 名称引用和影响说明；明确执行后停止下载 | 中心返回已废弃，已有安装允许继续使用及删除，不强制停用 |
| 已下架 | 保留名称和必要状态，可查看详情；不以公开地址继续下载 | 不提供更新或重新下载，已删除的 Host 不能自动补装 |
| 重新上架 | 确认存在可分发有效包后操作 | 状态恢复在架；Host 下次成功查询后更新展示，不自动安装或升级 |

下架后的旧下载地址不得绕过检查；活动下载的取消和下架边界由技术方案收敛，必须保证失败/中断不会被 Host 当作完整成功包。
中心下架只作用于来自该中心的安装，本地上传的同名包不受影响；中心不能发出按名称全局卸载或禁用指令。

本稿首版不提供已发布插件及历史版本的永久销毁入口，以保留可查询的下架事实；需要停止分发使用下架。
这不限制用户在 Host 删除已安装插件。发布数据的空间清理和物理销毁不扩展为本循环的新管理系统，后续有明确需求再安排。
删除后同名重传的依赖仍按名称解析，不依赖中心历史记录 ID；具体文件恢复/运维动作不在本稿中作为日常 UI 流程。

### 4.6 面向 Host 的发现、读取、下载与状态查询

| 使用路径 | 中心提供的结果 | 不能混淆的情况 |
| --- | --- | --- |
| 读取 Agent 目录 | 完整有效 Agent 配置；成功空列表有效 | 未授权、网络失败和空列表不能互相代替 |
| 浏览市场 | 可发现插件及其内容、版本和平台支持 | 不用隐藏架构专用条目模拟一个插件 |
| 选择安装包 | 目标 Host 系统/架构下最新兼容可用版本，以及明确的包内容校验信息 | 整个市场最新版本不等于该平台最新可安装版本 |
| 查询更新 | 与调用方当前版本对比的可用新版本 | 不主动下发安装动作、不要求已废弃插件更新 |
| 下载具体包 | 核验身份、当前上架状态和包事实后的文件传输 | 不能通过静态路径或过时下载地址绕过下架 |
| 查询已装中心插件状态 | 已在架、已废弃或无法确定的明确结果 | 当前版本不支持目标平台、网络错误、列表缺项、从未存在的名称不能直接当作下架 |

复用现有企业身份和中心身份信息；LLM 调用 key 不用于本循环 API，不引入新 Token、市场账号或续期机制。
中心返回自身能够确定的事实，不根据客户端发来的名称宣称该客户端插件一定来自中心；安装来源由 Host 保存并核对。
中心可读配置不携带用户插件凭证，公开中心兼容信息不等于匿名可下载插件。

### 4.7 审计、失败与页面反馈

Agent 创建/修改/删除、插件上传或同版本替换、说明修改、上架/下架等管理写入进入既有审计，记录操作者、名称、版本、支持平台、结果及替换时的新旧 SHA 摘要等必要信息。
不记录包二进制、用户秘密或整段提示词正文；不为分发新建浏览/下载统计和逐字内容历史系统。

并发修改、身份失效、包不可用等由中心返回明确失败；Admin 保留可恢复的未提交内容，沿用既有提交状态和离开拦截。
上传已发出后取消等待不等于服务端必定回滚，重新进入详情必须以中心事实为准；不能自动重复写操作制造第二个发布结果。

## 五、模块边界、数据与交接契约

- 企业中心持有 Agent 配置、插件发布目录、版本及其当前完整包事实。业务元数据持久化和审计复用现有 PostgreSQL；包文件放受保护存储，不放公开 Admin 静态目录。
- Admin 通过正式 API 管理，不自行读包目录、模拟中心发布状态或对依赖问题作第二份权威判断。沿用已有路由、Ant Design 和请求生成方式。
- 原有身份、模型与调用记录接口保持自身职责；本循环不把插件配置塞进模型配置，也不改变已确认的中心模型选择规则。
- Center OpenAPI 描述实际已实现的配置、管理和分发接口。包格式和接口必须在 C01 技术方案中定稿，供 C03 无歧义消费；不创建另一个共享业务 SDK 或跨工程源码依赖。
- C02 不需要本循环接口即可交付，双方数据库、端口、目录和迁移链隔离。共享版本台账与规范由协调方更新。
- C01 向 C03 交付：名称与内容引用规则、统一包及完整环境要求、Agent 配置读取、匹配平台下载、更新/废弃状态和失败语义，以及相应已验证契约。
- C03 负责本地/远程来源覆盖、会话冻结、安装状态及用户配置。本循环不创建这些本地事实的中心副本。

删除本次新增机制后的核查：现有身份、审计、页面和 OpenAPI 足以承载管理流程，应直接复用；
Agent 配置及发布包/版本具有独立归属与生命周期，现有模型记录不能承载，需要新增相应业务事实。
具体表、文件和内部模块在技术方案按最小新增原则设计，不为未来市场治理预设额外发布工作流。

## 六、关键取舍与兼容

| 取舍 | 理由与影响 |
| --- | --- |
| Agent 完整长文本，默认能力可为空 | 保留 Agent 表达能力，不强制等同于工具组合 |
| 正常编辑保留引用名称 | 依赖按名称稳定，不引入别名或批量改写机制；换名需新建并显式处理旧项 |
| 新插件先不上架，已有在架插件接纳完整新包后可发现 | 避免首包尚未检查就暴露；不增加独立版本审批或自动安装流程 |
| 无法由中心验证的 Host 本地能力标明需核对 | 保留名称引用而不伪造可用性，真实安装与配置判断归 C03 |
| 同版本允许替换当前完整包 | 支持测试阶段频繁上传，不引入多包对比；上传者自行注意已分发版本稳定性，客户端暂不检测同版本内容变化 |
| 已发布插件以可查询的下架替代本版永久销毁 | 已安装插件可以可靠识别废弃；不增加独立墓碑库或存储清理平台 |

以上具体管理方案已随本稿确认。它们不改变总体设计中已确认的来源、名称引用、手动更新及下架后可用可删规则。

中心数据升级继续沿用现有迁移和准入方式；数据库与包文件联合备份恢复。升级失败不得开放会伪造发布状态的新接口。
Center 软件仍独立发版；新增能力的兼容声明、旧 Host 行为及具体版本在技术方案核查，不机械改动 Runtime 或所有协议版本。
新能力不可用时不能破坏原用户、模型和审计功能。已有中心数据、Token 生命周期和超级管理员规则保持原契约。

## 七、验收标准

| 编号 | 场景 | 必须观察到的结果 |
| --- | --- | --- |
| C01-A01 | 管理员与普通用户访问管理/分发入口 | 权限在服务端生效；普通用户不能管理，登录用户可读取授权分发内容 |
| C01-A02 | 新建、编辑、删除 Agent，包含长文本和空默认列表 | 文本完整保存回读，名称唯一；纯提示词配置有效；删除不改写其他事实 |
| C01-A03 | 插件内容选择、同名冲突及独立 Host 能力引用 | 按名称和来源可解释；冲突不猜测，中心未知能力不伪装已验证 |
| C01-A04 | 首包、不同版本、同版本同 SHA 重传及异 SHA 替换 | 一个版本只有一个当前完整包；同 SHA 无变化，异 SHA 完整校验后替换；失败保留原包，不产生平台子包或跨包比较 |
| C01-A05 | 包损坏、入口缺失、平台/名称冲突、外部软件声明 | 结构错误拒绝，原可用版本保留；中心不执行包内程序；声明可供 Host 使用 |
| C01-A06 | 上传取消、断连、磁盘不足、发布前失败或重启 | 半包不被发现/下载，不伪成功；数据库与文件状态可核查恢复 |
| C01-A07 | 新插件上架、在架插件发布新版本 | 完整有效包才能分发，更新查询可见；不下发强制安装或自动升级动作 |
| C01-A08 | 不同 Host 平台和兼容要求查询 | 返回匹配包或明确原因；最新兼容版本按目标平台判断，不按桌面平台猜测 |
| C01-A09 | 下架、旧下载地址、状态查询及重新上架 | 下架明确可查询且停止下载；重新上架返回当前事实；不发送远程卸载指令 |
| C01-A10 | 未知名称、无匹配包、登录失效和中心故障 | 与已废弃区分，不靠空列表或未找到猜测下架 |
| C01-A11 | 管理写入与审计、并发编辑及迟到响应 | 成功事实与审计一致，冲突/失败可见；无秘密及提示词正文泄漏 |
| C01-A12 | 正式 Admin 页面、路由直达、未保存离开和身份恢复 | 真实 API 驱动，无模拟权限/发布状态；刷新后数据来自中心 |
| C01-A13 | 旧中心数据升级及数据库/包文件恢复 | 原身份/模型功能不回退，新发布事实与可读取文件一致 |
| C01-A14 | OpenAPI 与中心独立运行交接 | 契约只包含已实现能力；不启动 Desktop/Host 也能真实验证本循环 |

上述为 C01 后台能力验收要求，2026-09-23 已按[开发计划](开发计划.md)收口并获用户确认。真实平台安装、具体插件包的正式封装和 Agent 执行留给 C03；不以 C01 上传成功替代 G4/G5 的整体验收。
验证使用隔离非生产库和独立包目录，遵循数据库操作规则；结论进入计划/进度，不另建测试报告。

## 八、风险与后续设计

主要风险是完整运行环境使包体变大、包文件与数据库发布边界不一致、名称/平台匹配错误、长文本被现有管理请求上限截断，
以及中心误把本地就绪条件当作可验证事实。这些风险分别由传输与存储设计、契约验证和 C03 实际运行验证处理。

本循环需要技术方案：定稿包格式/入口约定、名称校验、上传与下载、状态查询、持久化/恢复、身份并发、版本兼容及 Host 交接。
还需要界面交互设计指导：细化 Agent 长文本编辑、依赖选择、插件版本完整包与支持平台组织、上传/替换反馈及下架提示，沿用现有管理台设计体系。

本稿、技术方案与交互指导均已确认并完成 C01 实施。C01 只交付企业中心与正式后台的管理、接纳和分发能力；M4 所用 CAD 归档为后台验收样本，不代表正式插件封装或 Host 可用性。阶段结论见[阶段总结](阶段总结.md)。
