## 一、计划信息与设计依据

- 日期：2026-09-22。状态：2026-09-23 用户确认 M0—M4 和 C01 后台能力验收；2026-09-27 随 v0.28.0 统一归档，未单独提交或推送。
- 依据：[总体设计](../../总体设计.md)、[功能设计](功能设计.md)、[技术方案](技术方案.md)、[界面交互设计指导](界面交互设计指导.md)。
- 目标：企业中心和正式管理后台形成 Agent 配置管理、单版本单一多平台完整包、同版本替换、受保护分发、更新/废弃查询的真实闭环，并向 C03 交付稳定契约。
- 范围：`apps/enterprise-center`、`apps/enterprise-admin` 及其正式 OpenAPI/生成 SDK；不修改 Desktop、Runtime Host、Assistant Runtime 或 Agent Core。
- 前置结论：C01 功能、技术与交互设计已经完成评审所需细化；本计划只拆实施顺序，不重复定义包格式、DTO、表结构或页面尺寸。

## 二、台账原则

- 按五个可核验能力结果推进。每个里程碑完成实现和最小有效验证后标记 `🟨 待确认`，汇报实际产出、未执行项和风险；只有用户明确确认后才进入下一里程碑。
- 计划确认只授权后续从 M0 开始，不授权连续实施 M1—M4，也不构成提交、推送、发布或生产数据库操作授权。
- C01 与 C02 保持已确认的并行边界：C01 只维护企业中心、企业后台、Center OpenAPI 和 Admin 生成 SDK；不触碰 C02 的 Desktop、Host、Runtime、应用协议或工作空间文件。
- 类型、接口、归档校验、并发、超时、页面状态和失败恢复以技术方案与交互指导为准；实施发现假设不成立时先停止扩大，更新设计并重新确认。
- 自动化及联调使用项目 `.runtime-test/` 下新建的 C01 独立场景、独立包目录、独立端口和已核实的非生产 PostgreSQL，不复用用户目录或其他循环数据。
- 数据库写入前核对实际主机、端口、数据库、schema、迁移账本和预期表，并按当前根规则确认目标与范围、完成独立备份及可读性和关键表精确数量核验；异常、影响范围不符或恢复验证失败立即停止。
- 不手改 OpenAPI 生成产物、构建产物或已发布迁移；不主动暂存、提交、推送、发布或清理无关工作树改动。

## 四、里程碑实施与验证

### M0 中心数据与完整包接纳

- **目标**：让中心能够安全接收一份完整插件归档，整体解析包内平台内容，并可靠创建或替换该插件版本的当前包。
- **前置依赖**：本计划获用户确认；实施前复核迁移序号、锁文件、Node 24 API 和技术方案拟选归档/YAML 依赖的实际可安装版本。
- **交付范围**：完成 C01 一次性数据库升级及 Entity/Repository 注册；增加受保护包根、staging、内容寻址文件发布和生命周期 owner；实现 ZIP/TAR.GZ 流式接收、安全扫描、清单/Skill/MCP/平台入口校验、限额、散列和取消/关闭；实现管理上传接口及 created/replaced/unchanged 结果、审计和提交未知恢复语义。同版本异 SHA 只切换当前引用，不覆盖旧 SHA 文件，不创建平台子包或包修订历史。
- **阶段边界**：不在本里程碑完成市场发现、resolve/下载、上下架页面或 Agent 管理；不得暴露依赖后续补写才能成立的成功结果。新插件保持未上架，尚不可由普通用户下载。
- **验证入口**：Center 工程执行定向 `typecheck`、`lint`、单元测试、真实 PostgreSQL 集成测试和 OpenAPI 检查。使用代表性 ZIP/TAR.GZ 覆盖单/多平台、运行时入口、符号链接/权限、路径逃逸、CRC/长度、压缩限额、取消和磁盘/提交故障；覆盖同 SHA 无变化、异 SHA 原子替换、失败保留旧包及并发后提交者成为当前包。
- **完成判定与 Review 重点**：C01-A04—A06 的上传与一致性部分成立；数据库、当前包记录、内容寻址文件和审计结果一致。Review 确认归档解析不执行上传代码、不把整包载入内存、不在数据库事务中传输/扫描大包，也没有多包比较、平台映射表、上传任务表或同版本历史表。

### M1 插件发布与受保护分发

- **目标**：授权用户可以基于目标 Host 平台、版本和所需能力确定性发现并下载当前完整包，管理员可以管理说明和发布状态。
- **前置依赖**：M0 获用户确认；M0 的包记录、文件 owner、身份短提交段和上传结果稳定。
- **交付范围**：实现插件管理列表/详情、说明条件修改、上架/下架/重新上架、市场列表与状态查询、resolve 和受保护下载；落实目标平台/Host/能力过滤、SemVer 排序、明确错误码、当前 SHA `If-Match`、`PACKAGE_CHANGED`、下载背压/限额、同版本替换竞态和下架取消；只在完整实现后声明 `plugin_market` 能力。
- **阶段边界**：不实现 Host 安装器、客户端同版本更新检测、自动更新、公开静态下载、Range/断点续传或包历史下载；Agent API 和 Admin 新页面留给后续里程碑。
- **验证入口**：Center 定向静态检查、单元/集成测试和 OpenAPI 检查；通过真实 HTTP 覆盖管理员/普通登录用户权限、未上架/在架/已废弃、重新上架、平台/Host/能力筛选、缺文件、慢下载、下架竞态及替换前后新旧 SHA 下载准入。验证旧 SHA 已准入下载可完整结束，未准入旧 SHA 返回 `PACKAGE_CHANGED`，响应字节、长度和 SHA 一致。
- **完成判定与 Review 重点**：C01-A07—A10 的插件中心侧成立；网络错误、无匹配平台、包不可用和已废弃可区分。Review 确认下载每次重新鉴权、上架状态不可由旧 URL 绕过、同版本替换不伪造成客户端更新，也没有后台轮询、公开签名地址或第二套身份。

### M2 企业 Agent 配置与依赖诊断

- **目标**：中心保存和分发可复用的完整 Agent 配置，并依据插件名称与各版本当前清单提供可解释的依赖诊断。
- **前置依赖**：M1 获用户确认；插件版本、能力清单、发布状态和平台支持可以稳定查询。
- **交付范围**：实现 Agent 创建、读取、修改、删除、长提示词与 Skill/MCP 名称引用；落实名称规则、正文/列表限额、中心插件能力选择、Host 已有能力引用、失效引用保留、ETag 条件写和审计；实现企业用户完整 Agent 目录读取并只在全部实现后声明 `managed_agents` 能力。
- **阶段边界**：不实现本地 Agent、会话冻结、提示词装配、插件自动安装、模型/权限/记忆配置或 Agent 发布审批；这些仍归 C03 或明确非目标。
- **验证入口**：Center 定向静态检查、单元/集成测试和 OpenAPI 检查；覆盖中文名称、完整长文本、纯提示词 Agent、同名来源冲突、插件版本能力变化、下架/缺平台诊断、无插件 Host 引用、两个旧表单 ETag 冲突及普通用户越权写入。
- **完成判定与 Review 重点**：C01-A01—A03、A11 的服务端部分成立；成功空目录、读取失败和未授权可区分，提示词及秘密不进入审计。Review 确认引用按名称而非上传记录 ID，不为诊断新增依赖图表/缓存，不把中心诊断冒充 Host 就绪状态。

### M3 正式 Admin 管理闭环

- **目标**：管理员在正式同源后台完成 Agent 与插件的全部 C01 管理操作，并获得与中心事实一致的上传、替换、下载和失败反馈。
- **前置依赖**：M2 获用户确认；Center OpenAPI 已包含全部实际 C01 接口和错误语义。
- **交付范围**：导出 OpenAPI 并重新生成 Admin SDK；增加 Agents/AgentEditor、Plugins/PluginDetail 路由和导航；实现列表、完整提示词编辑、能力来源选择、插件版本/支持平台详情、上传 ZIP/TAR.GZ、同版本替换提示、带身份与 SHA 条件的流式下载、说明修改、上架/下架及依赖影响；复用现有身份、写入门、请求代次守卫、离开拦截和主题 Token。
- **阶段边界**：不修改原型，不把业务列表/上传任务放入全局 Store，不在浏览器解析整个归档，不实现客户端市场、安装状态、上传会话或后台常驻任务。
- **验证入口**：Admin 工程执行 `genapi:check`、`typecheck`、`lint`、定向单元测试和正式 `build`；Center 保持 `openapi:check`。使用正式 Center 和真实浏览器检查路由直达、窄窗口/缩放、长文本、键盘焦点、身份切换、上传进度与校验分离、created/replaced/unchanged、`PACKAGE_CHANGED`、412 草稿保留、取消及结果未知核对；浏览器文件保存降级按环境实际说明。
- **完成判定与 Review 重点**：C01-A12 及 A04—A11 的 Admin 观察结果成立；页面不推断发布、运行或安装成功，不泄漏 Token、路径、秘密或完整提示词。Review 确认生成代码未手改、页面状态就近、写入不自动重试、同版本替换警告清楚且没有虚构客户端更新。

### M4 集成收口与 C01 循环验收

- **目标**：在正式 Center/Admin 组合中收口 C01-A01—A14，并形成 C03 可以直接消费的稳定中心与包契约。
- **前置依赖**：M3 获用户确认；各里程碑遗留和未执行环境已经列明。
- **交付范围**：复用 M0—M3 已通过结果，只补跨模块风险、部署装配、升级/恢复和文档交接；验证正式同源 bundle、容器包准入、数据库与包根联合备份恢复、OpenAPI/SDK 一致、旧中心能力缺失行为。整理 ZIP/TAR.GZ 代表性包样本和 C03 所需清单、占位符、resolve、下载及错误语义，不提前实现 C03。
- **验证入口**：在新的隔离 C01 场景使用正式 Center、Admin、PostgreSQL 和包目录走通“上传/替换完整包 → 上架 → 创建 Agent → 普通企业身份读取/resolve/下载 → 下架/重新上架 → 后台审计核对”。执行 Center `typecheck`、`lint`、相关单元/集成测试、`openapi:check`、`build:bundle`、`package:docker`，Admin `genapi:check`、`typecheck`、`lint`、相关测试和 `build`；按实际发布范围进行必要浏览器/文件系统验证，未具备的平台明确保留。
- **完成判定与 Review 重点**：C01-A01—A14 全部收口或未执行项经用户明确接受；数据库、包文件、API、Admin 展示和审计相符，恢复后可重新下载当前包，孤儿文件不反向生成业务记录。最小新增审查确认没有第二份身份、发布状态、平台包、安装状态、版本历史、队列或跨工程源码共享。

| --- | --- |

| 浏览器与组合路径 | 使用隔离 Center/Admin 和真实浏览器按当前里程碑抽查核心路径；大包、文件保存 API、窄窗口、缩放、焦点和取消按风险执行，不用截图或测试数量代替结论 |

## 六、C01 完成条件与交接

1. M0—M4 分别完成、验证并获用户确认，C01-A01—A14 与实际结果一致；未执行平台和环境有明确影响，不写成已通过。
2. 企业中心持有 Agent、插件、版本当前完整包和发布状态的唯一权威事实；Admin 仅发送管理意图和展示响应，C03 不需要读取中心数据库或包目录。
3. 每版本单一完整包、包内平台权威声明、同版本替换、SHA 条件下载、名称依赖和废弃语义已经通过正式 OpenAPI 与样本稳定交付；客户端同版本更新明确不在本循环实现。
4. 数据库迁移、受保护包目录、内容寻址文件、备份恢复、关闭和孤儿文件边界可运维；没有把测试数据、秘密或用户配置混入包或审计。
5. C01 循环验收获确认后才整理阶段总结并进入提交准备；提交、阶段归档和进入 C03 仍分别遵循用户授权及 C02 完成条件。C01 完成不代表 v0.28.0 已完成或可发布。
