## 二、背景、现状与目标

当前已有完整会话、工作空间、草稿、MCP/Skill 选择和 Host 文件能力，本循环调整其组织与入口，并补齐无用户工作目录的端到端行为。

| 已核查现状 | 对设计的影响 |
| --- | --- |
| AppShell 顶栏承载侧栏开关、应用标题、打开 Web、Runtime 状态、账号及窗口控制 | 移除顶栏必须为已有操作安排归宿，不能只隐藏容器 |
| 侧栏顶部当前为“新对话”下拉、搜索及“会话/已归档”切换，主控会话另占列表分组 | 高频入口改成“新建会话/助理会话”快捷菜单；移除常驻归档选项但保留归档业务与按需查询能力 |
| 固定会话仍位于工作空间/独立会话分组；列表已有分页和搜索 | 置顶复用已有持久事实，分组需保持分页、搜索及归档语义 |
| 新会话草稿按工作空间及无工作空间分别保存，每个归属一份，当前只在客户端进程内存在 | 切换初始化归属需要明确移动和冲突，不能默认覆盖目标草稿，也不新增草稿持久化系统 |
| 新建工作空间先调用目录选择，再打开编辑窗口；表单和 Host 均要求主目录 | 不选目录需要同步修改创建、编辑、冻结环境、存储与恢复假设 |
| Host 按规范化主目录复用/恢复工作空间；每个工作空间已有独立私有目录 | 私有目录可复用；无用户目录不能用相同空值或名称作为恢复身份 |
| 会话保存创建时目录和提示词；现有 Skill/MCP 选择器按当前草稿/会话加载可用项 | 新界面和快捷入口必须沿用同一执行及冻结边界 |

现状核查入口：`apps/desktop/src/app/AppShell/`、`features/sessions/SessionSidebar/`、`features/workspaces/WorkspaceEditorDialog/`、`stores/NewSessionDraftStore.ts`、`stores/RootStore.ts`；`crates/assistant-runtime/src/runtime/workspace.rs`；`apps/runtime-host/src/storage/workspace.rs`、`storage/session_resources.rs`、`resources/environment.rs`。上述为源码依据，不是文件级实现计划。

本循环完成后，用户能够：

1. 在侧栏通过“新建会话”“助理会话”快捷菜单进入高频任务，在左下角查看账号及连接状态并进入相关操作。
2. 将常用会话独立置顶，仍保持原工作空间归属。
3. 打开新会话页面后直接选择、切换或清空工作空间，使用可编辑的快捷装配入口。
4. 先填写工作空间名称，再决定是否添加工作目录；仅使用私有目录也能进行文件操作、运行任务并恢复历史。

## 四、功能范围与使用路径

### 4.1 工作台布局与窗口操作

布局仍由左侧导航、中间会话、右侧资源区组成。移除横跨应用的现有顶部菜单栏，中间区保留会话标题、子任务导航及必要操作；右侧资源和审批工作区沿用现有职责。

- 侧栏顶部安排原生窗口控制所需空间、展开/收起入口和主要导航操作；会话列表上方固定显示“新建会话”“助理会话”两个快捷菜单项，搜索及按需筛选作为紧凑图标操作；中部滚动展示会话，底部固定账号与 Runtime 入口。
- “新建会话”直接打开全局无工作空间草稿，不再在顶部展开工作空间下拉；在指定工作空间新建仍使用对应工作空间入口，并可在初始化页切换工作空间。
- “助理会话”打开既有主控/助理会话；它只是现有 Controller Session 的高频入口，不创建新的会话类型、列表或持久状态。未加载、不可用及无权限时展示真实状态，不生成替代会话。
- 移除会话列表顶部常驻的“会话/已归档”切换，不把“已归档”继续作为一级选项。默认列表只展示活动会话；归档动作及归档事实继续保留，需要查找历史时从搜索/筛选入口显式选择“已归档”，不新增回收站或改变恢复语义。
- 侧栏展开时，macOS 使用真实系统红绿灯并与侧栏顶部对齐；按钮和拖动区不能覆盖导航点击区。
- 侧栏收起时保留紧凑导航带，使展开导航和账号入口仍可直接访问；macOS 红绿灯始终可达。窄窗口先收起可让出的导航内容，不能把窗口控件或发送按钮挤出可视区。
- Windows/Linux 原生窗口保留最小化、最大化/还原、关闭及可拖动区域，位于可达的顶部局部区域，不恢复整条应用菜单栏。Web 不绘制原生红绿灯、拖动区或窗口控制。
- 点击、双击和拖动的原生语义沿用平台已有行为；键盘焦点、控件名称和浮层遮挡需要纳入交互验证。
- 收起导航或关闭桌面窗口不停止 Runtime。退出桌面客户端、退出登录、停止 Runtime 继续是不同动作。

紧凑导航带是本文已确认的展示方案，具体尺寸、折叠临界点、macOS 原生定位与全屏适配由后续交互指导和技术方案确定。

### 4.2 左下角账号与 Runtime 统一入口

展开侧栏时直接展示当前用户/个人身份、当前 Host 的可识别信息和 Runtime 连接状态；收起时使用紧凑入口和可展开详情，不用一个无文字的颜色点代替错误信息。

点击统一入口打开二级菜单：

- “设置”“修改密码”“退出登录”平级；修改密码只在既有身份能力支持时出现。
- Desktop 原“打开 Web 端”迁入同一菜单，仍使用独立普通登录，不改变鉴权方式；Web 不显示此项。
- Runtime 状态及错误可以查看；需要时提供既有“重新连接”。Host 配置、受控启停等仍经既有设置/生命周期入口执行，不在菜单中另造控制流程。
- 应用版本信息保留在设置的应用信息位置，不占用会话标题空间。

| 当前情况 | 表现与可操作范围 |
| --- | --- |
| 已连接 | 显示当前身份及 Host，按既有权限开放菜单 |
| 重连、断开、Runtime 停止或组件不匹配 | 显示实际状态与原因；保留可用的设置/连接入口，业务写操作不伪装可用 |
| 企业已认证但业务初始化失败 | 沿用现有初始化失败界面，可重试、改密或退出；不为展示侧栏创建假的业务快照 |
| 未登录或身份失效 | 使用现有登录入口和清理规则；不保留前一账号的会话、草稿或菜单身份 |

退出登录继续显示本人任务中断及各端退出影响确认；被动身份失效立即清理。入口移动不扩大普通 Web/远端 Desktop 的 Host 管理权限。

### 4.3 会话置顶独立分组

1. 将“固定会话”统一改称“置顶”，既有固定状态直接沿用。
2. “置顶”分组位于工作空间分组之前，样式和展开/折叠方式与独立会话一致。空分组可保持标题及简洁空态，不新增引导任务。
3. 置顶会话从原工作空间或独立会话列表抽出，只显示一次；可查看原归属，不复制会话、不移动工作空间绑定。
4. 取消置顶回到原分组，按原排序参与展示，不承诺回到历史屏幕行号。
5. 置顶列表复用既有会话排序、分页与固定状态。默认导航只展示活动会话；搜索/筛选显式切到“已归档”后只展示归档范围。搜索结果按既有搜索语义展示，不同时在分组重复命中条目。
6. 工作空间被移除时，其会话仍按既有规则隐藏，置顶不能绕过隐藏规则；恢复后按原置顶状态重新显示。
7. 置顶/取消失败时明确提示并以 Runtime 事实恢复显示；刷新、重连和重启不依靠客户端残留列表推断状态。

### 4.4 新会话初始化页面

从上到下组织快捷入口、初始化选项、任务输入区、既有底部工具栏。已选工作空间显示自定义名称及目录末级；未选中时显示“选择工作空间”，不在列表中加入“无工作空间”。C02 不放置 Agent 空按钮，C03 在同一选项区域增加 Agent 选择及依赖状态。

默认进入规则：

- 全局“新对话”直接打开无工作空间草稿，不要求先在下拉菜单选择目录。
- 工作空间上的“新对话”打开该工作空间草稿；若已有草稿则继续编辑，不创建另一份。
- 页面中的工作空间选择器可搜索活动工作空间、通过入口 close 按钮清空归属，或打开新建工作空间窗口；只显示自定义名称、目录末级或“仅私有目录”，同名同目录项再用短标识区分。
- 创建新工作空间成功后可作为当前草稿目标，按 4.5 的相同规则处理；取消创建时当前草稿和选择不变。
- 未连接时保留仍属于当前身份的可见草稿，提示连接问题；发送只在正式连接与配置条件满足后可用。
- 首次发送仍沿用既有会话物化及附件提交路径；选工作空间、点快捷入口、添加附件不提前创建 Session。
- 首条消息成功后转为正常会话布局；已有会话不出现可修改冻结归属的工作空间选择器。

### 4.5 工作空间切换、清空与草稿冲突

区分两种用户意图：从侧栏打开另一个草稿是“查看该草稿”；在当前初始化页面修改工作空间是“改变这份草稿的归属”。沿用每个工作空间和无工作空间各一份草稿的机制。

| 操作条件 | 本稿建议行为 |
| --- | --- |
| 从侧栏打开另一个工作空间草稿 | 原草稿保留，展示目标已有草稿或空草稿，不移动内容 |
| 在初始化页切换/清空，目标无内容且未自定义设置 | 移动当前草稿到目标归属，保留文字、附件选择、引用与执行选项；原位置不保留重复副本 |
| 目标已有文字、附件、引用、能力选择或自定义执行设置 | 不覆盖、不拼接；告知目标已有草稿，提供“取消”和“打开目标草稿并保留当前草稿” |
| 选择当前相同归属 | 不修改内容，不重新创建草稿或会话 |
| 首次发送正在进行 | 不允许同时移动草稿；先等待当前发送结果 |
| 首次发送失败或结果尚不明确 | 保留原草稿与已有重试事实；结果未知的物化请求在查明前不修改其冻结载荷。明确处理原物化尝试后再变更归属，不把一次重试变成另一个会话 |

“目标为空”不能只检查输入框文字；附件、引用、能力选择、非默认模型/执行设置及尚未解决的物化尝试都需要保护。冲突对话框不提供一键覆盖，避免为简单切换增加多草稿或自动合并机制。

移动后重新检查目标工作空间的 Skill/MCP 可用性和引用归属。文字与附件选择不静默删除；不可用能力、失效附件或引用在发送前标明并让用户处理，不把旧工作空间的能力选择当作目标已具备。异步加载、文件选择、上传和资源页回调仍按原 owner 核对，晚到结果不能写入另一个草稿。

清空归属等同切换至无工作空间草稿，不清空文本、不删除工作空间。仅私有目录工作空间仍是可选项；无工作空间是未选中状态，不进入浮层列表。

草稿继续遵循现有客户端进程生命周期，不新增写盘、跨端同步或历史草稿列表。跨 Host 或账号切换沿用现有清理规则，不能把旧用户的草稿移动到新域。

### 4.6 快捷入口

快捷入口是客户端代码内预设的装配方式，点击后让用户检查和继续编辑，不自动发送，也不改变核心任务类型。

C02 提供少量实际可用的入口，首先覆盖：

| 入口形式 | 点击结果 |
| --- | --- |
| 文本模板 | 将模板放入当前输入区，用户补充后发送；已有文本时先展示内容并选择追加或取消，不静默替换 |
| Skill | 复用当前工作空间的 Skill 选择；显示已选项并允许移除，继续现有按需加载 |
| MCP | 复用当前变体与上下文的 MCP 选择；显示已选服务并允许移除 |
| 组合入口 | 在现有可表达的选择和模板范围内一起应用，应用前检查冲突并展示结果 |

首批通用入口可采用“整理文档”模板、“使用技能”“使用 MCP 服务”，具体名称与模板文案在交互指导中评审。能力入口无可用项时显示原因并引导已有设置，不假装完成装配，也不在 C02 自动下载安装任何插件。C02 不为多项组合新增多选能力契约；C03 再接入真实 Agent 快捷装配。

快捷入口不会悄悄改动工作空间、模型或权限模式。再次选择有冲突的能力时明确提示将替换当前选择；已有文字和附件保持。快捷入口本身不成为第二份会话配置，最终控件中的实际选项才是发送依据。

### 4.7 新建与编辑工作空间

创建路径为：点击“新建工作空间” → 打开编辑窗口 → 填写名称 → 按需添加目录 → 保存。打开窗口时不弹出系统目录选择器、不创建业务工作空间。

- 名称为必填，沿用既有校验和可重名规则。首次选择目录可在名称仍空时带出目录名，不覆盖用户已填名称。
- 初始不选工作目录，窗口明确显示“仅使用私有目录”；用户也可以添加主目录及有序附加目录，沿用既有上限和去重规则。
- 取消目录选择只回到原编辑窗口；名称、目录列表和其他未保存内容保持。保存失败保留表单并展示实际原因。
- 同一编辑窗口允许修改名称、添加目录、设为主目录、调整附加顺序、移除目录；移除最后一个目录回到“仅使用私有目录”。还有目录时必须有一个主目录，不产生“只有附加目录”的新状态。
- 编辑只影响工作空间当前设置以及之后新建的会话；保存前明确告知已有会话仍用原目录。
- 放弃有改动的表单沿用现有产品确认对话框；创建成功只选择工作空间或打开其草稿，不生成空会话。

本机原生 Desktop 使用系统目录选择器；Web 或连接远端 Host 的 Desktop 使用既有 Host 目录选择器。所选目录必须属于当前 Host，不把客户端本机路径误发给远端。没有目录时由 Host 创建和管理私有目录，前端不拼装目录路径。

### 4.8 仅私有目录的执行与展示

这种工作空间仍是普通工作空间，拥有稳定身份、名称、会话归属和既有私有目录，不新增业务类型或切换模式字段。

| 范围 | 可观察行为 |
| --- | --- |
| 默认执行位置 | 文件相对路径、Agent Shell 默认 cwd、从该工作空间新开的用户终端均使用工作空间私有目录；不回退操作系统 Home 或 Host 进程 cwd |
| 多会话共享 | 同一工作空间的会话共享工作空间私有目录，各自保留 Session 私有目录和附件；无工作空间会话仍使用自己的 Session 私有目录 |
| 界面与提示词 | 显示“仅使用私有目录”及实际执行位置，区分当前工作空间配置与会话冻结位置；不把 Host 私有路径伪装成用户已选择的目录 |
| 文件权限 | 复用既有私有目录与冻结环境的授权规则及显式 Ask/Deny；不新增权限状态，不授予用户根或兄弟工作空间访问权 |
| Skill/规则发现 | 从实际工作位置沿用既有工作区发现约定，并保持个人/公共来源优先级；不扫描整个 Runtime Home，也不借无目录回退读 OS Home 的规则 |
| 资源失败 | 目录不可用或无法创建时返回明确失败，不展示为空列表或自动换至其他工作位置 |

目录从空改为有、从有改为空、替换主目录时，既有会话保持原冻结环境。Fork、恢复与 Clear 延续现有冻结语义；工作空间名称可更新，但旧会话目录与提示词不随新设置重写。新终端按其创建来源解析，已运行终端不被编辑操作自动换目录。

Host 数据整体移动时，仅按既有受管布局重定位可证明归属的私有资源；不能把合法重定位误解为允许按工作空间当前配置改写旧会话执行环境。具体兼容和重定位方案归技术方案。

### 4.9 移除、重新打开与恢复

- 移除工作空间继续是既有假删除：隐藏其工作空间和会话，不删除用户目录、工作空间私有文件或历史；未发送草稿仍按既有移除清理规则处理，不能承诺一并恢复。
- 有用户主目录的工作空间继续支持按原规范化目录恢复；活动目录冲突保留原校验，不能覆盖另一工作空间。
- 新建无工作目录工作空间始终创建新身份，即使名称相同也不合并。它不能通过“再次选择相同空目录”恢复。
- 在工作空间分组标题保留唯一的“恢复已移除工作空间”入口，活动列表为空时仍可打开；不在每个工作空间菜单重复设置。恢复时选择明确的原记录，至少能找回仅私有目录记录。使用名称、移除时间和目录摘要帮助区分同名项，恢复后沿用原身份、私有目录和历史会话。
- 恢复入口复用既有移除状态与保存事实，不增加回收站状态、独立管理页或过期删除策略。恢复失败保持已移除，不伪造新工作空间替代。

## 五、模块边界与跨循环交接

| 模块 | 本循环职责与契约影响 |
| --- | --- |
| Desktop/Web | 布局、账号菜单、分组、草稿移动/冲突、快捷入口与工作空间表单；复用现有连接与草稿 owner |
| Tauri | 原生窗口定位、拖动与控件适配；目录选择、资源打开仍经受控桥接，不装配 Runtime |
| assistant-runtime | 工作空间业务校验、恢复意图、会话冻结环境和权限派生；不认识快捷入口类别或窗口布局 |
| runtime-host | 可选用户目录的持久保存、私有目录建立及恢复，环境/文件/终端/Skill 装配和存储兼容；不另存会话权威状态 |
| assistant-protocol / TS 投影 | 表达真实的无用户工作目录、当前与冻结环境及必要恢复查询；保持轻量，不暴露物理表或 UI 草稿状态 |
| Agent Core / 工具适配器 | 沿用既有执行契约；只有上层装配变化，不增加“私有目录工作空间”执行分支 |

工作目录可选涉及已必填的跨层事实，必须统一检查生产者、消费者、持久化和恢复，不使用空字符串或假路径回避契约。恢复入口需要取得已移除记录和提交明确恢复意图；技术方案优先扩展既有工作空间生命周期与查询，不创建独立恢复实体。

C01 并行维护企业中心/Admin/OpenAPI；C02 不读取其新插件或 Agent 接口，也不修改中心 PostgreSQL 迁移。共享版本文件、根依赖和构建配置由协调方维护，发生交叉先协调唯一修改方。

交付 C03 的是可工作的初始化页面、原有草稿和实际选项机制，以及可空工作目录的完整 Host 能力。C03 在同一初始化区域接入 Agent 和依赖提示，快捷入口复用本循环的应用/冲突交互，不重新定义草稿或工作空间。

## 八、风险、兼容性与后续设计

1. **必填路径假设分布较广。** 仅改表单会导致环境构造、终端、Skill 扫描或恢复失败。技术方案须逐条核对路径来源，明确旧数据和旧客户端准入；不默认创建兼容双写。
2. **冻结环境与当前配置不同。** 空/非空目录变更不能按当前工作空间回填旧会话；受管目录重定位也不能扩大为任意历史改写。
3. **草稿和原生资源的生命周期。** 附件选择、上传、引用及右栏资源必须随真实 owner 处理，移动失败保持可恢复；不引入另一套草稿存储来规避。
4. **无目录恢复需要可发现入口。** 既有同主目录恢复不足，本文明确选择原记录的方案已随功能设计确认；精确查询、恢复契约和冲突处理归技术方案。
5. **窗口控制存在平台差异。** 红绿灯定位、全屏/缩放、原生浏览器覆盖和浮层都需实机检查；具体未覆盖平台在交付时声明。
6. **快捷入口不能承诺尚无的能力。** C02 只展示真实的已有选择和模板；C03 的 Agent/插件状态接入不得要求重做本循环的草稿所有权。

本循环需要技术方案：工作目录可选涉及协议、存储、环境冻结、恢复和跨层消费者；窗口控制与草稿资源迁移也有平台/生命周期取舍。
本循环需要界面交互设计指导：明确侧栏展开/收起及窄窗口、新会话空态与冲突对话框、创建/恢复工作空间窗口和连接异常的可操作表现。

功能设计及第六节取舍已确认；精确接口、迁移方案、恢复幂等与失败收尾、原生定位以及首批入口文案由[技术方案](技术方案.md)和[交互指导](界面交互设计指导.md)细化并确认。完成必要设计确认后才进入循环开发计划与首个实现里程碑。
