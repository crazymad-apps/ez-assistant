# v0.33.0 F02 技术方案：企业多模型结构与调用地址

## 一、方案结论

2026-11-05 用户要求聚焦企业模式下多模型的数据结构及 URL。本文替代此前的草案；用户已确认本方案方向。

依据：[功能设计](功能设计.md)、[总体设计](../../总体设计.md)。核心改动是将企业下发的单模型改为 Provider／模型集合，允许会话选择具体项，并与已有个人配置并存。身份、任务、队列、压缩、重试等复用现有机制，不在 F02 重新建设。

**调用地址沿用现有 Provider 级代理：同一个 Provider 共用一个基础 URL，模型由请求体 model 区分；不同 Provider 的基础 URL 不同。** 不为每个模型新增路由，也不改成所有 Provider 共用一个入口后再额外传 Provider 头。

## 二、企业中心的数据结构

现有 Provider、目录和固定参数本来就支持多个模型，保留这些结构；单模型限制主要在默认配置下发和代理只允许默认项。

| 数据 | 处理方式 |
| --- | --- |
| providers | 沿用组织归属、Provider ID、上游连接及密钥；一个 Provider 可提供多个模型 |
| model_fixed_configs | 沿用 Provider ID＋model ID 的固定参数，不复制模型配置 |
| model_settings | 保留组织默认 Provider／model 引用，增加“允许成员自主选择”开关，默认关闭 |
| 组织可用模型关联 | 新增 organization_id＋provider_instance_id＋model_id 的唯一关联；只存授权关系，参数仍从原目录／固定配置解析 |

默认模型必须是允许集合中的一项；空集合没有默认。已有默认失效时明确展示失效，不自动换模型。策略保存统一校验集合、默认和开关，复用现有事务与审计。

普通成员的有效集合：开关开启为全部获准项，关闭仅默认项。目录里存在某模型不等于成员可以调用。个人模型不写入这个集合。

## 三、下发从单项改为集合

继续使用现有 `GET /api/runtime/model-configuration`，一次返回当前组织的有效配置，不新增“每个模型一个配置接口”。以下是结构示意，字段沿现有 DTO 扩展，具体定义由 OpenAPI 生成：

```ts
{
  center_id,
  organization_id,
  allow_member_selection,
  default_model: { provider_instance_id, model_id } | null,
  providers: [{
    provider_instance_id,
    provider_type,
    provider_display_name,
    endpoint,                 // 该 Provider 的中心代理基础 URL
    protocol,
    server_history_enabled,
    server_history_support,
    models: [{
      model_id,
      state, reason,          // 单项可用性，不能让一个坏模型阻断其他项
      parameters,
      server_history_binding // 按具体模型及主体计算，不能在 Provider 下共用
    }]
  }]
}
```

下发仅包含成员获准项及安全配置，**不包含上游真实密钥**。endpoint 指向中心代理，不是上游地址；Host 根据已认证组织核对响应。集合级获取失败与模型本身不可用分别表达。管理员查看完整目录仍使用原管理接口。

Provider 信息放在外层，模型参数放在模型项，避免每个模型重复一整份连接配置。客户端可按“组织模型 → 服务商 → 模型”展示；模型实际身份为 Provider ID＋model ID，不能只用名称。

## 四、URL 如何复用

已有基础 URL：

```text
/api/llm/providers/{provider_instance_id}/v1
```

在此基础上沿用具体协议路径，例如 `/chat/completions`、`/responses`，以及已有 `/responses/compact`、`/responses/input_tokens`。同一 Provider、同一操作的多个模型调用同一个 URL，只改变请求体的 `model`。

| 选择 | 请求路径示例 | 请求体 |
| --- | --- | --- |
| Provider A 的 model-x | `/api/llm/providers/{A的UUID}/v1/chat/completions` | `{"model":"model-x", ...}` |
| Provider A 的 model-y | 同上 | `{"model":"model-y", ...}` |
| Provider B 的 model-x | `/api/llm/providers/{B的UUID}/v1/chat/completions` | `{"model":"model-x", ...}` |

表中 UUID 占位表示不同的实际 Provider ID，不是新增别名。相同模型名在不同 Provider 下由 URL 区分；同一 Provider 下由 model 区分。Responses／WS 继续复用各自已有传输路径，不增加模型专属 URL。

中心收到请求后按三项定位并授权：**凭据确定组织，URL 确定 Provider，请求体确定模型。** Provider 必须属于该组织，模型必须在当前策略允许范围；不能因为 URL 可猜测就放行。原来 admit 中“只能等于默认模型”的判断替换为该规则。调用记录仍保存实际 Provider／model。

个人模型继续使用本人配置的上游 endpoint，由 Host 直连，不套用中心代理 URL。切换 Provider 时换基础 URL，切换同 Provider 的模型时保持基础 URL；两者都使用所选模型自己的参数和续接绑定。

## 五、Runtime 与客户端的最小调整

1. **企业配置从单项变集合**：现有 ExternalModelConfiguration 扩为组织模型集合，保留真实 Provider ID，不再把所有企业模型压成同一个 managed Provider。
2. **显式选择生效**：现有 ModelSelection 增加来源 local／organization，保留 Provider ID＋model ID；local 在企业模式下显示为“个人”。null 仍表示跟随默认，企业默认来自组织，纯本地默认沿原逻辑。
3. **个人与组织配置并存**：复用 ConfigRegistry，组织刷新只替换组织集合，不清空本地 Provider、个人参数和会话选择。个人管理继续使用既有 Store 和命令；组织项只读。
4. **按所选来源装配调用**：组织项走现有 CenterModelTransport，个人项走现有 HostModelServiceFactory 直连。取消企业模式忽略显式选择及强制所有请求走中心的限制。
5. **界面复用**：现有模型选择器按来源分组；设置页从整体只读改为组织只读、个人可编辑。组织默认／允许集合在后台维护，普通成员不能通过本地编辑修改共享配置。

所选项失效时保留引用并报错，不按名称回退到另一来源。Run 内冻结配置、排队期间禁止换模、辅助模型能力检查和续接隔离都沿已有机制使用完整模型引用，不另建一套执行流程。

## 六、兼容与验证范围

- 旧组织默认作为初始允许集合的唯一项，开关关闭；null 选择继续跟随。旧 managed 显式引用无法证明真实 Provider 时要求重新选择，不猜测映射。个人数据不清空，组织密钥不复制到个人配置。
- 中心运行 DTO、Host 解析及 Rust／TS 的模型引用一起更新。企业协议拟由 5 提升为 6，配套客户端检查双来源能力；具体按 F01 最终基线核对，不改写 F01 验收结论。
- 核心验证：同 Provider 两模型共用 URL；不同 Provider 同名模型不串用；策略关闭／移除后直接代理请求被拒；个人直连不带中心凭据；组织刷新不覆盖个人配置；选择重启后保持，失效不自动切源。
- 实现时同步核对模型选择的持久化和既有续接绑定，来源变化不复用错误的原生上下文；无法兼容则保留历史并明确阻止继续。迁移遵循仓库原有备份与确认规则，本轮不执行。

### M1 实施边界

- 企业协议 `[6,6]` 的集合同时核对中心、当前组织和服务商代理路径。个人直连复用原 Adapter 和用户域身份核验，中心明确拒绝身份时停止发送，中心暂不可达时按 F01 保留仍有效的本地域。
- 显式引用保存来源、Provider 和 model ID。SQLite 升级保留旧 `managed` 的标识和历史，只标记为组织来源。旧记录缺少可靠的真实 Provider 证据时，要求重选。原跟随默认的空引用继续跟随。
- 企业域原生压缩窗口按完整选择、执行配置与 Conversation 绑定。接不上的窗口明确报错。仍依赖原生窗口的会话切到本地摘要时拒绝发送，避免隐式丢弃前缀。既有企业域原生窗口若无法匹配新绑定，需要继续使用可证明相容的历史或新建会话。
- 当前 Host 已可通过正式命令保存与执行选择，Desktop／Host Web 的双来源管理与选择交互按 M2 实施。
