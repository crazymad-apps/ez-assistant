## 三、审查发现

### 3.1 高优先级：`ModelRoute.endpoint` 未参与路由校验

涉及位置：

- `crates/agent-model/src/route.rs:16`。
- `crates/agent-provider-openai-compatible/src/service.rs:112`。

`ModelRoute.endpoint` 明确定义为 HTTP 类协议的 base URL，但 `OpenAiCompatibleService::check_route` 只校验 provider 和 protocol。实际请求始终发往构造服务时传入的 `base_url`，不会核对请求中的 endpoint。

当 Runtime 选错同 Provider、同协议但不同 endpoint 的服务实例时，请求会被静默发往服务实例绑定的目标；调用链和调试信息仍可能记录 `route.endpoint`，造成实际请求目标与路由、审计信息不一致。

建议：

1. 明确 endpoint 的唯一事实来源。
2. 如果 endpoint 保留在 `ModelRoute`，Adapter 应在请求建立前对规范化后的 endpoint 进行严格匹配，不匹配时返回 `ModelError::Route`。
3. 增加 endpoint 不匹配且 Transport 未收到请求的回归测试。

### 3.2 高优先级：空工具列表会静默取消显式工具选择约束

涉及位置：`crates/agent-provider-openai-compatible/src/encode.rs:47`。

`encode_request` 在 `request.tools` 为空时无条件省略 `tool_choice`。因此：

- `ToolChoice::Required` 会静默退化为 Provider 默认行为。
- `ToolChoice::Named` 会静默退化为 Provider 默认行为。
- `ToolChoice::Named` 在工具列表非空时也没有验证指定名称是否存在。

调用方显式要求必须使用工具时，模型仍可能直接回答。这改变了请求语义，也隐藏了上游工具装配错误。

建议：

1. `Auto` 和 `None` 在无工具时可以省略。
2. `Required` 和 `Named` 在无工具时返回 `ModelError::Config`。
3. `Named` 必须验证目标名称存在于 `request.tools`。
4. 补充空工具列表和具名工具不存在的回归测试。

### 3.3 高优先级：响应流中断可能被错误报告为成功

涉及位置：`crates/agent-provider-openai-compatible/src/service.rs:281`。

`event_stream` 将 `BodyStream` 的 `Err` 和正常 EOF 一并中止读取，随后调用 `ChunkAssembler::finalize`。如果中断前已经收到 `finish_reason`，`finalize` 会生成 `TurnFinished`。

因此，在 finish chunk 之后、usage 或 `[DONE]` 之前发生连接重置时：

- 真实传输失败可能被报告为成功。
- usage 等尾部信息可能静默丢失。
- 上层无法据此决定是否需要重试或记录传输异常。

现有中断测试只覆盖了尚未收到 `finish_reason` 的场景，没有覆盖该分支。

建议：

1. `Some(Err(error))` 应立即产生唯一的 `TurnFailed(ModelError::Transport(...))`。
2. 正常 EOF 与传输错误应保持不同语义。
3. 增加“finish chunk 后出现 `BodyStep::Fail`”的回归测试，并断言最终状态为传输失败。

### 3.4 中优先级：`provider_options` 可覆盖或伪造规范请求字段

涉及位置：

- `crates/agent-model/src/request.rs:74`。
- `crates/agent-provider-openai-compatible/src/encode.rs:101`。
- `crates/agent-provider-openai-compatible/src/encode.rs:127`。
- `crates/agent-provider-openai-compatible/src/schema.rs:36`。

匹配 Provider 命名空间的私有选项未经字段冲突检查写入 `extra`，再由 `#[serde(flatten)]` 平铺到请求根。

具体风险：

- 私有选项可以覆盖已经写入 `extra` 的 `max_tokens`、`reasoning_effort` 等动态字段。
- 使用 `model`、`messages`、`stream`、`tools` 等保留键时会生成重复 JSON 字段；Provider 对重复键的处理可能改变模型、消息、流式模式或工具定义。
- `ProviderOptions` 的透明派生反序列化会绕过 `insert` 对空命名空间和非对象值的校验；编码器又会静默忽略非对象值。

建议：

1. 为 `ProviderOptions` 实现受控反序列化，复用构造期不变量。
2. 定义并拒绝请求根保留键。
3. 合并私有选项时检测与动态 Profile 字段的冲突，不允许静默覆盖。
4. 增加保留键、动态字段冲突和非法反序列化输入测试。

### 3.5 中优先级：debug 推送会阻塞模型主流程

涉及位置：

- `tools/debug-viewer/src/client.rs:21`。
- `tools/debug-viewer/src/client.rs:49`。
- `crates/agent-provider-openai-compatible/examples/chat.rs:119`。
- `crates/agent-provider-openai-compatible/examples/chat.rs:157`。

`DebugClient::post` 直接等待 HTTP 请求完成，客户端使用的默认 reqwest 配置没有请求超时。CLI demo 又在请求建立和每个模型事件上串行等待 `post`。

当 viewer 接受连接但迟迟不返回响应时，模型事件消费会无限挂起；即使 viewer 正常工作，每个 delta 也会增加一次串行 HTTP 往返。这与模块约束中的“fire-and-forget、绝不影响主流程”不符。

建议：

1. 主流程只向有界队列执行非阻塞入队。
2. 使用独立发送任务消费队列。
3. 为连接和请求设置较短超时。
4. 明确队列满、发送失败和关闭时的丢弃及一次性告警策略。
5. 增加 viewer 不响应时模型主流程仍能继续的确定性测试。

### 3.6 中优先级：流式响应未验证后续 chunk 的身份一致性

涉及位置：`crates/agent-provider-openai-compatible/src/decode.rs:88`。

`ChunkAssembler` 只使用首个 chunk 的响应 ID 和模型，后续 chunk 的 `id`、`model` 和 choice index 没有与首个值进行一致性校验。来自不同响应或不同 choice 的数据可能被合并进同一 `AssistantMessage`，并被错误归属到首个响应身份。

外层 `LifecycleValidator` 只能看到组装后的规范事件，无法发现原始 chunk 身份变化。

建议：

1. 首个有效 choice chunk 确立响应 ID、模型和 choice index。
2. 后续 chunk 必须与已确立身份一致，否则返回 `ModelError::Protocol`。
3. 明确 usage-only chunk 的身份校验规则。
4. 增加响应 ID、模型和 choice index 中途变化的回归测试。

### 3.7 低优先级：debug-viewer 架构文档互相矛盾

涉及位置：

- `docs/modules/debug-viewer.md:5`。
- `docs/modules/debug-viewer.md:13`。
- `docs/重要决策与变更记录.md:26`。
- `tools/debug-viewer/src/server.rs:39`。

提交中的模块文档同时声明使用 `ServeDir` 和使用 `include_str!` 内嵌静态页；重要决策记录也写为“内嵌静态页”，而实际代码使用 `ServeDir` 从源码目录运行时读盘。

建议在 `M7` 收口时选定一种交付语义，并同步模块约束、重要决策、开发计划和实现说明。
