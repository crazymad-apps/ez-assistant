# v0.1.0 开发计划：基础类型与模型层

## 一、计划信息

- 版本：`v0.1.0`
- 状态：已确认
- 版本设计：[`版本设计.md`](版本设计.md)
- 上位架构：[`Agent 系统技术架构`](../../modules/agent-system.md)
- 开发范围：规范类型、单次模型 Turn、OpenAI-compatible/DeepSeek Adapter 和 testkit。

本计划不包含 `v0.2.0` 的 Agent Engine、工具执行和多轮工具循环。计划确认前不进入代码实现。

## 二、实施原则

- 严格按里程碑依赖顺序推进；当前里程碑验证通过后再进入下一项。
- 每个里程碑完成实现和验证后，状态先更新为“待确认”并停止工作；只有用户明确确认后才更新为“已完成”并进入下一里程碑。
- 每个公共类型和 trait 必须有本版本内的实际调用方或替换边界。
- Provider-neutral 类型不出现 OpenAI、DeepSeek、HTTP、SSE 或应用协议字段。
- Provider 原生 schema、参数兼容和特殊消息只存在于 Adapter。
- 默认 Harness 完全离线、确定性运行；真实 API smoke test 不作为版本完成前提。
- 不为后续 Agent Loop、Context、Safety 或 Memory 提前创建空抽象。
- 实施中发现设计边界需要改变时，先更新版本设计与本计划，再扩大代码范围。


## 六、M1：`agent-types` 规范类型

### 目标

建立能够承载普通对话、reasoning 和 tool-call 往返的最小 Provider-neutral 数据模型。

### 实施内容

1. 标识类型：
   - `MessageId`
   - `PartId`
   - `ToolCallId`
   - `ProviderId`
   - `ProtocolId`
2. 规范对话：
   - `ConversationSnapshot`
   - `ConversationMessage::{System, User, Assistant, Tool}`
   - `SystemMessage`、`UserMessage`、`AssistantMessage`、`ToolMessage`
3. Assistant 内容：
   - `ReasoningPart`
   - `TextPart`
   - `ToolCall`
   - `OpaqueProviderState`
4. Tool 模型协议类型：
   - `ToolDefinition`
   - `ToolChoice`
   - Tool arguments
   - `ToolResult`
5. 模型结果值：
   - `ModelIdentity`
   - `FinishReason`
   - `TokenUsage`
6. 为不变量提供受控构造：
   - 非空/格式受限的标识和名称。
   - Tool Result 必须关联 `ToolCallId`。
   - Assistant Part 保持原始顺序。
   - opaque state 必须携带 Provider、Protocol、状态类型和格式版本。
7. 实现必要的序列化 round-trip；不把 Provider 原生 JSON 结构作为公共类型。

### 测试

- 每个 ID newtype 的构造、比较和序列化。
- 四种 Conversation Entry round-trip。
- reasoning/text/tool call/provider state 混合顺序保持。
- 多 Tool Call 与对应 Tool Result 关联。
- 非法名称、缺失 call ID 和非法 opaque state 被拒绝。
- 未知 Provider State payload 可原样往返，但不会被规范层解释。

### 验证

```bash
cargo test -p agent-types
cargo clippy -p agent-types --all-targets --all-features -- -D warnings
```

### 完成判定

- 能表达 DeepSeek 工具调用前后的完整规范对话。
- crate 无 I/O 和应用层依赖。
- 所有公开不变量均有测试。

## 七、M2：`agent-model` 单次调用 SPI

### 目标

定义一次 Provider Turn 的请求、流式事件、错误、取消和生命周期边界。

### 实施内容

1. `ModelRoute` 与 `ModelCapabilities`：
   - Provider、协议、模型和 endpoint 标识。
   - reasoning、tool call、stream 等能力声明。
2. `ModelRequest`：
   - system parts。
   - 规范历史对话。
   - Tool definitions 和 choice。
   - generation/reasoning 配置。
   - 命名空间隔离的 Provider options。
3. `ModelCallContext`：
   - cancellation token。
   - 可选 trace/correlation context。
   - 不包含 `RunId` 和 credential。
4. `ModelService` 与 `ModelEventStream`。
5. 规范事件：
   - Turn start/terminal。
   - reasoning/text part lifecycle。
   - tool-call lifecycle。
   - usage 更新。
6. `ModelError` 分类：配置、路由、认证、Transport、Provider、限流、协议、Tool arguments 和取消。
7. 实现流生命周期验证器：
   - Part start/delta/finish 配对。
   - Tool arguments 完整性。
   - 唯一终态。
   - 终态后数据拒绝。
8. credential 以 Adapter 构造依赖注入，不进入请求、上下文、事件和 debug 输出。

### 测试

- 合法纯文本、reasoning、tool-call 事件序列。
- delta 缺少 start、重复 finish、终态缺失、双终态和终态后事件。
- 调用建立前失败与流建立后失败的语义差异。
- 不同阶段取消只产生一个受控结果。
- 错误展示不泄露 prompt、credential 或原始敏感 body。

### 验证

```bash
cargo test -p agent-model
cargo clippy -p agent-model --all-targets --all-features -- -D warnings
```

### 完成判定

- Fake 实现可以只通过 SPI 完成一次 Model Turn。
- 生命周期验证不依赖任何具体 Provider。
- 模型层没有工具执行或自动继续逻辑。

### 实际结果

状态：✅ 已完成（2026-07-17 实现与验证通过，用户 review 确认）。

产出（`crates/agent-model/src/`）：

- `route.rs`：`ModelRoute`（provider/protocol/model/endpoint）、`ModelCapabilities`（reasoning/tool_calls/streaming，默认不支持）。
- `request.rs`：`ModelRequest`（route、system、conversation、tools、tool_choice、generation、reasoning、provider_options）、`GenerationConfig`、`ReasoningConfig`/`ReasoningEffort`、`ProviderOptions`（命名空间隔离、仅接受 JSON 对象）。
- `context.rs`：`ModelCallContext`（`CancellationToken` + 可选 `TraceContext`），不含业务 `RunId` 与 credential。
- `event.rs`：`ModelEvent` 十一个变体；`TurnFinished` 携带完整聚合的 `AssistantMessage`（finish reason 与最终 usage 在其中）；opaque provider state 无流事件，只出现在最终消息。
- `error.rs`：`ModelError` 九个分类（Config/Route/Auth/Transport/Provider/RateLimited/Protocol/ToolArguments/Cancelled），纯数据值类型（Clone/Eq），只携带脱敏诊断信息。
- `service.rs`：`ModelService` trait（`capabilities()` + `stream()`）。
- `lifecycle.rs`：`LifecycleValidator` 流包装器。

最终 Rust 签名（版本设计第八节概念接口的落地）：

```rust
pub trait ModelService: Send + Sync {
    fn capabilities(&self) -> &ModelCapabilities;
    fn stream(&self, request: ModelRequest, context: ModelCallContext) -> ModelStreamFuture<'_>;
}

pub type ModelStreamFuture<'a> =
    Pin<Box<dyn Future<Output = Result<ModelEventStream, ModelError>> + Send + 'a>>;
pub type ModelEventStream = Pin<Box<dyn Stream<Item = ModelEvent> + Send>>;
```

关键语义：

- 建立前失败（含建立前取消）由 `stream` 返回 `Err`；流建立后失败与流中取消以唯一 `TurnFailed` 终态结束。
- `LifecycleValidator` 强制：首个非终态事件必须是 `TurnStarted`；Part 按 ID 配对（允许不同 Part 交错）；`TurnFinished` 时不允许未结束 Part 且消息 ID 必须与 `TurnStarted` 一致；缺终态补发 `TurnFailed(Protocol)`；终态后数据一律丢弃；契约违反以唯一 `TurnFailed(Protocol)` 替换。
- 测试不启动 Tokio runtime：用 noop waker 手动 poll，无 sleep、无网络，全确定性。

验证（实际执行）：

- `cargo fmt --all --check` 通过。
- `cargo clippy -p agent-model --all-targets --all-features -- -D warnings` 通过。
- `cargo test -p agent-model`：23 个测试全部通过（合法文本/reasoning/交错 tool-call 序列；delta 缺少 start、重复 finish、终态前事件、双 start、终态缺失、双终态、终态后事件、开放 Part 终态、消息 ID 不一致；建立前失败与流中失败语义差异；建立前与流中取消的唯一受控结果；错误 Display 脱敏；ProviderOptions 校验；Fake 仅通过 SPI 完成完整 Turn）。
- `cargo clippy --workspace --all-targets --all-features -- -D warnings` 与 `cargo test --workspace` 通过（agent-types 10 个测试保持通过）。

偏差：

- 修复 M1 遗漏：`agent-types` 根部未导出 `ToolCall`（`AssistantPart::ToolCall` 的载荷类型无法具名引用），已在 `crates/agent-types/src/lib.rs` 补上导出；纯增补，不改变任何 JSON 形态。

遗留/风险：无已知阻塞；`LifecycleValidator` 对终态后违规数据按契约静默丢弃（不产生第二个终态），如后续版本需要观测此类违规，可在 Runtime 事件层补充。

## 八、M3：`agent-testkit` 确定性测试能力

### 目标

为 Provider Adapter 和后续 Agent Engine 提供可脚本化、无网络、无 sleep 竞态的测试基础。

### 实施内容

1. `ScriptedModelService`：按脚本返回事件、建立失败或流中失败。
2. `RecordedTransport`：记录请求并按 fixture 返回 HTTP/SSE 数据。
3. `EventCollector`：收集事件并断言生命周期和最终 AssistantMessage。
4. 可控 cancellation gate/barrier。
5. 错误、流中断和畸形响应注入。
6. fixture 约定：
   - 可审阅文本格式。
   - 不包含真实凭据、用户内容或不可再现动态值。
   - 明确 Provider profile 和预期规范事件。

### 测试

- Scripted 纯文本、reasoning、tool-call 和失败脚本。
- Recorded Transport 请求捕获与响应回放。
- cancellation gate 不依赖不稳定 sleep。
- fixture 中敏感 header 和 token 被拒绝或脱敏。

### 验证

```bash
cargo test -p agent-testkit
cargo clippy -p agent-testkit --all-targets --all-features -- -D warnings
```

### 完成判定

- 后续 Adapter 契约测试不需要真实网络。
- 所有关键时序均可确定性控制。
- testkit 不进入生产依赖闭包。

### 实际结果

状态：✅ 已完成（2026-07-17 实现与验证通过，用户 review 确认）。

产出（`crates/agent-testkit/src/`）：

- `script.rs`：`ScriptedModelService`（`ModelService` 的脚本化 Fake）+ `ModelScript::{FailEstablishment, Events}` + `message_events`（由完整 AssistantMessage 生成规范事件序列）。记录每次调用的规范请求供断言；建立前取消返回 `Err(Cancelled)`，流中取消以唯一 `TurnFailed(Cancelled)` 结束。
- `record.rs`：`RecordedTransport` 按序回放 fixture 响应并捕获全部请求；`RecordedResponse` body 为有序 `BodyStep::{Chunk, Fail}`，可注入中途断流（`Interrupted{after_bytes}`）；建立前失败以 `Connect` 脚本表达；`UnexpectedRequest` 提示 fixture 不足。
- `collect.rs`：`EventCollector::collect` / `collect_validated`（先套 `LifecycleValidator`），`CollectedEvents` 提供 `assert_single_terminal` / `assert_finished` / `assert_failed` 等断言。
- `cancel.rs`：`CancelGate` —— token 交给 `ModelCallContext`，`watch` 包装任意事件流并计数，`cancel_after(n)` 在第 n 个事件后精确取消（无 sleep）。
- `fixture.rs`：`validate_request` / `validate_response` 拒绝敏感 header（authorization/cookie 等）与疑似 credential 文本模式（`Bearer `/`sk-` 等）；违规信息只含 header 名与位置，不携带值。

设计要点：

- `CancelGate.watch` 是流组合子而非服务内嵌逻辑，可包装任意 `ModelService` 的输出（含未来真实 Adapter）。
- 畸形事件序列通过 `ModelScript::Events` 原样回放注入，与 `LifecycleValidator` 组合验证消费方契约处理。
- 未自建 barrier：`tokio::sync::Barrier` 已覆盖并发汇合语义，不为无差异化行为新增抽象（替代计划中的 barrier 项）。
- `RecordedTransport` 以值类型承载 HTTP 语义，与 M5 的 Transport trait 桥接（trait 定义属 M5 Adapter 边界）。
- 测试用 `#[tokio::test]` 驱动异步收集，无网络、无 sleep、无用户目录 I/O。

验证（实际执行）：

- `cargo fmt --all --check` 通过。
- `cargo clippy -p agent-testkit --all-targets --all-features -- -D warnings` 通过。
- `cargo test -p agent-testkit`：13 个测试全部通过（scripted 纯文本/reasoning/tool-call 完成、建立前与流中失败、脚本耗尽、畸形序列原样回放与 validator 拦截、请求捕获与按序回放、connect 失败、断流字节计数、fixture 敏感信息拒绝与脱敏、gate 精确取消与建立前取消）。
- `cargo clippy --workspace --all-targets --all-features -- -D warnings` 与 `cargo test --workspace` 通过（agent-model 23、agent-types 10 保持通过）。

偏差：

- `crates/agent-testkit/Cargo.toml` 增加 `serde_json` dev-dependency（测试构造 JSON 值；生产依赖未变）。
- barrier 未实现（理由见上）；fixture 只落地"校验"职责，可审阅文本格式随 M4/M6 的首批真实 fixture 定型。

遗留/风险：M2 的 agent-model 单测保留了自带的 mini fake（agent-model 不能反向依赖 testkit，避免循环），与 `ScriptedModelService` 存在少量逻辑重叠；不影响行为。

## 九、M4：OpenAI-compatible 纯协议 Codec

### 目标

在不涉及真实 HTTP 的情况下完成规范请求与 Chat Completions 原生协议之间的双向转换。

### 实施内容

1. 定义 Adapter 内部原生 schema：
   - request messages。
   - tool definitions/choice。
   - assistant tool calls。
   - tool result messages。
   - response/chunk、usage、finish reason 和 error body。
2. 实现 canonical → native 编码：
   - system/user/assistant/tool。
   - reasoning/text/tool calls。
   - tool call/result ID。
   - generation/reasoning/provider options。
3. 实现 native chunk → canonical event 解码器。
4. 使用 Tool Call index/ID 聚合跨 chunk arguments。
5. 未知兼容字段默认忽略；影响继续对话的字段必须显式映射或进入受控 Provider State。
6. Profile 决定字段名称和参数支持，不在 Codec 外散落 Provider 名称判断。

### 测试

- 普通文本请求和响应。
- system + 多轮消息编码。
- reasoning 与 text 分片交错。
- 单个、并行、arguments 跨 chunk 的 Tool Call。
- Tool Result 的 `tool_call_id` 回填。
- finish reason 和 usage 映射。
- 畸形 JSON、未知 tool index、重复 call ID 和不完整 arguments。
- canonical → native → canonical 语义往返。

### 验证

```bash
cargo test -p agent-provider-openai-compatible codec
cargo clippy -p agent-provider-openai-compatible --all-targets --all-features -- -D warnings
```

### 完成判定

- Codec 单元测试完全不启动 HTTP 服务。
- Provider 原生类型没有泄漏到 `agent-types` 或 `agent-model`。
- Tool Call 分片能稳定组装并产生合法规范事件。

### 实际结果

状态：✅ 已完成（2026-07-20 实现与验证通过，用户 review 确认）。

产出（`crates/agent-provider-openai-compatible/src/`）：

- `profile.rs`：`Profile` 方言配置（reasoning 字段名、reasoning effort 字段名、generation 参数支持、max tokens 字段名）+ `Profile::openai_compatible()` 基础方言；Codec 不判断 Provider 名称，DeepSeek 具名方言留待 M6。
- `schema.rs`：Chat Completions serde wire 类型（request/messages/tool defs/choice/assistant tool calls/tool result/response/chunk/usage/error body）；未知字段默认忽略；随方言变化的 reasoning 字段经 `#[serde(flatten)]` extra map 承接、按 Profile 字段名查取。
- `encode.rs`：`encode_request(&ModelRequest, &Profile) -> Result<ChatRequest, ModelError>`——system 头部按序逐条、user 单 part 字符串/多 part 数组、assistant 的 reasoning/text 各自保序拼接 + tool_calls、tool result `tool_call_id` 回填、generation/reasoning 按 Profile 支持输出（设置但不支持 → `Config`）、`provider_options` 按 Provider 命名空间合并进请求根、固定 `stream: true` + `include_usage`。

- `codec_tests.rs`：28 个离线测试，纯同步、无 Tokio、无网络。
- 错误复用 `agent_model::ModelError`（Protocol/ToolArguments/Config），文本只含字段名与 index 等脱敏诊断。
