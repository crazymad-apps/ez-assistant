# v0.1.0 版本设计：基础类型与模型层

## 一、版本信息

- 版本：`v0.1.0`
- 状态：已确认
- 开始日期：2026-07-17
- 上位约束：[`Agent 系统技术架构`](../../modules/agent-system.md)
- 模块约束：[`agent-core`](../../modules/agent-core.md)
- 关联输入：当前无独立输入文档，范围来自 Agent Core 版本路线图。

## 二、版本目标

建立 Agent Core 最底层、与应用和具体 Provider 解耦的模型能力，使调用方能够：

1. 使用统一规范表达 system、user、assistant、reasoning、tool call 和 tool result。
2. 发起一次独立模型 Turn，并消费结构化流式事件。
3. 通过 Provider Adapter 将规范请求转换为 OpenAI-compatible 请求并解析响应。
4. 无损保留 DeepSeek thinking mode 工具调用链所需的 `reasoning_content`、`tool_calls` 和 `tool_call_id`。
5. 使用 scripted/recorded testkit 在不访问真实网络的情况下验证协议行为。

本版本完成的是模型层闭环，不实现 Agent 工具循环。

## 三、非目标

以下内容明确不进入 `v0.1.0`：

- `AgentExecution` 状态机和多轮工具循环。
- Tool Registry、Tool Dispatcher 和真实工具执行。
- FileSystem/Shell 能力契约及实现。
- Conversation Journal、Execution Recorder 和持久化。
- Prompt Compiler、token 预算、上下文压缩和 overflow 恢复。
- Safety、Approval、执行预算和 Guardrail。
- Memory Service、Memory Plugin 和长期记忆实现。
- Runtime 会话、业务 Run、`RunId`、调度和 Tauri 集成。
- Anthropic、Gemini、OpenAI Responses API 等其他协议 Adapter。
- Provider 模型目录、账户配置 UI、自动模型回退和计费策略。

上述能力分别由 `v0.2.0` 及后续版本实现。

## 四、当前实现核查

当前仓库只有最小占位实现：

- `crates/agent-core/src/agent.rs`、`model.rs`、`tool.rs` 尚无领域实现。
- `agent-core` 仍直接依赖 `assistant-protocol`，与 Core 内部模型类型不进入应用协议的目标边界不一致。
- 当前没有规范消息、模型流、Provider Adapter、协议测试或 testkit。
- Runtime 和 Desktop 均未形成对 Core 公共 API 的实际依赖，可在本版本内直接建立正确边界，无需兼容迁移。

## 五、总体设计

```text
Caller
  │ canonical ModelRequest
  ▼
ModelService
  │
  ▼
OpenAI-compatible Adapter
├── Route / Capability Profile
├── Protocol Codec
├── HTTP Transport
└── Stream Decoder
  │ canonical ModelEvent stream
  ▼
Caller / Testkit
```

模型层一次只处理一个 Provider Turn：

```text
规范请求 → Provider 请求 → 流式响应 → 规范事件 → 唯一终态
```

模型层不执行工具，也不因收到 Tool Call 自动发起下一次请求。

## 六、目标物理边界

`v0.1.0` 计划建立以下 crate 边界：

```text
agent-types
    ▲
    ├── agent-model
    │       ▲
    │       └── agent-provider-openai-compatible
    │
    └── agent-testkit

agent-core
    └── 后续承载 Agent Engine；本版本不成为 Provider 实现容器
```

### 6.1 `agent-types`

承载 Provider-neutral、无 I/O 的规范类型：

- 消息、内容 Part 和对话快照。
- `MessageId`、`PartId`、`ToolCallId` 等协议标识。
- Tool definition/call/result 的模型协议类型，不包含工具执行 trait。
- token usage、finish reason、模型标识和错误分类所需值类型。

约束：

- 不依赖 Tokio、HTTP、Tauri、Runtime、数据库和 Provider SDK。
- 不依赖 `assistant-protocol`。
- 不放置服务 trait、全局 Registry 或运行时句柄。

### 6.2 `agent-model`

承载单次模型调用的稳定边界：

- `ModelService`。
- `ModelRequest` 和 `ModelCallContext`。
- `ModelEvent`、`ModelEventStream` 和 `ModelError`。
- Provider Route、Capability 和 Codec/Transport 所需的公共接口。
- 流生命周期与唯一终态约束。

本 crate 不知道具体 API Key 来源、配置文件位置和应用 Session。

### 6.3 `agent-provider-openai-compatible`

承载 OpenAI Chat Completions 兼容协议 Adapter：

- OpenAI-compatible 请求/响应 schema。
- 规范消息编码和流式 chunk 解码。
- HTTP/SSE Transport 实现及可替换测试 Transport。
- OpenAI-compatible 方言能力配置。
- DeepSeek profile 与 reasoning/tool-call 兼容。

Provider Adapter 不依赖 `agent-core`，只依赖 `agent-model` 和 `agent-types`。

### 6.4 `agent-testkit`

提供其他 Core crate 共用的确定性测试能力：

- Scripted Model Service。
- Recorded Transport 和响应 fixture。
- Model event collector/assertion。
- 规范消息与 Provider 请求的往返测试辅助。
- 可控取消点和错误注入。

testkit 不进入生产执行路径。

### 6.5 `agent-core`

保留为未来 Agent Engine 的主 Facade/编排 crate。本版本只允许建立对基础 crate 的合理依赖，不通过大规模 re-export 提前承诺公共 API，也不放入 Provider HTTP 实现。

现有 `agent-core -> assistant-protocol` 依赖在本版本实现阶段移除。

## 七、规范对话模型

### 7.1 对话条目

`v0.1.0` 只定义模型调用实际需要的最小集合：

```rust
pub enum ConversationMessage {
    System(SystemMessage),
    User(UserMessage),
    Assistant(AssistantMessage),
    Tool(ToolMessage),
}
```

`ContextSummary` 在上下文系统版本中引入，本版本不提前定义未被调用的行为。

### 7.2 User Message

用户消息由有序片段组成，区分真实输入与应用注入文本：

```rust
pub struct UserMessage {
    pub id: MessageId,
    pub parts: Vec<UserPart>,
}

pub enum UserPart {
    Text(TextPart),
    Injected(TextPart),
}
```

- `Text`：用户真实输入；`Injected`：上层应用注入的约束/上下文文本。
- 引入原因：UI 展示需隐藏注入片段，注入语义必须随持久化存活，落盘重建后仍可区分。
- 回放时 `Injected` 仍进入发给模型的内容；Core 与 Adapter 不关心来源，只在 UI 消费时过滤。
- `parts` 序列化形态由 `Vec<{id, text}>` 变为 `Vec<{type, data}>`（tag 为 `text` / `injected`）；v0.1.0 无已发布持久化数据，无需迁移。
- 多模态片段（图片、文件等）在后续版本以新变体扩展。

### 7.3 Assistant Message

一次 Assistant 响应作为有序、原子的消息：

```rust
pub struct AssistantMessage {
    pub id: MessageId,
    pub model: ModelIdentity,
    pub parts: Vec<AssistantPart>,
    pub finish_reason: FinishReason,
    pub usage: Option<TokenUsage>,
}

pub enum AssistantPart {
    Reasoning(ReasoningPart),
    Text(TextPart),
    ToolCall(ToolCall),
    ProviderState(OpaqueProviderState),
}
```

Part 顺序必须保留。UI 是否展示 reasoning 与规范对话是否保存 reasoning 是两个独立问题。

### 7.4 Tool Call 与 Tool Result

本版本只定义模型协议需要的数据：

- Tool 名称和 JSON Schema definition。
- 流中逐步形成的 Tool Call。
- 已校验为完整 JSON 值的最终 arguments。
- `ToolCallId` 与 Tool Result 的严格关联。
- 文本和结构化 Tool Result 表达。

工具输入 schema 校验和真实执行属于 `v0.2.0`。

### 7.5 Provider State

只有无法稳定映射到规范 Part、但 Provider 后续请求必须回传的内容才进入 `OpaqueProviderState`。它至少携带：

- Provider/Protocol 标识。
- 状态类型和格式版本。
- 不透明 payload。

DeepSeek 的文本 `reasoning_content` 应映射为规范 `ReasoningPart`，不能因为实现方便全部塞入 opaque payload。

## 八、模型服务契约

概念接口如下，最终 Rust 签名在开发计划中确定：

```rust
pub trait ModelService: Send + Sync {
    fn stream(
        &self,
        request: ModelRequest,
        context: ModelCallContext,
    ) -> ModelStreamFuture;
}
```

### 8.1 ModelRequest

包含：

- 已解析的模型 Route。
- system 指令 Part。
- 规范历史对话。
- 模型可见 Tool definitions。
- tool choice。
- generation/reasoning 选项。
- 命名空间隔离的 Provider options。

Provider options 由对应 Adapter 校验和解释，调用方不得依赖静默透传任意字段。

### 8.2 ModelCallContext

只承载单次调用的控制面信息：

- Cancellation token。
- 可选 trace/correlation context；它不是业务 `RunId`。

Provider credential 通过 Adapter 构造时注入的安全访问能力提供，不进入规范 `ModelRequest`、`ModelCallContext` 或事件。模型库不读取应用配置文件，不自行扫描环境变量，也不记录 credential。

### 8.3 ModelEvent

规范事件覆盖：

```text
TurnStarted
ReasoningStarted / Delta / Finished
TextStarted / Delta / Finished
ToolCallStarted / Delta / Finished
UsageUpdated
TurnFinished
TurnFailed
```

生命周期约束：

- 每个成功创建的流只有一个终态：`TurnFinished` 或 `TurnFailed`。
- Start/Delta/Finished 必须按 Part ID 配对。
- Tool arguments 可以分片到达，但 `ToolCallFinished` 前必须形成完整可解析值。
- 终态后到达的 Provider 数据视为协议错误，不继续产生业务事件。
- 调用建立前的认证和连接失败由 `stream` 返回错误；流建立后的 Provider/协议失败以受控终态结束。

## 九、OpenAI-compatible 与 DeepSeek 适配

### 9.1 首版协议范围

首版只支持 Chat Completions 风格的 OpenAI-compatible HTTP/SSE 协议，不把 Responses API 或 Anthropic Messages 混入同一个 Codec。

Adapter 通过能力 Profile 表达差异，而不是在 Agent Core 中判断 Provider 名称：

- reasoning 字段名称和是否支持。
- tool call delta 形式。
- thinking/reasoning 配置。
- generation 参数支持情况。
- endpoint 与认证方式。

### 9.2 DeepSeek 必须满足的行为

根据 [DeepSeek Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode/)：

- 流式 `reasoning_content` 解码为有序 `ReasoningPart`。
- 发生工具调用的 AssistantMessage 必须同时保留 reasoning、content 和全部 tool calls。
- 下一次 Provider 请求必须完整回传上述 AssistantMessage。
- Tool Result 必须使用对应的 `tool_call_id`，并保持调用顺序。
- thinking mode 下不生效或不支持的 generation 参数由 Adapter 依据能力处理，不能由 Agent Engine 写 Provider 特判。

本版本通过本地 fixture 和请求捕获验证这些要求；真实 API 只作为可选 smoke test，不进入默认 Harness。

## 十、错误与取消

错误至少区分：

- 配置错误。
- 认证错误。
- Transport 错误。
- Provider 返回错误。
- 限流或暂时不可用。
- 响应 schema/协议错误。
- Tool arguments 组装错误。
- 取消。

错误类型保留 source 和可诊断 metadata，但不得默认携带 API Key、完整 prompt 或未脱敏响应正文。

取消必须能够终止连接和流解析，并产生唯一受控结果；是否重试或切换模型不属于模型层。

## 十一、Harness 设计

### 11.1 默认测试

默认测试完全离线，至少覆盖：

- 纯文本非流式语义和流式分片。
- reasoning 与最终文本交错。
- 单个、多个、分片 Tool Call。
- Tool arguments 跨 chunk 拼接。
- usage 和 finish reason。
- HTTP 错误、Provider 错误、畸形 SSE、未知字段和流中断。
- 取消发生在连接前、reasoning 中、tool arguments 中和终态前。
- 唯一终态及终态后数据拒绝。

### 11.2 DeepSeek 契约测试

建立固定场景：

```text
User
→ Assistant(reasoning + tool call)
→ ToolResult(tool_call_id)
→ 下一次 Provider Request
```

断言下一次请求完整包含 `reasoning_content`、`content`、`tool_calls` 和对应 `tool_call_id`，并能再次解析为相同规范语义。

### 11.3 可选真实 Smoke Test

- 只在显式环境开关和凭据存在时运行。
- 不进入 `cargo test --workspace` 默认集合。
- 不把真实响应和凭据提交到仓库。
- 失败时明确区分协议回归与外部网络/额度问题。

## 十二、验收标准

`v0.1.0` 必须同时满足：

1. 规范类型不依赖 Tauri、Runtime、数据库或 `assistant-protocol`。
2. 模型服务只能执行一个 Provider Turn，不包含工具继续循环。
3. OpenAI-compatible Adapter 可以完成规范请求编码和流事件解码。
4. DeepSeek reasoning + tool-call + result 往返契约测试通过。
5. 所有成功创建的模型流满足唯一终态和 Part 生命周期约束。
6. 默认测试不访问真实模型网络，且可确定性复现错误与取消。
7. `agent-core` 不承载 Provider HTTP 细节，并移除不合理的应用协议依赖。
8. 新 crate 的依赖方向、公共 API 和错误边界有文档和测试覆盖。
9. 通过版本开发计划规定的 workspace 格式、静态检查和测试。

## 十三、风险与控制

| 风险 | 控制 |
| --- | --- |
| 规范消息过度贴近 OpenAI | 使用 Part/Turn 模型，Provider schema 只存在于 Adapter |
| 为未来 Provider 提前抽象过多 | 首版只实现一个通用 Model SPI 和一个 OpenAI-compatible Adapter；其他协议以后用实际调用方检验 |
| OpenAI-compatible 厂商方言差异扩大 | 使用显式 Capability/Profile，不用散落的 Provider 名称判断 |
| 流式事件出现半完成状态 | 使用明确 parser state 和唯一终态契约，并覆盖畸形流测试 |
| opaque state 变成任意 JSON 逃生口 | 限定用途、标识 Provider/Protocol/版本，优先映射规范 Part |
| crate 拆分造成空壳和 re-export 层 | 每个新增 crate 必须有独立调用边界、测试和禁止依赖；`agent-core` 不提前聚合无调用方 API |
| DeepSeek 协议变化 | 契约集中在 Adapter，使用官方协议 fixture/可选 smoke test更新，不修改 Agent Engine |

## 十四、设计结论

- `v0.1.0` 只完成基础类型、单次模型 Turn、首个 OpenAI-compatible/DeepSeek Adapter 和 testkit。
- Provider-neutral 类型与应用协议分离，`agent-core` 不再依赖 `assistant-protocol`。
- Provider 兼容由 Adapter 的 Route、Codec、Transport 和 Decoder 承担。
- reasoning、文本、tool call 和 provider state 以有序 AssistantMessage 保真保存。
- 本版本不实现 Agent Loop；完成后进入 `v0.2.0` 的 Engine 与工具循环设计。

当前没有阻塞开发计划的开放问题。版本设计确认后进入 `v0.1.0` 开发计划阶段。
