## 二、背景与版本目标

`v0.1.0` 至 `v0.6.0` 已分别建立模型、Agent Loop、上下文、安全、记忆和可靠性能力。
这些能力当前分布在多个 crate 中，专项 Demo 也分别采用自己的装配方式。外部宿主若要运行
完整 Agent，需要直接理解并组合 `ExecutionSpec`、模型服务、工具快照、上下文窗口、
授权器、Recorder、记忆工具和取消控制等底层类型。

现状适合逐层建设和验证，但还不是适合 Runtime 接入的候选 SDK：

- 缺少一个清晰、长期可用的 Agent 装配与启动入口；
- 公共入口、扩展 SPI 和 Adapter 内部能力尚未按候选稳定范围完成系统审查；
- 各专项 Demo 能独立证明能力，却没有一个只通过候选公共 API 运行完整 Agent 的示例；
- 配置责任、临时便利行为和正式 Runtime 必须显式提供的能力尚未统一说明；
- 缺少公共文档、兼容矩阵和可重复的本地性能基线。

本版本目标如下：

1. 新增轻量 `agent-sdk` Facade，为上层提供单会话 Agent 的统一装配和执行入口。
2. 收敛公共 API、扩展 SPI、crate 依赖和配置输入，形成首次候选稳定基线。
3. 通过独立 B/S Core Demo 端到端装配模型、工具、安全、记忆、上下文和观察能力。
4. 确保不同会话未来可以通过异步任务并发运行，慢 UI、断开的观察者或单次取消不会阻塞
   Provider I/O 或污染其他执行。
5. 补齐 SDK 导读、最小示例、扩展示例、兼容矩阵和本地性能基线，使未来 Runtime 可以在
   不依赖 Demo 私有契约的情况下接入。

## 三、版本边界

### 3.1 本版本包含

- 独立 `agent-sdk` crate 及候选公共入口。
- 单会话、不可变、可重复启动执行的 Agent 装配结果。
- SDK 对底层 Core、Model、Context、Tool 和 Memory 契约的薄层组合。
- 必填配置、可选配置、校验错误和临时 Recorder 的明确语义。
- 公共导出面、错误类型、命名、文档和 crate 依赖的收敛。
- 独立 B/S Core Demo，使用候选 SDK 完整验证既有能力。
- 不同临时 Session 的并发、取消隔离、慢观察者和 UI 断开验证。
- 确定性性能基线与平台、Provider、能力兼容矩阵。
- 既有专项 Demo、Harness 和全 workspace 回归。

### 3.2 本版本不包含

- 正式 `assistant-runtime`、`assistant-protocol` 或 Desktop 接入。
- 产品 Session、Run、Journal、数据库、队列、恢复、分支、调度和持久化设计。
- 正式审批 UI、持久授权、Trace 落盘与保留策略。
- 后台服务托管、跨进程 Runtime、sidecar、daemon 或本地产品 HTTP 服务。
- 自动记忆观察、自动整合、Embedding、向量数据库或新的 Recall 能力。
- Tool Result 裁剪、任务 drain、自动续跑、todo、ask_user 或同批工具并行。
- 同一 Session 并发执行。
- 新的模型、工具、安全、记忆或可靠性业务能力。
- 动态插件市场、统一 Adapter 父接口或跨领域错误父类型。
- crates.io 发布、正式稳定版承诺或所有 workspace crate 的机械版本号同步。

Core Demo 可以私有实现临时 Session、Journal、审批、JSON Store、Trace 和 HTTP/SSE DTO，
但这些实现不得成为 SDK、Runtime 或产品协议。

## 四、核心对象与生命周期

### 4.1 Agent 的定义

`agent-sdk::Agent` 是一个会话生命周期内冻结的 Agent 能力装配结果，不是跨会话共享的全局
服务，也不是拥有业务状态的 Runtime Agent。

Agent 持有本会话可以稳定复用的事实：

- 冻结的 `SystemPromptSnapshot`；
- 已构造的模型服务；
- 不可变工具集快照；
- 上下文窗口判断配置；
- 显式执行预算；
- 可选 Guardrail 配置。

Agent 不持有：

- 动态 Conversation History；
- SessionId、RunId 或产品状态；
- 当前活动 Run、排队和调度状态；
- Journal 或数据库连接的所有权；
- 当前审批交互；
- Pinned Memory Store 的实时内容。

新建会话根据最新输入构建新的 Agent；恢复会话根据持久化的原 System Prompt 快照重建
Agent。Pinned Memory 在会话初始化时进入冻结 Prompt，后续 Store 修改不会反向改变该 Agent。

### 4.2 AgentExecution 的定义

一次 `start` 产生一个既有 `agent-core::AgentExecution`。每次执行输入至少包含上层已经选定的
完整 `ConversationSnapshot`，并绑定本次取消、授权和记录能力。执行结束后，上层使用
Recorder 与 `ExecutionOutcome` 更新自己的权威 Journal，再为下一次执行生成新快照。

SDK 不复制 Agent Loop，不创建第二套执行状态机，也不把 Core 终态包装成另一套相同枚举。

### 4.3 单会话串行

同一会话中会改变上下文的执行必须串行：前一次执行完成、最终消息提交并形成新的对话快照
之前，不能启动下一次执行。

该约束由拥有 Conversation Journal 的上层宿主负责。`agent-sdk` 不引入 Session 调度器，
`agent-core` 也不知道两个 Execution 是否属于同一会话。Core Demo 的临时 Session 层必须
保证同一时刻最多一个活动 Run；首期重复提交可以明确返回 SessionBusy，不要求实现排队。

### 4.4 不同会话与共享资源

不同会话使用各自的 Agent 和 Journal。底层无会话状态且线程安全的模型服务、HTTP 连接池、
Transport 或本地能力可以通过 `Arc` 共享，但这只是资源复用，不改变“一会话一 Agent”的
公共语义。

不同会话的执行可以由上层作为独立 Tokio task 并发推进。系统不为每个 Session 或 Agent
分配固定操作系统线程，也不建立线程亲和性。

## 五、agent-sdk Facade

### 5.1 职责

`agent-sdk` 只负责：

- 提供清晰的 Agent Builder；
- 校验并冻结会话级 Agent 装配；
- 把每次调用机械映射为现有 `ExecutionSpec`、`ExecutionInput` 和 `ExecutionContext`；
- 提供不要求持久化宿主的临时 Recorder 便利能力；
- 暴露普通调用方完成装配、启动、观察、取消和取得结果所需的最小公共入口。

它不负责：

- 解析 TOML、JSON、环境变量或命令行参数；
- 合并应用默认值、Agent Profile、Session 覆盖和 Run 覆盖；
- 根据 Provider 名称选择配置；
- 创建正式 Journal、审批协调器或持久化 Store；
- 自动压缩、continuation、重试整个 AgentExecution 或调度 Run；
- 依赖具体 Provider Adapter、本地工具 Adapter 或任何 Demo。

### 5.2 薄层原则

SDK 不为已有 Core 类型创建字段相同、语义相同的镜像包装。普通入口优先直接复用
`ExecutionInput`、`ExecutionContext`、`AgentExecution` 和 `ExecutionOutcome` 等现有契约。
确需新增的公共类型只能表达 Facade 自身拥有的新语义，例如 Agent 构建错误或临时 Recorder
选择，不能仅用于改名。

SDK 顶层只导出普通使用路径必需的少量类型。Provider Codec、文件/Shell 能力、RecallSource、
策略 Adapter 和测试辅助类型继续由所属 crate 导出；SDK 不成为全 workspace 的通配聚合层，
也不隐藏专业扩展边界的真实归属。

### 5.3 配置输入与默认值

Agent 构建时：

- Model Service 必须显式提供；
- System Prompt Snapshot 必须显式提供，空 Prompt 也必须由调用方明确构造；
- Context Window Evaluator 必须显式提供；
- Tool Set 缺省为空集合；
- Guardrail 缺省关闭；
- Execution Budget 沿用 Core 全 `Option`、缺省无隐藏上限的语义；
- SDK 不加入根据模型、环境或工作模式变化的隐藏默认值。

每次执行时：

- Conversation Snapshot 必须显式提供；
- Tool Authorizer 必须显式提供，SDK 不静默使用 AllowAll；
- Cancellation 必须有明确来源；
- Recorder 允许缺省为 SDK 临时实现，正式 Runtime 必须显式提供绑定当前 Run/Session
  Journal 的 Recorder。

所有构造失败都在启动副作用前返回结构化错误。配置文件路径、覆盖优先级、credential 来源、
Plan/Build 和 Ask/Auto 继续属于 Runtime 或应用宿主。

### 5.4 临时 Recorder

SDK 提供的临时 Recorder 只服务无持久化的最小调用和示例：

- 遵守 Core 的 begin/complete 两阶段工具交换协议；
- 保证当前执行中的 Tool Call/Result 可以正常结算和继续；
- 不写文件或数据库，不承诺进程异常恢复；
- 不冒充 Conversation Journal，也不自动保存最终 AssistantMessage；
- 文档必须明确说明它不适合正式 Runtime。

具体采用可选参数、独立便利方法还是最小 Options 类型，由技术方案在不复制 Core 契约的前提
下确定。无论接口形状如何，完整入口始终允许 Runtime 显式传入自己的 Recorder。

## 六、异步 I/O 与并发兼容

未来 Runtime 同时面对 Provider I/O 与 UI I/O：

```text
UI / WebView / Browser ←→ Runtime ←→ LLM Provider
                              └────→ File / Shell / Memory
```

Core 与 SDK 必须保持以下性质：

- Provider 流由 AgentExecution 异步消费，不同步等待 UI 网络写入或页面渲染；
- 普通 AgentEvent 是允许丢弃的观察流，不是权威 Conversation Journal；
- UI 读取缓慢、SSE/IPC 断开或普通观察队列满，不改变 AgentExecution 结果；
- Completion 和 Core 唯一终态继续可靠收敛；
- 取消一个执行不传播到其他会话；
- 公共 SPI 不依赖线程局部状态，跨异步任务共享的能力满足既有 `Send + Sync` 约束；
- CPU 密集或阻塞系统调用不得直接长期占用异步执行任务的 Runtime worker；
- Shell 启动的子进程是独立 OS 进程，不等同于给 Session 分配线程。

Core Demo 必须验证至少两个临时 Session 的独立执行。该验证只证明下层能力不会妨碍未来
Runtime 并发，不定义正式 Runtime 的队列、公平性、最大并发数或资源配额。

## 七、B/S Core Demo

新增 `tools/core-demo`，作为开发者显式启动的候选 SDK 验证宿主。它只监听 loopback，不属于
产品进程、正式 Runtime、sidecar 或 daemon。

### 7.1 最小职责

Server 私有实现：

- 临时 Session 和内存 Conversation Journal；
- 每 Session 一个 Agent 和活动 Run 闸；
- SDK、真实 OpenAI-compatible Provider、本地文件/Shell Adapter 的装配；
- Demo 私有 Pinned Memory JSON Store 与 RecallSource；
- 简单 Ask/Allow/Deny 审批协调；
- AgentEvent 到 SSE 的非权威实时转发；
- 最终消息、错误、取消和压缩交接的可见状态；
- 可选复用 v0.6 观察接缝进行诊断，但不复制完整回放产品。

Browser 只负责：

- 创建和切换临时 Session；
- 提交任务；
- 展示 reasoning、text、工具和终态；
- 处理简单审批；
- 取消当前 Run；
- 观察两个 Session 独立推进。

### 7.2 Demo 边界

- HTTP/SSE DTO、Session、Journal、审批、JSON 文件和页面状态全部是 Demo 私有实现；
- 页面关闭只断开观察，不自动取消 Server 中的 Run；
- 同一 Session 的重复提交不得形成重叠执行；
- 不要求服务重启后恢复聊天或活动 Run；
- 不引入正式身份认证；沿用 loopback、Host、Origin 和 POST 来源校验降低跨站误触；
- 不把工作目录描述为 OS 强沙箱；Shell 仍以当前用户权限运行；
- 不重新实现 Safety、Memory、Reliability Demo 已有的完整专项 UI，只覆盖 SDK 端到端入口。

## 八、公共 API 与 crate 边界收敛

### 8.1 候选稳定范围

本版本对以下范围建立首次候选稳定基线：

- SDK 的 Agent 构建、启动、事件、取消和完成路径；
- Runtime 未来必须实现或装配的 Model、Tool、Authorizer、Recorder、Memory 和 Context SPI；
- Provider-neutral Conversation、Message、Tool Call/Result、Model Request/Event 与错误；
- OpenAI-compatible Adapter 和本地工具 Adapter 的正常构造与替换边界。

“候选稳定”表示命名、所有权、错误处理和文档已经收敛，未来 Runtime 不应通过私有模块、
Demo 类型或旁路访问完成正常接入；它不等于 `1.0` 稳定承诺。Runtime 与真实应用集成发现
必要问题时仍可在 `0.x` 阶段调整，但必须明确记录破坏性变化并迁移全部调用方。

### 8.2 公共面审查

公共面审查遵循：

- 只被单模块使用的类型保持私有；
- 只有两个以上稳定调用方共享的能力才上提；
- 只为测试或 Demo 暴露的实现移回 testkit 或宿主私有模块；
- Provider wire/schema 等高级 API 可以保持所属 crate 公共，但不从 SDK 普通入口重复导出；
- 不为获得统一外观合并职责不同的 crate；
- 不创建统一 Adapter 父接口、统一错误父类型或动态插件系统。

### 8.3 crate 版本与发布

`v0.7.0` 是项目能力里程碑，不要求把所有 Cargo package 从当前版本机械同步为 `0.7.0`。
本版本不执行 crates.io 发布。归档时保存公共 API 基线和兼容结论，供 Runtime 首次集成及后续
版本识别破坏性变化。

## 十、性能基线与兼容矩阵

### 10.1 性能基线

性能验证聚焦本地确定性路径，不把真实网络和模型响应时间计为 Core 性能：

- 大型 Conversation Snapshot 的上下文布局和请求组装；
- 较大 Tool Set 的注册、冻结和 schema 投影；
- 高频 AgentEvent 下慢消费者、断开消费者与可靠终态；
- 两个独立 Session 执行时的取消和结果隔离；
- SDK Agent 构建与重复启动的额外开销。

基线记录测试规模、主机、构建模式和实际结果，用于发现明显退化；本版本不制定跨硬件的
绝对吞吐或延迟 SLA，也不以易波动的微小差异作为验收失败。

### 10.2 兼容矩阵

兼容矩阵至少区分：

- macOS、Linux、Windows 的编译支持与实机验证状态；
- OpenAI-compatible 通用 Profile 与 DeepSeek 已验证能力；
- reasoning、tool call、流式、Provider State 和 usage 等模型能力；
- 文件、Shell、进程取消和 detached 模式的平台差异；
- SDK 临时 Recorder 与正式 Runtime Recorder 的能力差异；
- 已实测、仅编译/单测覆盖和未验证三种证据等级。

当前主机无法实测的平台必须明确标记，不能用条件编译成功冒充实机行为通过。

## 十一、既有验证宿主关系

- Runtime Harness 继续累计验证 v0.2/v0.3 的确定性执行和上下文交接；
- Safety Demo 继续专项验证策略、审批、真实文件/Shell 和 Guardrail；
- Memory Demo 继续专项验证 Pinned Memory、冻结快照和 Recall；
- Reliability Demo 继续专项验证 Trace、Replay、Retry 和故障矩阵；
- Core Demo 只验证候选 SDK 能否把上述公共能力组合成完整使用路径。

Core Demo 可以复用所属 crate 的公共能力和少量静态页面资产，但不得直接依赖其他 Demo 的
私有 Rust 模块、HTTP DTO、存储格式或运行时状态。

## 十二、风险与控制

- **Facade 演变为 Runtime**：通过不持有动态历史、Run、调度、持久化和审批交互控制范围。
- **重复包装造成双重契约**：优先直接复用 Core 输入、上下文、事件和终态，仅新增 Facade
  真正拥有的语义。
- **便利默认掩盖安全要求**：Authorizer 始终显式；临时 Recorder 明确无持久恢复能力；
  AllowAll 只能由调用方主动选择。
- **单会话重叠执行**：由持有 Journal 的宿主设置活动 Run 闸；Demo 对重入明确失败。
- **UI 背压影响模型**：UI 转发与 Provider 消费解耦，普通观察事件断开或丢弃不改变执行。
- **公共导出过度收敛**：以真实普通调用方和扩展调用方为依据，不为了缩小数量破坏专业
  Adapter 的可替换性。
- **性能基准失真**：记录环境和规模，以稳定本地路径与明显回归为判断依据。
- **Demo 被误当产品契约**：目录、模块文档、页面提示和依赖方向同时标记私有验证定位。

## 十三、当前已确认的设计结论

1. 新增独立 `agent-sdk`，不让 `agent-core` 同时承担便利装配 Facade。
2. Agent 采用长期复用但无动态会话状态的方案，并按单会话构建和理解。
3. Agent 持有冻结 System Prompt、模型、工具、上下文和执行限制，不持有 Conversation、Run
   或 Journal。
4. 新建会话构建新 Agent；恢复会话使用原冻结 Prompt 重建，不重新读取最新 Pinned Store。
5. 同一会话执行串行，由上层宿主保证；SDK 不实现 Session 调度器。
6. 不同会话使用不同 Agent，可以异步并发并共享线程安全的底层服务资源。
7. 多会话并发不采用一会话一线程；Core 和 SDK 不依赖线程亲和性。
8. Provider I/O 与 UI I/O 解耦，慢 UI 和观察者断开不改变执行结果。
9. SDK 保持薄层，优先直接复用现有 Core 类型，不复制执行状态机和同义 DTO。
10. Model、System Prompt 和 Context Window 显式提供；工具缺省为空，Guardrail 缺省关闭，
    Budget 没有隐藏上限。
11. Authorizer 每次执行显式提供；Recorder 可以缺省为无持久化临时实现，正式 Runtime 必须
    传入权威 Journal Recorder。
12. 综合验证宿主采用独立 B/S Core Demo，不修改正式 Runtime、Protocol 或 Desktop。
13. v0.7.0 建立候选公共 API 基线，但不发布 crates.io，不机械同步所有 Cargo 版本。
14. 性能只建立可重复本地基线，不制定跨硬件 SLA；兼容矩阵区分实测、编译/单测和未验证。

## 十四、技术方案约束

后续技术方案必须基于真实代码核查：

- `ExecutionSpec`、`ExecutionInput`、`ExecutionContext` 和各 Demo 当前重复装配点；
- 哪些字段真正属于会话级 Agent，哪些必须保持每次执行绑定；
- `ToolSetSnapshot`、`SystemPromptSnapshot`、Evaluator 和底层服务的 Clone/Arc 成本与并发边界；
- 临时 Recorder 如何满足两阶段协议且不引入第二套 Journal；
- SDK 最小公共导出以及专业扩展从所属 crate 导入的完整路径；
- B/S Demo 如何复用现有公共能力而不依赖专项 Demo 私有模块；
- AgentEvent 非阻塞观察、可靠终态、Completion 和 UI SSE 转发的断开行为；
- 不同 Agent 共享 ModelService/Transport 时的并发、取消和错误隔离；
- 现有 public API 中不必要暴露、错误命名、重复类型和文档缺口；
- 基准规模、测量方式、兼容矩阵证据来源和不可实测平台的标记方式。

技术方案不得以 Facade 为由把 Provider、本地文件/Shell、Memory Store、Trace Collector 或
Demo Runtime 实现迁入 `agent-sdk`。

## 十五、验收标准

开发计划必须覆盖以下可观察结果：

1. 外部宿主可以只通过候选公共入口构建一个会话级 Agent，并启动、观察、取消和取得一次
   AgentExecution 的可靠结果。
2. SDK 机械复用现有 Core 执行状态机和终态，不存在第二套 Agent Loop、事件或结果事实源。
3. Agent 的 System Prompt 在会话内冻结；新建和恢复会话的构建方式与 v0.5.0 语义一致，
   Pinned Store 修改不改变当前 Agent。
4. 同一 Demo Session 不会出现重叠执行；前次结果提交后才能以新 Conversation Snapshot
   启动下一次执行。
5. 至少两个 Demo Session 可以独立推进；一个执行的取消、失败、慢事件消费者或 UI 断开
   不影响另一个执行，也不阻塞自身 Provider 流和可靠终态。
6. Model、System Prompt、Context Window 和 Authorizer 没有隐藏选择；空工具集、关闭
   Guardrail 和无隐藏 Budget 上限行为明确可测。
7. SDK 临时 Recorder 可以完成纯文本和多轮工具闭环，但明确不具备持久恢复能力；显式
   Runtime 风格 Recorder 仍可完整替换并观察 begin/complete。
8. B/S Core Demo 可以使用真实 OpenAI-compatible Provider、本地文件/Shell、Pinned Memory、
   Recall、安全策略、取消和上下文交接完成端到端人工验证。
9. Core Demo 只监听 loopback，具备既定来源校验和安全提示，其 Session、HTTP DTO、Journal、
   Store 和 Trace 均未进入正式 SDK 或产品协议。
10. 公共 API 审查完成：普通入口、扩展 SPI 和高级 Adapter API 归属明确，无仅为 Demo 或
    单模块需要而错误上提的新公共抽象。
11. 仓库导读、最小示例、扩展示例、Demo 启动说明、候选 API 基线和兼容矩阵可以让未来
    Runtime 在不读取 Demo 私有实现的情况下完成装配。
12. 性能基线覆盖上下文、工具集、事件背压、双 Session 隔离和 SDK 开销，并记录可复现的
    环境、规模与结果，不包含真实网络模型延迟。
13. macOS、Linux、Windows 及 Provider/能力矩阵明确区分实测、编译或单测和未验证，当前
    主机未实测的平台不被宣称通过。
14. 既有 Provider Codec、Core Tool Loop、Recorder、取消、Guardrail、上下文压缩、Memory、
    Retry/Replay、Runtime Harness 和所有专项 Demo 回归不受破坏。
15. `assistant-runtime`、`assistant-protocol` 和 Desktop 不产生代码或行为变更；本版本不引入
    产品 Session/Run、持久化、调度、正式审批或 Trace 策略。
