- 关联文档：
  - [`功能设计`](功能设计.md)（✅ 已确认 2026-08-04）

- 界面交互设计指导：不单独编写。Core Demo 只是私有验证页，页面分区、交互语义和

本计划只规定实施顺序、里程碑边界和验证门槛。`agent-sdk` 的单会话薄 Facade、Core 请求

重新引入正式 Runtime、Protocol、Desktop 或产品会话设计。

## 二、实施原则

1. M0 → M8 严格顺序实施。每个里程碑完成实现和验证后标记为 `🟨 待确认`并停止，获得用户
   明确确认后才进入下一里程碑。
2. 开发计划确认只授权开始 M0，不授权连续执行后续里程碑。
3. 先稳定 Core 的请求配置和 SDK 公共入口，再实现 Core Demo；Demo 不反向决定或承载公共
   Agent 契约。
4. 公共类型变更必须在所属里程碑一次性迁移全部生产者、消费者、示例和测试，不保留新旧并行
   入口或宿主私有包装旁路。
5. `agent-sdk` 只保存会话内冻结的能力配置，不保存 Conversation、Run、Journal、审批状态、
   Store 或调度状态；这些动态状态只存在于 Core Demo 私有宿主。
6. 同一 Demo Session 的上下文变更 Run 串行，不同 Session 使用独立 Agent/Journal 异步并发；
   不为 Session 绑定操作系统线程，也不让 SSE 消费速度反压 Provider 流。
7. Core Demo 的 Session、HTTP DTO、Journal、Memory Store、策略、CLI 和页面代码不得被提升为
   SDK、正式 Runtime 或 Protocol 契约。
8. 测试优先使用 scripted model、gate、channel、barrier、tempfile 和受控本地命令；并发正确性
   不用不稳定 sleep 推断，普通自动测试不读取用户应用数据或访问真实 Provider。
9. 真实文件/Shell 只在 M5 的专用临时目录验证，真实 Provider 与跨能力综合浏览器闭环集中到
   M7、M8；credential、完整 prompt、文件内容和 Shell 输出不得进入 fixture 或普通日志。
10. 性能 baseline 只建立可复现首份测量，不提前制定跨硬件 SLA，也不因微小波动增加缓存层、
    Arc 包装或专用 benchmark 框架。
11. 公共 API 只处理有真实搜索证据的边界问题；不为候选版批量重命名、私有化或新增包装类型。
12. `assistant-runtime`、`assistant-protocol` 和 `apps/desktop` 保持零代码、零直接依赖变化；
    Desktop/Tauri 不纳入本版本构建门禁。
13. 每个里程碑开始前重新核对工作树、Rust 规范、对应模块约束和长期 Agent 架构；发现实现与
    已确认方案冲突时停止扩大改动，先回到设计确认。
14. 每个里程碑完成后只挑选公共契约、核心语义、安全、并发或后续依赖中的重点供用户 Review；
    若没有重要 Review 点，直接说明，不人为制造问题。
15. 不主动执行 `git add`、`git commit` 或 `git push`，不覆盖或清理与当前版本无关的工作树改动。

## 三、目标依赖结构

```text
agent-types ◄── agent-model ◄── agent-provider-openai-compatible
     ▲              ▲
     │              ├── agent-context
     │              └── agent-core
     │                    ▲
agent-memory ◄── agent-tools ───┘
                     ▲
                     └── agent-tools-local

agent-core / agent-context / agent-model / agent-tools / agent-types
    ▲
    └── agent-sdk

agent-sdk / agent-core / agent-context / agent-model / agent-tools /
agent-memory / agent-provider-openai-compatible / agent-tools-local
    ▲
    └── core-demo（私有 B/S 验证宿主）

agent-testkit ──► agent-sdk examples/测试、Core 与 Core Demo 确定性测试
```

- `agent-sdk` 直接依赖 Core、Context、Model、Tools 和 Types，只重导普通构建与执行所需类型；
  不直接依赖 Provider、本地 Adapter、Axum、Tauri 或 Demo。
- `agent-memory` 通过 `agent-tools` 提供普通记忆工具壳；SDK 不读取 Memory Store，也不直接暴露
  记忆存储 API。
- `core-demo` 是唯一可以向下装配全部候选能力的顶层宿主；任何产品 crate 都不得依赖它。
- 正式 Runtime、Protocol 和 Desktop 的既有依赖图保持不变。

## 六、M1：Core 请求配置与既有宿主迁移

  Demo/Harness 明确选择默认或指定请求配置。

## 七、M2：agent-sdk 薄 Facade 与离线示例

### 目标

实现普通宿主可直接使用的会话级 Agent 构建入口，完整复用 Core 执行状态机、事件、取消和
终态，不引入第二套 Runtime。

### 前置依赖

M1 已确认。

### 实施内容

- 实现 `AgentBuilder::new(model, system_prompt, context_window)` 及工具、请求配置、Budget 和
  Guardrail 可选配置。
- 实现非 Clone 的 `Agent`，保存冻结的 `ExecutionSpec`，提供只读能力信息和：
  - `start(input, ExecutionContext)`：供 Runtime 风格宿主显式绑定 Recorder/Authorizer；
  - `start_ephemeral(input, cancellation, authorizer)`：为无持久化调用创建每次执行独立的临时
    Recorder。
- 实现已确认的五类 `AgentBuildError` 及 ToolChoice/模型能力校验；不隐藏选择模型、Prompt、
  Context Window 或 Authorizer。
- 临时 Recorder 严格遵守 begin/complete receipt 协议；正常取消时接收 Core 补齐后的完整
  exchange，随后只在进程内丢弃，不提供恢复承诺。
- SDK 顶层只重导普通入口需要的类型；扩展 SPI 和高级 Adapter API 继续从所属 crate 导入。
- 增加 Builder、构建错误、冻结配置、临时 Recorder、显式 Recorder、事件断开、共享模型并发
  与取消隔离测试。
- 增加离线 `minimal.rs` 和 `custom_controls.rs` examples，testkit 只作为 dev-dependency。

### 自动测试或人工核对

- 默认值和五类构建错误均有确定性测试，失败时不发起模型调用。
- 空 ToolSet、ToolChoice None、关闭 Guardrail 和无隐藏 Budget 上限行为明确。
- 临时 Recorder 可完成纯文本、单工具和多轮工具；receipt 错配和 pending 重入明确失败。
- 显式 Recorder 可完整替换临时路径并观察 begin/complete。
- 一个事件消费者断开不影响 Completion；两个 Agent 共享 ModelService 时请求、取消和结果隔离。
- examples 不访问网络、文件、用户环境或真实 Provider。

```bash
cargo run -p agent-sdk --example minimal
cargo run -p agent-sdk --example custom_controls
cargo tree -p agent-sdk --depth 3

```

### 完成判定

- 普通宿主只通过 SDK 即可构建并启动 AgentExecution；
- SDK 没有复制 Agent Loop、事件、结果、Session 或 Journal。

### Review 重点

重点 Review `AgentBuilder`、`Agent`、两种 start 路径、构建错误和临时 Recorder 语义。这是
本版本最重要的候选公共 API 门禁。

## 九、M4：Core Demo 多 Session B/S 基础宿主

### 目标

建立只使用内存状态和确定性模型的 B/S 验证宿主，先证明多 Session 所有权、Run 串行、
Provider/UI I/O 解耦和断线恢复，不提前接入真实工具、Memory 或 Provider。

### 前置依赖

M3 已确认。

### 实施内容

- 实现 `core-demo serve` CLI、loopback 监听、显式 data-dir 与启动安全提示。
- 实现私有 ServerState、Session、Run、内存 Journal/Recorder 和每 Session active Run gate；每个
  Session 持有独立 Agent 和冻结 System Prompt。
- 实现技术方案规定的 global/session snapshot、SSE、create session、start/cancel run 和 approval
  路由骨架；审批路由本阶段可返回无待审批状态。
- 复用 Safety Demo 的 Host、Origin、POST 来源、CSP 和 no-store 原则，但不建立代码依赖或
  升级为正式协议。
- 实现 Agent event supervisor：先更新内存投影和可靠结果，再 best-effort broadcast；SSE lag/
  断开通过 snapshot/sequence 恢复，浏览器断开不取消后台 Run。
- 实现原生 HTML/CSS/JS 页面：Session 列表、对话/运行区、输入和运行状态；浏览器选中 Session
  仅保存在页面本地。
- 使用 scripted model 覆盖双 Session 并发、同 Session Busy、取消隔离、慢/断开 SSE 和最终
  AssistantMessage 对 delta gap 的收敛。

### 自动测试或人工核对

- Router 覆盖 Host/Origin/POST/CSP/no-store 和 loopback 约束。
- 同一 Session 重复提交返回 Busy，前次 complete 后才能以新 Conversation Snapshot 再运行。
- 两 Session 可同时推进；取消、失败或慢事件消费者互不影响。
- 页面刷新/SSE 重连不取消 Run，snapshot 可以恢复权威最终状态。
- pending exchange 不作为完成 Conversation 暴露，begin/complete 顺序由私有 Journal 保证。
- 本阶段不执行真实文件/Shell、不读取 Memory Store、不访问真实 Provider。

### 验证

```bash
cargo test -p core-demo -p agent-sdk
cargo run -p core-demo -- --help
cargo tree -p core-demo --depth 3
cargo clippy -p core-demo -p agent-sdk --all-targets --all-features -- -D warnings
cargo fmt --all --check
```

另启动 scripted Core Demo，在浏览器人工核对 Session 切换、Busy、取消、刷新和 SSE 重连。

### 完成判定

- B/S 宿主完成多 Session 和双 I/O 基础闭环；
- UI 不是权威状态源，Demo 类型未进入公共 crate。

### Review 重点

重点 Review Session/Run 所有权、supervisor 与 SSE 解耦，以及页面展示是否足以支撑后续完整
能力验证；不 Review 产品 UI 视觉定稿。

## 十、M5：本地工具、安全策略与审批闭环

### 目标

通过 SDK 和 Core Demo 私有上层装配真实本地文件/Shell、Plan/Build × Ask/Auto 与审批交互，
证明 Authorizer 和工具执行边界可由未来 Runtime 复用。

### 前置依赖

M4 已确认。

### 实施内容

- Core Demo 装配 `LocalFileSystem`、`LocalShell` 和标准文件/Shell 工具壳，使用用户显式 workdir。
- 复用已确认的 resolved invocation 和装配式 Allow/Deny 策略，Demo 私有组织 Plan/Build 与
  Ask/Auto；Plan 未识别的授权事实最终明确拒绝，Auto 仍是上层 All Allowed 选择，不进入 Core。
- 实现私有 approval coordinator、pending approval 投影和 approve/deny API/UI；审批取消、Run
  取消和完成 race 只允许一个可靠终态。
- 页面完整展示工具名、resolved 文件路径或 Shell command、workdir、策略结果和实际执行结果。
- 保留 Shell 流式 stdout/stderr、超时、取消、输出上限、managed/detached 和审计能力；不把
  工作目录描述为系统沙盒。
- 使用临时目录、受控命令和 scripted model 覆盖文件操作、Shell、四种模式、白名单优先、
  Guardrail、审批和取消。

## 十一、M6：Pinned Memory、Recall 与会话冻结

### 目标

为 Core Demo 增加可人工验证的私有 JSON Memory Store 和 RecallSource，证明新建会话 Prompt
冻结、当前会话不热更新和普通记忆工具路径。

### 前置依赖

M5 已确认。

### 实施内容

- 在 Core Demo 内实现私有 JSON pinned/recall store，使用专用 data-dir、原子替换和明确错误；
  不新增 `agent-memory-local`。
- 新建 Session 时读取最新 Pinned Memory，构建最终 System Prompt 后创建 Agent；当前 Session
  后续编辑 Store 不改变其 Prompt Snapshot。
- 恢复/重建测试使用已持久化的最终 System Prompt，而不是按当前 Store 重新生成；Demo 本版本
  不承诺进程重启后的完整 Session 恢复。
- 装配标准 pinned add/update/delete/list 和 `recall_memory` 工具壳；RecallSource 结果天然携带
  来源，单 Source 失败不破坏其他结果。
- 页面增加 Memory 管理和会话 Prompt/来源查看所需的最小交互，不把 Store DTO 提升为 SDK API。
- 覆盖原子写失败、当前 Agent 冻结、新 Session 最新快照、Recall 部分失败和工具调用闭环。

### 自动测试或人工核对

- Store 修改不刷新当前 Agent，新 Session 读取最新 Pinned 内容。
- 恢复构建使用持久化最终 Prompt，不混用当前配置重新渲染。
- pinned 工具修改动作已在当前 Conversation 中可见，不篡改当前 System Prompt。
- RecallSource 的来源、attributes 和部分失败语义完整保留。

- Pinned Memory、Recall、JSON Store 和 Session Prompt 冻结可独立验证；

### Review 重点

## 十二、M7：上下文交接、真实 Provider 与并发闭环

### 目标

完成 Core Demo 的上下文压缩续跑、显式请求配置、可选有限重试和真实 OpenAI-compatible Provider
装配，并验证两个 Session 的 Provider/UI 双 I/O 隔离。

### 前置依赖

M6 已确认。

### 实施内容

- Core Demo 私有装配 `CompactionCoordinator`、Checkpoint、replacement Conversation 和
  continuation；每次续跑复用同一 Agent 的冻结 Prompt、ToolSet 和 ModelRequestConfig。
- 增加 `--max-compaction-handoffs` 显式次数上限，达到上限时返回可诊断终态，不隐藏无限续跑。
- 装配真实 `OpenAiCompatibleService`；DeepSeek thinking 通过 `ModelRequestConfig` 显式启用，
  不增加 Provider 包装器。
- 通过 `--retry-transient` 显式选择 `RetryingModelService`；只重试建流前已确认的瞬态错误。
- 完善 CLI 启动参数、credential 读取边界、模型 Profile 和页面中的请求配置/连接状态展示。
- 使用 gate/barrier 做两个 Agent 共享 ModelService 的确定性并发、一个取消/失败不影响另一个、
  慢 SSE 不反压 Provider 和 compaction handoff 测试。
- 使用真实 Provider 完成 reasoning + tool call + result + final answer，页面刷新后仍可从 snapshot
  收敛；真实测试只使用专用 workdir/data-dir。

### 自动测试或人工核对

- 压缩只在完整 Checkpoint 上交接，未完成 Step 不进入 replacement Conversation。
- continuation 复用同一冻结 Prompt 和请求配置，次数上限明确生效。
- Retry 只发生在事件流建立前；流内失败不透明重试。
- 两 Session 同时执行时，一个的取消、失败、慢 UI 或 SSE 断开不污染另一个。
- credential 不进入页面 snapshot、Journal、普通日志、fixture 或错误文本。
- 真实 Provider 的 reasoning/tool-call 往返不丢失 Provider State。

### 验证

```bash

cargo test -p agent-core -p agent-sdk -p core-demo
cargo clippy -p agent-context -p agent-model -p agent-provider-openai-compatible \
  -p agent-core -p agent-sdk -p core-demo \
  --all-targets --all-features -- -D warnings
cargo fmt --all --check
```

另以用户明确提供的 Provider 配置启动 Core Demo，人工执行技术方案第 13.4 节八项闭环；记录
命令、环境和结论，不记录 credential 或敏感内容。

### 完成判定

- 上下文续跑、真实 Provider、可选 Retry 和双 Session I/O 隔离全部闭环；
- Demo 没有形成正式 Runtime/Protocol 行为。

### Review 重点

重点 Review compaction continuation、显式请求配置、Retry 边界和多 Session 隔离；真实模型回答
措辞不作为 API 正确性的判断依据。

## 十六、实施结论

实施顺序固定为：

```text
工程与边界
→ Core 请求配置
→ agent-sdk
→ 候选 API/导读
→ B/S 多 Session 宿主
→ 本地工具/安全
```

重新确认。
