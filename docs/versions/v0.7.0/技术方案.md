## 二、现有实现核查

### 2.1 可以直接复用的契约

| 现有能力 | 所属位置 | v0.7.0 用途 |
| --- | --- | --- |
| `AgentExecution::start` | `agent-core` | SDK 最终仍调用的唯一 Agent Loop 入口 |
| `ExecutionSpec` | `agent-core` | 会话级 Agent 冻结能力的底层表示 |
| `ExecutionInput` | `agent-core` | 每次执行的完整 Conversation Snapshot |
| `ExecutionContext` | `agent-core` | 每次执行的取消、Recorder 和 Authorizer |

| Safety Demo 的 snapshot + SSE 模式 | `tools/safety-demo` | 只参考断线恢复和 UI 解耦语义，不建立代码依赖 |
| Memory Demo 的 JSON Store 语义 | `tools/memory-demo` | 只参考私有持久化边界，不提升为公共 Adapter |
| Runtime Harness 的压缩交接 | `tools/runtime-harness` | 只参考行为，Core Demo 私有装配公共 Context API |

### 2.2 当前装配缺口

1. 仓库当前有 14 处 `ExecutionSpec` 字面量构造表达式和多处 `ExecutionContext` 构造；
   每个宿主都重复克隆模型、Evaluator、ToolSet、Prompt、预算和 Guardrail。其余
   `ExecutionSpec {` 文本命中是结构体定义或函数返回类型，正式 `assistant-runtime` 与
   Desktop 当前均没有构造点。
2. `ExecutionSpec` 不可 Clone，虽然其全部字段均可安全 Clone；会话内重复执行只能重新
   手工拼装结构。
3. `ModelRequest` 已包含 `tool_choice`、`generation`、`reasoning` 和 `provider_options`，
   但 Core 的 `build_request` 当前每 Step 固定使用 `Auto`、默认 generation、无 reasoning
   和空 Provider Options。
4. Safety Demo 为显式启用 DeepSeek thinking 额外实现 `DeepSeekThinkingModel` 包装器；
   Memory Demo 和 Reliability Demo 依赖 Provider 默认值，不能从 `ExecutionSpec` 看出真实
   请求配置。
5. `ExecutionContext.recorder` 在 Core 中正确保持必填，但无持久化调用方必须自行实现或
   依赖 testkit；没有适合普通 SDK 示例的生产无持久化路径。
6. 现有专项 Demo 分别证明安全、记忆和可靠性，没有一个通过统一候选入口完成完整 Agent
   装配，也没有多临时 Session 的 Provider/UI 双 I/O 验证。
7. 当前 README 仍只列早期三个 crate，没有候选公共 API 导读、能力矩阵或性能基线。

### 2.3 不采取的重构

- 不把 `agent-core`、`agent-model`、`agent-context`、`agent-tools` 和 `agent-memory` 合并。
- 不创建 `agent-memory-local`、`agent-recording`、`agent-safety` 或统一 Adapter crate。
- 不让 SDK 依赖 OpenAI-compatible、本地文件/Shell、Axum、Tauri 或任一 Demo。
- 不为所有已有类型增加 SDK 镜像 DTO，不创建第二套事件、错误和执行结果。
- 不把 Safety Demo、Memory Demo 或 Runtime Harness 的私有 Runtime 代码抽成公共库。
- 不以候选版名义批量私有化全部已有公共 API；只修正有真实调用证据的问题。

## 三、目标依赖与调用关系

### 3.1 crate 依赖

```text
tools/core-demo / future assistant-runtime
                    │
                    ▼
                agent-sdk
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
   agent-core  agent-context  agent-model
        │                       │
        ▼                       ▼
   agent-tools              agent-types
        │
        ▼
   agent-memory

tools/core-demo ──→ agent-provider-openai-compatible
tools/core-demo ──→ agent-tools-local
```

`agent-sdk` 的普通直接依赖只包含它直接使用的抽象 crate：`agent-core`、`agent-context`、
`agent-model`、`agent-tools` 和必要的 `agent-types`。它不直接依赖或调用 `agent-memory` API：
Pinned Memory 在进入 SDK 前已经渲染进 System Prompt，Recall 与修改能力已经作为普通工具
进入 ToolSet。由于 `agent-tools` 自身依赖 `agent-memory`，后者仍会出现在 SDK 的传递依赖
闭包中，不能把“无直接依赖”表述为完全不包含。

`agent-testkit` 继续不进入 SDK 的生产依赖；SDK 自身测试和 examples 可以把 testkit 作为
dev-dependency 使用，避免生产依赖闭包携带测试实现。

### 3.2 运行调用链

```text
Runtime / Core Demo
  │ 新建或恢复会话：得到冻结 SystemPromptSnapshot
  │ 编译 model / tools / context / budget / guardrails / model request config
  ▼
AgentBuilder::build
  │ 校验跨字段配置
  ▼
Agent（单会话、不可变、无动态历史）
  │ start(input, execution_context)
  ▼
AgentExecution::start
  │
  ├── ModelService / Provider I/O
  ├── ToolAuthorizer / Tool Adapter
  ├── ExecutionRecorder / Journal
  └── AgentEvent + Completion + Control
```

Agent 只消除稳定能力的重复装配，不接管上层在两次执行之间更新 Conversation 的责任。

## 四、Core 请求配置补全

### 4.1 `ModelRequestConfig`

在 `agent-core::spec` 增加本次 AgentExecution 内每个 Model Step 复用的配置：

```rust
#[derive(Clone, Debug, PartialEq, serde::Serialize, serde::Deserialize)]
pub struct ModelRequestConfig {
    pub tool_choice: ToolChoice,
    pub generation: GenerationConfig,
    pub reasoning: Option<ReasoningConfig>,
    pub provider_options: ProviderOptions,
}

impl Default for ModelRequestConfig {
    fn default() -> Self {
        Self {
            tool_choice: ToolChoice::Auto,
            generation: GenerationConfig::default(),
            reasoning: None,
            provider_options: ProviderOptions::new(),
        }
    }
}
```

该类型属于 Core 执行规格，而不是 Provider 路由：

- 它只包含已经存在于规范 `ModelRequest` 的语义字段；
- endpoint、credential、model 和 context window 仍属于 `ModelService` 构造；
- Provider Options 继续按命名空间隔离，由具体 Adapter 校验；
- 同一个 AgentExecution 的每个 Step 使用同一冻结配置；
- Core 不判断 Provider 名称，也不自动启用 DeepSeek thinking。

`ExecutionSpec` 增加：

```rust
pub model_request: ModelRequestConfig,
```

并补充 `Clone`。`Engine::build_request` 从该字段 Clone 四项配置，不再写死默认值。现有所有
直接构造点机械补充 `ModelRequestConfig::default()`，线上默认行为保持不变。

### 4.2 DeepSeek 配置迁移

真实 DeepSeek 宿主显式构造：

```rust
let mut provider_options = ProviderOptions::new();
provider_options.insert(
    "deepseek",
    serde_json::json!({"thinking": {"type": "enabled"}}),
)?;

let model_request = ModelRequestConfig {
    tool_choice: ToolChoice::Auto,
    generation: GenerationConfig::default(),
    reasoning: Some(ReasoningConfig { effort: None }),
    provider_options,
};
```

Safety Demo 删除只为注入请求字段存在的 `DeepSeekThinkingModel`。Runtime Harness、Memory
Demo、Reliability Demo 和 Core Demo 使用相同显式配置。Provider Adapter 继续执行自身方言
校验；该配置不进入 SDK 默认值。

### 4.3 配置验证边界

Core 的低层 `ExecutionSpec` 仍表示上层已经解析完成的事实，不增加配置文件或 Profile 合并。
候选 `AgentBuilder::build` 做以下低成本跨字段验证：

- `ModelService::context_window_tokens()` 必须大于零；
- ToolSet 非空时模型必须声明 tool-call 能力；
- `ToolChoice::Required` 必须存在至少一个工具；
- `ToolChoice::Named(name)` 必须命中冻结 ToolSet；
- reasoning 配置存在时模型必须声明 reasoning 能力。

`ToolChoice::None` 与非空 ToolSet 是合法组合，表示工具已注册但本 Agent 的模型请求明确禁止
调用；由于请求仍携带工具定义和显式选择，模型仍须声明 tool-call 能力。具体 Provider Profile
是否接受显式 `None` 继续由 Adapter 在编码期校验。`Auto` 与空 ToolSet 也是合法组合。

generation 数值和 Provider Options 内容继续由具体 Adapter 解释；SDK 不复制 Provider 校验。
空 Prompt、空 Conversation、空 ToolSet、关闭 Guardrail 和全 `None` Budget 都是合法值。

### 5.2 `AgentBuilder`

建议公共形状：

```rust
pub struct AgentBuilder {
    model: Arc<dyn ModelService>,
    system_prompt: SystemPromptSnapshot,
    context_window: Arc<ContextWindowEvaluator>,
    tools: ToolSetSnapshot,
    model_request: ModelRequestConfig,
    budget: ExecutionBudget,
    guardrails: Option<GuardrailConfig>,
}

impl AgentBuilder {
    pub fn new(
        model: Arc<dyn ModelService>,
        system_prompt: SystemPromptSnapshot,
        context_window: Arc<ContextWindowEvaluator>,
    ) -> Self;

    pub fn tools(self, tools: ToolSetSnapshot) -> Self;
    pub fn model_request(self, config: ModelRequestConfig) -> Self;
    pub fn budget(self, budget: ExecutionBudget) -> Self;
    pub fn guardrails(self, guardrails: GuardrailConfig) -> Self;
    pub fn build(self) -> Result<Agent, AgentBuildError>;
}
```

三个必填项进入 `new`，避免 typestate builder 和运行时 `MissingField(String)`。默认行为直接
沿用底层显式语义：空 ToolSet、默认 ModelRequestConfig、全 `None` Budget、无 Guardrail。
`guardrails` 不接收双重 `Option`；不调用即关闭，调用即启用给定配置。

Builder 不提供 `from_env`、`with_deepseek`、`with_local_tools`、`plan`、`build_mode`、`ask`
或 `auto` 等上层快捷方法。

### 5.3 `Agent`

```rust
pub struct Agent {
    spec: ExecutionSpec,
}

impl Agent {
    pub fn start(
        &self,
        input: ExecutionInput,
        context: ExecutionContext,
    ) -> AgentExecution;

    pub fn start_ephemeral(
        &self,
        input: ExecutionInput,
        cancellation: CancellationToken,
        authorizer: Arc<dyn ToolAuthorizer>,
    ) -> AgentExecution;

    pub fn system_prompt(&self) -> &SystemPromptSnapshot;
    pub fn tool_definitions(&self) -> &[ToolDefinition];
}
```

- `Agent` 不实现 `Clone`，避免公共语义鼓励把同一会话 Agent 当作跨会话全局服务；
- `start(&self, ...)` 允许同一会话顺序复用；方法自身不维护锁或活动 Run；
- 每次启动只 Clone 不可变 `ExecutionSpec`，随后仍调用唯一 `AgentExecution::start`；
- `system_prompt` 和 `tool_definitions` 只用于宿主显示/核查冻结状态，不暴露可变内部状态；
- 不提供 `append_user`、`messages`、`resume`、`compact` 或 `start_session`。

Rust 类型系统不会识别两个 `start` 是否属于同一业务 Session，因此不会在 SDK 中加入
`AtomicBool`、Semaphore 或 SessionBusy。上层必须在 Journal 同一所有权边界设置活动 Run 闸；
Core Demo 对该行为提供确定性测试。

### 5.4 临时 Recorder

`start_ephemeral` 每次创建一个私有 `EphemeralExecutionRecorder`，不使用全局单例。内部仅持有：

```rust
struct PendingExchange {
    receipt: ExchangeReceipt,
    assistant: AssistantMessage,
}

struct EphemeralExecutionRecorder {
    next_receipt: AtomicU64,
    pending: Mutex<Option<PendingExchange>>,
}
```

行为如下：

1. `begin` 在短同步锁内拒绝重复 pending，保存完整 AssistantMessage 并返回唯一 receipt；
2. `complete` 校验 receipt，原子移除 pending，接收完整 ToolMessage 批次后丢弃；
3. 锁不跨 `.await`，实现只返回立即 ready 的 boxed future；
4. Recorder 只服务本次 AgentExecution，不提供读取、序列化或恢复 API；
5. 正常取消继续遵守 Core 既有收敛契约：若已存在 pending exchange，Core 先为未结算调用
   补齐 interrupted ToolResult 并调用 `complete`；临时 Recorder 完成结算后丢弃该交换；
6. 只有进程异常退出或执行任务未正常收敛时，未持久化 pending 才会随 Recorder 丢失；
7. 最终无工具 AssistantMessage 仍只从 `ExecutionOutcome::Completed` 返回。

它不是 Noop：错误 receipt 或协议重入明确返回 `RecordError`。它也不是内存 Journal：完成后不
保存历史，进程中断后没有恢复事实。正式 Runtime 只能使用 `Agent::start` 显式传入自己的
Recorder。

### 5.5 `AgentBuildError`

新增 SDK 自有且 `#[non_exhaustive]` 的结构化错误：

```rust
#[non_exhaustive]
pub enum AgentBuildError {
    ZeroContextWindow,
    ToolCallsUnsupported,
    RequiredToolChoiceWithoutTools,
    NamedToolChoiceNotRegistered { name: ToolName },
    ReasoningUnsupported,
}
```

错误不包含 prompt、credential、Provider Options 正文或工具 schema。底层已经由构造器验证的
错误不重新包装进这一枚举。

### 5.6 顶层导出

`agent-sdk` 顶层导出自身的 `Agent`、`AgentBuilder`、`AgentBuildError`，并精选重导普通调用
路径直接需要的现有类型：

- `AgentExecution`、`ExecutionInput`、`ExecutionContext`、`ExecutionOutcome`；
- `ExecutionBudget`、`ModelRequestConfig`；
- `ExecutionRecorder`、`ToolAuthorizer`、`AllowAllAuthorizer`；
- `ContextWindowEvaluator`；
- `ModelService`、`SystemPromptSnapshot`；
- `ToolSetSnapshot`。

不重导 Provider schema、Transport、文件/Shell 请求、Memory 全部领域类型、Dispatcher、
策略 Adapter 或 testkit。专业扩展继续直接依赖所属 crate。SDK 不提供 wildcard prelude。

## 六、所有权、并发与 I/O

### 6.1 会话级所有权

```text
DemoSession / future Runtime Session
├── Agent                         冻结能力
├── Conversation Journal          动态权威历史
├── ActiveRun                     串行闸与取消
└── Approval Coordinator          当前交互
```

新建会话读取最新 Pinned Store 并渲染 Prompt 后创建 Agent。恢复会话读取持久化的原 Prompt
快照创建 Agent，不重新读取最新 Store。压缩 continuation 复用同一 Agent。

### 6.2 多会话并发

不同 Session 各有 Agent，但可以共享：

- `Arc<dyn ModelService>` 和内部 HTTP connection pool；
- `Arc<LocalFileSystem>` / `Arc<LocalShell>` 等线程安全能力；
- Pinned Store 和 RecallSource 的 Demo 私有同步实现；
- Runtime 未来提供的全局限流器。

每次 `AgentExecution::start` 创建一个 Tokio task。多会话依赖 Tokio Runtime 的有限 worker
线程异步推进，不创建一会话一线程。单个任务可能在不同 worker 上被轮询，所有公共 SPI 保持
`Send + Sync` 且不得依赖 thread-local 会话状态。

### 6.3 Provider 与 UI 解耦

Core Demo 的 AgentEvent 消费任务只做两件事：更新短临界区内的 Session 投影，并向有界
`tokio::sync::broadcast` 发布带 sequence 的轻量通知。它不等待 SSE 客户端写入。

```text
Provider Stream → AgentExecution → Demo Supervisor → Session Snapshot
                                           │
                                           └─ try/broadcast notification
                                                       │
                                                       ▼
                                                 SSE connection
```

- SSE 慢消费者收到 gap 后重新获取 snapshot；
- 页面关闭只结束该 SSE consumer，不持有 AgentExecution future 或 cancellation；
- Core 普通 AgentEvent 即使丢弃，Completion 和终态仍独立可靠；
- Demo Journal 和最终 `ExecutionOutcome` 是权威状态，浏览器不拼接 delta 作为持久事实；
- 运行中的流式缓冲允许因 Core 或 SSE 背压出现缺口，Run 完成时必须用
  `ExecutionOutcome::Completed` 的完整 AssistantMessage 校准并替换临时展示；
- 任意 Session 的取消令牌只属于其当前活动 Run。

SDK 不新增全局 executor、worker pool、广播器或并发限制。正式 Runtime 未来在上层配置全局
模型并发数与公平性。

### 7.2 CLI 与配置

真实启动入口：

```text
core-demo serve
  --workdir <ABSOLUTE_OR_RELATIVE_PATH>
  --data-dir <PATH>
  [--port <0..65535>]
  [--max-compaction-handoffs <N>]
  [--retry-transient]
```

- `workdir` 与 `data-dir` 必填，启动时解析为绝对路径并冻结；
- 二者都不是系统隔离边界；文件工具可接收绝对路径，Shell 以当前用户权限运行，人工验证使用
  专用目录；
- `port` 默认 `0`，只能绑定 `127.0.0.1`；
- 最大压缩交接次数显式可见，默认值写入 CLI help 和页面配置摘要；
- `retry-transient` 缺省关闭，启用时使用文档列明的有限 attempt、等待和 Retry-After 上限；
- 只有 `serve` 读取仓库根 `.env` 和 Provider credential；help、测试和 baseline 不读取；
- DeepSeek 环境变量沿用现有 Demo 的 `DEEPSEEK_API_KEY`、`DEEPSEEK_BASE_URL`、
  `DEEPSEEK_MODEL`、`DEEPSEEK_CONTEXT_WINDOW_TOKENS`；
- credential 只进入 `BearerCredential`，不进入页面、错误、日志、Snapshot 或 Store。

### 7.3 Server 状态

```rust
struct DemoRuntime {
    resources: Arc<SharedResources>,
    sessions: Arc<RwLock<BTreeMap<DemoSessionId, Arc<DemoSession>>>>,
    events: EventHub,
}

struct DemoSession {
    agent: Agent,
    journal: Arc<DemoJournal>,
    state: Mutex<DemoSessionState>,
    approvals: ApprovalCoordinator,
}

struct DemoSessionState {
    active_run: Option<DemoRun>,
    next_run: u64,
}
```

`DemoSessionId`、`DemoRunId`、状态枚举和 DTO 都保持 binary 私有。状态锁只保护 Session map、
活动 Run 和短投影；模型、审批等待、文件、Shell、Memory、压缩和 HTTP future 均不得持锁
`.await`。

启动 Run 的顺序：

```text
校验输入
→ 短锁确认 Session idle
→ 用户消息进入 Demo Journal
→ 冻结本次 Plan/Build × Ask/Auto 与 cancellation
→ 标记 active Run
→ 释放锁
→ 构造本次 Authorizer + Recorder + ExecutionContext
→ Agent::start
→ 独立 supervisor 消费 events 与 completion
```

同一 Session 已有 active Run 时返回 `SessionBusy`，不会自动取消、覆盖或排队。不同 Session
互不持有对方的锁和取消令牌。

### 7.4 私有 HTTP/SSE

建议路由：

```text
GET  /api/snapshot
GET  /api/events
GET  /api/sessions/{session_id}/snapshot
POST /api/sessions
POST /api/sessions/{session_id}/runs
POST /api/sessions/{session_id}/runs/current/cancel
POST /api/sessions/{session_id}/approvals/{approval_id}/decision
```

全局 snapshot 只返回 Session 摘要、全局 sequence 和脱敏配置；指定 Session 的 snapshot 返回
该会话的 Journal、Run、审批投影和相应 sequence。当前选中哪个 Session 只属于浏览器本地
展示状态，Server 不保存 UI 选择。SSE 通知携带 `session_id + sequence + event kind`，只提示
客户端局部更新或重新拉对应 snapshot，不承载权威完整消息。

沿用 Safety Demo 已验证的安全边界：loopback、严格 Host、POST 必须同 Origin、无通用 CORS、
`Cache-Control: no-store`、限制性 CSP、`textContent` 渲染和不可信内容禁止 `innerHTML`。
不设置访问 token；页面固定提示 Shell 以当前用户权限运行，路径规则不是 OS 沙箱。

### 7.5 页面结构

页面使用原生 HTML/CSS/JavaScript，不增加 Node/Vite 工程：

```text
┌─────────────┬─────────────────────────┬──────────────────┐
│ Sessions    │ Journal / streaming     │ Run inspector    │
│ 新建与状态   │ 当前会话消息与工具过程     │ 模式/审批/终态     │
└─────────────┴─────────────────────────┴──────────────────┘
```

桌面宽屏固定视口高度，Session 列表、消息区和检查器分别滚动；窄屏允许整体滚动。只有用户原本
位于消息底部时才自动跟随。断线、sequence gap 或 snapshot 校准期间禁用写动作。

页面只提供 SDK 验证必需的：新建/切换 Session、Plan/Build、Ask/Auto、提交、审批、取消、
实时事件和终态。不加入设置中心、历史搜索、Trace 回放或产品导航。

## 八、Demo 能力装配

### 8.1 模型与重试

Core Demo 构造 `OpenAiCompatibleService`，使用 `ModelRequestConfig` 显式启用 DeepSeek
thinking，并通过 DeepSeek Provider Options 指定 `reasoning_effort=high`。启用
`--retry-transient` 时在其外包装现有 `RetryingModelService`；不启用时直接使用 Provider
Service。重试原因固定为 connection、timeout、rate-limit 和 unavailable，追加尝试间隔固定为
250ms/1s，`Retry-After` 上限为 5s。Demo 不复制 retry 实现，也不透明重试已建立流。

### 8.2 文件、Shell 与安全

- 使用 `agent-tools-local` 的 LocalFileSystem/LocalShell；
- 使用 `agent-tools::SessionPathResolver` 和标准文件/Shell 工具壳注册 ToolSet；
- Plan/Build 能力规则与 Ask/Auto fallback 保持 Demo 私有；
- Plan 全部策略未识别的授权事实由最终 Authorizer 明确 Deny，不允许 fail-open；
- 通过现有 typed policies、`ComposedToolAuthorizer` 和最终 Authorizer 装配；
- AllowAll 只能是用户明确选择 Auto 后的最终 fallback；
- Shell command、workdir、timeout、process mode 和风险提示完整展示；
- Demo 不持有 detached 服务句柄，行为和风险沿用 v0.4.0 契约。

不从 Safety Demo 导入私有模块。规则实现只覆盖 Core Demo 页面展示的最小行为，不新增产品
审批契约和持久授权。

### 8.3 Pinned Memory 与 Recall

Core Demo 在 `data-dir` 私有实现：

```text
pinned-memory.json
recall-records.json
```

实现遵循 Memory Demo 已验证语义：同目录临时文件、flush、sync、persist 后更新内存；单进程
单 writer；Recall 每次读取或使用受控缓存，结果保留 source。Store/Source 代码留在 Core Demo，
不新建 `agent-memory-local`，也不让 Core Demo 依赖 Memory Demo binary。

新 Session 创建时：

```text
基础说明 parts
→ 最新 Pinned Store 渲染 part
→ Recall Source 使用说明 part
→ SystemPromptSnapshot
→ AgentBuilder
```

同一 Session 内记忆工具修改 Store 后不重建 Agent；新 Session 读取最新 Store。页面可以展示
当前 Agent 的冻结 Prompt 摘要和 Store revision/条目数，但不默认打印完整敏感正文。

### 8.4 Journal 与 Recorder

Core Demo 使用真正的私有内存 Journal Recorder，而不是 SDK 临时 Recorder：

- UserMessage 在 Run 创建前进入 Journal；
- begin 保存 pending Assistant tool call；
- complete 原子提交 Assistant + 整批 ToolResult；
- 最终 Completed message 由 supervisor 提交；
- snapshot 只投影 completed exchange；
- Demo 进程异常后不恢复 Journal，这一限制在页面和文档明确说明。

SDK 的 `start_ephemeral` 由离线 examples 和单元测试验证；完整 B/S Demo 用显式 Recorder 证明
未来 Runtime 替换路径。

### 8.5 上下文压缩交接

Core Demo 私有 `CompactionCoordinator` 只调用 `agent-context` 公共能力：

```text
ExecutionOutcome::CompactionRequired
→ 从 Demo Journal 读取最近 completed snapshot
→ ContextLayout + RollingSummarySameModel
→ validate_replacement
→ 原子替换 Demo Journal 当前有效 snapshot
→ 检查显式 handoff 上限
→ 使用同一 Agent 启动 continuation
```

压缩不刷新 System Prompt，不重新读取 Pinned Store，不生成新 UserMessage。Provider Overflow
所在未完成 Step 不进入 Journal。摘要输出预算固定为 1024 tokens，并至少保留最近 1 个完整
User Turn；`--max-compaction-handoffs` 默认值为 2。到达显式 handoff 上限后 Run 受控失败，不
形成隐藏无限循环。该协调器是 Demo 私有验证代码，不进入 SDK。

### 8.6 可靠性观察范围

Core Demo 只展示 AgentEvent、模型重试 attempt 摘要和宿主状态，不复制 v0.6.0 的 JSONL、
Complete/Incomplete、Wire Replay、Model Replay 或 Timeline。完整可靠性仍由 Reliability Demo
专项验证。

## 九、公共 API 候选基线

### 9.1 三层清单

归档时把公共面按三层记录：

1. **普通入口**：`agent-sdk` 的 Agent 构建和执行路径；
2. **扩展 SPI**：ModelService、Tool、ToolAuthorizer、ExecutionRecorder、RecallSource、
   CompressionStrategy 等上层实现边界；
3. **高级 Adapter API**：Provider Codec/Transport/Wire、Dispatcher、resolved invocation、
   本地能力配置等专业接口。

SDK 只重导第一层直接需要的类型，不用可见性修改把第二、三层隐藏起来。

### 9.2 审查办法

- 使用 `cargo doc --workspace --no-deps` 和 rustdoc broken-link warnings 检查公共文档；
- 使用 `rg '^pub '` 与 rustdoc 输出生成人工可审阅清单；
- 对每个候选公共类型记录所有权、失败语义、线程安全和调用方；
- 删除或私有化必须有“仅单模块/仅测试/仅 Demo 使用”的实际搜索证据；
- 公共 enum 的演进策略逐项记录，不机械给所有既有 enum 添加 `non_exhaustive`；
- 新增 SDK 错误使用 `#[non_exhaustive]`，其余 serde 类型保持既有兼容形状。

不引入 `cargo-public-api` 或 `cargo-semver-checks` 新工具链依赖：当前尚未发布 crate，也没有可
比较的发布基线。首次候选清单作为后续人工和工具比较的基准。

### 9.3 crate 版本

根 `[workspace.package].version` 和现有 package 版本本版本保持不变；项目 `v0.7.0` 仍是能力
里程碑。是否发布、哪些 crate 同版本和 MSRV 承诺留给 Runtime 真实接入后的独立决策，不在
本版本写入无法验证的兼容承诺。

## 十一、性能基线

### 11.1 实现方式

不引入 Criterion 或 nightly `#[bench]`。在 `tools/core-demo/examples/core_baseline.rs` 使用
标准库 `Instant`、`std::hint::black_box` 和确定性 scripted/fake 能力，固定预热与迭代次数。

运行命令：

```bash
cargo run -p core-demo --release --example core_baseline
```

程序输出机器可复制的 JSON 行，至少包含 case、input_size、iterations、elapsed_ns、target、
profile 和 rustc version。运行者把主机 CPU/内存、操作系统、命令和结果写入兼容性基线文档。

### 11.2 测量用例

1. 以固定数量的完整 User Turn/Tool Exchange 构造 ContextLayout；
2. 注册并冻结固定数量的合成 Tool Definition；
3. 使用大量 scripted text delta 验证慢/断开 AgentEvent consumer 不阻塞 Completion；
4. 两个独立 Agent/Session 并发执行并取消其中一个；
5. 同一 Agent 顺序重复启动，记录 Facade 相对直接 Core 装配的额外成本。

功能正确性由普通测试断言；baseline 只报告测量，不以时间 sleep 判断并发顺序。真实 Provider
网络、磁盘、Shell 和浏览器渲染不纳入 Core 性能数字。

### 11.3 判定

本版本建立首份结果，不制定跨硬件绝对 SLA。若 SDK 相比直接 Core 路径出现数量级额外分配、
明显阻塞或随 Session 数线性复制共享资源，必须在验收前修复或记录为 blocker；微小波动不作为
失败依据。

## 十五、风险与控制

- **SDK 复制 Runtime**：Agent 不持有动态历史、Run、调度或 Store；压缩和 SessionBusy 只在
  Demo 私有上层实现。
- **请求配置扩大 Provider 特判**：Core 只 Clone provider-neutral 字段；DeepSeek 选项由
  宿主显式构造并由 Adapter 校验。
- **临时 Recorder 被误用**：仅通过名称明确的 `start_ephemeral` 使用，每次执行独立，文档
  固定说明无持久化和恢复。
- **Agent 可被误并发启动**：文档和类型定位明确一会话一 Agent、同会话由宿主串行；不在
  无 Session 所有权的 SDK 内添加不可靠锁。
- **UI 反压 Provider**：Supervisor 先更新内存投影，再 best-effort broadcast；SSE 自己消费
  broadcast，绝不直接持有模型流。
- **ToolSet/Prompt Clone 成本**：先用 baseline 量化；只有出现数量级问题才调整内部共享表示，
  不提前把所有请求类型改为 Arc。
- **Demo 私有实现重复**：重复只限顶层验证宿主；不为消除少量重复提前制造错误公共层。
- **平台声明过度**：证据分级，条件编译和 fixture 不写成实机通过。
- **候选 API 过度承诺**：记录首次基线和破坏性变更规则，但不宣称 1.0 或 crates.io 稳定性。

## 十六、方案结论

本方案没有遗留开放性架构问题。后续开发计划可以直接按以下主线拆分：

```text
Core 请求配置补全
→ agent-sdk 薄 Facade
→ 公共 API/文档收敛
→ B/S Core Demo 基础宿主
→ 完整能力装配与多会话 I/O 验证
→ 性能/兼容基线与版本验收
```

任何实现中发现需要让 SDK 持有 Session/Run、让 Core 等待 UI、引入正式 Runtime 类型或新增
业务能力的情况，都属于偏离本方案，必须停止扩大改动并回到设计确认。
