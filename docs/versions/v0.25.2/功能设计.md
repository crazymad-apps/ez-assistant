## 二、背景与目标

Host 已能独立承载 Runtime 与随包 Web，但无桌面环境下仍缺少面向用户的本机管理入口。
现有 Host 只有底层启动命令；Desktop 的发现、启停和设置能力依附桌面入口，不能直接满足
服务器终端、SSH 会话或不启动 Desktop 时的日常管理。

本版形成以下闭环：安装 Client → 必要时配置本机 Host → 启动或复用实例 → 查看就绪状态
和访问地址 → 通过随包 Web 使用 Agent → 显式停止或重启 Host。

成功标准：

1. Client 使用 TypeScript 与 Node.js，能够脱离 Desktop 独立管理本机 Host。
2. Client 与 Desktop 同级，各自分发包内置 Host，同机共存时共享同一用户、同一 Runtime Home 的实例。
3. 普通操作通过命令完成；`config` 交互配置访问设置，Host 未启动时也可使用。
4. 启动、就绪、不可用与停止具有真实反馈；退出 Client、关闭终端或断开 SSH 不等于停止 Host。
5. Client／Desktop 与 Host 每次连接初始化都执行双向应用协议兼容检查；数据库单独执行 Host 准入保护。
6. 提供可配置的 Host 自启服务，默认关闭，主要满足 Linux 服务器重启后自动启动 Host 的需要。
7. Client 可以独立更换技术架构；其构建、运行或私有组件不可用时，Host／Desktop 仍能独立构建和正常使用。

## 四、功能范围与使用路径

### 4.1 产品安装与本机目标

- Client 与 Desktop 均可单独安装，各自保留自己的随包 Host 文件；Host 不作为第三种产品单独分发。
- Client 运行时为 Node.js，分发主要走 npm（2026-09-10 用户补充）。用户预装受支持 Node/npm，平台附件携带编译 Host/Web；npm 升级或卸载不能删除固定保留的在用 Host、修改服务或共享数据。
- 每次命令操作一个本机 Runtime Home。默认与 Desktop 使用同一用户数据目录；允许显式指定
  绝对路径，不因当前工作目录变化切换数据，也不维护另一份“当前远端”或连接 profile。
- Runtime Home 是实例和共享数据的边界。隔离实例必须显式使用不同目录与不冲突的端口；
  不把路径别名视为允许同库多开的依据。默认端口沿用 7240。
- Client 安装目录、Desktop 安装目录和共享用户数据分开。卸载一个产品保留共享数据和另一产品文件；
  若活动 Host 来源将被移除，须先明确提示停止／切换要求，不能留下未说明的后续启动路径。

正式可执行入口名称为 `ez-assistant`，命令参数、退出码与反馈以交互指导为准，不沿用 `ez-client-demo` 名称。

### 4.2 命令入口与状态

普通命令执行一次后退出，只有 `config` 进入交互流程。无参数显示入口说明，不启动 Host、不进入常驻菜单。

| 命令 | 正常行为 | Host 未运行时 |
| --- | --- | --- |
| `start` | 发现并复用兼容实例；无实例时按当前手动／服务管理方式启动，等待业务就绪后报告成功 | 显式启动 |
| `status` | 查询进程、兼容情况、启动阶段、就绪状态、版本、地址、自启配置及当前管理方式 | 返回“未启动”，仍可查询自启配置，不创建实例 |
| `stop` | 展示共享实例的影响范围，发出受控停止并等待原实例退出 | 明确“已停止”，作为无操作成功返回 |
| `restart` | 先核实当前来源可再次启动，受控停止原实例，再按原来源和配置启动 | 提示先使用 start，返回未执行 |
| `config` | 交互配置本机 Host 的访问设置和自启服务 | 可离线配置访问设置及自启策略，不隐式启动业务服务 |
| `web` | 输出当前有效 Web 地址；可用时请求系统浏览器打开 | 提示先启动，不隐式启动 |

`status` 的“未启动”“初始化中”“业务就绪”“初始化失败”是既有事实的组合展示，
不为这些展示状态增加持久化生命周期。不能把 PID 存在、监听可达或启动请求已发出当作业务就绪。
初始化阶段沿用已有诊断，不编造百分比、剩余时间或任务恢复进度。

普通命令不弹出交互选择，帮助明确 `stop`／`restart` 影响全部连接与任务；执行时再次展示该范围。
输出支持重定向，非 TTY 不播放动画。查询成功与操作成功使用成功退出码；参数错误、操作失败、
不兼容和用户取消均可区分，具体代码由交互指导统一。`config` 缺少 TTY 时明确失败，不从管道自动提交配置。

基础诊断使用已有启动阶段、错误及日志来源，必要时给出日志位置；本版不单独建设持续日志流或运维面板。
只查询诊断也需遵守认证边界。不兼容时能安全读取多少就展示多少，不能靠调用未知业务命令补全状态。

### 4.3 首次启动与日常使用

首次使用路径：

1. 安装 Client，检查命令帮助与版本。
2. 通过普通 Web 使用 Agent 时，先进入 config 设置访问密码，本机 Web 也需要密码。
   仅使用原生 Client 管理 Host 可以暂不设密码；非本地访问保持默认关闭，需要其他设备访问时再显式开放。
3. 执行 start，观察发现、版本检查和 Host 原有初始化阶段。
4. 业务就绪后获得地址；通过 Web 登录、配置模型和使用 Agent。
5. 命令退出或 SSH 断开后，Host 已接纳的任务继续。再次执行 status 查询同一个实例。
6. Linux 服务器需要开机自启时，在 config 中开启自启服务；查看实际启用结果，
   系统重启后由服务机制启动同一 Runtime Home，再通过 Client 或 Web 连接。

启动失败路径：

- 已有 Host 正在初始化时，等待或显示其真实阶段；不因暂未就绪启动第二实例。
- 已有 Host 初始化失败时，显示诊断并退出；修复后由用户显式 restart，不自动重试迁移或清理数据。
- 等待超时或用户取消等待时，报告当前已知状态和下一步查询方式。只终止 Client 的等待，
  不将超时解释成 Host 已停止，不撤销已经接纳的 Host 操作。
- 端口冲突、无权访问目录、发现信息无效、认证失败和 TLS 错误分别说明；
  不自动换端口、删锁文件、删除未知进程或放宽证书校验。

### 4.4 交互式 config

进入时展示目标 Runtime Home、在线／离线状态与脱敏当前配置，然后选择修改项。
配置分为“Host 访问设置”和“启动设置”；前者由 Host 配置能力负责，后者配置本机自启服务，
详见 4.6。自启不混入 Host 访问协议或业务数据库，表单不涉及模型、Agent 或远端 Client 登录资料。

| 配置项 | 行为 |
| --- | --- |
| 访问密码 | 显示已设置／未设置；遮罩输入、二次校验、独立确认保存，不回显原文或哈希 |
| 非本地访问 | 默认关闭；已有密码时才可显式开启 |
| 监听端口 | 统一端口，默认 7240；即时校验合法范围，实际占用按 Host 能力核实 |
| HTTP／HTTPS | 两种协议均继续认证；HTTPS 使用 Host 证书与私钥 |
| 证书与私钥 | 输入本机 Host 可访问的文件路径；正式保存与启动按既有 TLS 要求校验 |
| 允许的 IP 或域名 | 可填写 IPv4、IPv6 和域名，不按地址类别限制输入；域名匹配忽略大小写并支持国际化域名。开启非本地访问后可直接用 IP；localhost 经转发访问时按域名登记 |

访问设置先形成草稿，预览并确认后提交；校验失败就地修正。退出有未保存草稿时默认返回编辑，
用户可明确放弃。Esc／Ctrl+C 取消当前配置流程。已经独立保存成功的密码或配置不因随后取消而回滚；
取消只放弃未提交内容，不能显示“全部修改已撤销”。

**在线访问配置：**

- 使用正在运行 Host 的既有访问配置能力，读取真实结果，不直接修改其配置文件。
- 密码保存后已有普通登录失效，本机原生权限路径沿用既有规则；密码与其他草稿分别保存。
- 非本地访问开关及域名沿用即时生效语义。监听端口、协议或证书修改保存后明确提示需要重启，
  不自动重启共享 Host；展示当前地址与待生效设置的区别。
- 开启非本地访问期间修改监听配置，须先关闭并保存；修改后先保存、显式重启，再重新开启。
  配置预检通过不代表下次启动时端口必然可用。
- 多个 config、Desktop 或 Web 同时修改时，复用现有配置冲突机制：旧草稿提交失败，
  明确要求重新读取和确认，不静默覆盖其他入口已保存的设置。
- Host 正在初始化或处于只可诊断状态时，不冒充离线访问配置；提示等待或显式停止后再编辑访问设置。
  本机自启配置的查询和关闭不依赖 Runtime 业务就绪。

**离线访问配置：**

- 确认目标没有活动 Host 后，使用同一 Host 配置来源和校验语义完成访问配置。
  不启动 Runtime 业务、读取会话或触发数据库初始化／迁移，也不建立 Client 专用配置副本。
- 只有用户确认保存时才产生配置写入；没有配置时展示默认值，读取失败不得误判为首次初始化。
- 首次密码与访问设置可在启动前配置，保存后明确“供下次启动使用”；不声称已建立监听或已开放访问。
- 保存前重新确认 Host 状态和配置是否变化。若编辑期间 Desktop 启动了 Host 或另一入口保存了配置，
  本次保存停止并要求重新读取，不与运行中 Host 并行写入。
- 离线配置仍由 Host 所属的配置能力承担解析、校验、密码处理和写入规则。
  具体调用方式在技术方案确定，不以本需求为由在 Node 中复制整套 Rust 配置实现。

### 4.5 Web 入口

`web` 使用已发现实例的实际地址，不能把待重启的端口当作当前可用地址。
在无图形终端中只输出地址；浏览器打开失败时保留地址并说明结果，Host 继续运行。
服务器上显示的 loopback 地址只代表服务器本机；不得将它表述成其他设备必然可达的访问地址。
外部访问依赖用户配置的域名／服务器地址、开放设置及网络条件，不自动猜测公网 IP。

Client 首版打开普通 Web 登录入口，不输出或传递本机 bootstrap 凭据，不新增 CLI 浏览器免登录机制。
Desktop 已有的普通登录快捷入口继续保留原有授权边界。
未设置密码时，web 输出当前地址并提示先在 config 设置密码，不打开无法登录的页面，返回失败；
无浏览器或浏览器调用失败但已交付核实地址时，提示手动打开，不误称已经登录，按交互指导返回成功。

### 4.6 自启服务配置

Client 的 Host 自启是本版已确认的可选配置，默认关闭，主要面向 Linux 服务器。Desktop 保留自身桌面启动逻辑，不套用 systemd＋linger；本版不新增 Desktop 开机／登录自启功能。以下是 Client 服务器模式的启停语义，
具体服务实现、权限与注册方式归技术方案；不要求 Client 保持常驻。

- config 提供自启开关，展示实际启用状态、目标 Runtime Home、运行用户和注册的 Host 来源。
  首次安装或普通 start 不自动开启；仅进入配置或退出草稿不注册服务。
- 用户确认开启后，完成平台所需服务注册并核验结果；失败时分别展示服务文件、开机启用、linger
  和当前运行的实际结果，无法回读时显示未知，不能将部分失败统一写成未启用或成功。
  服务按明确的用户身份使用原数据目录，不默认切换为 root 或新目录。
- 开启自启只配置后续自动启动，不立即启动、重启或接管当前手动 Host；
  关闭自启阻止后续自动启动，不顺带停止当前实例。当前运行状态与自启状态分别展示。
- 已有手动 Host 时，开启自启后继续复用当前实例，不拉起第二份；需要转由服务管理时，
  经显式停止再启动完成切换。服务启动与 Client／Desktop 启动竞争仍服从同一实例锁。
- 已由服务管理的 Host，其 start／stop／restart 须与平台服务状态协调，保留受控关闭语义。
  显式 stop 后不能被服务立即拉起；stop 不等于关闭开机自启，下次系统启动仍按配置执行。
- 关闭自启的操作应能在 Host 未运行或业务初始化失败时完成。服务使用的安装路径将被卸载时，
  先处理对应自启注册，不删除共享数据或另一产品的服务／安装文件。
- 系统自启同样执行数据库准入和启动诊断；失败不自动修改兼容下限、修复数据或切换随包版本。
  Host 自启成功不表示旧任务自动继续，任务恢复仍沿用 Runtime 既有规则。
- 自启能力按平台如实展示，主要验收 Linux 服务器重启与无需交互登录的启动路径。
  其他平台支持范围及无可用服务机制时的提示归技术方案，不把 Linux 的结果视为全平台通过。

## 五、共享 Host 与兼容保护

### 5.1 Client／Desktop 共存和生命周期

1. 各安装包持有自己的 Host 文件，运行实例依 Runtime Home 识别。两个入口同时启动时，
   由 Host 现有实例锁决定所有者；另一端重新发现、验证并复用获胜实例。
2. Client 与 Desktop 都不得因已有 Host 版本不同或尚未就绪而另开同库实例。
3. 关闭窗口、退出 Client／Desktop、关闭浏览器与停止 Runtime 是不同动作；
   只有显式停止才受控结束 Runtime。断线仍沿用现有业务恢复规则，不自动重放工具或继续旧任务。
4. 本稿建议普通 restart 保持当前 Host 来源和版本，不因调用方不同切换到其随包版本；
   Desktop 的重启入口须同步这一行为。重启前核实原来源可再启动，缺失时先失败，不先停后猜来源。
5. 重启失败分别展示“原实例未停止”或“已停止但未重新就绪”，不误报成功，也不自动切换版本补救。
6. 本版不提供热替换或自动升级。用户安装新产品后，已有兼容实例可继续运行；
   要使用新随包 Host，明确停止原实例后由目标安装的 start 启动，数据库检查仍然执行。
   若已配置自启，还须显式同步服务注册的 Host 来源，不能让下次开机悄然切回另一版本。

### 5.2 应用协议最低兼容版本

Client、Desktop、Host 分别携带当前软件版本号和最低兼容软件版本号，均使用 `0.25.2` 这样的软件发布版本。
用户在技术方案评审中明确使用软件版本号，不另设独立协议版本号。
同一发布版本的三个组件使用同一份最低兼容版本定义，只表达应用协议层兼容性。
UI 样式、客户端内部实现或数据库格式本身不直接决定这个下限。
本节适用于 Client、Desktop 和随包 Web；智能终端的设备连接兼容留待两项目后续同步设计。

对任一客户端与 Host，只有同时满足以下条件才可完成业务连接初始化：

```text
客户端当前版本 ≥ Host 声明的最低兼容版本
Host 当前版本 ≥ 客户端声明的最低兼容版本
```

- Client 与 Desktop 之间不直接比较版本。版本不同且双向条件均满足时允许连接。
- Host 也必须检查实际调用方的版本要求，不能只依赖客户端自行检查；具体交换方式归技术方案。
- 检查覆盖首次初始化、断线后重新初始化、Host 重启后连接，以及启动竞争后的重新发现。
  Desktop 既有本机与远端入口均适用；Client 本版仍只管理本机。
- 版本通过不代表认证或权限通过，也不替代按入口实际需要检查能力。
  现有独立协议版本字段及整数相等检查在本版移除，能力检查按实际入口保留。
- 任何方向不满足时，当前客户端连接／启动失败，显示双方当前版本和未满足的下限。
  保留已有 Host 与任务，不自动停止、升级、降级、替换、修复或另开实例。
- 缺少或无法解析兼容声明时，不能猜测为兼容。可读取的安全诊断仍可展示；旧入口的具体拒绝路径
  和发布衔接在技术方案核对，不默认保证所有已发布程序都能执行新检查。
- Web 继续随 Host 发布，共用前端初始化的变更须检查缓存旧页面和重连路径；
  不为 Web 建立第四套独立产品版本，也不能将旧页面默认视作新版本客户端。

### 5.3 数据库最低兼容 Host 版本

数据库持久保存自己的最低兼容 Host 版本，与应用协议下限相互独立。
数据库实际迁移到哪个版本和最低允许哪个 Host 访问是两个事实；必须保留既有迁移账本及校验。

- Host 先取得实例锁，再对已有数据库只读核实兼容信息；满足下限前不得进行迁移、业务写入、
  修复、FTS 初始化或持久日志模式修改。Client 与 Desktop 不直接打开数据库判断或改写下限。
- Host 低于数据库下限时，业务初始化失败，保留原数据库与业务文件。
  沿用 v0.25.1 已认证的启动诊断能力；诊断监听存在不表示业务就绪，不新增救援端口。
- 数据结构、字段语义及持久化格式变化都可能要求提升下限。提升与造成不兼容的数据迁移原子提交；
  不因启动较新 Host 就覆写下限，不允许旧 Host 降低下限。
- 达到下限仅是必要条件，仍须通过完整性、迁移链和目标数据校验。
  本版不默认放开较旧 Host 读取任意较新数据库，不通过删除现有高版本库拒绝检查实现“兼容”。
- 已发布旧库尚无此信息，须在技术方案明确识别、首次建立和失败策略。
  缺少、损坏、来源不明分别处理，不统一当成可写的新库。
- 新库、已知旧库升级与既有高版本拒绝路径均需验收。迁移继续沿用独立备份、实际回读验证和
  失败停止规则；会话正文与附件不是 SQLite 备份的一部分，不宣称已整体备份。

## 六、模块边界、现有基础与契约影响

| 能力／模块 | 已有事实 | 本版新增或调整的必要性 |
| --- | --- | --- |
| 正式 Client | 只有临时交互 Demo | 新增面向用户的本机产品入口，Node 负责命令、交互与连接，不装配 Runtime |
| [Host 发现与锁](../../../apps/runtime-host/src/endpoint.rs) | 私有发现、实例身份和 Runtime Home 锁 | 复用所有权基础，补双产品来源与竞争结果展示；不增加第二份实例注册表 |
| [Host 启动诊断](../../../apps/runtime-host/src/startup.rs) | 监听后提供 Starting／Ready／Unavailable，业务受就绪约束 | Client 消费既有阶段；兼容失败接入现有诊断，不复制 Runtime 状态机 |
| [Host 访问配置](../../../apps/runtime-host/src/access/mod.rs) | 密码、配置校验、冲突检查、即时策略与待重启投影 | 在线直接复用；离线尚无面向 Client 的入口，须补安全调用路径 |
| Client 本机服务适配 | 现有 Host 独立运行不等于已有系统自启服务 | 对接平台既有服务机制并核验注册状态；不新增常驻 Node 管理进程或 Runtime 业务配置副本 |
| [Desktop bootstrap](../../../apps/desktop/src-tauri/src/runtime_bootstrap.rs) | 发现、启动、受控停止；当前 restart 启动调用方随包 Host | 增加双向兼容，按共存策略修订重启来源；保持原生认证边界 |
| [协议状态与能力](../../../crates/assistant-protocol/src/host.rs) | 已有软件版本、协议版本、能力和启动状态 | 补客户端与 Host 的兼容声明／准入契约，检查所有实际生产者和消费者 |
| [存储迁移](../../../apps/runtime-host/src/storage/migrations/mod.rs) | 完整账本前缀、高版本拒绝、独立备份与事务迁移 | 增加独立存储下限与写入前准入；现有迁移版本不能替代下限 |
| [Desktop TypeScript Client](../../../apps/desktop/src/runtime-client/RuntimeClient.ts) | 有协议绑定与 HTTP 客户端，但含浏览器依赖 | 只提取两端实际稳定复用的部分，不整体搬入会话／SSE 客户端 |

Runtime 继续持有会话、Run、配置与调度权威状态。Host 负责传输、进程和本地存储适配；
共享应用协议保持轻量。业务入口、Agent Loop、工具、记忆和模型内部契约不因新增 Client 改变。

用户明确 Client 的可替换性为硬约束：Host、Desktop 与共享协议不得反向依赖 Client 的源码、
交互框架、构建脚本、运行时或私有状态。Client 通过既有应用协议与 Host 本机管理契约完成适配；
单纯替换其技术栈不触发 Host／Desktop 改造、共享配置迁移或兼容下限提升。
服务器服务直接启动 Host，Desktop 保留自身启动与连接逻辑；Client 升级保留在用 Host 文件和自启注册。两产品共享 Host 时仍使用同一发现、实例锁和兼容检查，不因此共用自启策略。

最小新增核查结论：生命周期和访问配置应以现有 Host 为基础；确有缺口的是 Client 入口、离线配置
调用路径、平台自启服务适配、跨组件兼容声明，以及数据库独立下限。删除这些缺口后现有事实不足以完成需求，
但不需要自建 daemon、第二数据库、通用客户端 SDK、会话副本或新的配置版本计数器。

## 七、关键取舍

| 取舍 | 理由 |
| --- | --- |
| TypeScript + Node.js | 用户明确选择，保持成熟 Node 运行环境；依赖版本另行锁定 |
| 命令式管理 + config 交互 | 普通操作可直接执行，访问设置通过预览和确认降低配置错误 |
| Client 聚焦本机管理 | Web 已覆盖 Agent 使用，本版无需另建远端目标与终端会话体验 |
| 双产品各带 Host、默认共用实例 | 两端均可独立安装，避免同库多进程与任务割裂 |
| 协议与存储各维护下限 | 两者保护不同兼容边界，不能用单个软件版本相等判断代替 |
| 基于现有诊断和配置路径 | 保留已有安全与恢复规则，避免 CLI 形成第二套业务机制 |
| 自启可配置且默认关闭 | 满足 Linux 服务器开机启动需要，用户仍可选择纯手动管理 |

| A18 | 原有 Desktop 本机／远端及随包 Web | 连接、认证、初始化和已有功能不因兼容改造回退；缓存旧页和重连有明确结果 |

| A23 | Client 架构替换与组件不可用 | Host／Desktop／协议构建不依赖 Client 工程或依赖安装；保留在用 Host 文件，使 Client 入口和 Node 不可用后，服务器服务仍直接启动 Host，Desktop 的既有启动、连接、使用和受控启停仍正常；不要求 Desktop 管理服务器 unit；仅 Client 内部变更不提高兼容下限 |

所有涉及 Host 与存储的自动化验收使用隔离 Runtime Home。用户实际数据库的操作仍须按

## 九、风险、产品取舍与后续文档

### 主要风险与处理要求

| 风险 | 处理要求 |
| --- | --- |
| 已发布旧程序不会自动执行新兼容检查 | 技术方案核对实际旧二进制、旧库和现有拒绝路径，明确首版准入范围，不承诺任意历史版本互通 |
| 数据库下限与迁移账本得出不同结论 | 两者均需满足；不能仅新增下限就删除既有高版本拒绝，也不能重复运行已提交迁移 |
| 离线编辑期间出现在线 Host 或新配置 | 提交时核实状态，复用配置冲突与实例所有权机制，冲突后保留当前正式配置 |
| 重启／卸载涉及另一产品的活动 Host | 停止前确认来源和后续路径，避免重启隐式升级或卸载后无可用来源 |
| 自启服务与手动进程的管理方式不同 | 分别展示自启与运行状态，协调受控停止、启动竞争、安装来源和卸载；Linux 实测无需登录的系统启动路径 |
| 原型只覆盖模拟交互 | 正式验收补真实 Host、Desktop、Web 与隔离存储证据，保留未验证平台和视觉项的实际状态 |

### 已转入技术方案与计划的产品取舍

| 项目 | 本稿建议 | 影响 |
| --- | --- | --- |
| 首批平台 | 以现有 Unix Host 为基础，macOS 与 Linux；Windows 后续核定 | 具体架构与安装格式见技术方案，实机条件在 M0 核对，不以本机原型代表跨平台通过 |
| Node 分发 | Client 包携带 Node runtime，用户无需预装 Node；Desktop 是否附加 CLI 暂不纳入 | 影响包体、签名和升级装配；Host 各自内置的已确认方向不变 |
| 普通重启 | 保持当前运行 Host 的来源和版本；换版本使用显式停止后从目标安装启动 | Desktop 当前重启路径需要同步调整，缺失来源须在停止前发现 |

自启服务的“纳入本版、配置形式、默认关闭、主要面向 Linux 服务器”已获用户明确确认；
4.6 的具体启停语义与技术方案保持一致；用户已认可 root 使用系统级 systemd、普通用户使用用户服务加 linger 的方向，
平台服务实现、权限和崩溃后策略按技术方案及开发计划落地。

### 归属技术方案的事项

- 三组件软件版本与最低兼容软件版本的唯一来源、首个下限、版本解析、初始化交换方式及旧协议整数的移除。
- 已发布 v0.25.1 等旧端缺少新声明的实际行为；新旧库识别、首次建立存储下限与旧 Host 防护衔接。
- 离线配置复用 Host 能力的入口，实例锁与配置冲突协调，TLS、配置错误及保存后的真实结果读取。
- 当前 Host 可执行来源的可靠获知、重启前校验、并发停止／启动、等待上限与取消清理。
