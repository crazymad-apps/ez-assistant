## 二、背景与问题

### 2.1 外部工具需要统一接入 Runtime

ez-assistant 已有本地文件、Shell、记忆和产品控制工具，但尚不能连接用户配置的 MCP Server。
用户需要让同一个 Agent 访问 GitHub、知识库或其他外部系统，同时继续受到产品现有的权限、审批、
取消、审计和结果持久化约束，不能让 LLM 绕过 Runtime 直接连接 MCP。

### 2.2 全量暴露 MCP 工具会挤占模型上下文

一个 MCP Server 可以提供几十个甚至更多工具。如果把所有 Server 的所有 Tool Schema 都作为模型
原生工具平铺到每次请求中，输入成本和误选概率都会随目录增长。Server 本身已经给出了业务范围，
更自然的路径是先选择 Server，再在该 Server 内查看或搜索工具。

Runtime 需要掌握已连接 Server 的工具目录以便发现和调用，但这不等于把完整目录全部发送给 LLM。
模型初始只需要知道可用 Server 的名称和业务范围，完整工具定义按需返回。

### 2.3 工具目录更新不应引入复杂的自动通知机制

MCP 允许目录发生变化，但首版没有必要建立活动 Run 的 Catalog revision、差异通知、自动重载或
上下文失效状态机。用户需要更新目录时，通过 Slash 入口提交一条结构化刷新 Command。
Command 与普通用户输入共用可见、可排序的可靠队列，但消费后直接执行 Runtime 控制动作而不创建
Agent Run。执行结果实时入库并更新 Snapshot，后续模型请求从规范 Conversation 和最新 Server
目录中获得结果。

### 2.4 只做 Tools 不能把连接层做成 Tools 专用实现

MCP Server 还可能提供 Resources 和 Prompts。它们与 Tools 共用 Server 身份、传输、认证和连接，
但发现方式、内容结构和 LLM 使用路径不同。首版只实现 Tools；连接与配置仍以 MCP Server 为对象，
不能把 Server 错误建模为“Tool Server”，也不为尚未实现的能力提前建立通用 Catalog 或统一条目类型。

## 三、版本目标与成功标准

`v0.23.0` 形成以下能力闭环：

1. 用户可在设置中的 MCP 管理页新增、编辑、启停、删除、批量导入和测试 MCP Server；Runtime
   从独立的用户私有 `mcp.json` 读取 Server，并通过 stdio 或 Streamable HTTP 建立连接；
2. 默认 Run 的模型上下文只看到当前可用 MCP Server 的名称和简短业务范围；用户通过 `/mcp`
   手动选择 Server 时，下一条输入直接携带该 Server 的有界工具定义上下文；
3. 模型仍可通过固定的 `discover_mcp_tools` 在一个明确 Server 内搜索工具，或取得该 Server 的全部工具
   定义；手动选择不增加第三个模型工具；
4. 模型通过固定的 `call_mcp_tool` 调用目标 Server 的实际工具，Runtime 完成参数校验、权限、审批、
   审计和 MCP 调用；
5. MCP 工具结果进入现有普通 Tool Result 与 Agent Loop，不建立 MCP 专属回复循环；
6. 用户通过 `/mcp refresh` 或 `/mcp refresh <server>` 提交结构化 Command；Command 按可见队列顺序
   消费，不创建 Agent Run，执行结果实时入库并更新 Snapshot；
7. Server 配置、连接和刷新语义能够在后续增加 Resources、Prompts 时继续复用，而现有 Tools 网关
   不需要改名或改写调用契约。

成功标准是用户能够完成以下路径：

- 配置一个 stdio MCP Server，刷新后让 LLM 发现并成功调用其中的工具；
- 配置一个 Streamable HTTP MCP Server，使用同一套发现、调用和结果展示路径完成调用；
- 在设置的 MCP 管理页粘贴一份标准 `mcpServers` JSON，一次导入一个或多个 Server；也可通过
  表单新增或编辑单个 Server，页面不会读取或回显已有 secret 值；
- 设置页保存只更新全局 `mcp.json`；用户通过会话中的 `/mcp refresh` 提交结构化 Command，
  队列消费后 Runtime 才替换活动连接与目录；设置页不提供刷新队列操作；
- 同时配置多个业务范围不同的 Server 时，LLM 先按名称和说明选择 Server，再只在该 Server 内发现
  工具，不进行跨 Server 工具相关度竞争；
- 用户输入 `/mcp` 后能够从可用 Server 中单选一个目标，所选 Server 以可移除标签绑定下一条输入，
  并在该 Run 首次模型请求中直接披露有界工具定义；
- Composer 中附件与引用位于最上方，Goal、Skill、MCP 等输入标签统一位于其下方、正文输入框上方；
- Server 工具较少时，LLM 可以一次取得全部完整定义；工具较多时，仍能使用查询条件获得有界结果；
- MCP 工具与现有产品工具同时存在时，模型原生 ToolSet 只增加固定网关，不随 MCP 工具数量线性增长；
- 未通过参数 Schema 校验、权限规则或用户审批的调用不会发送给 MCP Server；
- 权限界面、审计和工具详情展示实际 Server 与原始工具身份，而不是只显示通用网关名；
- MCP Server 连接失败、工具不存在、参数无效、调用超时或返回错误时，当前 Agent Loop 得到明确且
  可恢复的 Tool Result，其他 Server 和非 MCP 工具仍可工作；
- 用户修改配置或 Server 工具目录后执行 `/mcp refresh`，后续模型请求使用刷新结果；
- MCP 刷新 Command 入队后立即持久化并出现在 Queue Snapshot，队列阻塞时不会越过当前 Run
  或审批，但用户可调整其后续顺序；
- MCP 刷新结果以控制结果在 Desktop 投影，并以 user-role message 进入模型上下文，
  但不把原始 Slash 文本当作需要 LLM 解释的业务指令；
- 一个连接成功但不提供 Tools 的 MCP Server 不会被误判为连接失败，只是不进入当前工具发现目录；
- MCP 返回的文本和当前系统已经支持的工具内容能够沿用现有结果、裁剪、持久化和展示链路；
- 配置中的认证材料不会进入模型上下文、协议读响应、普通日志、错误详情或调试事件。

## 四、明确非目标

本版本不包含：

- MCP Resources 的列举、读取、订阅或对话注入；
- MCP Prompts 的列举、参数填写、对话插入或自动转换为 Skill；
- Sampling、Roots、Elicitation、Tasks、MCP Apps 或其他 MCP 扩展；
- 把 MCP Tool 注册成数量随目录变化的 Provider 原生工具；
- 在所有 MCP Server 之间平铺搜索工具；
- 把完整 MCP Catalog 写入 Session 冻结 System Prompt；
- `search/load/call` 三套模型网关、独立 `load_mcp_tools` 或 MCP 定义专属 continuation；`/mcp` 是
  Composer 输入修饰器，不是模型网关；
- 工具目录变化的自动监听、主动通知 LLM、目录差异消息、Catalog revision 或活动 Run 冻结目录；
- 让队列 Command 越过阻塞的 Run 或审批立即执行，以及在 Agent Step 间隙进行轮内消息插入；
- 项目级 `.mcp.json`、工具市场、远程 Registry、插件包、自动安装或配置同步；
- 交互式 OAuth 登录、Dynamic Client Registration 或浏览器授权流程；
- 兼容旧 HTTP+SSE Transport；
- 把 MCP Prompt 与现有 Skill 合并为同一领域对象或自动互相转换；
- 为未来 Resources、Prompts 提前创建统一 `McpItem`、通用 Catalog、持久化目录或第二套权限系统。

## 五、用户与 LLM 使用路径

### 5.1 配置与连接

- MCP Server 属于 Runtime 全局用户私有配置，不绑定单个 Session，也不由 Desktop 持有权威状态。
- 设置弹窗增加一级“MCP”管理页，作为普通用户维护 Server 的主要入口；这里配置的服务可供所有会话
  使用，页面提供 Server 列表、新增、编辑、启停、删除、批量粘贴导入、连接测试和当前 Runtime 状态，
  不要求用户手工维护主 `config.toml`。列表与详情不加副标题，详情删除入口放在 Header 右侧。
- Server 清单独立保存在 Runtime Home 下的 `mcp.json`，使用生态常见的 `mcpServers` 对象格式；
  `config.toml` 最多保留连接超时、调用超时和并发数等全局运行参数，不保存逐 Server 表。
  工具调用的全局超时仅作缺省值；服务可单独设置更长或更短的时间，留空恢复继承，不设固定的业务
  耗时上限。连接、目录与关闭的保护时限不因此放宽。
- 首版只管理用户级全局 `mcp.json`，不读取或写入 Workspace/项目级 `.mcp.json`。后续增加项目级来源时，
  在同一 Server 配置模型上增加来源与覆盖关系，不改变本版文件格式和管理协议。
- 每个 Server 至少具有稳定配置键、可供用户和 LLM 识别的名称、可选业务说明、启停状态和一种
  Transport 配置。
- stdio 配置表达可执行命令、参数、受控工作目录和必要环境；它启动的子进程属于工具能力实现，
  不改变 Desktop 与 Runtime Host 的正式双进程产品拓扑。
- Streamable HTTP 配置表达 endpoint 与必要的静态认证材料；非 loopback 明文 HTTP、安全 header
  范围和 secret 承载方式由技术方案按现有配置安全边界确定。
- 管理页支持粘贴完整 `{ "mcpServers": { ... } }` 或裸 Server map，一次预览并导入多个 Server；
  同名 Server 必须由用户明确选择替换，解析、校验和冲突确认完成后才一次写入，不能出现半批成功。
- 管理页表单按 `command` 或 `url` 判断 stdio 与 Streamable HTTP；导入时兼容常见 `type`、`transport`
  别名，保存时规范化为一种稳定格式。已有 Server 的 secret 只显示键名和“已配置”，留空表示保持，
  只有用户明确替换或删除时才修改。
- Runtime 启动或显式刷新时读取 `mcp.json` 并连接启用的 Server。单个 Server 失败只形成该 Server 的诊断，
  不阻止 Runtime 或其他 Server 使用。
- 管理页的连接测试只对当前草稿建立临时候选连接，复用实际刷新时的 Tools 目录与 Schema 校验后关闭，
  不保存草稿、不替换活动连接，也不授予工具权限。工具说明较长只警告并完整保留，不阻止连接成功；
  无效 Schema 和目录整体超限仍会失败。
- 保存、启停或删除只可靠更新配置文件，不绕过 Session 队列直接修改活动连接。设置页只保留重新读取
  配置快照的图标，不显示刷新队列状态条；用户在会话执行 `/mcp refresh`，或下次 Runtime 启动时加载。

### 5.2 Run 开始时披露 Server 目录

默认情况下，在每个 Run 的首个模型请求前，Runtime 生成一段隐藏的 MCP Server 目录上下文。目录只
包含当前可用 Server 的稳定名称和简短业务范围，例如：

```text
github：管理仓库、Issue、Pull Request 和 Actions
notion：管理页面、数据库和内容块
```

约束如下：

- 不包含完整工具名称、参数 Schema、认证材料、连接地址或内部诊断；
- 只投影当前至少存在一个可向模型披露工具的 Server；如果某 Server 的所有 Tool 都被明确
  Deny，该 Server 不进入模型目录；
- 不显示为用户消息气泡，也不把 Server 说明写入 Session 冻结 System Prompt；
- 同一个 Server 的工具数量变化不触发对活动 LLM 的主动消息；
- Server 名称和说明只是能力选择信息，不能提升外部内容的指令优先级；
- 精确 Provider role、消息包装、是否复用现有 Runtime Hidden Message 投影，由技术方案确定，但不得
  为此创建新的产品 Session、Run 或用户输入。

若当前输入带有用户手选 MCP 标签，则不再注入全部 Server 目录，而改为只注入所选 Server 的有界工具
定义，并把该 Run 的 MCP 网关范围限制为该 Server；具体冻结和超限方式见 5.3。

如果当前没有可用 MCP Server，固定网关可以不装配，或返回明确的“当前没有可用 MCP Server”；
具体选择由技术方案结合现有按 Run Tool Assembly 确定。

### 5.3 用户手动选择 MCP Server

Composer 增加 `/mcp` 入口，交互与 `/skill` 保持一致：输入或选择 `/mcp` 后打开 MCP Server
选择器，用户单选一个当前可用 Server，Composer 清空 Slash 文本并显示可移除的 `MCP · <display name>`
标签。它只修饰下一条完整用户输入，本身不入队、不创建 Command，也不触发 LLM；可以与一个 Skill、
Goal、附件和引用同时存在。

用户提交后，Runtime 将稳定 Server key 和冻结展示名与 Input、UserMessage 标签、首次 Run 原子绑定，
并在该 Run 开始时生成隐藏 Runtime 上下文，标明“该 Server 由用户显式选择”。在不超过上下文上限时
直接披露该 Server 当前所有可披露 Tool 的完整定义；完整定义超限时改为披露有界摘要，并明确要求模型
通过 `discover_mcp_tools` 取得目标工具的完整 Schema。明确 Deny 的工具不进入两种披露结果。

手动选择的作用是省去模型在多个业务范围之间的第一层判断，并把本次 Run 的 MCP 披露和调用范围限定
为所选 Server；它不授予调用权限，不冻结连接，也不绕过调用时的当前目录、Schema、权限和审批重校验。
后续普通输入若未再次选择 MCP，不自动继承 Composer 标签；Conversation 只保留可审计的选择标签，
不把整份动态工具定义永久写入历史，也不建立 Session 级“当前 MCP”开关。若同一条输入还启动 Goal，所选
Server 随 Goal 自动续跑继承；用户带新 MCP 标签恢复 Goal 时替换，Goal 完成或清除后结束该继承。

选择器数据只来自 Runtime 的脱敏 Server 摘要投影，Desktop 不读取配置或工具目录。不可用、已禁用、
无可披露 Tool 的 Server 不可选择；选择后、提交前发生刷新导致 Server 不再可用时，提交返回明确错误并
保留草稿和标签，不能静默换成其他 Server。

### 5.4 在指定 Server 内发现工具

模型使用一个固定工具：

```text
discover_mcp_tools(server, query?, detail)
```

它同时承载“搜索”和“列举”两种简单语义：

- 传入 `query`：只在指定 Server 的工具名称、说明和参数摘要内搜索；
- 不传 `query`：列举指定 Server 的工具；
- `detail="summary"`：返回工具名称和短说明，适合先选择工具；
- `detail="full"`：返回选中范围内的完整参数定义；不传 `query` 时表示请求该 Server 的全部工具定义。

发现结果作为普通 Tool Result 进入下一次模型调用。它不创建隐藏 UserMessage、不结束当前 Run、
不触发专属 continuation，也不维护“已加载工具”第二份 Session 状态。结果过大时允许分页、截断或
要求缩小查询；具体上限和返回结构由技术方案确定。

Runtime 不提供跨 Server 工具搜索。模型已经通过 Server 名称和业务说明完成第一层选择，工具搜索只
处理一个业务范围，减少重复名称和错误归属。

`discover_mcp_tools` 是只读的目录操作，本身不发起权限审批。它只返回当前 Run 中可披露的
Tool：Allow、Ask 和未匹配工具保持可发现，明确 Deny 的工具对 LLM 隐藏；即使模型猜中被隐藏
的名称，调用时仍必须被权限层拒绝。用户端权限诊断可继续显示被 Deny 的规则和工具身份。

### 5.5 调用实际工具

模型始终使用另一个固定工具：

```text
call_mcp_tool(server, tool, arguments)
```

其中 `server` 使用稳定配置键，`tool` 使用该 Server 返回的原始工具名，`arguments` 是目标工具参数。
Runtime 不从拼接后的公开名称反向猜测 Server 或工具身份。

调用前必须：

1. 确认 Server 当前启用且可用；
2. 确认工具存在于 Runtime 当前目录；
3. 使用当前工具 Schema 校验参数；
4. 将通用网关调用解析为实际 MCP Server 与工具身份；
5. 按实际身份执行现有 Plan/Build 能力限制、权限匹配、用户审批、Guardrail 和审计；
6. 获准后通过 `rmcp` 发起 `tools/call`。

发现行为不授予工具调用权限。模型即使猜中 Server、工具名和参数，也不能绕过上述校验和授权。
是否要求模型先取得 `detail="full"` 只影响模型调用质量，不成为安全边界，也不引入持久加载账本。

### 5.6 MCP 权限身份与审批

- MCP Tool 使用独立的类型化授权事实，但继续复用现有 Runtime Authorizer、Plan/Build、
  Ask/Auto、三级权限文件、一次性允许、审批和审计链路，不建立第二套权限系统；
- 权限匹配身份是稳定 Server 配置键与原始 Tool 名，不是通用 `call_mcp_tool` 网关名；
- 交互审批默认只生成当前精确 Server + Tool 的保守规则；整个 Server 或全部 MCP 的通配
  放行只能由用户手工编辑权限文件，审批界面不自动扩大范围；
- 完整 arguments 必须进入审批展示和审计，但首版不用通用参数匹配权限规则；持久允许
  某个 Tool 时，界面必须明确说明该范围适用于其后续所有参数；
- Plan 和 Build 向模型披露相同 MCP 能力，MCP 调用不因 Plan 被整类硬禁，但仍受当前变体
  的权限规则、Ask/Auto 和工作流指令约束；
- MCP Server 提供的只读、破坏性或其他 Tool 注解只能用于风险提示，不是可信授权事实，
  不能据此自动 Allow。

### 5.7 结果与错误

- MCP Tool Result 转换为现有 provider-neutral Tool Result，并继续普通 Agent Loop；
- 文本、结构化内容和系统已经支持的图片结果复用既有输出限制、持久化与产品展示；
- MCP 返回的外部文本、Schema 注解、链接和嵌入内容全部按不可信内容处理，不能成为 System 指令；
- 不支持或无法安全投影的内容必须形成明确诊断，不能静默丢失或伪装为成功；
- 连接失败、Server 不可用、未知工具、参数无效、权限拒绝、用户拒绝、调用超时、远端错误和结果
  超限需要保持可区分，具体稳定错误契约由技术方案确定；
- 取消 Run 时必须停止等待 MCP 调用；stdio 子进程和 HTTP 请求的取消、超时与关闭顺序由连接所有者
  负责，不由 Agent Core 直接管理。

### 5.8 手动刷新与 Command 队列

首版只提供：

```text
/mcp refresh
/mcp refresh <server>
```

- `/mcp refresh` 重新读取全局 `mcp.json` 并刷新所有启用 Server；
- `/mcp refresh <server>` 刷新一个明确 Server；
- Slash 文本只是 Desktop 的交互入口；它在提交前转换为结构化 MCP 刷新 Command，Runtime 不再从
  普通消息文本猜测控制意图；
- Command 与普通用户输入共用 Session 可靠队列。它入队后立即持久化并更新 Queue Snapshot，
  以可识别的控制指令行显示，用户可使用现有排序能力调整其后续位置；
- 同一 Session 的队列保持严格阻塞。存在活动 Run、待审批或其他队列阻塞时，Command 不得
  被消费；本版不支持立即执行、越过阻塞或在 Step 间隙将 Command 插入活动 Run；
- 队列解除阻塞后，队列消费者按顺序执行 Command；Command 执行期间占用当前队列消费位，
  但不创建 Agent Run；
- 执行结果实时入库并更新 Queue、Conversation 与 Session Snapshot。Desktop 将其投影为控制结果而非
  普通用户气泡；模型层以 user-role message 编码同一份可靠结果，不把原始 Slash 文本交给 LLM
  解释；
- Command 成功、部分成功、失败或 Server 未找到都形成明确终态结果，不包含 secret；执行
  失败不会永久卡住队列，结算后继续消费下一项；
- 刷新不计算新增、删除或变更差异，不监听 Server 自发目录变化，也不自动产生通知消息；
- 刷新含义是“刷新 MCP Server”，而不是永久限定为“刷新 Tools”。本版本实际只读取 Tools，未来启用
  Resources 或 Prompts 后可以沿用同一用户入口。

刷新使用“候选连接完整可用后再替换”的最小语义：候选连接必须完成 Transport 建立、MCP
initialize 和 Tools 目录获取，成功后才替换旧状态；某 Server 刷新失败时保留上一份可用连接和
目录并明确报错，用户在配置中删除或禁用 Server 时才关闭其旧连接。全局 `mcp.json` 无法解析时保留
整份旧状态；全局刷新中单个 Server 失败不阻止其他 Server 成功替换。连接成功但不提供 Tools
是有效结果，不属于刷新失败。

MCP 连接与配置是 Runtime 全局状态：一个 Session 消费刷新 Command 时，其他 Session 已开始的
MCP 调用继续使用原连接完成；受影响 Server 中尚未获准的待审批调用失效并返回可重新发现、
调用的明确 Tool Result；刷新完成后发起的新调用使用新连接和目录。精确并发和关闭顺序由
技术方案落实，但不得为此引入通用 Catalog revision 或分布式状态同步。

## 六、模块职责与契约影响

### 6.1 Assistant Runtime

- 持有 MCP Server 配置解释、启停事实、可用目录和 Runtime 级连接使用入口；
- 在 Run Tool Assembly 中装配固定 MCP 网关，并为模型投影可用 Server 目录；
- 把 `call_mcp_tool` 解析为实际工具身份后接入现有权限、审批、审计、取消和结果持久化；
- 将结构化 MCP 刷新 Command 纳入 Session 可靠队列、严格阻塞和统一消费，不为 Command
  创建 Agent Run；
- 持久化脱敏刷新结果，更新 Queue、Conversation 和 Session Snapshot，并向产品与模型分别
  形成控制结果和 user-role message 投影；
- 不让 Session、Conversation 或 Desktop 成为 MCP 连接与目录的第二权威所有者。

### 6.2 Runtime Host 与 MCP Adapter

- 使用 `rmcp` 建立 stdio 和 Streamable HTTP 连接，持有 Client 与 Transport 生命周期；
- 管理 stdio 子进程、HTTP 请求、连接关闭、超时和底层协议错误；
- 向 Runtime 提供工具列举与调用所需的窄能力，不把 `rmcp` 类型泄漏进应用协议或 Agent Core；
- 连接对象以 MCP Server 为边界，并保留完整 Client 生命周期，不能在首次 `tools/list` 后退化为
  只剩工具数组的“Tool Server”；
- 不因 Server 当前没有 Tools 而把有效 MCP 连接标记为失败。

具体 MCP Adapter 是否属于 Host 私有模块、现有 Runtime 资源装配还是需要新的物理 crate，必须由
技术方案先根据第二个真实调用方和依赖方向判断，不在功能设计中预设新增 crate。

### 6.3 Agent Core、Agent Tools 与模型层

- Agent Core 继续只处理普通模型工具调用、Tool Result 和 Agent Loop，不直接依赖 MCP 或 `rmcp`；
- 模型原生 ToolSet 只增加固定的 `discover_mcp_tools` 与 `call_mcp_tool`，不注册每个实际 MCP Tool；
- 网关工具定义和执行端口优先复用现有 Tool Registry、Dispatcher 与 resolved invocation；MCP
  调用提供独立类型化授权事实，不让通用网关身份代替实际 Server + Tool；
- 不为发现结果增加特殊模型消息类型，也不要求 OpenAI-compatible Adapter 支持私有动态 Tool Schema。

### 6.4 Assistant Protocol 与 Desktop

- 应用协议增加脱敏 MCP 管理快照与增删改、启停、导入、测试意图，以及 Server 摘要、输入选择标签、
  结构化 MCP 刷新 Command、队列项投影、执行终态与脱敏结果所必需的最小契约；
- Desktop 在现有设置弹窗中增加一级“MCP”页面；页面只使用 Runtime 管理协议，不直接读取或
  写入 Runtime Home 文件，不缓存连接或工具目录权威状态；
- Desktop 在现有 Slash Command 菜单中提供 `/mcp` Server 选择器和刷新入口；前者形成下一条输入的
  MCP 标签，后者转换为结构化 Command；队列阻塞时
  作为可见行展示并复用现有排序能力，消费后以控制结果而非普通用户气泡展示；
- Composer 的内容垂直顺序统一为“附件与引用 → Goal/Skill/MCP 标签 → 文本输入框”；标签之间保持
  Goal、Skill、MCP 的稳定顺序，每个标签都可以在提交前独立移除；
- Desktop 不读取 MCP 配置原文件、不连接 MCP Server、不缓存工具目录、不判断调用权限；用户在导入
  或表单中主动输入的未保存草稿只驻留当前设置页，Runtime 返回快照不回显 secret；
- MCP 工具审批和详情复用现有组件，但必须展示实际 Server 与工具名称；
- 页面与弹窗交互、状态、焦点、批量导入和危险操作确认按
  [`v0.23.0 界面交互设计指导`](界面交互设计指导.md) 落实。

## 七、关键取舍

### 7.1 先选 Server，再发现工具

MCP Server 已经表达业务范围。按 Server 分级发现比跨服务平铺搜索更符合模型判断过程，也减少相似
工具名互相竞争。代价是模型可能多一次发现调用，但工具归属明确且上下文可控。

### 7.2 合并搜索与全量列举

`discover_mcp_tools` 使用可选 `query` 和 `detail` 同时支持搜索、摘要和完整定义，不再拆成
`search_mcp_tools` 与 `load_mcp_tools`。它的参数结构保持简单，不使用复杂 `oneOf`，避免增加模型
选错网关的机会。

### 7.3 完整定义使用普通 Tool Result

完整 Tool Schema 本身就是一次发现调用的结果，现有 Agent Loop 会自然把它放入下一次模型请求。
因此不新增 discovery 结果专用 Hidden UserMessage、披露账本、特殊 continuation 或同批加载状态。
上下文压缩后若模型仍需要定义，可以再次发现。唯一例外是用户通过 `/mcp` 手动选择 Server：Runtime
在对应 Run 开始时通过现有 InternalContext 边界预加载有界工具定义；这不是 discovery 的隐藏
continuation，也不把动态定义永久写入 Conversation。

### 7.4 手动选择复用输入标签，不成为控制 Command

`/mcp` 与 `/skill` 一样先修改 Composer 草稿，再随下一条输入可靠提交；`/mcp refresh` 才是进入可靠
队列、无需 LLM 的控制 Command。两者共享 Slash 前缀但业务类型不同，Runtime 不从普通消息文本二次
猜测。手动选择保存的是 Server 身份和本次有界披露，不是长期连接选择或授权规则。

### 7.5 手动刷新代替自动通知

目录动态变化通常不是用户任务的主路径。首版使用 `/mcp refresh` 明确控制更新时间，不监听目录
变化、不打断 Run、不维护差异或 revision。代价是外部 Server 变化不会立即可见，但行为简单、可控、
易诊断。

### 7.6 Tools 首版与后续能力分开

Tools、Resources 和 Prompts 共用 Server 连接，但不共用发现与 LLM 投影。首版只实现 Tools；以后在
同一 Server 连接下并列增加 Resource/Prompt 能力和各自入口，不修改现有 Tool 网关，也不把 MCP
Prompt 自动变成 Skill。

### 7.7 stdio 与 Streamable HTTP 同版交付

本地 MCP 常用 stdio，远程和独立部署使用 Streamable HTTP。两种 Transport 在首版共同接入同一个
Server 连接边界，避免后续为 HTTP 重构配置、身份、生命周期、权限或调用链。旧 HTTP+SSE 不进入
兼容范围。

### 7.8 权限按实际 MCP Tool 分级匹配

`call_mcp_tool` 只是模型可见网关，不是授权对象。Runtime 在权限判断前将其解包为实际
Server + Tool，避免允许一次网关后意外放开所有 MCP。默认审批只持久化精确工具身份，更大
范围必须由用户手工表达。Deny 同时约束披露和执行，参数和 Server 自报注解不成为首版的
通用权限匹配或自动放行依据。

### 7.9 刷新是队列 Command，而非新 Run

MCP 刷新需要可见排队、稳定顺序、可靠入库和 Snapshot，因此不建立绕过队列的专用快捷执行路径。
队列消费者根据类型区分“普通输入创建 Run”和“Command 直接执行”；两者共用排序与阻塞语义。
Command 结果的业务身份与模型编码保持分离：产品展示控制结果，模型底层仍通过 user-role
message 获得同一份已持久化事实。轮内立即执行属于后续 Run 编排版本，首版不提前预留。

### 7.10 Server 注册表独立于主配置

逐 Server 连接记录使用独立 `mcp.json`，避免模型配置、认证引用和 Server 生命周期混在主
`config.toml` 中，也让用户可以直接导入 MCP 服务文档常见的 `mcpServers` 片段。设置页是主要维护
入口，JSON 文件是可移植的持久化与高级编辑边界；页面写配置与 Runtime 应用配置保持分离，后者仍
统一走可靠刷新 Command，不增加绕过队列的第二条连接更新路径。

## 八、验收标准

1. Runtime 能从用户私有配置解析并启用多个 MCP Server，单个无效配置或连接失败不会阻止其他
   Server 和非 MCP 功能使用。
2. 设置弹窗包含一级“MCP”页；页面可列举脱敏 Server、显示配置与 Runtime 状态，并完成新增、
   编辑、启停、删除、连接测试和一次导入多个 `mcpServers` 条目。
3. MCP Server 清单保存在独立全局 `mcp.json`；主 `config.toml` 不含逐 Server 配置。批量导入冲突需
   明确确认并原子写入，配置快照与错误不回显 secret。
4. 至少一个真实或官方兼容 stdio MCP Server 完成连接、工具列举和工具调用闭环。
5. 至少一个真实或官方兼容 Streamable HTTP MCP Server 完成同等闭环，业务层不出现第二套发现或
   调用路径。
6. 未选择 MCP 标签的 Run 首个模型请求只投影可用 Server 的名称和业务说明，未请求的全量工具名称
   和 Schema 不进入初始上下文。
7. `/mcp` 打开可用 Server 单选器；选择后形成下一条输入的可移除标签，本身不入队、不创建 Command
   或 Run，并且可以与 Skill、Goal、附件和引用组合。
8. 带 MCP 标签的输入原子冻结 Server 身份，在首次模型请求中披露明确 Deny 过滤后的工具定义；完整
   定义超限时退化为有界摘要并引导模型继续 discover，不能无限扩大上下文。
9. Composer 在现有会话和新会话草稿中都按“附件与引用 → Goal/Skill/MCP 标签 → 文本输入框”展示，
   Queue 和用户消息继续显示随输入冻结的 Skill/MCP 标签。
10. `discover_mcp_tools` 在指定 Server 内支持有查询摘要、无查询列举和 `detail="full"` 完整定义，
   不提供跨 Server 工具搜索；发现本身不审批，且不返回明确 Deny 的工具。
11. 大目录和大 Schema 具有确定上限与明确的继续查询方式，不因一次全量请求无限扩大上下文。
12. 发现结果通过普通 Tool Result 回到下一模型 Step，不产生隐藏用户消息、第二个 Runtime Run 或
   MCP 专属 continuation。
13. `call_mcp_tool` 使用明确的 Server、原始工具名和参数调用实际工具，并在发送前完成 Schema 校验。
14. MCP 实际工具身份进入现有权限、审批、Guardrail、审计和产品详情；允许通用网关不等于允许所有
   MCP 工具。
15. MCP 权限可精确匹配 Server + Tool；交互审批不自动扩大为整个 Server 或全部 MCP，
    arguments 完整展示和审计但不参与首版通用规则匹配，Server 自报注解不会自动放行。
16. Plan 和 Build 的 MCP 工具披露一致；Plan 不硬禁全部 MCP，但对应变体的权限规则、Ask/Auto
    和既有工作流约束仍生效。
17. MCP 文本、结构化内容、图片和错误按照既有 provider-neutral 工具结果能力完成有界转换、持久化
    与展示；不支持内容有明确诊断。
18. Run 取消、调用超时、Server 断开和 Runtime 关闭不会遗留失控的 HTTP 请求或 stdio 子进程。
19. `/mcp refresh`、`/mcp refresh <server>` 以结构化 Command 进入
    Session 队列，入队即持久化并出现在
    Queue Snapshot；队列阻塞时不消费，可调整后续顺序，但不越过阻塞或执行轮内插入。
20. MCP 刷新 Command 被消费时不创建 Agent Run；成功、部分成功和失败结果都实时入库、
    更新 Queue、Conversation 与 Session Snapshot，Desktop 显示控制结果，LLM 底层以 user-role message
    获得同一事实。
21. 刷新只在候选连接完成 Transport、initialize 和 Tools 目录后替换旧状态；失败时保留上一份
    可用状态，明确删除或禁用 Server 时关闭旧连接，单 Server 失败不阻止其他 Server 替换。
22. 全局刷新不中断其他 Session 已开始的 MCP 调用；受影响 Server 中尚未获准的待审批调用
    失效，刷新后的新调用使用新连接和目录。
23. 首版不建立目录自动通知、Catalog revision、披露账本或 Resources/Prompts 的空壳业务状态。
24. 连接成功但不支持 Tools 的 Server 保持“已连接但无 Tools”的可诊断状态，为后续能力保留连接
    兼容性。
25. 配置 secret、HTTP 认证材料和 stdio 敏感环境不进入模型上下文、应用协议读响应、普通日志、错误、
    调试事件或测试快照。
26. 连接测试不持久化未保存草稿、不替换活动 Registry、不授予权限，结束后关闭临时候选连接与
    stdio 子进程。
27. 现有非 MCP 工具、Skills、普通会话恢复、上下文压缩和多 Session 并发回归通过。

## 九、风险、兼容性与待确认项

### 9.1 风险与技术方案必答项

- `rmcp` 的目标协议版本、具体 feature 和 stdio/Streamable HTTP API 需要以实际依赖解析与兼容测试
  为准，不能只依据文档示例；
- MCP Tool Schema 可能包含复杂 JSON Schema、极大描述或恶意文本，技术方案必须明确支持边界、
  编码、大小限制和校验失败语义；
- Streamable HTTP 的 endpoint、redirect、TLS、静态认证 header 和 secret 生命周期必须复用现有
  Runtime 私有配置与脱敏原则；交互式 OAuth 明确不在本版本；
- stdio 命令以当前用户权限启动，必须限制环境继承、明确工作目录、输出上限、取消和进程树关闭；
- `/mcp refresh` 与并发 Run 的最小所有权方案必须说明替换时机和失败恢复，但不得默认引入 revision、
  双目录账本或复杂活动 Run 迁移；
- 现有 Input 接受、队列和 Run 创建强绑定，技术方案必须核查可靠队列、持久化、Snapshot 和
  消费器的最小拆分，不得为 Command 伪造 Agent Run；
- MCP 独立授权事实会影响权限文件、规则匹配、审批投影和兼容读取；技术方案必须基于现有
  typed facts 和 schema version 核查给出可回归的增量方案；
- MCP 工具返回的图片、链接、嵌入资源和结构化内容必须先核查现有 Tool Result 能力，不为来源差异
  复制一套附件或消息生命周期；
- MCP Server 与 Tool 名称可能重复、包含 Provider 不友好字符或在刷新后变化。内部调用始终使用
  Server 配置键与原始工具名；面向模型和 UI 的显示/编码规则由技术方案验证。
- 独立 `mcp.json` 需要兼容常见生态片段，同时不能静默接受拼写错误；技术方案必须区分可规范化别名、
  可保留但不生效的未知字段与必须拒绝的冲突字段，并保证批量导入原子写入。
- 管理页不能读取或回显已有 secret。技术方案必须给出“保持、替换、删除”三态编辑以及并发窗口
  防覆盖机制，不能用脱敏占位符覆盖真实配置。

### 9.2 兼容性

- 当前项目尚未发布 MCP 配置或协议契约，不为输入文档中的 `search/load/call` 候选方案保留别名、
  迁移或双轨；本版本直接以最终的 `discover/call` 收口；
- 首版全局 Server 配置使用独立 `mcp.json` 的 `mcpServers` map；未来增加项目级 `.mcp.json` 时只新增
  配置来源和优先级，不改变单个 Server 的字段语义。主 `config.toml` 不再承担逐 Server 配置兼容；
- 后续增加 Resources 时，在既有 Server 连接下新增独立的发现与读取入口；增加 Prompts 时新增独立
  的发现与取得入口。两者不修改 `discover_mcp_tools` 或 `call_mcp_tool`；
- `/mcp refresh` 始终表示刷新 Server 的已启用能力。未来能力扩展不要求用户改用新命令；
- MCP Prompt 默认只能作为一次性外部模板进入对话；是否提供用户显式“保存为 Skill”属于后续产品
  功能，不能在底层自动互转；
- Server 配置、Transport、认证、连接诊断和稳定配置键属于跨能力共享事实，不能复制成 Tool、
  Resource、Prompt 三套配置。

### 9.3 待确认项

本文没有阻塞功能设计确认的开放产品问题。以下实现问题统一进入技术方案：

1. `rmcp` 精确版本、协议兼容范围和 Cargo feature；
2. 全局 `mcp.json` 规范化、原子写入、并发编辑、静态 HTTP 认证材料与 stdio 环境白名单；
3. Server 目录隐藏上下文的精确模型投影形式；
4. `discover_mcp_tools` 的分页、排序、大小上限和完整 JSON 返回结构；
5. JSON Schema 支持范围、参数错误格式和 MCP 内容转换矩阵；
6. 连接 owner、并发刷新、失败时保留状态、超时、取消和受控关闭；
7. MCP 授权 facts、精确与手工通配 matcher、权限文件兼容、审批与审计 DTO 的最小调整；
8. 统一队列中结构化 Command 的存储、排序、阻塞、消费、终态、恢复与 Snapshot 投影；
9. Command 可靠结果向 Desktop 控制记录和 LLM user-role message 的双投影形式；
10. 应用协议、MCP 管理页、批量导入、连接测试、Slash Command 参数解析和 Desktop 反馈的最小改动；
11. 是否需要新增物理模块或 crate；只有现有边界无法承载且存在真实复用/替换需求时才允许新增。

## 十一、版本内追加修正

2026-09-03 用户反馈所有会话的上下文边栏技能区为空，期望展示已有的三个技能。本版将技能区从
“仅展示已激活项”修正为“展示会话可用技能，并标识已激活状态”：

- 只消费当前 Session 已冻结的技能目录与激活快照，不重新扫描全局设置，不修改会话数据；
- 未加载项显示“可用”，实际激活项仍显示“用户激活”或“智能体激活”，同名只显示一次；
- 已激活项保持原顺序并优先展示；旧会话或目录不可用时保留对应提示，不用当前全局技能伪造历史。

该显示修正替代 v0.19.0 交互指导中“技能分区只列出已激活项”的约定，不改变技能加载、权限、
持久化或模型注入机制，也不提前进入 M7。
