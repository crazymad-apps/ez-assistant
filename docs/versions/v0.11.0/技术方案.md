# v0.11.0 技术方案：Workspace、附件与 Session 执行环境

## 一、方案信息

- 版本：`v0.11.0`
- 状态：已确认
- 关联功能设计：[`功能设计`](功能设计.md)
- 影响范围：`assistant-runtime`、`assistant-protocol`、`apps/runtime-host`、
  `agent-types`、`agent-provider-openai-compatible`、`agent-tools`、`agent-tools-local`
- 核查依据：2026-08-10 实际源码、现有 Cargo 依赖图、`v0.10.0` 持久化格式与
  Runtime/Host/Protocol/Tool 模块约束

本文只承接实现级内容：跨层契约、数据格式、目录布局、上传提交、故障恢复、
Session 环境编译、Provider 编码和验证方法。产品语义、用户路径与非目标以功能设计
为准，不在本文重复定义。

## 二、现状核查

### 2.1 Runtime 与持久化

当前 Runtime 已具备以下可直接扩展的边界：

- `AssistantRuntime` 持有 Session Registry，`SessionController` 持有冻结的
  `SystemPromptSnapshot`、model key 和持久化会话工作集。
- `RuntimeStore` 按业务原子操作表达存储需求，没有泄漏 SQL、文件 offset 或路径。
- Host 的 `LocalRuntimeStore` 通过有界队列把 SQLite 和 Conversation JSONL 交给单一
  命名阻塞线程，已具备 staged append、generation 切换和 pending tool exchange 恢复。
- Conversation 仍是每行一条 `ConversationMessage` 的 JSONL；SQLite 只保存结构化关系和
  短生命期提交事实。

因此本版本不引入新 Repository crate、ORM、Message/Part 表或另一套会话正文。
Workspace、Session 绑定和附件元数据扩展现有 SQLite Store，File References Part 继续随
User Message 进入现有 JSONL。

### 2.2 User Part 与 Provider 编码

`agent_types::UserPart` 当前只有：

- `Text(TextPart)`：用户真实输入；
- `Injected(TextPart)`：已有 Core 内部类型，当前仅由上下文压缩流程在临时请求中
  使用。Runtime 不会为 Workspace 或附件生成这类 Part。

OpenAI-compatible Adapter 当前把 `Text` 与 `Injected` 都编码为 user text content；多 Part
时使用保序的 text part 数组。新增 File References 后延续这个结构边界，不在
Runtime 中把附件拼入用户正文。

### 2.3 工具装配限制

当前 `AssistantRuntime` 全局持有单一 `ToolSetSnapshot` 和
`default_authorizer`。这只适合无路径上下文的 `echo_text`：

- `FsReadTool`、`FsWriteTool`、`ShellExecTool` 等标准工具在构造时已冻结
  `SessionPathResolver`；
- 绑定不同 Workspace 的 Session 必须有不同默认工作目录；
- 不能用一个全局 resolver 支持多 Session，也不能在执行期修改已冻结的工具
  定义。

本版本必须先把工具装配调整为按 Run 编译。这不是提前实现 `v0.12.0` 的权限
体系，而是 Session 环境进入真实文件工具的必要构造边界。

### 2.4 Host 传输约束

Host 当前的 Unix Domain Socket 和 length-prefixed JSON frame 是 `v0.8.0`
用于验证双进程边界的阶段性实现。为避免将来如果启用远程 Runtime 时再长期
维护 UDS 与 HTTP 两套连接、错误、事件和上传实现，本版本趁正式客户端尚未接入时
先统一传输口径。

`v0.11.0` 直接统一为 HTTP 通信口径：

- 本地 Runtime Host 只绑定 `127.0.0.1` 动态端口，使用进程级 Bearer Token；
- 远程 Runtime 是可选能力且默认关闭；后续如显式启用，必须使用 HTTPS 和远程身份，
  并复用同一组路由、DTO、上传语义和事件模型；
- 普通命令保持有界 JSON，附件通过独立 HTTP 路由流式传输字节，不进入 JSON、
  Base64 或本地源路径。

本版本不实现远程部署、多用户认证、续传或分块会话，但开始实现的本地 API 本身
应保持可被后续可选远程客户端复用的边界。项目尚未对外稳定发布，不为旧 UDS wire 保留
并行兼容层。

## 三、目标架构

```text
桌面 Runtime Client / 验证客户端 / 可选远程客户端
    │
    │ 同一组 HTTP API：Command / SSE / Streaming Upload
    ▼
apps/runtime-host
├── HTTP Router / Auth / Command Dispatch
├── SSE Event Projection / Streaming Upload
├── HostSessionEnvironmentFactory
│   └── Runtime Home 布局 + 冻结 SystemPromptSnapshot
├── HostRunToolFactory
│   ├── 安全默认 echo 装配
│   └── 显式验证模式：本地文件 + Shell + Authorizer
└── storage::LocalRuntimeStore
    ├── SQLite 结构化关系
    ├── Conversation JSONL
    ├── content-addressed blobs
    └── Session 附件可读视图
            │
            ▼
assistant-runtime
├── Workspace Registry
├── Session / Workspace 冻结关系
├── Attachment 业务操作
├── UserMessage Parts 构造
└── 按 Run 编译 Model + Tools + Authorizer
            │
            ▼
       agent-sdk / agent-core
            │
            ▼
 OpenAI-compatible Provider Adapter
```

权威边界保持不变：

- Runtime 持有 Workspace、Session 绑定、Attachment 业务语义和消息组装；
- Host 实现路径、SQLite、Hash、文件复制、可读视图和本地工具适配；
- Core 只消费一次 Run 已冻结的 System Prompt、Conversation、ToolSet 和 Authorizer；
- Protocol 只暴露业务 ID、意图和脱敏投影，不暴露 Blob 路径、SQLite 实体或
  文件句柄。

HTTP 只替换进程通信实现，不改变上述业务所有权。Host 可以持有连接、请求体流、
本地访问 Token 和 SSE 订阅，但不因此保存 Session/Run 的第二份状态。

## 四、领域类型与构造边界

### 4.1 标识与投影

`assistant-protocol` 新增两个不透明 ID：

```text
WorkspaceId
AttachmentId
```

它们延续现有 ID 的非空、有界、无顺序语义规则。不把路径、Hash、Session ID 或时间
编码进 ID。

Protocol 投影包含：

- `WorkspaceSummary`：Workspace ID、用户工作目录、Workspace 私有目录、活动/已移除
  状态和时间投影；
- `AttachmentSummary`：Attachment ID、Session ID、原始名、大小、Agent 可读路径、
  可用状态和上传时间；
- `SessionSummary.workspace_id: Option<WorkspaceId>`：只投影冻结绑定，不复制
  Workspace 全部信息。

`WorkspaceSummary` 中的 Workspace 私有目录有意保持客户端可见，使用户能够直接定位并
检查 Agent 在其中保存的内容。连接远程 Runtime 时，该值表示远程 Host 上的可查看诊断信息，
客户端不根据该路径访问自己的本地文件系统。

`AttachmentSummary` 中的 `agent_readable_path` 是已确认的模型/工具可读引用，不是
Blob 物理路径。客户端不得根据它推导数据库或去重布局。

### 4.2 Runtime Store DTO

`RuntimeStore` 扩展业务操作，而不暴露通用 CRUD：

```text
load_runtime() -> RecoveredRuntime(workspaces + sessions + ...)
register_workspace(command) -> StoredWorkspace
remove_workspace(command) -> StoredWorkspace

create_session(NewStoredSession + SessionExecutionEnvironment)

upload_attachment(NewAttachmentUpload) -> StoredAttachment
```

Store 负责上传提交与启动恢复，Runtime Registry 负责 Attachment 查询和列表，避免为了
只读投影把生产请求机械转发到阻塞存储 worker。M3 的批量解析由 Runtime 在 Registry 中按
请求 ID 顺序完成，并整体确认它们属于目标 Session 且可用。Runtime 不接受客户端直接提交
原始名或 Agent 路径，避免伪造跨 Session 引用。

### 4.3 Session 执行环境

新增 Runtime 内部不可变值 `SessionExecutionEnvironment`，包含：

Workspace 私有目录和 Session 私有目录统一归类为 **Agent 私有目录**，再按作用域区分。
Session 附件目录是静态参考文件空间，不纳入 Agent 私有目录口径。
字段名保留用途名称，避免把持久附件和可清理临时文件混为同一种资源。

```text
workspace_id: Option<WorkspaceId>
working_directory: absolute UTF-8 path
workspace_private_directory: Option<absolute UTF-8 path>
session_attachment_directory: absolute UTF-8 path
session_private_directory: absolute UTF-8 path
```

绑定 Workspace 时，`working_directory` 为用户工作目录；未绑定时为 Session
私有目录。Session 附件目录和 Session 私有目录始终存在，因此普通会话也能上传附件
和执行临时文件操作。

Host 提供 `SessionEnvironmentFactory` 构造边界：

1. 根据 Runtime Home、Session ID 和可选 Workspace 投影一次生成稳定路径；
2. 把基础 System Prompt 与确定性的目录 Part 组装为 `SystemPromptSnapshot`；
3. 同时返回 `SessionExecutionEnvironment`，交由 Store 持久化。

这是现有 `SystemPromptFactory` 的有语义扩展，不在 Runtime 中硬编码 Runtime Home，也不
让 Host 在每次 Run 重新生成路径。启动恢复时直接使用 Store 中的环境事实，
不重新调用工厂改写旧 Session。

### 4.4 按 Run 编译工具与 Authorizer

用 `RunToolFactory` 取代 Runtime 的全局 `ToolSetSnapshot + default_authorizer`
构造参数：

```text
RunToolFactory::compile(SessionExecutionEnvironment)
    -> RunToolBundle {
         tools: ToolSetSnapshot,
         authorizer: Arc<dyn ToolAuthorizer>
       }
```

`compile_run_agent` 在 Run 开始前同时冻结当前模型、Session System Prompt、上下文
配置、工具定义和 Authorizer。Tool Bundle 在单次 Run 内不变，不保存到 Protocol
或 Conversation。

该边界使 `v0.12.0` 可以根据单次 Run 的 Plan/Build、Ask/Auto 和规则快照同时
生成工具集与 Authorizer，不需再次改造 Runtime 主流程。

## 五、Workspace 路径与生命周期

### 5.1 登记与身份

Workspace 登记请求只接受本机绝对 UTF-8 目录路径。Host Store 在阻塞 I/O 边界：

1. 读取目录元数据，确认是可访问目录；
2. 通过 `canonicalize` 解析当前真实绝对路径；
3. 以 canonical path 作为 Workspace 唯一身份，保存该路径而不保存未展开的
   `~`、相对路径或符号链接别名；
4. 为新 Workspace 创建 `~/.ez-assistant/data/workspaces/<workspace-id>/agent/`；
5. 写入 SQLite 后才向 Runtime 报告登记成功。

同一 canonical path 已经活动时幂等返回原 Workspace；已假删时原地恢复原
Workspace ID 和私有目录。如果目录当前不可用，不根据字符串猜测旧 Workspace，
而是返回 `WorkspaceUnavailable`。

### 5.2 绑定与假删

- `CreateSessionRequest` 增加可选 `workspace_id`。
- Runtime 在 Session ID 分配后、任何文件或数据库写入前确认 Workspace
  存在、未移除且用户目录当前可用。
- Session 绑定与创建 Session 在同一 SQLite 事务中提交；没有换绑命令。
- 假删 Workspace 只更新 lifecycle 和时间，不删除用户目录、Agent 私有目录、
  Session 绑定或已冻结的 System Prompt。
- 新 Session 不能绑定已假删 Workspace；已绑定 Session 的运行和归档恢复不受
  假删状态影响。

用户目录在日后丢失时，Runtime 保留登记和冻结环境。需要该目录的新 Session
创建或 Run 准备返回明确错误；附件查询和归档 Session 的纯读取投影仍可用。

### 5.3 SystemPromptSnapshot 确定性格式

新 Session 在基础 System Prompt 之后追加一个独立目录 Part。绑定 Workspace 的格式为：

```xml
<runtime_directories>
  <working_directory>/absolute/user/workspace</working_directory>
  <workspace_private_directory>/absolute/runtime/workspaces/ws_.../agent</workspace_private_directory>
  <session_attachment_directory>/absolute/runtime/sessions/session_.../attachments</session_attachment_directory>
  <session_private_directory>/absolute/runtime/sessions/session_.../private</session_private_directory>
</runtime_directories>
```

未绑定 Workspace 时不输出 `workspace_private_directory`，`working_directory` 指向
Session 私有目录。规则如下：

- 标签和字段顺序固定；
- 路径按 XML text 规则转义，不使用 Debug 格式；
- 不列举任何目录内容，不读取 `AGENTS.md`，不添加动态时间或可用性文字；
- 完整渲染结果只在 Session 创建时生成一次，随 `SystemPromptSnapshot` 持久化。

## 六、附件数据格式与文件布局

### 6.1 Runtime Home 布局

```text
~/.ez-assistant/
└── data/
    ├── runtime.sqlite3
    ├── blobs/
    │   └── sha256/
    │       └── <first-two-hex>/<64-lowercase-hex>
    ├── staging/
    │   └── uploads/<operation-id>.part
    ├── workspaces/
    │   └── <workspace-id>/agent/
    └── sessions/
        └── <session-id>/
            ├── conversation.<generation>.jsonl
            ├── attachments/
            │   └── <attachment-id>/<safe-display-name> -> content blob
            └── private/
```

`blob_hash` 是 Blob 身份而不是纯内容摘要。它使用 SHA-256 计算以下确定性字节序列的
小写十六进制值：

```text
"ez-assistant-attachment-v1\0"
+ u64_be(original_name_utf8_byte_length)
+ original_name_utf8_bytes
+ original_file_bytes
```

域分隔符和文件名长度帧避免与普通内容摘要混用或产生拼接边界歧义。文件名按收到的 UTF-8
字节计算，文件正文不做换行、编码或文件类型归一化。因此只有原始文件名和字节都相同时才复用
物理 Blob；同内容不同名会产生不同 Blob。数据库另存 byte size 用于完整性核对。

`safe-display-name` 仅用于保留可读扩展名和帮助工具判断格式：

- 原始名始终单独存储，不会被 safe name 覆盖；
- 只取源文件的 basename，拒绝空名、`.`、`..`、非 UTF-8 和嵌入的路径分隔符；
- 路径组件中的控制字符替换为 `_`，文件名过长时保留扩展名并确定性截断；
- Attachment ID 是上层目录，因此同名文件不会冲突。

### 6.2 Blob 与 Session 视图

Blob 是物理正文，Session attachment 是业务附件与 Agent 可读视图：

- 同名且同内容只保留一份 Blob，同内容不同名不复用；
- 不同 Session 对同名同内容文件使用不同 Attachment ID 和可读路径，但复用同一 Blob；
- 同一 Session 以 Blob Hash 唯一，重复上传同名同内容文件返回首次 Attachment，不新建视图；
  首次上传保存的原始名称和稳定路径保持不变。

macOS/Unix 的首个实现使用 **相对符号链接** 建立 Session 视图。这比硬链接更明确
表达“视图指向内容库”，并且移动整个 Runtime Home 的物理目录时链接内部相对关系
仍可保持。可读路径本身是持久化的绝对字符串，不能因 Runtime Home 被换到新根就
静默改写；整体 Runtime Home 迁移必须由后续迁移能力保留旧路径别名，不在本版本
自动完成。

Windows 不是当前 Host 平台；未来支持时必须提供同样稳定的普通文件可读视图或平台
链接实现，不得把 Unix 符号链接暴露为 Protocol 契约。

### 6.3 SQLite 表

在现有 schema 上只增加新表，不修改 Conversation JSONL 的权威形式：

```sql
CREATE TABLE workspaces (
    workspace_id       TEXT PRIMARY KEY,
    user_directory     TEXT NOT NULL UNIQUE,
    agent_directory    TEXT NOT NULL UNIQUE,
    lifecycle          TEXT NOT NULL CHECK (lifecycle IN ('active', 'removed')),
    created_at_ms      INTEGER NOT NULL,
    updated_at_ms      INTEGER NOT NULL,
    removed_at_ms      INTEGER
);

CREATE TABLE session_resources (
    session_id             TEXT PRIMARY KEY REFERENCES sessions(session_id) ON DELETE CASCADE,
    workspace_id           TEXT REFERENCES workspaces(workspace_id),
    working_directory      TEXT NOT NULL,
    attachment_directory   TEXT NOT NULL UNIQUE,
    private_directory      TEXT NOT NULL UNIQUE,
    created_at_ms          INTEGER NOT NULL
);

CREATE TABLE attachment_blobs (
    blob_hash          TEXT PRIMARY KEY,
    size_bytes         INTEGER NOT NULL CHECK (size_bytes >= 0),
    relative_path      TEXT NOT NULL UNIQUE,
    created_at_ms      INTEGER NOT NULL
);

CREATE TABLE attachments (
    attachment_id          TEXT PRIMARY KEY,
    session_id             TEXT NOT NULL REFERENCES sessions(session_id) ON DELETE CASCADE,
    blob_hash              TEXT NOT NULL REFERENCES attachment_blobs(blob_hash),
    original_name          TEXT NOT NULL,
    agent_readable_path    TEXT NOT NULL UNIQUE,
    state                  TEXT NOT NULL CHECK (state IN ('ready', 'unavailable')),
    created_at_ms          INTEGER NOT NULL,
    UNIQUE (session_id, blob_hash)
);
```

补充约束：

- `session_resources.workspace_id` 同时表达 Session 的唯一 Workspace 绑定；
  主键保证一个 Session 最多一行，不提供 UPDATE 换绑操作。
- Workspace 私有目录从 `workspaces.agent_directory` 取得，不在每个 Session
  重复存储。
- `attachment_blobs.relative_path` 只允许由 Host 生成的 Runtime Home 内相对路径；
  Protocol 和 Runtime 不能接收客户端传入的该值。
- 消息引用只存在 JSONL File References Part，不增加 message-attachment 表，
  不缓存消息级引用次数。
- Blob 的 Session 引用数通过 `attachments` 按 `blob_hash` 统计不同
  `session_id` 得到，本版本不保存可失真的 `reference_count`。
- 本版本没有永久删除 Session 或 Attachment 业务命令，因此不执行 Blob 回收。

为便于 Session 附件列表和 Workspace 绑定查询，增加
`attachments(session_id, created_at_ms, attachment_id)` 和
`session_resources(workspace_id, session_id)` 索引。

## 七、上传协议与一致性

### 7.1 HTTP API

Runtime Host 对本地和后续可选远程客户端使用同一组路由：

```text
POST /commands
GET  /events
POST /sessions/{session_id}/attachments
GET  /capabilities
GET  /health
```

- `/commands` 使用有界 JSON 请求体，承载 `RuntimeCommand` 并返回
  `RuntimeCommandResult`；JSON body 继续使用 `1 MiB` 上限；
- `/events` 使用 SSE 投影 `RuntimeEvent`，不增加持久 sequence 或重放游标；订阅者落后于
  有界 Runtime 广播时，Host 先发送私有 `stream_gap` 控制事件并关闭当前流，客户端重连后
  查询 Conversation、Run、Session 等权威快照再继续消费增量；
- `/sessions/{session_id}/attachments` 使用 `multipart/form-data`，只接受一个
  `file` part；
- `/capabilities` 返回协议版本、单文件上限和当前 Host 能力，客户端不从部署位置
  推测能力；
- `/health` 只表达当前 Host 实例可达与是否已完成 Runtime 恢复。

HTTP 状态码表达传输级结果，业务失败仍使用稳定 `RuntimeErrorCode` 和脱敏消息。
`assistant-protocol` 定义命令、结果、事件和附件投影，不定义 HTTP client、流式字节
或本地文件路径。

模型调用观察沿同一 SSE 通道投影 attempt 开始、建流前失败、重试等待和建流成功；事件只
包含稳定失败分类，不包含 Provider 原始文本。最终模型失败使用专用错误码，并把失败阶段、
attempt/retry 次数和是否已有可见输出压缩为安全消息，复用 Run 现有错误列持久化，不增加 schema。

### 7.2 上传身份与内容去重

上传的 Session ID 来自路由，原始文件名来自 multipart `file` part。Host 完整接收文件并
按 6.1 计算 Blob Hash 后，以 `(session_id, blob_hash)` 判定业务附件是否已存在：命中时返回
首次 Attachment。不同 Session 对同名同内容文件仍建立各自的 Attachment，底层复用 Blob；
同内容不同名文件的 Blob Hash 不同，因此不复用物理正文。

Host 在读取大请求体前只向 Runtime 检查 Session 准入；Hash 尚未形成，因此重复上传仍需完整
传输。完成 staging 后 Runtime 再次复核 Session lifecycle 和业务约束，由 Store 按 Blob Hash 去重
并提交 Attachment 事实。Host 只持有请求体与短期 staging 状态，不持有 Attachment 业务状态机。

`v0.11.0` 不增加上传进度事件和业务取消命令。客户端可以根据已发送字节展示本地
进度；响应丢失时可以使用同一原始文件名重新上传，Blob Hash 会收敛到首次 Attachment。上传成功后消息提交失败
不回滚 Attachment。

### 7.3 大小与流式写入

- 每个文件固定上限为 `1 GiB`；该上限属于 Host 文件入口资源约束，不进入
  model 配置，并通过 `/capabilities` 向客户端显式公布。
- Host 以有界缓冲区流式读取 multipart 文件 part，同时写入 staging file、统计 size 和
  按 6.1 计算 Blob Hash，不把整个文件读入内存。
- 客户端本地读取失败属于客户端错误；Host 不接收也不解析客户端源路径。
- staging 文件 I/O 使用异步文件写入与有界并发，不让慢上传长时独占
  SQLite/Conversation 的单一存储线程。

staging 完成后才把一个小型 finalize 命令发送给存储 worker；该命令独占 SQLite
connection 并完成 Blob、视图和元数据提交。

### 7.4 提交顺序

上传成功点是“Blob 和 Agent 可读视图已同步，附件行已提交”。顺序为：

```text
1. 检查 Session 是否允许上传
2. 流式接收 HTTP 文件 part 并写入 create_new staging file，计算 size + Blob Hash
3. flush + sync_all staging file
4. finalize 命令进入单一存储 worker 后检查 `(session_id, blob_hash)`；已命中时
   删除本次 staging 并返回已有 Attachment
5. Blob 已存在：验证 size 与 Hash 后删除 staging
   Blob 不存在：atomic rename staging -> content-addressed path，同步父目录
6. 创建 attachment 目录与临时相对符号链接，atomic rename 为稳定视图，同步目录
7. SQLite 事务插入/复用 attachment_blobs，插入 attachments(state=ready)
8. commit 后返回 AttachmentSummary
```

此顺序确保 SQLite 不会先指向一个从未完整落盘的文件。中断语义：

- 第 7 步前崩溃最多留下 staging、未引用 Blob 或未引用视图，不存在已报告
  成功的 Attachment；
- SQLite commit 后、回复前崩溃时 Attachment 已是成功事实，同名同内容重传返回它；
- SQLite 写入失败时尝试删除本次新建视图，删除失败不能改写主错误；
- 未引用文件属于后续清理范围，`v0.11.0` 不增加定时回收。

启动恢复和附件解析会确认 Blob 是普通文件、size 一致、视图是指向期望 Blob
的符号链接。视图缺失但 Blob 完整时可以原路径重建；Blob 缺失、size 不符、
视图路径被其他类型占用或链接指向异常时，不覆盖未知文件，把 Attachment 标记为
`unavailable` 并返回脱敏错误。Hash 在新 Blob 写入和复用旧 Blob 时验证；不在每次
Run 开始前无界重读全部历史大文件。

### 7.5 本地发现与访问边界

Host 继续使用 Runtime Home `run/runtime.lock` 作为单实例内核锁。Runtime Store 打开与
结构化恢复完成后，Host 绑定 `127.0.0.1:0`，由操作系统分配动态端口，不监听
`0.0.0.0` 或局域网地址。Host 为本次进程生成高强度随机 Bearer Token，并将以下
发现信息原子写入 Runtime Home `run/runtime.json`：

```json
{
  "address": "http://127.0.0.1:43127",
  "instance_id": "runtime-instance-id",
  "access_token": "process-scoped-secret",
  "pid": 12345
}
```

- 发现文件是本机敏感数据，初始化时按当前用户私有权限创建，Token 不进入日志、
  错误或 Runtime 事件；
- Tauri Rust 启动层读取发现文件，将当前 `base_url`、`instance_id` 和 Token 作为
  启动配置注入受信任 WebView。WebView 内的 HTTP Runtime Client 可直接调用 Command、
  Upload 和事件流，不要求每个 Runtime 请求再经 Tauri command 代理；
- WebView 只在内存中持有 Token，不写入 `localStorage`、URL、普通日志或前端事件；
  桌面应用必须配套 CSP、受控导航和本地资源边界，因为 WebView XSS 会同时意味着 Token 泄露；
- 所有路由包括 `/health` 与 `/capabilities` 均要求 Bearer Token。Host 校验本地
  authority；无 `Origin` 的本地原生/验证客户端可通过，携带 `Origin` 时只允许精确登记的
  Tauri WebView Origin，处理必要的 CORS preflight，拒绝未知 Origin 与通配符 CORS；
- 退出时只有在发现文件仍属于当前 `instance_id` 时才删除，避免旧进程清理新实例；
- 远程监听默认关闭；后续版本如显式启用远程部署，必须用 HTTPS 终结 TLS 并
  替换认证提供方，不改变 Runtime Client 的路由与业务 DTO。

本地 Token 是防止同机浏览器网页误调 Runtime 的应用层门槛，不是对同用户恶意进程的
强安全隔离。这一边界必须在文档与 UI 中保持真实。

`serve` 不再接受 `--socket`，开发验证也从 `run/runtime.json` 发现端口，避免产品与
测试形成两种启动口径。v0.11.0 不提供任意 `--listen` 或公网绑定参数；远程部署必须在
后续版本同时完成 TLS、身份与运维边界，不能通过开放当前本地参数偷渡。

“统一客户端”指共用同一 `HttpRuntimeClient` 与业务 API，不表示本地发现和远程登录
必须相同：

```text
Local  target = runtime.json 发现的 base URL + process token
Remote target (可选) = 用户/管理员显式配置的 HTTPS base URL + remote credential provider
```

桌面客户端可把 target 注入 WebView 内的同一 `HttpRuntimeClient`，上层 UI 不分叉业务命令。
纯浏览器部署在显式配置后可访问远程 HTTPS Runtime。纯浏览器直连本地 Runtime 也
保留为后续可选能力，默认关闭；启用时需要显式 Origin 白名单、面向浏览器的授权/启动
交付和对应审计，不要求必须增加 companion bridge，也不允许通配符 CORS 或在 URL 中
传递 Token。

WebView 携带 Authorization header 订阅事件时使用可中止的 `fetch` streaming SSE 客户端；
不使用无法设置自定义 Authorization header 的原生 `EventSource`，也不把 Token 放入
SSE query string。

## 八、User Message 与模型编码

### 8.1 规范类型

`agent-types` 新增：

```text
UserPart::FileReferences(FileReferencesPart)

FileReferencesPart {
  id: PartId,
  files: Vec<FileReference>
}

FileReference {
  original_name: String,
  readable_path: String
}
```

`AttachmentId` 是 Protocol/Runtime 中选择和校验 Session 附件的业务身份。Runtime
解析成已冻结的原始名和可读路径后，不再把应用层 ID 复制到
`agent-types`，避免底层规范对话反向依赖 `assistant-protocol`。该 Part 不包含
Base64、文件正文、Hash、Blob 路径或解析结果。未来 UI 投影如果需要
Attachment ID，由 Runtime 使用唯一 `agent_readable_path` 关联附件投影，不改变模型层类型。

`SubmitInputRequest` 和 `ReenterFromUserMessageRequest` 增加有序
`attachment_ids`，缺省为空以保持旧客户端 JSON 的反序列化兼容。Runtime 依次解析附件，
并且只由 Store 结果构造 Part：

```text
UserMessage.parts = [
  Text(...),
  FileReferences(...),   // attachment_ids 非空时有且仅有一个
]
```

用户文本仍按现有规则必须非空白。File References 顺序等于请求 ID 顺序；
重复 Attachment ID 作为无效请求拒绝，不静默改写用户选择。

现有 `UserPart::Injected` 保留作为 Core 已有的临时压缩请求类型；本版本不新增
产品级 Internal Injection Part，也不把 Workspace 文件列表或附件信息放进 `Injected`。

### 8.2 Conversation 持久化

File References Part 直接随 User Message 进入当前 JSONL，例如：

```json
{"role":"user","turn":{"id":"message_...","parts":[{"type":"text","data":{"id":"part_...","text":"分析这个文件"}},{"type":"file_references","data":{"id":"part_...","files":[{"original_name":"report.pdf","readable_path":"/Users/.../.ez-assistant/data/sessions/session_.../attachments/attachment_.../report.pdf"}]}}]}}
```

行顺序继续是 Message 顺序，不增加 sequence、Message 表或 Part 表。排队期间
`queued_message_json` 保存完整 User Message；提交到 JSONL 后按既有逻辑置空。

历史重新输入构造新 User Message 时同样使用新请求中的 `attachment_ids`。旧尾段的
File References Parts 随 generation 切换消失，`attachments` 表不做删除、减计数或分支保留。

### 8.3 OpenAI-compatible 编码

Adapter 按 User Part 顺序产生 text content parts：

1. `Text` 使用原文；
2. `Injected` 延续现有临时文本语义；
3. `FileReferences` 渲染为一个独立文本 content part。

文件 Part 的稳定模型格式为：

```xml
<attached_files>
  <file>
    <name>report.pdf</name>
    <path>/absolute/stable/path/report.pdf</path>
  </file>
</attached_files>
```

多文件按 `files` 顺序重复 `<file>`。name/path 使用 XML text 转义，标签、缩进、
换行和尾部换行通过编码回归测试冻结。该文本只声明用户附加的可读文件，
不包含伪造的 Tool Call、Tool Result 或“文件已读取”文字。

OpenAI-compatible wire 仍只使用原生 user text content parts，不声明图片、音频或
Provider 文件上传能力。因此任意格式附件都是工具可读文件，不会因扩展名改变
模型请求类型。

## 九、本地工具与附件静态边界

### 9.1 两种 Host 装配

Runtime Host 保留 fail-closed 默认：

- 默认 `serve`：继续只注册低风险 `echo_text`，未匹配工具不隐式放行；
- 显式本地验证模式：通过名称明确带风险的 serve 参数启用，注册现有全部
  标准文件工具和 `shell`，不弹出审批。

参数建议使用 `--unsafe-unrestricted-local-tools`，帮助文本必须明确：Shell 以当前用户
权限运行，Workspace 不是沙箱，仅能在隔离测试目录中使用。正式 Plan/Build、
Ask/Auto、规则保存、审批和审计仍属于 `v0.12.0`。

验证模式注册：

```text
read_file / list_directory / find_files / search_content
write_file / edit_file / delete_file
shell
echo_text
```

Host 直接依赖 `agent-tools-local`，用共享 `LocalFileSystem` 和 `LocalShell` 能力、
每 Run 独立 `SessionPathResolver` 构造标准工具壳。Shell 继续使用脱敏 EnvironmentPolicy、
超时、输出上限和进程树取消。

### 9.2 附件静态保护

附件静态是产品流程不提供覆盖/编辑命令，不是 OS 安全沙箱承诺。首个实现
采取以下分层：

- Blob 创建完成后按当前用户只读 mode 初始化；
- 结构化文件 Authorizer 对落在任何 Session attachment 目录下的
  Write/Edit/Delete 明确 Deny，Read/List/Search 允许；
- Workspace、Workspace 私有目录和 Session 私有目录在显式验证模式下允许读写；
- Shell 可以绕过结构化文件 Authorizer，同一 OS 用户也可以改 mode；因此文档、CLI
  和验证报告都不得宣称 Session 附件目录是强沙箱。

Hash 用于上传、物理复用和完整性诊断，不能阻止当前 OS 用户主动篡改。
`v0.12.0` 的正式权限模型可收紧结构化工具和 Shell；真正的不可绕过隔离需要另一
OS 身份、sandbox 或远程执行环境，不在本版本伪装实现。

## 十、Runtime 业务流程

### 10.1 Workspace Registry

`AssistantRuntime` 在 `open` 恢复 Workspace 投影，用读写锁保护按 Workspace ID 排序的
Registry。登记、假删或恢复同一 Workspace 时：

1. 经 Runtime operation gate 确认未关闭；
2. 调用 Store 完成文件系统与 SQLite 业务操作；
3. Store 成功后更新 Registry；
4. 然后才返回投影/发布可丢事件。

列表缺省只返回 active Workspace。Get 按 ID 可返回 removed Workspace，便于诊断历史
Session 绑定。不增加单独 RestoreWorkspace 命令；重新登记同一 canonical path
即执行恢复。

### 10.2 Session 创建

```text
校验 model key 和可选 active Workspace
→ 分配 Session ID
→ SessionEnvironmentFactory 准备稳定环境 + SystemPromptSnapshot
→ Store 创建 Session 目录、空 Conversation 和 SQLite Session/Resource 关系
→ SessionController 持有恢复投影
→ 发布 SessionCreated
```

Store 先创建并同步 Session attachments/private 目录与空 Conversation，再在一个 SQLite
事务中插入 `sessions` 和 `session_resources`。事务失败只尝试删除本次新建且
仍为空的目录，不递归删除未知内容。

### 10.3 上传与消息提交

上传只允许目标 Session 为 active。上传成功后 Attachment 已是 Session 资源，不与
之后的 Input 建立数据库原子关系。

`SubmitInput` 执行：

```text
校验 active Session 和非空文本
→ 如果输入幂等 Key 已命中，直接返回首次 Input/Run
→ 按顺序解析全部 Attachment ID
→ 构造 Text + 可选 File References UserMessage
→ 用既有 accept_input 事务持久化 queued message + Run
→ 唤醒 Session queue driver
```

输入幂等查询必须早于附件二次解析；同 Key 重试延续“只信任 Key”的既有
语义，不因重试 payload 已经改变而要求旧附件仍可用或再比较内容。

### 10.4 Run 准备

queue driver 领取 Input 后：

1. 根据当前 model key 与配置快照编译 ModelService；
2. 确认 Session 冻结环境中需要的工作目录当前可用；
3. `RunToolFactory` 根据 `working_directory` 冻结 ToolSet 和 Authorizer；
4. 组装 Agent，然后按既有 staged append 提交 User Message 并开始执行。

任一准备失败都沿用当前队列语义：本 Run 失败、保留输入顺序并等待显式
重试，不跳过中间输入。Workspace 被假删不算准备失败；冻结用户目录真实不可用才返回
`WorkspaceUnavailable`。

## 十一、存储恢复与兼容

### 11.1 v0.10.0 数据兼容

本项目尚未进入对外稳定发布，不建立并行数据格式或“V2”路径。Host 保持一个
读取最新格式的兼容入口：

- schema 初始化通过 `CREATE TABLE IF NOT EXISTS` 添加新表；
- 既有 `sessions` 表不增加必填列，避免破坏 v0.10.0 投影；
- 既有 Session 没有 `session_resources` 时，Host 按已冻结的 Runtime Home 布局补建
  unbound Session 资源行和 attachments/private 目录；
- 补建不修改 `system_prompt_json`、Conversation、model key、lifecycle 或历史 Run；
- 旧 Conversation 不包含 File References，现有 JSONL 反序列化直接保持原样。

补建操作在 Host 写入发现文件并开放 HTTP 服务前完成。任一补建错误停止启动，
不部分开放新 Runtime；
补建必须幂等，重启不重复改写已存在资源行。

### 11.2 附件恢复

Host 启动时：

1. 延续完成现有 body append、pending tool exchange 和 Run 状态恢复；
2. 确认 Workspace Agent 私有目录、Session attachments/private 目录的类型；
3. 按 Attachment 记录确认 Blob 与视图元数据；
4. 仅在目标路径缺失且 Blob 可用时重建原路径视图；
5. 将无法安全修复的 Attachment 标记为 unavailable，但不因单个附件阻断其他
   Session 恢复；后续启动或显式解析确认 Blob 与原视图恢复后，可原地转回 ready。

`staging/uploads` 中的无引用 `.part` 和未记录视图不在本版本自动删除。它们不是
附件业务事实，也不会被列表或消息引用。

### 11.3 冻结路径与内部迁移

- Blob 在 Runtime Home 内变更物理位置时，只更新内部 `relative_path` 和视图链接，
  `agent_readable_path` 不变；
- Workspace 用户目录被用户移动时不自动追踪新位置；原 Workspace 保持但不可用，
  新目录需要登记为新 Workspace；
- Runtime Home 整体迁移不在本版本实现；任何未来迁移都不得通过重写历史
  Message/SystemPromptSnapshot 来“修复”路径。

  通过 `cargo add`、Cargo.lock 和许可证核查后固定。

  里程碑中通过 `cargo add`、Cargo.lock 和许可证核查后固定，不在文档猜版本。
- `assistant-runtime` 不依赖 `agent-tools-local`、SQLite 或 Hash 库；
  `assistant-protocol` 不引入文件 I/O 或路径解析依赖。
- 不新增 Workspace、Attachment 或 Storage crate；当前只有正式 Host 一个本地存储
  调用方，第二个稳定调用方出现后再评估上提。

## 十四、验证方案

### 14.1 单元与存储集成

所有自动测试使用 `tempfile` Runtime Home 和测试 Workspace，不读写用户真实目录：

- Workspace canonical path 幂等登记、假删、原 ID 恢复、新 Session 绑定拒绝和旧
  Session 继续使用。
- Session environment 路径冻结、四类目录区分、未绑定默认工作目录和
  `SystemPromptSnapshot` 精确格式。
- 文本、空文件、包含二进制字节的文件、1 GiB 边界前后的有界测试；大文件测试
  使用 sparse/limit reader，不在常规测试中真实写入 1 GiB。
- 源文件上传后修改/删除不影响 Blob，同名同内容只有一个 Blob，同内容不同名有不同 Blob，不同 Session 有
  不同可读视图。
- 同一 Session 同名同内容重复上传返回首次 Attachment，断线/回复丢失重传不产生第二个业务事实。
- staging 完成、Blob rename、view rename、SQLite commit 四个故障注入点重开恢复，
  不出现数据库 ready 但文件不存在的成功事实。
- File References JSONL round-trip、参考顺序、XML 转义、Provider wire 精确快照，
  以及旧 Text/Injected 编码回归。
- 历史重新输入消除尾段 File References，但 Session Attachment 数量和 Blob 不变。
- v0.10.0 数据目录首次启动补建 unbound Session 资源，不改写旧 Prompt/JSONL。

### 14.2 正式 Host 离线端到端

新增 `apps/runtime-host/tests/v0_11_offline_acceptance.rs`，延续 v0.10.0 的实证方式：

1. 创建隔离 Runtime Home、Workspace、附件源文件和 loopback fake
   OpenAI-compatible Provider；
2. 以显式不受限本地工具模式启动第一个真实 Host 进程；
3. 验证客户端从 `runtime.json` 发现动态地址与 Token，通过 HTTP 登记
   Workspace、创建 Session、流式上传文件并提交带 File References 的 User Message；
4. fake Provider 先发起 `read_file` 或 `shell` Tool Call，再校验工具结果中的随机
   token 并返回最终答案；
5. 关闭 Host，删除/修改源文件，用同 Runtime Home 启动第二个真实 Host；
6. 验证 Workspace/Session/Attachment/Conversation 恢复、路径不变、归档恢复、假删
   和同 Blob 的独立 Session 视图；
7. 验证 SSE 事件、连接断开不取消 Run、无 Token/未知 `Origin` 请求被拒绝、
   精确登记的 WebView Origin 可通过预检和访问，以及
   进程退出后只读检查 SQLite、JSONL、Blob 数量和符号链接目标。

该验收驱动正式 Runtime Host、正式 Store、真实 Provider Adapter 和真实本地工具，
不新建第二套 Demo Runtime 或产品 fake 模式。

人工验收使用正式 Host 显式开启的 feature-gated 私有 Web Demo，以简单静态页面直接

或公共 Web 协议。Demo 按 `call_id` 实时更新工具状态和有限输出，并在 Run 终结后以
Conversation 快照校准；模型 attempt/retry 和最终脱敏诊断使用正式 RuntimeEvent/RunSnapshot。
Demo 默认关闭，只在 loopback 上随当前 Host 实例提供。

## 十五、风险、遗留与排除项

### 15.1 主要风险

- **文件系统与 SQLite 无联合事务**：通过“完整文件先落盘，数据库最后提交”和
  Session Blob Hash 唯一约束收敛；崩溃可留孤立文件，不会对外伪造成功附件。
- **稳定绝对路径限制 Runtime Home 迁移**：这是为保证历史上下文和 Prompt Cache 主动
  接受的约束；后续迁移必须保留别名，不能静默重写历史。
- **符号链接与 Shell 可绕过静态规约**：结构化工具拒绝写附件，但不宣称 OS 强
  隔离；真正沙箱属于后续执行环境能力。
- **HTTP 攻击面高于 UDS**：本地只绑定 IPv4 loopback，使用每进程高强度 Token、
  私有发现文件、Host/Origin 校验和精确 CORS 白名单收窄边界；Token 注入 WebView 后
  需要同时守住 CSP 和导航边界。不将这些措施表述为对同用户恶意进程的强隔离。
- **现在切换传输会扩大 v0.11.0 改动面**：这是在正式 Desktop Runtime Client 出现前最后
  的低成本窗口；通过先建立有界 Command/SSE/Upload 三条边界控制范围。
- **按 Run 编译工具改动构造链**：通过专门 Factory 和现有 compile_run_agent 边界收口，
  不把工具构造分散到 queue driver。
- **合法未引用附件长期累积**：这是已确认的业务语义；本版本只保证它们可查询且
  不误判为损坏，不偷偷增加清理策略。

### 15.2 明确遗留

- 未引用 staging、Blob 和视图的定时清理；
- 用户主动移除 Session Attachment 和永久删除 Session 时的 Blob 回收；
- 上传进度事件、取消、断点续传、分块会话和 Runtime Home 整体迁移；
- 可选远程 Runtime 开关与部署、TLS 终结、用户身份、多租户数据边界和远程运维；
- Workspace Instructions 自动发现/注入、记忆或插件 Internal Injection；
- 正式 Plan/Build、Ask/Auto、审批、审计、Shell 范围限制和 OS 沙箱；
- 正式桌面附件草稿、进度、预览和 Conversation 展示 DTO。

### 15.3 不纳入

- Artifact 业务对象或附件版本历史；
- 按 PDF/图片/音频类型建立不同业务管线；
- 把文件正文、Base64、解析文本或 Workspace 文件列表自动注入模型；
- Session 换绑 Workspace；
- Message/Part 关系表、消息级附件计数或持久化流式 chunk；
- 将 Host 私有 Unix 符号链接、Blob 相对路径或上传 staging 暴露为应用协议；
- 保留 Unix Socket/length-prefixed frame 作为第二套 Host 通信机制。

## 十六、重点 Review 项

1. **统一 HTTP 传输**：默认只启用本地 loopback HTTP；后续如显式启用远程 HTTPS，
   复用同一组 Command/SSE/Streaming Upload API。不保留 UDS 双轨，不传本地源路径。
2. **稳定视图**：macOS/Unix 使用 Session 私有相对符号链接指向 SHA-256 Blob；
   Agent 可读绝对路径一次分配并持久化。
3. **工具装配**：Runtime 从全局 ToolSet/Authorizer 改为按 Run 基于冻结 Session
   环境编译；这是多 Workspace 的必要边界，也是下版本权限的承接点。
4. **验证权限**：默认 Host 仍 fail-closed；只在显式危险参数下开启无审批本地
   文件/Shell 能力，附件的结构化写操作仍拒绝。
5. **数据兼容**：不修改现有 `sessions` 必填列，通过新表和幂等补建把 v0.10.0
   Session 转成最新 unbound 环境，不重写旧 Prompt 和 Conversation。
6. **Part 边界**：File References 是新的持久化 User Part；现有 `Injected` 仅保留为
   Core 内部临时能力，本版本不新增或持久化产品 Internal Injection。
