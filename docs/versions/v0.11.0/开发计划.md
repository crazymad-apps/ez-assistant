# v0.11.0 开发计划：Workspace、附件、统一 HTTP 通信与 Web Demo 验收

## 一、计划信息与设计依据

- 版本：`v0.11.0`
- 状态：已确认
- 当前阶段：M0–M5 均已确认，版本已验收并归档
- 功能范围：[`功能设计`](功能设计.md)
- 实现依据：[`技术方案`](技术方案.md)
- 版本状态：[`docs/版本管理.md`](../../版本管理.md)
- 实际实施记录：[`开发进度`](开发进度.md)

本计划只维护里程碑顺序、状态、交付范围、验证入口和确认门禁。HTTP 路由、
认证、数据格式、文件布局、提交顺序和错误语义以已确认技术方案为准，不在本文
重复定义。

本版本不建设正式桌面页面，不单独安排产品 UI 里程碑。为验证 WebView/浏览器直连
Runtime 的 HTTP 边界，正式 Host 会附带默认关闭的 feature-gated 私有 Web Demo。
该 Demo 只是验收客户端，不构成产品 UI、业务事实源或公共协议。

## 二、台账原则

1. M0 至 M5 顺序推进；每个里程碑完成实现和验证后先标记 `🟨 待确认`，只有用户
   明确确认后才改为 `✅ 已完成`并进入下一里程碑。
2. M0 优先完成现有 Host 通信的整体替换。M0 确认前不开始 Workspace、Attachment、
   File References 或工具装配代码，避免新业务同时跨 UDS 和 HTTP 调试。
3. M0 的完成条件包含移除 Unix Socket、自定义 frame、握手和 `--socket`；不把
   “HTTP 已可用但旧通道仍存在”视为里程碑完成。
4. 正式 Runtime Host 默认只绑定 IPv4 loopback；可选远程 HTTPS 能力默认关闭且不在
   本版本实现。不为验证便利新增任意公网监听参数。
5. 私有 Web Demo 只在显式 feature 与启动开关同时开启时可用，不引入前端框架、
   单独数据 Store 或第二套 Session/Run 状态。页面只通过正式 HTTP API 查询快照和发送意图。
6. 协议、Runtime、Host、私有 Demo 和验收客户端同步演进，保持
   `PROTOCOL_VERSION = 1`，不建立 V2 或其他并行代际。
7. 自动测试只使用 `tempfile` 创建的隔离 Runtime Home、Workspace、SQLite、文件和
   loopback Provider；不读写用户真实 `~/.ez-assistant` 数据。只有默认忽略的真实 LLM
   smoke 可脱敏只读模型配置。
8. 任何 schema 或文件恢复测试都在临时数据集中执行；开发与验收不对用户现有
   `runtime.sqlite3` 执行迁移、覆盖、删除或批量更新。
9. 实际实现与设计假设不符时停止扩大改动，先修订设计并重新确认；不在实现中静默
   改变传输安全、稳定路径、附件静态或历史重新输入语义。
10. 实际产出、验证结果、偏差、遗留和风险写入 `docs/开发进度.md`；本计划只维护
   里程碑状态。
11. 不主动执行 Git 暂存、提交或推送。

## 四、里程碑台账

### M0：Runtime Host 统一 HTTP 通信、UDS 退场与 Web Demo 外壳

- 前置：`v0.11.0` 功能设计、技术方案和本开发计划均已确认。
- 目标：在不改变现有 Session/Run 业务语义的前提下，把正式 Host 和全部现有验证客户端
  一次性切换到本地 HTTP，为后续 Workspace 和 Attachment 开发建立唯一通信底座。
- 交付范围：
  - 正式 HTTP Host 启动、有界 Command JSON、SSE 事件、健康与能力查询；
  - Runtime Home 单实例锁、动态 loopback 端口、私有发现文件和 owned cleanup；
  - Bearer Token、Host/Origin 校验、精确 WebView CORS 白名单、预检和脱敏错误；
  - 现有 RuntimeCommand dispatch、断线不取消 Run、慢客户端背压和受控关闭的 HTTP 迁移；
  - 新增默认关闭的 feature-gated 私有 Web Demo 外壳，使用简单静态资源验证
    Command、SSE、授权和浏览器直连；
  - 离线验收 support 和 v0.10.0 回归场景改用 HTTP 发现与访问；
  - 退役现有 Ratatui Demo 及其 UDS 客户端依赖，不同时维护两套私有人工验收 UI；
  - 删除 Unix Socket endpoint、frame/handshake、旧客户端通道和 `--socket`，不保留双轨；
  - HTTP 服务端/客户端依赖的选择、锁定与许可证核查，以及对应模块约束同步。
- 验证入口：

  ```bash
  cargo test -p assistant-runtime-host -p assistant-protocol --all-features
  cargo test -p assistant-runtime-host --test v0_10_offline_acceptance --all-features
  cargo clippy -p assistant-runtime-host -p assistant-protocol --all-targets --all-features -- -D warnings
  cargo fmt --all --check
  cargo run -p assistant-runtime-host -- --help
  ```

- 完成判定：正式 Host 只通过动态 loopback HTTP 对外提供能力；现有 Command 与 SSE 事件
  在新通道上通过回归；未授权、未知 Origin、超限 JSON 和 stale endpoint 均有稳定结果；
  客户端断开不取消 Run；私有 Web Demo 可加载 Conversation 历史，并把 SSE 文本增量直接
  投影到消息列表中的 Assistant 消息；
  工作树不再存在产品 UDS/frame 运行路径或继续运行的 Ratatui 客户端。
- Review 重点：Host 是否仍只做传输与装配；发现文件和 Token 是否不进入日志；精确
  Origin 白名单是否支持 WebView 直连且拒绝通配符 CORS；SSE 断开是否不影响 Runtime Run；
  UDS 删除是否没有遗留隐式验证依赖。
- 技术依据：技术方案 2.4、第三节、7.1、7.5、12.1、13.2、14.2 和 15.1。

### M1：Workspace Registry 与 Session 冻结环境

- 前置：M0 已确认。
- 目标：建立可持久的 Workspace 关系和 Session 冻结执行环境，使后续附件和工具始终使用
  同一份稳定目录事实。
- 交付范围：
  - Workspace 应用 ID、登记/查询/列表/假删意图和脱敏投影；
  - Workspace、Session 绑定和执行环境的 RuntimeStore 业务端口与 Host SQLite Adapter；
  - 用户目录 canonical 身份、Workspace 级 Agent 私有目录和新旧 Session 的稳定目录；
  - Session 创建时可选绑定、无换绑、假删后新绑定拒绝和原 Workspace 恢复；
  - `SystemPromptSnapshot` 中稳定目录信息的确定性构造，不注入文件列表；
  - v0.10.0 数据的幂等 unbound Session 环境补建与重启恢复。
- 验证入口：

  ```bash
  cargo test -p assistant-runtime -p assistant-runtime-host -p assistant-protocol --all-features
  cargo clippy -p assistant-runtime -p assistant-runtime-host -p assistant-protocol --all-targets --all-features -- -D warnings
  cargo fmt --all --check
  ```

- 完成判定：同一 canonical Workspace 幂等登记并可假删/恢复；多 Session 可共用同一
  Workspace 私有目录；Session 绑定在重启后保持；旧 Session 成为 unbound 且不改写历史
  Prompt/Conversation；用户目录不被复制或删除。
- Review 重点：Runtime/Host 所有权、Workspace 假删不等于物理删除、Session 无换绑、
  `SystemPromptSnapshot` 冻结以及补建不改写旧业务事实。
- 技术依据：技术方案 4.1、4.3、第五节、6.1、6.3、10.1、10.2 和 11.1。

### M2：Attachment 存储、流式上传与恢复

- 前置：M1 已确认。
- 目标：建立独立于 Message 的 Session Attachment 事实，完成 HTTP 流式上传、物理正文
  复用、稳定 Agent 可读视图和中断恢复。
- 交付范围：
  - Attachment ID、列表/查询投影、上传准入/提交和 Session 内 Blob Hash 去重语义；
  - multipart 单文件流式入口、大小上限、staging、SHA-256、Blob 复用和有界 I/O；
  - SQLite Attachment/Blob 元数据、Session 稳定附件视图和同名文件隔离；
  - 文件与 SQLite 的提交顺序、并发 Hash 复核、失败清理和脱敏错误；
  - 重启后 Blob/视图校验、原路径修复和 unavailable 投影；
  - 上传成功即保留 Session 关系，不与后续 Message 提交回滚。
- 验证入口：

  ```bash
  cargo test -p assistant-runtime -p assistant-runtime-host -p assistant-protocol --all-features
  cargo clippy -p assistant-runtime -p assistant-runtime-host -p assistant-protocol --all-targets --all-features -- -D warnings
  cargo fmt --all --check
  ```

- 完成判定：任意格式文件可在有界内存中流式上传；同名同内容可复用 Blob，同内容不同名不复用，不同 Session
  保持独立附件和稳定路径；源文件变化不影响附件；同一 Session 同名同内容重传不产生第二份业务
  事实；设计中的中断点不会恢复出 ready 数据库行但文件缺失的伪成功状态。
- Review 重点：大请求体是否真正流式处理；Host 是否在 Runtime 准入/提交之间只持有短期
  资源；是否以文件完整落盘后再提交业务行；稳定视图与内部 Blob 是否解耦。
- 技术依据：技术方案 4.2、第六节、第七节、10.3、11.2、12.2 和 15.1。

### M3：File References 持久化与模型编码

- 前置：M2 已确认。
- 目标：让 User Message 以结构化且可恢复的 File References Part 引用 Session Attachment，
  并向模型提供确定性文件名称/路径提示而不自动读取正文。
- 交付范围：
  - `UserPart::FileReferences` 领域类型、顺序、校验和 Conversation JSONL round-trip；
  - SubmitInput/Reenter 携带 Attachment ID 列表、Runtime 整批解析和跨 Session 拒绝；
  - 消息提交失败不回滚 Attachment，历史重新输入消除尾段 Part 但不删除 Session 附件；
  - OpenAI-compatible Adapter 对 Text/Injected/FileReferences 的保序编码、XML 转义和稳定快照；
  - 不将文件正文、Base64、自动解析结果或伪 Tool Call 注入模型。
- 验证入口：

  ```bash
  cargo test -p agent-types -p agent-provider-openai-compatible -p assistant-protocol -p assistant-runtime -p assistant-runtime-host --all-features
  cargo clippy -p agent-types -p agent-provider-openai-compatible -p assistant-protocol -p assistant-runtime -p assistant-runtime-host --all-targets --all-features -- -D warnings
  cargo fmt --all --check
  ```

- 完成判定：Conversation 重启后 Text/FileReferences 类型、顺序和内容不变；同附件
  重复引用保持完全相同路径；跨 Session ID 不可伪造引用；Provider wire 精确匹配已确认格式；
  历史重新输入不误减 Session Attachment。
- Review 重点：File References 是否仍是 User Message 内的独立持久化 Part；是否只保存
  Agent 需要的原始名称和稳定路径；Provider 编码是否保序、确定且不伪造工具行为。
- 技术依据：技术方案 4.2、第八节、10.3、12.1、14.1 和 15.3。

### M4：按 Run 工具编译与真实文件验证

- 前置：M3 已确认。
- 目标：把 Session 冻结环境接入每个 Run 的工具和 Authorizer 装配，使 Agent 能按引用
  真实读取附件，同时保持默认 Host fail-closed。
- 交付范围：
  - Runtime 的 RunToolFactory/RunToolBundle 构造边界和单 Run 不可变装配；
  - Workspace、Workspace 私有目录、Session 附件与 Session 私有目录的每 Run 路径解析；
  - Host 顶层装配 `agent-tools-local` 的标准文件和 Shell 能力；
  - 默认 `serve` 继续仅开放低风险工具，显式危险验证模式才启用无审批本地工具；
  - 结构化文件工具拒绝附件 Write/Edit/Delete，并保持 Shell 不是 OS 沙箱的真实说明；
  - fake Provider 主动发起文件工具读取的集成回证。
- 验证入口：

  ```bash
  cargo test -p agent-tools -p agent-tools-local -p assistant-runtime -p assistant-runtime-host --all-features
  cargo clippy -p agent-tools -p agent-tools-local -p assistant-runtime -p assistant-runtime-host --all-targets --all-features -- -D warnings
  cargo fmt --all --check
  ```

- 完成判定：不同 Workspace Session 不共享可变 resolver；每个 Run 冻结工具与 Authorizer；
  默认 Host 不因引入本地 Adapter 而隐式放权；显式验证模式中 Agent 能通过 File References
  读到附件内容；结构化写操作无法把附件解释为可编辑工作文件。
- Review 重点：工具是否按 Run 编译而非修改全局快照；Runtime 是否仍不直接依赖
  `agent-tools-local`；默认授权是否 fail-closed；CLI 是否对无限制模式的风险提示足够清晰。
- 技术依据：技术方案 2.3、4.4、第九节、10.4、13.1、13.3 和 14.1。

### M5：Web Demo 端到端回证与版本验收准备

- 前置：M4 已确认。
- 目标：通过两次正式 Runtime Host 进程和真实 HTTP 客户端回证 v0.11.0 完整业务链，
  完成 workspace 回归、可选真实 LLM smoke 和版本验收证据准备。
- 交付范围：
  - 正式 Host 离线验收测试，覆盖 HTTP 发现/授权/SSE、Workspace、Attachment、
    File References、真实文件工具、归档恢复和两次进程启动；
  - 扩展私有 Web Demo，覆盖 Workspace 登记/选择、浏览器文件上传、Attachment 列表、
    带 File References 的消息提交、运行状态和归档恢复人工验收；
  - 断线后从权威快照恢复，不依赖事件重放，不因断线取消 Run；
  - 工具 proposed/running/output/completed 的实时投影，以及模型 attempt/retry 与最终脱敏失败诊断；
  - SQLite、Conversation JSONL、Blob 数量、Session 视图和稳定路径的分层只读核对；
  - 默认忽略的真实 LLM smoke，只读使用现有模型配置并在临时 Runtime Home/Workspace 中
    要求模型实际调用文件工具；
  - 敏感信息、原始文件内容、Token、API Key、Prompt 和完整模型回复的泄漏检查；
  - 功能设计 16 条验收标准到自动化/人工证据的映射，以及长期模块文档同步。
- 验证入口：

  ```bash

  cargo clippy --workspace --all-targets --all-features -- -D warnings
  cargo test --workspace
  cargo doc --workspace --no-deps
  cargo metadata --format-version 1 --no-deps

  cd apps/desktop
  npm run build
  npm run tauri -- build --no-bundle
  ```

- 可选真实 LLM 入口：

  ```bash
  cargo test -p assistant-runtime-host --test v0_11_real_llm --all-features -- --ignored --nocapture
  ```

- 完成判定：功能设计 16 条验收标准全部具有实际证据；全 workspace 回归与桌面
  构建通过；正式 Host 两次启动后的数据、路径和业务投影一致；未执行项、偏差、
  遗留和风险已明确记录；私有 Web Demo 可完成本版本人工业务验收，可进入正式版本验收。
- Review 重点：验证是否使用正式 Host/Store/Provider Adapter/工具而非第二套 Demo Runtime；
  是否真实覆盖进程重启与文件故障；是否分清数据库、文件、Runtime 投影和 HTTP 结果；
  真实 LLM 验证是否严格隔离且不泄漏凭证。
- 技术依据：功能设计第七节，技术方案第十四节和第十六节。
