# v0.11.0 功能设计：Workspace、附件与系统上下文

## 一、设计信息

- 版本：`v0.11.0`
- 状态：已确认
- 影响模块：`assistant-runtime`、`assistant-protocol`、`apps/runtime-host`、`agent-core`、
  `agent-tools`、`agent-tools-local`
- 需求来源：Runtime 阶段路线、
  [`Workspace 与附件讨论`](../../inputs/260810-v0.11.0-Workspace与附件讨论.md)，以及 2026-08-10
  的 Workspace、附件、交互和传输方式讨论

本版本涉及应用协议、持久化、文件数据和跨模块执行契约，功能设计确认后必须单独形成技术方案。
本版本不建设正式桌面页面，因此暂不单独形成界面交互设计指导；本设计只定义未来客户端必须遵守
的业务交互语义。

## 二、背景与目标

`v0.10.0` 已形成可靠的 Session、Conversation、Run 和归档恢复闭环，但 Session 仍缺少稳定的
工作空间关系，用户也无法把本地文件作为可恢复、可重复引用的会话资源交给 Agent。当前
System Prompt 可以按 Session 冻结，但 Workspace 引入的多类稳定目录仍需要形成明确的
Agent 上下文语义。

`v0.11.0` 当前已确认部分的目标是：

1. 建立独立、持久化的 Workspace，使多个 Session 可以复用同一用户工作目录和 Workspace 级
   Agent 私有文件。
2. 建立统一的文件上传能力，把用户选择的各种文件保存为 Session 私有、静态的附件资源。
3. 文件内容不自动展开进模型上下文，Agent 只获得稳定引用，并按需使用文件工具、Shell 或脚本
   读取和处理。
4. 文件上传与消息提交保持独立的可靠边界，同时在客户端交互上仍表现为一次自然的发送动作。
5. 明确 Text 和 File References 两类持久化 Part 的来源、可见性和恢复语义。
6. 保证附件可读路径和 Workspace 相关稳定目录在 Runtime 重启、归档恢复和会话重建后
   保持稳定，不因动态重算改变历史模型输入或破坏 Prompt Cache。

本版本的 System Context 只增加 Session 已绑定 Workspace 的稳定目录信息。Workspace Instructions
的自动发现与注入、逐轮动态上下文以及产品级持久化 Internal Injection Part 均不纳入
`v0.11.0`。现有 Core 为上下文压缩构造临时请求时使用的 `UserPart::Injected` 保持原语义，
不属于本版本新增业务范围。

## 三、非目标

以下内容不进入当前已确认范围：

- Artifact、产物注册、发布、版本、不可变快照或独立产物生命周期。Agent 在 Workspace 中生成
  的文件仍是普通工作文件，Session 私有目录中的文件仍是 Session 范围的普通私有文件。
- 根据文件类型建立图片、PDF、文本、音频等不同的附件业务流程。
- 自动提取、解析、总结或向模型直接注入附件正文；附件也不自动作为多模态内容发送给模型。
- 修改或覆盖已经上传的附件内容。需要不同内容时重新上传为新的附件。
- Session 创建后直接更换绑定的 Workspace；切换 Workspace 通过创建或显式 Fork 新 Session
  完成。
- 把用户工作目录完整复制到 Runtime Home，或把 Workspace 私有目录当作用户项目的镜像和备份。
- 自动发现、读取或注入 `AGENTS.md` 等 Workspace Instructions，以及检测其变化或更新已有
  Session 的提示词。
- 为每条 User Message 生成 Internal Injection Part，或在本版本接入记忆召回、插件上下文等逐轮
  动态注入来源。
- 正式桌面端 Workspace、附件和文件预览页面；正式桌面产品仍在后续版本建设。
- Plan / Build、Ask / Auto、正式权限作用域、审批、审计和 Shell 沙箱；这些仍属于后续权限版本。
- 定时回收未被消息引用的 Session 附件、已删除 Session 的附件或没有 Session 引用的物理内容。
- 先上传到全局文件库、稍后再选择 Session 的长期独立上传业务。
- 在功能设计中冻结数据库表、字段、Hash 算法、上传分片、文件布局或软链接方案。

## 四、功能范围与使用路径

### 4.1 Workspace 关系

Workspace 是独立、可持久化的业务对象，不等同于 Session：

- 一个 Workspace 可以被多个 Session 复用；
- 一个 Session 最多绑定一个 Workspace，也可以是不绑定 Workspace 的普通会话；
- Session 创建后不直接换绑 Workspace；
- 需要在另一个 Workspace 中继续工作时，创建新 Session，未来也可以通过显式 Fork 创建；
- Session 归档和恢复不改变其 Workspace 关系；
- Workspace 与 Session 的业务状态由 Runtime 持有，客户端不保存第二份权威关系。
- Runtime 支持创建、查询、列出和移除 Workspace；
- 移除 Workspace 采用假删：它不再出现在正常列表中，也不能再绑定新 Session；
- 已绑定 Session 保留历史关系并可继续使用，假删不改写其 `SystemPromptSnapshot`；
- 假删绝不删除用户工作目录、Workspace 级 Agent 私有目录或历史数据；
- 重新登记同一 Workspace 时恢复原 Workspace，而不创建与原历史断开的重复关系；
- 用户工作目录暂时不可用时保留 Workspace 登记，依赖该目录的操作返回明确错误，不自动删除、
  换绑或重建 Workspace。

### 4.2 Workspace 的两类持久目录

每个 Workspace 同时管理两类不同用途的目录：

1. **用户工作目录**：用户已有的项目或工作目录。Runtime 保存其 Workspace 关系，但不复制整个
   目录内容；其中的文件仍是用户和 Agent 可以持续读写的普通工作文件。
2. **Workspace 级 Agent 私有目录**：由 Runtime 在 `~/.ez-assistant` 中为 Workspace 管理的持久
   目录，用于保存 Workspace 范围的 Agent 私有文件。

Workspace 级 Agent 私有目录具有以下能力语义：

- 生命周期跟随 Workspace，而不是单个 Session；
- 绑定同一 Workspace 的多个 Session 可以共同使用；
- 不污染用户工作目录，也不承担用户项目备份职责；
- 路径在 Workspace 生命周期内保持稳定，Runtime 重启和 Session 切换后继续有效；
- 不存放 Session 私有附件和 Session 临时文件。

Session 仍拥有独立的附件空间和 Session 私有目录。Workspace 级 Agent 私有目录和 Session
私有目录都由 Runtime 管理，前者供同一 Workspace 的多个 Session 复用，后者只属于单个
Session。附件目录用于静态参考文件，不与 Agent 私有目录混为同一种用途。因此 Agent 执行时
需要区分用户工作目录、Workspace 私有目录、Session 私有目录和 Session 附件目录。具体路径
布局和工具暴露方式由技术方案确定。

### 4.3 统一的文件附件

附件统一按“文件”处理，不根据文件格式建立不同的业务类型：

- 用户选择文件后，文件内容被上传并复制到 Runtime 管理的存储；
- Runtime 不长期依赖用户原始路径，原文件后续变化不影响已经上传的附件；
- 上传成功后的附件源内容保持静态，不通过产品流程修改或覆盖；
- 内容类型、大小等信息可以用于展示和诊断，但不决定 Agent 的处理方式；
- Agent 根据任务自行判断使用文件读取、Shell、脚本或其他已获准工具处理文件；
- 附件是 Session 资源，可以被同一 Session 的多条 User Message 重复引用；
- Session 归档时附件继续保留，恢复后仍使用原引用和原内容。

同一 Session 中原始文件名和内容都相同的文件只形成一个业务附件，重复上传返回首次附件及其稳定路径；
文件名不同时按不同附件处理。不同 Session 仍保持独立的业务附件关系和可读视图。Hash、物理复用方式和跨平台实现属于
技术方案。

### 4.4 文件上传与消息提交

文件上传和 User Message 提交是两个独立业务操作，但客户端应把它们组织成一次自然的发送体验：

1. 用户选择文件时，客户端只维护本地输入草稿和附件展示状态；
2. 用户点击发送后，客户端先提交文件；
3. 每个文件上传成功后，Runtime 完成文件落地、附件持久化和 Session 引用关系记录，并返回该
   Session 中稳定的文件引用；
4. 所有待发送文件均上传成功后，客户端再提交包含 Text Part 和 File References Part 的
   User Message；
5. Runtime 接受消息后，按既有可靠输入语义创建并排队 Run。

失败语义如下：

- 文件上传失败时，客户端不继续提交消息，保留正文和文件状态供用户重试；
- 多个文件中只有部分上传成功时，已经成功的附件及其 Session 关系不回滚；
- User Message 提交失败时，已经上传的附件及其 Session 关系不回滚；
- 重试消息提交时可以直接复用已经上传成功的文件引用；
- 上传成功但尚未被任何 Message 引用的文件是合法的 Session 附件，不视为损坏数据；
- User Message 提交继续遵循既有幂等语义，相同幂等 Key 不重复创建 Message 和 Run。

上传协议、并行或顺序传输、文件级幂等、大小限制和临时文件处理属于技术方案，不进入本节。

### 4.5 稳定的 Agent 可读路径

每个附件在上传成功时一次性分配 Agent 可读路径，并将该路径作为附件持久化事实保存。在附件
生命周期内，该路径不得因为以下变化而改变：

- Runtime 重启；
- Session 归档与恢复；
- Conversation 或 Session 重建；
- 物理内容去重或内部存储迁移；
- 同名文件再次上传；
- 后续 Message 再次引用同一附件。

同一 Session 中重复引用同一附件时，必须向 Agent 提供完全相同的路径字符串，避免历史上下文
变化和 Prompt Cache 失效。

Agent 可读路径与 Runtime 内部物理位置是不同概念。物理内容可以复用或迁移，但 Runtime 必须
继续维持原可读路径有效。路径的具体格式、映射方式和跨平台行为由技术方案确定。

### 4.6 User Message Parts

User Message 区分以下两类持久化 Part：

| Part | 来源 | UI 可见性 | 是否属于用户正文 | Agent 语义 |
| --- | --- | --- | --- | --- |
| Text Part | 用户输入 | 可见，显示为消息正文 | 是 | 用户自然语言输入 |
| File References Part | 用户选择文件 | 可见，以附件卡片等附属组件展示 | 否 | 文件原始名称和稳定可读路径的有序列表 |

Text Part 和 File References Part 都属于持久化会话数据。File References Part 虽然不属于
用户正文，但不能因此被视为临时数据。

File References Part 具有以下语义：

- 属于 User Message；
- 按用户选择顺序保存文件引用列表；
- 保存文件原始名称和稳定的 Agent 可读路径；
- 不包含文件正文、Base64、内容摘要或自动解析结果；
- UI 恢复历史消息时重建为可见附件组件，而不是混入正文文本；
- Runtime 构造 Agent 输入时保持结构化边界，不自动展开引用文件。
- Runtime 向 Agent 构造 User Message 时，先传递用户正文，再传递文件引用列表；二者不合并为一份
  业务正文。Provider 需要扁平字符串时，也必须按同一顺序确定性渲染。
- Agent 看到的文件引用必须明确表示“用户附加的可读文件”，不伪造已经发生的文件读取或 Tool Call。
具体标记格式和 Provider 编码进入技术方案。

### 4.7 附件生命周期与消息历史

附件是 Session 资源，Message Part 只描述某条 User Message 使用了哪些附件：

- 数据库不维护消息级附件引用次数；
- 同一附件被同一 Session 的多少条消息引用，不改变 Session 对附件的持有关系；
- 从历史 User Message 重新输入并销毁尾段时，对应 Text 和 File References Parts 随消息一起销毁；
- 尾段销毁不减少 Session 级附件关系，也不立即删除文件；
- 已上传但未进入消息、或者已经不再被当前 Conversation 引用的附件仍可以保留为 Session 资源；
- Session 归档和恢复不改变附件内容、稳定路径或 Session 关系。

用户主动移除 Session 附件、永久删除 Session 和定时物理回收的产品能力不在本版本
范围内，不能从消息尾段销毁中隐式推导。

### 4.8 数据权威边界

附件元数据、Session 关系和生命周期属于 Runtime 的结构化业务数据；文件正文保存在文件系统。
Conversation 正文继续保存持久化 Message Parts，包括 File References，不在 SQLite 中复制
整条消息正文。

Runtime 内部物理路径不作为 Message Part 或跨层协议中的附件身份。Agent 可读路径是稳定的执行
引用，不等同于物理 Blob 位置。数据库结构、文件布局、提交顺序和故障恢复方式统一由技术方案
定义。

## 五、模块边界与契约影响

- `assistant-runtime`：持有 Workspace、Session 绑定、假删状态、附件、Session 引用、稳定可读路径、
  消息 Parts 和恢复语义的业务权威；负责文件上传和消息提交之间的状态衔接。
- `apps/runtime-host`：提供 Runtime Home、具体数据库与文件系统基础设施，并装配真实文件和 Shell
  能力；不持有第二份 Workspace 或附件业务状态。
- `assistant-protocol`：承载 Workspace 意图、文件上传结果、User Message 的 File References Part
  和客户端所需投影；不暴露 Runtime 内部 Blob 路径或数据库结构。
- `agent-core`：继续只负责单次 Agent 执行，消费已经冻结的 System Prompt 和 Conversation；不知道
  附件数据库、上传流程或 Workspace 生命周期。
- `agent-tools`：继续提供实现无关的文件与 Shell 能力契约，不引入附件存储职责。
- `agent-tools-local`：提供真实本地文件和 Shell Adapter。其路径访问、写入能力与附件静态语义之间
  的保护方式由上层装配和技术方案负责。
- 正式桌面端：未来负责本地草稿、附件组件和“先上传文件、后提交消息”的无感交互，但不持有
  Workspace、附件、Message 或 Run 的权威状态。
- 本版本可在正式 Runtime Host 中提供默认关闭的私有 Web Demo，用于人工验证 HTTP、
  Workspace、附件上传和消息引用。该 Demo 不是正式桌面 UI、不持有第二份业务状态，
  也不把页面结构提升为产品契约。

具体 DTO、错误类型、数据库 Repository、上传帧和目录模块划分均进入技术方案。

## 六、关键取舍

### 6.1 用户目录与 Agent 私有目录并存

Workspace 不复制用户项目，但需要在 Runtime Home 中拥有独立的 Workspace 级 Agent 私有目录。
前者是用户工作事实，后者是多个 Session 可复用的 Agent 私有状态；两者不能混为镜像或备份。

### 6.2 所有附件统一作为文件

上传文件可能具有任意格式，Runtime 不提前推断处理方式。Agent 通过工具按需读取，必要时自行编写
脚本处理，避免为每种格式固化不同业务管线。

### 6.3 文件先于消息独立提交

文件上传成功就形成 Session 附件事实，不与随后 User Message 的成功绑定。这样消息失败后可以
复用已经上传的内容，也避免跨文件系统和会话正文制造表面上的全局原子操作。

### 6.4 文件引用是可见附属内容，不是正文文本

文件引用由用户显式选择，属于 User Message 并在 UI 中可见；但它不拼接进自然语言正文，也不
自动展开文件内容。结构化 Part 同时服务 UI 恢复和 Agent 文件定位。

### 6.5 Workspace 移除不等于删除目录

Workspace 假删只从新建 Session 的可选范围移除登记，不改写已有 Session，不删除用户目录、
Workspace 私有目录或历史数据。该能力是业务列表管理，不是文件系统删除或权限撤销。

### 6.6 稳定目录信息进入 SystemPromptSnapshot

Session 绑定 Workspace 后，用户工作目录、Workspace 级 Agent 私有目录、Session 私有目录和
Session 附件目录的稳定信息进入该 Session 的 `SystemPromptSnapshot`。快照不列出 Workspace 文件，也不自动
发现或注入 Workspace Instructions。

### 6.7 Agent 可读路径是稳定事实

路径会进入 Agent 上下文并影响后续工具调用和 Prompt Cache，因此不能临时生成或随物理布局变化。
底层存储可以迁移，但必须维持原路径映射。

### 6.8 不引入 Artifact

当前普通工作文件、Workspace 私有文件、Session 附件和临时文件已经有清晰归属。没有独立的发布、
交付或版本生命周期时，不增加 Artifact 业务对象。

## 七、验收标准

1. Runtime 重启后能够恢复 Workspace、Session 绑定和 Workspace 级 Agent 私有目录；多个绑定同一
   Workspace 的 Session 可以访问同一私有文件，用户工作目录未被复制。
2. Runtime 可以创建、查询、列出和假删 Workspace；假删后不再对新 Session 可选，已绑定 Session 继续
   保留关系和使用能力，用户目录、Workspace 私有目录和历史数据均未被删除。
3. 重新登记已假删的同一 Workspace 后恢复原关系；用户目录不可用时保留 Workspace 登记并返回
   明确错误，不自动换绑或重建。
4. 一个 Session 最多绑定一个 Workspace；不绑定 Workspace 的 Session 仍可正常存在；既有
   Session 不能通过普通操作直接换绑。
5. 文本、图片、PDF、表格或其他测试文件均走同一上传能力，Runtime 不根据格式自动把内容展开进
   模型上下文。
6. 上传后修改或删除用户原始文件，不影响 Runtime 中已经形成的 Session 附件。
7. 文件上传成功后立即形成可恢复的附件与 Session 关系；即使尚未提交 User Message，Runtime
   重启后该附件仍然存在。
8. 任一文件上传失败时客户端不继续提交 User Message；部分文件已经上传成功时不回滚成功附件。
9. 文件全部上传成功但 User Message 提交失败时，附件和 Session 关系保持不变，随后可以直接复用
   原文件引用重试消息提交。
10. 恢复 Conversation 后，Text 和 File References Parts 的类型、内容和顺序与首次持久化结果一致；
    File References 在 UI 投影中仍是附属文件列表，不混入正文。
11. File References Part 不包含文件正文或 Base64；Agent 收到原始名称和稳定可读路径后，可以按需
    使用真实文件工具、Shell 或脚本读取测试附件；模型输入不伪造已经发生的文件读取。
12. 同一附件在后续 Message、Runtime 重启、Session 归档恢复和物理内容复用后继续使用完全相同的
    Agent 可读路径。
13. 绑定 Workspace 的新 Session 在 `SystemPromptSnapshot` 中冻结稳定目录信息，但不列出 Workspace
    文件，不自动发现或注入 Workspace Instructions。
14. 原始文件名和内容都相同时可以只保存一份物理正文，但不同 Session 保持独立附件关系和各自稳定的可读视图，
    Message 不暴露内部物理 Blob 路径。
    同一 Session 重复上传同名同内容文件返回首次 Attachment，不产生第二个业务附件。
15. 从历史 User Message 重新输入并销毁尾段后，相关 Message Parts 不再出现在 Conversation；
    Session 附件关系和附件文件不因此减少或删除。
16. 本版本不引入 Artifact、产品级持久化 Internal Injection Part 或 Workspace Instructions
    自动注入 API；Workspace 输出继续表现为普通文件。

## 八、风险、兼容性与待确认项

### 8.1 风险与缓解方向

- **稳定路径与物理迁移冲突**：技术方案必须把 Agent 可读路径与物理 Blob 位置分开，任何去重和
  迁移都不能改变历史路径字符串。
- **完整文件与 Shell 权限可绕过静态附件语义**：v0.11.0 验证环境允许完整工具能力，但不能把
  修改附件解释为受支持行为；原始附件、Agent 可读视图和写入目标的隔离方式进入技术方案。
- **文件系统与数据库无法天然组成单一事务**：技术方案必须定义上传成功点、失败恢复和可识别的
  中间状态，不能向客户端报告不存在的附件。
- **大文件占用内存或阻塞传输**：上传大小、流式写入、分片和取消策略由技术方案基于正式协议
  边界确定。
- **合法未入消息附件持续累积**：消息失败不回滚附件是确认语义；自动清理暂不实现，后续根据
  实际数据规模设计回收能力。

### 8.2 兼容性

- `v0.10.0` 既有 Session 没有 Workspace 和附件关系，升级后继续作为未绑定 Workspace 的普通
  Session，不为其虚构目录或附件。
- 既有 `SystemPromptSnapshot` 冻结语义保持不变；新 Session 只在创建时增加已绑定 Workspace 的
  稳定目录信息，不改写历史 System Prompt。
- Conversation 新增 File References Part 时必须保证正文格式、恢复和历史重新输入同步演进，
  不建立另一套 UI 专用消息正文。
- Runtime、Host 和客户端协议仍按当前早期阶段统一演进，不建立并行协议代际。

### 8.3 后续功能事项

本功能设计没有未解决的当版本功能问题。以下事项已明确不纳入 `v0.11.0`：

- Workspace Instructions 的自动发现、优先级、冻结和更新；
- Internal Injection Part 以及记忆、插件或其他逐轮动态上下文；
- 用户主动移除 Session 附件、永久删除 Session 时的附件处理和定时物理回收；
- 把 Workspace 移除扩展为文件权限撤销或物理目录删除。

### 8.4 由技术方案承接的事项

- 数据库表、字段、索引和 Repository 边界；
- 文件 Hash 算法、Blob 布局、去重和 Session 私有视图；
- 上传协议、分块、大小限制、进度和取消；
- Agent 稳定可读路径的格式、映射和跨平台实现；
- 稳定目录信息在 `SystemPromptSnapshot` 中的确定性渲染，以及 File References Part 向各 Provider
  模型消息的编码格式；
- 文件系统与 SQLite 的提交、重试和恢复顺序；
- 附件静态内容保护与完整文件、Shell 能力之间的实现边界；
- Runtime、Host、Protocol 和工具模块的具体代码结构，以及正式 Runtime Host 或专门验证入口的
  端到端验收方案。
