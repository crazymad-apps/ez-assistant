## 二、目标与首批范围

产品维护一套内置资源，使插件、MCP 和 Skill 有明确的产品来源与可维护的交付边界。复用现有发现、选择、启停、按需加载和调用机制；不将通用辅助插件整体并入产品，也不要求用户先安装该插件才能取得首批内置能力。

| 首批资源 | 用户结果 | 边界 |
| --- | --- | --- |
| DeepSeek 搜索 MCP | 用户配置自己的 Key 后，Agent 可以选择并调用搜索能力，结果保留来源 | 与主模型解耦；没有 Key 时明确提示待配置，不自动借用其他模型／独立 MCP 的凭据或发起计费请求 |
| `skill-creator` Skill | Agent 可以发现并按需加载创建／更新 Skill 的操作指导 | 用户新建的 Skill 写入实际用户或项目 Skill 目录；内置正文按产品资源管理，不写回应用安装内容 |

“内置插件、MCP、Skill”表示本次维护与接入范围，不强制为每项能力套一层插件。首批两项是否通过同一个内置插件组织，还是各自作为 MCP／Skill 资源，由技术方案按现有归属和最小新增原则确定。

DeepSeek 网页读取 `deepseek_fetch` 存在于旧 MCP 中，本轮已确认技术方案仅提供搜索，不纳入首批。其他辅助能力、更多服务商及资源市场不在首批计划内。

## 三、现有能力与实际缺口

- Host 已有用户／工作区 Skill 扫描、已安装插件 Skill 归并与稳定来源优先级；没有可直接宣称已完成的统一内置来源。需要明确内置资源如何参与发现和同名选择，不能假称复制文件就能生效。
- MCP 已有用户配置、插件描述符、生命周期、工具发现、权限与调用链，可复用。产品内置来源的装配、配置所属、可见性与启用规则仍需设计，不能伪造一次用户插件安装或静默修改原 `mcp.json`。
- 独立通用辅助插件的 DeepSeek MCP 和 Skill 可作为实现／正文参考；复用前核对依赖、许可证、维护来源和配置适配，不复制其整包、随包运行时或历史用户配置。

## 四、产品行为与数据边界

1. 内置资源与用户安装插件、用户／项目 MCP 和 Skill 的来源应可辨识；同名冲突、优先级及用户覆盖能力必须显式设计，不静默覆盖现有用户资源。
2. 内置内容由产品维护，用户配置、凭据和运行数据分别归当前 Host 的用户域；产品升级不能用默认文件覆盖用户已保存的 Key 或启停选择。源码目录、安装资源、用户可写目录的具体位置留技术方案确定。
3. DeepSeek 搜索使用独立配置，不绑定会话主模型；默认可见、默认禁用，缺配置明确提示。用户在编制计划时再次确认默认不启用；保存 Key 不自动启用，主动启用并刷新后才连接，升级保持原启停选择，没有明确启用记录时仍禁用。保存配置不等于验证连接成功，也不自动请求真实服务。
4. Skill 继续通过目录与按需加载使用，不能将完整 `skill-creator` 正文塞进所有会话系统提示词；旧会话采用现有冻结／刷新语义，不自动改写历史激活内容。
5. 内置资源的版本、升级和缺失诊断应能够对应实际交付；不预设新的数据库目录表、独立更新器、双写配置或安装／迁移任务。用户已确认随 Host 版本交付和更新；不另建中心独立更新链路。
6. Desktop、Web 与 Client 连接同一 Host，能力的权威来源与生命周期归 Host／Runtime，不在 UI 再维护一套内置目录或业务状态。支持平台和无需外部运行时的交付要求按实际技术方案验证，不以现有插件包声明代替内置版平台验收。

## 八、插件 MCP 配置与 Agent 自配置：合理性及可行性（2026-10-23）

用户已明确要求补齐该能力；以下保留源码核查与功能分析依据。功能方向已确认，具体实现以已确认的[技术方案](技术方案.md)为准，尚未进入实现。

### 8.1 现有能力及问题根因

| 已有位置 | 核查事实 |
| --- | --- |
| [插件详情](../../../../../apps/desktop/src/features/settings/SettingsDialog/PluginSettingsPage.tsx) | 包内 MCP 当前只展示名称；可以保存插件清单声明的参数、上传原生配置文件，但没有按 MCP 进入详情及编辑环境变量的入口 |
| [MCP 设置编辑器](../../../../../apps/desktop/src/features/settings/SettingsDialog/McpSettingsPage/ServerEditor.tsx)与[协议](../../../../../crates/assistant-protocol/src/mcp.rs) | 独立 MCP 已有详情、环境变量／请求头、Keep／Replace／Remove、安全回读和测试连接，可复用已有交互与值修改语义；当前快照缺少插件／内置的配置归属信息 |
| [Runtime MCP 管理](../../../../../crates/assistant-runtime/src/runtime/mcp.rs) | 配置查询来自独立 MCP 配置源，插件候选在刷新时另行合并；普通 mutation 显式拒绝修改插件声明的 MCP key。不是只放开前端编辑就能实现 |
| [插件能力装配](../../../../../apps/runtime-host/src/plugins/capabilities.rs) | 已将描述符 env／headers 中的 `${config.<name>}` 绑定到用户插件参数，并注入保留目录变量；缺少任意单个插件 MCP 的用户环境变量修改入口。已支持的声明参数绑定不应重复存储成另一份环境变量值 |
| Agent 调用边界 | MCP 发现／调用与管理配置是两种权限；现有 HTTP 管理命令和用户 `/mcp` 控制入口不等于模型已有配置工具。文件／Shell 可修改部分用户文件，但不保证身份校验、并发保护和生效结果，不能作为正式自配置的唯一实现 |
| 既有 DeepSeek 参考实现 | 只读取插件原生 `deepseek-search.json`，明确不回退环境 Key；若内置版采用环境变量入口，必须同步适配内置 MCP 的读取方式，不能只增加无效表单 |

合理性：插件包拥有默认实现与启动定义，用户拥有服务实例所需的配置。允许查看和配置服务，不应要求改写、重打包或重新安装插件。内置资源也应遵守同样的用户配置规则，避免出现第三套管理路径。

### 8.2 推荐的详情与配置边界

- 在插件详情的 MCP 列表提供可点击入口，MCP 设置中也能按来源进入同一详情。未启用、缺参数或未连接的服务仍应可配置，不能只列已进入运行目录的成功连接。
- 展示服务所属插件／内置来源、启动定义摘要、配置状态、连接及工具状态；命令、参数和平台资源路径由包定义，插件／内置来源下默认只读。可编辑当前用户的环境变量；HTTP MCP 对应请求头语义，不能把本地进程 env 当作远端服务的配置。
- 用户覆盖只作用于目标服务的运行环境，保留其他变量；不改包内 `server.json`，不写系统环境，不覆盖 Host 注入的资源／配置／数据目录。已有声明参数到 env 的绑定应在详情中指向同一字段来源，不允许参数页与 MCP 页分别保存两份值。
- 使用可校验的来源及服务身份定位；插件升级时包摘要作为来源一致性检查，不能把用户配置绑死到每次变化的包摘要。重名不凭显示名称猜测，用户域和远端目标沿现有连接上下文核验。
- 配置值保持单一权威来源，展示时按需计算生效环境。包默认值、用户替换／移除与保留变量的合并规则须明确，不能仅靠删除覆盖值就模糊地表示“恢复默认”或“移除包默认变量”。实际存储位置及最小必要类型由技术方案确定，不提前建新表或独立配置管理服务。
- 保存、刷新和测试分别返回实际结果。保存后标识待刷新；目标刷新复用现有连接退役和调用取消机制，不重放工具或重新运行 Run。测试连接只验证进程／协议／目录，真实搜索请求另行执行，不把工具目录成功当作 Key 或搜索 API 已验证。

### 8.3 Agent 自配置建议

- 提供 Runtime 拥有的有限管理能力：查询目标服务及配置键／是否已设置、修改被允许的用户配置、刷新目标并查询结果。UI 与 Agent 调用同一业务实现，不复制配置逻辑，不向模型开放任意 HTTP Command 或原生管理凭据。
- 管理能力不能依赖被配置的 MCP 自己提供；否则服务缺 Key 或连接失效时无法自助配置，修改／重连还可能中断管理调用。工具的准确数量、名称与装配归属在技术方案确定。
- 管理修改沿现有用户意图、权限模式及审批机制执行；用户已明确要求配置时在其授权范围内完成，不机械增加逐字段确认。网页／MCP 输出只是资料，不构成修改配置的授权。内置不自动获得高于用户插件的管理权限。
- 普通配置可由 Agent 直接填写；已有敏感值只返回字段名和已设置状态，支持保持／替换／移除，不回读给模型。首期建议敏感 Key 从现有用户详情页输入，Agent 检查状态后继续配置和验证；若还要在对话中由模型传入 Key，须单独解决用户消息／模型请求／工具参数及可靠历史的暴露边界，不能仅凭 UI 掩码或 `Debug` 脱敏宣称密钥不会进入历史。用户已在对话提供的 Key 也不能被描述为从未进入会话。
- 配置能力只限定管理入口的授权和脱敏，不把现有文件／Shell 描述成无法访问这些目录的操作系统沙盒。
- 接纳用户域和目标身份、冻结来源及配置版本后提交；并发更新使用现有版本校验，过期则返回冲突，不覆盖其他窗口或 Agent 的新值。工具结果区分已保存、待刷新、刷新失败和实际调用成功。

### 8.4 DeepSeek 及升级建议

内置 DeepSeek 搜索优先采用详情页管理的服务级环境变量作为统一 Key 入口，具体变量命名及支持项在技术方案核对；内置实现直接读取该入口，不同时维护一个隐藏的原生文件 Key 副本。独立通用辅助插件既有原生配置契约保持原归属，不未经确认引入双读回退或迁移已有用户凭据。

对首批内置 DeepSeek，没有要求用户另行维护原生 JSON 的必要。Key 与需要用户定制的连接参数通过同一 MCP 详情／Agent 管理入口保存并在启动时注入；实现默认值留在代码或资源定义，查询条数等单次请求选项优先沿工具参数传递，不为这些值自动增加文件配置。Host 为环境变量持久化所采用的物理格式与用户必须创建 `deepseek-search.json` 是不同问题，不因取消后者而另造数据库或同步文件。

已有通用原生配置文件接口是无格式约束的受管文件存储，不专指 JSON；它在 v0.28.0 插件契约中用于插件自有配置的按需导入，可承载原格式文件。已核对的首批内置能力没有这项依赖；它不再作为默认用户配置路径，也不为假想需求扩展。仅对实际依赖文件格式的插件保留既有适配能力，是否收起空文件上传入口在交互方案确定。现有独立通用辅助确实依赖文件读取，不能在本轮分析中直接删除接口、文件或迁移凭据；若以后撤销该契约，需单独核对实际依赖及兼容影响。

同一个参数只有一个事实源：不让用户同时填写环境变量与原生 JSON，不生成一份含 Key 的 JSON 作为环境配置副本，不增加 file/env 双读回退。确需第三方文件配置时，文件为该配置的权威来源，而非另一套自动镜像。随 Host 更新只替换内置实现和默认资源，保持用户环境变量、凭据及配置意图；新版本缺少／变更字段时报告实际兼容问题，不静默清空或扩大作用范围。

### 8.5 结论与验证重点

方案合理且可行，已有表单、秘密值修改语义、插件用户参数、目录注入、版本检查及 MCP 生命周期可复用；实际新增重点是插件／内置服务的配置来源与详情投影、受管用户覆盖、Agent 管理入口，以及内置 DeepSeek 配置读取适配。不能归结为只改 UI，也不需要重建 MCP 连接或执行框架。

功能验收补充：未连接／缺配置也能进入详情；两入口同值回读；用户及服务隔离；同名和升级保留；秘密不回显；并发冲突不覆盖；Agent 修改及目标刷新；目标配置失败不影响其他服务；重连不重放工具；工具目录握手与真实搜索分别验证。F06 只补操作指引，不能用 Skill 文本代替本次缺少的正式管理能力。


## 同名 MCP 规则调整（2026-10-23 用户确认）

多个来源声明相同 MCP 标识时，按用户添加 > 普通插件 > 内置资源选用已启用配置；同级插件按标识升序固定选择。其他来源保留原配置和管理入口，展示优先使用的来源，不因同名报错或锁定。停用高优先级条目后刷新，选用下一份启用配置。真正的配置错误及并发修改保护保持，详见技术方案。
