## 三、职责、状态和依赖

保持 `Desktop -> assistant-protocol <- Runtime Host -> assistant-runtime`。本方案不新增公共进程管理协议、监听端口、业务状态机或业务数据库结构。

- Desktop 原生层持有本机进程操作及窗口操作；WebView 发送意图并展示原生结果。
- `RuntimeBootstrapCoordinator` 继续持有 Runtime Home、当前启动来源和 `lifecycle_gate`。停止、重启、应用内更新共用现有串行入口。
- 原生进程适配放在 Desktop 的 `runtime_bootstrap` 私有模块内，向协调器提供识别、结束和等待能力；Windows 复用已有平台模块，macOS 按实际 FFI 边界增加私有平台文件。安装执行模式调用同一实现，不复制停止逻辑，不增加 crate 或公共 trait。
- Host 继续拥有业务准入、持久化、可靠提交及中断恢复。Desktop 不读写业务数据库，不自行修补执行状态。
- 操作中只短暂保留目标的 PID、启动时间、所有者和原生句柄，以及必要的文件身份。它们是操作系统事实的快照，不建立新的登记表或长期缓存。
- discovery 和 Runtime Home 锁沿用现有格式，不添加第二份 PID 文件；发现文件仅作定位线索，不能单独授权结束进程。

### 3.1 串行与取消

沿用 `updater permit -> lifecycle_gate` 的顺序；原生确认与 WebView 确认进入同一协调入口，禁止重复获取同一 gate。
确认、下载和来源校验阶段不停止进程；发出结束后等待本次操作收束，重复点击复用现有忙碌状态，不启动第二个停止／重启任务。

`lifecycle_gate` 只约束当前 Desktop，不能宣称跨进程互斥。多个客户端及外部启动造成的竞争由 Runtime Home 实例锁和目标身份复核处理：发现换代就返回冲突，不追着结束后继实例。

## 四、本机目标识别与原生结束

### 4.1 目标证明

普通停止／重启以明确的本机 Runtime Home 为范围；远端连接不参与进程识别。复用私有文件的大小、owner、普通文件及符号链接／reparse 校验。

识别时组合以下事实，而不是依赖其中一个值：

1. 当前操作指定的 Runtime Home 及其 `run/runtime.lock` 的实际文件身份。
2. 操作系统报告的锁／文件占用进程；有 discovery 时交叉核对其 PID、实例和同一安全文件的修改时间。进程创建时间晚于发现记录时拒绝结束，防止陈旧 PID 复用；实际锁占用者不一致时也拒绝结束。
3. 进程归属当前系统用户，读取并固定真实映像全路径；不能凭文件名、路径前缀或命令行子串结束进程。有安全发现记录时，以 PID、创建时间和目标锁归属证明原实例；旧路径可因安装器移动映像而改变，不再访问旧文件或把旧路径不变作为结束条件。无发现记录时，实际映像必须与当前已知随包来源的规范化全路径一致，否则拒绝结束。
4. 固定进程启动时间；Windows 同时持有该进程的内核句柄。发出结束前复核目标和发现信息未发生不相容变化。

**不以旧文件摘要作为结束条件**。安装后的磁盘文件可能已经更新，运行中映像仍属于旧版本；停止核对进程和安装／Runtime Home 归属，不能要求旧进程对应的磁盘字节仍存在。

2026-10-20 实施核查确认 macOS 映像路径会随文件移动而变化，故发现记录的旧路径仅为来源线索；修改时间来自既有安全文件句柄，不增加持久化字段。读取前后复核文件长度／时间，发出结束前再次固定实际映像和原生身份。保存配置后专用重启若失去原实例记录而锁仍被占用，返回实例变化，不能结束未知启动中实例。

启动中尚无 discovery 时，优先根据操作系统报告的 Runtime Home 锁占用定位；本次 Desktop 正在启动的子进程也可使用已取得的原生身份。不得把任意同名进程视为该 Home 的 Host。

### 4.2 Windows

建议使用已有 `windows-sys` 的 Win32 API，补齐所需 feature，不引入 PowerShell、WMI 脚本或未公开的 NT 结构解析：

- 在短期 Restart Manager session 中批量登记确定的文件路径，查询占用者。普通管理登记目标 `runtime.lock`；安装交接登记待替换的 Desktop／Host 映像文件。
- `RmGetList` 的结果提供 PID 和创建时间；用 `OpenProcess` 获取最小所需的查询、终止和同步权限，核对 Token SID、`QueryFullProcessImageNameW` 和 `GetProcessTimes`。
- 通过同一个 `OwnedHandle` 调用 `TerminateProcess`，再有界等待进程对象变为已退出。不能在核对之后重新按 PID 打开另一个目标。
- Restart Manager 仅用于资源归属查询，不对其整张返回列表执行 `RmShutdown`。混入扫描器、安装器或其他文件占用者时不得一并结束。
- 查询失败、结果不完整、锁仍被占用却无可证明目标时返回错误；不能把空查询结果直接当作“Host 已停”。

微软定义 Restart Manager 的资源可按文件或具体进程登记，进程标识包含 PID 与创建时间；查询返回使用所登记资源的应用和服务。
依据：[RmRegisterResources](https://learn.microsoft.com/en-us/windows/win32/api/restartmanager/nf-restartmanager-rmregisterresources)、[RmGetList](https://learn.microsoft.com/en-us/windows/win32/api/restartmanager/nf-restartmanager-rmgetlist)、[RM_UNIQUE_PROCESS](https://learn.microsoft.com/en-us/windows/win32/api/restartmanager/ns-restartmanager-rm_unique_process)。

`TerminateProcess` 返回仅表示已发起结束，必须等待进程对象；不能把 API 成功等同于文件占用已释放。
依据：[TerminateProcess](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-terminateprocess)。

**实施前的定向可行性门禁**：在隔离 Windows Host 上确认 Restart Manager 能识别本项目实际打开方式下的 `runtime.lock`，覆盖早期布局升级／配置准备阶段尚未发布 discovery 的情况。若不能，先修订目标证明方案并确认，不偷偷改成按名称结束，也不先加持久 PID 登记兜底。

### 4.3 macOS

建议使用系统 `libproc`／`sysctl` 查询当前用户候选进程的真实映像、启动时间和文件描述符；以目标锁的设备号／inode 核对实际持有者，避免仅解析 `ps` 文本。
平台适配封装必要的 `proc_pidinfo`、`proc_pidfdinfo`、`proc_pidpath` 查询，并有界分配和重试；接口结构以目标 SDK 头文件为准。
Apple 的公开 XNU 头文件包含进程及文件描述符查询结构，见 [proc_info.h](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/proc_info.h)。

直接强制停止通过现有 `nix` 依赖补齐 signal feature 后发送 `SIGKILL`，发信号前再次核对 PID、启动时间、用户及目标锁归属。
macOS 此路径没有 Windows 进程句柄式的原子“核对身份并终止”；必须如实保留查询到发信号之间的竞争限制，不能宣称两平台保证完全等价。发现退出／换代时停止本次操作，不向重新解析到的新 PID 补发信号；实机必须覆盖目标先退出和 PID 陈旧的路径。

### 4.4 完成条件、无目标与失败

- 目标进程已退出，且目标 Runtime Home 实例锁确实可取得，才将本机停止标记为成功；有后继实例持锁时返回实例变化。
- 新装或已停止、锁不存在／可取得且无目标占用时返回已停止，不为停止操作创建 Home 或启动 Host。
- 只读识别无法证明归属、权限不足、进程退出超时或锁仍占用，均保留 Desktop 和可重试入口；不自动扩大为全系统扫描清理。
- 强制结束后可能残留 discovery；沿现有启动和原子发布路径处理，不凭文件残留认定进程存活，也不先删文件伪造已停止。
- 沿用 30 秒停止等待预算和现有错误码，如 `RuntimeStopFailed`、`DiscoveryInvalid`、`ConfigurationConflict`；必要原因放入安全文案，不增加平行错误体系。
- 本次只结束已证明的 Host。两平台正式进程包装的隔离探针均确认强制退出父进程后独立 Shell／MCP 仍可能存活；PTY 前台进程／Windows 终端 Job 随 owner 结束。故仅保证目标 Host 退出和锁释放，不承诺全部子进程退出；不按进程树批量结束无关或已脱离的进程。完整业务恢复仍沿 Runtime 的可靠历史，不重放工具副作用。

## 五、重启、配置保存和应用内更新

### 5.1 普通重启

1. 在 gate 内解析当前 Desktop 随包 Host 的绝对路径，复用 `runtime_source` 校验真实文件、摘要稳定性和 `--build-info-json`；只校验当前来源，不查询旧 Host 的版本作为停止准入。
2. 当前随包文件不可用时提前返回，保留仍运行的旧 Host；独立“停止”入口不受此来源检查影响。
3. 固定目标身份并原生结束，核验进程与锁释放。
4. 再核对当前来源未被替换，以原 Runtime Home 启动当前 Host；使用既有等待、迁移诊断和业务准入。
5. 新 Host 未就绪时明确显示“原 Runtime 已停止，新 Runtime 启动失败／尚未就绪”；不再次结束不属于本次启动的后继实例，也不反复启动第二个 Host。

正式版始终使用当前安装旁的随包 Host；保留 Dev 已有的显式来源覆盖与身份隔离，不把日常开发来源规则扩大成正式版自动择源。
这里改变的是本机重启来源，不改变普通业务版本、企业协议或存储兼容下限。

### 5.2 保存配置后重启

复用 `ExpectedHostConfiguration` 的实例及 revision 事实，保留保存后核对，不重置模式或中心配置。
若能够回读原实例，继续核对已保存 revision；若管理接口不可用，不能谎称配置已核对成功，也不能让普通版本无关停止入口失效。
此时专用“应用已保存配置并重启”返回配置结果待核对，用户仍可明确使用普通停止／重启；该操作只承诺重启目标，配置结果在新 Host 就绪后回读。无自动补写或自动降级配置。

### 5.3 应用内更新

继续复用候选签名／摘要、下载完成后的核对、更新 permit、`DesktopHandoff`、现有 `pending-update.json` 及新实例恢复入口。
修改 handoff 的停止实现，使其不依赖旧 Host 健康、业务兼容或旧摘要；有已确认实例时仍检查实例没有换代。

只换停止实现，不顺手重做更新源发现和认证。Host HTTP 不可用时未必能发现企业更新源，不能将“原生可停止”写成“离线也可发现和下载更新”；此时直接安装包路径负责覆盖安装。
M2 将 `DesktopHandoff` 的停止与手动安装换代统一接入 M0 原生停止，删除 `upgrade.rs` 的旧版 HTTP 停止分支及专用等待；只在原安装路径的当前有效文件已替换、且不构成已知软件降级时提示显式换代。普通系统重开与来源未变化时不停止 Host。安装恢复重新核验当前随包来源、版本及运行摘要。Desktop 入口识别本机待换代后先保留显式交接按钮，不继续读取旧 Host 的企业协议形成遮挡；用户点击后完成交接，再进入新版登录与业务准入。

### 5.4 登录前、旧 Host 与企业中心协议不兼容时的更新（2026-10-20 核查）

用户要求确认 macOS 登录页能否在本机 Host 企业协议过期时完成更新。当前源码已经区分业务登录和桌面更新：

1. 登录入口初始化 `DesktopUpdateStore` 并调用 `prepare_desktop_update`；本机更新定位使用 `desktop_update_target -> inspect_target`，不要求普通业务连接先成功。
2. Host 的 `/capabilities`、`/desktop-update-context` 在业务登录／版本准入之外开放。更新上下文从生效的本机配置提供中心地址与 Host 协议声明，不以旧 Host 成功登录中心为前提。
3. 原生更新器直接请求中心公开 `/api/info` 与 `/api/desktop-updates/...`，发现、清单复核、文件下载不带企业账号 Cookie／Token；Host 协议范围与中心有效范围不相交时进入“需要更新后继续使用”。网络错误和非法声明不被当作明确不兼容。
4. 本机更新选择并验签的是随包新版 Host 的企业协议能力，不用旧 Host 的协议范围排除可修复问题的新包。中心必须已发布该平台可下载、能兼容当前中心的新版本。
5. 用户在登录入口确认后下载、校验、停止旧本机 Host、安装 Desktop 与随包 Host、重启并在同一 Home 恢复；当前 macOS 目标为 arm64，更新文件仍为 `.app.tar.gz`。

因此，**仅旧 Host 与中心的企业协议不兼容，并不必然阻断登录前更新**。M2 已将安装停止接入原生能力，并验证来源绑定后旧 Host 暂停无响应时仍能结束；不再依赖旧管理 HTTP。极旧 Host 没有更新上下文、尚未发布 HTTP 或无法识别中心地址时，现有更新源发现仍可能失败；不能把修复原生停止写成已消除所有旧版本的更新依赖。

M2 已使用本版隔离签名候选完成 GUI 下载、原位替换、重启、原 Home 接续与新版 Host 正式登录；DMG 覆盖后的显式交接及实际工作区登录也已通过。候选为 ad-hoc 应用签名，不据此声明 Developer ID／公证发布验证通过。

F01 的应用内更新回归必须包含：已配置企业中心且完全未登录；旧 Host 协议与中心不相交；新版随包 Host 协议相交；登录入口完成更新后原 Home／配置保留、运行中的 Desktop／Host 均为预期新版本，能够重新登录。另覆盖无兼容包、包撤回／断网、不可写安装位置和原生停止失败；不能只确认更新按钮出现或下载完成。

## 六、退出、偏好与窗口唤起

### 6.1 默认与确认

- Rust 的 `DesktopCloseBehavior` 默认及前端默认改为 `quit_desktop`，配置读取使用现有缺失字段默认规则；已有有效值直接沿用。不增加“升级时判断是否手选”的逻辑。
- 登录后的偏好按账号分区保存；关闭行为同时在同一写锁和原子替换中同步到原生关闭所读取的设备入口，避免界面已选退出而关闭按钮／Command + W 仍按旧值隐藏。其他设备布局和账号分区保持原值，不新增配置文件或修改初始化规则。
- `DesktopLifecycleStore` 每次发起退出时初始化“同时停止后台服务”为选中；取消时清理当次选择。原生托盘确认默认按钮同步为“退出并停止”。
- 托盘、应用菜单、系统退出、原生关闭及自绘关闭都走现有生命周期协调器；保留 Host、取消、失败结果在所有入口一致。
- 连接中／断开／版本不匹配时允许进入原生停止／重启，不能再以 `Connected` 作为唯一使能条件。操作忙碌仍由原生协调器拒绝重复请求。
- 确认只用简短的会话中断说明表达本机影响；2026-10-20 用户要求去掉复杂说明和任务计数，因此删除退出确认专用的局部计数传递，不新增全局任务计数。原生三个选择为退出并停止／保留后台并退出／取消；WebView 沿用默认勾选停止的既有结构。
- 正在查看远端时，停止仍只操作本机 Home，不使用远端当前活动数冒充本机总数。

### 6.2 系统入口

macOS 在 `app.run` 处理 `RunEvent::Reopen`，复用 `get_window("main")`、显示、取消最小化及聚焦；不重建 child WebView。
隐藏窗口保留 Dock 图标，Dock／Finder 都能进入同一显示路径；真正退出应用后图标由系统正常移除。

Windows 保留当前单实例插件、正式／Dev 标识隔离及初始化 StartupGuard；插件回调仍只调用已有显示函数，不发起第二轮 Host bootstrap。
只在安装版复现单实例问题后做对应修复，覆盖快速重复启动、初始化中转交、隐藏、最小化、崩溃后重开和升级交接。

## 七、直接安装交接

### 7.1 Windows：保留 MSI，使用新包内置的安装前动作

建议在当前 `wix/main.wxs` 增加 **Binary 表中的 EXE Custom Action**，使用本次新包内的 Desktop 可执行文件，以专用内部参数进入安装准备模式。
该分支在创建 Tauri／WebView、单实例插件和普通 Host bootstrap 之前分流，完成后退出；无需依赖旧版应用已支持新参数，也不在安装目录增加第二个长期程序。
微软支持从 Binary 临时流运行 EXE，返回非零即安装失败，见 [Custom Action Type 2](https://learn.microsoft.com/en-us/windows/win32/msi/custom-action-type-2)。

安装准备模式只有确定的安装路径及操作类型，不接受任意 PID／任意命令。安装路径由 MSI 的本次目标和既有产品注册事实提供，核对为本产品安装；不信任仅有相同 exe 文件名的目录。
保持当前 per-user 身份，不提权结束其他用户进程，不读取、打印或传递 bootstrap Token。

执行顺序：

1. 用户开始安装，安装说明已告知会中断相关本机工作；仅打开安装器不执行停止。静默／被动安装同样在 execute sequence 执行，应用内更新沿原确认。
2. 在 `InstallValidate` 检查文件占用之前执行同步安装准备；此时也必须早于当前 `RemoveExistingProducts`／文件替换。使用 `Return="check"`，不采用忽略错误或异步返回。
3. 获取既有 Windows 启动 mutex，与正在初始化的 Desktop 串行；只识别待替换安装中的当前用户 Desktop／Host。先结束旧 Desktop 并确认退出，再处理 Host，移除旧客户端继续启动 Host 的来源。
4. 利用本次安装映像文件的实际占用查询确定 Host，即使其 Home 自定义或尚未发布 discovery 也不依赖旧 HTTP。普通管理的 Home 约束与安装的映像归属约束分别明确，安装不结束其他安装提供的共享 Host。
5. 等待已核实目标真实退出，复查安装映像占用；已知目标仍存活或存在不能处理的占用时失败，不以安排重启代替本 Feature 的成功条件。
6. 关闭准备模式进程，再进入 MSI 原有替换流程；安装完成后的启动沿安装选项。该模式不创建运行目录、不启动 Host，不迁移用户数据。

准备动作仅持有启动 mutex 到自身结束，**不宣称它覆盖整个 MSI 事务**。停止旧 Desktop 已消除其自动拉起竞争；用户随后手动启动造成的新占用仍需 MSI 文件占用机制阻止／重试，且安装后回读确认不能遗留旧映像。
MSI 不能把重启后才替换文件视为本次成功；安装提交前须核验目标没有重新占用待替换映像，失败进入安装回滚／明确重试。具体检查动作及其在 MSI 执行脚本中的位置须通过定向安装原型确认。MSI 使用 Restart Manager 的行为受系统策略影响，不能以默认启用推断无需安装版验证，依据 [System Reboots](https://learn.microsoft.com/en-us/windows/win32/msi/system-reboots)。

当前准备动作不是可回滚的文件写入：安装停止旧进程后取消／失败，MSI 可以回滚安装文件，但不能恢复被中断的执行任务。
只在确认实际安装内容有效后允许用户重新启动，不在 rollback custom action 中自动启动旧版本或修改数据库。

实施时先验证：新 Desktop 在临时 EXE 路径下不依赖安装目录／WebView 初始化即可执行准备；WiX 的实际生成顺序确实在占用检查和旧包移除之前；升级卸载旧包时不重复执行新包停止动作。

M3 实施使用现有 Desktop 的两个内部模式：安装准备在 `InstallValidate` 前同步执行，安装脚本提交前只读复查占用。二者均先于窗口／插件初始化分流；准备阶段持有原 StartupGuard，按当前用户安装注册事实核对路径，再先退出 Desktop、重新查询并结束其 Host。私有 Windows 适配复用 OwnedHandle 和进程身份校验，安装映像查询补充只读 ToolHelp 快照，以启动时的固定产品映像名及已注册安装目录共同核对，允许目录内旧文件重命名，避免仅按当前文件持有者查询漏掉旧进程；结束前复核捕获的实际映像、创建时间、owner 和同一内核句柄。最终同时核对进程、Restart Manager 占用，以及本安装目录的系统延迟重命名记录，不把重启后才替换计为成功；随包捕获及搜索工具只复查占用，不扩展强制结束对象。注册表只读复用依赖图已有 winreg 安全封装，不新增注册表 FFI 或长期 helper。该实现在 M3 已通过两版 Windows x64 MSI 的实际时序与安装验证。随包 runtime-tools 采用显式 HKCU KeyPath 与卸载目录，组件 GUID 按最终应用标识稳定生成，使 Dev 与正式安装保持独立；不关闭 ICE 校验。
若 Tauri 模板／链接依赖不能承载，先修订方案，不能悄悄增加长期 helper 或换安装器。

### 7.2 macOS：保留 DMG，分别处理手动安装与应用内更新（已确认）

2026-10-20 用户确认保留 `.app + .dmg`，不改为 PKG 或加入自定义安装应用；应用内更新沿用签名 `.app.tar.gz` 和现有企业中心发布布局，不新增安装签名证书或提权服务。

手动覆盖安装继续由 Finder 复制。在实际运行新版 Desktop 后，复用本机目标识别及原生停止能力，在业务准入前处理需要换代的旧 Host；停止后使用当前随包来源和原 Runtime Home 启动。
如果普通 bootstrap 返回版本不兼容，也必须保留这一原生处理入口，不要求先建立业务连接；无需换代的正常重开只恢复已有窗口。
尚未实际运行新版二进制时不能宣称交接完成，旧 Desktop 仍存活的 Finder／Dock／LaunchServices 组合必须实机验证。

应用内更新复用第五节流程：登录前发现并绑定中心更新源，校验包内新版 Host 与中心相容，用户确认后下载与验签，原生停止本机目标，再由现有 Tauri 更新器替换和重启。
更新恢复继续使用原有 `pending-update.json`，核对安装版本和原 Home，不能沿旧摘要或其他安装路径重新启动旧 Host。
旧 Host 管理 HTTP 不可用时，只要有效更新来源已经取得，停止阶段使用本版原生能力完成；有效来源尚未取得时准确返回来源不可用，不伪造可下载更新。

当前 `writable_installation` 要求应用 bundle 及父目录可写。沿用不可写安装位置的明确错误，不借本次 DMG 保留决策增加新的授权服务；正常用户可写安装位置必须完成更新闭环。
本节与第五节 5.4 的验收同时覆盖完全未登录、旧 Host 企业协议不相交、兼容新版包、原 Home 接续和新版重新登录。

未采用 PKG 的理由：额外引入 Installer 签名、公证及目录 owner／权限策略，可能影响当前更新预检；同时需要处理已有应用位置及发布元数据。Finder 拖拽没有安装前执行入口，见 [Apple 分发说明](https://developer.apple.com/documentation/xcode/packaging-mac-software-for-distribution)，本版不承诺复制前自动停止。

## 八、FFI、权限与兼容边界

本方案需要超出现有获准函数范围的 Desktop 局部 FFI。现有 Windows 存活检查、owner SID 和 StartupGuard 的例外不能自动扩展。
2026-10-20 用户按本方案推进，以下有限边界随方案确认；已同步批准范围至 [Rust 编程规范](../../../../specs/Rust编程规范.md)及 [Desktop 模块约束](../../../../modules/desktop.md)：

- Windows：资源占用查询、进程映像／创建时间／Token owner 查询、`TerminateProcess` 及有界等待。`OwnedHandle` 独占关闭进程／Token，Restart Manager session 必须收束；不改 DACL，不启用调试权限，不使用任意进程注入。
- macOS：只读进程和 FD 身份查询；缓冲区长度、SDK 布局及 PID 有效性逐项校验。信号优先使用现有依赖的安全封装。
- 只在相应私有平台函数局部允许 unsafe，保留 package 级 deny 和其他 workspace 的 forbid；不放宽整个模块或 workspace。
- 同步阻塞查询／等待在受控阻塞任务执行，不阻塞 WebView 主线程；StartupGuard 仍在获取线程释放，不跨异步迁移。

授权范围仍来自用户已确认的停止／安装意图；原生能力不开放为任意 PID 操作。普通业务连接继续认证与版本准入，远端停止未纳入。
本 Feature 不预期业务 DTO、数据库 DDL、存储兼容下限或既有偏好值迁移；实际发现新契约需求时先修订方案，不以本机管理为由绕过存储保护。

## 十、取舍与下一步

- 不通过降低普通版本准入、扩展逐版本 HTTP 停止桥或调大超时来解决原生结束问题。
- 不使用全局 `taskkill /IM`、`pkill` 或 WiX 按文件名配置的 `CloseApplication` 批量结束；该元素的 Target 本身是 exe 文件名，无法表达本方案的目标归属，见 [WiX CloseApplication](https://docs.firegiant.com/wix3/xsd/util/closeapplication/)。
- 不增加新的 PID 持久化事实、管理服务、生命周期状态机或通用进程管理 crate。操作系统资源归属、现有 Home 锁及协调器足以表达目标；可行性验证失败时先回到方案，不叠加兜底层。
- 不将“Host 进程已结束”夸大为“所有工具子进程已清理”，不将“安装命令成功”夸大为“没有遗留旧运行映像”。
- 本方案与 macOS DMG 取舍及[开发计划](开发计划.md)已确认，M0、M1 已获用户确认，当前 M2 已于 2026-10-21 获用户“继续”确认，M3 已获用户确认，F01 已完成；Windows 实际锁占用查询已通过前置核实，macOS 登录前更新及 DMG 接续已在 M2 实机验证并获用户确认；Windows x64 MSI 及更新恢复已完成验证，M3 已获用户确认，F01 已完成。

## 九、2026-10-21 追加：PKG 安装前交接

本节对应功能设计第九节及开发计划 M4；下列为补充实施方案，不声明已接入正式产品。

1. **分发装配**：当前 `release-macos.mjs` 生成 App／DMG 与独立 `.app.tar.gz` 更新包。后续复用已签名 App 与资源，经 `pkgbuild`／`productbuild` 制作系统安装包，再封装 DMG；`.app.tar.gz` 的更新与登录前恢复契约保留。应用与 DMG 使用 Application 签名，PKG 使用 Installer 签名，不用前者替代后者。
2. **执行入口**：现有 `runtime_bootstrap/installation.rs` 是 Windows 专有入口，不能直接启用即声称 macOS 支持。新增 macOS 安装准备适配时保持私有平台边界，在新包程序的普通 GUI／bootstrap 前分流，复用原生查询、停止、等待及现有实例事实；不建临时管理 HTTP 服务。包脚本同步调用新包内签名程序并原码返回，打印脱敏阶段及系统错误。
3. **权限与范围**：正式 PKG 目标是 `/Applications/EZ Assistant.app`，系统授权与旧 App／Runtime 的实际用户身份分离。原生 Home 校验依赖有效用户，不能在 root 上下文直接放宽 owner 校验；需先核对本次安装目标与实际用户，再在对应用户身份下管理其目标。目标路径、用户、进程创建时间／映像与实例锁共同确定范围，不接受任意 PID、Home 或同名清理。未知或其他用户占用保守失败。具体原生身份适配在 M4 开始时核查，若系统安装时序不能满足则先修订方案。
4. **交接与失败**：先 Desktop 后 Host，确认原进程身份退出，再在同一预算内等待原实例锁释放；不能以一次非阻塞锁失败立即判断停止失败，也不能无限等待或忽略锁失败。运行中被替换、实例变化及新的占用按真实结果拒绝。停止后的安装失败不会恢复活动任务；不声称 PKG 文件回滚等于业务回滚。安装脚本不以 root 启动 GUI／Host，正常用户启动新版后按现有规则接续 Home。
5. **本次原型根因**：隔离探针将“进程身份已不可查询”视为完整退出，随后仅尝试一次 `flock`；实际进程清理期间锁仍可短暂占用，返回暂时不可用并产生非零退出。已复现相同失败、补全错误诊断并修正为有界等待；持续占用仍阻断。正式 `native_stop.rs` 已在 `process.exited()` 后继续按同一预算等锁释放，因此不为该原型缺陷重复改写生产停止逻辑。
6. **验收边界**：当前用户目录探针验证不能替代正式 App、管理员授权、真实安装恢复及正式签名验证。生产集成、包时序、其他用户隔离与登录前旧协议更新分别实测，完成后再更新手册及关闭追加范围。

M4 实施核查补充：系统 PKG 的 root 文件归属会被现有更新器的可写检查拒绝，因此安装完成后仅将固定 App 交给经系统核实、与准备阶段一致的用户；不递归修改系统目录或 Home，不跟随符号链接。准备阶段先在该用户身份检查安装父目录可写，不满足既有自更新条件时在停止前拒绝。root 借助系统用户切换工具运行新包维护入口，清空继承环境，不执行用户 shell／profile；临时签名 helper 在父进程等待结束后回收，不新增常驻权限进程。PKG 后置脚本失败时文件可能已经安装，必须如实说明并允许重新安装，不能套用 MSI 的回滚承诺。

M4 真实安装修正：App 主程序的签名绑定 bundle 元数据，直接复制为包脚本辅助程序会被系统签名检查终止。打包阶段将维护副本以 Application 证书单独签名并校验，再交由 PKG 同步执行；原 App 保持原签名。
