# F04 技术方案：本地压缩链路统一

## 一、方案信息

- 所属版本：`v0.32.1`，版本整体保持 **开发中**。
- 状态：**技术方案已确认**。2026-10-22 用户明确“可以，按这个技术方案继续编制 F04 开发计划”；[开发计划](开发计划.md)已确认，M0 已于 2026-10-23 获用户确认，M1 已于 2026-10-23 获用户确认，M2 实现与验证完成，待用户确认及 F04 验收。[功能设计](功能设计.md)此前已确认。

## 三、请求归一与候选生成

### 3.1 唯一归一位置

无工具规则放在 `RollingSummarySameModel::compact` 内、分区得到非空 head 后、调用 `collect_model_turn` 前。优先直接调整现有几处赋值，不新增公开请求工厂、策略类型或模型装饰器。

| 字段 | 摘要请求规则 |
| --- | --- |
| ModelService／模型身份 | 使用调用方冻结并按现有装配链构造的同模型服务；复用已有资源准备、超时、取消和有限重试装饰器 |
| System Prompt | 保留冻结值，不重渲染、不为摘要选择另一个提示词或模型 |
| conversation | 保留经过一致性验证的完整有效请求及顺序，在末尾追加已有 request-only 摘要指令；不删除历史调用／结果、图片、reasoning 或受保留边界保护的内容 |
| tools | 清空本次摘要请求的可用定义；不修改正常请求及其后续工具快照 |
| tool_choice | 内部统一为 `None`；两个 Adapter 在空工具下均省略线上字段 |
| generation | 仅将 `max_output_tokens` 设为现有摘要预算 4096，其余冻结参数不变 |
| reasoning／provider_options | 沿用已解析配置及现有校验，不注入工具参数或为 400 尝试不同组合 |
| 摘要范围／指令 | 沿用当前 `ContextLayout`、完整轮次优先与轮内回收规则、最近轮次保留策略及摘要指令，不另写一份手动模板 |

`CompactionInput.normal_request` 仍表示未压缩时的真实请求。清空工具只作用于被移交／复制到策略中的摘要请求，自动成功后的正常推理仍沿原 Agent 工具能力继续。删除 `UnsupportedToolSuppression` 不代表放宽正常生成时的工具能力校验；异常摘要响应中出现 ToolCall 仍必须拒绝。

### 3.2 手动与自动输入如何对齐

自动继续消费 Core 在 `CompactionRequired` 中交出的精确正常请求；手动由 `compile_session_compactor` 使用当前已解析的模型、generation、reasoning、Provider Options、Session Prompt 与 Journal 准备输入。请求准备与模型装配继续位于 [`runtime/model.rs`](../../../../../crates/assistant-runtime/src/runtime/model.rs)，不在策略中读取配置、目录或凭据。

保留 `validate_live_request` 的真实语义：Journal 必须是正常请求 conversation 的有序精确子序列，额外消息只允许已有 Runtime 隐藏 request-only context。不能为了表面参数一致，把自动请求粗暴替换成裸 Journal，丢掉正在生效的隐藏上下文或资源投影。相同**有效上下文**和配置才要求相同业务请求；不同上下文、owner 专属资源映射及生成标识不作字节相等承诺。

配置 reload 不改变已经冻结的本地压缩调用。提交前重查 owner／上下文身份，但不因无关配置更新废弃活动 Run 的冻结配置。保留现有手动模型接纳校验及原生模式额外 `ensure_current` 边界，不扩展成全局模型发布锁。

### 3.3 共用候选管线

继续只使用 `RuntimeContextCompactor::compact_once`：

1. 完整产品历史的执行投影必须与源 Journal 一致；精确正常请求必须通过 `validate_live_request`。
2. 现有布局分区并发起同模型摘要；无可回收 head 直接返回 NoOp，不调用模型。
3. 摘要必须完整结束、含非空文本且没有工具调用；保留现有结构、配对、后缀与严格缩小校验。
4. 从可靠产品历史恢复 Pinned Memory 的程序化净变化，按现有 MCP／Shell 环境规则补齐上下文，再次验证结构及实际压缩效果。
5. 沿现有合并校验确认候选可接回完整产品历史。临时摘要指令和 request-only 内容不会因此写回原始历史。

本地投影继续尊重最近可靠原生截断边界，不展开边界前历史或转换原生密文。摘要策略、Pinned Memory 和 Store 各自已有的验证边界保留，不把存储权威验证删成只有一次前端／内存检查。

手动把共享 NoOp 映射为 `CompactSessionOutcome::NoOp`；自动仍按既有无法回收／恢复上限结束，不能把 NoOp 当成已经解除 overflow。该映射发生在调用方，不分叉摘要算法。

## 四、可靠提交与 owner 适配

### 4.1 收敛方式

在现有 `context_compaction` 模块提取一个私有异步提交函数，接收既有 `ContextReplacement`、源 generation、取消令牌，以及就近传入的同步核验、投影安装和故障收口回调。调用方先取得对应 mutation 屏障，再调用它。回调不执行异步 I/O，也不持状态 MutexGuard 跨 await。

该函数集中执行：**取消检查 → 核验冻结来源与 owner → Store `replace_context` → 核对实际提交边界 → 安装投影**。原 Store 错误进入同一内部映射；成功返回现有 `ContextReplacementResult`，不新增提交结果或恢复实体。投影安装后才允许发布成功事实和恢复后续生成。

父 Run 与手动还共用一个私有 Session 投影安装函数，集中维护 Journal、`persisted_message_count`、产品 `message_count` 与 `body_generation`。child 沿已有 `replace_conversation` 及 registry 安装回调处理其独立状态。不同目标的锁、身份和结束通知由薄适配外壳保留，不让共享函数反向调用 Runtime 接纳、Agent 启动或 UI。

| 入口 | 目标与提交前核验 | 屏障及完成方式 |
| --- | --- | --- |
| 手动 Session | `IdleSession`；源 generation／快照、无 pending、相同 active_compaction／operation_id，沿当前健康／空闲接纳规则 | 接纳期 operation → model binding → Session mutation；模型等待释放这些门禁。提交重新取得 Session mutation；返回独立命令结果与原幂等记录 |
| 父 Run 自动 | `Run`；相同活动 run_id、active_compaction、源 generation／快照、无 pending、取消状态 | 模型等待不持 mutation；提交取得 Session mutation；安装后继续原 Run，保留原 attempt、起点及剩余预算 |
| child 自动 | `ChildTask`；完整 session_id／child_task_id／parent_run_id 所有权、活动执行、源 generation／快照、无 pending、取消状态 | 模型等待不持 parent／child mutation；提交严格 parent → child → Store；安装 child Journal、generation、产品计数及 registry 后继续该 child |

父与 child 当前提交核验主要比较 Journal；本次补齐冻结 generation 与 owner 核验，防止内容相同却已换代的 ABA 情况。Store 沿既有契约再次核对目标活动身份与机制；共享内核要求返回的 source generation 与冻结值一致，并只使用 Store 实际返回的 result generation，不能假定 `source + 1`。

状态同步使用既有观察协调器的短同步边界。Session／child 的内存安装、registry 与 `ConversationCommitted` 发布保持同一可观察顺序；不在 Store／模型等待期间占用观察锁。既有 `SessionCompactionGuard` 负责主会话成对 Started／Finished，child 保留自身事件归属，不伪造 Session 手动操作。

### 4.2 失败与提交临界点

| 时点 | 处理 |
| --- | --- |
| 请求／候选失败、提交前取消或来源变动 | 不调用 Store、不安装候选、不发布成功；手动按当前操作记录结束，自动返回原执行受控终态 |
| Store 返回错误 | 保留 `StoreError` 来源及种类；冲突按上下文过期解释，其余按存储失败解释。不在 Runtime 自动再次生成或提交，文件与指针的恢复由 F02 Store 原流程决定 |
| Store 已成功，收到较晚取消 | 已完成的可靠提交不能被改写成“未发生”；先完成相应投影与提交事实，再按原执行取消语义停止继续。手动已提交结果返回 Compacted |
| Store 已成功，投影／registry 安装失败或返回边界不符 | 保留已提交事实，不重新调用模型、不把幂等成功覆盖成 Interrupted、不发布虚假成功。Session 使用现有 `mark_faulted` 隔离，并撤销易失 active_run 占用、取消原执行及其 child；Store 未完成控制不改写。child 没有独立 fault 标记，沿所属 Session 的故障边界隔离并中止继续，不新增 child 故障状态 |

最后一种错误需要在既有 `RuntimeCompactionError::Projection` 中保留“提交前／提交后”和已返回的提交结果等必要上下文，避免调用方将提交后错误走入普通失败结算。它是现有错误的内部数据扩充，不新增持久状态或对外恢复协议。

特别是 child：当前 `controller` 在普通错误后仍会执行终态落盘；提交后投影失败必须直接转入已有持久化故障收口，禁止使用旧 Journal／旧 registry generation 再追加终态、返回正常委派结果或唤醒父级继续。父 Run／手动同样不得从陈旧投影再次写入。可靠历史和控制记录保留给现有重新加载／重启恢复路径，不在故障回调内尝试连续补救。该分支是提交重构的必测项。

手动任务仍由 Runtime 自持有，HTTP future 丢失不取消已接纳操作。共享提交内核不能被传输层断开中途丢弃；沿现有 shutdown 等待与 Store 恢复边界处理进程中断。不引入新的 detached 任务或超时重提交循环。

### 4.3 文件历史、幂等与用量

沿用 F02 的文件唯一历史、可靠换代、回执恢复及手动 `prepare_session_compaction`／`finish_session_compaction`。`IdleSession` 的幂等结果随原子替换记录；同一 operation 回读已提交结果时不得再次发模型请求。自动不新增 operation 表或普通输入，重启不恢复执行或自动重做摘要。

有效 Journal 的消息数与完整产品历史物理消息数分开：前者供 `persisted_message_count`，产品计数必须使用 `ContextReplacementResult.product_message_count`。摘要 usage、被替换 head 的 `compacted_usage` 与窗口 adjustment 沿既有消息事实计算；不在父 Run 或 SQL 增加汇总副本，不因结果回读再次记账。不扩大为新建失败调用计费账本。

## 五、错误、重试与展示

### 5.1 统一映射且不新增协议字段

在 `context_compaction` 为现有 `RuntimeCompactionError` 增加共用的安全协议映射方法，手动命令、父 Run 结算与 child 结算均从它取得错误。保留 `ModelError`、`StoreError` 及投影阶段，不再用 `Err(_)` 或 `.map_err(|_| ...)` 抹去可诊断来源。

| 来源 | 对外解释 |
| --- | --- |
| 模型明确拒绝 | `context_compaction_failed`，消息带稳定类别；`Provider`／`Unavailable` 已有 HTTP status 时带状态码 |
| 连接、超时、流中断等 | 同一压缩错误码，消息带现有模型／transport kind；不猜测模型错误对象没有保存的 HTTP 状态 |
| 空摘要、意外 ToolCall、校验不通过、无缩减 | 同一压缩错误码，使用固定安全原因，不附摘要或原文 |
| 来源／owner／generation 冲突 | `snapshot_stale`；说明压缩来源已变化，不自动覆盖 |
| Store 不可用 | `storage_unavailable`；错误来源留在内部链，不公开路径、SQL 或底层原始文本 |
| 投影／内部不变量失败 | `internal`；提交后失败必须明确已提交但当前状态不可继续使用 |
| 取消／NoOp | 通过现有专用结果或执行取消终态处理，不作为普通压缩错误 |

共用映射产生既有 [`RuntimeErrorInfo { code, message }`](../../../../../crates/assistant-protocol/src/error.rs)，例如安全消息可表达 `context compaction failed (kind=provider, status=400)`；触发 `reason` 仅作附加诊断，不能替代失败来源。无需新增错误码、DTO 字段或 Provider 专属应用契约。不直接格式化整个错误链，不带凭据、prompt、文件内容或未脱敏上游正文。

`RuntimeError::ContextCompactionFailed` 委托此映射；保留其现有 boxed source，在协议转换时识别内部 `RuntimeCompactionError` 并调用共用映射，其他未知来源保持固定安全错误，不强转或输出原文。手动不再单独把模型来源映成泛化 `model_execution_failed`。普通生成的模型失败映射保持原样。自动恢复次数耗尽仍使用原有上限终态，不伪造没有发生过的模型错误。

### 5.2 消费者与兼容

- 手动：HTTP command 失败仍返回 `RuntimeErrorInfo`；[`SessionManagementController`](../../../../../apps/desktop/src/stores/SessionManagementController.ts) 经现有 `displayError` 展示安全 message，成功／NoOp／取消继续使用已有结果。
- 父 Run／child：共用错误进入现有 Run／ChildTask 终态、文件历史与快照，Desktop／Web 按现有错误展示读取；验证展示不丢失类别及状态码，不增加新的处理过程行。
- [`SessionCompactionFinishedOutcome::Failed`](../../../../../crates/assistant-protocol/src/event.rs) 只有 code，目前用于压缩状态收口，不承担详细原因；继续保留该形状。详细原因来自手动命令错误或原执行终态，不为重复展示增加事件字段。
- TypeScript Client 继续消费原 command／快照／事件形状。序列化结构、TS 生成协议和公开命令均不变；安全 message 的内容调整不作为字符串协议供客户端解析。

不保证已经断开的手动命令连接能在重连后获得新的持久详细错误档案；沿现有操作结果和快照恢复，不为此新增错误历史服务。

### 5.3 调用与重试边界

仅使用已有 `agent-model` 有限建立重试及既有同模型装配参数，不包第二层摘要重试。普通 HTTP 400 仍有界失败；限流／暂不可用／传输错误是否重试服从已有类别、阶段和策略。流已经产生输出后不扩大成无条件重发。失败不改参数重试整个 Run、不重放历史工具，也不切到原生 compact。

## 六、原生机制与兼容边界

原生 `/responses/compact` 继续由 `RuntimeContextCompactor` 按冻结 `context_management_mode` 独立分派。无工具请求归一仅位于本地 Rolling Summary，因此不改原生请求、opaque ProviderState、可靠边界或切换规则。共享提交函数可以承载两机制已有的可靠替换动作，但不能从提交失败推导跨机制回退，不能重新选择机制。

F04 不新增数据库表、迁移、会话文件格式或配置项，不改变 `RuntimeStore` 公开端口，也不提高软件版本、应用兼容下限或企业协议范围。继续采用当前 `0.32.1` 及既有兼容声明。移除的是内部工具抑制门禁及已无意义的 crate 错误分支，需检查 workspace 消费者并在实现时一起编译；不保留未发布中间态兼容层。

`agent-context` 约束中原先“为缓存复用保留工具定义”的规则按已确认功能方向修订；缓存前缀复用可能下降，不能为了恢复缓存命中重新带入工具。正常生成、标题和其他模型任务不受摘要参数变更影响。

## 七、实施影响与验证设计

| 范围 | 预期改动 |
| --- | --- |
| agent-context | 本地请求归一、废弃错误分支清理、共享策略和能力边界回归 |
| assistant-runtime | 共用提交／Session 投影、安全错误映射、父／child／手动适配；补 generation 核验及提交后故障收口 |

验证复用已有 compaction、Store 故障注入及 HTTP 测试，不单独创建测试宿主或验证报告：
