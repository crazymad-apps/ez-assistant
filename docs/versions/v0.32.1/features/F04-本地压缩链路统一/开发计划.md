## 四、各里程碑范围与完成判定

### M0 摘要请求归一

**范围与实施顺序**：

- 核对本地摘要唯一调用点及 `UnsupportedToolSuppression` 的 workspace 消费者，先补能复现自动请求保留工具定义的行为测试。
- 在 `RollingSummarySameModel::compact` 的非空 head 分支、模型调用前清空当前请求 tools，保留内部 `ToolChoice::None` 与现有输出预算；删除已无意义的工具抑制能力门禁、错误分支和旧测试断言。
- 保留精确正常请求、request-only 隐藏上下文、冻结参数与现有布局。复用 `compact_once` 的完整历史投影、Pinned Memory、环境恢复及复验；不另建手动请求模板或改写原生请求。
- 在现有 Chat／Responses 测试中核对最终线上 JSON。两编码器已支持空工具省略字段，生产代码仅在实际测试证明缺口时调整。

**验证与判定**：

- 覆盖同一有效上下文、同配置的手动／父／child 请求：线上无 tools／tool_choice，系统提示词、历史、reasoning、Provider Options 和摘要预算按同一规则保留。生成标识及 owner 资源映射差异不作字节等同要求。
- 模型不支持显式工具选择时无工具摘要仍可调用；正常生成工具定义及后续调用保持。NoOp 不调用模型，ToolCall 摘要响应仍拒绝；多轮／轮内、图片、配对、保留后缀和原生截断边界回归保持。
- 入口复用 [`rolling.rs`](../../../../../crates/agent-context/src/rolling.rs)、[Runtime compaction 测试](../../../../../crates/assistant-runtime/src/runtime/tests/compaction.rs)及两协议已有测试；实际 HTTP 请求体使用本地模拟服务捕获，不能仅断言内部 `ModelRequest`。
- 先执行 `cargo test -p agent-context` 与 Adapter 的相关编码／HTTP 测试，再执行直接受影响 Runtime 请求对照。移除公共 crate 错误分支后核对 workspace 消费者编译；对本里程碑改动执行格式及相关包严格静态检查。

**完成判定**：A01、A02 请求问题修正，A03／A06 的候选边界回归通过；没有为兼容扩大重试或删除历史事实。请求统一已经可用，不依赖 M1 才消除原兼容缺口。完成后汇报并等待 M0 确认。

### M1 可靠提交与错误收口

**范围与实施顺序**：

- 按技术方案在现有 `context_compaction` 提取私有提交内核与 Session 投影安装函数；三入口接入现有 `Run`／`ChildTask`／`IdleSession` 目标。保留触发外壳、手动托管／操作幂等及自动原执行继续。
- 冻结并复核源 generation、快照、无 pending、活动 owner 和取消状态。手动沿 operation → model binding → Session 接纳；提交沿 Session 或 parent → child → Store。模型等待不持 mutation／观察锁，状态 MutexGuard 不跨 await。
- 将 Store 返回的实际 generation 与产品消息数作为唯一安装依据；内存投影与观察事件按同一短同步边界发布，成功发布前不恢复后续生成。
- 完整区分提交前失败、Store 失败、提交成功后的取消与投影／registry 失败。扩充现有内部错误携带必要阶段／来源；提交后故障隔离所属 Session，禁止陈旧 Journal 再写终态或父级正常继续，不抹除已提交幂等事实、不自动补救重提。
- 共用安全协议映射，父／child 不再吞掉原错误，手动使用同一原因口径；通过现有 `RuntimeErrorInfo` 保留类别及可得 HTTP 状态。沿原 code 区分来源过期、存储不可用和内部失败，不增加 DTO 字段或解析 message 的业务逻辑。
- 核对 Desktop／Web、TS Client 的现有错误消费；只有可复现的展示缺口才改展示代码。同步 Runtime 模块的提交／错误约束。

**验证与判定**：

- 在原 Runtime 测试中覆盖三目标成功提交、手动 NoOp／取消／同 operation 回读、自动身份和剩余预算不变；手动不创建 Run、不消费暂存输入。断言模型调用与可靠替换次数，不以事件数量代替存储事实。
- 使用可控模型和 Store 故障注入，覆盖内容相同但 generation 已变、owner 变化、上下文变动、模型冻结与无关 reload、并发接纳、提交前取消、提交成功后取消、Store 冲突及失败。
- 分别注入 Session 投影、child Journal 和 child registry 安装失败：文件已提交时不重复调用模型／提交、不把手动成功记录改成 Interrupted、不从旧 generation 追加终态、不发布成功或正常继续；其他 Session 不受模型等待阻塞。
- 手动／父／child 的普通 400、transport／timeout、无效候选得到同口径安全错误；重试次数沿既有策略，不泄露 prompt、凭据、正文或原始上游响应。现有原生 compact 成功／失败及事件收口同步回归。
- 入口为 `cargo test -p assistant-runtime compaction`，结合现有故障／委派测试的实际名称执行必要补充；错误类型与分支改动执行 Runtime 相关严格静态检查。确有前端修改时运行对应展示单元测试及构建。

**完成判定**：A04—A08 的 Runtime 规则通过，特别是提交后故障路径已经可验证，不能留到 M2 再设计；没有新的权威状态、协议形状或存储端口。完成后汇报并等待 M1 确认。

### M2 正式 Host 联合验证与 Feature 验收准备

**范围与实施顺序**：

- 在新建隔离 Runtime Home 中扩展现有[正式 Host 压缩集成测试](../../../../../apps/runtime-host/tests/v0_27_context_compaction.rs)，使用实际 Host／文件 Store／HTTP command 路径验证手动、父 Run 与 child；复用本地模型服务，不新建验证宿主。
- 核对摘要提交前后与重启回读的完整文件历史、有效上下文、owner、generation、物理计数和 usage。覆盖同一手动 operation 回读、换代恢复与原执行合法继续；重启不自动续跑、重做摘要或重放历史工具。
- 在 Host HTTP 边界覆盖两协议无工具请求、普通 400／瞬态错误及取消的组合；查询实际接口，核对错误类别和状态码贯通命令、Run／child 快照及历史。
- 沿现有 Desktop／Web 压缩入口及终态展示验证成功、NoOp、取消和失败；未修改 TS Client 也核对其原 command／事件结构可消费。不增加提前处理过程或另造手动 Run。
- 回归原生 compact 的独立调用与可靠截断边界、本地切换后不展开旧窗口、无跨机制回退；确认没有 SQL 历史副本、配置／文件格式变更或软件兼容声明变更。
- 真实兼容场景使用已有授权及可用配置补对照；不将读取已有记录当成新验证，不把本地模拟服务通过写成真实上游通过。无法执行时记录具体限制并交由用户验收判断，不擅自扩大授权或发布范围。

**验证与判定**：

- 先运行 `cargo test -p assistant-runtime-host --test v0_27_context_compaction` 及直接相关存储／原生回归，再汇总受影响包的测试、格式和严格静态检查；需要验证跨 crate 错误分支消费者时执行 workspace 编译检查。仅当新失败、消费者影响或未闭合风险需要时扩大到 workspace 测试，已通过且未受新改动影响的检查不机械重跑。
- 无前端代码改动时复用现有契约／展示回归完成核对，不为文档或 Rust 内部重构执行全量 UI 构建。存在展示改动则运行对应前端测试与 `npm run build`。
- 存储、数据库及接口分开核验；本地 SQLite 写入只涉及已核实的新建隔离场景，涉及表和精确结果按实际代码确认，不预先凭表名声称无需检查。结束后收尾本次启动的 Host／模拟服务，不停止日常进程。

**完成判定**：A01—A09 均有实际结论，必需的本地可控场景通过；真实上游与未测平台限制明确列入验收。无新机制越界、无历史副作用重放；M2 实现验证状态改为待确认，提请用户确认末里程碑及 Feature 验收。测试包按用户后续要求提供，不把未打包／未安装写成实机通过。

实施中若发现必须新增协议／存储格式、修改原生语义或重开已完成 Feature，停止扩大改动，说明与已确认方案的偏差后重新确认。已有无关工作树或检查失败单独报告，不覆盖用户改动，也不将未执行的验证记为通过。
