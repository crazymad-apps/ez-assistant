# F02 技术方案：分支历史与会话存储修正

## 一、方案信息与结论

- 所属版本：`v0.32.1`；版本整体 **开发中**，F02 **已完成，2026-10-22 用户按实际交付范围验收收口**。
- 2026-10-21 用户确认 [功能设计](功能设计.md)，要求继续技术方案。方案编制阶段仅核查源码、Cargo 依赖和文档；后续实施与验证结论见开发计划，不将设计基线表当作当前实现状态。
- 用户后续明确：**轮次、Step、消息归属等历史结构只存会话文件，数据库不再保存可重建副本**。本次按该指令撤回保留 `run_message_refs` 历史投影的取舍；2026-10-21 用户以“可以，按调整后的技术方案继续编制 F02 开发计划”确认本方案。[开发计划](开发计划.md)已获确认，用户授权连续推进至 M4，做好测试后提请验收；M0—M4 及验收前修正已完成，2026-10-22 用户验收收口；完成范围与限制见[开发计划](开发计划.md#feature-验收结论2026-10-22)。
- 上位边界：[总体设计](../../总体设计.md)、[Agent 系统技术架构](../../../../modules/agent-system.md)、[Rust 架构设计规范](../../../../specs/Rust架构设计规范.md)。本方案不重开 F01，不改变 F04 的压缩算法。

采用以下方案：

1. 演进现有每 owner 的 JSONL：同一个文件同时保存规范消息与可靠的历史归属，不增加旁路历史库或第二份正文。Core 继续只接收解码后的规范消息。
2. 复用 staged append 和 generation 切换，贯通“无新增消息但状态变化”的提交；SQLite 只保存会话目录元数据、必要执行控制及独立记账／搜索用途的数据；不保存 Run／Step 历史或消息归属副本，删除 `run_message_refs`。该规则同时适用于本地执行与继承历史。
3. 历史身份由会话／owner 与原 ID 共同定位。真实执行 ID 继续沿现有全局分配及约束，不为复制历史重建全部执行表的主键。
4. 保留已使用的 `0.32.1` 无 DDL 登记，演进原迁移账本以容纳同发布版本的追加迁移；明确拒绝同版本旧候选写入新格式，不提升产品版本或借用 `0.32.2`。
5. 复用现有 Session mutation gate 保护本会话可靠提交与读取；观察层用已有全局 sequence 的作用域水位替代“所有事件都使当前快照失效”。前端增加有限读取和 owner 隔离，修正无关会话触发当前详情重读。

## 二、真实实现与依赖核查

### 2.1 实施前已有机制及缺口（设计基线）

`cargo metadata --no-deps --format-version 1` 已确认：`assistant-runtime` 依赖协议、Agent 能力、Serde 和 Tokio，不依赖 SQLite；`assistant-runtime-host` 已依赖 `rusqlite`、`sha2`、`tempfile` 等所需基础设施；协议仅依赖轻量数据／生成工具。本方案不新增 crate、第三方依赖或系统 FFI。

### 2.2 文件独占历史结构的硬边界

输入队列必须临时持久化在 SQLite，不能只放内存或因移除 SQL 历史结构而迁出数据库；该要求适用于尚未消费的输入及其排队控制（2026-10-22 用户再次明确）。暂停期间保留同一队列原件；重启由 SQL 中的 queued 事实恢复为需手动恢复执行，沿用既有 Runtime 暂停／恢复机制，不额外保存可派生的暂停副本。

| 事实 | 存储位置与保留边界 |
| --- | --- |
| 已提交消息、消息与轮次／Step 关联、attempt 历史、可靠起止／终态、历史控制结果和展示反馈 | **仅存当前 generation 的会话历史文件**。查询时解码，允许当前进程内有界缓存；不建立 SQLite 表、JSON 列、物化视图或磁盘旁路副本 |
| 输入队列（待消费正文、顺序、优先级及恢复控制）、接纳与幂等 key、活动 Run／child、pending 工具交换、恢复回执 | SQLite 临时保存待消费输入及推进未完成工作所必需的控制事实；消费结果可靠写入会话文件后才释放已消费载荷，完成后释放活动控制行，不能积累成历史 Run／child 台账 |
| 实际调用记账与会话 Token 汇总 | 沿用独立 `model_request_records`／`session_usage` 的 request 去重和数值汇总，不保存消息→Run→Step 关系；调用的历史归属从文件读取，继承用量不计入目标新增费用 |
| 当前工作计划、Goal、用户配置、Workspace、会话列表摘要、审批和运行句柄 | 现有领域所有者；保留当前可操作状态和目录元数据，不以这些表恢复产品历史结构 |
| 附件 blob、工具图片与物理资源 | 现有资源存储与上传控制；已用于历史的稳定资源绑定随文件保存，详情不靠关联表拼回历史 |
| 全文搜索与 Recall | 既有文本检索索引只保存检索所需内容／词项和完整 owner、generation、message 定位，不保存轮次、Step、attempt、终态、历史 child 树或时间线。命中后的历史结构和时间从文件读取 |

本规则不是“文件为主、数据库副本可重建”，而是**数据库没有这份历史结构副本**。删除历史关联表之后，读取、分页、AroundRun、详情、Fork、重试资格核对和重启显示仍必须成立。SQL 执行控制不可用时不能据此自动重建并执行历史任务。

`runs`／`child_tasks` 仅承载尚未完成的执行控制：接纳、运行、取消和当前恢复所需的 ID／状态等。可靠终态写入文件后，在同一完成事务中释放相应活动行；`finished_at_ms`、历史错误／终态和父子历史关系不长期留在控制表。已结束 child 的父工具交换若尚未闭合，所需结果只在既有未完成恢复回执中临时保留，父交换完成后释放，不保留为可查询的历史副本。

Skill／MCP 的 SQL 选择只属于待消费 Input。首次 User 提交或启动前终结先将选择与 User 归属写入同一可靠帧，再于原完成事务删除该 Input 的选择行并清空 `skill_activation_json`；失败保留原队列和回执，不能影响其他待消费输入。模型激活随工具交换写入所属 owner 文件，不再插入 SQL；Fork 继承选择同样只写目标文件。会话装配按文件事实补齐已消费 Input 的内存选择，物化重试和 Fork 校验也回读文件，均不回写 SQL。旧源先完整迁出已提交选择再清理历史部分，保留真实 queued 选择；目标准入拒绝历史选择或已消费激活 JSON 重新出现。

Volatile Store 遵循同一选择生命周期：队列保留用户选择，消费提交冻结历史后释放选择控制和 Input 内的激活载荷；模型激活及 Fork 继承直接写所属历史。读取合并主会话／child 的历史与尚未消费的选择，已消费 Input 只读补齐技能，不能重新安装选择控制；去重按完整历史 owner 核对。

父交换复用 `pending_tool_starts` 的 started 行，临时 `delegated_child_json` 仅保存 child ID 及其现有文件 generation；终态、父绑定和最终正文仍从该 child 文件核对，不复制到回执。child 的可靠结算事务提交此位置，回滚预检不发布它；父交换同帧提交 ToolMessage 和只读 child 描述，再随原 receipt 删除临时位置。位置用于定位既有 generation，不另立计数或执行身份；文件、父 Run／call 或代次不符时阻止恢复，不从 SQL 终态兜底。旧源仅在已备份的升级上下文按原语义闭合，正常恢复不使用该旧读取路径。

有该父回执的 child 在自身可靠结算事务中显式删除原 child 回执，再释放终态控制，不等待父交换结束。父交换未闭合期间，阅读、标题／Recall、删除影响和图片引用收集可使用该临时位置，但每次仍核对 child 文件的完整 owner、generation、父 Run／call 和可靠终态，不把位置或返回值保存成第二份历史目录。父帧提交后由文件目录承接；位置损坏时明确失败，图片扫描停止完整资源清理。控制删除失败会回滚本次位置、状态和回执变更，重启继续完成同一 child 帧。

没有父工具回执的 Store child 不能借终态控制行充当历史目录。其终结复用原 `child_body_appends`，并在主文件暂存一个零消息的 child 目录帧；两个回执通过原 child operation ID 关联，核对同一 Session、child、generation、终态及时间后，先同步两个文件，再于同一 SQL 事务应用效果、精确删除两份回执并释放控制。主文件只增加阅读描述，不伪造父 ToolMessage 或可见消息。任一回执均可进入同一恢复入口；尾部冲突、依赖不符或完成事务失败时，两份回执及原控制都保留，普通读取不发布半份结果。准备目录时只保留 child 的阅读事实，不在两 owner 提交期间额外保留另一份 child 正文。

正常父帧中的 child 描述也只从当前工具回执所指文件冻结；普通消息追加不扫描终态 child 控制来推断关联。旧库完整迁出与用户裁尾使用不同的保留边界：旧 SQL 已知的 owner 内 child 目录即使缺少父工具正文也要保留原关系，独立 child 文件必须一并校验并换代；不据此补造父消息、归属或开始时间。

重试仍复用原 Input：原请求幂等接纳事实可以保留，但首次／最近 Run、下一个 attempt、失败原因和重试资格从当前 owner 文件取得，不为重试保留所有终态 Run 行。提交新 retry 时持 Session gate，核对文件中的最后一次本地 attempt／终态、Input 归属和现有控制行，再原子创建新的实际 attempt；继承记录不可重试。已提交控制指令及 Skill／MCP 的历史结果同样只从文件读取，幂等回执不能保存一份供历史展示的完整结果。

## 三、历史文件与 Store 契约

### 3.1 文件布局与编码

保留现有路径：主会话 `data/sessions/<session>/conversation.<generation>.jsonl`；child 位于同会话的 `child-tasks/<child>/body-<generation>.jsonl`。不额外保存正文副本或常驻 `history.jsonl`。

文件第一行为 Host 私有格式头，固定标识 `ez_assistant_history`、格式 `1`、完整 owner 和当前 generation；新建空会话也有格式头。格式号只用于解码协议识别及拒绝未知格式，不是每次写入自增的 revision。
之后每行是一个可靠提交帧，包含：

- 既有 `operation_id`，用于 staged append 补齐及核对重复结果；不另造提交 ID。
- 本批规范 `messages`，以及这些消息与原 Run／Input、attempt、Step 的关联；未知值明确为空。关联按消息 ID 保存，不能用 ID 排序代替正文顺序。
- 本次真正变化的可靠历史事实：Run 起止／终态、已提交控制结果、Skill／MCP 展示事实、消息反馈或 child 历史描述。字段来自现有领域 DTO 的必要子集，不直接序列化 UI 快照。
- 阅读所需的资源绑定：被消息实际引用的附件 ID、blob 身份、原名、大小／媒体类型和受管相对位置，以及 child 描述所指向的固定正文／图片资源。首次引用随消息提交，Fork／换代检查点只带保留范围内的绑定；不能只保存旧绝对路径然后声称数据库引用可重建。尚未用于历史的上传仍属于既有附件准入状态。
- 本批事实的 `inherited` 标记。普通调用为 false，Fork 继承为 true；正文中的 Provider usage 不因标记而改写，实际调用汇总只接纳本地真实发生的调用。

帧是业务原子提交的物理单位，允许 `messages=[]` 且存在状态事实；全空帧拒绝。父工具调用与完整结果仍在同帧闭合，pending 内容和逐 token 增量不进入文件。开始／终态各记录一次必要变化，不为诊断输出持续落盘。

generation 替换写入“格式头 + 有界消息批次 + 历史检查点帧”；检查点是现有事实在新文件中的归一化编码，不新建快照生命周期。大历史分批写入，不把全会话塞成一个 JSON 行。常规帧沿现有消息／工具输出限制有界处理；迁移分批大小使用同一编码上限，单条既有超大消息按有界流式读取处理，不能因拆帧损坏工具配对。

offset LRU 扩展为“帧字节位置 + 帧内消息位置”，分别维护物理消息与可见消息 ordinal；元数据帧、格式头和隐藏消息不增加可见总数。文件长度／generation 失效规则保持，不缓存第二份完整正文。消息定位、分页、Recall、工具详情及 Markdown 导出共用该解码结果。

### 3.2 RuntimeStore 端口的最小演进

- 扩展现有 Conversation window／raw window 及 LoadedSession 返回值，直接从文件提供相关可靠历史归属；移除 `load_run_message_refs` 及所有从 SQL 反查历史消息轮次／Step 的路径。
- Fork 沿现有输入的源 Session、generation 和规范前缀，在同一次 Store 操作内读取并裁切可靠历史，写入目标文件；返回后使用既有只读历史接口查询，不再为同一事实增加一份 Fork DTO。只读 child 正文及资源由同一操作准备，不携带可执行 Run／Input。历史事实使用独立的不可执行数据表示：现有 `StoredRun` 必须有实际 Input 和执行状态，直接复用会使恢复代码误接纳继承记录；该表示仅归 `assistant-runtime::storage` 的历史边界，Host 和 Volatile Store 共用。
- 优先扩展现有 append、settle、rewrite 和 Fork 操作；不建立第二个 HistoryRepository trait。Host 私有帧编解码不进入公开协议；内存 Store 实现同样的历史裁切和执行隔离语义，不模拟磁盘文件。
- Runtime 的 `SessionState.runs` 和 child 活动 Registry 仅保存真实执行。历史归属以只读投影参与产品查询，不加入取消、queue、Goal 或副作用恢复路径。
- 文件已有可靠终态时，Run 查询、会话视图、幂等返回与重复取消共用该终态，不让进程内旧状态、正文、错误或结束时间覆盖文件。工具列表从完整产品历史按原 Assistant／call ID 配对，不能从裁剪后的模型 Journal 重建；参数沿现有安全投影。当前进程只可按已知 Step／call ID／工具名补充同一次调用的易失 stdout／stderr，重启后留空，不把 ToolResult 文本伪造成输出流。未 prepare 的旧进程活动控制仍可显示已有 interrupted 诊断，首次执行准备才可靠结算，该诊断不得覆盖文件终态。相关只读投影不重入调用方持有的 Session mutation gate。
- child 列表、详情及重复取消同样以自身文件中的可靠终态为准，内存控制只补充活动观察或已明确不可读的诊断。尚未开始的 accepted child 可只有格式头，不能为读取成功而补造历史；已存在目录绑定却缺失自身事实仍须报错。继承目录不能被同 ID 的控制覆盖，也不能通过取消入口恢复为执行。Volatile Store 在正常 child 提交时冻结同样的描述与消息归属，结算后实际移除控制，正文读取和清理不依赖终态执行对象。
- 现有 `AcceptedInput` 直接区分真实未完成控制与终态只读结果；幂等接纳、物化重试和按 key 查询固定返回原 Input；尚未领取时没有 Run，领取后返回原首次 Run。终态从当前 owner 文件返回 `StoredInputHistory`／`StoredRunHistory`，不还原 `StoredRun` 或 `RunRecord`；只有非重复的新接纳能进入执行 lane。物化比较按稳定消息位置读取原 User 一条，不解码其他排队载荷或吞掉坏文件。
- 最小接纳身份中的原始行序与临时队列优先级分开；可靠 Input 历史和只读恢复核对原序，不把消费前的优先级写成历史身份。Volatile 同样在完成后释放完整 Input 控制，读取只构造临时投影，真正的新 retry 才恢复所需控制。清空／重新输入保留的原物化 Input ID 仍对新消息和命令保留，不能因当前代次已无原消息而允许复用、把旧 key 改绑到新输入。
- Volatile 完成命令仅保留最小原接纳身份，结果与正文由独立历史读取，可靠提交后实际释放命令控制；Fork 仅写目标历史。问答控制只保留 pending，回答、取消或执行终结导致失效时在同一独占提交冻结终态并释放控制；EndTurn 回答产生的未消费输入继续留在队列。重新输入仅按本 Session 保留的历史裁切问题，不能依据已释放的 Run 控制清理其他会话的待回答问题。
- 首次物化与 Session key 同事务保存最小原 Input ID，仅用于幂等定位，不保存正文、Run 快照或历史结果。清空／重新输入移除原 Input 后仍保留该身份，原 key 查询及重试返回 `snapshot_stale`，不能改绑到当前最早输入或重新执行。旧库只有在未换代、原首条 Input 与首次 Run 的接纳身份可证明时补齐绑定；其他旧 key 保留未知并明确返回过期，不从排序、相同时间或后续正文猜造。Volatile Store 使用同样的独立身份绑定，删除整个 Session 时一并删除。
- 标题检索复用既有检索页的 `partial`／`failed_owners`，与正文检索合并局部失败，不为短查询省略文件读取失败。Session 标题仍读会话目录元数据，历史 child 标题读文件描述；只有真实未完成 child 补充控制标题。全文检索不可用但仍有可靠标题时保留标题并标记 partial，不创建另一个标题历史索引。
- 删除确认的影响数取文件历史身份与当前未完成 Run／child、上传身份的并集，同一身份只计一次；复用现有位置索引的唯一键，不拼接完整历史事实或重建执行。文件不可读或有未完成尾帧时不签发猜测的数量；确认和真正删除仍沿既有 Runtime 门禁。
- `SessionView.runs`、`ListRuns` 中本会话已发生的真实 Run 从文件投影，活动状态由当前控制记录补充；读出的历史值不安装为可执行 `RunRecord`。`GetRun` 同样先核对所属会话，不以控制表中找不到终态行判为历史丢失。继承轮次只在 Conversation 中按原 ID 展示，不伪造可控制 Input；历史 child 从文件描述和目标目录读取，不能注册为活动 child。

## 四、可靠提交、恢复与索引

### 4.1 沿用既有 staged append

统一顺序如下，整段在单 Store worker 和所属 mutation gate 内完成：

```text
验证 owner / generation / 操作前置条件
→ 回滚预检业务 effect
→ SQLite 保存既有 staged receipt（完整新帧和 effect）
→ 核对文件基长，补齐同一 payload 并 fsync
→ SQLite 单事务应用必要执行 effect、更新目录数量、显式删除 receipt，再释放已完成控制行
→ 更新 Runtime 内存投影并发布事件
```

扩展 `body_appends`：`run_id` 允许为空，仅供没有 Run 的元数据提交；`message_count_delta` 允许零。`child_body_appends` 同样允许零消息的可靠状态提交。这些 receipt 的 payload 仅在跨介质操作未完成期间存在，用于补齐同一个可靠提交；操作完成即删除，不是历史读源或可重建历史索引，也不为查询延长保留期。`message_step` 等用于写帧的临时值随 receipt 释放，不能落到永久消息关联表。保留每 owner 至多一个 pending append 的约束；kind 与 target 必须对应，空 Run 不能执行 Run effect。旧 pending 在转换源固定前按原 payload 和 effect 可靠闭合，不能为删表直接丢弃；原始恢复证据由配套备份保留。

事务内先核对并显式删除提交回执，再释放 Run／child 控制行，防止外键级联提前删掉 receipt 而绕过影响数量校验。父 Run 释放前还须核对没有仍需处理的 child 或 pending；任何失败回滚整个完成事务，不按级联删除代替正常收敛。

所有起止路径都经过该算法，包括首次领取、复用 UserMessage 的 retry、零输出失败／取消、启动前失败及 child 终结。现有直接改 SQLite 的快捷路径不能漏过文件历史。输入队列继续临时保存在 SQLite，包含待消费正文、顺序、优先级、暂停及必要接纳／执行控制；排队期间不迁走、不提前写成会话历史，也不因删除历史表而清掉队列。只有实际提交并形成可靠历史后才将阅读事实写入文件，再释放已消费载荷及不再必要的控制字段；必要幂等接纳事实按本方案保留。2026-10-21 用户再次明确此边界。

控制指令沿现有 generation 替换，写入消息和冻结结果后一次事务完成原 Input；其外部配置／MCP 动作仍按既有语义处理，不因历史写入重试而再次执行。消息反馈只提交到文件元数据帧，移除历史反馈表的普通读写。Skill／MCP 的排队选择仍是执行输入，实际写入消息时将阅读事实带入文件，并释放不再承担排队／恢复作用的记录；不能继续写入已提交的历史 activation／selection 副本。

完成命令的原 `inputs` 行仅保留输入身份、Session、幂等 key、种类／已消费标记及数据库行序号；命令正文、结果、消息 ID、接纳时间、variant、origin 和临时优先级全部置空，不用占位值凑旧约束。队列命令继续保留完整载荷。保留原唯一键是为了让普通消息、控制命令及内部接纳共用同一幂等命名空间，不另建历史表或 key 索引。精确提交与重复接纳先定位原身份，再从文件读取完成值并核对，不能全量解码其他排队命令；缺少对应文件事实时明确失败，不重新执行命令。

消息 Input 的待消费正文在可靠消费时释放，执行中仍保留必要恢复字段。最后一个未完成 Run 可靠终结后，与回执和 Run 控制释放同一事务清空消息 ID、接纳时间、variant、origin、Goal／跨会话／渠道／Shell 字段，只留上述最小身份；另一未完成 attempt 仍引用时暂不释放。字段释放失败回滚整个完成事务。正常历史加载按 Input ID 读取所属文件的一条索引事实，即使 SQL 被重新填入过期字段也不解码为历史；下次准入拒绝这种残留。会话不可读时诊断装配可以省略历史 Input，精确查询仍明确失败，不误判为原身份已经删除。

真正接纳新的 retry 时，从已核对的本地文件事实恢复本次未完成控制所需的 Input 值，与 accepted Run 同事务；不恢复已消费正文或历史选择。结束后再次释放这些临时值。幂等命中、物化查询和普通历史阅读不执行这一步。重新输入先按文件消息位置核对本地 Input，再按最小 SQL 身份取得真实队列行序号，不再按 SQL 的历史消息列寻找裁切点。

释放 SQL 控制不意味着释放可靠文件中的身份。普通输入与控制命令在幂等命中返回后，先以完整 owner／当前 generation 的位置索引检查新 Input、Run（命令无 Run）及消息 ID；消息和命令共用 Input 命名空间，继承身份同样参与检查。实际队列和活动控制仍由原 SQL 唯一约束保护，不另建历史 ID 表，也不扫描其他会话。冲突在接纳及写回执前明确失败；M1 再落实 Runtime 生成 ID 时避开继承历史并重新分配的行为。

重新输入检查整个当前历史，不能借截断尾部复用旧身份；新 retry 只分配新的 Run ID，沿文件事实检查该 ID，原 Input／User 身份按既有重试语义复用。首次物化创建新的独立 owner，依靠既有目录与 Session 原子准入保证其为空；Goal held Input 只是修改真实队列绑定，不生成新身份。

内部代理报告在源回执准备前检查目标身份，并在最终 SQL 接纳前再次检查目标当前文件。源回执只能阻止源 owner 变化，不能假定报告目标在暂存或崩溃期间保持不变。目标出现冲突或不可读时，保留源回执和原控制，不插入报告、不覆盖目标历史，重启仍只尝试闭合原提交。EndTurn 回答的新输入归原 owner，由自己的唯一回执阻止历史变化，不借这项检查读取未完成尾帧。

Fork 的控制结果只写目标文件，不复制已完成命令的 SQL 身份；清空和重新输入分别按现有清理事务、保留文件中的命令身份释放过期 key。命令换代提交失败只在确认旧指针仍权威时删除准备件，提交结果不明时保留可能已发布的新文件。

问答只将未回答的问题保留为 SQL 控制，按 Session 归属，不依赖已结束父 Run 的控制行。回答、取消及 Run 结束造成的失效先可靠写入文件，再在完成事务删除原 pending；正常读取合并文件终态与真实 pending，不从终态 SQL 恢复。EndTurn 回答与下一条输入接纳共用一个零消息回执：文件只冻结回答，最终事务同时释放 pending 并插入新 Input／accepted Run、调整队列顺序。新输入正文及其选择仍临时留在 SQL，实际消费前不产生 User 消息或历史轮次。失败保留原回执、pending 和队列，恢复只闭合同一提交，不重新接受答案或重复调整顺序。

历史重新输入沿用既有正文换代事务：比较源／准备件文件中的 child 目录确定裁切范围，在切换事务中清除对应 owner 的派生检索条目。替换 User 本来就是本次可靠上下文变更；事务取得新 Input 的真实顺序后，将 Input／accepted Run／消息归属补入未发布的准备件并同步回读，再提交指针。它不代表模型已经开始，真实领取仍沿既有开始提交记录；普通待消费队列继续留在 SQL。切换失败保留旧文件及 child，提交结果不明时保留准备件，不能删除可能已发布的新代次；提交后的旧文件清理保持既有 best-effort 语义。

### 4.2 崩溃与错误语义

| 故障位置 | 处理 |
| --- | --- |
| receipt 创建前 | 文件未变，返回失败；不发布事实事件 |
| receipt 已保存、文件未写或只写部分 | 按同一基长／payload 补齐，不能直接忽略半帧或重跑工具 |
| 文件已 fsync、SQLite effect 未完成 | 文件已包含不可撤销的提交意图；保留 receipt，重启完成相同 effect 后才开放该 owner；不能将其当作可自由截掉的尾巴 |
| effect 校验失败、基长不符或帧内容冲突 | 当前 owner fail-closed，保留现场，停止后续写入；不猜测文件／表哪一份正确 |
| SQLite 已提交、进程未更新内存 | 下次从文件恢复只读历史，从未完成控制事实恢复执行门禁；提交后的检索索引／通知失败不报告“业务未发生”并诱发重复执行 |
| 无 receipt 的坏尾行或未知格式 | 报历史不可用，不自动截断；修复必须基于可靠证据及数据操作授权 |

已接受的操作可能在客户端超时后由 Store 完成；取消等待读取不能撤销已持久化迁移或 staged 提交。Store worker 仍为唯一阻塞线程和 Connection owner，保留原有有界队列、背压及 shutdown；不增加每会话线程或不可观察后台修复任务。

### 4.3 新 generation 和重建

Fork、历史重新输入、clear、控制结果及压缩换代均先写完整新文件和必要资源、重新解码核验并 fsync，然后事务 CAS 切换既有 `body_generation`。孤儿新文件不被读取；失败不覆盖旧 generation。选择新 generation 时沿用现有跳过孤儿文件的规则，不假设一定为旧值加一。

- 压缩保留完整产品消息及其原归属；新增摘要／原生边界使用已有系统用途，不给它虚构 Step。有效上下文仍由 `agent-context`／Runtime 当前规则派生。
- 重新输入按现有截断边界删除尾段关联并创建真实新 Input；同步裁切历史元数据及 child 引用，不把继承 Input 当作可重试对象。
- clear 切到只有格式头的空历史，复用现有清理收据；删除沿现有 session staging 回收整目录和引用。
- 重建只生成目标 owner 的进程内历史投影、内存 offset 和既有文本检索索引，**不向 SQLite 重建历史结构**；不得据此生成 `inputs`、活动 `runs`、pending exchange、审批或 Goal。确需全库恢复时仍是独立运维流程。

`run_message_refs` 在迁移核验后删除，普通提交、恢复和修复均不得再创建它或替代表。Run／Step、消息归属和终态直接从文件解码；内存索引随 owner／generation／文件提交失效，重启后按需重建，不落磁盘。独立用量表保留本地真实 request 去重和数值，移除其中仅供历史拼装的 Run 关联；用量重建不能对所有 Assistant usage 无条件 backfill。文件中无法还原的旧辅助调用只从原账本按真实记录迁入，不推算缺失 token。

主会话、child 与手动压缩的 generation 切换只为相对可靠源正文新增的调用记账：复用位置索引核对完整 owner、source generation 和消息 ID，保留消息即使带有 usage 也不借换代补记费用。实际新增的摘要／系统边界在新文件中冻结本地来源，不虚构 Run 或 Step；原正文中归属未知的旧消息不因换代变成本地调用。费用与指针切换共用事务，失败不提前记账。

待完成的旧用量回填只接受文件中明确的非继承本地消息来源；升级源则仅依赖原真实归属关系。继承或缺少证据的旧 Assistant／摘要跳过，独立账本已有记录与数值保留，不能从相同正文、排序或 token 推断缺失请求。正常 request 去重继续生效，回填标记与计费更新同事务，读取和重启不产生新调用。

## 五、Fork、历史身份与子任务资源

### 5.1 裁切与完整性

Runtime 持源会话 mutation gate，核对 `expected_generation`，读取同一可靠历史及资源清单；按 Assistant 消息定位，再包含其完整 Tool 结果闭包。过滤每条历史关联，只保留前缀内的消息、控制结果、Skill／MCP 事实和明确关联的 child。

- 某 Run 已可靠终结且其全部关联消息／结束边界均在保留范围内时，保留终态和起止；原失败重试各保留自身 attempt，不能将共享 UserMessage 再造为新输入。
- 若该 Run 还有关联消息在截取点后，或尚无可靠结束边界，保存 `partial=true` 与最后保留消息 ID。目标中该 Run 的终态、结束时刻及依赖后续执行的错误为空，界面显示“截至分支点”；可保留真实开始时刻，但不显示完整耗时。原始消息不改写为 cancelled／interrupted。
- 无输出 retry 不能凭共享 User 判断落在截点之前。正常终结帧在既有 Run 历史内冻结 `finished_after_message_id`，指向终结提交时本 owner 的正文末位置；该锚点可能属于另一 Input，与 Run 自身的 `last_message_id` 不同。裁切据真实锚点和已选 attempt 的 Input 关系保留前序尝试，排除截点后的空输出尝试；重新输入也裁掉结束位置已在尾部的无归属尝试。旧数据无法证明该位置时保持未知，不按时间、ID 或数组排序推断，亦不新增数据库历史副本。
- 源会话仍在运行时，只能复制已经可靠提交的前缀；不复制 pending exchange、未确认结果、活动审批或尚未提交的流式内容。
- 继承记录统一 `inherited=true`；再次 Fork 保持只读语义，不把第一层继承转为本地执行。

目标创建使用既有新 Session ID、环境、附件与工作计划／暂停 Goal 规则。先准备目标所有文件并核验，再在现有 Fork 事务创建 Session 和资源绑定；不创建继承 Run／Input／child 执行行，也不复制幂等 key、队列或响应 ID 续接 owner。

### 5.2 身份／引用检查矩阵

| 现有位置 | F02 处理 |
| --- | --- |
| `runs.run_id`、`inputs` 与活动 `(input_id,attempt)` | 保留必要执行控制约束，终态长期归文件；新 ID 避开当前 owner 继承历史，碰撞时重分配。首次／最近 Run 和历史 attempt 不再靠 SQL 终态行计算 |
| `run_message_refs` | 迁移可靠关联到文件后删除表；所有历史写入、查询和重建调用点一并移除，不能换名建等价表或塞进 JSON 列 |
| `skill_activations`、`mcp_input_selections`、`message_feedback` | 已提交阅读事实迁入文件并移除历史副本；Skill／MCP 选择只在排队期间临时保留，可靠消费提交后释放，评价删除整表，不再通过 FK 留存历史链 |
| `model_request_records.run_id`、`session_usage` | 保留独立实际用量统计，移除仅用于历史关联的 Run 字段；request 去重与数值不变，不复制继承调用 |
| `pending_tool_exchanges`、`body_appends` | 只用于未完成执行及提交恢复；其临时 receipt／payload 在可靠完成后释放，不能成为永久历史读源 |
| `session_feedback` | 只保留当前真实待回答／待处置状态；已回答、取消和失效的阅读结果归文件，处置后释放控制行，不从历史恢复 pending |
| `child_tasks.parent_run_id`、child 活动 Registry | 只保存未完成工作的 parent 绑定，终态 child 描述及正文从文件读；释放控制行前确保父恢复所需证据仍在未完成回执或文件中，不能依赖终态 child 表修父结果 |
| Runtime 的 Session 内 `runs`、authorizer、Journal owner、任务注册表 | 执行查找严格先定位 Session；历史只进入只读投影／有界内存索引，不能注册为活动任务 |
| Desktop 的 child view／live／generation／工具与导航缓存 | child key 使用完整 owner；每设备独立 Store 可隐含目标，跨目标共享导航显式携带目标 |

SQL 的执行主键只约束当前工作；历史 ID 在各会话文件中独立解释。所有历史查询与工具详情使用 `ConversationOwner + message_id + call_id`，不能退回来源会话找同 ID；AroundRun 和重试校验也直接读目标文件，不重建永久 Run／Message 对照表。

### 5.3 child 历史与文件资源

保留前缀中可靠 `delegate_task` 结果明确引用的 child：父工具结果可靠闭合时 child 已按现有链路先结算。复制其可靠终态描述、正文和工具图片到目标同名 child 目录，owner 改为目标 Session，child ID 可保留，不复制临时工作目录／取消句柄／执行器。
实际 child 的文件格式头还保存所属 Session、parent_run_id 和 parent_tool_call_id；在现有创建流程先准备私有文件，再提交活动控制行。父 pending 恢复通过本会话 child 文件中的可靠终态及该绑定定位已结束 child，按需建立仅内存的 owner 索引，不要求保留终态 child 表。没有有效终态的孤儿准备件不能被当作父成功结果。父历史描述记录该 child 的固定 generation 与必要资源引用，读取无需来源会话；child 查询、分页、around、工具详情和 Recall 均先查目标 owner 的历史描述，再读目标文件。继承 child 不计入活动数量，不接受取消。

子任务结果存在但原正文或图片已不可用时，复制可证明的描述和父结果，明确资源不可用，不留下指向源会话的活动链接，不假造空正文。没有可靠父结果关联的进行中 child 不复制；不能扫描正文文本猜测 task_id。附件仍按现有 blob／新引用机制改绑，引用路径只做已确认的结构化改写；不批量替换自由文本、冻结 Prompt 或 Provider payload。

正文不可复制时，在目标文件的既有 child 描述中记录 `body_unavailable=true`，保留已证明的终态、消息数量和时间，不创建空正文文件；这不是新的执行错误或控制状态。child 产品快照投影 `inherited` 和 `body_unavailable`，不可用正文的用量保持未知，树中显示“继承／正文不可用”并关闭正文入口；正常图片仍独立复制，已缺失图片由目标资源入口报告不可用。Host 的故障缓存、Volatile 的正文与 Desktop 的视图／实时输出／分页水位均使用完整 `(Session, child)` 归属。

Recall 的派生键同步加入 Session：head 主键改为 `(session_id,owner_kind,owner_id)`，文档唯一键、owner 索引及 `document_id` 也包含 Session。只保留所属 Session 的外键，移除将可重建历史索引绑定到活动 `child_tasks` 的 child 外键；索引建立前从目标历史描述核验 child 归属、generation 和资源可用性。标题从该历史描述取得，不能全局按 child ID 查源执行表。源 child 删除／历史裁切时显式使对应 owner 索引失效，整个 Session 删除仍由 Session 外键级联；保留 FTS 定义和触发器并重建派生内容。这是既有文本检索索引的归属修正，只保留词项／检索文本和定位所需字段，不增加历史 child 表，也不把 Run、Step、attempt、状态或时间复制到索引。搜索结果的历史属性按命中的完整 owner 回读文件。

旧 Fork 没有可靠来源／轮次关联时，迁移只能保留现有消息和可证明事实，状态／时间未知；不通过标题、时间接近或消息相似度自动“修复”。如以后用户提供可验证的来源再另行制定精确修复方案，本 Feature 不创建猜测修复向导。

### 5.4 长会话分支性能修正（2026-10-22 草案，暂缓实施）

用户要求先在生产数据的隔离副本上按阶段计时，再提出方案。本轮已复现末尾分支的长时间等待及同用户 Store 查询被阻塞；主要成本落在主／child 新 generation 的无缓冲 JSON 写入，锁取得、文件同步和数据库提交不构成主要耗时。较早分支仍全量解码源历史，新分支发布后又经过恢复装配和全量正文加载。详细计时在会话中说明，不将原始生产数据、运行日志或临时计时代码纳入流程交付。本节为后续修正草案，尚未实施，不改写既有可靠性与独立历史边界。

用户随后明确“算了，先把问题记录一下”。本问题已登记至版本[遗留事项](../../遗留事项.md)，当前仅保留定位结论与备选优化方向，不启动实现；后续是否推进另行安排。以下顺序仅作为重新启动修正时的候选方案：

1. **共用新 generation 写入增加有界缓冲。** 在 `conversation::write_generation` 与升级的 `write_upgraded_generation` 文件边界使用有界写缓冲，建议从 256 KiB 开始；codec 继续接受既有 `Write`。缓冲显式 flush 成功后才执行文件同步，再沿原完整内容／元数据校验、目录同步与 SQLite 事务发布。不改变文件格式、历史字段、队列或提交顺序，不减少校验，不把缓冲 flush 当作持久化完成。覆盖主／child 与迁移共用路径，写入、flush、同步及校验错误仍阻止发布。
2. **消除新分支的重复装配和源历史重复解码。** 先评估将已可靠提交的 `StoredSessionFork.conversation` 及已核实元数据装入新会话已有进程内状态，避免刚写完立即当成重启恢复并再次读取完整正文；保持完整 owner／generation、child 只读目录和上下文模式的既有语义，不能直接跳过必要校验或恢复。较早分支再复用既有消息定位和有界读取，按选中 Assistant 及 Tool 闭包读取前缀；Runtime 继续持有裁切／继承业务语义，Store 承担文件读取与准备。附件查找优先复用已核实的文件事实，减少 Runtime 与 Store 重复加载 child 正文。全程不增加 SQL 历史副本或持久化索引。
3. **并发范围依据残余耗时收敛。** 首轮先保留唯一 Store worker 和 Connection 所有权。若复测仍出现明显跨会话阻塞，再细化受监督的文件准备生命周期，将重文件 I/O 与短事务发布分开，保留源会话串行、同一 generation／可靠截点和最终发布复核。只缩短全局锁不能解除单 worker 排队；也不能只把整个函数移到无监督后台任务。涉及退出、断连、源删除和准备失败的所有权与清理边界，须在并发方案确认后实现。
4. **前端区分复制与加载。** 复用现有待处理状态，分别展示后端分支复制和复制完成后的会话加载；持续等待不自动重发有副作用的分支命令。本轮不为进度新增持久化任务或历史表。

每轮验收同时核对分支命令、列表／新会话读取、并发普通查询的耗时和内存，区分首次读取与已加载源会话，区分后端接口与实际页面渲染。正确性继续覆盖完整／半轮 Tool 闭包、独立 child／图片／附件、重复分支、删除来源与重启、文件失败不发布、继承控制拒绝、费用与队列不新增。优化收益须由同样本复测确认，不预先承诺倍率。真实用户库和既有备份不进入测试写入范围。

## 六、执行时间与应用协议

### 6.1 输入暂存与实际领取（2026-10-22 用户确认修正）

- 入队只在既有 SQLite 输入队列暂存正文、顺序、优先级、来源及选择，不创建 Run、不分配执行 attempt、不发送 `RunAccepted`，也不生成会话正文或处理过程。撤销直接移除暂存项及其选择；排队幂等重发返回同一 Input，Run 为空。
- 普通发送、新会话物化、Goal 恢复／held 指导、主控投递、代理报告及设备输入共用此边界。`SubmitInputResult`、物化结果及 Goal 恢复结果允许 Run 为空；设备／主控接纳回执不保证 Run 身份。协议与配套客户端同步调整，不保留旧“入队即 Run”的并行行为。
- 唯一 Session 队列驱动仍先准备配置、Shell 和能力，准备期间输入可撤销、暂停或置顶。重新取得模型绑定 gate 与 Session mutation 并核对队首、正文代次和配置后，才通过既有 Store 业务端口实际领取并创建首次 Run 控制，随后发布 `RunAccepted`。候选权限装配直接引用 Input，不以提前创建 Run 查找选择。
- 领取后的正文与真实开始沿原 staged append 提交；准备失败在领取后可靠结算失败，未开始不计执行耗时。领取提交后崩溃按未完成执行中断收敛，不把已领取工作恢复成可撤销队列。尚未领取输入重启后仍需手动恢复。显式 Retry／空闲历史重入的立即领取继续使用各自原子入口，不复制新的用户输入。
- 前端优先绑定实际运行／停止中的轮次；主会话未开始且无正文的 Run 不追加空处理过程。`accepted` 控制状态与输入队列暂存状态不混用。
- 同版本追加 `f02_queue_claim_v1` 迁移：沿已有独立备份、核验和事务入口，将旧 queued／首次 accepted／未开始且无正文回执、工具交换或 child 的控制还原为纯暂存 Input，解除暂存 Skill 的 Run 绑定；保留正文、原身份、顺序和优先级。已进入开始／结算正文回执的 Run 保留给原 staged append 恢复；不一致的工具／child 控制拒绝迁移，真正开始的 Run 不受影响；带未知迁移 key 的库由旧 Host 准入拒绝。

### 6.2 执行时间

- 将既有 `StoredRun.started_at_ms` 贯通 `RunRecord`、`RunSnapshot`、`RunStarted`、Assistant 历史投影及 Desktop `LiveRunProjection`；Assistant 字段命名为 `run_started_at_ms`。Input 的 `accepted_at_ms` 保持暂存接收时间；Run 的 `created_at_ms` 从实际领取创建时起记录，二者不再共用入队时间。
- 起点为 `runtime/input/mod.rs` 已有 `commit_user_message` 的可靠领取时刻，记录成功后安装同一个值；retry 复用 UserMessage 也写自身起点。收到 `ExecutionStarted` 只发布该已保存值，不使用事件发送时间。continuation／模型 attempt 不重置起点。
- child 直接使用已保存的 `started_at_ms`，排除 accepted／permit 等待；不借用父开始时间。
- 未开始／Accepted 不挂载秒级计时器；终态且无开始时间也不显示执行耗时。运行中用现有 Host 时间锚点与本地单调时钟显示，结束用可靠结束减开始；时间缺失／逆序保持未知。
- Conversation 的 User／Assistant 及 child 展示沿现有 DTO 增加缺省 false 的 `inherited`；Assistant 增加缺省 false 的 `partial`。截取记录的 `status`／结束时间使用已有可空语义，不新增伪执行终态。界面对继承项隐藏重试／取消／继续原任务，仍允许阅读、反馈和再次 Fork；服务端活动控制始终以实际执行 Registry 校验。

新时间与历史字段采用可选／安全缺省。入队结果 Run 可空是本次用户已确认边界的配套契约修正；当前未发布版本统一到最终形态，交付配套客户端／Host，不承诺旧测试客户端继续按非空 Run 读取新接纳结果。软件版本及最低兼容版本保持 `0.32.1`，企业协议保持 4，不新增握手协议或历史表。

## 七、快照一致性与前端加载

### 7.1 可靠读取屏障

`get_session_view` 在 `prepared_session` 完成后取得目标 Session 既有 mutation gate，先冻结本次共享配置 Arc／Workspace／设备名称等输入，再读取会话和 child 的可靠历史，合并该 Session 内存投影。
`load_product_conversation_window` 本身只调用 Store 和检查窗口；现有分页／around 的外层入口才持 owner gate。快照直接复用这个无重入的私有 helper，不能改为调用会再次取得同一 mutation gate 的公共分页命令。

让同 Session 的 child 创建、开始、工具可靠提交、压缩换代、终态及相关 Skill activation 也经过 parent mutation gate：只覆盖 Store 提交、短内存安装及事件发布，不覆盖 Provider、工具、用户等待、permit 或网络目录扫描。child 自身 gate 保留，用于独立 Journal 一致性；统一顺序为 parent → child → Store，释放同步 state 锁后再 await／发布。
禁止在持 child gate 时再等 parent；取消等待审批或子任务时先释放 parent。现有 Core／Authorizer 等待不持该 gate。不同 Session 继续并发，同 Session child 的模型／工具仍并行，只有短提交串行；Store 本来即为单 worker。

读取期间同 owner 的可靠消息、终态与数量不交错；减少现有重复的整份 Conversation 读取，一次可靠读取同时派生产物、文件引用和上下文计量。不得为页面新增全库扫描或另一份常驻正文缓存。

审批使用已有 `ApprovalRegistry` 的 Session revision，原子复制审批列表与 revision，并在快照完成前比较；登记／移除与 revision 更新收敛到同一短 registry 临界区。审批等待不取得 parent gate，不再为同一审批事实新增版本字段；相关事件仍沿现有观察发布边界处理。

### 7.2 作用域水位与实时事件

在现有 `ObservationCoordinator` 中派生“最后相关事件的全局 sequence”：按 Session、Workspace 和实际共享配置，以及 application 摘要范围记录。它们复用已分配序号，不引入各实体的持久 revision 或新事件流水。

- Session 的状态、queue、workplan、goal、反馈、审批、正文和 parent／child 运行事件只影响所属 Session；child 事件同时影响包含该 child 的 Session 视图。
- Workspace 只影响引用它的会话及 application 列表；配置、模型、MCP／Skill／插件实际生效目录等按当前快照真正读取的共享输入失效。仅下载进度等与快照无关的事件不扩大范围。
- application 只在列表／摘要及共享能力发生变化时失效，普通 text／reasoning／tool 输出不会仅因有全局序号而使首页初始化失败。
- 设备名称等已有输入不一定有 RuntimeEvent，快照直接捕获其不可变值；确需更新时在现有更新入口失效依赖，不能假称全局事件已覆盖所有变化。

每次读取比较其依赖水位；实际相关变化才重试，保留后端最多四次的既有上限。该 map 仅属于进程内已加载会话／观察中的依赖，随 owner 卸载回收，Runtime 新实例从零建立；初值为当前已发布水位。shared／application 水位生命周期属于 Runtime。用途是拒绝跨相关发布边界的混合快照，不是写入 CAS；不匹配返回既有 `snapshot_busy`。

实现按在途读取登记 Session／Workspace 依赖；同一依赖可被多个读取共同观察，最后一个读取结束即回收条目，不为历史会话常驻维护 map。application 只依赖实际摘要发布，主视图按当前配置与 MCP 目录、child 用量按当前配置、受 owner gate 保护的历史页按 MCP 工具投影分别核对共享输入；不消费的目录或下载进度不扩大屏障。安全返回水位仍取同一发布边界内的全局 sequence，作用域水位仅用于判断本次读取是否跨过相关变化。

实时内存变化与对应事件的序号／广播在观察协调器的同一个短同步发布边界安装；读取在同一边界捕获实时字段和水位，不能先复制文本后拿较新序号。重点调整 `run/supervisor.rs` 当前“先改 RunRecord、之后另行 send”的窗口，以及对应 child／审批发布；不持观察锁跨 Store、异步 gate 或 I/O。统一同步锁顺序为观察协调器 → 短 state／registry 锁，禁止持 state 锁调用 send。

成功快照的 `observed_sequence` 是该次相关状态已包含的安全发布水位；无关事件继续由全局 SSE cursor 消费，不因读取某 Session 而前移全局 cursor。主会话／child 的实时协调按 owner 水位合并，已纳入快照的事件去重，水位之后的事件保留。读取期间的 generation 换代继续返回 stale，不能用作用域水位绕过。
`get_child_task_view` 复用该 Session 的读取屏障及 child owner 核对；分页／around／详情沿同样的 generation 和 owner 约束。SSE gap 仍走现有权威快照恢复，不增持久回放服务。

### 7.3 初始化阶段与实际进度

登录后的 `ensure-ready` 仍只发送一次，初始化由用户域 owner 承担，页面取消只停止等待。等待期间每 500ms 查询已有、已认证的 `/health`；查询只读取本人现有槽位中的启动投影，不创建 Runtime，不等初始化锁，不触发第二次迁移。用户槽位同时拥有加载锁与启动句柄，用户关闭后释放 Ready 服务引用；不另建进度注册表。未创建槽位时保持 Host 身份服务的原有健康行为，其他用户的状态不可见。

`RuntimeHostHealth` 在既有阶段基础上细分历史备份、备份核验与历史迁移，提供可选的当前阶段 `progress={completed,total}`。数据库快照按 SQLite 页、历史复制按文件、历史迁移按主／child owner、核验按已完成的校验项发布；阶段切换清空上一阶段进度，就绪清空阶段和计数。不知道总量时只显示实际阶段，不推算百分比或预计耗时，不公开路径、用户名、SQL 或文件正文。Desktop 与 Web 共用既有文案映射，初始化页面显示当前阶段和计数。

初始化涉及可靠备份与迁移，不套用下节详情读取的 15 秒预算；进度查询失败不重新发起初始化，最终成功／失败由原 ensure-ready 请求决定。

### 7.4 前端请求预算与选择隔离

沿 `RuntimeLifecycleCoordinator` 管理详情读取，每个目标 owner 同时只有一次加载流程。用户选择及连接切换时取消旧流程；一次流程用 AbortController 对象身份区分，覆盖 A→B→A，不只比较最终 SessionId。该对象不是新持久 generation。

- 一次总预算 **15 秒**，包括等待、响应正文解析及退避；最多 **3 次**请求，只有 `snapshot_busy` 自动重试，退避依次 **250ms、750ms**。单次请求占用剩余总预算，不叠加成 45 秒；整体到期中止 fetch／body 等待。
- 详情的单个查询最多三次实际发送。application 刷新按活动／归档列表各自已加载的数量，从列表起点一次读取所需前缀，不逐页补拉（2026-10-22 用户确认）。既有 `get_application_snapshot` 接收可选 `active_sessions_limit`／`archived_sessions_limit`，缺省各 100；相同观察边界内返回排序、摘要、下一偏移与事件水位。下一偏移按实际查询长度计算，先于工作区可见性过滤和固定入口补入。`list_sessions` 及两种 Store 摘要实现不再将大前缀截断为 200／201 条，只保留数值边界和 `has_more` 前瞻空间；查询不读取正文、不产生持久化结构。选中会话确实不在所读前缀时，沿用单条摘要补充；每个具体只读查询各自最多三次，整个组合仍共用一次 15 秒预算。generation／事件换代重新读取基线时，同一具体查询的发送次数继续累计，不能叠加重试层或丢弃已加载列表。
- `snapshot_stale` 沿既有 generation 恢复入口处理，但受同一总预算约束；不与 busy 重试层相互无限重启。普通存储／协议错误不自动重试，鉴权按既有登录失效处理，真实连接关闭继续由 SSE／连接层处理。
- 状态为 idle／loading／error，成功后由既有投影展示。耗尽显示“会话暂时繁忙，请重试”，超时显示“读取会话超时，请重试”；单会话读取失败不直接将 Host 标为断线。
- 同一加载中的重复刷新合并；只有相关变化需要时在完成后安排一次后继刷新，不能每个事件都重置预算或发起并发重试。
- application 与 selected Session 的刷新标记分开。其他会话只影响其列表摘要，不能自动重读当前详情；定时器保留最早已排定的刷新，不让持续事件无限延迟执行。
- 当前列表刷新触发范围保持：标题变化、Run 开始／结束仍会重新读取已加载列表前缀，正文流式输出不触发该整段刷新。2026-10-22 用户明确“先这样吧，继续”，本轮保留此行为，不继续实施单条摘要增量更新。
- 保留 RuntimeProjection 的全局 SSE 缺口检测；Session／child 快照只更新 owner 水位。被新选择替代的成功、错误、timer 和 finally 均须再次核对请求身份，不能清掉新请求的 loading 或错误。

HTTP 返回晚于 SSE 时，已显示的新事件不能被旧快照覆盖。复用协调器初始连接的事件缓冲做法，为一次在途 owner 读取保留相关 envelope（最多 2048 条、合计 2 MiB）；成功后在同一前端 action 安装 owner 快照基线，再直接向该 owner 应用 sequence 大于快照水位的事件一次，不再次经过已消费的全局 cursor。先处理既有 animation-frame pending，避免它在重放后重复追加。缓冲溢出或检测到 gap 就丢弃本次快照，按剩余总预算重新同步；不得安装截断事件后的状态。缓冲随请求结束／切换释放，不保留成永久事件日志。

主视图的活动 Run 快照包含实时基线，因此替换本 owner 的活动投影后只补水位之后的增量；父视图不能据此清掉快照之后创建或变化的 child。child 视图只包含可靠正文和任务属性，不包含完整的易失 Step 基线：保留已显示的未提交 Step，仅补快照覆盖过的任务属性，不能再次追加同一 text／tool delta；可靠正文中的 Step 继续封口。已包含在 owner 快照中的主执行事件与 child 属性事件不再更新该 owner，但仍沿全局 SSE 游标正常消费。缺口恢复期间按同一有界 application 读取缓冲全局事件，先验证连续性再安装基线并恢复流；连续性或容量失败仍受原预算和尝试上限约束。

初始 application 快照读取也使用该有界只读加载语义，避免入口仍因全局输出长期繁忙。重试按钮只重读快照，不提交 Input、不执行历史 Agent。页面关闭只取消等待，不取消运行中任务或已经进入 Store 的恢复操作。
Host 现有 `user_domain::ensure` 将初始化锁交给受监督任务，HTTP 断开不会中断该域初始化；此生命周期保持，不因前端请求预算新增第二个初始化任务或强制停止 worker。

### 7.5 等待定位

复用 Command `request_id` 关联同一次请求：访问身份核验、`user_services`／用户域准备、SessionLoader、mutation gate 等待、Store 排队与读取、投影及响应完成分别记录耗时。诊断使用现有日志入口，只包含阶段、耗时和必要的不透明 owner；不输出凭据、正文、SQL 或真实业务路径。
实现复用普通 stderr 日志，以 `EZ_ASSISTANT_REQUEST_DIAGNOSTICS=1` 显式开启；默认无该阶段输出。Host 在正文解码前用进程实例与请求序数建立临时关联，解码后只记录客户端 request_id 的固定长度摘要，既不提前消费正文，也不为记录身份跳过鉴权。task-local 只随本次请求 future 存活，不传播到后台 Run；阶段 Guard 在成功、错误或取消离开时均记录耗时，但离开不冒充业务成功。Store 分别记录入队等待与等候 worker 回答，后者包含排队后等候及实际存储工作，不假称为纯 SQL 执行时间。响应记录序列化阶段及 HTTP 状态，不包含响应正文。
日志说明“等待在哪一层”，不能由 health Ready 或 storage worker 空闲推断无等待，也不承诺本方案已还原此前多会话同时卡顿的现场根因。验证需区分已修复机制与尚未重现的历史现场。

## 八、迁移、准入、备份与回退

### 8.1 同发布版本追加迁移

不修改 `v0_32_1.rs` 已执行入口的含义，也不将 F02 命名为新产品版本。演进现有 `schema_migrations` 为复合主键 `(version, migration_key)`：原行保留原 version／applied_at_ms，migration_key 固定为 `release`；追加 `(0.32.1, f02_history_v1)`。migration_key 是编译进 manifest 的有序迁移身份，不是可随意传入的动态脚本，也不按字符串排序。

旧账本到新账本的桥接在独占实例锁和单一 SQLite 事务中完成，并与 F02 的表变更、全部已准备历史文件的 generation 指针切换、旧历史关联删除、校验、兼容下限提升和追加迁移身份同次提交；文件必须先按第 8.3 节完整准备，不能先删唯一旧数据源。切换事务失败整体回滚。既有发布入口顺序、原校验逻辑和原行不变，先执行缺失的 release 再执行 F02 迁移；已经登记 0.32.1 的库只执行追加迁移。每次打开只核对已提交前缀及目标结构，不反复 DDL／备份。

当前迁移器严格要求“版本列表末项等于软件版本”，必须改为“发布版本与静态迁移身份共同构成前缀”；软件版本仍取 0.32.1，启动诊断同时保留原 `database_version` 产品版本，migration_key 不伪装成软件版本，也不是 Agent Step。对后续 0.32.2 的迁移只保留可追加契约，不实施该版业务。

F02 提交后存储最低 Host 提升至 **0.32.1**，与该追加迁移一起声明。同版本旧候选仍不能写新库：其只读准入会因严格账本结构／旧兼容声明不匹配而拒绝，早于业务目录修复和可写连接。不能只靠 min version 比较来保护同版本候选；必须用实际旧二进制核实拒绝且源数据未变。旧二进制可能显示“账本／兼容元数据不支持”的旧提示，不能承诺它具备新提示文案。

### 8.2 表与文件影响

| 对象 | 变更与验证要求 |
| --- | --- |
| `schema_migrations`、`database_compatibility` | 保留 release 行，原子追加 migration_key 并提高独立存储下限；精确核对旧行及新主键，迁移身份不存 Agent Step |
| `body_appends`、`child_body_appends` | 支持零消息和无 Run 的合法提交；旧 pending 按既有规则闭合后再切换。新 receipt 完成即删除，不长期保存历史 payload |
| `run_message_refs` | 所有可靠关联先写文件并逐项核对，再删除表、历史关联查询和插入路径；新 schema 不含等价副本 |
| `runs`、`child_tasks` | 可靠终态及历史错误／关系迁入文件，清除已有终态历史行；物理删除 Run 的错误与结束时间列、child 的最终消息／错误／结束时间列，保留未完成执行控制。所有指向终态行的历史 FK 必须先迁移或移除，不能直接级联丢数据 |
| `inputs` | 保留必要接纳、排队、去重和待处理控制；已完成指令结果、历史首末 Run／attempt 由文件读取，不用 Input 行承载完整历史结果副本 |
| `skill_activations`、`mcp_input_selections`、`message_feedback`、`session_feedback` | 先按已提交／当前控制用途逐项拆分；已提交历史值只留文件，对应表／列删除或清空历史部分，不再保留已完成 activation、selection、反馈台账。未完成问答／输入继续按原控制语义恢复 |
| `model_request_records`、`session_usage` | 保留实际本地 request 去重、用量与独立计费数值，移除供历史拼装的 Run 关联；迁移前后实际用量不变，不把该表扩展为执行历史 |
| `conversation_recall_documents`、`conversation_recall_heads` 及 FTS | owner 键加入 Session，移除活动 child 外键；只保留检索内容和消息定位，历史时间／轮次属性从文件回读，FTS 及触发器配套核对 |
| `sessions` 当前文件指针、列表元数据及资源 | 完整文件核验后切换 generation；会话目录摘要和资源管理保留，不扩展成第二份轮次树 |

旧 child 终态只在全部 owner 文件准备、校验及指针切换后于同一迁移事务释放；先移除派生索引对 child 的外键及 FTS 触发器，仍有原回执或工具交换时不允许级联清除。最终验证拒绝残留终态，异常回滚指针、schema、账本及原控制。正常 child 的控制加载、执行目标和在途资源指针只查询未完成状态，终态位置从文件目录读取；已对齐库若出现违规终态行，下次准入明确失败，不能自动删行或重新迁造历史。

父 Run 同样在文件可靠结算、原回执精确删除且无 child／工具交换／激活依赖后，于同一事务释放控制；删除失败回滚全部完成效果，恢复只闭合原提交。升级先迁出全部文件，再依次释放已结束 child 与 Run；最终准入拒绝残留终态 Run。普通控制查询只读 accepted／running／cancelling，即使 SQL 被注入过期终态也不解码其载荷。旧终态 queued Input 的修复仅限已备份的迁出上下文。会话列表活动时间读取可靠完成事务更新的 Session 元数据，不再聚合已经释放的 Run 行。

全部文件核验及终态行释放后，在同一切换事务删除 `runs.error_code`／`error_message`／`finished_at_ms`，以及 `child_tasks.final_message_id`／`error_code`／`error_message`／`finished_at_ms`。正常创建与结算不写这些列；结算值已冻结在文件和未完成回执中，SQL 只在完成事务内更新状态／取消标记，再显式释放控制。未完成控制的 DTO 对应终态字段为空，不从 SQL 模拟历史。旧源准入和已备份恢复仍严格要求并读取原列，目标拒绝这些列即使以空列重新出现；不能为开发过程中的中间布局保留兼容列。

旧活动 Run 若携带无法解释的终态值，升级保留完整备份并拒绝，不能在删列时悄悄丢掉。删列任一步失败也回滚已移除的其他列、原控制行、全部指针和迁移账本；配套备份保留原终态数值与文件，后续重试继续按既有未发布 generation 规则准备。

独立用量表在同一切换事务物理移除 `run_id`，保留原请求唯一键、owner、类型、模型、全部 token 数值及完成时间；汇总原件保持。正常写入不再接受 Run 关联参数，不能用空列保留历史兼容；旧源仍严格核对原列存在，目标拒绝该列重新出现。此变更不授权从继承历史重建费用，历史回填与换代的本地调用边界仍按第四节核对。

旧源的布局验证仍严格要求 `run_message_refs`、`message_feedback` 等原结构完整；目标验证只复用各发布版本保留部分的约束，并拒绝已删除历史表或同名视图重新出现，不以空表兼容或缺表推断版本。消息评价随原消息和准确变更时间迁入文件后才删除整表；正常评价与取消评价沿文件零消息提交，清空会话通过 generation 换代移除评价，旧源恢复才访问旧评价表。

`inputs` 沿既有“重建被引用表”的迁移路径重建：已备份且所有文件准备完成后，版本执行器在事务外临时关闭 FK，在唯一切换事务内逐列复制队列和身份、保留原行序号及计数上限，去除已迁出命令及已结束消息 Input 的历史字段，保留真实队列及未完成控制，再核验全部 FK 和完整性并恢复 FK。来源布局继续校验旧命令形状，目标约束区分完整排队命令和完成后的最小身份；失败回滚 schema、全部输入与引用，不级联丢弃 Run、待提交回执或选择。

### 8.3 先迁出历史，再删除旧表

原草案的“先改 schema、首次打开时再懒转换”撤回：它要求长期保留未访问会话的 SQL 历史源，与本次边界不符。F02 首次升级在该用户域开放业务前完成一次历史迁出，之后启动及普通查询仍按需读取文件，不每次扫描全库。

1. 持实例独占锁，核对源 schema／文件和预期影响，先完成第 8.4 节的独立配套备份；备份未验证前不进行恢复写入、迁出或删表。
2. 按既有规则闭合旧 staged／pending／clear 恢复，只修可靠事实，不执行 Provider 或工具；将已完成恢复后的数据固定为转换源。恢复若改变源文件或控制状态，应明确这是已完成的恢复提交，不能称为后续 schema 事务失败时也一并回滚。
3. 逐 Session／child 流式读取原文件和旧 SQL 关联，准备尚未发布的新 generation。把 Run／Step、message refs、历史 attempt／终态、控制结果、激活／选择、反馈和资源绑定写入文件，重新解码并按原主键逐项核对；记录消息及关联的精确数量和关键字段一致性。源历史暂不删除，内存只保存转换所需的有界批次和待切换 owner 清单。
4. 全部目标准备成功后，在单一 SQLite 事务内复核源 generation／数量及关键字段，切换全部当前文件指针、删除历史副本／旧表、收敛执行控制 schema、更新迁移与兼容元数据。事务失败则旧指针和旧历史表保持，新文件只是未引用准备件；不能报告部分升级成功。
5. 提交后普通历史读取只走新文件。旧源不作为业务回退读取或新的在线副本；独立备份在本轮全部迁移提交及校验成功后删除，失败时保留；未引用准备件按已核验操作身份清理，清理失败不能回滚已提交的升级。

目录准备以完整 owner 游标分批读取，每批最多 64 项，不装载全库 child 请求、配置或执行对象；全局仅保留原方案的待切换清单和 child 目标 generation 定位。旧终态 queued Input 同样分批闭合，正文只在处理该 Input 时加载；真实待消费队列不参与该收敛。分批不改变全部准备成功后一次切换的事务边界。

若某个源文件损坏、关联不完整到无法证明安全迁出或数量不符，停止本次升级并保留现场，不能先删 SQL、补空文件或悄悄跳过。升级前无法安全迁移属于数据升级失败，需报告并按安全规则重新处理；升级成功后普通查询遇到单个坏会话仍按 owner 隔离，不阻塞其他会话或以全局扫描恢复。旧分支原本缺失的归属继续保持未知，不据此捏造历史。

删除 `runs`／child 终态行之前，逐项检查 `skill_activations`、`pending_tool_exchanges`、`body_appends`、`session_feedback`、父子任务关系及用量查询的外键／子查询；历史引用移到文件，真实未完成控制引用保留，必要的 FK 表重建仍由迁移器统一控制。不能让 `ON DELETE CASCADE` 把尚未迁出的阅读事实或未完成恢复证据一起删除。

### 8.4 备份与恢复规则

2026-10-22 用户明确收窄范围：F02 第一次结构变更前只保全 SQLite 快照、受管主会话／child 历史文件及既有小型配置。文件按受管目录白名单选择：`data/sessions/<session>/conversation.<generation>.jsonl`、`child-tasks/<child>/body-<generation>.jsonl`；待删除恢复目录 `data/staging/deletions/<session>.<operation>/` 下相同层级的历史也纳入。保留所有已有历史代次，不进入 `private`、项目、`.venv`、`node_modules`、缓存、附件、工具图片或上传目录；未被迁移改写的资源保持原位。不跟随链接扫描外部工作区。SQLite 由 Backup API 生成独立快照，不把打开的源库当普通文件复制。

文件仍使用独立副本与逐项校验，不采用硬链接。先只读重开备份数据库核对 integrity／FK、精确表数量及字段摘要；再核对历史文件集合、长度与摘要，最后发布清单。清单声明 `file_scope=session_history_only`；该配套备份用于迁移回退，恢复时须保留原域内未被改写的项目与资源，不能当作完整用户目录副本使用。已有坏历史按原字节保留，不把备份有效等同于原历史健康。空间不足、复制或验证失败均停止迁移，不删除旧备份。

只做这次升级必要的独立备份，不在每次普通读取重拷全库。2026-10-22 用户明确“成功后就删掉”：正式用户域数据库启动入口在本轮全部迁移、目标结构、完整性／外键及账本校验提交成功后，立即删除本轮生成的独立配套备份；任一步失败均保留，不在单个前序版本成功时提前清理。只使用本轮返回的确切备份目录，不枚举删除既有备份，不跟随顶层链接。删除失败记录清理诊断，不能回滚已提交升级或误报为数据库迁移失败；不会宣称残留已清理。此规则不扩展到 Host 布局迁移或配置清理的其他备份。

本次全部历史迁出前的文件和 SQL 结构事实在升级期间由同一配套快照保护；原数据目录里的旧 generation 不属于本条备份目录清理范围。备份包含隐私与可能的配置凭据，沿现有私有权限，不能登记为交付产物或写入公开日志。

不提供自动原地降级。若切换事务尚未提交，事务回滚保留切换前的指针与表；已按第 8.3 节完成的可靠恢复不被该事务撤销；升级失败且配套备份仍保留时，退回旧候选必须停止新 Host，将当前数据集另行保全，按用户明确确认恢复**同一备份中的数据库、文件与配套配置**。升级成功后本轮临时备份已删除，不再承诺可用它降级；需要回退时必须另有完整且匹配的恢复来源。这会失去备份后的新工作，须先说明；不能只恢复 SQLite、只改兼容下限或删除迁移登记。恢复后才允许旧 Host 写入，恢复动作本身另行核对和授权。

技术方案确认不等于操作用户库。实际验证只创建 `.runtime-test/` 下新的隔离 Home；写入前列明实际主机（本机）、SQLite 无网络端口、源／目标文件路径、表和预期影响，核对正式接口实际读取来源。生产／共享数据迁移、批量修复或恢复仍需用户明确确认及已验证备份。

## 九、最小新增审查与否决方案

| 选择 | 必要性或否决原因 |
| --- | --- |
| 同 JSONL 的可靠历史帧 | 现有纯消息不含 Run／Step／时间，无法满足独立会话历史；扩展文件即可，不需要另建历史数据库 |
| 不可执行的存储历史表示 | `StoredRun` 的 Input／恢复语义不能承载只读继承；该表示只有值和校验，不持执行句柄或独立生命周期 |
| staged append 的零消息支持 | 真实存在 retry start 和零输出终态，不能靠新增空消息或只改 SQLite 填补 |
| 原迁移账本的 migration_key | 已使用同版本且 release 已登记，现有版本主键不能表达追加迁移；直接重写旧入口不会执行，伪造新产品版本会违背版本主线。扩展原账本即可，不另建 F02 迁移账本 |
| 观察作用域水位 | 仅 parent gate 不覆盖共享配置和实时事件；全局 sequence 又误受其他会话影响。复用既有 sequence 的作用域投影，有明确比较消费者及失效／重启／测试语义 |
| 删除永久历史关联副本 | 本地执行和继承历史都直接读文件；可重建不是保留 SQL Run／Step／消息归属副本的理由，不能换表、JSON 列或物化视图继续保存 |
| 不保存事件全量回放／新计时系统 | 已有可靠起止和消息提交，不需要将 token 事件落盘或创建计时任务 |
| 不使用无限重试或多个互相嵌套的超时层 | 只读恢复也必须有总预算；多个会话一起等待不能靠不断重置 loading 隐藏 |

格式头版本、原 generation、原 operation ID、现有全局 SSE sequence 各司其职；不新增每 Run／会话的持久 CAS 版本。若实现删除某个拟新增字段后仍能由上述事实确定结果，就删除该字段。

### 验收后修正：长会话读取超时（2026-10-23）

主会话视图构建复用同一观察屏障内已核验的 child 历史事实，取消每个 child 前后各一次主历史重读；正文、最终消息继续核验 owner／generation，变化沿原快照重试处理。Host 定位单个 child 时使用已有位置索引读取其最新事实帧，避免重复物化全部 sibling 目录；完整目录消费者及 pending 校验保持。

不新增历史 SQL 表、正文缓存或协议字段，不放宽前端读取预算；历史仍以会话文件为准。本修正针对读取超时，已暂缓的长会话复制分支优化保持原状态。

### 验收后修正：长会话加载与输入响应（2026-10-26）

用户将加载及发送后的本地等待重新纳入本版修正。测量区分文件索引构建、完整正文读取、追加校验，以及真实 HTTP 接纳到本机假模型收到首个请求；覆盖冷／热加载和另一会话并发接纳。

### 2026-10-27 用户确认后的读取边界修正

本节更新前述长会话性能补充的读取策略。冷恢复顺序扫描一遍文件；每遇到有效压缩点立即丢弃此前无效正文，EOF 完整校验之后才安装执行窗口并进入业务。主会话后续输入和模型步骤在 Journal 中增量维护有效窗口；净记忆、能力上下文和产物／文件引用元数据单独归并，历史正文继续只存在会话文件中。图片在当前实际请求需要时校验，不在打开主会话时全量解码历史图片。
