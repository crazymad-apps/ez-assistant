# v0.13.0 开发计划：单层子 Agent 与同步任务委派

## 一、计划信息与设计依据

- 版本：`v0.13.0`
- 状态：已完成
- 当前阶段：M0–M5 已确认，版本验收通过并归档
- 功能范围：[`功能设计`](功能设计.md)
- 实现依据：[`技术方案`](技术方案.md)
- 版本状态：[`docs/版本管理.md`](../../版本管理.md)
- 实际实施记录：[`开发进度`](开发进度.md)

本计划只维护里程碑顺序、交付范围、验证入口、完成判定和 Review 重点。
并行分组算法、子任务状态与存储结构、恢复矩阵、协议字段、默认预算和源码
落点均以已确认技术方案为准，不在开发计划中建立第二套设计。

本版本不单独编写正式界面交互设计指导。Runtime Host Web Demo 只在最后里程碑作为
验收载体，不形成桌面产品 UI 契约。

## 二、推进原则

1. M0 至 M5 顺序推进。每个里程碑完成实现和验证后先标记为 `🟨 待确认`；
   只有用户明确确认后，才能标记 `✅ 已完成`并进入下一里程碑。
2. M0 只建立 Core 通用的两种执行模式和 ToolSet 派生能力，不引入子任务业务类型。
   先用确定性假工具锁定普通工具仍串行、显式并行组确实重叠执行。
3. M1 先建立子任务标识、状态、Store 契约、SQLite 关系与独立 JSONL 正文，不启动
   真实子 Agent。跨介质可靠边界确认前，不让子执行产生工具副作用。
4. M2 只先完成单个 `delegate_task` 的端到端闭环。单任务的继承、隔离、权限、落盘和
   结果回传未确认前，不扩大到多子任务并发。
5. M3 在已确认的单任务链路上增加同级并发、审批归属、单独取消、父级级联取消、
   超时和配额；不在该阶段同时改写恢复算法。
6. M4 完成启动恢复、归档/恢复、公共查询与 HTTP/SSE 契约。恢复只形成中断终态和
   一致性修复，不自动续跑或重放历史工具。
7. M5 只使用正式 Runtime 命令、查询和事件扩展 Web Demo，不为 Demo 新建业务状态、
   私有调度链路或第二套子 Agent 协议。
8. Plan/Build 的父 Agent 工具定义必须保持字节等价；执行模式属性不进入 Provider 可见
   Tool Definition，不因子 Agent 导致工具 Schema 频繁变动或缓存失效。
9. 子 Agent 必须复用现有 Agent Core、Provider、Context、Tool、Authorizer、Guardrail、Recorder、
   文件/Shell 和 Runtime 基础设施。出现重复 Agent Loop、重复存储工作者或伪 Session/Run 时
   停止扩大改动并重新 Review。
10. 自动测试只使用 `tempfile` Runtime Home、临时 Workspace、临时 SQLite 和 loopback Provider；
    不读写用户真实 `~/.ez-assistant` 业务数据。
11. 默认忽略的真实 LLM 验证可以脱敏读取用户模型配置，但 Runtime Home、SQLite、Conversation、
    Workspace、权限文件和子任务目录必须使用隔离临时路径。若确需启动会写入用户默认
    数据库的 Host，必须按项目数据库安全规则单独核对、备份、验证并再次取得用户确认。
12. 每个里程碑同步记录实际产出、验证结果、偏差、遗留和风险到本版本
    [`开发进度`](开发进度.md)；
    不主动执行 Git 暂存、提交或推送。

## 四、里程碑台账

### M0：Core 显式执行模式与 ToolSet 派生

- 前置：功能设计、技术方案和本开发计划均已确认。
- 目标：不引入 Runtime 子任务概念，先让 Agent Core 具备默认串行、显式可并行的稳定
  执行语义，并支持从同一份基础 ToolSet 派生父工具集。
- 交付范围：
  - `Serial` 和 `ParallelEligible` 两种内部执行模式，默认为 `Serial`；
  - 执行模式跟随 resolved tool 记录冻结，不进入 Provider Tool Definition 或权限事实；
  - 连续显式并行调用分组、普通工具串行屏障、原始顺序结果结算；
  - 并行组的授权、Recorder started/完成、预算预留、Guardrail、取消和错误收敛；
  - `ToolSetSnapshot` 的受校验消费式追加/派生，保留工具名称、Schema、顺序和实现句柄；
  - 默认工具全部串行的回归与假并行工具的重叠执行证据。
- 验证入口：

  ```bash
  cargo test -p agent-tools -p agent-core -p agent-testkit --all-features
  cargo clippy -p agent-tools -p agent-core -p agent-testkit --all-targets --all-features -- -D warnings
  cargo fmt --all --check
  ```

- 完成判定：普通多 Tool Call 的开始与结束顺序不变；显式并行组存在可确定观测的时间
  重叠；混合 batch 不跨越串行屏障；每个 Tool Call 始终与唯一结果配对；新属性不改变
  Provider 可见工具定义。
- Review 重点：默认值是否真正保持历史串行行为；是否把业务子任务类型泄漏进 Core；
  并行组是否提前跨过预算、可靠 started 或取消边界；ToolSet 派生是否重建或重排现有工具。
- 技术依据：技术方案 2.2、6.1–6.2、第十五节、16.1 和第十七节。

### M1：子任务领域、存储与可靠正文基础

- 前置：M0 已确认。
- 目标：建立子任务的唯一标识、结构化关系、独立正文和可靠落盘能力，但不启动真实
  子 Agent 或产生工具副作用。
- 交付范围：
  - `ChildTaskId`、子任务状态与 Runtime 内部快照的基础契约；
  - delegation 配置的 schema、领域验证、默认值和脱敏编译投影；
  - `RuntimeStore` 的 child 关系、状态、列表/读取和正文操作，以及 Volatile Store 对齐；
  - Host SQLite 兼容性新增 child 关系/状态表与索引，不改写旧 Session/Run 数据；
  - 每个子任务的独立 JSONL Conversation 目标，复用现有 generation、append、pending tool exchange
    和原子文件基础语义；
  - Runtime Recorder 公共算法与主 Run/子任务目标的私有抽取，Core Recorder trait 不变；
  - 父 Run/子任务所有权、跨 Session 拒绝、旧数据兼容和幂等 schema 测试。
- 验证入口：

  ```bash
  cargo test -p assistant-protocol -p assistant-runtime -p assistant-runtime-host --all-features
  cargo clippy -p assistant-protocol -p assistant-runtime -p assistant-runtime-host --all-targets --all-features -- -D warnings
  cargo fmt --all --check
  ```

- 完成判定：隔离临时数据库可幂等升级且旧数据不漂移；子任务关系和 JSONL 正文可独立
  创建、追加、查询与重建；正文不复制到 SQLite；主/子 Recorder 通过同一可靠算法但不共享
  Conversation mutation gate。
- Review 重点：SQLite 是否只保存关系和状态；子正文是否仍是规范 `ConversationMessage`；
  Host worker 是否仍是唯一阻塞存储所有者；Recorder 抽取是否没有建立并行持久化实现。
- 技术依据：技术方案第四、9.1–9.2、10.2–10.3、11.1–11.3、12.1–12.2、第十五节和 16.1 节。

### M2：单子任务执行与结果回传

- 前置：M1 已确认。
- 目标：将 `delegate_task` 作为普通工具接入正式父 Run，复用现有执行能力完成一个子任务
  的可靠创建、独立执行、最终结果落盘和父 Tool Result 回传。
- 交付范围：
  - 稳定 `delegate_task` 工具定义、参数验证、授权事实和结果/错误编码；
  - Host Base ToolSet、Child ToolSet 和 Parent ToolSet 的单向派生，子 Agent 不可见 `delegate_task`；
  - 父 Run 冻结模型、Provider 请求、Context Window、变体、Workspace、附件视图、权限上限和
    基础 ToolSet 的子执行装配；
  - 子 Agent 身份指令、自包含任务输入和历史事实的一次性构造与持久化；
  - `ChildTaskRegistry`、`ParentDelegationController` 和单个 `ChildTaskController` 的最小生命周期；
  - 子任务 OS 临时目录 lease，既有 Workspace/Session/Workspace Agent 私有目录继续作为持久目标；
  - 子内部文件、Shell 和其他工具逐调用复用 Authorizer、Guardrail 与 child Recorder；
  - 子终态先可靠提交，再将最终结果写回父 Tool Result；中间轨迹不进入主 Conversation。
- 验证入口：

  ```bash
  cargo test -p agent-tools -p agent-core -p assistant-runtime -p assistant-runtime-host --all-features
  cargo clippy -p agent-tools -p agent-core -p assistant-runtime -p assistant-runtime-host --all-targets --all-features -- -D warnings
  cargo fmt --all --check
  ```

- 完成判定：确定性 Provider 可通过一次委派产生独立子执行；子 Agent 不读取完整父历史、
  不能再委派；模型/变体/工具/权限继承可验证；成功、执行失败和信息不足均形成正确的
  父 Tool Result；临时目录终态后释放。
- Review 重点：子 Agent 是否真正复用 `AgentExecution`而非新 Agent Loop；子工具集是否只由 Base ToolSet
  构造；子输入是否没有泄漏父 reasoning/完整历史；子终态和父结果的顺序是否可恢复。
- 技术依据：技术方案第五、6.1、第七–八、10.1、10.3、11.2、第十三节、第十五节和 16.2 节。

### M3：同级并发、审批、预算与取消收敛

- 前置：M2 已确认。
- 目标：在单子任务闭环上完成多个 `delegate_task` 同批并发、资源上限、审批隔离、
  单独取消和父级级联取消，保持主 Conversation 仍由父 Run 串行结算。
- 交付范围：
  - `delegate_task` 声明 `ParallelEligible`，多个连续委派调用使用 M0 的并行组；
  - 父 Run 子任务总数、同时运行数、每子任务 step/tool/output/timeout 上限；
  - 并发配额的入队、获取、取消与释放，不在等待 Semaphore 时占用长时间 Runtime 状态锁；
  - 子任务审批快照的 child 关联、sibling 独立等待和 Session/Workspace 持久授权共享；
  - 单独取消 child、父 Run 级联取消全部 child/待审批项、Runtime shutdown 收敛和唯一终态竞态；
  - 一个 child 失败/取消/超时时 sibling 继续，全部结果齐备后父 Agent 继续汇总；
  - 父、子 Agent 分别保存实际 usage，Runtime 不写入父 Run 聚合副本。
- 验证入口：

  ```bash
  cargo test -p agent-core -p agent-testkit -p assistant-protocol -p assistant-runtime -p assistant-runtime-host --all-features
  cargo clippy -p agent-core -p agent-testkit -p assistant-protocol -p assistant-runtime -p assistant-runtime-host --all-targets --all-features -- -D warnings
  cargo fmt --all --check
  ```

- 完成判定：两个子执行有确定性重叠证据；审批中的 child 不阻塞 sibling；单独取消不影响
  父与 sibling；父取消不再发起汇总模型请求；配额与超时全部形成可解释结果；长锁、permit
  和取消句柄无泄漏。
- Review 重点：并发只是否作用于显式模式；审批和规则作用域是否未变；取消竞态是否可能
  覆盖已可靠完成终态；共享 Workspace 无冲突追踪的局限是否被如实保留。
- 技术依据：技术方案 4.2、6.2、8.2、10.1、第十三–十四、16.2 和第十七节。

### M4：恢复修复、归档与公共观察契约

- 前置：M3 已确认。
- 目标：让子任务在 Runtime 重启、Session 归档/恢复和客户端断线后都有可解释、可重建的
  权威状态，并通过正式协议提供查询、取消和事件观察。
- 交付范围：
  - 启动时 child -> parent 的顺序恢复，未完成 child 进入 `interrupted` 且不自动续跑；
  - begun 未启动、started 结果未知、ready 终态和父结果未回写等可靠点的一致性修复；
  - 父 `delegate_task` Tool Call/Result 成对，恢复不重放模型或工具副作用；
  - Session 归档/恢复的子任务关系和正文保留，子任务不进入普通 Session/Run 列表；
  - child list/get/cancel 命令、快照、结构化错误、生命周期事件和 approval 的可选 child 关联；
  - Host `/commands` 和 `/events` 薄适配，以及 Web Demo 所需的子 Conversation 私有读取入口；
  - SSE 丢失/重连后用权威查询重建，客户端不从事件流推断子任务终态。
- 验证入口：

  ```bash
  cargo test -p assistant-protocol -p assistant-runtime -p assistant-runtime-host --all-features
  cargo clippy -p assistant-protocol -p assistant-runtime -p assistant-runtime-host --all-targets --all-features -- -D warnings
  cargo fmt --all --check
  ```

- 完成判定：可靠点故障注入后全部恢复状态与矩阵一致；重启不产生新模型请求或
  工具调用；归档/恢复不丢失 child；查询、取消和事件的所有权校验正确；旧客户端可忽略新的
  可选 child 字段。
- Review 重点：恢复是否在启动接受新输入前完成；子终态是否优先于父结果修复；是否误用 SSE
  作为持久化事实；是否把完整子 Conversation 过早承诺为公共产品协议。
- 技术依据：技术方案第十一、第十四、16.2–16.3 和第十七节。

### M5：Web Demo、正式 Host 回证与验收准备

- 前置：M4 已确认。
- 目标：通过正式 Runtime Host、HTTP/SSE、真实文件/Shell Adapter、浏览器和真实 LLM 回证
  完整单层委派链路，形成可进入版本验收的证据。
- 交付范围：
  - Web Demo 的父 Run/子任务展开查询、状态、reasoning/text/tool/usage、审批和单独取消；
  - 父、子 usage 分项展示和纯前端动态合计，不写入 Runtime 聚合字段；
  - 页面刷新、SSE 重连和长时间子执行的权威重建、逐帧批处理与增量 DOM 更新；
  - 正式 Host 离线端到端场景：单任务、并行任务、一成一败、审批隔离、单取消、父取消、
    超限、归档/恢复和两次 Host 启动中断修复；
  - Plan 子 Agent 私有目录修改与 Workspace 修改拒绝，Build 子 Agent 不重叠文件修改与父级复核；
  - 默认忽略的真实 LLM 验证：单委派、并行探索、内部 Shell/文件审批、修改验证与父结果汇总；
  - API Key、Bearer Token、完整 Prompt、文件正文、内部物理路径和子 Agent 中间轨迹的跨边界泄漏检查；
  - 功能设计 18 条验收标准到自动/人工证据映射，长期模块约束与版本文档同步。
- 验证入口：

  ```bash
  cargo fmt --all --check
  cargo clippy --workspace --all-targets --all-features -- -D warnings
  cargo test --workspace
  cargo doc --workspace --no-deps
  cargo metadata --format-version 1 --no-deps

  cd apps/desktop
  npm run build
  npm run tauri -- build --no-bundle
  ```

- 真实 LLM 入口：在 M5 实现时新增的 `v0_13_real_llm` ignored 测试，具体命令以实际
  Cargo target 为准，不在实现前预造不存在的命令。
- 完成判定：功能设计 18 条验收标准全部有证据；正式 Host 至少两次启动后 child 关系、
  正文、终态和父结果一致；全 workspace 回归与桌面构建通过；真实 LLM 可完成委派和汇总；
  未执行项、偏差、遗留和风险已记录；Web Demo 可用于人工验收。
- Review 重点：Demo 是否只消费正式契约；长子任务是否会导致全屏重绘或 usage 重复累计；
  真实 LLM 是否完全隔离用户数据且不泄漏 credential；是否将 Demo 私有查询误当成正式桌面协议。
- 技术依据：功能设计第七节，技术方案第十四、第十六–十七节。
