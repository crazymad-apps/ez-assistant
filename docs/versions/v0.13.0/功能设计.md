# v0.13.0 功能设计：单层子 Agent 与任务委派

## 一、设计信息

- 版本：`v0.13.0`
- 状态：已确认
- 影响模块：`assistant-runtime`、`assistant-protocol`、`apps/runtime-host`、
  `agent-core`、`agent-tools`
- 需求来源：Runtime 阶段路线、`v0.12.0` Plan/Build 与正式权限基线，以及
  2026-08-12 关于单层子 Agent、同步委派、上下文隔离、权限继承、持久化、取消和
  usage 展示的用户会话结论

本版本涉及父 Run 与子任务关系、独立 Agent 执行、跨层事件、持久化、权限、并发、
取消和恢复，功能设计确认后必须单独形成技术方案。本版本不建设正式桌面界面，
Runtime Host Web Demo 只作为验收载体，不形成正式产品 UI 契约。

## 二、背景与目标

`v0.12.0` 已建立 Plan/Build、Ask/Auto、分层权限、正式审批、本地工具执行和工具
中断恢复。面对可以拆分的复杂任务时，当前父 Agent 仍需在一个上下文中完成全部查询、
分析和修改，存在以下限制：

- 多个互不依赖的分析任务不能并行执行；
- 大量探索过程会占用主 Conversation 的上下文；
- 父 Agent 无法把边界明确的任务交给隔离执行单元，再只接收最终结果；
- Runtime 缺少对子任务状态、取消、审批、异常恢复和执行记录的统一管理。

`v0.13.0` 的目标是：

1. 让父 Agent 通过标准工具调用委派一个或多个边界明确的子任务。
2. 让每个子 Agent 使用独立上下文执行，只接收父 Agent 明确提供的任务和必要背景。
3. 允许同一模型步骤中的多个委派并行执行，同时保持主 Session 的规范对话由父 Run
   串行结算。
4. 让子 Agent 继承父 Run 的模型、Agent 变体、Workspace 和权限上限，且不能自行扩权。
5. 让父 Agent 只接收每个子任务的最终结果，不把子 Agent 的 reasoning、工具调用和
   中间输出展开到主 Conversation。
6. 为客户端提供子任务查询、过程观察和单独取消能力，并保持父 Run 取消时的级联语义。
7. 在 Runtime 重启或异常中断后形成可解释、可重建且不自动重放副作用的父子执行记录。

## 三、非目标

以下内容不进入 `v0.13.0`：

- 多层或递归委派；子 Agent 不能继续创建子 Agent。
- 后台委派、跨父 Run 持续运行、定时任务或 Runtime 重启后自动续跑。
- 使用历史子任务标识继续旧子任务或向运行中的子 Agent 追加新任务。
- 用户可配置的 Agent Profile，以及 researcher、reviewer、coder 等专用子 Agent 类型。
- 由模型为单个子任务选择模型、Provider、工具集、变体、预算或执行深度。
- 子 Agent 直接向用户提问、发送消息或提交最终用户回复。
- 子 Agent 独立出现在普通 Session 列表中，或被单独归档、恢复和继续对话。
- Workspace 文件读取/修改追踪、文件归属、陈旧读取检测、文件锁、并发写冲突检测、
  自动合并或独立 Git Worktree。
- 为子任务建立新的权限层级，或允许子任务突破父 Run 的权限和能力上限。
- 为子 Agent 重建一套模型调用、Agent Loop、上下文、工具、权限、Guardrail、Recorder、
  文件或 Shell 基础设施。
- 父 Run 聚合 token usage 或费用的持久化副本；合计只由客户端动态计算。
- 正式桌面端子任务树、审批交互或成本页面；这些由桌面端版本单独设计。
- 在功能设计中冻结数据库表、字段、JSONL 编码、目录名称、HTTP 路由、Rust 类型、
  默认预算数值或模块树。

## 四、功能范围与使用路径

### 4.1 子任务的业务身份

子任务是父 Run 创建和管理的受控执行单元，不是独立的用户 Session：

- 每个子任务只属于一个父 Run 和对应 Session；
- 子任务拥有自己的状态、执行上下文、记录和取消目标；
- 子任务不能接收普通用户输入，也不能脱离父 Run 继续运行；
- 主 Session 的规范 Conversation 仍只由父 Run 串行修改；
- 子任务的中间过程不直接写入主 Conversation；
- Session 归档和恢复时，已经形成的子任务记录随 Session 一起保留。

客户端可以从父 Run 展开查询子任务，但不能把子任务当成普通 Session 操作。

### 4.2 标准工具调用形式

父 Agent 通过名为 `delegate_task` 的标准 Tool Call 创建子任务：

- 一次 `delegate_task` Tool Call 只对应一个子任务；
- 委派至少包含可展示的短描述和完整任务目标；
- 父 Agent 可以附加必要背景和期望返回内容；
- 任务信息必须足以让一个没有主对话历史的 Agent 独立工作；
- 模型不能在调用中指定模型、工具、变体、后台执行、递归深度或预算；
- 子任务标识、父子关系和状态由 Runtime 产生，不由模型填写。

同一个模型响应可以产生多个 `delegate_task` Tool Call。它们沿用现有多 Tool Call
语义并行执行，不另建批量任务数组或第二套委派协议。

### 4.3 同步等待与结果回传

`v0.13.0` 只支持当前父 Run 内同步等待的委派：

1. 父 Agent 发出一个或多个 `delegate_task` Tool Call；
2. Runtime 创建对应子任务并开始执行；
3. 多个同级子任务可以并行；
4. 父 Agent 在等待期间不进入新的模型推理步骤；
5. 每个子任务结束后形成与原 Tool Call 配对的 Tool Result；
6. 当前步骤的结果齐备后，父 Agent 继续推理、核验并统一回复用户。

子任务成功时只向父 Agent 返回最终结果；失败、取消、超时或中断时返回明确的结构化
结果。单个子任务没有成功不会自动让父 Run 失败，父 Agent 可以使用其他成功结果、解释
失败或调整方案。只有父 Run 自身无法维持委派关系或继续执行的基础设施错误，才按父 Run
失败处理。

子 Agent 的结果不是直接面向用户的最终回复。父 Agent 负责判断、核验、整合并以自己的
Assistant Message 回应用户。

### 4.4 继承环境、隔离对话

子 Agent 继承父 Run 已冻结的执行环境，但不复制完整主 Conversation：

- 继承父 Run 的模型配置和模型请求能力；
- 继承父 Run 的 Plan 或 Build 变体，不能自行切换；
- 继承 Session 已绑定的 Workspace、附件可读视图和相关稳定路径；
- 继承 Session 冻结的 System Prompt 基础语义；
- 使用独立的子 Agent 身份指令，明确任务边界、结果职责和禁止再次委派；
- 只接收委派任务、显式背景和完成任务所需的固定环境信息；
- 使用独立对话历史，不读取父 Agent 的 reasoning 或完整历史消息。

子 Agent 身份指令和实际任务输入属于历史执行事实，必须随子任务记录持久化，不能在
重建时根据新版本模板动态改写。

### 4.5 单一通用子 Agent

本版本只提供一种通用子 Agent：

- 默认使用父 Run 已冻结的模型，不允许模型在委派时自行选择其他模型；
- 不提供可选角色、预设专业身份或用户可安装 Profile；
- 任务差异通过父 Agent 提供的任务描述和背景表达；
- 子 Agent 不能注册或调用 `delegate_task`，从能力上保证只有一层委派；
- 子 Agent 不提供直接向用户澄清、发送消息、创建计划任务等超出当前任务的能力。

Plan 和 Build 父 Agent 都看到完全相同的 `delegate_task` Tool Definition，避免变体切换
导致工具定义和模型缓存无谓变化。子 Agent 继承当前变体的行为与能力上限。

### 4.6 Workspace 与临时工作空间

父 Agent 与所有子 Agent 共享同一 Session 所绑定的 Workspace，因此子 Agent 对普通
Workspace 文件的修改会立即对父 Agent 和同级子任务可见。

每个子任务同时拥有独立的临时工作空间，用于临时脚本、中间结果和只服务该任务的文件，
避免不同子任务默认使用同一临时路径。该空间不属于 Session 持久数据，任务终止后可以清理；
需要长期保留或交给父 Agent 继续使用的文件，必须写入共享 Workspace 或既有 Session/Workspace
Agent 私有目录。临时空间的物理位置、可靠清理时点和异常遗留回收由技术方案确定。

子任务临时空间只是现有文件与 Shell 能力的任务级工作目录，不形成新的文件对象、附件类型、
Artifact、文件工具或存储系统。

本版本不提供共享 Workspace 的文件冲突保护：

- 父 Agent 应只并行委派文件范围互不重叠的任务；
- 委派内容应明确子任务只分析还是允许修改；
- 子 Agent 在最终结果中主动说明实际修改和验证结果；
- 父 Agent 根据返回结果决定是否重新读取文件、运行验证或处理冲突；
- Runtime 不承诺检测两个子任务修改同一文件，也不自动选择、回滚或合并结果。

上述约定用于降低冲突概率，不构成文件并发安全保证。统一文件追踪和冲突控制留给后续版本。

### 4.7 权限与审批

`delegate_task` 本身进入 `v0.12.0` 已建立的权限和审批体系：

- 创建子任务需要对当前 `delegate_task` 调用形成最终授权决策；
- 审批向用户展示任务标题、目标和父 Run 关联；
- 仅本次、Session、Workspace 和拒绝沿用现有审批语义；
- Global 规则仍只能手工编辑并显式重载；
- 对委派调用的允许只表示可以启动子 Agent，不自动允许子 Agent 内部的文件、Shell
  或其他工具调用。

子 Agent 内部工具继续逐调用经过现有 Authorizer：

- 继承父 Run 的 Plan/Build 能力上限和当时有效的权限规则；
- 不能获得父 Run 不具备的工具或权限；
- Plan 子 Agent 仍只能在已确认的 Agent 私有空间执行结构化修改；
- Build 子 Agent 仍在普通权限和 Guardrail 边界内执行；
- 子 Agent 的待审批调用通过 Runtime 交给客户端处理；
- 一个子任务等待审批时，其他同级子任务可以继续运行；
- Session 或 Workspace 持久授权形成后，对其作用域中的父 Agent 和其他子 Agent
  同样有效，不增加“仅对子 Agent”权限层级。

子 Agent 不能直接向用户发起业务澄清。缺少必要信息时，它应结束当前任务并在结果中说明
缺失内容，由父 Agent 决定是否询问用户或重新委派。

### 4.8 状态观察与取消

客户端可以通过正式 Runtime 能力：

- 查询一个父 Run 下的子任务列表；
- 查询单个子任务的当前状态和已持久化执行记录；
- 观察子任务创建、开始、等待审批、完成、失败、取消和中断等生命周期变化；
- 指定子任务进行单独取消；
- 取消父 Run 并级联取消其所有未完成子任务和待审批项。

单独取消子任务时，同级子任务继续执行。被取消子任务形成取消结果；全部结果齐备后，父 Agent
仍可继续推理。取消父 Run 时不再调用模型汇总，父 Run 按取消终态结算。

取消沿用现有协作式语义。模型请求和工具应观察取消；不能及时退出的底层操作继续由 Runtime
既有超时和有界关闭机制处理。本版本不提供模型侧取消子任务工具。

### 4.9 持久化与恢复语义

父子执行的持久化遵循“关系状态与执行正文分离”的既有原则：

- Runtime 保存 Session、父 Run 和子任务之间的结构化关系与生命周期状态；
- 主 Conversation 保存父 Agent 发出的 `delegate_task` Tool Call，以及父 Agent 实际收到的
  最终 Tool Result；
- 每个子任务独立保存任务输入、子 Agent 输出、内部工具调用与结果和最终结果；
- 子任务 reasoning、中间文本和内部工具过程不复制到主 Conversation；
- 子任务最终结果同时存在于子任务记录和父 Tool Result 中，因为它是父模型真实看到的
  上下文事实。

Runtime 重启后不自动续跑子任务：

- 尚未完成的父 Run 和子任务进入可解释的中断终态；
- 子任务待审批项失效，旧审批不能在重启后触发工具；
- 已可靠保存最终结果但尚未写回父 Conversation 时，可以通过一致性修复补齐对应结果；
- 未完成的委派调用补齐中断结果，避免主 Conversation 留下无结果 Tool Call；
- 历史子任务的模型调用和工具副作用不自动重放。

确切可靠点、修复顺序和跨介质一致性由技术方案确定。

### 4.10 预算与 usage

委派必须有明确的资源上限，防止模型无限创建并行执行或单个子任务长期占用资源：

- 单个父 Run 可创建的子任务总数受限；
- 同时运行的子任务数量受限；
- 每个子任务具有独立的模型步骤、工具调用、输出和执行时间上限；
- 上限由用户或 Runtime 配置决定，模型不能通过 `delegate_task` 参数修改；
- 达到上限时形成明确失败结果，不静默丢弃任务或无限排队。

父 Agent 和每个子 Agent 分别保存自身实际模型调用产生的 usage。Runtime 不额外保存父 Run
聚合 token 或费用字段；客户端需要展示总消耗时，根据父子关系动态汇总。子任务最终 Tool Result
不需要把 usage 作为模型正文重复传回父 Agent。

具体预算维度、默认值、配置位置和上下文窗口处理进入技术方案。

### 4.11 Runtime Host Web Demo 验证

本版本继续扩展默认关闭的 Runtime Host Web Demo，用于验证正式 Runtime 能力：

- 发起可触发单个和多个并行委派的真实 LLM 任务；
- 展示父 Run 与子任务关联、状态、内部消息和工具活动；
- 处理父任务及子任务中的审批；
- 单独取消子任务和取消父 Run；
- 页面刷新或 SSE 重连后从权威查询恢复状态；
- 分别展示父 Agent 和每个子 Agent usage，并在页面动态计算合计；
- 验证完成、失败、取消和 Runtime 重启中断后的历史重建。

Demo 的树形布局、卡片样式、快捷输入和具体交互文案属于私有验收实现，不进入正式协议或
未来桌面端界面承诺。

## 五、模块边界与契约影响

- `assistant-runtime`：持有父 Run、子任务、并发调度、取消、状态、恢复和权限组合的业务权威；
  负责把子任务最终结果结算为父 Tool Result，并优先复用现有 Session、Run supervisor、
  执行装配和持久化能力。
- `agent-core`：继续执行实现无关的 Agent Loop 和标准 Tool Call/Tool Result；不持有 Session、
  父 Run、子任务业务标识、持久化关系或客户端查询状态。委派如何接入现有工具执行边界由技术方案
  基于真实代码核查确定。
- `agent-tools`：提供模型可见的稳定工具契约或必要能力接缝；不创建 Runtime 子任务、不保存父子
  关系，也不自行处理审批和恢复。
- `apps/runtime-host`：装配子任务存储和 Runtime 所需基础设施，通过 HTTP/SSE 转发用户意图、
  查询和事件；不建立第二份调度或状态权威。
- `assistant-protocol`：承载客户端所需的子任务查询、取消意图、状态和事件投影；不暴露数据库表、
  JSONL 位置、内部任务句柄或模型实现。
- Runtime Host Web Demo：只消费正式查询和事件，不在前端推断子任务终态、权限或恢复结果。
- 正式桌面端：本版本不修改其产品交互，未来通过同一正式 Runtime 能力设计子任务执行树。

## 六、关键取舍

### 6.1 模型侧是工具，Runtime 侧是受管子任务

标准 Tool Call 让模型沿用现有工具调用习惯，也让最终结果自然进入父 Agent 的下一轮上下文。
但子 Agent 自身具有独立循环、状态、取消和持久化，必须由 Runtime 作为子任务管理，不能伪装成
一次普通文件函数调用。

### 6.2 单层、同步、单任务调用

单层委派已经能覆盖并行探索和任务拆分的主要价值。暂不引入递归、后台运行、恢复旧任务和批量
参数，可以避免在首个版本同时建立任务树调度、跨 Run 通知和耐久后台生命周期。

### 6.3 继承能力，但隔离对话

子 Agent 需要与父 Agent 在相同模型、Workspace 和权限事实下工作，但不需要消费完整主对话。
父 Agent 显式提供自包含任务，使主上下文只承担最终结果，降低无关探索过程的 token 占用。

### 6.4 不建立子 Agent 专用权限层

现有 Session、Workspace、Global 和仅本次授权已经表达用户信任范围。新增子 Agent 作用域会让
规则文件、审批选项和用户理解成本同步膨胀；子 Agent 只需保证不能超过父 Run 权限上限。

### 6.5 不提前建设文件协作系统

文件追踪、陈旧读取检测、冲突控制和自动合并是独立能力。首个委派版本只要求父 Agent 拆分互不
重叠的工作并由子 Agent 自报修改，不把使用约定描述为并发安全保证。

### 6.6 usage 保持执行单元原始事实

父 Agent 与每个子 Agent 的 usage 都是实际模型调用事实。父 Run 合计是可以按父子关系计算的
展示数据，本版本不保存第二份聚合值，避免同步和重复计数问题。

### 6.7 子 Agent 是现有执行链的复用装配

子 Agent 与父 Agent 使用同一个 Agent Core、Provider Adapter、Context、Tool Registry、真实
文件/Shell Adapter、Authorizer、Guardrail 和 Recorder 契约。Runtime 只增加父子任务编排、
隔离输入、生命周期和结果回传，不建设一套 child-only 执行引擎或平行基础设施。确实需要不同的
行为时，优先通过现有不可变执行规格和既有能力装配表达。

## 七、验收标准

1. 父 Agent 可以通过一个 `delegate_task` Tool Call 创建一个子任务；调用不允许模型指定
   模型、工具、变体、后台模式、递归深度或预算。
2. 同一父模型响应产生多个 `delegate_task` Tool Call 时，对应子任务可以并行执行；父 Agent
   在结果齐备后继续下一次模型推理。
3. 子 Agent 使用独立对话，只接收委派任务、显式背景和固定环境信息；完整父 Conversation、
   reasoning 和中间工具历史不会复制给子 Agent。
4. 子 Agent 继承父 Run 冻结的模型、Plan/Build 变体、Workspace 和权限上限；不能切换模型、
   自行扩权或创建下一层子 Agent，并复用现有 Agent Loop、Provider、上下文、工具、权限、
   Guardrail 和 Recorder 能力。
5. Plan/Build 父 Agent 获得完全相同的 `delegate_task` Tool Definition；Plan 子 Agent 和 Build
   子 Agent 分别遵守对应能力上限。
6. 每个子任务拥有独立临时工作空间，并与父 Agent、同级子任务共享 Session 所绑定的
   Workspace；需要持久保留的文件进入既有持久目录，任务临时空间不进入 Session 归档，系统
   不宣称提供文件冲突检测、锁或自动合并。
7. `delegate_task` 创建操作经过现有权限体系；允许创建子任务不会自动允许其内部工具，子 Agent
   的文件、Shell 和其他调用仍逐项授权。
8. 一个子任务等待审批时，其他同级子任务可以继续；Session/Workspace 持久授权对相同作用域内
   的父 Agent 和其他子 Agent 生效，不新增子 Agent 专用权限层。
9. 子 Agent 不能直接向用户提问或回复；信息不足时形成明确结果，由父 Agent 决定询问用户、
   重新委派或结束任务。
10. 子任务成功、失败、超时或单独取消都形成与原 `delegate_task` Tool Call 配对的结果；单个
    子任务未成功不会自动导致父 Run 失败。
11. 客户端可以查询父 Run 的子任务列表、单个子任务状态和执行记录，并观察其主要生命周期事件；
    页面刷新或 SSE 重连后可从权威查询恢复展示。
12. 单独取消子任务不取消同级任务；取消父 Run 会级联取消所有未完成子任务和待审批项，且不再
    发起父模型汇总。
13. 主 Conversation 只保存父 `delegate_task` Tool Call 和最终 Tool Result；子 Agent 的任务输入、
    reasoning、文本、内部工具调用与结果保存在独立子任务记录中。
14. Runtime 重启后不自动续跑父 Run 或子任务；未完成任务进入中断终态，旧审批失效，历史工具
    副作用不重放，并通过一致性修复保持父 Tool Call/Result 成对。
15. 单个父 Run 的子任务总数、并发数和单个子任务执行预算均受 Runtime 控制；模型不能修改上限，
    达到上限时得到可解释结果。
16. 父 Agent 和每个子 Agent 分别保留自己的实际 usage；Runtime 不持久化父 Run 聚合 usage，
    Web Demo 能根据父子关系动态展示合计。
17. Session 归档和恢复保留已完成及已中断的子任务关系与执行记录，子任务不作为普通 Session
    独立出现或接受继续输入。
18. Runtime Host Web Demo 能使用真实 LLM 验证单任务委派、并行委派、独立上下文、内部工具
    审批、结果汇总、单独取消、父级取消、刷新恢复和重启中断；Demo 交互不进入正式 UI 契约。

## 八、风险、兼容性与技术交接

### 8.1 风险与缓解方向

- **并行文件冲突**：共享 Workspace 没有锁或变更追踪。通过自包含任务、互不重叠的任务拆分、
  独立私有目录和结果自报降低风险，但不承诺检测冲突。
- **并行成本放大**：一次模型响应可创建多个子任务。必须由 Runtime 设置总数、并发和单任务预算，
  并让客户端分别展示 usage。
- **上下文不足**：子 Agent 不读取完整父 Conversation。父 Agent 必须传递必要背景；信息不足时
  子 Agent 返回缺失内容，不能直接骚扰用户或自行猜测关键约束。
- **结果未经核验**：子任务最终结果是子 Agent 的执行结论。父 Agent仍负责复核关键事实、文件
  修改和外部副作用后再向用户报告。
- **取消与落盘竞态**：子任务可能在取消同时完成模型或工具调用。技术方案必须定义唯一终态、
  可靠结果点和父 Tool Result 结算顺序。
- **跨介质一致性**：父 Conversation、子任务记录和结构化关系分别落盘。技术方案必须保证任一
  可恢复状态都能形成成对、可解释的委派调用与结果。

### 8.2 兼容性

- 旧 Session、Conversation 和 Run 不包含子任务，继续按原样恢复，不创建或推断历史委派记录。
- `delegate_task` 是新增工具；Plan/Build 的现有工具定义在升级后统一增加它，不改变两种变体
  工具定义一致的约束。
- Session、Workspace 和 Global 权限文件沿用既有语义；未配置委派规则时按现有 Ask/Auto
  fallback 处理，不迁移或伪造持久授权。
- 现有普通 Tool Call、审批、pending tool exchange、归档、历史重新输入、模型切换和取消语义
  保持不变；子任务只在父 Run 明确产生委派调用后存在。
- Runtime、Host 和 Web Demo 使用同一正式协议同步演进，不为子任务建立第二套本地传输机制。

### 8.3 功能确认状态

单层委派、同步等待、上下文隔离、权限继承、共享 Workspace、独立临时工作空间、取消、持久化、
异常恢复和 usage 语义已经完成讨论并确认；实现级选择由技术方案承接。

### 8.4 由技术方案承接的事项

- `delegate_task` 的最终模型 Schema、结果编码和与现有并行 Tool Call 的装配位置；
- 父 Run、子任务与独立执行记录的标识、状态机、数据库关系、索引和兼容迁移；
- 子任务 JSONL 或既有记录格式的复用方式、可靠写入点、generation 和父结果结算顺序；
- 子 Agent System Prompt、身份指令、任务输入的具体构造、持久化和 Provider 渲染；
- 子任务临时工作空间的物理位置、创建与清理时点、异常遗留回收，以及需要持久保留的文件
  如何复用既有 Workspace 和 Agent 私有目录；
- 现有 Agent Core、ExecutionSpec、Context、Model、Tool、Authorizer、Guardrail、Recorder、
  Run supervisor 和持久化能力的复用清单，以及确实需要新增的最小编排接缝；
- 模型、工具、Authorizer、Guardrail、Recorder、取消令牌与冻结规则快照的继承和收敛方式；
- 委派审批事实、Session/Workspace 持久规则匹配和子任务待审批投影；
- 子任务并发调度、公平性、父 Run 等待、单独取消、级联取消和 Runtime 有界关闭；
- 子任务总数、并发数、step、tool call、输出 token、上下文窗口和执行超时的配置与默认值；
- 完成、失败、超时、取消、中断和部分可靠落盘时的一致性修复矩阵；
- 子任务查询、取消、事件、错误和 usage 投影的正式协议与 HTTP/SSE 路由；
- Runtime、Host、Protocol、Core、Tool、Store 和 Web Demo 的具体模块边界与验证方案。
