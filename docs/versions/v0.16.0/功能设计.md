## 二、背景与问题

当前产品已具备 Session 附件、稳定文件引用、只读图片预览、模型配置和正式 Agent Tool Loop，
但规范 User Message 只能保存文本、注入文本和文件引用。图片会被当作普通文件告诉模型，无法作为
视觉输入发送给原生多模态模型。像 DeepSeek 这类没有图片输入能力的主模型，也没有一个可调用外部
视觉模型的正式识图工具。

不同模型服务商虽然普遍采用“文本 Part + 图片 Part”的 Chat Completions 形态，但图片来源、
扩展字段和限制并不完全一致：

| Provider | 已确认的基础形态 | 需要隔离的差异 |
| --- | --- | --- |
| OpenAI | User content 数组包含 `text` 与 `image_url`，支持 URL 或 Base64 Data URL | 图片精度 `detail` 位于 `image_url` 内 |
| GLM | OpenAI-compatible 的 `text` 与 `image_url`，官方示例包含 Base64 Data URL | `thinking` 等 Provider 根级扩展 |
| Qwen | `text` 与 `image_url`，支持 URL 或 Base64 Data URL | Part 级 `min_pixels`、`max_pixels` 和高分辨率扩展 |
| Kimi | `text` 与 `image_url`；官方 Chat API 接受对象或字符串形态 | 当前视觉指南以 Base64/文件 ID 为正式路径，并明确公网图片 URL 的限制 |

核查依据：

- [OpenAI Images and vision](https://developers.openai.com/api/docs/guides/images-vision)
- [GLM OpenAI SDK 接入](https://docs.bigmodel.cn/cn/guide/develop/openai/introduction)
- [GLM-4.6V 示例](https://docs.bigmodel.cn/cn/guide/models/free/glm-4.6v-flash)
- [Qwen OpenAI-compatible Chat](https://help.aliyun.com/zh/model-studio/qwen-api-via-openai-chat-completions)
- [Kimi Chat API](https://platform.kimi.com/docs/api/chat)
- [Kimi Vision 指南](https://platform.kimi.com/docs/guide/use-kimi-vision-model)

图片能力接入还会暴露当前 reasoning 兼容层的不足。GLM、Qwen、Kimi、DeepSeek 在
Chat Completions 响应中都可以使用 `reasoning_content`，但开启参数、强度档位和历史 reasoning
回放规则并不相同：GLM 原生接口使用 `thinking` 对象，百炼/Qwen 使用 `enable_thinking` 等根级
参数，Kimi 依据模型使用 `thinking.keep` 或始终保留，DeepSeek 则要求工具调用链完整回传
`reasoning_content`。当前扁平 Profile 主要按 DeepSeek thinking-enabled 形态设计，不能把这些差异
继续压缩成几个字段名和布尔开关。

本版本以 OpenAI 当前开启推理时使用的 `low`、`medium`、`high`、`xhigh`、`max` 五个递增强度名称
作为产品内稳定 key，但不假设每个 Provider 或模型都支持全部档位。用户在会话输入框中看到的是
当前模型协议实际提供的档位文本；不支持的档位不显示。核查依据：

- [OpenAI Model guidance](https://developers.openai.com/api/docs/guides/latest-model)
- [GLM 深度思考](https://docs.bigmodel.cn/cn/guide/capabilities/thinking)
- [GLM 思考模式与历史回放](https://docs.bigmodel.cn/cn/guide/capabilities/thinking-mode)
- [Qwen 深度思考](https://help.aliyun.com/zh/model-studio/deep-thinking)
- [Qwen OpenAI-compatible Chat](https://help.aliyun.com/zh/model-studio/qwen-api-via-openai-chat-completions)
- [Kimi Thinking Models](https://platform.kimi.com/docs/guide/use-thinking-models)
- [DeepSeek Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode/)

与此同时，桌面端存在一个已定位的队列可靠性缺陷：用户手动中断 Run 后，用户暂停与 Runtime
重启恢复使用了同一门禁，后续新消息只排队不执行，行级恢复也只能临时放行一条输入。

当前 macOS arm64 `.app` 和 `.dmg` 已能构建并完成本机验收，但仍使用 ad-hoc 签名，没有
Developer ID、公证和 stapling，不能作为可信的站外分发产物。用户已经注册 Apple Developer
账号，本版本需要把发布能力从“本机可运行”推进到“可验证的 Developer ID 站外分发”。

## 三、版本目标与成功标准

### 3.1 版本目标

1. 将图片建立为 Provider-neutral 的规范用户消息内容，使原生支持图片输入的主模型能够直接理解
   用户附加的图片。
2. 为不支持图片输入但支持 Tool Call 的主模型提供识图工具，由单独配置的多模态模型完成识别，
   再让主模型结合识别文本继续回答。
3. 让用户在发送前能够知道当前 Session 使用“主模型直接识图”“辅助模型识图”还是“当前不可识图”，
   避免静默上传图片或误以为模型已经读取图片。
4. 让支持 thinking 的模型默认开启思考，兼容不同 Provider 的请求参数、reasoning 响应和工具调用
   回放规则；用户可在会话输入框为后续 Run 选择当前模型实际支持的推理强度。
5. 修复手动中断后的队列暂停状态机，使用户发送新消息或显式恢复后回到正常自动串行，同时继续保留
   Runtime 重启后的显式恢复门禁。
6. 使用 Developer ID Application 对桌面应用及随包 Runtime 完成有效签名，通过 Apple 公证并把
   ticket 附加到正式 macOS arm64 分发产物。

### 3.2 成功标准

- 同一张已上传图片无需重新选择，即可随规范 Conversation 持久化、恢复、重放和 Fork；
  Conversation 与 SQLite 中不保存图片 Base64 正文。
- 静态模型目录或用户 override 明确支持图片输入的模型走原生图片 Part；不支持图片输入的主模型只能
  在满足工具与辅助模型条件时走识图工具，Desktop/Core 不按模型名称自行猜测能力。
- 识图工具只接受图片路径、目标和可选背景；辅助模型一次调用直接返回文本，不在工具内部再发起
  第二次总结调用。
- 图片缩略图显示在用户消息正文上方，点击后复用现有附件预览弹窗；识图工具复用现有工具执行卡片。
- 支持 thinking 的模型默认启用思考；GLM、Qwen、Kimi、DeepSeek 的开启参数、响应解码和必要历史
  回放由对应模型协议正确处理，不由 Runtime 或 UI 拼接原生请求字段。
- Composer 提供会话级 effort 选择器，包含“默认”和当前模型实际支持的协议档位；选择在后续 Run
  开始时冻结，模型切换遇到不匹配时只向下选择可用档位，否则回到“默认”。
- 手动中断后再次发送消息可以恢复自动串行，不再出现 Session 永久停在“等待继续”的状态。
- 交付的 macOS arm64 DMG 能通过签名、公证、ticket 和 Gatekeeper 检查，并能从 DMG 安装后启动
  Desktop 与随包 Runtime。

- 自研 OCR 引擎、CV 推理服务或本地视觉模型；OCR 只是多模态模型可能返回的识别内容；
- 把所有附件自动转成图片、PDF 逐页转图或 Office 文档截图；
- 把浏览器、computer-use 或其他 Agent 工具在执行中生成的截图/图片作为多模态 Tool Result 回传；
- 接入 OpenAI Responses API，或把现有模型协议从 `openai_chat_completions` 切换为
  `openai_responses`；上述两项已记录到
  [`v0.17.0 输入`](../../inputs/260819-Agent工具图片回传与Responses-API.md)；
- 允许主模型直接控制 Provider 私有的 `detail`、像素上下限或其他视觉调优参数；
- 强制识图模型输出 JSON Schema，或提供面向程序消费的通用视觉结构化 API；
- 自动选择价格最低、质量最高或跨 Provider 动态路由的辅助视觉模型；
- thinking 的会话级开关、模型设置页中的 thinking/effort 默认值、消息级临时 effort 覆盖；
- 在 Desktop 暴露 `thinking`、`enable_thinking`、`thinking_budget`、`reasoning_effort` 等原生请求字段；
- Skills、MCP、插件、后台自动化和计划任务；
- Mac App Store 上架、Apple Distribution 签名、自动更新、发布网站或 CI/CD 发布流水线；
- Windows/Linux 签名与安装包，以及 macOS x86_64 或 Universal Binary；
- 修改 Runtime 与 Desktop 的双进程产品拓扑。

## 五、核心概念与能力判定

### 5.1 统一文件引用与公共图片处理

图片继续归入规范 User Message 现有的有序文件引用 Part，不新增与文件引用平行的图片 Part。
`FileReference` 只保存统一的资源身份，不增加图片宽高或图片类型字段；图片只在模型调用
边界由服务端读取实际内容、执行公共预处理后，再按当前能力投影成 Provider 图片 Part。

文件引用继续只表达：

- 原始文件名和 Runtime 分配的稳定可读资源；
- 用户选择的顺序；Part 身份继续由现有 File References Part 持有。

普通文件与图片保存在同一个文件引用列表中并保持原始顺序。不需要引入第二套资源类型，也不批量
改写历史 Conversation；历史附件在首次缩略图请求或模型调用时按实际内容识别。

Runtime Host 在真正调用模型前读取资源并验证可用性，实时提取 MIME、宽高和像素总量，按一套覆盖
所有目标模型的公共策略完成方向校正、色彩转换、等比缩小和 JPEG 编码。原生多模态和辅助识图必须
复用同一预处理结果，不允许按 Provider 分别维护缩放、压缩或转码方案。

附件 Blob 可以保存由服务端按实际内容检测的通用 MIME 类型，并向 Desktop 投影；它是所有文件共有
的内容事实。图片宽高和像素总量只在缩略图生成或 LLM 预处理时实时提取，不写附件表或 Conversation。

公共预处理结果只服务本次调用，并以 Base64 Data URL 作为 OpenAI、GLM、Qwen、Kimi 的共同传输
基线；不会依赖公网 URL，也不会把结果写入 Conversation、SQLite、配置、日志或普通调试事件。
原始附件保持不变；转换失败、图片损坏或资源缺失必须形成明确错误，不能静默省略图片继续请求。

缩略图继续持久化为原始 Blob 同目录下的派生文件，名称使用 `<原 Blob 文件名>.thumbnail.jpg`；不在
附件表增加缩略图路径或尺寸字段。历史缩略图缺失时按查看请求生成，不批量修改数据库。

### 5.2 模型图片能力

模型能力由 Runtime Host 按精确 `(provider, protocol, model_id)` 从随包静态目录解析，用户显式
capability override 优先。`provider` 只表示实际推理服务，同一 Provider 可以同时提供纯文本模型和
视觉模型；协议兼容模式继续使用已有术语 `protocol`，并作为能力映射键的一部分，不再称为另一种
Provider。

随包目录是软件发布资源 `model-catalog.json`，不属于用户 `config.toml`，也不提供界面或文件级编辑
入口；厂商模型资料变化通过更新目录并发布新软件版本交付。

当前 Session 的识图路径按以下顺序确定：

1. 编译后的主模型能力支持图片输入：使用原生多模态路径。
2. 主模型不支持图片输入，但支持 Tool Call，且已配置一条有效的辅助视觉模型：使用识图工具路径。
3. 以上条件都不满足：图片仍可作为普通附件保存和操作，但界面明确提示当前组合不具备识图能力。

辅助视觉模型复用已有模型配置和 credential 管理，不建立第二套明文密钥来源。用户可以从编译后明确
支持图片输入的模型中指定默认识图模型；配置缺失、失效或错误时，识图工具不可用并提供可诊断原因。

### 5.3 模型协议适配

规范文件引用不携带 `image_url`、`detail`、`min_pixels`、Provider 文件 ID 或任何 Provider 原生字段。
`model_key` 表示用户创建的模型配置实例及 Session 稳定引用；模型 Route 的 `provider` 只表示实际
服务身份，Endpoint 和 credential 是该配置实例的连接信息。`protocol` 选择基础协议族，
`provider + protocol` 共同选择协议适配，由 Adapter 把同一规范消息编码成 OpenAI、GLM、Qwen、Kimi
或其他兼容服务接受的请求。

多模态差异不继续扩充当前扁平 `Profile` 的布尔值和可选字段集合。现有 Profile 如何与新的具名
模型协议衔接或迁移，属于技术方案；无论采用何种代码结构，兼容判断都必须集中在模型
服务装配与 Codec 边界，不能散落到 Core、Runtime 或 UI。

Profile 重构必须保持以下职责归属：Provider 身份、protocol 选择、Endpoint 和 credential 属于模型
Route；图片 Part、max-output 字段、reasoning 请求/响应字段、工具 Schema 和 usage 统计形态属于协议适配；
temperature、top-p、stop、tool choice、图片输入和可选 effort 属于模型及模式能力；历史 reasoning
是否丢弃、只在工具链保留或全部保留属于 reasoning 回放策略。不能再用“响应中是否存在某字段”
反推出完整模型能力，也不能用一个 `supports_*` 布尔值表示随 thinking 模式变化的条件限制。

现有模型配置里的 `protocol = "chat_completions"` 保留字段名，但协议值需要细化。本版本配置 schema
升级时，迁移器把旧值转换成 `openai_chat_completions`；新配置显式保存 `protocol` 并参与静态目录
匹配。当前只有一个协议选项时界面可以默认选中，但系统仍只保留并持久化这一套协议字段。

静态目录未收录的 `(provider, protocol, model_id)` 保留当前 `protocol`，并采用该协议的保守能力基线，
关闭未知图片/reasoning 能力；协议本身没有实现时配置无效，不能静默改用 OpenAI 协议。高级用户可以
显式 override capability。服务私有调优参数继续走受控协议 Adapter 或服务私有 options，不反向污染
规范消息。

### 5.4 Thinking、reasoning 与会话 effort

支持 thinking 的模型在本版本默认开启思考。产品不提供关闭入口，也不把 thinking 开关写进模型
配置；不同 Provider 是否需要显式开启参数、默认是否已经开启，均由模型服务装配后的协议保证，不能
依赖服务商默认值偶然一致。暂不支持 thinking 的模型不伪造 reasoning 能力。

产品内 effort 使用五个稳定 key 表达从低到高的相对强度：`low < medium < high < xhigh < max`。
“默认”是独立状态，表示 Session 不保存显式强度，由当前协议选择该模型的默认开启档位；目标服务
默认已开启时可以省略强度，默认会关闭思考时必须显式发送一个有效开启档位。它不是
第六个强度档位，也不等同于关闭 thinking。五个 key 只用于保存会话意图、排序和跨模型降级；它们
不承诺不同模型在同名档位下具有相同 token、延迟或质量。

每条有效模型服务向 Runtime 提供当前实际可用的 effort 选项。每个选项包含稳定 key 和由对应协议
提供的显示文本；Desktop 原样展示这些文本，不自行翻译 API 映射，也不展示该模型不支持的档位。
随包静态模型目录的每个三元组条目可以提供 `effort_map`，以稳定 key 映射显示文本和受限 wire value；
map 的 key 就是该模型的实际支持列表，不再同时维护另一份 effort 数组。wire value 在配置编译后只
进入 Adapter 私有映射，不进入应用协议或前端状态。

effort 是 Session 权威配置，入口位于 Composer 输入框工具区：

- 新建 Session 初始为“默认”；修改后只影响该 Session 后续启动的 Run。
- Run 启动时冻结当前 effort；执行中的 Run 不受随后修改或模型切换影响。
- Session 切换模型时，如果当前 effort 仍可用则保持不变；否则按五档顺序选择不高于原档位的最高
  可用档位，并在同一次 Session 状态变更中更新配置。
- 如果没有可向下降级的档位，或新模型完全不支持 effort，则回到“默认”；不得自动向上选择更强档位，
  也不得保留一个 UI 不可见但仍会影响请求的失效值。
- effort 变更和模型切换都由 Runtime 校验、持久化并投影最新 Session 状态，Desktop 只发送意图。

模型协议还必须明确 reasoning 响应字段和历史回放策略。共同的 `reasoning_content` 可以继续解码
为规范 Reasoning Part，但工具调用链或跨轮次是否必须回传、是否保留全部历史以及开启/强度参数如何
编码，必须由 GLM、百炼/Qwen、Moonshot/Kimi、DeepSeek 等具名协议分别处理。不能用统一占位文本
替代目标服务要求的原始 reasoning，也不能因目标协议不支持回放而破坏 Tool Call/Result 配对。

## 六、功能范围与使用路径

### F01 图片选择、上传与消息呈现

**用户目标**：像附加普通文件一样选择图片，并在发送前后清楚确认选择了哪些图片。

- 继续复用现有系统文件选择、流式上传、Session Attachment 和发送幂等链路。
- 图片与非图片附件可以出现在同一条用户输入中；图片保持用户选择顺序。
- 上传阶段根据文件内容验证实际图片类型和基本元数据。无效图片、超限、读取失败和格式不支持都提供
  附件级错误，不因其中一张图片失败而假装整条消息已正确发送。
- 已发送用户消息的图片以缩略图条显示在消息正文上方；正文仍使用现有文本展示。
- 点击缩略图复用现有 `AttachmentPreviewDialog`，继续支持只读预览、系统打开和在目录中显示。
- 非图片附件保持当前附件样式，不强行转换成缩略图。
- 历史图片资源不可用时保留消息和文件名，缩略图显示不可用占位，点击后沿用现有安全错误处理。

### F02 识图路径提示

**用户目标**：发送图片前知道图片将由谁处理，以及当前配置是否具备识图能力。

- Composer 根据当前 Session 冻结模型和当前有效配置显示简洁能力提示：
  “当前模型直接识图”“将通过 `<辅助模型>` 识图”或“当前配置不可识图”。
- 该提示是 Runtime 能力投影，不由 Desktop 根据 Provider 名称推测。
- 切换空闲 Session 的模型、重新加载配置或辅助视觉模型失效后，提示随权威快照更新。
- “当前配置不可识图”不阻止用户把图片作为普通文件附件发送，因为用户仍可能需要复制、移动或让
  文件工具处理它；但界面不能暗示模型已经看到了图片内容。
- 无论原生还是辅助路径，图片字节都会发送到对应外部模型服务。界面应让用户能识别目标模型，
  不在失败回退时静默换用另一个 Provider。

### F03 原生多模态主模型

**用户目标**：在支持图片输入的模型 Session 中直接询问截图、照片、图表或界面内容。

1. 用户提交包含文字和图片的消息。
2. Runtime 把文字和现有统一文件引用作为同一条规范 User Message 持久化，不写入图片尺寸。
3. 模型调用准备阶段由 Host 公共预处理器临时读取并转换有效图片资源，Adapter 只按照当前 Provider
   协议 Adapter 把同一 JPEG 结果编码为原生图片 Part；Adapter 不访问文件系统或预处理图片。
4. 主模型在正常 Agent Loop 中直接返回文本、Reasoning 或 Tool Call；现有流式展示、取消、重试、
   usage 和持久化规则保持不变。

多轮恢复、上下文压缩、Run 重试和 Session Fork 必须继续使用规范文件引用和 Runtime 的稳定资源
解析，不能依赖最初上传请求中已经失效的客户端临时路径或一次性 Provider 文件 ID。历史图片进入
后续模型请求的具体上下文选择和成本估算由技术方案在既有 Context 系统边界内确定。

只要包含图片的历史用户消息仍被选入上下文，原生视觉模型路径就必须从稳定文件引用重新生成图片
输入，不能只保留历史文字；但不得把上一次请求的 Base64、Data URL 或 Provider file ID 原样持久化
和回放。文本主模型路径不接收图片输入，继续通过历史识图工具结果或新的工具调用理解图片。

### F04 文本主模型的识图工具

**用户目标**：继续使用 DeepSeek 等文本主模型，同时按需调用另一条多模态模型识别图片。

当主模型不支持图片输入但支持 Tool Call，且默认辅助视觉模型有效时，Runtime 为本次执行装配普通
识图工具。统一文件引用中的图片在线上编码为包含名称和稳定路径的文本引用，使主模型能够选择图片
并调用工具，而不是把二进制图片错误发送给文本模型。

首版工具输入固定为：

```text
image_paths: Vec<String>    必填，要识别的一张或多张图片
goal: String               必填，同时描述识别目标、关注点和期望表达方式
background: Option<String> 可选，仅提供图片之外的必要上下文
```

`goal` 同时承担“看什么”和“怎样回答”的职责，例如：

```text
识别图片中的表格，并按 Markdown 表格输出；无法确认的单元格标记为 unknown。
```

首版不提供 `focus`、`expected_output`、`detail` 等重复或 Provider 私有参数。需要关注的区域和输出
要求都写进 `goal`；主模型没有额外背景时可以省略 `background`。

工具执行链固定为：

1. 主模型发出一次识图 Tool Call。
2. 工具验证路径、权限、资源类型和辅助模型能力。
3. 工具根据 `goal` 和可选 `background` 组织视觉请求，只调用一次辅助多模态模型。
4. 辅助模型直接返回文本；内部提示要求尽量包含与目标相关的观察、必要 OCR、无法确认项和不确定性。
5. 工具以普通文本 Tool Result 回给主模型，不在工具内部增加第二次总结调用。
6. 主模型结合 Tool Result 继续正常 Agent Loop，生成最终用户回答。

首版不强制辅助模型输出 JSON。模型、Provider、usage、结束原因、超时、错误和重试事实进入受控的
工具详情与观测数据，不混入模型可见的识别正文。未来确有程序化消费需求时，再单独设计显式
`output_schema`，不重新引入语义含糊的 `expected_output`。

识图工具必须走普通 Tool Registry、Dispatcher、授权、取消、有限建立重试、超时和工具审计链路。
读取 Session 附件或 Workspace 图片时遵循现有文件访问边界；向外部视觉 Provider 发送图片是实际
数据外发，不得绕过当前 Plan/Build、Ask/Auto 和权限决策。工具调用在消息流中继续使用现有工具卡片，
详情至少能说明图片数量、目标、实际辅助模型、结果状态和 usage，但不展示 credential 或图片 Base64。

### F05 识图失败与不确定性

- 图片缺失、损坏、类型不支持、超过 Provider 限制或临时转换失败时返回稳定错误，保留原消息和附件。
- 辅助视觉模型未配置、配置失效、不支持图片或连接失败时，识图 Tool Result 明确失败，不自动换用
  未经用户选择的其他模型。
- 用户取消父 Run 时，正在进行的原生多模态调用或辅助视觉调用都应收到取消并按现有规则可靠收敛。
- 辅助模型已开始输出后发生流中失败，不透明重试整次识图，避免重复费用和不一致结果；建立前重试
  继续遵守现有有限重试策略。
- 视觉模型结论不被包装成确定事实。无法确认、文字模糊或图片信息不足时，结果应明确说明限制；
  主模型不得把工具失败伪装成已经完成识别。

### F06 会话级推理强度

**用户目标**：在不修改模型连接配置的前提下，为当前会话后续回答选择合适的推理强度。

- Composer 输入框工具区提供 effort 选择器；thinking 仍默认开启，不在本版本提供开关。
- 当前模型存在可选 effort 时，选择器包含“默认”和 Runtime 投影的有效档位；完全不支持 effort 时
  不显示选择器。Desktop 不维护 Provider、模型名称或 effort 映射表。
- 选项直接显示当前协议提供的文本，稳定 key 仍使用 `low`、`medium`、`high`、`xhigh`、`max`。
  Provider 接受的原生字段名、枚举或预算值不向用户暴露。
- 用户选择后，Runtime 更新并持久化 Session effort；下一次发送、重试或 continuation 创建新 Run 时
  使用更新后的值，已经运行中的 Run 保持其启动快照。
- 模型切换导致档位不匹配时自动向下降级。例如 `max` 切到最高仅支持 `xhigh` 的模型后使用
  `xhigh`；`medium` 切到只支持 `low/high/max` 的模型后使用 `low`。没有更低可用档位时回到“默认”。
- 自动降级后的值就是新的 Session 配置，界面随权威快照更新；不在后台保留切换前的隐藏 effort。
- 当前模型完全不支持 effort 时，选择器隐藏，协议适配仍保证支持 thinking 的模型默认开启。

连接验证也必须使用当前模型协议的默认 thinking 语义，但不能读取某个业务 Session 的 effort。真实
Run 的 request、重试 attempt 和同一 AgentExecution 后续 Model Step 必须复用 Run 启动时冻结的
effort，不在执行中自行升降档。

### F07 手动中断后的队列恢复

**用户目标**：中断当前回答后，可以直接发送新的要求或恢复某条排队输入，不让 Session 永久卡住。

本版本把“用户手动暂停”和“Runtime 重启后等待显式恢复”恢复为两个独立状态：

- 用户点击中断：取消当前 Run，并暂停自动领取下一条排队输入；不设置 Runtime 重启恢复标志。
- 中断后提交新消息：新消息仍进入队尾；同一次提交清除用户暂停并唤醒队列。若已有积压，先执行原
  队首，再按 FIFO 自动串行到新消息；若无积压，新消息直接成为队首并开始执行。
- 恢复指定排队输入：将目标移动到队首，清除暂停并恢复整个队列的自动串行，而不是只放行这一条。
- 恢复整个队列：清除暂停但不改变现有顺序，从当前队首继续自动串行。
- 重试被中断的 Run：视为用户显式继续，清除用户暂停；Runtime 重启恢复所需的一次性通行证语义
  保持独立。
- Runtime 重启恢复：继续保持 `resume_required`，新提交输入不能解除该门禁，防止未知历史副作用
  自动继续；用户必须显式恢复整个队列或按现有重试语义处理。
- “拒绝并停止本轮”在停止父 Run 时同步进入用户暂停，避免队列紧接着执行后续输入。

Desktop 不增加新的常驻队列区域。现有 QueueDrawer 行级恢复继续使用；Runtime 重启后需要恢复时，
界面提供可到达的整体继续入口。`resume_session` 与 `resume_queued_input` 的协议合并属于技术方案，
但产品层只保留一个“恢复队列”意图，其中目标输入可选。

Desktop 与随包 Runtime 均可正常启动。

本版本的正式发布目标是 macOS arm64 站外分发：

1. 使用有效的 Developer ID Application 身份签署随包 Runtime、Desktop 主程序和完整 `.app`；
   嵌套可执行内容必须全部处于有效签名链中。
2. 启用 Apple 公证要求的 Hardened Runtime、secure timestamp 和最小必要 entitlements；发布产物
   不携带允许调试的 `get-task-allow`。
3. 生成并签署当前正式 DMG，把最终分发容器提交 Apple notary service。
4. 公证成功后把 ticket staple 到正式分发产物，并保留 submission ID 和脱敏验证结果作为验收证据。
5. 对最终 DMG 而不是中间构建目录执行完整性、签名、Gatekeeper 和 stapler 验证，再完成从 DMG

## 七、模块边界与契约影响

### 7.1 `agent-types`

- 保持现有 `FileReference` 最小结构，不新增图片专用 User Part 或图片宽高字段；
- 不包含 Attachment ID、图片正文、Base64、Provider URL、文件 ID 或视觉参数；
- 继续保证 Conversation 序列化、持久化重放和 Part 顺序稳定。

### 7.2 `agent-model`

- 在模型能力中显式表达图片输入支持；
- 保留 Provider-neutral 的 reasoning 请求语义，并表达模型当前可用的 effort key；
- 定义公共图片预处理契约，由 Runtime Host 提供唯一实现；
- 单次 Model Turn 继续只接受语义消息，不携带 Runtime Attachment、credential 或 Provider 路由；
- 不负责读取图片文件或决定辅助视觉模型。

### 7.3 `agent-openai-compatible`

该 crate 由 `agent-provider-openai-compatible` 重命名，只负责 OpenAI-compatible 模型协议适配，不再
使用 Provider 命名。

- 把 Host 公共预处理器生成的相同 JPEG 输入编码为具体 Provider 接受的图片 Part；
- 只处理 wire 字段差异，不读取、解码、缩放、压缩或转码图片；
- 以具名协议编码 thinking 开关与 effort，解码 `reasoning_content`，并按 Provider 规则回放历史
  reasoning；
- Provider 差异集中于具名协议/Codec，不在 Core、Runtime 或 UI 按名称分支；
- 继续保证 wire 观察脱敏，不记录 Authorization，也不把图片 Base64 写入普通可持久化诊断。

### 7.4 `agent-tools`

- 承载模型可见的稳定识图工具定义、输入 Schema 和能力抽象；
- 不绑定具体视觉 Provider、credential、Runtime 配置或本地文件 I/O；
- 工具结果继续使用现有文本 Tool Result 契约。

### 7.5 `assistant-runtime`

- 持有模型图片能力、辅助视觉模型选择、每次 Run 工具装配、权限、usage、取消和审计语义；
- 持有 Session effort 权威状态、模型切换时的向下降级、Run 冻结和模型协议装配；
- 在 Session/Run 冻结规则下决定原生或工具路径，不让 Desktop 成为路由权威；
- 修复用户暂停与重启恢复两套队列状态的迁移和恢复行为；
- 对统一文件引用、消息兼容和公共图片处理提供应用级不变量。

### 7.6 `runtime-host`

- 实现原图受控读取、调用期 MIME/尺寸探测、唯一公共预处理、Base64 编码和具体辅助模型 Adapter；
- 在 Blob 同目录生成、读取和清理 `<原 Blob 文件名>.thumbnail.jpg` 派生缩略图，不写附件表；
- 在模型工厂中按编译后的 `protocol` 选择明确协议适配，不持有第二份 Session 或模型路由状态；
- 保持上传、资源读取、大小限制、临时文件清理和 credential 的安全边界。

### 7.7 `assistant-protocol`

- 向 Desktop 投影附件实际 MIME 和识图路径所需的最小能力事实，不投影图片像素尺寸；
- 投影 Session 当前 effort、当前模型实际可选的稳定 key 与协议显示文本；不投影原生 wire 字段；
- 模型设置支持指定辅助视觉模型，但不要求编辑图片/reasoning capability，也不暴露请求对象或 credential；
- 队列恢复命令收敛时检查所有生产者、消费者、序列化和生成 TypeScript 类型。

### 7.8 Desktop 与 Tauri

- Desktop 只展示 Runtime 的能力判定、图片缩略图、会话 effort 选项、工具详情和错误状态；
- Composer 承载会话 effort 选择器；模型设置页不增加 thinking 或 effort 字段，前端不复制协议映射；
- 复用现有附件选择、上传、预览弹窗和工具卡片，不建立前端图片正文缓存或模型直连；
- Tauri 原生层继续只通过稳定资源身份执行预览/系统打开；
- 发布配置负责 macOS bundle、Developer ID、公证和最终产物验证，Runtime sidecar 不能漏签。
- 左侧会话列表搜索固定为当前列表中的会话标题匹配，不显示“当前会话/工作区/全局”等范围选择，
  也不搜索消息正文；Agent 使用的 Conversation Recall 和 Runtime 全文检索契约保持不变。

## 八、关键取舍

1. **文件资源统一、wire 投影独立**：图片首先是现有附件和文件资源，只在模型调用边界经过公共预处理
   后投影成 Provider 图片 Part；不为供应商协议在规范 Conversation 中复制图片引用或元数据类型。
2. **持久化引用，不持久化 Base64**：避免 Conversation/SQLite 膨胀、重复复制、日志泄漏和迁移成本；
   图片正文继续由既有 Attachment 资源管理。
3. **本地图片首版使用调用期 Base64 Data URL**：这是当前四家文档中最稳定的直接传输交集，
   不依赖公网 URL 生命周期；所有 Provider 使用相同 JPEG 预处理结果，文件上传优化留待后续真实需求。
4. **能力查表编译，用户覆盖优先**：随包静态目录以精确 `(provider, protocol, model_id)` 提供已核实能力；
   用户 override 只用于自定义或尚未收录模型，未知组合按当前协议的能力基线保守降级。
5. **协议参与查表，不扩充扁平 Profile**：图片、thinking 开启参数、effort 编码、reasoning
   回放、generation 限制和 usage 字段分别归入明确协议或模型能力，避免 Profile 继续积累互相
   耦合的字段名与布尔开关；具体拆分结构由技术方案确定。
6. **OpenAI 五档只作为稳定 key**：使用 `low`、`medium`、`high`、`xhigh`、`max` 保存会话意图和
   排序，不把它们误称为所有模型共同支持的五档；UI 只显示当前协议实际提供的文本。
7. **不匹配只向下降级**：模型切换不能暗中提升成本和延迟；没有更低可用档位时回到 Provider 默认，
   不保存隐藏失效值。
8. **原生路径优先**：主模型能直接看图时不默认增加识图 Tool Call、第二模型费用和信息损失；
   辅助工具只解决文本主模型的能力缺口。
9. **识图工具最简输入**：`goal` 已能同时表达关注点和输出要求，删除 `focus` 与
   `expected_output`；`background` 仅在存在额外上下文时提供。
10. **辅助模型直接返回文本**：视觉调用不强制 JSON，也不在工具内部增加总结调用；主模型本就会在
   Agent Loop 下一步消费结果并组织最终回答。
11. **识图仍是普通工具**：不引入绕过 Registry、权限、取消、超时和审计的隐藏模型调用通道。
12. **用户暂停与恢复暂停分离**：手动中断是用户可通过新输入解除的短暂停顿；Runtime 重启可能伴随
    未知副作用，必须继续显式恢复。
13. **先完成站外可信分发**：当前产品已有 DMG 基线，Developer ID + notarization 是最短闭环；
    Mac App Store、自动更新和 CI 发布具有不同证书、审核和运维边界，不混入本版本。

## 九、验收标准

### 9.1 图片消息与兼容

- [x] 图片与文本能作为同一条规范 User Message 持久化、恢复、重试和 Fork，重启后引用仍有效。
- [x] Conversation、SQLite、配置、日志和普通调试事件不保存图片 Base64 正文。
- [x] 实际 MIME、大小和顺序经过验证并可供 Runtime/Desktop 使用；宽高和像素总量在缩略图或 LLM
  预处理时实时校验但不持久化；损坏或缺失不被静默忽略。
- [x] 旧 Conversation 和旧 Attachment 数据无需人工修改即可读取；旧普通文件引用不被错误追溯转换。
- [x] 至少使用官方协议 fixture 覆盖 OpenAI、GLM、Qwen、Kimi 的图片请求编码差异，并验证
  `用户 capability override > 三元组静态目录 > 当前协议保守能力基线` 的解析优先级。

### 9.2 原生多模态路径

- [x] 声明支持图片输入的主模型能接收单图与多图，并结合用户文本返回可观察结果。
- [x] 原生多模态调用继续支持流式输出、取消、有限建立重试、usage、上下文恢复和错误分类。
- [x] Provider 不支持的类型、大小或字段在请求前或结构化 Provider 错误处失败，不降级成无图请求。

### 9.3 Thinking、reasoning 与 effort

- [x] 支持 thinking 的 GLM、Qwen、Kimi、DeepSeek 模型默认启用思考，请求使用各自协议
  要求的开启参数，响应 reasoning 能稳定解码为规范 Part。
- [x] 非流式与流式 fixture 覆盖 `message.reasoning_content` 和 `delta.reasoning_content`；thinking
  关闭入口不进入本版本。
- [x] 工具调用链按 Provider 规则完整回放必要 reasoning；需要保留全部历史、只保留工具链或忽略
  旧 reasoning 的模型均有独立 fixture，不能用通用空格占位冒充原始内容。
- [x] Composer 显示“默认”和当前模型实际支持的 effort 协议文本；不支持的档位不显示，模型设置页
  不出现 thinking/effort 配置。
- [x] 静态目录和高级 override 的 `effort_map` 能把稳定 key 映射为 label 与受限 wire value；无效 key、
  空 label、错误 wire 类型、重复实际强度和不存在的默认 key 均在配置编译期失败。
- [x] Session effort 使用 `low/medium/high/xhigh/max` 稳定 key 持久化，下一 Run 冻结使用；执行中的
  Run 不因配置变化而改变。
- [x] 模型切换遇到不匹配档位时按稳定顺序向下降级，并更新 Session 权威状态；没有向下候选时回到
  “默认”，不会自动向上提升或保留隐藏失效值。
- [x] Adapter 按模型协议编码实际 wire 参数；Desktop、Core 和规范 Conversation 不包含
  `thinking_budget`、`enable_thinking` 等供应商私有配置。

### 9.4 识图工具路径

- [x] 文本主模型在 Tool Call 和辅助视觉模型均可用时获得识图工具；其他组合显示明确不可用原因。

- [x] 单图、多图、OCR 目标、无额外背景、不确定结果、资源缺失、辅助模型失败和用户取消均有测试。
- [x] 工具调用经过普通授权、审计和工具详情链路；usage 能区分主模型与辅助视觉模型且不重复计算。
- [x] 原生模型与工具路径不会因失败而静默切换 Provider。

### 9.5 Desktop 交互

## 十、风险、兼容性与后续设计要求

### 10.1 Provider 与图片成本

- Provider 的图片格式、数量、尺寸、像素和 token 计费存在差异，并可能随模型变化。技术方案必须
  基于当前官方文档建立可维护限制和 fixture，不把某一家上限写成全局事实。
- Base64 会扩大单次 HTTP 请求体；必须限制图片数量、单图大小、总请求体和内存峰值，避免 Runtime
  同时复制多份大图片。
- 视觉模型可能误读 OCR、图表或细节。内部提示和最终回答需要保留不确定性，但不能声称提供确定性 OCR。

### 10.2 隐私与数据外发

- 原生和工具路径都会把图片发送给外部 Provider。能力提示、模型选择、权限和工具详情必须避免
  用户不知道实际目标服务。
- 图片正文、Base64 和 credential 不进入普通日志、错误、Debug Viewer 或持久 Trace；若完整
  Provider Trace 未来需要记录图片，必须另行设计显式敏感数据策略，本版本默认排除。

### 10.3 Reasoning 协议与强度兼容

- 同名 effort 只表达相对顺序，不保证跨模型的实际 token、延迟或质量一致；UI 显示当前协议文本，
  但不能暗示不同 Provider 的 `high` 具有相同效果。
- Provider 支持范围会随模型版本变化。技术方案需要把“稳定 key”“模型实际选项”和“wire 编码”
  分层，并通过 fixture 固定当前已核查行为；只有 Runtime Host 的版本化静态目录可以按精确
  `(provider, protocol, model_id)` 解析，Desktop 或 Core 不得按模型名称前缀判断。
- reasoning 历史会增加上下文和费用，错误丢弃又可能破坏工具调用。回放策略必须参与上下文布局、
  压缩和重试核查，确保仍需回传的 reasoning 不被摘要或协议切换意外破坏。
- 当前 Conversation 可能包含由另一 Provider 产生的 Reasoning Part。技术方案必须定义目标协议的
  可移植投影与失败边界，不能把 Provider 私有状态当成普通文本拼进用户可见正文。

### 10.4 兼容与迁移

- 规范 User Part、Attachment 元数据、模型能力、配置和应用协议都会演进。技术方案必须逐一核对
  生产者、消费者、序列化、旧 Conversation、SQLite migration、配置缺省值和生成 TS 类型。
- 旧模型配置默认不声明图片输入，也不自动指定辅助视觉模型；升级后行为可诊断但不能凭名称自动开启。
- 若需要数据库 schema 迁移，实施时必须遵守根 `AGENTS.md` 数据库规则，先明确实际数据库、表、
  影响范围、备份和验证方案；本功能设计不授权执行任何生产数据写操作。

### 10.5 Apple 发布依赖

- Apple 公证依赖有效会员、证书私钥、Team ID、网络和 Apple 服务。账号已注册不等于证书和公证
  credential 已就绪；实施前必须只读核查，不得在文档中假设已经成功。
- 公证是外部服务步骤，失败时必须保存 submission ID 和脱敏日志、停止发布，不用 ad-hoc 或跳过
  stapling 的包冒充正式产物。
- 当前只验收 macOS arm64。未来增加 x86_64/Universal、CI 或自动更新时，需要重新设计签名身份、
  多架构 sidecar、secret 管理和发布回滚。

### 10.6 后续设计文档判断

本版本必须继续编写独立技术方案，因为它涉及规范消息、模型能力、模型协议、配置、持久化、
应用协议、工具授权、队列状态机和 macOS 签名链。技术方案必须基于真实源码和依赖核查确定类型、
迁移与分里程碑验证路径。

本版本不单独创建界面交互设计指导。图片缩略图复用现有消息附件区和预览弹窗，识图过程复用工具卡片，
会话 effort 选择器复用 Composer 现有工具区和选择控件，队列复用现有 QueueDrawer，能力提示和视觉细节继续遵循
[`桌面端设计语言`](../../resources/桌面端设计语言.md)。若技术方案发现需要新增复杂的模型路由设置页或
改变 Composer 主结构，再补充专题交互指导并重新确认。

## 十一、确认结论

功能范围与技术方案均已按会话讨论确认，当前没有遗留产品开放问题。版本进入 `计划中` 并编写
`v0.16.0` 开发计划；开发计划确认前，不修改代码、数据库或签名配置。
