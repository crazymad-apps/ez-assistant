## 二、台账与实施原则

1. 按 M0—M7 依次实施。用户已于 2026-08-19 明确授权 M1—M5 连续实施、自主验证且中途无需确认，
   因此该范围完成后统一汇报；M6 已完成 Developer ID、公证与验证链路，用户同意进入 M7；用户于
   2026-08-19 明确当前不发版，最终源码发布件和干净环境 smoke 延后到实际发版时执行。
2. 开发计划确认后、开始 M0 前，先把 [`版本管理`](../../版本管理.md) 状态从 `计划中` 更新为`开发中`，
   并从模板初始化或续写本地 `docs/开发进度.md`。计划确认不等于批准后续全部里程碑。
3. Runtime 继续持有 Session、Run、输入队列、模型能力、effort、附件和持久化的权威状态；Desktop
   只发送意图并展示投影，不能推测协议能力、乐观改写队列或持有第二份可写业务状态。
4. 图片和普通文件继续使用统一文件引用。原生图片模型与辅助识图工具共用 Host 公共预处理器；
   Adapter 不读取文件系统，不建立按模型分叉的图片预处理链。
5. `model-catalog.json` 是随签名 App 发布的只读程序资源；用户配置继续使用 `config.toml`。模型能力
   只按 `(provider, protocol, model_id)` 精确编译，Desktop/Core 不猜模型名称或 Provider 前缀。
6. 数据库迁移只在隔离临时 Runtime Home 和测试数据库中开发、验证。任何读取或迁移用户实际 Runtime
   Home 前，必须重新列明文件、表、影响范围，完成只读核对、独立备份及可读性/精确数量验证，并在
   写操作前再次取得用户确认。
7. 真实模型验证只使用本版本所需的最小 Provider 组合，凭据沿用安全配置且不进入日志、fixture 或
   文档。图片正文、Data URL、API Key、Apple 私钥和公证凭据不得进入普通 Trace 或提交内容。
8. macOS 正式产物只能在 Developer ID、公证、staple、逐层签名和 Gatekeeper 证据全部成立后视为
   可分发；实际发版时，Apple 服务超时、凭据缺失或干净环境未验证都不能把当次产物按发布成功处理。
9. 本版本不新增顶层产品进程，不实现远程模型目录热更新、thinking 开关、Provider 专属图片预处理、
   Agent 工具生成图片的中间回传、`openai_responses` 协议、Mac App Store、Universal Binary、
   CI 发布或自动更新，也不主动执行 Git commit/push；工具图片回传与 Responses API 已转入
   [`v0.17.0 输入`](../../inputs/260819-Agent工具图片回传与Responses-API.md)。

## 四、里程碑明细

### M0：模型协议与能力编译底座

前置依赖：本开发计划已确认；版本状态已更新为 `开发中`。

目标：先形成可独立测试的模型路由、协议和能力编译边界，为图片与 reasoning 实现提供唯一事实源，
同时保证现有纯文本模型链路不回归。

交付范围：

- 将 `agent-provider-openai-compatible` crate、Cargo package、workspace 依赖和相关模块引用重命名为
  `agent-openai-compatible`，不再用第二个 Provider 概念表示协议实现；
- 扩展现有 `protocol`，当前显式支持 `openai_chat_completions`，旧 `chat_completions` 配置按确认方案
  迁移；尚未实现的协议在配置编译期失败；
- 引入随包只读 `apps/runtime-host/resources/model-catalog.json`、严格反序列化、schema version、
  三元组唯一性和精确别名校验；不提供运行期写回或远程更新；
- 实现“用户 capability override > 静态目录 > 当前协议保守能力基线”，reasoning override 整块
  覆盖，不做跨来源逐字段合并；
- 编译 `effort_map` 的稳定 key、label、受限 wire value 和默认档位，拒绝无效 key、空 label、错误
  类型、重复实际强度和悬空默认值；
- 把扁平 Profile 拆为 Route、Protocol Adapter、Model Capabilities 和 Reasoning Replay Policy，
  建立后续图片资源输入和五档 effort 所需的 Provider-neutral 契约；
- 保留现有 DeepSeek/OpenAI-compatible 纯文本、工具调用、reasoning、usage 和错误分类行为。

验证入口：

- JSON 目录正常、重复三元组、未知字段、错误 schema、未知协议、完整 override 和保守降级测试；
- `effort_map` 字符串/正整数 wire value、子集、无 effort、默认值和非法组合测试；
- 现有 OpenAI-compatible/DeepSeek 请求 golden、SSE、工具调用、usage、重试和回放回归；
- `cargo fmt --all --check`；
- 受影响 Rust package 的单元测试与 Clippy，重命名后使用 `cargo metadata` 核对不存在旧生产依赖。

完成判定：Runtime 能从唯一编译入口得到确定的 Route、Protocol Adapter 和 Capabilities；现有文本
模型行为保持兼容；仓库生产依赖不再使用旧 crate 名称；不包含图片 I/O、Session effort 或 Desktop UI。

Review 重点：术语和依赖方向是否收敛；静态目录是否真为只读；用户 override 是否可能注入任意 wire
字段；未知模型/协议是否 fail-safe。

### M1：原生多模态与公共图片链路

前置依赖：M0 已确认。

目标：让原生支持图片的主模型通过正式 Runtime/Host 链路读取统一文件引用，并以同一公共预处理结果
生成模型请求；不为图片建立第二套附件系统。

交付范围：

- 在隔离数据库中实现 `attachment_blobs.media_type` 增量迁移及新 Blob 实际 MIME 写入；旧值保持
  `NULL`，不批量回填，不增加图片宽高或缩略图数据库字段；
- 在 Host 实现唯一公共图片预处理器：签名嗅探、解码安全限制、EXIF 方向、sRGB、透明背景合成、
  等比缩小、统一 JPEG 和全局资源上限；原图不改写；
- 实现受控模型资源解析和取消传播，Adapter 只接收已准备的图片字节，不访问文件系统；
- 在规范消息保留统一文件引用，原生模型调用时生成有序图片 Part；历史消息重新从 Blob 预处理，
  不保存或复用 Data URL；
- 在 `agent-openai-compatible` 实现已确认 Provider/协议的图片 Part 编码、请求 golden、结构化失败和
  日志脱敏；失败时不静默降级为无图请求；
- 生成 `<原 Blob 文件名>.thumbnail.jpg` 派生文件及按需恢复能力，为 M5 提供正式 Host 入口；缩略图
  不产生 Attachment/Blob 数据库记录。

验证入口：

- 使用隔离 Runtime Home 覆盖新旧 Blob、MIME 不一致、PNG/JPEG/WebP/静态 GIF、透明图、EXIF、
  损坏图、动画图、极端尺寸、取消和资源缺失；
- 验证单图、多图、文本/文件混排顺序、历史恢复/Fork/重试及 Data URL 不落盘；
- OpenAI、GLM、Qwen、Kimi 请求 fixture 与至少一个获授权原生视觉模型的隔离真实调用；
- 受影响 Rust 测试、`cargo fmt --all --check` 和 Clippy。

完成判定：正式 Host 可以从统一文件引用完成原生图片模型调用和历史回放；公共预处理和缩略图只有
一套实现；Conversation/SQLite/日志不出现 Base64 或图片尺寸业务字段；尚不要求 Desktop 完成交互。

Review 重点：文件访问边界、解码资源上限、取消、隐私、旧附件兼容，以及是否出现任何 Provider
专属预处理分支。

### M2：辅助识图工具闭环

前置依赖：M1 已确认。

目标：让 DeepSeek 等文本主模型通过普通 Tool Call 调用已配置的视觉模型，并保持工具、权限、取消和
usage 语义与现有 Agent Loop 一致。

交付范围：

- 在 `agent-tools` 定义 `inspect_images`，输入仅包含 `image_paths`、`goal` 和可选 `background`；
- 建立 Provider-neutral `ImageInspector` 能力壳，Runtime 仅在主模型不支持图片、支持 Tool Call 且辅助
  视觉模型有效时注册工具；
- 在 Runtime 配置中引用既有视觉 `model_key`，复用 credential 和模型能力编译，不建立第二套密钥；
- Host 使用 M1 公共预处理结果对辅助视觉模型执行一次、无工具的普通模型调用，直接把文本终态作为
  Tool Result；不启动嵌套 Agent 或隐藏的第二次总结；
- 将父 Run 取消、剩余超时、有限模型重试、资源错误和模型错误可靠映射到工具终态；
- 工具详情投影目标、辅助模型、状态、耗时、主/辅助 usage 分栏和脱敏错误，复用现有授权、审计及
  工具卡片协议。

验证入口：

- 工具 Schema、条件注册、无辅助模型、无 Tool Call、原生视觉主模型和不可识图组合测试；
- 单图、多图、OCR、无 background、不确定结果、资源失败、辅助模型失败、超时和父 Run 取消；
- usage 不重复计算、工具详情脱敏、审批拒绝/恢复和可靠 Tool Exchange 回归；
- 一个文本主模型加一个辅助视觉模型的隔离真实闭环；
- 受影响 Rust 测试、格式和 Clippy。

完成判定：文本主模型可通过一次普通工具执行获得图片描述并继续原 Agent Loop；原生与工具路径不会
相互随机切换；失败、取消、usage 和审计均可解释。

Review 重点：是否存在隐藏 Agent/额外模型调用、工具是否越过权限链、辅助凭据是否泄漏、主辅助
usage 是否混淆。

### M3：Reasoning 与会话 effort

前置依赖：M2 已确认。

目标：完成多服务 thinking/reasoning 协议兼容，并把推理强度实现为可持久化、可冻结、可原子降级的
Session 配置。

交付范围：

- 扩展 `ReasoningEffort` 为 `low/medium/high/xhigh/max`，由 M0 编译后的 `effort_map` 形成模型有效选项
  和 wire 映射；支持 reasoning 的模型默认开启，不增加关闭入口；
- 完成 OpenAI、GLM、Qwen、Kimi、DeepSeek 已确认请求字段、流式/非流式 reasoning 解码、工具链回放
  和 Replay Policy；Provider 私有字段不进入规范 Conversation 或应用协议；
- 在隔离数据库中实现 `sessions.reasoning_effort`、`runs.reasoning_effort` 增量迁移，Session 保存用户
  意图，Run 真正启动时冻结；
- 增加 Runtime 设置 effort 命令、事件和投影；配置 reload 重新校验有效项，不修改 running Run；
- 模型切换在同一 Store 操作中同时更新 `model_key + effort`，不匹配时只向下降级，无候选回到默认；
- 生成 TypeScript DTO，在 Composer 工具区实现“默认 + 当前模型有效选项”，不支持时隐藏；Desktop
  原样显示目录 label，不保存 wire value 或复制映射。

验证入口：

- 五档排序、子集、默认、无 effort、配置 reload、重启、Fork、重试和 Run 冻结测试；
- 模型切换全矩阵、Store 失败原子性、revision 并发冲突和隐藏失效值测试；
- 各已确认 Provider 的请求/响应/reasoning 回放 fixture，以及连接验证默认 thinking 语义；
- Desktop 选择器可见性、修改失败回滚、运行中修改、窄宽和键盘/屏幕阅读器测试；
- `npm run test`、`npm run build`，以及受影响 Rust 测试、格式和 Clippy。

完成判定：Session effort 在重连/重启后稳定，Run 使用冻结值，模型切换不会向上增强或保留隐藏值；
支持 thinking 的模型始终按协议开启；Desktop 不包含 Provider wire 映射。

Review 重点：默认是否被误当成关闭、跨模型降级是否原子、reasoning 回放是否破坏工具链、运行中
配置变化是否污染已启动 Run。

### M4：中断后队列状态机修复

前置依赖：M3 已确认。

目标：修复用户中断后队列永久等待，并保持 Runtime 重启后的副作用恢复门禁不被新消息误清除。

交付范围：

- 将 `queue_paused_by_user` 与 `resume_required` 恢复为两个正交事实，统一 driver claim 条件；
- `interrupt_run` 与“拒绝并停止”只设置用户暂停；首次成功 `submit_input` 只清用户暂停；
- `resume_queued_input` 接受可选目标：无目标恢复全队列，有目标先原子置顶再恢复全队列；移除
  `retry_override_input` 对持久门禁的旁路；
- 旧 `resume_session` 保留一个版本兼容转发，新 Desktop 和测试只使用统一命令；
- 所有变更继续通过 Session mutation gate 和持久化优先顺序，Store 失败不提前清门禁或 wake；
- Desktop 使用 Runtime Queue Snapshot 展示 automatic/paused/resume-required，不做乐观状态改写。

验证入口：

- 执行附件 C 的 12 项 Runtime 回归矩阵和协议/Desktop 矩阵；
- 覆盖 interrupt/submit、interrupt/resume 并发、无效目标、Store 失败、幂等 submit、SSE 重连；
- 正常自动队列、置顶、取消单项、审批拒绝与 Runtime 重启恢复无回归；
- 受影响 Rust 测试、Desktop 测试/构建、格式和 Clippy。

完成判定：手动中断后新输入能恢复正常串行；重启恢复仍需显式确认；指定输入执行完后余下队列不会
再次卡住；所有失败路径保持权威状态不变。

Review 重点：两个门禁是否又被成对写入、wake 是否被误作业务事实、无效/失败操作是否产生部分更新、
旧命令是否只做兼容转发。

### M5：Desktop 图片体验

前置依赖：M4 已确认；M1、M2 的 Host/Runtime 图片能力已稳定。

目标：把已完成的两条识图能力以现有桌面设计语言交付给用户，不在前端复制模型或附件业务判断。

交付范围：

- 用户消息正文上方按原始顺序显示有界图片缩略图网格，非图片附件和 Context Panel 保持现状；
- 缩略图缺失时通过正式 Host 入口按需生成，点击后复用现有附件预览弹窗和安全路径处理；
- Composer 根据 Runtime 投影展示主模型直接识图、辅助模型识图、当前不可识图三种状态；发送图片
  作为普通附件不因不可识图而被禁止；
- 识图工具继续使用现有工具卡片，详情展示目标、辅助模型、状态、usage 和脱敏错误；
- 完成生成协议类型、Store/SSE 重连、消息分页、历史来源导航、窄窗口和可访问性适配。

验证入口：

- Desktop 组件测试覆盖单图/多图、混合附件、缩略图错误、预览、三种能力状态和工具详情；
- Playwright 覆盖上传发送、历史恢复/分页、模型切换、原生识图、辅助识图和不可识图；
- `npm run lint`、`npm run test`、`npm run build`、`npm run test:e2e`；
- 对应 Protocol/Runtime/Host 测试和 Tauri `--no-bundle` 集成构建。

完成判定：用户能明确看到发送的图片、处理路径和结果；预览与现有附件体验一致；页面不加载完整
历史 Data URL，非图片附件、分页和历史导航无回归。

Review 重点：Desktop 是否猜测 MIME/能力、缩略图是否造成 DOM/内存膨胀、错误是否误导为已识图、
现有消息布局和键盘操作是否退化。

### M6：macOS Developer ID 可信分发

前置依赖：M5 已确认；构建机可访问目标团队的 Developer ID Application 私钥和有效公证凭据。若
凭据或 Apple 服务不可用，只完成只读核查并停止，不能把未签名/未公证产物标记为完成。

目标：把现有 ad-hoc arm64 bundle 提升为可验证的 Developer ID 站外分发产物。

交付范围：

- 只读核对 codesigning identity、Team ID、证书有效期、私钥可用性及公证凭据方案，不回显 secret；
- 增加最小 `Entitlements.plist` 和所需 Tauri macOS release 配置，启用 Hardened Runtime 与 secure
  timestamp，不增加调试或宽权限 entitlement；
- 保持 sidecar 在签名前准备，由 Tauri 正确签名嵌套 Runtime、App 与 DMG，不使用 `codesign --deep`
  作为签名实现；
- 新增只读 `verify-macos-release.mjs`，要求显式 App/DMG 路径，逐层检查架构、Authority、Team ID、
  runtime flag、entitlements、ticket、DMG 和 Gatekeeper；
- 执行正式 arm64 构建、公证、日志核查和 staple，记录 submission ID、产物 SHA-256、大小与脱敏证据；
- 实际发版时，在无开发环境变量的干净用户或机器中从最终 DMG 安装，确认 Desktop 能启动并连接
  签名后的 Runtime。

验证入口：

- 附件 D 的 `codesign`、`spctl`、`stapler`、`hdiutil`、`notarytool log` 全部门禁；
- Desktop/Runtime 基础启动、附件、模型设置和独立生命周期 smoke；
- 凭据扫描确认仓库、构建日志和验收证据不包含私钥、API Key、Apple ID 密码或 `.p8` 内容。

完成判定：签名、公证、staple 和独立验证链路已由一个完整 arm64 验证批次跑通，并形成可重复发布
脚本与手册。若当前版本需要实际分发，最终源码产物和干净环境首次启动必须另行通过；用户明确暂不
发版时，这两项作为发布门禁延后，不阻塞开发版本归档。

Review 重点：凭据处理、entitlement 最小化、sidecar 签名顺序、验证脚本是否误用“最新产物”、构建后
是否修改已签名内容，以及证据是否足以复查。

### M7：跨专题回归与验收准备

前置依赖：M6 已确认。

目标：把各里程碑的局部证据合并为版本级可验收状态，消除跨专题回归和文档偏差；本里程碑确认后才
进入流程规定的独立“版本验收”阶段。

交付范围：

- 在隔离环境和经确认的备份副本上验证旧配置、旧 Attachment、旧 Session/Run、Conversation、Fork、
  重启恢复和增量 schema；不直接以用户真实 Runtime Home 做破坏性测试；
- 使用同一图片集完成至少一个 OpenAI-compatible 原生视觉模型、一个国内视觉服务和一个文本主模型
  加辅助视觉模型的正式 Host 真实链路；记录模型、协议、请求限制、结果和费用范围；
- 汇总图片、effort、队列、Desktop、签名分发、取消、重试、usage、隐私与日志脱敏的交叉回归；
- 清理已被附件 C 吸收的临时修复文档入口，更新模块约束、重要决策、版本文档和本地开发进度；
- 准备版本验收所需的环境、命令、真实模型结果和签名产物证据，但不提前把版本标记为 `验证中` 或
  创建“已通过”结论。

版本门禁：

```bash
cargo fmt --all --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace

cd apps/desktop
npm run lint
npm run test
npm run build
npm run test:e2e
npm run tauri -- build --no-bundle
```

真实 Provider 与 Apple 外部验证分别记录环境、目标、结果、费用、未执行项和原因，不能混入离线
workspace 门禁的通过数字。实际发版时仍需针对当次最终源码重新执行签名、公证验证和干净环境 smoke。

完成判定：功能设计全部验收项已有可复查证据，workspace 与 Desktop 门禁通过，无已知阻断缺陷，
文档、生成协议、模型目录和实现一致；用户确认 M7 后，版本状态进入 `验证中` 并创建
`验收记录.md`。

Review 重点：是否遗漏跨专题组合、是否触碰真实用户数据、外部验证是否被模糊成自动化通过、设计与
实际实现是否存在未重新确认的偏差。
