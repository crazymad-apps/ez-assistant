## 二、现状与问题

### 2.1 已有能力

当前正式 Runtime 已具备一条统一压缩链路：

1. Agent Core 根据上下文窗口判断或 Provider overflow 返回 `CompactionRequired`；
2. Runtime 读取当前规范快照，调用 `RollingSummarySameModel` 生成候选 replacement；
3. replacement 通过结构与工具配对校验后，Runtime 原子切换 Context generation；
4. 自动压缩继续同一业务 Run，手动压缩在空闲 Session 上独立完成；
5. 原始产品历史继续保留，模型只使用派生的有效上下文；
6. 自动压缩次数有界，不会无限执行“压缩—重试”。

现有能力已经确立以下正确边界，本循环应复用而不是重建：

- 压缩策略只生成候选，不提交 Checkpoint、不驱动 Agent Loop；
- Runtime 负责持久化、generation 切换、续接、取消和失败收敛；
- replacement 必须保持合法消息顺序及完整 Tool Call/Result 配对；
- 已执行工具不会因续接而重放；
- System Prompt 和 Pinned Memory 快照在 Session 创建时冻结，记忆工具变更写入权威 Store，
  只影响未来新建 Session，不静默改写当前 Session 的 System Prompt。

### 2.2 已确认的主要缺口

| 缺口 | 当前事实 | 用户影响 |
| --- | --- | --- |
| 压缩后继续使用旧 usage | replacement 原样保留最近 User Turn，其中 Assistant Result 的 usage 仍是压缩前累计值；窗口判断继续把它当作新 generation 的权威占用 | 第一次压缩实际已经释放空间，Runtime 仍立即触发第二次压缩，最终耗尽两次恢复额度并错误失败 |
| 摘要旁路请求未保持完整缓存前缀 | 当前请求使用同一模型和 System Prompt，但只发送 compressible head、清空工具定义；真实会话中的摘要请求缓存命中为零 | 长历史摘要重复计费并增加延迟，无法复用刚完成的正常请求缓存 |
| 当前 User Turn 整体保护存在潜在上限 | 当前布局按完整 User Turn 分块，并至少原样保留最近一个 User Turn；同一 Run 的多次模型/工具交互可能都在保护尾部 | 架构上可能出现真实轮内空间不足，但已诊断会话不能证明该问题已经发生，必须在 usage 修复后单独验证 |
| 记忆变化依赖模型自行概括 | 成功的 `pin_memory`、`update_pinned_memory`、`unpin_memory` 结果是可靠事实，但当前摘要提示只笼统要求保留重要结果 | 摘要可能漏掉新值、保留旧值或复活已删除记忆，当前长会话失去必要约束 |
| 连续压缩后的语义稳定性不足 | 旧 Context Summary 会再次进入可压缩 head，由模型重新表达 | 多次压缩可能累积遗漏；失败原因也难以区分“无内容可压”与“压后仍不够” |

### 2.3 真实会话诊断结论

2026-09-18 对“基于草图的密集架与设备布置及墙厚标注”本地会话进行了只读核查：

1. 模型窗口为 `256000`，自动压缩阈值为 80%，即 `204800`；压缩前最后一次父模型结果为
   `205421` token，因此第一次阈值压缩正常触发。
2. 第一次摘要请求输入 `189995`、输出 `4014` token，摘要成功；但 replacement 保留的最新
   Assistant Result 仍带有 `205421` 的旧 usage。
3. 下一次预检误判新 generation 仍超过阈值，立即再次压缩。第二次摘要请求只输入 `5901`、输出
   `3663` token，本质上是在重新摘要第一次摘要，并没有处理新的空间增长。
4. 旧 usage 再次触发阈值判断，Runtime 达到两次自动恢复上限，以
   `context compaction recovery limit reached (reason=threshold_reached)` 结束 Run。
5. UI 中的 `1912K Token` 是子任务 32 次请求的累计消耗，不是父上下文大小；该子任务单次最大请求
   为 `104241` token，未发生子任务压缩。

因此，本次真实故障的直接根因是 **generation 切换后仍把压缩前 usage 整值当作新上下文占用**，不是已经证实的轮内
真实空间不足。C02 先修复该缺陷，再用专门样本验证 protected tail 是否仍会造成容量问题；没有证据时
不提前引入轮内剪枝、确定性瘦身或多阶段组合压缩。

## 三、目标与非目标

### 3.1 循环目标

1. **修正 usage 基线**：Context generation 切换后，压缩前 Assistant Result 的 usage 先扣除压缩点前最后一条
   Assistant usage，以差值加新 Summary 与后续增量作为临时近似值；下一次真实模型结果恢复权威基线。
2. **保持旁路请求缓存前缀**：摘要仍使用当前模型，以原模型可见上下文及工具定义作为不变前缀，
   只在末尾追加无工具执行的压缩指令，不预先改写或瘦身原上下文。
3. **验证真实轮内容量**：usage 缺陷修复后构造同一 Run 多次工具交换的大上下文场景；只有证据证明
   protected tail 仍阻断继续执行时，才设计最小的轮内压缩边界。
4. **保留当前任务语义**：压缩后继续保留用户当前目标、已确认约束、未解决事项、必要工具结果、
   未完成交互以及当前 Provider 继续执行所需状态。
5. **程序化保留记忆变化**：从可靠的成功记忆工具交换中提取变化，按当前 Session 的净效果合并，
   由程序写入压缩点 summary，不依赖摘要模型自行发现和准确转述。
6. **可靠续接与有界失败**：可压缩时继续同一 Run；不可压缩、压缩请求失败或空间仍不足时，
   给出稳定、可诊断的终态，不重放工具、不形成无效循环。
7. **覆盖正式运行路径**：父 Agent、子 Agent、阈值触发、Provider overflow 和手动压缩使用一致的
   eligibility、完整性与有效性原则；入口可以保留各自的后续语义。

### 3.2 明确非目标

- 不预先指定必须使用 Tool Result 剪枝、Rolling Summary、分块摘要或混合策略。
- 当前不在摘要前确定性瘦身原上下文，也不引入“先瘦身、再 Rolling Summary”的多阶段组合压缩。
- 不因潜在风险直接拆分最近 User Turn；轮内边界调整必须以 usage 修复后的独立复现证据为前提。
- 不删除、覆盖或改写原始 Conversation History；派生上下文仍不是第二份产品历史。
- 不新增另一套压缩状态机、后台压缩 Worker 或独立记忆账本。
- 不改变 Agent Core、Runtime、Context Engine 和 Memory Store 的既有权威状态归属。
- 不在当前 Session 内热更新冻结的 System Prompt/Pinned Memory 快照。
- 不把普通 Tool Result、失败的记忆工具调用、模型自述或自然语言猜测当作记忆变更事实。
- 不在 C02 重做会话界面、历史分页或子会话占用展示；它们属于 C05。
- 不承诺任意大小、任意内容都能成功压缩。当前用户输入本身过大、未闭合交换或受保护内容已超过
  模型上限时，允许明确失败，但必须有界且不损坏历史。

## 四、核心概念与不变量

### 4.1 原始历史、有效上下文与压缩候选

- **原始历史**是用户和 Runtime 可回查的完整事实，不因压缩删除。
- **有效上下文**是下一次模型请求实际使用的派生快照，可以由 Context Summary、保留原文及必要
  Provider 状态组成。
- **压缩候选**是尚未提交的 replacement。它只有同时通过结构完整性和有效空间校验后，才能成为
  新 generation。
- 压缩策略不能提交持久化、修改 Journal 或自行启动 continuation；这些仍由 Runtime 统一编排。

### 4.2 摘要旁路请求与缓存边界

- 摘要请求继续使用当前执行的同一个模型，不单独选择摘要模型。
- 请求以正常模型调用已经使用的 System Prompt、原模型可见 Conversation、工具定义及其他影响输入
  前缀的稳定配置为基础；不得在旁路请求前裁掉或重写 Tool Result、日志或其他历史正文。
- 压缩指令只追加在原上下文末尾，并明确禁止工具调用。技术方案应优先保留工具定义、通过既有
  `ToolChoice::None` 控制行为，避免因清空工具定义破坏缓存前缀。
- 旁路请求不修改 Journal 或原始历史；只有合法候选在 Runtime 原子提交后才改变有效执行上下文。
- 当前已验证窗口能够容纳旁路摘要请求，C02 不引入分段摘要、预瘦身或组合压缩。未来若出现旁路请求
  本身超限的独立证据，再作为新的设计输入评估。
- Provider 是否实际命中缓存仍由上游决定；C02 保证本方不主动破坏可复用前缀，并记录真实
  `cached_input_tokens` 作为验证证据。

### 4.3 usage 基线与有效空间

一次压缩只有同时满足以下条件才算有效：

1. 候选 replacement 通过共享结构、Tool Call/Result 配对和 Provider 状态约束；
2. 候选相对来源快照确实减少下一次请求需要承载的上下文；
3. generation 切换后，在压缩前产生、但被 protected tail 保留的 Assistant usage 只作为减法近似的原始事实，
   不再把其 `total_tokens` 整值视为新上下文占用；
4. 在取得压缩后的首个真实模型结果前，窗口判断使用“保留 usage - 压缩点前最后 usage +
   新 Summary 估算 + 后续未计量增量”；无法得到可解释差值时明确按 usage 不可用处理；
5. 首个真实模型结果到达后，直接使用其 Provider usage，不再应用压缩减法；
6. 结果及失败原因可观察，但报告不记录 prompt、摘要正文、凭证或原始工具结果。

空间判断应复用现有模型窗口、Provider usage 和未计量增量的统一口径。技术方案可以完善派生快照的
评估方式，但不得创建与实际模型请求长期漂移的第二份 token 账本，也不能把差值估算伪装成 Provider
实际用量。手动压缩、重启恢复和父/子 Agent 也必须能恢复同一个压缩偏移事实，不能只用当前 Run 内
短暂布尔值掩盖问题。

### 4.4 轮内保护边界的验证原则

当前完整 User Turn 保护规则先作为基线保留。C02 在 usage 修复后使用真实模型窗口构造以下验证：

- 同一 Run 内多次模型与工具交换，压缩后首个请求能否正常建立新 usage；
- protected tail 的真实模型输入是否仍超过窗口或无法形成必要余量；
- 单个较大 Tool Result 是否仍可由一次原上下文旁路摘要处理。

只有第二项获得明确失败证据，才进入轮内边界调整。届时仍必须原样保护当前 UserMessage、未完成工具
交换、必要 Provider opaque state 和必须逐字使用的用户内容；被保留的 Tool Call/Result 完整配对，
被整体替换的闭合交换不能只遗留一侧。具体边界需要回到功能设计重新确认，不能在技术方案中默认扩张。

### 4.5 记忆变化的程序化保留

本设计严格区分两类事实：

- Pinned Memory Store 中的持久数据由现有 Store 继续权威保存；压缩不会删除或重新写入这些数据。
- 当前 Session 需要知道“冻结快照之后发生了什么”，这属于模型可见上下文连续性，而不是新的
  Memory Store。

程序只从以下来源识别记忆变化：

1. 当前 Session 创建时冻结的 Pinned Memory 快照；
2. 已完成且状态为成功的 `pin_memory`、`update_pinned_memory`、`unpin_memory` Tool Call/Result；
3. 先前压缩点中由程序生成并可可靠识别的记忆变化段。

合并结果表达相对冻结快照的**当前净效果**：

- 新增后更新，只保留最新有效值；
- 既有记忆更新，明确以新值覆盖冻结快照中的旧值；
- 删除既有记忆，保留足以抵消冻结快照旧值的删除事实；
- 同一 Session 新增后又删除，且不再对当前任务产生约束时，不保留已经归零的变化；
- 失败、拒绝、取消或缺少成功结果的调用不产生变化；
- 连续压缩只合并一次当前净效果，不重复堆叠，不把旧值或已删除值恢复为有效记忆。

该净效果由程序写入 Context Summary 中的稳定、可识别区域；模型生成的自然语言摘要不能覆盖、伪造
或删除该区域。具体表示、大小上限及与摘要正文的组合方式由技术方案决定，优先复用现有
`ContextSummaryMessage`，不因格式差异新增一份持久化实体。

通过 UI/API 在 Session 外修改记忆仍遵守现有语义，只影响未来新建 Session；C02 不把这类外部变化
偷偷注入当前 Session。

### 4.6 续接与失败不变量

- 自动压缩成功后继续同一个业务 Run，不重复提交原 UserMessage。
- 成功切换 generation 后，至少完成一次基于新上下文的真实模型调用，才能重新根据 Provider usage
  判断阈值；不得在此之前用旧累计 usage 连续压缩。
- 已完成工具调用不重放，待处理审批和未闭合交换不被压缩越过。
- 压缩生成模型请求保留正常请求的工具定义以稳定输入前缀，但使用 `ToolChoice::None` 禁止工具调用，
  不产生业务副作用。
- 候选生成、持久化或内存投影任一步失败时，不出现半提交 generation。
- 取消手动压缩不改变有效上下文；自动压缩沿用不可取消的原子切换边界。
- 对同一来源 generation 不重复提交相同操作；NoOp、无效候选和失败均稳定收敛，自动压缩次数保持
  有界。模型摘要正文不要求字节级确定。
- 不可压缩、压缩输入自身超限、候选无有效收益、候选不合法和 Provider 失败应保留可区分的内部原因，
  对协议层继续使用受控、脱敏的错误投影。

## 五、主要场景

### 5.1 压缩后调整 usage 基线

1. 用户提交一个长任务；Agent 在同一 Run 中完成多次模型与工具交换。
2. Runtime 在下一次模型调用前判断上下文达到阈值。
3. 摘要旁路请求以原模型上下文作为不变前缀生成候选；候选原子提交后进入新 generation。
4. 新 generation 对被保留的旧 Assistant usage 应用压缩差值调整，不直接用旧 `total_tokens` 触发第二次阈值压缩。
5. Run 使用 replacement 完成一次真实模型调用，新 Result 的 Provider usage 成为新的判断基线，不再做减法。

### 5.2 Provider 返回上下文溢出

1. usage 不可用、估算偏差或上游计算口径不同，Provider 返回明确 overflow。
2. Runtime 复用同一压缩能力处理当前有效快照。
3. 有效候选提交后只重试模型调用，不重放已经完成的工具。
4. 若压缩输入也超限或候选仍无有效空间，在有限次数内终止并给出稳定错误。

### 5.3 真实轮内容量验证

1. usage 基线缺陷修复后，构造同一 Run 多次工具交换并逼近阈值的正式 Host 场景。
2. 仍使用一次原上下文旁路摘要，不预先瘦身 Tool Result，也不引入第二阶段摘要。
3. 若压缩后的首个真实模型请求成功，则轮内保护不足不成立，不新增轮内拆分机制。
4. 若请求因 protected tail 的真实大小继续 overflow，保存输入构成和失败证据，回到功能设计决定是否
   调整轮内边界；本设计不提前授权实现该机制。

### 5.4 记忆增删改后发生一次或多次压缩

1. Agent 成功新增、更新或删除 Pinned Memory，Store 已提交权威结果。
2. 压缩前由程序从可靠 Tool Result 及既有程序段计算相对冻结快照的净效果。
3. 模型摘要完成后，程序把净效果写入压缩点 summary 的受控区域。
4. 后续再次压缩时重新合并为当前净效果；旧值、重复项和已删除值不会重新出现。
5. 当前 Session 继续理解该变化，未来 Session 仍从 Store 读取最新持久状态。

### 5.5 手动压缩

空闲 Session 的手动压缩复用相同候选、完整性和有效空间规则。没有可压缩内容或无法产生有效收益时
返回 NoOp，不为“看起来执行过”而切换 generation；取消和快照竞争继续遵守现有语义。

## 六、模块责任与影响边界

| 模块 | C02 职责 | 不承担的职责 |
| --- | --- | --- |
| `agent-context` | 上下文布局、可压缩/保护边界、压缩策略、候选校验和空间效果所需的纯能力 | Session、Run、持久化、continuation、Memory Store 写入 |
| `assistant-runtime` | 选择当前有效快照，提供冻结上下文和可靠记忆变化事实，提交 generation，续接 Run，收敛取消/失败 | 实现 Provider 编码或在 Runtime 外复制业务状态 |
| `agent-types` | 仅在现有规范类型无法表达最终候选时，经技术方案证明后做最小调整 | 为某个策略提前增加未使用公共类型 |
| `agent-memory` / `agent-tools` | 继续提供现有记忆领域契约和可靠工具结果；只有事实不足时才做最小补充 | 新建压缩专用 Memory Store 或改变当前 Session 热更新语义 |
| `assistant-protocol` | 仅投影用户需要区分的压缩结果和脱敏错误；优先复用现有事件 | 暴露摘要正文、工具结果或内部策略细节 |
| `runtime-host` | 装配正式 Runtime 并参加真实 Host 验收 | 持有第二份压缩状态或实现算法 |

技术方案必须先证明现有 `ContextLayout`、`CompressionStrategy`、`CompactionCandidate`、
`ContextSummaryMessage`、Context generation 和记忆工具结果中哪些可以直接复用，再决定最小改动。

## 七、验收标准

### A. usage 修复、旁路请求与继续执行

1. 使用真实故障同构样本达到阈值并成功压缩后，压缩前的 `total_tokens` 不再触发第二次自动压缩。
2. replacement 完成一次真实模型调用并取得新 usage，原 Run 继续；不重复原 UserMessage 或已完成工具。
3. 父 Agent、子 Agent、手动压缩及重启恢复均能从 Context Summary 恢复同一 usage 减法偏移，不依赖仅存于
   单个 Future 的临时状态。
4. 摘要请求保持正常调用的 System Prompt、Conversation 前缀和工具定义，只追加压缩指令并通过
   `ToolChoice::None` 禁止工具调用。
5. 定向请求投影测试证明本方未破坏缓存前缀；真实 Provider 验证记录 `cached_input_tokens`，但不把
   上游必须命中缓存作为本地正确性的唯一判据。

### B. 压缩效果与有界失败

6. usage 修复后完成同一 Run 大上下文验证，并据实记录 protected tail 是否仍造成真实空间不足；
   未复现时不实现轮内拆分。
7. 当前用户输入或受保护内容本身确实超过窗口时，Run 在有限次数内明确失败，不循环压缩、不提交空洞摘要。
8. 压缩请求 overflow、Provider 失败、摘要为空、候选无效及持久化失败均保持原始有效上下文，且结果可区分、可诊断。
9. 连续多次压缩后仍只有一条当前有效 Context Summary 链路，原始历史可回查，结构校验持续通过。

### C. 记忆变化连续性

10. `pin → update` 后压缩，summary 只包含最新有效值；连续再次压缩不重复、不退回旧值。
11. 冻结快照中已有记忆被 `update` 或 `unpin` 后压缩，当前 Session 能识别覆盖或删除效果。
12. `pin → unpin` 的净零变化不会留下仍然有效的记忆；删除项不会被后续摘要复活。
13. 失败、拒绝或取消的记忆工具调用不会写入程序化记忆变化段。
14. 压缩不会额外修改 Memory Store；新建 Session 仍以 Store 的最新权威内容构建快照。

### D. 一致性、恢复与回归

15. 父 Agent、子 Agent、阈值触发、overflow 和手动压缩共享相同完整性与有效性原则。
16. 工具调用与结果配对、消息顺序、Provider state 隔离及原始历史定位均通过定向测试。
17. generation 提交保持 Store 先行、内存投影随后；冲突、取消或重启恢复不产生半提交上下文。
18. 未达到压缩条件的普通短 Run 不增加额外模型调用、持久化写入或记忆扫描副作用。
19. 既有跨 Turn Rolling Summary、手动压缩、自动压缩次数上限及错误脱敏回归通过。

C02 完成以以上用户结果和验证证据为准，不以实现了某个名为“剪枝”的类型或策略为准。

## 八、进入技术方案前必须回答的问题

以下属于实现选择，不改变本功能设计的目标；技术方案必须逐项给出证据和取舍：

1. 如何表达“generation 切换后对旧 usage 应用哪一次压缩减法”，使活动 Run、手动压缩和重启恢复都能
   恢复同一事实，又不创建长期漂移的第二份 token 账本？
2. 摘要请求如何保留正常请求的工具定义和完整缓存前缀，同时使用 `ToolChoice::None` 保证无工具副作用？
3. usage 修复后的轮内容量验收如何构造；若无法复现真实空间不足，如何明确关闭轮内拆分候选？
4. 程序化记忆变化段如何编码、校验、合并和限制大小，同时继续使用一条 Context Summary？
5. 哪些 Provider state 必须保留，旧状态何时可以随闭合内容压缩，怎样避免跨 Provider 误用？
6. 现有 `MAX_AUTOMATIC_COMPACTIONS` 是否继续足够，失败原因如何映射到既有协议而不扩散内部实现？
7. 父/子 Agent 和手动压缩是否需要不同策略配置；若不同，哪些不变量必须共用？
8. 如何构造正式 Host 的确定性大上下文验收样本，并证明 usage 已重建、工具未重放、历史可回查和
   恢复一致？

## 九、设计结论

C02 首先修复已证实的 usage generation 问题：replacement 提交后对被保留的旧 usage 扣除压缩点前最后一条
Assistant usage，再加新 Summary 与后续增量作为临时近似；首个真实模型结果恢复权威基线。摘要保持为同模型单次旁路请求，
以原上下文和工具定义作为稳定缓存前缀，
不预先瘦身、不做多阶段组合。最近 User Turn 是否需要更细压缩必须在该修复后重新验证，不能由本次
故障直接推导。记忆工具造成的当前净变化仍由程序写入压缩点 summary；原始历史、Memory Store 和
Runtime 控制权保持不变。
