## 二、现有实现核查与复用结论

| 现有事实 | 本方案结论 |
| --- | --- |
| `ContextWindowEvaluator` 从当前快照最后一条 Assistant 取 `usage.total_tokens`，只估算其后 User/Tool 增量 | 保留单一评估入口；压缩后对仍保留的旧 Assistant usage 应用一次持久化减法偏移 |
| Rolling Summary 已按完整 User Turn 分块，至少保留最近一轮，并使用同一 `ModelService` | 保留布局与保护规则，不实现轮内拆分 |
| 当前摘要请求只发 compressible head，并清空 tools/reasoning/provider options | 改为直接复用 Core 交接的完整正常 `ModelRequest`，只在末尾追加压缩指令 |
| `ContextSummaryMessage` 已分开摘要模型、摘要请求 usage 和被替换历史 usage | 继续使用同一消息，增加两个可选兼容字段；不新增持久化实体 |
| Runtime 已以 Store 先行、内存 Journal 随后的方式原子替换 generation | 不改提交次序、`ContextReplacement` 或 SQLite schema |
| 完整产品历史保留旧消息，执行投影从最新 Context Summary 开始 | 旧 Assistant usage 仍保留用于历史和总量展示，不会通过清空 usage 修复预检 |
| Pinned Memory 成功工具结果是单一 JSON `{id,category,content}`，失败结果有明确 Error 状态 | Runtime 可从已闭合工具交换确定性归并，无需读 Memory Store 或反解 System Prompt XML |
| Runtime Pinned Memory 已有 256 条、单条 16 KiB、整体 128 KiB 限制 | 程序化上下文段复用同一限制，不新增另一组动态配置 |

本轮不需要更改 `agent-memory` 或 `agent-tools` 的工具输出契约。需要改动的最小主路是
`agent-types -> agent-context -> agent-core -> assistant-runtime`；Provider Adapter 只需同步 Context Summary 新的模型可见渲染。

## 三、总体执行流程

### 3.1 自动压缩

```text
Agent Core 即将发起正常模型请求
    ↓ 阈值预检或 Provider ContextOverflow
CompactionRequired
    - reason / step / consumption
    - 本次本来要发送的完整 ModelRequest（仅进程内交接）
    ↓
Runtime 读取同一 generation 的权威 Journal 快照
    + 同一 generation 的完整产品历史
    ↓
校验 Journal 消息是 ModelRequest.conversation 的有序原样子序列
    ↓
单次同模型旁路请求
    - 原 System / Conversation / Tools / Reasoning / Provider Options
    - 末尾追加压缩指令
    - ToolChoice::None
    - max_output_tokens = 4096
    ↓
构造 System prefix + Context Summary + 原样 protected tail
    - 写入 usage 减法偏移
    - Runtime 写入 Pinned Memory 净变化段
    ↓
结构、边界、原样尾部和程序化段校验
    ↓
Store 原子提交新 generation → Journal 替换 → 同一 Run 续跑
```

上述只产生一次摘要模型请求和一次 generation 提交。摘要请求不写 Journal，不执行工具，
不改变原始产品历史。

### 3.2 手动压缩

手动压缩仍使用同一布局、候选、usage 减法偏移、记忆归并和提交校验。它发生在空闲 Session，没有一个
正在执行、可以交接的正常 `ModelRequest`，因此不伪造“与上一次 Run 工具前缀完全相同”的证据。
它使用当前 Session 的冻结 System Prompt、当前有效 Conversation 和当前模型请求配置，不装配 Run 专属工具；
所以工具列表为空，且不将 cache hit 作为手动入口验收项。

这是对功能设计 A4 的适用边界澄清：“保持正常请求完整前缀”仅适用于由活动父/子 Agent 交接的自动压缩。
手动压缩仍必须满足无工具副作用、候选合法、usage 可近似投影和原子提交。

## 四、usage 压缩偏移

### 4.1 表达方式

不再将被保留的旧 Assistant usage 整体判定为失效。在 `ContextSummaryMessage` 增加可选字段：

```rust
#[serde(default, skip_serializing_if = "Option::is_none")]
pub usage_adjustment: Option<ContextUsageAdjustment>,

#[serde(tag = "type", rename_all = "snake_case")]
pub enum ContextUsageAdjustment {
    Subtract {
        retained_assistant_id: MessageId,
        subtract_total_tokens: u64,
    },
    Unavailable,
}
```

新候选优先找到：

1. protected tail 中最后一条带 usage 的 Assistant，其 ID 写入 `retained_assistant_id`；
2. compressible head 中最后一条带 usage 的 Assistant，其 `total_tokens` 写入
   `subtract_total_tokens`。

如果 head 只有前一条 Context Summary，而它的 `Subtract` 仍指向本次保留的同一 Assistant，则沿用前一个
`subtract_total_tokens`，使立即发生的第二次有界恢复仍可将旧偏移传递下去。protected tail 仍有旧
Assistant usage、但无法得到可解释的被减值时，新 Summary 显式写入 `Unavailable`，不借用旧 usage。
如果 replacement 中根本没有旧 Assistant usage，则不写 adjustment；此时首次预检本来就没有可用的
Assistant 基数，首个新 Assistant 会自然成为新的 Provider usage 权威值。

该字段是一次压缩形成的不可变调整事实，不是软件版本、配置 revision、可变 token 账本或新的 Context
generation。旧数据没有此字段时保持原读取语义，不做 SQLite 迁移或历史回填。

不采用以下方案：

- 不清空被保留 Assistant 的 `usage`：否则完整历史和 UI 累计消耗会失真，原样尾部也会被改写。
- 不使用 Run 内存布尔值：它无法覆盖手动压缩、进程重启和子任务恢复。
- 不在 Checkpoint 外建立另一份 token/generation 账本：它会与真实模型请求漂移。

### 4.2 窗口判断规则

`context_token_usage` 先定位最新 Context Summary：

1. 无 `usage_adjustment` 时保持旧 Summary 的兼容行为。
2. 最新 Summary 显式为 `Unavailable` 时，`completed_tokens=None`，评估结果为 `UsageUnavailable`，由下一次真实
   Provider 请求或 overflow 收敛。
3. 最新 Assistant ID 等于 `retained_assistant_id` 时，它仍是压缩前保留的旧 Result，使用：

   ```text
   adjusted_completed_tokens =
       retained_assistant.total_tokens.saturating_sub(subtract_total_tokens)
       + estimate(rendered Context Summary)
   total_tokens = adjusted_completed_tokens
       + estimate(messages after retained Assistant)
   ```

4. 最新 Assistant ID 与 `retained_assistant_id` 不同时，说明压缩后已完成一次新模型请求；直接使用该 Result 的
   Provider `total_tokens`，不再减去任何偏移。
5. 最新 Assistant 没有 usage 时，继续遵守“不借用更早 Result usage”的现有规则。

这个差值估算会把两次旧 usage 共有的 System Prompt、工具定义等稳定前缀一并抵消，因此可能偏低。
本方案明确将它作为“压缩后、新 Provider usage 到达前的临时近似值”，不伪装成 Provider 实际用量，也不进入
UI 累计。低估使阈值预检延后时，仍由 Provider-neutral `ContextOverflow` 触发第二次有界恢复。

因此，第一次压缩后不会再直接把 `205421` 整值当成新 generation 占用；首个新 Assistant Result 到达后，
窗口判断立即恢复使用 Provider 真实 usage。

### 4.3 候选、重启、改写与分叉

- `validate_replacement` 校验 `Subtract` 指向 Summary 之后原样保留的 Assistant，且该消息带有 usage。
- `merge_context_replacement_with_product_history` 继续校验完整原样后缀，调整事实与它在同一 JSONL 正文中原子提交。
- 重启后从最新 Summary 读取调整事实，不依赖 Run Future 或内存 generation 状态。
- 历史改写或 Session 分叉如果截掉 `retained_assistant_id` 但仍保留 Summary，将新 Session/新 generation 的调整状态
  收敛为 `Unavailable`；不为了继续使用近似值而保留已被用户截断的消息。Summary 也被截掉时不保留调整。
- 改写/分叉后仍执行完整 Conversation 与工具配对校验。

## 五、摘要请求与缓存前缀

### 5.1 Core 交接精确正常请求

仅从 Journal 重建压缩请求不足以保证缓存前缀一致。正常请求还包含：

- 父 Agent 的 disclosure 与 shell request-only context；
- 子 Agent 在具体任务中追加的 `load_skill` 工具；
- 该 Run 冻结的 generation、reasoning 和 Provider Options；
- 同一 `AgentExecution` 中已追加、但与请求专用上下文相对位置不可由 Store 重新猜测的工具交换。

因此在 `ExecutionOutcome::CompactionRequired` 增加一个**仅进程内可用**的 `CompactionHandoff`：

- Engine 在阈值预检命中时，交接它本来即将发送的 `ModelRequest`。
- Provider overflow 时，交接与溢出请求语义完全一致的 `ModelRequest`。
- handoff 字段使用 `Option`并从 `ExecutionOutcome` serde 中跳过；实时 Engine 必须产生 `Some`，旧 JSON 及
  录制文件读取为 `None`，不能用脱离原进程的旧 outcome 自动续跑。
- `CompactionHandoff` 自定义脱敏 `Debug`，不打印 System、Conversation、工具 schema 或 Provider Options。
- `AgentEvent::ExecutionCompactionRequired` 不增加正文，UI、SSE、调试事件和可持久 Trace 只保留 reason/step/consumption。

这不让 Core 执行压缩；Core 只交付已经拥有的正常请求事实，候选生成、记忆归并、提交与续跑仍属于 Runtime。

### 5.2 `CompactionInput` 与旁路请求

`CompactionInput` 收敛为：

```rust
pub struct CompactionInput {
    pub model: Arc<dyn ModelService>,
    pub normal_request: ModelRequest,
    pub layout: ContextLayout,
}
```

`layout` 从权威 Journal 快照构造，用于决定 replacement；`normal_request` 来自 Core handoff，用于建立旁路模型请求。
Runtime 在调用策略前验证 Journal 快照的全部消息是 `normal_request.conversation` 中的有序、原样子序列；
额外项只能是 Runtime 生成的 hidden/request-only context。不一致时视为 snapshot race/内部错误，不提交候选。

`RollingSummarySameModel` 克隆 `normal_request` 并只做以下变更：

1. 在完整 `conversation` 末尾追加一条 Runtime hidden 压缩指令；
2. `tool_choice` 设为 `ToolChoice::None`；
3. 保留 temperature、top_p 和 stop，只将 `generation.max_output_tokens` 设为 `4096`；
4. System Prompt、原 Conversation、工具定义及顺序、reasoning 和 Provider Options 均不变。

压缩指令明确：只输出简洁摘要，不调用工具，不重复将由 Runtime 原样保留的最近 User Turn，不复制或改写
程序化权威上下文。模型如仍返回 Tool Call，当前的 `summary_text` 校验继续拒绝结果，不执行任何工具。

`4096` 是结合真实会话约 `4014` output token 的摘要消耗确定的首版固定上限。它为长任务的约束、
未决事项和必要工具结果留出空间，但不引入按窗口比例动态计算。摘要请求本身如因模型窗口或输出限制
无法建立，仍按现有受控失败语义保留原 generation，不在本循环再增加自动降档或多阶段摘要。

正常请求含非空 tools 但模型能力未声明 `ToolChoice::None` 时，在建立模型流前明确失败并保留原上下文；
不通过清空 tools 或改用 Auto 做隐式降级，否则会违背已确认的缓存和无工具语义。

### 5.3 缓存验证口径

- 单元测对比原 `ModelRequest` 和摘要请求，断言追加指令之前的 System、Conversation 和 Tools 字节投影一致；
  同时断言 reasoning/provider options 不变。
- 父 Agent 用例必须包含 disclosure/shell context；子 Agent 用例必须包含任务级 `load_skill`，防止用重建请求
  伪造成功。
- 正式 Provider 验收记录摘要请求 `cached_input_tokens`；命中与否由 Provider 决定，本地验收只要求前缀未被
  本方改写，不将上游必须返回非零值当作正确性前提。

## 六、程序化 Pinned Memory 净变化

### 6.1 Context Summary 内的可信边界

在 `ContextSummaryMessage` 再增加一个可选字段：

```rust
#[serde(default, skip_serializing_if = "Option::is_none")]
pub programmatic_context: Option<String>
```

`text` 只保存模型生成摘要，`programmatic_context` 只能由上层宿主写入确定性内容。两者仍属于同一条
Context Summary，不是第二份历史、Memory Store 或独立账本。

`agent-types` 提供唯一模型可见渲染方法：

```text
<model generated summary text>

Programmatically maintained context. This section is authoritative when it conflicts with prose:
<programmatic_context JSON>
```

Provider Adapter、窗口估算和压缩请求都复用该方法，不在各模块手写拼接。存储和重新归并直接读取独立字段，
不从模型文本搜索标记，因此模型无法通过模仿分隔符伪造权威状态。旧 Summary 缺少字段时按无程序化状态读取。

### 6.2 Runtime 私有数据形状

`assistant-runtime` 定义不对外暴露的 `PinnedMemoryDeltaV1`，以紧凑 JSON 写入
`programmatic_context`：

```json
{
  "kind": "pinned_memory_delta",
  "version": 1,
  "upserts": [
    {
      "id": "memory-id",
      "category": "preference",
      "content": "current value",
      "origin": "frozen_snapshot"
    }
  ],
  "deleted_ids": ["another-memory-id"]
}
```

- `upserts` 和 `deleted_ids` 按 ID 排序，序列化结果确定。
- `origin` 只有 `created_in_session` 和 `frozen_snapshot`，用于区分“本 Session 新增后删除”与“删除冻结快照
  中的旧条目”。它是压缩净变化语义，不是 Memory Store 业务属性。
- `attributes`、Store revision、时间、Session ID 和用户信息不进入段落。
- 字段使用严格 serde schema；版本未知、字段多余、ID/归类/正文非法、重复 ID 或同时出现于
  upsert/delete 均拒绝候选。

### 6.3 事实提取与归并算法

Runtime 只扫描当前 generation **完整产品历史**中已闭合的 Assistant Tool Call / Tool Result 配对，
并且只识别 `pin_memory`、`update_pinned_memory`、`unpin_memory`。完整产品历史已保留被 Summary 替换掉的原始消息，
所以每次从 Session 起点线性重算净变化，不建立增量游标或另一份账本：

1. 从空集开始，按产品消息和 Tool Call 原顺序处理全部可靠事实；Context Summary 本身不当作工具事实。
2. 最新 Summary 如已有 `programmatic_context`，先执行严格格式校验，但不把它作为跳过原始历史的增量游标；
   新段落始终以当前完整产品历史的重算结果覆盖。
3. 只有 `ToolResultStatus::Success` 且 content 是单一合法 JSON entry 时产生变化。失败、拒绝、取消和 interrupted
   结果全部忽略。
4. `pin_memory` 将完整返回值写为 `created_in_session` upsert。
5. `update_pinned_memory` 使用完整返回值覆盖旧值；已是 `created_in_session` 时保留该来源，否则标为
   `frozen_snapshot`。
6. `unpin_memory` 如删除 `created_in_session` 条目，直接移除 upsert，形成净零；否则移除旧 upsert 并写入
   `deleted_ids`，用来抵消冻结 System Prompt 中的旧值。
7. 成功的记忆工具结果如无法解析，说明规范历史与工具契约不一致；此时压缩失败并保留原 generation，
   不当作普通文本忽略。

重算使旧 Context Summary 没有 `programmatic_context` 时也能从仍然保存的原始工具结果建立首个权威段，不需要
SQLite 迁移或历史回填。这一过程仍不查询当前 Memory Store，因为 Store 还可能包含其他 Session 或 UI
在冻结快照后完成的变化；
把它们注入当前 Session 会破坏已确认的冻结语义。

### 6.4 组合点、限制与失败原子性

Rolling Summary 策略先生成已经结构校验的候选。`RuntimeContextCompactor` 随后：

1. 对同一 source generation 读取完整产品历史，并校验其最新执行投影与权威 Journal 快照相同；
2. 从该完整历史归并 `PinnedMemoryDeltaV1`；
3. 写入候选 Context Summary 的 `programmatic_context`；
4. 再次执行 replacement、usage 调整、工具配对与原样后缀校验；
5. 通过后才返回 Runtime 提交。

程序化段复用 `pinned_memory_limits()`：最多 256 个有效 ID，每条 ID/归类/正文复用现有限制，紧凑 JSON
不得超过 128 KiB。超限时整个候选失败，不截断、不淘汰条目、不提交半份记忆状态。

`agent-context` 只保存通用的 `programmatic_context` 字符串并统一渲染；Pinned Memory 工具名、V1 JSON 类型、归并和
限制都留在 `assistant-runtime`，不让 `agent-context` 或 `agent-types` 反向依赖记忆领域。

## 七、replacement、Provider State 与效果判定

### 7.1 replacement 形状

候选仍是：

```text
System prefix
ContextSummary {
  model-generated text,
  programmatic context,
  summary-call usage,
  compacted usage,
  usage adjustment
}
protected tail（原样）
```

- 最新 User Turn 中的 User、Assistant、Tool 消息及 Provider state 完整保留。
- compressible head 中的 Provider state 随被替换原文一起移出有效上下文；不将不透明载荷复制进摘要。
- 摘要请求使用同一已编译模型服务和精确路由；既有 Adapter 仍负责检查保留状态的 provider/protocol/
  route fingerprint，Runtime 不解释或跨 Provider 转换。
- 摘要响应中的 reasoning/provider state 不进入 Context Summary，只接纳非空 Text 与该请求 usage。

### 7.2 最小有效性门禁

本循环不引入 Provider 外 token 计数器。候选本地门禁为：

1. 存在至少一个完整 compressible block；
2. 一次摘要输出上限为 4096 token，输出非空且无 Tool Call；
3. 紧凑序列化后的 replacement Conversation 字节数小于源快照；允许“旧 Summary 替换为更短 Summary”
   这种消息数不变、但内容确实缩小的第二次有界恢复；
4. System prefix、protected tail、Tool Call/Result 配对、usage 调整和程序化段全部合法。

字节数只是“候选至少确实变小”的保守门禁，不作为 token 用量、不持久、不进入 UI。真正是否适配
Provider 窗口由下一次真实请求和 Provider overflow 决定。如果字节门禁对已有合法压缩样本产生假阴性，
实施中必须回到技术方案复核，不自行换成另一套 token 启发式。

## 八、父 Agent、子 Agent 与手动入口

| 入口 | 摘要请求来源 | 提交目标 | 共同不变量 |
| --- | --- | --- | --- |
| 父 Agent 阈值/overflow | Core live handoff 的完整正常请求 | 当前 Run 的 Session generation | 一次摘要、usage 减法偏移、记忆净变化、原子提交 |
| 子 Agent 阈值/overflow | 具体 child Agent live handoff，已含其 `load_skill` | ChildTask generation | 同上，不使用父 Agent 工具列表 |
| 手动压缩 | 当前 Session/model 编译的无 Run 请求配置 | IdleSession generation | 同一布局、候选校验、usage 减法偏移、记忆净变化 |

`RuntimeContextCompactor` 不再在构造时冻结一份可能缺少后续工具的摘要请求。自动入口的精确请求每次来自
Core handoff；手动入口才使用构造时冻结的无 Run profile。这同时修复当前父 compactor 在最终工具装配前创建、
子 compactor 在任务级 `load_skill` 追加前创建的不一致。

## 九、错误、取消与有界恢复

### 9.1 新增内部错误分类

`CompactionError` / `RuntimeCompactionError` 增加结构化内部原因，至少区分：

- live handoff 缺失或与 Journal 不一致；
- `ToolChoice::None` 与当前工具/模型能力不兼容；
- 摘要请求失败或 overflow；
- 摘要响应为空或包含 Tool Call；
- usage 调整引用的 Assistant 无效或不在保留后缀中；
- 成功记忆工具结果或程序化段无法校验；
- 程序化段超限；
- 候选未实际变小；
- 原子持久化或内存投影失败。

协议层仍优先复用 `ContextCompactionFailed`、`ModelExecutionFailed` 和现有手动压缩 outcome，不把 prompt、摘要、
工具结果或程序化 JSON 投影到 UI。如果实施时现有 code 无法支持用户可操作分支，再单独证明新协议码必要性。

### 9.2 有界续跑

- 保留 `MAX_AUTOMATIC_COMPACTIONS = 2`，不因当前 bug 上调或删除。
- 新 generation 在无新 usage 时使用压缩差值近似预检；无法形成差值时才返回 `UsageUnavailable`。请求成功即恢复
  Provider 真实 usage；Provider overflow 则可进行第二次
  真实恢复尝试。
- 摘要请求本身 overflow、候选无效或第二次仍无法继续时，保持原 generation 或以最后已成功提交的
  generation 有界结束，不循环生成摘要。
- 自动压缩沿用当前不可取消的原子提交边界；手动取消发生在提交前时不改变有效上下文。

### 9.3 M2 同步修复：Desktop 可靠投影归属

M2 验收期间发现偶发的新会话页面混入其他会话可靠 Assistant Turn。只读核查确认新旧正文仍分别位于
各自 Session JSONL，异常内容带可靠消息操作栏，不是 live tail 或持久化串写。该缺陷按用户要求在当前
版本同步修复，但不改变 C02 的压缩、协议或持久化契约。

Desktop 直接复用现有事实形成三道门禁：

1. `get_session_view` / `get_child_task_view` 返回后，先核对请求 owner、快照实体 owner 与
   `ConversationPage.owner` 完全一致；不匹配按协议错误拒绝，不进入可靠投影或 live reconcile。
2. `RuntimeProjectionStore` 按 Session/Child 记录已应用的现有 `observed_sequence`，拒绝并发读取中迟到的
   更旧快照。该 Map 只是前端请求排序状态，不新增协议 revision、generation 或持久化事实。
3. 同 owner、同 generation 的最新页只有在首条消息仍存在于缓存时才保留已加载的更早分页；完全无交集
   或空页边界不连续时，以服务端最新页替换缓存，禁止通过集合并集永久保留失配消息。

`ConversationView` 继续只渲染当前 owner 的可靠投影，不通过强制重挂载掩盖 Store 污染。Runtime 现有
Session 路径和 JSONL 读取不修改。

## 十一、验证方案

### 11.1 `agent-types` / Provider 投影

- 旧 Context Summary JSON 读取两个新字段为 `None`，新 JSON round-trip 保留 usage 调整和程序化段。
- 统一渲染保证模型摘要在前、权威程序化段在后；窗口估算与 Provider 投影使用相同文本。
- OpenAI-compatible 及其他现有 Context Summary 消费方回归，不改变旧 Summary 的 wire 结果。

### 11.2 `agent-context`

- replacement 保留旧 Assistant usage；调整指向该 Assistant 时按“保留 usage - head 末 usage + Summary 估算”计算。
- 覆盖被减值小于、等于和大于保留 usage 的情况；减法饱和到零，不出现无符号下溢。
- 前一个 Summary 的 `Subtract` 指向同一保留 Assistant 时可继承偏移；指向不同或无法解释时收敛为 `Unavailable`。
- 调整为 `Unavailable` 时返回 `UsageUnavailable`；首个新 Assistant 到达后直接使用其 usage；更新的 Assistant 无 usage 时不回退。
- 旧 Summary 无调整字段时保持兼容逻辑；`Subtract` 指向丢失、位于 Summary 前或指向无 usage 消息时拒绝。
- 旁路请求在追加指令前与原 `ModelRequest` 的 System/Conversation/Tools 完全相同，且保留采样、reasoning 和
  Provider Options；差异只有 ToolChoice、输出上限和末尾指令。
- 摘要返回 Tool Call、空文本、超限或候选未变小均不产生可提交 replacement。

### 11.3 `agent-core`

- 阈值预检交付下一个真实请求快照；Provider overflow 交付同语义请求快照。
- handoff 中含完整 tools/request-only context，但 `Debug`、AgentEvent 和 serde JSON 不包含正文。
- consumption、step 和现有终态事件对称性不变；旧 outcome JSON 继续可读。

### 11.4 `assistant-runtime`

- 以真实故障同构数据构造 `205421 >= 204800`：第一次压缩后下一次模型请求真实建立，不立即第二次压缩。
- 在压缩提交后、新模型请求前重启，结果与不重启一致。
- 父 Agent handoff 包含 disclosure/shell context；子 Agent handoff 包含具体任务 `load_skill`，Journal 子序列校验通过。
- 手动压缩后下一个 Run 对保留旧 usage 应用相同减法调整；NoOp、取消和 snapshot race 不改 generation。
- 改写/分叉分别覆盖 Summary 前、被调整 Assistant 前后的截断，确保引用存在性与工具配对。
- 旧 Summary 无程序化字段但完整产品历史仍含记忆工具结果时，首次新压缩可重算并补建净变化段。
- `pin -> update`、冻结条目 `update`、冻结条目 `unpin`、`pin -> unpin`、连续多次压缩、失败/拒绝/取消结果、
  非法成功 JSON 及 128 KiB 超限全部有定向测试。
- 完整产品历史中的旧 Assistant usage 和原 Tool Result 仍可查；执行投影只有一条最新 Summary 起点。
- 新请求在 protected tail 过大时真实 overflow，允许第二次恢复，最多两次后受控失败。

### 11.5 正式 Host 验收

在隔离的临时 Runtime Home 中运行，不对 `~/.ez-assistant` 做批量写入或清理：

1. 重放长任务阈值样本，记录压缩次数、generation、首个新 Provider usage 和最终 Run 状态。
2. 检查摘要模型请求记录，证明缓存前缀投影一致，并记录真实 `cached_input_tokens`。
3. 构造同一 Run 多次模型/工具交换、大 Tool Result 且逼近窗口的样本，观察修复 usage 后 protected tail 是否
   仍导致真实 overflow。
4. 未复现时，形成“C02 不实现轮内拆分”的关闭证据；复现时保存脱敏的输入构成和失败边界，停止本
   实现扩张并回到功能设计确认，不现场加剪枝。

## 十二、问题回答与方案结论

1. **旧 usage 如何处理？** Context Summary 持久化被调整 Assistant ID 和压缩点前最后 Assistant 的 `total_tokens`；
   新 Result 到达前使用差值加 Summary/后续增量近似预检，新 Result 到达后恢复 Provider 真实 usage。
2. **如何保持缓存前缀？** Core 交接它真实即将发送/已 overflow 的完整 `ModelRequest`；策略只改
   ToolChoice、输出上限并在末尾追加指令。
3. **轮内容量如何处理？** 保留现有完整 User Turn 规则，usage 修复后用正式 Host 样本验证；未复现即关闭
   剪枝候选，复现则回退到功能设计。
4. **记忆如何可信保留？** Context Summary 使用独立的 `programmatic_context`，Runtime 从成功工具结果还原净变化，
   使用确定 JSON 和现有 128 KiB 限制。
5. **Provider state 如何处理？** protected tail 原样保留，head 随压缩整体替换；同一模型服务和 Adapter 继续
   实施路由绑定，不复制摘要响应的不透明状态。
6. **自动上限是否改动？** 保留两次。修复后第二次只会由真实 overflow/新基线再次超限触发，不再被旧
   usage 虚假消耗。
7. **父/子/手动是否完全相同？** 候选、usage、记忆和提交不变量相同；自动入口使用 live request，手动入口因
   没有活动 Run 而使用无 Run profile，不声称缓存命中。
8. **如何证明修复完成？** 同时取得请求投影、故障同构定向测试、重启/分叉/子任务测试、记忆归并测试与
   隔离 Runtime Home 的正式 Host 证据，不以单个类型或单测通过代替端到端结果。

方案结论是：用 Context Summary 内的持久化减法偏移修正压缩后旧 usage，用 Core live request 保证自动压缩前缀真实一致，
用同一 Context Summary 的独立程序化字段保留记忆净变化。这三处都复用现有压缩、历史和提交主线，不引入剪枝、
多阶段摘要或第二份权威状态。
