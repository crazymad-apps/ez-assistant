## 二、背景与目标

企业用户身份需要由中心统一管理。后台管理员与以后通过 Host 使用助手的普通用户使用同一套账号和 Token 认证机制，但不共用页面入口：企业后台仅供管理员使用，普通用户在本机 Runtime 的 Desktop/Web 入口登录、退出、查看本人身份和修改本人密码。中心仍是身份与密码的权威来源，Runtime 不另建本地密码体系。现有 Host 单所有者密码机制继续服务个人模式，不能直接充当中心账号系统。

当前仓库已有 TypeScript Client、React/Vite Desktop 和 Host 私有认证/迁移实现，尚无独立 Center 应用。可参考现有工程实践及 [Host 迁移机制](../../../../../apps/runtime-host/src/storage/migrations/mod.rs)的显式迁移、准入和验证职责；不把 Rust Host 私有认证服务搬成中心依赖，不因中心建设修改 C02 所属 Runtime。

C01 的完整用户路径为：部署者配置中心与 PostgreSQL → 初始化首个管理员 → 管理员登录创建用户 → 通过真实身份 API 验证普通用户登录、本人身份、改密和退出 → 管理员调整用户权限或停用用户 → 验证旧登录态被撤销并查看相关审计。普通用户的 Runtime 页面入口与端到端接入由 C03 完成，C01 不建设普通用户后台页面。

完成本循环后，C03 可以基于稳定身份与登录契约接入 Host，C04 可以基于同一登录态管理限定用途的 LLM key。中心独立运行无需 Desktop、Client 或 Runtime 常驻。

## 三、非目标

- 不建设工作站注册、设备审批、Host 列表或中心路由。
- 不实现 Host 登录接入、用户本地建库与业务数据隔离，这些属于 C03。
- 不实现 Provider/模型管理、LLM 代理、配置分发、调用内容快照，这些属于 C04；页面不展示可点击但未实现的占位功能。
- 不实现多租户 SaaS、组织部门树、自定义角色、逐资源 ACL、SSO/LDAP、邮件/短信注册及找回密码。
- 不建设独立的管理员认证系统、手工 API Key 管理页或短时 key 续期流程。
- 不执行 C02 的上下文优化，不修改个人 Host 的现有访问机制。
- C01 提供可重复的构建、启动、初始化与迁移验证；正式企业安装制品、全套跨产品升级演练与发布归 C06。

## 四、功能范围与使用路径

### 4.1 首次部署与管理员初始化

部署者提供中心服务及数据库所需配置，启动前完成数据库准入和有序迁移检查。配置错误、数据库不可用或迁移失败时，明确报告失败，不能开放看似可用但无法持久化的管理服务。

首次初始化 SQL 直接创建超级管理员，不提供公网“抢先注册管理员”入口，也不另设初始化代码或配置。默认用户名 admin，密码按用户要求为 123456；SQL 只存预生成密码摘要，成功后重复启动不覆盖原账号、不重置密码。自动升级开关默认开启，关闭时不执行结构升级或账号初始化，需显式运行升级命令。升级和业务使用同一个数据库账号。公开默认密码应在正式使用前修改。

中心部署具有稳定的身份标识，用户记录具有稳定的用户 ID；两者用于后续 Host 判断本地数据归属，不建立工作站登记表。中心原地重启、升级以及完整数据恢复保留身份；全新部署不默认继承另一中心的身份。

首个管理员初始化完成后，打开中心地址进入登录页，使用同一登录流程进入管理后台。

### 4.2 用户和角色

首版只提供普通用户、管理员两种固定角色；超级管理员通过用户表独立字段标记，不新增第三种角色或权限配置引擎：

| 操作 | 普通用户 | 管理员 |
| --- | --- | --- |
| 登录、退出、查询本人身份、修改本人密码 | 允许，通过本机 Runtime 入口 | 允许，通过后台本人账号入口或 Runtime 入口 |
| 进入企业管理后台 | 不允许 | 允许 |
| 列表查询企业用户、创建用户、编辑显示名称 | 不允许 | 允许 |
| 设置用户角色、启用/停用 | 不允许 | 允许，受最后管理员保护约束 |
| 用户管理中重置任意用户密码（包括自己） | 不允许 | 允许，不校验目标用户原密码 |
| 查询中心管理审计 | 不允许 | 允许 |
| 使用后续企业模型能力 | 依后续循环接入 | 与普通用户遵循相同托管规则 |
| 查看任意 Host 的本地会话、文件或运行状态 | 本循环不提供 | 管理员角色不自动授予此能力 |

用户的最小信息为稳定 ID、唯一登录账号、显示名称、角色、超级管理员标记、启用状态及必要创建/更新时间。密码作为认证秘密单独处理，不作为列表或详情返回字段。

超级管理员规则（2026-09-18 用户明确）：

- 用户表增加布尔字段 `is_super_admin`，独立于角色字段；普通新建用户默认不带该标记。它是持久化的用户属性，不根据账号名、用户 ID 或前端传参推断。
- 带标记的用户默认具有管理员角色，并默认具有系统提供的全部权限，不依赖逐项授权；服务端权限判定必须识别此标记，不能只检查角色字段。
- 禁止删除该用户，不能仅隐藏删除按钮。这是超级管理员的固定保护规则；当前首版仍不提供任何账号删除功能，不因增加此规则而新增普通用户删除入口。
- 全部权限不表示绕过身份认证、凭证用途、个人改密原密码校验及业务不变量，也不新增读取任意 Host 本地数据的能力；企业模式模型托管规则保持不变。
- 两种密码操作同样适用于超级管理员：管理员用户管理可重置其密码，个人改密仍需原密码；成功后按统一规则撤销登录态。

首次初始化明确创建带标记的超级管理员。用户随后确认：管理 API 禁止停用超级管理员、将其降为普通用户或清除标记；不提供授予超级管理员的管理入口，仍允许编辑显示名称和管理重置密码。允许运维直接在数据库给其他用户赋予 is_super_admin 标记；代码一律按标记判断权限和保护，不能绑定 admin 用户名、固定 ID 或“只有初始化账号”。直接赋予标记但 role=user 的启用账号也具有管理权限，系统不自动改写角色；最后管理员保护继续按角色或标记判断。人工数据库操作遵循项目安全规则。

- 管理员创建账号并设置初始密码；普通用户不开放自行注册。初始密码交付由企业已有渠道完成，中心不新增通知系统。
- 首版登录账号创建后不改名，显示名称可编辑；稳定用户 ID 不随显示名称、密码、角色或启用状态变化。
- 账号采用启用/停用，不提供物理删除和旧账号复用，保留身份与审计关联。再次启用仍是原用户，但不会复活已撤销登录态。
- 用户列表可按账号/显示名称检索、按角色和启用状态筛选，并提供有界分页。
- 保证至少一个启用的管理员存在；不能通过停用或降权移除最后一个管理员，并发操作也必须维持此约束。
- “修改本人密码”是个人账号操作：只能修改当前用户密码，必须校验原密码，管理员走此入口时也不例外。
- “重置用户密码”是管理员的用户管理操作：可直接为任意用户设置新密码，包括其他管理员和管理员自己，不校验目标用户原密码。是否需要原密码取决于所用操作，而不是目标是否为自己；两种操作分别鉴权、校验和记录审计，不能合并为按目标身份自动切换的同一功能。

### 4.3 统一登录、登录态和退出

管理员与普通用户复用同一认证能力，而不是同一登录页。管理员通过中心登录页进入企业后台；普通用户通过本机 Runtime 的 Desktop/Web 入口进行登录、退出、身份查询和本人改密，不进入企业后台，也不为其提供中心本人账号页。后台入口必须校验管理员权限；普通用户访问时明确提示使用 Runtime，不能仅隐藏管理菜单。普通用户仍可通过统一身份 API 完成本人操作，由 C03 接入 Runtime。

- 登录成功签发一个新的内存 Token，返回当前用户身份和权限事实；不相信调用方提交的角色或用户 ID。
- 允许同一用户多处登录，各登录态并存，不因新登录踢出其他会话，也不覆盖其他会话的秘密。
- 刷新页面不主动撤销 Token；前端仍持有有效凭据时可查询本人。Center 进程关闭或重启会清空全部 Token 和关联 key，必须重新登录；用户和中心稳定身份不变。
- 显式退出只撤销当前登录态及其关联凭证，其他登录态继续有效。退出重复请求保持幂等，不重新激活登录态。
- 修改/重置密码、停用账号或改变角色时，撤销该用户全部登录态和关联 key；操作成功后重新登录才应用新的认证或权限状态。修改显示名称不撤销登录态。
- 角色变更使用统一撤销规则，避免已有登录态长期持有旧管理员权限；不另加权限 revision 或第二份权限缓存事实。
- 账号不存在、密码错误或账号停用时，对未登录者统一返回登录失败，不泄露账号是否存在。暂时不可用和访问受限使用可识别的结果类别。
- 不使用短时登录凭证加刷新令牌的双层机制。凭证在显式退出、上述撤销动作或服务重启前有效，基本登录频率保护由技术方案落实，不引入验证码平台等额外服务。

本功能设计定义权限变化后新请求的行为。已经通过授权且正在提交的写操作与撤销之间的顺序由技术方案明确并测试；不能承诺撤销会回滚已提交操作。Host 活动 Run 的取消与恢复归 C03/C04。

### 4.4 临时 LLM key 与登录态的关系

本循环确定并验证登录态和限定用途凭证的生命周期，供 C04 直接复用：

1. 每次成功登录签发新的 Token 关联 LLM key；它与本次登录态对应，不与用户全局记录或某个模型绑定。
2. key 在所属登录态有效期间持续有效；登出、账号停用、改密及角色变更按上述规则撤销，不增加短时 TTL 或续期机制。
3. key 的唯一用途是后续 LLM 代理准入。它不能调用身份查询、账号管理或管理审计接口；后台登录凭据也不能被当作 Provider API Key 使用。
4. 管理页面不显示或管理 LLM key；后续 Host 登录接入通过同一认证核心取得自己登录态的 key，不建立另一套账号体系。
5. key 不出现在普通用户资料、审计记录、日志、URL 或错误消息中。秘密保存与签发方式属于技术方案，不能为了页面重载重复返回既有秘密。

C01 通过真实登录、撤销、重启和权限测试验证该凭证关系；不为测试创建假的 LLM 代理或新的公开凭证校验业务入口。C04 负责真实代理消费、认证替换及调用结果验证。

### 4.5 管理后台页面

| 页面 | 可完成的用户动作 | 主要反馈 |
| --- | --- | --- |
| 登录页 | 输入账号和密码并登录 | 提交中、统一登录失败、服务不可用、成功跳转 |
| 本人账号页（管理员） | 查看账号/显示名称/角色、输入原密码修改本人密码、退出 | 原密码错误、修改结果；改密后提示重新登录 |
| 用户管理页（管理员） | 查询、筛选、创建、编辑显示名称、调整角色、启停；不输入原密码重置任意用户（包括自己）密码 | 字段错误、账号重复、权限失效、最后管理员限制、保存成功/失败；重置自己密码后提示重新登录 |
| 管理审计页（管理员） | 按时间、操作者、操作类型和结果查询记录，查看脱敏详情 | 有界分页、空状态、无权限、查询失败 |

后台仅向管理员开放，不提供普通用户账号门户；普通用户的本人账号操作界面属于 C03 的 Runtime 接入。功能权限在服务端判定；隐藏菜单不代替接口拒绝，统一身份 API 的本人操作仍按普通用户权限开放。刷新、切换页面或重复提交后，应从服务端实际状态恢复，不能仅靠前端按钮变色宣称保存成功。

用户列表和详情展示超级管理员标记，但不据此默认提供标记编辑入口。启停、角色修改和重置密码的界面明确展示目标账号及登录态失效影响，避免操作对象混淆；不为每个普通字段修改增加额外审批流程。页面布局、表单细节与按钮状态在交互设计指导中细化。

### 4.6 管理审计

中心记录管理员初始化、登录成功/失败、退出、创建用户、编辑用户、改密/重置密码、启停和角色变更。涉及账号管理的越权拒绝也应有可追溯结果，不记录所有普通读取请求以免膨胀为全站请求录制。

最小检索事实包含发生时间、操作类型、已认证操作者（无认证时为空）、目标用户、成功/失败结果、稳定失败原因和必要请求关联标识。角色/启用状态等普通字段可记录变更前后值；改密只记录事件，不记录原密码、新密码、密码摘要、登录 token 或 LLM key。

- 成功的用户管理变更与对应审计在同一数据库事务中提交，避免“账号已变更但无成功记录”。事务失败时返回失败，不写伪成功记录。
- 登录失败或越权等拒绝事件记录脱敏结果；审计记录失败不能将认证失败变为成功。数据库不可用时使用脱敏服务日志说明故障，不伪装成数据库审计已保存。
- 审计页只读；首版不提供任意修改/删除审计、全文内容搜索、导出或复杂保留策略页面。
- 本循环不记录 prompt、模型回复、文件正文或工具参数，也不建立 LLM 内容快照目录；这些属于 C04。

### 4.7 持久化、启动与故障恢复

用户、密码摘要、中心身份和管理审计由 PostgreSQL 持久化。Token 直接作为进程内 Map 的键关联用户，不入库、不计算哈希；关联 LLM key 同样只在内存。没有独立 Session 实体、会话 ID 或会话表；单实例重启后统一重新登录。

按现有 Host 库表管理原则组织显式 SQL 与有序升级，具备已执行记录、事务、准入、失败停止及实际结果验证；业务读写按用户新确认采用 TypeORM，但不按程序实体自动同步 Schema，不改变升级账本与开关。具体升级执行时机、备份入口和版本字段由技术方案确定。

C01 必须提供从空的隔离数据库启动、初始化账号、重启后恢复和重复执行迁移的可重复验证，且能清楚诊断配置错误、数据库断连和迁移不兼容。测试和开发数据不能指向用户 Runtime Home 或借用 C02 的测试数据；实际数据库写操作遵循项目数据库安全规则。

## 五、模块边界与契约影响

| 责任 | C01 的权威事实与行为 | 后续循环接入方式 |
| --- | --- | --- |
| 账号 | 稳定用户身份、角色、超级管理员标记、启用状态、密码验证 | C03 依据已验证身份路由本地用户域；不以登录账号或显示名称作为持久归属 |
| 登录态与本人账号操作 | 登录、身份查询、本人改密、退出、撤销及重启后的有效性 | 管理后台仅供管理员消费；C03 在 Runtime 提供普通用户操作入口，复用同一身份规则，不自行签发中心身份或保存另一套密码 |
| LLM key | 每次登录签发、限定用途、关联登录态、撤销 | C04 在代理入口校验后再访问上游；不将 key 与模型 ID 绑定 |
| 管理审计 | 已发生的中心身份/管理动作 | C04 增加模型管理动作与调用记录时复用必要关联，不能混淆调用正文与管理日志 |
| 存储与生命周期 | PostgreSQL 准入、显式迁移、服务启动关闭 | C06 将已验证能力编排为正式部署、备份恢复和发布流程 |

跨中心/Host 的稳定语义应在 C01 技术方案中给出契约样例与测试，包括身份归属、凭证用途、撤销、失败类别及协议兼容职责。除本稿明确的用户表超级管理员标记外，HTTP 路径、DTO 和详细存储 Schema 由技术方案确定。

具体框架采用已确认技术方案中的 Node.js/TypeScript、NestJS/Fastify、React/Vite；PostgreSQL 与 TypeORM 业务访问为最新确认边界。工程布局由技术方案固定，依赖组合仍需实施验证，不以设计确认代替构建与运行证据。

C01 不修改 Rust Core、Runtime 上下文、Host SQLite 迁移或现有 `assistant-protocol` 生成产物。若技术方案发现必须更改共享契约或根构建配置，先与 C02 协调文件归属；不创建 Runtime 用户域占位实现来模拟 C03 已完成。

## 六、关键取舍

| 选择 | 理由与代价 |
| --- | --- |
| 固定管理员/普通用户两角色，超级管理员使用独立字段标记 | 覆盖当前管理与使用需求，避免新增角色和权限配置引擎；服务端落实全部权限与禁止删除规则 |
| 管理员建号、账号停用不物理删除 | 保持身份、历史审计与后续本地数据关联稳定；暂不提供自助注册或清除账号的产品动作 |
| 多登录态并存、当前登出局部撤销 | 支持多终端使用；密码/角色/启用状态等身份变更统一撤销全部登录态，减少旧权限残留 |
| 无短时 TTL/刷新令牌 | 遵循用户确认的内存 Token 生命周期，中心重启全部失效；运维上必须能够通过停用/改密显式撤销 |
| 登录态与 LLM key 同一生命周期、不同用途 | 满足后续 endpoint/key 接入，同时避免把代理 key 升级为管理凭证 |
| 身份服务在 C01 完整验证，Host/LLM 接入后续完成 | 能以真实后台独立验收中心账号闭环，并保留与 C02 的代码和验证环境边界 |

## 七、验收标准

下表是 C01 完成标准，已结合各里程碑结果和用户页面确认完成核对；循环验收结论见开发计划。验证覆盖真实 PostgreSQL、服务和管理页面，单元测试不代替完整用户路径。

| 编号 | 验收场景 | 通过条件 |
| --- | --- | --- |
| C01-A01 | 干净部署与重复初始化 | 首个 SQL 创建默认超级管理员 admin / 123456，仅存摘要；无公开抢占入口；重复操作不覆盖已有身份 |
| C01-A02 | 统一认证与不同产品入口 | 管理员可登录后台；普通用户不能进入后台，通过真实身份 API 可登录、查询本人、改密和退出，无法操作账号管理或读取管理审计；Runtime 页面接入在 C03 验收 |
| C01-A03 | 用户管理闭环 | 创建、检索、筛选、分页、编辑显示名称、启停、改角色、重置密码实际持久化；账号重复明确失败 |
| C01-A04 | 最后管理员与并发变更 | 不能通过并发停用/降权操作使启用管理员归零，失败操作没有部分变更 |
| C01-A05 | 多端与重复登录 | 同一用户两次登录产生不同 Token 和 key，各自有效；退出一端只撤销该端，重复退出不改变其他会话 |
| C01-A06 | 停用、两种密码操作和角色变更 | 本人改密必须验证原密码（包括管理员），原密码错误不改密码或撤销会话；管理员通过用户管理可无原密码重置任意用户（包括自己），普通用户不可调用；审计区分两种操作。成功改密/重置、停用或角色变更后，目标用户全部旧登录态及 key 失效；启用或重新授权不复活旧凭证；显示名称修改不改变身份 |
| C01-A07 | 凭证用途与伪造身份 | LLM key 不能调用管理或身份接口；篡改用户 ID/角色不会取得相应权限；失败登录不签发凭证 |
| C01-A08 | 服务重启 | 已有用户与稳定中心身份保留，旧 Token/key 全部失效；重新登录不创建新用户 |
| C01-A09 | 管理审计与秘密排除 | 成功/失败可检索，管理变更与成功审计一致；数据库、日志及接口无密码明文或 token/key 泄漏 |
| C01-A10 | 故障与事务 | 数据库不可用、迁移失败和提交异常明确失败；不开放半初始化管理服务，不显示伪成功或留下部分账号变更 |
| C01-A11 | 真实管理页面操作 | 后台页面覆盖管理员日常操作和错误状态，分别验证本人改密与用户管理重置自己密码；不提供普通用户后台页面；直接调用 API 仍执行相同权限和原密码校验规则 |
| C01-A12 | 独立性与交接 | Center 单独构建运行，C01 私有测试与 C02 互不污染；提供可消费的身份、会话、key 生命周期契约，不要求先实现 Host/LLM 代理 |
| C01-A13 | 超级管理员标记与保护 | 标记在用户表持久化、重启不丢失；带标记用户默认具有管理员角色及全部权限，普通用户不能通过伪造字段提权；禁止删除，不因操作者也是超级管理员而绕过；不豁免身份认证、凭证用途及个人改密校验 |

循环验收只在开发计划中保留完成结论、用户确认、未完成项与必要风险，不单独创建验证记录或归档验证数据。用户确认验收、明确授权提交并完成阶段归档后，C01 才记为完成；本循环完成不代表 `v0.27.0` 企业产品已经可发布。

## 八、风险、兼容性与待确认项

### 8.1 评审结论与待补充确认项

本稿经评审保留以下方案，不再次展开已确定的总体目标：

- 固定两角色；管理员建号；账号首版不可改登录名、可改显示名称；账号停用而不物理删除。
- 多端登录并存；改密、角色变更和停用统一撤销目标用户全部登录态。
- 首个管理员由部署者服务端初始化。

2026-09-18 用户已明确两项边界：普通用户通过本机 Runtime 操作本人账号，企业后台仅供管理员使用，但复用统一认证；管理员的用户管理重置可覆盖任意用户（包括自己）且不需要原密码，个人改密入口则始终需要原密码。这些边界已在 C01 中实现，Runtime 页面接入仍归 C03。

同日用户明确：用户表增加超级管理员字段标记，带标记用户禁止删除、默认具有全部权限和管理员角色。随后确认首次初始化 SQL 创建带此标记的管理员；其补充规则现已确认：禁止 API 停用/降权/改标记，不提供授予入口，但支持数据库直接赋予其他用户该标记，所有判断只依赖标记。

如需调整这些选择，先在本功能设计收敛，不通过实现时临时新增第二套流程解决。

### 8.2 留到技术与交互设计的事项

- 框架版本、Center 工程目录、构建/启动入口与模块组织。
- 密码及 token 的安全存储、Cookie/显式凭据的接入方式、同源保护、HTTPS 部署约定、登录频率保护。
- 登录与停用/撤销的并发顺序、最后管理员约束的事务实现、失败审计与业务事务的边界。
- 稳定中心身份、用户身份、会话与限定 key 的字段、错误类型、协议兼容声明和契约测试。
- 显式 SQL 迁移、数据库准入、隔离测试资源与故障注入方案。
- 页面结构、表单校验、操作影响提示、加载/空/失败/失效状态。

上述事项已在技术方案、交互设计与 M0—M3 实现中收敛，当前没有阻塞 C01 的设计待决项。超级管理员规则按用户已确认的身份标记与接口保护执行。
