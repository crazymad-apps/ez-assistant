## 二、背景、现状与目标

### 2.1 设计时的既有事实与问题

1. v0.27.0 已修复一种压缩后沿用旧 usage 导致重复压缩的故障，并交付本地摘要、必要记忆
   变更保持和有界失败；本版不将该故障重新表述为尚未修复。
2. 当前最新完整用户轮次受保护。同一用户指令下不断积累工具结果时，即使更早历史已摘要，
   该轮仍可能耗尽窗口；既有隔离用例已证明此边界存在。
3. 当前窗口判断以最近完整响应的 `total_tokens` 加后续增量为主要基线，压缩后存在临时修正。
   压缩完成后不能立即得到新有效窗口的真实计量，是本地滚动压缩已有的限制：先使用临时
   估算，待下一次正常模型请求返回再由其真实 usage 校准。服务端压缩延续这一计量问题，
   并非首次引入；本版主动计量用于缩短该空档，适用于两种模式各自的有效输入。
   调用消耗与下一次有效输入并不天然相同，尤其不能直接用服务端压缩前的 usage 表示压缩后占用。
4. v0.29.0 已支持 Responses 历史续接与链失效后的本地重建，尚未接入原生 compaction item；
   历史续接、服务端自动压缩、输入计量是三种不同能力。
5. 产品历史已用 JSONL 保存规范消息，Assistant 的有序 Parts 已承载不透明 ProviderState。
   本地摘要已有完整产品历史与有效上下文的分别投影，无需另建一份持续追加的压缩历史。

用户近期“压缩后仍经常超过 50%”的反馈需要结合实际有效输入核查；不能仅凭显示数字确定
根因。M0 使用合成样本验证真实协议；后续按用户授权诊断实际会话，收口结果见开发计划，不将合成样本外推为所有用户任务的效果证明。

### 2.2 最终用户结果

- 长任务在支持的压缩策略下能够继续，包括同一用户轮次内持续进行工具交互和多次有效压缩。
- 用户知道当前使用本地摘要还是服务端原生压缩，以及自动触发由 Agent 还是服务端负责；模型配置决定唯一机制，真实路由能力负责准入校验，失败有明确原因。
- 历史消息仍可查看，任务约束、必要记忆变更和工具结果关系保持；取消、重启和断流不重放工具。
- 主会话和子任务展示各自当前有效上下文的占用与可信度，累计调用消耗继续单独展示。
- 无法安全回收、输入本身过大或能力不可用时停止无效恢复，保留历史并给出可采取的下一步。

成功不定义为所有任务压缩后低于 50%。应先区分固定提示/工具定义、必要任务输入、保留的近期
内容、可回收旧交互与计量误差；隔离样本与效果目标见技术方案。

## 三、范围与非目标

### 3.1 本版范围

| 能力 | 交付边界 |
| --- | --- |
| 高占用诊断 | 区分显示问题与真实容量问题，构造可重复的长文本、轮内工具和图片场景；真实用户样本另按授权处理 |
| 策略统一 | 模型配置决定会话唯一机制；服务端模式自动/手动均使用原生压缩，本地模式自动/手动均使用本地摘要，操作串行且不跨机制回退 |
| 本地改进 | 从保护整个最新轮次改为评估已闭合交互的回收机会，保护当前任务和未完成交互；连续成功压缩后可继续 |
| 原生状态 | 接收、可靠保存、回放统一 compact 返回的完整有效窗口；自动/手动共用状态格式与投影 |
| 窗口计量 | 基于实际有效输入区分精确、估算与未知；压缩、换模、重建后重新校准 |
| 恢复 | 覆盖正常续接、断流、链失效、重启、Fork、换模和路由变化，恢复次数有界 |
| 展示 | 复用现有上下文面板、输入区占用提示和子任务状态栏；不进行页面整体改版 |
| Goal 长任务 | 取消 Goal 累计 token 限制；用量继续统计，运行次数、连续失败及其他执行约束保留。累计次数超过上限可完整恢复，不作为会话存储损坏；自动续跑仍受次数门禁限制 |

### 3.2 明确非目标

- 不承诺任意超大单条消息、单张图片或当前任务不可缩减输入都能压缩后继续。
- 不新增任意历史编辑、工具结果外置/按需取回协议、自动重新读取文件或自动重放工具。
- 不将密文摘要转换为普通文本、长期记忆、跨模型通用状态或用户可编辑内容。
- 不增加独立压缩守护进程、后台自动维护会话、第二份上下文历史或企业中心会话存储。
- 不纳入 F02 的截图采集、预览窗口、窗口占用和插件实现；F01 处理其已有规范工具图片输入。
- 不在服务端模式启用本地摘要，不跨压缩协议兜底，不允许自动/手动操作并发提交不同窗口。
- 本版暂不引入普通生成请求内的 `context_management/compact_threshold` 自动压缩；保留 `POST /responses/compact` 作为统一原生压缩入口。输入计量仍是独立可选能力。

## 四、策略选择与使用路径

### 4.1 模型配置决定会话唯一机制

2026-10-10 用户明确：模型配置启用服务端压缩后，必须统一行为，同一会话绝不能有两种
压缩机制相互抢占。此约束覆盖自动、手动、阈值溢出恢复、断流恢复和后续 Run，不只限制
同一时刻或单次 Run。

用户随后澄清：**暂不引入回退机制，是因为当前缺少可靠的兜底方案，并非认定回退本身
不合理。** 因此，本版不做跨机制自动回退；保持当前机制的有限重试、可靠状态恢复和链失效
重建仍然保留。未来若形成经过验证、能保持上下文完整性和状态一致性、不会造成机制抢占的
兜底方案，可以单独设计并确认，不把本版取舍扩大为永久禁止回退的架构原则。

模型配置的“上下文压缩”分组区分两个子项：

- **启用服务端压缩**：选择压缩机制。关闭使用本地摘要；开启后新压缩使用上游原生状态；已有 Agent 摘要仍可作为文本上下文复用，不触发本地摘要器。
- **服务端自动压缩**：选择自动触发方，仅在启用服务端压缩后有意义。关闭由 Agent 按窗口阈值/模型超限判断后调用 compact；开启由服务端在正常请求内判断和执行，Agent 不再竞争触发自动 compact。

“服务端自动压缩关闭”不表示“Agent 自动压缩关闭”。手动入口始终跟随所选压缩机制。
能力声明用于校验配置，不能代替上述用户选项，也不因接口可用而自动开启。

| 启用服务端压缩 | 服务端自动压缩 | 行为与本版范围 |
| --- | --- | --- |
| 关闭 | 关闭/不可选 | 本地摘要；Agent 自动和用户手动共用本地机制 |
| 开启 | 关闭 | Agent 决定自动时机；自动/手动共用 HTTP compact。本版交付此原生路径 |
| 开启 | 开启 | 服务端决定自动时机；手动仍走同一原生机制的 compact。正常请求内自动能力本版暂缓，子项展示为暂不支持，不接受启用 |
| 关闭 | 开启 | 无效组合，配置校验拒绝，不能悄悄启用服务端机制 |

开启服务端压缩要求路由已核实支持 compact 及完整窗口回放；不支持/未知或原生状态不能
可靠处理时拒绝启用，不回退本地。服务端自动触发还需要单独验证对应能力，不能从 compact、
WS 或历史续接支持推断。本版不实现该触发路径，不因细分配置而扩大实施范围。
配置沿现有模型参数来源与固定参数规则，不增加会话级自由混搭开关。

每次新 Run 或空闲手动操作读取当前模型参数并确定唯一压缩机制；活动 Run 保持冻结，
自动、手动及错误恢复不得竞争或跨机制回退。参数刷新已是应用配置的入口，无需再次选择
相同模型，也不要求新建会话；新操作准入时可靠更新机制并重建执行投影，完整原始历史保留。

重建从后向前找最近可用压缩点。服务端模式接受相容原生窗口，也直接接受已有 Agent
文本摘要：保留原有装配逻辑，以 system message item 承载摘要，再接其后完整消息；
不转换为原生摘要，不为切换额外调用 compact。本地模式不解密原生状态；最近可靠边界为
原生压缩点时，从该点截断，仅使用后续历史，接受原生摘要无法沿用造成的信息损失，
不退回更早文本摘要或重新展开边界前原文。路由或作用域
不相容的密文不得发送；必要输入仍超限时沿当前机制有界处理，失败明确报告。

> 2026-10-16 记录纠错：用户确认此处原有“从最近文本摘要及后续原始事实重建；没有文本摘要则使用原始事实”
> 是误记，已按原决策纠正。当前代码仍采用原错误规则，修复尚未实施；不追认本版已交付或已验证此行为。
> 详见[输入纠错](../../../../inputs/260729-上下文裁剪压缩.md)。

个人直连与企业中心代理都纳入支持矩阵，但必须逐路径确认。企业路径需要能力下发、请求参数、
流式原生项、HTTP/WS 续接与计量路径共同可用；仅透传创建请求不代表全部支持。
未完成验证的组合标为未支持；启用服务端压缩时明确拒绝，不自动改用本地策略。
未开启该配置的新会话仍可使用已支持的本地策略，不把个人直连结果外推至企业路径。

### 4.2 自动执行

1. Runtime 从完整产品历史生成当前有效上下文，加入本次冻结的系统指令、工具定义及必要上下文。
2. 在正常模型调用前评估输入限制、输出预留与当前计量可信度。
3. 本版服务端自动压缩保持关闭，Runtime 维持窗口阈值/模型超限两类触发来源：本地模式进行摘要；原生模式调用与手动相同的 HTTP `/responses/compact`。阈值判断不生成本地摘要，不同时启用普通请求内的服务端自动阈值。超限后的同机制恢复受输入准入、重试与无进展预算限制；M0 已核实 compact 自身也可超限，此时停止重复恢复。
4. 完整压缩结果通过校验并可靠提交后，更新有效上下文，重新校准占用，沿同一 Run 继续。
5. 成功回收后允许以后再次压缩；连续无进展、错误或超出恢复预算时停止，保留最新可靠历史。

自动压缩阈值统一为配置窗口的 90%，本地摘要与服务端原生压缩使用同一比例，达到阈值即触发。
模型返回上下文超限时仍沿当前机制启动有界恢复，手动压缩不受该阈值限制。
原生压缩请求本身也必须满足上游准入约束；原生压缩不能被当作接收任意超窗请求的保证。

### 4.3 手动压缩与取消

手动入口跟随会话唯一机制。本地模式执行本地摘要；原生模式调用 HTTP
`POST /responses/compact`。自动和手动共用同一个原生实现，仅触发来源不同。

| 当前策略 | 自动触发 | 用户点击“立即压缩” |
| --- | --- | --- |
| 本地摘要 | Runtime 达到窗口阈值或收到模型超限后组织普通摘要请求 | 同一套本地摘要流程 |
| 服务端原生压缩 | Runtime 根据相同触发来源调用 HTTP compact，按准入及恢复预算执行 | 同一套 HTTP compact 请求和完整窗口提交 |

这里的“本地”指 Runtime 组织普通摘要请求，模型仍通过配置的模型服务执行。
原生压缩内容由上游生成，本地只判断触发时机并可靠提交结果，不混入本地摘要。

- 本体只知道标准 HTTP 请求和结果。企业 API 路由转发上游 `/responses/compact`；订阅路由由企业中心封装为 Codex V2 WS `response.create` 加 `compaction_trigger`，将完整成功结果规范化为 compact JSON 返回。本体不拼 trigger、不实现 WS、不判断订阅类型。
- 普通生成 `/responses` 仍沿既有 HTTP → WS → SSE 桥接；压缩入口返回完整 JSON，不能仅把上游 WS 帧原样当 compact 响应。
- 自动/手动共用原生能力、作用域、状态校验、有效投影和费用来源。完整返回窗口整体保存和回放，不仅提取密文；中心适配须保留该协议要求的任务/图片内容。
- 手动复用同会话互斥、取消和失败提示；活动 Run/pending 未收口时拒绝。压缩提交后旧续接失效，下一正常调用从新窗口建立链，不维护第二个链头。
- 自动压缩属于 Run 内受管操作，随 Run 取消；手动沿现有取消入口。只有完整可靠结果才生效，未提交状态不激活。
- 不支持或未知的路由明确拒绝，不回退本地摘要或临时换另一压缩机制。

2026-10-10 用户澄清：HTTP 是本体统一接口，API/订阅差异归企业中心转发封装。此次
暂缓的是普通生成请求中的服务端自动阈值机制，不能扩大为删除 HTTP compact 能力。

## 五、本地回收与必须保护的内容

### 5.1 回收边界

本地摘要继续使用当前模型的旁路请求和既有可靠提交机制。优先摘要较早完整轮次；当主要体积
来自同一当前用户轮次时，允许评估其中较早且已闭合的工具交互，不再仅因属于最新轮次就永久保护。

“已闭合”要求该批 Assistant 工具调用和全部结果均可靠保存，且不存在仍待执行/待落账的配对。
一个并行工具批次不能只摘要其中部分调用或结果。近期仍直接供下一步使用的完整交互保留；
摘要需要包含任务目标、关键约束、已做动作与结果、当前进度、未完成事项和必要引用。

当前任务指令不能凭空消失或被另一条伪造用户消息取代。技术方案必须明确原始用户指令、
轮内摘要与保留尾部如何形成合法有序上下文，并检查现有 Summary 布局和历史替换校验；
若必须改变现行完整轮次保护规则，应同步架构与模块约束。

### 5.2 不变量

- 完整产品历史保留；有效输入可以使用摘要，但不能把摘要写回覆盖原文或伪造原始消息身份。
- 未闭合工具调用、对应结果以及同批次配对不可切断；压缩不触发任何真实工具执行。
- 冻结系统提示与工具定义保持；MCP 目录/选择、Shell 上下文与程序化记忆变更按现有规则恢复。
- 图片和文件引用以真实模型投影计入窗口；历史图片详情与来源仍可读取，不把图片字节数当 token。
- 本地摘要请求不先裁掉原始输入来伪装为原前缀，避免无依据破坏缓存；但不承诺缓存一定命中。

### 5.3 进展与有界失败

有效压缩不能仅以摘要非空、序列化字节变短或模型请求成功判断。应确认合法上下文、必要信息
保留以及下一次调用可进入；可计量时检查实际回收，无可靠计量时明确证据限制。

现有“整个 Run 最多两次自动压缩”需要调整为对连续无进展或恢复失败设置上限，使持续取得
进展的长任务可以再次压缩。Run 的步数、工具、时间和取消预算继续生效，不能借压缩重置。
具体次数和进展判定归属技术方案，并覆盖“换一个摘要但容量不降”的情况。

不可缩减任务输入、当前未完成交互或固定提示本身过大时，有界返回“必要上下文超出模型限制”。
给出缩小输入、拆分任务或选择更大窗口模型的操作方向；不循环摘要同一内容直到超时。

## 六、历史、原生状态与有效上下文

### 6.1 已确认方向

2026-10-10 用户已确认：保留现有 JSONL 完整产品历史；原生自动压缩项复用 Assistant
响应有序 Parts 中的 ProviderState，补充明确的上下文替代语义；本地摘要与原生项由统一
投影识别。字段名称和编码在技术方案定稿，不另建持续追加的压缩历史，不将密文伪装为文本摘要。

| 数据/投影 | 含义与使用者 |
| --- | --- |
| 完整产品历史 | 原始 User、Assistant、Tool、已提交摘要/原生状态等；用于历史展示、审计、Fork 截断和兼容重建 |
| 有效上下文 | 当前策略、兼容路由下实际参与后续模型调用的规范内容，由已提交历史派生 |
| 原生压缩项 | Provider 生成的不可解读状态；按历史归属、协议与格式回放，不因模型名称或企业入口地址改变而丢弃 |
| 历史续接信息 | 续接 ID、绑定与一致性依据；用于减少传输，不能自动充当压缩边界 |

本版以统一 compact 的完整返回窗口形成替代边界，复用 Assistant 有序 Parts 的
ProviderState 保存。窗口内部 output 的顺序与保留项必须整体保持，不仅提取密文，
不在容器内部再次裁剪。后续消息及闭合工具批次继续追加，原始历史保留。

示例：`U1 → 已完成交互 → 压缩状态 W → 后续完整交互 X`，其中 W 包含 compact 的
整个有效窗口。重建使用稳定指令/工具 + W 整体展开 + X；历史面板仍能查看 U1 和早期
交互。W 的内部保留规则由上游协议与中心适配确定，本体不解密或重新摘要。

### 6.2 可靠生效

- 上游流中收到原生项不等于压缩完成；中心取得完整成功终态并返回 compact JSON 后，本体仍须校验完整窗口、原生项合法性与存储限制。
- 有工具调用时，沿用现有工具执行与完整批次落账边界；不能先让历史只留下半组工具交换。
- 原生状态及其必须保留的有序内容可靠提交后，才更新后续有效输入与占用展示。
- 断流、取消、校验失败或写入失败，未提交的新状态不激活，继续保留上一可靠边界。
- 读取时不依赖内存中的第二份压缩账本；重启可从可靠产品历史重新推导有效上下文。

密文不进普通消息文案、记忆提取或常规诊断日志。复用现有大小和格式校验，不因支持原生
压缩取消 ProviderState 的资源限制；超限作为明确错误处理。

## 七、续接、断流与其他恢复场景

| 场景 | 行为与停止条件 |
| --- | --- |
| 正常链有效 | 按现有绑定和一致性检查继续增量发送；本地有效投影变化不擅自修改远端链 |
| 传输断流，但未确认链丢失 | 沿用已有有限传输重试；不把每次断流都等同于历史失效，不重放已执行工具 |
| 明确返回历史链不可用 | 每个逻辑模型调用至多进入一次本地重建，使用最近已可靠提交且相容的压缩状态及其后完整内容 |
| 最新压缩只收到一部分 | 忽略该未提交结果，从上一可靠状态恢复；后续已可靠提交的内容仍须保留 |
| 重建输入仍超限 | 按所选策略的有界恢复处理；仍不可装入则明确失败，不无上限向前尝试或重复全量发送 |
| Runtime 重启 | 重建有效投影；用户继续任务时重新评估链与计量；不自动重放工具或自动恢复已中断 Run |
| Fork 到历史位置 | 从截断后的完整历史生成新执行绑定，只选该位置之前完整有效的边界；父会话的远端续接身份不直接继承 |
| 换模/入口地址/续接绑定变化 | 旧 ID 不能续接时重建新链，已有完整压缩窗口仍可参与最近边界选择；不按模型名称、入口地址或临时周期丢弃窗口。原生模式可复用 Agent 文本摘要，本地模式不解密原生状态；不额外生成交接摘要，不调用另一机制兜底 |
| Provider/Protocol 或窗口格式不兼容 | 明确报告不兼容，不静默丢弃最近原生窗口退回大量旧原文；原生项是否被当前上游接受由上游判定 |
| 原生项损坏或可靠边界不合法 | 不使用损坏状态；按可恢复的完整历史检查，有界失败并报告，不能静默截掉数据继续 |

重建中的“完整”指完整有效模型输入，包括稳定指令、工具定义、可靠压缩项和必须保留的后续项；
并不默认把全部原始历史再次发送。保留原始历史的用途之一是换模后的重新准备，但它可能
很大；按目标机制无法装入时明确停止，不能临时调用本地摘要来为服务端模式准备输入。
技术方案说明准入、安全切换与停止条件，不能假定原生密文可转码。

Fork 只使用授权继承的截断历史内完整边界；新绑定只隔离临时续接 ID，不因绑定变化丢弃该历史内的压缩窗口。子任务具有自己的模型、历史和压缩边界，不继承父会话的不透明状态。

## 八、窗口计量与界面行为

### 8.1 统一计量口径

“当前上下文”是当前已提交状态及待发送内容组成的有效模型输入。它包含真实投影后的系统
指令、工具定义、消息、工具结果、图片和原生状态；不是 HTTP 本次增量 body 的大小。
输出预留参与请求能否装入的判断，但不伪装成已经占用的输入 token。

累计消耗、上一轮消耗、缓存命中沿用现有账本语义。压缩不倒扣已发生费用；原生自动压缩
响应按 Provider 返回的 usage 记账，不因保存一个 ProviderState 再重复计费。

| 可信度 | 展示与判断 |
| --- | --- |
| 精确 | 当前输入及路由获得可核实的 Provider 计量；可显示 token 和百分比 |
| 估算 | 沿用正常响应 usage 基线与新增内容估算，明确“约”；压缩后尚未校准时说明计量滞后 |
| 未知 | 缺少可用 usage 基线且无法形成有依据的估算；显示“占用未知”，不显示 0 |

实际输入变化后，旧精确结果不能继续标为精确。压缩、换模、路由变化、历史重建、工具集合
变化均触发重新评估；尚未计量的新内容存在时，应降为估算或未知。
单次调用报告的总消耗不能直接作为服务端压缩后的有效窗口权威值。

### 8.2 计量获取与失败

本节处理既有“压缩后计量滞后”问题，不能将额外计量接口误写为服务端压缩才能产生的需求。
本地摘要与服务端压缩完成可靠提交后，都面对新有效输入尚未被正常请求计量的空档；
本版在路由支持时主动计量，不必为取得窗口信息等待下一次正常模型生成。

支持的 Responses 路由可使用输入 token 计量接口，但该能力需要独立声明和验证，尤其覆盖
原生压缩项、工具图片与续接场景。只有确认服务返回的数字对应完整有效窗口，才标为精确。
无法核实密文占用时不得用密文字节/字符数估算。

主动计量接口不支持、失败或不能核实完整窗口时，两种模式均沿用现有方案：最近一次正常
响应 usage 加新增内容估算，等待下一次正常请求返回后校准；接口不可用不直接导致占用未知。
本地压缩沿用既有扣除已回收内容、加入摘要的临时修正。服务端压缩后允许暂时计量滞后，
已有数字作为待校准的参考估算显示“约”，不能宣称是新窗口的精确占用，也不按密文长度
推算压缩率。compact 调用的 usage 仍只用于消耗记账，不能替代压缩后窗口基线。
只有既无可用基线、又无法形成有依据的估算时才显示未知。后续正常请求的 usage 只校准
实际计量过的输入；若请求内部又发生压缩，仍须保留估算及待校准说明。

计量在输入结构或可靠边界发生变化时按需获取；复用当前请求准备结果，界面刷新不反复发请求。
技术方案给出远端计量的超时、合并与调用频率预算，不新增持久化计量流水或全局缓存服务。
共享窗口规则不自行联网，计量由模型/宿主能力装配提供。

展示计量失败不单独终止本可执行的任务。未知时沿所选策略、显式模型限制和现有 Provider
溢出错误进行有界处理，不能把未知当成无限可用或随意跳过已知输入限制。

### 8.3 最小界面调整

- 复用现有占用环和上下文面板；显示当前策略，精确值正常显示，估算值带“约”，未知使用中性状态。
- 提示明确说明当前有效输入、模型窗口及可信度；已知输入上限与输出预留可在详情解释。
- 重新校准期间优先显示既有估算并标“约”；压缩后旧基线注明待校准，不冒充新窗口精确值；无可用估算才显示未知，不先显示 0。
- 本地压缩沿用现有进行中/取消/完成/失败反馈；服务端只展示有真实依据的结果状态。
- 子任务沿用同一口径，显示自身窗口；父会话累计与子任务消耗继续分开，不串用模型窗口。
- 不显示密文、续接 ID、内部请求哈希；失败文案聚焦“历史连接失效，重建失败”或“必要输入过大”等可理解原因。

本版无需单独界面交互设计指导，上述状态在现有组件内完成。未来若需要新增
操作流程或明显改变状态流，应先补交互指导再进入开发计划。

## 九、模块边界与普通工具契约

| 所属层 | 职责和必要调整 |
| --- | --- |
| agent-types | 在既有有序 ProviderState 中表达原生上下文替代事实，保持格式/资源限制和工具配对语义 |
| agent-model / Adapter | 明确各项路由能力、原生项编解码、输入计量与续接兼容；不隐藏工具循环或持有产品会话状态 |
| agent-context | 共享合法布局、轮内回收边界、窗口判断和进展规则，不依赖 Runtime ID、数据库或网络 |
| agent-core | 单次执行继续使用宿主装配能力，保持工具执行与取消/预算边界 |
| assistant-runtime | 唯一策略 owner、完整历史和有效投影、可靠提交、父/子任务编排与有界恢复 |
| Runtime Host | 现有文件持久化、模型路由及传输适配，不保留第二份上下文权威状态 |
| 企业中心 | 能力下发、必要代理端点和既有身份/调用管理；不保存产品 Session 历史或独立运行压缩调度 |
| 协议 / Desktop / Web | 在现有 usage/context 与压缩投影上表达策略及可信度，客户端不自行决定压缩或计算另一套占用 |

现行架构禁止 Provider 在原执行内隐藏压缩；本 Feature 需要明确允许已声明的服务端原生
自动压缩，同时仍禁止 Adapter 自行发隐藏摘要请求或 Agent Loop。有效占用基线、最新完整
轮次保护及有效上下文起始布局也需按最终技术方案同步，不能只改实现而保留冲突规范。

Computer Use 已从本版剥离。F01 继续保证规范工具调用/结果和图片来源可核验、完整历史可展示、父/子任务上下文独立；未来 Computer Use 分支回并时不得依赖压缩内部字段或绕过这些契约。本版不等待其实现与验收。

最小新增核对：现有 JSONL、有序 Parts、ProviderState、Summary、可靠追加、Session 互斥、
usage 账本和上下文面板足以承载主要流程，继续复用。仅靠现有事实尚无法区分“普通原生状态”
与“替代此前上下文的原生状态”，现有占用投影也无法表达数字可信度；这两项语义必须补足，
具体落点由技术方案确定。删除额外历史文件、压缩服务或全局计量缓存后，能力闭环仍成立，
因此不引入这些机制。

## 十、验收标准

| 编号 | 场景与完成判定 |
| --- | --- |
| A01 | 开关与路由能力共同决定准入：启用服务端压缩只启用原生机制；服务端自动压缩单独决定触发方，本版不可启用；不支持/未知明确拒绝，不回退本地摘要；仅支持或仅有历史续接能力不会自动开启 |
| A02 | 本地摘要后新请求可继续，完整历史可见；当前系统/工具、任务约束、记忆变更和必要运行上下文保持 |
| A03 | 同一用户指令的持续工具任务至少经历多次有效回收并继续；本地轮内改进有直接验证，不仅调整阈值 |
| A04 | 巨大必要输入、未闭合工具批次、无进展摘要和连续失败均有界停止，错误可理解；Run 总预算不被压缩重置 |
| A05 | 原生压缩项在文本前/后、同响应多个原生项及工具调用组合中保持顺序；后续续接与重建不丢保留项或切断配对 |
| A06 | 流结束前断开、用户取消、终态校验失败和落账失败均不激活未提交压缩结果；旧可靠状态和已完成工具结果可恢复 |
| A07 | 链失效时从可靠相容压缩项及后续内容重建成功；每逻辑调用最多一次链重建，无完整原始历史的默认重发，无工具副作用重放 |
| A08 | 正常 ID 续接不会因本地压缩投影的前缀变化每轮失效；HTTP/WS 及代理绑定保持正确隔离 |
| A09 | 重启、边界前后 Fork、同模型新绑定、换模和路由变化符合恢复表；活动 Run 不因配置刷新改变机制，新 Run 接纳最新参数并复用可用边界；Agent 摘要通过原有 message item 装配，不生成转换摘要；模型/入口地址/续接绑定改变不丢弃窗口，协议或格式不兼容明确失败，过大重建有界失败 |
| A10 | 文本、工具定义、图片、原生状态及增量发送场景的计量口径正确；缓存不扣窗口，估算/未知不标精确，失败不显示 0 |
| A11 | 压缩前后占用重新校准，累计消耗保持；主会话/不同子任务/不同模型不串值；界面刷新不重复计量请求 |
| A12 | 本地自动/手动共用摘要；原生自动/手动共用 HTTP compact，企业中心封装 API/订阅差异；完整窗口可靠提交后新建续接链，互斥/取消/能力守卫覆盖 UI 和 Runtime，不并发、不跨机制回退，超限恢复有界 |
| A13 | 旧历史、无新语义的 ProviderState、既有本地摘要可按确认的兼容策略读取；新状态的旧 Host 准入与回滚边界明确 |
| A14 | 既有 MCP、Shell、工具图片详情、记忆变更、审批审计与历史续接不回退；普通工具图片来源契约无需读取压缩内部数据 |

确定性边界以测试验证，原生项真实可回放性、压缩效果和代理兼容性需要受支持路由的真实验证。
假 Provider 或模拟 token 数不能替代上述真实能力结论；未验证组合不能登记为支持。
本地容量与原生容量的样本目标和通过条件见技术方案；不承诺所有任务固定压缩比例。

## 十一、兼容与已确认取舍

### 11.1 兼容和数据边界

沿用现有 JSONL，不因新增语义默认重写全部历史；旧消息缺少新事实时仍遵循原有语义。
旧 Host 即使能反序列化新字段，也可能不理解压缩边界，因此必须评估存储最低 Host 准入、
应用协议、TS 投影、企业接入要求与回滚；不能只凭“可选字段”宣称完全兼容。

本版尚未公开发布的中间形态直接统一到最终设计，不为设计中的临时命名新增别名或双写。
实际迁移和既有数据写入另遵循用户数据安全规则。恢复备份也不能替代对新
格式和最低 Host 版本的兼容检查。

### 11.2 已确认的功能取舍

1. 本地轮内已闭合交互回收纳入必要交付，同时保留当前任务约束、近期完整交互及未闭合配对。
2. 用户已明确模型配置决定会话唯一机制，自动、手动与各类恢复不得混用；该约束已按 §4.1 固定，不再列为自动选路的候选取舍。
3. 按用户后续澄清，原生模式自动/手动共用 HTTP compact，API/订阅差异由企业中心封装，普通请求内的自动阈值机制暂缓；本地模式共用摘要，两种触发来源串行提交同一有效上下文。
4. 展示采用精确/估算/未知三种口径；计量接口不可用时沿用既有 usage 与增量估算，压缩后等待正常响应校准，不将参考估算冒充精确值。

2026-10-10 用户确认功能取舍及 JSONL、ProviderState、可靠边界与重建方向；后续实现和验收修正已收敛到技术方案，2026-10-13 确认本版验收。
