# v0.12.0 M5 验证与验收准备

## 一、当前结论

M5 已完成实现、验证并获得用户确认。本记录保存进入版本验收前的证据索引；最终版本结论
由 [`验收记录`](验收记录.md) 承接。

本轮形成三条相互独立的回证链路：

1. 临时 Runtime Home、SQLite、Workspace 和 loopback Provider 驱动的正式 Host 自动验收；
2. 私有 Web Demo 的真实浏览器交互验收；
3. 只读既有模型配置、业务数据完全隔离的真实 LLM Plan → Build → Shell 审批 smoke。

## 二、M5 实际交付

- Web Demo 支持 Plan/Build 与 Ask/Auto 切换，模式切换不创建 Message 或 Run；每次提交显式携带
  当前 variant。
- “继续调整计划”和“开始实施”只切换 Session variant 并填充普通 User Message，不增加协议
  状态机。
- Demo 展示 pending approval 的已解析事实、持久规则预览和 Runtime 提供的可用决定；决策仍由
  Runtime 原子消费。
- 权限重载展示三层文件状态和安全诊断；无效 JSON 不替换旧 cohort。
- 页面选择、刷新和 SSE 重连统一从 Session、Run、Conversation、Attachment 与 pending approval
  快照重建，不复制业务权威状态。
- 高频正文、reasoning 和工具输出按动画帧批量写入 DOM，自动滚动每帧至多一次且尊重用户主动
  上滚；历史使用离屏 Fragment 一次挂载，并对 Demo 同时展示的消息数和超长文本设上限。
- 正式 Host 回归覆盖 Session 模式持久化、两次进程启动、Global 手工 JSON reload、Injected Part、
  Workspace Allow 的 variant 隔离和重启后 pending approval 清理。
- 默认忽略的真实 LLM 测试完成 Plan 调查、显式 Build、真实 Shell 审批和隔离文件修改验证。

## 四、实际执行的验证

以下入口已在当前工作树实际通过：

```text
node --check apps/runtime-host/src/http/web_demo/app.js
cargo fmt --all --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace
cargo test -p assistant-runtime-host --all-features
cargo test -p assistant-runtime-host --no-default-features
cargo test -p assistant-runtime-host --test v0_12_real_llm --all-features -- --ignored --nocapture
cargo doc --workspace --no-deps
cargo metadata --format-version 1 --no-deps
cd apps/desktop && npm run build
cd apps/desktop && npm run tauri -- build --no-bundle
git diff --check
```

真实浏览器另外完成模式切换、快捷 Build、Ask/Auto、权限重载和页面刷新后的权威状态恢复，
浏览器 Console 无错误。长任务渲染修复后又实际启动临时 Host，复查页面加载、连接、Session
选择和历史重建入口，Console 仍无错误；临时配置副本和 Runtime Home 已删除。

实机会话暴露出原 `request_timeout_ms = 300000` 被 reqwest 解释为完整 SSE 请求总预算，两个
持续输出的模型 Step 均在约 300 秒被本地切断。修复后默认 Transport 不再设置 reqwest 总请求
timeout，而是分别约束响应建立和相邻正文 chunk 空闲时间；连续 chunk 可以超过配置时长继续
完成，空闲超时仍形成建流后 `TurnFailed(Timeout)` 且不透明重试。新增真实 loopback HTTP
回归覆盖响应建立超时、持续流超过配置时长和流空闲超时三条路径。

修复后执行：

```text
cargo clippy -p agent-provider-openai-compatible -p assistant-runtime -p assistant-runtime-host --all-targets --all-features -- -D warnings
cargo test -p agent-provider-openai-compatible --all-features
cargo test -p assistant-runtime --all-features
cargo test -p assistant-runtime-host --all-features
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace
```

结果：Provider 102 项通过、1 项真实 API smoke 按设计忽略；Runtime 85 项通过；Host 46 项单元
测试、v0.10/v0.11/v0.12 正式验收测试均通过，2 项真实 LLM smoke 按设计忽略；随后 workspace
all-target/all-feature Clippy、完整测试、fmt 和 diff check 通过。

一次并行运行 Host `all-features` 与 `no-default-features` 时，两套构建竞争同一 target，Web Demo
测试短暂取得不含启动开关的二进制并以参数错误退出；停止并行后串行重跑同一 all-features 套件
全部通过。该现象属于验证编排干扰，不是 Runtime、HTTP 或 Demo 行为失败。

## 五、数据与安全边界

- 自动测试只使用 `tempfile` 目录和临时 SQLite；没有读取或写入用户默认业务数据库。
- 真实 LLM smoke 只读 `~/.ez-assistant/config.toml`，复制到临时 Runtime Home；Session、Run、
  Conversation、权限文件、Workspace 与测试输出均位于临时目录并由测试清理。
- 真实 smoke 产生少量模型费用；执行成功。
- Host 输出检查未发现 API Key、Bearer Token、完整 Prompt、测试文件内容或完整模型回复。
- 浏览器人工验收使用的临时 Host 已关闭，含配置副本的临时目录已删除。

## 六、进入版本验收前的已知边界

- Web Demo 仍是默认关闭的私有验收客户端，不是正式桌面 UI；其卡片、快捷文案和布局不构成产品
  交互契约。
- Plan Shell 使用当前 OS 用户权限，不是强沙箱；结构化文件硬边界不能约束 Shell 绕过。
- pending approval 只属于活动 Runtime 内存；重启后 Run 按 interrupted 结算，需要用户重新发起。
- Global 权限仍只能手工编辑并显式 reload，审批不会写入 Global。
- 当前没有已知阻断版本验收的问题。
