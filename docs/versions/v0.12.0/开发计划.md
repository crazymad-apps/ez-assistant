# v0.12.0 开发计划：Plan/Build、分层权限与正式工具策略

## 一、计划信息与设计依据

- 版本：`v0.12.0`
- 状态：已确认
- 当前阶段：M0–M5 与版本最终验收均已确认，版本已归档
- 功能范围：[`功能设计`](功能设计.md)
- 实现依据：[`技术方案`](技术方案.md)
- 版本状态：[`docs/版本管理.md`](../../版本管理.md)

- M5 证据索引：[`验收准备`](验收准备.md)

本计划只维护里程碑顺序、交付范围、验证入口、完成判定和确认门禁。模式冻结位置、
JSON 权限格式、审批状态机、SQLite schema 与工具中断恢复以已确认技术方案为准，
不在计划中建立第二套设计。

本版本不建设正式桌面 UI。Runtime Host Web Demo 只在最后里程碑扩展，用于通过正式
HTTP API 验收已经完成的 Runtime 能力；它不提前主导协议或业务状态设计。

## 二、推进原则

1. M0 至 M5 顺序推进。每个里程碑完成实现和验证后先汇报为 `🟨 待确认`；只有用户
   明确确认后，才能标记 `✅ 已完成`并进入下一里程碑。
2. M0 先完成模式历史事实与持久注入。M0 确认前不让 Plan/Build 影响工具集，避免
   Message、Input、Run 和工具编译同时变化。
3. M1 先建立严格 JSON 权限文件、CAS 写入、Registry 与 reload。M1 确认前不启用
   正式权限决策，避免 Authorizer 依赖尚不稳定的规则源。
4. M2 完成规则匹配、能力硬策略、Auto fallback 和 Guardrail，但正式 Host 仍保留
   v0.11 安全默认；M3 的审批闭环完成后才删除危险验证开关并默认装配正式本地工具。
5. M3 的持久授权必须先成功写入权限文件并更新 Registry，才能让 pending Tool Call
   继续；不允许为了 Demo 先放行、后补写。
6. M4 只在 Recorder 和 Tool Exchange 可靠边界保存 pending started 事实，不得把 SSE
   或可丢 AgentEvent 当作恢复事实，也不建立永久工具审计副本。
7. Protocol、Runtime、Host 和 Web Demo 同步演进，继续使用 `PROTOCOL_VERSION = 1`，
   不建立 V2、兼容路由或第二套权限格式。
8. 自动测试只使用 `tempfile` Runtime Home、临时 Workspace、SQLite、权限文件和
   loopback Provider，不读写用户真实 `~/.ez-assistant` 数据。
9. 所有 schema 迁移测试只针对隔离副本。开发过程中不得启动会迁移用户默认数据库的
   Host；任何默认目录真实验证都必须重新列明数据库和文件范围并取得确认。
10. 默认忽略的真实 LLM smoke 只能脱敏只读用户模型配置；Runtime 数据、Workspace、
    权限和工具输出仍必须位于临时目录。
11. 实际源码与技术方案假设不符时停止扩大改动，先修订方案并重新确认，不在实现中
    静默改变权限优先级、Plan Shell、Global 手工维护或重启不续批语义。
12. 每个里程碑同步记录实际产出、验证结果、偏差和遗留到 `docs/开发进度.md`；
    不主动执行 Git 暂存、提交或推送。

## 四、里程碑台账

### M0：Agent 变体、持久注入与模式数据兼容

- 前置：功能设计、技术方案和本开发计划均已确认。
- 目标：先让 Plan/Build 和 Ask/Auto 在 Session、Input、Run、Conversation 与协议中拥有
  唯一且可恢复的历史语义，不改变正式工具权限行为。
- 交付范围：
  - `AgentVariant`、`ApprovalMode` 公共枚举及序列化契约；
  - Session 当前 variant/approval mode、Input variant、Run approval mode 的 Runtime 状态；
  - Session 模式切换命令、快照与事实事件；
  - SubmitInput/Reenter 必填 variant，Retry 继承 Input variant 并捕获当前 approval mode；
  - Text、FileReferences、Injected 的确定顺序，以及 Plan/Build V1 注入模板；
  - 幂等命中不更新 Session variant，活动 Run 不受后续切换影响；
  - SQLite 四个增量列、v0.11 数据 Build + Ask 默认、required projections 与幂等迁移；
  - Volatile Store、Host Store、恢复和序列化测试同步更新。
- 验证入口：

  ```bash
  cargo test -p agent-types -p agent-provider-openai-compatible -p assistant-protocol -p assistant-runtime -p assistant-runtime-host --all-features
  cargo clippy -p agent-types -p agent-provider-openai-compatible -p assistant-protocol -p assistant-runtime -p assistant-runtime-host --all-targets --all-features -- -D warnings
  cargo fmt --all --check
  ```

- 完成判定：模式切换不产生 Message/Input/Run；每次提交按请求 variant 持久化 Injected；
  重启后 Session、Input 和 Run 投影一致；旧数据不改写 Conversation 且按 Build + Ask 恢复；
  历史 Run 不从 Session 当前选择反推。
- Review 重点：状态是否放在正确实体；Submit 幂等和事务成功点；注入是否持久化而非重建；
  旧数据库迁移是否只在临时数据上验证且允许回退旧 Host。
- 技术依据：技术方案第四、第五、11.1、12.1、13.1–13.3 和 17.1 节。

### M1：JSON 权限文件、CAS 存储与显式重载

- 前置：M0 已确认。
- 目标：建立三层权限唯一规则源及其可靠加载、结构化修改和显式 reload，不接入真实
  Tool Call 决策。
- 交付范围：
  - Global、Workspace、Session `permissions.json` 的领域类型和严格 Serde schema；
  - allow/deny/ask、variant 集合与 general/file/shell tagged matcher 校验；
  - exact/recursive path、exact/prefix command 与 process mode 匹配基础；
  - `PermissionFileStore` 业务端口和 Host scope 到固定目录的解析；
  - 普通文件/symlink 校验、缺失文件、原始字节 revision、CAS 原子替换与目录同步；
  - `PermissionRegistry` 的不可变作用域快照和 invalid/empty/ready 状态；
  - 启动加载、按 Session cohort 显式 reload、失败保留完整旧快照；
  - ReloadPermissions 命令、结果、诊断和事件；
  - 结构化 rules 数组追加、精确规则去重和稳定格式化 JSON。
- 验证入口：

  ```bash
  cargo test -p assistant-runtime -p assistant-runtime-host -p assistant-protocol --all-features
  cargo clippy -p assistant-runtime -p assistant-runtime-host -p assistant-protocol --all-targets --all-features -- -D warnings
  cargo fmt --all --check
  ```

- 完成判定：三层文件均可独立加载；缺失文件形成空规则；任一无效文件不会部分替换
  Registry；Runtime 外部修改只有显式 reload 后生效；revision 冲突不会覆盖用户修改；
  reload 不重建 Session、Prompt 或 Conversation。
- Review 重点：JSON 是否是唯一规则源；Host 是否只处理物理 I/O；CAS 是否真正核对原始
  revision；Global 快照替换是否影响所有 Session 而不产生第二份缓存事实。
- 技术依据：技术方案第七、第八、12.1、12.4、13.4 和 14.1–14.3 节。

### M2：Runtime Authorizer、能力上限与 Guardrail

- 前置：M1 已确认。
- 目标：把 Plan/Build 硬边界、Host 基础设施策略、三级规则和 Ask/Auto fallback 编译成
  单个 Runtime Authorizer，并正式装配现有 Core Guardrail。
- 交付范围：
  - 保持 Factory 只接收 Session 环境，扩展 ToolSet + infrastructure policies bundle；
  - Plan/Build 共享完全相同的工具名称、说明、参数 Schema 和顺序，避免切换变体使模型缓存失效；
  - Plan 对 Agent 私有目录内的 write/edit/delete 按权限决策，对用户 Workspace、附件和其他
    路径硬拒绝；Build 按完整权限决策，二者都保留 Shell；
  - Host 附件静态保护由最终 Authorizer 改为 Continue/Deny infrastructure policy；
  - RuntimeToolAuthorizer 的 hard policy、Deny、Ask、Allow、scope 和 fallback 顺序；
  - General/File/Shell typed facts 与 JSON matcher 的确定性匹配；
  - 每个 Tool Call 读取最新 Permission Registry，Run 只冻结 variant/approval mode/scope；
  - Auto 不能越过 Plan 非私有路径 mutation、附件 mutation、Deny、Ask 或未知 facts；
  - Agent 全局 Guardrail 配置、默认阈值、off/observe/enforce 编译与事件投影；
  - scripted approval seam 与单元测试；正式 Host 默认装配切换延后到 M3。
- 验证入口：

  ```bash
  cargo test -p agent-core -p agent-tools -p assistant-runtime -p assistant-runtime-host --all-features
  cargo clippy -p agent-core -p agent-tools -p assistant-runtime -p assistant-runtime-host --all-targets --all-features -- -D warnings
  cargo fmt --all --check
  ```

- 完成判定：Plan/Build Tool Definition 完全一致；Plan 私有目录 mutation 能按权限执行，
  用户 Workspace、附件和其他路径 mutation 会在执行前被拒绝并产生稳定 Tool Result；
  三级规则、变体和 Ask/Auto 的组合全部有确定结果；活动 Run 的后续调用能读取 reload 后完整
  快照；Guardrail 使用 Runtime 配置而非 Core 隐藏默认。
- Review 重点：Runtime 是否是权限业务所有者；Host policy 是否不再隐式 Allow；变体切换是否
  没有改变 Tool Definition；Run 冻结工具但不冻结规则的边界；Plan Shell 是否未被误写为
  只读沙箱。
- 技术依据：技术方案第六、7.2、8.2、10.3、13.3 和 14.3 节。

### M3：审批状态机、持久授权与正式本地工具启用

- 前置：M2 已确认。
- 目标：完成 Ask 的 Runtime 内存挂起、用户决策、Session/Workspace 规则持久化和取消恢复，
  再用它替换 v0.11 危险验证模式。
- 交付范围：
  - ApprovalId、ToolApprovalSubject、pending snapshot、available decisions 和 rule preview；
  - Runtime Approval Registry、oneshot 等待、原子状态转换和 Run cancellation race；
  - ListPendingApprovals、DecideApproval 及 requested/resolved/cancelled 事件；
  - AllowOnce、AllowSession、AllowWorkspace、Deny，未绑定 Workspace 的服务端拒绝；
  - Session/Workspace exact Allow 先 CAS 写 JSON、更新 Registry、再返回 Core Allow；
  - decision 前规则二次校验，新的 hard Deny/explicit Deny 不能被旧 approval 覆盖；
  - 断线查询重建、Run 取消清理、Runtime shutdown 清理和重启不恢复 pending；
  - 正式 Host 默认装配文件/Shell + Runtime Authorizer；
  - 删除 `--unsafe-unrestricted-local-tools` 及无审批 Authorizer，不保留双轨产品路径。
- 验证入口：

  ```bash
  cargo test -p assistant-protocol -p assistant-runtime -p assistant-runtime-host --all-features
  cargo clippy -p assistant-protocol -p assistant-runtime -p assistant-runtime-host --all-targets --all-features -- -D warnings
  cargo fmt --all --check
  cargo run -p assistant-runtime-host -- --help
  ```

- 完成判定：Ask 可以可靠挂起和恢复客户端投影；四种决定按作用域生效；文件写入失败或
  revision 冲突不会执行工具；取消和重启不会遗留可操作 approval；正式 Host 不再需要危险
  开关即可在权限体系下使用真实工具。
- Review 重点：审批等待是否不持有 Session mutation lock；持久 Allow 的写入顺序；过期决定
  是否能触发副作用；Global 是否完全没有交互写入口；危险验证模式是否彻底退场。
- 技术依据：技术方案 7.3、8.3、第九节、12.2–12.4、13.4 和 14.1 节。

### M4：工具开始可靠点与异常恢复

- 前置：M3 已确认。
- 目标：在不建立永久工具审计的前提下，让 pending tool exchange 可恢复地区分
  “工具未开始”与“工具已开始但结果未知”。
- 交付范围：
  - `pending_tool_starts` 表、外键级联和 v0.11 schema 增量兼容；
  - `ExecutionRecorder::mark_tool_execution_started` 及 Core 副作用前可靠调用；
  - complete_tool_exchange 结算 Conversation Tool Results 后清理 pending start；
  - begun 未开始、begun 已开始、ready 有结果的启动恢复；
  - 移除 Tool audit Runtime DTO、Store 业务方法、协议查询和永久投影；
  - Recorder、Core、Volatile Store、Host Store 与异常注入测试。
- 验证入口：

  ```bash
  cargo test -p agent-core -p agent-testkit -p assistant-runtime -p assistant-runtime-host -p assistant-protocol --all-features
  cargo clippy -p agent-core -p agent-testkit -p assistant-runtime -p assistant-runtime-host -p assistant-protocol --all-targets --all-features -- -D warnings
  cargo fmt --all --check
  ```

- 完成判定：started 写入失败不会执行工具；正式 Tool Result 提交后不留临时
  started 记录；崩溃恢复不把未知副作用伪装成成功或普通失败，也不重新执行工具。
- Review 重点：Core 新 Recorder 方法是否仍实现无关；pending start 是否只在 exchange
  生命周期内存在；跨 JSONL/SQLite 的结算顺序；恢复对未开始和结果未知的区分。
- 技术依据：技术方案第十、11.2–11.3、12.1、14.1–14.2 和 15.3 节。
