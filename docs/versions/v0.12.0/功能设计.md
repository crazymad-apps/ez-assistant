# v0.12.0 功能设计：Plan/Build、分层权限与正式工具策略

## 一、设计信息

- 版本：`v0.12.0`
- 状态：已确认
- 影响模块：`assistant-runtime`、`assistant-protocol`、`apps/runtime-host`、
  `agent-core`、`agent-tools`、`agent-tools-local`
- 需求来源：Runtime 阶段路线、`v0.4.0` Safety Demo 的权限验证结论、
  `v0.11.0` Workspace 与正式本地工具基线，以及 2026-08-11 关于 Plan/Build、
  分层授权、权限文件和 Runtime Host 模式语义的用户会话结论

本版本涉及应用协议、Session 结构化状态、权限文件、审批挂起、工具中断恢复和跨模块
执行契约，功能设计确认后必须单独形成技术方案。本版本不建设正式桌面端界面，
因此不单独形成界面交互设计指导；必要的可视化操作只放入 Runtime Host Web Demo
作为验收载体，不成为正式产品 UI 契约。

## 二、背景与目标

`v0.11.0` 已建立 Workspace、Session 私有目录、附件、统一 HTTP 通信和按 Run 装配
真实文件/Shell 工具的基线，但正式 Runtime 尚未形成以下产品能力：

- Session 无法稳定表达当前使用 Plan 还是 Build 变体；
- User Message 没有按变体带入持久化的工作流指令；
- 真实工具仍以显式验证配置运行，缺少 Runtime 权威的 Ask/Auto、审批和分层规则；
- 用户的审批选择无法在 Session、Workspace 和 Global 层级形成可检查、可编辑的
  持久策略；
- 工具开始后若 Runtime 意外中断，缺少区分“未开始”和“结果未知”的
  最小恢复事实。

`v0.12.0` 目标是：

1. 将 Plan/Build 收敛为同一 Agent 的两个固定变体，由 Runtime 统一装配、
   持久化和冻结。
2. 通过每条 User Message 的持久化内部注入向模型表达当前工作流，不改写
   用户正文，也不改写 Session 已冻结的 System Prompt。
3. 将 Plan/Build 能力上限与 Ask/Auto 审批方式保持为两个独立维度，并由
   Runtime Authorizer 给每个真实 Tool Call 形成最终决策。
4. 建立 Session、Workspace 和 Global 三级可编辑权限文件，以及“仅本次”的
   临时授权语义。
5. 在审批中只允许产生本次、Session 和 Workspace 授权；Global 规则只允许
   用户手工维护，防止 Agent 执行过程无意扩大全局权限。
6. 在 Tool Result 尚未正式落盘时，可靠记录工具是否已经开始，以便 Runtime
   重启后形成可解释的中断结果，不另建永久工具审计历史。
7. 通过正式 Runtime Host 的 Web Demo 验证模式、真实文件/Shell、审批、
   权限重载、取消和恢复链路。

## 三、非目标

以下内容不进入 `v0.12.0`：

- 可由用户自定义、安装或扩展的 Agent 变体；本版本只提供内置 Plan 和 Build。
- 正式桌面端模式选择器、审批卡或权限管理页；它们在桌面端版本
  单独设计。
- 独立的长期工具审计页、审计查询/导出协议和审计保留策略。
- 把计划作为独立数据库对象、Workspace 文件、Artifact 或带版本的交付物。
- 为 Plan 制造 OS 级只读沙箱，或引入容器、虚拟机、独立用户、权限降级与
  强隔离执行环境。
- 把 Workspace 或 Session 目录描述为强安全边界；Shell 仍然以当前操作系统
  用户权限运行。
- 在交互审批中创建 Global 授权、自动更改 Global 权限文件或提供一键全局
  放行。
- 自动监视权限文件变化；手工修改通过显式重新加载生效。
- 权限规则的云端同步、跨 Runtime 共享、多用户身份和远程管理。
- Workspace Instructions 自动发现与注入、文件列表注入、记忆召回或其他新的
  System Context 来源。
- 子 Agent、并行任务委派、计划任务调度和新的长期后台 Job 生命周期；子 Agent
  进入 `v0.13.0`，自动化与后台任务在后续版本单独设计。
- 将工具输出登记为 Artifact、产物快照、发布或下载对象；工具生成的文件
  继续是所在目录中的普通文件。
- 在功能设计中冻结数据库表、字段、权限文件格式、HTTP 路径、Rust 类型或模块树。

## 四、功能范围与使用路径

### 4.1 固定 Agent 变体

Plan 和 Build 是同一个 Agent 的两个内置变体，共享模型、Conversation、Workspace、
工具基础设施和 Session 生命周期，但使用不同的工作流指令和能力上限。

- **Plan**：先理解任务、检查上下文、消除会影响方案的歧义，最终以 Assistant
  Message 形成可执行的计划，不自动进入实施。
- **Build**：在用户实际提交 Build 输入后执行实施、修改、验证和结果交付。

计划不形成独立的“待审批 Plan”业务状态。用户希望开始实施时，以 Build
变体提交一条普通 User Message；继续调整计划时，以 Plan 变体提交普通
User Message。正式 Runtime 不为此定义专用计划按钮、快捷语句或特殊决策接口；
Web Demo 可使用快捷输入验证这条路径。

### 4.2 Session 当前变体与 Run 冻结

Runtime 在 Session 结构化数据中持久保存当前变体，用于客户端或 Demo 重建
当前选择。该状态与每次提交实际使用的变体是两个相关但不同的事实：

1. 只切换变体、不提交消息时，Runtime Host 只更新 Session 的当前变体；不创建
   Message、Run 或模式注入，也不改变活动 Run。
2. 每次提交 User Message 都必须明确携带本次使用的变体，不依赖数据库中
   原有状态隐式推断。
3. 提交请求携带的变体是本次输入的权威值；若它与 Session 当前状态不一致，
   以实际提交为准。
4. Runtime 接受输入后同步更新 Session 当前变体，按该变体持久化 User Message
   注入，并为对应 Run 冻结变体。
5. Run 创建后的变体切换只影响 Session 当前状态和之后的提交，不改写活动或
   历史 Run。
6. 已经被 Runtime 接受的提交即使后续模型或工具执行失败，Session 当前变体
   仍保持为该次提交值。

Session 当前变体是重建和下一次输入的默认状态，不是已经创建的 Message 或 Run
的历史依据。Session 归档和恢复保留该状态。

### 4.3 每条 User Message 的变体注入

Plan 和 Build 对每条新 User Message 使用不同的内部注入文本。注入项具有以下语义：

- 注入项属于 User Message 的持久化 Part，不在每次恢复会话时动态重建；
- 注入项不属于用户自然语言正文，正式客户端不应将它渲染为用户输入；
- Runtime 构造模型输入时，确定性地将它与用户正文组合；
- 注入项记录提交当时的变体语义，后续修改内置注入模板不回写历史 Message；
- Conversation 恢复、历史重新输入、上下文压缩和归档恢复都必须保留已持久化
  的注入内容和顺序。

Plan 注入引导 Agent 先调查和形成计划，允许在 Agent 私有空间编写分析脚本和中间文件，
但不得修改用户 Workspace 或附件并开始实施；
Build 注入引导 Agent 根据用户当前输入和历史上下文实施并验证。注入文本的具体内容、
版本化方式和 Provider 编码进入技术方案。

### 4.4 Plan/Build 能力边界

Plan/Build 决定能力上限，Ask/Auto 只在该上限之内决定未命中动作如何获得
最终授权。

Plan 与 Build 向模型提供完全相同的工具名称、说明和参数定义。切换变体不得增删或改写
Tool Definition，避免模型侧 Prompt Cache 因工具定义变化而失效。二者的差异只体现在持久化
注入指令和工具执行前的 Runtime 授权结果；模型在 Plan 中提出结构化写入调用时，Runtime
根据目标路径判断是否位于 Agent 私有空间，超出允许范围时拒绝并形成普通错误 Tool Result。

Plan 的正式能力语义为：

- 允许使用文件读取、列目录和搜索等结构化只读能力；
- 允许在 Session 私有目录和已绑定 Workspace 的 Agent 私有目录中写入、编辑、删除和移动，
  用于分析脚本、缓存和中间产物；这些操作仍遵守普通权限规则；
- 拒绝对用户 Workspace 和其他非 Agent 私有路径执行结构化写入、编辑、删除和移动，且
  Ask/Auto 与历史授权都不能把这些路径放开；
- Session 附件目录在所有变体下继续保持不可修改；
- 允许使用 Shell 以支持代码查询、构建信息检查、测试探测和必要分析；
- Shell 继续走完整权限规则与审批，不因 Plan 变体获得隐式放行；
- Plan 注入要求 Agent 仅在 Agent 私有空间写入分析产物，不使用 Shell 修改用户 Workspace
  或开始实施；但 Shell 以当前用户权限运行并可以绕过结构化文件策略，因此 Plan 不是 OS
  强只读边界。

Build 允许在权限和 Guardrail 边界内使用完整的结构化文件与 Shell 能力，包括
读取、写入、编辑、删除、移动和执行命令。

未知工具、无效输入和无法形成稳定授权事实的调用不进入审批，并继续按
现有 fail-closed 契约形成错误 Tool Result。

### 4.5 Ask/Auto 审批方式

Ask/Auto 不修改 Agent 变体，只决定能力上限内的未匹配工具调用如何结算：

| 方式 | 未命中的普通调用 | 明确拒绝 | 明确必须询问 |
| --- | --- | --- | --- |
| Ask | 挂起当前调用并请求用户决策 | 仍拒绝 | 仍询问 |
| Auto | 在变体能力上限内自动允许 | 仍拒绝 | 仍询问 |

Ask 是新 Session 的默认审批方式。Auto 不等于跳过 Authorizer，也不能越过 Plan
非 Agent 私有路径的结构化写入限制、明确 Deny、强制询问规则或 Guardrail 终止。Run 开始时冻结
当时的变体和审批方式，活动 Run 期间的后续修改只影响之后的 Run。

### 4.6 分层权限与授权选项

权限规则有三个持久层级和一个临时决策：

| 范围 | 权威存储 | 产生方式 | 生命周期 |
| --- | --- | --- | --- |
| 仅本次 | 不持久化权限规则 | 交互审批 | 只解除当前 Tool Call |
| Session | Session 私有权限文件 | 交互审批或手工编辑 | 跟随 Session，包括归档恢复 |
| Workspace | Workspace 级 Agent 私有权限文件 | 交互审批或手工编辑 | 跟随 Workspace，包括假删恢复 |
| Global | Runtime Home 中的全局权限文件 | 只允许用户手工编辑 | 对当前 Runtime Home 内的 Session 生效 |

工具调用需要用户决策时，审批能力只提供：

- 仅本次允许；
- 当前 Session 允许；
- 当前 Workspace 允许；
- 拒绝当前调用。

未绑定 Workspace 的 Session 不提供 Workspace 授权。任何交互审批都不提供 Global
允许或持久 Global Deny；Global 权限只能通过文件手工管理。拒绝当前调用不自动
生成持久 Deny 规则。

模型一轮产生多个 Tool Call 时，每个调用仍拥有独立最终决策和 Tool Result；
Runtime 不提供一次不可见的全局放行。审批请求是否以单个或组合形式向
验证 Demo 投影，由技术方案确定，但不得改变逐 Tool Call 权威决策。

### 4.7 授权规则的变体维度

通过审批产生的 Session 和 Workspace 规则只在当前 Agent 变体中生效：

- Plan 中保存的授权不自动放行 Build 中的同类调用；
- Build 中保存的授权不自动放行 Plan 中的同类调用；
- Global 规则由用户手工明确它适用 Plan、Build 或两者；
- 仅本次授权天然绑定当前 Tool Call 及其冻结变体，不需要形成后续规则。

变体维度用于防止“规划时允许”无意扩大为“实施时允许”，不改变 Plan/Build
能力上限必须先于普通规则评估的约束。

### 4.8 规则匹配与用户可见语义

权限范围和规则匹配对象是两个不同概念：Session/Workspace 说明规则保存在哪里、
持续多久，匹配对象说明之后哪些调用可以复用该授权。

交互审批默认保存一个保守、稳定且可向用户说明的匹配范围：

- 文件能力至少区分操作类型与已解析的稳定逻辑路径；
- Shell 默认绑定完整命令和有效工作目录；
- 其他工具使用工具身份和可稳定识别的操作对象；
- 审批产生的规则不自动扩大为未向用户展示的通配符、命令前缀或整类工具放行。

用户需要更宽的规则时，通过手工编辑相应权限文件完成。任何审批请求都必须
向客户端提供完整操作事实和将被保存的匹配范围，不允许客户端自行重新解析
模型原始参数。

### 4.9 权限加载与冲突语义

Runtime 根据当前 Session、已绑定 Workspace 和当前变体组合有效权限。权限决策
必须满足：

1. Plan/Build 能力上限先于普通规则与 Ask/Auto 评估；
2. 明确 Deny 不能被 Session、Workspace、Global、仅本次或 Auto 允许覆盖；
3. 明确必须询问的规则不能由历史 Allow 或 Auto 静默放行；
4. 除上述强制规则外，越具体的作用域优先：Session 优先于 Workspace，Workspace 优先于
   Global；
5. 所有规则都必须在当前变体内匹配，没有匹配时才进入 Ask/Auto fallback。

精确规则语法、匹配算法、同层多条规则的顺序和诊断形式由技术方案确定，
但不得改变上述功能语义。

### 4.10 权限文件与显式重新加载

三级权限都使用专用权限文件作为规则的唯一权威数据源，不在 SQLite 中复制
一份可执行规则：

- Session 文件位于 Session 私有空间；
- Workspace 文件位于 Workspace 级 Agent 私有空间，不污染用户工作目录；
- Global 文件位于 `~/.ez-assistant` Runtime Home。

Runtime 自己处理 Session 或 Workspace 审批时，只有在权限文件写入成功后才能对当前
调用返回已授权，并立即更新 Runtime 中的有效规则，不要求用户再次重载。

用户在 Runtime 外部手工编辑任一权限文件后，通过显式“重新加载权限”能力请求
Runtime 重新读取规则，不要求重启 Runtime，也不重建 Session、System Prompt、
Conversation 或模型配置。

重新加载成功后，新规则影响后续 Tool Call；已在执行的工具不中断。已经等待
审批但尚未执行的调用，真正执行前必须根据最新规则再次校验。任一相关文件
加载失败时，Runtime 保留上一份完整有效规则并返回可定位的诊断，不能部分应用、
默认全放开或默认全拒绝。

### 4.11 审批生命周期

审批是 Runtime Authorizer 在一个活动 Run 内的挂起状态，不进入 Agent Core 公开词汇：

- Runtime 持有 pending approval 的权威状态，客户端只提交决策意图和展示投影；
- 审批决策必须定位到仍然存在的 pending approval，过期、已取消或已结算请求
  不能再触发工具副作用；
- Run 取消必须同时取消审批等待，不留下可继续操作的孤立请求；
- Runtime 重启后不恢复 pending approval；按既有规则将未完成 Run 结算为 interrupted，
  不自动续跑或代替用户补决策。
- 客户端断线不自动批准或拒绝；Runtime 继续持有活动请求，重连客户端可恢复
  当前投影。
- Session 归档必须继续遵守既有“无活动 Run”前置，不在 pending approval 期间归档。

### 4.12 工具中断恢复与 Guardrail

Runtime 不为每个权限判断建立独立的永久审计记录。持久权限由三级 JSON 规则表达，
正式工具调用和结果由 Conversation 中成对的 Tool Call/Tool Result 表达，pending
approval 只是活动 Run 内的内存状态。

为处理进程在工具副作用期间中断的情况，Runtime 只在 pending tool exchange 生命周期内
保留“该 Tool Call 已开始”的临时事实。完整 Tool Result 正式落盘后清除该事实；
重启恢复时，没有开始事实的调用可标记为未执行，已开始但没有稳定结果的调用必须
标记为结果未知，两者都不自动重新执行。

本版本将已在 Core/Safety Demo 验证的 Guardrail 接入正式 Runtime，至少覆盖完全相同
调用的重复检测和连续失败检测。Guardrail 可产生诊断或在完整 Tool Call/Result
结算后终止当前执行，但不自动产生持久权限规则，也不替代用户审批。
阈值、运行策略和诊断投影由技术方案确定。

### 4.13 Runtime Host Web Demo 验证

本版本扩展正式 Runtime Host 已有 Web Demo，使开发者可以：

- 为 Session 切换 Plan/Build 并验证未提交时只更新 Session 状态；
- 提交时明确携带变体，恢复页面后看到 Runtime 保存的当前变体；
- 查看 Plan/Build 注入带来的模型行为差异，但不把内部注入伪装成用户正文；
- 切换 Ask/Auto，查看 pending approval，并选择仅本次、Session、Workspace 或拒绝；
- 查看审批将保存的规则范围、命中层级和工具执行结果；
- 显式重新加载权限并查看诊断；
- 恢复 Conversation、取消活动 Run，并核对审批、中断 Tool Result 和消息投影。

Demo 的控件、快捷输入、卡片、排版和文案是私有验收实现，不写入正式协议或
未来桌面交互契约。

## 五、模块边界与契约影响

- `assistant-runtime`：持有 Session 当前变体、Run 冻结变体、模式注入、权限规则
  编译结果、pending approval、Guardrail 和取消的业务权威。
- `apps/runtime-host`：提供结构化状态、pending tool start 的本地存储、三层权限文件与真实
  文件系统基础设施，并通过 HTTP/SSE 转发意图和事件；不持有第二份 Session、
  Run 或审批权威状态。
- `assistant-protocol`：承载变体选择、带变体的消息提交、审批请求与决策意图、
  权限重载和客户端所需投影；不暴露权限文件物理布局或存储表。
- `agent-core`：继续只消费冻结 ExecutionSpec 和最终 Allow/Deny Authorizer，不持有
  Plan/Build、Ask/Auto、权限文件或 pending approval；只在工具副作用前调用实现无关的 Recorder 接缝。
- `agent-tools`：继续提供工具 SPI、resolved invocation 和类型化授权事实，不引入
  Session、Workspace 或规则持久化。
- `agent-tools-local`：继续执行真实文件和 Shell 能力，遵守上层最终决策；不自行
  弹出审批、写权限文件或定义业务作用域。
- Runtime Host Web Demo：只展示 Runtime 投影并提交用户意图，不复制权限计算或
  审批状态机。
- 正式桌面端：本版本不修改其产品交互；未来通过同一正式协议使用 Runtime
  能力，不重新实现权限规则。

具体 DTO、表结构、文件布局、规则类型、并发控制、HTTP 路由和 Rust 模块划分全部
进入技术方案。

## 六、关键取舍

### 6.1 变体固定，内部装配

Plan/Build 是产品级工作流语义，不开放为用户可定义的任意 Agent Profile。这使
Runtime 可以稳定解释能力上限、注入和历史 Run。

### 6.2 实际提交的变体永远优先

Session 当前变体用于恢复客户端状态，不是提交时的隐式参数。每次提交明确
携带变体，可以避免多客户端或重连后的旧状态让 Runtime 在错误模式下执行。

### 6.3 注入项持久化，不动态重算

工作流指令是模型当时真实看到的输入。将它作为 Message Part 持久化，能保证
恢复、压缩和历史重建不会因新版模板而改写旧对话。

### 6.4 Plan 允许 Shell，但不伪称强只读

有效规划需要构建、测试、仓库状态和专用命令的查询能力，因此正式 Plan 不像
`v0.4.0` Safety Demo 那样全面禁止 Shell。但 Shell 可绕过结构化文件规则，所以
必须持续展示当前用户权限边界，不将 Plan 描述为 OS 沙箱。

### 6.5 权限规则使用文件而不是数据库副本

权限需要可检查、可手工编辑，并且按 Session、Workspace 和 Global 拥有清晰归属。
专用文件作为唯一规则源，避免文件与 SQLite 两份规则发生分歧。SQLite 仍然保存
Session 当前变体、pending tool start 和其他结构化关系。

### 6.6 Global 权限不从审批产生

Global 规则影响所有 Workspace 与 Session，不应从 Agent 执行期间的一次快捷操作产生。
本版本只允许用户直接编辑 Global 权限文件，并显式重新加载。

### 6.7 授权规则区分 Plan/Build

Plan 与 Build 对同一 Shell 或工具的用途和风险不同。为当前变体保存授权会增加
少量重复审批，但可以避免规划阶段的信任静默扩大到实施阶段。Global 手工规则仍然
可以明确同时适用两个变体。

### 6.8 计划转实施使用普通输入

计划是 Assistant 对用户任务的回答，不是独立业务对象。用户以 Build 变体提交下一条
普通消息即可进入实施；Demo 可提供快捷输入，但 Runtime 不因一种当前界面形态
增加专用状态机。

## 七、验收标准

1. 新 Session 具有可恢复的当前变体；只切换变体不产生 Message、Run 或模式
   注入，Runtime 重启或 Session 归档恢复后仍能返回该状态。
2. 每次 User Message 提交都明确携带 Plan 或 Build；它与 Session 旧状态不同时仍以
   提交值创建消息和 Run，并更新 Session 当前变体。
3. 每个 Run 冻结自己的变体；Run 开始后切换 Session 变体不改变其工具能力、
   注入或历史记录。
4. Plan 和 Build User Message 分别持久化对应内部注入 Part；Conversation 恢复、
   压缩和历史重新输入不动态重算或改写旧注入，用户正文保持原样。
5. Plan 以 Assistant Message 输出计划后停止，不自动创建 Build Run；只有用户以 Build
   提交普通 User Message 后才进入实施。
6. Plan 可使用结构化文件工具和受权限控制的 Shell；结构化修改仅允许落在 Agent 私有空间，
   用户 Workspace、附件和其他路径的修改被能力上限拒绝，Ask、Auto 和历史授权都无法放开。
7. Build 在权限与 Guardrail 边界内可使用完整文件与 Shell 能力；未知工具或无效
   授权事实不进入审批且 fail-closed。
8. Ask 中未命中普通调用可挂起并等待决策；Auto 可自动允许能力上限内的普通
   未命中调用，但不能越过明确 Deny、必须询问规则、Plan 能力上限或 Guardrail。
9. 审批只提供仅本次、Session、Workspace 和拒绝；未绑定 Workspace 时不提供
   Workspace 选项，任何审批都不能产生 Global 规则。
10. Session 和 Workspace 审批在权限文件写入成功后立即生效；写入失败不返回已持久
    授权，也不执行该调用。
11. Session、Workspace 和 Global 三级权限文件是唯一规则源，SQLite 中没有另一份
    可执行权限规则；Session 归档恢复和 Workspace 假删恢复保留对应文件。
12. 审批生成的 Session/Workspace 规则只对保存时的 Plan 或 Build 变体生效；
    Global 手工规则可明确适用单一变体或两者。
13. 审批默认保存对用户可见的保守匹配范围；它不静默扩展为通配符、命令前缀
    或整类工具授权，更宽规则只能通过手工编辑权限文件形成。
14. 手工修改权限文件后，显式重新加载可在不重启 Runtime、不重建 Session 或
    System Prompt 的情况下更新后续调用；任一文件无效时保留上一份完整有效规则并
    返回定位诊断。
15. Run 取消会取消 pending approval，过期决策不能触发工具；Runtime 重启后不恢复
    pending approval 或自动续跑中断 Run。
16. pending tool exchange 内每个 Tool Call 在副作用前可靠记录开始状态；完整
    Tool Result 落盘后该临时状态被清除。重启恢复能区分未开始与结果未知，
    且不自动重新执行。
17. 完全相同调用和连续失败 Guardrail 在正式 Runtime 生效，终止时仍保持 Tool Call/
    Result 成对和 Run 可解释终态。
18. Runtime Host Web Demo 能使用真实 LLM 完成 Plan 调查、普通输入转 Build、Ask/Auto、
    真实文件/Shell、三种允许范围、拒绝、权限重载、取消和历史恢复的端到端验证；
    Demo 交互不进入正式 UI 契约。

## 八、风险、兼容性与技术交接

### 8.1 风险与缓解方向

- **Plan Shell 不是只读边界**：Shell 可修改文件、访问网络并启动进程。必须依靠明确
  注入、权限规则、审批和持续风险提示，不得向用户声称 Plan 可以防止
  任意本地副作用。
- **持久授权范围过宽**：Session 可长期保留，Workspace 会被多个 Session 复用。
  审批默认使用精确稳定范围并展示实际规则，更宽范围只由用户手工编辑。
- **Global 手工误配**：Global 规则可同时影响多个 Workspace。重新加载必须先完整校验
  再替换旧快照，并返回文件级诊断。
- **文件与数据库跨介质一致性**：Session 变体、pending tool start、Conversation 和权限文件使用
  不同存储介质。技术方案必须定义可识别的成功点和失败恢复，不能向客户端
  报告尚未成为事实的持久授权。
- **重新加载与活动调用竞态**：已执行工具不能回滚，pending approval 也不能依赖
  旧规则绕过新 Deny。执行前的二次校验与快照替换边界进入技术方案。
- **审批无人处理**：无客户端在线的 Ask Run 可以长时间挂起。本版本不以超时隐式批准；
  超时、无人值守策略和结构化终态由技术方案依据 fail-closed 原则确定。

### 8.2 兼容性

- `v0.11.0` 旧 Session 没有当前变体，升级后按 Build 处理，保持之前可使用完整工具的
  工作流语义；不为历史 User Message 伪造 Plan/Build 注入。
- 旧 Session 的新提交同样必须显式携带变体，客户端可使用 Runtime 返回的 Build 默认
  状态。
- 旧 Conversation 不含内部变体注入 Part，仍按原样恢复和传入模型；只有新提交
  产生新 Part。
- 权限文件缺失表示该层无显式规则，不是错误。新 Session 默认 Ask；结构化只读
  能力按默认策略可使用，需要副作的未匹配能力进入审批。
- Session 和 Workspace 现有归档、假删、历史重新输入和模型切换语义保持不变；
  这些操作不隐式清理或放大持久权限。
- Runtime、Host 和 Demo 使用同一正式协议同步演进，不为新变体或审批建立并行的
  历史协议代际。

### 8.3 功能确认结论

本功能设计已确认当前版本功能边界，没有未决的产品功能问题。实现细节由技术方案承接。

### 8.4 由技术方案承接的事项

- Session 当前变体、Run 冻结变体、pending tool start 和审批相关的数据库表、
  字段、索引与迁移；
- 消息提交、变体切换、审批决策和权限重载的 HTTP DTO、路由和错误；
- 变体注入 Part 的类型、持久化编码、模板内容、版本化与 Provider 渲染；
- 三级权限文件的确切路径、JSON schema、规则语法、变体表达、迁移和手工编辑诊断；
- 规则合并、逻辑路径与 Shell 命令规范化、匹配和执行前二次校验；
- 权限文件的锁、原子替换、写后验证、旧快照保留和 Runtime 内编译结果替换；
- pending approval 的排队、同批 Tool Call 组织、取消竞态、断线重连、无人值守和重启清理；
- pending tool start 的可靠写入、清理、重启恢复和与 Tool Result 的关联；
- Guardrail 阈值、Observe/Enforce 配置、终止结算和诊断事件；
- Runtime、Host、Protocol、Store、Authorizer 与 Web Demo 的具体模块边界和端到端验证方案。
