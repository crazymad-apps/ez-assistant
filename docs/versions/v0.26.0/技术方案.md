## 二、源码与依赖核查结论

本轮只读检查了当前 `v0.25.3` 源码、SQLite schema、协议导出、Desktop Store 和离线
Cargo 依赖树，未打开用户 Runtime Home、未访问 Provider、未修改数据库。

| 主题 | 已核实事实 | 本版技术结论 |
| --- | --- | --- |
| 模型目录 | `list_provider_models`、无固定配置的 `prepare_model`、模型详情和首次固定均可调用 `ModelServiceFactory::discover_models`；发现沿用推理 transport 超时 | 新增唯一显式刷新命令；原列表、详情、选择和执行全部改读 Provider 内的持久快照 |
| Provider 存储 | `providers` 只有连接与凭据列；`StoredProvider` 已由 Runtime 配置 Registry 以 `Arc` 持有 | 快照跟随 `StoredProvider`，在 `providers` 增加可空列，不新增表或独立快照实体 |
| Run/Input | `commit_user_message` 才把 Input 从 `queued` 改为 `committed`；`fail_before_start` 直接 `settle_run`，而 settlement 不收敛仍为 `queued` 的来源 Input | 扩展原子结算，使启动前失败同时提交原 UserMessage、终结 Run 并收敛 Input |
| 中断恢复 | `SessionLoader::prepare` 已有单 Session 门禁和中断 Run 恢复；普通 `load` 不恢复，部分空闲敏感命令先 `session()` 再拒绝 | 保留读写分离，但会话组合视图和空闲敏感 mutation 统一先走 `prepare` |
| Live step | Runtime 已在规范消息提交后、`RunFinished` 或下一 step 前发布 `StepCommitted { owner, step, generation }`；Desktop 未把它交给 live store，且从最新 30 条会话页反推提交 step | 复用现有事件，不增加 `run_id` 或序号；按有序事件、当前非终态 Run 和 generation 封口 |
| 工具参数 | 历史 `ToolInputSnapshot` 已存在；`ToolActivitySnapshot`、父/子 `ToolProposed` 和 General 审批缺输入；历史投影函数位于 `runtime/product.rs` | 抽出 Runtime 唯一投影器，协议统一携带有完整性标志的输入投影 |
| 审批模式 | Run 创建时把 `approval_mode` 复制到父/子 `RuntimeToolAuthorizer` 和 `RuntimeApprovalResolver` | Run 字段只保留接纳时审计；每次工具授权从 `SessionController` 读取实时模式 |
| Desktop 默认 | `desktop-preferences.json` 已按本机顶层与远端规范化 origin namespace 原子保存；新草稿硬编码 Ask，显式模型为空并跟随 Runtime 默认 | 在同一偏好对象增加审批默认值和最近具体模型；只改变新草稿初值，不新增 Runtime 配置或设置页 |
| Shell | `detached` 只有主 Shell 正常退出且 stdout/stderr EOF 才交接；结算超时或取消仍清理进程组 | 不改执行代码，只修订 Tool Schema 说明、用户文案、模块文档和测试命名 |
| Windows 还原图标 | `DesktopWindowControls` 用一个完整边框元素叠加另一个完整边框伪元素；两者内部透明，后层边线会透过前层 | 改为组件内专用 SVG：完整绘制前窗，只绘制后窗暴露边缘，不改窗口状态和命令链路 |
| Desktop 滚动回弹 | macOS 已按平台关闭 overscroll，但 Windows WebView2 仍匹配不到该规则 | 对 macOS/Windows 原生平台的根、body 与后代设置 `overscroll-behavior: none`，普通 Web/Linux 不变 |
| 默认 Agent Shell | `AgentShellSetting` 用三行 grid 呈现标题、全宽选择器和副标题 | 改为 `max-content + minmax(0, 1fr)` 单行 grid，删除副标题，不改设置状态和命令 |

离线 `cargo metadata` 与 `cargo tree` 证明依赖方向已经满足本方案：`assistant-runtime` 不依赖
SQLite 或 HTTP Client，在线发现继续通过 `ModelServiceFactory` 注入；SQLite 只由 Host worker
所有；Desktop 只消费应用协议。当前 workspace、Host、Desktop 和协议版本均为 `0.25.3`。

## 三、目标架构与新增边界

```text
设置页“刷新在线模型”
        │ 唯一目录联网入口（5s connect / 20s 整次发现）
        ▼
assistant-runtime ── ModelServiceFactory ──► Provider /models
        │ 成功才原子替换
        ▼
RuntimeStore ──► Host SQLite providers.catalog_* 列
        ▲
        │ 所有选择、详情、Run、标题、压缩和 child 只读本地事实
Desktop / Web ◄── HTTP Command / Snapshot / SSE
```

本版最小新增如下：

1. Provider 内嵌一份最后成功模型目录及状态；只有显式 refresh 会修改。
2. Store 新增一个目录原子替换操作和一个“终态 Run + queued Input”定向修复操作。
3. 协议增加目录快照 DTO、显式刷新命令和工具输入投影；不增加 live 日志或第二套事件流。
4. Authorizer 持有 Session 状态读取能力，不再持有审批模式副本。
5. Desktop 偏好对象增加每连接目标的审批默认值和最近具体模型，新草稿创建时复制两项基线。
6. Windows/Linux 共用的自定义窗口控件以确定矢量路径修复还原图形，不增加资源文件或协议状态。

## 四、模型目录快照与关键路径断网

### 4.1 领域与持久化形状

`assistant-runtime` 在 `StoredProvider` 中增加私有值对象：

```text
StoredModelCatalog {
  models: Vec<DiscoveredModel>,
  refreshed_at_ms: i64,
  connection_changed: bool,
}
```

它没有 ID、revision 或独立生命周期。公开协议使用：

```text
ProviderModelCatalogSnapshot {
  provider_instance_id,
  models,
  refreshed_at_ms: Option<i64>,
  connection_changed,
  diagnostic: Option<ModelCatalogDiagnosticCode>,
}
```

`diagnostic` 首版只有 `stored_snapshot_invalid`。`refreshed_at_ms = None` 且无诊断表示从未刷新；
损坏快照按空目录加载并返回诊断，不能导致 Provider、Runtime 或 Session 整体加载失败。

`apps/runtime-host` 的 `providers` 表由 `v0.26.0` 增量迁移增加：

```sql
model_catalog_json TEXT NULL,
model_catalog_refreshed_at_ms INTEGER NULL,
model_catalog_connection_changed INTEGER NOT NULL DEFAULT 0
```

约束为：目录 JSON 必须是数组，时间必须为非负整数；正常写入时 JSON 与时间同时为空或同时非空；
无快照时 `connection_changed` 必为 0。发现现有文件发生外部损坏而不能解码时，读取层保留 Provider
连接并返回诊断，不尝试启动时改写或自动联网修复。

目录沿用发现层现有上限：最多 100 页、10,000 个模型、整次响应 8 MiB。落库前再次验证模型 ID、
重复项、标准化元数据和编码后 8 MiB 上限；不保存 Provider 原始响应、响应头或底层错误。

### 4.2 Store 原子操作

`RuntimeStore` 新增业务操作：

- `replace_provider_model_catalog(replacement)`：以 Provider ID 和当前 Provider `Arc` 对应的
  连接事实为前置条件，单事务只替换三列；失败不改变旧值。
- `put_provider` 继续保存连接。创建时目录为空；更新时保留目录，仅当目录发现输入改变才把
  `connection_changed` 置为 true。

目录发现输入包括 `provider_type`、`endpoint`、`models_path`、`discovery_format` 和凭据；显示名称与
推理 `protocol_preference` 不影响目录，因此不置 stale。删除 Provider 仍由现有外键/同行删除一起
移除快照。

显式刷新按以下顺序执行：

1. 在 `model_binding_gate` 下捕获当前 Provider `Arc` 和连接输入，随后释放写门禁。
2. 使用捕获值在门禁外联网，固定 `connect_timeout = 5s`、整次分页
   `request_timeout = 20s`；不自动重试、不重定向到其他主机。
3. 成功解析完整目录后重新取得配置写门禁，检查 Provider 仍是同一 `Arc`。
4. 先提交 Store 原子替换，再更新 Registry 中该 Provider 的不可变 `Arc`，发布 `ConfigChanged`。
5. 任一网络、解析、存储或 currentness 检查失败均保留旧快照；连接已并发变化时返回
   `configuration_conflict`，不把旧连接结果写到新连接。

### 4.3 命令语义与本地装配

- `list_provider_models` 改为只读本地 `ProviderModelCatalogSnapshot`，绝不调用 Factory。
- 新增 `refresh_provider_models`，仅模型管理页和固定配置页的“刷新在线参考”显式调用。
- `get_model_configuration`、`save_model_fixed_config(origin=online)`、`set_default_model`、
  `set_auxiliary_vision_model` 和 `prepare_model` 统一使用本地快照。
- 模型选择器调用 `list_provider_models` 合并目录与固定记录；展开菜单、打开 Session 或加载应用
  均无目录网络。
- 执行参数优先级保持“固定配置 > 快照元数据与内置模板”。快照找不到模型或合并后仍缺执行必需
  参数时立即返回可操作错误，不在线补齐、不自动改选模型。
- `validate_model_connection` 仍是用户显式触发的推理连接验证，不属于目录刷新，也不能顺带改目录。

Provider 管理页首次进入只读取本地目录；“刷新”按钮才调用新命令。失败时保留并继续展示旧列表、
原刷新时间和连接变更标记。新建 Provider 后空目录是正常状态。

### 4.4 当前模型模板复核

OpenAI `/models` 只返回 ID、创建时间、所有者和退役日期等基础信息，不提供上下文窗口、最大输出、
图片、工具或推理档位，因此 GPT-6 Astra 仍由内置精确模板补齐；现有 `gpt-6-astra` 的 1,050,000
上下文、128,000 最大输出、图片/工具支持和 low/medium/high/xhigh/max 档位与官方资料一致，不新增
模糊前缀匹配。

DeepSeek 官方当前 ID 改为 `deepseek-flash`，并把旧 `deepseek-v4-flash`、
`deepseek-v4-flash-vision-exp` 临时路由到同一 V4.1 Flash。三者统一使用 1,000,000 上下文、384,000
最大输出、图片/工具支持和 low/high/max 档位；`deepseek-v4-pro` 保持不支持图片。模板仍只补在线
`Unknown`，不扩展目录，也不覆盖用户固定配置。

## 五、Run/Input 收敛与恢复

### 5.1 启动前失败的原子结算

现有 Input 只有 `queued | committed` 两态，本版不引入第三种失败态。启动前失败时保留用户输入的
正确方式是把原 `queued_message` 作为规范 UserMessage 提交，再把 Input 标为 committed，并把 Run
标为 failed。

`StoredRunSettlement` 和 Host `settle_run` 按以下不变量扩展：

- 来源 Input 已 committed：沿用现有 Run 结算。
- 来源 Input 仍 queued：settlement 必须携带与 `user_message_id` 一致的原 UserMessage；Host 在同一
  staged append 完成点中追加消息、清空 `queued_message_json`、置 committed、终结 Run。
- UserMessage 身份、Run/Input/Session 关联、当前状态任一不匹配即整次冲突，不只改一半。
- Shell 切换失败等已有可见内部消息排在原 UserMessage 之后；不替换或丢弃用户原文。

`runtime/input/mod.rs::fail_before_start` 统一承接模型、本地参数、Shell、Skill、Tool 装配及
currentness 复核后的真实准备错误。队列被取消、暂停、置顶或配置并发变化而使旧准备失效时，仍按
现有逻辑放弃该准备，不误写 failed。Store 结算失败则标记 Session faulted，交给恢复路径处理，
不连续重试或扩大修改范围。

### 5.2 既有异常数据的定向修复

新增 `StoredTerminalRunInputReconciliation` 及
`RuntimeStore::reconcile_terminal_run_input`。它只接受以下精确条件：

```text
run.session_id == input.session_id
run.input_id == input.input_id
run.status.is_terminal()
input.state == queued
input.queued_message.id == input.user_message_id
```

Host 使用现有 staged append/operation receipt：追加原 UserMessage，并在同一恢复提交中把 Input
置 committed；不改 Run 终态、不执行工具、不增加模型输出。相同 operation 重放返回首次结果；
状态已经正确时为幂等 no-op，关联不一致则停止并报告存储冲突。

`prepare_interrupted_run_settlements` 同时生成两类动作：

- `running | cancelling`，或 `accepted + committed Input`：按现有语义结算为 interrupted。
- 任意 terminal Run + 它自己的 queued Input：执行上述定向修复。

合法的 `accepted + queued Input` 保持队列事实，不被批量修改。迁移脚本不扫描或重写 Run/Input；
数据修复归属共用的单 Session 运行时恢复路径，从而沿用正文恢复、事务和幂等机制。

### 5.3 会话装载入口

保留 `SessionLoader::load` 为无修复的纯历史读取入口；`SessionLoader::prepare` 仍是唯一执行恢复
入口，并在同一 Session gate 下按“存储恢复 → Run/Input 定向结算 → 重新加载 → 安装状态”执行。

以下入口改走 `prepare`：

- `get_session_view` 等需要展示 active/queue 真相的组合视图；
- 删除预检/删除、归档、清空、换模型、历史重入、手动压缩等所有先判断 idle 的 mutation；
- 新输入、继续队列和已有执行准备入口。

应用级会话列表、标题搜索和 Provider 引用统计继续使用有界只读查询，不因列表加载而扫描或修复正文。
前端 mutation 失败继续通过现有 `interaction_error` 显示，不把 Runtime 拒绝吞掉。

## 六、Live step 投影一致性

### 6.1 复用 `StepCommitted`

不修改 `StepCommitted { owner, step, generation }`。现有事实足够，依据是：

- 同一主 Session 改变 Conversation 的父 Run 串行；事件在该 step 可靠提交后、下一
  `StepStarted` 或 `RunFinished` 前发布。
- `ConversationOwner::MainSession` 可在当前有序事件位置唯一对应该 Session 的非终态 Run。
- `ConversationOwner::ChildTask` 已携带 `child_task_id`，一个 child 只有一条执行流。
- `generation` 防止 clear/fork/替换后的旧提交事件封口新 Conversation。

Desktop 若在该事件位置找不到唯一非终态 Run，或 generation 与当前 owner 不一致，不猜测目标；
直接作废该 owner 的 live 尾部并请求权威快照。

### 6.2 Desktop 状态与算法

`LiveExecutionStore` 为主 Run 保存 `Map<runKey, Set<step>>`，为 child 保存
`Map<child_task_id, Set<step>>`，并记录 owner generation：

1. `StepCommitted` 加入 live 事件白名单并按 envelope sequence 处理。
2. 收到提交事件立即删除对应 live step、记录 sealed；之后该 step 的 delta、tool proposed、
   output、completed 和快照补回全部 no-op。
3. `ensureStep` 改为按 step 数字升序插入；`part_id` 只在同一 step 的 segments 内去重。
4. `RunSnapshot.active_step = N` 时，`1..N` 的更早 step 必然已完成交接，可作为 sealed 基线；最新
   Conversation 页只用于确认当前/可见 step，不再是判断全部已提交 step 的唯一来源。
5. `StepCommitted` 同时触发所选 Session/child view 的 80ms 合并刷新，由权威 Conversation
   segment 替代已删除的 live step。
6. Run/child 终态或 owner generation 改变时清理对应 seal 状态。

`RuntimeLifecycleCoordinator::#handleStreamGap` 在发起异步 snapshot 之前同步调用
`live_execution.invalidateForGap()`，清除 pending frame、主 Run/child live 尾部和 seal 水位；
保留已由权威 Session 快照持有的稳定列表。这样缺口两侧内容不会继续拼接。重连仍以现有
`observed_sequence` 过滤缓冲事件，不建立重放日志。

### 6.3 上下文用量与压缩原因

Runtime 与窗口判断统一复用 `agent-context::context_token_usage`，显式分开终态和临时态：
`completed_tokens` 为最近完整 Assistant Result 的 Provider `total_tokens`，`pending_tokens`
仅估算其后尚未得到 usage 的 User/Tool 文本增量。下一完整响应到达后替换终态基数，已计量的临时
增量清零，即使新实际值低于旧估算也以实际值为准；终态 usage 缺失时不复用更早 step 的基数。
两者相加供 SessionView 展示和下一请求预检，不维护第二份可变账本，不额外调用 Provider 计数端点。
ProviderState 密文不再按 `1 byte = 1 token` 叠加；图片等无法本地可靠计量的内容仍由既有 Overflow
交接兜底。

`SessionUsageSnapshot.context` 投影同一结果，不再取最近 `input_tokens`。活动 Run 收到
`UsageUpdated` 后，Desktop 仅在 run id 与权威 `active_run` 一致时，以最新已完成 step 的
`total_tokens` 推进快照显示，但不回退快照已经计入的 Tool Result 增量；可靠 SessionView 更新后自然接管。自动压缩提示直接读取既有
`threshold_reached | provider_overflow`，不新增协议或持久化字段。

## 七、工具输入唯一投影

### 7.1 协议形状

保留现有 `ToolInputSnapshot` 类型化枚举，新增公共包装：

```text
ToolInputProjection {
  value: ToolInputSnapshot,
  redacted: bool,
  truncated: bool,
}
```

`Unavailable` 表示旧事实或类型无法安全恢复。以下位置统一使用该包装：

- `ToolEventSnapshot.input`、`ToolDetailSnapshot.input`；
- 新增的 `ToolActivitySnapshot.input`；
- 父 `RuntimeEvent::ToolProposed.input` 与子 `ChildTaskEvent::ToolProposed.input`；
- 新增的 `ApprovalSnapshot.input`。

`ToolApprovalSubject` 继续只表达权限匹配和精确规则预览；General 不再为了展示参数而扩展权限匹配
语义。审批 UI 展示 `ApprovalSnapshot.input`，规则保存仍消费 `exact_rule_preview`。

### 7.2 Runtime 投影器

把 `runtime/product.rs::project_tool_input` 抽到私有 `runtime/tool_input_projection.rs`，成为
协议发送前唯一参数投影边界。它接受工具名、参数 JSON、可选 MCP 身份及 `raw | resolved` 来源：

- 实时与历史来自规范 Tool Call，使用 raw；审批来自
  `ResolvedToolInvocation::resolved_arguments()`，使用落实默认值和绝对路径后的 resolved。
- 两种来源输出同一类型、字段命名、脱敏和截断规则；raw 无法证明默认值时诚实省略或标为
  unavailable，不由 Desktop 猜测。
- file/files/shell/delegation/image/MCP 使用现有类型化投影；其他工具进入 General JSON 摘要。
- MCP 身份来自 Registry 的固定解析结果，不从网关名或参数文本猜测。

固定显示上限为：最大嵌套深度 6、集合最多 50 项、单字符串最多 2,000 Unicode 字符、最终投影
最多 16 KiB。达到任一上限即设置 `truncated = true`；无法序列化使用 `Unavailable`。

键名忽略大小写、`-` 与 `_` 后匹配 `authorization`、`api_key`、`access_token`、
`refresh_token`、`token`、`password`、`passwd`、`secret`、`client_secret`、`private_key`、
`cookie`、`set_cookie`，命中后整个值替换为固定 `***` 并设置 `redacted = true`。不得把被替换值、
底层序列化错误或 Provider 原始参数写入事件和日志。

Shell 完整 command、工作目录与多路径文件列表是审批关键事实。若 Ask 审批所需的这类字段因上限
被截断，Resolver 拒绝创建审批并以安全错误拒绝该调用，不能让用户批准不可见后缀；未触发审批的
历史/live 展示仍可截断并明确标记。Desktop 只按类型渲染并显示“已隐去敏感值”“内容已截断”或
“参数不可用”，不再次解析 JSON 或执行二次脱敏。

## 八、审批模式实时生效

### 8.1 Authorizer 持有关系

`RunAuthorizationScope` 只保留冻结 `variant`；`RuntimeToolAuthorizer` 改持有
`Arc<SessionController>`，移除 `approval_mode` 字段。`ParentDelegationController` 和 child
Authorizer 复用同一个 Session `Arc`，不复制父 Run 接纳时模式。

`PermissionApprovalResolver::resolve` 增加本次 `effective_approval_mode` 参数；
`RuntimeApprovalResolver` 不再持有冻结模式，创建 `ApprovalSnapshot` 时记录本次授权读取到的值。
`runs.approval_mode`、`StoredRun.approval_mode` 和 `RunSnapshot.approval_mode` 暂时保留，注释和 UI
语义改为“Run 接纳时模式”，仅用于审计/兼容，不参与工具授权。

### 8.2 判定顺序与线性化

每个 resolved invocation 独立执行既有硬边界和权限合并：

```text
Plan/基础设施硬拒绝
  → 显式 Deny
  → 显式 Ask（读取当前模式，仅用于审批快照）
  → 显式 Allow/工作区默认 Allow
  → 读取 Session 当前 approval_mode
       Ask  => 登记审批
       Auto => Allow
```

`SessionController::current_approval_mode()` 只持有短 `state` 锁。读取完成的那个时点就是单次调用的
模式判定点；同批并行工具可以分别位于切换边界两侧，不伪造整批原子性。

`set_session_approval_mode` 保持“Session mutation gate → Store 提交 → state 短锁更新 → 发布事件 →
回复成功”的顺序。内存 state 更新是线性化点：成功回复后才开始读取的授权必然看到新值；更新前已经
读取或已登记的审批保持原结果。Store 成功但 state 更新失败时 Session 进入 faulted 并由恢复重新
加载，不回复成功。切换不遍历 Approval Registry，不自动决定 pending 审批，也不撤销已授权工具。

## 九、Desktop 新会话默认值与界面收口

### 9.1 偏好存储

`DesktopPreferences` 增加：

```text
default_approval_mode: "ask" | "auto"
last_model_selection: Option<ModelSelection>
```

- Rust 两个字段都使用 `#[serde(default)]`，默认 Ask/None；审批未知枚举、非对象模型选择、空白身份或
  超过 256 字符的 Provider/模型 ID 视为无效偏好，由现有可见读取错误路径整体回退默认。
- TypeScript 同样只接受完整的 `{ provider_instance_id, model_id }`，缺失字段回退 None；该值只包含
  二元模型身份，不保存参数、凭据、目录元数据或推理强度。
- Tauri 原生 Desktop 继续写同一个 `desktop-preferences.json`：本机用顶层 `local`，每个远端使用
  已规范化 HTTP/HTTPS origin 的 `hosts` namespace。
- 普通 Web 客户端忽略这两个设备默认字段：审批仍为 Ask，模型继续跟随 Runtime 全局默认；保存 Web
  视图时也不把它们写入 `localStorage`。

`RootStore` 持有当前目标的设备偏好值，并在资源/草稿恢复之前应用到
`NewSessionDraftStore.default_approval_mode/default_model_selection`。`createDraft` 把当时两项默认复制进
草稿；已经存在的草稿不因之后的默认变化被重写。

### 9.2 更新时机

- 草稿审批切换：Composer 改调 RootStore 方法；先更新该草稿与内存默认，再调现有 300ms 串行偏好保存。
- 已物化 Session 审批：`setSessionApprovalMode` 只有 Runtime command 返回成功后才更新 Desktop
  默认并排队保存；命令失败不改默认。
- 草稿模型切换：`ModelSettingsPopover.on_model_change` 改调 `RootStore.setNewSessionDraftModel`；具体选择
  同时更新草稿和 `last_model_selection`，选择“默认模型”的 null 同时清除设备覆盖，然后排队保存。
- 已物化 Session 模型：`RootStore.setSessionModel` 等待 `SessionManagementController` 返回；只有成功
  才把请求中的具体选择或 null 写入设备默认，失败保持旧默认。
- 偏好保存失败沿用 `interaction_error` 显示“桌面状态保存失败”，不回滚已成功的 Runtime Session
  切换，也不静默回滚已经选择的草稿审批或模型。
- `isDraftCustomized` 接收当前审批和模型默认作为基线；Auto 或与最近模型相同的显式选择不再固定视为
  自定义，模型身份使用字段值比较而不是对象引用比较。

连接目标切换会销毁旧 RootStore 并加载新 namespace，因此本机审批/模型默认不会传播到远端，两个
远端也互不覆盖。

### 9.3 最近模型的失效处理

偏好先做字段级校验；Runtime 连接并取得 Application Snapshot 后，再用其中的 Provider 身份确认
`last_model_selection.provider_instance_id` 仍存在：

- Provider 存在时保留模型 ID。不能只因当前目录快照没有该 ID 就清除，因为它可能仍有固定配置，或
  目录快照尚未刷新/已陈旧；最终可执行性继续由 v0.26.0 的本地 `prepare_model` 校验。
- Provider 不存在时清除内存与持久化设备覆盖，显示“上次使用的模型所属服务商已删除，已改用默认
  模型”，不得自动选择其他 Provider 或联网刷新。
- 如果启动恢复已创建一个完全空白、尚未物化且模型仍等于该继承值的草稿，可随失效处理一并回退
  null；已输入内容、手动改过模型或开始物化的草稿保持不变。
- 模型在草稿创建后被其他客户端删除时，物化由本地准备快速失败并保留草稿，用户重新选择；不能因
  失败静默改写设备默认或自动重发输入。

“默认模型”仍由现有 null 表达：偏好为 None、草稿 `model_selection = null`，物化 manifest 省略
`model_selection`，Runtime 在接纳时使用其全局默认。本版不复制 Runtime 默认模型到设备偏好，也不
改变 `set_default_model` 的业务含义。

### 9.4 模型冻结提示

`SettingsCascadePopover` 增加触发器级 `disabled_reason` 展示：禁用时用现有 `Tooltip` 包裹整体触发
区域并关联 `aria-describedby`。`ModelPicker` 在整体禁用时不再把同一原因复制到每个 Provider
category；空闲时 Provider 分类仍可正常展开。冻结条件继续使用权威 Session view 的 active Run 与
queued Input，不新增前端猜测状态。

### 9.5 Windows 标题栏还原图标

问题只位于 `features/desktop-lifecycle/DesktopWindowControls` 的图形实现：当前 `.restore_icon` 自身是
完整方框，`::before` 又绘制一个完整透明方框，后窗被前窗覆盖的边仍会透出，形成截图中的内部线。

本版在该组件内使用专用 inline SVG 替换还原态的重叠 CSS 边框：

- 使用固定 `viewBox`，前窗为完整闭合轮廓；后窗只画暴露的上边、右边和必要的短连接段，不绘制会落入前窗内部的左/下边。
- SVG 使用 `fill="none"`、`stroke="currentColor"` 和非缩放线宽，外层尺寸保持 12px，并与最大化图标共享视觉中心。
- 图形限定在窗口控件组件，不加入通用 `IconName`，因为它是平台标题栏 glyph，不是产品内容图标。
- 保留 42px 按钮热区、hover/关闭色、Tooltip、`aria-label`、首次 `isDesktopWindowMaximized` 查询、
  `desktop://window-maximized` 监听和 `toggleMaximizeDesktopWindow` 返回值更新；不改 Rust command。
- 删除只服务旧还原图形的透明重叠边框规则，避免新旧两套轮廓同时生效。

组件测试分别断言最大化前后 glyph、Tooltip 与无障碍名称；视觉验收在 Windows 100%、125%、150%
系统缩放和明暗主题下检查线宽、居中与多余边线，并在 Linux 共用控件上做一次回归。截图比较使用控件
局部稳定区域，不把整窗平台渲染差异纳入像素门禁。

### 9.6 macOS/Windows 滚动边界回弹

`main.tsx` 在 React 挂载前提供初始平台值，原生平台读取完成后写入准确的 `macos` 或 `windows`。
`styles/platform.scss` 对这两个原生平台的根节点、`body` 和后代设置 `overscroll-behavior: none`，
使实际拥有 `overflow` 的嵌套容器到达边界时不再把越界滚动传给上层。

该属性不禁用 `overflow`，也不拦截 wheel/touch 事件，因此容器内的普通滚轮、触控板滚动和惯性仍
保留；Linux 和普通 Web 不匹配平台选择器。首版不增加 JavaScript `preventDefault`、原生
事件监听或 WKWebView 私有 API，避免破坏滚动性能、辅助输入和嵌套容器行为。

### 9.8 标题旁路超时与失败诊断

标题任务继续独立于 Session 主 Run，保留有界总时限，但由 20 秒放宽为 120 秒；transport 自身的
连接/流空闲超时仍按现有配置执行，两者不互相冒充。模型错误按既有 `ModelFailureKind` 转成
`model_execution_failed` 安全摘要，旁路总超时使用 `timeout`，缺少规定工具调用按协议失败处理，
Store 提交错误沿用 Runtime 安全错误映射。

`SessionTitleGenerationFinished` 增加可选 `error`；成功和取消不携带，旧事件缺失时默认 `None`。
Desktop 手动触发提示区分超时、模型调用失败和其他失败，仍保留重试入口且不显示 Provider 原文。
该字段为当前 `0.26.0` 内的 additive 变化，不修改数据库，也不要求机械提高协议 minimum。

### 9.7 默认 Agent Shell 单行布局

`AgentShellSetting` 保留语义化 section、标题和 `SelectionPopover`，删除 `small` 副标题，并把外层
grid 固定为 `max-content minmax(0, 1fr)`。选择器通过业务页 class 保持 `min-width: 0`，在窄宽度下
缩小并继续使用自身省略规则，标题不换行。加载、Unix 禁用、可用性筛选、保存命令、popover 与
`aria-label` 均不改变。

## 十、Shell `detached` 说明收口

执行实现保持不变。修订范围为 `agent-tools/src/standard/shell.rs` 的模型可见描述、Desktop 详情文案、
`agent-tools.md` / `agent-tools-local.md` 和相关测试名称/断言：

- `managed`：工具负责现有可管理进程树的完整收敛。
- `detached`：只有主 Shell 正常退出且两条输出管道在 deadline 内 EOF 后才完成交接；交接后 Run
  取消或 Session reset 不再由本工具主动停止后代。
- 在交接完成前发生超时、取消或输出未 EOF，仍按现有逻辑清理进程组。
- 不承诺服务健康、后台句柄、自动停止、恢复或跨平台 daemon 语义。

正常交接、继承管道导致的结算超时、取消和 managed 父进程退出四类现有测试保留；只调整与真实
语义不符的名称和说明，不弱化清理断言。

## 十一、协议、版本与迁移兼容

### 11.1 应用协议

workspace、Host、Desktop、Client 和 TS 协议包的软件版本统一升为 `0.26.0`；发布版本与应用协议
`min_compatible_version` 分开决策，不能因发版而机械同步提升 minimum。

按当前方案，本版会改变 `list_provider_models` 响应形状，并给 Tool/Approval 快照增加新必需结构；同时
旧 Host 的 list 仍会隐式联网。若最终协议保持这些破坏性形状和语义，应用协议 minimum 必须升为
`0.26.0`，`v0.25.x ↔ v0.26.0` 双向按现有握手拒绝，不建设两套响应形状或临时兼容分支。

M0 在修改 minimum 前必须先形成 Rust/TS DTO、command/result、SSE 快照和 Host 行为的兼容差异表。
如果最终实现消除了所有破坏性变化，并证明 `v0.26.0` 与 `v0.25.3` 在受支持能力上可安全双向工作，
则保留当前 `0.25.3` minimum；只有差异表和跨版本测试证明旧端无法安全解码或执行时，才提升到满足
全部最终能力的最小版本。数据库中的历史 Conversation、Run、Input 和 Desktop 旧偏好继续兼容读取。

### 11.2 数据库迁移与恢复

新增 Host `v0_26_0` migration。按当前仅增加可空/有安全默认值的 Provider 目录列、不批量改写
Run/Input 的设计，数据库最低 Host 版本继续声明为 `0.25.3`，不随数据库 schema version 机械提升；
旧 Provider 均成为“尚未刷新”。迁移继续使用现有 admission、独立 SQLite backup、事务和逐版本
验证框架。

M0 必须用 v0.25.3 旧库和新库夹具验证旧 Host 的显式拒绝路径、Provider 既有读写 SQL 对新增列的
保留行为，以及新 Host 的升级/读取/写入结果。只有证明旧 Host 会误读、破坏或覆盖新数据，且现有
schema version 拒绝不足以建立安全边界时，才把数据库 minimum 提升到 `0.26.0`，并同步记录证据和
恢复影响。

开发验收只对 TempDir/隔离 Runtime Home 执行：迁移前明确核对数据库文件、`providers`、`sessions`、
`runs`、`inputs` 表与预期范围；验证备份可读并精确 `COUNT(*)`；迁移后逐表复核数量、Provider 新列
默认值、schema version 和数据库最低 Host 版本。任何数量、关联或验证不符立即停止，不对用户
`~/.ez-assistant` 做手工修复或迁移演练。

回退到 `v0.25.x` Host 应由既有 schema version/账本检查明确拒绝为较新数据库；若 M0 证明必须提升
数据库 minimum，则也由 minimum 检查拒绝。两种路径都保留原数据库和迁移前备份；恢复方案是重新
使用 `v0.26.0`，或由用户明确选择恢复整份迁移前备份，不能删列后继续运行。

## 十二、失败语义与并发不变量

| 场景 | 结果 |
| --- | --- |
| 目录刷新网络/解析失败 | 返回分类错误；旧目录、时间和 stale 状态不变 |
| 目录刷新期间连接被编辑 | currentness 失败；不落库旧连接结果 |
| 快照损坏 | Provider 继续加载，目录为空并显示诊断；不自动联网 |
| Run 准备失败 | 原 UserMessage、Input committed、Run failed 在同一可恢复结算完成 |
| 恢复发现 terminal Run + unrelated queued Input | 不修改；必须通过精确 run.input_id 关联 |
| `StepCommitted` 无唯一 live 目标 | 作废 owner live 尾部并刷新，不猜 Run |
| 工具参数命中敏感键 | Runtime 发送 `***` 和 redacted 标志，原值不出边界 |
| 审批关键字段被截断 | 不创建审批，安全拒绝该工具调用 |
| Ask/Auto 与授权并发 | 每个调用以读取 Session state 的时点决定；pending 不追溯 |
| Desktop 偏好写失败 | 显示错误；不回滚已成功 Session 切换 |
| 最近模型的 Provider 已删除 | 清除该目标的设备覆盖并提示；新草稿跟随 Runtime 默认，不自动改选或联网 |
| `detached` 交接前取消/超时 | 保持现有进程组清理，不宣称存活 |
| 标题模型/协议失败 | 保留原标题并发布 `failed + safe error`；不吞掉分类 |
| 标题旁路达到 120 秒总时限 | 取消模型调用，发布 `timeout`，不阻塞 Session 主 Run |

必须持续成立的不变量：

1. 除 `refresh_provider_models` 外，没有生产调用点执行 `discover_models`。
2. 任一 terminal Run 的来源 Input 不得保持 runnable；合法 `accepted + queued` 不被误收敛。
3. sealed step 不再接纳任何 live 内容；gap 后旧 live 内容不能复活。
4. Desktop 永远不接收未脱敏、无界的 General/MCP 参数。
5. 显式 Deny/Ask/Allow 的优先级不因 Auto 或 Desktop 默认值改变。
6. 本版不修改 `agent-context` 策略选择或 `RollingSummarySameModel` 行为。

## 十四、实施边界与确认结果

技术依赖顺序为：协议/迁移基线 → 模型目录与断网 → Run/Input 收敛 → live/tool 投影 → 实时审批与
Desktop 审批/模型偏好 → UI（含 Windows 还原图标、macOS/Windows 滚动和 Shell 默认值布局）/Shell 收口 → 跨平台与升级回归。具体里程碑
产出、命令和每阶段确认门禁写入独立[开发计划](开发计划.md)；本文不构成代码实现授权。

2026-09-16，用户确认以下技术取舍：

1. 模型目录作为 Provider 三列内嵌快照，固定 5 秒连接、20 秒整次发现超时，不设 TTL 或配置项。
2. 启动前失败提交原 UserMessage 并将 Input 置 committed；既有 terminal+queued 通过运行时单
   Session 恢复定向修复，不在迁移中批量改写。
3. `StepCommitted` 不增 `run_id`；无法唯一定位时作废 live 尾部并回读权威快照。
4. Run 的 `approval_mode` 只保留接纳时审计，父/子每次授权实时读取 Session 当前值。
5. 软件版本固定升到 `0.26.0`，应用协议与数据库 minimum 分别按最终破坏性变化取最小必要版本：
   当前协议方案需要 `0.26.0`，当前增量数据库方案继续使用 `0.25.3`；M0 以兼容差异表和跨版本测试
   复核，未出现破坏性变化时不得机械抬高。
6. Windows 还原态使用组件内专用 SVG，只绘制后窗暴露边缘；窗口状态、按钮行为和 Rust command 保持不变。
7. Desktop 按连接目标保存最近具体模型；选择“默认模型”清除设备覆盖，Provider 删除时回退 Runtime 全局默认。
8. macOS 使用平台限定的 CSS overscroll 边界收口，不引入事件拦截；默认 Agent Shell 使用单行两列布局并删除副标题。
