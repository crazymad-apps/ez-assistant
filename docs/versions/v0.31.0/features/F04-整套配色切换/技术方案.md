## 三、目标结构与新增必要性

### 3.1 单一选择与所有者

```text
main 装配 AppearanceStore（页面生命周期）
  ├─ 恢复客户端主题偏好
  ├─ 当前 theme_id → 内置预设 → 根语义变量 / 明暗属性
  ├─ AppearanceContext → 设置、查看器、图标、登录装饰及 Markdown 业务调用方
  └─ Desktop 窄桥接 → 主窗口外观；主题保存 → 原有偏好文件

ApplicationConnectionStore → 可替换的 RootStore → Session / Run / 资源 owner
                       （不拥有、不保存主题）
```

新增 `AppearanceStore` 位于 `src/stores/`，由 `main.tsx` 显式创建并作为 App 参数传入，
`AppearanceContext` 放在 `src/app/`。Store 在连接切换及 RootStore dispose 时继续存续；仅页面退出
时释放订阅，不在 React StrictMode 模拟卸载时销毁。测试显式注入 Store，不导出可变全局单例。

这个 Store 有独立的应用生命周期，且设置、Markdown、代码、图标和登录都消费它；现有 RootStore
随身份替换，SettingsStore 只负责页面导航，均不能直接承担此所有权。Store 仅持有当前选择、最近
成功保存值、读取／保存错误和正在处理的操作；不复制预设颜色或每个渲染器的当前主题。

主题标识固定为 `default_light`、`monokai`、`solarized_light`、`solarized_dark`，只在客户端内部使用。
已确认的主题标识失效时默认 `default_light`；不新增 schema version、revision、主题迁移表或别名。

### 3.2 内置颜色的单一来源

新增应用内静态 `apps/desktop/theme-presets.json`，恰好四项，包含主题标识、显示名称、明暗属性、
启动背景、UI／终端语义颜色、通用语法角色色及 Shiki 内置主题名称。前端直接导入，原生通过
`include_str!` 编译内嵌并只投影主题身份、明暗和启动背景；不在运行时读仓库路径或请求网络。

新增静态表是为了让启动原生背景、预览和前端颜色共享同一事实。它不是用户主题格式，不开放导入，
不提供可扩展 schema／主题管理服务。保留 `tokens.scss` 中的尺寸、字体、间距、动画、层级等非颜色
Token；颜色写入由一个应用函数完成，组件仍使用已有 `--ez-*`。仅对实际缺失的焦点、代码、登录装饰
和材质补语义颜色，禁止为每个组件新造同义 Token。

每次应用先写全部颜色变量及 `color-scheme`，最后更新 `data-theme` 与 `data-color-mode`；兼容
Streamdown 的根 `.dark` 由同一函数派生。它们都是渲染结果，不是独立可写选择。根样式仅由应用
外观 owner 修改，业务组件不直接操作。预览卡读取同一表，以自己的样例局部消费，无需创建渲染器。

内置表采用完整字段约束，构建／定向测试检查四套字段齐全、颜色可解析、明暗及启动背景匹配；
新增 Token 时四套必须同时补齐。运行时不接受用户传入的 CSS 或任意主题路径。

## 四、偏好读写、并发与兼容

### 4.1 Desktop 文件边界

2026-10-13 用户强调复用现有应用配置、不得重复建设。现有 `desktop_preferences.rs` 已提供配置目录、
文档读取、写锁及安全文件替换；本 Feature 在此模块内扩展主题字段与字段级读写，前端仍通过
`native-bridge/desktopPreferences.ts` 访问。下面的窄命令只是现有偏好模块的主题入口，不另建
配置服务、存储模块或第二套文件读写路径。

沿用 `desktop-preferences.json`，在 `PreferencesDocument` 顶层新增 `theme_id`，与 flatten 的
本机布局及 `hosts` 并列；`DesktopPreferences` 视图 DTO 不新增此字段，各 namespace 不保存主题。

原生新增窄命令并在现有 invoke 注册处接入：

| 命令 | 输入／输出 | 职责 |
| --- | --- | --- |
| `load_desktop_theme` | 无输入；返回 `{ theme_id, recovered_unknown }`，读取失败返回现有偏好错误 | 只投影设备主题，区分旧文件缺字段与未知主题 |
| `save_desktop_theme` | 一个有效 `theme_id`；完成或偏好写错误 | 在同一文件中更新唯一主题字段 |
| `apply_desktop_theme` | 一个有效 `theme_id`；完成或窗口外观错误 | 只设置原生外观，不写偏好、不接触 Host |

命令只对受信任 main WebView 开放，不给第三方 child WebView 新增权限；前端统一通过
`native-bridge` 包装，Web 分支不 invoke。显示值和错误结构是 Desktop 私有契约，不进入
`assistant-protocol`。将应用与保存分开，才能准确表达“原生适配失败”与“偏好未保存”。

读写规则：

1. 文件不存在／字段缺失为正常默认。边界允许读入未知字符串或错误 JSON 类型并局部回退，返回
   `recovered_unknown: true`；不能用严格 enum 反序列化使整个合法偏好文件失效。
2. 文件格式损坏、超限或不可读返回读取错误；界面临时使用默认主题，但保存拒绝覆盖未能安全读取
   的原文档。主题功能不增加损坏文件修复／清空入口。
3. 提交严格校验四个已知标识。主题与布局写复用 `PREFERENCES_WRITE`，锁内重读最新文档，只修改
   自己拥有的字段，再复用现有私有权限、暂存文件、同步和替换路径。
4. 布局写保留最新主题值，主题写保留全部布局及 `hosts`。原始主题字段只在主题明确保存时规范化，
   不能因拖动侧栏就静默修正未知值。未成功替换前不回报保存成功。
5. 进程内写锁不宣称提供跨进程并发编辑保证；本 Feature 不引入文件锁服务或多实例同步。按现有
   单客户端运行边界验收，同配置多进程的支持若确有需求另行评估。

`load_close_behavior` 和既有布局加载继续沿用原行为；抽取共用的文档写入私有函数即可，不新建
存储 trait、第二份偏好文件或主题缓存文件。

### 4.2 Host Web 的最小保存方式

使用同一浏览器 `localStorage`，新增 `ez-assistant:theme` 键，值仅为主题标识字符串。
既有 `ez-assistant:view` 继续保存原布局白名单，不读写主题。与功能设计“复用展示偏好存储、
只增加主题选择”一致；独立键是同一个主题事实的唯一保存位置，不是双写副本。

选择单独键的具体理由：不同标签的布局快照可陈旧，整份 JSON 读改写跨标签不具有事务原子性；
即使写前重读也可能覆盖刚保存的主题。一个独立标量键足以隔离这两种写入，无需为配色引入
Web Locks、IndexedDB 或跨标签消息协议。

只在用户选择或重试主题时写主题键，布局变化不触碰它；同步 `setItem` 成功即本地保存完成。
多标签显式选择以最后一次成功写入为准，已有页面不实时改色，刷新后读取保存值。首次读取、访问
存储和写入都捕获异常；禁用／配额失败时保留内存效果并提示未保存。不把 token、账号或资源身份放入键值。

### 4.3 快速选择与失败

AppearanceStore 将选择立即投影到 CSS；原生 apply 与持久化各保持单一执行中的任务，合并尚未
开始的选择，只执行最新期望值。执行中的请求不能取消实际已发生的副作用，所以完成后核对当前
期望再决定是否继续。不得并发 apply 导致旧原生主题最后生效。

保存成功值只由实际成功结果更新；UI 的保存中／未保存由“当前选择、成功值、执行中任务和最新
相关错误”推导。完成回调通过任务对象身份判断，不靠主题字符串判断同值往返，覆盖 A→B→A
及失败后重试；不新增持久化序号或 CAS。旧错误不盖住新选择，最后一次失败不自动无限重试。

保存失败保留当前主题，外观页显示重试；原生 apply 失败另行说明窗口适配异常，以实色 CSS
覆盖不协调的材质，不能将其误记为偏好保存失败。保存完成与原生完成分别依据实际结果。
关闭设置不销毁 owner；退出桌面客户端时将其 pending save 纳入既有生命周期 flush 等待，不能
仅等待 RootStore 的视图快照。Web 页面直接关闭无法保证异步工作完成，但主题键本身为同步写入。

### 4.4 已发布偏好兼容

旧文件没有 theme_id，直接使用默认浅色；旧布局字段、host namespace 和资源格式均不变。
现有 Rust 反序列化未拒绝未知字段，旧客户端可以读取新增主题字段，但其重新序列化文档会丢弃
未知主题；旧 Web 只改布局键，不主动删新增主题键。再次升级时 Desktop 若字段已丢失就回到默认。

本方案推荐接受 Desktop 降级后主题偏好可能丢失，不为此增加双写或迁移服务。该已发布格式的
增量与降级边界随技术方案评审确认；未确认前不修改用户偏好。Runtime／Center 的存储与兼容版本不变。

## 五、启动恢复与原生窗口

### 5.1 首次展示顺序

这里的“恢复”仅指启动时从既有应用偏好读取主题字段并应用颜色，不新增恢复框架、持久化快照
或恢复任务。现有原生启动已通过同一模块读取关闭行为，主题读取复用该配置路径与文档解析。

Desktop 不能在工作区 connect 后才读取主题。主窗口改为保留原配置、在 setup 中显式构建：

1. 仅将合并配置中的 main 设为 `create: false`，保留平台窗口配置、capability 标签和插件安装。
2. setup 取得应用配置目录，使用同一有界偏好读取函数得到主题；缺失正常默认，失败默认并保留
   可供前端显示的失败事实。读取不依赖 Host、企业认证或 Runtime Home。
3. `WebviewWindowBuilder::from_config` 继承现有配置，在 build 前设置预设明暗与原生启动背景。
   继续由既有窗口状态插件恢复尺寸／位置等，不新增第二个窗口或隐藏后等待 Host 的显示门禁。
4. 前端入口先初始化 AppearanceStore：Web 同步读主题键；Desktop 通过窄读取命令恢复。
   应用颜色后再挂载 App 与连接 owner，主体内容第一帧使用正确主题。
5. Desktop 前端恢复设置 1.5 秒等待上限；超时以默认主题进入并提示。迟到读取结果不得覆盖用户
   后续选择；页面 owner 退出后不回填。超时不触发写入或重置文件。

初始化期间 `#app` 尚无主体，基础样式使用透明背景承接原生启动底色；颜色 Token 在恢复完成后
统一应用，不先把默认白色主体渲染出来。Web 的站点主题在应用绘制前同步设置；浏览器在加载 HTML
之前自己的空白页面不属于本应用可控范围。

不采用静态注入的旧主题作为每次 reload 的权威值；主页面 reload 重新读取最新保存主题。
M0 的 macOS 隔离验证观察到：主体挂载前为对应明暗的 Sidebar 材质，材质会影响启动底色，
不能承诺其逐像素等于预设 RGB；正文首次挂载后使用预设语义色。其他系统与所有首帧组合仍待集成验收。
平台默认窗口出现至 WebView 初绘的细节必须实测，尤其 WKWebView；如现有安全 API 无法消除系统
首帧限制，应报告影响并评审，不能擅自增加不受控注入或窗口常驻遮罩。

### 5.2 运行中原生适配

从现有本地 Tauri 源码确认 `Window::set_theme` 支持显式 Light／Dark；macOS／Linux 为应用级
影响。按应用统一主题使用，不暴露另一个系统跟随开关。由于资源区可以创建 child WebView，
查找主窗口继续用 `get_window("main")`，不能假定其始终是单 WebviewWindow。

窗口背景与主 WebView 背景分别按能力设置；Windows alpha 能力、macOS WebView 动态背景 API
限制按库注释处理。macOS 保留透明和 Sidebar 材质，主题提供侧栏覆盖色；减少透明度或原生适配
失败时使用主题实色。首次启动背景与工作区材质之间的变化属于同一主题内的展示，不重建窗口。

主窗口主题在 macOS／Linux 可能改变子 WebView 感知到的系统明暗。第三方页面可按其自身 CSS
响应系统外观，本项目不向其中注入主题样式、滤镜或脚本；“内容保持原色”指不改写页面内容，
不承诺冻结第三方网页自身的响应式配色。原生边界的这项限制在交互指导与实机验收中明确。

启动改造同时检查窗口状态恢复、托盘显示、第二实例唤起、关闭／退出及更新后重开，不改变这些
生命周期语义。原生 API 失败不得阻止 App 进入或触发 Host 重启。

## 六、界面与渲染器接入

### 6.1 页面、状态与图标

- 在 SettingsStore 既有页面联合中增加 `appearance`，导航新增外观页；使用现有设置容器、Button
  与提示组件。预览卡作为该页面私有组件，单选语义与键盘行为由交互指导明确。
- F02 控制工作区外完整设置的关闭与入口限制，F04 只消费 AppearanceContext；不为恢复主题挂载
  SettingsDialog，也不调整 F02 登录表单状态。
- 替换固定的文本、背景、边框、焦点、阴影及状态颜色；区分真正颜色与 mask 中仅用于 alpha 的
  黑白值，不机械替换素材、图片和数据内容色。
- 登录点阵与静态渐变读取预设角色色；移除 `prefers-color-scheme` 的选择逻辑，保留减少动画、
  可见性和鼠标能力监听。颜色变化优先更新现有材质，不重建登录表单或连接 owner。
- 文件／文件夹图标解析显式接收预设明暗；浅色使用 manifest.light 覆盖，深色用默认映射，缺图
  沿用现有回退。更新资源树及目录预览调用方，不复制四套资产或将主题藏入图标模块可变全局状态。

### 6.2 Markdown 与代码高亮

继续使用现有 Streamdown、代码插件及安全链接／图片处理。公共 MarkdownContent 只接收只读
主题描述 props，不导入 AppearanceStore、RootStore 或应用 Context；会话、推理、工具详情、搜索、
系统上下文、技能说明、资源预览及更新面板等业务调用方读取 Context 后传入，避免漏掉工作区外
的 Markdown。已有 ConversationMarkdownContent 沿用其封装，不为其余调用方另建平行包装层。
每套主题创建对应代码插件，两个
themes 槽位都传当前 Shiki 名称，避免主题明暗仍受其他 `.dark` 状态影响；更改实际插件身份触发
上下文更新，不能只修改未被消费的 shikiTheme。根 `.dark` 仍由应用派生，服务第三方控件默认样式。

在 MarkdownContent 私有辅助模块封装插件生命周期：

1. 当前 Markdown 文本与主题形成一次局部渲染作用域；文本／主题变化或卸载时失效旧作用域。
2. 转发 highlight 参数时包裹 callback，只有对应作用域仍有效才交还结果，防止旧主题或旧流片段
   覆盖新内容。作用域为局部对象身份，不持久化、不另加全局 generation。
3. 异步高亮尚未返回时同步提供当前代码的普通文本 token，使背景和文字立即使用当前主题；不能
   继续显示上次主题的 token 等待加载。异常保持可复制的原文，使用既有错误回退。
4. 保留代码块、消息和资源的稳定身份，不将 theme_id 拼进 Streamdown 或整条消息的 key；颜色
   更新不触发图片重取、滚动归零或正文重建。

当前插件高亮结果缓存使用代码长度与首尾片段组成 key，存在内容不同但 key 相同的可能；本 Feature
不扩大为高亮缓存重构。私有适配在接收结果时核对拼回的 token 文本与请求原文一致，不一致就保留
当前普通文本，避免显示错误代码；后续性能优化另行评估。

Markdown 样式把行内代码、代码区、标题和复制按钮的固定色改为语义变量；保留 token 自带的
语法色，不使用通配 `color: ... !important` 抹掉高亮。数学插件继续按需加载，普通文字继承当前色。

### 6.3 Mermaid

当前 Mermaid 渲染 effect 没有取消旧异步结果，单改配置不足以满足快速切换要求。通过 Streamdown
公开的 components.code 扩展点，仅为 Mermaid 图表接入 Markdown 私有组件；其他 fenced code
继续组合导出的 CodeBlock／复制按钮，行内代码继续原语义，保留语言、流式未完成状态与原有布局。
不复制整套 Markdown parser，也不修改 node_modules。

图表组件在 source／主题变化时清理旧 effect，以局部 active 标志拒绝迟到结果；外层容器与阅读位置
保持，新的 SVG 就绪前使用相同空间的当前主题占位／可读源码。插件包装用一条模块私有 Promise
链串行执行“取本次配置并 initialize → render”，原因是实际依赖共享一个可变 Mermaid 实例；
失败后继续队列，已失效且未开始的工作直接跳过，不引入持久任务队列或后台 worker。

默认图表使用 base theme 与预设角色色；保留作者显式 class/style。安全配置继续 strict、禁止自动
页面扫描，原有 Mermaid 插件的安全默认不得被外部内容覆盖。仅接收库生成并经既有安全机制处理
的 SVG，保持链接和脚本限制；源码解析失败显示现有可读回退。

这是本 Feature 的定向风险项：实现前先验证公开组件组合能保留复制、流式和安全行为；若实际
API 不支持方案，停止扩大改动并修订本节，不通过整条 Markdown 重挂载绕过状态保持要求。

### 6.4 Monaco

在既有 loadMonaco 成功后一次注册四个 theme definition，以 vs／vs-dark 为基底。通用 Monarch
token（comment、keyword、string、number、type、delimiter 等）由同一预设的语法角色色映射；
编辑器背景、文字、行号、选择、搜索、菜单与边框映射当前语义色。显式列出有限映射，不将 TextMate
scope 直接当 Monaco token，也不引入 TextMate 引擎、Oniguruma 或主题转换框架。

现有与后续实例统一 `editor.setTheme`；共享 Monaco 加载装配只注册一个应用主题订阅，并由应用
owner 释放。异步加载完成时读取当时的当前主题，不能使用发起加载时捕获的旧值。设置主题不 dispose
editor 或 model，不替换 URI、选区、查找、折叠和滚动状态；其加载失败继续现有失败显示。

### 6.5 xterm

继续 `terminal.options.theme = readTerminalTheme()`，保留现有 MutationObserver 与 addon dispose。
批量写根属性后合并刷新，不因为每个 Token 的变化重复 fit；系统明暗事件不再产生新的主题选择。
新终端打开前读取当前变量，隐藏实例仍更新，切换不调用 clear/reset、重建 TerminalController、
重连 WebSocket 或重启 PTY。保留 minimumContrastRatio 现值及 ANSI／RGB 原有语义，验收按最终
渲染结果检查，不修改终端输出内容。

  误报，原数据保持；在临时隔离目录运行，禁止使用实际应用偏好。
- AppearanceStore 定向测试：A→B→A、旧成功／失败乱序、退出等待、读取超时迟到、重试当前值与
  RootStore 更换后主题保留。使用注入的读写／原生适配，不建立测试专用生产抽象。
- Web 测试：主题键与旧布局键相互独立、多标签布局不覆盖主题、存储禁用／配额失败及清除恢复；
  不用真实浏览器配置做故障注入。
- Markdown 测试：延迟旧主题及旧文本回调、未知语言、缓存 key 碰撞回退、图表旧 SVG 丢弃、

  登录、会话、菜单／弹窗、代码、图表与状态色；保持 F02 工作区外设置限制。
- 构建与规范：前端 build/lint 及相关测试；Rust fmt 与 Desktop 定向测试。涉及 Tauri command、
  配置和窗口启动时按仓库矩阵完成 workspace 测试及 Tauri no-bundle 构建；若实现扩大到公共协议
  或 Runtime，再增加相应全工作区 clippy 门禁，不能用文档方案视为已通过。
- 平台验收：macOS 和 Windows 的 Release WebView 检查首屏、材质、系统明暗交叉、终端正式 CSP、

## 八、风险与确认边界

1. 首屏原生绘制和 Sidebar 材质依赖平台能力；文档已明确安全 API 路径，真实视觉效果仍须实机证明。
2. Streamdown 的异步回调及 Mermaid 全局配置需要局部适配；优先使用已核查公开入口，禁止重建
   会话／资源来掩盖异步问题，禁止在本轮默认升级依赖。
3. 默认浅色、经典主题弱文字与透明侧栏需要在交互指导中校验实际对比度，不能仅因采用知名配色
   就视为可读性通过。语法引擎映射是协调配色，不承诺逐字符完全相同。
4. 主题文件的增量、Desktop 降级后选择可能丢失，以及 macOS／Linux 应用级明暗对第三方网页自身
   响应式外观的影响随本方案明确评审，不建立额外同步或兼容机制。
5. F02 同时调整入口和连接阶段，实施时以其已确认最终行为合并；本方案不重写 F02 权限及状态 owner。

本方案、[界面交互设计指导](界面交互设计指导.md)及[开发计划](开发计划.md)已确认；用户要求持续推进到人工验收，当前完成结论及未实测项见开发计划。
左侧导航栏移除局部固定文字色重定义，直接继承全局语义变量，不增加侧栏独立配色或同步机制。
本 Feature 的确认不替代版本总体设计确认，也不授权生产配置变更或发版。
