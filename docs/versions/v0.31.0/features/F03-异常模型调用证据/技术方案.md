## 二、目标与现状核查

### 2.1 用户结果

1. 在关闭正常正文留存的情况下，可以显式开启异常证据保留，查询已接纳调用的请求及实际收到的响应。
2. 请求正文按消息阅读，响应按事件过程阅读；几字一个的文本增量合并，同一内容不被最终快照重复展示。
3. 中断、模型错误、坏事件、采集截断、存储失败和未采集分别表达；可返回实际原文核对。
4. HTTP 转发结果、响应内容观察结果、快照完整性分别呈现，不将任一结果称为整个 Agent 任务成功。

### 2.2 已核查实现

以下路径均相对仓库根，结论来自当前源码及两工程 `package.json`，不是运行环境检查。

| 现有入口 | 实际能力与缺口 |
| --- | --- |

Center 继续使用 Node／TypeScript、TypeORM／pg、node-pg-migrate 和 ws；Admin 继续使用 React、

## 三、总体方案与最小新增判断

```text
已认证、已接纳的单次调用
  → 既有 CallRecording：冻结留存模式、请求 Capture
  → HTTP 转发 / WebSocket 桥接
      ├─ 既有响应 Capture：保留实际字节
      ├─ 有界响应观察：计量与终态分类
      └─ WS 转换失败时：保留首个导致失败的原始帧
  → 同一调用结算：确定是否发布文件，更新检索元数据，释放缓冲
  → 管理员显式查看快照
  → Admin 本地投影：请求消息 / 事件流程轴 / 聚合内容 / 异常原文
```

- **沿用调用身份和生命周期**：一条 `llm_calls` 对应一次模型尝试，重试仍是另一条调用，不合并成 Run 日志。
- **正文与投影分离**：原始快照是证据，消息卡片、事件序号、聚合结果只在页面内存在，不建事件表或预解析缓存。
- **状态分开**：保留既有 `outcome` 与 usage；新增响应观察摘要，因为转发、计量和协议终态是不同事实。
- **少量必要增量**：留存模式、响应观察摘要及来源元数据；WS 未转发失败帧的可选快照。
  后者沿用同一调用、文件权限和保留周期，不形成新的日志系统。
- **不加修订号**：调用结算复用 `settled` Promise，策略写入复用身份服务串行事务；本 Feature 不引入
  revision、generation、事件订阅、持久队列或第二套快照 owner。

必答检查：**删除新增机制后，现有事实是否足够？**
消息展示与事件聚合足够由原快照派生，故只新增页面私有投影；异常留存无法由布尔开关表达，需调整模式；
HTTP 结果不能表达模型终态，需记录观察摘要；未进入 HTTP 输出的 WS 错误帧不存在于两侧原快照，
才允许增加这一份有界、可选的失败证据。

## 四、采集策略与响应观察

### 4.1 留存模式

以 `mode: off | anomalies | all` 替换 `enabled`，后台显示“关闭”“仅异常与未确认”“全部调用”。

| 模式 | 调用期间 | 结算时 |
| --- | --- | --- |
| `off` | 不建立正文 Capture；元数据和 usage 仍按既有机制记录 | 无正文，说明当时未启用 |
| `anomalies` | 请求、响应从调用开始暂存于有界内存 | 明确正常才释放而不落盘；异常或观察结果未确认则保存现有证据 |
| `all` | 同样使用有界 Capture | 所有已接纳调用保存已有正文 |

“仅异常”不能等错误发生后才开始采集，否则无法恢复前面的请求与响应。模式在 `begin` 冻结，
中途修改只影响新调用。新安装默认 `off`；已有 `enabled=false/true` 分别迁移为 `off/all`，
不自动开启生产异常采集。保留已有天数，异常正文与正常正文共用保留期，不另加期限或清理任务。

`anomalies` 仅在转发完成、观察到该调用类型的正常结果、且观察过程无缺失或冲突时丢弃正文。
`upstream_error`、`interrupted`、已接纳后的 `rejected`、异常终态、坏格式、缺失结束信号及观察超限均保留。
usage 缺失本身不等于模型异常；计量是否完整与响应是否正常分别计算。

准入前的无效凭据、请求体超限和无效模型参数继续走原拒绝路径；不为未经认证或未形成调用的流量建立正文日志。
没有发送上游时只保存已经接纳的请求并说明原因，不生成假的上游响应。

### 4.2 有界观察与分类

在 `llm/` 内抽出当前 usage 的 SSE／JSON 分帧能力，由 usage 与响应观察共同消费同一次解析结果；
它有两个明确消费者，但仍是 Center 私有模块，不上提为跨工程协议框架。
每条完整帧解析一次，处理后释放；不为终态分类额外缓存一份完整 SSE。

沿用当前单事件 1 MiB、JSON 8 MiB、共享解析缓冲 16 MiB 的资源边界。按字节识别 LF／CRLF／CR
及空行，正确处理跨 chunk 的 UTF-8、`data:` 多行、注释、BOM 与尾部残片；分片边界不成为事件边界。
超大事件跳到真正的帧边界，标记观察不完整；不能把其后半段当成新事件。单帧超限不是转发中止理由。

| 输入 | 响应观察规则 |
| --- | --- |
| Responses SSE | 识别 `response.completed/failed/incomplete/cancelled` 及 `error`；核对已知终态基本结构、响应身份。未知附加事件保留，不单凭事件名未知判错 |
| Chat Completions SSE | 按 choice index 跟踪非空 `finish_reason` 及 `[DONE]`；`stop/tool_calls/function_call` 表示相应生成结束，`length/content_filter` 单独标记受限，缺少可靠结束标记为未确认 |
| 非流式 JSON | 按实际协议与 kind 判断错误对象、Responses status、Chat choices／finish_reason；合法 JSON 本身不是成功证据 |
| compact / input_tokens | 分别识别压缩返回结构与计量返回结构，不套用普通生成 SSE 终态规则；计量调用仍不计入业务消耗 |
| 格式不支持、解析预算不足、字段冲突 | 标记未确认或明确的格式异常；仍转发原始字节，不猜测成功 |

观察摘要使用 `pending / normal / anomalous / unconfirmed`，配一个稳定、脱敏的原因码。
`normal` 的 UI 文案是“响应正常结束”，不是“任务成功”；HTTP 状态和既有 `outcome` 继续单独展示。
明确异常不能被后续正常事件覆盖；已知终态之后出现冲突终态或不合法内容也须保留异常事实。
未识别的合法扩展项只降低相应展示能力，不自动否定已确认的协议终态。

原始错误消息只进入受保护正文；普通日志、列表摘要与审计不记录 Provider 错误正文、请求内容或凭据。
原因码区分 `connect_timeout`、`upstream_idle`、`downstream_idle`、下游连接关闭、中心关闭、
主体撤销及桥接配置失效；在各原始触发点传递静态原因。无明确来源的 `cancelled` 显示“调用中断，原因未确认”，
不显示“用户主动取消”。

### 4.3 Center 与 Runtime 的覆盖边界

本方案覆盖 Center 可观察的异常，包括 HTTP 200 内的失败事件、坏 JSON／SSE、常见结构冲突及缺失终态。
但 Center 不复制 Rust Adapter 的完整校验：工具参数 schema、不支持的特定 item、Provider 私有语义、
Runtime 内部处理失败，仍可能在 Center 判为正常后才失败。

检索当前 Host／Runtime／Adapter 未发现既有 `x-ez-call-id` 失败回报通道。仅有响应头并不等于已经建立
Run 与调用的可靠关联。本草案建议不新增该通道，也不假称“仅异常”保证捕获全部 Runtime 失败。
对这类偶发问题使用现有 `all` 模式定向录制，历史未保存内容无法补录。
这是本方案明确的覆盖取舍；若要求所有 Runtime 失败都能追溯，须另行设计主体校验、逐 attempt 关联、
回报丢失和暂存期限，不能只补一个回调后宣称闭环。

## 五、快照、来源与持久化

### 5.1 原始字节与链路来源

请求仍是 Host → Center 的请求体；普通 HTTP 响应为 Center 从上游实际收到、准备转发的正文，
不代表每一字节已送达 Host。普通 WS 响应为桥接生成的 SSE，compact 响应为桥接生成的 JSON。
响应 ID、`store` 等已发生转换时必须明确来源，不把它们称为未经转换的上游帧。

新调用记录 `response_source`（`upstream_http / websocket_bridge / websocket_compact`）及规范化的
`response_content_type`、`response_content_encoding`；只保留这些必要头信息，不存整套请求／响应头。
历史空值显示“历史记录未记录来源”，不能按当前 Provider 配置反推历史传输方式。
中心控制错误仍用固定错误码表达，不生成替代上游正文的合成证据；WS 普通桥接与 compact 转换分别标明来源。

WS 在消息接收、解析与转换的原 owner 中，在丢弃首个失败帧前提供一个同步观察接缝：

- 仅当该帧导致解析／桥接失败且尚未进入响应快照时，复制到同一调用的可选 `upstream_failure` Capture。
- 保存一次，最多 1 MiB，共用 64 MiB 采集预算；预算不足或超限如实标记部分／无法保存。
- 无效 JSON、二进制失败帧和转换前 `error` 均可保留；没有收到失败帧时不创建空文件。
- 普通 HTTP、已完整保存到响应侧的错误事件不重复保存第三份证据；不录制整个 WS 帧序列或成功转换请求。
- 新增同目录固定文件 `upstream-failure.bin`，作为该调用的一个可选快照种类，和其他快照一起恢复、校验、清理。
  UI 标注“上游失败帧”，单独展示，不插入已交付 SSE 冒充同一条事件流；无法确定位置时只挂在终止诊断下。
- WS 升级握手失败等没有业务帧的情况只记录已知状态和原因，不承诺握手错误正文已采集。

### 5.2 保留原文与阅读失败

快照继续沿用原路径与不可覆盖发布，`request.txt/response.txt` 名称不变；新写文件保存实际捕获字节，
不为使文本可解码而裁掉 UTF-8 尾部，也不格式化、聚合或去重文件内容。摘要与长度针对这些字节计算。

`SnapshotContent` 保留 `text`，增加可空 `body_base64`：有效 UTF-8 且无压缩编码时返回 `text`；
非 UTF-8 或压缩字节只返回 Base64，两者互斥。前端将其展示为“非文本证据”并按需查看有界字节预览／Base64，
不自动解压、不执行 HTML、不加载内容中的远程资源。UTF-8 末尾截断可提供明确标记的可读前缀，仍可查看原字节。
新读取逻辑不再因解码失败而把完整文件改记为存储失败；解码能力与文件完整性分开。

每次最多处理一个 8 MiB 快照；后台正文读取设置两个并发槽，超出立即返回可重试的繁忙结果，不无界排队。
Base64 膨胀和 JSON 编码临时内存计入读取侧资源评估，不能将 64 MiB 采集预算表述为整个进程内存上限。
Admin 同一详情页依次读取两侧正文，失败帧单独按需读取，不预加载列表中其他调用。

### 5.3 状态与存储增量

复用 `complete/partial/failed/expired/missing/pending/disabled`；增加 `not_received`，区分未收到响应与
曾保存但文件丢失。`disabled` 结合 reason 区分 `policy_off` 和 `normal_not_retained`，对应“未启用”与
“按策略未保留正常正文”。有响应头且正常结束的零字节正文是 `complete + 0`，不是未收到；
零字节且连接失败则是 `not_received`。在预算为零但实际收到字节时标采集失败，不标未收到。

建议在唯一迁移账本中新增一个迁移，编号在实施时按最新序列分配，不修改已有迁移：

| 位置 | 增量及原因 |
| --- | --- |
| `llm_recording_settings` | 用 `mode` 替换 `enabled`，一次转换 `false→off`、`true→all`；不双写两套策略 |
| `llm_calls` | `response_observation`、`response_observation_reason`：记录留存决策的依据，正文过期后仍能识别当时的观察结论 |
| `llm_calls` | `response_source`、`response_content_type`、`response_content_encoding`：避免把桥接正文／二进制当成原始 SSE 文本；均为小型白名单值或受限规范化值 |
| `llm_calls` | 可空 `upstream_failure_snapshot` JSONB，仅承载可选失败帧的 state/path/bytes/sha256/reason，不存正文；结构由写入边界校验，不建第三套五列常驻空字段 |
| 两侧快照状态约束 | 增加 `not_received`；现有部分／失败原因继续用既有 reason 字段表达 |
| `management_audit` | 结构不变；既有查看审计的 side 可为 `upstream_failure`，策略审计记录 mode 和保留期，不记录正文 |

历史观察字段保持空，表示当时未记录，不批量读取旧文件重算或把历史 `forwarded` 填成 `normal`。
无须新增业务表、事件索引或全局计数；查询异常观察状态可在现有列表查询增加一个枚举筛选条件，
是否需要索引由定向查询验证决定，不提前建设多列索引矩阵。

### 5.4 结算、失败恢复和保留期

1. `begin` 先插入最小索引，再发送上游；无法建立索引时仍拒绝发送。
2. `anomalies/all` 建立请求与响应 Capture；观察失败不改变转发结果，也不发起重试。
3. `settle` 通过同一个 Promise 执行一次，更新网络与观察摘要，根据冻结模式决定发布或释放。
4. 文件发布按既有 `.part → fsync → hard link → 删除 .part`；发布后的各快照元数据逐个结算。
   保留其中成功的一侧，不能因另一侧失败而把整个调用说成“无证据”。
5. 调用结束时所有 Capture／解析缓冲必须释放。写盘失败仅改变快照状态；普通日志只输出固定诊断码。
6. 进程被强制结束时，尚在内存的正文无法恢复；重启沿用 unknown／missing／partial 的保守恢复语义，
   不从已记录 `normal` 推断未落盘正文存在，也不重新执行上游请求。
7. 清理复用原任务及 active 排除；增加可选失败帧的清理，先文件后元数据，任何异常停止该清理轮次。
   保留天数按当前策略作用于已有文件；缩短期限需沿用确认提示，关闭采集不删除历史正文。

## 六、正文阅读与事件聚合

### 6.1 页面结构与读取生命周期

沿用 `/calls/:id`、现有详情元数据和主题，不新增顶级页面。正文区改为左右分栏：左侧约 40% 为请求，
右侧约 60% 为响应过程；窄屏改为上下排列。两侧完整性独立展示，另一侧加载失败不遮蔽已读内容。
保留显式“查看正文”动作及查看审计；未点击前只显示元数据，点击后分别读取并呈现两侧，提供“收起正文”。

顶部只摘要转发状态、响应观察和证据完整性；异常原因就近放在对应节点。详情诊断中的 SHA、字节数、
来源、原文入口默认折叠。事件流程轴表达顺序，不按节点距离编码耗时；只有调用起止时间可计算整体时长。
没有事件接收时间就不显示时间瀑布、首字耗时、token 速度或播放动画。

复用 `useResourceQuery` 的身份／取消守卫。切换调用、身份、卸载和收起正文时释放原文、解析结果及展开状态；
相同快照由已有 SHA 标识，刷新元数据不重复解析已加载且 SHA 未变的正文。
迟到响应不能混入新调用；重新鉴权失败时按现有机制清空页面，不将正文放入浏览器持久存储。

### 6.2 左侧请求消息

- Chat `messages`、Responses 字符串／数组 `input` 及 `instructions` 按实际请求组织；以“系统提示词”独立标注，
  不把独立字段伪装成曾发送的 `system` 消息。
- 按角色及顺序显示消息，文本、实际返回的 reasoning／summary、工具调用、工具结果分别成块。
  tool call 与 result 通过已有 ID 标识关联，不重排、不补造缺失结果。
- 图片／文件只展示类型与引用摘要；Data URL、加密推理及压缩项默认折叠，不自动解码图片或打开外部地址。
- 模型参数、tools、response format 等非消息字段独立折叠，未知字段仍可在原文查看，不能无声丢弃。
- `previous_response_id` 显示“本次含历史引用，仅展示实际发送的增量”，不跨调用拼装推测历史。
- 请求 JSON 截断或损坏时显示可读原文和明确错误位置，不自动补括号后按“完整消息”展示；完整解析成功才生成消息列表。

### 6.3 右侧事件流程轴

采用 Ant Design `Timeline`、`Collapse`、`Tag`、`Alert`、`Typography` 等现有组件，Sass Module 只管理布局。
内容依然作为安全文本节点展示，不引入 Markdown／HTML 执行或另一套聊天组件库。

| 节点 | 默认展示 | 展开内容 |
| --- | --- | --- |
| 响应建立及生命周期 | 中文名称、原事件类型 | 原始事件与字段 |
| 输出文本 | 合并后的可读段落、完成状态、源事件数量 | 对应的原始增量及原文位置 |
| 推理／摘要 | 简短预览，可展开完整已返回内容 | 已返回的摘要／推理字段；不推测隐藏思考 |
| 工具调用请求 | 工具名、call ID、参数生成状态 | 聚合参数；合法 JSON 才结构化展示，否则保留文本 |
| 错误／异常 | 原因、已知位置、完整性 | 错误原文／失败帧／尾部残片 |
| 未识别事件 | 原事件名和折叠摘要 | 完整原始事件 |

工具调用节点只表示模型提出调用，不表示工具已经执行；这是单次模型调用页面，不补画工具运行耗时或结果。
响应未返回推理时不创建推理节点。心跳、注释等无内容帧默认收拢为来源信息，不逐行占据流程轴。
非流式 JSON 直接显示“响应对象”及其输出项，不伪造 `response.created` 或 delta 事件；
compact 显示窗口／输出项，input_tokens 显示计量对象，不生套聊天回答卡片。

### 6.4 聚合与去重规则

1. **区分 chunk 和事件**：网络 chunk 在现有快照中已失去边界，不能还原或展示“网络 chunk 数”。
   卡片标注“聚合 N 条增量事件”，不是 chunk 数或 token 数。
2. **稳定归属**：Responses 使用响应身份、output/item index、content/summary index、事件类别和 call ID 的已知组合；
   Chat 使用 choice index、文本／reasoning／tool 类别、tool index／ID。缺失或冲突身份的事件单独展示并提示，不能误并到上一项。
3. **只合并相邻同类增量**：同一内容项连续 delta 合为一块；切到另一个输出项、工具、错误或生命周期事件时封口。
   A→B→A 保留三段及关联，不把最后一段挪到 B 之前。同类后续段可标为“续段”，不能因全局分组破坏顺序。
4. **保留来源**：每个聚合块保留原文起止范围／事件序号；这些是本次解析的局部定位，不是新增持久事件 ID。
5. **完成快照校准**：`*.done`／`response.completed` 的完整文本或参数按相同身份与已有增量比较；一致则只标记完成，
   合法前缀扩展可补足并标明来自终态快照。互相矛盾时并列保留增量与终态值、标记冲突，禁止盲目覆盖或重复拼接。
6. **不按字面去重**：两条相同 delta 可能是合法重复文字，不能依文本相同删除；只有协议明确身份与语义支持时才合并完成快照。
7. **坏帧恢复**：SSE 单事件损坏只影响该节点；从下一条完整帧继续，尾部未完成帧单列。
   整个 JSON 文档损坏不进行猜测性修复。前端解析结论标为“阅读解析”，不能覆盖后端记录的响应观察。

### 6.5 异常表现

| 情况 | 页面表现 |
| --- | --- |
| HTTP 错误及结构化 error | 顶部显示转发错误；响应侧显示错误对象，保留已收到正文 |
| HTTP 200 内 failed／incomplete | HTTP 转发结果单独显示；响应节点标明模型失败／未完整结束 |
| 断流／无结束事件 | 已生成内容保留，最后一段标未完成；未确认原因不归因于用户 |
| SSE 坏事件／终态冲突 | 在准确事件位置标异常；允许查看原文并继续阅读其他完整事件 |
| 快照达到大小或共享预算上限 | 明确“采集在此截断，后续未知”；不得据截断尾部认定上游断流 |
| 观察／展示解析达到上限 | 明确是哪一层解析不足；原快照可能仍完整，不能改记成快照损坏 |
| 未收到／合法空响应 | 前者显示未收到及已知原因；后者显示完整零字节，模型结果按协议另外判断 |
| 文件完整但编码不可读 | 显示字节证据入口，不显示“保存失败”；不把替换字符当作原文 |
| 未采集／正常未留存／已过期／文件丢失 | 分别解释原因，正文入口不可用，不统一称为“暂无内容” |
| 正文读取失败 | 保留元信息并可重试；不把权限、网络或文件读取错误伪装成模型事件 |

颜色与图标辅助状态，文字必须独立可辨；键盘可展开来源及异常，长工具参数可换行，窄屏及缩放不遮挡正文。

### 6.6 页面性能边界

页面私有解析器一次扫描快照，用原文切片定位，避免每条 delta 同时保留完整 JSON 树、字符串副本和 DOM。
首次展示至多 100 个流程块，继续查看每次增加 100 个；单块长正文先显示有标识的预览，展开按段加载。
原始事件列表每次最多渲染 50 条；原文也分段显示，不一次挂载 8 MiB 的高亮内容。

按批次让出主线程并检查页面取消状态，原始帧索引上限 20,000、单事件语义解析上限 1 MiB；
达到上限后提示“展示解析已到上限”，保留剩余原文入口，不假装响应在此结束。
这些是本地投影／渲染限制，不新增后端事件分页或快照副本；不默认引入 Worker 和新的解析服务。

### 7.2 兼容与迁移建议

本次仅扩展 Center/Admin 管理契约，建议配套部署，不提高 Host 企业协议 3 或应用兼容下限；
Host 的代理路径及字节转发契约不变。旧后台缺失 `mode` 的策略写入明确拒绝并提示刷新，
不保留 `enabled` 别名或双读双写；历史快照路径及已记录摘要保持可读。

这里有真实既有调用数据，因此新增迁移而不是重写已执行 SQL。模式一次转换、历史新字段置空及状态约束
更新放同一迁移事务。迁移会删除旧策略列，兼容与回退方案纳入本文设计基线；实际迁移仍须独立核实并取得所需操作授权，不能仅因版本未公开发布就删用户数据。
不能原地运行旧 Center 回退；需要匹配的程序、数据库和快照目录备份一起恢复。

本设计阶段未连接数据库、未执行迁移或更改采集配置。实施前分别核实实际主机、端口、数据库、
`llm_calls/llm_recording_settings/management_audit` 及 API 读取关系。生产／共享数据迁移遵循根安全规则，
先获得明确确认并完成独立备份、可读性与关键表精确数量／恢复验证。
隔离测试使用 `.runtime-test/` 下新建场景及经核实的独立库，禁止指向用户 Runtime Home。

## 八、验证、风险与后续步骤

### 8.1 验收标准

1. `off/anomalies/all` 三种模式可辨；已有开关和保留期准确迁移，未授权环境不会自动启用正文采集。
2. 仅异常模式能留下错误调用请求和实际收到的响应；正常可确认调用不落正文，未确认原因可追溯。
3. HTTP 非 2xx、连接超时、上游空闲、下游关闭、HTTP 200 内模型失败与进程中断的原因及证据完整性正确。
4. Responses／Chat 的 SSE 与 JSON、普通生成／配置测试／compact／计量分别采用适当观察规则，缺失 usage 不被误判为失败。
5. 按不同 chunk 切分相同字节得到相同事件及聚合结果；多 choice／多 tool／交错输出不混并或乱序。
6. delta 与 done／完整终态不重复展示，冲突不丢证据；工具参数不完整时可读且不假称已执行。
7. 坏帧、UTF-8 切分、非文本字节、超大事件、尾部截断与未知事件可核对原文；存储、观察和阅读解析状态互不冒充。
8. WS 桥接来源标识准确；转换前失败帧可单独查看，compact 未产生下游正文时不伪造完整响应。
9. 两侧快照及可选失败帧共享资源边界；写入／元数据结算失败、进程重启与清理失败不会产生假完整或重复副作用。
10. 左消息右流程轴、异常节点、原文展开、分批显示、窄屏和键盘操作可用；没有伪造的事件耗时／chunk 数。
11. 切换调用、关闭正文及换身份清除内容，迟到响应被丢弃；正文按需鉴权并审计，公开路由不可访问。
12. Runtime 专属失败漏记边界按第四节披露，不把 Center 的 normal 当作 Runtime 成功；历史未采集内容不宣称可恢复。

### 8.2 最小有效验证路径

在既有 `tests/unit/llm-transport.test.ts`、`llm-usage.test.ts`、`llm-websocket.test.ts`、
`llm-records.test.ts`、`llm-snapshots.test.ts` 对应层补核心分类、限额和恢复用例；新增 Admin 私有解析器的
聚合／顺序／坏帧测试。避免在多层重复枚举同一行为，不为文案或布局增加源码快照测试。
迁移、策略权限、真实文件／索引一致性在隔离 PostgreSQL 与正式管理 API 下定向验证，沿用
`tests/integration/calls.test.ts` 的相关测试组织，执行前先核实该文件连接目标，不直接运行全部集成测试。

按改动执行两工程类型检查、lint、构建、相关单测、OpenAPI 与 SDK 一致性检查；浏览器验证真实调用详情、
读写权限与关键异常交互。使用合成 HTTP／WS Provider 确定性产生故障；真实 Provider 回证另按实际路由安排，
模拟通过不等于线上各 Provider 均已覆盖。只在计划／进度留完成结论，不另建验证报告。

### 8.3 主要风险与设计取舍

- **后台覆盖有限**：仅异常模式不能保证保留所有 Runtime 独有失败；本版建议不新增 Host 回报与暂存窗口。
- **资源不足可能缺证据**：保持 8 MiB／64 MiB 上限及明确的不完整原因；不以诊断完整性阻塞正常转发。
- **字节与来源增量**：原始字节读写及 WS 首个失败帧能补当前盲区，但需要与旧快照恢复、清理和权限一起验证。
- **隐私与磁盘使用**：新增模式默认关闭；管理员显式启用，沿用已有期限，不因“仅异常”暗示内容不含敏感信息。
- **未确认响应可能较多**：部分非标准 Provider 无标准终态，会按未确认留存；不能为了减少文件量直接按 HTTP 200 丢弃。
