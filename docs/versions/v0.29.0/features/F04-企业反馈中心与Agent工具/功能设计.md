## 一、目标与范围

用户手动填写、委托 Agent 整理，以及 Agent 自主发现问题后调用正式工具，都提交到同一个企业反馈中心。
提交者能查看本人记录和处理说明，管理员能查看全部记录并处理；只有中心可靠保存后才显示提交成功。

首版包含带结构化目标的文本反馈、本人列表与详情、管理员处理、正式 Agent 提交工具、同次提交幂等和明确失败结果。
不包含附件、截图上传、整段会话或日志采集、自动文件读取、离线队列、工单指派、SLA、邮件或站外通知。
不把现有 `ask_user`/阻塞反馈、消息点赞或 F03 待处理提醒改造成问题工单。

## 二、现有能力核查与归属

| 已有能力 | 本次复用及限制 |
| --- | --- |
| Center IdentityService、Bearer 鉴权、管理员权限、审计、PostgreSQL/TypeORM、显式 SQL 迁移 | 复用身份、事务和管理约束；现有用户、审计、调用记录都不能承载有独立处理生命周期的反馈正文 |
| Admin 路由、分页查询、写入守卫、Ant Design、OpenAPI 生成请求 | 新增反馈业务页面，沿用现有页面和身份隔离机制 |
| Desktop/Web AccountMenu、弹窗、RuntimeClient | 账号菜单增加反馈入口，客户端只持有草稿和查询投影 |
| Host 企业访问和 RunToolFactory/工具注册 | 同一企业身份的中心传输与正式工具装配，不让模型获得 Token 或指定中心 URL |
| Runtime `feedback` 与 `session_feedback` | 属于向用户提问和恢复，不用于企业反馈，不新增等待用户回答状态 |

反馈是新增业务事实，独立身份与处理生命周期属于 Center；Host 和客户端不保存第二份工单状态。
Agent Core 保持通用工具边界，不依赖中心 API、数据库或应用协议。
实现优先通过现有 Host 工具装配提供产品工具，不为这一能力提前新增通用反馈 crate 或平台服务。
删除新增反馈记录后，现有事实不能表达正文、本人查询和管理员处理结果，因此需要新增中心反馈聚合；
除此之外不引入队列、同步服务或另一套身份。

## 三、用户路径

### 手动反馈

企业模式账号菜单增加“反馈中心”，打开本人反馈列表，提供“新增反馈”入口；填写表单后点击“提交反馈”确认提交。
新建表单包含反馈目标、标题、问题描述、复现步骤、期望结果；目标、标题和描述必填，后两项可选。
先选择目标类型，再填写或选择对应对象及具体内容位置，规则见下节；不把目标仅写在标题或正文中。
提交前能看到将附带的版本和系统信息；不自动读取项目、文件、会话内容或工具日志。
本稿建议标题上限 120 字符，描述 4000 字符，复现步骤和期望结果各 2000 字符；
实现时同时设置 UTF-8 请求上限，不能只依赖 UI 校验，也不扩大 Center 通用 JSON 接收上限。

成功后打开中心返回的详情，显示编号、提交时间、状态和正文；提交中禁止重复点击。
明确失败保留当前草稿。结果未知时提示“尚未确认提交结果”，重试同一份内容使用同一提交标识。
修改内容后视为新提交，不能用旧标识覆盖旧记录。关闭表单或退出身份不建立后台自动提交。
个人模式不显示企业反馈入口，也不装配提交工具；中心不支持反馈时提示能力不可用。

本人列表按提交时间倒序分页，展示目标、标题、状态、时间和来源；详情显示自己的目标、正文、环境信息和当前处理说明。
不支持用户修改或删除已提交记录；刷新读取中心事实，首版不增加处理结果推送。
身份/Host 切换清空草稿和列表，旧身份的迟到响应不得进入新身份页面。

### 反馈目标

2026-10-02 用户补充要求：反馈增加目标字段，区分平台、某个插件、知识库的具体内容，便于后续统计。
每条反馈只有一个主要目标，手动入口与 Agent 工具共用同一结构和校验；涉及多个独立问题时分别提交，
同一问题涉及的其他对象可在描述中说明，避免一条反馈被重复计入多个主要目标。

| 目标类型 | 目标对象与具体内容 | 示例 |
| --- | --- | --- |
| 平台 | 固定指向 ez-assistant；可补充功能或页面位置 | 平台 → 会话中的文件预览 |
| 插件 | 指定插件的已有标识与名称，可补充实际版本、工具或功能位置 | 某插件 → 某工具执行失败 |
| 知识库 | 指定知识库的已有标识或明确引用、名称；针对具体内容时填写文档/条目标识或位置，可细化到章节 | 某知识库 → 某文档 → 某章节内容错误 |

目标由类型、对象引用、提交时名称和可选内容定位组成，属于反馈记录的一部分，不新建反馈目标目录或知识库实体。
插件优先复用现有 `plugins.name`/Host 插件清单中的标识，显示名称不作为聚合键，版本与工具名作为细分信息。
本轮未在当前产品模块中找到正式知识库目录契约；先接收已有知识来源提供的引用和内容定位，
能够从来源取得标识时直接复用，手动填写的名称/位置保留为未解析引用，不能伪造知识库 ID 或宣称已核验存在。
类型与明确对象是必填，具体内容定位在反馈针对某个文档、条目或章节时必填；反馈整个知识库的问题时可不填。
不自动读取目标内容、访问链接或上传文档；定位信息仅用于说明对象，不构成访问授权。

后续统计使用“目标类型 → 对象引用 → 内容定位”的维度；有稳定引用的对象按引用聚合，
手动未解析引用单独归类，不能仅凭相似名称合并成同一对象。插件版本可以进一步细分。
首版保存这些字段，并在管理列表提供目标类型和对象筛选；本次不扩大为统计仪表盘。
目标改名、插件下架或知识内容移除后，既有反馈仍保留提交时名称和定位，不级联删除反馈。
目标及内容定位参与提交内容一致性校验；同一幂等标识不能改为反馈另一个对象。

### Agent 提交

正式工具名为 `submit_feedback`，支持结构化反馈目标、标题、描述、可选复现步骤和期望结果。
Agent 使用实际可见的插件/知识来源标识定位目标；无法确定对象时明确缺失信息，不猜测标识或默认归入平台。
Host 从当前有效企业访问上下文确定提交者、中心和环境，模型不能指定账号、Token、中心地址或处理状态。
工具来源统一记为 Agent；不要求模型判断“用户委托”与“自主发现”来建立两种不同权威来源。
两类使用路径均为验收对象，但来源字段只区分手动与 Agent。

用户要求反馈时，Agent 总结相关问题并提交；自主发现时，只反馈与产品能力有关的明确问题，
不因普通任务失败、模型猜测或反馈接口报错反复上报。工具说明要求内容不含凭据和无关私人信息，
默认不携带完整会话、日志、项目路径或文件；不承诺对任意自然语言秘密做自动完美识别。

不新增每次人工确认，也不借用 ask_user 等待流程。接入既有工具授权与审计规则，
具体权限模式映射在技术方案中核清，不能通过 Shell/HTTP 绕开正式工具；显式禁用仍应拒绝。
提交失败作为普通工具失败返回，Agent 可以继续原任务；取消/超时不等于中心回滚。
成功结果必须包含真实编号及状态；返回未知时只允许对同次调用复用幂等标识查询或重试，不能虚报成功。
同一 tool call 的传输重试复用标识，不承诺对不同调用的相似正文自动合并。

## 四、管理员路径与记录内容

Admin 新增“反馈中心”导航，列表支持目标类型、目标对象、状态、来源、提交者筛选及标题搜索，服务端分页。
详情展示目标类型、对象名称/引用、具体内容定位、正文、实际提交主体、提交时名称、时间及必要环境信息；沿用既有表格、详情和表单组件。
管理员可将记录改为待处理、处理中、已解决、已关闭，并填写本人可见的处理说明。
状态可重新打开；已解决/已关闭必须填写说明。首版仅保存当前状态和说明，沿用现有审计记录变更，
不另建回复线程、状态历史表或私密内部备注。

记录包含：中心生成的编号、提交者不可复用的稳定身份、提交时用户名/显示名称、来源、结构化反馈目标、正文各字段、
版本/系统信息、创建/更新时间、当前状态、处理说明及最后处理者。
环境信息只收 Desktop（适用时）与 Host 实际版本、实际客户端类型和各自适用的系统/架构；
Web 不猜测原生版本，客户端自报信息只用于诊断，不作为权限依据。

用户身份由认证上下文决定，不信任请求体中的 owner。本人查询/详情必须由中心限定 owner，
猜测反馈编号不能读取他人记录；管理员沿用 role/is_super_admin 权限规则。
为 F05 固定边界：删除用户不能级联删除反馈，提交时名称继续显示，新建同名用户不能获得旧反馈。
具体外键和删除策略由技术方案与 F05 对齐，不提前实现用户删除或更改现有身份生命周期。

## 五、可靠性与失败语义

- 中心在同一事务保存反馈和创建审计；处理状态与审计也共事务。提交后才返回成功。
- 同一主体与同一提交标识只创建一次，重复相同内容返回同一编号；不同内容复用标识明确拒绝。
  并发重试与中心重启后仍有效，幂等事实落在反馈记录，不新增独立幂等服务或表。
- 网络失败、未登录、中心不可达、不支持能力、无权限和结果未知分别返回可理解的结果。
  不因普通反馈失败注销有效身份，不把失败递归提交为新反馈。
- 手动与工具共用同一中心创建/查询事实；没有离线暂存和自动后台重发。
- 管理员并发修改不能静默覆盖：在现有事务串行段内比较当前状态/说明与提交者读取的原值，冲突后重新读取再提交；具体约定见技术方案，不新增版本字段。
- 中心确认失效或账号切换后禁止沿用旧身份发送；旧成功回执不能显示为新身份的反馈。

## 六、与 F01 并行的边界

2026-10-02 用户明确要求在 F01 同步推进时启动 F04，作为并行排期授权；不代表后续设计、计划、里程碑门禁免除。
F01 安装包/升级与 F04 反馈没有业务状态、表或生命周期依赖。两者不能宣称文件层完全无重叠。

| 共享接入点 | 协调规则 |
| --- | --- |
| AccountMenu | F01 修改顶部升级入口；F04 增加菜单项，业务组件与状态各自私有；接入前重新读取最新文件 |
| Center app/注册、错误映射、能力声明、DataSource、OpenAPI | 仅添加本 Feature 注册，不覆盖其他注册；按最新完整源码导出 OpenAPI |
| SQL 迁移序号 | 实现前核对已存在和另一 Feature 预留序号，再确定唯一文件名；本设计不抢占编号 |
| Admin 导航、路由、生成 SDK | 增量注册各自页面，统一从最新 Center 契约生成；不手改生成产物 |
| Host 企业身份、Runtime 协议入口 | 复用已有身份，不修改 F01 兼容错误和升级生命周期；协议更改先核查全部生产者消费者 |
| 验证环境 | F04 使用 `.runtime-test/` 下新建专属场景、独立库/Home/端口，不复用 F01 或 7320/17241 用户环境 |

进入实现前再次检查 F01 实际改动；如同一共享接入点正被写入，串行完成该接入，不能覆盖另一 Feature 的工作。
本轮仅改 F04 文档及版本索引，不修改 F01 业务文件，不把用户说明推断为 F01 某个里程碑已确认。

## 七、验收与下一阶段

1. 企业用户在 Desktop/Web 手动提交并查看本人反馈；个人模式与旧中心不出现虚假可用入口。
2. 用户委托及 Agent 自主工具提交都真实落入同一中心，显示真实编号；不进入用户问答等待状态。
3. 用户隔离、管理员权限、账号切换和迟到响应正确；F05 同名账号历史归属边界明确。
4. 并发重复提交、丢失回执后重试和中心重启不重复建单；不同正文复用标识拒绝。
5. 管理员处理结果对本人可见，审计与业务事务一致；并发处理冲突有明确恢复入口。
6. 失败/取消/超时结果真实，不误停原任务，不自动上传额外资料、不递归反馈。
7. F01 升级入口和兼容处理不受影响；隔离环境验证不写入现有用户库。
8. 手动与 Agent 的平台、插件、知识库反馈遵守同一目标校验；具体知识内容可定位，管理列表可按类型和对象筛选。
   同一插件标识对应的显示名称变化后仍可归为同一目标，未解析知识引用不错误合并；目标变化不能复用旧提交标识。

功能设计已确认，技术方案与交互指导明确了工具授权、身份重验、幂等键、表/历史归属、协议与兼容影响；
两稿和[开发计划](开发计划.md)已获确认；计划按中心闭环、用户手动反馈、Agent 工具、联合验收划分 M0—M3，M0 已确认，用户授权推进至 M2；M1/M2 实现及当前环境验证完成，M2 结果待确认，M3 未开始。
实现与验证范围以各里程碑完成结论为准，不将设计中的后续能力标为已实现。
