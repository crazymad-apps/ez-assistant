## 二、台账原则

1. 只实施已获确认的当前里程碑。计划确认后从 M0 开始；每步完成实现和验证后先标记“待确认”，
   用户明确确认才标记完成并进入下一步。本轮用户明确授权推进至 M2，M1 验证完成后按该目标继续 M2；M3 仍另行确认。M3 同时承载 F04 验收，不另造重复验收阶段。
2. 每一步交付可运行、可定向验证的结果，不把未验证骨架留到 M3。后续里程碑补新能力与联合场景，
   不以“后续再测”代替本步身份、事务或副作用验证。
3. 具体字段、接口、状态和 UI 细节以已确认设计为准，本计划只维护交付、验证、确认与风险。
   发现实际实现与设计假设不符时停止扩大改动，先修订并确认相应方案。
4. F01/F04 已获并行排期授权；实现前重读共享入口的最新改动，重叠接入串行整合。
   迁移编号、Center 注册/OpenAPI、Admin 导航/生成 SDK、Host 协议入口和 AccountMenu 重点协调，
   不覆盖 F01 或其他工作树内容，不把其他 Feature 的状态改为已确认。
5. 验证使用项目 `.runtime-test/` 下按场景新建的 F04 独立目录、数据库、Runtime Home 和端口。
   首次写入前核实实际连接主机、端口、库、表及应用读取路径；同一已核实场景不重复要求逐条确认。
   新建且无用户数据的一次性库按根 AGENTS 已授权规则操作；共享/用户库仍按安全规则单独确认和备份核验。
6. 测试数据库只用于本 Feature 验证，不以本计划授权更新现有 7320 Center、17241 Host 或日常用户目录。
   汇报实际目标与影响、备份情况及验证结果；详细数量和输出留在会话，不写成独立验证报告。
7. 每步按风险做最小有效验证，报告已执行、未执行及原因；代码通过不等于已部署，构建通过不等于原生实测。
   不主动提交、推送、发布或替换用户正在使用的产品。

## 四、M0 中心接收与管理处理

**目标**：中心已经具备可持久化、可管理的真实反馈能力；后续用户入口与工具可以直接接入。

**交付范围**：

- 反馈单表、显式增量迁移、Entity/数据源/维护计数接入；沿用唯一升级账本与现有身份事务。
- 用户创建、本人列表/详情，管理员列表/详情/处理接口，三类结构化目标和有界字段校验。
- 同次提交幂等、内容不一致拒绝、处理原值冲突和同值 no-op；业务与审计同事务。
- 实际能力声明、错误映射及 OpenAPI；从最新完整契约生成 Admin SDK。
- 正式 Admin 导航、列表/筛选、详情和处理表单，身份隔离、离开守卫及冲突恢复。

**验证入口**：Center 真实隔离 PostgreSQL/API 与事务故障场景；Admin 真实页面操作；
相关类型检查、静态检查、OpenAPI/生成 SDK 一致性、构建和核心回归。
旧数据兼容用新建隔离场景从既有迁移生成少量夹具后升级，不复制用户数据库。

**完成判定**：同一用户的创建重试只形成一条反馈与一次创建审计；不同主体不可互读，管理员可按目标筛选并处理，
本人 API 可读取真实处理结果；并发处理、注销/停用交错和事务失败不造成伪成功或部分落账。
迁移、关键字段及实际接口核验相符，历史用户/插件引用边界明确。

**Review 重点**：owner 来自认证上下文；名称不参与授权或稳定聚合；未解析知识引用不错误合并；
没有新增身份、幂等服务、版本列或统计缓存；正文不进入日志/审计，管理表单不绕过写入守卫。

## 五、M1 用户手动反馈闭环

**目标**：普通企业用户能够在 Desktop/Web 自行提交并查看本人反馈，完整经过正式 Host 和 Center。

**交付范围**：

- Host 当前中心访问与反馈传输适配、能力查询、反馈 Commands/DTO 及生成 TS；既有调用者保持行为一致。
- 账号菜单入口和独立反馈面板：列表、三类目标表单、提交、详情、环境预览和处理结果刷新。
- 同一草稿的提交标识、未知回执核对/重试、内容修改后的新提交提示、草稿离开及分页恢复。
- 个人模式、能力缺失、网络失败、身份失效/切换、旧响应隔离和受限响应大小的真实反馈。

**验证入口**：新建隔离正式 Host + Center + 数据库，通过 Desktop/Web 实际页面完成创建及读取；
结合 M0 Admin 完成一次处理后由提交者刷新读取。定向验证请求丢失回执、身份换代和超限，
执行涉及 Rust 包及共享协议检查、Desktop/Client 消费编译、前端核心回归和构建。

**完成判定**：三种目标可填写并准确落入中心；手动重复点击及同内容重试不多建记录，
未知结果不被标成失败或成功；本人列表/详情与数据库一致，其他用户及原身份迟到响应不可见。
普通读取/参数错误不会注销有效账号；平台/版本显示不混淆远程 Host 和本机 Desktop。

**Review 重点**：当前主体在发送前与回执后复核；Token 不进入前端 DTO；无 Host 反馈 Store/迁移、
离线队列或会话问答状态；AccountMenu 接入兼容 F01 最新交互，F01 业务状态保持独立。
窄窗、缩放、键盘、焦点和滚动本步即验证，不能全部推迟至 M3。

## 六、M2 Agent 正式反馈工具

**目标**：Agent 直接调用真实反馈能力，用户委托和自主发现都能得到中心回执。

**交付范围**：

- Host 私有 `submit_feedback` Tool，复用 M1 的内容与当前中心访问；企业域装配，个人域不装配。
- 普通 General 授权 facts、Host 默认 Allow 与显式规则合并；Plan/Build 使用相同工具定义。
- 目标与正文的无 I/O resolve、真实结果/编号、未知结果及取消清理；工具说明明确失败后不可递归上报。
- 复用已有工具调用/结果展示，不建立 `ask_user` 待答状态、F03 待办或自动重放路径。

**验证入口**：真实 Registry/Schema 与 Runtime 权限链；受控模型驱动正式 Host，经真实隔离 Center/API
完成用户委托和自主提交。覆盖主/子 Agent 的当前用户域，默认 Ask/Auto、显式 Deny/Ask、Plan/Build，
中心缺能力、凭据失效、取消、丢失回执及结果错误。执行涉及包编译/静态检查和定向工具、权限回归。

**完成判定**：两条 Agent 路径均真实落库，目标与 owner 正确，编号来自中心；显式拒绝时没有 POST，
未知结果保留未知，不在后台再次发送或宣称回滚。反馈失败不额外终止原任务，取消仍遵循原 Run 行为。
现有权限文件保护和普通工具、用户问答功能不退化。

**Review 重点**：模型不能指定身份、中心 URL 或处理状态；工具定义保持稳定，未改 Core SPI；
没有硬编码绕过权限，默认 Allow 不能压过显式 Deny。不同 tool call 可能重复这一边界如实反馈，
不能把新调用冒充对同次提交的安全重试。

## 七、M3 联合验收与 Feature 收尾

**目标**：把已验证的各入口组合起来完成 F04 验收，不新增未设计能力。

**交付范围与验证入口**：

- 手动、用户委托和 Agent 自主提交共用中心列表与处理；平台、插件、知识库及具体内容可定位、可筛选。
- 提交者看到真实处理结果；同名目标不错误归并，目标下架/名称变化保留历史，用户归属不按用户名重绑。
- 中心重启后记录和提交去重仍有效，重新登录按同一稳定主体查询；Host/客户端重启不自动重放历史工具。
- 复用 M0—M2 已有效的事务和边界验证，只针对新增接入或剩余风险补测；集中检查三种入口的契约一致性。
- 与 F01 在当时已可验证的共享入口做联合回归；若其功能尚未完成，准确记录覆盖范围并交版本整体验收，
  不将 F01 的未完成工作当作 F04 业务依赖，也不宣称未实施场景已通过。
- 当前可用 Desktop 原生 WebView、Web/Admin 浏览器与必要平台场景；无法执行的原生或平台专项明确保留，
  由用户按实际结果决定验收，不拿构建或模拟页面替代实测。

**完成判定**：功能设计验收项逐项有可追溯结论，未完成项和平台限制明确；无数据归属、重复副作用、
授权或真实成功判定缺陷遗留。同步必要模块约束、Feature 计划、版本台账与本地进度，结果标为待确认。
用户确认后 M3/F04 才标为完成，版本整体验收仍独立进行。

**Review 重点**：新增对象均有明确所有权和必要性；删除冗余机制不影响正确性时应收敛；
没有借收尾扩大为统计仪表盘、知识库系统、附件上传、用户删除或安装升级实现。
