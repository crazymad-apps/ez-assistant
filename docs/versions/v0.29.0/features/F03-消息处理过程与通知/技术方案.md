## 一、现状与最小新增判断

依据[功能设计](功能设计.md)。2026-09-30 核查实际源码：

- `features/notifications/NotificationStore.ts` 已有事件消费、去重、关闭、权限、前台抑制及点击时身份校验；RootStore 已有权威 Session 重读与审批导航；不新建投递服务。
- `Runtime::get_conversation_page_around_run` 从指定 Run 的可靠 message IDs 倒序定位最后可见消息，返回锚点与 owner/generation。M0 用 limit=1 即可取得精确末条消息；不能用当前会话尾页或任意历史文本替代。
- `ConversationView/conversationRows.ts` 已按相邻同 Run 聚合；`ToolSegments.tsx` 已保留片段与连续工具顺序；复用其工具详情、子任务树、Collapse 和 useOutputFollow。
- `AssistantMessageSnapshot` 有 run_id/step/status/finished_at_ms，但 created_at_ms 当前固定 None；RunSnapshot 已有可靠 created_at_ms。LiveRunProjection 目前有缺值时 Date.now 回退，不能用于可靠计时。
- `ReasoningPart`、ModelEvent::ReasoningDelta、产品 AssistantSegment 均只有 text；Responses Adapter 接收 summary/content 但未投影明确语义。不能声称现有 DTO 已足够区分摘要与原文。

删除新增通知实体后，现有机制已足够承载内容与投递；因此仅增加 feature 私有内容组装函数。后续应用内待处理是现有审批/问题的派生列表，不新增持久化通知或第二套等待生命周期。

## 二、M0 内容组装

RootStore 将当前 RuntimeClient 的只读内容解析回调注入既有 NotificationStore。发布先去重，再检查系统开关、权限与前台状态；只有有机会投递时才读取来源会话及可靠正文。解析后再次核对既有 scope、投递 generation、withdrawn 和焦点，Web Locks 内也在最终 show 前检查，防止迟到内容越过身份切换或已处理事项。

1. `get_session` 读取目标父 Session 摘要，仅用于读取标题并验证 session_id；不应用到当前页面、不改变导航、水位或会话缓存。
2. turn 事件使用 `get_conversation_page_around_run(session_id, run_id, limit=1)`。必须同时匹配 owner、anchor_message_id 和 assistant.run_id；只读取该消息的 text 片段。最后消息无正文时直接兜底，不向前搜索 reasoning/工具或另一轮回复。
3. 审批工具名、问答问题来自触发事件内的冻结事实。只有标题通过 Session 读取；正文查询异常不外显原始错误。
4. 会话不存在/身份校验失败时丢弃通知；可靠正文暂不可取时使用已冻结的事件兜底。通知仍只消费一次，不建立补发队列或查询重试循环。
5. 私有纯文本转换器先限制输入处理长度，再移除常用 Markdown 标记、链接目标、HTML 标签/注释及控制字符，解码常用实体、合并空白并按 Unicode 码点截断。它只是通知摘录，不替换 Markdown 渲染器，也不执行或加载 HTML。

不增依赖、协议、事件、表、存储迁移或兼容分支；原生和 Web 共用同一 title/body，平台桥接不变。

用户“继续推进”确认 M0 并授权推进 M1；随后用户“继续”确认本节具体兼容方案。已按本节实施 Agent/Runtime/Protocol/Desktop 数据链路，M1 已完成实现与当前环境验证，用户已确认并授权 M2。M2/M3 后续实施与收尾结果见[开发计划](开发计划.md)。

### 3.1 reasoning 来源

summary 是 reasoning 内的摘要内容，不是独立消息或额外生成的摘要；本节只保留已有来源标记，为后续同一 reasoning 区域的展示规则提供依据。

`agent-types::ReasoningPart` 增加 `source: ReasoningSource`，取值 `raw | summary`。`raw` 表示普通或未标注摘要的 reasoning，不能据此声称它是模型全部内部推理；`summary` 只表示 Provider 明确返回的摘要。旧 JSON 缺字段读取为 `raw`；序列化 `raw` 时省略字段，`summary` 时保存字段。此默认值针对已存在的正式历史记录，不建立同版中间格式别名、额外迁移器或回填任务。

同一来源随 `ModelEvent::ReasoningDelta`、`AgentEvent::ReasoningDelta`、父/子 Runtime reasoning 事件和可靠 `AssistantSegment::Reasoning` 传递；每个 delta 自带来源，避免普通观察事件被丢弃后仅凭 Started 事件恢复。Core 只传递中立事实，应用协议定义轻量对应枚举，由 Runtime 穷尽映射，不让 Protocol 依赖 Agent crate。

来源只能在 Adapter 已知边界赋值：

| 输入 | 规范来源 |
| --- | --- |
| Chat reasoning / reasoning_content | raw |
| Responses summary 片段及 summary_text 事件 | summary |
| Responses reasoning content / reasoning_text | raw |
| 已有 DashScope Qwen 方言声明将 reasoning_text 对应到最终 summary | summary，从首个 delta 即一致 |
| 历史缺少 source | raw，不解析 part ID 或重新分析正文 |

Responses 的 TextState 将来源保留到补齐 done 文本和最终规范消息；同一 part 的实时与最终来源必须一致。纯 encrypted item 仍只有 ProviderState，不生成空 reasoning。原生 ProviderState、消息顺序、工具配对及请求编码策略保持既有语义；不新增摘要模型调用，也不把摘要并入正文。

### 3.2 活动快照与可靠历史

当前 `RunRecord.reasoning` / `RunSnapshot.reasoning` 是合并字符串，无法恢复片段身份和来源。M1 将这一个内存观察投影改为有序 reasoning parts；应用 DTO 使用 `reasoning_parts`，每项仅有 `part_id/source/text`，删除旧 `reasoning` 字符串字段及其消费者，不保留两个正文副本。新 DTO 归 `assistant-protocol`，不暴露规范对话或 ProviderState。

`RunRecord` 按既有 active_step 清理观察内容、按 part ID 聚合；可靠结算与 hydrate 从完整 AssistantMessage 校准同一投影。Desktop 的 `LiveReasoningSegment` 保存来源，实时增量及快照恢复复用同一 part ID，避免先生成合成 snapshot ID、后收到真实 ID 造成重复片段。已提交 Step 继续由 Conversation 接管，来源不会改变封口、owner、generation 或分页水位规则。前端仅按目标 Run 记录已纳入 reasoning 快照的事件水位，拒绝重复旧增量；晚到快照不覆盖更新的实时尾部，不提升全局水位或吞掉其他 owner 的事件。

主会话和 child 的历史分页共用现有可靠 Conversation 投影，因此已提交 reasoning 在重连、重启、压缩保留尾部和 Fork 中保留来源。child 实时事件透传来源，但现有 child snapshot 没有未提交正文缓存；断线丢失的未提交 child delta 仍不能恢复，等待可靠消息接管，不为此新增 child 观察日志或第二套执行状态。失败与取消也不得把未提交 delta 宣称为可靠历史。

### 3.3 可靠起止时间与活动时钟

耗时口径固定为 Run 被接受到可靠终结，包括排队、模型重试和审批/问答等待。child 独立使用自身被接受到终结的时间，不借用父 Run 起点。

| 投影位置 | 字段和事实来源 |
| --- | --- |
| AssistantMessageSnapshot | 新增可选 `run_created_at_ms`，只取关联 RunSnapshot.created_at_ms；既有 message.created_at_ms 含义不变 |
| RunAccepted | 增加来自已接受 Run 的 `created_at_ms` |
| RunFinished | 增加来自可靠结算 Run 的 `finished_at_ms` |
| ChildTaskEvent::Created / Finished | Created 已有 task.created_at_ms；Finished 补入可靠 child.finished_at_ms |
| RunSnapshot / ChildTaskSnapshot | 复用既有可靠起止字段，不新增存储列 |
| ObservedSnapshot | 增加 `observed_at_ms`，表示本次 Host 读取投影时的墙钟时间，供无后续事件的活动快照校准 |

`ObservedSnapshot` 时间只用于显示时钟锚点，不改变 observed_sequence 语义，也不能授权跳过实时事件。新增读取时间无需持久化，无法取得时保持未知。所有新增起止字段允许未知；不以 envelope.emitted_at_ms、Date.now、RunStarted、首次 delta 或组件挂载时间填补缺失的业务起止时间。

前端在收到有效快照/事件时记录 Host 时间与本地单调时钟的对应点；活动显示以该锚点推进，避免直接相减两台机器的墙钟。接收基准在进入帧缓冲前记录，随正文按帧发布；读取快照时使用客户端接收/应用点，它只是当前连接的显示估计，包含网络传输误差。账号/Host 换代、gap 清理后重新建立，不写浏览器存储。折叠和重挂载只读相同起止事实。

终态只使用可靠 `finished_at_ms - created_at_ms`，停止活动推进。任一起止缺失、非有限/非安全整数或结束早于开始时显示耗时不可用，不取绝对值、不补零、不延长到当前时刻。无 Run 归属的旧消息/Fork 继承消息保持未知；child 历史耗时从所属 ChildTaskSnapshot 读取，不伪造主 Run 归属。

### 3.4 兼容、F06 与回退影响

已确认并采用以下处理范围：

1. **持久历史：**为既有 ReasoningPart 采用缺省 raw / raw 不序列化字段的规则；新 summary 保存来源，旧数据不回填、不迁移、不批量重写。JSONL、pending/staged 消息载荷和离线 Model/Agent 录制中涉及相同类型的读取均须覆盖。
2. **F06 哈希：**已核查 `responses/continuation.rs::assistant_hash` 会序列化规范 AssistantMessage。旧 raw 在新代码下必须保持原序列化字节，避免仅增加缺省字段就使已保存续接前缀失效；新 summary 及其续接元数据由同一版本一起计算。禁止为展示修补旧 part 来源、改写 ProviderState 或删除本地可靠历史。
3. **应用协议：**同一未发布 v0.29.0 统一切换 `reasoning_parts`，同步 Rust 生产者、Host 转发测试、TS 生成物和 Desktop 消费者；不保留旧字符串双读双写。已发布旧版客户端已被 F06 确定的 0.29.0 最低兼容版本拒绝。本次不再提升软件、应用最低版本或数据库最低版本；同版旧开发二进制不能与新页面混用，实施验收必须重建配套 Host/页面。
4. **回退：**旧代码可能忽略新 source，重写后会丢失来源，F06 保存的新哈希也可能因此不再匹配。不得承诺旧 v0.29.0 开发二进制能原地无损回退；若实际更新包含用户数据的运行环境，部署前另行确认并保留同一时点的完整 Runtime Home。当前 M1 仅在新建隔离环境验证，不更新用户服务或共享库。
5. **Rust API：**公开 struct/enum 字段变化需要仓库内直接调用者同步重编译。testkit、context 测试、Core Demo、Runtime Harness 等只适配规范来源字段，不引入产品语义。TS 仅通过现有 Rust 导出器生成；Client 的共享包构建一并核验。

这些新增项各自解决现有字段无法表达的来源、片段身份或时间事实；没有新增业务实体、持久表、迁移版本、通知服务、事件日志或 Provider 调用。运行期仍只有既有 Run/child/Conversation 权威状态。

### 3.5 实施与验证边界

实施顺序为 Agent 类型/Adapter 与事件链、Runtime/Protocol 和生成 TS、Desktop 数据投影及计时纯逻辑。M2 再接实际折叠与耗时 UI，不提前改消息布局。

核心验证覆盖：旧 JSON 缺来源的字节稳定性、raw/summary 混合及 Qwen 首 delta/done 一致、Core 透传、可靠结算/重启/分页/child 来源、当前 Step 快照恢复和迟到增量不重复、F06 旧前缀续接及新摘要回放、可靠时间在排队/等待/失败/取消下的稳定性、远程时钟偏移及缺值降级。隔离数据使用 `.runtime-test/` 新建目录。

公共 Rust/协议改动执行 workspace Clippy 与测试、格式检查；Desktop 执行构建和定向投影测试，共享协议包及 Client 检查生成绑定。最终分别报告实施结果和未实测平台；M1 完成后停止等待确认。

## 四、M2 处理过程展示

`ConversationView` 继续按 Run 聚合，实时尾部与首条可靠消息共用稳定行 key；child 只连接自己的最后一个消息段，上下文摘要/控制结果保持独立边界。feature 私有 `ProcessingTurn` 组合既有 Collapse、消息片段、工具详情与子任务入口，不增加全局折叠 Store 或持久状态。

- 处理过程头部始终显示状态与耗时；最新无工具消息的正文在外层可见，后续 Step/工具事实到达后才移入过程。终态将最后一条含正文的消息保留在折叠外，不以同条或后续是否有工具调用判定回复；失败/中断原因也在折叠外；取消仅保留头部状态，不追加重复提示。
- 活动过程初始展开，历史初始收起；新中间 Step 展开，普通增量和同 Step 提交不覆盖手动选择；可靠终态收起。分页、owner/generation 和显式引用定位分别处理，定位先展开对应历史过程再恢复原消息锚点。
- 相邻工具跨消息合组，正文/reasoning 截断分组；组头只显示最后一条工具的动作名称与类型图标，展开项与组头左对齐、同图标尺寸与字号，不增加内层竖线或缩进；明细保留状态、原 message/call 身份与子任务入口。reasoning 仅在同一消息的连续区域内选择已有 summary，否则保留原文展开，不能拿后一步摘要隐藏前一步原文。
- reasoning 收起预览只滚动自身到最新内容，内容及可用宽度变化均校准；原文区域仍复用自由滚动和 owner 内阅读位置。summary 是同一 reasoning 区域的非交互行，不新增摘要消息。
- 耗时叶组件消费 M1 的可靠事实和 Host 锚点，只有活动期间订阅秒级刷新；等待计时、终态冻结、未知降级。正文和折叠不随计时重挂载。审批/问答仍使用底部唯一工作区。
- Turn 内文字片段保留原 message ID；引用投影按该 ID 过滤正文，保持原 UTF-16 locator，避免相邻 Step 混入。终态自动收起时，过程内部焦点回到过程头部。

沿用现有系统字体及小/正文两档字号，白色表面、灰阶文字与边框（`--ez-surface`、`--ez-text-secondary`、`--ez-text-muted`、`--ez-border`），仅交互焦点和错误使用既有强调色。用纵向缩进区分过程，最终回复保留正文权重，不增加独立卡片或页面装饰。

## 五、应用内提醒（M3）

会话标题栏组合既有 DropdownMenu，提供独立于侧栏显隐的“待处理”入口；列表按父会话分组、逐事项定位，短提示仅由已连接状态的其他会话新事件触发，自动消失或主动关闭均不改变 pending。应用内点击调用 NotificationStore 的同一激活链路，但不查询系统权限或要求原生聚焦；系统点击仍保留原生聚焦。

PendingNotificationStore 仅持有审批查询/事件的客户端投影、来源标题和短提示，不形成业务实体或持久状态。反馈直接复用 FeedbackStore.requests，避免复制问题或答案草稿。ApplicationSnapshot 会话分页且不携带全局反馈，恢复采用 list_sessions(all) 完整分页，再通过 list_pending_approvals 和 FeedbackStore.refresh 补齐；四个 worker 顺序读取，所有在途读取结算后才结束一次同步。事件发生时按会话校验读取版本，会话列表顺序变化时重试完整扫描，持续变化或查询失败显示“待处理事项尚未同步”并提供重试，不能把失败当空列表。

RootStore 按身份、连接和 projection.is_stale 驱动恢复；启动、重连及 gap 只恢复列表，不重放短提示。连接/身份换代使旧查询失效，身份变化清理旧投影和提示。点击继续重读目标会话及问题，子任务审批保留父会话唯一处理区；打开后重读列表，不能以点击动作冒充处理成功。会话删除也使在途 FeedbackStore 读取失效。

## 六、验证与配置

M0 用 NotificationStore 的竞态回归、内容归属/截断测试及正式 Host + Chrome Notifications 检查真实 title/body、去重与点击；不修改用户通知偏好或运行中的 Host。后续按里程碑验证流式与历史一致、等待/终态、分页锚点、子任务、重连和身份隔离。

测试仅使用项目 `.runtime-test/` 下新建一次性场景，沿用现有 Host setup 的实际迁移与测试夹具。生产、共享或用户 Home 不操作。构建、Web 实测和原生横幅验收分别记录结论。
