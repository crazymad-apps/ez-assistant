## 一、实现方向与现状依据

沿用 Center 的管理、文件及审计机制，Desktop 原生层负责唯一更新操作。程序每 5 分钟轻量检查，用户点击后下载并校验，停止当前在用本机 Host，再安装并启用新版随包 Host。HTTP 与 HTTPS 使用同一流程。普通用户不参与版本、架构、兼容或 Host 来源选择。

以下路径相对仓库根，已核查实际源码及 `cargo metadata --no-deps --offline`，不把设计中的接口描述为已经存在。

| 现有入口 | 本次处理 |

## 二、依赖与构建产物

### 2.1 固定依赖边界

| 依赖 | 选定版本与用途 |
| --- | --- |
| `tauri-plugin-updater` | `=2.12.0`，使用 Rust API 获取更新描述和执行平台安装；其 Tauri 依赖为 `^2.10`，与当前固定版本相容 |
| `minisign-verify` | `=0.2.4`，校验小清单及有界下载流；与 updater 使用同一签名格式，不引入第二套签名算法 |
| `tauri-plugin-single-instance` | Windows 使用 `=2.4.5`，Tauri 依赖为 `^2.10`；不启用按版本分组的 `semver` feature |
| `@fastify/multipart` | Center 使用 `10.1.2`，声明支持 Fastify 5；只用于一次上传多份发布文件的流式解析 |

核查时最新版 updater `2.13.1`、single-instance `2.5.2` 均要求 Tauri `^2.12`，本 Feature 不直接引入。以上是清单及源码核查结果，实际 Cargo 解析、编译和平台安装仍是实施验证项。UI 不安装 updater/process 的 JS 插件，也不向 WebView 开放通用安装权限。

Tauri 配置启用 `dangerousInsecureTransportProtocol: true`，正式允许 HTTP；HTTPS 继续正常检查证书。更新地址动态取自当前企业中心，不写死公共 Release 或备用中心。Windows 使用 `installMode: passive` 显示系统进度。

### 2.2 一个小清单绑定最终文件

每个平台构建输出一组可直接上传的文件：`release.json`、`release.json.sig` 和首次安装/在线更新文件。Windows 两种用途引用同一个 MSI，macOS 分别为 DMG 与 `.app.tar.gz`。上传界面自动读取和匹配，管理员不填写技术字段。

`release.json` 限制 64 KiB，固定包含：

- 产品标识、Desktop 软件版本/兼容下限、目标 `windows-x86_64 / windows-aarch64 / darwin-aarch64`；
- 随包 Host 的软件版本/兼容下限及支持的企业协议集合；
- 每份文件的用途、文件名、字节数、SHA-256；在线制品另包含 Tauri `.sig` 文件的完整内容。

软件版本首版限定项目实际使用的三段非负整数版本，按数值比较；不接收预发行标签、构建标签或管理员自报的适配声明。元数据由构建脚本从产品发布常量、目标构建参数和随包 Host 构建信息生成。Host 当前协议值从硬编码收敛为唯一发布常量，实际协议检查和构建信息共用；不维护另一份手工兼容表。异构产物在对应目标运行环境核对构建信息，不运行错误架构的程序或拿构建机架构代替目标。

生成顺序固定为：最终 Host/App/安装器文件 → 平台签名、公证及装订完成 → 在线制品签名 → 清单及清单签名。macOS 如装订改变 App，须重新生成更新压缩包；所有摘要、签名都指向最终字节。现有 `createUpdaterArtifacts` 可用于生成在线制品，但最终发布脚本必须拒绝签名后又发生变化的文件。

清单直接使用 Tauri signer 和同一发布私钥签名，不增加密钥体系。可信公钥作为产品构建资源供 Desktop 与 Center 使用，统一保存于 `packages/assistant-protocol/resources/desktop-update.pub`，Center 装配复制、Desktop 构建嵌入。隔离候选构建可通过 `EZ_DESKTOP_UPDATE_PUBLIC_KEY_FILE` 指定公钥文件，仍在构建时嵌入，不允许运行时或 WebView 替换信任根。Center 可用 `CENTER_DESKTOP_UPDATE_PUBLIC_KEY_FILE` 指定部署公钥绝对路径；未配置且没有内置公钥时只关闭上传，不影响已有其他业务。私钥仅由发布环境提供，既不上传 Center，也不随包分发。2026-10-02 按用户本地部署及打包要求已配置专用长期签名材料，与历史隔离测试密钥分离；保管与发布方式见[macOS 发布流程](../../../../release/macOS发布流程.md)。

Center 只校验小清单签名，再将上传流的 SHA-256、大小与签名清单比较。Node 使用已有 `node:crypto` 的 Ed25519/Blake2b 能力，局部解析 Tauri/Minisign 格式并验证签名、密钥 ID 和可信注释签名；不手写密码算法、不运行签名服务。实现用 Tauri 生成夹具与 Rust `minisign-verify` 交叉验证，拒绝未支持的编码。

这一步证明文件与受信构建声明一致，无须在 Center 再读大文件验证一次 updater 签名，也不解包或试运行 MSI/App。后台准确显示“发布清单已验证、文件一致”，不把这些检查表述为平台安装验收。

## 三、Center 数据与管理接口

### 3.1 两个必要的存储对象

| 表 | 权威内容 |
| --- | --- |
| `desktop_releases` | 主键 `version`；管理员更新说明 `notes`，创建/修改时间 |
| `desktop_release_targets` | 复合主键 `(version, target)`；原始 `manifest_text`、`manifest_signature`、`manifest_sha256`、发布状态及首次发布时间 |

目标行的文件引用由签名清单中的 SHA 派生；没有单独的文件表、上传任务表或校验状态表。只在所有文件接收验证成功后创建/替换目标行，半包不成为可发布草稿。原文必须保留以便验证签名，不能只存重新序列化后的 JSON。

状态为 `draft / published / withdrawn`。每个平台独立发布；首次发布后目标文件永久不可覆盖，撤回不解锁覆盖，重新发布只能使用原文件。草稿允许修正；同一清单重复上传返回已有结果。更新说明在版本行统一维护，允许管理员修正文案，不改变已签名的构建信息或制品。

使用现有 `IdentityService.write` 的短事务和审计。发布/撤回请求携带页面读取的目标摘要与原状态，说明修改携带原说明；事务内比较原值，变化则返回冲突并要求重新读取。摘要是实际制品身份，不另加自增 revision、ETag 列或状态同步服务。重复设置同一状态为 no-op，不重复审计。

新增显式 SQL 迁移，接入 `database/source.ts`、迁移资源及 `counts.ts`。迁移编号在实际接入时与 F04 核对，不在设计中占号。旧表、身份和用户域保持原归属；实施采用 `007-desktop-releases.sql`，与 F04 的 `006` 分离。验证仅使用新建隔离库。

### 3.2 文件与上传

新增 `CENTER_DESKTOP_RELEASE_ROOT`，默认 `data/desktop-releases`，独立于公开静态目录。复用现有私有暂存/内容寻址规则及关闭收尾方式，安装包服务管理自己的在途流；不将插件 `scanArchive` 带入新路径。

上传使用一个 multipart 请求，先传清单原始 UTF-8 字节的 base64 与签名文本，再传 1—2 个制品。base64 仅用于小清单传输，防止浏览器 multipart 文本换行转换；解码后严格保留原始字节（最多 64 KiB）。管理员身份在收正文前校验，提交时重验。每个文件仅接收一遍，同时计算 SHA 与大小，落盘后以不可覆盖方式发布，再提交数据库引用与审计。数据库失败可留下无引用的内容文件，但绝不让文件存在推导为已发布；首版不增加自动历史清理。

首版每份制品上限 512 MiB，总上传上限 1 GiB，清单签名上限 8 KiB；最多两个并发上传，沿用现有长上传总时限和空闲超时。超限提前结束接收。字段、文件数量、重复用途、路径分隔符及多余文件均拒绝；不允许管理员填外部下载 URL。暂存失败只清理本次拥有的临时文件。

发布、列表、发现只读已接纳的小元数据；发布/下载打开文件时以实际句柄检查类型和长度，不重新扫描摘要。内容文件由本服务不可变持有；同摘要重复内容的异常检查是接纳路径，不进入每 5 分钟轮询。

### 3.3 接口

路径均在 Center 下，由 Controller/DTO 导出 OpenAPI，Admin 重新生成 SDK。

| 接口 | 权限与用途 |
| --- | --- |
| `GET /api/desktop-releases` | 管理员，返回版本摘要及平台发布情况；首版完整列表，不新增分页体系 |
| `GET /api/desktop-releases/:version` | 管理员，说明、目标状态与制品详情 |
| `POST /api/desktop-releases/packages` | 管理员，上传一组完整平台文件，创建或修正草稿 |
| `PUT /api/desktop-releases/:version/notes` | 管理员，比较原说明后修改版本说明 |
| `PUT /api/desktop-releases/:version/targets/:target/publication` | 管理员，比较目标摘要/原状态后发布或撤回 |
| `GET /api/desktop-updates/:target/:current_version` | 公开只读，返回单个适用更新或 204 |
| `GET /api/desktop-updates/:target/releases/:version` | 公开只读，安装前核对固定候选仍已发布且文件可用 |
| `GET /api/desktop-updates/:target/releases/:version/files/:purpose` | 公开只读，下载当前已发布目标的 `installer / updater` 文件 |

公开接口返回 `Cache-Control: no-store`，不暴露草稿、审计、用户/账号信息或私有插件。下载使用固定服务端文件引用和流式响应，不返回存储路径，不提供目录浏览。撤回提交后拒绝后续发现/下载，并取消该目标尚在传输的流；客户端在安装前最后复查。复查通过后提交给本地安装器的操作不能远程撤销。

上传、说明修改、发布、撤回沿用现有成功/拒绝审计，制品版本和平台写入审计 details，不借用用户 ID 列。上传结果未知时 Admin 查询该版本平台的摘要核对，不自动再次写入。

## 四、轻量发现与登录前接入

### 4.1 来源取得

Host 增加只读 `GET /desktop-update-context`，与 `/capabilities` 使用同一公开访问边界，不要求业务登录、软件兼容通过或用户数据库就绪。只投影当前进程已生效的企业中心 URL 与 Host 支持的企业协议集合；个人模式返回无来源。不返回中心 Token、密码、Runtime Home 或用户数据，不把待重启配置当成生效配置。

该 DTO 放 `assistant-protocol` 并生成 TS 投影；它有 Host/客户端两个消费者。现有 capabilities 继续保持无地址约束，不复制 Host 软件版本字段。Host 的上下文、能力与原生连接绑定一并读取；目标变更使旧结果失效。

原生 `RuntimeConnection` 在登录尝试前保留当前目标的更新上下文，所以登录失败或业务 Store 被销毁仍可更新。个人模式、旧 Host 未提供该接口或来源暂时无法取得时，不猜测中心、不新增来源表单或提示。已发布旧 Desktop 没有 updater，首次进入支持版仍手工安装；不为旧业务协议建立通用降级读取。

### 4.2 检查和选包

原生更新 owner 确定来源后立即检查，随后每 5 分钟一次。定时任务使用跳过错过 tick 的语义；休眠恢复最多补一次，同一上下文只允许一个在途检查。UI 刷新/菜单开关不新建计时器，断网不高速重试。检查使用 `Updater::check`，元数据请求总超时 5 秒；Center 将更新说明限制为 16 KiB，完整候选响应限制为 256 KiB，原生接纳前再次核对字段长度。上游 `check` 会先解析 JSON，这里不将应用层长度校验宣称为底层接收流的硬内存上限。

Center 使用当前企业协议范围、请求目标和签名构建信息，按数值版本顺序选一个高于当前 Desktop 的完整已发布目标。本机更新使用新随包 Host 的声明判断；远端连接仅额外传现有 Host 的软件版本/下限和协议集合，判断新 Desktop 能否继续连接。未取得必要事实时不猜测可用，UI 不显示这些分类。

动态响应沿用 updater 字段 `version / url / signature / notes / pub_date`，附原始清单及清单签名。原生层从 `Update.raw_json` 验证清单，核对响应版本、当前设备目标与在线制品签名一致，再接纳候选；下载路径由当前中心和固定接口拼出，并要求响应 URL 与之相同，不采用任意响应地址。无候选返回 204；后台检查失败移除待升级按钮，已开始操作独立保留。

HTTP 正常支持，检查与下载不携带业务凭据、不跟随重定向。每次检查只传小元数据并轻量核对候选文件，无包体预下载、全量散列或独立 HEAD 探测链。

### 4.3 强制更新

Host 将有效但不相交的协议范围映射为既有 `center_protocol_incompatible`；范围为零、反转、类型错误等归无效响应/中心不可用。`client.rs` 已拆开原有混合分支；不新增中心“强制升级”开关。

Desktop 的原生登录、RuntimeClient 错误和持续连接检查统一保留结构化原因。每 5 分钟检查时复核中心当前公开协议范围，使已登录场景也能发现明确不兼容；同一份中心信息不得重复请求。网络错误不建立门禁，已经建立的门禁也不因网络失败解除。

`ApplicationConnectionStore` 记录当前连接的更新要求，退出业务视图并停止客户端订阅，但不调用退出账号、停止 Runtime 或取消任务的命令。确认更新后的本机停止才执行既有受控收尾。远端服务问题仍由原连接错误处理，不把本机更新宣称为远端已修复。门禁下的发现/下载与普通更新共用原生 owner。

## 五、Desktop 更新操作与 Host 交接

### 5.1 唯一状态与下载

在 `src-tauri/src/desktop_update/` 建立私有 owner，放在 Tauri State 中。它拥有候选、检查任务、下载取消句柄及当前阶段；界面 Store 只消费快照，保存面板开关。原生命令只接收“更新当前候选”“取消下载”“读取状态”，不接收任意文件、命令、公钥或安装地址。

```text
已发现 → 用户确认 → 下载并校验 → 停止本机 Host → 安装 → 新应用启动/连接
                    ↓取消或失败       ↓失败       ↓失败
                  保留现有安装       中止安装    根据实际版本恢复
```

状态事件用于提示刷新，界面重开后读取权威快照；不另建持久化事件日志。只有一个更新操作，重复点击返回当前进度。来源/目标切换取消尚未安装的操作并丢弃迟到结果；进入停止/安装短阶段后，原生层拒绝并发切换与生命周期动作，UI 同步禁用相关入口。计时、下载任务由该 owner 保存取消句柄和任务句柄，应用正常退出时取消并等待；不创建脱离生命周期的后台任务。阶段锁不跨网络等待；停止/安装用同一个生命周期锁串行，不能在持锁方法内再次调用会取同一锁的公开 shutdown。

updater `2.12.0` 的标准 `download()` 将完整文件累积到内存，chunk 回调只给长度且不能返回取消错误。因此本方案复用已有 reqwest/临时文件能力进行有界流式下载，并用同一 `minisign-verify` 在接收流中验签；不同时调用 updater 下载再重复校验。接收总量以签名清单大小为硬上限，超过或少于声明即失败；取消关闭响应并删除本次临时文件。总时限 30 分钟、无新字节 60 秒，失败后重新下载，不做断点续传。

清单签名绑定版本、目标和在线制品签名，下载验签再绑定实际字节，避免 HTTP 响应虚报高版本指向旧包。采用这条唯一校验链；现有 Tauri CLI `2.11.4` 的通用 signer 不支持版本参数，不假定其生成了 updater `requireSignedVersion` 所需注释，也不为此升级整套 CLI。不得仅靠未签名响应的 version 比较放行安装。

安装前以只读接口复核同一目标摘要仍可用。校验完成后才允许停止 Host。调用 `Update::install` 时读取已验证的同一私有文件句柄，限制在 512 MiB 内；这是上游安装 API 要求的内存副本，不是第二次下载、解包或全包校验。安装的跨平台差异留在 updater 内，不自制安装器。

### 5.2 本机停止与重新启动

更新 owner 调用既有 `RuntimeBootstrapCoordinator` 的窄交接方法，复用同一个 `lifecycle_gate`。在锁内固定实际本机实例、PID、地址与原生证明，执行既有 shutdown，等待原 PID 退出和运行锁释放；不能仅以 discovery 消失认定已停止，也不能重发现后向后继实例补发停止。

不读取旧可执行文件来源来决定能否更新，不等待全局任务空闲。停止归 Host 现有关闭流程，结束任务与终端、保存数据；不在更新器维护 Run/Session 清单。30 秒停止上限沿用现有约定，失败中止安装。远端目标只更新本机 App，禁止停止远端 Host。

安装后启动当前 App 内的随包 Host，保持原 Runtime Home。普通启动/重启仍遵循各自语义；仅用户已经确认的更新交接使用随包切换。对于现有 `0.26.0`，只保留已有经过验证的窄关闭 wire 适配，不根据任意旧 Host 声明动态降低业务版本下限。

Native 启动失败不修改数据库、不自动降级；Host 备份、迁移、最低软件准入和初始化继续由既有实现负责。等待发现只证明进程可连接，随后仍需正常身份/业务就绪检查。

### 5.3 跨进程重启与失败

在开始停止/安装前，原生层原子写一个私有 `pending-update.json` 到 Desktop 应用配置目录。只记录原版本、预期版本、制品摘要、当前连接目标，以及本机所用 Runtime Home；路径均由原生已有状态确定，不含凭据或任务数据。它只补足安装使 Desktop 进程退出的交接缺口，不是更新队列或自动重试日志。

新版启动先比对自身实际版本，再恢复目标并启动/连接随包 Host；达到真实就绪后删除标记。仍是旧版本时说明上次更新未完成，允许重新打开旧应用或重新安装；标记本身不能触发再次下载、强制停止或断言成功。异常文件不触发安装操作。首次安装没有标记，沿用原入口。

Windows updater 启动 MSI 后会直接退出进程，不能在同步 `on_before_exit` 回调中异步停止 Host。停止、标记落盘和必要资源关闭必须在调用安装前完成；回调只做同步清理。沿用 MSI `AUTOLAUNCHAPP`，安装完成后启动真实新程序，保留当前用户安装身份与固定安装位置；不设置提权更新任务。MSI 已启动后，旧 UI 不承诺还能回报最终失败。

macOS 完成 App 替换后由原生层重启。只读 DMG、不可写位置先拒绝原位安装，提示把应用移到“应用程序”后重试。安装前失败且旧文件完整时可启动旧随包 Host 恢复；文件已改变或数据准入不允许时留在恢复入口，不自动切换旧二进制访问新数据。

## 六、Windows 单实例

在 Windows 的 Tauri builder 最先注册 single-instance，先判断实例再装配会启动 Host 的工作。回调复用 `desktop_lifecycle` 的显示、取消最小化、聚焦逻辑，忽略第二进程带来的任意业务参数，不改变身份或会话。开发/正式按既有 identifier 隔离，同一产品的不同版本保持同一实例身份。

源码核查发现 `2.4.5` 在已存在互斥量但通知窗口尚未创建时可能继续启动。因此使用现有 `windows-sys` 在插件注册期间加一个短启动互斥区，主实例完成通知窗口注册后释放；后来的启动先等待该短区，再交由插件判断已有实例。等待有上限，超时结束本次启动，不能另开完整客户端。该锁只保护注册竞态，不持有整个产品生命周期，也不引入新服务或端口。

进入安装阶段后已有窗口只能显示更新进度，不能因重复启动恢复业务准入；安装器重启在旧进程退出、实例句柄释放后执行。`on_before_exit` 不提前释放单实例所有权来制造两个活动 Desktop。Windows x64/arm64 均需真实验证冷启动并发、托盘隐藏、最小化、安装重启与 MSI 身份/安装位置。

## 七、接入顺序与验证边界

Center 与 Admin 的 Controller、实体、上传配置、路由、SDK、审计文案同步接入；Host/共享协议的更新上下文与错误保真同步生成。Desktop 原生状态、native bridge 和界面投影一起接入，不为未发布中间格式加兼容别名。

F04 当前已接入 Center 注册、Admin 路由及 `006-feedback.sql`，后续还涉及 AccountMenu 和共享协议；实施这些入口前读取最新状态，重叠接入串行处理，保留 F04 的反馈能力与现有生成内容。版本整体仍为开发中，不重开 F02/F03 验收。

验证按核心风险分层：

1. 构建清单/签名夹具覆盖文件错配、元数据篡改、旧包冒充新版本及错误平台；流式接收/下载覆盖取消、超限、截断和签名失败，无重复大文件扫描。
2. Center 用项目 `.runtime-test/` 中新建的隔离环境验证上传—发布—发现—撤回、普通用户拒绝、匿名只读范围、并发草稿替换及失败审计一致性；HTTP/HTTPS 均覆盖。实施前核对实际库连接与读写表，遵守根 AGENTS 的数据库规则。
3. 原生侧覆盖每 5 分钟检查合并、旧上下文迟到返回、门禁误判、下载失败不停止 Host、实际退出及锁释放、不同原安装来源交接、失败后版本核对。
4. 页面只验证主要流程、入口显隐、面板重开/取消、登录页和管理员发布；不为静态文案、组件库行为或 CSS 值堆叠测试。
5. 真实平台验收区分首次手工安装与后续在线更新，三个目标逐一核对签名/安装身份、实际新版本、随包 Host 和原数据恢复；没有对应设备的部分如实保留，不以构建通过替代。

方案阶段已完成代码、依赖清单和上游源码核查；未安装新依赖、生成密钥、连接数据库、构建安装包或操作用户 Host。方案及交互指导确认后已形成[开发计划](开发计划.md)并获用户确认，M0 已确认，M1、M2 已实现并验证；用户授权自主推进至 M2 的范围已完成，M3 未开始，每个实施里程碑独立验收。
