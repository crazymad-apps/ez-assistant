### 2.2 用户结果

管理员能上传、验证、发布和撤回企业 Desktop 安装包；客户端自动检查，仅在发现适用且可下载的更新时显示更新按钮，用户确认后完成下载、校验、安装和重新连接。明确不兼容时留在登录入口，能够升级或得到具体的恢复路径。

Windows 重复启动恢复并聚焦已有窗口；安装后的首次启动能够接续正常生命周期。升级全过程区分文件替换、进程重启、数据准入和企业登录，不用一个“成功”掩盖其中的失败。

### 2.3 首版范围

沿用实际发布矩阵：Windows x64、Windows arm64、macOS arm64，均为 Desktop 与随包 Host 的整包。Windows 保持现有系统下限和当前用户安装范围，不借 F01 改成管理员安装或系统服务。

一个企业更新渠道，全量更新。首版不增加灰度、差分、自动降级、独立 Host 发布、CLI 自动升级、个人公开更新渠道、Linux/macOS Intel Desktop 支持或常驻更新进程。

## 三、企业安装包管理

### 3.1 管理对象与入口

Enterprise Admin 新增“安装包”入口，沿用已有导航、列表、详情、表单和权限体系。

管理员按产品版本管理更新说明和各平台制品。版本、系统、架构、随包 Host 版本及兼容信息由现有构建脚本生成一份小清单，上传时自动带入，管理员主要维护更新说明和发布状态。中心校验清单的必要字段及其与制品的对应关系，不重新构建、试运行安装包或逐个平台探测兼容性。这些信息用于后台发布和程序自动适配，不转成普通用户需要理解或选择的列表。

按“版本 + 平台架构”发布：可先发布已验收的平台，不让缺少另一平台制品阻塞发布；列表明确显示已覆盖和缺失平台，不能把某个平台完成标成全平台可用。F01 整体验收仍覆盖首版三个目标。

每个目标包含首次安装制品及在线更新制品；二者可以引用相同文件，也可能使用不同格式。后台展示文件用途、大小、校验结果和签名状态。缺少必要文件或校验失败时不可发布。

### 3.2 上传、发布与撤回

1. 上传进入私有暂存，显示实际传输状态；接收文件时同步计算大小与摘要，结合构建清单和必要的可信签名校验完成接纳。平台、版本和兼容信息读取清单，不通过全量解包、执行程序或重复扫描大文件取得；校验结果随对应的不可变制品保存。
2. 管理员核对更新说明、目标平台、兼容范围和完整制品后显式发布。上传不自动发布。
3. 正式发布后的平台制品及构建信息不可覆盖；修复制品应产生新版本。未发布草稿可以修正，完全相同内容重复上传不制造新版本；更新说明允许管理员修正文案。
4. 撤回后不再用于新检查、新下载或尚未提交的安装。客户端安装前重查该制品仍可用；已进入系统安装器的操作不能承诺远程撤销，已安装版本不会自动降级。
5. 首版只提供撤回，不提供安装包物理删除或自动清理历史文件。撤回保留追溯信息，首次安装下载同样遵循发布状态。
6. 上传校验失败不污染已发布版本。发布/撤回与审计共同提交；网络结果不明时重读实际状态，不以自动重发写请求代替核验。

安装包只保存公开分发所需信息，不打入中心凭据、用户配置、Runtime Home 或会话数据。该边界由构建打包时的固定文件范围和发布验收保证，中心上传不增加全包内容扫描。

2026-10-02 用户要求校验保持简单、避免拖慢操作，后续实现遵循以下成本约束：

- 构建阶段生成元数据并完成平台验收；中心上传只做必要的字段、文件对应关系、完整性与签名校验，不重复平台验收或增加独立校验服务。
- 发布、列表、选包和检查更新读取已保存的元数据与接纳结果；实际下载时只增加文件可读性、大小等轻量检查，不重新计算整个文件的摘要或签名。内容发生变化时必须作为新制品重新接纳。
- 客户端下载后保留安装前必要的完整性与签名校验，优先复用更新器现成结果，不叠加同义的自定义校验。性能验证重点检查是否存在重复读取和上传结束后的额外长等待，不预先承诺未经实测的固定耗时。

## 四、普通更新

### 4.1 入口与检查

- 2026-10-02 用户明确调整：取消常驻“检查更新”按钮，仅在发现适用且可下载的更新时，于账号菜单顶部用户信息右侧渲染更新按钮。沿用输入截图位置，可访问名称为“更新应用”。
- 确定企业中心后启动检查一次，应用运行期间每 5 分钟自动检查一次；休眠恢复最多补一次，不积压定时检查。同一来源的并发检查合并，不提供单独的手动检查入口。
- “可用更新”要求本次检查成功、候选满足第 4.3 节且下载入口可用，不能仅凭较大的版本号或旧缓存显示按钮。可用性核对复用轻量元数据和文件可读性检查，不预下载安装包，也不增加全包扫描。
- 自动检查只获取元数据，不后台下载、不弹出抢焦点的强制对话框。普通更新允许暂缓。
- 没有可用更新或检查失败时，普通界面保持原样，不渲染更新按钮或占位说明，等待后续自动检查；已发现的包撤回或变为不可用时同步移除待升级入口。
- 切换企业中心或 Host 后作废旧检查结果；下载绑定发起时的来源和制品，不把另一中心的结果混入当前界面。

### 4.2 更新面板

点击更新按钮打开简洁的更新面板，说明“有新版本可用”，提供更新说明及“更新并重启”操作。普通用户不需要查看兼容范围、系统架构、Host 来源或版本列表。面板与账号菜单生命周期分离，关闭菜单不丢失进行中的进度；未发现可用更新时不提供空面板入口。

“更新并重启”旁简短说明：更新会重启应用，并停止当前使用的本机后台，进行中的任务和终端会中断。一次确认覆盖下载、校验、停止本机 Host、安装及启动新版随包 Host，不另设 Host 选择或接管确认。用户点击后才开始下载；目标制品或本次更新对象变化时重新确认。

```text
每 5 分钟自动检查 → 无可用更新或检查失败：不显示按钮
                 → 发现适用且可下载的更新：显示更新按钮
用户点击更新并重启 → 下载 → 校验
校验通过 → 停止当前在用的本机 Host → 安装
         → 启动新版随包 Host → 重新连接
任一步失败 → 展示具体阶段与下一步，不推断后续成功
```

- 下载/校验失败时不执行安装，已打开面板保留失败原因；仅在重新确认目标包可用后提供“重试下载”，不另设“检查更新”按钮。建议首版失败后重新下载，不承诺断点续传。
- 下载阶段允许取消；开始修改安装文件后不提供虚假的“取消并恢复”承诺。
- 下载期间可继续使用；校验通过后进入停止和安装流程，不增加等待所有任务空闲的步骤。停止或安装失败时展示简单原因与重试方式，不假装已经完成。
- 普通面板可收起；已开始的下载及安装操作保留进度入口，再次打开读取同一原生操作状态，不重复启动操作。后台检查结果变化不隐藏或取消已开始的操作；安装前仍复查目标包。
- 更新检查、下载取消、关闭面板不取消 Agent Run。

### 4.3 自动确定更新

程序根据当前设备和已发布信息自动确定一个可用更新。平台、架构、版本顺序及必要兼容判断留在内部，用户只需要知道“有更新”，无需选包、选择版本或处理 Host 匹配。

无可用更新时普通入口隐藏。需要强制更新却暂时取不到更新时，登录页只说明“暂时无法更新，请稍后重试”；更新已开始后发生错误，按下载、安装或重新连接等用户能理解的步骤提示。详细诊断留给内部日志，不展开兼容矩阵或来源分类。

## 五、不兼容时的登录页升级

### 5.1 何时必须更新

- 企业中心明确判定当前版本无法继续使用时，回到登录页，提示“需要更新后继续使用”，阻止进入业务界面；有可用更新时显示“更新并重启”按钮。登录时和使用过程中均适用。
- 网络不通、密码错误等问题沿用原有错误处理，不误判为必须更新。

### 5.2 登录前发现和下载

Center 提供独立、只读、无需业务登录的更新发现与制品下载接口，只返回已发布的 Desktop 版本信息、公开更新说明及所需文件。管理列表、草稿、审计、插件包和用户数据继续鉴权；不将现有管理接口整体开放。

已发布的安装包与更新说明对能访问此中心地址的人可读。它消除“先登录才能升级、先升级才能登录”的循环，避免额外引入安装账号、长期下载密钥或匿名会话体系。

更新地址直接沿用已选企业中心地址，登录前仍能取得；不能依赖业务 Session 创建成功、模型配置加载成功或用户数据库就绪。地址的取得和旧协议降级读取范围由技术方案落实。

正式支持 HTTP 和 HTTPS 更新发现与下载，包括登录前升级。HTTP 企业中心直接使用原地址，不要求额外部署 HTTPS 分发入口或由用户开启特殊选项；安装包签名与完整性校验保持一致。

### 5.3 门禁内恢复

登录入口显示“需要更新后继续使用”，按同一自动检查周期刷新；有可用更新时显示“更新并重启”，暂时没有时显示简短恢复提示，不增加独立的“检查更新”按钮。保留既有连接重试；关闭面板、重启 UI 或重新输入密码不能绕过同一目标的兼容判定。

登录页与普通入口使用相同的停止和更新流程，无需用户另行停止 Host、清理任务或判断安装来源。

安装后重新验证；Desktop 已更新但 Host 未就绪、数据迁移失败或中心仍不兼容时，分别展示对应状态，不能自动进入业务界面。

## 六、Host、安装与失败恢复

### 6.1 本机 Host 统一交接

2026-10-02 用户明确：停止当前正在使用的本机 Host，升级后启用随包 Host，不再按原 Host 来自 Desktop、CLI 或其他安装位置分支处理，也不以来源不同拒绝更新。

1. 下载和校验完成后，通过现有本机管理能力受控停止当前在用的本机 Host；已经停止则继续。
2. 等待该实例实际退出、释放运行锁，再执行安装。沿用现有停止流程封闭准入、取消任务、结束终端并完成数据收尾，不增加等待空闲的另一套生命周期。
3. 安装完成后，在同一 Runtime Home 启动新版随包 Host，重新连接。原有配置、身份绑定和数据继续由 Host 读取与恢复，不另建空目录或复制数据。

原生层仍固定实际本机目标与实例并使用本机管理凭据，避免误停其他进程；这是执行正确性核对，不是安装来源限制。停止失败或超时则中止安装，显示“暂时无法完成更新，请重试”，不以强杀代替正常收尾。

该流程只处理当前在用的本机 Host；连接远端时保留原远端目标，本机应用更新不停止远端服务。任务中断和持久队列恢复沿用 Host 现有语义，升级器不删除历史、不重放工具。

### 6.2 安装与重启

建议采用 Tauri 官方 updater 执行平台更新，原生层拥有升级操作；UI 只显示状态和发送意图。按官方文档，macOS 更新制品为 App 的压缩包，Windows 可复用 MSI，更新签名为必要校验；这与系统代码签名、公证分别处理。[Tauri Updater](https://v2.tauri.app/plugin/updater/)

macOS 保留签名公证及安装位置核验；从只读 DMG 运行、位置不可写等条件不得假装可原位更新。Windows 保留当前用户 MSI 安装身份、禁止降级和用户数据保留语义，用户确认后可显示系统安装进度，不采用无反馈的静默安装。

下载散列正确不等于来源可信。升级使用随应用可信配置中的验证公钥，不能接受待下载响应自带的任意公钥；正式私钥归发布环境管理，不上传企业中心、不写仓库。密钥建立、备份和平台签名链的具体方案在技术方案中确认。

进入系统安装器前完成需要异步等待的偏好保存、Host 退出和资源释放。Windows 更新器会在安装前退出应用，不能把完整异步收尾寄托于退出回调。[Tauri Windows 更新退出钩子](https://v2.tauri.app/plugin/updater/#windows-before-exit-hook)

### 6.3 失败与恢复边界

- 检查/下载/校验失败：当前安装保持可用；仅普通兼容状态允许继续使用业务。
- 本机 Host 已停止但安装尚未修改文件即失败：安装内的旧随包 Host 仍完整且能够通过数据准入时，可用它恢复服务；否则留在恢复入口，不按旧来源建立多套回退策略，也不循环重启。
- 安装器失败或结果未知：明确状态，提供重新打开应用或重新安装可信完整包的路径；不把安装器启动或进程退出当成安装成功。
- 新 Desktop 已启动但 Host/数据准入失败：展示真实启动阶段与原因；不重复执行迁移、不自动切回旧二进制访问新数据。
- 安装文件恢复与 Runtime Home 恢复是两个动作。已升级数据的回退继续遵循既有备份、最低 Host 准入及完整恢复规则，不新增自动数据库降级。

已有公开 `0.26.0` 不包含本功能，不能通过服务端开关补出内置更新。首次进入支持 F01 的版本仍需手工安装；必须分别验证“旧公开版 → 首个支持版”的安装/数据交接，以及“支持版 → 更高版本”的在线升级。F01 的本机交接统一遵循第 6.1 节；旧协议关闭适配在技术方案中核实，不向用户增加来源选项。

## 七、Windows 单实例

同一 Windows 用户会话、同一产品标识只保留一个 Desktop。正式与开发应用标识继续隔离，不把开发验证唤起到正式产品。

重复启动时恢复已有主窗口：隐藏则显示、最小化则还原，然后聚焦；保持当前连接、登录和正在阅读的会话，不重新初始化 Host。首选官方 single-instance 插件，回调复用已有窗口生命周期能力。[Tauri Single Instance](https://v2.tauri.app/plugin/single-instance/)

安装重启需等旧进程释放实例所有权后再启动新版本。安装中重复启动不能把旧界面复活为可用业务，也不能误将新版启动转发给尚未退出的旧实例。注册时机、安装器启动参数及超时恢复在技术方案和 Windows 实机中闭合。

## 八、模块归属与最小新增

| 归属 | 本 Feature 的职责 | 优先复用 |
| --- | --- | --- |
| Center | 安装版本/平台制品、发布状态、选择、分发和管理审计 | 既有身份串行段、数据库迁移账本、事务审计、流式文件生命周期 |
| Admin | 安装包管理视图及用户意图 | Ant Design、既有导航、页面查询/写入守卫、OpenAPI 生成请求 |
| Desktop 原生层 | 本机更新检查/下载/校验/安装、状态快照、窗口单实例 | Tauri 插件、原生资源及 Desktop 生命周期、本机实例发现与管理凭据 |
| Desktop UI | 账号入口、更新面板、登录门禁、阶段和恢复提示 | 既有 Dialog、Button、连接状态和 native bridge |
| Host / Runtime | 当前本机实例受控退出、新随包 Host 启动及数据恢复 | 现有本机管理、准入关闭、任务/终端收尾及 shutdown；不增加空闲检查台账 |
| 共享协议 | 确有跨层消费者的兼容、更新发现或生命周期投影 | 既有协议及生成工具；Center 管理 DTO 继续由 OpenAPI 维护 |

新增 Desktop 安装包记录是必要的：其平台、签名、发布和安装生命周期不等于插件包，不能复用插件身份或伪造插件清单。具体表结构在技术方案决定，不在功能设计阶段建表。

新增原生更新操作有独立的平台安装生命周期；普通入口与强制入口共用一个 owner。删除它会让下载和安装无人管理，但无需增加 Runtime Session、Agent 工具、持久任务队列或新产品进程。

已有兼容判定、审计、软件版本和 Host 状态足够承载的部分不再复制。首版不默认新增业务 revision、发布流水号、下载 Token 表、全局通知中心或通用包管理框架。

F04 同步设计已登记[共享接入协调](../F04-企业反馈中心与Agent工具/功能设计.md#六与-f01-并行的边界)。两者独立维护业务数据和验证环境；AccountMenu、Center 注册/迁移、Admin 路由和生成契约接入前重新读取最新状态，重叠接入串行处理。本设计不提前占用迁移编号，也不修改 F04 文档。

## 九、验收标准

1. 三个目标均有可核验的 Desktop 与随包 Host 制品；构建清单与产物一致，首次安装和在线更新用途清楚；非法元数据、文件错配、损坏或无效签名被拒绝。中心不重复执行平台验收，发布与检查更新不全量读取安装包。
2. 非管理员不能上传/发布/撤回；发布与审计一致，失败不污染当前版本；撤回后新发现、下载和安装前复查均不能使用该包。
3. HTTP 和 HTTPS 企业中心均可直接发现与下载更新，包括登录前升级，签名与完整性校验一致。登录前只读分发仅暴露已发布安装包和公开说明；不能访问草稿、用户数据、管理审计或私有插件。
4. 启动及每 5 分钟自动检查且不下载；仅发现适用可下载包时显示更新按钮，无新版、无适用包、检查失败和撤回时不显示待升级入口，无独立手动检查按钮。已开始操作的进度保持可达；点击确认后才下载，暂缓、取消、面板重开、重复点击和来源切换不产生重复操作或串状态。
5. 程序自动确定可用更新，普通用户不选择版本、架构或 Host 来源，不阅读兼容矩阵；无可用更新时入口隐藏，更新失败采用简短可操作提示。
6. 明确中心不兼容时登录前及运行中均能进入门禁；密码错误、网络故障和非法响应不误判。门禁下可发现与下载，关闭 UI 或失败重试不能绕过准入。
7. 用户确认更新后，当前在用本机 Host 按现有停止流程结束任务、终端并收尾，退出前不安装；升级后同一 Runtime Home 启动新版随包 Host。原安装来源不同不阻止交接，远端及其他无关实例不被停止。
8. 覆盖取消下载、错误散列/签名、撤回竞态、磁盘/权限不足、安装失败、Host 退出超时、新版启动和数据准入失败，各自保留可理解的恢复路径。
9. Windows 两个架构实际验证重复启动、托盘隐藏、最小化、安装后重启、开发/正式隔离及 F02 标题栏/终端行为；构建不替代实机结论。
10. macOS 实际验证签名公证 App 的原位更新、DMG/只读位置失败、Host 文件替换和重启后的实际版本；旧公开版首次手工升级与后续在线升级分别验收。
11. 重启后继续验证 F06 可靠上下文恢复和 F03 待处理入口，历史工具不重放，任务状态和用户数据不由更新 UI 改写。

## 十、已确认选择与后续设计

2026-10-02 已按用户明确要求确定：启动及每 5 分钟自动检查，取消手动检查按钮，只有存在适用且可下载的更新时才显示更新按钮。本项不再列为待确认选择。

同日用户进一步明确：普通用户只需理解需要更新，不承担兼容、架构、版本列表或 Host 来源判断；本机统一停止当前在用 Host，升级后启用随包 Host。旧稿的来源分类和占用暂缓方案删除，改为复用受控停止及一次更新影响提示。

HTTP 和 HTTPS 更新支持已由用户明确，直接沿用企业中心地址；删除初稿的 HTTPS 分发前置要求，保留安装包签名与完整性校验。

用户修订后要求继续，以下产品选择作为方案基线：

1. 首版三个平台目标、单渠道全量升级、按版本/平台独立发布；已发布制品不可覆盖，撤回不物理删除。
2. 登录前公开最小只读分发，仅提供已发布安装包和公开更新说明。
3. Windows 沿用现有 MSI 和当前用户安装；新增更新签名不承诺解决既有 SmartScreen/代码签名提示。

本 Feature 已形成独立技术方案和界面交互指导，落实安装执行、协议及文件/数据库发布一致性；用户操作保持简单。方案覆盖以下实现问题：

- 实际 updater 依赖版本及与当前 Tauri 的兼容、HTTP/HTTPS 支持配置、制品格式、最终签名/公证顺序、可信版本元数据与密钥保管；
- Center 最小数据模型、具体接口、更新源配置、文件限制、发布/撤回竞态与审计事务；按第三节合并必要校验，避免重复全量读取和复杂校验流水线；
- 登录前获得中心地址及兼容信息的路径、结构化错误传播、已登录时持续兼容检查和旧版行为；
- 当前在用本机 Host 的受控停止、实际退出核对、同一 Runtime Home 的随包 Host 启动与失败恢复，复用现有生命周期而不新增来源分类和空闲门禁；
- 单实例与安装器重启衔接、原生更新进度恢复和平台验收条件。

上述问题见[技术方案](技术方案.md)，页面布局及状态见[界面交互设计指导](界面交互设计指导.md)，两稿已于 2026-10-02 获用户继续指令确认。[开发计划](开发计划.md)已获确认，现从 M0 开始，每个里程碑完成后按项目规则停止汇报。

M0 已获用户确认；用户授权自主推进至 M2，M1、M2 已完成当前环境的实现与验证，结论见[开发计划](开发计划.md)。已使用隔离签名的真实 macOS 候选完成普通更新和登录前更新、自动重启及原数据接续。正式密钥、公证、Windows 实机与跨 Feature 联合验收仍归 M3，尚未开始；F01 与版本整体验收保持未完成。
