## 一、整体思路

本地继续保存完整、可恢复的有效上下文。服务端续接只是减少每次上传的历史内容，不改变本地会话的权威地位。

首次请求发送完整有效上下文；后续请求如果可以续接，就发送上次的响应 ID 和新增消息、工具结果。当前指令、工具定义和生成参数仍随请求发送。

这里的“完整有效上下文”是当前指令、压缩摘要和保留消息，不是把压缩前的全部历史重新发一遍。

## 二、配置放在哪里

服务商身份和协议决定默认是否支持续接，具体连接提供启用开关，默认关闭；自定义接口可显式覆盖能力判断。企业连接由管理员配置，个人连接由用户配置，不在每个模型上重复设置。

HTTP 原生路由要求保存响应并按 ID 续接；Center WebSocket 桥接路由要求连接内接续可用，具体按第十节。未知或不支持的接口继续发送完整有效上下文。

## 三、状态怎么保存和恢复

复用现有消息中的 ProviderState，随回复一起可靠保存响应 ID、对应的用户/连接/模型，以及它覆盖到哪段历史。不另建一套会话或响应表。

**Desktop/Host 重启本身不是重建条件。** Center 桥接连接丢失时按第十节重建；HTTP 原生存储的旧 ID 仍以服务商实际有效性为准。Desktop 或 Host 重启后，从已保存消息恢复续接状态；身份、配置和上下文一致，就继续使用原 ID。未完成的响应、尚未可靠保存的状态不能作为续接依据，工具恢复沿用现有机制。

主会话和每个子任务分别维护自己的续接状态。摘要、标题、识图和连接测试不参与业务会话的续接。

## 四、什么时候重建

| 情况 | 处理思路 |
| --- | --- |
| 正常新增消息或工具结果 | 使用旧 ID，只发送新增内容 |
| 重启，原状态仍一致 | 恢复旧 ID，继续续接 |
| 压缩成功提交 | 用摘要和保留消息建立新链；压缩失败不影响原链 |
| 切换模型 | 用目标模型重建，包括同服务商切换，以及 A→B→A 中间没有调用 |
| 身份、连接或上游配置变化，历史被改写 | 旧状态失效，使用当前有效上下文重建 |
| 服务商明确拒绝旧 ID，且本次尚未开始生成 | 同一 Run 最多自动重建一次 |

续接前还要确认已发送的历史内容没有变化，不能只比较消息数量或 ID。模型切换和配置变化需要留下可持久恢复的失效标记，避免重启或切回后误用旧链；正常重启、同一用户的登录 Token 更新不使其失效。

网络错误、认证失败、流中断等继续按原有错误流程处理，不一律全量重发，也不重新执行已完成的工具。

## 五、各层怎么配合

- **Runtime**：管理本地上下文、续接状态的保存与恢复，以及压缩、模型切换后的失效处理。
- **Responses Adapter**：接收完整本地上下文，校验续接状态，决定实际发送全量还是增量，并从完整响应提取新的续接状态。Agent Core 保持服务商无关。
- **企业中心**：下发续接策略与配置标识，转发前检查身份和配置仍有效。即使代理地址不变，上游模型、地址或密钥改变，也不能继续使用旧绑定；管理员关闭后不能绕过。
- **现有设置界面**：增加连接开关和能力说明，企业普通用户只读。

优先复用现有配置、消息持久化、压缩和恢复流程。旧会话没有响应 ID 时，首次全量建立新链即可。具体字段与兼容处理按下节核查结果落实。

## 六、M0 持久化与旧版本兼容处理（已确认）

### 现状核查

- 连接权威配置由 Host 的 `storage/model_management.rs` 直接读写 SQLite `providers` 表；不是整份 JSON 配置。新增开关和能力覆盖需要接入现有版本迁移。
- `AssistantPart::ProviderState` 已可由现有消息存储保存，不需要新增响应表或改写历史消息。当前 Responses 编码器对同路由但不认识的状态类型返回配置错误，不能宣称旧 Host 能正常继续带有新续接状态的会话。
- `ProviderConnection` 当前没有拒绝未知字段；旧 Host 可能忽略新客户端提交的续接设置，旧客户端也不能完整表达新设置。仅给新字段默认值不足以保证混用版本时的读写正确性。
- Host 已有独立数据库最低兼容版本、逐版本迁移事务及升级前备份；SQLite 备份会重新只读连接并核对表数量与字段摘要，但明确不包含 Conversation 或附件文件。

### 已确认的升级边界

1. M0 将开发构建软件版本及 Desktop/Client ↔ Host 应用协议最低兼容软件版本统一为 `0.29.0`，沿用现有双向兼容检查拒绝旧客户端/Host 混用，避免新增设置被静默忽略或覆盖。Host ↔ Center 的企业协议版本不因此自动改变，留在 M2 核查。
2. 新增 `0.29.0` Host 数据迁移，在既有 `providers` 表增加连接级启用开关（旧记录默认关闭）和能力覆盖（旧记录默认使用服务商判断）。使用现有迁移账本，不创建第二份连接或续接表；数据库最低兼容 Host 提升至 `0.29.0`，防止旧 Host 处理新消息状态或修改已升级配置。
3. 既有规范消息保持原样；续接凭据仅随新完成的 Assistant 消息写入。旧会话首次使用时从本地有效上下文建立新链；工具交换仍遵守现有 pending/complete 可靠提交和恢复顺序。
4. 数据迁移、账本及最低版本更新在同一版本事务中提交；失败则回滚该版本。已有数据升级前复用现有已验证备份流程；本轮开发验证仅创建 `.runtime-test/` 下的一次性隔离环境，不启动指向用户 Runtime Home 的新版 Host。
5. 不提供原地降级迁移。新版本写入会话以后，不能仅恢复 SQLite 或替换旧二进制就宣称恢复完成。若实际部署需要回退，须在升级前停止 Host，另行备份并核验同一时点的完整 Runtime Home；恢复时同时处理数据库、消息及附件，升级后的新增数据需要单独保留。实施前仍按实际环境取得数据操作授权。

2026-09-28 用户已确认本节应用/数据库兼容下限及回退限制，M0 按该边界完成实现与隔离验证；不得把本节约定或隔离结果当作已经升级用户环境，或完成完整 Runtime Home 回退验证。

### M0 实现落点

连接开关、能力覆盖及内部启用周期绑定共同保存到 `providers`，默认关闭；关闭清除绑定，再开启换新，正常重启保留。主会话 owner 与该绑定交给 Responses Adapter，后台调用与 M0 子任务保持无状态，子任务独立续接属于 M1。Adapter 的不透明消息状态记录响应 ID、请求位置以及完整历史/参数和 Assistant 内容摘要；校验通过才发送增量。完整 SSE 校验产生的是候选，既有消息提交仍是续接和工具执行门禁。

默认能力使用当前官方接口身份；百炼当前 `/compatible-mode/v1` 路径参考[创建响应官方文档](https://www.alibabacloud.com/help/zh/model-studio/qwen-api-via-openai-responses)。停止维护的旧路径与其他自定义接口需显式声明支持；真实服务可用性留待 M3 验证。

## 七、M1 实现边界

模型切换仅凭当前路由无法识别 A→B→A，因此在现有 `sessions` 增加内部续接周期绑定，与显式选择原子保存；默认模型变化时，与全局选择同事务更新跟随默认的会话绑定。固定参数变更/重置及会话 reasoning effort 变化，也与相应设置原子更新受影响会话的周期；同值设置不换新，正常恢复保留；不新增会话表或业务日志。压缩使用现有可靠正文 generation，提交后按新 generation 派生冻结服务，失败压缩不换代。未发布的 `0.29.0` 迁移统一包含该字段，不为 M0 临时形态建立兼容迁移。

全局生成参数通过 `reload_config` 接纳时，先原子更新全部会话的持久周期，再发布新配置；失效写入失败则不发布。初次装载与同值 reload 保留周期，普通 Host 重启可以继续恢复。无效配置仍阻止新 Run 的模型装配，仅在内存保留最后已接纳的非敏感生成参数用于下一次比较，不保留旧可执行配置；因此经过无效配置的参数 A→B→A 也不会漏掉失效。该路径复用会话字段，不增加配置或续接表。

每个子任务用自身 ID 和正文 generation 构造独立服务，继续复用现有 Journal、工具落账与预算；后台摘要、标题、识图和连接验证仍无状态。Runtime 的模型装饰器只接纳建流前明确历史失效，要求 Adapter 用同一完整本地请求重建一次；恢复额度在同一 Run/child 的压缩 continuation 中共享，不从流式事件猜测预算，不重执行历史工具。

结构化允许列表仅接受 `previous_response_not_found`、`invalid_request_error` 与 `param=previous_response_id` 同时匹配且本次实际发送了旧 ID 的 HTTP 400/404。该错误语义参考 [OpenAI 官方 WebSocket 文档](https://developers.openai.com/api/docs/guides/websocket-mode)；HTTP 与其他服务商的真实路由行为仍须 M3 核验，不推导其他错误码，也不将普通 400/404、认证、超时或流内错误归为历史失效。

## 八、M2 企业接入与兼容处理（已确认）

### 现有入口与必要变化

入口核查时，企业连接由 Center 的 `ModelsService` 经 TypeORM 读取 PostgreSQL `public.providers.connection` 和秘密 `api_key`；默认选择读取 `public.model_settings`，固定值读取 `public.model_fixed_configs`。当时 `runtime/model-configuration` 只下发代理地址、模型和参数；Host 将其编译为只读外部配置，续接强制关闭。当时代理在 `ModelsService.admit` 内重新验证当前 LLM key 身份、默认模型与协议，但不知道 Run 冻结的上游配置。

仅比较代理 URL 或当前配置摘要不能识别上游地址/密钥 A→B→A、关闭再开启或默认模型切回。需要复用现有 Provider 记录保存内部启用周期；Runtime/Adapter 消费该周期的用户绑定投影，Center 在转发前比较冻结绑定与当前权威配置。不增加响应 ID、会话或 Token 表，不让代理维护第二套历史。

### 配置与转发闭环

1. Admin 现有连接表单增加默认关闭的续接开关和能力覆盖。按真实上游连接判定能力；只允许有效 Responses 接口且明确支持时启用。Host 下发后的代理地址不能替代真实上游能力判断，企业普通用户继续只读。
2. Center 保存内部随机周期，连接的执行属性、凭据、策略变化时换新；关闭清除，再开启换新。默认模型切换及生效参数变化也在现有身份串行段和数据库事务中换新受影响的 Provider 周期，包括 A→B→A 无中间调用。同值设置、未影响生效参数的刷新、同一用户重新登录与普通重启保持周期。模板 reload 的失效写入先于快照发布，失败不发布。
3. Center 下发启用策略、真实上游能力及不透明配置绑定。绑定由内部周期、中心/用户主体、Provider 实例、模型、协议与生效参数派生；不包含登录 Token、抓取时间或可读取的上游秘密。Host 将绑定接入现有 `ExternalModelConfiguration`/Provider 周期，主会话与 child 的 owner 仍由 Runtime 派生；后台调用继续无状态。
4. Host 的 Center transport 随冻结配置发送私有绑定请求头，授权头仍使用当前登录凭据。Center 在现有准入段检查实际用户、策略和绑定；头仅供中心校验，不转发上游。原始请求 Buffer 保持不变，扩展现有准入字段解析来校验 `store`、`previous_response_id` 的类型与重复键。无状态请求显式 `store=false`；保存或续接请求必须在管理员启用时带有效绑定。管理员连接测试始终无状态。失效返回既有中心控制错误，Host 刷新配置并提示重试，不冒充服务商历史失效或自动重放工具。

### 已确认的升级边界

- **数据库**：新增 `005-server-history.sql`，沿用唯一 `pgmigrations` 账本与升级事务，不修改已发布的 001—004。在 `public.providers` 增加可空内部周期，并给旧连接 JSON 补默认关闭和空能力覆盖；保留原凭据、目录、固定参数、默认引用和调用记录。已有数据升级前仍须按数据库规则停写、独立备份并实际恢复核验，再使用现有 SQL 升级事务执行，不能把本次开发授权视为实际用户库升级授权。
- **企业协议**：Host ↔ Center 协议及最低版本统一为 **2**。新增的策略/绑定下发和代理请求准入是明确契约，旧 Host/Center 混用在登录或配置加载时拒绝；不默默忽略管理员开关，不加入旧协议降级路径。软件 `0.29.0` 与企业协议 2 是两个独立边界；Center/Admin 自身软件版本不机械改为 `0.29.0`。
- **Admin 契约**：新连接策略字段为必需写入字段，由 Swagger 生成 OpenAPI 和 Admin SDK。旧缓存页面缺少字段时拒绝保存，需刷新使用配套 Admin；不得把缺失字段默认解释为关闭并覆盖已启用策略。中心部署携带匹配的 Admin 静态资源。
- **部署与回退**：实际部署前停止旧 Center、备份并核验 PostgreSQL 与需保留的文件存储，升级账本后启动新 Center/Admin，再使用 `0.29.0` Host；升级期间企业用户可能暂时无法登录或调用模型。旧 Center 会因更新的迁移账本拒绝启动；不提供原地降级。需要回退时停写并恢复匹配的数据库及文件备份，升级后的新增数据另行保留。
- **本轮实施环境**：本轮只新建 `.runtime-test/` 下的一次性隔离场景，先核对 PostgreSQL 主机、端口、库、角色及上述实际读取表，再实施迁移和 HTTP/Host 联调；不升级用户 Runtime Home、现有中心或共享数据库。

## 九、M2 联调缺陷修正：MCP 目录可靠上下文（2026-09-29 用户确认）

本节取代 v0.23.0 每 Run 临时注入且不落账的目录方案。该方案导致本地历史与实际请求不一致，
使 F06 的可靠前缀校验退回全量；不能通过放宽 Adapter 校验解决。

- 复用 Session 控制队列和 `McpRefresh`：显式刷新将结果与当前权限过滤后的完整 Server 目录写入
  同一条 user-role 消息，不创建或触发 Run；空目录也明确写入，失败结果不伪造刷新成功。
- 默认目录首次随实际领取的用户输入持久化；后续普通轮次沿用已有目录，不逐轮追加。手选 MCP 的
  有界工具披露随该输入持久化，仍保持当前 Run 的网关作用域；重试不改写已提交输入。
- 自动、手动和 child 压缩在候选中恢复目录。自动/child 使用该执行冻结的目录，手动使用当前目录；
  已保留相同内容时不重复。缺失或变化时在压缩点后的有效上下文末尾写入隐藏 user 消息，与新摘要
  同一次 generation 提交。保留的旧消息必须原样，恢复消息必须有新的身份，补入后仍须严格缩小。
- child 首次披露随自身输入落账；同执行内的 continuation 直接读取 Journal。Shell 环境的同类
  临时补入同步收敛为首次落账与压缩恢复，避免它继续破坏 MCP 场景的接续。
- 复用既有 InternalContext、控制消息和 replacement 操作，不增加数据库表、配置或协议字段；
  不批量改写旧历史。旧续接前缀不匹配时保持原有完整重建，之后以新的可靠历史续接。

回归覆盖刷新不调用模型、首轮及后续请求与持久历史一致、重复刷新幂等、目录删除后的空结果、
手选/child、压缩后的可靠恢复及下一轮不重复注入。该修正归入当前 M2 联调收尾，M3 不自动启动。

## 十、企业中心桥接 Responses WebSocket（2026-09-29 已确认）

### 10.1 目标与实施位置

目标是减少 Host → Center、Center → 上游两段请求重复携带的历史正文，降低上传耗时。保留本地完整有效上下文、HTTP 客户端和既有工具可靠提交；不承诺减少模型计算 Token 或首 Token 时间。

推荐链路：

```text
EZ Host ── HTTP Responses / SSE ── 企业中心 ── Responses WebSocket ── 上游
             首次全量                         首次全量建链
             后续 ID + 增量                   复用同一连接，ID + 增量
```

上游可以是直接开放该协议的服务，也可以是已启用 WebSocket 凭据的 CLIProxyAPI。Center 不接管 Codex 登录、OAuth 刷新或账号池；只有 HTTP 入口的代理不能靠 Center 单方面变成支持 WebSocket 的服务。个人直连仍按原 HTTP 方案，本提案不为 Desktop/Host 新增 WebSocket 模型客户端。

桥接也可以实现于 CLIProxyAPI，但本稿选择企业中心，便于统一企业身份、配置冻结、调用记录和错误恢复，不维护第三方分叉。CLIProxyAPI 核查版本明确要求下游为 WebSocket 且凭据启用 WebSocket，HTTP 下游走原 HTTP 执行器；源码能说明现状，不能据此断言作者未做桥接的动机。

### 10.2 能力与连接状态分开判断

连接策略回答“这个入口能否接续”，连接状态回答“当前链还能否使用”。上游 `store:false`、首次建连、断线均不能单独作为能力不支持的证据。HTTP 原生保存与 WebSocket 连接内接续是两种实现方式。

| 已知条件 | 本次行为 | 能力是否降为不支持 |
| --- | --- | --- |
| 明确不支持接续，配置为普通 HTTP | Host 每次发送完整有效上下文，Center 沿用 HTTP 转发 | 是，来自该路由能力/配置 |
| 能力未知 | 默认不启用接续；管理员核实实际入口后配置 | 不冒充已支持或明确不支持 |
| 已配置 WebSocket 接续，无旧 ID | 本次直接以全量上下文建连并生成，无须先制造一次失败 | 否 |
| 已配置 WebSocket 接续，有有效连接和链头 | HTTP 增量转换为同一连接上的 WebSocket 增量 | 否 |
| 旧 ID 对应连接已断开、回收或随 Center 重启消失 | 在生成前报告历史失效，Host 最多全量重建一次 | 否 |
| 上游明确拒绝所选 WebSocket/续接能力 | 报告该路由不支持；管理员纠正能力/传输配置 | 是，但不能归类为旧 ID 过期 |
| 认证、限流、网络超时、普通 400/404 或握手暂时失败 | 保持原错误分类，不全量重发、不修改能力 | 否 |

握手成功仅证明传输可用；首轮生成成功也不证明增量接续已验证。真实接入验收必须包含第二次仅上传工具结果或新增输入的调用。明确不支持的判据采用已核实路由的结构化错误允许列表，不从错误文字或 HTTP 状态码泛化判断。

首版不自动根据单次运行错误永久改写管理员配置，也不让一次瞬时失败关闭全企业的接续。已知不支持的路由在配置下发阶段走全量 HTTP；运行中才发现配置误判时报告错误，修正配置后按现有刷新/重试流程恢复。若要求此场景同一 Run 自动转为全量 HTTP，需要另行补齐 Host 的有界配置恢复，不能宣称仅 Center 改动已经实现。

### 10.3 配置及既有契约的复用

- 在 Center/Admin 的现有连接配置增加 `responses_transport: http | websocket`，默认 `http`，仅 Responses 可选择。接续开关和能力覆盖仍复用现有字段；WebSocket 模式的“支持”指所选入口的连接内接续能力。界面说明“连接失效后自动用本地上下文重建”，不称为永久云端存储。
- endpoint 沿用现有基础地址及 `/responses` 路径拼接规则，WebSocket 路由转换 `http→ws`、`https→wss`；禁止自动追随重定向。不同私有后端所需的路径、认证或协议头必须单独核实，不能仅换 URL scheme 就宣布兼容。首版验收入口为标准 Responses WebSocket 及配置正确的 CLIProxyAPI。
- 传输选择加入现有配置身份与启用周期计算。改传输、上游、密钥或生效参数均使旧绑定失效，继续覆盖 A→B→A；正常登录 Token 更新不失效。
- 对 Host 下发的是 Center 对外提供的有效接续能力和原有绑定，不能直接用上游的 `store` 响应字段覆盖该能力。Host 请求中的 `store:true` 在桥接路由表示按已启用策略建立接续链；向需要 `store:false` 的上游发送 `false`，响应保留实际值。不得伪造上游已持久保存，也不提供 GET/DELETE response 等未实现能力。
- 业务消息的 response ID 与 ProviderState 沿用现有保存方式。无需新增 Host/Center 业务会话表、云端历史库、会话 ID 请求头或 Desktop 通知状态。
- 摘要、标题、识图、连接测试和关闭接续的请求仍走无状态 HTTP，不占用业务连接。首版桥接仅承接现有业务流式 Responses；不支持的桥接请求形态在准入时明确拒绝，不静默丢弃语义。

### 10.4 Center 只持有连接及响应 ID 映射

复用 `llm/proxy.ts` 的准入、记录和取消生命周期，在 `llm` 内增加专用 WebSocket 传输实现及其私有连接管理。现有 HTTP transport 是逐请求转发，不能持有跨请求的 socket，因此需要这份内存资源状态；不抽象成通用会话服务。

每次无 `previous_response_id` 的全量业务请求创建独立连接。不能按现有 history binding 直接共用 socket：该绑定覆盖用户、Provider 和模型配置，同一用户多个会话/child 仍可能相同。

每条连接只保存认证主体、冻结绑定、上游连接、最新完整响应 ID、在途标记和回收时间，不保存第二份消息历史。Center 向 Host 返回随机不透明响应 ID，内存映射到该连接的真实上游 ID；所有响应事件中的响应标识与 `previous_response_id` 引用一致转换，工具 `call_id`、输出 item ID、工具参数和正文保持不变。

处理增量时先校验登录、权限和配置，再按“主体 + 冻结绑定 + 不透明 ID”找链。不同主体不能靠猜测 ID 访问连接；未知或不属于当前主体的 ID 对外统一不可用，不泄露连接存在性。只接受最新完整链头；旧头、复制 ID 或过期头不创建分叉，交本地全量重建。

同一连接一次只允许一个请求；占用冲突返回独立的 busy 错误，不误报历史失效。不同业务链可并发。首次请求失败、取消、流中断、交付失败或结果不明均销毁该连接及映射；下一次明确报告旧链不可用，不把可能已生成的请求在本次调用中自动重放。只有完整成功终态可发布下一链头，失败响应不能续接。

连接由 Center 服务生命周期持有，HTTP 响应结束后保留空闲连接。设置可配置的空闲期限、每用户/全局连接数和单帧/缓冲区上限；优先回收空闲链，全部在途时拒绝新建，不驱逐正在生成的链。退出服务、用户失效、连接策略关闭或配置变化时主动关闭相关连接。部署仍为现有单实例；多实例需要另行处理连接归属，不在本稿扩展。

### 10.5 HTTP 与 WebSocket 转换及错误边界

1. 复用原鉴权、冻结配置与请求上限校验，先建立调用记录，再连接上游。普通 HTTP 路由继续保持原始 Buffer 转发。
2. 仅桥接路由解析并转换请求：添加 `type: response.create`，按 WebSocket 协议处理 HTTP 专用字段，替换映射后的旧 ID，并按该上游要求设置 `store`；其他模型参数、instructions、工具和 input 不改变。不把 HTTP body 连同不适用字段直接塞入 WebSocket。
3. 首轮发送完整 input；后续仅发送 Host 传来的增量，Center 不私下补全整段历史。当前指令、工具定义和生成参数仍按协议发送，不承诺整个请求只有新增消息。
4. WebSocket JSON 事件按顺序转换为现有 SSE 事件流，保留模型语义并完成响应 ID 映射。增量文本及时转发；慢客户端触发有界背压，超限/超时中止，不无限聚合完整响应。
5. 在交付首个 SSE 事件之前，如果本地已经确定无有效链，返回 HTTP 400，错误体精确为 `code=previous_response_not_found`、`type=invalid_request_error`、`param=previous_response_id`。Center 生成的响应带现有控制标记；当前 Host 对未知控制码会交回 Responses Adapter，Adapter 已识别这个组合。需要用当前正式 Host 验证该路径，不能只测 Center JSON。
6. 上游在生成前明确拒绝旧 ID 时可转换为同一历史失效错误。已经开始生成或交付事件后，不再把流内失败包装为可自动重建的 HTTP 错误；断开并按既有失败流程处理。网络断线不能直接伪装成旧 ID 失效来重发当前请求。
7. 复用 Runtime 的同一 Run 最多一次全量恢复额度；沿用当前预算及已落账工具结果，不重执行历史工具。Center 自身不做隐藏的生成重试，不与 Host 重试叠加。

Center 不把 `store:false` 改成 `true`。在该桥接路由中，接续根据 Center 下发的能力、绑定及有效 ID 判断；现有 Adapter 不以 `store:false` 一概禁用的行为可以复用，但不能据此反推普通 HTTP 路由也支持。原先错误配置为支持的 CLIProxyAPI HTTP 路由需要纠正，不能继续将其当作 HTTP 原生存储服务。

### 10.6 重启、压缩与审计

Host 重启后仍恢复本地 ProviderState：Center 连接尚有效就增量，否则按明确历史失效全量重建。**Center 重启必然丢失桥接连接**，但不改写持久配置绑定；旧 ID 的下一次调用触发一次重建。这是本提案对原“重启后继续旧 ID”承诺的明确限定，HTTP 原生保存路由仍沿用原约定。

压缩成功、模型/上下文变化后，Host 已有机制发出不带旧 ID 的完整有效上下文；Center 建立新连接。由于客户端不发送被替换链的 ID，旧连接按空闲期限回收，不能为了立即清理而按用户/模型关闭其他会话的链。压缩失败保留旧上下文和连接。

调用详情的请求/响应快照继续表示 Host ↔ Center 的实际 HTTP 内容；桥接后不得标为上游原始字节。沿用既有采集限制和用量解析，用量仍来自上游。验收分别观察两段真实请求字节数、首次建连耗时、复用请求耗时和失效重建次数；用测试传输捕获与现有日志即可，不为性能验收新增历史库或独立监控平台。

### 10.7 兼容、边界调整与实施顺序

本节已确认的基线调整：允许 Center 增加 WebSocket 模型传输及易失连接映射；桥接请求/响应允许协议转换；接续能力不再只指持久化 `store:true`；Center 重启的桥接链需要重建。本地会话权威、Host HTTP 接口、工具可靠提交及 MCP 修正保持原设计。

### 10.10 M2 补充二：生命周期与实际应用联调（完成结果待确认）

2026-09-30 用户确认当前增量手工验证并要求继续。沿用 IdentityService 的事务串行边界：模型写入仅收集受影响服务商，数据库提交后同步发布失效；回滚不发布，同值保存不换代。ModelProxy 订阅配置和主体失效，取消该范围内在途桥接并释放 socket/响应映射；准入等待期间先登记候选，防止撤销后继续建连。普通 HTTP 请求继续原取消语义。

连接所有权记录 provider ID 仅用于资源回收，不保存第二套配置或历史。用户停用/角色变化及事务结果不明沿用现有凭据撤销，同时清理对应连接；同主体退出后重新登录不换绑定、不主动清链，旧凭据立即失效。订阅由 ModelProxy 生命周期解除。

新增启动变量约束空闲期限、全局/每用户连接数及帧/缓冲字节上限，范围和默认值见 [Center README](../../../../../apps/enterprise-center/README.md#responses-websocket-接续)。达到容量先回收空闲链，全部忙碌则拒绝新建；背压等待仍受取消和空闲超时约束。压缩产生新链，旧链按空闲规则回收，不影响该用户其他业务链。
