## 二、台账与实施原则

1. 按 M0—M7 顺序实施。本计划获得确认后只开始 M0；每个里程碑完成实现与
   最小有效验证后标记为 `🟨 待确认`，获得用户确认后才进入下一里程碑。
2. 开始 M0 前将 [`版本管理`](../../版本管理.md) 从 `计划中` 更新为 `开发中`；
   计划整体确认不等于授权连续实施后续里程碑。
3. Runtime 始终是 WorkPlan、Goal、Input/Run ·调度、预算与持久化事实的唯一业务权威者；
   Host 只实现存储和传输 Adapter，Desktop 只提交意图和展示快照。
4. `agent-core` 仍只处理单次 `AgentExecution`；不向 Core、Provider Adapter 或 Desktop 下沉
   Goal 状态机，不引入 Judge、第二模型或独立 Worker。
5. Conversation 历史只追加。新老 UserMessage、Input 和 SQLite 数据必须兼容读取；
   不就地重写用户旧 Conversation，不从旧文本猜测 WorkPlan 或 Goal。
6. 数据库 schema、迁移和恢复验证只使用测试 fixture 与隔离临时 Runtime Home；
   本计划不授权读写或迁移用户实际 Runtime Home。若需对真实用户库执行任何迁移验证，
   必须另行核对目标、备份并在写入前取得明确确认。
7. 所有竞态用例都必须核对持久事实，不仅断言内存状态或 UI 展示；故障注入不得执行历史工具副作用。
8. 真实 Provider 测试保持 `#[ignore]`，只读复用当前配置凭据，不输出 credential、
   objective 全文、reasoning、完整 response ID 或私有附件路径。
9. 不主动执行 Git commit/push；每个里程碑开始前重新核对工作树、授权、
   对应语言规范与模块约束。

## 四、里程碑明细

### M0：规范消息来源与产品投影

前置依赖：本开发计划已确认；版本状态已更新为 `开发中`。

目标：先建立 Runtime 来源与转录可见性的规范语义，让后续 Goal continuation 有可依赖的
消息、持久化和产品投影边界。

交付范围：

- 为 `UserMessage` 增加具有旧数据安全缺省的 origin 和 transcript visibility，
  统一新消息构造与反序列化验证；
- Chat/Responses 保持现有 `user` wire 形状，不泄漏应用元数据；
- 统一过滤分页、Around Message、导出、附件投影、display offset、FTS、Recall、
  标题和用户输入统计，raw Conversation 与 Context Layout 仍保留隐藏消息；
- 覆盖 compaction replacement、旧 fixture 和只追加历史约束。

验证入口：

```bash
cargo test -p agent-types
cargo test -p agent-context
cargo test -p agent-openai-compatible
cargo test -p assistant-runtime
cargo test -p assistant-runtime-host
cargo clippy -p agent-types -p agent-context -p agent-openai-compatible \
  -p assistant-runtime -p assistant-runtime-host --all-targets --all-features -- -D warnings
```

完成判定：旧 UserMessage 无需重写即可读取；Runtime hidden UserMessage 会进入模型上下文与审计，
但不出现在任何用户转录、搜索、标题或导出路径中；不增加 Provider role。

Review 重点：默认值是否破坏旧 JSONL，产品投影是否存在遗漏入口，模型上下文是否误过滤 hidden message。

### M1：Session WorkPlan 闭环

前置依赖：M0 已确认。

目标：在不依赖 Goal 的情况下，形成 Session 总体目标与 Todo 的持久领域闭环。

交付范围：

- 建立跨层稳定 `TodoItemId`，实现 WorkPlan 不变量、revision、完整替换 CAS、
  ToolCallId 幂等和清空语义；
- 在父 Agent 的 Runtime 派生工具中提供 `update_plan`，child Agent 不获得该工具；
- 建立临时库迁移、正式 Host Store、Volatile Store、重启恢复、Fork 独立副本与 Session 删除；
- 在新父 Run 领取时冻结 WorkPlan Injected Part，不回写已有消息。

验证入口：

```bash
cargo test -p assistant-protocol
cargo test -p assistant-runtime
cargo test -p assistant-runtime-host
cargo run -p assistant-protocol --example export_typescript -- --check
cargo clippy -p assistant-protocol -p assistant-runtime -p assistant-runtime-host \
  --all-targets --all-features -- -D warnings
```

另用隔离临时 Runtime Home 验证旧 schema 迁移、CAS conflict、重复 ToolCallId、重启、Fork、
删除和旧 Session 空状态恢复。

完成判定：未开启 Goal 的 Session 也能持久建立工作计划；新 Run 获得当时最新冻结计划；
重启、Fork 与清空不会与 Goal 事实耦合。

Review 重点：完整替换是否误删 item，CAS 与幂等是否能阻止旧工具结果覆盖新状态，
WorkPlan 是否被错误实现成 Goal 子对象。

### M2：Goal 领域与 Agent 终止信号

前置依赖：M1 已确认。

目标：建立不依赖第二模型的 Goal 权威领域，并让 Agent 只能通过当前 Run 的结构化信号
报告 complete 或 blocked。

交付范围：

- 建立跨层稳定 GoalId，实现 objective 不可变恢复快照与 hash、Running/Paused/Completed、pause reason、
  generation、turn 与冻结预算；
- 建立 Goal 正式/临时 Store 持久化及旧 Session 空状态兼容；
- 实现父 Agent Runtime 派生 `update_goal` 工具和每 Run signal latch，
  拒绝混合工具批次、重复信号与信号后副作用；
- 证明 latch 只是 Run 内存事实，模型流、Recorder、取消或进程失败时不提前转换 Goal。

验证入口：

```bash
cargo test -p assistant-protocol
cargo test -p assistant-runtime
cargo test -p assistant-runtime-host
cargo test -p agent-core
cargo test -p agent-tools -p agent-testkit
cargo run -p assistant-protocol --example export_typescript -- --check
cargo clippy -p agent-tools -p agent-testkit -p agent-core -p assistant-protocol \
  -p assistant-runtime -p assistant-runtime-host \
  --all-targets --all-features -- -D warnings
```

完成判定：只有匹配 GoalId/generation/RunId 的单独结构化信号可被 latch 接受；
Todo 状态、final answer 文本或工具证据都不被 Runtime 用来猜测 Goal 完成。

Review 重点：Tool signal 是否提前持久终态，侧效工具是否可以越过 latch，objective 恢复副本是否成为可编辑第二权威。

### M3：Goal Input 通道与首次启动

前置依赖：M2 已确认。

目标：让首次 `/goal` 从用户输入幂等建立 Goal-bound Run，并从调度层区分用户队列与
Runtime continuation 通道。

交付范围：

- 为 StoredInput 增加 origin 与可选 Goal binding，校验其与 UserMessage 来源/可见性组合；
- 为 `SubmitInputRequest` 增加有缺省的 normal/start_goal/resume_goal 提交意图，
  同步协议生产者、消费者与 TypeScript 导出；在一次接受中构造可见用户消息、
  Goal Injected Part、objective 快照、Goal、Input 和首次 Run；
- 将 Session 内部队列分为 user_inputs 与最多一条 goal_inputs，Goal Running 时只自动领取匹配 generation 的后者；
- 对已存在 Goal、幂等重试、不支持 Tool Call 的模型和非法持久行 fail-closed。

验证入口：

```bash
cargo test -p assistant-protocol
cargo test -p assistant-runtime
cargo test -p assistant-runtime-host
cargo test -p agent-openai-compatible
cargo run -p assistant-protocol --example export_typescript -- --check
cargo clippy -p assistant-protocol -p assistant-runtime -p assistant-runtime-host -p agent-openai-compatible \
  --all-targets --all-features -- -D warnings
cd apps/desktop
npm run build
```

完成判定：同一幂等 key 只产生一个 Goal/Input/Run；首次消息对用户可见且完整保留附件；
Runtime continuation 只有 Injected Part 且不进入用户 Queue；Goal Running 时普通用户输入可持久但不被自动执行。

Review 重点：origin 与 binding 是否被误合并，用户输入是否可被 Goal 意外消费，
`/goal` 字面量或 Runtime 内部说明是否泄漏为用户正文。

### M4：原子续跑、停止与恢复

前置依赖：M3 已确认。

目标：建立跨业务 Run 的可崩溃恢复续跑链，使 Run 结算、Goal 转换、预算和下一轮创建没有半状态。

交付范围：

- 实现 GoalSettlementEffect，在同一 Store 操作中结算 Run、CAS Goal、扣减预算并
  Complete/Pause 或插入下一条 Runtime Input/Run；
- 实现 Stop/Resume/Clear、generation fencing、取消意图、held input 显式绑定与终态后 `resume_required`；
- 覆盖 Run/token/连续失败预算、usage unknown、普通 Retry 隔离和迟到 signal/continuation；
- 实现重启 `Paused(RecoveryRequired)`、compaction objective 恢复、Fork `Paused(Forked)`、
  历史重入与 Session 删除语义；
- 对 staged append、SQLite 事务和内存投影边界做逐点故障注入。

验证入口：

```bash
cargo test -p assistant-runtime
cargo test -p assistant-runtime-host
cargo clippy -p assistant-runtime -p assistant-runtime-host \
  --all-targets --all-features -- -D warnings
```

另用隔离临时 Runtime Home 精确核对故障注入后的 SQLite 行、JSONL generation、Goal generation、
Input 来源、Run 状态和孤立 continuation。

完成判定：不存在“Run 已完成但无后继”或“预算未扣但后继已入队”；
停止、重启、Fork 和迟到回调都无法越过 generation 重启 Goal；恢复必须是显式意图。

Review 重点：JSONL 与 SQLite 是否真的形成无半状态提交，事务失败是否 fail-closed，
恢复是否会重放历史工具副作用。

### M5：应用协议与正式 Host 闭环

前置依赖：M4 已确认。

目标：通过轻量 `assistant-protocol` 向 Desktop 提供完整、可恢复的 WorkPlan/Goal 投影与用户意图。

交付范围：

- 复用 M1/M2 已建立的稳定 ID 与 M3 提交 mode，增加 WorkPlan/Goal/Composer capability/held queue 快照 DTO、
  其余命令、事件与稳定错误；
- 更新 SessionView、HTTP Command、SSE 失效提示、Runtime Client 与 TypeScript 导出；
- Host 保持传输/存储 Adapter 边界，不复制 Goal 状态机；未知事件和 sequence gap 继续让快照 stale；
- 正式 Host 离线端到端覆盖 WorkPlan 更新、至少三次 continuation、blocked/resume、Stop 与重启。

验证入口：

```bash
cargo test -p assistant-protocol
cargo test -p assistant-runtime
cargo test -p assistant-runtime-host
cargo run -p assistant-protocol --example export_typescript -- --check
cargo clippy -p assistant-protocol -p assistant-runtime -p assistant-runtime-host \
  --all-targets --all-features -- -D warnings
```

完成判定：Desktop 所需事实都能从 SessionView 恢复；命令只表达 start/stop/resume/clear/
clear plan 等用户意图；内部 objective payload、Injected Part、SQLite 结构与 Provider 内容不进入协议。

Review 重点：协议是否泄漏 Runtime 实现，Host 是否产生第二份权威状态，
TypeScript 生成物和所有生产者/消费者是否同步。

### M6：Composer 交互重组

前置依赖：M5 已确认。

目标：依据交互指导落地 Todo/Goal 长任务状态与五项 Composer 底栏，在不隐藏安全事实的前提下降低密度。

交付范围：

- Desktop projection/store/controller 接入 WorkPlan/Goal 快照和 clear/stop/resume 意图，不本地推导权威转换；
- 实现 `/goal` 一次性标签、仅 `×` 取消、失败草稿保留和模型能力门禁；
- 按 Todo floating summary、Goal row、Approval Restore、Queue、Approval/Input 顺序重组 Composer；
- 实现执行设置与模型设置的分类级联、键盘导航、边界翻转、焦点返回和单前台浮层；
- 把 image handling 投影到 Context Panel，底栏仅保留添加、执行设置、上下文用量、模型设置、发送/停止；
- 补充 DeepSeek `deepseek-v4-flash-vision-exp` 的官方精确能力路由：Chat 原生附件与
  聚合工具图片、Responses 原生附件与 function output 图片；
- 补齐工作空间行的假删入口、二次确认与 Runtime 命令链；移除后隐藏分组和关联会话，
  重新添加同一目录时恢复原 Workspace ID 与会话，不额外创建空会话；
- 覆盖长模型名、`720px` 及更窄宽度、浮层滚动、reduced motion、ARIA 和 macOS `WKWebView`。

验证入口：

```bash
cd apps/desktop
npm run lint
npm run test
npm run build
npm run test:e2e
```

完成判定：所有 Runtime 状态都可从快照恢复；Todo 不占布局高度，Goal/Approval/Queue 层级符合已确认顺序；
底栏标准宽度只有五个常驻项；窄宽度无水平滚动，主操作和 Ask/Auto 状态可见。

Review 重点：Goal 标签是否会被 Esc 误取消，hover 是否误展开 Goal，Approval 与 Queue 是否被错误互斥，
级联是否隐藏权限事实或把 model/effort 建成依赖组合。

### M7：跨层回归与验收准备

前置依赖：M6 已确认。

目标：在不扩大版本范围的前提下完成跨层回归、真实链路和版本验收前的可复查证据。

交付范围：

- 汇总旧 Conversation/Input/Session 兼容、只追加历史、上下文压缩、队列、审批、权限、取消、
  Recall、附件、Fork、重启和删除回归；
- 通过正式 Host + fake Provider 完成可重复的跨 Run Goal 场景，核对事件、SQLite、JSONL 与 Desktop 投影；
- 在用户已配置且明确同意产生请求时，执行至少一条支持 Tool Call 模型的真实 Goal 自动续跑链；
- 补齐模块约束、协议文档和必要的中文注释，不在本里程碑顺手新增功能。

验证入口：

```bash
cargo fmt --all --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace
cd apps/desktop
npm run lint
npm run test
npm run build
npm run test:e2e
npm run tauri -- build --no-bundle
```

完成判定：功能设计验收项全部具有可定位的自动化或人工证据；真实链路能在无 Judge 情况下
至少跨一次 Run 自动续跑并可靠结束；所有未执行项、实际偏差与风险明确记录。

实际结果（2026-08-22）：workspace Rust fmt、全 targets/features Clippy `-D warnings` 与测试门禁，
Desktop lint、106 项单测、生产构建、正式临时 Host Playwright E2E，以及 Tauri release
`--no-bundle` 构建全部通过。正式 Host + fake Provider 场景完成四 Run Goal、WorkPlan 更新、
blocked/resume、Stop/cancel 和重启恢复，并只读核对 SQLite、当前 JSONL 与产品 Conversation 投影。
经用户明确授权后，默认 ignored 的正式 Host 真实 Provider 用例在隔离 Runtime Home 中通过：模型先
调用 `update_plan`，Runtime 至少跨一个业务 Run 自动续跑，再独占调用 `update_goal complete` 并清除
Goal；测试未观察到 Judge 工具，也未在 Host 输出中发现 access token、模型 credential 或目标正文。
版本验收仍需明确记录 100%/125%/150% 缩放、中文输入法和高 DPI 以人工检视为主，以及 Vite
既有 chunk size 非阻断警告。

Review 重点：真实 Provider 证据是否使用正式 Host 而非私有 demo，故障恢复是否触发历史副作用，
验收是否混淆数据库、文件、内存、协议与 UI 展示状态。

## 五、版本级完成条件

1. M0—M7 全部完成实现、最小有效验证并逐个获得用户确认。
2. WorkPlan 与 Goal 在领域、存储、协议和 UI 上保持独立，非 Goal 会话也可使用 Todo。
3. Goal 能从完整用户 UserMessage 启动，通过 Runtime hidden `user` 消息受控续跑，
   并由 Agent 的 complete/blocked 信号或 Runtime 预算/取消门禁可靠收敛。
4. 持久化、幂等、只追加、generation fencing、原子结算、重启、Fork、压缩和队列隔离均通过故障注入或端到端验证。
5. Desktop 完成已确认的 Composer 重组，安全状态、主操作、键盘交互和窄宽度均可用。
6. workspace Rust 门禁、Desktop lint/test/build/e2e、Tauri no-bundle 构建与至少一条真实跨 Run Goal 链路形成实际结果。
7. 全部里程碑确认后才把版本状态推进到 `验证中`，单独创建验收记录并开始版本级验收。
