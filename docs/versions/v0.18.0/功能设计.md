## 二、背景与问题

### 2.1 单个 Run 完成不等于用户目标完成

现有 Runtime 已具备持久 Input、同 Session 串行队列、Run 取消、上下文压缩续接、
执行预算、重启恢复和 Desktop 队列交互。这些能力可以让一条用户输入可靠完成
一次 Run，但 Runtime 还没有持有“用户的持续目标是否已完成”这个业务事实。

对于需要多轮核查、修改和验证的宽泛目标，模型可能在一次 Run 后只完成部分工作、
被输出上限截断，或得出需要用户决策才能继续的结论。这些情形需要 Runtime 层
的持久目标、完成报告和受控续跑，不应通过改变 Agent Core 的“无 Tool Call 即结束”
语义隐式实现。

### 2.2 Todo 缺少会话级权威状态

当前子任务、会话队列和 Run 都有可观察状态，但模型对宽泛目标做出的工作分解
没有可持久、可重启恢复的 Session 权威载体。只在对话正文中维护文本清单，
容易因上下文压缩、模型漏读或用户重定向而失真。

### 2.3 Composer 底栏的信息层级失衡

现有 Composer 底栏同时平铺了附件、Build/Plan、Ask/Auto、reasoning effort、识图能力、
上下文用量、模型和发送入口。其中既有高频动作，也有低频设置和纯派生状态；
随着 Goal/Todo 加入，继续横向增加控件会让快速识别、窄宽度适配和安全语义都更差。

Codex 与 OpenCode 的当前布局虽不完全相同，但共同方向是：

- 底栏只保留高频添加入口、主要执行上下文、模型和发送/停止；
- 相关选项在一个入口内分组，不把每个字段都做成常驻标签；
- Todo 以 Composer 顶边悬浮摘要承载，Goal 使用其下方的独立状态行；收起的待审批入口和
  Queue 按顺序放在输入框上方，前者位于后者上方并正常占据布局高度，完整审批窗口则与输入框互斥。

## 三、版本目标与成功标准

1. 为每个 Session 提供独立、常驻、可持久的工作计划，统一包含总体目标和 Todo List；
   它在是否开启 Goal 时都可使用，但不作为 Goal objective 或 Goal 生命周期的数据源。
2. 以用户使用一次性 `/goal` 标记提交的完整 UserMessage 作为 Goal objective，
   由 Runtime 持有 Goal 控制状态并实现跨 Run 自动续跑，不把调度下沉到 Core。
3. 让完成、阻塞、预算暂停、用户停止、取消和重启恢复都有持久且可观察的语义。
4. Goal 模式不绕过现有 Plan/Build 能力上限、Ask/Auto、权限规则、审批、Guardrail 或取消。
5. Desktop 分别展示工作计划的总体目标与 Todo 进度，以及 Goal 的
   运行/等待用户/暂停投影与剩余预算；完成后对应控制 UI 自动移除，
   用户可以显式启动、停止、恢复和清除 Goal。
6. Composer 底栏将行为、执行设置、模型设置和派生状态分组，常驻视觉项从现有
   8 项收敛为至多 5 项，不牺牲当前执行和权限语义的可查看性。
7. Runtime 重启后可恢复工作计划和 Goal 控制状态，但不在无用户动作时自动执行历史 Goal。
8. 补齐工作空间行的移除入口；移除不删除本地目录或历史会话，但工作空间及其
   会话从侧栏和标题搜索隐藏；用户重新添加同一目录时恢复原 Workspace ID 与会话。

## 四、明确非目标

本版本不包含：

- 独立裁判模型、证据账本、Receipt/Ledger、完成合约或事后 Review 体系；
- 以 Todo 未全部完成为由拒绝模型的首版 `complete` 报告；
- 通过文本相似度、Todo 是否变化或疑问句检测猜测“无进展”；
- 定时任务、后台 Job、开机启动、菜单栏常驻、崩溃自动拉起或通知投递；
- Skills、MCP、插件发现与安装生命周期；
- 多层 Todo、Todo 依赖图、证据绑定、自动排期或用户在首版 Desktop 中拖拽重排；
- 模型自行开启 Goal；模型可以建议，但必须由用户显式确认；
- 输出过程中的实时 steer 或打断后保留未结算的半个工具交换；
- 重新设计整个 Desktop 信息架构、会话页或设置中心；Composer 调整仅针对
  执行入口层级、Todo 悬浮层、Goal 状态行、待审批入口与 Queue 排布及相关窄宽度适配。

## 五、Todo（Session 工作计划）产品语义

### 5.1 定位与生命周期

- 每个 Session 最多一份工作计划，由 Runtime 持有权威状态并持久化；产品界面仍可简称 Todo。
- 工作计划统一包含一个总体目标和一组有序待执行任务。它是独立于 Goal 的 Session 能力，
  不存在 Goal 专属 Todo，也不把 Goal objective 复制为计划总体目标。
- 未开启 Goal 时工作计划仍有意义：它负责表达当前任务契约、跨手动 Run 保留进度，
  并在用户下一次发消息后继续为模型提供当前目标与未完成任务。
- Goal 与工作计划是两个可独立存在的能力：开启 Goal 不要求已有工作计划，
  也不自动创建、复制或清空 Todo；模型如需分解任务，仍使用普通计划工具。
- Goal 完成、暂停或清除不直接改写工作计划；当计划存在至少一个 Todo 且所有 Todo
  在一次计划更新后均为已完成时，Runtime 自动清除整份工作计划。空 Todo 的总体目标计划
  继续保留；用户也可随时显式清空。
- Session 归档保留工作计划；Session 删除时随 Session 整体删除。

### 5.2 首版结构与修改方式

- 工作计划首版由非空总体目标和有序的单层 Todo 清单组成；不存在任务时可以只有总体目标。
- 每个 Todo 项只表达稳定文本、状态和排序。
- 状态至少区分未开始、进行中和已完成；同时最多一项为进行中。
- 无论是否开启 Goal，模型都通过同一个受控计划工具更新总体目标与 Todo，
  不通过对话文本直接改写权威状态，也不提供 Goal 专属写入接口。
- Desktop 首版提供查看、折叠和显式清空；不提供拖拽排序或复杂逐项编辑。
- 计划工具只改变 Session 内部计划状态，不代表已完成外部副作用，也不作为
  Goal 完成的强制证据。

## 六、Goal 产品语义

### 6.1 开启与权威状态

- Goal 是 Session 上独立的持久自动续跑控制器，核心差异是一次 Run 结束且
  Agent 未终止 Goal 时，Runtime 会自动启动下一次 Run。Goal 与 Todo 可以独立存在，
  不要求、不复制也不改写工作计划的总体目标或任务。
- 一个 Session 同时最多存在一个 Goal 控制器。控制器保存 objective 消息引用、
  运行/暂停状态、世代、预算消费和暂停原因；完成只作为 Run 结算的终态事实，
  结算成功后控制器立即自动清除。
- Goal 只通过 Composer 的一次性 `/goal` 指令标记开启：用户输入 `/goal` 后，
  Composer 显示 `Goal` 标签，随后输入的正文和附件作为本次 Goal objective。
  标签只能在提交前通过点击其 `×` 取消，`Esc` 不承担取消语义；提交后标记自动消费，
  不影响后续普通输入。
- Goal objective 以该次提交的原始 UserMessage 引用表示，不降级为一段复制的字符串。
  其用户载荷包含正文、附件和稳定文件引用，并排除 Runtime 在持久追加前组装的 Goal 控制说明，
  避免续跑时递归嵌套。该消息同时是 Conversation 中的普通用户输入，不从历史中移走、
  不改写成独立的 Goal 文本。
- 模型可以在普通回复中提议进入 Goal，但提议本身不改变执行模式；用户仍需在后续输入中
  手动使用 `/goal` 标记开启。
- Goal 领域转换仍区分运行中、暂停和完成；`blocked`、用户停止、预算到限、
  连续失败、重启恢复和 Fork 都作为暂停原因保存。完成转换与控制器删除在同一次
  Run 结算中原子提交，不保留可交互的 Completed 行；Desktop 可将 `blocked` 原因投影为“等待用户”。
- 自动续跑需要的预算、世代和输入门禁是 Goal 的安全配套，不改变工作计划的产品结构；
  完整持久形状由技术方案确认。

### 6.2 Agent 终止与自动续跑

- Goal 运行时向 Agent 提供 Runtime 控制的结构化终止入口，至少区分
  `complete` 和 `blocked`；总体目标和 Todo 如需调整，仍使用独立的计划工具。
- `complete` 表示 Agent 自主确认 objective 已完成，Runtime 终止自动续跑并在所属 Run
  可靠结算时自动清除 Goal 控制器；
  首版不引入独立 Judge，也不用 Todo 全部完成作为强制门禁。
- `blocked` 表示 Agent 已无法在当前授权和上下文中继续，Runtime 停止自动续跑并
  等待用户显式恢复。Runtime 不根据疑问句、Todo 变化或回复文案猜测阻塞。
- 当前 Goal Run 可靠结算后，只要 Agent 未发出 `complete` 或 `blocked`，Runtime 就在
  核对世代与预算后追加一条内部续跑输入并启动下一次 Run；不要求 Agent
  每轮额外报告“继续”。
- 普通 final answer 不自动等于 Goal 完成，否则 Agent 的阶段性收尾文案会意外终止续跑。
- Runtime 只接受当前世代且来自当前 Goal Run 的终止信号；迟到信号不得改变
  已停止、已恢复或已完成的 Goal。

### 6.3 内部消息、可见性与只追加历史

- Goal 的动态说明和续跑提示统一作为 `user` role 输入进入模型上下文，
  不创造 Provider 不支持的 `internal` role，也不改写或动态重建 Session 的冻结 System Prompt。
- 首次 Goal 提交只追加一条用户消息：Runtime 在写入 Journal 前，将可见的用户正文和附件
  与一个对模型可见、对转录隐藏的 Goal Injected Part 组装成完整 UserMessage，再一次性追加。
- 自动续跑每次追加一条 Runtime 生成的 UserMessage，其内容是冻结的 Injected Part，
  至少包含 Goal objective、当前续跑轮次、剩余预算和继续执行要求。
- 规范 UserMessage 需能区分用户真实提交与 Runtime 生成输入，并提供明确的
  transcript 可见性事实。字段命名不得把“UI 不展示”混同为“模型不可见”；
  具体类型与序列化形状由技术方案确认。
- 用户首次 Goal 消息是用户来源且转录可见；Runtime 续跑消息是 Runtime 来源且
  转录隐藏。隐藏续跑不计入真实用户轮次、用户活跃、会话标题来源或用户原话搜索结果。
- Provider Adapter 只向线上请求投影支持的 role 和内容：初始正文与 Injected Part、
  隐藏续跑 Injected Part 均编码为 `user` 内容；来源和 transcript 可见性等应用元数据
  不得发送给 Provider。
- Conversation Journal 只允许追加新消息，不为启用、续跑、暂停或完成 Goal
  改写任何历史消息。每条 Injected Part 保存实际发给模型的冻结内容，确保恢复、回放
  和 Prompt Cache 前缀不因后续 Goal 状态变化而漂移。
- 内部续跑消息是可审计的 Runtime 事实，默认不进入主消息流；需要时只在
  调试/审计入口中查看，不冒充用户气泡。

### 6.4 预算、停止与竞态

- Goal 预算跨多个 Runtime Run 累计，不替代单次 AgentExecution 的 step、tool、output 预算。
- 首版以明确的 Run/轮次、token 和连续执行失败上限作为控制器刹车，不按
  Todo 文本是否改变判定无进展。
- 用户点击停止时，Runtime 立即把 Goal 置为用户暂停、提升世代号、清除未执行的
  内部续跑，并使用现有可靠取消链路取消当前 Run。
- 取消后仍可能到达的模型报告、Run 回调或排队任务必须携带世代并在不匹配时丢弃，
  不得把已停止 Goal 改回执行中。
- “停止”默认是可恢复暂停，保留工作计划、Goal 控制状态和已消费预算；“清除 Goal”
  只移除自动续跑控制状态，不清空工作计划。
- Goal 的内部状态操作不代表对外部工具副作用的补偿或回滚；已经可靠执行的外部
  操作仍按原工具契约处理。

## 七、输入队列与恢复语义

### 7.1 普通模式

没有活动 Goal 时，保持现有行为：用户输入先持久化，再由 Session 队列自动串行消费；
用户显式暂停或重启恢复态除外。

### 7.2 Goal 执行中

- Goal 运行时只有 Runtime 内部续跑输入可被自动消费。
- 用户在 Goal 运行中发送的新消息仍先持久保存，但作为“待处理指导”留在队列中，
  不自动注入当前 Goal、不中断当前 Run，也不会被下一次内部续跑顺带消费。
- Desktop 必须对这类输入明确显示“已暂存，不会自动应用”，不得沿用普通队列的
  “下一条自动执行”暗示。

### 7.3 等待、暂停和终态

- Goal 因 `blocked` 等原因暂停或被用户暂停时，用户此时新发送的消息是一次显式恢复动作：
  该消息进入下一次 Goal Run，并由模型判断是否更新 Goal 或 Todo。
- 运行期早先暂存的用户输入不因 Goal 进入等待、暂停或完成而自动消费。
  用户可以显式选择某一条作为恢复输入，或在 Goal 终止后确认恢复普通队列。
- Goal 完成或清除后，若仍有暂存用户输入，Session 进入需要显式恢复的队列状态，
  不将可能过时的内容立即全部执行。

### 7.4 重启、Fork 与 Session 生命周期

- Runtime 重启后恢复工作计划、Goal 控制状态、预算消费和队列事实；未完成 Goal 一律以显式
  恢复态出现，不自动重启模型或工具副作用。
- Fork 复制当前工作计划快照和 Goal 控制/预算摘要为新 Session 的独立副本，新 Goal 固定以
  Fork 暂停态开始、不继承正在执行的世代，必须显式恢复。
- Session 归档保留工作计划和 Goal 控制状态，但必须满足现有空闲门禁；恢复 Session 不等于恢复 Goal。
- Session 删除时随会话整体删除工作计划和 Goal 控制状态，不建立跨 Session 共享计划或 Goal。

## 八、权限、审批与执行边界

- Goal 不是第三种 Agent 变体；Plan/Build 继续决定能力上限，Goal 只改变是否基于
  本次 Goal objective 跨 Run 自动续跑。
- Goal 不是第三种审批模式；Ask/Auto 保持原语义，明确 Deny 和必须询问的规则不被
  Goal 或历史 Allow 覆盖。
- Goal 运行到工具审批时，当前 Run 继续使用现有 pending approval 语义；
  审批不伪装成 Agent 的 `blocked` 终止信号。
- 计划工具和 Goal 终止工具只改变 Runtime 内部状态，不读写工作区、不启动 Shell，
  也不因它们是内部工具而放宽同一轮其他工具的授权。
- 用户停止 Goal 使用已有取消链路，不跳过 pending Tool Exchange 结算、child task 取消和
  approval 清理。

## 九、Desktop 产品路径

### 9.1 Todo、Goal 与 Approval/Queue 排布

- 工作计划独立于临时活动面板，锚定在 Composer 顶边最上层，以悬浮摘要展示，
  不进入正常纵向布局流，不推动输入框、Queue/Approval 或对话区。
- 工作计划悬浮摘要只展示当前步骤缩略。鼠标悬停时以覆盖层
  展开有序 Todo 和当前进行项，展开和收起不得引起页面跳动。
- 键盘聚焦与点击提供和 hover 等价的检视能力；详情是 `pointer-events: none` 的纯展示层，
  不接受焦点或鼠标交互，鼠标离开摘要区域后立即关闭。键盘焦点离开摘要或按 Esc 时关闭。
- 活动 Goal 不合并进 Todo 悬浮摘要，而是在 Composer 输入区上方显示独立的紧凑状态行，
  展示执行/等待/暂停状态、objective 摘要和预算。Goal 行不使用 hover 打开详情，
  只在用户点击或键盘激活后展开；详情设定最大高度，内容超出时在内部滚动。
- 顶部排布顺序为 Todo 悬浮摘要、Goal 状态行、收起的待审批入口、Queue 和输入区；
  Todo 不占布局高度，后三者按实际存在情况进入正常布局。
- 完整 Approval Workspace 与输入框互斥：进入审批时由完整审批窗口替换 Composer 输入区域，
  不再额外显示一个待审批入口；审批窗口收起后恢复输入框。
- 收起后若仍有待审批项，在 Queue 上方显示紧凑的待审批入口；待审批入口和 Queue 可以同时存在，
  都进入正常纵向布局并占据实际高度，不再做互斥切换。
- 完整 Approval Workspace 仍是最高优先级的阻塞交互。它打开时关闭工作计划展开层，
  但不移除最上方的悬浮摘要，也不改变工作计划、Goal 控制器或 Queue 的 Runtime 状态。
- Goal 等待用户通过 Goal 状态行的强调样式提示，不替换待审批入口或 Queue；
  是否采取继续动作仍由用户显式决定。
- Goal 执行中提供停止；等待或暂停时提供继续与退出。完成后状态行随 Runtime 快照自动移除。
  Todo 详情不提供“清空工作计划”；用户对当前计划有异议时可中断当前轮次并输入新指导。
- Runtime 内部续跑消息默认不进入主消息流；Goal 详情只展示产品化状态与预算，
  完整内部消息需要时通过调试/审计入口查看。

### 9.2 Composer 底栏重组

底栏采用“左侧行为与执行上下文，右侧资源、模型与提交”的两组布局：

```text
工作计划悬浮摘要（hover / focus / click 展开 Todo，不占布局高度）
[目标摘要 · Todo 2/5]
Goal 状态行（存在 Goal 时显示，click / focus 展开有限高度详情）
[Goal 自动推进中 · objective 摘要 · 剩余预算]
待审批入口（仅完整审批窗口收起且仍有待审批时显示，占布局高度）
Queue（可与待审批入口同时显示，位于其下方，占布局高度）
┌────────────────────────────────────────────┐
│ 输入区域                                   │
│                                            │
│  [+] [Build · Auto ▾]   ○  [模型 · 强度 ▾] [↑] │
└────────────────────────────────────────────┘
```

1. **添加入口 `+`**
   - 代替当前独立纸夹按钮，点击后直接选择附件，不增加二级菜单；
   - 指令只通过正文输入 `/` 触发，Goal 只由 `/goal` 一次性指令开启；本版本
     不为指令帮助、上下文或尚未存在的 Skills/MCP 预造空菜单项。
2. **执行设置 `Build · Auto`**
   - 采用“设置分类级联”：触发器先打开汇总面板，面板内显示
     `执行模式  Build  >` 和 `审批模式  Auto  >`，每一行分别在右侧打开自己的二级选项；
   - 级联只表达菜单层级，不表达两项之间存在父子依赖；也不列出 Build+Ask、Build+Auto、
     Plan+Ask、Plan+Auto 四个排列组合，避免把两个独立事实伪装成一个策略枚举；
   - 触发器同时显示当前两个值，例如 `Build · Auto`；
   - 两者仍是独立业务事实，只合并交互入口，不新建组合枚举、不将 Goal 伪装为第三种模式；
   - 安全级别不得因合并而不可见，Ask/Auto 在常规宽度始终显示，窄宽度也要有
     图标、提示或其他可识别状态。
3. **上下文用量**
   - 保留紧凑圆环与悬停/聚焦详情，它是资源状态，不与可编辑设置混合。
4. **模型设置 `DeepSeek V4 Flash · 默认`**
   - 明确采用“设置分类级联”：触发器先打开汇总面板，面板内显示
     `模型  DeepSeek V4 Flash  >` 和 `推理强度  默认  >`；进入任一行后，右侧二级菜单
     只展示该分类的候选项。
   - 模型与 reasoning effort 是两个平级设置，不使用“先选模型、再进入该模型选择强度”的
     依赖级联，也不要求一次选择同时确定两项。
   - 模型切换仍受现有 Session 空闲门禁约束；切换后若原 effort 不再有效，按 Runtime
     现有投影规则回落到该模型的有效默认值并刷新一级摘要。
   - 当前模型没有可选 effort 时不显示“推理强度”分类行，避免制造只有一个虚假“默认”项。
   - 参考图中的“速度”等本产品尚未存在的设置不随交互骨架一并引入。
   - “原生识图 / 工具识图 / 不可识图”是低频派生信息，不进入底栏或模型级联；
     它移入右侧 Context Panel 的模型能力信息中，与当前上下文窗口、模型等会话事实一起查看。
5. **发送/停止**
   - 右端保持为唯一主操作；普通 Run 中按现有发送/中断语义切换；
   - Goal 执行中点击停止表示暂停整个 Goal 并取消当前 Run，不只停止某次续跑后立即自动再开。

### 9.3 `/goal` 一次性标记

- 用户在 Composer 中输入 `/goal` 后，指令文本被消费并转换为输入区内的 `Goal`
  标签，不把字面量 `/goal` 作为用户正文发送给模型。
- 标签存在时，当前正文、图片、文件和其他附件共同构成 Goal objective；
  提交后标签立即消失，下一次输入默认仍是普通提交。
- 提交前只能通过点击标签的 `×` 取消 Goal 标记，取消后保留已输入正文和附件；
  `Esc` 继续留给其他 Composer/弹层冲突更多的交互，不取消该标记。

### 9.4 宽度与可访问性

- 标准宽度只允许两个文本选择器：执行设置和模型设置；其他项为图标或状态。
- 窄宽度优先保留发送/停止、添加入口和模型识别；文字逐级截断，不使底栏横向滚动。
- 所有只显示图标的入口必须有可访问名称、键盘聚焦和可见 focus 状态；弹层不依赖悬停才能使用。
- 执行设置与模型级联不同时展开；Todo 覆盖层、Goal 详情、设置菜单和完整 Approval Workspace
  同时只保留一个前台交互层。待审批入口与 Queue 可同时显示，但不建立第二个浮层焦点。
- Composer 必须在中文模型名、长模型名、高 DPI 和 macOS `WKWebView` 下通过实机核对。

## 十、使用路径

### 10.1 普通会话使用 Todo

1. 用户提交一个需要多步处理的任务。
2. 模型通过计划工具建立或更新总体目标与 Todo；Desktop 在 Composer 顶边显示悬浮摘要，
   用户 hover、聚焦或点击后查看 Todo 列表。
3. 普通 Run 完成后不自动续跑；Todo 保留，用户可发送下一条输入继续。

### 10.2 启动并自动推进 Goal

1. 用户输入 `/goal`，Composer 显示一次性 `Goal` 标签。
2. 用户继续输入 objective 并可添加附件；提交时 Runtime 将完整 UserMessage
   与对转录隐藏的 Goal Injected Part 组装后，一次性追加到 Conversation。
3. Runtime 以该 UserMessage 作为 objective 创建 Goal 控制状态并启动首次 Run；
   Todo 是否存在不构成开启条件。
4. Agent 如需分解工作，可通过独立计划工具维护 Todo；如已完成或无法继续，
   通过 Goal 终止入口报告 `complete` 或 `blocked`。
5. Agent 未终止 Goal 时，Runtime 结算当前 Run、核对世代与预算，再追加一条
   转录隐藏的 Runtime UserMessage 并启动下一次 Run。
6. Agent 报告 `blocked`、预算到限、连续失败或用户停止时不再续跑，
   等待用户显式恢复；报告 `complete` 时在可靠结算中终止续跑并自动清除 Goal。

### 10.3 用户在 Goal 中提供新指导

1. Goal 执行中的新消息只作为待处理指导暂存，UI 明确告知不会自动应用。
2. Goal 进入等待或暂停后，用户可新发送一条恢复消息，或显式选择已暂存指导。
3. 恢复消息进入下一次 Goal Run；Agent 可根据内容继续 objective，也可通过独立计划工具更新 Todo。

## 十一、模块与契约影响

### 11.1 `assistant-runtime`

- 持有 Session 工作计划、Goal 控制状态、世代、预算、内部续跑与 Goal 队列消费的唯一权威状态。
- Goal 控制器引用完整 objective UserMessage，不把工作计划的总体目标作为
  Goal 数据源；Todo 与 Goal 分别持久和恢复。
- 在现有 Session Controller、Input 持久化、Run 结算、取消、压缩 continuation 和恢复机制上
  增加 Goal 编排，不建立第二套 Session 执行器。
- 为每次 Run 冻结当前 Goal 世代，拒绝迟到报告，并在续跑前原子核对 Goal 状态、
  预算和队列事实。

### 11.2 `assistant-protocol`

- 对 Desktop 分别提供工作计划快照与 Goal 控制快照，以及列表/详情、
  停止/恢复/清除意图和必要事件；Goal 快照以 objective 消息引用为来源，
  不复制 Todo 的总体目标或任务。
- 区分用户真实输入、Runtime 内部续跑和待处理指导的稳定产品投影，不暴露
  SQLite 行、队列容器或 Controller 内部对象。
- Composer 合并选择器不引入新的组合业务类型；仍复用独立 variant、approval、model 和 effort 事实。

### 11.3 `runtime-host`

- 继续作为传输与具体存储 Adapter，不持有工作计划或 Goal 控制状态的第二份权威状态。
- 数据迁移、重启恢复、Fork、Session 删除和隔离 Runtime Home 验证必须覆盖新状态。
- 随包模型目录按 DeepSeek 官方精确型号将 `deepseek-v4-flash-vision-exp` 标记为原生图片输入；
  Chat Completions 的工具图片使用聚合 User Image，Responses 使用原生 function output 图片，
  不从其他 DeepSeek 型号或一次请求结果推断能力。

### 11.4 `desktop`

- MobX Store 只投影 Runtime 权威快照和用户意图，不在前端自行判断 Goal 是否完成、是否该续跑，
  也不用本地计时器模拟预算。
- 在 Composer 顶边分别投影不占布局高度的 Todo 悬浮摘要与可点击展开的
  Goal 状态行；完整审批窗口与输入框互斥，收起后把待审批入口置于 Queue 上方。
  底栏重组为添加、执行设置、上下文用量、模型设置和
  发送/停止五个常驻视觉项。
- 右侧 Context Panel 补充当前模型的图片理解路径等低频能力信息，不把它复制回底栏。
- 当 Runtime 快照与流式事件冲突时以快照恢复，不使用本地乐观 Goal 状态启动后续 Run。

## 十二、关键取舍

1. **Goal 与 Todo 分离**：Todo 是可选的 Session 工作计划；Goal 是引用原始 UserMessage 的
   自动续跑控制器。两者可以同时使用，但不互相创建、复制、清空或充当完成门禁。
2. **Agent 终止，Runtime 默认续跑**：语义完成与阻塞由当前 Agent 通过结构化入口报告；
   未收到终止信号就继续。Runtime 只负责持久、续跑、预算、世代和取消，不引入独立裁判模型。
3. **内部说明沿用 `user` role**：Goal 动态上下文属于 Runtime 注入的用户角色消息，
   通过来源和 transcript 可见性与真实用户输入区分，不修改冻结的 System Prompt。
4. **历史只追加**：首次提交在入 Journal 前组装完整 UserMessage，后续状态变化一律追加
   新事实，不回写历史消息；实际发送的 Injected Part 按次冻结。
5. **重启只恢复事实，不自动恢复副作用**：与现有持久 Input 和 interrupted Run 的安全语义一致。
6. **显式取消当前 Run**：用户的“停止 Goal”应当尽快停止继续的模型/工具活动；
   可靠结算由现有取消链路保证，不要求用户等待一个可能长时间运行的 Run 自然收尾。
7. **运行中输入可持久但不自动应用**：不丢掉用户指导，也不把时序不明的旧输入
   自动当成 blocked 问题的回答。
8. **合并入口，不合并业务事实**：执行设置与模型设置都使用“一级分类摘要、右侧二级选项”的
   设置分类级联；Build/Plan、Ask/Auto、模型和 effort 在 Runtime 与协议中仍保持独立含义。
9. **派生能力不做常驻控件**：识图能力移入右侧 Context Panel，不占用底栏或模型级联。
10. **长期进度与临时阻塞分层**：Todo 使用不占纵向空间的悬浮摘要和覆盖层，Goal 使用
   独立的有限高度详情；
   完整审批窗口与输入框互斥，收起的待审批入口位于 Queue 上方且二者均占布局高度。

## 十三、验收标准

1. 未开启 Goal 时也可建立和持久化工作计划；开启、暂停、完成或清除 Goal 都不会自动创建、
   复制、改写或清空总体目标与 Todo。
2. Goal 只能由一次性 `/goal` 标记开启；指令字面量不发送，标签提交后自动消费，提交前只能
   点击 `×` 取消且不丢失正文或附件，`Esc` 不取消标签。
3. 首次 Goal 提交的原始 UserMessage 同时保留为可见 Conversation 输入和 objective 来源；
   正文、图片、文件及稳定附件引用不被降级或复制为一个 `objective: String`。
4. 首次 Goal UserMessage 在单次追加前完成组装：用户载荷可见，Goal Injected Part 对模型可见、
   对转录隐藏；Goal 启用不修改 System Prompt，也不回写任何已存在消息。
5. 每次自动续跑都追加新的 Runtime 来源、transcript 隐藏的 UserMessage，并以 `user` role
   进入模型上下文；Provider Adapter 会移除来源和可见性元数据，只发送受支持的 role 与内容。
6. Runtime 内部续跑不生成用户气泡，也不计入真实用户轮次、用户活跃、会话标题来源或
   用户原话搜索；调试/审计入口仍能定位实际冻结的消息内容。
7. Agent 报告 `complete` 后 Goal 在所属 Run 的可靠结算中自动清除；Todo 是否存在或是否全部完成
   不构成拒绝门禁。工作计划仅在自身至少一个 Todo 全部完成时按独立规则自动清除。
8. Agent 报告 `blocked` 后 Goal 以该原因为暂停并展示“等待用户”；未发出 `complete` 或
   `blocked` 的可靠 Run 结算后，Runtime 自动追加下一轮输入，不要求 Agent 再报告“继续”。
9. Goal 达到 Run/轮次、token 或连续失败上限时暂停，不再创建内部续跑，并明确展示原因。
10. 用户停止 Goal 后，当前 Run 经现有取消链路收敛，排队续跑被清除，迟到信号不能重启 Goal。
11. Goal 执行中的用户输入不丢失、不打断、不自动消费；恢复某条暂存输入必须是用户显式动作。
12. Goal 完成或清除时如有暂存输入，普通队列不会在无确认时突然批量执行。
13. Runtime 重启能恢复工作计划、Goal 控制状态、冻结注入消息与预算事实，
    但未完成 Goal 必须由用户显式恢复后才执行。
14. Fork 后工作计划与 Goal 控制状态分别成为新 Session 的独立副本，不会与源 Session
    共享世代或后续状态变更。
15. Goal 中的工具仍逐项遵守 Plan/Build、Ask/Auto、明确 Deny、审批、取消和审计边界。
16. Todo 摘要锚定 Composer 顶边且不占布局高度，hover、键盘聚焦和点击均能展开居中的紧凑
    Todo 覆盖层；覆盖层不接收 pointer event，鼠标离开摘要后立即隐藏且不提供清空计划操作；
    Goal 状态行独立显示在输入区上方，只通过点击或键盘激活有限高度详情，不使用 hover 展开。
17. 完整审批窗口与输入框互斥；窗口收起后待审批入口显示在 Queue 上方且两者可同时存在、
    分别占据布局高度。
18. Composer 标准宽度下只有添加、执行设置、上下文用量、模型设置、发送/停止五个常驻视觉项。
19. 执行设置一级面板分别汇总 Build/Plan 和 Ask/Auto 当前值，两行各自打开右侧二级选项；
    当前权限模式不会被隐藏到无法识别，也不会被折叠为四个组合枚举。
20. 模型设置一级面板分别汇总模型和 reasoning effort 当前值，两行各自打开右侧二级选项；
    识图能力在右侧 Context Panel 查看，不进入级联、也不再常驻占用底栏。
21. 在 720px 及更窄宽度、长模型名称、键盘操作和 macOS `WKWebView` 中，Composer 不溢出、
    不横向滚动，主操作和安全状态可见。
22. 自动化测试覆盖 Goal 主状态与暂停原因、世代竞态、内部消息投影、只追加约束、
    队列隔离、预算、重启、Fork、权限、
    Desktop 投影与窄宽度；正式 Host 场景还要验证至少一条真实跨 Run Goal 续跑链路。
23. 工作空间移除前必须二次确认并明示不删除文件和会话；移除后工作空间及其会话
    不出现在侧栏、标题搜索或新会话选择中，重新添加同一目录后恢复显示。

## 十四、风险、兼容性与确认结论

### 14.1 主要风险

- **队列语义分叉**：现有提交输入会解除用户队列暂停并唤醒执行器；Goal 需要区分
  用户输入和 Runtime 续跑，如果只增加一个布尔标志容易在停止、重启和排队竞态中失效。
- **双重 continuation**：当前上下文压缩已在一个业务 Run 内部 continuation；Goal 是跨业务 Run 续跑。
  两者必须有独立身份和预算，不能相互重复计数或把压缩误判为 Goal 新一轮。
- **停止竞态**：模型报告、Run 结算、内部续跑入队和用户停止可以交错，必须以世代和持久状态
  为门禁，不依赖单进程内时序巧合。
- **内部消息泄漏**：Runtime 续跑需要以 `user` role 进入模型历史且可审计，但不应冒充用户输入进入
  普通消息流、Recall 摘要、用户活跃统计或用户原话搜索结果。来源和 transcript 可见性必须
  在规范消息层持久，不能只靠 UI 字符串前缀判断。
- **objective 漂移或递归复制**：如果 Goal 另存一份可变目标文本，或把带 Goal Injected Part 的
  消息再次整体嵌入续跑，恢复和多轮续跑会逐渐偏离用户原始输入。Goal 必须引用原始
  UserMessage，并从其用户载荷生成每轮冻结注入，不依赖 LLM 重新描述或 Runtime 模糊提取。
- **历史回写破坏恢复**：若启用或推进 Goal 时修改旧消息，会破坏审计、重放和 Prompt Cache
  前缀稳定性。Journal 写入和迁移需验证只追加约束。
- **Composer 过度隐藏**：减少控件不能让用户看不到 Auto 权限或在切换模型时误以为
  effort 仍然不变；两类设置的一级摘要必须清楚展示各分类当前值，二级菜单只负责列出候选项。
- **浮层遮挡与纵向压缩**：工作计划覆盖层、设置菜单和 Approval Workspace 可能争抢空间与焦点；
  需要统一前台浮层规则、避让定位、焦点返回和 Esc 行为。收起的待审批入口与 Queue 会共同
  占据高度，需要限制摘要尺寸并在窄窗口验证输入区域仍可用。

### 14.2 兼容性

- 旧 Session 没有工作计划或 Goal 控制状态时按空状态恢复，不通过扫描旧对话文本猜测或回填。
- 旧 UserMessage 缺少来源和 transcript 可见性字段时，一律迁移或读取为用户来源、转录可见；
  只有新的 Runtime 续跑事实使用 Runtime 来源和转录隐藏。
- Provider 协议不增加 `internal` role；不支持应用元数据的 OpenAI-compatible 端点继续只接收
  `system`、`user`、`assistant` 等既有消息角色及其可编码内容。
- 现有 Plan/Build、Ask/Auto、model、effort 和 image handling 协议事实不因 Composer 重组而改变含义。
- 旧队列恢复和 `resume_queued_input` 语义不得被 Goal 无条件改写；只在存在未清除 Goal 时应用
  Goal 专属消费规则。

### 14.3 确认结论

已根据用户反馈确认：

- 识图能力移入右侧 Context Panel，不进入底栏或模型选择器；
- 执行设置与模型设置均使用“一级分类摘要、右侧二级选项”的设置分类级联；
- 模型与 reasoning effort 是平级分类，不使用模型到强度的依赖级联；
- Goal 与 Todo/工作计划是独立功能；Goal 只负责基于本次完整 UserMessage objective 自动续跑，
  不要求或复制 Todo，Todo 在未开启 Goal 时同样可用；
- Goal 只通过一次性 `/goal` 标签开启，提交前只允许点击 `×` 取消，提交后自动消费；
- Goal 由 Agent 通过 `complete` 或 `blocked` 自主终止，不引入独立 Judge；没有终止信号时
  Runtime 自动续跑；
- Goal 动态说明和续跑均使用带 Runtime 来源/转录可见性标记的 `user` role 消息，
  不改 System Prompt、不增加 Provider role，Conversation 历史只允许追加；
- Todo 在 Composer 顶边浮动展示，hover 展开只读列表且不占纵向压缩空间；详情不接收
  pointer event，离开摘要后立即隐藏；Goal 在其下方
  使用独立状态行，点击或键盘激活有限高度详情，不使用 hover；
- 完整审批窗口与输入框互斥；窗口收起后，待审批入口位于 Queue 上方并与 Queue 同时占据布局高度。
- 停止 Goal 会取消当前 Goal Run，不等待其自然收尾；
- Goal 运行中的用户输入允许持久暂存，但不打断、不自动应用，之后由用户显式选择恢复；
- Fork 复制工作计划；只有 objective 原始消息位于 Fork 前缀时才复制 Goal，
  且新 Session 的 Goal 从暂停态开始。

功能设计已收口，未留下阻止开发计划的产品待确认项。
