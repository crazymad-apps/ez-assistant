## 二、台账原则

1. M0 至 M6 顺序推进，前一里程碑确认后才能进入下一里程碑。
2. 里程碑完成实现和验证后先标记 `🟨 待确认`，用户确认后才标记 `✅ 已完成`。
3. `assistant-runtime` 持有业务权威状态；Host、Demo 和未来桌面端只负责装配、传输或展示。
4. 自动测试不访问真实 Provider 或用户数据；真实模型验证只在 M6 使用显式配置执行。
5. 实际结果、偏差和遗留写入 `docs/开发进度.md`，本计划只更新状态。
6. 不主动执行 Git 暂存、提交或推送。

## 四、里程碑台账

### M0：Runtime Host 工程入口与依赖边界

- 前置：v0.7.0 已归档。
- 目标：建立正式 Runtime Host 入口，并固定 Desktop、Protocol、Runtime 和 Agent 层的依赖方向。
- 交付范围：Host 工程骨架、无副作用帮助入口、模块约束和 workspace 登记。
- 验证入口：

  ```bash
  cargo metadata --format-version 1 --no-deps
  cargo check -p assistant-runtime-host -p assistant-runtime -p assistant-protocol
  cargo run -p assistant-runtime-host -- --help
  ```

- 完成判定：工程可构建，帮助命令不启动 Runtime，依赖方向与模块约束一致。
- Review 重点：产品 Host 与验证工具的边界。
- 技术依据：技术方案第四、十四节。

### M1：Assistant Protocol 最小应用契约

- 前置：M0 已确认。
- 目标：形成 Runtime 与客户端共享的最小应用协议。
- 交付范围：应用 ID、命令、结果、快照、事件、状态和安全错误。
- 验证入口：

  ```bash
  cargo test -p assistant-protocol
  cargo clippy -p assistant-protocol --all-targets --all-features -- -D warnings
  ```

- 完成判定：公共类型可稳定序列化，Protocol 保持轻量且不泄漏 Agent 或传输实现。
- Review 重点：公共语义是否最小、错误和事件归属是否明确。
- 技术依据：技术方案第十、十五节。

### M2：Runtime 生命周期、Session 与内存 Conversation 基础

- 前置：M1 已确认。
- 目标：建立 Runtime 和 Session 的权威内存状态。
- 交付范围：Runtime 生命周期、Session 创建与查询、独立 Agent、内存 Conversation 和基础错误。
- 验证入口：

  ```bash
  cargo test -p assistant-runtime
  cargo clippy -p assistant-runtime --all-targets --all-features -- -D warnings
  ```

- 完成判定：Session 相互隔离，生命周期门禁有效，未完成工具交换不会进入 Conversation 快照。
- Review 重点：Runtime、Agent 和 Conversation 的所有权边界。
- 技术依据：技术方案第五至第七节。

### M3：单 Session Run 与 Agent 执行闭环

- 前置：M2 已确认。
- 目标：让一个 Session 可以完成真实 Agent Run，并可靠结算 Conversation。
- 交付范围：Run 启动与查询、用户消息入账、Agent 执行、工具交换记录和唯一终态结算。
- 验证入口：

  ```bash
  cargo test -p assistant-runtime -p agent-sdk -p agent-core
  cargo clippy -p assistant-runtime -p agent-sdk -p agent-core --all-targets --all-features -- -D warnings
  ```

- 完成判定：成功、失败、取消准备和异常执行都不会留下半成品 Run 或损坏 Conversation。
- Review 重点：唯一结算来源和失败后的 Session 可用性。
- 技术依据：技术方案第七、八节。

### M4：Runtime 事件、多 Session 并发、取消与关闭

- 前置：M3 已确认。
- 目标：补齐 Runtime 的观察、并发控制、取消和受控关闭能力。
- 交付范围：实时事件出口、Run 观察快照、多 Session 并发、公共取消和 Runtime shutdown。
- 验证入口：

  ```bash
  cargo test -p assistant-runtime -p agent-testkit
  cargo clippy -p assistant-runtime -p agent-testkit --all-targets --all-features -- -D warnings
  ```

- 完成判定：不同 Session 可并发，同一 Session 保持串行；慢观察者不影响执行，取消和关闭可靠收敛。
- Review 重点：事件不是事实源、并发隔离和 shutdown 完整性。
- 技术依据：技术方案第八、九、十三节。

### M5：Unix Socket Host、私有 TUI 与安全装配

- 前置：M4 已确认。
- 目标：通过独立 Host 和易用的私有客户端验证 Runtime 跨进程运行。
- 交付范围：
  - 本地进程通信、单实例和运行入口清理；
  - 真实模型和仅允许 `echo_text` 的安全默认装配；
  - 单屏私有客户端，可完成会话选择、发送、观察、取消、手动重连、退出和确认关闭。
- 验证入口：

  ```bash
  cargo test -p assistant-runtime-host --all-features
  cargo run -p assistant-runtime-host -- --help
  cargo run -p assistant-runtime-host --features demo-client -- demo --help
  cargo clippy -p assistant-runtime-host --all-targets --all-features -- -D warnings
  cargo fmt --all --check
  ```

- 人工核对：Host/Demo 分进程、终端恢复、客户端退出后 Run 继续、重新连接可查询，以及确认关闭后
  Host 退出并清理 endpoint。
- 完成判定：私有客户端无需记忆命令或手工 ID 即可完成最小验证；通信、安全、断线和关闭行为符合
  已确认方案。
- Review 重点：Host 与 Runtime 边界、安全默认值、客户端展示状态不成为第二事实源。
- 技术依据：技术方案第十一至第十五节。

### M6：真实 Provider 联调、全量回归与验收准备

- 前置：M5 已确认。
- 目标：完成真实链路验证和版本级回归，为正式验收提供证据。
- 交付范围：真实多轮对话、`echo_text` 工具闭环、双 Session、取消、断线恢复查询、受控关闭、文档
  收口和全工作区回归。
- 验证入口：

  ```bash
  cargo fmt --all --check
  cargo clippy --workspace --all-targets --all-features -- -D warnings
  cargo test --workspace
  cargo doc --workspace --no-deps
  ```

- 人工核对：使用显式 Provider 配置走完功能设计验收路径，不记录 credential 或完整交互内容。
- 完成判定：功能设计中的十四条验收标准均有自动或人工证据，未执行项、偏差和风险均已记录。
- Review 重点：真实使用路径、最终依赖方向、公共 API 范围和验收证据。
- 技术依据：技术方案第十五至十七节。
