# v0.8.0 功能设计：Assistant Runtime 初始化

## 一、设计信息

- 版本：`v0.8.0`
- 状态：已确认
- 影响模块：`assistant-runtime`、`assistant-protocol`、独立 Runtime 宿主、私有验证客户端
- 需求来源：`v0.7.0` 归档后的 Runtime 阶段路线，以及 2026-08-04 至 2026-08-05 的架构讨论
- 输入池评估：`260726-长任务机制参考（opencode调研）` 中的 Runtime drain、queue、steering 和
  持久恢复留待后续业务版本；`260729-上下文裁剪压缩` 继续留在 Context/Runtime 后续编排范围，
  两项均不进入本版本

## 二、背景与目标

`v0.1.0` 至 `v0.7.0` 已经形成可独立组合验证的 Agent Core、Agent SDK、模型、工具、安全、
上下文、记忆和可靠性能力，但正式应用层仍缺少能够长期承载这些能力的业务 Runtime。现有 Demo
分别维护私有 Session、Run、Journal 和 HTTP DTO，只能证明下层行为，不能作为正式产品后端。

长期架构中，Tauri 只负责页面展示和桌面平台适配；Session、Conversation、Run、Harness、策略、
审批、工作区、记忆、调度、持久化和事件记录等核心业务由 Assistant Runtime 持有权威状态。
桌面 UI 与 Runtime 最终分进程运行，Session 不创建操作系统子进程，而是在同一个 Runtime 进程
内通过逻辑控制器和 Tokio 异步任务管理。

本版本定位为 **Runtime 初始化版本**。目标是建立正式 Runtime 的最小能力闭环，并用一个私有
验证客户端证明 Runtime 可以脱离 Tauri 运行、管理 Session 和 Run、调用真实 Agent Harness，
而不是一次完成全部桌面应用和业务模块。

本版本成功后应形成以下基础：

1. 存在统一、可启动和可受控关闭的 Assistant Runtime。
2. Runtime 可以创建多个 Session，并为每个 Session 持有一个长期复用的 Agent。
3. Runtime 可以基于 Session 的规范 Conversation 启动、取消并结算一次真实 Run。
4. 同一 Session 不发生并发上下文修改，不同 Session 可以异步并发执行。
5. Runtime 可以把 Core 执行变化关联到 Session 和 Run，并向在线观察者发送 Runtime 事件。
6. Runtime 进程不依赖 Tauri 或验证客户端的页面生命周期。

## 三、非目标

以下能力明确不进入 `v0.8.0`：

- 正式 Tauri 页面、菜单栏、Dock、通知和桌面生命周期接入。
- macOS LaunchAgent、Windows/Linux 后台服务、开机启动和崩溃自动拉起。
- 自动重连、断线事件补取、增量事件游标和多客户端协作。
- 正式数据库、Repository、进程重启后的 Session/Run 恢复和数据迁移。
- Plan / Build、Ask / Auto、规则保存、审批交互和持久审计。
- 正式 Workspace、用户目录授权、文件上传、附件、文件变更和 Artifact 管理。
- Pinned Memory、RecallSource、Context continuation、计划任务和后台服务的正式 Runtime 编排。
- Harness Profile 管理、运行中配置变更、多模型切换和用户级配置界面。
- 轮内 steering、Run 自动排队、优先级和资源调度。
- 远程访问、本地 HTTP 产品服务以及公开的第三方客户端协议。

这些能力是后续 Runtime 业务版本的迭代方向，不因本版本暂不实现而改变其 Runtime 所有权。

## 四、功能范围

### 4.1 Runtime 生命周期

本版本提供一个独立于 Tauri 的 Runtime 进程入口。它能够：

- 使用显式启动配置初始化 Runtime 和默认 Agent 装配依赖。
- 建立仅供本机私有验证使用的通信入口。
- 接受创建 Session、查询快照、启动 Run、取消 Run 和关闭 Runtime 等最小操作。
- 在验证客户端断开后继续执行已经启动的 Run。
- 收到关闭请求后停止接受新 Run，取消并结算活动 Run，再结束 Runtime 进程。

本版本只保证 Runtime 独立于验证客户端，不承诺脱离用户登录会话、终端或操作系统服务管理器
长期存活。系统级守护和自动拉起由后续版本处理。

### 4.2 Session

Session 是 Runtime 管理规范 Conversation 和 Agent 装配的业务边界。

- 每个 Session 具有 Runtime 分配的稳定 `SessionId`。
- 创建 Session 时，Runtime 使用启动时提供的单一默认配置构造一个 Agent。
- Agent 持有该 Session 内冻结的模型、System Prompt、Context Window、ToolSet、模型请求配置、
  Budget 和 Guardrail 装配，但不持有动态 Conversation、Run 或调度状态。
- Runtime 持有 Session 的动态 Conversation、当前活动 Run 和生命周期状态。
- Session 在 Runtime 进程存活期间可被查询；本版本不承诺进程重启后恢复。
- 本版本不实现历史 Session 自动卸载、分支、归档或删除。

一个 Agent 只服务它所属的一个 Session；不同 Session 可以共享线程安全的底层模型服务和工具能力，
但不共享冻结的 Agent 会话装配。

### 4.3 Conversation

Runtime 内的 Conversation Journal 是本版本 Session 规范对话的内存权威状态，实时事件不是恢复
或后续模型输入的事实源。

- 启动用户 Run 前，Runtime 先把完整 UserMessage 写入 Conversation，再构造
  `ConversationSnapshot` 交给 Agent。
- 完整 AssistantMessage 和 ToolMessage 按 Core Recorder 契约结算到当前 Session。
- 工具副作用前必须先确认完整 Assistant Tool Call；完整批次 Tool Result 结算后才能进入后续模型
  Step。
- 已经完整提交的消息在 Run 失败或取消后保留，不回滚已经发生的规范交互。
- 尚未形成完整规范消息的文本增量、reasoning 增量和工具输出片段只作为观察事件，不直接写入
  Conversation。
- 任意供下一次 Run 使用的 Conversation Snapshot 都不能暴露未配对的 Tool Call/Result。

本版本只使用内存实现验证上述权威语义，不定义数据库 schema、正式文件格式或恢复协议。

### 4.4 Run

Run 是 Runtime 对一次 AgentExecution 的业务封装，具有独立的 `RunId`、所属 `SessionId`、状态、
取消控制和最终结果。

最小状态语义包括：

- 已接受但尚未进入 Core 执行。
- 正在执行。
- 正在响应取消。
- 已完成。
- 已失败。
- 已取消。

运行规则：

- 同一 Session 同时只允许一个改变 Conversation 的活动 Run。
- Session 已有活动 Run 时，新的启动请求立即返回 `SessionBusy`，本版本不自动排队。
- 不同 Session 的 Run 可以使用 Tokio 异步并发。
- Runtime 为每个 Run 创建独立取消令牌、Recorder、Authorizer 和 Agent 事件适配关系。
- `RunId` 和 `SessionId` 不进入 Agent Core；Runtime 在消费 Core 事件时补充业务关联。
- 取消必须传播到模型等待、工具执行和 AgentExecution；取消完成前 Session 仍视为忙碌。
- 单个 Run 失败或取消后，Session 仍可继续接受后续 Run。

`CompactionRequired` 在本版本作为明确的 Run 终态和 Runtime 事件对外暴露，但不自动启动压缩或
continuation。正式 Context 编排放到后续业务版本。

### 4.5 最小 Harness 接入

Runtime 复用 `agent-sdk` 和现有 Agent crate，不实现第二套 Agent Loop。默认验证装配至少覆盖：

- 一个可实际调用的 Provider 配置。
- 多轮规范 Conversation。
- 流式文本事件。
- 至少一种低风险的工具调用闭环。
- Core Recorder 和 Authorizer 的真实注入。
- Run 完成、失败和取消。

自动化测试优先使用 scripted model、fake tool、in-memory recorder 和 fake authorizer；人工验证可以
使用真实 Provider。用于证明工具循环的私有测试工具或临时目录不形成正式 Workspace、文件策略或
产品工具配置。

默认验证 Authorizer 只允许功能设计明确注册的低风险私有测试工具，其他已解析调用一律 Deny；
未知工具仍按 Core 既有协议错误结算。本版本不实现审批、信任规则或简化版 Ask/Auto。

### 4.6 Runtime 事件与快照

Runtime 将需要观察的生命周期变化和 Core AgentEvent 转换为带 Session/Run 关联的 Runtime 事件。
本版本事件用于在线验证，不作为 Conversation Journal，也不承诺持久化。

事件范围至少能够表达：

- Runtime 已启动和准备关闭。
- Session 已创建。
- Run 已接受、开始、进入终态。
- Agent 文本增量和工具执行阶段。
- Run 取消请求及取消完成。
- Runtime 或 Agent 执行失败。

验证客户端可以查询 Session、Conversation 和 Run 当前快照。客户端断开后：

- Runtime 和活动 Run 不受影响。
- 断线期间的实时增量可以丢失。
- 再次连接时只按当前快照展示，不补取缺失的历史增量事件。

本版本不增加事件 sequence、订阅游标或 Event Journal，以免提前固化正式桌面恢复协议。

### 4.7 私有验证客户端

本版本提供一个最小客户端验证 Runtime，不把它建设成正式桌面应用。

客户端采用 feature-gated 的单屏终端界面（TUI），只需要支持：

- 连接已经启动的 Runtime。
- 启动后加载 Session；没有 Session 时创建默认 Session，并允许从列表创建和切换 Session。
- 在固定输入区输入用户消息并启动 Run，不要求记忆命令语法或手工复制 Session/Run ID。
- 在会话区域展示规范 Conversation，在状态区域实时展示文本、reasoning、工具阶段和 Run 终态。
- 通过明确快捷键取消活动 Run、刷新当前快照、退出客户端或二次确认后关闭 Runtime。
- 断线后展示连接状态，并允许手动重连和重新查询当前 Session/Run 快照。

客户端不实现自动重连、历史事件回放、多客户端协作、本地状态持久化、产品级导航或正式错误引导。
TUI 中的选中项、输入缓冲和滚动位置只是本地展示状态；Session、Conversation 和 Run 事实每次来自
Runtime 快照或实时事件。它的终端布局、快捷键、传输封装和展示 DTO 保持验证私有，不自动进入
`assistant-protocol`。

## 五、使用路径

### 5.1 正常执行

```text
开发者启动 Runtime
→ 验证客户端连接
→ 创建 Session
→ Runtime 构造 Session Agent
→ 客户端提交 UserMessage
→ Runtime 先写入 Conversation，再创建 Run
→ Runtime 启动唯一 AgentExecution
→ Agent 流式输出或调用工具
→ Runtime 结算规范消息并广播观察事件
→ Run 完成
→ 客户端查询到最终 Conversation 和 Run 状态
```

### 5.2 同 Session 并发请求

```text
Session A 正在执行 Run 1
→ 客户端请求启动 Run 2
→ Runtime 返回 SessionBusy
→ Run 1 不受影响
```

### 5.3 多 Session 并发

```text
Session A 启动 Run A
Session B 启动 Run B
→ 两个 Run 异步并发
→ 各自只修改所属 Conversation
→ 事件和最终状态不会串线
```

### 5.4 客户端断开

```text
Run 正在执行
→ 验证客户端断开
→ Runtime 继续执行并结算 Run
→ 客户端再次连接
→ 查询当前 Session/Run 快照
→ 不补取断线期间的增量事件
```

### 5.5 取消与关闭

```text
客户端取消 Run
→ Runtime 传播取消
→ AgentExecution 和工具受控结束
→ Run 标记为 Cancelled
→ Session 可以接受下一次 Run

客户端请求关闭 Runtime
→ Runtime 停止接受新 Run
→ 取消并结算所有活动 Run
→ 发出关闭状态
→ Runtime 进程退出
```

## 六、模块职责与契约影响

### 6.1 `assistant-runtime`

负责：

- Runtime、Session、Conversation 和 Run 的权威内存状态。
- 每 Session 一个 Agent 的构造与持有。
- 同 Session 串行和不同 Session 并发。
- UserMessage 落账、Conversation Snapshot 构造和 Core Recorder 绑定。
- AgentExecution 生命周期、取消和 Runtime 事件适配。
- Runtime 启动和受控关闭的业务行为。

不负责：

- Tauri 窗口与页面状态。
- Provider 协议编解码和 Agent Loop。
- Demo TUI 和传输层展示 DTO。
- 本版本未纳入的持久化、审批、Workspace 和长期后台业务。

### 6.2 `assistant-protocol`

只纳入 Runtime 与未来应用客户端稳定共享所必需的应用级 ID、生命周期状态、快照、命令结果和
安全错误码。AgentExecution、ExecutionSpec、ModelEvent、Provider 状态、trait object 和传输连接
不得进入该 crate。

本版本的验证 TUI 状态、通信 envelope、调试字段和临时工具展示结构保持宿主私有。协议仍处于
`0.x` 初始化阶段，但字段和 enum 必须使用明确序列化语义并有 round-trip 验证。

### 6.3 独立 Runtime 宿主

该宿主是未来桌面客户端连接的正式产品 Runtime 进程入口，不是新增的 `tools/*` 验证宿主。
私有客户端只用于验证这个正式入口，不形成另一套 Runtime 或产品契约。

负责：

- 读取启动配置并装配具体 Provider、Agent 基础依赖和 Runtime。
- 提供仅本机使用的最小进程通信入口。
- 把传输消息适配为 Runtime 操作，把 Runtime 事件发送给在线客户端。
- 管理单个 Runtime 实例的进程入口和日志。

具体二进制位置、本地传输和进程单实例手段属于技术方案，不在功能设计中固化。

### 6.4 私有验证客户端

只负责发送验证意图和展示 Runtime 返回的快照、实时事件与错误。它不持有 Session、Run 或
Conversation 的权威状态，也不直接调用 Agent SDK/Core。

### 6.5 Tauri Desktop

本版本不修改正式桌面业务链路。长期依赖方向确定为：

```text
Desktop → assistant-protocol → Runtime Host → assistant-runtime → agent-sdk / agent-core
```

Tauri 后续只保留展示状态和桌面平台适配，不直接装配或执行 Agent。

## 七、关键取舍

### 7.1 初始化版本仍建立真实进程边界

只实现一个可嵌入 library 无法验证 UI/Runtime 分离目标。本版本建立最小独立 Runtime 进程和本机
验证入口，但不提前承担系统守护、桌面重连和正式 IPC 的全部复杂度。

### 7.2 Session 不使用操作系统子进程或永久线程

一个 Session 是 Runtime 内的逻辑业务单元。不同 Session 由 Tokio 异步任务并发；同一 Session
通过 Runtime 所有权和状态检查保证串行。Shell/MCP 等工具可能启动子进程，但不等同于 Session
进程。

### 7.3 首版忙碌即拒绝，不隐藏队列

自动排队会立即引入优先级、取消待运行任务、输入顺序和 UI 状态等业务语义。初始化版本使用
`SessionBusy` 明确拒绝并发启动，后续结合正式交互再设计排队或 steering。

### 7.4 内存 Journal 先验证权威语义

持久化不是把内存结构序列化即可，它需要事务、pending exchange 恢复、迁移和错误处理。本版本先
使用内存 Journal 验证消息提交边界，不定义可能很快被推翻的数据库和 Repository 契约。

### 7.5 事件可观察但不作为事实源

Runtime 事件可以丢失，Conversation 和 Run 快照才是查询依据。本版本不为私有 Demo 引入事件回放；
正式断线恢复应在持久化和桌面客户端需求明确后统一设计。

### 7.6 后续业务优先进入 Runtime

Plan/Build、审批、Workspace、文件上传、记忆和后台任务都应先形成 Runtime 行为，再通过
`assistant-protocol` 暴露给 Tauri。不能先在桌面端复制业务状态，再反向迁移到 Runtime。

## 八、验收标准

1. 可以在不启动 Tauri 的情况下启动独立 Runtime，并由私有客户端完成最小操作。
2. Runtime 可以创建至少两个 Session，每个 Session 持有独立 Agent 和 Conversation。
3. 一个 Session 可以完成真实多轮模型执行，并至少完成一次低风险工具调用闭环。
4. 新 UserMessage 在 AgentExecution 启动前进入规范 Conversation。
5. 已完整结算的 AssistantMessage 和 ToolMessage 在 Run 失败或取消后仍保留，未完成增量不进入
   规范 Conversation。
6. 同一 Session 的第二个并发 Run 返回 `SessionBusy`，且不影响当前 Run。
7. 两个 Session 的 Run 可以异步并发，消息、Recorder、取消和事件不会交叉归属。
8. Run 取消可以传播到 AgentExecution，并使 Session 在取消结算后重新可用。
9. 客户端断开不会取消活动 Run；重新连接后可以查询最终 Session 和 Run 快照，但不补取增量事件。
10. Runtime 事件能够关联正确的 Session/Run，并表达文本、工具阶段和唯一 Run 终态。
11. Runtime 收到关闭请求后拒绝新 Run、取消并结算活动 Run，然后退出进程。
12. 自动化测试不依赖真实 Provider；真实 Provider 和低风险工具闭环有明确的人工验证入口。
13. `assistant-protocol` 的公共 DTO 有序列化 round-trip 验证，私有 Demo DTO 未泄漏进公共协议。
14. `assistant-runtime` 不依赖 Tauri、具体 UI、数据库实现或 Provider 协议类型，Agent Core 不反向
    依赖 Runtime 或业务 ID。

## 九、风险、兼容性与待确认项

### 9.1 主要风险

- UI/Runtime 双进程已成为根约束和模块文档的正式基线；技术方案与实现必须继续区分独立产品
  Runtime、系统 daemon 和私有验证工具，避免再次混淆生命周期承诺。
- 旧 Demo 已存在多套私有 Session、Run 和 Journal；实现时必须复用行为证据，不能复制其类型和
  文件格式成为正式 Runtime。
- Runtime 同时消费 Core 事件、Recorder 提交和 completion，若职责划分不清可能导致消息重复或
  Run 终态竞态；技术方案必须定义单一结算路径。
- 独立进程会引入传输断开、进程关闭和取消竞态；本版本通过私有客户端、无事件回放和受控关闭
  限制问题范围。

### 9.2 兼容性

- `agent-core` 和 `agent-sdk` 的候选 API 允许根据正式 Runtime 集成结果做兼容性调整，但必须保持
  唯一 Agent Loop 和既有协议正确性。
- `assistant-runtime` 与 `assistant-protocol` 仍处于初始化阶段，本版本不承诺跨版本 wire 兼容；
  任何公共类型仍需明确语义并避免无意泄漏底层实现。
- Demo 私有 TUI、快捷键、Unix Socket envelope 和 JSON frame 均不具兼容承诺。

### 9.3 待确认项

本功能设计没有遗留产品开放问题。独立宿主的物理目录、本地传输实现、消息 envelope、Runtime
内部并发结构和测试夹具等属于技术方案，由技术方案在不扩大上述范围的前提下确定。
