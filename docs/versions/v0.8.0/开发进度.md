## M2：Runtime 生命周期、Session 与内存 Journal 基础

- 状态：✅ 已完成
- 计划产出：RuntimeConfig、AssistantRuntime、SessionAgentFactory、生命周期门禁、Session
  Registry、每 Session Agent、内存 Journal 与隔离/不变量测试。
- 实际结果：
  - 新增显式 `RuntimeConfig`、`AssistantRuntime`、`SessionAgentFactory` 与结构化 Runtime 错误；
    Runtime 构造时接收 Agent Factory 和 Authorizer，不依赖具体 Provider、Tauri 或传输。
  - Session Registry 使用进程内单调字符串 ID 和短临界区锁；创建 Session 时 Factory 每次构造
    独立 Agent，由对应 Session 长期持有，Factory 失败不会插入半成品 Session。
  - Running 状态允许创建 Session；ShuttingDown/Stopped 拒绝新的创建，但既有 Session 查询仍然
    可用。创建在 Agent 构造后会再次核对生命周期，避免关闭与插入竞态。
  - Session 持有独立内存 Journal 与活动 Run 槽位；查询只返回克隆后的 Protocol 快照，不向外
    暴露锁或内部控制器。
  - Journal 区分 completed Conversation 与 pending Tool Exchange；begin/complete 成批校验并
    原子提交，错误、错序或不匹配的 complete 不会把半成品暴露到 Conversation 快照。
- 验证：
  - `cargo test -p assistant-runtime`：9 passed，覆盖 Session/Agent 隔离、Factory 失败、生命周期
    门禁、稳定查询错误以及 Journal pending/顺序/重复完成不变量。
  - `cargo clippy -p assistant-runtime --all-targets --all-features -- -D warnings`：通过。
  - `cargo tree -p assistant-runtime --depth 3`：通过，依赖保持向 Agent/Protocol 下行，没有 Tauri、
    Host、具体 Provider 或平台传输依赖。
  - `cargo check -p assistant-runtime-host`、`cargo doc -p assistant-runtime --no-deps`：通过。
  - `cargo fmt --all --check`、`git diff --check`：通过。
- 偏差：M2 不创建 Run，因此没有提前增加空 Run Record 容器或查询包装；Session 只保留 M3 所需的
  活动 Run 槽位。Journal 写入入口已经实现并验证，但在 M3 接入 Run Recorder 前尚无生产调用方，
  以带原因的窄范围 lint 标注保留。
- 遗留与风险：本阶段没有 Run task、Tokio actor、操作系统线程、持久化、队列或平台传输；这些

## M3：单 Session Run、Recorder 与唯一结算链路

- 状态：✅ 已完成
- 计划产出：短随机业务 ID、start_run 原子门禁、绑定 Session/Run 的 Runtime Recorder、单一
  supervisor 结算链路、Run/Conversation 查询和异常路径测试。
- 实际结果：
  - Session、Run、规范 Message/Part ID 改为系统随机源生成的短 URL-safe 标识，使用 `s_`、
    `r_`、`m_`、`p_` 前缀和 12 字符主体；Session/Run 在 Registry 内检查碰撞。
  - `start_run` 在一个 Session 锁临界区内完成空闲/故障门禁、用户消息提交、不可变 Conversation
    Snapshot、RunRecord 和 ActiveRun 登记；空白输入、Busy 或非 Running 不产生半成品 Run。
  - `RuntimeRecorder` 绑定唯一 Session/Run，把 Core 的 begin/complete 映射到 Journal pending 与
    completed；run/receipt 不匹配会使 Session 进入内部故障状态，pending 不进入快照。
  - 每个 Run 启动一个短期 supervisor，同时消费 Core 观察事件并等待可靠 completion；completion
    是 Completed/Failed/Cancelled/CompactionRequired 和最终 AssistantMessage 的唯一结算来源。
  - completion panic 被转换为脱敏 Failed 并清理 ActiveRun；CompactionRequired 不自动创建第二次
    AgentExecution。Run 可通过公共 `get_run` 查询，Conversation 继续由 Runtime 权威持有。
  - 同步澄清 SDK 文档：`agent-sdk::Agent` 是冻结执行配置和启动 Facade，Runtime Session 才拥有
    动态 Conversation、Run 和 Journal。
- 验证：
  - `cargo test -p assistant-runtime -p agent-sdk -p agent-core`：Runtime 16、SDK 12、Core 36，合计
    64 passed；覆盖纯文本、成功工具循环、pending 隔离、挂起工具取消、SessionBusy、失败、压缩
    交接、completion panic、空白输入和未知 Run。
  - `cargo test -p assistant-protocol`：14 passed，公共 DTO、状态、错误码和 wire round-trip 通过。
  - `cargo clippy -p assistant-runtime -p agent-sdk -p agent-core --all-targets --all-features --
    -D warnings`：通过。
  - `cargo check -p assistant-runtime-host`、`cargo tree -p assistant-runtime --depth 3`、
    `cargo doc -p assistant-runtime -p agent-sdk --no-deps`：通过。
  - `cargo fmt --all --check`、`git diff --check`：通过。
- 偏差：根据 M2 Review，ID 从原计划的进程内递增字符串改为短随机字符串，并同步修订技术方案、
  开发计划和 SDK/Runtime 术语；Protocol 仍保持不透明字符串 newtype，没有 wire 变更。M4 才提供
  正式 `cancel_run`，M3 的取消场景通过私有测试控制句柄验证 Core 收敛和结算。
- 遗留与风险：M3 还没有 Runtime Event Hub、跨 Session 并发验证、公共取消、TaskTracker 或受控
  shutdown；这些属于 M4。仍只有内存 Journal/RunRecord，不包含 Repository 或落盘恢复。

## M4：Runtime 事件、多 Session 并发、取消与关闭

- 状态：✅ 已完成
- 计划产出：有界 Runtime Event Hub、Core 事件投影、公共取消、不同 Session 并发、Runtime 根取消
  令牌、TaskTracker 和幂等受控 shutdown。
- 实际结果：
  - `AssistantRuntime` 新增由 `RuntimeConfig::event_capacity` 控制的有界 broadcast Event Hub；
    subscriber 缺失、drop 或 lag 都不会反压 AgentExecution，调用方可重新查询 Session/Run 快照。
  - Session 创建、Run 接受/开始/取消/完成，以及 Core 的文本、reasoning、工具提出/开始/输出/完成
    被显式投影为 `assistant-protocol::RuntimeEvent`；Core 终态事件不产生第二个 Runtime 终态，
    `RunFinished` 只由 completion 结算后发布。
  - Run 快照实时累计 reasoning、正文和工具 stdout/stderr；正常完成时用最终 AssistantMessage 校准
    正文与 reasoning，失败和取消不会清空已经观察到的部分结果。
  - `cancel_run` 使用 Run 登记时即存在的子 CancellationToken，消除控制句柄稍后挂接的竞态；首次
    取消进入 Cancelling 并发布事件，重复取消及终态后取消幂等返回稳定快照，ActiveRun 仍由唯一
    supervisor 在可靠结算后清理。
  - 所有 Run supervisor 登记到 Runtime 级 `TaskTracker`；不同 Session 可并发等待模型或工具，
    同一 Session 继续以 Busy 明确拒绝并发写入，不为 Session 或历史记录保留常驻 task/线程。
  - shutdown 通过生命周期读写门禁与 start_run 的 supervisor 登记形成原子边界：进入
    ShuttingDown 后关闭任务登记、标记并取消活动 Run、等待 TaskTracker 清空，再进入 Stopped；
    重复 shutdown 幂等。Runtime Drop 不冒充完整异步 shutdown。
- 验证：
  - `cargo test -p assistant-runtime -p agent-testkit`：Runtime 20、Testkit 77，合计 97 passed；
    覆盖事件映射与唯一终态、慢/丢弃/lag 订阅者、跨 Session 并发、取消隔离与幂等、Session 复用、
    shutdown 等待，以及 start_run/shutdown 竞态。
  - `cargo clippy -p assistant-runtime -p agent-testkit --all-targets --all-features -- -D warnings`：通过。
  - `cargo tree -p assistant-runtime --depth 2`：通过；Runtime 依赖保持向 Agent/Protocol 下行，没有
    Host、Tauri、具体 Provider、socket 或平台实现依赖。
  - `cargo fmt --all --check`、`git diff --check`：通过。
- 偏差：为了不丢失 completion 已经就绪前缓冲的 Core 观察事件，supervisor 使用 event-first 的
  biased select 排空当前可用事件，但 completion 仍是唯一终态来源，且不会等待事件流额外关闭。
- 遗留与风险：Event Hub 仍是无 sequence、无持久化、无 replay 的实时观察通道；Host writer 背压、
  Unix Socket、私有 Demo 与进程关闭顺序属于 M5，正式 Repository/恢复仍不在 v0.8.0 范围内。

## M5：Unix Socket Host、私有 Demo 与安全装配

- 状态：✅ 已完成
- 计划产出：Unix Socket 私有 frame/握手、单活动客户端、命令与事件转发、单实例与 owned endpoint
  清理、显式 Provider/Agent/echo 工具安全装配，以及 feature-gated Demo 客户端。
- 实际结果：
  - Runtime Host 新增显式 `serve`/feature-gated `demo` CLI，装配 DeepSeek OpenAI-compatible
    Provider、每 Session Agent Factory、`echo_text` 和只精确允许该工具的 fail-closed
    `default_authorizer`；credential 不进入 wire 或普通输出。
  - 实现 4-byte big-endian 长度前缀、1 MiB 上限、JSON 私有 envelope、5 秒握手和协议版本校验；
    Runtime Command/Result 复用 Protocol，Conversation 查询、请求 ID 和握手保持 Host 私有。
  - 单活动客户端连接使用独立的可靠响应队列与可丢实时事件队列，优先发送响应；事件队列满或
    broadcast lag 不反压 Runtime。连接断开不取消 Run，第二个客户端可重连查询和取消。
  - endpoint 新建父目录设为 `0700`，稳定实例锁与 socket 设为 `0600`；既有目录必须已经是
    私有目录，不修改 `/tmp` 等共享目录。原握手探测方案在单活动客户端已连接时可能误判实例，
    已按 Review 结论改为标准库内核独占锁。lock 文件长期保留但进程结束时内核自动释放锁；只有
    成功取得锁的 Host 才能替换异常退出遗留的 Unix Socket，普通文件、目录与符号链接保持原样。
  - Runtime shutdown command、Ctrl-C 和测试 teardown 进入 Runtime shutdown；即使客户端发出
    shutdown 后先断开，Host 仍会完成关闭。TUI 的 `Q` 只结束本地客户端，`Ctrl+Q` 需要确认后
    才请求关闭 Runtime。
  - M5 Review 后把 Host 的进程启动参数从手写分支解析改为 `clap` 派生解析，由成熟库统一生成
    help、校验子命令、必填值和正整数。
  - 第二轮 Review 认为逐行 REPL 仍要求记忆命令和手工管理 ID，已修订功能设计、技术方案与开发
    计划，并已使用 `ratatui + crossterm + tui-input` 替换为单屏私有 TUI。TUI 自动创建/选择
    Session，提供消息输入、Run 增量展示、取消、手动重连、本地退出和确认关闭 Runtime；本地
    状态只负责展示，权威事实仍由 Runtime 快照和事件提供。
  - `Conversation / Run` 原先按逻辑行数计算滚动范围，长 reasoning/正文在终端折行后无法滚到底；
    已改为复用 Ratatui 的实际折行行数，补充右侧滚动条，并保持底部自动跟随与 `PgUp/PgDn` 回看。
- 验证：
  - `cargo test -p assistant-runtime-host`：18 passed；正式构建不带私有 TUI 依赖和模块。
  - `cargo test -p assistant-runtime-host --all-features`：31 passed；覆盖 frame、CLI、endpoint、
    握手、单实例、受控关闭、超限连接隔离、真实 Run 断线续跑/重连取消，以及 TUI 状态更新、
    多会话事件隔离、大小终端渲染和长内容视觉折行滚动；endpoint 测试额外覆盖实例锁互斥、
    stale Unix Socket 替换、未知 endpoint/lock 类型保护、权限及 identity cleanup。
  - `cargo test --workspace`：通过，全部 workspace 单元测试、集成测试和 doc-test 无失败。
  - `cargo clippy --workspace --all-targets --all-features -- -D warnings`：通过，包含 Host 的全部
    feature/target 及所有既有 workspace 消费者。
  - `cargo tree -p assistant-runtime-host --depth 3`：通过；Host 仅向 Protocol、Runtime、Agent、
    Provider 和通用基础库下行，不依赖 Desktop/Tauri 或本地 HTTP server。
  - `cargo doc -p assistant-runtime-host -p assistant-runtime --no-deps`、`cargo fmt --all --check`、
    `git diff --check`：通过。
  - macOS 双进程人工验证：临时 Runtime 目录为 `0700`；Ratatui 客户端自动连接并创建第一个
    Session，`Q` 退出后 Host 继续运行且终端恢复，重新连接后 `Ctrl+Q`/Enter 受控关闭 Host，
    endpoint 被清理，临时目录已移除。
  - macOS 异常恢复人工验证：Demo 占用唯一客户端连接时，第二个 Host 仍立即以实例锁返回
    `AlreadyRunning`；对测试 Host 执行 `SIGKILL` 后 socket 与 lock 文件均保留但内核锁释放，
    同一路径的新 Host 自动替换 stale socket 并成功启动；随后 Ctrl-C 清理 socket、保留稳定
    lock 文件。验证专用临时 lock 文件和目录已显式移除。
- 偏差：技术方案原物理树把 frame 单列为 `transport.rs`；实现按责任使用 `endpoint.rs` 承载
  socket 所有权与安全语义，`wire.rs` 同时承载长度 frame 和私有 envelope，避免增加空转包装层，
  功能与依赖边界不变。M4 Review 后 Runtime/Host 字段明确命名为 `default_authorizer`，并记录它
  只是无工作模式时的 v0.8.0 安全默认值。
- 遗留与风险：尚未执行真实 Provider 请求，这是 M6 的明确任务；事件仍无 sequence/replay，状态
  仍只在内存中，Host 尚未成为系统 daemon，均为本版本确认的非目标。

## M6：真实 Provider 联调、全量回归与验收准备

- 状态：✅ 已完成
- 计划产出：真实多轮对话、`echo_text` 工具闭环、双 Session、取消、断线恢复查询、受控关闭、
  十四条验收标准证据、文档收口和全工作区回归。
- 实际结果：
  - 使用独立临时 Runtime 目录和真实 DeepSeek Provider 创建两个不同 Session；Session A 连续完成
    两轮上下文对话，Session B 完成 `echo_text` 调用，Run 快照记录工具为 `completed`，在线事件按
    `ToolProposed → ToolStarted → ToolCompleted` 到达。
  - 活动 Run 在接受后立即取消并结算为 `cancelled`，`cancel_requested = true`，未提交未完成正文；
    同一 Session 随后成功完成新 Run，证明取消后门禁释放。
  - 另一个真实 Run 接受后主动断开客户端，三秒后重新握手并通过 `GetRun` 查询到 `completed`；
    最后通过 `ShutdownRuntime` 得到 `stopped`，Host 正常退出并清理 socket。验证只记录状态、字符数
