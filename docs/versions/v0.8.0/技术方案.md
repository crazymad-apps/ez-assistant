# v0.8.0 技术方案：Assistant Runtime 初始化

## 一、方案信息

- 版本：`v0.8.0`
- 状态：已确认
- 关联功能设计：[`功能设计`](功能设计.md)
- 影响范围：`assistant-runtime`、`assistant-protocol`、新增正式 Runtime Host、workspace 与模块约束
- 实施原则：建立最小真实进程与 Agent 闭环，不引入持久化、正式桌面客户端或后续业务模块

## 二、现状核查

### 2.1 现有 Runtime 与 Protocol

`crates/assistant-runtime` 当前只有 `config.rs`、`run.rs`、`scheduler.rs`、`session.rs` 四个占位
模块，`lib.rs` 仍写着“直接运行在 Tauri 主进程内”。`crates/assistant-protocol` 只有 crate 说明，
没有公共 ID、状态或命令。两者尚未形成需要兼容的实现。

本版本不沿用旧占位模块隐含的单进程和 Scheduler 范围：

- `assistant-runtime` 作为与部署无关的应用业务 library 实现。
- 空 `scheduler.rs` 从本版本公共模块中移除；Scheduler 以后在有真实调用方时重新设计。
- `assistant-protocol` 只加入本版本已经存在跨进程消费者的最小契约。

### 2.2 可直接复用的 Agent 能力

- `agent-sdk::Agent` 已持有冻结的 `ExecutionSpec` 与执行入口，不保存动态 Conversation。
- `Agent::start` 接收完整 `ExecutionInput` 和含 cancellation、Recorder、Authorizer 的
  `ExecutionContext`。
- `AgentExecution` 提供独立事件流、completion 和取消控制，Core 不持有业务 ID。
- `ExecutionOutcome::Completed` 携带最终 AssistantMessage；最终纯文本消息由 Runtime 落账。
- 工具中间轮通过 `ExecutionRecorder::begin_tool_exchange/complete_tool_exchange` 两阶段提交。
- Core 事件是可丢观察流，唯一执行结果由 completion 可靠返回。

Runtime 必须围绕这些既有边界编排，不复制 Agent Loop，也不能仅依赖事件流重建 Conversation。

### 2.3 Demo 参考边界

`core-demo`、`runtime-harness` 等已经验证过内存 Session、Run gate、Recorder 和事件展示，但它们的
类型、HTTP/SSE DTO、JSON Store、配置和状态机均保持私有。本方案只参考已经验证的行为顺序，
正式类型重新从 Runtime 责任出发定义。

## 四、物理组织

### 4.1 新增正式 Runtime Host

新增：

```text
apps/runtime-host/
├── Cargo.toml
└── src/
    ├── main.rs              # serve/demo 子命令和进程退出码
    ├── config.rs            # CLI/env 启动配置与校验
    ├── server.rs            # 本地连接、命令分发和受控关闭
    ├── endpoint.rs          # Unix Socket 所有权、单实例与安全清理
    ├── wire.rs              # frame 读写及私有握手/request/response/event envelope
    ├── resources.rs         # Provider、AgentFactory、测试工具装配
    ├── demo.rs              # feature 控制的 TUI 启动、UDS 连接与异步事件循环
    └── demo/
        ├── app.rs           # 私有展示状态、Runtime frame 投影与用户 Action
```

`endpoint.rs` 隔离平台 endpoint 的所有权与文件系统安全语义；长度前缀和私有 envelope 都属于同一
wire 契约，因此由 `wire.rs` 一并承载，不增加只有转发作用的 `transport.rs` 包装层。

Cargo package 名称使用 `assistant-runtime-host`，正式 binary 名称使用
`ez-assistant-runtime`。它是产品进程入口，不放入 `tools/`。

实现该 package 前先新增 `docs/modules/runtime-host.md`，并把路径、Rust 规范和模块约束登记到根
`AGENTS.md`；随后才把 package 加入 workspace。模块约束至少固定“产品进程入口、不得持有第二份
业务状态、不提供本地 HTTP、Demo feature 不构成产品契约”四项边界。

为避免为一次验证新增 Client crate，开发客户端作为同一 binary 的 `demo` 子命令存在，并通过
`demo-client` feature 编译：

```bash
cargo run -p assistant-runtime-host -- serve
cargo run -p assistant-runtime-host --features demo-client -- demo
```

正式发布构建不启用 `demo-client`。Demo 的 TUI 状态、快捷键、私有详情查询和 wire envelope 不形成
公共 API。

## 五、Assistant Runtime 公共入口

### 5.1 构造依赖

Runtime 构造时显式接收：

```rust
pub struct RuntimeConfig {
    pub event_capacity: NonZeroUsize,
}

pub trait SessionAgentFactory: Send + Sync {
    fn create_agent(&self) -> Result<Agent, AgentFactoryError>;
}

pub struct AssistantRuntime { /* private */ }
```

`AssistantRuntime::new` 接收 `RuntimeConfig`、`Arc<dyn SessionAgentFactory>` 和本初始化版本共享的
`default_authorizer: Arc<dyn ToolAuthorizer>`。它只是 v0.8.0 尚无工作模式时的显式安全默认值，
不表示长期把 Authorizer 固定为 Runtime 全局策略；未来 Run preparation 必须从同一份 Run 模式
快照同时生成模型可见的 UserMessage Parts 与该次执行的 Authorizer。不提供隐藏全局单例，不读取
环境变量，也不在 library 内选择 Provider。

`SessionAgentFactory` 是必要的应用装配边界：Runtime 必须为每个 Session 创建独立 Agent，同时
不能依赖具体 Provider。v0.8.0 的工厂同步创建 Agent，因为模型、Prompt、Context Window 和
ToolSet 已在 Host 启动时准备完成；未来需要异步读取 Pinned Memory 时再根据真实调用链演进，
本版本不提前增加异步工厂和初始化参数体系。

### 5.2 最小操作

Runtime 提供以下意图入口：

- 创建 Session。
- 列出 Session 摘要。
- 查询 Session 快照和规范 Conversation。
- 启动用户 Run。
- 查询 Run 快照。
- 取消 Run。
- 订阅实时 Runtime 事件。
- 受控关闭 Runtime。

创建、启动、取消和关闭使用明确命令方法；查询返回拥有值的只读快照，不暴露锁、Agent、取消令牌
或内部 map。

### 5.3 生命周期门禁

Runtime 生命周期为：

```text
Running → ShuttingDown → Stopped
```

`AssistantRuntime` 内部使用短时同步读写门禁协调“注册新 Run”和“开始关闭”：

1. `start_run` 在生命周期读门禁下完成 SessionBusy 检查、UserMessage 落账、ActiveRun 注册和
   supervisor task 注册。
2. `shutdown` 取得写门禁并将状态改为 `ShuttingDown`，此后新 Session/Run 返回
   `RuntimeShuttingDown`。
3. 关闭流程取消 Runtime 根 CancellationToken，已有 Run 的子令牌随之取消。
4. `TaskTracker` 关闭注册入口并等待所有 Run supervisor 完成结算。
5. 生命周期切换为 `Stopped`，Host 才退出进程。

门禁只覆盖内存状态转换，不跨模型、工具、文件或网络 `.await`。

## 六、Session 设计

### 6.1 数据结构

每个 Session 使用一个 `Arc<SessionController>`：

```rust
struct SessionController {
    id: SessionId,
    title: String,
    agent: Arc<Agent>,
    state: Mutex<SessionState>,
}

struct SessionState {
    completed: Vec<ConversationMessage>,
    pending_exchange: Option<PendingExchange>,
    runs: BTreeMap<RunId, RunRecord>,
    active_run: Option<ActiveRun>,
    next_message: u64,
    next_exchange: u64,
}
```

Session 不启动永久 actor task。`Mutex` 只保护短时内存转换，任何 `.await` 都在释放锁后发生。
Session Registry 使用读多写少的 `RwLock<BTreeMap<SessionId, Arc<SessionController>>>`；获取 Session
后立即释放 Registry 锁，Run 期间不持有全局锁。

### 6.2 ID

`SessionId` 和 `RunId` 位于 `assistant-protocol`，使用非空字符串 newtype，wire 形状透明。
Runtime 使用系统随机源生成带类型前缀的短随机标识：Session 为 `s_<12 chars>`，Run 为
`r_<12 chars>`。生成后仍在对应 Registry 内检查碰撞并在必要时重试；格式对调用方不构成契约，
客户端只能把 ID 当作不透明值。

短标识避免进程重启后的递增 ID 冲突，同时保持日志、CLI 和人工核对可读；Message/Part 等内部
规范 ID 使用相同生成机制和各自前缀。

### 6.3 Agent 生命周期

创建 Session 的顺序是：

```text
分配 SessionId
→ SessionAgentFactory 创建新 Agent
→ 构造空 Conversation
→ 原子插入 Session Registry
→ 发布 SessionCreated
```

工厂失败时不插入半成品 Session。Agent 创建后保持冻结，直到 Session 生命周期结束；不同 Session
的 Agent 可以共享 Host 工厂持有的线程安全 ModelService、ToolSetSnapshot 和其他底层能力。

## 七、Conversation 与 Recorder

### 7.1 单一权威状态

SessionState 中的 `completed` 是 v0.8.0 唯一规范 Conversation。`pending_exchange` 是工具副作用
前已确认但尚未完成的恢复事实，不进入任何 `ConversationSnapshot`。

启动 Run 在同一个 Session 锁临界区内完成：

```text
确认无 ActiveRun 和 pending exchange
→ 校验用户文本非纯空白但保留原始内容
→ 创建并追加 UserMessage
→ 从 completed 克隆 ConversationSnapshot
→ 注册 RunRecord 与 ActiveRun
```

因此不存在 Agent 已启动但 UserMessage 尚未进入规范历史的窗口。

### 7.2 RuntimeRecorder

每个 Run 创建一个绑定 `SessionController + RunId` 的 `RuntimeRecorder`：

```text
begin_tool_exchange
→ 校验当前 ActiveRun 和无 pending
→ 保存完整 AssistantMessage、RunId 和 ExchangeReceipt
→ 返回 receipt

complete_tool_exchange
→ 校验 receipt 与 RunId
→ 在一个 Session 锁临界区内追加 AssistantMessage + 完整 ToolMessage 批次
→ 清除 pending
```

任何 snapshot 只克隆 `completed`。Recorder 不持有数据库、文件或 Host 连接。

### 7.3 最终 AssistantMessage

Core 的工具中间轮由 Recorder 结算；没有后续工具调用的最终 AssistantMessage 只从
`ExecutionOutcome::Completed(message)` 得到。Run supervisor 是唯一最终消息提交者：

```text
Completed(message)
→ 校验当前 ActiveRun
→ 追加最终 AssistantMessage
→ 更新 RunRecord
→ 清除 ActiveRun
→ 发布唯一 RunFinished
```

AgentEvent 中的终态消息只用于观察和丢失计数，不能再次写入 Journal。这样避免 Recorder、事件流
和 completion 三条路径重复提交。

### 7.4 异常不变量

正常的模型、工具、预算失败与取消不会回滚已完成消息，Session 在 Run 结算后继续可用。
`RuntimeRecorder` 的 receipt/run 不匹配或锁状态矛盾表示 Runtime/Core 契约被破坏，不作为普通
模型错误恢复：对应 Session 标记为内部故障并拒绝后续 Run，Host 记录脱敏错误。v0.8.0 不伪造
数据库式恢复能力。

## 八、Run 并发与监督

### 8.1 Run 状态

公共 Run 状态：

```text
Accepted → Running → Completed
                   ├→ Failed
                   ├→ Cancelled
                   └→ CompactionRequired

Accepted / Running → Cancelling → Cancelled 或 Failed
```

终态不可再次改变。取消终态 Run 是幂等查询；取消不存在的 Run 返回 `RunNotFound`。

### 8.2 同 Session 门禁

`start_run` 在 Session 锁内检查 `active_run`。存在活动 Run 或 pending exchange 时立即返回
`SessionBusy`，不写入第二条 UserMessage，也不创建排队记录。

取消只设置 Run 状态为 `Cancelling` 并触发 CancellationToken；直到 supervisor 完成 Core 收敛、
Journal 结算和 ActiveRun 清理之前，Session 仍然忙碌。

### 8.3 不同 Session 并发

每个 Run 只创建一个 Runtime supervisor task；Core 内部仍只有自己的单一 Engine task。Runtime
不创建 Session 永久 task，也不为 Session 分配线程。所有 supervisor 注册到同一 `TaskTracker`，
由 Tokio 调度并在 shutdown 时统一等待。

### 8.4 Supervisor 单一结算路径

Supervisor 在同一个 task 中同时 poll Core 事件流和 completion：

```text
completion = pin(catch_unwind(completion))
loop {
    tokio::select! {
        event = events.next()    → project_non_terminal_event(event)
        outcome = &mut completion → break outcome
    }
}
→ drop events
→ settle_outcome_once()
```

- 非终态 AgentEvent 更新 Run 的观察投影后广播 RuntimeEvent。
- Core 终态事件不修改 Run 终态；若先于 completion 被观察到也只作为诊断事实。
- completion 唯一决定 Completed/Failed/Cancelled/CompactionRequired。
- completion 收敛后不等待事件流额外关闭，直接丢弃 receiver，避免异常残留 sender 拖住 Run 结算。
- completion panic 被转换为脱敏 Runtime internal failure，清理 ActiveRun，不能让 Session 永久忙碌。
- `CompactionRequired` 直接结算为 Run 终态，不启动压缩或 continuation。

## 九、Runtime 事件与快照

### 9.1 Event Hub

Runtime 使用有界 `tokio::sync::broadcast` 发布实时观察事件，容量由 `RuntimeConfig` 显式传入。
没有订阅者或订阅者落后时，发送不能阻塞 AgentExecution；慢客户端通过查询快照重新对齐。

本版本不分配事件 sequence、不持久化事件，也不增加 replay cursor。

### 9.2 RuntimeEvent 投影

`assistant-protocol` 定义产品层事件，不直接序列化 `AgentEvent`。最小事件包括：

- `RuntimeShuttingDown`
- `SessionCreated`
- `RunAccepted`
- `RunStarted`
- `RunCancelling`
- `TextDelta` / `ReasoningDelta`
- `ToolProposed` / `ToolStarted` / `ToolOutput` / `ToolCompleted`
- `RunFinished`

所有 Run 事件携带 `SessionId` 和 `RunId`。PartId、ToolCallId 和 MessageId 在应用协议中使用独立
newtype，由 Runtime 显式转换，不让 `assistant-protocol` 依赖 `agent-types`。

### 9.3 快照

稳定共享快照控制在：

```rust
SessionSummary {
    session_id,
    title,
    active_run_id,
    message_count,
}

RunSnapshot {
    run_id,
    session_id,
    status,
    cancel_requested,
    reasoning,
    text,
    tools,
    error,
}
```

运行中的 `reasoning/text/tools` 是观察投影，可能因 Core 事件背压不完整；Completed 时使用最终
AssistantMessage 重新校准最终文本。规范 Conversation 仍由 Runtime Journal 持有。

## 十、Assistant Protocol

### 10.1 公共契约

本版本加入：

- `SessionId`、`RunId`、应用层 `MessageId/PartId/ToolCallId`。
- 初始化协议常量 `PROTOCOL_VERSION = 1`，仅用于 Host 私有握手的兼容检查。
- `RuntimeLifecycle`、`RunStatus`、`ToolActivityStatus`、`ToolOutputChannel`。
- `CreateSession`、`ListSessions`、`GetSession`、`StartRun`、`GetRun`、`CancelRun`、
  `ShutdownRuntime` 的 request/result DTO。
- `SessionSummary`、`RunSnapshot`、`ToolActivitySnapshot`。
- `RuntimeEvent`。
- `RuntimeErrorCode` 和安全的 `RuntimeErrorInfo`。

命令表示用户或客户端意图，事件只表示已发生事实。enum 使用显式 serde tag 和 snake_case，
newtype 使用透明 wire 形状。

### 10.2 错误映射

稳定错误码至少包括：

- `invalid_request`
- `session_not_found`
- `session_busy`
- `run_not_found`
- `runtime_shutting_down`
- `agent_build_failed`
- `internal`

Runtime 内部错误保留 source；Host 只把稳定 code 和脱敏 message 发给客户端。Provider 响应正文、
prompt、credential、工具完整输出和 panic payload 不进入错误 DTO。

### 10.3 兼容范围

`assistant-protocol` 在 `0.x` 初始化阶段不承诺跨版本 wire 兼容，但每个已有字段的当前含义必须
稳定并有 round-trip 测试。新增正式桌面需求时扩展产品 DTO，不把 Host 私有 envelope 或完整
Agent Conversation 直接提升为协议。

## 十一、本地进程通信

### 11.1 传输选择

v0.8.0 在 macOS/Linux 使用 Tokio Unix Domain Socket：

- 不监听 TCP 端口。
- 不引入 Axum、HTTP、SSE 或 WebSocket。
- `assistant-runtime` 和 `assistant-protocol` 保持平台无关。
- Host 的非 Unix 构建返回明确 `UnsupportedPlatform`；Windows Named Pipe 留待正式桌面接入版本。

Socket 路径由 `--runtime-dir` 或等价启动配置显式确定，默认使用当前用户临时目录下的短路径，避免
macOS Unix Socket 路径长度问题。Host 创建的目录权限为 `0700`，socket 与同目录实例锁文件权限
均为 `0600`。

本版本不增加访问 token：socket 只允许当前操作系统用户访问，同用户进程本身拥有等价本地权限。
credential 永不进入 IPC。

### 11.2 Frame

私有 wire 使用：

```text
4-byte unsigned big-endian payload length
+ UTF-8 JSON payload
```

- 最大 payload 固定为 1 MiB；零长度、超限、无效 UTF-8 或非法 JSON 关闭当前连接。
- 读写使用 Tokio `AsyncReadExt/AsyncWriteExt`，不手写不受限缓存。
- 长度前缀允许消息正文包含换行，同时避免依赖 JSONL 扫描。
- frame 和 envelope 位于 Runtime Host，不进入 `assistant-protocol`。

### 11.3 握手与 envelope

首帧必须是：

```text
Hello { protocol_version, client_name }
```

服务端返回：

```text
HelloAck { protocol_version, runtime_version }
```

版本不一致时返回错误并关闭连接。后续私有 envelope 为：

```text
ClientFrame::Request { request_id, command }

ServerFrame::Response { request_id, result }
ServerFrame::Error    { request_id, error }
ServerFrame::Event    { event }
```

`request_id` 只关联当前连接内请求/响应，不是业务 ID。客户端必须允许事件先于某个请求响应到达，
不能假设严格的 response/event 顺序。

### 11.4 连接模型与背压

本版本一次只服务一个活动验证客户端；客户端断开后 Host 返回 accept，允许新的客户端连接。
这不构成多客户端协作契约。

每个连接有一个有界 writer channel：

- Response/Error 使用 await 发送，保证请求有结果或明确断线。
- Event 使用 `try_send`，慢客户端时允许丢弃。
- writer/reader 结束只清理连接任务，不取消 Runtime Run。

连接重建后重新订阅实时事件；不携带 sequence，不补发历史增量。

### 11.5 单实例与 endpoint 清理

单实例所有权与通信 endpoint 分离：

```text
runtime-dir/
├── runtime.lock
└── runtime.sock
```

- Host 打开或创建 `runtime.lock`，使用标准库 `File::try_lock` 获取非阻塞内核独占锁，并在整个
  进程生命周期内持有文件句柄。锁被占用时直接返回 `AlreadyRunning`，不再通过建立第二条客户端
  连接和握手推断实例状态。Runtime Host 明确要求 Rust 1.89 或更新版本，这是该标准库 API 的
  稳定版本边界，不为单个文件锁额外引入依赖。
- `runtime.lock` 是稳定锁载体，允许在正常和异常退出后继续存在；文件存在不代表锁仍被持有，
  进程结束时内核自动释放锁。PID 等文本至多作为诊断信息，不作为所有权依据。
- 取得实例锁后，Host 才能处理同目录、同名的旧 endpoint。已存在且类型确认为 Unix Socket 时
  视为上一次异常退出遗留并删除；普通文件、目录、符号链接等未知类型保持原样并返回安全错误。
- bind 成功后记录 socket 的 device/inode。正常 shutdown、启动失败回滚和 Ctrl-C 只删除仍与
  本实例 identity 相同的 socket，不删除稳定的 lock 文件或已被替换的路径。
- 父目录必须为 `0700`，lock 与 socket 必须为 `0600`。Host 不修改既有共享目录权限。

该方案同时解决强制终止后的 stale socket，以及单活动客户端占用连接时握手探测误判实例状态的
问题。

## 十二、Runtime Host 装配

### 12.1 启动配置

Host 首版只使用显式 CLI 与环境变量；进程启动参数使用 `clap` 派生解析，Demo 运行后由 Ratatui
单屏界面接收快捷键和文本输入，不再解析 `session use`、`run show` 等字符串命令：

- Runtime endpoint/runtime dir。
- Provider endpoint、model、credential 环境变量。
- context window 和必要模型请求配置。
- 是否启用开发 Demo feature。

Host 启动时一次校验，失败即退出；不实现配置文件合并、动态刷新和 UI 配置页。API Key 不打印、
不写普通配置、不发给 Demo，也不进入 Shell 环境。

### 12.2 AgentFactory

Host 构造一个共享 ModelService、SystemPromptSnapshot、ContextWindowEvaluator 和
ToolSetSnapshot。每次创建 Session 时，工厂使用它们构造新的 `AgentBuilder`/`Agent`：

```text
shared model + cloned frozen inputs
→ AgentBuilder
→ Agent
→ SessionController
```

Host 不缓存一个 Agent 给多个 Session。

### 12.3 验证工具与 Authorizer

Host 注册一个无文件、Shell、网络或持久副作用的私有 `echo_text` 工具，用于证明真实 Tool Loop。
默认 Authorizer 按工具名只允许 `echo_text`，所有其他已解析调用返回 Deny；未知工具由 Core 按既有
协议错误结算。

该 Authorizer 不读取 Plan/Build、Ask/Auto、工作区或信任规则，也不成为未来权限模式基础类。

### 12.4 Demo 子命令

`demo` 使用 `ratatui` 渲染、`crossterm` raw mode/EventStream 接收异步终端事件、`tui-input` 管理
Unicode 文本缓冲和光标，不自行实现终端绘制、按键解码或文本编辑器。终端 guard 必须在正常退出、
连接错误和事件循环错误时恢复 raw mode 与 alternate screen。

界面固定为单屏四个区域：

```text
┌ Sessions ──────┬ Conversation / Run ──────────────────┐
│ 会话列表        │ 规范消息、实时文本和工具阶段         │
├─────────────────┴──────────────────────────────────────┤
│ 输入消息                                             │
├────────────────────────────────────────────────────────┤
│ 连接状态 | Run 状态 | 快捷键提示                       │
└────────────────────────────────────────────────────────┘
```

交互固定为：启动时查询 Session，空列表时创建默认 Session；导航焦点下使用上下键选择 Session、
`N` 创建 Session、`R` 在断线后手动重连并查询快照、`Q` 只退出 Demo；`Tab` 在会话列表和输入区
切换，输入区按 `Enter` 发送，普通字符始终进入文本缓冲；`Ctrl+C` 取消活动 Run；`Ctrl+Q` 打开关闭
确认层，`Enter` 确认后请求关闭 Runtime，`Esc` 取消确认或返回导航焦点。运行中收到的 response 和
RuntimeEvent 与终端输入在同一个异步 update loop 中转成私有 `Action`，渲染函数只读取 `DemoApp`，
不得执行 UDS I/O 或 Runtime 命令。

`Conversation / Run` 按 Ratatui 实际折行后的视觉行计算滚动范围，并显示垂直滚动条；`PgUp/PgDn`
向上回看或向下返回，位于底部时随新增 Run 内容自动跟随到底部。

Demo 不做自动重连、历史事件补取、多客户端协作、认证或正式错误文案。连接恢复后以快照覆盖本地
事实投影；本地只保留选中项、输入缓冲、滚动位置和临时提示。

## 十三、关闭与异常处理

### 13.1 正常关闭

```text
ShutdownRuntime / Host 进程 Ctrl-C
→ Host 停止 accept 新客户端
→ Runtime 状态改为 ShuttingDown
→ 拒绝新 Session/Run
→ 取消所有活动 Run
→ 等待 TaskTracker 清空
→ 发送/打印关闭结果
→ 删除 owned socket
→ 关闭 lock 文件句柄并由内核释放实例锁
→ 进程退出
```

v0.8.0 只有“取消活动 Run 后关闭”一种产品语义，不提前加入 Graceful/Force 多模式。操作系统强杀
不属于 Runtime 协议。

### 13.2 客户端断开

reader/writer 或 Demo 进程结束时，只取消该连接的事件转发任务。Runtime、Session、Run、Recorder
和 Provider 请求都不持有连接对象，因此继续运行。

### 13.3 任务 panic 与通道关闭

- Runtime supervisor 使用 `catch_unwind` 把 Core completion panic 转成 `internal` Run 失败并清除
  ActiveRun。
- Event subscriber 关闭或 broadcast lag 不改变 Run outcome。
- Host writer 失败只关闭客户端连接。
- Runtime 内部 Journal 不变量错误使 Session 进入内部故障状态，不能伪装成普通成功或继续使用
  可能不配对的 Conversation。

优先复用 workspace 已有依赖，不新增 HTTP、UUID、数据库或 logging framework；Runtime Host 的

## 十五、测试与验证

### 15.1 `assistant-protocol`

- 所有 ID newtype 非空校验和 serde 透明 round-trip。
- Command/Response/Event 使用显式 tag 的 JSON round-trip。
- RunStatus、错误码和可选字段语义。
- 不依赖 Agent、Runtime、Tokio 或 Tauri 的依赖检查。

### 15.2 `assistant-runtime`

使用 scripted model、可控工具、barrier/channel 和 fake factory：

1. 创建两个 Session 得到两个不同 Agent 和独立 Conversation。
2. UserMessage 在模型收到 Snapshot 前已经落账。
3. 纯文本 Completed 只提交一次最终 AssistantMessage。
4. Tool Call 在副作用前 begin，完整 ToolResult 批次后才进入 Snapshot。
5. 失败和取消保留已完成消息，不暴露 pending exchange。
6. barrier 阻塞 Run 1 时，同 Session Run 2 返回 `SessionBusy` 且不追加 UserMessage。
7. 两个 Session 通过 barrier 证明并发，不使用 sleep 推断。
8. 取消传播后 ActiveRun 清除，Session 可启动下一 Run。
9. CompactionRequired 结算为终态且不启动第二次 AgentExecution。
10. drop Runtime event receiver 不取消执行。
11. completion panic/异常结束不会让 Session 永久 busy。
12. shutdown 拒绝新 Run、取消活动 Run并等待 TaskTracker 清空。

### 15.3 Runtime Host

在临时目录使用真实 Unix Socket 验证：

- 握手成功与版本不匹配。
- request/response 关联和实时事件。
- 无效、超限和截断 frame。
- 客户端断开后 Run 继续，重新连接可查询快照。
- 第二个 Host 在客户端已连接时仍由内核锁准确识别为 `AlreadyRunning`。
- 模拟强制终止后，下一 Host 自动取得已释放的锁并替换 stale Unix Socket。
- 同名普通文件、目录或符号链接不作为 stale socket 删除。
- Runtime shutdown 请求和 Host 进程 Ctrl-C 清理 socket。
- runtime 目录、lock 文件和 socket 权限。
- TUI 的 Action/update 测试覆盖 Session 选择、发送、取消、断线、手动重连和关闭确认；渲染测试使用

### 15.4 人工真实链路

1. 启动配置真实 Provider 的 Runtime Host。
2. 用 Demo TUI 创建并切换两个 Session。
3. 完成一次普通多轮对话。
4. 明确要求模型调用 `echo_text` 并观察 ToolProposed/Started/Completed 与最终文本。
5. 启动一个可控等待 Run，验证取消后 Session 可继续。
6. 在 Run 中按 `Q` 退出 Demo，确认 Runtime 继续；重新进入 Demo 自动查询最终快照。
7. 使用 `Ctrl+Q` 二次确认关闭 Runtime，确认活动 Run 被取消并且进程退出。

## 十七、风险、兼容性与开放项

### 17.1 风险控制

- **双终态/重复落账**：completion 是唯一 Run 结算入口；Core 终态事件只观察。
- **锁与异步死锁**：同步锁只保护短临界区，任何外部 `.await` 前释放。
- **关闭竞态**：生命周期读写门禁保证 Run 注册与 shutdown 不交错遗漏。
- **慢客户端反压 Runtime**：连接事件使用有界通道和 `try_send`，查询快照重新对齐。
- **私有 Demo 固化**：Demo 子命令和 wire 留在 Host，公共 Protocol 只保留稳定应用语义。
- **权限范围漂移**：只允许 `echo_text`，未匹配调用 fail-closed，不实现临时审批模式。
- **stale socket 误删**：只有取得内核实例锁后才能删除 app 私有目录中类型明确的 Unix Socket；
  其他文件类型保持原样并报错。

### 17.2 平台与兼容性

- Runtime library 和 Protocol 保持平台无关。
- Runtime Host v0.8.0 的本地传输验收平台是 macOS；Unix 实现可在 Linux 编译验证。
- Windows Named Pipe、系统服务和 Tauri 打包不进入本版本。
- 公共协议处于 `0.x`，不承诺跨版本 wire 兼容；业务 ID 和字段含义不得在本版本内静默改变。

### 17.3 开放项

本技术方案没有遗留实现开放项。Windows 传输、正式 Runtime Client crate、持久化、事件补取、
Plan/Build、审批、Workspace、记忆和系统后台生命周期均已经明确归属后续版本，不影响
`v0.8.0` 开发计划编写。
