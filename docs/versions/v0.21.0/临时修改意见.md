## Runtime 输入入口与 Channel 路由需要统一

### 当前问题

当前实现存在两个相互关联的问题：

1. `AssistantRuntime::resolve_current_controller_channel_session` 直接把 Device Channel 的目标解析为
   当前产品主控会话，`submit_session_channel_input` 又要求传入的 `session_id` 必须等于当前
   `SessionRole::Controller`。这使“本版本终端默认进入主控”的产品路由策略进入了 Runtime 通用输入链。
2. Runtime 将 Desktop `submit_input` 与 Device `submit_session_channel_input` 设计成两个平行业务入口，
   但二者最终都进入 `submit_input_with_source`，本质上仍是同一个 Session Input 用例。Desktop 本身也是
   Channel；未来 Remote、Web、Mobile 和 IM 不应继续通过新增平行提交函数接入。

上述拆分弱化了 Session 作为顶层兼容实体的语义，也容易把业务角色 `Controller` 与技术类型
`SessionController` 混淆。防止来源伪造、限制渠道能力和派生不同幂等身份属于调用边界的认证与校验，
不足以构成多套 Runtime 输入用例。

### 调整结论

- Runtime 只保留一个规范 `submit_input` 用例，统一接受 Desktop、Device 以及未来其他 Channel 的输入；
  不按渠道继续增加平行 Runtime 提交函数。
- 现有 `assistant-protocol::SubmitInputRequest` 继续作为 Desktop/既有协议兼容 DTO。Host Adapter 将其
  归一化为 Desktop Channel，并向 Runtime 单一入口补充可信来源上下文；来源身份不得直接相信外部
  wire payload 中的自报字段。
- Device WSS、未来 Remote/Web/Mobile/IM 同样由各自 Host Adapter 完成认证和归一化，然后调用同一个
  Runtime `submit_input`。渠道能力差异通过结构化来源和准入校验表达，而不是通过函数数量表达。
- Channel 目标选择属于 Host Channel Router 的产品路由职责。Host 使用
  `resolve_channel_input_target_session` 选择目标 Session；本版本策略仍选择当前产品主控，但不固化为
  Runtime 输入核心规则。
- Host 显式向 Runtime 提交目标 `session_id`，且不持有 Session 的第二份权威状态；目标选择读取
  Runtime 已有产品投影或查询结果。
- Runtime 只校验通用输入不变量：目标 Session 存在且可接受输入、结构化来源合法、Device 来源仍为
  paired、渠道能力组合有效、幂等身份稳定，以及 UserMessage/Input/Run 的可靠接受、投影和排队。
- Runtime 不再判断 Channel 目标必须具有 `SessionRole::Controller`。

### 后续统一修改范围

1. 删除 `AssistantRuntime::resolve_current_controller_channel_session`。
2. 删除 Runtime 的平行 `submit_session_channel_input` 入口，将其来源、幂等和准入逻辑合并进唯一
   `submit_input` 用例；现有 Desktop 协议 DTO 在 Host 边界完成兼容适配。
3. 收敛或删除仅为两个入口桥接而存在的 `submit_input_with_source` 层级，避免统一业务入口下继续保留
   无业务意涵的函数分叉。
4. 在 Host Channel Router 内建立 `resolve_channel_input_target_session`，迁移 Device Gateway 调用点，
   并由 Host 向统一 Runtime 入口注入经过认证的 Channel 来源。
5. 保留 Runtime 对 paired Device、目标 Session 状态、结构化来源、渠道能力组合和幂等身份的校验，
   移除“必须是当前 Controller”的硬编码限制。
6. 保持当前产品行为不变：本版本 Host 仍把智能终端输入路由到当前主控会话。
7. 补充 Runtime 与 Host 测试：Runtime 覆盖统一 Session Input 准入、不同可信 Channel 与来源防伪；
   Host 覆盖当前主控路由策略和 Desktop/Device 适配。
8. 统一修订以下正式文档中“Runtime 解析当前 Controller”以及 Desktop/Device 平行入口的表述：
   - `技术方案.md`
   - `技术方案附件B-Conversation与回复路由.md`

## 隐藏补播必须是同 Run 结算前的最后门禁

### 当前问题

当前 `run/settlement.rs` 在原 Run 已准备结算时创建新的 `NewStoredInput` 和 Run，先把原 Run 提交为
终态，再通过 `accept_input` 接受隐藏补播 Input。外层随后发布新的 `RunAccepted`，由普通 Queue 在原
`active_run` 已清除后执行补播。恢复逻辑还需要专门识别并丢弃 queued speech reminder。

这把“轮内提醒模型补充调用 `speak`”错误建模成了新的 Input/Run，并让原 Run 在实际输出周期结束前
提前成为终态。`RunSettlementResult::continuation` 也因此混入了 Goal 自动续跑和 speech reminder；两者
都应在当前 Run 真正结算前由统一的 `RunContinuation` 消费。

### 调整结论

- 隐藏补播属于同一业务 Run 内的 Runtime 定向续跑，保持相同 `RunId`、`active_run`、执行预算和输出周期；
  不创建新的 Input、Run、Queue 项或 `RunAccepted` 事件。
- 补播提醒不是与普通 continuation 平级的常规触发器，而是整个逻辑输出周期准备结束前的最后一道门禁，
  避免在 Tool/Skill 上下文变化、压缩恢复或 Goal 尚需续跑时提前触发。
- Session mutation gate 不需要跨 Provider 调用持续持有，但当前 Run 的逻辑所有权必须保留；只有补播续跑
  完成或门禁明确降级后，才允许正式 `settle_run` 并清除 `active_run`。
- 已进入 Host FIFO 的 `speak` 片段仍是不可回收的易失副作用；它与隐藏补播的同 Run 控制语义分开描述，
  不应在结算层文档中并列成两个结算后机制。

### 门禁顺序

```text
AgentExecution 返回结果
→ 优先处理 Tool/Skill ContextChanged continuation
→ 优先处理上下文压缩 continuation
→ 判断 Goal 是否还会产生 continuation
→ 确认当前逻辑输出周期确实准备结束
→ 检查目标是否真实需要语音且本周期尚未成功 speak
→ 最多一次插入隐藏补播提醒并在同一 Run 续跑
→ 再次完成或明确降级后正式 settle_run
```

补播门禁只在以下条件同时成立时触发：

- 当前执行候选结果为 `Completed`；
- 没有普通同 Run continuation；
- 没有压缩 continuation；
- 没有 Goal continuation；
- 当前输出目标真实需要语音；
- 当前输出周期尚未成功调用 `speak`；
- 当前输出周期尚未触发过补播提醒。

### 后续统一修改范围

1. 把补播门禁从 `run/settlement.rs` 移到 Runtime Run 执行编排中，并放在所有正常续跑判断之后、
   `settle_run` 之前。
2. 增加同 Run 的可靠内部消息提交接缝，原子保存本段最终 Assistant Message 与隐藏 Runtime UserMessage，
   保持 Run 为活动态后继续下一段 AgentExecution。
3. 删除 speech reminder 使用的 `NewStoredInput`、新 Run 分配、`accept_input`、普通 Queue 投影和
   `RunAccepted` 事件。
4. 删除 `RunSettlementResult::continuation`；只要已经生成 `RunSettlementResult`，就代表当前 Run 已经
   真实结束，不能再从结算结果派生同 Run continuation。
5. 删除 queued speech reminder 的恢复期识别、丢弃以及仅为独立 Input 合法化而增加的存储校验分支。
6. 修正 `run/settlement.rs` 模块注释和相关正式设计文档，不再把隐藏补播描述为 Run 结算后的独立机制。
7. 调整测试，验证整个补播过程只有一个业务 Run、原 Run 不会提前发布终态、门禁不会早于普通 continuation
   或 Goal continuation 触发，并且第二次仍未 `speak` 时只降级一次而不循环。

## 统一 Step、Loop、Run 与 RunContinuation 层级

### 概念边界

后续实现和文档统一使用以下层级：用户与 UI 感知的完整执行轮次对应 Runtime Run；不再把 Model Step
或 Agent Loop 混称为“Run”：

```text
Run
├─ Loop 1
│  ├─ Step 1
│  └─ Step 2
├─ RunContinuation
├─ Loop 2
│  └─ Step 3
└─ 所有续跑门禁结束后生成 RunSettlementResult
```

- **Step**：一次真实 Provider/LLM 请求，是模型调用原子。有工具调用和无工具调用的响应都属于 Step；
  无工具调用的 Step 只是当前 Loop 的候选终止 Step。
- **Loop**：一个 `AgentExecution`，由一个或多个 Step 与工具调用组成，直到返回一个
  `ExecutionOutcome`，是 Agent 执行的最小完整单元。
- **Run**：具有唯一 `RunId`、可靠状态和持久化终态的完整业务执行轮次，由一个或多个 Loop 串联组成，
  也是 UI 观察执行状态的稳定单位。
- **RunContinuation**：一个 Loop 结束后，由 Run 编排器决定当前 Run 是否启动下一个 Loop 的内部指令；
  它发生在 Loop 之间，但描述的是 Run 是否继续，因此不能命名为 `LoopContinuation`。
- **RunSettlementResult**：整个 Run 在 Store 可靠结算并同步 Session 内存投影后的 Runtime 内部结果；它
  不是单个 Loop 或单个 Step 的结果，也不是跨协议发送给 UI 的投影 DTO。

### 统一 RunContinuation

所有同 Run 的自动续跑都进入一套 Run 编排机制，不再由 Skill、Goal、工具图片、上下文压缩和补播各自
维护续跑分支，或额外创建 Input、Run、Queue 链路。建议的概念结构为：

```rust
pub(crate) struct RunContinuation {
    pub(crate) reason: RunContinuationReason,
    pub(crate) context: RunContinuationContext,
}

pub(crate) enum RunContinuationReason {
    ToolImageReady,
    SkillActivated,
    GoalProgress,
    ContextCompacted,
    SpeechReminder,
}

pub(crate) enum RunContinuationContext {
    CommittedConversation,
    InjectedUserMessage(UserMessage),
}
```

上述名称只记录当前 Review 的业务语义，最终代码应结合现有私有类型就近收敛，不为该草案机械增加公共
类型或层级。各原因的上下文来源固定如下：

| 原因 | 下一 Loop 的上下文 | 规范持久化行为 |
| --- | --- | --- |
| `ToolImageReady` | `CommittedConversation` | 已有 Tool Result Image Part，不新增规范 UserMessage |
| `SkillActivated` | `InjectedUserMessage` | 先可靠提交隐藏 Skill UserMessage |
| `GoalProgress` | `InjectedUserMessage` | 先可靠提交隐藏 Goal UserMessage |
| `ContextCompacted` | `CommittedConversation` | 使用已经提交的压缩 Conversation |
| `SpeechReminder` | `InjectedUserMessage` | 先可靠提交隐藏补播 UserMessage |

`RunContinuation` 表达执行控制，是否新增规范 UserMessage 是正交的上下文策略。只有在一个 Loop 结束后
为了启动下一个 Loop 而新增的隐藏 Runtime UserMessage 才属于该机制；原始外部 UserMessage 上的
Channel、Agent Variant、WorkPlan 等 Injected Part 仍是输入上下文增强，不属于 continuation。

### Goal 只保留领域状态机

Goal 继续保留 objective、generation、完成、暂停、等待用户和显式恢复等领域状态，但不再拥有一套独立
续跑管道。当前 `StoredGoalSettlementEffect::Continue` 同时承担 Goal 状态变化、隐藏消息构造、新 Input、
新 Run 和入队，职责过度耦合；后续应拆为 Goal 状态变化与普通 `RunContinuation::GoalProgress`。

- Goal 自动继续工作时保持当前 `RunId`，只启动下一个 Loop。
- Goal 暂停或等待用户代表当前 Run 结束；用户以后显式恢复 Goal 时才接受新的外部或控制输入并创建新
  Run，不能把跨用户等待期的恢复伪装为旧 Run continuation。
- Goal 自动续跑与其他同 Run continuation 共用 step 序列、执行预算、取消令牌和 `active_run` 所有权。

### read_image 保持 request-only 图片投影

`read_image` 应复用统一 `RunContinuation` 切换到下一个 Loop，但不能因此改变 v0.17 已确认的图片事实和
协议投影：

1. Assistant Tool Call 和含 `ToolResultPart::Image { relative_path, media_type }` 的完整 Tool Result 批次
   继续可靠进入 Conversation/Store。
2. 图片字节继续只物化到 Session 私有 `tool-images/`，Conversation 不保存 Base64、Data URL、Session
   绝对路径或第二份图片正文。
3. 对 `NativeFunctionOutput` 路由，Adapter 继续把规范 Image Part 投影到原生多模态 Tool Result。
4. 对 `AggregatedUserInput` 路由，Adapter 每次构建 Provider 请求时继续从已落账 Tool Result 批次
   确定性生成 wire-only user-role 图片信封；该信封不分配 MessageId，不写回 Conversation、Journal、
   Store、RuntimeEvent、Run step 或产品消息。
5. Runtime Recorder 在完整 Tool Exchange 可靠提交后识别 Image Part，令当前 Loop 返回需要
   `RunContinuation::ToolImageReady` 的控制结果；Run 编排器重新读取规范 Journal 后启动下一个 Loop，
   Adapter 再按精确协议路由动态生成图片输入。

因此，`read_image` 进入统一 Run continuation 只增加 Loop 边界，不增加新的持久化消息层，也不改变
Conversation 重建、Runtime 恢复、上下文压缩、Session Fork 或图片资源生命周期语义。

### Run 内 step 与预算不变量

- 同一 `RunId` 内所有真实开始的 Model Step 必须严格递增，切换 Loop 后不能从 1 重新编号，也不能重复
  或倒退。
- 工具活动、消息与 usage 继续关联实际 step；没有发起 Provider 请求的 continuation 准备动作不消费
  step。
- Run 的 step/tool budget 跨 Loop 累计消费，不能通过 Goal、图片、Skill、压缩或补播续跑重置预算。
- `RunAccepted` 与 `RunStarted` 每个 Run 只发布一次；内部 Loop 切换不得创建新的 Input、Run、Queue 项，
  也不得再次发布上述事件。

### 禁止向 UI 提前发布轮内 finish

`ExecutionCompleted` 只说明一个 Loop 产生了候选最终响应，`ExecutionContinuationRequired` 也只是 Loop
交接终态；二者都不能直接解释为 Run 完成。正确顺序为：

```text
Loop 返回 ExecutionOutcome
→ 按优先级检查并消费 RunContinuation
   ├─ 存在：提交所需上下文，保持 Run running，启动下一个 Loop
   └─ 不存在：可靠 settle_run，生成 RunSettlementResult，发布唯一 RunFinished
```

- continuation 决策必须发生在 `settle_run`、清除 `active_run` 和发布 `RunFinished` 之前。
- 同 Run Loop 切换期间允许发布 `ConversationCommitted`、`StepCommitted` 和工具活动事件，但 Run 在 UI
  投影中始终保持 `running`。
- 同 Run continuation 不进入正式产品协议；如需观察，只进入诊断或调试事实。UI 只按 `RunId + step`
  聚合流式状态，不感知 Loop 数量、continuation 原因或内部隐藏消息。
- 只有 Store 已提交 Run 终态后才能发布一次 `RunFinished`；不能先发布源 Run finish，再用
  `RunAccepted` 表达 Goal 或补播续跑。
- `RunSettlementResult::committed_step` 只表示最终 Assistant Message 所属 step，并不表示 Run 最后执行
  或提交到哪个 step；应考虑更名为 `final_message_step` 并同步修正文档注释。
- Desktop 收到 `ConversationCommitted`、`StepCommitted` 或 `RunFinished` 后仍通过 `get_session_view`
  获取权威 `SessionViewSnapshot`；`RunSettlementResult` 不直接跨层，也不作为 UI 页面替换数据。

### 后续统一修改范围

1. 在 Runtime Run 执行编排中建立统一 continuation 判定与循环，顺序覆盖 Tool/Skill 上下文变化、压缩、
   Goal 自动继续和最后一道补播门禁。
2. 让同一 Run 的每个新 `AgentExecution` 从累计 `next_step` 和剩余预算启动，补齐图片、Goal、Skill、压缩
   与补播交错场景的严格单调测试。
3. 为 `InjectedUserMessage` continuation 建立可靠提交接缝；Store 成功前不改变内存 Journal，成功后保持
   Run 活动态并开始下一 Loop。
4. 让 `read_image` 完整 Tool Result 批次提交触发通用 continuation 控制结果，但保持现有 request-only
   图片信封与全部存储/重建逻辑不变。
5. 拆除 Goal 自动 continuation 的新 Input/Run/Queue 创建与恢复特殊分支，保留显式恢复 Goal 时创建新
   Run 的正常命令语义。
6. 拆除 speech reminder 的新 Input/Run/Queue 创建与恢复特殊分支，并与本文件上一节的最后门禁规则
   一并实现。
7. 删除 `RunSettlementResult::continuation`，收窄它为真实 Run 终态提交后的内部编排结果；同步评估
   `committed_step` 更名。
8. 修正事件测试：任意数量的内部 continuation 只产生一组 `RunAccepted`/`RunStarted` 和唯一
   `RunFinished`；UI 可仅凭同一 Run 下严格递增的 step 稳定投影。
9. 同步修改正式技术方案、Agent/Runtime 模块约束和相关源码注释，明确 Step、Loop、Run、request-only
   Provider 投影与产品事件边界。
