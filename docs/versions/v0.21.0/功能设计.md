# v0.21.0 功能设计：多终端通信、智能终端与语音交互

## 一、设计信息

- 版本：`v0.21.0`
- 状态：已确认（2026-08-27）
- 版本主题：在既有主控会话和 Runtime 产品协议之上建立多终端通信语义、智能终端接入、
  语音交互与 PC 输出托管闭环。
- 影响模块：`apps/runtime-host`、`apps/desktop`、`crates/assistant-runtime`、
  `crates/assistant-protocol`，以及本版本新增的 Node 智能终端模拟器/H5 交互页。
- 需求来源：
  - [`多终端通信协议与 Gateway 边界讨论`](../../inputs/260827-多终端通信协议与Gateway边界讨论.md)；
  - `agent-robot` 当前 PCM、PTT、WSS 与语音链路验证基线；
  - 2026-08-27 用户会话中确认的设备发现、配对、输入来源、输出偏好、播报 Tool、
    PC 输出托管和模拟终端交互结论。
- 已有基线：`v0.20.0` 已建立主控会话、跨会话代理通信、可靠 Input/Run/Conversation、
  Runtime Event Envelope、HTTP Command + SSE、Queue、审批与恢复语义。

本文件只固定本版本最终应形成的产品能力、使用路径和关键取舍。Gateway 物理模块、协议类型、
媒体帧布局、证书与配对算法、ASR/TTS 配置入口、Provider 接口、存储字段和迁移方式由后续
技术方案基于真实代码进一步确定；具体图标、间距和视觉样式可在实现过程中结合现有界面调整。

## 二、背景与目标

### 2.1 背景

`v0.20.0` 已将主控会话建设为用户统一协调入口，并为消息来源、目标和跨会话报告建立了最小底座。
下一步需要让同一 Runtime 除 Desktop 外，还能接入具有不同输入、输出和连接能力的智能终端。

智能终端与 Desktop 的通信需求不同：Desktop 适合继续使用 loopback HTTP Command、SSE 和
Streaming Upload；语音或带屏终端需要局域网双向连接、设备身份、控制消息和 PCM 媒体流。
本版本不以 WebSocket 全面替换 SSE，而是建立稳定的应用语义边界，再由不同 Channel Adapter
完成各自的连接、投影和媒体处理。

本版本不开发真实智能终端固件。为形成可操作、可观察和可重复验证的闭环，使用一个 Node
智能终端模拟器实现真实设备协议客户端，并以 H5 页面提供虚拟屏幕、麦克风、扬声器、键盘、
状态和诊断交互。

### 2.2 版本目标

1. 在 Runtime Host 产品进程内形成清晰的 Process Host、Message Gateway、Channel Adapter 和
   Assistant Runtime 逻辑职责，保持 Runtime 为 Session、Run 和 Conversation 的唯一权威来源。
2. 保留 Desktop 既有 HTTP Command + SSE + Streaming Upload 契约，为智能终端增加 WSS、
   设备控制消息和 PCM 媒体通道，不把媒体帧伪装成 Runtime Event。
3. 建立设备发现、人工配对、稳定注册、可撤销身份、能力协商、连接和重连的产品闭环。
4. 让智能终端的语音或文字输入可靠进入主控会话，并在既有 Conversation 中保留可解释的来源、
   Input、Run、Assistant Message 和工具事实，不建设第二套对话或投递存储。
5. 在 Host 内接入 ASR/TTS：首版使用阿里百炼服务，并以可替换的平行 Provider 能力为后续服务商
   保留明确边界。
6. 使用播报 Tool 让模型生成适合朗读的压缩文本；允许同轮多次串行调用，每段立即合成并
   按调用顺序排队播放，避免长会话只能等到整轮结束。
7. 支持用户把 PC 端发起的主控回复托管到一台已配对终端，同时保证终端主动输入始终优先回复
   原来源终端。
8. 通过 Node/H5 模拟器完成发现、配对、注册、语音输入、文字输入、文字/语音输出、审批提示、
   重连和协议投影验证。

### 2.3 成功标准

- Desktop 既有主会话和 SSE 体验不因新增智能终端而迁移到 WebSocket 或改变权威恢复语义。
- 已配对模拟终端能够通过语音或文字与主控连续对话，Desktop 能在同一规范 Conversation 中观察
  完整过程和结构化来源。
- 回复目标按“明确来源/报告返回渠道优先、主控默认输出再使用 PC 托管”的规则确定，不发生跨设备误播。
- 长回答保留为完整 Assistant Message，终端按顺序播放播报 Tool 生成的自然分段压缩文本。
- 断线、重试、模型多 step、工具 continuation 和审批等待不会造成重复 Input 或中间内容误播。

## 三、明确非目标

本版本不包含：

- 真实 ESP32 或其他智能终端固件开发、烧录和实机验收；
- Wi-Fi 配网、离线唤醒词、OTA、NVS、Flash Encryption、Secure Boot 或量产凭据写入；
- 以 WebSocket 全面替换 Desktop SSE，或要求全部 Channel 使用同一种 wire transport；
- 将 Gateway 拆为独立产品进程、独立服务或第二套 Runtime Host；
- 多用户、租户、公网接入、多 Runtime 实例路由、IM Channel、通知中心和外部消息 Outbox；
- 让设备绑定或选择任意普通 Session；智能终端本版本统一接入主控会话；
- 在智能终端上处理审批、工具详情、权限配置、Goal、Skill、附件或完整历史管理；
- PC Desktop 正式麦克风、编解码和语音播放实现；本版只预留相同输出偏好语义；
- 离线期间的回答自动补播、跨重启恢复未完成媒体流或长期保存语音；
- 为开发临时音频增加容量管理、TTL、自动清理界面或独立持久化记录；
- 本阶段冻结具体图标、色彩、间距和最终视觉稿。

## 四、产品概念与职责

### 4.1 Message Gateway

Message Gateway 是 Runtime Host 产品进程内的逻辑职责，不是新的权威业务服务。它负责：

- 根据连接和凭据形成可信的终端身份与能力上下文；
- 将不同 Channel 的用户意图映射到现有 Runtime 命令和输入语义；
- 根据输入来源、PC 输出托管和终端能力决定回复目标与输出投影；
- 将 Runtime 事实和权威快照裁剪为各 Channel 能消费且有权消费的状态；
- 维护可丢弃的在线连接和媒体临时状态，不复制 Session、Run 或 Conversation。

Gateway 不接受客户端自报的用户身份、权限或任意投递目标作为信任事实。终端可以声明本轮输入
模态和期望输出形态，但 Host 必须以已认证身份、已协商能力和服务端策略确定最终有效行为。

### 4.2 Channel Adapter

- Desktop Adapter 保留现有 HTTP Command、SSE、Streaming Upload、Bearer Token 和快照恢复。
- Device Adapter 负责局域网服务发现、配对、WSS、设备控制消息、PCM、ASR/TTS、媒体取消和
  终端状态投影。
- Adapter 只解决“如何连接和翻译”；Session、Run、Queue、审批、Conversation 和工具执行仍由
  Runtime 持有权威状态。

`RuntimeEventEnvelope` 继续作为 Runtime 向 Gateway 发布业务事实的基线。Device Adapter 只选取
并转换设备需要的状态，不把完整 Runtime Event、工具参数、权限或 Conversation 历史直接下发终端。

### 4.3 智能终端

智能终端不是“语音设备”的同义词，而是具有可协商输入和输出能力的 Channel Endpoint。首版至少
需要表达以下独立能力：

- 文字输入；
- PCM 音频输入；
- 文字输出；
- PCM 音频输出；
- 播放取消；
- 屏幕或状态展示能力。

终端可以在合法能力范围内按本轮切换 `text`、`audio` 或 `text_and_audio` 输出偏好。输出偏好是
客户端请求，不是身份或授权事实；Host 根据能力协商结果得到实际输出形态。

### 4.4 Node/H5 模拟终端

Node 进程是真正的智能终端模拟器，负责服务发现、设备身份、配对状态、WSS、协议 codec、
重连、PCM 收发和终端交互状态机。H5 只是 Node 的本地交互与观察界面，提供：

- 虚拟屏幕、配对码和设备状态；
- 麦克风/PTT、文字输入、输出偏好和扬声器播放；
- capabilities 切换；
- 控制消息、媒体帧数量、阶段耗时和错误观察；
- 主动断线、重连和重置模拟设备。

H5 不直接连接 Runtime Command/SSE，也不读取完整 Runtime Conversation。它只展示 Node 通过正式
设备协议实际发送、接收和派生的状态，避免绕过 Device Adapter 后掩盖协议或投影问题。

## 五、设备发现、配对与注册

### 5.1 发现与连接方向

- Runtime Host 内的 Device Adapter 在本地局域网宣告可发现服务；
- Node/真实智能终端发现 Host 服务后主动建立出站 WSS；
- Host 不主动扫描并反向连接终端，终端不需要开放入站服务；
- 本版本假设终端和 Host 已处于可互访的同一局域网，不负责 Wi-Fi 配网。

服务发现只解决“在哪里连接”，不代表设备已经获得身份、Session 或操作权限。

### 5.2 配对路径

1. 用户在 Desktop 的智能终端管理入口进入添加/配对状态；
2. 未配对终端发现 Host 并发起受限的配对连接；
3. 终端通过屏幕显示配对码；没有屏幕的终端可以播报配对码；
4. Desktop 展示待配对设备，用户输入终端显示或播报的配对码；
5. Host 验证本次配对后登记稳定、可撤销的设备身份；
6. 设备完成能力协商并进入可交互状态。

配对码只用于本次人工在场确认，不能成为长期连接凭据。配对码长度、有效期、尝试限制、首次 WSS
信任建立、设备凭据签发和撤销方式由技术方案确定。

### 5.3 设备生命周期

- 同一稳定设备身份同时只允许一个有效在线连接；
- 临时断线不删除配对、设备名称或 PC 输出托管状态；
- 新连接替换旧连接时，旧连接应明确退出，避免同一回复被两个连接播放；
- 用户可以在 Desktop 修改设备名称或解除配对；
- 解除配对后，该设备不能继续提交输入或接收输出；若它是 PC 输出托管目标，同时解除托管；
- 已接受的 Runtime Run 不因设备断线或解除配对而回滚，完整结果仍进入主控 Conversation。

### 5.4 Desktop 最小设备管理

Desktop 设置增加“智能终端”入口，首版只需要：

- 启用或停用智能终端接入；
- 进入添加设备/配对状态；
- 查看待配对设备并输入配对码；
- 查看已配对设备及在线/离线状态；
- 修改设备名称；
- 解除配对。

本版本不建设设备仪表盘、消息统计、终端历史、批量操作或任意 Session 绑定选择器。

## 六、输入、主控会话与 Conversation

### 6.1 统一进入主控

- 智能终端的文字和语音输入都作为真实用户输入进入当前产品主控会话；
- 终端不创建或选择普通 Session；需要其他工作会话时，由主控使用 `v0.20.0` 已有代理能力协调；
- Desktop 与多个终端可以共享主控的连续上下文，同一主控中改变 Conversation 的父 Run继续按
  Runtime 既有串行和 Queue 语义执行。

### 6.2 既有 Conversation 扩展

终端交互必须进入既有规范 Conversation，不建设第二套 Device Conversation、Reply Store 或
Delivery Store。现有关系继续构成完整链路：

```text
UserMessage / Input
  └─ input_id 与结构化终端来源
       └─ Run
            └─ Assistant Message 与播报 Tool Call
```

终端来源至少应当让产品稳定解释：

- 来源 Channel 为智能终端；
- 稳定设备身份和当前展示名称；
- 输入模态为文字或音频转写；
- 本轮终端请求的输出偏好；
- Input、Run 与最终 Assistant Message 的既有关联。

同一组可信来源事实还要以产品隐藏、模型可见的内部 Part 随该终端 UserMessage 冻结，使模型明确知道
当前输入来自智能终端、是文字还是语音转写、期望文字/语音/双输出，并据此决定是否调用 `speak`。
Desktop 输入不增加这段渠道上下文，保持既有消息和模型输入行为。

实现可以扩展既有 Conversation/Input/Run 持久事实和产品投影，但不能为同一消息再保存第二份正文、
第二套顺序或另一条恢复生命周期。在线连接 ID 属于易失传输状态，不进入规范 Conversation。

### 6.3 Desktop 来源呈现

主控 Conversation 中的终端 UserMessage 使用低干扰来源标识，例如“客厅终端 · 语音”或
“桌面终端 · 文字”，不把标签写进正文。Assistant Message 沿用规范主控回答，不复制一份
“设备回复消息”。具体图标、标签样式和间距在实现阶段结合现有消息组件调整。

## 七、语音和文字输入

### 7.1 语音输入

语音链路为：

```text
终端开始收音
→ 通过 WSS 上送 PCM
→ 终端明确结束话语
→ Host ASR
→ 形成 transcript
→ Runtime 可靠接受 Input
→ 终端收到 input accepted
```

- ASR 位于 Runtime Host 产品进程内的 Device Adapter/媒体能力，不位于 Node 模拟器或 Runtime Core；
- ASR 成功后自动提交，不增加“确认转写后发送”的首版步骤；
- transcript 可以在终端/H5 和 Desktop Conversation 中显示；本版本不提供转写编辑；
- 无有效语音或 ASR 失败时不创建空 Runtime Input，终端回到可继续输入的状态；
- 同一句话在接受结果不明确时使用稳定身份重试，不能重复创建 Input 或 Run；
- Runtime 接受后，设备断线不取消 Run。

### 7.2 文字输入

- 文字输入是正式智能终端能力，不是绕过协议的 ASR 测试后门；
- Node/H5 使用同一 WSS 设备连接提交文字输入，直接跳过 PCM 和 ASR；
- 文字和语音 transcript 在进入 Runtime 后共享同一 Input、Queue、Run、审批和 Conversation 语义；
- Host 仍需按已认证设备身份和能力校验文字输入，不能接受 H5 直接调用 Runtime。

### 7.3 交互状态

智能终端对用户提供以下最小状态：

```text
空闲 → 收音中 → 识别中 → 已接受/排队中 → 处理中
     → 等待桌面审批 → 合成中 → 播放中 → 空闲
```

文字输入跳过收音和识别。H5 可以展示更细的阶段和诊断，但不能把这些诊断阶段升级为新的 Runtime
业务状态。

- 审批只在 Desktop 处理；终端只提示需要在桌面确认；
- Desktop 处理审批后，原 Run 继续，终端在仍在线且仍是有效目标时接收最终输出；
- 停止播放只取消媒体流，不隐式取消已经完成或仍在执行的 Runtime Run；
- 播放中开始新输入时先停止本地播放，再进入新的输入流程；
- 活动 Run 中接受的新输入继续使用主控既有 Queue，不创建设备专用调度器。

## 八、回复路由与 PC 输出托管

### 8.1 输入来源优先

终端来源、跨会话报告返回渠道和 PC 输出托管是同时存在的正交事实。回复目标按以下
优先级确定：

1. 输入来自智能终端：始终回复该来源终端，并使用本轮输入携带的输出偏好；
2. 主控从某个终端来源轮次向普通会话投递任务：代理报告形成新的主控输出周期，但返回
   原终端，不被 PC 输出托管截获；
3. 输入来自 PC Desktop，或代理报告没有明确外部返回渠道：结算时存在 PC 输出托管则
   发送到托管终端，否则只保留 Desktop 正常呈现；
4. 未来其他 Channel：默认回复原 Channel，不受 PC 输出托管影响。

因此 PC 输出托管不会截获或广播其他终端主动发起的回复，但会承接没有明确外部返回渠道的
主控代理报告。完整 Assistant Message 无论是否成功投递到设备，都进入主控规范 Conversation。

### 8.2 输出偏好

- `text`：向目标终端发送完整 Assistant 文字，不需要语音合成；
- `audio`：向目标终端发送最终播报音频，完整 Assistant 文字仍保留在 Desktop Conversation；
- `text_and_audio`：向目标终端同时发送完整文字和最终播报音频。

默认跟随终端来源时，输出偏好随该 Input 冻结。PC 输出托管时，最终结算使用托管终端当前声明且
经 Host 能力校验的输出偏好，使用户可以在文字、语音和双输出模式之间切换。

### 8.3 PC 输出托管

- 用户只能通过 Desktop 主动把主控的 PC 回复托管到一台已配对终端；
- 同一主控同时最多存在一个 PC 输出托管目标；
- 用户可以切换或解除托管，解除后 PC 回复恢复仅在 Desktop 呈现；
- 切换可以影响尚未投递的当前 PC 轮次和后续 PC 轮次，不影响任何终端来源输入；
- 没有明确外部返回渠道的主控代理报告视为主控默认输出，同样使用结算时的 PC 托管目标；
- 托管终端临时离线时不自动改投其他终端，也不在重连后补播已经完成的回答；
- 解除配对时同步解除对应托管；
- 托管只改变回复投递，不转移主控 Session、Conversation、权限或调度的权威状态。

### 8.4 Desktop 托管呈现

- 主控 Composer 内的低干扰频道图标是托管状态和切换的唯一入口，不把入口语义绑定为智能终端；
- 图标激活状态、tooltip 和无障碍名称表达当前是否托管及目标设备；
- 点击图标直接选择回复频道并完成更换或解除托管；菜单只列出当前在线目标，不展示在线状态文字；
- Desktop 与各渠道目标使用前缀图标表达分类，不增加副标题；管理智能终端保留纯文字快捷入口；
- 当前只开放 Desktop 和智能终端，未来移动端、IM 等渠道沿同一菜单按渠道类型扩展；
- 主控 Header 和右侧信息栏不重复展示托管状态或操作；
- 不在 Conversation 或 Composer 上方增加常驻托管提示条；
- Session Header 删除普通“空闲 / 运行中”状态 Tag，完整状态继续由现有运行区域表达；
- 侧栏状态、Queue、审批、压缩和 Composer 停止入口继续沿用既有产品语义。

具体图标、状态标记、信息栏布局和视觉细节在开发过程中调整，不作为本功能设计的冻结样式。

## 九、播报 Tool 与 TTS

### 9.1 完整回答与播报文本

- Runtime Conversation 保留模型正常生成的完整 Assistant Message；
- 当当前有效回复目标需要音频时，模型获得播报 Tool；
- 模型将适合朗读的压缩文本作为 Tool 输入，而不是把完整长回答直接交给终端播放；
- 播报文本作为既有工具调用事实进入 Conversation，不创建第二条 Assistant Message；
- Tool 不接受设备 ID、连接 ID 或任意投递目标，实际目标由 Gateway 根据来源和 PC 输出托管确定，
  防止模型误投其他设备。

### 9.2 分段播报与结束补齐

```text
第一次 speak(A) → 立即 TTS → 队列 A
后续模型或工具 continuation
第二次 speak(B) → 立即 TTS → 队列 A, B
播放端 → 先完整播放 A，再播放 B
```

- 单次 `speak` 最多 120 个 Unicode 字符，必须是可独立自然朗读的纯文本；
- 单个输出周期最多接受 20 次 `speak`；模型提示中明确该上限，超过上限的调用在 TTS 前失败；
- 超长播报由模型在句号、分号或完整语义边界串行分段，不使用 Host 硬截断；
- 每次合法调用在可靠工具 started 边界后立即合成，Host 用有界 FIFO 保持调用顺序；
- 播放端在相邻播报片段之间保留约 160 ms 气口，不截断前段尾音；
- 后续 continuation 失败不撤回用户已经听到或已排队的片段；新用户输入会打断当前及待播队列；
- 本轮真实结束时，若有效目标需要语音但整轮从未成功调用 `speak`，Runtime 插入一次
  隐藏的轮内 Runtime UserMessage 并续跑；
- 该提醒明示“这是播报交付提醒，不是真实用户交互”，模型不得道歉、问候、回应提醒或重新
  生成普通正文；
- 补齐续跑最多一次；仍未播报时明确降级，不朗读完整 Assistant Message，不无限循环。

TTS 失败不改变已经可靠完成的 Runtime Run 和完整 Assistant Message。目标支持文字输出时仍可看到
完整文字；目标只支持音频时收到明确的语音输出失败状态。

### 9.3 ASR/TTS Provider

- 首版 ASR/TTS 使用阿里百炼服务；
- ASR 与 TTS 是彼此独立、可替换的平行 Provider 能力；
- 后续服务商实现不得改变智能终端 WSS、主控 Input、Conversation 或回复路由语义；
- ASR 不可用时文字输入仍可使用；TTS 不可用时完整文字回答仍然有效；
- Device Adapter 只协商当前实际可用的媒体能力，不对终端宣告尚未配置或不可用的能力。

Provider 凭据来源、配置文件或 Desktop 设置入口、模型、音色、超时、重试和流式能力留到技术方案
核对现有配置体系后确定，功能设计阶段不提前冻结。

## 十、音频保留

- 开发模式允许把上行和下行音频写入约定的临时目录，方便人工比较原始 PCM、ASR 输入和 TTS 输出；
- 开发临时文件只需要基本关联命名和必要的路径安全、写入错误处理，由开发者手动查看和清理；
- Release 默认不保存原始音频、TTS 音频或完整媒体临时文件；
- 不为开发临时音频新增数据库、状态投影、自动清理、容量管理或 UI 生命周期。

## 十一、断线、恢复与错误反馈

### 11.1 设备断线

- Runtime 接受 Input 前断线时，终端可以用同一话语/消息身份重试，不能更换身份造成重复输入；
- Runtime 接受后断线不取消 Run；完整结果继续进入主控 Conversation；
- 断线期间完成的文字或音频不在重连后自动重发或重播；
- 临时断线保留配对和 PC 输出托管，后续新轮次在设备恢复在线后继续使用；
- 无法可靠恢复的媒体临时状态回到空闲或明确错误，不拼接两段音频流。

### 11.2 稳定错误口径

终端/H5 至少应能区分：

- 未发现 Host、Host 不可用或设备接入被停用；
- 配对码错误、过期、设备未配对或已撤销；
- 协议版本/能力不兼容；
- 音频格式、帧顺序、话语大小或媒体状态非法；
- ASR 失败、Runtime 拒绝、等待 Desktop 审批、Run 失败或取消；
- 播报候选缺失、TTS 失败、目标离线或播放取消。

错误信息只暴露稳定、可操作的产品含义，不向设备下发 Provider 原始错误、Runtime Token、工具参数、
权限细节或本地路径。

## 十二、模块职责与契约影响

### 12.1 Assistant Runtime

Runtime 继续持有：

- 主控 Session、Input、Run、Queue、审批、Conversation 和工具事实；
- 终端来源进入规范 Conversation 后的可靠接受、幂等、串行、结算和恢复；
- PC 输出托管这一稳定 Session 级产品状态；
- 本轮播报候选与可靠执行结算之间的业务协调边界。

Runtime 不处理 WSS 帧、mDNS、PCM codec、设备证书或浏览器交互。

### 12.2 Assistant Protocol

协议需要表达：

- 终端来源、输入模态和输出偏好的可信产品投影；
- 已配对设备、能力、在线状态和 PC 输出托管状态；
- Desktop 发起配对、改名、解除配对、切换/解除托管等用户意图；
- 播报 Tool 的既有工具事实以及 H5/设备需要的稳定结果和错误；
- Runtime Event、Snapshot 和不同 Adapter 投影所需的失效信息。

协议不承载 PCM、WebSocket ping/pong、证书私钥、配对算法内部材料或 Provider 凭据。

### 12.3 Runtime Host / Gateway / Device Adapter

Host 继续负责 Runtime 装配和进程生命周期，并在同一产品进程中组合 Gateway 与 Channel Adapter。
Device Adapter 负责局域网监听、发现、配对、连接、媒体和 ASR/TTS。Gateway 负责身份上下文、路由、
能力投影和回复目标选择。它们均不得持有第二份 Session/Run/Conversation 权威状态。

### 12.4 Desktop

Desktop 只提交设备管理和 PC 输出托管意图，并展示 Runtime/Host 返回的权威快照。它不根据连接动画、
消息正文、设备名称或本地计时器猜测配对、在线、来源、路由或播报结果。

### 12.5 Node/H5 模拟器

Node/H5 是本版本的智能终端协议和产品交互验证工具，不是第二个 Runtime Host，不装配 Agent Core，
不保存第二份 Conversation，也不成为 Desktop 的替代产品界面。

## 十三、关键取舍

1. **统一语义，不统一传输**：保留 Desktop SSE；设备使用 WSS；避免为新增终端重做既有可靠客户端。
2. **进程内 Gateway，暂不拆服务**：第一阶段没有多实例、公网伸缩或独立运维证据，不引入重复 Host。
3. **终端统一进入主控**：复用 `v0.20.0` 协调入口，不为每台设备创建和管理孤立 Session。
4. **扩展既有 Conversation**：来源、Run 和播报工具事实进入现有规范链路，不建设第二套消息存储。
5. **来源优先，PC 托管次之**：终端主动输入不会被 PC 托管截获，PC 可以显式把自己的回复导向终端。
6. **完整文字与压缩播报并存**：完整 Assistant Message 保持产品事实，模型用 Tool 生成更适合朗读的文本。
7. **自然分段、立即入队**：降低长会话首音频延迟，并用有界 FIFO 保证多次 Tool Call 的播放顺序。
8. **Node 是终端，H5 是交互面**：真实验证发现、配对、WSS 和重连，又保留方便的人工语音/文字操作。
9. **首版百炼、Provider 可替换**：先建立真实闭环，不把设备协议绑定到单一服务商。
10. **UI 保持克制**：设备详情进入设置，托管状态与操作只保留 Composer 单一入口，主控 Header
    移除普通空闲/运行 Tag，具体样式在实现过程中收敛。

## 十四、验收标准

1. Desktop 继续通过 HTTP Command + SSE + Streaming Upload 工作，既有事件 gap 和权威快照恢复通过。
2. Node 模拟器能够发现同一局域网的 Host，主动建立设备 WSS，并完成版本与能力协商。
3. 未配对模拟设备只能进入受限配对流程；正确配对码完成注册，错误/过期配对码明确失败。
4. 已配对设备重连后保持稳定身份；解除配对后不能继续提交或接收消息。
5. H5 麦克风输入经 Node 上送 PCM、Host ASR 和 Runtime 接受后，在主控形成一条真实用户消息和 Run。
6. H5 文字输入通过同一设备 WSS 进入同一主控，不经过 ASR，也不直接调用 Runtime。
7. ASR 空结果或失败不创建空 Input；同一音频请求重试不重复创建 Input/Run。
8. Desktop 在既有主控 Conversation 中显示终端来源和输入模态，不依赖正文前缀猜测。
9. 终端消息、完整 Assistant Message 和播报 Tool Call 全部位于既有 Conversation/Run 链路，
   不存在第二套 Device Conversation 或 Delivery Store。
10. `text`、`audio`、`text_and_audio` 三种输出偏好均按终端能力正确协商、执行或明确拒绝。
11. 终端来源 Input 始终回复来源终端，即使主控同时存在指向其他设备的 PC 输出托管。
12. PC 来源 Input 在设置托管后发送到所选终端；解除托管后不再发送；完整回答始终保留在 Desktop。
13. 同一主控只能选择一个 PC 输出托管目标；切换、设备离线、解除配对和解除托管行为符合设计。
14. 终端 A 通过主控投递普通会话任务时，最终代理报告返回 A，不被指向 B 的 PC 托管截获；
    没有明确外部返回渠道的代理报告则使用报告结算时的 PC 托管。
15. 模型同轮多次调用播报 Tool 时，每段均不超过 120 字符并按调用顺序入队，播放连续且无覆盖。
16. 播报 Tool 无权选择设备；最终目标完全由结构化来源和 PC 输出托管规则决定。
17. TTS 失败不把已完成 Run 改为失败；完整文字仍可在主控 Conversation 中查看。
18. 设备等待审批时只提示 Desktop 处理；审批完成后原 Run 继续，不重复提交输入。
19. Runtime 接受后设备断线不取消 Run；重连不自动重播断线期间完成的回答。
20. 开发模式可以在约定临时目录人工比较上下行音频；Release 默认不保存音频文件。
21. H5 能观察设备协议、状态、候选播报和音频结果，但无法绕过 Node 直接读取 Runtime 状态。
22. Desktop 能完成最小配对、设备列表、改名、解除配对和 PC 输出托管管理。
23. 主控 Header 不再显示普通“空闲 / 运行中”Tag；托管状态和操作只位于 Composer 输入区。
24. ASR/TTS 首版通过阿里百炼完成真实链路，文字能力可在语音 Provider 不可用时独立工作。

## 十五、风险、兼容性与后续设计项

### 15.1 主要风险

- 首次局域网 WSS 的服务端信任、配对码和长期设备凭据必须形成闭环；错误设计会让人工配对只有
  表面确认而没有实际安全价值。
- 播报 Tool 是模型行为，可能不调用、分段不自然或压缩质量不稳定；本版本以单次隐藏补齐、
  长度上限和有界队列收敛，不用 Host 硬切文本或朗读完整正文掩盖失败。
- 语音链路包含网络、ASR、Runtime、TTS 和播放多个阶段，必须避免任何媒体故障改变 Runtime
  已可靠接受和结算的业务事实。
- 主控同时接收 Desktop 和多个终端输入时，必须依赖既有 Queue 和结构化来源保证串行与精确回路，
  不能以当前在线连接或最后活跃设备猜测回复目标。

### 15.2 兼容性

- Desktop 既有客户端继续使用当前协议能力；新增字段和事件需要按协议既有默认兼容规则设计。
- Runtime Host 默认 loopback Desktop 入口保持不变；局域网 Device Adapter 是新增、可停用的入口。
- 已有 `User`、`ControllerDelivery` 和 `ProxyReport` 历史必须继续恢复和展示，不能因新增终端来源失效。
- 不支持智能终端能力的旧 Host/客户端应通过 protocol version/capabilities 明确降级或拒绝。

### 15.3 归入技术方案的事项

- Gateway、Device Adapter、Node/H5 的物理目录、crate/package 和依赖关系；
- 设备 WSS 控制 envelope、PCM 帧格式、消息身份、幂等和流控；
- mDNS 服务信息、首次配对安全协议、证书/密钥签发、保存与撤销；
- 既有 Conversation/Input/Run、Session 状态和产品快照如何最小扩展及迁移；
- “同轮真实结束”、单次补齐 continuation 和重启时易失播放队列的精确边界；
- 阿里百炼 ASR/TTS Provider 接口、凭据、模型、音色、配置入口和降级策略；
- 开发/Release 音频落盘开关和临时目录；
- 最小有效测试矩阵、正式 Host 集成测试和 Node/H5 端到端验证方式。

功能设计确认后，本版本需要继续形成技术方案；由于新增设备管理、配对、右侧托管信息和 H5
交互面，也需要形成界面交互设计指导，但具体样式可以在实现过程中结合现有组件调整。
