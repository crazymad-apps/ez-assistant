## 二、源码现状与可复用基线

### 2.1 Host 与传输

- `apps/runtime-host/src/server.rs` 当前只拥有一个 loopback `OwnedEndpoint`，通过 Axum
  暴露 `/commands`、`/events`、附件与资源路由，关闭时再受控关闭唯一
  `AssistantRuntime`。
- `OwnedEndpoint` 负责 Runtime Home 单实例锁、动态 `127.0.0.1` 端口、进程级 Bearer Token
  和私有 `runtime.json`。这些事实只服务 Desktop，不可复用为局域网设备发现或设备凭据。
- `HttpState` 只保存连接适配需要的 Runtime、Token、authority、资源路径和关闭令牌，符合
  “Host 不复制 Runtime 业务状态”的既有边界。
- 当前 `axum` 只启用 `multipart`，尚未启用 WebSocket；仓库也没有 TLS、mDNS、设备密钥或
  音频 Provider 依赖。

### 2.2 Runtime、Input 与 Conversation

- `SessionController` 已持有 mutation gate、Input 队列、Run、Conversation Journal、Goal、
  WorkPlan、主控角色和代理状态。设备输入继续进入同一个主控 Session，不建立 Device Session
  或第二个调度器。
- `RuntimeStore::accept_input` 已能原子接受 Input、首次 Run 和 queued UserMessage；
  `RuntimeStore::settle_run` 已能原子提交最终 Assistant Message、Run 终态、Goal effect 和
  可选 continuation。这两条是设备输入和最终回复路由的可靠接缝。
- 现有 `InputOrigin::{User, Runtime}` 表达业务创建者，`CrossSessionInputBinding` 表达
  v0.20.0 的主控跨会话来源。智能终端仍是真实用户输入，不应新增第三种 Input origin；
  需要增加的是与 origin 正交的 Channel 来源。
- 产品层 `ConversationInputSourceSnapshot` 已能把输入来源投影到消息与 Queue；可以增量增加
  Device variant，而不把设备标签写入正文。

### 2.3 Run 收敛与工具事实

- Core 的 Tool Call/Tool Result 已通过 pending、started、ready、staged append 可靠进入既有
  Conversation。播报 Tool 可以复用这条链，不能另建“播报正文表”。
- `run/settlement.rs` 在最终 Assistant Message 已加入 candidate Journal 后构造单个 Store
  settlement，并能识别 Goal continuation。最终输出调度应挂在 settlement 成功之后，不能根据
  `TextDelta`、`ToolCompleted` 或客户端事件猜测完成。
- Runtime Event 已有进程内 sequence 和 SSE gap 恢复语义，但事件允许丢失。设备播放不能把
  SSE/Runtime Event 当作可靠投递队列；需要 Runtime 在可靠结算后直接调用 Host 注入的输出端口。

### 2.4 Desktop 与主控基线

- v0.20.0 已建立软性单主控、主控工具、普通 Session 代理和主控产品投影；设备输入直接定位
  Runtime 当前主控，不开放终端选择 Session。
- Desktop 的 `RuntimeClient` 和 MobX Store 已以 Command + 权威快照 + SSE invalidation 重建。
  设备管理、配对和 PC 输出托管继续采用这一模式，不在 WebView 建 WSS 设备连接。
- Agent 只运行在 Runtime，Session/Conversation 是唯一规范事实。Desktop UI、Device 和未来 IM
  都是交互渠道；Desktop UI 必须始终展示所有显式 User/Assistant 正文。渠道托管和投递
  只做附加扇出，不会把规范内容从 Desktop 迁走。
- Session Header 现有运行状态可由右侧上下文和执行区域表达。本版本协议增加的托管状态只在
  Composer 的单一频道入口呈现，Header 不保留托管图标或普通“空闲/运行中”Tag。频道菜单当前
  将 Host 快照中在线的已配对设备映射为候选，不把离线设备或连接状态文案带入列表。

## 三、总体架构

```text
Tauri Desktop
  │ loopback HTTP Command / SSE / Streaming Upload
  ▼
Runtime Host 产品进程
├── HostSupervisor（进程级生命周期与故障分类）
│   ├── DesktopHttpService（既有 HTTP/SSE，未来本地媒体 Adapter 仍属于 Desktop Channel）
│   ├── SpeechService（Host ASR/TTS Provider Adapter）
│   ├── DeviceGatewayService
│   │   ├── Device Listener（LAN WSS）
│   │   ├── mDNS Discovery
│   │   ├── Message Gateway
│   │   └── Device Connection / Media Registry（易失）
│   ├── ChannelOutputDispatcher（零到多个附加渠道投递）
│   ├── Host Application Facade（命令协调与瞬时投影组合）
│   └── Device Registry Store Adapter（SQLite）
│
└── Assistant Runtime（唯一业务权威）
    ├── Controller Session / Input / Run / Conversation
    ├── Input Channel Source
    ├── PC Output Hosting
    ├── Output Cycle Coordinator
    └── ChannelOutputDispatcher Port

Node 智能终端模拟器
  │ mDNS + WSS + JSON Control + PCM
  └── H5（只连接 Node 的 loopback 交互端口）
```

“Message Gateway”是跨模块用例的逻辑名称，不新增 `gateway` crate，也不新增第二个产品服务。
首版只有 `runtime-host` 一个稳定调用方，拆 crate 会制造没有替换收益的公共 API。建议在
`apps/runtime-host/src/device/` 内按 `protocol`、`listener`、`connection`、`pairing`、`media`、
`speech` 和 `dispatch` 分模块；跨越 Host/Runtime 的稳定业务类型放在 `assistant-runtime`。

`HostSupervisor` 只是 `runtime-host` 内的进程级编排器，不成为第二个 Runtime。它统一持有根
`CancellationToken`、各子系统 child token 和受跟踪任务，但不保存 Session、Run、Device 或托管的
第二份稳定状态。

## 四、边界与依赖方向

### 4.1 `assistant-protocol`

只增加 Desktop 与 Runtime 都需要的稳定应用契约：

- Device ID、设备生命周期、能力和在线投影；
- 列出设备、开始/取消配对、确认配对、重命名、解除配对命令；
- 主控 PC 输出托管目标及设置/解除命令；
- Conversation/Queue 的设备来源投影；
- 设备与托管状态的 invalidation 事件。

不得加入：WSS path、TLS 对象、mDNS 字段、JSON 控制 envelope、16-byte PCM header、连接 ID、
音频缓冲、Provider 原始错误或 Node/H5 私有消息。

### 4.2 `assistant-runtime`

负责：

- 可信 Channel Input 接受用例和设备来源的业务校验；
- 将设备来源冻结到 Input，并随既有 Conversation/Queue 投影；
- Session 级 PC 输出托管权威状态及解除配对联动；
- 根据输入来源、代理报告返回基准与当前托管状态形成零到多个附加 delivery；
- 一个逻辑输出周期允许多次分段 `speak`，每次立即交给 Host 有界 FIFO；
- 可靠 Run/Goal 收敛后调用 `ChannelOutputDispatcher`；
- 稳定设备事实的登记、重命名、撤销和业务门禁，通过 Store 端口读写。

Runtime 不注入也不反向调用广义的 `DeviceGatewayControl`，不读取 pending pairing、在线连接或
媒体任务快照。Host 只能通过 Runtime 的受信任用例提交已验证的设备登记和设备输入；
Runtime 对 Host 的反向依赖只保留 `ChannelOutputDispatcher` 这一窄输出端口。

Runtime 不依赖 Axum、rustls、mDNS、DashScope SDK、PCM、WebSocket 或 Node 协议。

### 4.3 `runtime-host`

负责：

- 通过 `HostSupervisor` 启动、观察、降级和受控关闭 Desktop HTTP、Device Gateway、Runtime 与 Store；
- 独立的 LAN TLS Listener、WSS upgrade、mDNS 宣告和受控关闭；
- 首次配对传输、连接挑战、设备密钥验签、能力协商和单连接替换；
- 在线连接、媒体流、背压、心跳、重连和下行发送；
- PCM 到 ASR、TTS 到 PCM 的 Provider 适配；
- `RuntimeStore` 的设备与托管持久化实现；
- `ChannelOutputDispatcher` 的具体实现；
- 开发模式音频临时文件。

Host 可以持有配对窗口、pending request、连接、心跳、当前 capability/偏好、音频流和播放状态；
这些都是易失资源状态。设备注册记录、Session 托管和 Input 来源的权威事实仍由 Runtime 通过
Store 业务操作管理。

Desktop 命令仍使用同一 `/commands` 入口，但由 `HostCommand` 的 scope 显式分流：

- 配对窗口、pending 确认和设备接入开关属于 Host Device command；
- 稳定设备列表、重命名和 PC 托管属于 Runtime command；
- 撤销设备是 Host Application Facade 的组合用例：先由 Runtime/Store 原子撤销并清理托管，
  再由 Gateway best-effort 中断在线连接。断开失败不回滚撤销，后续输入和输出在稳定设备校验处继续
  fail-closed。

Host Application Facade 可以按 Device ID 瞬时组合 Runtime 稳定投影与 Gateway presence，但不持久该组合结果，
不回写 Runtime，也不成为第二份业务状态。

### 4.4 Desktop 与模拟器

- Desktop 只发送设备管理和托管意图，消费权威投影；不接触设备密钥或媒体流。
- Node 模拟器只作为设备协议客户端；H5 只操作 Node，不调用 Runtime Command/SSE。
- 设备或 H5 自报的 `device_id` 不能覆盖认证所得身份；它们可以在已协商能力范围内声明输入模态、
  本轮输出偏好和当前播放能力。

## 五、共同领域模型

### 5.1 稳定设备事实

Runtime 领域建议增加：

```rust
pub struct DeviceId(/* validated opaque string */);

pub enum DeviceLifecycle {
    Paired,
    Revoked,
}

pub struct PairedDevice {
    pub device_id: DeviceId,
    pub display_name: String,
    pub public_key: DevicePublicKey,
    pub lifecycle: DeviceLifecycle,
    pub paired_at_ms: i64,
    pub updated_at_ms: i64,
    pub revoked_at_ms: Option<i64>,
}
```

长期认证使用设备公钥，不持久化配对码、连接 Token 或设备私钥。在线、connection ID、RTT、
当前 capability 和输出偏好属于 Host 易失状态，再与稳定设备投影组合为 Desktop 快照。

### 5.2 Channel 来源

```rust
pub enum InputChannelSource {
    Desktop {
        modality: InputModality,
        requested_output: OutputPreference,
    },
    Device {
        device_id: DeviceId,
        modality: InputModality,
        requested_output: OutputPreference,
        client_input_id: String,
    },
}
```

模态和输出偏好属于 Channel 通用语义，不绑定 Device。旧 User Input 缺字段时安全缺省为
`Desktop { Text, Text }`；旧 Runtime Input 缺字段表示没有外部 Channel。
`client_input_id` 只用于解释与幂等核对，不作为连接 ID；
设备展示名称从 Registry 投影，重命名不改写历史 Input 的稳定设备 ID。

### 5.3 输出托管与附加投递

Controller Session 增加：

```rust
pub struct PcOutputHosting {
    pub device_id: DeviceId,
}
```

该字段只保存当前托管目标。变更时间不参与路由、幂等或并发控制；若未来需要
审计托管变更，再建立不会随取消托管而丢失的独立历史记录。

最终 Assistant Message 依然只有一份，并始终对 Desktop UI 可见。Runtime 另外形成零到多个附加
delivery；每条 delivery 的偏好由来源 Input 冻结，或在主控默认投递中取目标 Channel 当前
合法偏好。模型 Tool 永远不能提交渠道目标。本版实现 Device delivery；未来 Desktop 音频和
IM 只增加 delivery Adapter，不改 Conversation 或 Runtime 结算模型。

主控向普通会话投递任务时，以 `CrossSessionInputEnvelope` 包装业务来源
`CrossSessionInputBinding` 与公共 `ReplyRoute`，避免 `ControllerDelivery`、`ProxyReport`
重复定义回复字段。工具通过必填 `start_goal` 区分单轮任务与长任务；长任务在接受
`ControllerDelivery` 时原子创建 Goal，并由 `GoalInputBinding` 让 continuation 与后续
`ProxyReport` 原样传递回复路径。
明确来自 Device 的投递增加返回该 Device 的 delivery；没有明确外部返回渠道的报告使用主控默认规则，因此
在主控实际输出时仍需读取当前 PC 输出托管。

## 六、持久化方案

### 6.1 SQLite

正式 Host 增量增加 `devices` 表，并给 `sessions` 增加可空 PC 托管列：

```sql
CREATE TABLE devices (
    device_id       TEXT PRIMARY KEY,
    display_name    TEXT NOT NULL,
    public_key      BLOB NOT NULL UNIQUE,
    lifecycle       TEXT NOT NULL CHECK (lifecycle IN ('paired', 'revoked')),
    paired_at_ms    INTEGER NOT NULL,
    updated_at_ms   INTEGER NOT NULL,
    revoked_at_ms   INTEGER
);

ALTER TABLE sessions ADD COLUMN pc_output_device_id TEXT
    REFERENCES devices(device_id) ON DELETE SET NULL;
ALTER TABLE inputs ADD COLUMN channel_source_json TEXT;
```

具体迁移使用仓库既有 `schema.rs` 兼容新增列/表流程。恢复时必须验证：

- 只有 Controller Session 可以拥有 PC 输出托管；
- 托管目标必须是 `paired` 设备；
- `channel_source_json` 必须与 `InputOrigin::User`、可见 UserMessage 及目标 Controller 匹配；
- Device ID、公钥和枚举值非法时 fail-closed，不降级为 Desktop 来源。

解除配对使用单个 Store 事务把设备置为 `revoked` 并清除所有指向它的 PC 托管。历史 Input 只保留
Device ID，不以外键级联删除，保证 Conversation 来源仍可解释。

### 6.2 Conversation JSONL

不修改规范 UserMessage 的正文顺序，也不增加第二份消息。设备来源保存在 Input 结构事实中，
产品分页通过 `input_id -> channel_source` 投影来源。播报文本已作为普通 Tool Call/Result 进入 JSONL。

运行时崩溃后不恢复未播放音频、Host FIFO、输出周期或在线连接；已可靠完成的 Assistant Message、
播报 Tool 事实、Input 来源和 Run 终态仍可从现有数据集恢复。

## 七、并发、可靠性与故障隔离

1. `HostSupervisor` 持有根关闭令牌，Desktop HTTP、Device Gateway、Runtime 后台任务分别使用
   child token 和独立受跟踪 task group；任务必须等待收敛或超过明确 deadline，不允许脱离所有者。
2. Runtime、Store 或 Desktop HTTP 主入口意外退出是进程级致命故障，触发整体受控关闭。
   Device WSS 或 mDNS 异常进入可观察的 Device 降级状态：Desktop/Runtime 继续服务，已稳定保存的设备和
   托管事实不被改写。是否有限重启 Device 子系统由开发计划中的故障策略决定。
3. 每个已认证设备最多一个 connection owner；新连接通过 Registry 原子替换旧连接，旧连接停止
   接收下行并以 `connection_replaced` 结束。
4. 每个连接使用有界控制队列和媒体队列；慢设备只丢弃/终止本连接，不反压 Runtime 广播或
   Provider 流。
5. 上行话语在 ASR 成功前不进入 Runtime；成功后由 Host Channel Router 调用 Runtime 路由策略解析
   目标 Session，再调用 Session-generic Channel Input 入口，并由 Runtime 重新校验路由授权与派生确定性
   幂等 key。
6. Runtime 接受后，连接断开不取消 Run；任何附加 delivery 未成功也不改变 Run 终态。
7. 输出调度发生在 Store settlement 成功之后。各 delivery 独立成败，不回滚
   Assistant Message 或把 Completed Run 改成 Failed。
8. 本版本无离线 Outbox。终端离线、Runtime 重启或 Host 崩溃后不补播历史回复。

启动顺序固定为：单实例锁与配置 → Store 与 Runtime 恢复 → 构造子系统并绑定 listener →
发布 Desktop endpoint，仅在 Device Gateway ready 后发布 mDNS → Supervisor 进入观察循环。Store、Runtime
或 Desktop listener 失败时不发布未就绪的主服务；Device 子系统初始化失败时可在 Desktop 可用的前提下
进入降级状态。

关闭顺序固定为：停止新入口与撤回 mDNS → 收敛 Runtime Input/Run → 取消并限时排空设备媒体与连接
→ Runtime shutdown → Store flush/join → 清理 listener、`runtime.json` 和单实例资源。

## 九、协议与事件演进

- `assistant-protocol::PROTOCOL_VERSION` 仍表示 Desktop/Runtime 应用契约；设备 wire 独立使用
  `protocol_major/minor`，两者不共享版本号。
- Device 在线变化、设备资料变化和 PC 托管变化使用 invalidation 事件，Desktop 重新读取
  Application/Session 快照；事件不携带设备公钥、配对码或完整 Registry。
- 设备 WSS 不直接转发 `RuntimeEventEnvelope`。Gateway 从 Runtime 事实和自身连接状态生成
  `state_changed`、`input_accepted`、`playback_*` 等受限设备消息。
- Desktop 现有 SSE 不增加 PCM、ASR partial 或 TTS chunk，保持事件基线和恢复语义不变。

## 十、ASR/TTS 最小配置方案

本版确认使用现有 Runtime Home `config.toml`，增加独立 `[speech.asr]` 和
`[speech.tts]` 配置。首个 Provider 为 DashScope，ASR/TTS 仍保持平行 SPI 和 Adapter，
便于后续分别增加其他服务商。

本版不建设 Desktop ASR/TTS 编辑表单，不增加公共配置写入 DTO 或新 revision 结构。
Host 在启动和显式 reload 时校验配置，并向 Desktop 只投影 `ready | unavailable | degraded`
及必要的脱敏诊断。配置缺失时不影响 Runtime 和文字交互。

ASR 与 TTS 是两份平行配置，不用一个 `voice_provider` 大对象绑定；文字 Channel 能力不依赖它们。

## 十一、实施切面建议

技术方案确认后，开发计划宜按以下依赖顺序拆里程碑，但每个里程碑仍需单独确认后实施：

1. HostSupervisor、子系统生命周期、故障分类与既有 Desktop HTTP/Runtime 回归；
2. Runtime 设备领域、Input Channel Source、PC 输出托管与 Store 迁移；
3. Host 设备协议 codec、TLS/mDNS、配对与 Node 基础连接；
4. 文字输入、回复路由、文字输出和 Desktop 设备/托管最小闭环；
5. PCM、DashScope ASR、语音输入和开发音频保留；
6. 播报 Tool、跨 continuation 的分段 `speak`、结束补齐、TTS FIFO 与播放控制；
7. H5 完整监控、故障矩阵、协议 fixtures 和正式集成验收；
8. Desktop 界面收口、设置决策落地与全量回归。

## 十二、验收总门禁

- Desktop 既有 HTTP/SSE、Queue、审批、Goal、主控代理和 Conversation 恢复全量回归通过；
- Device Gateway 故障时 Desktop/Runtime 仍可用，Runtime、Store 或 Desktop 主入口故障时能按顺序受控关闭；
- Rust/Node 对设备控制 envelope 和 16-byte PCM header 使用同一 fixture 互验；
- 配对码过期/错误、撤销、连接替换、能力越界、坏帧、断线和慢客户端均 fail-closed；
- 语音/文字输入使用同一 Runtime Input 可靠链，重试不重复 Run；
- 任意 Channel 的显式 User Input 和最终 Assistant Output 均进入唯一 Conversation，并在 Desktop UI 可见；
- 终端来源优先于 PC 输出托管，多个终端不会串播；
- 附加 delivery 为零到多个，单渠道失败不影响规范 Conversation 或其他 delivery；
- Device 发起的主控投递将代理报告增加返回原 Device 的 delivery；无明确外部渠道的代理报告
  按结算时的 PC 托管决定是否增加 Device delivery；
- Tool 多次调用、工具 continuation、Context continuation 和 Goal continuation 中的 `speak` 均按调用顺序播放；
- 需要语音但整轮未调用 `speak` 时只触发一次明确非用户交互的隐藏补齐；
- TTS/连接失败不改变已完成 Run；ASR 失败不创建 Input；
- Release 默认不保存音频，开发模式音频可人工对比；
- Node/H5 不直连 Runtime，所有成功场景都经过正式设备 WSS。

## 十三、已确认边界

1. 首版安全模型为“安装级服务端证书 + 设备长期 Ed25519 密钥 + 配对码 SPAKE2 人工确认”；
2. 本版本不做离线补播、跨重启待播报文本恢复和设备侧审批；
3. Node/H5 模拟器是正式验收对端，临时直连页面不作为成功证据；
4. ASR/TTS 使用 `config.toml` 最小配置，本版不建设 Desktop 配置编辑页。
