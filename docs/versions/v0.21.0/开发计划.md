## 二、台账与实施原则

1. 按 M0—M9 顺序实施。开发计划获得用户确认后，开始 M0 前才把版本状态从 `计划中` 更新为
   `开发中`，并初始化或续写 `docs/开发进度.md`；每个里程碑完成后停止，提交结果与验证证据，
   获得用户明确确认后才能进入下一里程碑。
2. Agent 只运行在 Runtime。Session/Conversation 是显式输入和最终输出的唯一权威事实；Desktop、
   Device 和未来 IM 都只是输入与展示渠道，不新增 Device Conversation、Reply Store 或第二套消息顺序。
3. Desktop UI 始终展示所有渠道的显式用户输入和最终 Assistant Output。设备或未来渠道的附加投递
   可以为零到多个，任何单渠道失败都不能删除、转移或回滚 Desktop 中的规范正文。
4. Runtime/Store 持有设备注册、来源、PC 输出托管、Conversation 和投递业务事实；Host 持有配对窗口、
   设备候选、在线连接、心跳、媒体流和播放状态。Host 可以组合两侧投影，但不能保存第二份业务权威状态。
5. Desktop 继续使用 loopback HTTP Command、SSE 和 Streaming Upload；Device 使用 mDNS、WSS 和
   JSON/PCM codec。两种传输共享应用语义，不把 WebSocket 引入为 Desktop 的替代通道，也不把 PCM
   包装成 Runtime Event。
6. 配对严格采用“发现候选 → 人工验证配对码 → 完成 SPAKE2 → 签发并持久化长期身份”的顺序。
   未配对连接只能访问受限配对协议；设备自报的身份、能力或输出偏好都必须经过认证和协商后才生效。
7. 本版本允许为已确认的 mDNS、WSS/TLS、SPAKE2、Ed25519、音频和 Node 模拟器边界增加必要依赖，
   但每次引入前需核对维护状态、许可证、平台支持和最小 feature。不得借机更换 Axum、Tokio、Runtime
   Store 或 Desktop 前端基础框架。
8. Node 模拟器固定使用 Node.js 24 LTS 主版本，位于 `tools/device-simulator`，不加入 Cargo workspace。
   实现前先补充 `docs/modules/device-simulator.md`；H5 只能通过 loopback 私有桥控制 Node，正式验收
   不允许 H5 直连 Runtime Command/SSE 或数据库。
9. ASR/TTS 使用 Runtime Home `config.toml` 的 `[speech.asr]`、`[speech.tts]` 最小配置，首个 Adapter
   为 DashScope；ASR 与 TTS 保持平行 SPI。配置缺失不得影响 Runtime 和文字交互，本版本不增加
   Desktop 配置编辑表单、公共配置写 DTO 或冗余 revision 字段。
10. 默认自动化验证使用 fake Model、ASR 和 TTS。真实 DashScope smoke 保持显式、默认不执行；只有用户
    明确授权网络请求和可能费用后才能运行，且必须使用隔离 Runtime Home 并脱敏日志。
11. 所有 schema migration、设备撤销、恢复和崩溃测试只使用 `TempDir`、内存 Store 或隔离 Runtime Home；
    本计划不授权打开、迁移、删除或写入用户实际数据库。任何真实数据操作仍需按数据库安全规则另行确认。
12. 开发模式可把输入/输出 PCM 保存到临时目录供人工比较，Release 默认不保存；不增加 TTL、容量管理、
    自动清理界面或音频持久化记录。
13. 只在 wire PCM sequence、协议 message ID 和既有可靠输入幂等键等明确业务边界使用序号；`speak`
    输出周期只保存是否已播报和一次性补齐状态，不增加 candidate revision、播报历史或独立输出版本表。
14. 每个里程碑开始前重新读取对应语言规范和模块约束、核对工作树与当前授权；保留用户已有改动，
    不主动执行 Git commit/push。

### device protocol 1.0 冻结补充（2026-08-30）

agent-robot S3.1 已完成正式 ESP32-S3 终端联调并归档，因此从本条起冻结本版本的 device protocol 1.0
语义。冻结依据为 agent-robot implementation commit `b6992531e6e4495dfeccf249077a370db38be3d2`、
archive commit `c847fc6`、三份跨语言 fixtures，以及
`agent-robot/firmware/compatibility/device-protocol-v1.json` 记录的 ez-assistant 关键文件 SHA-256。
当前 ez-assistant 工作树仍不是可复现发布提交；M8 必须将冻结内容整理为正式提交并回填组合版本，
不得把基础提交 `4441687` 单独表述为 S3.1 配套版本。

本次冻结包含以下联调结论：

- 配对码为六位启动会话级状态；普通 Host/WSS/pairing-window 变化不换码。关闭 pairing window 不改变
  已配对身份，设备解除配对使用 `device_revoked`，终端清长期身份并重新进入配对扫描；
- 每个录音分段使用独立 `client_input_id`/stream。`input_segment_accepted` 只确认 Host 已完整接管该段
  PCM，终端据此释放缓存；`input_accepted` 只确认合并后的单个 Runtime Input，二者不得合并或替代；
- Host 在 `listen_stop` 后保留 2 秒连续输入窗口，`listen_start` 到达时立即暂停提交计时。各段 ASR
  可以并行，transcript 必须按录音顺序以换行合并，并且只向 Runtime submit 一次；
- 聚合状态按 Device ID 保存在 Host 进程内，不随单条 WSS 替换销毁。重连为丢失的 segment ack 重开
  2 秒窗口，同 ID/同 PCM 重传必须去重；Host 进程重启可以放弃尚未形成 Runtime Input 的聚合轮次；
- PTT 到达时 Host 必须立即介入：上一轮尚未提交 Runtime 时并入同一逻辑输入；已有活动 Run 时取消
  该 Run 和剩余播报，再开始新逻辑轮次。单独的“停止播放”仍只取消播放，不取消 Runtime Run；
- capture 已开始后迟到的 `playback_start` 属于正常抢占竞态。Host 接受 `playback_cancel` 后把该 speak
  delivery 结算为用户接管，不得返回 `tool execution failed`；真实 TTS/队列容量错误仍按失败处理。

冻结后若发现必须修改 wire 或上述恢复语义，必须先记录变更原因，同时更新 Rust Host、Node 模拟器、
ESP32 固件、附件 A/C、fixtures 和两端测试，再生成新的组合快照；不能只修改其中一端或增加兼容分支
绕过冻结门。

## 四、里程碑明细

### M0：Host 运行框架

前置依赖：本开发计划已确认；版本状态已更新为 `开发中`。

目标：先在 `apps/runtime-host` 内建立小而明确的 Host 运行框架，使现有 Runtime、Desktop Transport
和后续 Device Gateway/Speech 子系统拥有统一生命周期、取消和故障分级，同时不改变当前产品协议行为。

交付范围：

- 实现 HostSupervisor、受控启动顺序、共享取消令牌、子系统退出回收和进程关闭编排；
- 区分关键子系统、可降级子系统和单连接任务，落实启动失败、运行期失败与关闭超时策略；
- 将既有 HTTP/SSE/Runtime 装配迁入该生命周期，保持 Axum、Tokio 和双进程边界不变；
- 为后续 Gateway、SpeechService 和调试出向连接预留 Host 私有装配位置，不创建通用插件框架；
- 覆盖部分启动失败、可降级任务崩溃、关键任务退出、重复取消和有界关闭测试。

验证入口：

```bash
cargo test -p assistant-runtime-host
cargo clippy -p assistant-runtime-host --all-targets --all-features -- -D warnings
```

完成判定：既有 Desktop HTTP/SSE 和 Runtime 启停回归通过；关键故障会触发受控关闭，可降级子系统故障
不会拖垮 Runtime，所有已启动任务都能被回收且没有脱离 Supervisor 的长期后台任务。

Review 重点：Host 是否开始持有 Session/Run 权威状态；是否把单连接错误升级为进程故障；是否为了未来需求
增加抽象框架；既有关闭窗口、退出 Desktop 和停止 Runtime 三个动作是否被混淆。

### M1：Runtime 设备与渠道领域

前置依赖：M0 已确认。

目标：在不建设第二套会话或投递存储的前提下，把设备注册事实、通用 Channel 输入来源、输出周期、
附加 delivery 和 PC 输出托管纳入现有 Runtime/Store，并让旧 Runtime Home 可安全升级。

交付范围：

- 落实设备注册、展示名称、撤销状态、能力事实和 PC 输出托管的 Runtime 领域与 Store 端口；
- 将输入入口抽象在 Session 层，Device 只是通用 Channel Source 的一个变体，不在顶层硬编码
  `controller_session_id`；本版由产品策略把 Device 输入解析到当前 Controller；
- 扩展既有 Input/UserMessage/Conversation 来源元数据，不复制消息正文、顺序或恢复生命周期；
- 建立输出周期的来源关联、已播报/单次补齐状态和零到多个 Channel Delivery 结算事实；Desktop
  规范展示不是可被替换的 delivery；
- 落实终端来源、代理报告返回渠道和 PC 输出托管的优先级，以及设备解除配对时解除托管的组合操作；
- 完成 SQLite/内存 Store 迁移、旧数据缺省、重启恢复、幂等和 TypeScript 协议导出测试。

验证入口：

```bash
cargo test -p assistant-protocol
cargo test -p assistant-runtime
cargo test -p assistant-runtime-host
cargo run -p assistant-protocol --example export_typescript -- --check
cargo clippy -p assistant-protocol -p assistant-runtime -p assistant-runtime-host \
  --all-targets --all-features -- -D warnings
```

完成判定：旧会话和消息可无损恢复；任意显式输入与最终输出仍只有一份规范 Conversation 事实；PC 托管、
来源返回渠道和附加 delivery 可跨重启解释，且没有以 `revision`、候选历史或第二套回复表制造冗余状态。

Review 重点：Session 是否仍为最大兼容实体；Controller 绑定是否只存在于产品策略；Host/Runtime 状态所有权
是否清晰；代理报告是否被误当成独立输入渠道；changed time 是否只服务真实业务查询而非惯性落库。

### M2：安全 Gateway 与基础模拟器

前置依赖：M1 已确认。

目标：建立可被真实终端实现复用的安全发现、配对、注册和 WSS 基线，并让 Node 基础对端通过同一协议
完成发现、配对、重连和撤销验证。

交付范围：

- 在 Host 私有模块实现安装级服务端证书、mDNS 宣告、WSS listener、协议 envelope/codec、限流、
  heartbeat、连接替换和有界背压；
- 实现配对窗口、待配对设备候选、配对码 SPAKE2 验证、完成配对后的 Ed25519 长期身份登记，以及
  过期、错误次数、取消和撤销；长期凭据只在配对成功后持久化；
- 通过 Host Command 暴露“开启/关闭配对窗口、确认候选、重命名、撤销”等交互意图，不把这些动作
  塞入 Runtime Agent 指令系统；
- 完成能力协商和本轮合法输出偏好校验，设备可自报偏好但不能越过已认证身份和有效 capability；
- 新增 `docs/modules/device-simulator.md`，建立 Node 24 LTS 的 `tools/device-simulator` 基础工程、
  设备身份 Store、mDNS/WSS 客户端、codec、重连状态机和最小 CLI/本地页面；
- Rust 与 Node 共享并互验 JSON envelope、签名/挑战和基础错误码 fixtures。

验证入口：

```bash
cargo test -p assistant-runtime-host
cargo clippy -p assistant-runtime-host --all-targets --all-features -- -D warnings
cd tools/device-simulator
npm test
npm run lint
npm run build
```

完成判定：Node 能发现 Host、显示配对码、由 Host 确认后获得长期身份、重连并完成能力协商；错误码、过期、
旧 nonce、签名错误、撤销和同设备连接替换均 fail-closed，未配对设备不能提交业务输入。

Review 重点：是否先签发长期密钥再配对；设备候选是否仍为 Host 易失状态；证书/私钥是否进入日志或 H5；
是否出现明文 WS、关闭证书验证或 Host 反向扫描连接设备的捷径。

### M3：文字交互与回复路由

前置依赖：M2 已确认。

目标：先用不依赖语音 Provider 的文字链路打通正式 Device WSS、Runtime Input、唯一 Conversation、
Assistant Output 和多渠道附加投递，验证本版最核心的渠道模型。

交付范围：

- 设备以稳定 `client_input_id` 提交文字输入，Host 认证后映射到通用 Session 输入入口；
- 复用现有可靠 Input、Queue、Run、审批和 Conversation 链，accepted 前后断线重试不重复创建 Run；
- Desktop 继续接收规范 Input/Conversation/Event，Device 只接收经裁剪的轮次状态和允许的文字输出；
- 实现 Desktop Input 的 PC 托管附加投递、Device 来源优先、代理报告返回原 Device，以及无明确外部
  来源报告在结算时按 PC 托管决定附加投递；
- 附加 delivery 独立派发，一个终端断线或拒绝不得影响 Run settlement、Desktop 展示或其他终端；
- 覆盖多设备并发、来源设备与托管设备不同、解除托管、能力不足和连接切换场景。

验证入口：

```bash
cargo test -p assistant-protocol
cargo test -p assistant-runtime
cargo test -p assistant-runtime-host
cargo run -p assistant-protocol --example export_typescript -- --check
cd tools/device-simulator
npm test
npm run build
npm run test:m5-e2e
```

完成判定：Node 文字输入和 Desktop 输入都进入同一主控 Conversation；Desktop 始终显示完整显式输入与最终
输出；来源 Device 优先于 PC 托管，多个终端不串投，重试不产生重复 Input/Run。

Review 重点：是否将 Desktop 与 Device 设计成互斥单一输出渠道；是否把在线 connection ID 持久化；
是否让 Node 指定任意 Session/目标 Device；投递失败是否错误改变规范 Assistant Message。

### M4：Desktop 设备管理与托管

前置依赖：M3 已确认。

目标：以最小、清晰的 Desktop 交互让用户完成接入启停、候选配对、设备管理和 PC 输出托管，并能在
Conversation 与主控输入区理解当前来源和托管状态。

交付范围：

- 在设置中增加智能终端入口：启停接入、打开/关闭配对、查看候选、输入配对码、已配对设备、
  在线状态、重命名和解除配对；
- 在主控输入区域提供唯一的频道托管选择/状态图标，菜单只列出在线目标并支持切换或解除；Desktop
  和智能终端通过前缀图标区分，不显示副标题或在线文案，管理快捷项保留纯文字；完整设备能力进入
  设置详情，不在会话顶部或右侧信息栏重复提供托管入口；
- 主控 Conversation 对 Device UserMessage 展示低干扰“设备名 · 文字/语音”来源，不把标签写入正文；
- 移除会话顶部现有“空闲/运行” tag，相关会话状态继续由右侧信息和既有执行反馈承载；
- 展示 ASR/TTS 的 `ready | unavailable | degraded` 脱敏状态，但不提供 Provider、模型、声音或密钥编辑表单；

### M6：speak、TTS 与播放

前置依赖：M5 已确认。

目标：让模型通过 `speak` Tool 主动生成适合朗读的压缩文本，允许在长输出中分段立即交给

交付范围：

  `speak` 使用指令；Desktop 输入不插入；
- 同一逻辑输出周期多次调用按顺序立即交付；单次最多 120 个 Unicode 字符，超长内容由模型
  按自然句子或语义边界串行分段；
- Tool、Context、Goal continuation 和审批等待均继承周期；真实结束仍无 `speak` 时只插入一次
  明确非用户交互的隐藏 Runtime 提醒续跑；
- Runtime 结算附加语音 delivery，Host SpeechService 接通 fake TTS 和 DashScope TTS Adapter，输出正式 PCM；
- Device Adapter 实现 playback start/frame/end/cancel、目标连接校验、慢设备背压和新输入打断本地播放；
  用户 PTT 接管取消活动 Run，单独停止播放不取消 Run；

- TTS、播放或设备连接失败不改变已完成 Run 和 Desktop 正文；一次补齐后仍无合法 `speak`

### M9：统一输入与 Run 续跑收敛

前置依赖：附件 E 已确认；M8 的既有证据在本里程碑完成后重新执行受影响部分。

目标：删除设备输入、Goal 自动推进和缺失播报提醒形成的平行 Input/Run 管道，使 Session 成为统一
输入实体，并让自动续跑统一表现为同一产品 Run 内的多个 AgentExecution Loop。

交付范围：

- Desktop 与已认证 Device 由 Host Channel Adapter 注入可信来源，Runtime 只保留一个 Session 输入用例；
- 抽取 `ContextChanged → Context Compaction → Goal → Speech Reminder → settle` 门禁流水线；
- 增加活动 Run 的可靠续跑提交操作，原子提交候选 Assistant、可选隐藏 Runtime Message 与必要 Goal effect，
  不创建后继 Input、Run、Queue 项或第二份 continuation 表；
- Goal 保持独立领域，预算、generation、恢复和回复路径不进入通用续跑结构；显式恢复仍创建新 Input/Run；
- 删除旧 Goal/speech 后继 Run、恢复清理和事件分支，同步附件 B/C、模块约束及受影响测试；
- 重新执行 Runtime、Host Store、Gateway、Goal、播报及受影响跨层回归，并更新 M8 证据。

完成判定：所有自动推进保持原 `RunId`，每个 Run 只有一次 accepted/started/finished；Runtime 输入不再
写死 Controller 角色，Host 路由仍只读取权威状态；Goal 与播报门禁可靠落账且不会重复续跑；旧分支和
同版本兼容别名已删除；定向验证通过并形成可复核证据。

Review 重点：是否把 Goal 业务状态塞进通用续跑；是否新增 `NextRun`、revision、续跑表或公共 DTO；
是否由 Host 复制 Session 权威状态；是否通过页面分页或事件投影掩盖持久语义错误。

实施结果（2026-09-01）：

- Desktop 与 Device 已统一进入 `submit_session_input`；Device 的目标 Session 由 Host 读取 Runtime
  权威会话投影后路由，Runtime 只校验已配对来源和活动 Session，不再写死 Controller 角色；
- Goal 自动推进与缺失播报提醒已迁入同一产品 Run 的 AgentExecution 门禁，活动 Run 增量提交只追加
  Conversation 消息和必要 Goal effect，不创建后继 Input、Run、Queue 项或 continuation 表；
- Goal token/执行次数预算按 AgentExecution 结算，显式 Goal 恢复仍保留新 Input/Run 的业务语义；
  用户接管播报不会触发补播，旧后继 Run 恢复和兼容分支已删除；
- 已通过 `cargo fmt --all --check`、`git diff --check`、Runtime 247 项单元测试、Host 183 项单元测试
  （1 项手工性能基线忽略）、正式 Host Goal 协议测试，以及 Runtime/Host 全 target、全 feature Clippy。
