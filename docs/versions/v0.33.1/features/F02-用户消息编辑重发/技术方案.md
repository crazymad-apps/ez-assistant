# v0.33.1 F02 技术方案：用户消息编辑重发

## 一、状态与范围

更新：2026-11-11。**技术方案已确认，M0 存储实现已接入**。用户在核对单一历史来源、性能及内存索引后回复“好的，那没问题，继续把”，确认本方案并进入[交互指导](界面交互设计指导.md)。F01 独立验收已通过。依据：[功能设计](功能设计.md)、[总体设计](../../总体设计.md) 5.4、[版本总计划](../../开发计划.md)。

底部 Composer 支持完整输入编辑，复用原发送按钮提交历史重入；增加编辑准备查询、历史冲突校验及附属输入保存。同步修正领取时的 Goal 延续规则，供 F03 介入复用。2026-11-11 用户确认将已提交输入收敛到会话文件单一来源；本方案包含旧数据迁移，不新增表或依赖。

### 2.1 输入与历史的唯一来源

当前正文文件保存输入事实，SQL `inputs` 长期保留 Input ID、顺序和幂等键；历史加载、重入及重试仍依赖两者对应。改为按可靠提交边界交接：

| 状态／数据 | 唯一来源 |
| --- | --- |
| 尚未进入可靠历史的输入／命令 | SQL 暂存载荷、幂等键、顺序及必要执行控制；包含已领取但尚未提交用户消息的输入 |
| 已进入可靠历史的输入／命令 | 会话文件保存完整输入、Input 身份、顺序、幂等键、选择及 Run 历史；读取与幂等查询不要求 SQL 历史行 |
| 已提交但尚有执行工作 | SQL 只保留 Input 引用、Run 状态、未决交换和提交回执等必要控制；不可变输入从文件读取，不保留另一份历史键或载荷 |
| 已全部结算 | 删除 Input／Run 的控制行，不留永久幂等身份行；历史仍从文件读取 |

`StoredInputHistory.idempotency_key` 随输入事实保存；会话命令沿已有文件字段保存。后续 Run 结算、重试和元数据更新保留原键，不从已清空的 SQL 字段覆盖文件事实。键属于当前会话的接纳记录，不下发 UI，也不凭只读历史恢复执行。Session 配置、Goal 当前状态、资源所有权及实际用量账本仍按原职责存储。

Runtime 的历史投影及 Store 的查找索引均可从文件重建。文件代次切换即失效；同代追加只在可靠发布后更新。不得以缓存未命中判断请求未提交，也不把历史重新装进 `RecoveredRuntime.inputs` 作为执行控制。Volatile 同样从历史事实回读，移除长期 `input_identities` 权威。

性能约束：全局启动和列表查询不扫描历史。键映射并入当前 owner 已有的有界索引，在同次冷扫描中建立、可靠追加后增量维护；避免先为幂等扫一遍、再为会话装配重复扫描。热查询只返回命中的 Input／首次 Run，不调用全量历史快照接口复制所有事实；分页和预览不增加正文扫描。

## 三、协议与历史前置条件

### 3.1 查询与命令

| 接口 | 请求 | 结果 |
| --- | --- | --- |
| 新增 `GetUserMessageEdit` | `session_id`、`message_id` | `ObservedSnapshot<UserMessageEditPreparation>`：`ready` 含完整 `UserMessageSnapshot`、原 `variant`、`generation`、`message_count`；`blocked` 含类型化原因 |
| 调整 `ReenterFromUserMessage` | `session_id`、`message_id`、`message`、`variant`、`attachment_ids`、`quotes`、`skill_edit`、`mcp_edit`；必填 `expected_generation`、`expected_message_count`、`idempotency_key` | 原 `input_id`、`run`，增加 `user_message_id`、`generation`、可选 `execution_error: RuntimeErrorInfo?` |

`message`、`variant`、有序 `attachment_ids`／`quotes` 表达最终编辑内容，复用普通输入字段与 `QuotedTextSnapshot`。`skill_edit`／`mcp_edit` 分别使用 `retain`、`clear`、`select` 三种意图；`select` 仅传 Skill 名或 MCP server key。这样可区分保留原冻结内容与重新选择同名项，客户端不传 Skill 正文或内部 Part。有效原输入可原样提交，同样创建新的 Input 和首次 Run。Goal 按领取时当前状态处理。

查询不锁定会话或创建服务端草稿。`blocked` 表达非空闲、归档／只读、继承／非真实输入、无法完整还原原输入、Goal 目标边界或消息不存在；权限和读取失败走错误通道。可识别但当前不可用的附件／选择仍载入并标明状态，用户可移除或替换；提交校验最终保留的内容。

返回的 `generation` 为包含新消息的当前可靠代次，幂等命中时也如此。新输入已被后续裁尾删除时，按第六节拒绝重放。

### 3.2 历史冲突校验

- `generation` 检测裁尾、清空和压缩等替换；`message_count` 检测同代追加。
- `message_count` 取 Store 原始窗口 `total`，与 Session 完整产品计数核对；包含系统／隐藏／工具消息，不计 JSONL 元数据帧，也不是已加载行数、Run 数或 Journal 长度。
- 查询在同一 Session mutation 内读取原输入和上述两值；客户端原样回传。提交重新读取并比较，任一变化返回 `SnapshotStale`，保留草稿。纯标题／状态变化不视为正文冲突，运行和权限条件仍重验。
- `ConversationRewrite` 携带两个 expected；正式 Store 在准备文件前及事务切换时核对，SQLite CAS 同时检查 `body_generation` 与 `message_count`。Volatile 在单锁内检查。
- 当前 Goal 的 objective 边界、状态和运行条件在提交时重验，准备至提交的 Goal ID／generation 由内部 CAS 保护。

### 3.3 读取与能力准入

打开编辑时调用 `locate_conversation_message` + `load_conversation_raw_window(limit=1)`，提取共用 User DTO 投影；hover 不读取全文。查询核对 owner、generation、Input 关系和观察水位，沿现有读取预算与取消机制。提交仍需重建完整前缀，成本随历史长度增长。

`ApplicationCapabilities.user_message_edit` 默认 false，完整链路接通后开启，用于识别前期 0.33.1 Host。缺少能力时保留复制，禁用编辑并提示 Host 不支持。

## 四、原输入解析与重建

### 4.1 资格检查

查询与提交共用检查器：

- 仅允许当前可写主会话内、可见、非继承、有可靠本地 Input 归属的真实用户输入；核对 `StoredInputHistory`、origin、可见性和 `cross_session`。
- 拒绝隐藏输入、会话命令、ControllerDelivery、ProxyReport、只读 child、归档及未知来源。
- 复用 `SessionController::ensure_idle`，补查活动 child 和未决审批；Store 最终检查 queued Input／Run、pending tool exchange、body append、child 及 child pending。
- 目标位于当前 Goal objective 或之前时拒绝；保留前缀必须满足工具调用／结果配对。

### 4.2 重建规则

| 内容 | 处理 |
| --- | --- |
| 文本 | 使用编辑后正文，生成新 Text Part |
| 附件／图片 | 原附件按已上传资源载入；新增附件先沿现有上传流程取得 ID。最终 ID 列表按提交顺序经 `resolve_file_references` 校验 Session 归属及 Ready，未保留的附件不进入新输入 |
| 引用 | 提交最终有序列表；原 quote ID 从可靠原输入恢复冻结内容，新增引用沿 `normalize_quotes` 校验，统一生成新 Part ID。支持移除／重新引用，不直接改写引用原文 |
| 显式 Skill | `retain` 核对原 InternalContext 与 ledger 并复制精确冻结内容；`clear` 不附带；`select` 沿普通输入解析当前 Skill 并冻结。生成新 Activation、Part／boundary 与新归属 |
| 显式 MCP | `retain` 保留原 server key／冻结名称；`clear` 不附带；`select` 按当前目录解析。保留或新选均校验当前权限／服务，生成新 selection ID |
| Agent 变体 | 默认原变体，允许编辑草稿单独选择；通过 `create_user_message` 构造。模型、Shell、权限和会话配置使用当前值 |
| 其他内部上下文 | Goal、Channel、Shell 切换等由当前装配路径生成，不复制旧运行上下文 |

新消息、Input、Run 及其 Part／选择使用新身份；引用来源保留原 owner／message ID。冻结内部 Part 通过 `InternalBoundaryCoordinator` 重建，Skill 正文只在 Runtime／Store 使用。必要 Part 无法识别或恢复时拒绝提交。

引用来源位于保留前缀时，在 Store 确定实际新 generation 后、发布准备件前重新定位并核对原文范围；新代次可能跳过孤儿文件，不能假定 `old + 1`。来源在删除尾段时保留引文、标记不可定位；child／跨会话来源沿各自定位规则。前缀其他旧引用不批量重写。

输入至少包含文本、有效附件或引用之一；仅 Skill／MCP 不构成输入。按正文、有序附件／引用、选择意图和变体校验是否修改，允许仅更换附件或选择后提交。附件 Ready 不保证外部文件持续存在，后续变化按执行失败处理。

### 4.3 预编译

裁尾前完成附属输入准备与 Agent 预编译。`compile_run_agent` 接收显式 MCP 选择和领取时准备的 Goal 上下文；普通领取、编辑立即领取共用规则，F03 在交接后复用。

准备阶段不临时修改 Session，也不调用 Provider 或执行工具。普通队列异步装配后重验 Input、Goal ID／generation、历史和配置；失效则重新准备。实际启动仍校验当前配置和资源。

## 五、提交、事务与调度

### 5.1 提交顺序

```text
身份准入 → operation gate → prepare Session → Session mutation
  ├─ 幂等命中：返回可靠 Input／Run
  └─ 首次提交：资格、空闲、Goal、expected 检查
      → 重建输入与前缀 → 预编译 → Store::rewrite_from_user
      → 安装新 Journal／投影 → 发布事件 → 释放 mutation → 唤醒执行
```

编辑从前置检查至内存安装持有 Session mutation，与输入接纳、清空、压缩和归档串行；同步状态锁不跨 `.await`。幂等回读先于目标存在性、空闲和资源检查，身份准入始终执行；无法读取可靠结果时返回待核实错误。

### 5.2 存储事务

沿 `begin_replacement`／`commit_rewrite`：

1. 从文件核对目标 Input 与顺序，校验 expected 和空闲；分配实际 generation，准备保留前缀及新输入，不再查询目标 SQL 身份行。
2. SQLite 事务 CAS 原代次和消息数量，重验空闲；处理失效卡片、已删除 child 检索记录及资源关系。尾段 Input／Run 历史由新文件的保留范围决定，不再同步删除一套 SQL 历史。
3. 为新 Input 创建必要引用控制与首次 Accepted Run；若需恢复 Goal，同事务保存 Goal CAS 和绑定。已消费的显式 Skill／MCP 选择直接形成文件事实，只有实际未完成的激活控制留 SQL。
4. `freeze_rewrite_input` 写入完整 Input（含幂等键）、Run、origin、Skill／MCP 和引用事实；同步文件、回读校验后提交 SQLite 代次指针。新 Input 的键及历史载荷不另存 SQL。
5. 提交后清理旧代次文件及已删除 child 目录；前缀、新输入和其他会话／分支仍持有的资源保留。

编辑重发复用原代次已核验的位置与事实索引。新代次同步后用一次全文回读完成逐条正文比对、结构及事实校验和位置索引构建。追加输入事实时复核准备件的长度及修改时间，只回读新帧并推进私有索引，发布事务提交后才把索引放入 LRU。新写入的代次正文按编码后字节数切分 JSONL 帧，通常不超过 512 KiB。单条超限消息或完整工具交换独占一帧，已有文件仍按原格式读取。

`NewStoredInput` 使用已有 Skill／MCP 字段；结果返回新选择投影或从提交事实回读。Session 的 inputs、runs、选择、feedback、commands、Goal、计数及 Journal 安装完整后发布事件。

Volatile 在单锁内完成校验和准备后，统一改写历史及必要执行控制；返回值与正式 Store 一致。

### 5.3 失败边界

| 失败位置 | 处理 |
| --- | --- |
| 文件准备／SQL 提交前 | 旧历史有效；提交结果不明时保留恢复文件 |
| 已提交、内存安装前崩溃 | 从新代次恢复；新 Run 按中断／待恢复规则处理 |
| 内存安装失败 | 标记 Session 故障，通过重载／重启恢复 |
| 唤醒失败 | 保留接纳结果，返回 `execution_error`，进入既有执行恢复路径 |
| 提交后的文件清理失败 | 沿既有 best-effort 清理处理，不回报编辑失败 |

裁尾只处理会话历史及所属关系，不回滚文件、Shell、远端操作或实际使用账本。

### 5.4 Goal 与输入调度

| 状态／输入 | 规则 |
| --- | --- |
| Goal Running，普通队列输入 | 保留队列，Goal 自动续跑不领取这些输入 |
| Goal Paused，普通队列输入 | 按正常顺序及运行门禁领取；实际启动时自动恢复同一 Goal |
| Goal Paused，合法编辑重发 | 裁尾事务立即领取新输入，同时恢复同一 Goal |
| F03 介入（非队列输入） | 当前 Step 完成、旧 Run completed 后，优先于普通队列及旧 Goal 自动续跑启动；延续当前 Goal，Paused 时自动恢复 |
| 无 Goal／Goal 已完成或清除 | 正常启动输入，不重新打开已完成／清除的 Goal |

仅入队、等待 Step 或预编译失败不恢复 Goal。显式暂停队列、执行失败、重启及未决审批／反馈仍受正常运行门禁保护；恢复只绑定本次领取的输入。

实施改动：

1. `next_runnable_input` 的 Running 分支保留 Goal lane，Paused 改走普通队列。清理输入投影、Goal 暂停／结算中仅因 Goal 存在或队列非空写入的 `resume_required`，保留真正的暂停和恢复条件。
2. Composer 普通发送不再根据 paused 快照切换为 `resume_goal`；已有显式 Goal 控制入口保留。
3. 复用 `GoalControl::resume`、`inject_resume_context`、`GoalInputBinding`，提取领取时共用的私有准备逻辑。保持 Goal ID、objective、预算，generation／turn 按恢复规则推进，新指令进入真实用户上下文。
4. 扩展 `claim_input(StoredRun)`，同事务保存 Input 的 Goal 上下文／绑定、Goal CAS 和新 Run。编辑通过 `RewriteGoalEffect`、`NewStoredInput` 承载同样效果，正式 Store 与 Volatile 一致。
5. 提交后安装 Goal／Input／Run／lane；F02 已领取的 Accepted Run 在唤醒及幂等重试时复用绑定，不重复恢复。

F02 落实公共领取规则。F03 负责介入意图、Step 交接及竞争处理：队列项转换保留 Input 身份，旧轮结算到介入领取之间不允许普通队列或旧续跑插入；旧 Run completed 不代表 Goal 完成。异常仍保留真实终态和待恢复输入。

### 5.5 普通输入交接、重试与复制

- **交接**：普通输入领取仍只创建 Run；`commit_user_message` 才将用户消息、Input／Run 与键通过现有 append receipt 写入并同步文件。完成事务发布可靠边界，同时清掉 SQL 中已交接的键、载荷及只用于历史的字段。崩溃按原回执恢复；未发布的文件尾帧不能参与查询。
- **结算**：所有关联 Run、交换、子任务及提交回执都完成后，删除剩余 Input 控制行。尚有恢复工作时保留真实控制，不为清行级联丢弃依赖。无正文输出的失败／取消同样先可靠保存 Input／Run 终态，再释放控制；未领取队列取消不生成历史。命令完成采用相同交接原则。
- **重试**：`create_run_attempt` 从文件核对本地输入、最新 attempt 和可重试状态，重新创建必要的 Input 引用控制与新 Run；不要求旧 SQL 行仍在，不复制或重新接纳历史输入。启动只恢复 SQL 中的未完成工作，历史查询独立读取文件。
- **裁尾／压缩／清空**：同一 owner 的换代保留仍属于当前历史的 Input 与键；裁掉的记录及键一起离开当前代次。仅缩小执行上下文不丢弃仍保留在历史中的接纳事实；新索引由可靠文件派生，不维护 SQL 历史镜像。
- **分支复制**：新 Session 只继承截点内的只读消息与历史关系，清除复制事实中的输入及命令请求键，不生成历史 Input／Run 控制行；源会话不变。相同 Session 身份的完整备份／恢复则保留键。继承历史不能用于新会话的幂等命中或执行重试。

## 六、幂等与恢复

点击原发送按钮时，先完成新增附件上传，再生成 `IdempotencyKey`，冻结目标、expected、全部编辑字段和连接作用域；重投复用原附件 ID、key 及请求。修改请求前须先核实旧结果，再创建新意图。

幂等作用域保持当前身份域与 Session。新增 Store 接纳结果查询，供普通输入、命令和重入在准备资源前使用；返回已有接纳结果或跨类型键冲突。Store 写入边界在同一 Session 串行保护下复核：未提交输入查 SQL，已提交输入查当前可靠文件；返回原 Input 与首次 Run（尚未领取时可空），不创建新 attempt。SQL 的唯一约束只约束暂存键，不能代替文件检查。复用位置索引按需建立键到事实位置的派生映射，缓存缺失时读取文件，读取失败不能当作未接纳。

键随当前历史留存，不另建永久回执表。历史裁掉或清空后，不承诺其普通请求键仍可去重；F02 原请求仍受原目标及 expected 保护，禁止换新基线自动重发。既有 Session 首次物化身份约束保持，不能借清空重新物化。

| 情况 | 处理 |
| --- | --- |
| 明确校验拒绝 | 保留草稿与原历史；修正并重新核对后提交新意图 |
| 超时、断线或结果未知 | 进入 `uncertain`；同身份重连后自动重投原请求一次，后续由用户触发核实，始终使用原 key／expected |
| 首次请求未到达 Runtime | 重投可能完成首次写入，不能把核实操作描述为纯查询 |
| 首次已接纳 | 回读新 Input／Run，即使原目标消失或当前非空闲 |
| 幂等记录被后续裁尾删除 | 旧 expected 拒绝重放，提示当前历史无法确认原结果 |
| 已接纳、刷新失败 | 进入 `sent_refresh_pending`，只重试读取 |
| Host 重启，内存意图仍在 | 同 key 核实可靠结果；Run 中断／待恢复据实展示 |
| 客户端硬刷新／关闭 | 重新读取权威历史，不自动重放已丢失的内存稿件 |

请求取消只结束客户端等待。UI 分别处理校验拒绝、结果未知、接纳后执行失败和刷新失败，不自动更新 expected 后重发。身份／Host／组织切换后，原意图停止自动重投，回调仅作用于原连接。

沿用 `SnapshotStale`、`SessionNotIdle`、`SessionArchived` 及资源错误；新增 `UserMessageNotEditable` 表达原输入资格／完整性问题。具体不可编辑原因读取 typed blocked 结果。

## 七、前端接入与历史刷新

### 7.1 工具栏与 Composer 编辑模式

- 从 [ProcessingTurn](../../../../../apps/desktop/src/features/conversation/ConversationView/ProcessingTurn/index.tsx) 提取共用 `MessageActions` 及 SCSS Module，用户栏沿用样式，提供复制／编辑 icon、提示、aria-label 和 hover／focus 显隐。
- 复用当前 Session 的活动 Run 投影控制入口：存在活动 Run 时不渲染任何用户消息的编辑按钮，保留复制；结束后按资格恢复，hover、键盘与触摸一致。已打开的编辑稿继续保留并禁用提交；查询和提交仍由 Runtime 重验，不能只依赖按钮显隐。
- 复制复用 [copyText](../../../../../apps/desktop/src/platform/clipboard.ts) 及 HTTP 回退；失败显示固定提示，避免暴露 helper 中的原文。
- 编辑查询成功后，挂起普通草稿，将完整历史输入载入底部 Composer，并高亮原消息。输入框外侧上方复用 `ComposerSecondaryDrawer` 的外壳与标题栏样式，仅展示“正在编辑历史消息”和相邻的“返回原位置”“取消”；无描述段落、展开内容或折叠箭头。
- Composer 按编辑模式隐藏 Todo、Goal、Queue 等附属区域及其浮层，保留编辑稿的附件、引用和选择器；复用原 `expanded_drawer`，不重置展开状态，不停止业务订阅或发送状态变更命令。取消或接纳成功后，按最新投影恢复有效展开项。审批／问答沿现有工作区优先级占用输入区并保留编辑稿，结束后恢复编辑展示、重新核对资格。
- 提交复用现有发送 icon，编辑模式的提示／可访问名称为“发送修改”；不增加保存按钮。Enter 触发同一编辑提交，Shift + Enter 换行，IME 与 Ctrl + Enter 不提交；编辑模式不走普通队列或 F03 介入。会话控制命令及 Goal 创建入口不参与历史编辑提交。
- Composer 管理挂起的普通草稿与活动编辑草稿，复用附件、引用和 Skill／MCP 控件；完整保存各自正文、附属内容、变体及普通草稿的 Goal 标记。编辑内的选择只修改编辑稿，不调用 Session 变体设置。
- 原附件按 `attachment_id` 加载元数据并作为已上传项展示。附件选择、上传及引用加入操作绑定具体草稿身份；切换模式不清理挂起草稿的资源，异步结果不能写入另一草稿。取消只释放编辑新增且未提交的临时选择，不删除原附件或普通草稿资源。
- 编辑控制状态为 `loading / editing / submitting / uncertain / sent_refresh_pending`，绑定身份、设备、Session 和目标。返回原位置只定位，不结束编辑；取消或确认接纳成功即恢复普通草稿，明确失败则保留编辑稿。
- 提交／结果未知时禁用取消和重复发送；接纳成功但刷新失败仍恢复普通草稿，另行提示读取重试。切换会话可挂起编辑稿，改换编辑目标前处理未保存内容；断线保留，关闭后不持久恢复。
- 历史变化保留编辑稿，重新读取依据和附属信息须让用户核对。原发送按钮先按 Composer 模式分发：历史编辑调用重入，普通模式才使用队列／介入规则。

### 7.2 刷新顺序

1. Runtime 安装状态后发布 `ConversationCommitted { owner, generation }`、`RunAccepted` 及相应 Goal／队列事件。
2. 发起端记录接纳结果、结束可发送状态，再读取 SessionView；读取失败按第六节恢复。
3. [RuntimeProjectionStore](../../../../../apps/desktop/src/stores/RuntimeProjectionStore.ts)／[RuntimeLifecycleCoordinator](../../../../../apps/desktop/src/stores/RuntimeLifecycleCoordinator.ts) 按 owner、generation、observed_sequence 和请求身份拒收旧响应；收到新代次即失效旧正文、导航、预览、定位、child 和卡片。
4. [ConversationNavigationStore](../../../../../apps/desktop/src/stores/ConversationNavigationStore.ts) 清理旧 ID 及在途请求。发起端通过 `locateConversationMessage` 按 F01 顺序补齐到新用户消息；其他客户端保留有效锚点，被删除时提示并回到有效位置。
5. 事件缺失／重连由权威快照恢复。导航仅配对新用户与紧跟 Run 的可选最后正文，未生成时保留用户单项。

项目归属、创建时间和手动排序保持。

## 八、兼容与迁移

- 软件及应用最低兼容版本为 0.33.1；Rust／TS、导出、夹具及调用方同步。客户端发送前须校验编辑 capability，缺少时不调用旧重入；新请求仍有旧必填字段，不能依赖旧 Host 拒绝未知字段。新 Host 拒绝缺少编辑字段、expected／幂等键的旧请求，覆盖实际配套测试。
- F01 阶段数据库目标及最低 Host 为 0.33.0 的结论保持。F02 需迁移：数据库目标与最低 Host 调整为 0.33.1，历史文件格式由 1 升为 2；新格式保存输入键，`inputs` 收敛为暂存／未完成控制。旧 Host 须在恢复或写入前被数据库准入拒绝，同为 0.33.1 的早期包也必须通过存储目标／格式检查，不能只比较应用版本。
- Desktop、Host Web 和远端共用 Runtime 命令与身份隔离。新增查询加入只读准入，重入不加入只读自动重试。
- 日志仅记录关联 ID、阶段、耗时和安全错误；输入全文、引用、Skill 正文、路径及凭据不记录。HTTP 输入限制沿用现有约束。

迁移沿既有启动迁移器、实例锁、备份和文件代次提交机制执行，服务开放前完成：

1. 核对实际数据库与会话目录，独立备份数据库及关联文件并验证可读、关键表数量与文件对应关系。按旧格式处理未完成提交回执，取得一致的可靠边界；无法恢复则停止迁移。
2. 顺序读取各 owner 当前可靠文件，主会话的本地 Input 以 Session＋Input ID 关联旧 SQL 键并核对消息身份／顺序；命令沿现有身份、键及结果校验，不将文件中的队列顺序与 SQL 自增行号混为同一值。继承记录不带键。生成新格式的独立代次并校验，消息、Run 身份与先后关系保持。旧键为空仍为空，映射缺失或冲突直接失败，不猜测或丢弃。
3. 准备件全部同步后，在 SQLite 事务中复核原指针，切换文件代次、删除已完成身份行、清掉已交接控制行的历史字段，并更新迁移账本及兼容下限。未提交输入的载荷／键、未完成工作及其引用保持；有真实依赖的控制行不能当作历史残留删除。
4. 重开读取核验历史、队列、幂等和恢复引用后，沿原流程清理旧代次。发布前失败保留旧指针与数据；发布后以新文件为准。升级后不能只回退数据库，恢复必须配套数据库及文件备份，新版本产生的数据不能由旧 Host 继续写入。

格式兼容读取仅用于迁移，不保留常态双读／双写。迁移不补造缺失的 Skill、引用或来源事实；不能完整恢复的旧输入仍不可编辑。M0 以独立隔离库验证迁移、原件及配套备份；用户数据的实际升级按仓库数据库操作规则执行。
