## 二、消息展示

介入命令返回“已启动”后，用户消息直接出现在聊天列表，正文、附件和引用均来自已提交历史。当前 Run 被打断时，已输出 reasoning／正文保留在原轮次，状态按真实终态显示（通常为“已取消”）；新 Run 的回复位于介入消息下方。

```text
  原轮次：处理过程 · 已取消
  已输出的 reasoning、正文和实际工具结果……

                         ┌────────────────────────────┐
                         │ 请先调整接口，再继续测试。 │
                         └────────────────────────────┘
                                             [复制]
  新轮次：处理过程 · 运行中
  后续回复……

  待执行队列  2                                       ⌄
  │ 1  补充单元测试……                 [优先] [↳] [×] │
  │ 2  更新使用说明……                 [优先] [↳] [×] │
  附件／引用
  输入消息……
  ＋   执行设置                    模型设置   [发送]
```

↳ 为普通队列项“介入”，× 只属于普通队列原有移除操作。聊天列表中的介入消息没有撤回按钮，也没有等待领取后转正的气泡。“已启动”的消息已经保存且新 Run 已启动；尚无助手回复时仍正常显示用户消息。

## 三、提交与接续

Desktop 和 Host Web 根据当前编辑状态、Host 能力与队列项决定介入入口何时可用。快捷键和队列项按钮分别提交投递意图和已有 InputId。

1. Ctrl + Enter 或 macOS Command + Enter 发出介入命令并等待返回。期间显示“正在介入…”、保留草稿并禁用再次提交；主按钮沿现有规则（有内容为发送，请求期间禁用），不为介入切换为停止。
2. Host 把介入消息放到队首并取消当前 Run；旧输出可靠落盘后，介入消息按普通发送的流程被领取并启动新 Run。没有活动 Run 时直接领取。待回答的问题一并作废，不要求先回复。
3. 可靠提交的响应直接带回用户消息和 Run。清理本次草稿，按 messageId 合并正式消息。Run 输出和错误沿用现有展示。等待期间介入消息是队首的普通队列项，抽屉如实显示，被领取后移出。
4. 普通队列项“介入”等同于“优先”加打断当前 Run：原行移到队首，被领取后移出并显示正式消息；未执行时留在队首，不影响其他普通项的相对顺序。
5. 已进入聊天列表的介入消息不提供撤回，也没有待转正气泡；仍在队列中的可按队列原有的移除操作处理。复制及附件／引用预览沿普通消息样式；历史编辑遵循 F02 门禁。

本次命令返回后可再次介入：A 启动的 Run 被 B 打断时，A、B 两条用户消息都保留，A 的已输出内容仍位于 A 下方；尚无输出时不补空助手消息，缩略允许只显示 A。多端的介入由 Host 逐条串行处理；同一请求重试不新增气泡或再次打断 Run。

介入消息按已保存事实进入 F01 分页与导航。未接纳时保留原稿；连接中断时的表现与普通发送一致，用原幂等键核实，不能把提交进度当作发送成功。

## 四、输入入口

| 操作 | 行为 |
| --- | --- |
| Enter／点击发送 | 普通队列输入 |
| Ctrl + Enter；macOS 兼容 Command + Enter | 介入 |
| Shift + Enter | 换行 |
| IME 确认候选 | 不发送 |
| 普通队列项“介入” | 复用该条完整输入介入 |

macOS 提示“发送（Enter）· 介入（Command + Enter）”，其他平台提示 Ctrl + Enter。历史编辑、Slash 和专用问答沿原入口。等待回答时，专用问答保留，普通输入框提供介入快捷键。新会话和附件输入使用同一规则。

普通队列保留“优先／恢复、介入、移除”的操作顺序。抽屉不为介入消息增加专门的样式或计数；介入按钮名称、Tooltip 和可访问名称均为“介入”。

## 五、停止与异常

| 状态 | 展示与动作 |
| --- | --- |
| 请求提交、取消收尾或可靠保存中 | 提交位置显示“正在介入…”，同一请求禁用重复操作 |
| 回执未知／断线 | 显示“正在确认…”，重连核实原请求，不能换 key 重发 |
| 命令成功 | 响应中的正式消息直接显示，新 Run 后续输出沿原流式展示 |
| 请求期间用户停止 | 旧 Run 照常保存输出；介入消息不执行，留在队首，队列按原规则显示为已暂停，提示“已停止，消息保留在队列”并清理草稿。恢复队列后照常执行，也可移除 |
| 命令返回后用户停止 | 按原规则停止新 Run，保留已提交消息与输出 |
| 旧输出保存失败 | 展示真实故障；介入消息留在队列，清理草稿，沿现有故障恢复流程 |
| 未接纳（预检或接纳失败） | 保留草稿并显示原因，当前 Run 不受影响 |
| Host 不支持 | 不开放介入入口，不按普通输入代发 |

取消或失败终止后只有 reasoning 也保留原处理过程，可沿现有折叠／展开方式查看。可靠历史接替实时输出时保持内容和展开状态，刷新、重连及结算后重启仍可读。

停止控制执行，不移除历史。没有“撤回后恢复旧轮”的反馈：旧 Run 一旦被打断即结束。

运行中 Goal 被介入时，Goal 状态行沿现有投影先显示已暂停，介入消息启动后恢复为运行中；这是同一 Goal 的延续，不另外提示“Goal 已停止”，也不要求用户手动恢复。等待期间用户停止的，状态行保持已暂停，介入消息留在队列抽屉队首；恢复队列后消息执行，Goal 随之恢复。

## 六、滚动与可访问性

本端介入成功沿普通发送规则定位用户消息；之后主动上翻停止跟随。旧轮收尾、其他端提交、重连与 Run 状态变化不强制跳到底部。以真实 messageId 保持阅读锚点、展开状态和焦点。

复用普通气泡的窄屏换行、附件布局及主题。按钮支持键盘焦点与触屏，播报简短提交／执行状态，不重复朗读流式内容。

## 七、验收

核对 Desktop／Host Web 的快捷键、普通队列转换、正式消息直接展示、无撤回、连续介入、主按钮规则不变、待回答问题作废、取消与失败终止的输出留存、重连及跨 Host 隔离。持久消息进入分页／导航，全部未完成控制仍参与 F02 编辑门禁。实施与验收见 [Feature 开发计划](开发计划.md)。
