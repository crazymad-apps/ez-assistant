# v0.33.1 F03 技术方案：介入与运行打断

## 一、方案信息

- 日期：2026-11-12。状态：**已确认**。2026-11-12 用户回复“确认并编计划”。
- 依据：[功能设计](功能设计.md)、[总体设计 5.5](../../总体设计.md#55-enter介入与队列操作)、[版本总计划](../../开发计划.md#f03-介入与运行打断)。
- 介入是一条阻塞命令，由三个已有动作组成：**普通接纳 → 对该输入执行现有“优先” → 取消当前 Run**。旧 Run 的结算、新消息的领取与启动全部由现有队列驱动完成，发送代码只有一套。阻塞指调用语义，Rust 使用 await，不阻塞 Tokio 工作线程。
- 新增内容只有三项：终止输出留存、介入时作废待回答问题、命令对领取结果的等待（复用现有队列事件）。另有一把只在介入命令之间串行的锁（4.4）。接纳与存储代码不改；无介入专用队列、撤回、暂存气泡或新增数据库字段；不需要防止队列抢占的机制或停止检查。

已核对的现状：

- M0 开发前，`ExecutionOutcome::Cancelled` 与 `Failed` 都只携带 consumption／error，结算时都不追加当前未完成的消息。
- 公开的 `cancel_run` 只发信号，且拒绝绑定运行中 Goal 的 Run；`interrupt_run` 先置 `queue_paused_by_user` 再取消，并且只接受当前活动 Run。介入不串联这两个公开命令，直接复用底层取消与结算。
- 现有提交在存在待回答问题时拒绝新输入；介入不沿用这条门禁，见 4.3。
- 发送只有一条路径：普通发送是“接纳入队 + 唤醒驱动”，领取、写入用户消息和启动 Run 都在队列驱动内；F02 编辑重发最后同样交给驱动。驱动在 Run 结算后回到循环开头重新取下一项。
- 队列顺序在存储中持久：读取按 `COALESCE(priority_order, queue_order)` 排序；“优先”经 `prioritize_queued_input` 在一个事务内把其余条目后移、目标置首，跨重启保持。问答回复的队首插入只见到内存中的 `push_front`，未见对应的持久顺序写入，介入不沿用它。
- 驱动在关键节点已发布事件：领取并启动输入时 `RunAccepted`，Run 结算后 `RunFinished` 与 `QueueChanged`，用户停止时 `QueueChanged`。驱动自身在准备阶段就订阅这些事件作唤醒，收到后回到会话状态核对队首，事件滞后也按一次唤醒处理。
- 会话被标记为故障时只改状态，不发布任何事件。

## 三、命令与返回结果

### 3.1 提交入口

介入只表达“何时发”，与输入类型正交。`SubmitInputMode` 保持现有三个取值，不增加介入取值；提交请求增加独立的投递方式字段（普通排队／介入），缺省为普通排队。普通队列项“介入”是针对已有 InputId 的命令，保留该输入原有的类型与全部载荷。两个入口进入同一条介入流程。

快捷键和队列按钮的展示及触发由前端按[交互指导](界面交互设计指导.md#三提交与接续)决定。Runtime 根据投递方式或目标 InputId 处理介入，沿用现有输入、队列与 Goal 规则。

不新增介入任务 ID、轮询接口或撤回命令。提交新输入的介入请求必须携带输入幂等键。已有队列项沿用 InputId。

### 3.2 命令结果

命令在驱动对这条输入给出结论后返回。运行失败由现有 Run 状态和错误展示承载。

| 结果 | 条件 | 响应 |
| --- | --- | --- |
| 已交给 Run | 旧 Run 已可靠结算，用户消息已写入会话文件。新 Run 已启动，或驱动已按现有流程结算启动失败 | InputId、UserMessageSnapshot、RunSnapshot |
| 已入队、未执行 | 输入已在队首，但驱动未领取就停下（队列被用户暂停，或会话故障） | InputId 与未执行原因，无 Run |
| 未接纳 | 预检或接纳失败 | 错误，未取消任何 Run |

现有提交结果已有“只有 InputId、没有 Run”的形态，本次只补充可选的消息快照和未执行原因；普通排队的结果语义不变。新 Run 之后的模型／工具执行异步运行，不等待回复完成。

### 3.3 消息展示

请求进行时只显示提交状态。收到正式消息和 Run 时按 owner／generation／messageId 合并返回的正式消息，后续 SSE 与快照按同一身份去重。“已入队、未执行”时该输入就是普通队列项，由现有队列投影展示。不新增介入专属的中间状态。

## 四、请求内执行顺序

### 4.1 命令顺序

1. **查重与预检**：按输入幂等键查重，已存在则返回该输入的当前结果，不取消任何 Run。再校验会话状态、权限、正文、附件、引用、Skill／MCP 和模型；失败直接返回。
2. **接纳、优先并取消**：在同一次 Session mutation gate 内依次执行：普通接纳（排到队尾；队列项介入跳过这一步）→ 对该 InputId 执行现有“优先”→ 作废待回答问题（4.3）→ 停下当前执行：Goal 运行中则执行停止 Goal（第六节），否则对当时的活动 Run 请求底层取消。没有活动 Run 则只唤醒驱动。随后释放 gate。
3. **等待领取结果**：驱动结算旧 Run（含部分输出落盘），回到循环开头领取队首，沿现有流程写入用户消息并启动新 Run。命令按 4.5 等待该输入的结论，不读 SSE、不定时轮询。
4. **返回** 3.2 的对应结果。

快捷键介入等于“普通发送 + 队列项介入”：两个入口从“优先”起是同一段代码，接纳本身没有队首选项。接纳与“优先”是两次存储写入，若进程停在两者之间，结果只是一条队尾的普通排队消息，当前 Run 尚未被取消，无需补偿。

“优先”和取消请求在同一个 gate 内完成，旧 Run 结束时队首已经是介入消息，因此不存在被其他队列项抢占的空档，不需要额外的互斥。等待期间不持有 mutation gate，否则旧轮结算取不到 gate 会死锁。

第 2 步使用底层取消句柄，不调用公开的 `interrupt_run`：它会暂停队列，使驱动不领取介入消息。运行中 Goal 的 Run 不走底层取消，由停止 Goal 负责。

### 4.2 等待期间的停止

不做专门判断，完全是现有停止的效果：

- 用户停止会置 `queue_paused_by_user`，驱动结算旧 Run 后取不到可执行输入而退出，命令返回“已入队、未执行”。消息留在队首。
- 之后用户恢复队列则驱动照常领取；也可按队列原有方式移除。
- 命令返回“已启动”之后的停止，按原规则作用于新 Run，已写入的消息保留。

旧输出落盘失败时驱动把会话置为故障并退出，命令同样返回“已入队、未执行”，后续沿现有故障恢复流程。

### 4.3 待回答问题

- 接纳阶段跳过“存在待回答问题则拒绝新输入”的门禁，把仍处于待回答状态的问题标记为已取消并持久化，复用现有状态变更与存储写入，但不置队列暂停。
- Run 内的审批、工具内等待和 child 随第 2 步的取消协议清理，不批准未决工具、不伪造答案。
- 介入正文作为普通用户消息，不写入任何问题的答案。

### 4.4 连续介入与多端并发

同端提交期间禁用再次介入。多端的介入命令在一把进程内的 Session 级锁上串行，前一条返回后才处理下一条；这把锁只在介入命令之间使用，驱动不参与。它的作用是保持顺序：若不串行，后到的 B 会排到 A 前面，A 反而落在 RB 之后才执行。

- A 取消 R0 并启动 RA；B 取消 RA 并启动 RB。A、B 作为独立用户消息保留。RA 尚无输出时不生成空助手消息。
- A 的重试在第 1 步查重返回，不会打断 RB。
- A 因用户停止而留在队首后，B 的接纳会按普通新输入的规则清除暂停并排到队首：B 先执行，A 随后作为普通队列项执行。

不保存介入顺序字段，也不恢复后台介入任务。

### 4.5 领取结果的等待

复用驱动已发布的队列事件，写法与驱动准备阶段相同，不新增通知原语。

- **先订阅再动手**：命令在 4.1 第 2 步之前订阅事件，避免错过。
- **事件只作唤醒**：收到本会话的 `RunAccepted`、`RunStarted`、`RunFinished`、`QueueChanged` 或滞后信号时，读会话状态判断。用户消息已提交且 Run 已启动或已结算时，返回标准消息和 Run；没有活动 Run 且队列已暂停或会话故障，返回“已入队、未执行”，原因取自会话状态；否则继续等待。
- **补一处事件**：驱动的故障出口补发一次 `QueueChanged`，使旧 Run 结算失败或领取失败时命令能及时返回，界面的队列状态也随之刷新。其余故障位置不改。

结论以会话状态为准，漏一次事件不会判错。

## 五、取消与终止输出留存

### 5.1 立即取消与收尾

沿现有 cancellation 链路取消模型和工具，不等待 Step 正常完成。尚未授权的调用不再执行；保留已返回的工具结果，只为尚无结果的调用补 interrupted。工具交换闭合后才完成旧 Run 结算。取消清理迟迟不结束属于通用取消机制的问题，本 Feature 不增加超时分支。

### 5.2 终止输出留存

**M0 开发前的缺口**：`stream_turn` 只转发 Text／Reasoning delta；取消和失败两种执行结果都不携带当前未完成的消息，Runtime 结算时只写状态。客户端在权威快照没有活动 Run 后移除流式投影，已显示的内容随之消失。此前已完整提交的工具 Step 不在丢失范围内。

这是通用的终止处理，取消和失败共用一条路径：

1. Core 在观察事件可能被丢弃之前，按当前模型 Turn 的 messageId、partId 和顺序保留已接收的文本／reasoning；`TurnRestarted` 清理被替换的尝试。
2. `ExecutionOutcome::Cancelled` 与 `Failed` 都增加可选的部分消息，对应的终态事件同步；没有输出时为空，不生成空助手消息。内容来自 Core，不能从 Runtime／UI 的 delta 缓存反推。
3. 保留实际 reasoning、正文及消息身份。未完成的 ToolCall 参数和未验证的 Provider 状态不进入规范消息。取消使用 `FinishReason::Cancelled`，失败使用 `FinishReason::Failed`。两种值都表示只保存了部分输出，`TurnFinished` 仍只用于模型已完成的响应。
4. Runtime 结算只有一段逻辑：有部分消息就连同 Run／Step 来源一并追加，再写真实终态。沿现有 Session mutation gate 与 Store 结算，不新增部分输出的表、文件或第二份正文。与正常完成竞争、重复结算时不得为同一消息追加两份内容。
5. 工具执行期间终止沿原 exchange 收尾，不重复追加已落账的 Assistant Message，不留下没有结果配对的工具调用。
6. 进入下一次模型请求时，被终止的消息只投影已生成的正文，不回放半段 ToolCall／ProviderState，没有正文则不生成空 assistant 项；取消与失败使用同一条投影规则，Chat／Responses 编码与计量一致。
7. 客户端收到既有 `ConversationCommitted` 和 `RunFinished` 后刷新快照。终止 Step 的实时内容保留至可靠历史到达，交接时以已提交的同 Run、同 Step 消息及其片段身份为准。

Store 失败不发布可靠终态。提交前进程退出沿现有未完成 Run 恢复处理，不承诺逐 delta 写盘。`CompactionRequired`／`ContinuationRequired` 是执行交接而非终止，不在本项范围。普通停止、Goal 停止涉及的 Run 取消与介入打断共用这项能力，各入口的队列／Goal 控制语义保持独立。

实现时同步检查 Model／Core 终态的生产者与消费者、协议序列化和工具配对校验。

## 六、Goal

介入不新增 Goal 状态、领取规则或绑定方式，只在 4.1 第 2 步多一个分支：Goal 处于运行中时，用现有的停止 Goal 代替底层取消。

已核对的现状：

- 运行中的 Goal 下，驱动只领取 `goal_inputs` 队首且绑定当前 Goal 世代的输入，不取普通队列（`next_runnable_input`）。Goal 的续跑在同一个 Run 内进行，不是每轮一个新 Run。
- 绑定运行中 Goal 的 Run 以 Cancelled 结算时，Goal 状态不变（`prepare_goal_run_decision` 直接结算）。因此若只取消 Run 而不动 Goal，会留下“运行中但没有 Run、也没有可领取输入”的 Goal，介入消息永远不会被领取。公开 `cancel_run` 拒绝这类 Run 正是为此。
- `stop_goal_in_session` 在一次存储操作内把 Goal 置为 `Paused(UserStopped)`、世代加一、移除未领取的续跑输入，并取消绑定该 Goal 的活动 Run；它不置 `queue_paused_by_user`。
- 已暂停的 Goal（任何原因）在一条未绑定 Goal 的用户排队输入被领取时自动恢复：`prepare_claim_goal_resume` 把 Goal 恢复为运行中、世代与轮次加一，注入恢复上下文并把该输入绑定到 Goal。目标、累计用量与预算保留。

规则：

1. **运行中 Goal**：4.1 第 2 步在接纳、优先和作废问题之后，执行停止 Goal 的同一段状态变更（拆出不重复获取 gate 的内部函数供两处调用）。Goal 暂停后驱动回到普通队列规则，领取队首的介入消息并按现有逻辑恢复 Goal。不绕过 `cancel_run` 的拒绝，也不改 `next_runnable_input`。
2. **已暂停 Goal**：无分支，与普通发送相同，领取时恢复。
3. **等待期间停止**：Goal 已暂停，界面的停止走中断 Run，置队列暂停，结果同 4.2；Goal 保持 `Paused(UserStopped)`，恢复队列后消息被领取时再恢复。
4. **失败出口**：停止 Goal 的存储写入失败属于第 2 步失败。此时输入已接纳并位于队首，但没有取消任何 Run；命令返回“已入队、未执行”，Goal 仍在运行，消息按普通队列项等待。停止 Goal 成功之后的失败沿 7.2。

Goal 的用量结算、预算判断和完成信号不改。

## 七、存储、失败与兼容

### 7.1 保存位置

| 内容 | 沿用位置与机制 |
| --- | --- |
| 旧 Step reasoning／正文及终态 | 原会话文件；AssistantMessage、Run／Step 来源和 RunSettlement |
| 介入消息（领取前） | 原 inputs 队列，与普通排队输入相同 |
| 新用户消息与新 Run（领取后） | 原 claim／UserMessageCommit 路径；消息与幂等身份归会话文件 |
| 已有存储操作的中途状态 | 原 inputs／runs／body_appends 及其恢复机制 |

**不新增表或列，不新增迁移。** 介入消息在存储里没有任何标记，就是一条位于队首的普通输入。队首位置由现有“优先”写入持久顺序，跨重启保持；接纳的存储操作不改。

### 7.2 失败出口

| 发生位置 | 结果 |
| --- | --- |
| 预检或接纳失败 | 未接纳：不取消当前 Run，保留草稿 |
| 用户停止 | 已入队、未执行：消息留在队首，队列暂停 |
| 旧 Run 结算或输出落盘失败 | 已入队、未执行：会话故障，消息留在队列，沿原故障／恢复流程 |
| 领取或写入用户消息失败 | 沿驱动现有的失败处理。用户消息和失败 Run 已可靠结算时，回读标准结果 |

请求连接中断、回执丢失和 Host 重启与普通发送一致：用原幂等键核实该输入的当前结果；重启后尚未领取的消息仍在队列，按现有规则需用户恢复才继续。不新增介入专属的恢复分支。

### 7.3 格式与兼容

沿用历史格式 2，不重写历史、不修改 F02 已应用的迁移。

M0 在 Core 终态事件与 completion 增加可选的部分消息。应用协议复用既有会话快照、消息来源和终态事件。历史格式 2 的 AssistantMessage 增加 `failed` 结束原因，已存在的消息仍可直接读取。写入新原因后应使用包含 M0 的 Host 打开该会话。

介入阶段的应用协议涉及提交请求的投递方式字段、队列项介入命令、能力标记、提交结果的可选消息快照与未执行原因。Rust／TS、Host 路由与客户端需同步更新。

旧 Host 会忽略未知的投递方式字段并按普通排队处理，因此不能靠请求本身防止降级：Host 未声明介入能力时客户端不开放入口。

### 7.4 验证要点

- 介入没有独立的领取、写入或启动代码；普通发送的回归覆盖同一路径。
- 旧输出落盘前新消息不会被领取；落盘失败时命令不返回“已启动”。
- “优先”与取消请求之间没有可被其他队列项领取的空档；等待期间不持 mutation gate，无锁互等。
- 驱动故障时命令及时返回“已入队、未执行”，不等到请求超时；队首顺序重启后保持。
- 同键重试不重复接纳或打断；连续介入顺序、等待期间停止的结果符合 4.2、4.4。
- 取消与失败终止的部分输出跨刷新、重启保留，工具配对完整。

实现验证使用新建的 `.runtime-test/` 隔离 Runtime Home。

## 八、客户端接入

Ctrl／macOS Command + Enter 和队列项“介入”发出命令并 await 返回。期间显示“正在介入…”，保留草稿并禁用重复提交。

主按钮沿现有规则，不为介入增加特殊状态：输入框有内容时是发送（请求期间禁用），为空时才是停止。因此快捷键介入的等待期间主按钮不提供停止；队列项介入时输入框通常为空，停止按原规则可用。4.2 的“等待期间停止”描述的是 Host 收到停止时的结果（来自输入框为空时的主按钮或其他客户端），不要求界面在此期间额外提供入口。

按命令结果处理：

- **已交给 Run**：清理草稿，用响应中的真实用户消息和 Run 更新聊天列表，后续 SSE／快照按同一 messageId 合并。Run 的错误走现有展示。
- **已入队、未执行**：清理草稿，提示原因；消息由现有队列抽屉展示，不再保留一份草稿副本。
- **未接纳**：保留草稿并显示原因。

断线后用原幂等键核实，不换 key 重发。普通 Enter／发送按钮保持原队列行为。详见[交互指导](界面交互设计指导.md)。
