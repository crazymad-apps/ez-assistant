# v0.33.1 F04 技术方案：侧栏列表排序与分页

## 一、方案信息

- 日期：2026-11-16。状态：**已确认**。2026-11-16 用户回复“按建议确认”。
- 依据：[F04 功能设计](功能设计.md)（2026-11-16 已确认）、[总体设计 5.6](../../总体设计.md#56-侧栏列表排序拖拽与分页)。
- 范围：Host 存储的排序字段与查询、Runtime 移动与恢复默认命令、协议与应用快照、Desktop／Host Web 侧栏的数据接入。拖拽手势与视觉反馈归界面交互设计指导。
- 本方案只做设计，未改代码，未执行数据库操作。

## 二、源码核查与改动边界

| 位置 | 核查结论 | 本次改动 |
| --- | --- | --- |
| `workspaces` 表 | 有 `created_at_ms`、`lifecycle`，无排序字段；`load_workspaces` 按 `workspace_id` 排序全量返回 | 增加排序字段，查询改为按排序值取页 |
| `session_resources` 表 | 每个会话一行，含 `workspace_id`；已有索引 `(workspace_id, session_id)`。会话创建、分支、物化三条路径都经同一个 `insert_session_resources` 写入；存储恢复和加载会话时 `repair_session_resources` 会为缺行的旧会话补行 | 增加排序字段和分组索引；两处写入点统一赋值 |
| `sessions` 表 | 有 `is_pinned`、`lifecycle`、`role`、`created_at_ms`；`set_session_pinned` 只更新 `is_pinned` | 增加置顶顺序字段 |
| `query_session_summaries` | 全局查询，`ORDER BY is_pinned DESC, updated_at_ms DESC, session_id`，offset／limit 分页，支持标题筛选 | 全局排序改为创建时间；增加按分组查询 |
| 应用快照 | `get_application_snapshot` 带回全部项目、活动与归档各一段全局前缀，再在 Runtime 内过滤已移除项目的会话并补入主控会话；请求可传入已加载数量 | 快照改为按分组返回 |
| 前端刷新 | 收到 `session_created`／`session_changed`／`workspace_changed`／`run_finished` 等事件即整份重取应用快照，并按已加载数量取前缀；`appendSessionPage` 按 ID 合并“加载更多”的结果 | 沿用整份重取，请求改为携带各分组的已加载数量 |
| 迁移 | 同一版本可以有多个按 key 排序的迁移项（如 0.33.0 的三项）；0.33.1 现有 `release` 一项，最低 Host 已是 0.33.1 | 在 0.33.1 下追加一项 |
| Desktop 置顶 | `DesktopPinsStore` 把置顶列表整份写入本机偏好，新置顶追加在末尾，上限 2048 | 增加调整先后的方法 |
| 拖拽 | 侧栏没有拖拽实现，项目中没有拖拽依赖 | 实现方式在交互指导确定后于开发计划中决定 |

**不改动**：会话与项目的创建时间、`updated_at_ms` 的推进规则、置顶数据的归属、会话的项目归属、Run 与队列。

## 三、存储

### 3.1 字段与索引

| 表 | 新增字段 | 含义 |
| --- | --- | --- |
| `workspaces` | `sort_order INTEGER NOT NULL DEFAULT 0` | 项目在项目列表中的顺序 |
| `session_resources` | `sort_order INTEGER NOT NULL DEFAULT 0` | 会话在其项目内（或独立会话内）的顺序 |
| `sessions` | `pin_order INTEGER NOT NULL DEFAULT 0` | 会话在 Host Web 置顶区的顺序，仅在 `is_pinned = 1` 时有意义 |

- 三个字段规则相同：**数值大的排在前面**，相邻值间隔 1024，同值时按 ID 升序。
- `pin_order` 不替代 `is_pinned`：是否置顶仍只看 `is_pinned`，取消置顶时不清理 `pin_order`，避免两个字段表达同一事实。
- 会话排序值放在 `session_resources` 而不是 `sessions`，是为了和 `workspace_id` 建在同一个索引里。

| 索引 | 用途 |
| --- | --- |
| `workspaces(sort_order DESC, workspace_id)` | 项目列表取页 |
| `session_resources(workspace_id, sort_order DESC, session_id)` | 分组内取页；替换现有 `(workspace_id, session_id)` 索引前先确认无其他查询依赖 |
| `sessions(pin_order DESC, session_id) WHERE is_pinned = 1` | 置顶区读取 |
| `sessions(created_at_ms DESC, session_id)` | 全局列表（搜索对话框）按创建时间取页 |

各索引是否被实际使用以 `EXPLAIN QUERY PLAN` 为准，未被使用的不保留。

### 3.2 排序范围

| 范围 | 同范围的判定 | 展示时的过滤 |
| --- | --- | --- |
| 项目列表 | 全部 `workspaces` 行 | `lifecycle = 'active'` |
| 项目内会话 | `session_resources.workspace_id` 相同 | 会话生命周期、`role = 'standard'` |
| 独立会话 | `workspace_id IS NULL` | 同上 |
| Host Web 置顶区 | `is_pinned = 1` | `lifecycle = 'active'`、`role = 'standard'`、所属项目为活动或无项目 |

同一范围内的活动与归档会话、活动与已移除项目共用一套排序值，所以归档、恢复、移除、恢复项目都不需要写排序值，条目自然回到原位置。

### 3.3 赋值

| 时机 | 取值 |
| --- | --- |
| 新建项目 | 范围内最大值 + 1024，排在最前 |
| 新建会话、分支、物化、启动时补行 | 同上，在 `insert_session_resources` 和 `repair_session_resources` 的插入语句内直接计算 |
| 置顶 | 置顶范围内最小值 − 1024，排在最后；写入与 `is_pinned` 在同一条更新中完成 |

范围为空时取 1024。加减后超出 64 位整数范围时，先重排该范围再赋值（见 3.5）。

### 3.4 移动

移动以“把 A 放到 B 的前面或后面”表达，B 是用户松手位置的相邻条目。

```text
在一个立即事务内：
1. 读取 A 与 B，校验二者存在、属于同一范围、A ≠ B，且都处于可展示状态
2. 找到 B 在目标一侧的下一个条目 C（范围内除 A 以外、排序值紧邻 B 的那一项，不论其是否被过滤）
3. B 与 C 之间有空隙：A 取两者的中间整数
   没有 C：A 取 B ± 1024
   空隙不足或越界：重排该范围（3.5），重排时把 A 放到目标位置
4. 提交
```

- 第 2 步不过滤已归档、已置顶或已移除的条目。A 一定紧贴 B，与被隐藏条目的相对先后不保证，也不影响可见结果。
- 校验失败返回冲突错误，不做部分写入。
- 三个范围共用同一段实现，只是表、范围条件和字段不同。

### 3.5 重排与恢复默认

- **重排**：在同一事务内按当前顺序读出该范围的全部 ID，自后向前重新赋值为 1024、2048……，只改排序字段。
- **恢复默认**：按创建时间升序、ID 降序对该范围编号后乘以 1024，使新建的排在前、同一时间 ID 小的在前。用一条分组编号的更新完成，不逐行查询。
- 两者都是随范围大小增长的批量写入，不涉及消息正文和文件。

## 四、查询与分页

### 4.1 Host 查询

| 查询 | 条件与顺序 | 分页 |
| --- | --- | --- |
| 项目列表 | 指定生命周期，`sort_order DESC, workspace_id` | offset／limit，缺省不限数量 |
| 分组会话 | 指定分组与生命周期，`role = 'standard'`，`sort_order DESC, session_id` | offset／limit |
| 全局会话 | 沿现有筛选（生命周期、标题关键词），`created_at_ms DESC, session_id` | offset／limit |
| Host Web 置顶 | 见 3.2，`pin_order DESC, session_id` | 一次返回，上限 2048，与 Desktop 置顶上限一致 |

- 分组查询从 `session_resources` 的分组索引出发，联接 `sessions` 过滤生命周期和角色，读够一页即停。
- 项目列表缺省不限数量，是为了让“已移除项目”对话框等现有调用保持原行为；侧栏通过快照传入页大小。

### 4.2 继续使用 offset

评估过稳定游标，结论是保留 offset：

- 现有刷新机制是“按已加载数量从头重取”，本身就是 offset 语义，游标无法表达。
- 任何移动、创建、归档都会发布事件并触发整份重取，偏移漂移会在下一次刷新时纠正。
- 游标需要把排序值带出存储层，与“排序值不出现在协议中”冲突。

“加载更多”与重排并发时的保护放在客户端，见 7.2。

### 4.3 应用快照

快照仍是侧栏数据的唯一来源，一次调用返回事件水位一致的全部分组。

请求：

| 字段 | 含义 |
| --- | --- |
| `workspaces_limit` | 从头读取的项目数量；缺省为一页 |
| `session_groups` | 要读取的分组列表，每项含分组（某个项目或独立会话）、生命周期（活动或归档）和从头读取的数量。缺省表示“返回的每个项目和独立会话各读一页活动会话” |

返回（替换现有的 `active_sessions`、`archived_sessions` 及其 next_offset）：

| 字段 | 含义 |
| --- | --- |
| `workspaces`、`workspaces_next_offset` | 项目页及是否还有更多 |
| `session_groups` | 与请求对应的分组结果，每项含分组、生命周期、会话列表和 next_offset |
| `pinned_sessions` | Host Web 置顶区的会话，已按置顶顺序排好 |

- 首次连接时客户端不知道项目 ID，不传 `session_groups`；之后只传已展开或已加载的分组，折叠的项目不读取。
- Runtime 内“过滤已移除项目的会话”和“把主控会话补入活动列表”两段逻辑删除：前者由分组查询天然保证，后者不再需要（见 7.4）。
- 每个分组一次带索引的小查询，都在同一次存储调用内完成。事件触发的重取频率较高，分组数量多时的耗时列入验证。

项目列表、项目内会话和独立会话默认每页 10 条，首屏与加载更多使用相同页大小。

## 五、协议

| 改动 | 说明 |
| --- | --- |
| `ListWorkspacesRequest`／`Result` | 增加 `offset`、`limit` 和 `has_more` |
| `ListSessionsRequest` | 增加可选的分组条件（某个项目或独立会话）。带分组时按手动顺序，不带时为全局创建时间顺序 |
| `GetApplicationSnapshotRequest`、`ApplicationSnapshot` | 见 4.3 |
| 新命令：移动 | 目标是项目、分组内会话或置顶会话三者之一，带被移动条目 ID、相邻条目 ID 和前后位置。成功只返回确认，顺序由随后的快照带回 |
| 新命令：恢复默认 | 范围是项目列表、某个项目的会话或独立会话 |
| 新事件：侧栏顺序已变化 | 无载荷。移动和恢复默认成功后发布，客户端收到后重取应用快照 |

- 新增一个事件而不复用 `WorkspaceChanged`／`SessionChanged`，是因为这两个事件都绑定单个实体 ID，而恢复默认没有对应的单个实体。
- 排序值、间隔不出现在任何 DTO 中。
- 同步 TS 导出、HTTP 命令分发与企业代理准入；两个新命令是写命令，不进入只读自动重试。
- 移动与恢复默认失败时沿现有冲突错误码返回，是否需要区分“相邻条目失效”在实现时核对现有错误码后决定，不预设新增。

## 六、Runtime 执行与并发

- 两个新命令沿现有写命令的入口：身份准入 → operation gate → 存储调用 → 发布事件。不加载会话，不持有会话的 mutation 锁，因为不改会话状态。
- 存储层的写入本就串行，每次移动是一个立即事务。多端并发移动按到达先后依次执行，后一个基于前一个提交后的实际顺序。
- 移动、恢复默认与归档、删除、移除项目并发时，以事务内读到的状态为准：条目已不满足校验则返回冲突。
- 置顶写入沿现有 `set_session_pinned`，在同一条更新里一并写 `pin_order`；内存中的会话状态不需要保存 `pin_order`。
- 排序变更不更新 `updated_at_ms`，不发布 `SessionChanged`。
- 请求结果未知时客户端只重取快照，不重发命令，因此不需要幂等键。

## 七、客户端接入

### 7.1 数据结构

- `RuntimeProjectionStore` 中的应用快照按 4.3 的新结构保存。现有“加载更多”合并方法改为按分组合并。
- 新增加载更多项目、加载更多某分组会话两个入口，分别调用 `ListWorkspaces` 和带分组的 `ListSessions`。
- 重取快照时，请求中的项目数量和各分组数量取当前已加载数量，折叠的项目不放入请求。
- 展开一个尚未加载的项目时读取其第一页；切换到归档视图时读取当前展开分组的归档第一页。

### 7.2 迟到响应

- 客户端为每个连接目标维护一个本地递增的列表修订号，每应用一次应用快照加一。
- “加载更多”的响应返回时，如果修订号已变化，说明期间列表被整份刷新过，丢弃该响应，由用户再次触发。
- 应用快照之间沿现有的事件水位比较，旧快照不覆盖新快照。

### 7.3 移动与恢复默认

- 提交移动后等待命令结果，再由事件触发的快照重取得到最终顺序。是否在等待期间先行显示新位置由交互指导决定；先行显示时，命令失败须恢复为最近一次快照的顺序。
- 命令返回冲突时提示列表已变化，并立即重取快照。
- Desktop 置顶区的移动只调用 `DesktopPinsStore` 的新方法，按新先后整份写入本机偏好，不调用 Host。Host Web 置顶区调用 Host 的移动命令。

### 7.4 依赖全局列表的现有调用

| 调用方 | 处理 |
| --- | --- |
| 待办通知同步 | 遍历全部会话，不依赖顺序，保持不变 |
| 智能终端取主控会话 | 现在从全局第一页里找主控会话；全局改为创建时间排序后主控会话会落到靠后的页。改为按角色直接查询，复用 Runtime 内已有的主控查询 |
| 启动时的默认选中 | 改为取侧栏顺序下第一个已加载的会话：第一个有会话的项目的首条，其次独立会话首条；都没有则不选中 |
| Desktop 旧置顶导入 | 现在靠“置顶在前”翻页并提前停止；改为直接读取快照中的 `pinned_sessions` |
| 选中会话的补入 | 删除。选中的会话不在已加载页时侧栏不显示选中态 |
| 按 ID 查找会话摘要的界面（对话区、输入区、上下文面板等） | 统一为一个查找入口：先查会话视图，再查已加载分组和置顶。不再假定选中的会话一定在侧栏列表里 |
| 移除项目确认框的会话数量 | 现在按已加载列表统计，分页后不准确；改为不显示数量，只提示“该项目的会话会一并隐藏” |

主控会话不再补入列表。实现时核对是否有界面在打开主控会话之前就需要它的摘要，如有则由快照单独带回。

## 八、迁移与兼容

- 在 0.33.1 下追加一个迁移项，最低兼容 Host 保持 0.33.1，不重建表。
- 迁移内容：增加三个字段；按 3.5 的默认规则为每个范围初始化 `sort_order`；为已置顶会话按现有展示顺序（最近活动时间降序）初始化 `pin_order`，使升级前后 Host Web 置顶区的顺序不变；创建索引。
- 校验：三个字段可读；每个会话都有 `session_resources` 行；同一范围内排序值不重复。
- 备份沿迁移执行器现有流程。升级后不能只回退数据库给旧 Host 使用。
- 已安装过 0.33.1 早期测试包的数据库，存储目标同为 0.33.1 但缺少本迁移项：新包启动时补做本项；早期包遇到含本项的数据库必须拒绝启动。后者依赖按 key 的账本检查，需要在首个里程碑中实测。
- 协议：本版客户端与 Host 的最低配套已是 0.33.1，快照结构直接改为最终形态，不保留旧字段、别名或能力开关。0.33.1 的早期测试包与新包混用不在支持范围内。
- 分组编号的批量更新写法依赖所带 SQLite 版本，首个里程碑核对后确定具体语句。

## 九、验证要点与待确认

验证要点：

- 迁移：含大量会话、多个项目、已置顶和已归档数据的旧库升级后，各范围默认顺序正确，置顶区顺序不变；失败回滚后原库可用。
- 查询计划：项目列表、分组会话、全局会话、置顶四类查询均使用预期索引。
- 移动：前后放置、范围首尾、空隙耗尽触发重排、数值越界、相邻条目被归档或删除、跨范围请求被拒绝。
- 分页：把后页条目移到前部后重取第一页可见；并发移动下“加载更多”的迟到响应被丢弃。
- 成本：万级会话的单个分组执行重排与恢复默认的耗时；几十个展开分组时快照重取的耗时。
- 入列与不变：新建、分支、物化的会话排在最前；发送消息、改名、F02 编辑、F03 介入、归档与恢复后排序值不变。
- 调用方回归：7.4 所列各项。
- 隔离：不同用户的数据域互不影响；浏览远端设备时写入的是该设备的 Host。

已确认的取舍（2026-11-16）：

1. 按用户反馈，侧栏项目列表和各会话分组统一每页 10 条（见 4.3）。
2. 移除项目确认框不再显示会话数量（7.4）。
3. 启动默认选中取侧栏顺序下第一个已加载的会话，都没有则不选中（7.4）。
4. 新增“侧栏顺序已变化”事件，不复用现有两个事件（第五节）。
