## 一、计划信息

- 版本：`v0.3.0`
- 状态：✅ 已确认（2026-07-29；用户明确开始开发）
- 关联文档：
  - [`功能设计`](功能设计.md)（✅ 已确认 2026-07-29）
  - [`技术方案`](技术方案.md)（✅ 已确认 2026-07-29）
- 界面交互设计指导：本版本不修改桌面 UI；`runtime-harness` 只增加开发者命令和
  状态输出，按流程跳过独立界面交互设计指导。
- 前置条件：v0.2.1 已归档；v0.3.0 功能设计和技术方案已确认。

本计划只规定实施顺序、里程碑边界和验证门槛。公共类型、接口签名、状态机、布局算法、
Provider 编码和 Harness 验证语义以技术方案为唯一来源，不在本文件重复维护。

## 二、实施原则

1. M0 → M7 严格顺序实施；每个里程碑完成实现和验证后标记为 `🟨 待确认`并停止，
   获得用户明确确认后才进入下一里程碑。
2. 先建立依赖和公共契约，再实现共享 Context 能力；Core、Provider 和 Harness
   不各自维护窗口计算、历史切分或 replacement 校验。
3. `ContextWindowEvaluator` 是唯一窗口判断入口；Core/Harness 不直接计算
   `total_tokens / context_window_tokens`。
4. Harness 私有 `compact_context` 是本版本唯一压缩编排入口；它只组合
   `agent-context` 公共能力，四种触发原因通过轻量封装区分调度结果。
5. Core 只结束单次 AgentExecution 并交接；Provider 只报告错误；压缩、Checkpoint
   和 continuation 由临时 Harness 验证，正式 Runtime 接口留待总体设计。
6. 公共契约变更所在里程碑必须同步迁移全部 workspace 生产者和消费者，不能留下临时
   通配分支、重复 UserMessage 或隐式兼容路径。
7. `verify v0.3` 必须完全离线；真实 Provider smoke 需要再次取得用户确认，且不作为
   自动验收的前置条件。
8. 本版本不实现数据库、桌面 UI、TokenEstimator、Passthrough Strategy 或 Tool
   Result 裁剪；不新增第三方 crate。

## 三、目标依赖结构

```text
agent-types ◄──── agent-model
     ▲                  ▲
     └──── agent-context┘
              ▲
              ├──── agent-core
              └─ runtime-harness
```

- `agent-context` 不依赖 Core、Runtime、Provider Adapter、数据库或 Tauri。
- `agent-core` 与 `runtime-harness` 复用同一 Evaluator、Layout、Validator 和
  Strategy 契约；Harness 是临时验证调用方。
- Provider Adapter 继续只依赖 `agent-model` 与 `agent-types`。
- `assistant-runtime` 不在本版本新增依赖或公共契约。
- `runtime-harness` 只私有编排共享能力，不复制 Context 算法。
- `debug-viewer` 只消费事件和报告，不持有 Context 业务状态。

## 七、M2：共享窗口判断、布局与策略边界

### 目标

完成 `agent-context` 的确定性基础能力，让 Core 与 Harness 后续只负责调用和编排。

### 前置依赖

M1 已确认。

### 实施内容

- 实现 `ContextWindowEvaluator`、evaluation/decision/error 类型和构造期比例校验。
- Evaluator 只读取最新完整 Assistant Result 的 `usage.total_tokens`，并通过
  ModelService 获取上下文窗口；usage 缺失返回 `UsageUnavailable`。
- Core 继续直接构造既有 `ModelRequest`；不增加与其字段一一映射的 Compiler/Input。
- 实现 `ContextLayout` 的 protected System prefix、Context Summary、User Turn、
  Tool Exchange、可压缩 head 和 protected recent tail 划分。
- 实现公共 replacement validator，并复用 M1 的 ConversationSnapshot 结构校验。
- 建立 `CompressionStrategy`、输入、候选、NoOp、报告和错误契约。
- 建立 `RollingSummaryPolicy` 配置校验；本里程碑不发起模型压缩请求。
- 为未来 Tool Result 裁剪保留 Strategy 扩展边界，不增加裁剪类型或算法。

### 自动测试

- threshold ratio 非有限值、零值、负值、上界和边界相等行为。
- 最新 Assistant usage 定位、其后 ToolMessage、usage 缺失不向前回退、窗口为零。
- Core 的 v0.2 请求在 instructions、conversation、tools、generation 和 provider
  options 上保持不变。
- System prefix、滚动 Summary、多个 User Turn、完整多工具 exchange 和 ProviderState
  的布局稳定性。
- head/tail 只能在完整 User Turn 边界切分；无可压缩 head 返回可识别 NoOp 条件。
- 非法历史和非法 replacement 由共享校验入口拒绝。

### 验证

```bash

cargo fmt --all --check
```

### 完成判定

- Evaluator、Layout、Validator 和 Strategy 契约均有确定性测试；
- 仓库不存在第二处窗口比例或 Tool 配对算法；
- 尚未改变 Core 生命周期，也未提交 Checkpoint。

## 八、M3：Agent Core Preflight 与第四终态

### 目标

让单次 AgentExecution 在每个 Model Step 前使用共享 Preflight，并把阈值与 Provider
Overflow 可靠交接给上层编排。

### 前置依赖

M2 已确认。

### 实施内容

- `ExecutionSpec` 注入共享 `ContextWindowEvaluator`。
- `ExecutionInput` 改为只接收完整 `ConversationSnapshot`；Core 不再追加 UserMessage。
- 调整 Engine 顺序：max steps → Context Evaluator → ModelRequest 构造 →
  StepStarted → ModelService。
- 将 Provider 流内最新 usage 聚合为每个成功完整 Step 最多一次的
  `AgentEvent::UsageUpdated`；增加 CompactionRequired 的 reason、可靠终态和
  `ExecutionOutcome`。
- 阈值命中时在 StepStarted 前结束；建立前或流内 ContextOverflow 收敛为同一第四
  终态，普通错误继续 Failed。
- 保证 overflow Step 的临时增量不进入 Conversation History，也不触发 Tool 执行；
  已完成 Tool Exchange 不重放。
- 同步 Execution Recorder、示例、测试、Harness 和 debug-viewer 等所有公共契约
  消费方；Harness 此时只做兼容迁移，不实现自动压缩。
- debug-viewer 对新增事件提供基础可读展示，不加入 usage 聚合或 Context 判断逻辑。

### 自动测试

- 成功完整 Step 的多个 Provider usage 更新只投影一次最终 `UsageUpdated`；失败、取消
  和 Overflow Step 不投影 usage。
- Ready/UsageUnavailable 继续建立模型请求；threshold 不建立模型流、不发布
  StepStarted。
- 建立前与流内 ContextOverflow 都只产生一个可靠 CompactionRequired 终态。
- Completed、Failed、Cancelled、CompactionRequired 严格四选一；观察者断开不影响
  outcome。
- 流内 overflow 丢弃 reasoning/text/tool-call 增量且不执行工具。
- 上一完整 Tool Exchange 后的下一 Step 可交接，既有工具副作用不重放。
- ExecutionInput 迁移后新用户路径没有重复 UserMessage。

### 验证

```bash
cargo test -p agent-core -p agent-testkit
cargo test -p runtime-harness -p debug-viewer
cargo clippy -p agent-core -p agent-testkit -p runtime-harness \
  -p debug-viewer --all-targets --all-features -- -D warnings
cargo fmt --all --check
```

### 完成判定

- Core 可可靠表达压缩交接，但不调用 CompressionStrategy、不提交 Checkpoint、
  不创建 continuation；
- 旧三种终态和 v0.2 工具循环回归通过；
- 全部公共 API 消费方已迁移，没有临时双输入路径。

## 九、M4：同模型滚动摘要与 Provider Overflow

### 目标

实现 v0.3.0 唯一压缩策略，并完成真实 OpenAI-compatible 模型边界。

### 前置依赖

M3 已确认。

### 实施内容

- 在 `agent-context` 实现 `RollingSummarySameModel`。
- compression request 使用当前 ModelService 和正常请求的原始 instructions；Strategy
  内部在 `protected prefix + head` 后追加固定压缩指令，调用方不组织临时
  conversation。请求使用空 tools、`ToolChoice::None` 和显式
  `summary_output_tokens`，不进入 Agent Loop。
- 只接受 Stop、无 ToolCall、非空 Text 的完整结果；Reasoning 不进入摘要正文。
- 构造 `protected prefix + ContextSummary + recent tail` 候选，并只清除派生
  replacement 内旧 Assistant usage。
- 覆盖 NoOp、取消、空摘要、截断、ToolCall、普通模型错误和 compression request
  ContextOverflow。
- OpenAI-compatible Adapter 根据脱敏 fixture 的结构化 code/type 精确映射
  ContextOverflow，覆盖建立前和流内传播；不使用错误文本模糊匹配。
- 验证 Provider Profile 的 max output token 能力和显式 context window 装配。
- 回归 DeepSeek reasoning、tool-call、ProviderState 和普通错误分类。

### 自动测试

- 首次摘要、再次滚动摘要、最小近期轮次保护和多 Tool Exchange 尾部保真。
- 原始 snapshot usage 不变，候选 replacement 的旧 usage 清除。
- 摘要消息 ID、模型 identity、usage 和块数量报告准确。
- 无 head 返回 NoOp；任何非法响应不形成 Candidate。
- fixture allowlist 命中 ContextOverflow，未确认 code/type 仍为普通 Provider 错误。
- compression request 不携带工具，且 max output tokens 被正确编码。
- compression request 的 system instructions 与正常请求一致，临时压缩指令只在
  head 末尾追加，recent tail 不进入压缩请求。

### 验证

```bash
cargo test -p agent-context -p agent-testkit
cargo test -p agent-provider-openai-compatible
cargo clippy -p agent-context -p agent-testkit \
  -p agent-provider-openai-compatible --all-targets --all-features -- -D warnings
cargo fmt --all --check
```

### 完成判定

- Rolling Summary 能稳定生成合法候选或受控 NoOp/Err；
- Provider 只报告规范错误，不压缩、不重试；
- 仓库中没有 Passthrough、TokenEstimator 或 Tool Result 裁剪实现。

## 十、M5：Harness Checkpoint 与私有压缩编排验证

### 目标

在临时 `runtime-harness` 中验证 Checkpoint 数据形状、有效快照投影、四种触发来源和
三类调用封装，不为尚未总体设计的 `assistant-runtime` 建立产品契约。

### 前置依赖

M4 已确认。

### 实施内容

- 在 Harness Journal 中定义私有 `HarnessContextCheckpoint` 与有序
  `ConversationRecord`，不新增正式 Store SPI。
- 实现从最新 Checkpoint replacement 加后续 Message 构造 effective snapshot；
  原始 Message 查询不被 Checkpoint 替代。
- 实现 Harness 私有 `HarnessContextCoordinator::compact_context`：读取、布局、
  Strategy、通用校验、内存原子提交和结构化结果/报告。
- 实现私有 `BeforeRunThreshold`、`InRunThreshold`、`ProviderOverflow`、
  `UserRequested` 四种 cause；cause 不切换算法。
- 实现 `prepare_user_context`、`handle_compaction_required`、
  `handle_user_compaction` 三个私有轻量封装。
- 用户输入先落账再执行 Run 前 Evaluator；需要压缩时先提交 Checkpoint，再创建本轮
  Initial context；M5 只验证上下文规划，不接入实际 Run 创建。
- Run 内第四终态的 reason/step 保留在 Harness 私有记录；成功后返回关联现有
  `HarnessRunId` 的 continuation context，且不重复 UserMessage。
- 私有任务链维护 `max_automatic_compactions`；用户主动压缩不计数且接口不接收 Run
  分配状态。
- Journal commit、取消、NoOp、策略失败和次数耗尽均收敛为确定结果，不隐藏重试。
- 撤回 M0/M5 对 `assistant-runtime` 增加的 `agent-context` 等依赖、代码和文档承诺，
  恢复其原有空骨架。

### 自动测试

- 最新 Checkpoint 投影、后续消息追加、多次 Checkpoint 和原始历史不变。
- 四种私有 cause 均经过同一 Harness 编排核心，且只在 Candidate 校验通过后提交。
- Run 前压缩成功才返回 Initial context；NoOp/Err 时不返回执行输入。
- Run 内 threshold/overflow 压缩后返回 continuation context，reason/step 留在原
  Harness 记录，cause 不保存 step。
- 用户主动压缩的 Compacted/NoOp/Err/Cancelled 接口均没有 Run/任务链输入。
- 自动次数只在自动 Compacted 后增加；耗尽后不再调用策略。
- Journal 读取/提交失败不产生部分 Checkpoint；取消后不返回 continuation context。

### 验证

```bash
cargo test -p runtime-harness -p agent-context -p agent-core -p agent-testkit
cargo clippy -p runtime-harness -p agent-context -p agent-core \
  -p agent-testkit --all-targets --all-features -- -D warnings
cargo fmt --all --check
```

### 完成判定

- 四条触发路径共享一个 Harness 私有压缩编排核心；
- Checkpoint payload 只有完整 replacement，未引入数据库或多余位置字段；
- `assistant-runtime` 没有新增依赖、实现或公共类型；
- Core/Provider/Strategy 均未反向持有调度，Harness 类型明确保持临时私有。

## 十一、M6：Runtime Harness 累计场景与调试展示

### 目标

用完全离线的 Runtime Harness 验证 v0.3.0 全链路，并保留 v0.1–v0.2 累计回归。

### 前置依赖

M5 已确认。

### 实施内容

- 将 M5 已测试的有序 Message/Checkpoint Journal 投影接入 Chat 与场景，继续保持
  独立 pending Tool Exchange。
- 新用户路径改为先追加 UserMessage、执行 Harness Preflight，再决定是否创建 Run。
- 接入 CompactionRequired Run 结算、自动 continuation 和任务链压缩次数。
- 接入 M5 私有 `HarnessContextCoordinator`；共享窗口、布局、校验和 Rolling Summary
  继续只调用 `agent-context`。
- 增加 `/compact`；活动任务链期间按 Session 串行排队，完成后只执行压缩、不续跑。
- `/state` 增加 Checkpoint 数、effective replacement 角色、自动压缩次数和最近报告，
  不默认展示摘要正文。
- `verify v0.3` 累计执行 v0.1–v0.3 场景。
- debug-viewer 在右侧 Agent/Runtime 通道展示窗口判断、CompactionRequired、压缩报告
  和 continuation 关联；不新增业务判断。
- 补充离线验证命令、真实 chat 的显式窗口/阈值配置和人工操作说明。

### 离线场景

- 短上下文直通，无额外模型调用。
- UserMessage 落账后的 Run 前阈值压缩。
- 工具循环中下一 Step 前阈值压缩。
- Provider 建立前与流内 ContextOverflow 恢复。
- 用户 `/compact` 只压缩、不续跑。
- 多次 Rolling Summary 和最新 Checkpoint 恢复。
- 同 Session 用户任务与主动压缩串行。
- 无可压缩 head、非法摘要、次数耗尽、取消和 Store 失败。
- v0.2 全部既有场景回归。

### 验证

```bash
cargo test -p runtime-harness -p debug-viewer
cargo run -p runtime-harness -- list
cargo run -p runtime-harness -- verify v0.2
cargo run -p runtime-harness -- verify v0.3
cargo clippy -p runtime-harness -p debug-viewer \
  --all-targets --all-features -- -D warnings
cargo fmt --all --check
```

另启动 debug-viewer，离线注入或运行 v0.3 Harness，人工核对同一 Session 下首个 Run、
CompactionRequired Run、Checkpoint 和 continuation 的关联及通道展示。

### 完成判定

- `verify v0.3` 完全离线通过且包含 v0.1–v0.3 累计能力；
- `/compact` 和自动压缩行为可从 `/state`、Run 记录及 viewer 相互核对；
- Harness 私有编排没有复制 `agent-context` 的 Context 算法，也没有进入产品 crate。

## 十五、实施顺序结论

本版本不能先在上层直接拼出压缩闭环。正确顺序是先稳定公共消息和模型契约，再完成
共享窗口/布局规则，随后让 Core 具备可靠交接能力，最后实现策略与 Harness 私有
编排。这样每个后续里程碑都只装配已经确认的下层能力，也能在每个停点独立判断是否
存在跨层重复或职责倒置；正式 Runtime 接口在其总体设计阶段另行确定。
