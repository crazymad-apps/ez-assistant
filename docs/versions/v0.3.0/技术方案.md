## 二、现状核查

基于 2026-07-29 当前仓库实际代码、`cargo metadata --no-deps` 和
`cargo tree`：

- `agent-core::ExecutionSpec` 只有 `instructions`、`model`、`tools`、`budget`
  四个字段；`Engine::build_request` 使用完整 projection、默认
  `GenerationConfig` 和空 `ProviderOptions` 机械构造请求。
- `Engine` 在构造请求前已经发送 `StepStarted`；模型建立前/流内错误除 Cancelled
  外全部收敛为 `ExecutionFailed`。
- `ExecutionInput` 当前是 `{ conversation, user_input }`，Engine 再把
  `user_input` 追加到 projection。Harness 虽先把 UserMessage 写入内存 Journal，
  仍向 Core 同时传递独立 `user_input`。
- Core 目前只有 Completed、Failed、Cancelled 三种可靠终态；普通事件使用
  bounded mpsc，终态使用独立 oneshot。
- `agent-model` 已区分 `ModelService::stream -> Err`（流建立前失败）和
  `ModelEvent::TurnFailed`（流建立后失败），但 `ModelError` 尚无
  Context Overflow 分类。
- `ConversationMessage` 只有 System、User、Assistant、Tool；尚无可识别的
  Context Summary 类型。
- OpenAI-compatible Adapter 在请求编码前校验 ToolResult 引用的 ToolCall，
  但尚不校验每个 ToolCall 都有完整结果；ConversationMessage match 也尚未处理
  Context Summary。
- Adapter 的结构化错误解码只识别认证和限流 code/type；其他错误落到
  `ModelError::Provider`。HTTP 非 2xx 在流建立前分类。
- `GenerationConfig.max_output_tokens` 表示本次请求是否设置输出上限；
  OpenAI-compatible Profile 的 `max_output_tokens_field` 已表示对应方言能否编码该参数。
- `ModelService` 尚未暴露当前模型实际可用的上下文窗口；但
  `AssistantMessage.usage` 已保存 Provider 返回的 `TokenUsage.total_tokens`，可以
  作为统一窗口判断的真实计数来源。
- `assistant-runtime` 当前只有 Session/Run/Scheduler/Config 空模块和
  `agent-core`/`assistant-protocol` 依赖，没有正式存储或压缩实现。
- `runtime-harness` 已有单 Session、单活动 Run、内存 Journal、两阶段 Recorder、
  UserMessage 先落账、Run 终态落最终 Assistant 的参考语义；它尚无 Checkpoint、
  continuation 输入和 `/compact`。
- Workspace 使用 edition 2024、resolver 3、`unsafe_code = "forbid"`；已有
  serde、thiserror、futures、Tokio，不需要新增第三方依赖。

结论：

1. Context Preflight 是 Core 的正式调用点；Run 前判断和压缩编排由 Harness 临时验证。
   两者仍需要共享窗口判断、原子块划分和 replacement 校验，因此新增
   `agent-context`，避免把共享算法塞入 Core 或复制到 Harness。
2. Harness 直接使用 `ModelService` 和 `agent-context` Strategy 执行 compression
   request；Provider 和 Core 均不代为压缩。
3. `assistant-runtime` 尚未完成总体设计，v0.3.0 不为其新增依赖、Store SPI、Run
   类型或压缩公共入口；Checkpoint 和 continuation 只作为 Harness 私有行为验证。

## 四、共享上下文类型与 Preflight

### 4.1 Context Summary

`agent-types` 新增：

```rust
pub struct ContextSummaryMessage {
    pub id: MessageId,
    pub text: String,
}

pub enum ConversationMessage {
    System(SystemMessage),
    ContextSummary(ContextSummaryMessage),
    User(UserMessage),
    Assistant(AssistantMessage),
    Tool(ToolMessage),
}
```

- Summary 是派生上下文，不伪装成 User/Assistant，也不保存模型、usage 或策略字段。
- Rolling Summary 使用 compression response 的 AssistantMessage ID 作为 Summary
  MessageId，不另外引入 ID 生成依赖。
- Checkpoint 外部报告保存模型、usage 和策略；这些不进入 Summary 或 Checkpoint
  payload。
- 所有 ConversationMessage 消费方必须显式处理新 variant，禁止通配静默丢弃。

`agent-types` 同时为 `ConversationSnapshot` 增加 provider-neutral 的严格结构校验，
统一保证 ToolCallId 唯一、ToolCall/ToolResult 双向一一配对和顺序正确。
`agent-context` 与 Provider Adapter 都复用该校验，不分别维护两套配对算法。

OpenAI-compatible Adapter 把 ContextSummary 编码为 system message，并加固定前缀：

```text
[Context summary derived from earlier conversation]
<summary text>
```

这样线上协议仍合法，同时保留“派生摘要而非原始系统指令”的模型可见说明。Adapter
的 Tool 配对扫描把 ContextSummary 与 System/User 一样视为不产生 ToolCall 的消息。

### 4.2 预算配置

`agent-context` 定义 Rolling Summary 配置；窗口阈值直接进入 Evaluator，不为单个
数值创建额外配置结构：

```rust
pub struct RollingSummaryPolicy {
    pub summary_output_tokens: u32,
    pub minimum_recent_user_turns: u32,
}

impl ContextWindowEvaluator {
    pub fn new(
        compaction_threshold_ratio: f64,
    ) -> Result<Self, ContextWindowError>;
}
```

`max_automatic_compactions` 是上层多 Run 调度限制，不进入共享 Compression
Strategy；v0.3.0 仅由 Harness 私有任务链验证。

构造期必须验证：

```text
compaction_threshold_ratio.is_finite()
0.0 < compaction_threshold_ratio <= 1.0
summary_output_tokens > 0
```

`context_window_tokens` 不在 Policy 或独立 `ModelLimits` 中重复保存，而是当前
`ModelService` 实例的模型参数。v0.3.0 由 Harness 显式装配该值；Core、Harness 和
`agent-context` 均不得按模型名称猜测窗口。未来正式 Runtime 的配置来源另行设计。

### 4.3 Context Window Evaluator

```rust
pub struct ContextWindowEvaluator {
    compaction_threshold_ratio: f64,
}

pub struct ContextWindowEvaluation {
    pub used_tokens: Option<u64>,
    pub context_window_tokens: u64,
    pub used_ratio: Option<f64>,
    pub decision: ContextWindowDecision,
}

pub enum ContextWindowDecision {
    Ready,
    CompactionRequired,
    UsageUnavailable,
}

impl ContextWindowEvaluator {
    pub fn evaluate(
        &self,
        snapshot: &ConversationSnapshot,
        model: &dyn ModelService,
    ) -> Result<ContextWindowEvaluation, ContextWindowError>;
}
```

Evaluator 是唯一窗口计算入口，内部固定使用最近一次完整模型 Result 的
`TokenUsage.total_tokens`：

```text
used_ratio = total_tokens / context_window_tokens
CompactionRequired = used_ratio >= compaction_threshold_ratio
```

- Evaluator 从 `model.context_window_tokens()` 读取窗口并验证大于 0；比例计算、
  边界比较和报告生成全部封装在 Evaluator 中，Runtime/Core/Harness 不得自行读取窗口
  后裸算。
- Evaluator 定位 snapshot 中最新的 AssistantMessage（允许其后跟随 ToolMessage）；
  只读取该消息的 usage。最新 AssistantMessage 没有 usage 时直接返回
  UsageUnavailable，不向前寻找更旧计数。
- usage 缺失时返回 UsageUnavailable，不主动压缩，由 Provider Context Overflow
  作为兜底。
- 该计数表示最近一次 Provider Turn 已实际使用的完整上下文。Run 前新增的 UserMessage
  或 Model Step 间新增的 Tool Result 尚未包含在最近 usage 中；v0.3.0 接受这一滞后，
  不增加近似 Estimator，超限仍由规范 Overflow 路径收敛。
- 最新有效 Checkpoint 后，replacement 中旧 usage 已清理，因此返回
  UsageUnavailable。

### 4.4 ModelRequest 构造与 Preflight

`agent-model::ModelRequest` 已是 Provider-neutral 的统一请求契约。Core 的正常 Step
和 Rolling Summary 的压缩请求语义不同，分别直接构造该类型，不再增加与
`ModelRequest` 字段一一映射的 Compiler/Input/Error。Tool 配对继续通过
`ConversationSnapshot::validate_tool_exchange_pairs()` 的唯一入口校验。

Harness 的 Run 前验证和 Core Model Step 前都调用同一个
`ContextWindowEvaluator`。只有
Ready/UsageUnavailable 才继续；Core 随后直接构造既有 `ModelRequest` 并建立
Provider Turn，CompactionRequired 则走压缩交接。预算内正常路径不是 Compression
Strategy，不实现 `Passthrough` 类型，也不调用 `compact_context`。

ContextWindowEvaluation 只含 usage 数字、窗口、比例和判断，不包含 prompt、
credential 或 summary 正文。

### 4.5 原子历史块与 protected tail

`ContextLayout::build(snapshot)` 先调用 ConversationSnapshot 的共享结构校验，再完成
分块：

- protected prefix：开头连续的 System 块，始终原样保留；对话开始后再次出现 System
  时，压缩布局返回结构错误，禁止静默重排；
- ContextSummary：位于 protected prefix 之后的派生摘要块；再次滚动压缩时进入可压缩
  head，与后续较早历史共同生成新摘要；
- User Turn：从一个 UserMessage 开始，包含到下一个 UserMessage 之前的所有
  Assistant/Tool 消息；
- Tool Exchange：含 ToolCall 的 AssistantMessage 与其后完整 ToolMessage 批次必须
  位于同一 User Turn。

不变量：

- ToolCallId 在快照内唯一；
- 每个 ToolMessage 引用此前当前 exchange 中的 ToolCall；
- 每个 ToolCall 恰有一个 ToolResult；
- ToolResult 顺序与 AssistantMessage 中 ToolCall 顺序一致；
- ProviderState 保留在所属 AssistantMessage，不单独移动；
- 最后一个仍在执行中的 User Turn、`minimum_recent_user_turns` 和无法解释的
  ProviderState 所在块进入 protected tail；
- head/tail 只能在完整 User Turn 边界切分。

`ContextLayout::build(snapshot)` 只完成与策略无关的结构校验和原子分块；
`ContextLayout::partition(minimum_recent_user_turns)` 再根据 Rolling Summary Policy
计算 head/tail 边界。这样 Layout 不持有 Policy，后续新增 Strategy 仍可复用同一份
原子块。

当前执行因工具循环在下一 Model Step 前交接时，最后 User Turn 可包含若干已经完整
落账的 Tool Exchange，但整体仍作为 protected tail 原样保留。

合法 replacement 的固定顺序为：

```text
protected System prefix → 最新 ContextSummary → recent User Turn tail
```

没有可压缩 head 时不生成新的 ContextSummary。

### 4.6 Compression Strategy

```rust
pub trait CompressionStrategy: Send + Sync {
    fn compact<'a>(
        &'a self,
        input: CompactionInput,
        cancellation: CancellationToken,
    ) -> CompactionFuture<'a>;
}

pub struct CompactionInput {
    pub model: Arc<dyn ModelService>,
    pub instructions: Vec<String>,
    pub layout: ContextLayout,
}

pub struct CompactionCandidate {
    pub replacement: ConversationSnapshot,
    pub report: StrategyReport,
}

pub enum StrategyOutcome {
    Candidate(CompactionCandidate),
    NoOp {
        report: StrategyReport,
    },
}

pub struct StrategyReport {
    pub strategy: String,
    pub compressed_blocks: u32,
    pub retained_blocks: u32,
    pub model: Option<ModelIdentity>,
    pub usage: Option<TokenUsage>,
}
```

Strategy 只生成候选 replacement 和报告，不读取 Session、不提交 Checkpoint、不启动
AgentExecution，也不决定 continuation。`CompactionFuture` 返回
`Result<StrategyOutcome, CompactionError>`；没有可压缩 head 时明确返回 NoOp。

v0.3.0 只实现 `RollingSummarySameModel`：

1. 从 layout 选择可压缩 head 和 protected recent tail；head 为空返回 NoOp。
2. 使用 CompactionInput 中来自当前 ExecutionSpec 的同一个 ModelService。
3. compression request 的 `system` 原样使用正常 Agent 请求的 instructions，保证
   Provider 前缀缓存不会从 system prompt 开始失配；Strategy 内部构造
   `protected prefix + head + 临时压缩 UserMessage`，临时消息使用固定压缩指令和
   `UserPart::Injected`，只存在于本次请求，不进入 History 或 replacement。recent
   tail 不发送给压缩模型，只在生成候选时原样追加到新摘要之后。请求使用空 tools、
   `ToolChoice::None` 和 `summary_output_tokens`，不进入 Agent Loop。
4. compression request 不做本地 token 估算；Provider 报 Context Overflow 时直接
   返回 CompactionError，本版本不分块摘要。
5. 只接受 `FinishReason::Stop`、无 ToolCall、至少一个非空 TextPart 的
   TurnFinished；ReasoningPart 不进入 Summary 正文。
6. 生成 `replacement = protected prefix + ContextSummary + recent tail` 候选；保留
   tail 的全部模型语义和 ProviderState，但清空派生 replacement 中旧
   AssistantMessage 的 usage。

Strategy 不负责最终提交条件。候选统一交回上层编排；v0.3.0 由 Harness 私有入口复用
共享 validator，结构合法、摘要非空且确实替换了至少一个完整 head block 时才能提交。
v0.3.0 不用近似 token 数判断“压缩收益”，后续正常 Model Result 的真实 usage 才是新
窗口占用；自动压缩次数上限负责阻止无效循环。

清空 replacement 旧 usage 只影响派生快照，原始 Conversation History 中的 usage
保持不变。这样 Checkpoint 后首次 Run/Step 会得到 UsageUnavailable；下一次完整
Model Result 落入 replacement 之后，Evaluator 才重新获得与新上下文对应的真实计数，
避免误用压缩前的 `total_tokens`。

未来 ToolResultPruning/HybridCompression 只新增 Strategy 实现，继续复用上述输入、
validator 和结果；本版本不新增裁剪消息类型。

## 五、Agent Core 与模型边界

### 5.1 ExecutionSpec 与 ExecutionInput

`ExecutionSpec` 增加：

```rust
pub context_window: Arc<ContextWindowEvaluator>,
```

`ExecutionInput` 简化为：

```rust
pub struct ExecutionInput {
    pub conversation: ConversationSnapshot,
}
```

新用户输入由上层先写入 Conversation History，再进入有效 snapshot。Core 不再
区分“新用户 Run”与“continuation Run”，也不重复追加 UserMessage：

- 新用户 Run：上层追加 UserMessage 后传完整 snapshot；
- continuation Run：上层不追加 UserMessage，直接传最新 replacement 投影。

这比 `UserTurn/Continuation` enum 更简单，同时不让 Core 持有规范对话权威状态。
v0.3.0 由 Harness 私有 Journal 验证该行为；正式所有权接口留待 Runtime 总体设计。

Harness 在创建新用户 Run 前，先使用同一个 `ContextWindowEvaluator` 检查最新有效
snapshot 中最近一次可信模型 Result 的 usage：

- Ready/UsageUnavailable：创建本轮正常 Run 和 AgentExecution；
- CompactionRequired：以 `BeforeRunThreshold` 调用统一压缩入口，成功提交
  Checkpoint 后再创建本轮正常 Run；
- NoOp/Err：本次用户任务受控失败，不创建 AgentExecution。

这条路径发生时还没有 Harness Run，因此不会制造一个没有调用 Provider 的
CompactionRequired Run，也不称为 continuation。Core 仍在每个 Model Step 前执行
Preflight，作为单次 AgentExecution 内部的执行边界保证。

### 5.2 Step usage 投影与第四种可靠终态

新增一个可丢弃的 Step usage 事件和一种可靠终态：

```rust
AgentEvent::UsageUpdated {
    step: u32,
    usage: TokenUsage,
}

pub enum CompactionReason {
    ThresholdReached,
    ProviderOverflow,
}

AgentEvent::ExecutionCompactionRequired {
    reason: CompactionReason,
    step: u32,
    dropped_events: u64,
}

ExecutionOutcome::CompactionRequired {
    reason: CompactionReason,
    step: u32,
}
```

`ContextWindowEvaluator` 的结果只用于 Core 内部 Preflight 决策，不再重复发布
`ContextEvaluated`：阈值命中已经由可靠的 `ExecutionCompactionRequired` 表达，放行
则一定进入 `StepStarted`，单独的诊断事件没有新增事实。

Provider 流内可能出现一次或多次 `ModelEvent::UsageUpdated`。Core 缓存最新值，只在
收到完整 `TurnFinished` 后发布最多一次 `AgentEvent::UsageUpdated { step, usage }`；
最终 `AssistantMessage.usage` 存在时以它为准，否则回退到流内最新值。失败、取消或
Context Overflow 的未完成 Step 不发布该事件。它沿用普通 bounded mpsc 语义，只供
Runtime 投影、UI 展示和 debug 观察，不能驱动生命周期；最终消息中的 usage 仍是完成
结果的权威数据。

`ExecutionCompactionRequired` 与 Outcome 承载同一终态事实；CompactionRequired
进入现有可靠终态 oneshot，与 Completed/Failed/Cancelled 四选一。

Core 循环顺序调整为：

```text
max_steps 预检
→ next_step = completed/started steps + 1
→ ContextWindowEvaluator
   ├─ CompactionRequired：可靠终态结束，不发布 StepStarted
   └─ Ready / UsageUnavailable
      → 直接构造 ModelRequest
      → step 计数生效
      → StepStarted
      → ModelService::stream
      → 完整 TurnFinished
      → 若有 usage，发布一次 UsageUpdated
```

Provider 在已开始 Step 返回 ContextOverflow 时，Core 使用当前 step 发出同一终态。
该 Step 已产生的 Text/Reasoning delta 只是观察数据，Runtime/debug 聚合必须标记
discarded；它不进入 Conversation History。

### 5.3 Tool Call/Result 安全边界

当前 Engine 只有在完整 `TurnFinished` 后才提取 ToolCall、调用
`begin_tool_exchange` 和执行工具，因此：

- 建立前 ContextOverflow 不存在当前 AssistantMessage；
- 流内 ContextOverflow 的 ToolCall 增量尚未形成 AssistantMessage，也未产生
  ToolProposed 或工具副作用；
- 下一个 Model Step 开始前，上一个 Tool Exchange 已经通过
  `complete_tool_exchange` 原子完成；
- 上一个完整 Model Result 的 `usage.total_tokens` 作为下一 Step 前窗口判断依据；
  随后新增的 Tool Result 尚未进入该 usage，若因此超限则由 Provider Overflow 兜底；
- 压缩交接可直接丢弃当前未完成 Step，稳定事实以 Runtime 最新 completed history
  为准，不需要补 ToolResult。

非 ContextOverflow 错误不得转换为 CompactionRequired。未来若错误发生在工具副作用
阶段，继续走现有结算后 Failed/Cancelled 规则。

### 5.4 Context Overflow

`agent-model` 新增：

```rust
ModelError::ContextOverflow { message: String }

pub trait ModelService: Send + Sync {
    fn capabilities(&self) -> &ModelCapabilities;
    fn context_window_tokens(&self) -> u64;
    // 其余既有方法
}
```

- HTTP/请求建立前拒绝：`ModelService::stream -> Err(ContextOverflow)`；
- 已建立流的 Provider 若能报告同类错误：
  `ModelEvent::TurnFailed { error: ContextOverflow }`；
- 错误只携带脱敏诊断，不携带完整请求或响应正文。

OpenAI-compatible Adapter 只根据已确认 fixture 的结构化 error code/type 精确映射，
不使用任意 message substring 猜测。首期 allowlist 至少覆盖测试 fixture 中确认的
`context_length_exceeded`；新增 Provider 码必须先增加脱敏 fixture。

不在 `ModelCapabilities` 重复增加 max output 开关。上层调用方通过
`GenerationConfig.max_output_tokens` 表达本次请求的输出上限；OpenAI-compatible
Adapter 直接根据 Profile 的 `max_output_tokens_field` 编码，字段为空而请求显式设置上限时
返回 `ModelError::Config`。这样“本次是否设置”和“Provider 方言能否编码”各自只有
一个事实来源。

`context_window_tokens` 是模型服务构造参数，不新增 `ModelLimits` 数据结构，也不放进
只描述功能支持与否的 `ModelCapabilities`。OpenAI-compatible Service 构造时由调用方
配置显式传入窗口上限；v0.3.0 Harness 负责装配，未来产品配置归属留待 Runtime 总体
设计。不得在 Core 或 Evaluator 内按模型名硬编码。

## 六、Harness 临时压缩编排与内存状态

本节只定义 v0.3.0 的验证实现，不定义正式 `assistant-runtime` API。所有类型保持
`runtime-harness` 私有，并使用 `Harness` 前缀或模块私有可见性。

### 6.1 Checkpoint 与有序记录

Harness 扩展现有内存 Journal：

```rust
struct HarnessContextCheckpoint {
    replacement: ConversationSnapshot,
}

enum ConversationRecord {
    Message(ConversationMessage),
    Checkpoint(HarnessContextCheckpoint),
}
```

Checkpoint payload 只有 replacement，不增加 `covers_through`、revision、父
Checkpoint、strategy、model 或 usage。pending Tool Exchange 继续独立保存，不进入
completed records。

有效 snapshot 从尾部找到最新 Checkpoint，以 replacement 为起点并追加其后的 Message；
没有 Checkpoint 时使用全部 Message。Harness 的会话展示仍只读取原始 Message，
Checkpoint 不作为聊天消息。

本版本不定义 `ContextStateStore` 等正式 SPI，不实施数据库 schema 或迁移。读取和提交
失败通过 Harness Journal 的测试注入验证；未来产品 Store 的事务、Session 绑定与查询
接口由 Runtime 总体设计决定。

### 6.2 私有压缩编排入口

Harness 私有 `HarnessContextCoordinator::compact_context` 固定执行：

```text
读取 effective snapshot
→ ContextLayout
→ CompressionStrategy
→ 通用 replacement validator
→ 内存 Journal 原子追加 Checkpoint
→ 返回 Compacted / NoOp / Err
```

私有 cause 包含 `BeforeRunThreshold`、`InRunThreshold`、`ProviderOverflow` 和
`UserRequested`。cause 只进入临时报告，不切换算法。自动路径附带
`ContextWindowEvaluation`，用户主动压缩没有 trigger。报告不写入 Checkpoint。

轻量私有封装：

- `prepare_user_context`：UserMessage 落账后执行 Preflight；Ready/
  UsageUnavailable 返回 Initial context，阈值命中只有 Compacted 才返回 Initial
  context；
- `handle_compaction_required`：映射 Core reason，Compacted 后返回关联前一
  `HarnessRunId` 的 Continuation context，不重复追加 UserMessage；
- `handle_user_compaction`：只返回压缩结果，没有任务链或 Run 分配参数。

这些封装返回 `ExecutionInput` 和临时报告，不分配新的产品 Run ID，也不启动
`AgentExecution`。真正的 Harness Run ID 继续由现有 `HarnessRuntime` 私有状态分配。

### 6.3 临时任务链与调试

Harness 私有任务链保存 `automatic_compactions` 与
`max_automatic_compactions`。只有自动 Compacted 增加次数；UserRequested、NoOp、
失败和取消不增加。达到上限后不调用 Strategy。

M6 将把上述已测试的私有编排接入 Harness Chat、`verify v0.3`、`/compact`、`/state`
和 debug-viewer Runtime 通道。报告可包含 cause、strategy、窗口数字、head/tail
块数、模型 identity、usage、Checkpoint 结果与 Harness Run 关联，但默认不携带摘要
正文。

## 七、Provider 与 Harness 实现

### 7.1 Provider Adapter

需要更新：

- ConversationMessage exhaustive match 与 ContextSummary system 编码；
- 编码前复用 ConversationSnapshot 严格 ToolCall/ToolResult 校验，并补齐双向配对测试；
- ContextOverflow code/type 解码与 HTTP 建立前传播；
- OpenAI-compatible Service 构造参数和 `ModelService::context_window_tokens()`；
- DeepSeek reasoning/tool-call/ProviderState 既有 fixture 全量回归。

Adapter 不知道 Checkpoint、Compression Strategy、Run 或 continuation。

### 7.2 `agent-testkit`

新增：

- ScriptedModelService 增加显式 `context_window_tokens`，继续区分普通请求与
  compression request，并可脚本化每次 Result 的 TokenUsage；
- ContextOverflow 建立前/流内脚本；
- ContextLayout/replacement 断言辅助函数。

testkit 不提供真实 tokenizer、存储或 Runtime 调度。

### 7.3 `runtime-harness`

Harness：

- 扩展现有 `HarnessJournal`：有序 ConversationRecord + 独立 pending exchange；
- 新用户先追加 Message，再执行 Harness Preflight；Ready 或压缩成功后才创建 Run，
  并构造只含完整 snapshot 的 ExecutionInput；
- 支持 CompactionRequired Run 终态和 continuation Run；
- 使用私有 `HarnessContextCoordinator` 编排 `agent-context` 公共能力，不复制窗口、
  Layout、Validator 或 Rolling Summary 算法；
- 增加 `/compact`：无活动任务链时执行 UserRequested；活动任务链期间排队，链结束后
  执行，结果不续跑；
- `/state` 增加 Checkpoint 数、最新 replacement 消息角色、自动压缩次数和最近
  CompactionReport；
- `verify v0.3` 累计运行 v0.1–v0.3 场景，v0.2 场景保持可用。

debug-viewer 只需因强类型 AgentEvent 自动支持第四终态；如增加专用展示，只读取
Runtime 报告，不引入上下文业务逻辑。

## 八、配置与运行约定

v0.3.0 Harness 的离线/真实模式都必须显式装配：

- `compaction_threshold_ratio`；
- RollingSummaryPolicy；
- `max_automatic_compactions`；
- 带 `context_window_tokens` 参数的当前会话 ModelService。

离线 verify 使用小窗口和脚本化 TokenUsage 稳定触发边界；真实 chat 使用显式环境/CLI
配置，不根据模型名在 Core 内猜窗口。具体 CLI/env 名称在开发计划对应 Harness
里程碑中确定，不能成为 Core/agent-context 的隐藏默认。

`Passthrough` 不作为策略或配置值。窗口判断为 Ready/UsageUnavailable 时由 Core
自然继续构造正常请求。

## 十、兼容、风险与排除项

- **公共 API 变化**：ExecutionSpec 增加 context_window；
  ExecutionInput 改为完整 snapshot；
  AgentEvent/ExecutionOutcome 增加终态；ModelService/ModelCapabilities/ModelError/
  ConversationMessage 增加 variant。所有 workspace 消费方必须 exhaustive 更新。
- **usage 滞后或缺失**：窗口判断只使用最近完整 Result 的 Provider `total_tokens`；
  新增 User/Tool 消息尚未计入或 usage 缺失时不本地猜测，由规范 ContextOverflow
  兜底。
- **摘要失真**：原始 Message 记录不变；Summary 明示派生；protected tail 原样保留；
  空摘要、无可压缩 head 或非法 replacement 不提交。
- **隐藏重试**：Provider/Core 不重试；Harness 自动次数显式且有上限。
- **重复实现**：Evaluator/layout/validator/Strategy 在 `agent-context` 唯一实现；
  Harness 只增加私有 Checkpoint/continuation 编排，不复制共享算法。
- **Provider 误判**：只映射结构化、fixture 已确认的 code/type，不做任意错误文本
  substring 判断。
- **compression request 自身超限**：本版本失败，不实现分块/分层摘要。
- **取消**：Core、compression request、Store commit 和 wrapper 都必须有确定终态；
  取消后不 continuation。
- **存储**：本版本不实施数据库、迁移、重启恢复和多设备同步。
- **裁剪压缩**：只保留 CompressionStrategy 接口，不实现 ToolResultPruning、
  CompactedToolResult 或 HybridCompression。
- **正式 Runtime**：不修改 `assistant-runtime` 代码或依赖；Harness 私有类型不承诺
  序列化兼容，正式 Session/Run/Store/事件在 Runtime 产品版本重新设计。
- **UI/协议**：不修改桌面 UI 和 assistant-protocol；Harness 调试事件保持工具私有
  格式，正式应用事件留待 Runtime 产品版本设计。

验证方案，实施顺序与里程碑门槛由关联开发计划维护。
