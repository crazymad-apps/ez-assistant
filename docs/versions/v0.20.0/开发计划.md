## 二、台账与实施原则

1. 按 M0—M7 顺序实施。用户于 2026-08-26 明确授权连续实施并自行验收 M0—M3，因此这四个
   里程碑完成后直接进入下一项，不逐项等待确认；M3 完成后统一停止并提交用户审核。M4—M7
   仍按逐里程碑确认门禁执行。
2. 开始 M0 前将 [`版本管理`](../../版本管理.md) 从 `计划中` 更新为 `开发中`，并初始化或续写
   `docs/开发进度.md`。本次连续授权仅覆盖 M0—M3，不延伸到 M4 及后续里程碑。
3. M0 只收口 Runtime 私有的 Run 工具装配流水线，不引入 Controller 业务行为；既有冻结 ToolSet
   与现有条件工具的外部行为必须保持一致，再由 M2 增加主控工具装配环节。
4. 代理状态变更与 Queue 执行门禁必须分离：有无 Queue 都能立即切换代理；Queue 未排空时不接受
   主控投递、不产生中间报告，最后一项只报告最新结果；用户新输入继续原子退出代理。
5. 主控、普通 Session、Input、Run、Goal 和 Conversation 的权威状态只存在于 Runtime/Store；
   Desktop 不按标题、消息文本、generation 或本地计时器猜测。
6. clear 是不可撤销的产品历史删除。所有 schema migration、删除、崩溃点和恢复验证只使用
   `TempDir`、内存 Store 或隔离 Runtime Home；本计划不授权打开、迁移、清空或写入用户实际数据库。
7. compact 复用现有 rolling summary 与 generation replacement，不改变算法；Session 级
   `active_compaction` 只存在于 Runtime 内存，不能为了 UI 恢复新增持久字段。
8. 不新增 crate、第三方依赖、通用消息总线、通用插件 ABI、主控唯一索引、回复关联表或待生效
   proxy 状态；发现设计与真实代码不符时停止扩大改动，先回到设计确认。
9. 跨 Session 事务、JSONL 切换、清理回执和崩溃恢复必须在 Host/Runtime 边界通过故障注入回证，
   不能只断言内存投影或 Desktop 展示。
10. Controller 工具只由用户直接发给主控的父 Run 获得；代理报告、Goal continuation 和 child
    不能因处于 Controller Session 而获得跨会话能力。
11. 真实 Provider 测试保持 `#[ignore]`，只有用户明确同意产生网络请求后才执行；日志和测试输出
    不得包含 credential、用户正文、reasoning、附件或私有绝对路径。
12. 不主动执行 Git commit/push。每个里程碑开始前重新核对工作树、当前授权、对应语言规范和
    模块约束，保留用户已有改动。

## 四、里程碑明细

### M0：Run 工具装配流水线

前置依赖：本开发计划已确认；版本状态已更新为 `开发中`。

目标：先把现有 `compile_run_agent` 的逐项工具追加收口为 Runtime 私有装配流水线，为主控及未来
条件工具贡献建立稳定入口，同时保证本里程碑不改变任何 Run 的实际工具能力。

交付范围：

- 建立最小 Run Assembly Context、平行贡献环节和冻结输出，不改变 Agent Core Tool SPI；
- 将现有冻结 ToolSet 及 `load_skill`、计划、Goal、委派等条件工具迁入流水线；
- 实现确定性顺序、完全相同重复项去重、同名异义冲突 fail-closed 和不可变最终 ToolSet；
- 保持 parent/child、Goal continuation、Plan/Build 与现有模型能力门禁不变；
- 补齐装配矩阵和失败诊断测试，不提前实现 Controller 工具。

验证入口：

```bash
cargo test -p assistant-runtime
cargo test -p agent-tools
cargo clippy -p assistant-runtime -p agent-tools --all-targets --all-features -- -D warnings
```

完成判定：所有现有 Run 类型在改造前后得到等价工具集合；重复项和冲突行为确定，后续业务只需
新增装配环节，不再向 `compile_run_agent` 追加条件分支。

Review 重点：是否过度抽象为公共插件 ABI；既有工具是否被遗漏或重复；去重是否静默吞掉同名异义工具；
Agent Core 是否反向依赖 Runtime。

### M1：Session 角色、代理与主控基础

前置依赖：M0 已确认。

目标：建立可迁移、可恢复的 Session role/proxy 领域和产品层当前主控，使旧 Runtime Home 安全升级，
且尚未引入跨会话消息执行。

交付范围：

- 实现 Standard/Controller role、可选 proxy binding 和对应 Store 端口；
- 完成 SQLite 增量迁移、旧数据缺省、外键/自绑定/角色校验和易失 Store 对等语义；
- 按已确认稳定顺序选择当前 Controller；不存在时自动创建，产品并发入口不重复创建；
- 落实 Controller 不能归档、删除、Fork 或绑定 proxy 的 Runtime 门禁；
- 增加 role、proxy、Controller availability 的 Protocol 快照类型和 TypeScript 导出；
- 覆盖重启、多 Controller 脏数据、创建失败和旧协议缺省，不建立数据库 unique index。

验证入口：

```bash
cargo test -p assistant-protocol
cargo test -p assistant-runtime
cargo test -p assistant-runtime-host
cargo run -p assistant-protocol --example export_typescript -- --check
cargo clippy -p assistant-protocol -p assistant-runtime -p assistant-runtime-host \
  --all-targets --all-features -- -D warnings
```

完成判定：旧 Session 全部恢复为 Standard/无 proxy；无主控时只创建一条当前使用主控，重启不重复；
多个主控时选择确定；角色限制在 Runtime 权威生效，未新增 revision 或唯一约束。

Review 重点：是否按标题或查询第一条猜测主控；迁移是否重写 Conversation；proxy 是否错误落在 Desktop；
是否为单 owner 串行状态增加冗余 revision。

### M2：主控工具、投递与用户接管

前置依赖：M1 已确认。

目标：让用户直接发给主控的父 Run 获得最小跨会话工具，并建立受 proxy 与 Queue 约束的可靠投递、
结构化来源和用户直接接管闭环。

交付范围：

- 在 M0 流水线增加主控工具贡献环节，只为符合来源门禁的 Controller parent Run 装配查询、设置和投递；
- 实现显式 proxy 终态设置；有无 Queue 都立即切换，不增加 pending proxy；
- 实现 ControllerDelivery binding、持久 Input/UserMessage 来源、确定幂等键和目标自身模型/权限/审批；
- 目标存在 queued Input 时投递返回 busy，不插队、不改变 proxy、不保存延迟投递；
- 用户直接提交 Input 时，在同一业务事务关闭 proxy、删除未开始的 ControllerDelivery 并接受用户输入；
- 覆盖活动 Run 中途开关、并发投递/接管两种顺序、重试、Goal held 和来源恢复；
- 验证现有非用户来源、Goal continuation 和 child 的装配结果不含主控工具；M3 新增报告来源后
  继续复用同一门禁。

验证入口：

```bash
cargo test -p assistant-protocol
cargo test -p assistant-runtime
cargo test -p assistant-runtime-host
cargo run -p assistant-protocol --example export_typescript -- --check
cargo clippy -p assistant-protocol -p assistant-runtime -p assistant-runtime-host \
  --all-targets --all-features -- -D warnings
```

完成判定：主控不能向普通模式或仍有 Queue 的目标投递；状态切换不受 Queue 阻止；可靠投递只执行一次；
用户新输入无竞态地接管且不产生“已取消”报告，已活动 Run 不被静默取消。

Review 重点：状态变更与执行门禁是否再次混淆；投递是否绕过目标权限；是否同时持有两个 Session 锁；
用户接管是否只在 Desktop 关闭开关。

### M3：Queue 排空报告与崩溃恢复

前置依赖：M2 已确认。

目标：把代理报告作为源 Run settlement 的可选原子 effect，并严格落实 Queue 未排空不报告、
最后一项只报告最新结果及主控报告 Run 无控制能力。

交付范围：

- 实现 ProxyReport binding、稳定源 Run 终态、可选 Goal 来源和有界确定性报告正文；
- 在 Run/Goal settlement 应用后的 Queue 为空时，原子结算源 Run 并向 Controller 接受报告 Input/Run；
- Queue 未空的中间 Run 不生成、不缓存、不补发报告，最后一项只报告自身最新结果；
- 报告处理 Run 经工具流水线得到空主控贡献，只能向用户汇报或询问；
- 完成跨 Session 内存投影、幂等、锁顺序和 Store 提交后崩溃恢复；
- Host 异常退出产生 Interrupted settlement 时复用相同 proxy/Queue 门禁；
- 覆盖 completed/failed/cancelled/interrupted、Goal effect、Queue 新增、proxy 中途关闭和来源 Session
  删除后的报告恢复；来源 clear 的回归在 M4 补齐。

验证入口：

```bash
cargo test -p assistant-protocol
cargo test -p assistant-runtime
cargo test -p assistant-runtime-host
cargo run -p assistant-protocol --example export_typescript -- --check
cargo clippy -p assistant-protocol -p assistant-runtime -p assistant-runtime-host \
  --all-targets --all-features -- -D warnings
```

完成判定：报告与源 Run 终态不存在一边成功一边丢失；Queue 中间结果不会让主控和目标形成双重决策；
报告 Run 不能继续跨会话控制；重启不会重复、漏掉已提交报告或补发被门禁跳过的结果。

Review 重点：Queue 判断是否使用 settlement 后状态；是否缓存中间报告；恢复路径是否绕过 Queue 门禁；
报告正文是否泄漏 reasoning、工具、审批或 Provider 原始错误。

### M4：Session clear

前置依赖：M3 已确认。

目标：为完全空闲的 Standard/Controller Session 建立不可撤销的历史清空、System Context 重建、
结构删除和物理文件清理恢复闭环。

交付范围：

- 增加 clear Protocol Command/Result、operation 幂等和统一空闲门禁；
- 在删除前通过现有 Factory 准备并校验新的 System Prompt、Skill Catalog 和稳定 Session 资源身份；
- 原子切换空 generation，删除旧 Input/Run/Goal/WorkPlan/Recall 等结构事实并更新标题/proxy 语义；
- 保留 Session ID、Workspace、设置、权限、附件、private 目录和已确认的 Controller 关系；
- 实现不含正文的 cleanup receipt、精确路径物理清理、`cleanup_pending` 和启动恢复顺序；
- 覆盖准备失败、事务失败、文件清理失败、各崩溃点、重复 operation、Standard/Controller 差异和
  当前 generation 唯一可见性；
- 验证 clear 来源 Session 不删除其他 Session 已持久化的 ControllerDelivery/ProxyReport 历史；
- 所有破坏性测试只操作隔离临时目录，并精确核对删除与保留集合。

验证入口：

```bash
cargo test -p assistant-protocol
cargo test -p assistant-runtime
cargo test -p assistant-runtime-host
cargo run -p assistant-protocol --example export_typescript -- --check
cargo clippy -p assistant-protocol -p assistant-runtime -p assistant-runtime-host \
  --all-targets --all-features -- -D warnings
```

完成判定：clear 成功后旧历史立即退出 Conversation、Recall、导出和模型上下文；失败时旧状态完整保留；
cleanup pending 可在重启后只清理精确旧文件，不删除附件、private、权限或 Session 目录。

Review 重点：是否先删旧状态再准备新上下文；物理删除是否使用 glob/宽泛目录；清理失败是否谎报完成；
是否在用户实际 Runtime Home 上运行迁移或删除测试。

### M5：手动 compact 与统一压缩状态

前置依赖：M4 已确认。

目标：把 `/compact` 建成独立的空闲 Session 上下文操作，并让自动与手动 parent compaction 共用
不持久化的实时状态、开始/结束事件和恢复口径。

交付范围：

- 增加 compact/cancel Protocol Command、结果、错误和 operation 幂等；
- 抽取无 active-turn fallback 的手动 parent compactor，复用 rolling summary 和当前模型；
- 扩展 idle generation replacement，落实 no-op、取消前后边界、失败保旧和成功失效；
- 为自动/手动 parent compaction 建立 Runtime-owned guard、易失 `active_compaction` 和成对事件；
- 重启只恢复 receipt 终态，不恢复“压缩中”；child compaction 不投影到 parent Session；
- 把已有 Context Summary 内联投影为 ConversationItem；Desktop 在 generation 切换时保留当前
  已加载消息、去重保留轮次并直接渲染摘要分割项，不增加独立实体或持久化；
- 覆盖 busy 拒绝、重复 operation、HTTP future drop、事件丢失/乱序、自动压缩回归和用量投影。

验证入口：

```bash
cargo test -p agent-context
cargo test -p assistant-protocol
cargo test -p assistant-runtime
cargo test -p assistant-runtime-host
cargo run -p assistant-protocol --example export_typescript -- --check
cargo clippy -p agent-context -p assistant-protocol -p assistant-runtime -p assistant-runtime-host \
  --all-targets --all-features -- -D warnings
```

完成判定：手动 compact 不创建 UserMessage/Run/Goal continuation；成功的模型上下文只保留摘要与
近期轮次，Desktop 当前已加载消息不因 generation 切换消失；no-op/取消/失败不切换 generation；
自动与手动状态可实时观察且重启后不会永久残留。

Review 重点：是否把 compact 当业务 Run；是否持久化 active 状态；取消是否逆转已提交 replacement；
Desktop 是否把摘要边界放在正确历史位置，或通过 generation 猜测。

### M6：Desktop 完整交互闭环

前置依赖：M5 已确认。

目标：依据交互指导在现有侧栏、Header、Conversation、Composer、Queue 和确认框中完成 v0.20.0
全部可见能力，不建立第二份权威业务状态。

交付范围：

- 在“会话”页签下方、工作区列表上方显示固定主控分区，“已归档”页签隐藏；
- 实现 role/proxy 身份、代理开关、Queue 未排空说明和用户直接接管提示；
- 实现 ControllerDelivery 与 ProxyReport 中性来源呈现、稳定终态和来源 Session 导航；
- Controller 隐藏归档、删除和 Fork；clear 复用现有确认框并按 Runtime 快照重建；
- Composer 精确识别 `/compact`，自动/手动共用“正在压缩上下文”状态；手动取消复用现有输入框
  发送/终止主按钮，状态条不增加第二个取消按钮；
- 压缩前消息保持正常显示；在旧消息与近期轮次之间显示摘要分割线，默认收起，点击可展开或收起
  当前摘要正文；
- 较长 ProxyReport 默认限制显示高度，使用底部渐变表达收起状态，并允许用户展开或再次收起；
- 建立统一 Queue presentation selector，只隐藏 automatic dispatching head，修复待发送区闪现；
- 运行态指示使用固定尺寸、带合成提示的 SVG 圆环，Header 不重复展示与代理开关同义的身份标签；
- `read_file` 的模型可见定义明确调用无状态，续读必须显式传入上一页的 `next_offset`；
- 覆盖持续错误、焦点、键盘、中文输入法、窄宽度、缩放和减少动态效果。

验证入口：

```bash
cd apps/desktop
npm run lint
npm run test
npm run build

```

完成判定：用户可从主控或目标 Session 完成代理、投递、报告、接管、clear 和 compact 全链；
Queue 不闪现，压缩状态不残留，来源消息不伪装用户，所有界面状态均可从协议快照重建。

Review 重点：主控位置及归档页签行为是否准确；代理状态是否被 Queue 禁止切换；是否出现第二个取消按钮；
是否显示冗余压缩说明、按文本解析来源或用计时器掩盖 Queue。

### M7：跨层回归与验收准备

前置依赖：M6 已确认。

目标：在不扩大版本范围的前提下，证明主控、代理、clear、compact 和 Queue 修复在正式
Runtime Host、Desktop、SQLite/JSONL 与重启恢复中同时成立，并形成验收前可复查证据。

交付范围：

- 汇总旧 Session/Conversation/Input 兼容、自动压缩、Goal、WorkPlan、Skill、审批、权限、附件、
  Recall、Fork、child、归档、取消、重启和删除回归；
- 使用正式 Host + fake Provider 覆盖自动主控、活动 Run/Queue 中切换、投递 busy、Queue 最终报告、
  用户接管、报告能力门禁、clear、compact/cancel 和重启；
- 在隔离 Runtime Home 中只读核对 SQLite、当前 JSONL、cleanup receipt、文件保留/删除、协议快照和
  Desktop 展示，明确区分数据库、文件、内存和 UI 状态；

## 五、版本级完成条件

1. M0—M7 全部完成实现、最小有效验证并逐个获得用户确认。
2. 主控稳定自动创建并保持产品层软性单例；旧 Session 安全迁移，角色、代理和来源可在重启后恢复。
3. 工具装配流水线不改变既有工具行为，只有用户直接主控 Run 获得跨会话能力。
4. 代理状态可随时切换；Queue 未排空时没有主控投递或中间报告，最后一项只报告最新结果；用户输入
   原子接管且不产生取消噪声。
5. clear 在空闲门禁、上下文准备、结构删除、物理清理和崩溃恢复各层均无新旧混合，保留范围准确。

   压缩后不保留第二份产品历史。

   断线重建验证。
8. workspace Rust 门禁、Desktop lint/test/build/e2e、Tauri no-bundle 构建及隔离 Runtime Home
   故障恢复形成实际结果；真实 Provider 未获授权时明确记录未执行。
9. 全部里程碑确认后才将版本状态推进为 `验证中`，创建验收记录并开始版本级验收。
