## 二、背景与问题

### 2.1 当前 Session 之间没有正式通信关系

现有 Runtime 已持有多个独立 Session，并保证不同 Session 可以并发、同一 Session 中改变
Conversation 的父 Run 默认串行。`v0.13.0` 的子 Agent 是父 Run 内同步等待的受控执行单元，
不是独立 Session；`v0.18.0` 的 Goal 是单 Session 内跨 Run 自动续跑，也不承担跨会话通信。

因此，普通 Session 完成工作后只能在自己的 Conversation 中回复。用户如果希望在一个统一入口
收集结果、向不同 Session 转达后续指令，需要手工切换会话、阅读上下文并重复输入。未来接入
智能终端或 IM 时，如果每种入口直接控制任意 Session，还会把来源、回复目标、权限和会话状态
耦合到具体渠道。

本版本需要先建立一个产品内统一入口：主控会话负责与用户交流，并通过可靠、可归因的消息与
其他 Session 通信。它不是复杂任务编排器，不判断全局任务完成度，也不自动接管所有会话。

### 2.2 普通会话不能无条件持续上报

如果任何普通 Session 都能随时向主控发送消息，主控会被无来源、无边界的进度和中间状态淹没，
也无法区分用户是否希望由主控代理当前会话。因此需要显式的主控代理状态：用户授权后，普通
Session 才允许主控投递工作消息并把最新运行结果报告给主控；普通模式不接收主控工作消息，
只允许用户或主控显式切换代理状态。

### 2.3 Session 缺少用户主动的上下文生命周期控制

正式 Runtime 已能在上下文达到阈值或 Provider 报告 overflow 时自动 compaction，但 Desktop
没有用户主动压缩入口。Session 的 System Context 自创建后冻结，用户也没有在保留 Session
身份、Workspace 和设置的情况下清空 Conversation 并按当前 Persona、Pinned Memory、
Instructions、Workspace 环境和 Skills Catalog 重新开始的正式能力。

`clear` 与 `/compact` 必须明确区分：前者不可撤销地删除当前产品会话中的历史消息正文，
开启一个空的新会话纪元并重建 System Context；后者只是复用现有滚动摘要，用 Context Summary
和近期轮次替换较早上下文，不刷新 System Context，也不继续执行任务。

## 三、版本目标与成功标准

`v0.20.0` 形成三个相互协同但职责独立的闭环：

1. 建立具有稳定产品身份的主控会话，用户可以把它作为统一协调入口；
2. 建立显式代理切换，以及代理生效后主控到目标 Session 的消息投递和 Run/Goal 结果报告；
3. 建立会话 `clear` 与用户主动 `/compact`，让用户能明确控制 Conversation 和冻结
   System Context 的生命周期。

成功标准是用户能够完成以下路径：

- 在升级后看到 Runtime 自动准备的主控会话，并与它正常交流；
- 让主控先把普通 Session 切换为代理模式，再转达一次指令并在主控中收到运行结果；
- 显式为某个 Session 开启主控代理，让该 Session 的最新 Run/Goal 结果进入主控；
- 在主控中要求开启或关闭某个 Session 的代理状态；
- 直接在代理 Session 中输入时自动退出代理，不让旧的未执行主控队列继续干扰用户接管；
- 清空一个空闲 Session 的历史并在同一 Session 身份下获得按当前来源重建的 System Context；
- 输入 `/compact` 主动压缩较早上下文，且不会创建普通 UserMessage、业务 Run 或自动续跑；
- Session 空闲时发送普通消息，立即执行的输入不会先在 Composer 待发送区短暂闪现；
- 重启、客户端重连和重复请求后，主控身份、代理状态、消息投递、clear 与 compact 结果仍可解释、
  不重复且不依赖 WebView 在线。

## 四、明确非目标

本版本不包含：

- 多主控选择、主控层级、主控之间的路由或按 Workspace/用户/渠道分配主控；
- ManagedTask、跨会话任务状态机、任务依赖、自动分派、负载均衡或完成度 Judge；
- 主控读取、复制或持续同步普通 Session 的完整 Conversation；
- 完整托管模式、跨会话共享上下文或把普通 Session 的摘要注入主控作为长期镜像；
- 普通 Session 之间任意互发消息；
- 普通 Session 脱离代理状态主动向主控发送任意消息；
- 主控处理自动报告后，无需用户新指令就继续给目标 Session 下发任务；
- 向主控代理审批、在主控中处理其他 Session 的审批或由主控自动授权；
- started、模型 step、reasoning、工具调用、子 Agent 中间过程等实时进度上报；
- 系统通知、通知中心、通知偏好、声音、Dock/菜单栏提醒或外部推送；
- 智能终端、IM、Webhook、机器人账号、用户身份绑定或真实外部渠道接入；
- 渠道插件 ABI、通用消息总线、远程 Broker 或分布式 Session 路由；
- `clear` 的操作系统级安全擦除、备份销毁或取证不可恢复承诺；
- 为 `/compact` 新建第二套压缩算法，或保留一份与当前规范 Conversation 分离的完整历史副本；
- 主动压缩子 Agent Conversation，或向用户暴露 child task 的独立 `/compact`；
- 让主控绕过目标 Session 的模型、Plan/Build、Ask/Auto、权限、审批或 Workspace 边界。

## 五、术语与状态

### 5.1 会话角色

- **普通会话（Standard Session）**：现有用户工作会话，持有自己的 Conversation、Run、Goal、
  WorkPlan、Workspace、权限和冻结上下文。
- **主控会话（Controller Session）**：具有主控角色的正式 Session；同样由 Runtime 持有
  Conversation 和 Run，只额外获得受限的会话查询、代理切换和消息投递能力。
- **当前主控**：当前产品实际使用的主控会话。本版本产品入口软性限制只创建一个，但领域和
  存储允许存在多条主控会话记录。

### 5.2 普通会话通信状态

- **普通模式**：默认状态。Session 不接收主控工作消息，也不向主控报告 Run/Goal 结果；只允许
  用户或主控显式把它切换为主控代理模式。
- **主控代理模式**：用户显式授权主控代理当前 Session。主控只能向已经绑定自己的代理 Session
  投递工作消息；父 Run 结束时如果代理仍然生效，就把最新 Run/Goal 结果报告给绑定的主控。

代理状态必须关联具体 Controller Session，而不是只保存一个无法表达归属的布尔值。当前产品
虽然只使用一个主控，也不能让普通 Session 的代理事实依赖“数据库里碰巧只有一条”。

### 5.3 跨会话消息

- **投递消息**：主控发给普通 Session 的有界文本指令，具有稳定来源、目标和幂等身份。
- **代理报告**：父 Run 结束时，如果 Session 当下仍处于代理模式，Runtime 对最新 Run/Goal
  结果形成的有界报告；它不要求 Run 来自主控投递，也不是完整 Conversation 摘要或实时执行流。

### 5.4 会话上下文操作

- **Clear**：不可撤销地删除当前会话的历史消息正文和产品历史投影，清除依赖旧 Conversation
  的控制状态，并按当前来源重建 System Context；不保留软删除、归档或可恢复的旧 Conversation，
  但保留 Session 身份与明确列出的资源和设置。
- **Manual Compact**：用户通过精确 `/compact` 命令主动触发现有滚动摘要，把较早 Conversation
  替换为 Context Summary 与近期轮次；不重建 System Context。

## 六、主控会话

### 6.1 产品层软性单例

- 本版本的 Desktop 和正式 Runtime 产品入口只允许存在一个当前主控。
- 数据结构、领域关系和存储不增加“全库只能有一条主控”的唯一约束，为未来多主控保留空间。
- Runtime 按稳定顺序检索主控会话并使用第一条；具体排序键由技术方案基于现有 Session 稳定字段
  确定，不能依赖数据库未声明的自然返回顺序。
- 创建入口必须在 Runtime 内再次检查，避免两个客户端并发请求绕过 Desktop 的软限制。
- 如果恢复时已经存在多条主控记录，本版本不删除、不合并也不改写其他记录；只使用稳定检索到
  的第一条，并保留可诊断事实。

### 6.2 自动创建与恢复

- Runtime 启动恢复完成后，如果没有任何主控会话，自动创建一个。
- 自动创建使用当时有效的默认模型和 System Context 构建链；创建失败不得伪装为普通空会话，
  Runtime 应保持可诊断，其他普通 Session 仍按既有可用性工作。
- 主控身份是持久业务事实，重启和 Desktop 重连不能按标题、列表位置或图标推断。
- 主控会话沿用普通 Session 的持久 Conversation、同 Session 串行、Run 恢复和配置冻结语义。

### 6.3 生命周期与产品身份

- Desktop 将当前主控放在稳定、易识别的位置，与普通 Session 视觉区分。
- 当前主控不提供归档、删除或 Fork 为另一个主控的产品入口。
- 主控可以执行 `clear`，但 clear 后仍保持主控角色，普通 Session 已存在的代理绑定不因此消失。
- 主控可以作为普通助手与用户交流，但本版本新增的跨会话能力仍受本文约束，不把“主控”解释成
  无限制访问所有会话正文或替用户批准工具。
- 通知形态不在本版本设计；功能验收只要求主控 Conversation 能可靠恢复已经投递的消息事实，
  不承诺未读角标、全局待处理提示或任何具体提醒体验。

## 七、主控消息投递与运行结果报告

### 7.1 投递以前必须先建立代理关系

- 主控可以查询可作为目标的普通 Session，并按稳定 Session 身份选择目标；标题只用于展示，
  不能作为路由主键。
- 主控只能向已经进入主控代理模式、且明确绑定当前主控的 Session 投递文本工作消息。
- 目标处于普通模式时，主控必须先执行独立的代理切换；用户直接要求主控向该 Session 下发任务时，
  主控可以在同一个用户来源 Run 中先可靠开启代理，再执行消息投递。
- 代理切换和消息投递必须是两个可观察、可分别失败的业务动作，不能让投递命令在目标仍为普通
  模式时隐式修改代理状态。
- Runtime 在接受消息时再次核验代理归属；目标仍为普通模式、已绑定其他主控或并发退出代理时，
  稳定拒绝该次工作消息。
- 代理状态已经开启但目标仍有 queued Input 时，主控投递暂不执行并返回可解释结果；不插队、
  不改变代理状态，也不保存延迟投递任务。
- 投递必须先形成持久化事实，再进入目标 Session 的串行队列；重复请求不能重复追加消息或执行。
- 目标归档、不可恢复、故障或其他无法接受输入的状态应返回稳定结果，不静默丢弃。

### 7.2 来源可见且不可伪装用户

- 目标 Session 中的投递必须明确显示“来自主控会话”，不能伪装为用户在该 Session 直接输入。
- 模型必须能理解这是一条由主控代表用户转达的任务，但来源编码不能破坏 Provider 协议正确性。
- 主控收到的代理报告必须明确显示来源 Session、来源 Run 和实际终态。
- 用户重连后能从持久快照重建消息来源和报告来源，不能只依赖实时事件或客户端临时映射。

### 7.3 Run 结束时按当前代理状态报告

- Runtime 不在主控投递、目标 Input 和目标 Run 之间保存独立的回复关联状态。
- 任意父 Run 可靠结束时，Runtime 读取该 Session 当下的代理状态和结算后的输入队列；只有代理
  仍生效且已经没有 queued Input，才使用本次最终 Assistant 回复和稳定 Run/Goal 终态形成一条报告。
- 代理开启时已有队列，队列中的 Run 继续按原顺序执行；中间 Run 不报告，最后一项结算并使队列
  排空时只报告这次最新结果，不追溯补发前面的 Run。
- Run 执行中途开启代理且没有后续队列时，该 Run 在结束时可以报告；执行中途关闭代理时不报告。
- 模型执行失败、取消或中断时，如果结束时代理仍生效，使用稳定、脱敏的失败事实形成报告；
  不复制 reasoning、工具详情或原始 Provider 错误。
- 报告只需关联来源 Session 和来源 Run/Goal，并投递给当前绑定主控。后续技术方案应优先复用
  Session 代理状态、现有 Run 结算、幂等和 Session 队列，不为本版本增加消息—Input—Run 回复链、
  通用消息总线、复杂投递状态机、可插拔 Endpoint 或 Delivery Receipt 体系。

### 7.4 主控处理代理报告

- 代理报告作为有来源的 Runtime 输入进入主控自己的串行队列，并能唤醒一次主控 Run。
- 主控负责把目标结果组织成面向用户的 Assistant 回复。
- 处理代理报告的主控 Run 不开放向其他 Session 再次投递或切换代理的能力；主控只能汇报结果、
  说明缺少的信息或询问用户下一步。
- 用户随后直接向主控给出新指令时，新的用户 Run 才能再次使用跨会话投递和代理切换能力。

该限制是 v0.20.0 防止跨 Session 自动循环的产品边界，不预先决定未来是否引入有预算、轮次和
完成条件的自主编排。

## 八、主控代理模式

### 8.1 显式开启与关闭

- 普通 Session 默认处于普通模式。
- 用户可以在目标 Session 的显式入口开启或关闭主控代理。
- 用户也可以直接向主控要求开启或关闭某个 Session 的代理状态；只有来源为用户直接消息的
  主控 Run 才能执行该变化，处理代理报告的 Runtime Run 不能自行改变代理状态。
- 代理切换与普通文本投递是两个独立意图。发送一条消息不能静默开启代理；关闭代理后，主控必须
  再次可靠开启代理，才能投递新的工作消息。
- 代理状态切换不以输入队列为空为前提；有队列时也立即可靠切换，不增加“待生效代理”状态。
  Queue 只参与投递与报告的执行决策，不决定代理状态能否变更。
- 开启和关闭必须先可靠持久化，再更新 Desktop；重试不能反复切换或产生重复报告。

### 8.2 代理报告范围

代理模式只增加有界结果报告，不同步完整历史：

- 父 Run 可靠到达完成、失败、取消或中断终态时，可以形成最新 Run 报告；
- 存在 Goal 时，Goal 的完成、暂停、阻塞或预算终止等稳定结果可以随报告表达；
- 报告包含来源 Session、来源 Run、可选 Goal、稳定状态、最终 Assistant 回复和脱敏错误摘要；
- 不额外调用模型生成跨会话摘要，目标的最终 Assistant 回复就是本版本的主要报告正文；
- 不传输完整 Conversation、Context Summary、reasoning、工具调用、子 Agent 中间过程、附件正文
  或 Workspace 文件；
- 不报告 started、模型 step、普通进度和 token delta；
- 不报告等待审批。Run 卡在审批时保持原状，由用户通过既有审批入口处理；审批完成后继续执行，
  只在最终可靠结束时报告。

报告进入主控后，主控可以向用户汇报或询问，但不能未经用户新指令继续控制目标 Session。

### 8.3 用户直接接管

用户在代理 Session 中直接提交普通消息时，Runtime 必须把“退出代理”和“接受用户输入”作为
一个不可被主控新投递插入的业务边界：

- 先关闭代理，再接受本次用户输入；即使活动 Run 使本次输入只能进入队列，也按同一规则接管；
- 从代理关闭生效后，不再为任何尚未结束的 Run 产生代理报告；
- 尚未开始的主控排队指令不再执行；
- 不向主控额外发送“用户已接管”或“排队指令已取消”的消息；
- 已经活动的 Run 不因普通发送动作被静默取消，用户需要时继续使用现有停止入口；如果该 Run
  结束时已经是普通模式，就不向主控报告；
- 主控不能在普通模式下继续投递工作消息；用户直接要求后，主控可以重新开启代理并再投递。

手动 `/compact` 是上下文控制命令，不是普通 UserMessage，因此不会自动退出代理。普通 Session
执行 `clear` 后进入普通模式；主控自身 clear 不影响其角色和其他 Session 的代理绑定。

## 九、会话 Clear

### 9.1 用户目标

用户希望保留同一个 Session、Workspace 和已配置环境，但删除旧对话影响并按当前全局与
Workspace 来源重新开始。Clear 不是归档、删除 Session 或历史重新输入，也不是用一条空消息
覆盖列表。

Clear 对历史消息采用直接删除语义，不把旧 Conversation 隐藏为可恢复 generation，也不提供
撤销或历史回看。新的空 generation 只用于保证权威状态原子切换，不代表 Runtime 继续保留一份
可访问的旧会话正文。

Clear 完成后：

- 当前规范 Conversation 为空；
- 旧消息不再参与模型上下文、Conversation Recall、当前会话导出和产品历史分页；
- 当前会话不再持有依赖旧 Conversation 的 Goal、WorkPlan 和激活状态；
- System Context 使用执行 clear 时的当前来源重新构建；
- Session ID 和明确保留的设置、资源继续可用。

### 9.2 空闲门禁与确认

- Clear 只允许对 active 且完全空闲的 Session 执行。
- 存在活动 Run、活动子 Agent、待审批、未完成 Goal Run 或排队输入时拒绝 clear；不自动停止、
  批准、取消或清空这些工作。
- 用户必须先通过现有入口停止或处理相关状态，再重新发起 clear。
- Clear 属于不可撤销的产品历史清除，Desktop 执行前必须明确说明影响并取得二次确认。
- 客户端确认不能替代 Runtime 再次核验空闲状态；确认后状态变化时应稳定拒绝，而不是扩大清理范围。

### 9.3 清除与保留范围

Clear 清除：

- 当前 Conversation 中的 User、Assistant、Tool、Context Summary 和 Runtime 隐藏消息；
- 当前会话产品历史中的 Input、Run、Child Task 关联及其正文投影；
- Conversation Recall、消息反馈、工具图片引用等只服务旧历史的派生投影；
- Goal、WorkPlan、held input 和当前 Conversation 中的 Skill 激活状态；
- 自动生成且只来源于旧对话的标题内容，下一次普通用户输入可以重新生成标题。

Clear 保留：

- Session ID、创建关系和 active 生命周期；
- 用户手动设置的会话标题；
- Workspace 绑定；
- 当前模型、reasoning effort、Agent 变体和审批模式；
- Session 与 Workspace 权限文件及其正常作用域；
- 已上传的附件资源和 Session 私有目录内容；
- 主控会话的角色，以及其他 Session 指向该主控的代理绑定；
- 配置文件、Pinned Memory、Persona 和 Workspace 文件本身。

Clear 成功后，当前 Runtime Home 中承载旧 Conversation 的正文文件和派生检索内容必须进入确定的
删除与恢复闭环，不能只从 Session 指针移除后无限期保留为旧 generation。Clear 不承诺清理备份、
Full Trace、外部日志或操作系统可恢复残留，也不承诺存储介质级安全擦除。具体跨 SQLite/JSONL
提交、物理清理、失败重试和启动恢复策略由技术方案明确，但产品查询、Recall、导出和后续模型
上下文不得再暴露已 clear 的旧 Conversation。

### 9.4 重建 System Context

- Clear 必须重新经过正式 Session Environment/System Context 构建入口，读取执行时当前有效的
  Persona、Pinned Memory、根 `AGENTS.md`、Workspace 环境、Session 稳定目录与 Skills 来源。
- Clear 形成新的冻结 System Prompt Snapshot，并重新建立当前 Session 的冻结 Skills Catalog；
  后续普通 Run 使用新快照，不能继续混用旧快照。
- Workspace 绑定和 Session 私有目录身份保持不变，不通过创建另一个 Session 再偷偷替换 ID。
- 新 System Context 必须先成功生成并校验，再原子切换权威状态并删除旧 Conversation；不能先原地
  删除历史，再尝试构建新上下文。构建失败时保持原 Conversation、System Context、Goal/WorkPlan
  和产品投影不变。
- Clear 成功后发布统一失效事实，使分页缓存、上下文用量、Recall、Goal/WorkPlan、技能和运行投影
  一起重建，Desktop 不能局部清空列表后保留旧权威状态。

## 十、用户主动 `/compact`

### 10.1 命令识别

- Composer 中 trim 后完整内容精确等于 `/compact` 时，识别为 Runtime 上下文控制命令。
- `/compact` 不作为 UserMessage 写入 Conversation，不创建普通 Input 或业务 Run，也不触发
  Goal 创建、恢复或 continuation。
- `/compact` 与其他正文、附件、Goal 或 Skill 草稿组合时不执行；Desktop 应阻止含混提交并保留
  用户草稿，而不是截掉其他内容后悄悄压缩。
- 未来智能终端或 IM 可以把同一意图映射到正式命令；本版本不把斜杠文本本身定义成外部渠道协议。

### 10.2 执行门禁

- 主动 compact 只允许 active 且完全空闲、Conversation 已加载并且没有 pending Tool Exchange
  的父 Session。
- 活动 Run、子 Agent、审批、Goal continuation 或队列存在时直接拒绝 `/compact`，不排队，
  也不在任务结束后自动补做。
- 拒绝只返回稳定、可操作的原因，不把 `/compact` 当普通消息继续发送给模型。
- 用户处理完活动状态后可以重新发起命令。

### 10.3 压缩语义

- 主动 compact 复用现有 Runtime `agent-context` 滚动摘要策略、当前 Session 模型和冻结的
  System Prompt Snapshot。
- 生成候选成功后使用现有 generation replacement 语义：较早完整消息退出当前规范
  Conversation，以 Context Summary 和策略保留的近期轮次组成新的当前 generation。
- 被替换的较早完整消息退出当前 Conversation Recall、产品历史分页和导出；本版本不建立
  只供 UI 浏览的第二份完整转录。
- Desktop 收到压缩后的新 generation 时，不清空当前已经加载的消息列表；它以新 generation 中
  已有的 Context Summary 作为分割项，去重仍保留的近期消息后插入原列表。这只是当前展示列表的
  连续更新，不产生新的持久化历史或上下文实体。
- 主动 compact 不刷新 Persona、Pinned Memory、`AGENTS.md`、Workspace 环境或 Skills Catalog；
  这些只有创建 Session 或明确 clear 时重新冻结。
- 主动 compact 不计入单次 Run 的自动 compaction 次数，也不会在完成后继续先前任务。
- 无可压缩历史时返回成功的 no-op 结果“当前无需压缩”，不生成空摘要、不切换 generation。
- 模型、校验或持久化失败时保持旧 generation 为权威，不显示伪成功或只修改 Desktop 列表。

### 10.4 产品反馈

- Session 显式投影“正在压缩上下文”状态；现有自动压缩与用户手动
  `/compact` 共用同一开始/结束状态口径，不再由 Desktop 根据 Run 或请求 future 自行猜测。
- 该状态只是 Runtime 内存运行态，不持久化；Runtime 崩溃或重启后不恢复为“压缩中”，
  Desktop 从新快照清除旧提示。
- 手动压缩允许用户取消尚未提交 replacement 的模型请求；自动压缩仍由当前
  Run 恢复流程管理，本版本不额外开放取消入口。
- Desktop 复用 Composer 现有发送/终止主按钮取消手动压缩，不在压缩状态条增加第二个取消按钮。
- 成功后在最后一条被压缩的历史消息与近期轮次之间展示压缩边界，并更新最新上下文用量。
- 边界文字可点击展开或收起当前 Context Summary 正文；默认收起。摘要是模型上下文说明，不替代
  上方仍可阅读的原消息，也不能编辑或恢复为当前上下文。
- `/compact` 不改变普通/代理模式，也不产生主控代理报告。

## 十一、可靠性、并发与恢复

### 11.1 同 Session 串行

- 主控消息、普通用户输入、代理切换、clear 和 compact 都是 Runtime 业务意图，必须经过同一
  Session 权威状态和 mutation 边界协调。
- 不同 Session 仍可并发；主控忙碌时收到多个代理报告，按可靠接受顺序进入主控队列。
- 用户直接接管与主控并发投递必须由 Runtime 原子决定先后；Desktop 事件到达顺序不能成为事实源。

### 11.2 幂等与来源关联

- 消息投递、clear 和 compact 需要稳定幂等请求身份；网络重试不能重复执行模型调用、
  重复 clear、重复切换 generation 或重复形成代理报告。代理切换提交明确开/关终态，
  相同终态重复设置为 no-op；传输结果不明时先重读权威状态，不为它单独维护 revision 计数器。
- 代理报告必须精确绑定来源 Session 和 Run/Goal；主控不能按文本相似度猜测来源。
- 普通 Session 不能把任意历史 Assistant Message 重新包装为一条新的代理报告。

### 11.3 重启恢复

- 主控角色、主控稳定检索顺序、普通 Session 的代理归属和已经可靠接受的跨会话消息必须恢复。
- 沿用现有 Runtime 安全边界：重启后不因为发现未完成工作就静默访问 Provider 或重放工具副作用。
- 已可靠形成但尚未消费的代理报告继续保留；同一事实不能在每次启动后重复投递。
- clear 或 compact 在权威 generation 切换前中断时保留旧状态；切换后中断时以新状态恢复，不能拼接
  两个 generation 或混用新 System Context 与旧 Conversation。

## 十二、未来智能终端与 IM 的扩展边界

本版本只实现 Desktop 用户、主控 Session 和普通 Session 之间的产品内通信，但消息事实至少要能
稳定表达：

- 唯一消息身份；
- 来源类型与来源身份；
- 目标类型与目标身份；
- 可选的来源 Run/Goal 身份；
- 接受时间、投递状态和幂等身份；
- 对用户和模型可解释的来源归属。

这些是当前产品正确性所需事实，不代表已经确认通用 Endpoint、Channel、Thread、Delivery Router
或插件接口。未来外部渠道应优先接入主控，由主控与明确的内部 Session 通信；普通 Session 不需要
理解消息来自 Desktop、智能终端还是 IM。

通知能力本版本暂不设计。功能设计不得把未读角标、系统通知、外部推送或回复到原渠道写成已确认
承诺；这些由后续渠道与通知版本统一确定。

## 十三、模块职责与契约影响

### 13.1 Assistant Runtime

Runtime 持有：

- Session 角色、主控软性单例产品规则和稳定选择；
- 普通 Session 的代理归属与切换；
- 跨会话投递、代理报告、幂等、队列和恢复；
- 哪类主控 Run 可以使用跨会话能力，防止自动报告触发无限控制链；
- clear 的空闲门禁、范围、System Context 重建和统一状态失效；
- 手动 compact 的门禁、取消、generation replacement 和结果投影。

这些业务事实不能下推给 Desktop，也不能进入 Agent Core 的 Session/Run 所有权。

### 13.2 Assistant Protocol

协议需要表达用户意图和只读产品事实，包括但不限于：

- Session 角色和代理状态；
- 主控可查询的目标摘要；
- 有来源的投递和代理报告；
- clear/compact 命令、稳定错误和结果；
- clear/compact 后统一快照失效与恢复所需信息。

协议只承载跨层契约，不依赖具体数据库表、JSONL 路径或 Desktop 组件。

### 13.3 Runtime Host 与存储

Host 继续作为传输和基础设施适配层：

- 实现 Runtime 业务端口要求的可靠存储与 System Context 环境构建；
- 保证跨会话投递、代理状态、clear 和 compact 的事务/恢复语义；
- 管理 JSONL generation、SQLite 结构化关系、派生 Recall 和物理清理；
- 不持有第二份主控选择、代理状态或会话调度权威事实。

具体 schema、迁移、备份与回滚方案必须在技术方案中基于现有 SQLite/JSONL 实现核查后确定。

### 13.4 Desktop

Desktop 只负责：

- 展示主控身份、普通/代理状态、来源和关联；
- 发送创建/投递/代理切换/clear/compact 等用户意图；
- clear 二次确认和 busy/no-op/失败反馈；
- 区分 Runtime 自动队列中正在交给 Run driver 的队首与真正等待处理的输入，避免把前者短暂展示为
  “待发送”或“待执行”；
- 在快照失效后重新查询权威状态。

Desktop 不自行选择主控、不伪造跨会话消息、不根据列表是否为空推断 clear 成功，也不把
`/compact` 作为普通消息先落入本地列表。该队列呈现修复不能通过固定延迟、最短展示时长或
忽略 Runtime 快照实现；运行、暂停、Goal 暂存或真正排队的输入仍必须正常展示。

## 十四、关键取舍

1. **保留主控代理，不做完整托管**：完整历史仍由目标 Session 持有，主控只接收有界结果，避免
   多会话摘要漂移和主控上下文膨胀。
2. **产品单例、存储不唯一**：本版本交互简单，但不以数据库唯一约束封死未来多主控；当前使用
   稳定检索到的第一条。
3. **投递必须以代理关系为前提**：普通模式只允许显式切换代理；主控必须先可靠开启代理，才能
   投递工作消息。
4. **报告 Run/Goal 结果，不报告审批**：审批继续由用户在既有入口处理，主控不形成第二套审批面。
5. **自动报告不触发自主继续控制**：主控必须等待用户新指令，先建立有界、可回证的通信闭环。
6. **直接输入意味着用户接管**：退出代理并静默丢弃未执行主控队列，不打扰主控，也不静默取消
   已经活动的副作用执行。
7. **Clear 是同 Session 新纪元**：保留身份、环境设置、附件和私有目录，清空产品历史并按当前来源
   重建 System Context。
8. **Manual Compact 只是现有能力入口**：沿用 generation replacement，不建立双份历史；忙碌时
   直接拒绝，不排队。
9. **通知暂不设计**：先形成可靠消息事实，不用尚未确定的通知体验扩大本版本。
10. **报告按 Run 结束时的代理状态决定**：不冻结消息—Input—Run 回复关系，优先复用 Session
    代理状态和现有 Run 结算，不预建通用消息基础设施。

## 十五、验收标准

### 15.1 主控会话

- [ ] 无主控的既有 Runtime Home 启动后自动创建主控；重启后不重复创建。
- [ ] 产品入口并发创建时仍只产生一个当前使用的主控；存储不依赖数据库唯一约束。
- [ ] 存在多条主控记录时，Runtime 按稳定顺序使用第一条，不删除其他记录。
- [ ] Desktop 能稳定识别主控，不按标题或位置猜测；主控不能通过产品入口归档、删除或 Fork。

### 15.2 消息与代理

- [ ] 普通模式拒绝主控工作消息；主控可先显式开启代理，再向绑定自己的目标 Session 投递文本。
- [ ] 目标 Conversation 明确展示消息来自主控，主控明确展示报告来自哪个 Session 和 Run。
- [ ] 普通模式不接收主控工作消息，也不主动报告 Run/Goal；代理关系生效后才形成投递和报告。
- [ ] 用户能在目标 Session 或通过用户直接发给主控的指令开启、关闭代理。
- [ ] 存在 queued Input 时仍可立即开启或关闭代理；代理状态与 Queue 相互独立，不增加待生效状态。
- [ ] 代理开启但 Queue 未排空时不接受主控投递、不生成中间报告；最后一项使 Queue 排空后只报告
  最新 Run/Goal 结果，不追溯补发前序结果。
- [ ] 代理模式只报告稳定 Run/Goal 结果，不传完整历史、实时步骤或审批。
- [ ] 主控处理代理报告时不能继续投递或切换代理，只能回复/询问用户。
- [ ] 用户直接在代理 Session 发送消息后退出代理，未执行的主控排队指令不再执行且不向主控
  发送取消报告；活动 Run 可正常收敛，但结束时为普通模式则不报告。
- [ ] Run 中途开启代理后可以在结束时报告，中途关闭代理后不报告，不需要消息到 Run 的独立
  回复关联状态。
- [ ] 重启和断线恢复后，代理状态、消息来源、报告来源和未消费结果保持一致。

### 15.3 Clear

- [ ] Clear 只允许完全空闲的 active Session，busy 状态稳定拒绝且不产生部分清理。
- [ ] Desktop 在 clear 前取得明确二次确认，Runtime 在提交前再次核验状态。
- [ ] Clear 后当前 Conversation、Recall、导出、Goal、WorkPlan 和旧历史产品投影为空。
- [ ] Clear 不保留软删除、归档或可恢复的旧 Conversation；成功后旧消息正文进入确定的物理删除与
  恢复闭环，而不是只切换 Session 指针后无限期遗留。
- [ ] Clear 保留 Session ID、用户标题、Workspace、模型/effort/变体/审批、权限、附件和私有目录。
- [ ] Clear 使用当前 Persona、Pinned Memory、`AGENTS.md`、Workspace 环境和 Skills 来源重建并冻结
  新 System Context；准备失败时旧状态完整保留。
- [ ] 普通 Session clear 后退出代理；主控 clear 后仍保持主控角色和既有代理绑定。
- [ ] clear 重试、进程中断和重启不会出现新旧 System Context/Conversation 混合。

### 15.4 Manual Compact

- [ ] 精确 `/compact` 作为 Runtime 命令执行，不进入 UserMessage，不创建业务 Run 或自动续跑。
- [ ] `/compact` 与正文、附件、Goal 或 Skill 草稿组合时不执行且不丢失草稿。
- [ ] busy Session 直接拒绝 `/compact`，不排队；空闲后可重新提交。
- [ ] 有可压缩历史时沿用现有滚动摘要与 generation replacement，保留 Context Summary 和近期轮次。
- [ ] 较早完整消息退出当前规范 Conversation、Recall 和导出，不产生第二份持久产品历史；
  压缩发生时 Desktop 已加载的消息列表不闪退或清空。
- [ ] 压缩边界位于旧消息与近期轮次之间，默认收起，点击可查看或收起当前摘要正文。
- [ ] 无可压缩历史时返回成功 no-op；失败或取消时旧 generation 保持权威。
- [ ] `/compact` 不刷新 System Context、不改变代理状态、不产生主控报告，完成后给出可解释反馈。
- [ ] 自动与手动 parent compaction 共用 Session 级“压缩中”投影和开始/结束事件；
  该投影不入库，断线或重启后从 Runtime 当前快照重建，手动可取消而自动不新增取消入口。

### 15.5 Composer 队列呈现

- [ ] Session 空闲、Queue 为 automatic 且队首可立即交给 Run driver 时，发送成功后不显示
  一闪而过的待发送/待执行区域。
- [ ] 存在 active Run、Queue 暂停或等待恢复、Goal 暂存时，真实等待输入仍完整显示并可操作。
- [ ] automatic Queue 在无 active Run 的交接窗口包含多条 Input 时，只隐藏正在交接的队首，
  后续真正等待的 Input 继续显示。
- [ ] 修复不依赖 debounce、动画延迟或本地伪造队列状态；重连和事件 gap 后仍从权威
  SessionView 得到一致呈现。

### 15.6 架构与边界

- [ ] 不同 Session 继续并发，同一 Session 的投递、用户输入、代理切换、clear 和 compact 可靠串行。
- [ ] 目标 Session 继续使用自己的模型、Workspace、变体、权限和审批，主控不能扩权或代批。
- [ ] 正式 Host/Runtime、Desktop 重连和隔离真实模型验收覆盖完整闭环；不以 Harness 私有命令
  或客户端临时状态代替产品契约。
- [ ] 本版本没有引入系统通知、真实外部渠道、复杂任务编排或数据库主控唯一约束。

## 十六、风险、兼容性与后续设计

### 16.1 主要风险

- **消息循环**：主控报告 Run 若仍可投递，会形成跨 Session 无界循环；必须按输入来源冻结能力。
- **接管竞态**：用户退出代理与主控投递并发时，若只在 Desktop 切开关，会执行用户以为已取消的任务。
- **上下文泄漏**：代理报告若复制完整历史、工具详情或附件，会突破“有界结果”边界。
- **Clear 部分成功**：正文、结构化状态、System Context 和派生索引跨介质更新，必须避免只清一半。
- **Compact 误投递**：斜杠命令若先当 UserMessage 接受再识别，会污染 Conversation 并触发错误 Run。
- **冻结语义变化**：clear 是现有 System Context 只在 Session 创建时冻结规则的首个显式例外，
  必须保证只有用户确认的 clear 能触发刷新。
- **多主控脏数据**：存储允许多个但产品只使用第一条，排序与诊断必须确定，不能随查询计划漂移。

### 16.2 兼容性

- 既有 Session 默认保持普通模式，不因升级自动进入代理。
- 既有 Conversation、Goal、WorkPlan、Skills Catalog 和冻结 System Context 按原样恢复；只有用户
  明确 clear 才重建。
- 自动 compaction 的触发、摘要算法和 continuation 行为保持不变；本版本只将其
  观察状态与新增的用户 `/compact` 统一。
- 主控自动创建不改变普通 Session 的 Workspace、模型或列表身份。
- 旧客户端不认识新增角色和命令时必须由协议版本/能力检测稳定拒绝写操作，不得把 controller
  消息或 `/compact` 降级为普通 UserMessage。
