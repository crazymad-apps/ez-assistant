### M3 Queue 排空报告与崩溃恢复

- 目标：源 Run 可靠结算时按当前代理状态和结算后 Queue 决定是否向主控原子接受报告

- 状态：✅ 已完成
- 实际结果：ProxyReport 作为 `StoredRunSettlement` 可选 effect，与源 Run/Goal 结算在同一 Host
  事务中接受到 Controller；报告正文由确定性有界模板形成，只含稳定终态、最终 Text、脱敏错误
  和可选 Goal 摘要。Queue 中间 Run 不缓存或补发，最后一项才报告；报告 Run 的主控工具贡献为空。
  Store 提交后先投影源 Session，再释放源 mutation gate 并投影/唤醒 Controller。Host 异常恢复只
  返回待中断父 Run，由 Runtime 用同一门禁和模板提交 Interrupted settlement/report 后再发布 registry。
  统一审核期间进一步抽取 `AcceptedInput` 的 Session lane 投影，普通/Goal 用户输入、主控投递、
  代理报告和 Goal continuation 复用同一 Run/Input/Skill/lane 投影；承载所有无 Goal binding 输入的

## 本地决策与提醒

- 产品层软性限制一个主控，存储和领域不增加唯一限制；当前稳定检索第一条。
- 普通模式不接收主控工作消息；主控必须先开启代理才能投递，Run 结束时按当下代理状态决定报告。
- 主控处理自动报告时不得自主继续控制，必须等待用户新指令。
- 用户直接输入退出代理，未执行主控排队指令静默取消；主控后续必须按用户要求重开代理才能投递。
- Clear 保留附件和 Session 私有目录，只允许空闲 Session，并重建 System Context。
- `/compact` 沿用 generation replacement，busy 时拒绝、不排队；通知能力本版本暂不设计。
- 不保存消息—Input—Run 回复关联；技术方案优先复用 Session 代理状态、Run 结算、幂等和队列，
  不预建通用消息总线或复杂投递状态机。
- 每个 Run 通过统一工具装配流水线生成冻结 ToolSet；既有冻结 ToolSet（内部包含 Host 基础工具
  与 Runtime 已有工具）和主控工具是平行装配环节，
  最后按 ToolName 去重并校验冲突，为后续 Goal、Session 或插件工具注入保留扩展口。
