# v0.20.0 技术方案：主控会话、代理通信与会话上下文操作

## 一、方案信息

- 版本：`v0.20.0`
- 状态：已确认（2026-08-26）
- 关联设计：[`v0.20.0 功能设计`](功能设计.md)
- 实现基线：2026-08-25 当前源码、
  `cargo metadata --no-deps --format-version 1` 及现有 Workspace 依赖关系
- 影响模块：`assistant-runtime`、`assistant-protocol`、Runtime Host、Desktop；
  手动压缩直接复用 `agent-context` 现有滚动摘要策略，不修改其公共算法；
  `agent-core` 不增加 Session 或主控概念
- 依赖结论：不新增 crate，不新增第三方依赖，不改变 Desktop/Runtime
  双进程拓扑

本文只固定实现边界、权威状态、原子操作和恢复策略。主控入口、代理开关、
来源消息、clear 确认和 `/compact` 状态的具体布局，由
[`v0.20.0 界面交互设计指导`](界面交互设计指导.md) 单独确定。

## 二、源码现状与可复用基线

### 2.1 Session、Input 与 Run

- `SessionController` 已持有 Session `mutation_gate`、队列、Run、Goal、WorkPlan、
  Conversation Journal 和持久化消息数。代理切换、用户接管、Run 结算和上下文
  操作可以在这一既有临界区上排定先后，无需新建 Session actor 或常驻线程。
- `RuntimeStore::accept_input` 已能在一个 SQLite 事务中提交 Input、首次 Accepted
  Run、queued `UserMessage`、Goal 与 Skill Activation；主控投递和代理报告应复用
  这条可靠队列，不建第二套消息队列。
- `InputOrigin` 现为 `User | Runtime`，`UserMessageOrigin` 与
  `TranscriptVisibility` 已正交分离。本方案保留这两个 origin wire 值，使用新的
  结构化跨会话 binding 区分主控投递与代理报告，避免为 `inputs.origin`
  的旧 SQLite `CHECK` 重建整表。
- Session 的 System Prompt、Skill Catalog 和 Environment 当前是
  `SessionController` 的不可变字段。`clear` 是首个允许在原 Session ID 上重新冻结
  这三项的显式操作，因此需将它们收口为一份可原子替换的执行上下文快照。

### 2.2 Run 结算与现有工具装配

- `run/settlement.rs` 已在取得 Session mutation gate 后构造最终 Assistant 消息、
  稳定 Run 终态和可选 Goal effect，再调用单个 `RuntimeStore::settle_run`。
- Host 的 `AppendPurpose::RunSettlement` 和 `apply_run_settlement` 已能在一个
  Immediate transaction 中结算 Run、转换 Goal 并创建 continuation Input/Run。
  代理报告可作为该结算 effect 中另一条可选 `NewStoredInput`，与源 Run 终态
  同事务可靠接受。
- 当前 `compile_run_agent` 会把 `load_skill`、`update_plan`、`update_goal` 和
  `delegate_task` 逐项追加到 Host 返回的工具快照；v0.20.0 将这段既有逻辑收口为
  “既有冻结 ToolSet”装配环节，主控跨会话工具作为与其平行的新装配环节，
  不改 Agent Core Tool SPI。

### 2.3 SQLite/JSONL 与压缩

- 正式 Host 由单一阻塞 worker 独占 SQLite 连接与 Session JSONL。新跨会话事务
  仍由这个 worker 串行实现，不需要数据库分布式事务或远程 Broker。
- `ContextReplacementTarget` 当前只支持正在运行的 parent Run 和 child task；
  Host 会写入新 generation、事务切换 SQLite 指针，再 best-effort 删除旧文件。
- `RuntimeContextCompactor::for_parent` 使用保留最近一个 User Turn 的滚动摘要，
  但自动 overflow 路径还有“压缩当前活动 Turn”的 fallback。手动 compact 只复用
  前一策略；没有可压缩 head 时返回 no-op，不使用活动 Turn fallback。
- 现有 generation replacement 对旧文件仅作 best-effort 清理，足以支撑 compact，
  但不满足 clear 已确认的“直接删除并形成恢复闭环”。clear 必须增加有界、
  不保存消息正文的清理回执。

### 2.4 Desktop 与公共协议

- Desktop Composer 已在发送前识别 `/goal`、`/skill`、`/new` 等命令，
  且所有正式业务变更都经 `RuntimeClient.command`。`/compact` 应在上传附件与
  `submit_input` 之前转为独立 Command。
- `SessionSummary`、`SessionViewSnapshot`、`UserMessageSnapshot` 和 Runtime invalidation
  事件已是 Desktop 的重建基线。新角色、代理、消息来源和上下文操作都在
  这些稳定 DTO 上增量投影，Desktop 不保存第二份权威状态。
- 当前所有 Input 接受时都会先持久化为 queued；`submitInput` 返回后又立即执行
  `loadSession`，可能读到 automatic Queue 已包含新 Input、但 Run driver 尚未把它提交为
  active Run 的短暂交接窗口。`QueueDrawer` 直接渲染全部 `queue.items`，因此空闲会话发送消息时
  偶发出现待发送区闪现。这是 Desktop 呈现语义问题，不改变 Runtime durable inbox 设计。

## 三、总体方案与不变量

```text
Desktop 用户意图
        │
        ▼
assistant-protocol
角色 / 代理快照 / 来源投影 / clear / compact
        │
        ▼
assistant-runtime
SessionController + Run 工具装配流水线 + Run settlement
        │
        ▼
Runtime Host Store
SQLite 结构事实 + Session JSONL generation + 清理恢复
```

实现必须保持以下不变量：

1. Session 角色和代理归属是 Runtime/Store 权威事实，不从标题、列表位置、
   Conversation 文本或 Desktop 开关反推。
2. 代理状态是普通 Session 上的 `Option<ControllerSessionId>`，不是全局布尔值；
   数据结构可表达多个 Controller，当前产品只选稳定排序第一条。
3. 普通模式不接收主控工作消息。投递和开启代理是两个独立 Store 操作；
   一个用户来源的主控 Run 可以先调切换工具，再调投递工具。
4. 没有消息—Input—Run 回复关联。源 Session 的父 Run 在可靠结算时读取当前代理快照和
   结算后的 Queue；代理开启且没有 queued Input 时才附带一条最新报告，当时关闭或 Queue
   尚未排空时不附带，也不追溯补发。
5. 代理报告是主控 Session 的可靠 Runtime Input，不是 SSE 通知。报告只包含
   源 Session/Run/可选 Goal、稳定终态、最终 Assistant 文本或脱敏错误。
6. 每个 Run 的工具集统一经过装配流水线生成；现有冻结预设 ToolSet 与主控工具是
   平行装配环节。主控环节只对“Controller Session + 当前 Input 是真实用户输入”
   的父 Run 贡献工具，代理报告触发的主控 Run 不经过该环节。
7. 用户直接输入的接管、主控投递和代理切换共用目标 Session mutation gate
   及 Store 业务操作，竞态结果不依赖 Desktop 事件顺序。
8. `clear` 先准备新执行上下文，后切换空 generation 并删除旧结构事实；
   旧正文不成为软删除或可导航历史，但物理文件清理使用持久回执完成崩溃恢复。
9. 手动 compact 不是 Input/Run，不继续任务、不刷新 System Context、不改代理状态、
   不产生代理报告。
10. 本版本不增加通用 message envelope、endpoint registry、delivery receipt 状态机、
    消息总线、通用跨会话实时进度报告或主控自主编排。Session compaction 只提供有界的
    开始/结束运行态事件。

## 四、Session 角色、主控选择与执行上下文

### 4.1 Runtime 领域类型

`assistant-runtime` 增加最小领域值：

```rust
pub enum SessionRole {
    Standard,
    Controller,
}

pub struct SessionProxyState {
    pub controller_session_id: SessionId,
    pub changed_at_ms: i64,
}

pub struct SessionExecutionContext {
    pub system_prompt: SystemPromptSnapshot,
    pub skill_catalog: SessionSkillCatalog,
    pub environment: SessionExecutionEnvironment,
}
```

`SessionController` 保留稳定 `id` 和 `created_at_ms`；`role`、可选 `proxy`、可替换
`Arc<SessionExecutionContext>` 进入受 mutation gate 保护的权威状态。Run 编译时克隆
一份 `Arc` 快照，clear 只替换后续 Run 使用的快照，不修改已冻结的活动 Run。

当前 `system_prompt()`、`skill_catalog()`、`environment()` 返回长期引用的调用点
改为先获取执行上下文 `Arc`，再从同一快照读取三项，避免 clear 后混用新旧
Prompt、Catalog 和目录事实。

### 4.2 存储形状与稳定选择

`sessions` 表增量加列：

```sql
role                        TEXT NOT NULL DEFAULT 'standard'
                            CHECK (role IN ('standard', 'controller')),
proxy_controller_session_id TEXT REFERENCES sessions(session_id) ON DELETE SET NULL,
proxy_changed_at_ms         INTEGER
```

不对 `role = 'controller'` 建立 unique index。Host Store 在恢复边界验证：

- Controller Session 自身不能保存 proxy binding；
- proxy 目标必须是存在的 Controller Session，不允许自绑定；
- 旧数据全部迁移为 Standard + 无 proxy，不扫描 Conversation 或标题猜测角色。

当前主控的唯一排序键固定为：

```text
(created_at_ms ASC, session_id ASC)
```

Runtime 恢复后对所有 `role = controller` 的 Session 使用该排序，取第一条作为
当前主控。存在多条时只产生诊断投影，不删除、合并、降级或改写其他记录。

### 4.3 自动创建

`AssistantRuntime::open` 在 Store 恢复、Session registry 建立和配置加载完成后执行
`ensure_controller_session`：

1. 按上述排序检索已恢复 Controller；存在则直接选定；
2. 不存在时使用当前默认模型、未绑定 Workspace、当前 Persona/Pinned Memory、
   用户 Skills 和现有 `SessionEnvironmentFactory` 创建标题为“主控会话”的 Controller；
3. 自动创建通过与普通 Session 相同的 `NewStoredSession` 高层操作持久化，
   仅新增 `role` 事实；
4. 单 Runtime Host 内的 operation gate 让“检查 + 创建”串行。存储不使用唯一索引
   充当软性单例；
5. 如因配置无默认模型、System Context 构建或 Store 错误而失败，Runtime
   保留已恢复的普通 Session，投影 `controller_unavailable` 诊断，不创建伪主控。

成功 reload/修复配置后，若仍无 Controller，Runtime 可再执行一次同一幂等
`ensure_controller_session`；不运行定时重试任务。本版本不开放普通的“创建主控”公共命令。

### 4.4 主控产品生命周期门禁

Runtime 在既有 archive、delete、fork 入口核对 `role`：所有 Controller role Session 稳定拒绝
这三类变更。重命名、模型/effort、Plan/Build、Ask/Auto、附件、权限、Goal、WorkPlan
与普通对话仍沿用 Session 既有能力。Controller clear 保留 role，也不扫描或修改
其他 Session 指向它的 proxy binding。

## 五、Run 工具装配流水线与能力冻结

### 5.1 工具集

主控工具装配环节只对支持 Tool Call 的 Controller 用户 Run 贡献三个工具：

```text
list_managed_sessions
set_session_proxy
send_session_message
```

- `list_managed_sessions` 只返回有界的 active Standard Session 摘要：Session ID、标题、
  可选 Workspace 展示信息、当前是否绑定该 Controller、是否能接受变更。它不返回
  Conversation、附件、权限文件或工作区正文。
- `set_session_proxy` 提交目标 Session ID 和期望开/关状态。它只设置明确终态，
  不使用 toggle，也不夹带任务文本。
- `send_session_message` 提交目标 Session ID 和有界非空文本；Runtime 使用
  `(controller_session_id, controller_run_id, tool_call_id)` 派生内部幂等键，模型不提交
  任意幂等标识。

工具自身使用 Runtime 私有类型化策略放行，不写入文件/Shell 权限规则。
目标 Session 实际执行投递任务时，仍按自己冻结的变体、审批方式、Workspace、
模型和当前权限规则执行；主控工具不携带或提升目标权限。

### 5.2 统一装配流水线

`compile_run_agent` 不再直接承担所有工具的业务判断，而是向一个 crate-private 的
Run 工具装配流水线提交可信 Run Context。各装配环节彼此平行，只根据 Context 贡献
零个或多个工具，不直接修改其他环节的结果：

```text
Run Assembly Context
        │
        ├─ 既有冻结 ToolSet 装配环节（Host 基础工具 + Runtime 已有工具）
        ├─ 主控工具装配环节（本版本新增）
        └─ Goal / Session / Plugin 工具装配环节（后续按需接入）
        │
        ▼
统一合并 → 按 ToolName 去重与冲突校验 → 冻结 ToolSetSnapshot
```

装配 Context 只使用 Runtime 已确认的 Session、Input、Run、Goal、parent/child、模型能力与
配置快照事实，不读取消息正文猜测权限。装配环节可以被注册、移除或按 Context 返回空贡献；
因此未来动态注入工具只需增加或启用一个装配环节，不再向 `compile_run_agent` 追加分支。

最终合并按稳定流水线顺序执行，并以规范化 `ToolName` 去重：名称和冻结定义完全一致的重复
贡献折叠为一项；同名但定义、执行实现或授权语义不同的贡献视为装配冲突并 fail-closed，
不得静默覆盖前一环节。Agent Core 和 `agent-tools` 仍只接收最终不可变快照，不感知流水线来源。

### 5.3 主控工具装配环节

`RunAuthorizationInput` 增加当前 `StoredInput` 来源分类。主控工具装配环节只在下列可信条件
全部满足时贡献三个工具：

```text
session.role == Controller
AND input.origin == User
AND input.cross_session_binding == None
AND parent Run
```

因此：

- 用户直接发给主控的消息可以查询、切换和投递；
- 代理报告是 `Runtime + ProxyReport binding`，主控装配环节返回空贡献；
- child Agent 不继承 parent Run 的装配结果；
- Goal Runtime continuation 不会因为发生在 Controller Session 就获得跨会话工具。

流水线在 Run 创建时完成装配并冻结结果，不在执行中修改 ToolSet。工具调用入口仍依据同一
Run Context 形成的类型化授权事实复核调用，不能把“工具已出现在模型 schema 中”作为唯一
安全边界。这保证报告处理 Run 不能通过 prompt 注入取得主控能力。

未来 Goal 启用额外工具时，可增加 Goal 工具装配环节：Goal 有效时贡献工具，Goal 完成、取消、
换代或 clear 后返回空贡献，相当于后续 Run 不再取得这些工具。已开始 Run 保持自己的冻结
快照；若未来确有活动 Run 内立即撤权需求，再单独扩展 Tool Authorizer，本版本不提前设计。

v0.20.0 只建立内部装配流水线并接入既有冻结 ToolSet 和主控工具；不在本版本
冻结外部插件 ABI、通用动态注册协议、持久工具权属表或用户任意注入入口。

## 六、代理切换与并发顺序

### 6.1 显式设置，不使用 toggle

公共命令与主控工具最终都调用同一 Runtime 用例：

```rust
pub struct SessionProxyChange {
    pub target_session_id: SessionId,
    pub controller_session_id: SessionId,
    pub enabled: bool,
    pub changed_at_ms: i64,
}
```

该用例只接受期望终态，不接受“翻转当前状态”，避免重试将已成功的开启再关闭。
完整流程为：

1. 验证发起方是 Desktop 目标 Session 显式操作，或具有冻结主控工具的用户 Run；
2. 取目标 Session mutation gate，验证 active、healthy、Standard；切换不要求空闲，
   因此可与正在运行的 Run 或已有 Queue 排定顺序；
3. 验证 Controller 存在且 role 正确，当前产品还要求其为已选定的第一主控；
4. 当前 binding 已是期望终态时直接返回成功，不写 SQLite、不发布重复事件；
5. 否则在 Immediate transaction 中重新核对当前 role/binding 后写入期望 binding/空值和
   变更时间；Store 成功后才替换 Session 内存快照并发布失效事件。

本用例不读取 Queue 作为状态切换门禁，也不保存 pending proxy。Queue 只在主控投递与 Run
结算两个执行决策点读取；用户直接提交新 Input 仍走第九节原子接管。

本操作不使用 revision/CAS。Desktop 与主控工具都提交明确终态，同一 Session 的变更由
mutation gate 和 Host worker 串行，最终状态按服务端实际提交顺序确定。调用方不得在已经
观察到更新快照后盲目重放更早请求；本地 Command 传输失败时应先重读权威快照再决定是否重试。

### 6.2 Run 中途切换

Run settlement、`set_session_proxy`、主控投递和用户直接输入都取目标
Session mutation gate，因此结果只有两种确定顺序：

```text
开启代理提交 → Run 结算读到已开启 → 生成报告
Run 结算读到未开启 → 不生成报告 → 之后开启
```

以上第一行还要求本次结算 effect 应用后 Queue 已排空；若仍有 queued Input，则不生成报告并继续
执行队列，直到最后一项结算时只报告最新结果。关闭同理。Runtime 不在 Run 开始时冻结 proxy，
不在 Input 上保存“本 Run 应否回复”，也不在结束后追溯补发被 Queue 门禁跳过的 Run。

## 七、主控投递与跨会话来源

### 7.1 最小 binding，不建通用消息表

`InputOrigin` 继续保留 `User | Runtime`，`StoredInput`/`NewStoredInput` 增加：

```rust
pub enum CrossSessionInputBinding {
    ControllerDelivery {
        controller_session_id: SessionId,
        controller_run_id: RunId,
        controller_tool_call_id: ToolCallId,
    },
    ProxyReport {
        source_session_id: SessionId,
        source_run_id: RunId,
        source_goal_id: Option<GoalId>,
        source_run_status: RunStatus,
    },
}
```

SQLite `inputs` 只增加可空 `cross_session_binding_json TEXT`。这个 binding 是两类可见
Runtime Input 的来源身份，不是回复链、消息状态机或通用 channel envelope。
接受时必须交叉验证当前源 Session/Run/ToolCall 与目标；`source_run_status` 只允许稳定终态，
并与源 Run 本次结算结果在同一事务中冻结，使来源 Run 随后被 clear 后，Desktop 仍能在报告卡中
展示终态而无需解析报告正文。提交后 binding 是历史来源事实，
不对跨 Session ID 建外键。源 Session 稍后 clear/删除自己的 Run 时，已进入另一 Session
的投递/报告仍可恢复来源 ID，不因历史源 Run 已不存在而令 Runtime 启动失败。
恢复边界重新验证 binding 类型、ID 形状与本 Input/UserMessage 组合，非法组合 fail-closed。

`validate_input_message` 扩展为四种合法组合：

| 输入类型 | Input origin | Goal binding | Cross-session binding | UserMessage |
| --- | --- | --- | --- | --- |
| 真实用户 | `User` | 可选 | 无 | `origin=User`、visible、有 Text/File |
| Goal continuation | `Runtime` | 必须 | 无 | `origin=Runtime`、hidden、仅内部 Part |
| 主控投递 | `Runtime` | 无 | `ControllerDelivery` | `origin=Runtime`、visible、Text + 内部来源 Part |
| 代理报告 | `Runtime` | 无 | `ProxyReport` | `origin=Runtime`、visible、Text + 内部来源 Part |

新建的内部来源 Part 继续通过 `InternalBoundaryCoordinator` 构造，使模型明确知道
这是主控转达或 Session 报告；产品投影不解析该 Part 正文，而是直接读结构化
binding。

### 7.2 投递接受流程

`send_session_message` 在不持有 Controller Session mutation gate 的情况下调用
Runtime 跨会话用例，只取目标 Session mutation gate，避免交叉持有两个 Session 锁。

接受步骤：

1. 校验文本 trim 后非空且不超过固定上限；首版与普通文本 Input 使用同一上限，
   不支持附件、Skill、Goal mode 或主控代传权限参数；
2. 校验源 Controller Run 的能力是用户来源时已冻结的主控工具；
3. 取目标 mutation gate，校验 active、healthy、Standard，并且当前 proxy 精确绑定
   该 Controller；
4. 校验目标当前没有任何 queued Input；存在 Queue 时返回 `session_busy` 和稳定说明，
   不插队、不修改 proxy，也不保存延迟投递；
5. 使用目标 Session 当前 variant 和 approval mode 构造 `Runtime + ControllerDelivery`
   的 visible UserMessage、Input 和首次 Run；
6. Store `accept_input` 在同一事务中再次核对目标 Queue 为空，并以派生幂等键提交；
   同一 ToolCallId 重放返回首次 Input/Run，
   不再入队；
7. 成功后复用 Runtime 私有的 `AcceptedInput` 投影入口，把 Input、首次 Run、Skill ledger 与
   Session/Goal lane 一次性写入目标内存状态，再发布 Run/Queue invalidation 并唤醒既有
   queue driver；普通用户输入、主控投递、代理报告和 Goal continuation 不各自复制入队算法。

主控不能对普通模式的 Session 投递；这个准入在目标 mutation gate 内和
Store 事务中各校验一次。任务文本不会隐式修改 proxy。

### 7.3 队列与产品来源

现有 `user_inputs` lane 实际承载所有无 Goal binding 的可执行 Input，实现时重命名为
`session_inputs`，不新建 Controller 专用调度器。真实用户、主控投递和主控中的代理报告
按现有可靠 queue order 串行。Goal 存在时，它们与现有普通用户 Input 一样保持 held，
不越过 Goal controller。

`QueuedInputSnapshot` 和 `UserMessageSnapshot` 增加有默认兼容的来源投影：

```rust
pub enum ConversationInputSourceSnapshot {
    User,
    ControllerDelivery {
        controller_session_id: SessionId,
        controller_run_id: RunId,
    },
    ProxyReport {
        source_session_id: SessionId,
        source_run_id: RunId,
        source_goal_id: Option<GoalId>,
        source_run_status: RunStatus,
    },
}
```

ToolCallId 只是内部幂等与审计事实，默认不进入消息卡片。`source_run_status` 让 Desktop
显示“已完成 / 失败 / 已取消 / 已中断”，不是通用 Run 快照，也不携带实时进度。分页、重连和导出都通过
Input binding 投影来源，不按文本前缀猜测。Conversation Recall 可索引可见 Text，
但不索引隐藏的内部来源 Part。

`SessionSummary.queued_input_count` 继续表示该 Session 尚未开始的可见无 Goal Input 总数，
因此计入真实用户、ControllerDelivery 和 ProxyReport，排除 Goal continuation 等隐藏输入。

## 八、Run 结算时的代理报告

### 8.1 报告决策点

`settle_run_inner` 取得源 Session mutation gate 后，与 Goal effect 一起读取当前
`SessionProxyState`。只在下列条件满足时构造 `ProxyReport` Input：

- 源 Session 为 Standard 且当前 proxy 非空；
- 目标 Controller 仍存在，恢复事实与 role 合法；
- 源 Run 本次正在从非终态进入可靠终态；
- 本次 Run/Goal settlement effect 应用后，源 Session 不再存在任何 queued Input；
- 这不是手动 compact、clear、审批等待或 child task 终态。

决策不检查源 Input 是 User 还是 ControllerDelivery，也不检查 proxy 是否在 Run
开始前已开启。这直接落实“以结算时当前状态为准”。Queue 未排空的中间 Run 不产生报告 effect，
Runtime 不保存其候选正文，也不在后续排空时补发；最后一项只报告自身的最新结果。

### 8.2 报告正文

Runtime 使用确定性模板构造有界 Text 和内部来源 Part，不额外调用模型摘要。
字段来源固定为：

- 源 Session ID 与当前展示标题；
- 源 Run ID、`completed | failed | cancelled | interrupted` 等稳定终态；
- 可选 Goal ID、结算后 state/pause reason/budget 摘要；
- Completed 使用最终 Assistant Message 的 Text Part 合并结果；
- 失败/取消/中断使用已进入 `RuntimeErrorInfo` 的稳定代码和脱敏摘要。

不复制 Reasoning、ToolCall/ToolResult、ProviderState、原始 Provider 错误、附件正文、
child 过程、token delta 或完整 Conversation。最终文本超过报告上限时做确定性字符截断并
带 `truncated` 事实，不进行第二次 LLM 压缩。具体字符上限与普通 Input 上限在开发计划
的首个领域里程碑通过现有常量统一，不在协议中暴露数据库字节限制。

### 8.3 与源 Run 同事务接受

`StoredRunSettlement` 增加：

```rust
pub proxy_report: Option<NewStoredInput>
```

`StoredRunSettlementResult` 增加：

```rust
pub accepted_proxy_report: Option<AcceptedInput>
```

Host 将 proxy report 放入 `AppendPurpose::RunSettlement` 的可恢复 payload。有最终消息时，
现有预检事务先验证源 Run、Goal effect、结算后 Queue 为空、proxy binding 与报告 Input 形状，
然后才写 JSONL；
正式 finalize 事务同时：

1. 结算源 Run 及可选 Goal effect；
2. 以确定幂等键 `proxy-report:<source-session>:<source-run>` 向绑定 Controller
   插入 visible Runtime Input 和 Accepted Run；
3. 不写入任何“该报告是哪条主控投递的回复”关系。

若跨 Session 形状在事务内已不合法，整个结算不能伪装成“Run 已成功但报告丢失”；
该 Session fail-closed 并保留可恢复事实。正常产品路径中，Controller 不允许删除/归档，
proxy 又有外键和 Runtime 恢复校验，因此这是数据损坏门禁，不是普通业务分支。

### 8.4 内存投影与唤醒

Store 提交后先完成源 Session Run/Goal/Journal 内存投影，释放源 Session mutation gate；
再取 Controller Session mutation gate，将 Store 返回的 `AcceptedInput` 投影到主控队列、
发布 Run/Queue invalidation 并唤醒 queue driver。实现不同时持有源与目标两个 mutation gate。

若进程在 Store 提交后、内存投影前崩溃，报告 Input/Run 已是持久事实，下次
Runtime 恢复会将它重建到主控队列；不依赖 SSE 或双 Session 内存更新的时间差。

### 8.5 崩溃恢复产生的 Interrupted 报告

正常失败、取消、受控关闭产生的 Interrupted 继续走上述 `settle_run`。对于 Host 异常退出后
恢复出的非终态父 Run，也必须在把它变为 Interrupted 时按当时持久化的 proxy 状态和结算后的
Queue 决定是否生成报告：Queue 尚未排空则只中断本 Run、不报告；Queue 已空才随 settlement
接受 Interrupted 报告。不能先中断 Run、再以 best-effort 方式补发。

为避免 Host 存储层自行拼装业务消息，启动恢复把现有“直接中断非终态 Run”拆成一个有界的
Runtime/Store 协作步骤：Host 完成 append、pending exchange 等介质修复后返回待中断父 Run；
Runtime 使用与 8.2 节相同的固定模板构造 Interrupted settlement 和可选 ProxyReport；Store
再以一个 Immediate transaction 批量提交这些结算，之后才发布最终 Session registry。此步骤
不调用 Provider、不唤醒队列，也不引入逐 Run 的回复关联或投递状态表。

## 九、用户直接接管

### 9.1 接管并入用户 Input 接受事务

Desktop 仍只提交普通 `SubmitInputRequest`，不先单独发送“关闭代理”命令。Runtime
在目标 Session mutation gate 内读到 proxy 非空时，将接管 effect 与原有
`NewStoredInput` 一起交给 Store。Immediate transaction 的顺序固定为：

1. 在同一事务中将当前 proxy binding 置空；
2. 删除该 Session 中 `state = queued`、`origin = runtime`、binding 为
   `ControllerDelivery` 的 Input；其 Accepted Run 随外键级联删除；
3. 不删除 committed Input、正在活动的 Run 或普通用户队列；
4. 插入本次真实用户 Input 和首次 Run；
5. 提交后 Runtime 一次性替换 proxy 和队列投影，再发布失效事件。

该事务复用 `SubmitInputRequest.idempotency_key`：重试先返回已接受的用户 Input/Run，
不再次执行接管。若投递事务先发生，它可靠入队后会被接管事务删除；
若接管事务先发生，后续投递因 proxy 已关闭而拒绝。

### 9.2 已活动 Run 与无取消报告

用户接管不取消 `active_run`，也不解决它的 pending approval。活动 Run 稍后结算时
读到 proxy 已关闭，因此不生成报告。被删除的尚未开始 ControllerDelivery 不创建
cancelled Run 历史，也不向主控插入“已取消”、“用户接管”或其他消息。

## 十、Session Clear

### 10.1 命令门禁与上下文准备

`ClearSessionRequest` 只携带 Session ID、客户端生成的 operation ID 和当前
`body_generation`。Desktop 负责二次确认；Runtime 不接受“已确认”布尔值作为安全依据，
而是在提交前重新核对实际状态。

空闲检查在当前 `SessionController::ensure_idle` 基础上增加：

- Session active 且 healthy；
- 无 active/nonterminal parent Run、无 queued Input、无 pending Tool Exchange；
- 无 active/nonterminal child task；
- 无 pending approval；
- 无正在执行的 Session compaction（自动或手动）；
- Conversation 当前 generation 可读且与请求匹配。

Goal 或 WorkPlan 本身不是 busy，但任何由 Goal 持有的 Run/Input 会被上述门禁拒绝。
在没有执行事实时，clear 可以删除已暂停 Goal 和现有 WorkPlan。

Runtime 先在不删除任何旧事实的情况下准备新执行上下文：

1. 从 Store 一致读取当前 Persona 与 Pinned Memory；
2. 从 Workspace registry 取回原 Workspace 绑定；
3. 对同一 Session ID 重用 `SessionEnvironmentFactory::create_environment`，使 Host 重新读取
   当前 Workspace `AGENTS.md`、Persona、Pinned Memory 并生成 System Prompt；
4. 重新扫描同一 Workspace/用户四个 Skill Root，编译新 `SessionSkillCatalog`，
   并用它 augment System Prompt；
5. 校验 Factory 返回的 Workspace ID、working directory、attachment/private/tool-image
   目录与当前 Session 稳定资源身份一致；不允许 clear 借机换绑 Workspace 或目录。

任意准备步骤失败时直接返回，此时旧 Prompt、Catalog、Conversation、Goal、WorkPlan
和 proxy 均未变更。

### 10.2 高层 Store 操作

`RuntimeStore` 增加业务端口：

```rust
fn clear_session_history(
    &self,
    clear: SessionHistoryClear,
) -> StoreFuture<'_, SessionHistoryClearResult>;
```

`SessionHistoryClear` 包含 operation ID、Session ID、expected generation、新 System Prompt、
新 Skill Catalog、预期 role 和时间。它不包含旧 Conversation 正文，也不提供
可恢复旧 generation 的 API。

Host 首先在 Session 稳定目录内创建和 fsync 一个空的新 `conversation.<generation>.jsonl`，
然后开启 Immediate transaction，重新从 SQLite 核对 active/空闲/expected generation、
pending exchange、child、Run/Input 和当前 proxy binding。事务中的权威转换为：

1. `sessions` 切换到空的新 generation，写入新 System Prompt/Skill Catalog，
   `message_count = 0`；
2. 标题来源为 generated 时，Standard 重置为“New Session”，Controller 重置为“主控会话”；
   用户标题原样保留；
3. Standard Session 清空 proxy；Controller role 与其他 Session 的 binding 不改变；
4. 删除该 Session 的 Input、Run、run message refs、child tasks、Goal、WorkPlan、
   WorkPlan receipts、Skill activations、message feedback、model request records、旧上下文操作回执
   和其他仅属旧历史的结构事实；当前 clear receipt 在同一事务重新写入；
5. 重置 `session_usage`，删除该 Session 的 Conversation Recall documents/head；
6. 保留 `session_resources`、attachments/blob 引用、permissions 文件、Session private 目录、
   Workspace 绑定、模型/effort/变体/审批、pinned 和 created_at；
7. 写入一条不含正文的 clear cleanup receipt，再提交事务。

若事务失败，Host 删除尚未切换的新空文件，旧 generation 继续权威。
若事务已提交，新空 generation 是唯一权威对话，不允许因后续文件清理失败而将
SQLite 指针回退到已删除结构事实的旧 generation。

### 10.3 物理删除回执与崩溃恢复

新增的私有表只记录上下文操作与清理阶段，不保存消息文本：

```sql
CREATE TABLE session_history_operations (
    operation_id      TEXT PRIMARY KEY,
    session_id        TEXT NOT NULL REFERENCES sessions(session_id) ON DELETE CASCADE,
    kind              TEXT NOT NULL CHECK (kind IN ('clear', 'compact')),
    state             TEXT NOT NULL CHECK (state IN (
                          'preparing', 'no_op', 'cleanup_pending', 'completed',
                          'cancelled', 'interrupted')),
    source_generation INTEGER NOT NULL CHECK (source_generation > 0),
    result_generation INTEGER CHECK (result_generation IS NULL OR result_generation > 0),
    created_at_ms     INTEGER NOT NULL,
    finished_at_ms    INTEGER
);
```

clear 事务提交后状态为 `cleanup_pending`。Host worker 随即在经过严格路径校验的
`data/sessions/<session-id>/` 内执行：

- 删除除当前 generation 外所有符合产品命名规则的 Session `conversation.*.jsonl`；
- 删除旧 `child-tasks/` 正文目录；
- 删除旧 `tool-images/` 内容并重建空的稳定目录；
- 清理该 Session 的可重建 Conversation index cache，fsync 受影响目录；
- 全部成功后将 receipt 改为 `completed`。

删除实现不接受未解析 glob，不删除 `attachments/`、`private/`、permissions 或 Session
目录本身。遇到非预期文件类型、越界路径或 I/O 错误时停止清理并保留
`cleanup_pending`，不扩大删除范围。

Runtime Host 在 `load_runtime` 读取 Session 前先恢复 `cleanup_pending`：SQLite 已指向
新 generation 时继续上述精确清理；`preparing` 但未切换时删除已验证的未发布
新文件并标记 `interrupted`。已完成 receipt 可为相同 operation ID 的重试返回首次结果，
不提供恢复旧正文的能力。

Command 会在权威切换后同步尝试完成物理清理；若 I/O 阻止收尾，结果明确返回
`cleanup_pending` 而不谎报物理删除完成。无论清理是否已收尾，旧 Conversation 都已从
产品查询、Recall、导出和模型上下文中永久退出。这不扩展为备份、Trace、日志或
存储介质级安全擦除承诺。

### 10.4 Runtime 内存提交

Store 返回权威 `SessionHistoryClearResult` 后，Runtime 在仍持有 Session mutation gate 时：

- 替换 `Arc<SessionExecutionContext>` 和空 `InMemoryJournal`；
- 替换 body generation/message count，清空 Input/Run/Goal/WorkPlan/activation 投影；
- 从全局 child registry 移除本 Session 已删除的 child；
- 清空 queue/resume/usage 投影，Standard 同步退出 proxy；
- 保留附件 registry、permission scope 和目录资源；
- 不扫描删除其他 Session 已经持有的 ControllerDelivery/ProxyReport 历史；
- 发布一个 Session 级 `ConversationReset`/`SessionChanged` invalidation，Desktop 重读整个
  SessionView 与 Conversation，不依赖客户端局部清空。

内存投影失败时将 Session 标记 faulted；Store 的新空 generation 仍是唯一权威事实，
重启后按它恢复，不尝试回滚已提交的删除。

## 十一、用户手动 `/compact`

### 11.1 独立上下文操作，不创建 Run

Protocol 增加 `CompactSessionRequest/Result` 和 `CancelSessionCompactionRequest/Result`。
请求携带 Session ID、operation ID 和 expected body generation，结果为：

```rust
pub enum CompactSessionOutcome {
    Compacted {
        source_generation: u64,
        result_generation: u64,
        compacted_message_count: u64,
        retained_message_count: u64,
    },
    NoOp,
    Cancelled,
}
```

它不含 InputId/RunId，不发布 RunAccepted/RunStarted/RunCompleted，也不调用 Goal settlement。
手动压缩仍是独立上下文操作，不是业务 Run，不进入 Run 列表。

为了让手动与自动压缩共用一份 Session 运行态，`SessionState` 增加仅存内存的
`active_compaction`，而不再使用只表达手动命令的 `active_context_operation`。它持有
compaction ID、触发来源、源 generation、开始时间和可选 CancellationToken：

- 手动 compact 的 compaction ID 直接使用客户端 operation ID，并持有取消令牌；
- 自动 parent compaction 由 Runtime 生成 compaction ID，关联当前 Run ID 和
  `ThresholdReached | ProviderOverflow` 原因，不因本版本的统一投影而新增用户取消能力；
- child Agent 的私有 Conversation 压缩不设置 parent Session 的 `active_compaction`，
  避免把 child 内部恢复误表达为主会话正在压缩。

`active_compaction` 严禁写入 SQLite、JSONL 或其他持久化状态，也不从
`session_history_operations` receipt 反向恢复。Runtime 崩溃后该标记随进程自然消失；
重启时只按既有规则将未完成手动 receipt 标记为 `interrupted`、中断相关非终态 Run，
不把 Session 恢复为“压缩中”，避免因崩溃遗留永久 busy 状态。

### 11.2 Composer 识别顺序

Desktop 在 `submitDraft` 开始阶段按以下顺序识别：

1. 取作文框原值，判断 `value.trim() == "/compact"`；
2. 只有无附件、未武装 Goal、未选 Skill 时才调 `compact_session`；
3. 有任一组合状态时显示可操作错误并保留草稿/附件/标签；
4. 不调附件 upload，不调 `submit_input`，不把 `/compact` 追加到乐观消息列表。

Slash menu 可将 `/compact` 作为可发现项，但真正协议意图是 `CompactSession` Command，
不是对文本进行 Runtime 内部截获。

### 11.3 执行与取消

Runtime 的手动 compact 流程：

1. 取 Session mutation gate，校验 active、healthy、完全空闲、Conversation loaded、
   无 pending exchange 且 expected generation 匹配；
2. 按 operation ID 检查 `session_history_operations`。已有终态 receipt 直接返回首次结果；
   同 ID 正在执行时返回该操作已开始，不启动第二次模型调用；
3. Store 记录 `preparing` receipt，Session 内存注册 active compaction 并发布压缩开始事件，然后释放
   mutation gate；此状态使新 Input、clear、归档、模型切换和另一 compact 稳定返回 busy；
4. 使用当前 Session model、冻结 System Prompt 和
   `RollingSummaryPolicy(minimum_recent_user_turns = 1)` 生成 candidate；不使用自动 overflow
   的 active-turn fallback；
5. `NoCompressibleHistory` 转为 `NoOp`，Store 将 receipt 标记 `no_op`，不新建 generation；
6. 取消令牌在模型调用或 candidate 提交前触发时返回 Cancelled，旧 generation
   保持权威；一旦 replacement Store 事务提交，取消不再逆转已提交事实；
7. 候选生成后重新取 mutation gate，核对 operation 仍是当前操作、generation 与
   Conversation snapshot 未变，然后使用 idle replacement 提交；
8. Store 成功后替换内存 Journal/message count、清除 active compaction、发布压缩结束事件和
   Conversation/Session invalidation，不调 queue driver 继续任务。

HTTP 请求 future 异常结束时必须通过 Runtime-owned guard 取消未提交操作并清理
内存状态，不能因 drop 遗留永久 busy。Runtime 重启将尚为 `preparing` 的 compact receipt
标记 `interrupted`，并保留旧 generation；不自动重试模型调用。

手动流程与现有自动 parent compactor 都通过 Runtime-owned guard 收口状态清理和结束事件。
`Compacted | NoOp | Cancelled | Failed` 每个终态都必须恰好清除一次
`active_compaction` 并发布一次结束事件；不得只在成功 replacement 路径清理。

### 11.4 Idle generation replacement

`ContextReplacementTarget` 增加第三种精确目标：

```rust
IdleSession {
    session_id: SessionId,
    expected_generation: u64,
    operation_id: String,
}
```

Host 复用 `begin_replacement/commit_replacement` 写新 generation，但 SQL CAS 不再要求
`runs.status = running`，而是再次验证 active Session、expected generation、无 queued Input、
无 nonterminal Run/child/pending exchange，并且 operation receipt 仍为本次 `preparing`。
切换 generation 与将 receipt 改为 `completed` 在同一 SQLite transaction 中完成。

compact 后旧 generation 继续沿用现有 best-effort 文件清理和孤儿扫描；它不是可导航
双份历史。与 clear 不同，compact 的产品语义是用 Context Summary 替代较早消息，
不需要清空 Tool Image 或删除保留近期历史仍引用的资源。

## 十二、公共协议与事件

### 12.1 快照类型

`assistant-protocol` 增加下列最小类型：

```rust
pub enum SessionRoleSnapshot {
    Standard,
    Controller,
}

pub struct SessionProxySnapshot {
    pub controller_session_id: SessionId,
    pub changed_at_ms: i64,
}

pub enum ControllerAvailabilitySnapshot {
    Available { session_id: SessionId },
    Unavailable,
}

pub struct SessionCompactionSnapshot {
    pub compaction_id: String,
    pub trigger: SessionCompactionTriggerSnapshot,
    pub source_generation: u64,
    pub started_at_ms: i64,
    pub cancellable: bool,
}

pub enum SessionCompactionTriggerSnapshot {
    Manual,
    Automatic {
        run_id: RunId,
        reason: SessionCompactionReasonSnapshot,
    },
}

pub enum SessionCompactionReasonSnapshot {
    ThresholdReached,
    ProviderOverflow,
}
```

`SessionSummary` 增加带 serde 默认的 `role`、可选 `proxy`；
`ApplicationSnapshot` 增加当前 Controller availability 与多 Controller 诊断数；
`SessionSummary` 与 `SessionViewSnapshot` 均增加可选 `active_compaction`，使 Desktop
切换 Session 时能从 Runtime 当前内存投影重建“压缩中”状态。该字段是快照的易失
运行态，不对应任何 Store 列。`QueuedInputSnapshot` 和
`UserMessageSnapshot` 增加第 7.3 节的 source。旧 JSON 缺少新字段时安全读为
Standard、无 proxy、无 active compaction 和 User source。

`ConversationItem` 直接增加内联 `ContextSummary { message_id, text }` variant，内容投影自规范
Conversation 已有的 `ConversationMessage::ContextSummary`。它不是新上下文实体，也不增加独立
状态、计数或持久化。Desktop 按消息顺序把该项渲染为摘要分割线，不通过 generation 数字推断。

`body_generation` 已存在 `ConversationPage`；为了让 clear/compact 从一份一致 SessionView
发起，`SessionViewSnapshot` 显式增加 `conversation_generation`，Desktop 不从 cursor 解码。

### 12.2 命令

`RuntimeCommand`/`RuntimeCommandResult` 增量加入：

- `SetSessionProxy` / `SetSessionProxyResult`；
- `ClearSession` / `ClearSessionResult`；
- `CompactSession` / `CompactSessionResult`；
- `CancelSessionCompaction` / `CancelSessionCompactionResult`。

主控模型调用的 list/set/send 是 Runtime 私有工具，不为 Desktop 复制一组“伪造模型
工具调用”命令。Desktop 只有目标 Session 自身的显式 proxy 开关需要公共 Command；
用户要求主控投递时继续提交普通主控用户消息。

### 12.3 错误码

新增稳定、脱敏错误至少包括：

| 错误码 | 语义 |
| --- | --- |
| `controller_unavailable` | 当前无可用主控 |
| `controller_operation_not_allowed` | 当前 Run 来源不允许使用跨会话能力 |
| `session_not_proxied` | 目标仍是普通模式，不接受主控投递 |
| `session_role_restricted` | Controller 不允许归档、删除、Fork 等操作 |
| `session_compaction_in_progress` | 已有自动或手动 Session compaction 正在执行 |
| `session_compaction_not_found` | 取消目标已结束或不存在 |
| `session_history_cleanup_pending` | clear 已切换权威空历史，物理清理待恢复 |

既有 `session_not_idle`、`snapshot_stale`、`model_unavailable`、`storage_unavailable`、
`session_archived` 继续复用，不为每种 busy 组合增加错误枚举。

### 12.4 事件与重建

压缩观察增加两个有界 Runtime 事件：

```rust
SessionCompactionStarted {
    session_id: SessionId,
    compaction: SessionCompactionSnapshot,
}

SessionCompactionFinished {
    session_id: SessionId,
    compaction_id: String,
    outcome: SessionCompactionFinishedOutcome,
}

pub enum SessionCompactionFinishedOutcome {
    Compacted {
        source_generation: u64,
        result_generation: u64,
    },
    NoOp,
    Cancelled,
    Failed {
        code: RuntimeErrorCode,
    },
}
```

手动和自动 parent compaction 在发起模型请求前先更新 Runtime 内存投影，再发布
`SessionCompactionStarted`；所有成功、no-op、取消和失败路径都先清除投影，再发布
`SessionCompactionFinished`。同一个自动压缩可与关联 Run 的 active 状态同时存在，
二者不互相代替。

这两个事件只用于实时显示，不写入 SQLite、JSONL 或事件日志，不是独立持久事实。
Desktop 收到开始/结束事件时可立即更新本地投影；SSE gap、未知事件、客户端重连或
Runtime 重启后，必须以当前 `SessionSummary.active_compaction` /
`SessionViewSnapshot.active_compaction` 重建。Runtime 重启后该字段必然为空，Desktop 不得因为
没收到 Finished 事件而永久显示压缩中。

代理切换和 clear 继续只发布 Session/Conversation invalidation；compact 在上述生命周期事件之外，
只在 generation 变更时发布 Conversation/Session invalidation。主控投递与代理报告继续发布
现有 RunAccepted、QueueChanged、ConversationCommitted 和后续 Run 事件。不新建可丢失的
“消息已送达”事件作为业务事实。

SSE gap、未知事件、客户端重连或 Runtime 重启后，Desktop 统一重读
ApplicationSnapshot/SessionView/Conversation page。本版本不承诺未读数、系统通知或
外部渠道回执。

## 十三、Runtime Host 存储、迁移与恢复

### 13.1 增量 schema

本版本的正式 SQLite 变更为：

1. `sessions` 增加 role/proxy 三个字段；
2. `inputs` 增加 `cross_session_binding_json TEXT`；
3. 新增 `session_history_operations`；
4. `REQUIRED_PROJECTIONS` 同步更新，恢复边界解析并验证所有新字段。

这些迁移只是加列/加表，旧 `inputs.origin` 仍只允许 `user | runtime`，因此不需要
重建 `inputs` 大表或改写旧 Input。迁移在现有 schema Immediate transaction 中完成。

`active_compaction` 和 Started/Finished 事件不增加任何 schema 列或持久事件表。
`session_history_operations` 中的手动 compact receipt 只用于幂等结果和崩溃后标记
`interrupted`，不表示 Session 当前仍处于压缩中。自动 compaction 不为了 UI 状态新增 receipt。
任意 DDL/投影核验失败立即阻止 Host 开放端口，不在半迁移状态加载 Runtime。

自动迁移不将任何旧 Session 标记为 Controller，不生成 proxy，不重写 Conversation。
首次 Runtime open 在迁移与恢复后通过正常创建业务操作增加 Controller。

### 13.2 高层 Store 端口

`RuntimeStore` 新增或扩展的业务操作收口为：

- `create_session` / `fork_session`：持久 role，Fork 公共路径只创建 Standard；
- `set_session_proxy`：在 Session 串行边界内设置明确归属终态；
- `accept_input`：支持可选 cross-session binding 和用户接管 effect；
- `settle_run`：支持可选 proxy report Input 与权威接受结果；
- `interrupt_recovered_runs`：以 Runtime 构造的 Interrupted settlement 批量结算恢复候选，
  并原子接受可选 proxy report；
- `begin/get/finish_session_history_operation`：仅承载 clear/compact 幂等与恢复阶段；
- `clear_session_history`：切换空 generation、刷新上下文、删除旧结构事实并写清理回执；
- `replace_context(IdleSession)`：手动 compact 的空闲 generation replacement。

易失 Store 必须实现与 SQLite Store 相同的角色、代理顺序、接管、结算报告和
上下文操作约束，不为单元测试简化出另一套语义。

### 13.3 恢复顺序

Host `load_runtime` 前置修复顺序调整为：

```text
Session 删除操作恢复
→ clear cleanup receipt 恢复
→ body/child staged append 恢复
→ pending tool exchange 恢复
→ 标记未完成 compact 为 interrupted
→ Tool Image / Recall 修复
→ 收集非终态父 Run 恢复候选
→ Runtime 构造 Interrupted settlement 与可选报告
→ Store 原子中断父 Run、暂停 Goal 并接受报告
→ 加载结构投影
```

clear 恢复位于普通 staged append 之前，因为它可能已删除旧 Run/Input 并切换空
generation；不能再对已 clear 的旧 append 进行恢复。恢复后只有当前 generation 可被
`load_conversation`、分页、Recall 和导出访问。

### 13.4 内部幂等身份

主控投递与代理报告的幂等 key 使用 `assistant-runtime` 已依赖的 `sha2`
对结构化身份做版本化 digest，再转换为现有有界 `IdempotencyKey`；不把多个原始 ID
无界拼接进 SQLite 唯一列。比如：

```text
controller-delivery-v1 sha256(controller_session_id, run_id, tool_call_id)
proxy-report-v1       sha256(source_session_id, source_run_id)
```

同一源 Run 只有一条代理报告；Goal ID 是报告内容，不参与报告去重身份，
避免同一 Run 因 Goal 结算投影差异生成两条报告。

## 十四、Desktop 接入边界

Desktop 仅进行以下增量改造，具体布局与视觉等待交互设计指导：

- `RuntimeProjectionStore`/`RootStore` 从 ApplicationSnapshot 读取当前 Controller，
  不自行排序选择；
- Session 列表与 Header 按 `role`/`proxy` 展示身份，不按标题字符串猜测；
- 目标 Session 的代理开关调 `SetSessionProxy`，只提交期望开/关终态；
- Conversation 依 `UserMessageSnapshot.source` 显示“主控转达”或“会话报告”来源；
- 发送普通用户消息后始终重读 SessionView，不在前端先乐观关闭 proxy；
- Desktop 增加统一的 Queue presentation selector：当 Queue 为 `automatic`、无 active Run，
  且队首未被 Goal hold 时，把第一项视为正在交给 Run driver 的 dispatching head，不放入
  Composer 待发送区；其余 Input 仍按真实等待队列展示；
- Queue 非 automatic、存在 active Run 或队首被 Goal hold 时不应用上述过滤。QueueDrawer
  可见性、条目和数量必须消费同一 selector，Runtime `QueueSnapshot`、生命周期退出影响统计和
  durable queued count 保持原样；
- clear 复用现有 `SessionActionDialog` 框架执行不可撤销二次确认，成功或
  cleanup pending 后都以 Runtime 快照重建；
- `/compact` 在 Composer 本地转换为 Command；Desktop 对自动和手动压缩消费同一
  active compaction 投影与开始/结束事件，只在 `cancellable = true` 时开放取消；
- Context Summary 直接作为 `ConversationItem` 中的现有上下文事实投影；Desktop 在 generation
  切换时保留当前已加载消息，移除旧摘要项、按保留消息 ID 去重，再把当前摘要项渲染为可展开
  分割线，不新增另一套状态。

Controller 的归档、删除和 Fork 操作在 UI 中隐藏/禁用，Runtime 仍作权威拒绝。
本版本不在 `ConnectionStore`、localStorage 或 Desktop preference 中保存主控/代理状态。
控制通信的持久增量只有 Session role/proxy 列与 Input cross-session binding；
`session_history_operations` 仅服务 clear/compact 恢复，不是隐藏的消息投递状态机。

## 十六、测试与验收策略

### 16.1 Runtime 与易失 Store

单元/集成测试至少覆盖：

- 无 Controller 自动创建、重启不重复、多 Controller 稳定选择；
- 旧 Session 默认 Standard/无 proxy，Controller 归档、删除、Fork 被拒绝；
- proxy 重复设置相同终态 no-op、并发变更按服务端提交顺序生效、活动 Run 中途开/关；
- 普通模式拒绝投递；代理开启但目标有 Queue 时投递返回 busy 且不插队，Queue 为空时可靠入队且
  同 ToolCallId 不重复；
- ControllerDelivery 使用目标变体/审批/模型，不继承主控权限；
- 既有冻结 ToolSet 和主控工具通过平行装配环节合并；完全相同的重复工具被折叠，
  同名异义工具 fail-closed；
- 主控装配环节对用户来源 Controller parent Run 贡献工具，对报告、Goal continuation 和
  child 返回空贡献；
- 代理切换不受 Queue 限制；任意来源 parent Run 结算时代理开启且结算后 Queue 为空才报告，
  Queue 未空的中间 Run 不报告也不补发，最后一项只报告最新结果；
- 报告处理 Run 不装配 list/set/send 工具，用户新指令恢复工具；
- 报告不含 reasoning、工具详情、Provider 原始错误，审批等待不报告；
- 用户接管与并发投递的两种顺序，仅删未开始 ControllerDelivery，不产生取消报告；
- 崩溃恢复中断父 Run 时复用相同 Queue 门禁，不因恢复路径提前报告；
- 不同 Session 仍可并发，所有跨 Session 更新不交叉持有两个 mutation gate。

### 16.2 Host Store 与崩溃点

所有测试只使用 `TempDir`/内存 Store，不打开用户 Runtime Home。覆盖：

- schema 从旧版本加列/加表后精确行数和默认值核对；
- proxy 外键、role/binding 损坏、cross-session JSON 损坏的 fail-closed 恢复；
- 源 Run 有/无最终消息时，结算 + Goal effect + proxy report 的原子回滚和幂等；
- Store 提交报告后、Runtime 内存投影前重启仍能恢复主控队列；
- Host 异常退出后的非终态父 Run 按持久 proxy 生成或不生成 Interrupted 报告，
  且中断、Goal pause 与报告接受同事务；
- clear 在新上下文构建失败、空文件写入失败、SQLite 预检失败、事务前崩溃、
  事务后清理前崩溃和部分 I/O 清理失败等每个阶段；
- clear 后 SQLite 结构行数、当前 JSONL 空会话、Recall/导出/分页、Tool Image/child 目录、
  附件/private/permissions 保留的精确核对；
- compact no-op、cancel、模型失败、snapshot 竞态、idle replacement、receipt 重试和重启 interrupted；
- 自动与手动 parent compaction 都按顺序发布一次 Started/Finished，并在成功、
  no-op、取消、失败和 future drop 后清除 active compaction；child 压缩不污染该投影；
- 崩溃恢复不从 Store receipt 恢复 active compaction，重启后快照必然为空；
- compact 后模型 Conversation、Recall 和当前上下文导出只有 Context Summary + 保留轮次；
  Desktop 当前已加载列表通过该分割项连续更新；System Prompt/Catalog/proxy 完全不变。

### 16.3 Protocol、Desktop 与正式 Host E2E

- Protocol 覆盖所有新 enum/optional field/command/result/error 的 JSON round-trip 与 TypeScript 导出；
- Desktop 单测覆盖 `/compact` 精确匹配、组合草稿保留、clear 确认、来源渲染，
  自动/手动压缩的统一开始与结束呈现、手动可取消/自动不可取消，以及事件 gap
  或 Runtime 重启后从快照清除假性“压缩中”；代理 Command 传输结果不明时先重读
  快照再决定是否重试；
- Desktop 单测覆盖 Queue presentation selector：空闲 automatic 单条不闪现、多条只隐藏队首，
  active Run、paused/resume-required 和 Goal held 场景不隐藏真实队列；
- Desktop 单测覆盖有 Queue 时代理开关仍立即切换、开启态显示等待队列排空说明，以及用户新增
  Input 后按权威快照退出代理；
- 正式 Host 离线 E2E 用临时 Runtime Home 和 fake Provider 运行两次 Host，覆盖自动主控、
  切换、投递、报告、用户接管、clear、compact 与重启恢复；
- 验收后只读核对临时 SQLite/JSONL/目录，不连接真实 Provider，不操作用户数据库。

## 十七、关键取舍与风险控制

1. **使用 Input binding，不使用通用消息表**：当前只有主控投递和代理报告两种内部来源，
   直接复用 Session 队列和 Input/Run 恢复，不预建 endpoint/channel/delivery 模型。
2. **使用 Run 工具装配流水线**：冻结预设工具与各类条件工具以平行环节贡献，统一去重后
   冻结；后续 Goal、Session 或插件工具通过新增装配环节接入，不继续扩大
   `compile_run_agent` 的业务分支。
3. **报告进入源 Run 结算事务**：这保证不出现“Run 已成功但报告在崩溃中丢失”；
   它只增加一条可选 Input effect，不增加回复关联。
4. **代理状态与执行门禁分离**：运行中或有 Queue 时开关都立即生效，不冻结关联状态；主控投递和
   报告另在执行点检查 Queue。Queue 未排空不产生中间报告，关闭代理则阻止尚未结束 Run 的报告。
5. **用户接管是接受输入的原子 effect**：不先发一条关闭命令，因此不存在两个 HTTP
   命令之间又插入主控任务的窗口。
6. **clear 的可访问删除与物理清理分阶段**：SQLite 切换后旧历史立即不可访问，
   receipt 保证物理正文不被无限期遗留。清理失败不能伪装成未发生 clear，也不谎报已擦除。
7. **manual compact 使用轻量上下文操作而非 Run**：它需要取消与幂等 receipt，
   但不获得模型工具、Run 历史、Goal continuation 或代理报告。
8. **不扩大通知范围**：可靠消息进入主控 Conversation 就是本版本的可恢复结果；
   未读、系统通知、IM 回复和外部投递全部留待后续版本。

主要风险及门禁：

- **跨 Session 死锁**：工具投递只取目标锁；Run 结算后释放源锁，再投影主控队列；
- **自动消息循环**：主控工具按 Input source 冻结，ProxyReport Run 没有跨 Session 能力；
- **来源伪造**：模型不能提交 source ID 作为权威事实，Runtime 从当前 Run/ToolCall 注入；
- **clear 误删资源**：只删已验证 Session 目录中的产品命名正文/child/tool-image，
  不使用宽泛路径、未解析环境变量或 glob；
- **System Context 混用**：Prompt/Catalog/Environment 绑成同一 `Arc` 快照，clear 只整体替换；
- **compact 重复计费**：operation receipt + 内存 active compaction 拒绝同 ID 的第二次模型调用；
- **损坏主控绑定**：恢复时交叉验证当前 proxy 的 role、外键和自绑定，
  不将非法当前关系静默降级；已提交 Input 的历史来源 ID 不要求源 Run 永久存在。

## 十八、实现顺序建议

后续开发计划建议按以下依赖顺序拆里程碑，但本文确认不等于授权直接开发：

1. Session role/proxy 领域、Store schema/恢复和 Protocol 基础；
2. Controller 自动创建、稳定选择和 Desktop 身份投影；
3. 主控工具、ControllerDelivery、用户接管和来源展示；
4. Run settlement ProxyReport 原子接受、主控处理能力门禁和重启 E2E；
5. clear 上下文重建、结构删除、物理清理回执和 Desktop 确认；
6. manual compact 操作、idle replacement、取消/幂等和 Composer 入口；
7. Composer automatic dispatching head 呈现修复及回归；
8. 完整回归、正式 Host 双进程重启验收与文档收口。
