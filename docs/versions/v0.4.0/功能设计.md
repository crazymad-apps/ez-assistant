## 二、背景与目标

v0.2.0 已建立类型化工具、Registry、Dispatcher、Allow/Deny Authorizer 接缝、文件与
Shell 能力契约和可取消 Agent Loop，但仍存在四个能力缺口：

1. Authorizer 当前面对原始 Tool Call JSON，类型校验、路径解析和有效默认值发生在
   授权之后，授权事实与最终执行参数可能不一致；
2. Core 只有单一 Authorizer 接缝，没有可复用的策略装配能力，Plan/Build 工作模式和
   Ask/Auto 审批模式无法按职责组合；
3. 文件与 Shell 只有 fake/契约，没有可以由真实上层应用装配的本机执行实现；
4. 架构已预留 Guardrail，但重复调用和连续失败尚不能观察或强制终止。

同时，正式 `assistant-runtime` 的 Session、Run、审批、持久化和总体接口尚未完成
设计。脱离上层宿主无法验证安全策略、审批等待、真实工具副作用和取消清理，因此本
版本增加独立 `tools/safety-demo`，以临时前后端宿主验证完整闭环，但不把 Demo 类型
视为正式 Runtime 契约。

v0.4.0 的目标是：

- 在工具副作用前形成一份已经类型校验、默认值落实、路径归一化且语义冻结的 resolved
  invocation，授权与执行使用同一份事实；
- Core 提供只产生 Allow/Deny 的通用策略装配能力，上层可以独立组合工作模式边界和
  审批模式；
- 提供可复用的真实本地文件与 Shell 执行适配器，并明确它们不是 OS 沙盒；
- 实现可选的重复调用与连续失败 Guardrail，支持关闭、观察和强制终止；
- 通过安全 Demo 验证 Plan/Build × Ask/Auto、真实文件、真实 Shell、审批、取消、
  Guardrail 和审计展示。

## 三、明确非目标

本版本不实现：

- 正式 `assistant-runtime` 的 Session、Run、Approval Service、Repository、数据库、
  审计持久化、恢复、调度或产品 API；
- 新增正式 Approval Service/SPI 及审批生命周期，包括“仅本次/会话/持久允许”、规则
  保存、同批合并审批、审批超时、重启恢复和跨设备同步；既有 ToolAuthorizer 接缝
  继续保留并改为面对 resolved invocation；
- 把 `Ask` 加入 Agent Core 状态机或授权结果；Core 最终决策仍只有 Allow/Deny；
- 新增执行级资源预算，例如输入/输出 token、成本、总时长和聚合工具输出预算；
  v0.2.0 已有的 `max_steps`、`max_tool_calls` 保持现状；
- AgentExecution 总超时；Shell 超时和文件大小限制只属于具体工具；
- “无进展”Guardrail；在没有可靠、通用的进展信号前不引入主观启发式；
- Shell 命令 AST、管道或风险语义解析；
- OS 沙盒、容器、虚拟机、权限降级或对 Shell 文件访问的强隔离；
- 二进制文件、图片、PDF 或多媒体读取能力；
- 自动下载 ripgrep、由 Session/Runtime 持有句柄并负责健康检查、停止或恢复的托管服务；
- 交互式 TTY 或 stdin 输入；
- 正式桌面应用接线；`apps/desktop` 本版本不改；
- 把 `runtime-harness` 的私有 Run/Journal/Checkpoint 语义扩展为正式 Runtime；
- Tool Result 裁剪、Memory Plugin、任务 drain、todo 或 ask_user 等后续版本能力。

## 四、功能范围与使用路径

### 4.1 Tool Call 解析、授权与执行

工具调用顺序统一为：

```text
完整 AssistantMessage 进入 pending exchange
→ 查找工具并反序列化类型化输入
→ 校验字段并落实模型可见默认值
→ 解析路径、工作目录等确定性参数
→ 形成 ResolvedToolInvocation
→ Guardrail 预检
→ 类型化策略与上层 Authorizer 得到 Allow/Deny
→ Allow 执行同一个 resolved invocation
→ 完整批次 Tool Result 落账
```

ResolvedToolInvocation 表示“参数已解析并冻结”，不是预执行：

- 不访问真实文件系统；
- 不检查路径是否存在、文件类型或符号链接目标；
- 不读取文件、不启动进程、不申请审批；
- 只做类型校验、纯参数约束、默认值落实、词法路径解析、授权事实和稳定指纹生成。

未知工具和无效输入在 resolved 阶段直接形成错误 Tool Result，不进入授权或审批，也不
执行副作用。文件存在性和类型等真实状态只在授权通过后检查，避免未授权路径通过错误
信息泄露本机文件状态。

同一批 Tool Call 先全部完成无副作用解析，再按原有顺序逐个过闸和执行；Core 不推断
工具可安全并行。授权器仍可观察本轮批次上下文。

### 4.2 模型可见默认值

会影响返回范围、执行时长或副作用的参数不能只存在于工具构造器：

- read 的 offset/limit；
- search 的 max results；
- Shell 的 timeout；
- edit 的 replace-all；
- 其他输出或数量限制。

工具实例冻结时，实际默认值必须同步进入模型可见 Tool Definition。Resolved 阶段只能
落实已经公开的默认值；schema 展示值、执行值和测试断言必须一致。分页结果回显实际
offset、limit、next offset 和是否截断，让模型能够稳定续读。

Session 默认工作目录属于上层执行上下文。它可以在输入缺省时使用，但必须通过工具
说明或上层 instructions 明确告知模型。

### 4.3 两个独立工作维度

工作模式分为两个维度：

- 执行模式：Plan / Build，决定能力上限；
- 审批模式：Ask / Auto，只决定能力上限内的未匹配动作如何取得最终决策。

行为矩阵：

| 组合 | 行为 |
| --- | --- |
| Plan + Ask | Plan 白名单内直接执行；白名单外按 Plan 硬边界拒绝，不能请求越权审批 |
| Plan + Auto | 只自动执行 Plan 白名单内动作；白名单外仍拒绝 |
| Build + Ask | 类型化白名单命中直接执行；未命中进入上层审批 |
| Build + Auto | 类型化白名单命中直接执行；未命中由全放行 fallback 自动允许 |

Auto 等价于能力边界内的 All Allowed，不等于跳过 Plan/Build 边界。Mode Deny 先于
审批 fallback，Ask 或 Auto 都不能覆盖。

### 4.4 装配式策略

Core 只提供顺序装配策略的机制，不理解 Plan、Build、Ask、Auto、文件路径或 Shell
命令等业务规则：

- 每个策略可以明确 Allow、明确 Deny，或表示没有匹配并交给下一个策略；
- “没有匹配”使用组合机制内部结果，不增加公开 `NotApplicable` 授权决策；
- 第一条明确决策生效；全部未匹配时进入最终 Authorizer；
- Engine 最终只接收 Allow/Deny。

通用、文件、Shell 使用各自的类型化授权事实和规则类型：

- 通用策略可以按工具名或工具类别判断；
- 文件策略使用操作类型与完整绝对逻辑路径；
- Shell 策略使用完整命令、有效工作目录和有效超时；
- 不设计固定全局 whitelist 数据结构；
- 每个类型化策略自己装配白名单、拒绝规则和未匹配行为。

同一个类型化策略内部发生允许与拒绝规则冲突时，明确允许规则优先；不同能力层之间按
装配顺序处理，不能用下层允许覆盖上层 Mode Deny。Core 保留显式全放行实现，不提供
隐式默认放行。

### 4.5 Plan 模式临时工作区

Demo 每个 Session 持有：

- `session_workdir`：相对文件路径和 Shell 工作目录的默认根，不要求是代码项目；
- `temporary_workspace`：当前 Demo Session 生命周期内复用的临时可写目录。

Plan 文件规则：

| 范围 | 允许操作 |
| --- | --- |
| `session_workdir` | read / list / search |
| `temporary_workspace` | read / list / search / write / edit / delete |
| 其他路径 | Deny |

Plan 模式默认拒绝全部 Shell 和未知/未分类工具。临时工作区允许删除文件、空目录和
符号链接，支持讨论过程中反复生成、修改和删除方案文件。临时工作区生命周期只由 Demo
管理；未来正式 Runtime 再决定按 Session、项目或其他作用域管理。

### 4.6 真实文件能力

新增可复用的本机文件适配器，实现现有结构化能力：

- read；
- 非递归 list；
- 按文件名搜索；
- 按内容搜索；
- write；
- 精确替换 edit；
- delete 文件、空目录或符号链接。

路径行为：

- 文件与 Shell 都由上层注入默认 `session_workdir`；
- 相对路径基于该目录生成，绝对路径保持绝对；
- 使用成熟路径库执行不访问文件系统的词法绝对化，消除 `.`、`..`；
- 授权和执行使用同一份完整绝对逻辑路径；
- list/search 返回的目标路径使用完整绝对逻辑路径，后续调用不依赖隐含根目录；
- 不使用 canonical path 做权限判断；
- 路径权限是应用策略，不是物理沙盒。

符号链接行为：

- list 将“有效目标类型”和“是否符号链接”分开表达；
- 指向文件的链接显示为 File + symlink 标记；
- 指向目录的链接显示为 Directory + symlink 标记；
- 损坏链接显示为 Other + symlink 标记；
- read/list/search/write/edit 按宿主文件系统正常跟随链接；
- delete 符号链接只删除链接本身，不删除目标；
- 文件工具不提供创建符号链接的能力。

因为授权按逻辑路径判断，允许目录中的符号链接可能访问其目录外目标。Demo、文档和
审批展示必须明确这一点，不得把目录规则描述成真实路径沙盒。

文本与修改行为：

- read/edit/content search 以 UTF-8 文本为能力边界；
- read 返回给模型的文本去除 UTF-8 BOM，不把 BOM 暴露成正文字符；
- 明显二进制、包含 NUL 或非法 UTF-8 的直接读取/编辑返回稳定错误；
- 内容搜索遇到不支持文本的文件时跳过该文件，不使整次搜索失败；
- edit 保留 UTF-8 BOM 和原文件 LF/CRLF 风格；
- write 完整新建或覆盖文件，父目录必须已经存在；
- edit 保持唯一精确匹配/显式 replace-all 语义；
- delete 不递归删除非空目录；
- 设备、FIFO、Socket 等特殊文件不支持。

修改操作在同一适配器实例内按逻辑目标串行，并在写入前核对 edit 读取的内容，避免
同一进程内使用过期内容覆盖更新。文件操作开始副作用前检查取消；副作用已经开始后
完成当前文件句柄与清理，再让 AgentExecution 收敛为取消。本版本不承诺事务或跨进程
原子修改。

### 4.7 文件搜索后端

递归文件名和内容搜索不自行实现遍历引擎，优先使用系统已安装的 ripgrep：

- `rg` 只是 FileSystemTool::search 的内部后端，不作为模型可见工具；
- 通过参数数组启动，不经过 Shell 字符串拼接；
- 使用无用户配置模式，保证结果不被本机 ripgrep 配置文件静默改变；
- 内容搜索使用字面量匹配，与既有契约一致；
- ignore、隐藏文件、二进制和符号链接采用首期固定后端语义，不增加产品配置项；
- stdout 按记录和调用总量进行有界读取，不允许单条 JSON 或整次输出在解析前无限增长；
- 达到结果数、输出字节或单条记录上限时停止并清理搜索进程，返回已得到的部分结果和
  稳定截断原因；超大单条记录不生成内容预览，提示模型缩小路径或查询范围；
- stderr 持续排空但只有限保留，避免错误输出造成无界内存增长或管道阻塞；
- 取消与所有主动终止原因共用可靠的 kill + wait 清理路径；
- 不在运行时下载可执行文件；
- 找不到 `rg` 时返回明确的搜索后端不可用错误。

### 4.8 真实 Shell 能力

模型侧 Shell 输入保持完整 `command`，自然支持管道、重定向、条件执行和变量展开，另
提供显式 `process_mode`：缺省 `managed`，需要让服务在工具返回后继续运行时选择
`detached`。本版本不解析或改写命令内容，也不从 `nohup`、`&` 等语法猜测生命周期。

执行适配器使用平台默认 Shell：

- POSIX：`/bin/sh`，以 `-c` 传入完整命令；
- Windows：优先 `COMSPEC`，否则 `cmd.exe`，以 `/C` 传入完整命令。

Shell 程序和固定参数属于执行器配置，不是模型输入。模型可指定 command、workdir、
timeout 和 process_mode；resolved invocation 保存完整命令、绝对逻辑工作目录、有效
超时和进程模式。进程模式进入授权 facts、审批、指纹和审计，授权后不能变化。

Shell 策略只对完整命令字符串、工作目录和超时做规则匹配，不声称理解管道或子命令。
宽泛的 Shell glob/prefix 可能放行复合命令，不能作为强安全边界。Plan 默认拒绝全部
Shell；Build + Ask 展示完整命令供审批；Build + Auto 才允许未匹配命令自动通过。

执行行为：

- stdin 关闭，不提供交互式 TTY；
- stdout/stderr 分通道流式输出；
- 最终 Shell 结果分别保留 stdout/stderr，不把来源不可逆地聚合成单个字符串；
- 正常非零退出码属于已完成的 Shell 结果，不是工具基础设施错误；
- 超时保留已有输出、终止进程树并返回失败；
- 取消终止进程树、等待资源清理后收敛，不回喂模型继续推理；
- 输出达到工具上限后标记截断并继续排空管道，防止子进程阻塞；
- managed 模式下，即使 Shell 主进程正常退出，也必须终止并等待仍持有输出管道的后代
  进程，工具返回时不留下由本次调用启动的进程树；
- detached 模式允许命令在主 Shell 退出且 stdout/stderr 已收敛后留下脱管后代；在这
  两个条件满足前，timeout 或取消仍终止并等待整个进程树；
- detached 成功只表示启动命令已退出并完成输出交接，不表示后台服务健康；一旦工具
  返回，Session reset、Run 取消或 Demo 退出都不会自动停止该服务，也不提供后台句柄；
- Shell timeout 和输出限制属于工具策略，不进入 Core 资源预算。

环境变量默认继承当前进程的开发环境以保证工具链可用，但在创建子进程前应用敏感变量
过滤策略；默认至少过滤 `_API_KEY`、`_TOKEN`、`_SECRET` 通用后缀，明确允许项优先
于过滤规则，显式覆盖最后应用。Windows 环境变量名按 ASCII 大小写不敏感处理，覆盖
前移除等价旧键。完整继承必须由宿主显式选择，不能由空配置偶然获得。该机制不能阻止
Shell 主动读取当前用户有权访问的凭据文件。

### 4.9 Guardrail

v0.4.0 实现两个可选检测器：

- Repeated Invocation：连续出现相同 resolved invocation；
- Consecutive Failures：连续工具失败。

每个检测器独立配置：

- 未配置：关闭；
- Observe：达到阈值时发送诊断事件，不改变工具、审批或 Agent Loop；
- Enforce：达到阈值时可靠结算当前批次并终止 AgentExecution。

重复调用指纹使用工具名和归一化后的语义参数。文件路径使用完整绝对逻辑路径；Shell
使用完整 command 和有效 workdir，timeout 不参与重复指纹，避免只改变等待时间绕过
检测。指纹不同即重置重复计数。

以下计入连续失败：

- 未知工具或无效输入；
- 授权 Deny；
- 工具执行错误；
- 文件/Shell 超时。

工具成功会重置连续失败；Shell 非零退出是正常结果，也会重置。用户取消不参与
Guardrail。

Observe 在一段连续序列首次达到阈值时发送一次事件，序列重置后可再次触发。Enforce
必须补齐触发调用及同批剩余调用的 Tool Result，完成 pending exchange 后以明确的
Guardrail 终态失败结束，不能留下未配对 Tool Call/Result。

### 4.10 Safety Demo

新增独立前后端 `tools/safety-demo`，作为开发者显式启动的临时宿主：

- Rust 后端装配真实 OpenAI-compatible Model Service、Agent Core、真实本地工具、
  模式策略和 Demo Authorizer；
- Web 前端提供单个内存 Session 的对话、流式输出、审批、取消、模式选择、工具事件
  和审计时间线；
- 默认使用 Plan + Ask；
- Plan/Build 和 Ask/Auto 在每次 Run 开始时冻结，运行中修改只影响下一次 Run；
- Ask 只实现 Allow once / Deny，不实现保存、批量或超时；
- 审批卡展示 resolved 路径/工作目录、完整 Shell 命令、有效 timeout 和策略命中依据；
- 审计只保存在内存，不写正式 Runtime Journal 或数据库；
- Session 结束时清理临时工作区。

Demo 可以使用本地 HTTP/SSE，但只监听 loopback。本版本不增加访问令牌鉴权，启动 URL
可直接打开；后端仍拒绝未知 Origin、不开放通用 CORS，POST 必须来自当前 loopback
页面。`session_workdir` 由开发者启动参数显式传入，不能由网页请求静默改到其他目录。
Build + Auto 必须显示其具有当前用户权限的高风险提示。该入口仅用于开发验证，Host 与
Origin 校验不构成对本机其他进程的身份认证。

Safety Demo 是上层应用行为样例，不属于桌面产品进程、sidecar、daemon 或正式
`assistant-runtime`。产品 crate 不依赖 Demo，Demo 的 Session、Run、审批、审计和
HTTP 类型不得进入 `assistant-protocol`。

## 五、模块边界与契约影响

### `agent-tools`

- 将单阶段 dispatch 拆为 resolve 与 execute；
- 类型化输入只反序列化一次，resolved invocation 可供授权、Guardrail 和执行复用；
- 为文件、Shell 和通用工具提供各自的类型化授权事实；
- Tool Definition 能表达工具实例冻结后的实际默认值；
- 保留 Tool SPI、Registry、Dispatcher、能力契约和标准工具壳定义职责；
- 仍不访问真实文件系统或启动子进程。

### `agent-core`

- 在 authorize 前消费 resolved invocation；
- 提供按顺序组合策略与最终 Authorizer 的通用机制；
- Engine 最终只处理 Allow/Deny，不包含 Ask；
- 实现 Repeated Invocation 和 Consecutive Failures Guardrail 及诊断/终态事件；
- 保持两阶段 Recorder、逐调用过闸、顺序执行、取消结算和预算语义。

### `agent-tools-local`

- 作为本机基础设施 Adapter 实现真实 FileSystemTool 和 ShellTool；
- 持有默认工作目录、Shell launcher、工具限制和环境过滤机制；
- 负责真实 I/O、搜索子进程、Shell 子进程、输出流、超时、取消与进程树清理；
- 不依赖 Core、Runtime、Tauri、UI 或数据库；
- 不实现 Plan/Build、Ask/Auto、审批交互或审计持久化。

### `agent-testkit`

- 提供 resolved invocation、策略装配和 Guardrail 的确定性测试支持；
- 覆盖无效输入不进授权、同一 resolved 输入授权/执行一致、Allow/Deny、取消、重复调用
  和连续失败；
- 既有 v0.2/v0.3 累计场景保持通过。

### `tools/safety-demo`

- 负责临时 Session、Run、审批等待、策略装配、事件关联和内存审计；
- 直接依赖正式 Agent crate 与本地工具 Adapter；
- 不复用或扩大 runtime-harness 的 Context 私有契约；
- 不产生产品协议或正式 Runtime API。

### `assistant-runtime`

- 本版本不修改代码或依赖；
- 长期仍负责产品中的工作模式、审批、规则保存、审计、配置编译和本地工具装配；
- 后续可复用 `agent-tools-local`，但不得把 Safety Demo 的临时编排直接提升为产品契约。

### `apps/desktop` / `assistant-protocol`

- 本版本不修改；
- Safety Demo 页面和 HTTP DTO 不进入桌面应用或跨层产品协议。

## 六、关键取舍

- **Resolve 后授权，授权后执行同一事实**：避免文件策略、Shell 策略和执行器重复解析
  原始 JSON，消除授权与副作用参数不一致。
- **执行模式与审批模式正交**：Plan/Build 是能力上限，Ask/Auto 是上限内的 fallback；
  Auto 不能帮助模型越过 Plan 边界。
- **Core 只组合策略**：Ask、规则保存和用户交互属于上层；Core 保持 Allow/Deny 和一次
  AgentExecution 的稳定边界。
- **类型化策略自行装配名单**：文件、Shell 和通用工具参数不同，不强制使用一个全局
  whitelist 格式。
- **独立本地工具 Adapter**：真实机制不污染纯 Tool SPI，也不因正式 Runtime 尚未设计
  而塞入 Demo 私有代码；该取舍替代 2026-07-27“机制直接进入 agent-tools”的旧计划。
- **逻辑路径权限而非真实路径沙盒**：符合用户已经暴露符号链接即可操作的预期，但必须
  明示可能访问目录外目标。
- **完整 Shell command 而非 program/args 模型输入**：复合 Shell 操作是首要用例；
  program/args 只属于执行器内部启动形态。
- **搜索复用系统 ripgrep**：不自行维护递归和内容搜索引擎，也不在运行时下载工具。
- **Guardrail 显式可选**：关闭不检测，Observe 不改变行为，Enforce 才终止；没有隐藏
  启发式。
- **Safety Demo 独立于 Harness 和正式 Runtime**：它提供真实交互验收抓手，但不提前
  固化产品 Session/Run/Approval 契约。

## 七、验收标准

1. 未知工具和无效参数在授权前形成稳定错误 Tool Result，不触发策略、审批或真实
   副作用；有效调用只反序列化一次。
2. 授权器、Guardrail 和执行器观察并使用同一 ResolvedToolInvocation；文件相对路径、
   Shell workdir、默认值和有效 timeout 不会在授权后再次变化。
3. 影响结果的工具默认值进入冻结 Tool Definition；schema 展示值与执行值一致，read
   结果回显有效分页信息。
4. Core 能顺序装配通用、文件、Shell 等类型化策略；没有固定全局 whitelist；
   Engine 对外仍只有 Allow/Deny。
5. Plan + Ask、Plan + Auto、Build + Ask、Build + Auto 四种组合均有确定性覆盖；
   Plan Deny 不能被 Ask/Auto 覆盖，同一类型化策略内明确 allow 优先。
6. Plan 模式只允许读取 `session_workdir`、完整操作 `temporary_workspace`，并默认拒绝
   Shell、未知工具和其他路径；删除临时方案文件及空目录可用。
7. 真实文件 Adapter 可在临时目录完成 read/list/search/write/edit/delete；相对和绝对
   路径、`.`/`..` 归一化、UTF-8/BOM/换行、文件类型、结果限制和取消语义均可断言。
8. list 同时表达目标类型和 symlink 标记；读写编辑可跟随链接，删除链接只删除链接
   本身；目录规则明确不宣称真实路径沙盒。
9. 文件名和内容搜索通过系统 `rg` 的参数数组完成，支持字面量查询、结果上限、调用
   输出上限、单记录上限、稳定截断原因、取消和后端不可用错误；解析前无无界 stdout/
   stderr 累积，不通过 Shell 拼接或运行时下载。
10. 真实 Shell 可执行包含管道/重定向的完整 command，使用正确平台 launcher，关闭
    stdin，分通道流式输出，并报告退出码、超时、截断和 process_mode。
11. Shell 非零退出作为正常结果返回；managed 的正常退出、超时和取消都能终止并等待
    进程树；detached 只有在主 Shell 退出且输出收敛后才释放后代，审批和审计可明确区分
    两种模式；默认敏感变量过滤在 POSIX/Windows 语义下生效。
12. Repeated Invocation 与 Consecutive Failures 均可独立关闭、Observe 或 Enforce；
    Observe 只发诊断事件，Enforce 可靠结算 Tool Result 后以 Guardrail 原因终止。
13. Deny、无效输入、工具错误、超时、Guardrail 和取消路径都保持 Tool Call/Result
    配对；Recorder 失败继续阻断后续副作用。
14. Safety Demo 能以真实 Provider 完成对话、模式切换、审批、文件/Shell 工具、取消、
    Guardrail 和审计时间线人工验证；默认 Plan + Ask。
15. Demo 只监听 loopback 并限制 Host/Origin/POST 来源，不实现访问令牌；Build + Auto
    有明确高风险提示，Session 结束后临时工作区被清理。
16. `assistant-runtime`、`apps/desktop` 和 `assistant-protocol` 无代码改动；Demo 私有
    Session/Run/Approval/HTTP 类型没有进入产品 crate。
17. v0.2 与 v0.3 的累计测试和 Runtime Harness 验证保持通过，不因 Dispatcher、
    Authorizer、事件或 Tool trait 调整而回归。
18. 新增资源预算、AgentExecution 总超时、正式 Approval Service/SPI、审批持久化、
    No Progress Guardrail 和正式 Runtime 接线均未进入实现。

## 八、风险、兼容性与后续设计要求

### 风险

- 逻辑路径授权允许通过符号链接访问规则目录外目标，必须依靠明确展示和用户理解，不能
  作为强隔离；
- Shell 拥有当前用户权限，可以绕过结构化文件策略并访问网络、进程和凭据文件；
- Unix/Windows 的进程树终止、Shell launcher 和环境变量语义不同，需要跨平台验证；
- detached 服务不由 Session/Runtime 持有，可能在 Demo 退出后继续占用端口、文件或
  其他资源；页面必须明确提示，并由命令自身输出 PID/日志等后续管理信息；
- Unix 后代主动 `setsid`/`setpgid` 逃离原进程组时，managed 清理不能被描述为强沙盒
  或对恶意命令的绝对保证；
- 系统缺少 `rg` 时真实搜索不可用，需要清晰错误和验收环境说明；
- Tool trait、Dispatcher 和 Authorizer 接缝调整会影响全部现有工具、fake 和测试；
- 类型擦除必须保证 resolved input 的类型、授权事实和实际 executor 不可能错配；
- 本地 HTTP Demo 具备真实 Shell 权限且不做身份认证；同机进程可以直接调用 API，浏览器
  侧仅依赖 loopback、Host/Origin、POST 来源与无 CORS 降低跨站误触风险；
- 工具实例动态默认值与冻结 schema 若不同步，会重新产生模型预期与执行结果偏差。

### 兼容性

- 当前为 `0.x` 内部开发阶段，允许对 Tool/Dispatcher/Authorizer 公共契约做一次显式
  迁移，但所有 workspace 调用方必须同批更新；
- 规范 ToolCall/ToolResult、Provider 编码、Conversation Snapshot 和产品协议不因
  resolved invocation 改变；
- `max_steps`、`max_tool_calls`、Context CompactionRequired 和 v0.3 上下文语义保持
  不变；
- `assistant-runtime` 继续是空骨架，不接受 Demo 临时实现形成的兼容承诺。

### 后续设计要求

- 本版本涉及新增 crate、Tool/Authorizer 公共契约、跨平台真实 I/O、子进程、安全和
  Demo 服务，已形成归档内的 `技术方案.md`；
- 本版本新增完整 Web 页面、审批卡、模式状态和异常反馈，已形成归档内的
  `界面交互设计指导.md`；
- 技术方案需要基于实际依赖树核定 resolved 类型擦除、路径库、ripgrep 查找、进程组/
  Job Object、环境过滤、动态 Tool schema、测试矩阵和依赖方向；
- 界面交互指导需要明确页面布局、审批等待、取消、模式冻结、风险提示、断线和
  Guardrail 展示；
- 功能范围无遗留待确认项；具体默认数值、公共类型名称和第三方依赖版本由技术方案
  确认，但不得改变本文的可见性、安全和模块边界。
