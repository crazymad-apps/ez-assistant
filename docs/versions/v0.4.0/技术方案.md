## 二、现状核查

本方案基于 2026-07-31 当前仓库、`cargo metadata --format-version 1 --no-deps`、
`cargo tree -p agent-core --depth 2`、`cargo tree -p agent-tools --depth 2` 和
`cargo tree -p runtime-harness --depth 1` 的实际结果。

### 2.1 工具层

- `agent-tools::Tool` 当前只有 `Input` / `Output` 和 `execute`；类型擦除层在
  `execute_json` 中完成反序列化后立即执行，没有可供授权复用的中间事实。
- `Dispatcher::dispatch` 当前按名称查找工具后一次完成反序列化和执行；未知工具、
  参数无效和执行失败都直接形成错误 `ToolResult`。
- `ToolRegistry` 在注册时冻结 `ToolDefinition`，但类型化工具的 schema 会被擦除层重新
  派生，工具实例无法安全补充动态默认值。
- `register_erased` 和公开 `ErasedTool` 允许自定义实现自行维持 schema、反序列化和
  call ID 一致性；这与本版本要求的“resolved input、facts、executor 不可错配”冲突。
- 标准文件工具壳中的 read limit、search max results、edit replace-all，以及 Shell 的输出
  上限仍在构造器或执行阶段落实，未全部进入冻结的模型可见定义。
- `FileSystemTool` 方法没有取消上下文；请求路径是 `String`，并在契约注释中假定为
  相对能力根。`FileEntryKind::Other` 仍混合了符号链接与特殊文件。
- `ShellRequest` 同时携带未落实的 workdir、timeout 和输出上限；`ShellOutcome` 把
  stdout/stderr 不可逆聚合成一个字符串。

### 2.2 Core

- `ToolAuthorizer::authorize` 当前面对原始 `ToolCall` 和原始批次，无法安全判断文件
  绝对逻辑路径、Shell 有效工作目录或实际默认值。
- Core 已有强制必传的 Authorizer 接缝和显式 `AllowAllAuthorizer`，但没有顺序策略
  装配器。
- Engine 当前顺序为：

  ```text
  begin pending exchange
  → 每个原始 ToolCall authorize
  → 预算预检
  → Dispatcher::dispatch
  → complete exchange
  ```

- `max_steps`、`max_tool_calls`、取消收敛、Recorder 两阶段落账和可靠终态已实现，可在
  原控制流上增量加入 resolve 与 Guardrail，不需要重写 Agent Loop。
- `ExecutionError` 和 `AgentEvent` 尚无 Guardrail 分类；Engine 尚无重复指纹或连续
  失败状态。

### 2.3 上层与工程

- `assistant-runtime` 仍是正式 Runtime 骨架，本版本不能把 Demo 的审批、HTTP、
  Session 或 Run 类型写入其中。
- `runtime-harness` 已有真实 Provider 装配和内存 Journal 参考，但其定位是 v0.2/v0.3
  版本验证宿主，不能继续扩展成安全策略应用。
- `debug-viewer` 已证明 `axum + ServeDir + 静态 HTML/CSS/JS` 足以构成独立开发工具；
  Safety Demo 可以复用工程形态，但需独立实现 loopback、Host、Origin 与 POST 来源约束。
- workspace 使用 edition 2024、resolver 3、`unsafe_code = "forbid"`；当前 Tokio
  workspace 基础 features 不含 `fs`、`io-util`、`process`、`net` 和 `signal`，新增
  crate 需要在各自 manifest 中按需打开。

### 2.4 结论

需要同时完成三条技术链：

1. 在 `agent-tools` 中把类型化 Tool 迁移为
   `deserialize → resolve → execute resolved`，并让 Dispatcher 持有不可错配的一次性
   执行载荷；
2. 在 `agent-core` 中先解析整个批次，再按 resolved facts 执行 Guardrail、策略和
   Authorizer；
3. 在独立 `agent-tools-local` 中实现真实 I/O 和进程，在独立 `safety-demo` 中实现
   Plan/Build × Ask/Auto 及 Web 交互。

## 四、`agent-tools`：Resolved Invocation

### 4.1 Tool SPI

`Tool` 改为显式 resolve：

```rust
pub trait Tool: Send + Sync + 'static {
    type Input: DeserializeOwned + JsonSchema;
    type ResolvedInput: Serialize + Send + 'static;
    type Output: Serialize;

    fn name(&self) -> ToolName;
    fn description(&self) -> String;
    fn input_defaults(&self) -> ToolInputDefaults;

    fn resolve(
        &self,
        input: Self::Input,
    ) -> Result<ToolResolution<Self::ResolvedInput>, ToolError>;

    fn execute<'a>(
        &'a self,
        input: Self::ResolvedInput,
        context: ToolContext,
    ) -> ToolExecuteFuture<'a, Self::Output>;
}
```

- serde 反序列化仍是结构和类型校验；
- `resolve` 只允许纯计算：落实默认值、校验非零/上限、词法解析路径、构造 facts 和
  fingerprint；
- `execute` 只接收 `ResolvedInput`，不能再看到原始可选默认值；
- 普通工具可令 `ResolvedInput = Input`，通过辅助构造器生成
  `GeneralAuthorizationFacts`；文件和 Shell 使用专用 resolved 类型。

`ToolError` 保留现有两个分类，只给执行错误增加可选结构化 details：

```rust
pub enum ToolError {
    InvalidInput {
        message: String,
    },
    Execution {
        message: String,
        details: Option<Value>,
    },
}
```

- resolve 只可返回 `InvalidInput`；类型擦除边界对违反该约束、从 resolve 返回的
  `Execution` 统一归一化为 `InvalidInput`，不为此新增错误 trait；
- 普通执行失败返回没有 details 的 `Execution`；
- Shell 超时仍属于 `Execution`，details 使用稳定
  `{type: "timeout", stdout, stderr, truncated}`；
- 擦除层把两类错误统一转为 `ToolResultStatus::Error`。无 details 时保持文本结果；
  有 details 时使用稳定 JSON `{error: {message, details}}`。
- 取消仍不是模型可见 ToolError；Engine 在工具完成清理后进入取消收敛。

### 4.2 模型可见默认值

`ToolInputDefaults` 是只允许为派生 schema 的现有顶层 property 写入 `default` 的有序
映射。注册过程固定为：

```text
从 Input 派生 schema
→ 校验 defaults 引用的 property 存在
→ 写入 property.default
→ 冻结 name / description / schema
```

未知字段、重复字段或不能表示为 JSON 的默认值使 `ToolRegistry::register` 返回
`RegisterToolError::InvalidDefinition`，不能产生半注册工具。

默认值和执行配置来自同一个工具实例配置对象。例如：

```rust
pub struct ReadFileToolConfig {
    pub default_offset: NonZeroU32,
    pub default_limit: NonZeroU32,
    pub maximum_limit: NonZeroU32,
}
```

`input_defaults` 和 `resolve` 都只读取该对象，不能各自保存一份数值。

`description` 改为拥有的 `String`，注册时只生成一次，使输出字节上限、文件大小上限和
默认 workdir 说明可以随实例配置进入冻结定义。默认 workdir 只由冻结后的 Tool
Definition/schema 说明，不再在 Safety Demo 的系统 instructions 中维护第二份路径，
避免两份上下文分叉；它仍不是模型可修改参数。

### 4.3 公开 resolved 描述

```rust
pub struct ResolvedToolInvocation {
    call_id: ToolCallId,
    tool_name: ToolName,
    resolved_arguments: Arc<Value>,
    authorization_facts: Arc<dyn ToolAuthorizationFacts>,
    fingerprint: ToolFingerprint,
}

impl ResolvedToolInvocation {
    pub fn facts<F: ToolAuthorizationFacts>(&self) -> Option<&F>;
}

pub struct ToolFingerprint {
    tool_name: ToolName,
    semantic_arguments: Arc<Value>,
}
```

- `resolved_arguments` 用于审批展示和审计，不作为文件/Shell 策略的原始 JSON 输入；
- facts 只能通过带具体类型参数的 `facts::<F>()` 读取，类型不匹配返回 `None`；
- `ToolFingerprint` 比较结构化 JSON 值，不使用进程随机 hash，也不承担持久化 ID 或
  安全摘要职责；
- call ID 不进入 fingerprint；
- Shell fingerprint 的 semantic arguments 含 command、workdir 和 process_mode，不含
  timeout；
- 文件 fingerprint 含操作、绝对逻辑路径及会影响语义的其余 resolved 参数。

类型擦除后的实际 resolved input 不进入 `ResolvedToolInvocation`，也不公开
`Box<dyn Any>`。注册表内部为每次成功解析创建一个一次性 executor：

```rust
trait ErasedResolvedExecution: Send {
    fn execute(
        self: Box<Self>,
        context: ToolContext,
    ) -> Pin<Box<dyn Future<Output = ToolResult> + Send>>;
}
```

executor 同时捕获：

- 原类型化工具的 `Arc<T>`；
- 该工具的 `T::ResolvedInput`；
- 原 call ID。

因此 Core 只能要求 Dispatcher 执行该句柄，不能替换 payload、借用其他工具执行器或
制造 call ID 错配。执行方法消费 `Box<Self>`，同一 resolved 调用不能执行两次。

公开 `ErasedTool` 和 `ToolRegistry::register_erased` 从公共 API 移除；workspace 当前
只有 `agent-tools` 自身测试使用该逃生口，可迁移为 crate-private 合约测试。所有正式
工具统一经类型化 `register` 注册。

### 4.4 批次解析与 Dispatcher

```rust
pub struct ResolvedToolBatch {
    // 保持原 ToolCall 数量与顺序；每项是 Valid 或 Invalid。
}

pub enum ResolvedBatchItemRef<'a> {
    Valid(&'a ResolvedToolInvocation),
    Invalid(&'a ToolResult),
}

impl Dispatcher {
    pub fn resolve_batch(
        snapshot: &ToolSetSnapshot,
        calls: &[ToolCall],
    ) -> ResolvedToolBatch;

    pub fn execute(
        batch: &mut ResolvedToolBatch,
        index: usize,
        context: ToolContext,
    ) -> Result<ToolJsonFuture<'_>, DispatchError>;
}
```

- resolve 是同步、无 I/O 的纯操作；
- unknown tool 和反序列化/resolve 错误直接成为对应位置的 Invalid `ToolResult`；
- `ResolvedToolBatch` 对 Authorizer 公开只读迭代器，可查看同轮所有成功 resolved
  invocation 和每项原始位置；不能访问一次性 executor；
- `execute` 只接受成功 resolved 的位置并消费内部句柄；重复执行和错误位置转换为
  绑定原 call ID 的内部合约错误结果；
- index 越界时不存在可绑定的原 call ID，因此返回显式 `DispatchError`，不得伪造
  Tool Result ID 或 panic；
- Engine 不再调用单阶段 `dispatch`。为避免形成两套语义，旧
  `Dispatcher::dispatch` 删除，不保留旁路。

## 五、路径、文件与 Shell 契约

### 5.1 绝对逻辑路径

`agent-tools` 新增：

```rust
pub struct AbsolutePath(PathBuf);

pub struct SessionPathResolver {
    session_workdir: AbsolutePath,
}
```

构造规则：

1. `session_workdir` 必须可表示为 UTF-8；不可表示时启动配置失败，不做 lossy 转换；
2. 输入为空字符串时返回 InvalidInput；
3. 相对输入调用 `absolutize_from(session_workdir)`；
4. 绝对输入同样经过词法 de-dot；
5. 结果必须是绝对路径；
6. 不调用 metadata、exists、canonicalize 或 read_link。

`AbsolutePath` 内部保持平台原生 `PathBuf`，序列化为完整 UTF-8 平台路径。权限规则使用
`Path::starts_with` 对词法组件做 Exact/Recursive 判断，不用字符串前缀。

该规则不会解析符号链接。Windows 大小写、短路径、junction 和 Unix symlink 的物理
等价性不进入授权；这会产生保守拒绝或链接逃逸，但不会被描述为 OS 沙盒。

### 5.2 类型化授权事实

```rust
pub struct GeneralAuthorizationFacts {
    pub tool_name: ToolName,
}

pub enum FileOperation {
    Read,
    List,
    Find,
    Search,
    Write,
    Edit,
    Delete,
}

pub struct FileAuthorizationFacts {
    pub operation: FileOperation,
    pub path: AbsolutePath,
}

pub struct ShellAuthorizationFacts {
    pub command: String,
    pub workdir: AbsolutePath,
    pub timeout: Duration,
    pub process_mode: ShellProcessMode,
}
```

- facts 只描述实际 resolved 调用，不携带名单、模式或审批结论；
- search 的 path 在 resolve 后始终存在，缺省即 session workdir；
- Shell 的 timeout 和 process_mode 都是最终有效值，供审批展示和规则判断；重复指纹
  仅排除 timeout，process_mode 必须进入指纹，避免两种生命周期互相伪装。

### 5.3 文件能力契约调整

`FileSystemTool` 的每个方法增加：

```rust
pub struct FileToolContext {
    pub cancellation: CancellationToken,
}
```

所有请求中的路径改为 `AbsolutePath`。关键响应：

```rust
pub struct ReadFileResult {
    pub path: AbsolutePath,
    pub offset: NonZeroU32,
    pub limit: NonZeroU32,
    pub content: String,
    pub next_offset: Option<NonZeroU32>,
    pub truncated: bool,
}

pub struct FileEntry {
    pub path: AbsolutePath,
    pub kind: FileEntryKind,
    pub is_symlink: bool,
}

pub enum FileEntryKind {
    File,
    Directory,
    Other,
}

pub enum SearchTruncationReason {
    MaxResults,
    MaxOutputBytes,
    OversizedRecord,
}

pub struct SearchFilesResult {
    pub matches: Vec<SearchMatch>,
    pub truncated: bool,
    pub truncation_reason: Option<SearchTruncationReason>,
}
```

- symlink 是正交标记，不再与 kind 互斥；
- list 的每项和 search 的每条匹配返回完整绝对逻辑路径；
- search 的 `max_results` 保持模型可选且受实例最大值限制；`max_output_bytes` 和
  `max_record_bytes` 是实例固定限制，写入冻结 description 并回显到 resolved
  arguments/request，模型无需猜测执行边界，也不能通过输入提高它们；
- `truncated = true` 时必须携带唯一稳定原因；超大单条记录不返回截断 preview；
- `FileToolError` 增加：
  - `UnsupportedEncoding`
  - `UnsupportedFileType`
  - `SearchBackendUnavailable`
  - `Cancelled`
  - `TooLarge`
- `Cancelled` 只用于能力层完成清理后的控制传播，工具壳不会把它回喂模型。

### 5.4 Shell 能力契约调整

```rust
pub enum ShellProcessMode {
    Managed,
    Detached,
}

pub struct ShellRequest {
    pub command: String,
    pub workdir: AbsolutePath,
    pub timeout: Duration,
    pub max_output_bytes: NonZeroU64,
    pub process_mode: ShellProcessMode,
}

pub struct ShellOutcome {
    pub exit_code: Option<i32>,
    pub stdout: String,
    pub stderr: String,
    pub truncated: bool,
    pub process_mode: ShellProcessMode,
}

pub enum ShellToolError {
    InvalidInput { message: String },
    Io { message: String },
    TimedOut {
        stdout: String,
        stderr: String,
        truncated: bool,
    },
    Cancelled,
}
```

- timeout 不再是成功 outcome 中的布尔值；它是模型可见失败并保留结构化部分输出；
- 非零 exit code 仍是成功 `ShellOutcome`；
- stdout/stderr 始终分别流式发送和分别保留；
- 输出上限是 resolved 工具配置，模型不能把它提高到 Adapter 上限之外。
- process_mode 缺省 `Managed`，由模型显式选择 `Detached`；工具不解析 command 来猜测
  `nohup`、`&`、管道或后台意图。

## 六、`agent-core`：策略装配

### 6.1 Authorizer 契约

```rust
pub trait ToolAuthorizer: Send + Sync {
    fn authorize<'a>(
        &'a self,
        invocation: &'a ResolvedToolInvocation,
        batch: &'a ResolvedToolBatch,
    ) -> AuthorizationFuture<'a>;
}
```

- Authorizer 不再接收原始 `ToolCall`；
- batch 包含原始位置与所有 resolve 结果的只读视图；
- 无效项不会调用 Authorizer；
- `ToolAuthorization` 仍只有 `Allow` / `Deny { reason }`。

### 6.2 策略机制

```rust
pub enum PolicyEvaluation {
    Decide(ToolAuthorization),
    Continue,
}

pub trait ToolPolicy: Send + Sync {
    fn evaluate(
        &self,
        invocation: &ResolvedToolInvocation,
        batch: &ResolvedToolBatch,
    ) -> PolicyEvaluation;
}

pub trait TypedToolPolicy<F>: Send + Sync {
    fn evaluate(
        &self,
        facts: &F,
        invocation: &ResolvedToolInvocation,
        batch: &ResolvedToolBatch,
    ) -> PolicyEvaluation;
}
```

`Continue` 只属于组合协议，不是 Engine 可见的公开授权结果，也不引入
`NotApplicable` 业务状态。

`TypedPolicyAdapter<F, P>` 负责：

1. 从 invocation 读取 `facts::<F>()`；
2. 类型不匹配时 Continue；
3. 匹配时调用具体 typed policy。

`ComposedToolAuthorizer` 持有有序 `Vec<Arc<dyn ToolPolicy>>` 和必传 final
`Arc<dyn ToolAuthorizer>`：

```text
逐策略 evaluate
→ 第一条 Decide 立即返回
→ 全部 Continue 才 await final authorizer
```

- Core 不提供 Plan/Build、名单、路径或 Shell matcher；
- `AllowAllAuthorizer` 继续是显式 final authorizer；
- 同一具体 policy 内“allow 优先 deny”的算法由该 policy 实现；
- 不同 policy 间严格第一条明确决策优先，因此 Mode Deny 必须装配在审批 fallback
  之前且无法被覆盖。
- policy 是无 I/O 的同步判断；审批、等待和其他异步组织仍只存在于 final authorizer，
  不新增异步 policy 包装层。

## 七、`agent-core`：Guardrail 与 Engine

### 7.1 配置

```rust
pub struct ExecutionSpec {
    // 既有字段不变
    pub guardrails: Option<GuardrailConfig>,
}

pub struct GuardrailConfig {
    pub repeated_invocation: Option<GuardrailCheckConfig>,
    pub consecutive_failures: Option<GuardrailCheckConfig>,

    pub mode: ActiveGuardrailMode,
    pub threshold: NonZeroU32,
}

    Observe,
    Enforce,
}
```

- `ExecutionSpec.guardrails = None`：整个 Guardrail 关闭；
- detector 为 `None`：该检测器关闭；
- 没有 Off enum，也没有隐藏阈值。

### 7.2 状态

Engine 私有状态：

```rust
struct RepeatedInvocationState {
    last: Option<ToolFingerprint>,
    consecutive: u32,
    emitted_at_threshold: bool,
}

struct ConsecutiveFailuresState {
    consecutive: u32,
    emitted_at_threshold: bool,
}
```

- 状态跨模型 step 保留，只在当前 `AgentExecution` 内存在；
- resolved fingerprint 不同或出现 invalid item 时，重复序列重置；
- ToolResult Success 重置连续失败；
- Error 结果计入连续失败；
- Shell 非零退出为 Success，因而重置；
- 取消分支在结果分类前收敛，不进入失败计数。

### 7.3 事件与终止

新增：

```rust
pub enum GuardrailKind {
    RepeatedInvocation,
    ConsecutiveFailures,
}

AgentEvent::GuardrailTriggered {
    kind: GuardrailKind,
    mode: ActiveGuardrailMode,
    threshold: NonZeroU32,
    observed: u32,
    call_id: ToolCallId,
}

ExecutionError::GuardrailTriggered {
    kind: GuardrailKind,
    threshold: NonZeroU32,
}
```

- GuardrailTriggered 是普通诊断事件；最终仍以可靠
  `ExecutionFailed { GuardrailTriggered }` 收敛；
- Observe 在一段序列第一次达到阈值时发一次事件，超过阈值不重复发；
- Enforce 也先发事件，然后完成当前 pending exchange，再发可靠失败终态；
- Recorder complete 失败仍优先收敛为 Record error，因为未完成落账不能宣称
  Guardrail 已可靠结算。

### 7.4 新批次控制流

```text
begin pending exchange
→ ToolProposed（保持原事件）
→ resolve_batch（整个批次，无 I/O）
→ 逐原始位置处理：
   ├── Invalid
   │   → ToolCompleted(Failed)
   │   → ConsecutiveFailures
   └── Valid
       → RepeatedInvocation
       → policy chain / final authorizer（与取消 race）
       ├── Deny → error ToolResult → ConsecutiveFailures
       └── Allow
           → max_tool_calls 预检
           → ToolStarted
           → execute 同一一次性句柄
           → 取消检查
           → ToolCompleted
           → ConsecutiveFailures
→ complete exchange
→ 下一模型 step
```

Enforce 结算：

- Repeated Invocation 在当前调用执行前触发：当前调用及批次剩余项统一补
  Guardrail error ToolResult；
- Consecutive Failures 在当前失败结果产生后触发：保留当前真实失败结果，只给剩余项
  补 Guardrail error ToolResult；
- 两者都为所有补齐项发送 ToolCompleted(Failed)，按原序 complete 整批后终止；
- budget 和取消仍沿用既有专用结算路径，不计入 Guardrail。

## 八、`agent-tools-local`：真实文件

### 8.1 配置与边界

```rust
pub struct LocalFileSystemConfig {
    pub max_text_file_bytes: NonZeroU64,
    pub ripgrep_program: OsString,
    pub max_search_stderr_bytes: NonZeroU64,
}

pub struct LocalFileSystem {

    locks: PathLockTable,

```

Safety Demo 装配值固定为：`max_record_bytes = 64 KiB`、单次搜索
`max_output_bytes = 1 MiB`、`max_search_stderr_bytes = 64 KiB`；这些值由构造配置注入，
不是 `agent-tools-local` 的隐藏全局常量。

- Adapter 接收的请求路径已经是 `AbsolutePath`，不再解析默认 workdir；
- 标准工具壳、路径解析器和本地能力由上层宿主直接装配；本 crate 不提供未被调用方需要
  的 `LocalToolSetBuilder` 或其他总装辅助层；
- Adapter 不判断 Plan/Build、名单或审批。

### 8.2 文本读取

执行步骤：

1. 检查取消；
2. `metadata` 跟随 symlink，要求最终目标为普通文件；
3. 按配置上限读取字节；
4. 拒绝 NUL；
5. 识别 UTF-8 BOM，并从返回给模型的正文中移除；edit 内部读取仍记录并保留物理 BOM；
6. 严格 UTF-8 解码，不做 lossy 转换；
7. 使用共享分页函数生成带行号结果和有效 offset/limit/next_offset。

设备、FIFO、Socket 和目录返回 UnsupportedFileType；过大返回 TooLarge。检查发生在授权
之后，因此不会向未授权调用泄露文件状态。

### 8.3 list 与 symlink

对每个直接子项：

1. `symlink_metadata` 得到 `is_symlink`；
2. 非链接直接按自身 metadata 分类；
3. 链接再调用 `metadata` 跟随目标：
   - 目标文件：File + true；
   - 目标目录：Directory + true；
   - 目标特殊类型：Other + true；
   - 损坏或不可解析：Other + true。

结果按完整逻辑路径的文件名分量稳定排序。list 不递归，不额外改变系统对链接的行为。

### 8.4 write/edit/delete 与锁

`PathLockTable` 使用：

```text
std::sync::Mutex<HashMap<AbsolutePath, Weak<tokio::sync::Mutex<()>>>>
```

同步锁只用于取得或创建 per-path async mutex，释放后才 `.await`。write、edit、delete
在同一 Adapter 实例内按逻辑目标串行；read/list/search 不串行。等待 per-path async
mutex 时直接与 cancellation race，取消不能一直等待前一个 mutation 释放锁；不为这一
处控制流再抽取通用锁包装器。

write：

- 检查取消和内容 UTF-8/NUL/字节上限；
- 父目录必须已存在；
- 已存在目标若最终为目录或特殊文件则拒绝；
- `tokio::fs::write` 正常跟随 symlink；
- 不创建父目录，不承诺原子替换。

edit：

- 持有目标锁完成读取、BOM/换行分析、精确替换和写回；
- 纯 LF 文件按 LF 匹配和写回；
- 纯 CRLF 文件把模型传入 old/new 的 LF 转为 CRLF 后匹配和写回；
- mixed ending 文件不做全局转换，只进行原字节对应的 UTF-8 字符串精确替换；
- 写前再次读取并与首次读取字节比较，不一致返回 ConcurrentModification；
- 保留原 BOM；
- 不承诺阻止检查后由其他进程产生的 TOCTOU。

delete：

- 使用 `symlink_metadata` 先识别链接；
- 链接只 unlink 本身；Windows 对目录链接使用对应 remove-dir link 语义；
- 普通文件 remove_file；
- 普通目录只 remove_dir，非空失败；
- 不递归；
- 不跟随链接删除目标。

每个 mutation 在首个副作用前检查取消。副作用开始后不直接 drop future，完成当前句柄
关闭和必要清理后返回；Engine 再统一取消收敛。

### 8.5 ripgrep 搜索

通过共享的本地进程启动器执行系统 `rg`，不用 Shell：

按名搜索：

```text
rg --no-config --files --null -- <absolute-root>
```

- 按 NUL 有界读取路径记录；
- 在 Adapter 中对最后一个路径分量做字面量子串匹配；
- 只返回文件；
- 读取到 `max_results + 1` 时标记 truncated、终止并清理 rg。

内容搜索：

```text
rg --no-config --json --fixed-strings -- <query> <absolute-root>
```

- 只解析 JSON `match` 消息；每条 delimiter record 在追加前检查
  `max_record_bytes`，累计 stdout 在保留/解析前检查 `max_output_bytes`，禁止先
  `read_until` 或 `read_to_end` 到无界 `Vec` 再做后处理；
- path、lines 只有 `text` 时才接收，二进制/base64 或非法 UTF-8 匹配跳过；
- 行号使用 rg 报告的 1 起始行号；
- 达到 `max_results + 1` 后停止并清理。

共同规则：

- query/path 通过参数数组和 `--` 传入；
- 不读取用户 rg 配置；
- 不额外传 `--hidden`、`--no-ignore` 或 `--follow`，首期固定采用系统 rg 默认：
  遵循 ignore、跳过隐藏项、默认不遍历目录 symlink、内容搜索跳过二进制；
- exit 0 为有匹配，exit 1 为无匹配，两者成功；exit 2 或 stderr 错误转 Io；
- spawn NotFound 转 SearchBackendUnavailable；
- 不下载 rg；
- 结果数、stdout 总量或单记录超限时终止并等待 `rg`，返回已有部分结果及对应稳定
  truncation reason；超大记录本身不生成 preview；
- stderr 始终并发排空，但只保留 `max_search_stderr_bytes` 前缀；
- 取消、上限和解析错误共用一个 `terminate_and_wait` 路径，不遗留子进程。

## 九、`agent-tools-local`：真实 Shell

### 9.1 Launcher

```rust
pub struct ShellLauncher {
    pub program: OsString,
    pub fixed_args: Vec<OsString>,
}
```

默认值：

- POSIX：program `/bin/sh`，fixed args `["-c"]`；
- Windows：program 取 `COMSPEC`，未设置时 `cmd.exe`，fixed args `["/C"]`。

启动器由 `LocalShellConfig` 注入并可在测试替换，但不是模型输入。完整 command 只作为
最后一个参数传入，不拆分、不重写。

### 9.2 环境过滤

```rust
pub struct EnvironmentPolicy {
    pub allow_exact: BTreeSet<OsString>,
    pub deny_exact: BTreeSet<OsString>,
    pub deny_suffixes: Vec<OsString>,
    pub overrides: BTreeMap<OsString, Option<OsString>>,
}
```

`EnvironmentPolicy::default()` 继承父环境但默认拒绝 `_API_KEY`、`_TOKEN`、
`_SECRET` 后缀；确需完全继承时必须调用语义明确的 `EnvironmentPolicy::inherit_all()`。
不维护 Provider 名单，也不引入复杂规则对象。

顺序：

1. 读取父进程 `vars_os`；POSIX 按原始名称匹配，Windows 对 allow、deny、suffix 和
   override 都使用 ASCII 大小写不敏感键；
2. allow_exact 命中则保留；
3. 否则应用 deny_exact / deny_suffixes；
4. 最后应用 overrides；Windows 先移除所有大小写等价旧键，再按 override 名称执行
   Some 写入或 None 删除；
5. 对 Command 使用 `env_clear + envs` 注入结果。

这实现“同一 policy 内 allow 优先 deny，显式 override 最后生效”。Adapter 不内置具体
Provider 名称；Safety Demo 使用默认通用后缀过滤，不重复维护 DeepSeek/OpenAI 名单。

### 9.3 进程、输出、超时和取消

启动：

- stdin = null；
- stdout/stderr = piped；
- Unix 包装 `ProcessGroup::leader()`；
- Windows 包装 `JobObject`；
- Tokio 包装 `KillOnDrop` 作为异常 drop 的最后兜底。

执行器并发排空 stdout/stderr，通过有界内部 channel 汇总：

- 每块先按通道发送 ToolOutput；
- 输出累计达到 `max_output_bytes` 后设置 truncated，停止向 sink 和最终结果追加新
  字节，但继续读取并丢弃，防止管道反压卡死；
- UTF-8 采用跨 chunk 增量解码；非法序列用 U+FFFD 展示，不影响进程回收；
- 上限是 stdout+stderr 合计前缀上限，最终仍按两个字段保存。

生命周期使用同一个绝对 deadline 和 cancellation，覆盖主 Shell 等待、输出收敛和清理：

- managed：主 Shell 正常退出后仍主动终止并等待进程组/Job Object，再结束 reader；
  工具成功返回时不留下仍属于原进程树的后台后代；
- detached：只有主 Shell 已退出且 stdout/stderr reader 均已 EOF，才允许返回并释放
  后代；这要求命令自行把长期进程的 stdin/stdout/stderr 与工具管道分离；
- detached 在释放条件满足前发生 timeout/cancellation，仍 kill 整组、wait 并结束
  reader，不因为选择 detached 而绕过清理；
- kill/wait 失败返回 Io，不能伪装为已清理；所有清理动作保持幂等。

detached 是 fire-and-forget，不生成 Session 持有的后台句柄，不提供健康/就绪探测、
自动停止、重连或恢复。Unix 后代若主动 `setsid`/`setpgid` 逃离进程组，无法由当前组
清理保证覆盖；该限制必须记录，不能把 process group 描述为恶意命令沙盒。本版本仍不
提供 stdin 或 TTY。

## 十、`tools/safety-demo`

### 10.1 进程与配置

启动：

```text
cargo run -p safety-demo -- --workdir <path> [--port <port>]
```

- `--workdir` 必传，启动时解析为 session_workdir，Web API 不能修改；
- `--port` 缺省 `0`，由 OS 分配 loopback 空闲端口；
- 仅 `127.0.0.1` 监听；
- 只有该命令加载 `.env` 和真实 Provider credential；
- Provider 配置沿用 Harness 已验证的 `DEEPSEEK_API_KEY`、`DEEPSEEK_BASE_URL`、
  `DEEPSEEK_MODEL`、`DEEPSEEK_CONTEXT_WINDOW_TOKENS` 与
  `Profile::deepseek()`；
- Demo 在真实 ModelService 外装配薄包装器，为每个 Step 显式注入
  `thinking: { type: enabled }`；Core 保持 Provider-neutral，不依赖 DeepSeek 默认模式；
- DeepSeek Profile 在流式 `TurnFinished` 和非流式完整消息形成前校验“Tool Call 必须
  携带 reasoning”；Provider 违反约束时当前 Turn 以 Protocol 错误结束，不执行工具、
  不向 Journal 提交不可回放的 Assistant Tool Call；
- 启动失败早返回脱敏配置错误，不打印 credential。

每次进程只创建一个 DemoSession：

```rust
struct DemoSession {
    session_workdir: AbsolutePath,
    temporary_workspace: TempDir,
    journal: DemoJournal,
    active_run: Option<DemoRun>,
    pending_approval: Option<PendingApproval>,
    audit: Vec<AuditEntry>,
    next_sequence: u64,
}
```

状态由一个上层 `tokio::sync::Mutex` 保护，但任何模型、审批等待、文件或 Shell future
都不能在持锁时 `.await`。长操作取得所需快照和句柄后释放锁。

TempDir 在正常 reset/shutdown 时显式 `close()` 并报告清理错误；进程异常终止仍受
TempDir drop 的尽力清理约束，SIGKILL 无法承诺清理。

### 10.2 Demo Journal 与 Run

- 私有 DemoRecorder 实现 Core 两阶段 Recorder；
- UserMessage 先进入内存 Journal，再启动 Core；
- 最终 Completed AssistantMessage 由 Demo 加入 Journal；
- 同一时间只允许一个活动 Run，第二个 start 返回 409；
- Run 冻结 `ExecutionMode` 和 `ApprovalMode`，页面改值只影响下一 Run；
- active Run 持有 `ExecutionControl`，cancel 幂等；
- Demo 不实现 checkpoint、continuation、持久化或恢复。

默认 Guardrail：

```text
Repeated Invocation: Observe, threshold 3
Consecutive Failures: Enforce, threshold 5
```

数值进入本次 ExecutionSpec，页面状态明确展示；detector 的所有模式仍由自动测试完整
覆盖。

### 10.3 模式策略

Demo 私有规则：

```rust
enum RuleEffect { Allow, Deny }
enum PathScope { Exact(AbsolutePath), Recursive(AbsolutePath) }
enum CommandPattern { Exact(String), Prefix(String) }
```

分别实现 General、File、Shell typed policy；每个 rule set 先找 Allow，再找 Deny，
最后 Continue。

装配：

```text
Plan
→ PlanCapabilityPolicy（对每个 valid invocation 必定 Allow 或 Deny）
→ final authorizer（理论上不可达）

Build
→ DemoTrustedRulesPolicy（Allow / Deny / Continue）
→ Ask: DemoApprovalAuthorizer
  Auto: AllowAllAuthorizer
```

PlanCapabilityPolicy：

- session_workdir Recursive：Read/List/Find/Search Allow；
- temporary_workspace Recursive：所有 FileOperation Allow；
- 其他文件操作 Deny；
- Shell Deny；
- General/未分类工具 Deny。

如果 temporary_workspace 将来位于 session_workdir 内，临时工作区的显式 Allow 仍先于
只读范围的 Deny。Plan + Auto 的 final AllowAll 不会被调用，因此 Auto 无法越过
能力边界。

Build 首期 trusted rules 允许 session_workdir 的只读文件操作和 temporary_workspace
全部文件操作；其他调用 Continue。Shell 默认无信任规则：

- Ask：进入一次性审批；
- Auto：进入 AllowAll；
- 显式 Deny 规则若以后装配，仍在 fallback 前生效。

Command Prefix 只用于证明 Shell typed rule 可装配；页面和文档标注它会连同管道、
重定向及后续复合命令一并放行，不是安全解析。

### 10.4 一次性审批

`DemoApprovalAuthorizer` 为每个调用创建私有 approval ID、oneshot 和审计项：

- UI 只可选择 Allow once / Deny；
- 不保存规则、不批量、不超时；
- 卡片数据来自 ResolvedToolInvocation 的 typed facts；
- 文件展示 operation + 完整绝对逻辑路径；
- Shell 展示完整 command + workdir + effective timeout + process_mode；detached 固定
  提示“返回后不再由 Session 管理，取消/reset/退出不会停止服务”；
- General 展示 tool name；
- 用户决定后 Authorizer 返回 Core Allow/Deny。

取消：

- Authorizer 持有当前 Run cancellation；
- cancellation 与审批 oneshot race；
- pending future 被 Engine drop 时，RAII guard 从 Session 移除对应审批并发送
  approval_cancelled 事件；
- 取消不会留下页面仍可操作的审批卡。

### 10.5 本地 HTTP 安全

启动时：

1. 监听地址固定为 `127.0.0.1`，端口默认由 OS 分配；
2. 控制台输出可直接打开的 `http://127.0.0.1:<port>/`；
3. 本 Demo 不生成访问令牌，`/api/*` 不要求 Bearer，也不设置鉴权 cookie；
4. 页面直接请求 snapshot 并建立 SSE。

这是面向开发者的临时验证入口，不提供本机进程之间的身份认证。同机进程能够直接调用
API；浏览器侧防护只用于降低跨站页面误触风险，不能描述成安全沙盒或完整鉴权。

中间件：

- Host 必须是实际 loopback host/port；
- 出现 Origin 时必须精确等于当前 `http://127.0.0.1:<port>`；
- POST 无正确 Origin 直接拒绝；
- 不返回通用 CORS header，OPTIONS 不放行；
- API 与静态页统一 `Cache-Control: no-store`；
- 返回 CSP：`default-src 'self'; connect-src 'self'; object-src 'none'; base-uri 'none'`；
- 不记录 Provider credential、完整文件内容或完整 Shell 输出。

私有路由：

```text
GET  /api/snapshot
GET  /api/events
POST /api/runs
POST /api/runs/current/cancel
POST /api/approvals/:approval_id/decision
POST /api/session/reset
```

- SSE 事件有 Session 内递增 seq；落后或断线后前端重新取 snapshot，不把 SSE 当权威；
- reset 只在无活动 Run 和无 pending approval 时执行，否则 409；
- HTTP DTO、DemoSession、DemoRun 和 approval ID 全部留在 binary 私有模块。

### 10.6 内存审计

每条审计至少记录：

- seq、时间、run 本地 ID、call ID、tool name；
- resolved facts 的展示快照；
- 命中的 policy 名称和规则说明；
- 是否进入审批及用户决定；
- started/completed/cancelled/timeout；
- Shell exit code 或文件错误分类；
- 不记录 credential、完整文件内容或未截断输出。

审计只用于页面时间线，不进入 Core AgentEvent、Conversation Journal 或正式 Runtime。

## 十一、默认值与配置约定

首期冻结值：

| 配置 | 默认 | 上限/说明 |

| find/search max results | `100` | 单次最大 `1000` |

## 十四、风险、兼容与排除项

### 风险与控制

- **逻辑路径不是物理沙盒**：symlink 可访问名单目录外目标；facts、审批和文档始终使用
  “逻辑路径策略”措辞。
- **Shell 可绕过文件规则**：Plan 硬拒绝 Shell；Build + Ask 展示完整命令；
  Build + Auto 明确高风险。
- **类型擦除错配**：实际 payload 与 executor 封装在一次性对象内，Core 不接触 Any；
  移除公开 erased 注册旁路。
- **动态默认分叉**：同一配置对象同时驱动 schema 和 resolve，并以注册/契约测试固定。
- **进程树平台差异**：使用 process-wrap，Unix/Windows 分平台测试；不以直接 child
  kill 冒充整树清理；明确记录 Unix 主动脱离进程组的机制限制。
- **输出造成内存或反压问题**：stdout/stderr 并发排空，有界 channel，达到上限继续
  drain 但不继续累计。
- **本地 HTTP 暴露 Shell**：Demo 不做身份认证，同机进程可直接调用 API；监听限制为
  loopback，并保留严格 Origin/Host、POST 来源、无 CORS、CSP 和 no-store，降低浏览器
  跨站误触风险。启动页面必须明确这是当前用户权限下的开发验证工具。
- **TempDir drop 不是强恢复**：正常 shutdown/reset 显式 close；崩溃残留在验收中作为
  开发工具限制说明。

### 兼容性

- `Tool`、`FileSystemTool`、`ShellTool`、Dispatcher 和 ToolAuthorizer 是明确的
  `0.x` 不兼容迁移；所有 workspace 调用方同批更新。
- `ToolCall`、`ToolResult`、Conversation、Provider Codec 和
  `assistant-protocol` 不变。
- `ExecutionSpec` 新增 guardrails 字段，所有构造点显式传 None 或配置；无隐藏默认。
- `max_steps`、`max_tool_calls`、Recorder、取消、Context 和 Provider 行为保持现有
  语义。
- `assistant-runtime`、desktop、runtime-harness 私有契约不因 Demo 扩张。

### 本版本继续排除

- 正式 Approval Service/SPI 和审批持久化；
- AgentExecution 总超时和新增 Core 资源预算；
- No Progress Guardrail；
- Shell AST、风险解析、命令重写；
- OS 沙盒、权限降级或容器；
- 自动下载 rg；
- 二进制/多媒体文件工具；
- TTY、stdin，以及由 Session/Runtime 持有后台句柄并管理健康、停止或恢复的服务；
- 递归删除和创建 symlink；
- 正式 Runtime、桌面端和产品协议接线。
