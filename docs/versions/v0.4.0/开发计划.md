- 版本：`v0.4.0`

- 关联文档：
  - [`功能设计`](功能设计.md)（✅ 已确认 2026-07-31）

本计划只规定实施顺序、里程碑边界和验证门槛。公共类型、默认值、策略语义、文件与
Shell 行为、HTTP 安全和页面交互以已确认设计为准，不在本文件重复维护。

## 二、实施原则

1. M0 → M11 严格顺序实施。每个里程碑完成实现和验证后标记为 `🟨 待确认`并停止，
   获得用户明确确认后才进入下一里程碑。
2. 原开发计划确认只授权进入 M0；本次修订确认只授权进入 M11，不授权跳过 M11 直接
   恢复版本验收。
3. 先建立 workspace 和长期模块约束，再迁移 Tool SPI；公共契约变更必须在所属
   里程碑内同步迁移全部生产者和消费者，不保留新旧派发旁路。
4. `resolve`、授权和执行必须共享同一个 prepared/resolved invocation；Core 不解析
   原始 JSON，也不接触类型擦除载荷。
5. Core 只提供策略装配、Allow/Deny 和 Guardrail 机制；Plan/Build × Ask/Auto、
   白名单优先规则和一次性审批只由 Safety Demo 组织。
6. 文件与 Shell 真实执行只进入 `agent-tools-local`；Core 不直接访问文件系统或启动
   子进程。
7. 本版本对 `Tool`、文件/Shell capability、Dispatcher 和 Authorizer 进行明确的
   `0.x` 不兼容迁移，不为不存在的外部稳定调用方保留兼容层。
8. 自动测试只使用临时目录、脚本模型和受控子进程，不读取用户真实文件、不访问网络、
   不运行破坏性 Shell。
9. 真实 Provider 联调需要用户在对应里程碑再次明确授权；未获授权时记录为未执行，
   不以此阻塞确定性实现验证。
10. `assistant-runtime`、`assistant-protocol`、`apps/desktop` 和
    `tools/runtime-harness` 的私有 Session/Run/Context 编排不在本版本修改。
11. 每个里程碑开始前重新核对工作树和对应 Rust/前端/module 规范；发现设计与现状不符
    时停止扩大改动，先修订设计并重新确认。
12. M10 的原验收准备结论因最终 Review 发现 B1/S1 等问题而撤回；M11 只修正已确认的
    Review 项并重新建立验收候选，不借机扩展 Runtime、后台任务管理或通用抽象。

## 三、目标依赖结构

```text
agent-types ◄── agent-tools ◄── agent-core
                    ▲               ▲

                    ▲               │
```

- `agent-tools-local` 只依赖 `agent-tools` 和基础设施依赖，不依赖 Core、Runtime、
  Provider、Tauri 或 UI。
- `safety-demo` 是最上层的独立开发工具；产品 crate 不依赖它。
- `agent-core` 继续只依赖工具契约，不感知本地 Adapter 或 Demo 工作模式。
- `assistant-runtime` 本版本保持零代码、零依赖变化。
- 新增依赖限定为技术方案确认的 `path-absolutize`、`process-wrap` 和 `tempfile`，不得
  顺手引入 Shell parser、glob、文件遍历或前端框架。

## 六、M1：Resolved Tool SPI、Registry/Dispatcher 与全量迁移

### 目标

把工具调用稳定拆成反序列化、resolve 和一次性执行三个阶段，并在同一里程碑迁移全部
现有工具和调用方。

### 前置依赖

M0 已确认。

### 实施内容

- 在 `agent-tools` 新增 resolved 描述、typed facts、fingerprint、批次结果和一次性
  executor。
- `Tool` 改为技术方案规定的 `Input → ResolvedInput → Output` 生命周期。
- 工具定义由工具实例的动态默认值和 schema 一次冻结；注册时校验默认字段存在。
- Registry 只通过类型化 `Tool` 注册，移除公开 `ErasedTool/register_erased` 旁路。
- Dispatcher 提供 whole-batch resolve 和 resolved execute，保序返回 valid/invalid
  item；invalid item 不产生 executor。
- executor 与 resolved payload 封装在同一对象中，只能消费一次；公共 API 不暴露
  `Any`。
- 迁移标准文件/Shell 工具壳、agent-testkit `ScriptedTool`、runtime-harness demo
  tool、示例和测试。
- 本里程碑只迁移现有 capability 语义；文件/Shell 新契约留到 M4。

### 自动测试或人工核对

- schema 默认值与 resolve 后实际值一致，未知默认字段注册失败。
- unknown tool、JSON 反序列化失败和 resolve 失败均不产生 executor。
- whole-batch resolve 保序且单项错误不改变其他项。
- resolved arguments、facts 和 fingerprint 来自同一 resolved input。
- facts 类型不匹配返回 `None`；executor 不可重复消费。
- runtime-harness 既有场景和所有现有工具调用方完成显式迁移。
- 公开 API 中不存在新的裸类型擦除注册旁路。

### 验证

```bash
cargo test -p agent-tools -p agent-testkit
cargo test -p runtime-harness
cargo clippy -p agent-tools -p agent-testkit -p runtime-harness \
  --all-targets --all-features -- -D warnings
cargo fmt --all --check
```

### 完成判定

- 所有工具均通过唯一 resolve/execute 路径工作；
- workspace 中不存在仍按原始 JSON 直接执行的旧 Dispatcher 路径；
- Core 尚未改变授权顺序，策略与 Guardrail 尚未实现。

## 七、M2：Core resolved 批次授权与装配式策略

### 目标

让 Core 对完整 resolved batch 做授权，并提供不含业务模式的顺序策略装配机制。

### 前置依赖

M1 已确认。

### 实施内容

- `ToolAuthorizer` 改为接收 resolved invocation 公开描述，不再接收原始 `ToolCall`。
- 新增顺序 Policy Chain，策略结果仅为 `Allow / Deny / Continue`；全部 Continue
  时进入最终 Authorizer。
- 提供 General、File、Shell 类型化 policy adapter；每类 policy 只读取对应 facts。
- 提供显式 `AllowAllAuthorizer`，但不把 Auto、Plan 或 Build 写进 Core。
- Engine 在 Recorder pending exchange 后先 resolve 整个批次，再按原顺序处理
  valid/invalid item。
- invalid item 直接形成稳定错误结果，不进入 policy、authorizer 或 execute。
- valid item 的 policy、authorizer、审计事件和 executor 共享同一个 resolved 事实。
- 保持预算检查、取消、Recorder complete 优先级、Context 交接和终态可靠性。
- 同步 agent-testkit 的 scripted authorizer/policy/gate 和全部构造点。

### 自动测试或人工核对

- 第一条明确 Allow/Deny 生效，全部 Continue 才进入 fallback。
- typed policy 不处理错误 facts 类型。
- 前序 Deny 不能被后续 AllowAll 覆盖。
- invalid item 不进入任何授权或执行路径。
- 同一批次中 valid/invalid 混合时结果顺序和 Recorder 结算完整。
- Authorizer 展示的 facts 与 executor 实际使用的 resolved input 一致。
- 取消、预算拒绝、Recorder complete 失败和 v0.3 Context 终态不回归。

### 验证

```bash
cargo test -p agent-core -p agent-tools -p agent-testkit
cargo test -p runtime-harness
cargo clippy -p agent-core -p agent-tools -p agent-testkit \
  -p runtime-harness --all-targets --all-features -- -D warnings
cargo fmt --all --check
```

### 完成判定

- Core 可装配任意类型化 Allow/Deny 策略，但不知道 Plan/Build 或 Ask/Auto；
- 授权与执行使用同一个 resolved invocation；
- Guardrail 和真实 I/O 尚未进入 Core。

## 八、M3：Repeated/Consecutive Guardrail 与 Engine 收敛

### 目标

实现两个可选、可观察、可强制终止的通用 Guardrail，并保证批次、Recorder 和终态完整
收敛。

### 前置依赖

M2 已确认。

### 实施内容

- 新增 `GuardrailConfig` 及两个 `Option<GuardrailCheckConfig>`：
  Repeated Invocation、Consecutive Failures。
- 每项支持 Off（`None`）、Observe 和 Enforce；Core 不注入默认阈值。
- Engine 使用 resolved fingerprint 维护重复序列和连续失败计数。
- Repeated fingerprint 的文件/Shell构成严格遵循技术方案，Shell timeout 不进入
  fingerprint。
- 统一 invalid、Deny、ToolError、Timeout、Success、Shell nonzero exit 和
  cancellation 对连续失败状态的影响。
- Observe 每个越界序列只发一次事件但继续执行；Enforce 在副作用前终止当前项，并为
  当前项和剩余项形成完整结果。
- 增加明确 Guardrail 事件、错误分类和可靠终态；Recorder complete 失败仍优先。
- agent-testkit 增加确定性 detector、事件和批次收敛测试，不用 sleep 猜测顺序。

### 自动测试或人工核对

- 两个 detector 分别覆盖 `None / Observe / Enforce`、阈值边界和配置非法值。
- Observe 同一序列只通知一次，序列重置后可再次通知。
- Enforce 前不执行当前项或剩余项，但 Recorder exchange 保持完整。
- invalid、Deny、ToolError 和 Timeout 计失败；Success 与 Shell nonzero exit 重置；
  cancellation 不计失败。
- Guardrail 与授权、预算、取消、Context CompactionRequired 的优先级符合技术方案。
- 既有 Completed/Failed/Cancelled/CompactionRequired 可靠语义不回归。

### 验证

```bash
cargo test -p agent-core -p agent-testkit
cargo clippy -p agent-core -p agent-testkit \
  --all-targets --all-features -- -D warnings
cargo fmt --all --check
```

### 完成判定

- 两类 Guardrail 可由上层独立省略或配置；
- Observe 与 Enforce 的事件、执行和终态差异可确定性验证；
- Core 中不存在 Demo 默认阈值、模式或审批行为。

## 九、M4：文件/Shell capability 契约与 testkit fake

### 目标

完成真实 Adapter 所需的类型化路径、文件、Shell、输出和取消契约，并迁移所有标准工具壳
与 fake，不在本里程碑执行真实 I/O。

### 前置依赖

M3 已确认。

### 实施内容

- 在 `agent-tools` 引入基于 `path-absolutize` 的 `AbsolutePath`/`SessionPathResolver`，
  相对路径基于显式默认工作目录做词法归一化。
- 权限事实使用完整绝对逻辑路径，不用 canonical path 做权限判断。
- 文件 facts 包含 operation、resolved path 和模型可见有效参数。
- 文件请求显式携带 read offset/limit、search max results、edit replace_all 等默认。
- `FileEntryKind` 保留目标类型，symlink 作为正交标记；特殊文件使用稳定错误分类。
- `FileSystemTool` 增加执行取消上下文并完成 read/list/find/search/write/edit/delete
  契约迁移。
- Shell resolved facts 包含完整 command、resolved workdir 和 effective timeout。
- Shell launcher 配置保留平台默认 Shell 预设，command 原样交给 Shell，不解析 AST。
- Shell 输出改为分离 stdout/stderr、exit code、timeout/cancel/truncated 和输出 sink
  事件。
- 更新标准工具壳、agent-testkit fake、schema、错误映射、fingerprint 和所有构造点。

### 自动测试或人工核对

- 相对/绝对路径、`.`/`..`、不同默认工作目录和不存在目标均稳定 resolve。
- schema 中所有默认参数与 resolved facts 一致，LLM 不依赖隐藏默认。
- symlink 与 File/Directory 目标类型可同时表达。
- Shell command、workdir、timeout 和输出上限在定义、facts 和 fake 执行中一致。
- stdout/stderr 分离，非零退出仍是完成结果，不误判 ToolError。
- capability fake 可确定性模拟成功、I/O 错误、timeout、cancel 和 truncated。

### 验证

```bash

cargo test -p agent-core
cargo test -p runtime-harness
cargo clippy -p agent-tools -p agent-testkit -p agent-core \

cargo fmt --all --check
```

### 完成判定

- 文件和 Shell 的模型输入、授权 facts 与执行契约一致；
- 全部 fake 和现有 Harness 完成迁移；
- `agent-tools` 仍不访问真实文件系统或启动进程。

## 十、M5：真实本地文件 Adapter 与 ripgrep 搜索

### 目标

在 `agent-tools-local` 实现可取消、边界明确的真实文本文件能力，并将递归搜索委托系统
`rg`。

### 前置依赖

M4 已确认。

### 实施内容

- 实现真实 read/list/find/search/write/edit/delete。
- read 按 UTF-8 文本、显式 offset/limit 和文件大小上限工作。
- list 返回目标类型与 symlink 正交信息；不对系统原生 symlink 行为增加产品规则。
- write 直接写入 resolved 路径并正常跟随 symlink；edit 在持锁期间读取、精确替换、
  写前复核并写回目标；两者都不承诺原子替换。
- delete 文件或 symlink 时只删除该节点；普通空目录可删除，非空目录不递归删除，
  特殊文件拒绝。
- 增加按绝对逻辑路径的进程内共享路径锁，保证 write/edit/delete 串行。
- find/search 通过系统 `rg` 执行，不自行递归遍历；使用 `--no-config` 并保持 `rg`
  默认的 ignore、隐藏项和目录 symlink 行为，不额外传 `--hidden`、`--no-ignore`
  或 `--follow`。
- 解析 `rg` machine-readable 输出，落实结果上限、truncated、二进制跳过和稳定错误。
- 后端不可用时返回明确错误，不自动下载 `rg`。
- 所有自动测试只使用 `tempfile` 临时目录和仓库内受控 fixture。

### 自动测试或人工核对

- UTF-8 读取分页、空文件、超限、非 UTF-8 和特殊文件分类。
- list 普通文件/目录/symlink，symlink 目标为文件或目录时正交信息正确。
- write 新建/覆盖、edit 单次/replace_all/零匹配/多匹配和并发锁。
- 通过 symlink write/edit 修改目标；delete symlink 只删除链接本身。
- 取消发生在副作用前不写入；提交后取消不伪装成未执行。
- `rg` 内容/名称搜索、空结果、长路径、结果截断、二进制跳过和未安装错误。
- 路径 facts 与实际执行使用同一个 normalized absolute logical path。

### 验证

```bash
cargo test -p agent-tools-local filesystem
cargo test -p agent-tools-local search
cargo test -p agent-tools-local
cargo clippy -p agent-tools-local --all-targets --all-features -- -D warnings
cargo fmt --all --check
```

在系统存在 `rg` 时运行标记为 ignored 的真实 `rg` 临时目录用例，并单独记录命令和
结果；系统不存在时记录未执行原因。

### 完成判定

- 七类文件操作均有真实临时目录测试和稳定错误语义；
- 搜索只委托系统 `rg`，没有仓库自建递归遍历器；
- 没有读取用户真实项目或执行递归删除。

## 十一、M6：真实 Shell Adapter、进程树、输出与取消

### 目标

实现平台 Shell 启动、环境过滤、流式分离输出、上限、超时、取消和整进程树回收。

### 前置依赖

M5 已确认。

### 实施内容

- 实现平台 launcher：POSIX 使用技术方案预设 Shell，Windows 使用 `COMSPEC`/
  `cmd.exe`，允许构造时覆盖。
- command 原样作为 Shell 参数，不做语法解析、风险评分或命令重写。
- 以 resolved workdir 启动进程；工作目录只作为逻辑策略事实，不宣称系统沙盒。
- 构建敏感环境变量过滤和显式注入；审计只记录变量名摘要，不记录 credential。
- 使用 `process-wrap` 配置 Unix process group、Windows Job Object 和 kill-on-drop。
- 并发排空 stdout/stderr，通过有界 channel 流式输出。
- 合计达到输出上限后停止累计和推送新字节，但继续 drain，最终分别保存两个前缀并
  标记 truncated。

## 十六、M11：最终 Review 修正与重新验收准备

### 实施内容

#### A. Shell 生命周期与环境策略

- 在标准 Shell 工具输入、resolved 参数、`ShellAuthorizationFacts`、fingerprint、
  capability request/outcome、Demo 审批和审计中加入 `process_mode`；缺省为 `managed`，
  可显式选择 `detached`，不解析 command 猜测后台语义。
- 重构 Shell 执行状态机，使同一个绝对 deadline 和 cancellation 覆盖主 Shell 等待、
  stdout/stderr 收敛及清理阶段。
- managed 在主 Shell 正常退出后也终止并等待仍属于进程组/Job Object 的后代；timeout
  和 cancellation 保持 kill + wait。
- detached 只在主 Shell 退出且两条输出管道 EOF 后释放后代；此前 timeout/cancel 仍
  清理整组。它不创建 Session 后台句柄，不提供健康检查、自动停止或恢复。
- `EnvironmentPolicy::default()` 使用通用敏感后缀，增加显式 `inherit_all()`；Windows
  allow/deny/suffix/override 匹配和覆盖按 ASCII 大小写不敏感处理。
- 页面审批和结果明确展示 detached 风险，不把启动命令成功写成“服务健康”。文档记录
  Unix 后代主动逃离进程组的机制限制。

#### B. ripgrep 有界结果

- 保留 `rg --json`，将文件名 NUL 记录和内容 JSON 记录都改为追加前检查的有界 reader；
  不先把完整 record/stdout 读入内存再截断。
- resolved search request 同时冻结 `max_results`、`max_output_bytes` 和
  `max_record_bytes`；结果提供 `max_results`、`max_output_bytes`、
  `oversized_record` 三种稳定截断原因。
- 任一上限命中后终止并等待 `rg`，返回已得到的部分结果；超大单记录不生成 preview，
  让模型缩小路径或查询范围。
- stderr 持续排空但有限保留；主动停止统一复用 `terminate_and_wait`，不再分散维护
  kill/wait 错误路径。

#### C. 契约一致性与确定性测试

- 类型擦除边界把 resolve 阶段误返回的 `ToolError::Execution` 归一化为
  `InvalidInput`；只修正阶段语义，不新增错误 trait。

- 修正 Fake 中可表示但不可能由真实文件系统产生的状态：read 不把隐式目录当文件、
  list 不把文件当目录、write 不覆盖隐式目录；文档继续声明 Fake 不模拟空目录、
  symlink、特殊文件或全部 OS errno。

## 十九、实施顺序结论

v0.4.0 按以下依赖链推进：

```text
工程边界
→ Resolved Tool 闭环
→ Core 策略装配
→ Guardrail
→ 文件/Shell 契约
→ 真实文件
→ 真实 Shell
→ Demo 安全宿主
→ Demo 模式与审批
→ Demo 页面
→ 集成收口
→ 最终 Review 修正
→ 独立版本验收
```

该顺序保证每一步都有可编译、可测试、可确认的产物，同时把真实副作用和上层审批放在
底层契约稳定之后。本次修订确认后只进入 M11；M11 完成并经用户确认后，才重新进入独立
版本验收。
