## 阻断（1 条）

### B1. Shell 正常退出时不回收后台进程树，exec 可绕过 timeout/取消无限挂起

- 位置：`crates/agent-tools-local/src/shell.rs:166-173`、`shell.rs:219-220`
- 问题：`ProcessSignal::Exited(Ok(status))` 分支直接返回，只有 timeout/cancel 走
  `terminate_and_wait`。`sh -c 'sleep 300 & exit 0'` 场景下主 shell 秒退，但后台进程
  继承了 stdout 管道写端，`settle_output` 需等管道 EOF 才结束——此时 `select!` 已退出、
  timeout future 已 drop、取消 token 不再检查，exec 挂起到后台进程自然结束，
  **完全绕过 timeout 和 cancellation**。即使后台进程重定向了 stdout，exec 返回后
  后台进程仍存活，进程树泄漏。
- 依据：技术方案要求"Shell 主进程正常退出时……后台后代也被回收，满足 exec 返回即
  进程树结束"。本条直接违背本版本"安全与执行控制"的核心契约。
- 修复方向：Exited 分支在回收输出前对进程组执行 kill（组已空则无害），或给
  `settle_output` 加取消/超时兜底。

#### B1 处理结论（2026-08-02，用户已确认方案）

问题需要拆成“调用失去 timeout/cancellation”与“后台进程是否允许存活”两部分处理：

- `settle_output` 脱离原 timeout/cancellation 后可能无限等待的问题成立，必须修复；
- “主 Shell 正常退出后无条件 kill 整个进程组”的原修复建议不采用，因为用户存在明确
  的 fire-and-forget 场景，例如
  `nohup java -jar app.jar >app.log 2>&1 </dev/null & echo $!`；此时后台服务存活是预期
  副作用，不是进程泄漏；
- Shell 将显式区分默认 `managed` 与主动 `detached` 两种进程模式，不解析 command 猜测
  `nohup`、`&` 或其他 Shell 语法；进程模式进入 schema 默认值、resolved arguments、
  `ShellAuthorizationFacts`、fingerprint、审批和审计；
- `managed` 在主 Shell 正常退出、timeout 或 cancellation 后清理可管理进程树；
  `detached` 只在主 Shell 正常退出且 stdout/stderr 已收敛后释放所有权，启动阶段或输出
  收敛阶段发生 timeout/cancellation 时仍 kill + wait；同一绝对 deadline 覆盖等待主
  Shell 和等待输出的完整阶段；
- `detached` 只表示启动命令完成后不再由当前 Tool/Session 管理，不承诺服务已就绪、
  持续健康或能够自动停止；Session 级进程句柄、状态、日志游标和 stop 能力仍属于后续
  独立的受管进程能力；
- 实现时需要为 Unix ProcessGroup 与 Windows Job Object 分别验证释放所有权和
  kill-on-drop 行为，并补充 managed 后台清理、detached 存活、未重定向输出 timeout、
  cancellation 和测试自清理用例。

处置方案已于 2026-08-02 合并进权威功能设计、技术方案、界面指导和 M11 开发计划。
以下问题正文与处理结论保留处置阶段的历史状态；对应 Tool 契约与实现现已由 M11 完成。

## 严重（1 条）

### S1. 内容搜索对匹配行长度、单条 JSON 消息和总输出均无上限

- 位置：`crates/agent-tools-local/src/search.rs:150-172`
- 问题：`read_until(b'\n')` 无界缓冲，rg `--json` 对命中行输出完整 `lines.text`。
  命中几百 MB 的 minified 文件时：单行全量读入内存、全量 JSON 解析、完整行回喂模型。
  `max_results` 只限条数不限字节。read 路径有大小上限，search 是明显的不对称缺口。
- 修复方向：至少对单行做截断（保留前 N KB）并加总量上限，模块约束中写明。

#### S1 处理结论（2026-08-02，用户已确认方案）

问题成立，归档前需要修复；保留系统 `rg --json` 和现有结构化解析，不切换为自定义文本
分帧，也不在完整大 JSON 已进入内存后才做字符串截断：

- 为 stdout 实现真正有界的 JSON record reader；单条记录超过配置上限时不再继续扩容、
  不解析残缺 JSON，立即终止并等待 `rg`；
- 同时限制单次搜索读取的 stdout 累计字节数；达到总量上限或 `max_results` 时终止并等待
  `rg`，返回上限前已经完成解析的部分结果；
- `SearchFilesResult` 除 `truncated` 外增加稳定的截断原因，至少区分
  `max_results`、`max_output_bytes` 和 `oversized_record`，让模型缩小目录、收紧查询或
  改用更适合局部提取的工具；
- 超限记录不返回内容 preview：出现无法由人或模型合理阅读的单条结果，本身就是搜索
  范围或提取方式需要调整的控制信号；
- stderr 从无界 `read_to_end` 调整为“有限保留但持续排空”，防止错误输出形成另一条
  无界内存通道；
- 补充单条超限、累计超限、部分结果保留、三类截断原因、进程树清理、cancellation 和
  stderr 截断测试。

Safety Demo 的收口默认值确定为单记录 64 KiB、stdout 累计 1 MiB、stderr 保留
64 KiB；底层仍由构造配置注入。限制必须在读取/分配完整 record 之前生效。方案已合并
进权威设计和 M11 计划；该句记录处置当时状态，对应能力契约与实现现已由 M11 完成。

## 一般（核心代码）

### G1. resolve 阶段返回 `Execution` 错误未归一化

- 位置：`crates/agent-tools/src/tool.rs:265-268`
- 问题：技术方案规定 resolve 只可返回 `InvalidInput`，但类型系统不强制。实现不当的
  工具在 resolve 阶段返回 `Execution` 会被原样转为执行失败 ToolResult，绕过 Guardrail
  对"resolve 失败 vs 执行失败"的语义区分（污染连续失败计数）。
- 修复方向：擦除层把 resolve 返回的 `Execution` 归一化为 `InvalidInput`（或至少
  debug_assert）。

### G2. `Cancelled` 映射为模型可见文本依赖隐式跨 crate 约定

- 位置：`crates/agent-tools/src/standard/shell.rs:269`、`standard/fs.rs:104-108`
- 问题：技术方案明确 Cancelled 只用于控制传播、不回喂模型；当前保证完全依赖 engine
  侧取消收敛（engine.rs:415）。旧 builtin 实现有"此映射仅为类型完备"的注释，新代码
  丢失，后续维护者易误以为该分支会正常回喂模型。
- 修复方向：恢复注释，注明 Cancelled 分支的可达性前提。

### G3. FakeFileSystemTool 与真实实现多条边界路径错误变体不一致

- 位置：`crates/agent-testkit/src/fs.rs:72-245`
- 分歧明细（fake vs 真实 `LocalFileSystem`）：
  - read 目录路径：fake `NotFound` vs 真实 `UnsupportedFileType`（filesystem.rs:49-50）；
  - list 文件路径：fake `NotFound` vs 真实 `UnsupportedFileType`（filesystem.rs:191-192）；
  - write 覆盖隐式目录：fake 静默成功 vs 真实 `UnsupportedFileType`（filesystem.rs:87-90）；
  - delete 非空目录：fake `InvalidInput` vs 真实 `UnsupportedFileType`（filesystem.rs:146）；
  - search 不存在根路径：fake `Ok(空)` vs 真实 `Io`（search.rs:262-268）。
- 影响：fake 偏宽容，下游用 fake 断言错误分类时会在真实实现上失败。当前 fake fs
  未接入任何 harness，属潜在风险。
- 修复方向：对齐错误变体，或在 fake 文档中显式列出已知分歧（含空目录不可表达的
  连带差异：真实 delete/list 空目录成功，fake 报 `NotFound`）。

### G4. read 保留 BOM 但 edit 匹配前剥离 BOM，read→edit 往返确定性失败

- 位置：`crates/agent-tools-local/src/filesystem.rs:164-169` vs `filesystem.rs:294-300`
- 问题：read 输出含 `\u{feff}`（测试 filesystem.rs:500 明确断言），模型照抄该文本
  作为 `old_string` 调 edit 时，因 `prepare_edit` 先 strip BOM 再匹配，必然报
  "old_string not found"。
- 修复方向：read 也剥离 BOM，或 edit 对 old/new string 做同样的 BOM 归一。

### G5. Windows 环境变量名匹配区分大小写

- 位置：`crates/agent-tools-local/src/environment.rs:54-70`
- 问题：Windows 环境变量名大小写不敏感，但 `allow_exact`/`deny_exact` 用
  `BTreeSet<OsString>`、`deny_suffixes` 用字节级 `ends_with`，全部区分大小写。
  `deny_suffixes: ["_TOKEN"]` 挡不住 `github_token`；override 插入 `PATH` 时父环境
  `Path` 仍残留，可能注入重复键。Windows 无实机，静态审查结论：Unix 正确，Windows
  有绕过缺口。
- 附带：`EnvironmentPolicy::default()` 全透传（设计明确如此），但与根 AGENTS.md
  "敏感环境变量默认不传递给子进程"存在张力；当前只有 safety-demo 装配了 deny 规则。
  建议提供 `deny_common_secrets()` 构造器或在 `Default` 文档显著标注风险。

### G6. engine.rs 两处文档注释残缺/过时

- 位置：`crates/agent-core/src/engine.rs:509-512`（`converge_cancelled` 注释句子
  残缺，语义悬空）、`engine.rs:263-266`（`execute_batch` 注释未覆盖 Guardrail 终态

### G7. DeepSeek reasoning 校验边界用例缺口与误伤窗口

- 位置：`crates/agent-provider-openai-compatible/src/decode.rs:544-564`
- 缺用例：`"reasoning_content": ""`（空串）+ tool calls——DeepSeek 最可能偶发的
  形态，流式/非流式各缺一条；`reasoning_content: null` 流式用例缺失；有 text 无
  reasoning + tool calls 未覆盖。
- 误伤窗口：`Profile::deepseek()` 固定开启该校验（profile.rs:102-117），但调用方可

  reasoning 工具调用会被误判为 Protocol 错误。当前仓库内无此用法，建议在 profile
  文档显式声明"关闭 thinking 不属于本 Profile 的支持形态"。

## 处置建议

以下为 2026-08-02 逐项核查后的统一处置结论。原则是优先修复契约、安全和确定性缺口，
不为消除少量重复、统一展示风格或假想扩展增加抽象层。

### 归档前纳入统一收口

1. **B1：接受问题，调整原修复方向。** 按已确认的 `managed` / `detached` 显式生命
   周期和贯穿输出收敛阶段的 deadline/cancellation 方案处理，不解析 Shell AST，不在
   正常退出后无条件 kill 用户明确要求脱离的服务。
2. **S1：接受。** 保留 `rg --json`，增加有界 record reader、stdout 总量上限、有限
   保留并持续排空 stderr，以及可见的截断原因；不引入自定义搜索引擎或 JSON 流式
   tokenizer。
3. **G1：接受，但只做擦除边界归一化。** `Tool::resolve` 若错误地返回
   `ToolError::Execution`，在 `TypedToolErasure::resolve` 就地转换为 InvalidInput 结果并
   补测试；不新增 ResolveError trait 或拆分整套错误层级。原 Review 所称“污染连续失败
   计数”并不准确，因为当前 Guardrail 对 invalid 和 execution Tool Result 都按 Error
   计数；修复理由是维持 resolve/execute 阶段语义，不是改变失败计数。
4. **G2：接受。** 只恢复 Cancelled 映射分支的不可达前提注释，不改变 Engine 取消
   收敛或能力错误类型。
5. **G3：部分接受。** 修复 Fake 当前表示能力内的明显不可能状态：read 隐式目录、list
   文件、write 覆盖隐式目录，并补对应测试；不为对齐真实 OS 的所有错误变体给 Fake
   增加空目录、symlink、特殊文件或虚拟 errno 层。search 不存在根和非空目录删除等
   backend/表示相关差异写入 testkit 边界说明。
6. **G4：接受。** read 的模型可见文本不暴露 UTF-8 BOM；edit 继续识别并在物理文件中
   保留 BOM。这样 read → edit 不要求模型携带不可见字符，也不改变磁盘编码形式。
7. **G5：接受 Windows 实际安全缺口。** Windows 下 allow/deny/suffix/override 对环境
   变量名按 ASCII 大小写不敏感匹配，并在 override 前移除等价旧键，补平台条件测试。
   `EnvironmentPolicy::default()` 改为包含通用 `_API_KEY`、`_TOKEN`、`_SECRET` 后缀
   过滤；需要完整继承的测试或宿主必须显式选择，不增加 Provider 名单或复杂规则对象。
8. **G6：接受。** 修正文档注释，不抽取执行状态机辅助层。
9. **G7：部分接受。** 增加空字符串、null、有普通 text 但无 reasoning 的流式/非流式
   Tool Call 用例；明确 `Profile::deepseek()` 是 thinking-enabled Profile。Safety Demo
   已在请求装配时拒绝 disabled 冲突，本轮不为泛化一个当前不存在的调用方增加新的
   Provider option 校验框架。
10. **搜索 terminate：并入 S1。** 复用共享 `terminate_and_wait` 的错误语义，不能吞掉
    kill 失败或无界 wait。
11. **mutation lock 取消：接受。** write/edit/delete 等待同路径锁时直接用
    cancellation 与 lock acquisition 竞争，不新增锁管理抽象。
12. **低成本测试和文档：接受。** 补绝对路径 de-dot、越过 workdir、重复/尾部分隔符
    和 Windows drive-relative 条件测试；补标准 write/edit/delete 的
    resolve → execute 用例；注明 Unix process group 无法约束主动 `setsid/setpgid`
