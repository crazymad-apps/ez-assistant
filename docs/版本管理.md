## Runtime 阶段版本路线

后续仍按照“Runtime 业务能力 → 应用协议 → 独立 Harness 回证 → Tauri 展示”的顺序推进。
`v0.21.0` 已完成并归档，在 `v0.20.0` 主控会话底座上建立了进程内 Gateway 逻辑边界、智能终端
发现与配对、WSS/PCM、语音与文字输入、播报 Tool、PC 输出托管、Node/H5 验证，以及 Session
单一输入和同 Run 多 Loop 编排；Desktop 继续使用 HTTP Command + SSE。实际结果见
[`版本总结`](versions/v0.21.0/版本总结.md)。
`v0.18.0`—`v0.20.0` 也均已完成并归档；`v0.20.0` 在不引入复杂任务编排、通知或真实外部
渠道的前提下，建立了主控会话、会话消息代理、clear 和用户主动 `/compact` 闭环，并修复空闲
会话发送消息时待发送区短暂闪现。实际结果见
[`v0.20.0 版本总结`](versions/v0.20.0/版本总结.md)。

`v0.18.0` 已以相互独立但可协同的 Todo、Goal 和 Composer 执行入口形成长任务产品闭环：
工作计划提供 Session 级常驻总体目标与 Todo，Goal 以本次完整 UserMessage 为 objective，
由 Runtime 持有预算、世代和跨 Run 续跑控制状态，
Desktop 在 Composer 顶边以不占布局高度的浮层展示工作计划；完整审批窗口与输入框互斥，
窗口收起后待审批入口位于 Queue 上方且两者都占布局高度。底栏收敛为添加、执行设置、上下文用量、
模型设置和发送/停止五个常驻视觉项。当前范围、技术取舍与实施顺序见
[`v0.18.0 功能设计`](versions/v0.18.0/功能设计.md)和
[`v0.18.0 技术方案`](versions/v0.18.0/技术方案.md)、
[`v0.18.0 开发计划`](versions/v0.18.0/开发计划.md)。

`v0.14.0`–`v0.14.2` 已完成并归档，正式 Desktop 已具备主会话、输入、队列、审批、会话资源、
附件、子 Agent 观察、设置、权限管理和原生生命周期闭环。桌面 MVP 因同时
涉及正式协议、Runtime、Host、WebView 和原生平台边界，拆为 `v0.14.0`–`v0.14.2` 三个连续、
可独立回证的实施版本；功能设计与技术方案保持一份统一基线，不为补丁版本复制。该路线不再是验证
Runtime 的 Demo 美化，而是建设正式桌面产品闭环。已确认 Demo 提炼出的视觉与交互基准见
[`桌面端设计语言`](resources/桌面端设计语言.md)；已完成桌面 MVP 的功能范围见
[`统一功能设计`](versions/v0.14.0/功能设计.md)，实现级方案见
   [`统一技术方案`](versions/v0.14.0/技术方案.md)。`v0.15.0` 已进一步完成记忆、冻结上下文、
   Conversation Recall 与历史来源导航闭环，详见 [`版本总结`](versions/v0.15.0/版本总结.md)。

## 后续能力地图

以下方向排在桌面 MVP 之后，具体版本号在前序能力稳定后确认：

Agent 工具图片回传与 Responses API 已由 `v0.17.0` 完成，详见
[`版本总结`](versions/v0.17.0/版本总结.md)。Todo、Goal 与 Composer 执行入口已由 `v0.18.0` 完成，
本地 Skills 与内插时间线已由 `v0.19.0` 完成，主控会话与简单代理通信底座已由 `v0.20.0`
完成；其余候选方向如下，具体版本号在前序能力稳定后确认：

1. **MCP 与插件**：形成外部工具/资源连接、可启停、可诊断且受权限约束的扩展生命周期；
   是否引入插件包、市场或远程安装须由后续版本另行确认。
2. **自动化与后台任务**：持久计划任务、后台 Job、执行记录、重启补跑、通知意图和投递目标。
3. **多客户端与渠道**：`v0.21.0` 已建立智能终端、来源/目标、PC 输出托管和附加投递基线；移动端、
   IM、用户身份、频道、线程、通知和外部投递路由仍由后续版本设计。
4. **系统后台生命周期**：在桌面链路稳定后接入 macOS 菜单栏、Dock、LaunchAgent 以及其他平台
   的用户级后台运行、崩溃拉起和受控停止机制。
5. **可替换执行环境**：在本地文件与 Shell 能力之外，按实际需要装配容器、SSH 或远程文件系统，
   不改变 Agent Core 与 Runtime 的既有能力边界。

## Runtime 阶段共同约束

- 输入可靠性：客户端意图先形成持久化输入事实，再唤醒 Session 执行器；重复请求必须可幂等识别，
  不能因连接重试重复追加消息或执行副作用。
- 会话并发：不同 Session 可以并发，同一 Session 中改变规范对话的父 Run 默认串行；父 Run 内的
  子 Agent 可以并行，但不得直接并发修改主 Conversation，结果由父 Run 汇总并结算。
- 文件去重：上传附件以“原始文件名 + 文件字节”的 Blob Hash 与大小识别不可变文件正文；同名同内容可以只保存一次，
  同内容不同名不复用。Session 和用途保存在独立引用中。Workspace 内的可变文件仍按路径和修订管理。
- 权限分层：Plan/Build 先限定能力上限；Session、Workspace 和 Global 使用独立权限文件，
  交互审批只能产生仅本次、Session 或 Workspace 允许，Global 规则只能手工维护。
  明确 Deny 和必须询问规则不能被历史 Allow 或 Auto 覆盖；其余规则按 Session、
  Workspace、Global 从具体到宽泛匹配，并在对应 Plan/Build 变体中生效。
- 配置与上下文：全局配置、会话冻结事实和单次 Run 覆盖必须分开；模型、工具、权限、Instructions、
  Pinned Memory 等变化不能静默改写正在运行或恢复中的 Session Snapshot。
- 数据生命周期：持久化不仅包含正常读写，还必须为 schema migration、备份、导入导出、归档、
  清理、损坏诊断和恢复保留正式入口。
- 集成回证：每个业务模块都使用正式 Runtime 重新验证 Core 候选 API，再决定哪些接口进入稳定承诺。

路线图只确认能力顺序和长期约束，不预先决定数据库产品、Repository 物理拆分、具体 Hash 算法、
UI 信息架构或插件 ABI；这些实现问题由对应版本技术方案基于真实代码和依赖核查确定。

## 版本与输入规则

- 状态统一使用：`待启动`、`设计中`、`计划中`、`开发中`、`验证中`、`已完成`、`已暂停`。
- 尚未纳入版本的想法保存在 [`docs/inputs/`](inputs/)；只有与当前版本目标一致的输入才进入
  功能设计，其他输入继续保留。
- 每个版本形成一个可独立验收的能力闭环，并依次经过设计、计划、分里程碑确认、验收和归档。
- 版本状态以用户确认和实际阶段为准；归档完成不依赖 Git commit、tag 或 push。
- 逻辑组件边界遵循 [`Agent 系统技术架构`](modules/agent-system.md)；物理 crate、协议和存储形态
  在对应版本设计中确认。
