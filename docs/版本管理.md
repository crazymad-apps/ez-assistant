# ez-assistant 版本管理

本文只维护当前版本状态、阶段路线和已归档版本入口。具体范围、设计、实现过程与验证证据以
对应版本归档为准；流程规则统一见 [`开发流程规范`](specs/开发流程规范.md)。

## 当前阶段

- 当前目标版本：`v0.9.0`。
- 状态：`待启动`。
- 已完成基线：`v0.8.0` 已建立正式 `assistant-runtime`、轻量应用协议、独立 Runtime Host 和
  真实跨进程 Agent 执行闭环。
- 当前开发重点：建立 Runtime Home、版本化配置、模型管理和凭据引用，形成第一个可由正式
  Runtime 持有并由客户端管理的全局业务能力闭环。
- 应用边界：Tauri 是展示层和桌面平台适配层；Session、Conversation、Run、Harness、策略、
  审批、工作区、记忆、调度、持久化和事件记录等产品业务由 Runtime 持有权威状态。
- 长期物理架构：桌面 UI 与 Runtime 分进程运行；Session 不创建操作系统子进程，而是在同一
  Runtime 进程内按逻辑控制器和 Tokio 异步任务管理。该方向由后续版本逐步实现。
- 最近完成：[`v0.8.0 版本总结`](versions/v0.8.0/版本总结.md)。
- 下一步：进入 `v0.9.0` 功能设计，确认 Runtime Home、配置、模型与凭据的功能范围和成功标准。

## Runtime 阶段版本路线

后续按照“Runtime 业务能力 → 应用协议 → 独立 Harness 回证 → Tauri 展示”的顺序推进。下表用于
明确相邻版本的目标和依赖；各版本的完整范围、非目标、实现选择和验收标准仍由对应功能设计确认。

| 版本 | 主题 | 主要能力闭环 |
| --- | --- | --- |
| `v0.9.0` | Runtime Home、配置与模型管理 | 建立全局根目录、版本化配置、模型配置的增删改查、默认模型、能力声明、连接验证、凭据引用和最小诊断；每条可执行模型配置继续直接绑定 protocol、provider、endpoint、credential 与 model，不建立“账户 → 模型”业务层级。 |
| `v0.10.0` | 可靠会话与持久化执行 | 持久化 Session、Message、Run 和 Journal；用户输入先落账再唤醒执行，支持请求幂等、同 Session 输入排队、恢复、retry、undo、branch、archive、事件游标以及数据迁移、备份、导入导出和保留清理。 |
| `v0.11.0` | Workspace、附件与系统上下文 | 管理会话工作目录、临时工作区、附件、Artifact 和项目 Instructions；以内容 Hash 校验并复用相同 Blob，业务引用与物理内容分离；新会话冻结 System Context Snapshot，既有会话通过明确更新演进。 |
| `v0.12.0` | Harness、分层权限与真实工具 | 正式接入 Plan / Build、Ask / Auto、Guardrail、文件与 Shell；权限规则支持单次 Run、Session、Workspace/工作目录和 Global 作用域，覆盖审批、规则保存、审计、长期后台进程和工具产物管理。 |
| `v0.13.0` | 子 Agent 与任务委派 | 建立父 Run 与子任务关系、独立上下文和工作区视图、权限收敛、取消与审计；同一父 Run 内允许多个子 Agent 并行执行，主 Session 的规范对话仍由父 Run 串行结算。 |
| `v0.14.0` | 正式桌面端 MVP | 在前述 Runtime 契约稳定后进入桌面端正式功能与交互设计，完成 Runtime Client、启停与托盘、重连、Session、模型、Workspace、审批和子任务执行树等产品入口。 |

完成 `v0.13.0` 后，Runtime 已具备支撑正式桌面设计所需的主要业务契约；`v0.14.0` 不再是验证
Runtime 的 Demo 美化，而是按“功能设计 → 交互设计 → 技术方案 → 开发计划 → 实现验收”建设
正式桌面产品闭环。

## 后续能力地图

以下方向排在桌面 MVP 之后，具体版本号在前序能力稳定后确认：

1. **记忆与长期助手能力**：正式装配 Pinned Memory、RecallSource、历史会话检索、Persona 和
   System Context 来源管理。
2. **Skills、MCP 与插件**：形成可发现、可启停、可诊断且受权限约束的扩展生命周期，不把工具
   注册、数据源选择或模型 Provider 固化在 Runtime 主流程中。
3. **自动化与后台任务**：持久计划任务、后台 Job、执行记录、重启补跑、通知意图和投递目标。
4. **多客户端与渠道**：在保持桌面优先的前提下，为未来消息来源、用户身份、频道、线程和投递
   路由保留稳定扩展边界。
5. **系统后台生命周期**：在桌面链路稳定后接入 macOS 菜单栏、Dock、LaunchAgent 以及其他平台
   的用户级后台运行、崩溃拉起和受控停止机制。
6. **可替换执行环境**：在本地文件与 Shell 能力之外，按实际需要装配容器、SSH 或远程文件系统，
   不改变 Agent Core 与 Runtime 的既有能力边界。

## Runtime 阶段共同约束

- 输入可靠性：客户端意图先形成持久化输入事实，再唤醒 Session 执行器；重复请求必须可幂等识别，
  不能因连接重试重复追加消息或执行副作用。
- 会话并发：不同 Session 可以并发，同一 Session 中改变规范对话的父 Run 默认串行；父 Run 内的
  子 Agent 可以并行，但不得直接并发修改主 Conversation，结果由父 Run 汇总并结算。
- 文件去重：上传文件和定稿 Artifact 以内容 Hash 与大小识别不可变 Blob；相同内容只保存一次，
  文件名、来源、Session 和用途保存在独立引用中。Workspace 内的可变文件仍按路径和修订管理。
- 权限分层：Plan / Build 先限定能力上限；规则按单次 Run、Session、Workspace/工作目录、Global
  从具体到宽泛匹配，具体作用域不能突破能力上限。同一作用域内明确 Allow 与 Deny 冲突时以
  Allow 为准，未匹配动作再交给 Ask / Auto 和该层默认策略处理。
- 配置与上下文：全局配置、会话冻结事实和单次 Run 覆盖必须分开；模型、工具、权限、Instructions、
  Pinned Memory 等变化不能静默改写正在运行或恢复中的 Session Snapshot。
- 数据生命周期：持久化不仅包含正常读写，还必须为 schema migration、备份、导入导出、归档、
  清理、损坏诊断和恢复保留正式入口。
- 集成回证：每个业务模块都使用正式 Runtime 重新验证 Core 候选 API，再决定哪些接口进入稳定承诺。

路线图只确认能力顺序和长期约束，不预先决定数据库产品、Repository 物理拆分、具体 Hash 算法、
UI 信息架构或插件 ABI；这些实现问题由对应版本技术方案基于真实代码和依赖核查确定。

## 版本与输入规则

- 状态统一使用：`待启动`、`设计中`、`计划中`、`开发中`、`验证中`、`已完成`、`已暂停`。
- 尚未纳入版本的想法保存在 [`docs/inputs/`](inputs/)；只有与当前版本目标一致的输入才进入
  功能设计，其他输入继续保留。
- 每个版本形成一个可独立验收的能力闭环，并依次经过设计、计划、分里程碑确认、验收和归档。
- 版本状态以用户确认和实际阶段为准；归档完成不依赖 Git commit、tag 或 push。
- 逻辑组件边界遵循 [`Agent 系统技术架构`](modules/agent-system.md)；物理 crate、协议和存储形态
  在对应版本设计中确认。
