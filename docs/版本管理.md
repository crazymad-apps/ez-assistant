### 手机原生 App 与后续路线

**手机端需要独立的原生 App 开发计划，不能用 Web 移动适配代替。** Web 响应式布局只解决
手机浏览器的访问体验；Desktop、Web、CLI、手机原生 App 是不同的客户端形态，共用 Runtime
能力与业务协议。手机 App 首批平台、技术路线、版本号和交付顺序尚未确定。

后续手机 App 设计应讨论：

- 登录、节点选择、会话输入／查看、审批、停止与附件；
- 系统通知、录音、拍照、文件选择和系统分享等移动设备能力；
- 切后台、锁屏、网络切换后的通知和恢复体验，任务执行仍归 Runtime。

后续方向保留跨节点 Agent 协作、融合文件空间、持久自动化，版本号暂不固定。此前
“v0.26 完整 Web 工作区与手机体验 → v0.27 协作 → v0.28 文件 → v0.29 自动化”的编号不再
作为当前排期，完整 Web 工作区先按上表讨论，原生 App 单列规划。

- 跨节点协作：A 委派 B，B 汇报完成、阻塞或待决策事项，用户可进入 B 原会话介入；复用现有
  会话代理与语音路由基础，具体可靠交付与通知机制另行设计。
- 融合文件空间：跨节点发现、读取、预览、引用文件和产物；优先把修改／测试委派给文件所属
  节点。多端并发写、同步冲突、会话迁移和操作系统级挂载不预先纳入。
- 持久自动化：时间触发、暂停／取消、执行记录、重启策略和通知，复用既有 Session 输入、Goal
  与预算；不把目前长任务能力视为已经具备持久调度。
- [整套配色主题](inputs/260905-整套配色主题预设与切换方案.md)已有独立讨论结论，版本归属仍待定。

### 访问认证：单所有者、只设置密码

用户明确当前不考虑多账号、多租户，**每个 Runtime 只设置一个访问密码，不需要用户名、注册
或完整账号体系**。本节替代此前所有者账号、联合身份签发方、OAuth 及细粒度角色的候选展开，
不为这些假想需求提前建设机制。

- 所有 Web 都需要认证，包括本机、内网和外网；普通入口使用密码登录，Desktop 标题栏的
  “打开 Web 端”快捷入口可携带普通登录 token 快速登录。复用同一认证机制，不增加一次性票据
  和独立兑换体系；处理后清除链接 token。登录后仍检查权限，不因同源或本机来源免认证。
- 本机 Desktop 通过私有 bootstrap 自动认证；远程 Desktop 使用目标地址和密码，本机启动
  凭据不直接分发到远程入口。CLI 在 v0.25.2 复用本机连接能力。
- v0.25.0 设置中直接设置／修改密码，不增加忘记密码、找回或独立重设流程。空密码或未设密码时
  Host 禁止开启非本地来源访问；远程 Desktop／Web 允许 HTTP，HTTPS 可选。认证有效期、改密
  失效、两种协议的 Cookie／终端和 HTTPS 信任路径见已定稿技术方案。
- Desktop 入口页兼作加载页并静默启动本机 Runtime，由用户选择本机或其他 Host，不自动连接
  上次目标；同时只连接一个 Host。主界面不返回入口页，通过设置切换，直接丢弃未发送草稿，
  不提供独立取消连接。macOS 可选 Keychain 记住对应目标密码，仍由用户手动连接。
- 首版按单所有者使用，不预设多角色或逐会话 ACL；既有 Plan／Build、工具权限和审批继续有效。
- 密码用于人访问 Runtime，节点长期身份和配对凭据属于另一机制；不通过复制密码建立节点网络，
  不让中继保存业务访问密码。密码安全存储、可选 HTTPS 接入与登录保护在技术方案中落实。
  允许客户端 HTTP 直连不改变后续 Runtime 间端到端加密与中继密文转发的独立要求。

节点授权目前仅确认指导原则：显式建立信任、连接不等于业务授权、可以撤销。同连一个中继
不自动互相信任。“允许对方管理整个节点”只是简化候选，尚未固定为产品机制；配对方法、授权
范围、确认位置、撤销影响及其交互，到对应实现阶段结合方案继续讨论，并在实施前明确。

### Runtime 间通信：保留业务基线，增加外层安全传输

用户明确本次讨论的通信协议指 **Runtime 与 Runtime 之间的外层包装**。全盘保留现有
HTTP Command、Snapshot、SSE、Streaming Upload 及其业务协议基线，不为组网另造会话命令、
事件模型、业务回执或文件协议，也不默认全面替换 SSE。

```text
既有 HTTP Command / Snapshot / SSE / Streaming Upload
                         ↓
               节点传输适配／隧道
                         ↓
             加密直连，或经中继转发
                         ↓
                  对端既有应用服务
```

- 外层只处理连接、对端身份、目标寻址、流承载、关闭与传输错误等职责。透明隧道还是薄流映射、
  封装格式及接口需后续验证，不提前定义新 JSON 消息分类或并行协议体系。
- 直连／中继变化不改变业务身份、目标节点和权限；恢复沿用既有快照、请求及事件机制。
  中继收包不等于目标 Runtime 接纳任务，不因传输超时生成新的业务输入。
- 默认加密，包括内网通信；目标是 Runtime 两端之间端到端加密。中继只接触转发密文及必要的
  路由／流量元数据，不能读取聊天、文件和业务操作。加密与配对身份核验采用成熟实现，不自创算法。
- 长期节点身份应跨重启保持；首次建立信任和后续连接认证分开。加密连通不替代目标业务授权。
- 直连优先、中继兜底；不承诺所有 NAT／防火墙都能穿透。中继必须对参与节点可达，首阶段按
  单中继部署评估，多级中继、高可用和全网自动发现不预先建设。

### 中继与 Runtime 的职责隔离

**中继领域与 Runtime 业务领域保持独立，不因同机部署或同进程装配而耦合。**

| 职责 | 承担内容 | 边界 |
| --- | --- | --- |
| 中继 | 连接接入、密文转发、流控与服务使用限额 | 不识别会话、消息、审批、任务或文件业务，不判定 Runtime 业务授权 |
| 节点通信适配 | 对端身份验证与既有应用协议的传输适配 | 不创建第二套会话业务，不把打洞／中继细节传入业务层 |
| Runtime 业务 | 既有命令、权威状态和业务权限判定 | 不依赖具体中继或直连路径，不复制远端权威状态 |

- 中继可以限制谁能使用转发服务，这与谁能操作目标 Runtime 是两种授权。
- S 可以同时运行自己的 Runtime 和提供中继，物理装配方式待技术方案验证；不能因此混合两者
  的状态、协议和生命周期。中继故障与 S 自身 Agent 任务应隔离。
- 若用户登录 S 的 Web，由 S 代表用户访问 B，S 的应用接入／客户端职责会接触业务内容；此时
  S 是业务调用方。它与 S 单纯为 A—B 转发密文的中继职责必须分别表达和实现。
- 中继不创建远端 Session／Run 副本、业务离线任务队列或中心任务调度。B 始终持有自身会话、
  Run、审批和文件的权威状态；不把既有语音设备 Gateway 协议直接当作节点协议。

### 传输选型候选与待验证项

QUIC + TLS 1.3 及 iroh 是本轮提出的候选，**尚未确定采用**。iroh 的形态如下：

- [`iroh`](https://docs.rs/iroh/latest/iroh/) 是可嵌入的 Rust 网络库，提供加密连接与流，并处理
  直连、打洞及中继路径；可评估为外层字节通道，不承载本项目业务协议。
- [`iroh-relay`](https://docs.rs/iroh-relay/latest/iroh_relay/) 提供中继库和独立服务器程序；
  可自托管，是否嵌入 Host 另行评估。
- [官方托管中继](https://docs.iroh.computer/concepts/relays)属于可选服务，不是采用库的前提。
  若选用，须明确自有中继、发现配置及是否使用公共基础设施，不能隐式依赖默认公共服务。
- 加密依据见 [QUIC TLS 标准](https://www.rfc-editor.org/rfc/rfc9001.html)和
  [iroh 安全说明](https://docs.iroh.computer/deployment/security-privacy)。此前 WebRTC／ICE／TURN
  讨论保留为背景，不构成已选定的路线。

后续验证包括现有 HTTP／SSE／Upload 的承载兼容、自托管中继、受限网络、跨平台支持、连接恢复、
资源限额与职责装配。协议包装、库版本、节点发现、配对交互及撤销机制均待相应设计与实现阶段确认。

## Runtime 阶段共同约束

- 输入可靠性：客户端意图先形成持久化输入事实，再唤醒 Session 执行器；重复请求必须可幂等识别，
  不能因连接重试重复追加消息或执行副作用。
- 会话并发：不同 Session 可以并发，同一 Session 中改变规范对话的父 Run 默认串行；父 Run 内的
  子 Agent 可以并行，但不得直接并发修改主 Conversation，结果由父 Run 汇总并结算。
- 文件去重：上传附件以“原始文件名 + 文件字节”的 Blob Hash 与大小识别不可变文件正文；同名同内容可以只保存一次，
  同内容不同名不复用。Session 和用途保存在独立引用中。Workspace 内的可变文件仍按路径和修订管理。
- 权限分层：Plan/Build 先限定能力上限；Session、Workspace 和 Global 使用独立权限文件，
  交互审批只能产生仅本次、Session 或 Workspace 允许，Global 规则只能手工维护。
  明确 Deny 和必须询问规则不能被历史 Allow 或 Auto 覆盖；其余规则按 Session、
  Workspace、Global 从具体到宽泛匹配，并在对应 Plan/Build 变体中生效。
- 配置与上下文：全局配置、会话冻结事实和单次 Run 覆盖必须分开；模型、工具、权限、Instructions、
  Pinned Memory 等变化不能静默改写正在运行或恢复中的 Session Snapshot。
- 数据生命周期：持久化不仅包含正常读写，还必须为 schema migration、备份、导入导出、归档、
  清理、损坏诊断和恢复保留正式入口。
- 集成回证：每个业务模块都使用正式 Runtime 重新验证 Core 候选 API，再决定哪些接口进入稳定承诺。

路线图只确认能力顺序和长期约束，不预先决定数据库产品、Repository 物理拆分、具体 Hash 算法、
UI 信息架构或插件 ABI；这些实现问题由对应版本技术方案基于真实代码和依赖核查确定。

## 版本与输入规则

- 状态统一使用：`待启动`、`设计中`、`计划中`、`开发中`、`验证中`、`已完成`、`已暂停`。
- 尚未纳入版本的想法保存在 [`docs/inputs/`](inputs)；只有与当前版本目标一致的输入才进入
  功能设计，其他输入继续保留。
- 每个版本形成一个可独立验收的能力闭环，并依次经过设计、计划、分里程碑确认、验收和归档。
- 版本状态以用户确认和实际阶段为准；归档完成不依赖 Git commit、tag 或 push。
- 逻辑组件边界遵循 [`Agent 系统技术架构`](modules/agent-system.md)；物理 crate、协议和存储形态
  在对应版本设计中确认。
