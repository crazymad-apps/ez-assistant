# ez-assistant 重要决策与变更记录

本文只保留跨版本长期有效的架构和协作决策。当前模块细节以
[`Agent 系统技术架构`](modules/agent-system.md)和对应 `docs/modules/` 文档为准；版本过程、
验证数字和临时实现放入版本归档，不在这里重复。

已被替代的方案不再与现行决策并列保留正文，替代关系统一记录在文末，避免读者误把历史方案
当成当前约束。

## 当前有效决策

### 260812 · 工具历史与中断恢复分层 · 已确认

- **决策**：不建立逐 Tool Call 永久审计表、resolved facts 副本或公开审计查询。
  持久权限以 Global/Workspace/Session 三级 JSON 规则为准；正式工具历史以
  Conversation 中成对的 Tool Call/Tool Result 为准；pending approval 是活动 Run 的内存状态。
- **恢复事实**：只在 pending tool exchange 生命周期内持久已越过副作用边界的
  call ID。完整 Tool Result 落盘后级联清理；重启时用它区分“未开始”与
  “已开始但结果未知”，两者都不自动重新执行。
- **理由**：永久 facts 投影与权限文件、Conversation 和实时审批状态重复，会引入
  不必要的保留、隐私、一致性与数据增长问题。临时 started 事实已足以解决不可
  重放的工具副作用恢复问题。

### 260810 · Runtime Host 统一 HTTP 通信口径 · 已确认

- **决策**：正式 Runtime Host 从 v0.11.0 起统一使用 HTTP 应用协议。默认只启用
  本地 Host，并只绑定 IPv4 loopback 动态端口。远程 Host 是默认关闭的可选能力；
  后续如显式启用，必须使用 HTTPS 和远程身份，并复用同一组 Command、SSE、
  Streaming Upload 路由和业务 DTO。
- **取舍**：项目尚未对外稳定发布，不为 v0.8.0 的 Unix Domain Socket、私有
  length-prefixed frame 和握手保留并行兼容层。附件通过独立 HTTP 路由流式传输，
  不把 Base64、字节数组或客户端本地源路径塞入普通 Command。
- **本地安全边界**：Host 每次启动生成高强度进程级 Bearer Token，以当前用户
  私有发现文件交付地址、实例身份和 Token。Tauri Rust 启动层可将连接配置注入
  受信任 WebView，由 WebView Runtime Client 直连 Host，不必代理每个请求。所有路由均校验
  Token、Host 和 Origin；默认只允许精确登记的 Tauri WebView Origin，不允许通配符
  CORS。Token 只存在于 WebView 内存，不进入 URL、持久前端存储、事件或日志。
  纯浏览器直连本地 Runtime 保留为默认关闭的未来开放选项，启用时需独立授权与
  Origin 白名单。这些措施不声称隔离同用户恶意进程。
- **范围**：v0.11.0 只实现本地 HTTP Host 与其验证客户端；可选远程开关与部署、TLS 终结、
  用户身份、多租户数据边界、断点续传和远程运维仍由后续版本明确实现。
- **影响**：本决策只替代 v0.8.0 的 Host 传输实现，不改变桌面 UI/Runtime 双进程、
  Runtime 的业务权威状态、Host 的适配层定位或“客户端断开不取消 Run”的生命周期语义。

### 260717–260805 · UI/Runtime 双进程分层架构与阶段重心 · 已生效

- **决策**：产品采用桌面 UI 与 Runtime 双进程、Runtime 内部模块化架构。Tauri 进程只承载
  WebView、桌面平台适配和 Runtime Client；独立 Runtime Host 是正式产品进程，承载
  `assistant-runtime`、Agent 装配和业务权威状态。Runtime 是 Session、Message、Run、Journal、
  调度、持久化和后台任务的权威所有者；Core 只负责一次 `AgentExecution`；WebView 只发送意图
  并展示 Runtime 状态。
- **理由**：核心业务需要在桌面客户端退出后继续运行，并为后续后台任务、计划任务和多种客户端
  保留统一入口；同时 Runtime/Core 分层仍需阻止 Agent Engine 反向依赖产品调度、存储或部署形态。
- **并发与生命周期**：Session 不创建会话级操作系统子进程。不同 Session 在同一个 Runtime Host
  中使用 Tokio 异步并发，同一 Session 中改变上下文的 Run 默认串行，历史 Session 不绑定永久
  线程。关闭窗口、退出桌面客户端和停止 Runtime 是三个动作；客户端断开不默认取消 Run，停止
  Runtime 必须走受控关闭。
- **阶段变化**：`v0.1.0`–`v0.7.0` 已完成 Agent Core 候选能力阶段。后续开发重点转向正式
  `assistant-runtime`、`assistant-protocol` 和桌面应用闭环；先确定 Runtime 权威状态和恢复
  语义，再固化跨层协议与 UI，不从 Demo 反推产品契约。
- **边界**：Runtime Host 是产品进程，不是新增 `tools/*` Demo，也不因独立进程自动等同
  于系统 daemon 或常驻 Worker 池。`v0.8.0` 只建立手动启动的正式进程入口和最小本机
  通信；`v0.11.0` 经独立设计决策将通信统一为 HTTP，但不同时引入系统托管。
  LaunchAgent、开机启动、崩溃拉起、托盘控制和完整桌面重连由后续版本实现。Shell、MCP 等工具
  启动的子进程与独立开发工具不构成 Session 进程或额外产品 Runtime。

### 260727–260804 · Agent Core、SDK 与 Runtime 的执行边界 · 已生效

- **决策**：Core 接收冻结的 `ExecutionSpec`、完整 `ExecutionInput` 和包含 cancellation、Recorder、
  Authorizer 的执行控制面；不加载 Session、不分配业务 RunId、不解释应用配置，也不等待 UI。
  Agent Loop、工具结算、预算与 Guardrail 只有一套实现。
- **理由**：便利入口可以减少装配样板，但不能复制 Agent 状态机或把 Runtime 的动态所有权隐藏
  进一个长期复用对象。
- **SDK**：`agent-sdk` 是 Core 的薄 Facade。一个 Agent 保存其生命周期内冻结的模型、System Prompt、
  Context Window 判断器、ToolSet、请求配置、Budget 与 Guardrail，但不保存动态 Conversation、
  Session、Run、Journal、审批、Store 或调度状态；最终仍调用唯一的 `AgentExecution::start`。
  Agent 的实际生命周期由上层 Host 决定；正式 Runtime 自 `v0.9.0` 起为每个 Run 编译独立 Agent。
- **权威记录**：Runtime 在用户消息落账后构造规范 Conversation Snapshot，并为每个 Run 注入绑定
  Session/Run 的 Recorder、Authorizer 和事件适配器。完整 Assistant Tool Call 必须在副作用前由
  Recorder 确认，Tool Result 批次完成后再原子结算；普通事件流不是恢复事实源。
- **并发**：同一 Session 串行由 Runtime 保证，不由 SDK 隐藏加锁；不同 Agent 可共享线程安全
  ModelService、工具能力和其他底层资源。

### 260729–260804 · Context 能力与 Runtime 编排所有权 · 已生效

- **决策**：窗口判断、规范历史布局、replacement 校验和压缩策略位于共享 `agent-context`；Core
  在每个 Model Step 前预检，并以 `CompactionRequired` 可靠终态把后继动作交回上层。Provider
  只报告 provider-neutral overflow，不在流建立后隐藏重试或压缩。
- **理由**：Context 算法需要被 Core 与 Runtime 复用，但 Session、Checkpoint 和恢复策略是产品
  编排，提前公开 Demo 类型会固化尚未验证的 Runtime 契约。
- **Runtime 责任**：Run 前判断、用户消息落账、Checkpoint、主动压缩、continuation、恢复次数和
  并发控制属于正式 Runtime。压缩后必须启动新的 AgentExecution，且不能破坏 Provider State、
  Tool Call/Result 配对或已完成 Turn。
- **验证与产品契约**：`runtime-harness` 和 `core-demo` 已验证上述行为，但其中 Session、Run、
  Checkpoint、Journal 和 continuation 类型均为私有样例。正式 Runtime 应复用下层算法与行为
  证据，不能直接复制 Demo 类型或文件格式。

### 260731 · 工具机制、安全策略与审批分层 · 已生效

- **决策**：`agent-tools` 保持 Tool SPI、Registry/Dispatcher、能力契约和标准工具壳；真实本地
  文件与 Shell 机制位于 `agent-tools-local`。Dispatcher 先无副作用 resolve，再让 Authorizer、
  Guardrail 和执行器共同使用同一份类型化冻结事实，避免重复解析原始 JSON。
- **理由**：文件、Shell 和通用工具需要不同的类型化授权事实；真实 I/O 与上层策略分离后，
  本地或远程 Adapter 才能替换且不会污染 Core。
- **授权**：Core 的最终结果只有 Allow/Deny；Deny 转换为错误 ToolResult。Plan/Build 表达能力
  上限，Ask/Auto、规则保存、审批交互与无人值守策略由 Runtime Authorizer 组织；Auto
  不能覆盖明确 Deny，无法识别的授权事实必须 fail-closed。
- **安全边界**：结构化文件策略不是 OS 沙盒，Shell 以当前用户权限运行并可能绕过文件规则；
  workdir 也不是沙盒。Runtime 负责工作目录、策略、确认、敏感环境过滤和中断恢复，Adapter 负责
  文件 I/O、进程、输出、超时、取消和进程树清理。

### 260803 · Pinned Memory 与 RecallSource 分层 · 已生效

- **决策**：少量常驻 Pinned Memory 在创建 Session 时确定性渲染进 System Prompt，并随完整
  System Prompt Snapshot 冻结；Store 修改只影响后续新 Session，恢复、继续、压缩续接和分支复用原
  快照。
- **理由**：常驻 System Prompt 信息与按需检索具有不同的生命周期和上下文成本，合并成统一 Memory
  Service 会模糊冻结语义并让 Core 承担应用编排。
- **检索记忆**：大量或外置信息通过普通 `recall_memory` 工具召回；`RecallSource` 只表示可替换
  数据源，多来源协调、超时、排序、去重和部分失败位于工具背后的实现。Source 是否对 LLM 可见
  由 System Prompt、Skill 和授权决定。
- **所有权**：`agent-memory` 只承载实现无关的领域与能力契约，不建立 `agent-memory-local`。
  正式 Runtime 负责选择 Store/Source Adapter、持久化冻结的 System Prompt 和装配记忆工具；Memory Demo
  的 JSON、Session、Journal 与 CLI 不是产品契约。

### 260724–260804 · 模型配置与 Provider 隔离 · 已生效

- **决策**：每条应用模型配置直接包含 protocol、provider、endpoint、credential 和 model；不设
  “账户 → 模型”两层结构。endpoint、credential、model 与 context window 在配置编译时绑定到
  ModelService 实例，切换模型就是切换完整服务句柄。
- **理由**：调用目标是配置期事实，system/conversation/tools 等是调用期语义输入；混在每次请求
  中只会产生冗余路由校验和 Provider 配型分支。
- **请求边界**：`ModelRequest`/`ModelRequestConfig` 只承载 system、conversation、tools、tool
  choice、generation、reasoning 和命名空间化 Provider options 等单次语义输入，不携带路由或
  credential。Runtime 负责编译配置，Core 不按 Provider 名称分支。
- **协议隔离**：Provider 特有 reasoning、tool call、opaque state 和响应字段由具体 Codec 保真
  往返；例如 DeepSeek 对 reasoning content 的要求只能存在于 Adapter 和契约测试中。

### 260806 · Runtime 配置所有权与模型绑定 · 已生效

- **配置所有权**：`v0.9.0` 首期使用 Runtime Home 下由用户手工维护的版本化配置文件；Runtime
  负责读取、显式 reload、静态校验和脱敏诊断，不提供软件内 CRUD、写回或 revision。正式桌面模型
  管理在 `v0.14.0` 与 Runtime CRUD、原子保存和冲突处理一起实现。
- **默认位置**：Runtime Home 固定为当前用户主目录下的 `~/.ez-assistant`，Host 启动时解析为
  绝对路径，`--runtime-home` 继续提供显式覆盖。该选择采用 Hermes 一类本地 Agent 的单根目录
  可发现性；不照搬 OpenCode 的 XDG 配置/状态分层，因为当前 Runtime 只有一个权威数据根。
  未发布早期实现使用过的 macOS Application Support 路径不参与自动回退，避免形成双配置源。
- **schema 演进**：能够保持旧配置含义和默认行为的扩展不提升 schema version；破坏性变化才
  升版，并由配置入口在内存中把仍受支持的历史格式转换为当前统一配置，读取和 reload 不自动
  写回。桌面端未来可在用户显式编辑并保存时覆盖为最新格式，但支持版本范围、原子替换与冲突
  处理在 `v0.14.0` UI/CRUD 设计中再具体确认；v0.9.0 不提前建立只有单一版本的迁移框架。
- **credential**：每条模型配置直接保存 API Key，不建立 credential 实体或跨模型引用，不从
  环境变量、`.env`、CLI 或系统凭据存储读取；不同模型允许填写相同 Key，Runtime 不去重或校验
  相同关系。配置文件及其副本属于敏感数据，secret 不进入应用协议读响应、事件、错误或普通日志。
- **绑定粒度**：模型配置维度下 Session 只冻结用户输入的 model key，同时继续独立冻结已经渲染
  完成的 `SystemPromptSnapshot`；每个 Run 开始前按当前有效配置解析 endpoint、credential、model
  和静态上限，并复用 Session 冻结的 System Prompt 执行规格。配置 reload 只影响后续 Run 的模型配置，不
  重建 System Prompt，也不改变活动 Run；Session 切换 model key 的 Runtime 能力已在 `v0.10.0`
  完成，正式桌面入口仍归 `v0.14.0`。
- **配置维度**：context window 和模型最大输出是模型静态硬上限；Transport/Retry 是 Runtime 模型
  通信策略；Generation 与 max steps/tool calls 是 Agent 默认和执行限制；tool choice 与是否启用
  reasoning 由 Run 业务流程在 Profile 允许范围内决定。配置中的 provider 表示实际供应商，
  protocol 表示 wire API 契约；兼容 Profile 由 Runtime 根据 provider 推导，不要求用户另填。
  DeepSeek Profile 恒启用 reasoning、只接受 `ToolChoice::Auto` 默认语义；其他供应商默认使用
  不开启 reasoning 的标准 Chat Completions Profile。有效单轮输出取模型硬上限与 Agent 请求
  上限的较小者。

### 260807 · Runtime 有界关闭与 Host 子任务观察 · 已生效

- **有界关闭**：Runtime 受控关闭必须有明确等待上限。正常路径先停止新工作、传播取消并等待
  Run supervisor；超时后终止仍未退出的 supervisor，把尚未结算的活动 Run 记录为脱敏内部失败，
  随后允许 Runtime Host 退出，不能无限等待不响应取消的模型、工具或 Recorder。
- **任务所有权**：Runtime 显式持有 supervisor 的终止能力；Host 显式观察连接 writer/event
  与信号任务结果，正常取消可忽略，panic/JoinError 必须进入稳定 Host 错误。Core 内部执行任务
  对 panic/JoinError 的完整所有权已由 `v0.10.0` 的 execution-owned observer 实现；Core、Runtime、
  Store worker 和 Host 各自观察本层任务，不依赖外围兜底掩盖内部异常。

### 260723–260803 · 观察、Trace 与重试边界 · 已生效

- **开发观察**：`tools/debug-viewer` 是独立开发工具，通过 POST 接收并以 SSE 展示 `llm`、
  `agent`、`runtime` 三类通道；产品进程只建立出向推送，不监听调试端口。Viewer 事件允许丢失，
  不进入 `assistant-protocol`，也不是 Journal 或 Full Trace 的权威来源。
- **理由**：UI 增量、业务恢复事实和完整诊断副本在可靠性、敏感度及保留周期上不同，必须使用
  各自的数据链路，不能为了记录方便建立一套平行且会漂移的业务事件模型。
- **库内观测**：模型、Provider、Core 和工具层只产出本层原生事件或安全观察接缝；tracing 仅记录
  模型标识、耗时、计数和终态等元数据，禁止 credential、prompt、响应正文和工具内容。库不初始化
  subscriber，消费与持久化归应用进程。
- **完整 Trace**：Runtime 负责关联 Session、Run、AgentExecution、逻辑模型调用和 attempt，并
  决定录制模式、访问权限、保留与删除。Full Trace 包含 prompt、reasoning、工具参数和响应正文，
  属于高敏诊断副本；认证信息在记录类型构造前排除。Trace 失败只标记 Incomplete，不改写 Agent
  结果；Journal 失败仍是权威业务错误。
- **回放与重试**：Wire Replay 重走 Provider Decoder，Model Replay 重现规范模型服务，二者均不
  执行历史工具、审批或 Journal 副作用。通用重试只允许显式、有限、可取消地处理
  `ModelService::stream()` 建流前结构化瞬态错误；一旦返回事件流就不透明重试。

### 260726 · 版本主线与确认门禁 · 已生效

- **决策**：开发以版本为唯一主线，依次经过目标确认、功能设计、所需技术/交互设计、开发计划、
  分里程碑实现、版本验收、归档和提交准备。具体规则统一由
  [`开发流程规范`](specs/开发流程规范.md)定义。
- **理由**：版本是范围、设计、实现和验收的共同主键；分阶段确认可以防止临时推断进入长期
  契约，也让验证证据与实际改动保持对应。
- **门禁**：每个里程碑完成实现与验证后必须等待用户确认；计划确认不等于后续里程碑自动获批。
  版本状态由实际阶段和用户确认驱动，归档完成不依赖 Git 提交。
- **文档职责**：未纳入版本的输入留在 `docs/inputs/`，在途事实放入 `docs/design/` 和本地开发
  进度，长期模块约束放入 `docs/modules/`，完成版本移入 `docs/versions/`。根 `AGENTS.md` 是统一
  开发约束入口。

### 260812 · 工具默认串行与显式并行资格 · 已生效

- **决策**：工具在注册时冻结 `Serial` / `ParallelEligible` 内部执行属性，默认 `Serial`；属性不
  进入 Provider 可见 Tool Definition 或授权规则。Core 只并发连续、全部显式具备并行资格的调用，
  Invalid 与 Serial 项都是不可跨越的顺序屏障。
- **可靠边界**：并行组仍逐调用独立授权，并在启动任何执行 future 前完成预算预留和每项 started
  记录；组内 future 全部收敛后，结果按原 Tool Call 顺序观察 Guardrail 并原子完成 tool exchange。
- **理由**：不能从 read/write、工具名或模型批次自动推断外部副作用是否独立。默认串行维持历史
  行为，显式资格只提供调度能力；具体业务工具仍需自行承担任务独立性和并发上限。

## 已整合的替代关系

- 260806 前已完成版本使用的 Unix Domain Socket 和私有 frame 保留为历史验证事实；
