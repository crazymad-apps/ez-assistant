- **260803 · v0.6 完整 Trace、分层回放与模型建立重试边界 · 已确认**
  - 决策/变更：正式完整 Trace 由 Runtime 关联 Session、Run、AgentExecution、逻辑模型
    调用和 attempt 并负责持久化生命周期；Core、Model、Provider 和工具层只暴露各自原生
    事实与观察接缝，不直接落盘。Trace 复用完整 `ModelRequest`、`ModelEvent`、`AgentEvent`
    和 Runtime/Journal 事件，只新增 Provider wire 与 retry attempt 事件。记录失败只将 Trace
    标为 Incomplete，不改变模型或 Agent 结果；Wire Replay 重走 Provider Decoder，Model
    Replay 重现规范模型服务，Timeline 只读，均不重新执行历史工具、审批或 Journal 副作用。
    通用模型重试只允许处理 `ModelService::stream()` 直接返回的建流前结构化瞬态错误，策略
    必须显式、有限、可取消、可观察；事件流建立后的任何失败都不透明重试。
  - 原因：只有记录真实语义请求、Provider 编码请求与原始响应，才能可靠复现线上模型协议
    问题；另建平行 Trace 事件会与既有原生事实漂移。Trace 是诊断副本而非权威 Journal，不能
    因磁盘或观察背压破坏正常执行。建流后 delta 可能已经可见，透明重试无法无损回滚或拼接，
    因而必须把同一步重试严格限制在尚未返回事件流的边界。
  - 影响与后续动作：`agent-model` 增加结构化错误、attempt 事件和可装配建立重试；
    OpenAI-compatible Adapter 增加安全 wire 观察；v0.6 使用顶层 `tools/reliability-demo`
    私有验证 JSONL、Complete/Incomplete、Wire/Model Replay 和 Timeline，不修改正式 Runtime、
    Protocol 或 Desktop。未来 Runtime 可复用下层接缝，但不得直接把 Demo 文件、metadata、
    宿主事件或 CLI 提升为产品契约。

- **260803 · v0.5 Pinned Memory 与 RecallSource 分层 · 已确认**
  - 决策/变更：长期记忆拆为两个独立子域。少量 Pinned Memory 在新建 Session 时
    确定性渲染为 System Prompt Part，并随完整 Prompt Snapshot 冻结；Store 修改只影响
    后续新 Session，恢复、继续、压缩续接和分支复用原快照。大量或外置信息仅通过固定
    `recall_memory` 普通工具召回，`RecallSource` 只表示数据源适配器；Source 可见性由
    System Prompt/Skill 表达，多来源协调与降级属于工具背后的实现。Core 不增加
    MemoryService、Memory 专用阶段或公共 Orchestrator，v0.5 不实现自动观察与整合。
  - 原因：Pinned 信息与按需检索的生命周期、上下文成本和修改语义不同；将二者塞入统一
    Memory Service 会模糊工具与 Prompt 边界，并让 Core 承担应用编排。固定工具定义可以
    复用现有授权、Recorder 和 Tool Loop，Source 仍可替换为本地、远程或混合实现。
  - 影响与后续动作：新增实现无关的 `agent-memory` 和顶层 `tools/memory-demo`；标准
    记忆工具壳归 `agent-tools`。Demo 私有实现 JSON Store、RecallSource、Session 和
    Journal，仓库不创建 `agent-memory-local`，正式 Runtime、Protocol 与桌面应用在本
    版本不改代码，未来接入时自行确定正式 Adapter 与持久化契约。

- **260731 · v0.4 策略/审批分层与真实工具 Adapter 落点 · 已确认**
  - 决策/变更：Agent Core 只接收 resolved tool invocation、组合通用/文件/Shell
    类型化策略并得到最终 Allow/Deny；Plan/Build 是能力上限，Ask/Auto 由上层
    Authorizer 作为 fallback 组织，`Ask` 不进入 Core 状态机。真实文件与 Shell
    机制新增独立 `agent-tools-local` 基础设施 Adapter，`agent-tools` 保持纯 Tool
    SPI/Registry/Dispatcher/能力契约；正式 `assistant-runtime` 本版本不改代码，
    由独立 `tools/safety-demo` 临时验证 Session 工作目录、Plan 临时工作区、审批、
    真实副作用、取消和审计。结构化文件权限按词法归一化后的绝对逻辑路径判断，不以
    canonical target 构造物理沙盒；已允许路径中的符号链接可被读写编辑，删除链接只
    删除链接本身。Shell 继续以当前用户权限运行，默认过滤 Provider credential 等
    敏感环境变量，工作目录和文件策略均不得表述为 Shell 沙盒。
  - 原因：文件、Shell 与通用工具需要不同的类型化规则，固定全局 whitelist 无法
    表达；授权原始 JSON 会使策略与实际执行重复解析并可能产生差异。真实机制直接放入
    `agent-tools` 会引入 OS I/O 和子进程依赖并破坏现有纯契约边界，只写在 Demo 又会
    导致未来 Runtime 重写。正式 Runtime 总体接口仍未设计，不应把临时审批和 Session
    类型提前固化为产品契约。
  - 影响与后续动作：本决策替代 260727“真实文件/Shell 机制直接进入
    `agent-tools`、策略进入 Runtime”的物理落点；长期“机制与策略分离”原则继续有效。
    v0.4.0 需要新增本地 Adapter 与 Safety Demo，并同步 Tool/Dispatcher/Authorizer、
    Guardrail 和模块文档；后续 Runtime 可复用 Adapter，但不得直接提升 Demo 私有
    API。

- **260728 · Debug Viewer 分层通道与 Runtime 推送选择 · 已确认**
  - 决策/变更：debug-viewer 始终在同一实例中接收 `llm`、`agent`、`runtime` 三个通道，不按启动项固定单一事件层；浏览器只做通道展示筛选。`llm` 承载 Adapter 解码后的规范 `ModelRequest` / `ModelEvent`，`agent` 承载强类型 `AgentEvent`，`runtime` 承载 Run、Session、Journal 与调度事件。原先尚未实际使用的 `DebugChannel::Sched` 在 v0.2.1 更名为 `DebugChannel::Runtime`。Runtime 推送方可选择 `provider`、`agent` 或 `both`，其中 `agent` 包含 Agent + Runtime 两个通道，`both` 为默认。debug-viewer 作为上层独立开发工具可以直接依赖 `agent-core`；Core、Provider 库和产品协议不依赖 viewer。
  - 原因：viewer 同时观察模型、Agent 和 Runtime 三层更利于关联排障；接收端常驻多通道比启动多个互斥实例简单。`sched` 无法准确覆盖 Run 生命周期和 Journal 等非调度事件，且尚无实际生产者，现在更名没有迁移成本。强类型 `AgentEvent` 比 JSON 中转更直接，不会造成产品依赖反转。
  - 影响与后续动作：v0.2.1 功能设计与技术方案已同步；实现时更新 debug-viewer 线格式、客户端、页面筛选、模块约束和测试，并由 `tools/runtime-harness` 的 ModelService decorator 与 Agent/Run 消费器按选择推送。这里的 provider 事件不包含原始 SSE frame、HTTP header 或 credential。

- **260727 · v0.2.0 审查修订：授权语义、预算预检、取消结算与 ExecutionSpec 定名 · 已生效**
  - 决策/变更：依据 [`v0.2.0 代码审查`](versions/v0.2.0/代码审查.md) 统一六处方案与实现口径。① 授权：Core 只保证逐 Tool Call 独立过闸（`authorize → Allow 即 dispatch`），不设"整批放行才执行"的引擎规则；审批编排（串行询问、攒批询问、规则自动放行）归 Runtime authorizer 实现，`authorize(call, batch)` 携带本轮批次上下文供其实现批次审批交互。② Deny 语义：Deny 在授权闸处转换为错误 ToolResult，回喂模型、驱动循环继续的唯一载体是 error ToolResult，对模型与循环不存在"被拒绝"类别；reason 措辞归 Runtime。③ 预算：`max_steps` 模型调用前预检、`max_tool_calls` dispatch 前预检（副作用前硬边界）；同批超额时未执行调用先结算错误 ToolResult 再以 `BudgetExceeded` 受控终止。④ 取消：收敛为 `ExecutionCancelled` 前由 Core 为批次内未结算调用补记 interrupted 错误 ToolResult，journal 的 Tool Call/Result 配对不破坏。⑤ `ExecutionPlan` 更名 `ExecutionSpec`，避免与后续 plan 模式的任务规划产物歧义；四字段（无 `context`）维持 260726 确认结论。⑥ Registry 不变量加固：`ToolDefinition` 注册时冻结（重名检查、快照定义与名称索引不再受实现方动态定义影响）；类型化工具 `input_schema` 由擦除层固定以 `Input` 派生，`register_erased` 自定义实现自行负责一致性。
  - 原因：审查发现功能设计"全部放行后执行"与技术方案"逐 call 交错"互相矛盾、预算检查晚于工具副作用、取消后 journal 可能残留未配对 Tool Call、Registry 重名与 schema 同步不变量依赖实现方自觉、`ExecutionPlan.context` 共享事实不一致；`ExecutionPlan` 命名与 plan 模式冲突越晚改成本越高。批次语义参考 opencode 调研结论：其"并行交错"由 AI SDK 并发派发决定且不存在批次预授权，在串行引擎上逐 call 独立过闸 + Runtime 侧编排是更干净的边界。
  - 影响与后续动作：功能设计（§4.2/§4.7/§六/§七）、技术方案（§4.2/§六/§七）、开发计划（M3/M4）、`agent-system.md`（§5.1/§10.4）、`agent-core.md`（权限预留/核心约束）、`agent-tools.md`、`assistant-runtime.md`、`assistant-protocol.md`、`版本管理.md`、inputs 长任务调研已同步；`agent-tools` Registry/擦除层修复与回归测试随 M1 重新验证；authorizer 批次上下文在 M3 落地；M4 Harness 增补同批 Allow+Deny、取消结算配对与预算四类边界用例；审查原文随版本归档至 `docs/versions/v0.2.0/代码审查.md`。

- **260724 · 模型层 tracing 埋点约定 · 已生效**
  - 决策/变更：明确模型层（`agent-model` 与 Provider Adapter）tracing 埋点约定：库代码只在调用边界 emit span/事件（`stream` 建立、唯一终态、受控失败），字段限定模型标识三元组（provider/protocol/model，来自服务构造期绑定）、耗时、delta/事件计数等元数据；任何字段不得携带 credential、prompt 正文、响应正文（与 `ModelError` 脱敏边界一致）。库不初始化 subscriber，subscriber 归应用进程（v0.2.0 起为 Runtime/desktop 进程）。`v0.1.0` 不实施埋点代码：进程内尚无 subscriber 归属，提前埋点无法验证且空增依赖；开发期可见性由 debug-viewer 的结构化事件承担，`v0.2.0` Runtime 接入时按本约定补齐埋点。
  - 原因：tracing 是"库内 emit、应用进程消费"的观测通道；没有 subscriber 归属时实施埋点既无法验证也无消费方。
  - 影响与后续动作：260723 调试查看器决策中"模型层只产出规范事件与 tracing 埋点"的实施时点由本条目明确为 `v0.2.0`；届时字段命名与脱敏边界以本约定为准。

- **260724 · 模型配置形态与调用目标归属 · 已生效**
  - 决策/变更：应用的模型配置采用一层结构：每条模型配置直接携带 protocol、provider、endpoint、credential、model（及可选连接/生成偏好），用户直接切换模型，不设"先选账户再选模型"的两层结构。模型层 SPI 的归属边界由此确定：endpoint、credential 与 model 全部属于服务实例的构造期参数，一个服务实例即一条编译完成的模型配置；`ModelRequest` 退化为纯语义输入（system/conversation/tools/generation 等），不携带任何路由信息；`ModelRoute` 类型、`check_route` 校验与 `ModelError::Route` 变体一并删除（代码审查 3.1 先移除 `ModelRoute.endpoint`，本条为最终收敛）。Runtime 不做 provider 与 model 的运行时配型：一条模型配置在配置编译期一次性编译为一个服务实例，切换模型即整体切换服务句柄，配型问题结构性不存在。
  - 原因：本地优先场景没有多账户/组织语义，两层配置是过度设计；"一连接多模型"确认为伪需求，请求级携带路由三元组只剩冗余与永不失败却必须维护的运行时校验。调用目标（配置期才变化）与语义输入（每次调用可变）是两类东西：前者归服务构造参数，后者归请求。
  - 影响与后续动作：Runtime 的模型配置存储（`v0.2.0+`）按一层形态设计；模型条目在配置加载时编译为服务实例（构造期绑定 endpoint/credential/model/超时），运行时按条目整体取用；同 provider 多条目（官方、自建网关）是各自独立的配置与服务实例；事件与响应消息中的模型身份来自线上响应（chunk/response 的 `model` 字段 + Profile 的 provider），不依赖请求；调试通道的 endpoint/model 由推送方从服务构造参数填写。
