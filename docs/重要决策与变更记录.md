- **260727 · 真实文件/Shell 工具实现的落点与实施时点 · 已确认**
  - 决策/变更：真实 `FileSystemTool`/`ShellTool` 实现采用"机制归 agent-tools、策略归 Runtime"的分层：`agent-tools` 承载机制层基础设施实现（本地 fs 读写、子进程 spawn、流式 stdout/stderr、超时、取消、输出上限等执行机制）；Runtime 以装饰器包装机制实现，注入策略层（工作根目录圈定、路径逃逸防护、权限审批、审计、敏感环境变量过滤策略）。Core 与契约保持不变，真实实现经 `FsReadTool::new(real_fs, ...)` 等装配进 `ToolRegistry`。v0.2.0 不实施真实实现，本版本无调用方（引擎测试只用 fake），实施时点归后续 Runtime 接线版本，与权限/审计机制（路线图 v0.4.0 安全与执行控制）同批设计。
  - 原因：真实实现的难点与风险在策略层而非 I/O 机制，策略依 `AGENTS.md` §四属 Runtime 职责，提前实施会造成"能力已完成"的错觉且缺乏验收抓手；机制层独立于策略可测试、可复用，`agent-tools` 作为独立 crate 是机制层的自然归属。
  - 影响与后续动作：v0.2.0 范围与开发计划不变；后续 Runtime 接线版本设计真实工具时按本分层落地，机制实现入 `agent-tools`（模块约束同步更新 `docs/modules/agent-tools.md`），策略装饰器入 `assistant-runtime`；届时 `agent-system.md` §四相关表述按实际落点核对一次。

- **260727 · v0.2.0 审查修订：授权语义、预算预检、取消结算与 ExecutionSpec 定名 · 已生效**
  - 决策/变更：依据 [`v0.2.0-代码审查.md`](design/v0.2.0-代码审查.md) 统一六处方案与实现口径。① 授权：Core 只保证逐 Tool Call 独立过闸（`authorize → Allow 即 dispatch`），不设"整批放行才执行"的引擎规则；审批编排（串行询问、攒批询问、规则自动放行）归 Runtime authorizer 实现，`authorize(call, batch)` 携带本轮批次上下文供其实现批次审批交互。② Deny 语义：Deny 在授权闸处转换为错误 ToolResult，回喂模型、驱动循环继续的唯一载体是 error ToolResult，对模型与循环不存在"被拒绝"类别；reason 措辞归 Runtime。③ 预算：`max_steps` 模型调用前预检、`max_tool_calls` dispatch 前预检（副作用前硬边界）；同批超额时未执行调用先结算错误 ToolResult 再以 `BudgetExceeded` 受控终止。④ 取消：收敛为 `ExecutionCancelled` 前由 Core 为批次内未结算调用补记 interrupted 错误 ToolResult，journal 的 Tool Call/Result 配对不破坏。⑤ `ExecutionPlan` 更名 `ExecutionSpec`，避免与后续 plan 模式的任务规划产物歧义；四字段（无 `context`）维持 260726 确认结论。⑥ Registry 不变量加固：`ToolDefinition` 注册时冻结（重名检查、快照定义与名称索引不再受实现方动态定义影响）；类型化工具 `input_schema` 由擦除层固定以 `Input` 派生，`register_erased` 自定义实现自行负责一致性。
  - 原因：审查发现功能设计"全部放行后执行"与技术方案"逐 call 交错"互相矛盾、预算检查晚于工具副作用、取消后 journal 可能残留未配对 Tool Call、Registry 重名与 schema 同步不变量依赖实现方自觉、`ExecutionPlan.context` 共享事实不一致；`ExecutionPlan` 命名与 plan 模式冲突越晚改成本越高。批次语义参考 opencode 调研结论：其"并行交错"由 AI SDK 并发派发决定且不存在批次预授权，在串行引擎上逐 call 独立过闸 + Runtime 侧编排是更干净的边界。
  - 影响与后续动作：功能设计（§4.2/§4.7/§六/§七）、技术方案（§4.2/§六/§七）、开发计划（M3/M4）、`agent-system.md`（§5.1/§10.4）、`agent-core.md`（权限预留/核心约束）、`agent-tools.md`、`assistant-runtime.md`、`assistant-protocol.md`、`版本管理.md`、inputs 长任务调研已同步；`agent-tools` Registry/擦除层修复与回归测试随 M1 重新验证；authorizer 批次上下文在 M3 落地；M4 Harness 增补同批 Allow+Deny、取消结算配对与预算四类边界用例；`docs/design/v0.2.0-代码审查.md` 作为历史记录保留原文。

- **260717 · 整体技术架构 · 已生效**
  - 决策/变更：采用单进程模块化架构；Tauri 负责应用与系统能力，Runtime 持有会话、Run、调度和持久化，Agent Core 负责单次执行。模型、工具、记忆和安全能力保持可替换；文件能力结构化开放，Shell 作为独立通用工具。
  - 原因：满足当前本地优先场景，同时保留向其他部署形态和能力实现演进的边界。
  - 影响与后续动作：具体约束统一以 [`Agent 系统技术架构`](modules/agent-system.md) 和各模块文档为准，重大边界变化再新增记录。

- **260723 · 调试查看器架构 · 已生效**
  - 决策/变更：调试数据流采用"独立工具 + 出向推送"：`tools/debug-viewer` 是独立 Rust bin（`POST /ingest` 接收、SSE `/events` 广播、`ServeDir` 伺服静态页），产品进程内不监听任何调试端口，只由推送端（当前为 CLI demo，v0.2.0 起为 Runtime 的 DebugSink 汇点）建立出向连接。模型层只产出规范事件与 tracing 埋点，不感知调试。
  - 原因：需要网页端实时查看 LLM 数据流与将来的调度行为，同时遵守单进程架构、不在产品进程引入本地 HTTP 服务的硬约束。
  - 影响与后续动作：线格式归 `tools/debug-viewer` 所有，不进入 `assistant-protocol`；credential 永不进入调试 payload；`DebugChannel::Sched` 调度通道随 v0.2.0 Runtime 接入补齐；`agent-model` 的 `ModelEvent`/`ModelError` 为此补充 serde 派生。

- **260724 · 模型层 tracing 埋点约定 · 已生效**
  - 决策/变更：明确模型层（`agent-model` 与 Provider Adapter）tracing 埋点约定：库代码只在调用边界 emit span/事件（`stream` 建立、唯一终态、受控失败），字段限定模型标识三元组（provider/protocol/model，来自服务构造期绑定）、耗时、delta/事件计数等元数据；任何字段不得携带 credential、prompt 正文、响应正文（与 `ModelError` 脱敏边界一致）。库不初始化 subscriber，subscriber 归应用进程（v0.2.0 起为 Runtime/desktop 进程）。`v0.1.0` 不实施埋点代码：进程内尚无 subscriber 归属，提前埋点无法验证且空增依赖；开发期可见性由 debug-viewer 的结构化事件承担，`v0.2.0` Runtime 接入时按本约定补齐埋点。
  - 原因：tracing 是"库内 emit、应用进程消费"的观测通道；没有 subscriber 归属时实施埋点既无法验证也无消费方。
  - 影响与后续动作：260723 调试查看器决策中"模型层只产出规范事件与 tracing 埋点"的实施时点由本条目明确为 `v0.2.0`；届时字段命名与脱敏边界以本约定为准。

- **260724 · 模型配置形态与调用目标归属 · 已生效**
  - 决策/变更：应用的模型配置采用一层结构：每条模型配置直接携带 protocol、provider、endpoint、credential、model（及可选连接/生成偏好），用户直接切换模型，不设"先选账户再选模型"的两层结构。模型层 SPI 的归属边界由此确定：endpoint、credential 与 model 全部属于服务实例的构造期参数，一个服务实例即一条编译完成的模型配置；`ModelRequest` 退化为纯语义输入（system/conversation/tools/generation 等），不携带任何路由信息；`ModelRoute` 类型、`check_route` 校验与 `ModelError::Route` 变体一并删除（代码审查 3.1 先移除 `ModelRoute.endpoint`，本条为最终收敛）。Runtime 不做 provider 与 model 的运行时配型：一条模型配置在配置编译期一次性编译为一个服务实例，切换模型即整体切换服务句柄，配型问题结构性不存在。
  - 原因：本地优先场景没有多账户/组织语义，两层配置是过度设计；"一连接多模型"确认为伪需求，请求级携带路由三元组只剩冗余与永不失败却必须维护的运行时校验。调用目标（配置期才变化）与语义输入（每次调用可变）是两类东西：前者归服务构造参数，后者归请求。
  - 影响与后续动作：Runtime 的模型配置存储（`v0.2.0+`）按一层形态设计；模型条目在配置加载时编译为服务实例（构造期绑定 endpoint/credential/model/超时），运行时按条目整体取用；同 provider 多条目（官方、自建网关）是各自独立的配置与服务实例；事件与响应消息中的模型身份来自线上响应（chunk/response 的 `model` 字段 + Profile 的 provider），不依赖请求；调试通道的 endpoint/model 由推送方从服务构造参数填写。
