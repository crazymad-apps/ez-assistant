## 二、版本背景、最终目标与成功标准

本版本形成可交付企业内部使用的完整链路：管理员部署企业中心、管理用户与完整模型目录；用户在普通电脑上的 Host 登录，首次登录自动建立自己的本地数据库；不同终端通过已有 Desktop/Web 访问同一 Host；模型调用经中心透明转发，企业可查询调用日志及按策略保存的内容快照。

同时解决已反馈的长任务继续执行与观察问题，使个人版和企业版共用的 Runtime 能力持续演进。企业中心不接管 Agent 执行，不保存本地业务数据的第二份权威副本。

版本成功需要同时满足：

| 编号 | 最终用户结果 |
| --- | --- |
| G1 | 管理员可部署中心、管理用户及权限，通过同一登录体系使用管理后台；普通企业用户可以登录并退出 |
| G2 | 同一 Host 服务多个用户，首次登录自动建库，重新登录恢复本人数据；通过产品接口不能读取或操作其他用户数据 |
| G3 | 中心完整管理 Provider、模型与固定参数；Runtime 只获得当前默认配置和临时 key，企业用户只能使用中心默认模型 |
| G4 | 模型默认项变化时旧配置被明确拒绝，Runtime 主动刷新；流式调用、取消、失败和日志记录形成完整闭环 |
| G5 | 可回收的单轮上下文能够释放空间并继续执行；正文、思考、子会话占用和历史分页能正确反映长任务状态 |
| G6 | 个人版与企业 Runtime 可独立选择发布；中心独立部署和升级，协议兼容即可协作；安装、升级、恢复与回归有真实验证证据 |

循环验收只证明该循环约定的能力已完成；G1—G6 及整体验收全部满足后，才将本版本企业交付标记完成。

## 四、产品边界、运行拓扑与权威状态

### 4.1 产品与部署形态

```text
企业中心（独立部署）
├── 管理后台 + 统一认证 + 模型管理 + LLM 透明代理
├── PostgreSQL：用户、模型配置、审计与调用索引；Token/key 仅进程内存
└── 本地持久目录：请求/响应内容快照
         ↑ 认证 / 获取当前配置 / LLM 请求
普通电脑上的 Runtime Host（一个进程、一个监听）
├── 已认证用户 A：本地数据库、Journal、配置投影与运行状态
└── 已认证用户 B：本地数据库、Journal、配置投影与运行状态
         ↑ HTTP Command / SSE / Streaming Upload / WS 终端
Desktop / Web；Client 保持既有 Host 管理产品职责
```

Desktop 与 Client 继续各自携带 Host；普通电脑允许远程访问即可共享，不新增“工作站”业务实体。中心后台仅供管理员使用；普通用户在本机 Runtime 的 Desktop/Web 入口登录、退出、查询本人身份和修改本人密码，不进入中心后台。两类入口使用同一套企业账号和身份规则，身份与密码权威仍归 Center；C01 验证中心接口，C03 完成 Runtime 入口接入。

首版设计建议每个企业 Host 只配置一个中心地址和一种运行模式；切换中心或个人/企业模式属于显式配置操作，不将已有个人数据自动认领给首次登录的企业账号。中心身份与稳定用户 ID 共同界定本地用户数据归属，用户名重命名不应创建新数据库。

### 4.2 权威事实归属

| 事实 | 权威所有者 | 其他层允许持有的内容 |
| --- | --- | --- |
| 企业用户、状态、角色、登录态、临时 key 有效性 | Center | Host 的已认证上下文与必要凭证，不接受客户端任意指定用户身份 |
| 完整 Provider 目录、真实 endpoint/key、固定参数、企业默认模型 | Center | Runtime 当前有效配置投影；中心 Provider ID 只需通过代理 endpoint 路径传达 |
| 用户 Session、Run、队列、审批、记忆、工作空间、Journal | `assistant-runtime` 的对应用户域 | Host 装配存储与传输；客户端展示，不另存业务权威状态 |
| 用户本地数据库/文件的物理访问与迁移 | Host 的存储 Adapter | Runtime 使用既有 Store 端口，不依赖 SQLite/PostgreSQL 类型 |
| Host 监听、进程管理、网络接入、实例锁 | Host/既有本机管理机制 | 企业账号权限不自动授予停机、改监听或访问所有用户数据的能力 |
| 中心管理日志、代理调用结果、快照文件状态 | Center 后台服务 | 数据库保存必要索引；内容文件单独保存 |
| 视口、草稿、页面缓存、连接目标 | 客户端 | 涉及用户业务内容的缓存随身份分区，退出/切换账号时清理旧投影 |

现有 [Host HTTP 认证](../../../apps/runtime-host/src/http/auth.rs)、[模型配置编译](../../../crates/assistant-runtime/src/config/managed_model.rs)、[模型管理契约](../../../crates/assistant-protocol/src/model_management.rs)和 [Host 迁移执行器](../../../apps/runtime-host/src/storage/migrations/mod.rs)是复用核查入口。现有实现面向单所有者；增加企业身份必须覆盖状态、传输和存储，不能仅给数据库目录加用户后缀。

### 4.3 用户隔离边界

1. Center 登录成功后，Host 按稳定身份打开或首次创建该用户的本地数据库及配套文件域；失败登录不建库。同一用户并发首次进入只能形成一个有效数据域。
2. 会话列表、历史、Run、child、主控会话代理、记忆检索、工作空间、附件、配置、MCP 用户配置、审批、SSE、上传下载、文件预览和 WS/PTY 终端都必须由认证上下文选择用户域。
3. 同一用户多个连接共享自己的业务状态；不同用户连接、Run 和模型凭证不得互相覆盖。所有者路由属于应用/Host 边界，不把企业账号传入 Agent Core。
4. 本机 bootstrap 仅证明本机管理身份，不能替代企业用户登录或成为浏览其他账号数据的入口。Center 管理员角色也不默认获得所有 Host 会话的读取权。
5. Skill/MCP 的用户配置与本地业务文件按用户域装配；显式使用的相同外部工作目录仍可能共享底层文件，不复制为独立文件系统。原生浏览器/语音设备等共享能力必须明确归属；无法绑定用户的企业入口在完成设计前不开放。
6. Shell、PTY 和外部 MCP 仍可能以同一操作系统用户权限访问文件；本版只承诺应用层逻辑隔离，不承诺对同机恶意工具代码的强隔离。

## 五、架构原则与全局不变量

### 5.1 复用与低耦合

- 个人与企业模式共用主干、Runtime、模型编译、Provider Adapter 和客户端主体；产品模式差异集中在身份来源、模型配置来源与可用命令边界。
- Agent Core 不感知企业中心、账户、数据库或产品模式。业务状态仍由 Runtime 唯一持有；Host 负责按身份选择和装配用户域。
- 用户域采用多个 Runtime 实例装配还是 Runtime 内分区，由 C03 技术方案依据现有依赖决定；必须同时满足单 Host 进程、单用户唯一状态、共享进程资源有界、逐用户恢复隔离。
- Center 首版采用模块化单体。用户认证、模型目录和代理/日志各有明确职责，按实际稳定调用边界组织代码，不提前拆微服务。
- PostgreSQL 16.14 业务读写使用 TypeORM（pg 驱动），复杂查询允许参数化 SQL；升级保留 node-pg-migrate 和显式 SQL 事务。参考 Host 的升级账本、准入、备份与结果校验职责，不直接照搬 SQLite 实现。不使用逐字段结构比对或 ORM Schema 自动同步。升级与业务共用一个账号，启动自动升级默认开启且可配置关闭，关闭后通过显式升级命令处理。

### 5.2 登录与临时凭证

- 后台管理员与 Runtime 普通用户共用用户、Token 认证，通过权限区分功能；临时 LLM key 是该登录态的限定用途凭证，不是另一套用户系统。
- 用户表以独立字段标记超级管理员；带标记用户禁止删除，默认具有管理员角色及系统提供的全部权限，不新增第三种角色。首个 SQL 创建默认超级管理员 admin / 123456（仅存摘要）、中心身份和初始化审计，不另设初始化代码/配置，重启不重置密码。该标记不改变 Host 数据所有权、凭证用途及既有业务规则；停用和标记管理边界由 C01 功能设计收敛。
- 个人改密与用户管理重置是两个操作：前者必须校验原密码，管理员也不例外；后者凭管理员权限为任意用户（包括自己）直接设置新密码，不校验原密码。不能因目标是操作者自己就把管理重置转为个人改密。
- 每次登录签发新 key，在所属登录态登出前持续有效；不增加短时 TTL 和续期机制。关闭页面、断网与显式登出是不同动作。
- 凭证只能用于中心代理，不能用于进入管理接口。登出必须撤销对应 key，不因 Host 还保存其副本而继续有效。
- 用户确认允许多个内存 Token 并存，登出只删除当前 Token 和关联 key；管理员停用账号撤销其全部 Token。Token 不入库、不计算哈希、不引入 Session 实体，Center 单实例重启后须重新登录；前端管理凭据，后端统一 Bearer 鉴权。
- 同一用户不同登录态的 key 与发起请求/Run 的执行上下文绑定，不能保存在会互相覆盖的用户全局字段中。不得因另一终端重新登录而替换活动执行的凭证。

### 5.3 模型托管与刷新

- Center 沿用 Provider 实例与 `(provider_instance_id, model_id)` 的完整模型管理关系，包括目录显式刷新、固定参数和默认项；不引入别名或中间映射。
- Runtime 仅接收当前生效模型、中心代理 endpoint、临时 key、固定参数及现有模型编译必需的类型/协议/能力信息；不下发完整目录、真实上游地址或真实 Provider key。
- endpoint 路径携带中心 Provider ID，Runtime 将地址作为不透明连接参数处理；不额外传递中心 `provider_instance_id` 字段。既有本地模型记录若需要 ID，由托管配置适配解决。
- 企业用户不可改 Provider、固定参数、默认模型或会话模型；客户端屏蔽相关入口，Runtime 拒绝对应变更命令。主调用、标题、压缩、子任务与视觉相关调用统一受托管策略约束，不保留可绕行的本地辅助模型配置。
- 中心检查路径 Provider ID 与实际模型协议请求中的 `model` 对应的真实模型身份是否仍是当前默认项；不匹配时在访问上游前返回稳定的配置过期错误。`model_id` 是内部身份名称，不要求改写现有 Provider 请求字段。
- Runtime 收到配置过期错误后主动获取当前配置。并发刷新应合并且有界；无默认模型、刷新失败或再次变化必须给出明确失败，不使用个人配置兜底。
- 本稿建议登录、显式刷新及配置过期错误触发取配置。仅固定参数变化不增加 revision，不要求即时推送或中心逐参数校验；下次成功获取配置后生效。上游 endpoint/key 变化由中心直接使用最新值，无需终端刷新。
- 已冻结的执行规格不会被刷新静默改写。本稿建议首版刷新后结束已拒绝的调用并明确提示重试，后续新执行使用新配置；不重放整个 Run 或已执行工具。自动重试若后续需要，必须单独证明符合冻结规格及无重复副作用边界。
- 默认 Provider 改变后，旧 Provider 的 opaque state 不得发送到新 Provider；沿用已有模型切换与 Provider 状态隔离约束，具体旧会话重绑定在 C04 明确并验收。

### 5.4 透明转发与日志

- Runtime 继续构造现有 Provider 请求；中心只做身份/当前模型核验、上游路由、认证替换和传输，不重写统一请求/响应模型，不重复校验固定参数上限。
- 实际上游地址只来源于后台配置；用户不能借 endpoint 路径或请求字段指定任意转发目标。客户端秘密头不直接透传给上游。
- SSE 分块、正文、reasoning、工具调用与上游业务错误保持现有协议语义；代理层不根据模型内容执行业务，也不隐藏重试已开始的流。
- 取消、断连、超时和背压由中心后台服务处理。连接建立/空闲超时与整段长流时长分开，避免持续输出的请求被固定总时限误杀。
- 登录与管理操作、调用用户/Provider/模型、开始结束时间、结果和必要关联信息进入中心日志。中心未观察到的 Runtime 工具执行不伪造为完整中心审计；其本地事实继续由 Runtime 持有。
- 完整请求/返回快照在响应正常结束、失败或中断收敛时由 Center 后台服务统一写本地文本文件；数据库只保存检索字段、文件定位和完整性状态。它不是 Agent Runtime 的落盘任务。
- 本稿建议完整快照默认关闭、由管理员显式开启；正常日志不含 prompt、正文或任何 key。完整快照保存原始正文，不声称能识别并脱敏正文中全部业务秘密。
- 写盘前的内容累积必须有界；超过限制、中途失败、磁盘满、进程异常时不能把记录标成完整。已成功返回的 LLM 结果不因随后快照落盘失败而改写为调用失败；记录结果与模型调用结果分开。

### 5.5 上下文压缩优化与长任务观察

- C02 以“上下文压缩优化”为目标，核查单轮 Run 内上下文增长、现有压缩边界和压缩后仍无法继续的原因；评估摘要质量、保护范围、触发与续接机制等改进。剪枝仅是候选方案之一，不作为必选实现或验收条件。
- 复用既有压缩入口、派生上下文和一致性校验，保留原始 Conversation 及可回查标识；具体策略与派生表示由 C02 技术方案确定。
- 优化必须覆盖当前 Run，保护未完成交互、当前任务要求、工具配对与必要 Provider 状态；保护范围应支持有效压缩，由具体方案论证。
- 压缩与续跑保持现有控制归属，不重放历史工具；实际无法释放足够空间时有界失败，不反复无效压缩。
- 记忆变更从可靠事实提取，并在连续压缩中保留必要有效约束；不复活已删除或被新值取代的旧记忆。
- 历史分页有效性取决于对应历史是否改变，其他会话/用户实时事件不能使其无故失败；游标真的失效时仍必须拒绝。
- 正文列表和 reasoning 独立保存用户跟随意图；新内容不会把“原本在底部”误改为离底，用户主动上滚不被抢回。
- 子会话上下文占用使用自己的当前窗口事实，与累计 token 消耗区分；未取得数据不能显示为零，也不能借用父会话数值。

## 七、跨循环契约与兼容约束

### 7.1 必须先对齐的契约

| 提供方 → 使用方 | 稳定事实 | 明确排除 |
| --- | --- | --- |
| C01 → C03/C04 | 中心稳定用户身份、权限、登录会话、登出/停用与 key 撤销关系 | 工作站注册、模型与 key 固定绑定、两套登录体系 |
| C03 → C04/C05 | 已认证用户域、数据/事件/终端所有权、执行与凭证上下文 | 从请求体直接信任 user ID、跨账号全局缓存 |
| C04 → Runtime | 当前有效模型配置、代理 endpoint/key、稳定配置过期错误 | 动态 revision、全模型目录、额外 Provider ID 下发、静默改模型 |
| C02 → C05 | 压缩结果、当前上下文与真实累计用量的既有事实 | 新 UI 估算权威、历史正文改写 |
| C01/C04 → C06 | 中心配置与迁移入口、数据库/快照存储位置、协议兼容声明 | 安装包写死 Provider key、中心与 Runtime 锁步升版 |

C01 设计时先确定跨中心/Host 的身份和会话契约，再实现中心登录；C03 设计时验证全部用户域入口；C04 设计时确定托管配置与错误契约。契约字段与序列化测试由各循环技术方案确定，后续循环不得静默改变前序已验收语义。

### 7.2 技术栈与工程边界

已确认边界为 Node.js 方向、PostgreSQL、显式升级 SQL，现有 Runtime 继续使用 Rust。2026-09-18 用户确认业务访问转向 TypeORM，替代此前“不使用 ORM”的限制；数据库升级方式与 HTTP 契约不变，影响 C01 内部数据访问及事务验证，不改变 C03/C04 的依赖边界。Center 使用 TypeScript + NestJS/Fastify，管理页面使用 React + TypeScript + Vite，首版作为单一中心产品交付。具体依赖组合与运行效果须经实施验证，设计确认不是已实现事实。

2026-09-18 用户确认：后端 `apps/enterprise-center/` 与前端 `apps/enterprise-admin/` 分别维护 npm 包、锁文件、依赖及构建；发布时将前端静态产物装入 Center 制品，由一个 Node 服务同源提供，一次部署。两个工程跟随同一 Center 软件版本，不因此增加独立前端发布渠道，也不改变 Center 与 Runtime 独立发版的约定。

支持的 Node/PostgreSQL 版本及依赖锁定在 C01 技术方案核查后确定。中心可复用稳定模型契约，不能依赖 Desktop UI 或 Host 私有存储；不为了复用类型将 NestJS、数据库实体或 ORM 类型放入 `assistant-protocol`。

### 7.3 升级与发布

- Runtime 套件（Desktop、Client、Host）维持统一软件版本；个人/企业两个发布渠道独立记录最新版本，允许交错与跳版。
- Center 独立软件版本、制品和升级节奏；通过双方协议能力和最小兼容要求判断协作，不比较软件版本是否相等。
- Desktop/Client 与 Host 的应用协议兼容、Host 与本地数据库的存储兼容、Center 与 Host 的企业协议兼容分别判断。只有契约实际变化才调整相关下限。
- 本地个人数据继续属于原模式；企业首登建库不迁走、清空或隐式重命名个人数据库。企业各用户库独立执行适用的准入/迁移，失败不得回退到别人的库。
- Center 升级必须分别考虑 PostgreSQL 与快照目录，备份恢复说明包含两者的关联核验；旧程序不满足数据库要求时拒绝写入。
- 继续单仓库、单长期 `main`。普通功能分支短期使用；已发布支持线允许 hotfix，分支保留，修复必须同步回主干。
- 循环编号不进入 SemVer 或安装包兼容声明。本阶段不修改 Cargo/npm 软件版本、不创建发布标签。

### 9.2 主要风险

- 用户隔离可能遗漏主控会话、Recall、子任务、Gateway、PTY、缓存和配置等非主会话入口；C03 必须给出完整入口清单和越权证据。
- 默认模型切换与冻结执行规格、Provider state 的冲突不能靠替换全局配置掩盖；C04 必须验证旧会话与活动执行。
- 响应结束才落盘存在进程异常前内容丢失窗口；完整性状态必须反映真实结果。本版不承诺无损合规留痕或崩溃前逐字持久化。
- 上下文压缩优化涉及上下文语义正确性，作为独立 C02 严肃验证；方案必须由问题核查和效果验证支持，不能预先将剪枝视为结论。
- 中心不可用时企业新登录与新模型调用受限；本版不预先引入离线凭证、离线模型兜底或高可用集群。

### 9.3 变更与推进规则

1. 总体设计确认后，各循环仅细化自己的能力、技术和交互；总目标、非目标、状态归属及跨循环契约作为检查依据。
2. 改变范围或契约时，先记录原因、涉及循环和需重新验证的证据，经确认后同步总体设计与相关文档。
3. 影响已归档循环时显式重开，保留原阶段结论与变更原因，重新验证和确认；不把缺陷悄悄留到后续循环。
4. 版本级技术方案需要先收敛身份/数据域/托管配置的共同契约；管理后台与企业登录需要交互设计。各循环实现前仍须形成自己的开发计划。
5. 当前版本保持开发中，C01 M0—M3 与循环验收均已确认，随本次授权提交完成阶段归档；用户允许 C01/C02 分会话推进。各循环后续设计与里程碑仍分别确认，不能将并行授权视为全部代码里程碑已获批准。
