## 三、技术栈与工程结构

### 3.1 已确认的技术组合

| 部分 | 方案 | 理由 |
| --- | --- | --- |
| 服务运行时 | Node.js 24 LTS、TypeScript | 现有 Client 已覆盖 Node 24；首版只验证一个中心运行时主线 |
| HTTP/模块装配 | NestJS + FastifyAdapter | Nest 负责模块、依赖装配和管理 API；Fastify 承载 HTTP，C04 可在同一监听内接入流式代理 |
| 数据库 | PostgreSQL 16.14、TypeORM 1.1.1（pg 驱动）、node-pg-migrate 9.0.0 | 用户确认改用 ORM；关闭 Schema 同步，保留显式升级 SQL |
| 管理页面 | React + TypeScript + Vite、MobX、Sass、Ant Design 6 | 用户授权正式沿用原型组件和样式；服务端投影用 MobX、表单草稿用组件状态 |
| 密码与随机凭据 | Node 内置异步 `scrypt`、`randomBytes` | 中心不迁移 Host 密码；无需为该独立密码存储增加原生密码库依赖 |
| 验证 | Vitest、真实 PostgreSQL 集成测试、Playwright | 测试位于应用根 `tests/`，不依赖正式用户数据 |

Node 24 在核查时为 LTS；该选择不是追随 Current 版本。[Node 发布状态](https://nodejs.org/en/about/previous-releases)。Nest 官方提供 Fastify 适配，但要求选用对应平台的插件，不能直接照搬 Express 中间件。[Nest Fastify 文档](https://docs.nestjs.com/techniques/performance)。2026-09-18 用户选定 PostgreSQL 16.14，替代未发布 M0 的 PG18 试验基线；准入允许 16.14 及后续 16.x 补丁，实际验证版本为 16.14，不自动接受其他主版本。现有 PG18 隔离数据保留，不执行原地降级。

2026-09-18 只读 npm 元数据核查：`@nestjs/core` 与 `@nestjs/platform-fastify` 为 `12.0.3`，后者依赖 Fastify `5.12.4`；`pg` 为 `8.23.0`。建议以这些版本作为首次装配候选，不单独升级 Fastify 到另一个补丁。React `19.2.8`、Vite `8.2.1`、TypeScript `7.0.2` 等前端版本来自当前 Desktop 清单，不宣称为最新版本。实现前需验证 Nest、TypeScript 装饰器编译、Fastify 插件及测试工具兼容，精确版本写入 Center 清单和私有锁文件；本轮未安装或验证这些组合。

Nest 模块只按真实能力划分，Controller 保持薄；不使用 CQRS、微服务、Passport/JWT、Redis 或消息队列。框架不能把所有成功响应包装为统一 JSON，以免后续破坏透明代理的流式输出。

### 3.2 工程归属

2026-09-18 用户确认前后端拆为两个独立工程，各自维护 package、锁文件、依赖、开发命令和构建：

```text
apps/enterprise-center/
├── package.json / package-lock.json
├── src/
│   ├── main.ts / app.module.ts
│   ├── identity/           # 登录、当前身份、密码、Token 及 key
│   ├── users/              # 管理员用户操作与 SQL
│   ├── audit/              # 写入和管理员查询
│   ├── database/           # 业务 DataSource、维护 Pool、准入、有序 SQL 升级
│   └── contracts/          # 中心 HTTP DTO、运行时校验和错误码
├── scripts/                # 构建与制品装配入口
└── tests/                  # unit、integration、support、契约夹具

apps/enterprise-admin/
├── package.json / package-lock.json
├── src/
│   ├── app/ / features/    # 管理后台壳与业务视图
│   ├── components/ / styles/
│   └── request/openapi/   # Hey API + Axios 从后端 OpenAPI 生成的类型及请求方法
└── tests/                  # unit、e2e、support
```

这些是职责位置，不要求一次创建所有空目录。后端采用 NodeNext/ESM、严格类型检查及独立 Nest 编译配置，构建使用 TypeScript 编译器，不把开发期 `tsx` 当作生产执行器。前端维护自己的浏览器 TS/Vite 配置，不依赖 Nest、数据库、密码或后端配置模块；两个应用不跨目录导入对方业务源码。

后端 `build` 只编译后端，前端 `build` 只构建静态页面；安装、类型检查和单元测试也各自独立。前端测试需要真实后端的场景只放集成/E2E，不把后端运行设为前端日常构建前提。

发布装配先分别构建两个工程，再将 Admin 静态产物复制到 Center 制品的 `public/admin/`，生产仍只有一个 Node 服务，同源提供页面与 API，不需要第二个前端服务进程。开发时后端可仅启动 API；正式制品启动必须检查后台静态资源完整，缺失则明确失败。制品装配在临时产物目录进行，不把生成资源反写为后端源码或手改 `dist/`。

拆工程不引入两套对外发布版本：Admin 是 Center 制品的一部分，两个 package 版本跟随同一个 Center 软件版本；完整制品配对构建和验收，不单独给 Admin 建发布渠道。Center 与 Runtime 的独立版本节奏保持不变。正式分发流水线归 C06，C01 已需验证双工程构建后的同源运行。

生产由 Center 同源提供 `/admin/` 静态资源与 `/api/`；开发 Vite 将 `/api/` 代理给 Center，不开放任意 CORS。2026-09-18 用户明确要求引入路由库，替换手工视图切换：使用 React Router 8.4.0、createHashRouter 与嵌套 Outlet，集中声明 `/login`、`/users`、`/audit`、`/audit/:id` 和未匹配页面。Hash 模式保持现有静态资源部署和未知 API/资源 404，无需服务端 SPA fallback。本人账号、创建/编辑与改密保持原型弹窗，不把密码/表单草稿/审计正文放进 URL 或 history。详情复用 GET /api/audit 的可选数字 id 精确筛选，不新增表或版本字段；未登录跳转登录页，成功后仅返回白名单本地路径。2026-09-20 修正刷新行为：先恢复 Cookie 中的 Token 并核验身份，有效时保留原路由，无凭据或确认失效才重新登录。菜单、面包屑和浏览器前进/后退由路由管理，提交中与编辑中导航通过 useBlocker 拦截。

Admin 不直接跨应用导入 Desktop 源码。2026-09-18 用户要求正式前端沿用原型 UI，确定 Ant Design 6 的表格、表单、弹窗与选择控件；不复制 Desktop、不抽取公共 UI 包、不引入 Pro/Umi。适用边界见 [UI 框架决策与原型](UI框架决策与原型.md)及 enterprise-admin 模块约束。

接口生成按用户指定参考 genapi.js 使用 @hey-api/openapi-ts 的 @hey-api/client-axios 插件，默认读取 Center 的 openapi.json，支持 OPENAPI_INPUT/OPENAPI_OUTPUT。生成结果放 src/request/openapi，由 genapi:check 校验一致性；密码 writeOnly 对应操作的 writable DTO，不手写另一套请求契约。

新增长期模块约束分别放在 `docs/modules/enterprise-center.md` 与 `docs/modules/enterprise-admin.md`，并登记根 AGENTS 映射；文件在方案确认后的实施准备中建立，不在源码目录另设约束体系。

## 四、权威状态与数据设计

### 4.1 最小数据集合

使用独立中心数据库，表均属于 Center。表名与关键字段建议如下；时间统一为 UTC `timestamptz`，HTTP 输出 ISO 8601 字符串。2026-09-18 用户要求行主键不使用 UUID：`users.id`、`management_audit.id` 使用 PostgreSQL `integer GENERATED ALWAYS AS IDENTITY`，由数据库生成而非应用分配，接口 JSON 为数字并校验 1—2147483647 的规范十进制输入；`center_id`（跨中心身份）与 `request_id`（请求追踪）不是行主键，保留 UUID。C01 尚未发布，001-initial.sql 直接统一为数字主键，不为中间 UUID 形态保留兼容。

| 表 | 必要字段 | 约束与归属 |
| --- | --- | --- |
| `center_identity` | 单例主键、`center_id`、`created_at` | 初始化生成稳定中心身份；升级/重启不更换，不添加工作站记录 |
| `users` | `id`、`username`、`display_name`、`role`、`is_super_admin`、`enabled`、`password_hash`、创建/更新时间 | 账号唯一，角色仅 `user/admin`；超级管理员标记非空、默认 false；密码摘要不进入查询 DTO |
| `management_audit` | `id`、时间、操作者/目标用户 ID、动作、结果、原因码、`request_id`、受限详情 | 只保存允许字段；失败认证允许操作者为空；不保存请求/响应正文或秘密 |
| `pgmigrations` | `id`、`name`、`run_on` | node-pg-migrate 管理的唯一升级记录，不沿用 Runtime 软件版本；不另建版本表 |

Token 不入库：IdentityService 持有 `Map<token,userId>`；关联 key 使用 `Map<llmKey,token>`，不计算 Token/key 哈希、不设独立 Session 实体或 ID。当前没有独立权限表、角色关联表、key 表、动态 revision、设备表或通用配置表需求。Center 身份由现有单例表表达，不另造安装登记实体。

账号限制为 3—64 个 ASCII 字母/数字及 `._-`，输入 trim 后转小写持久化；显示名支持 Unicode。2026-09-20 用户将新密码规则调整为至少 6 位，必须包含 ASCII 英文字母和数字；保留 128 个 Unicode 字符、512 UTF-8 字节上限，不要求大小写并存或特殊符号，也不禁止其他字符。密码不 trim、不改变 Unicode 内容，创建/个人改密/管理重置前后端使用同一规则，OpenAPI 同步 minLength 和 pattern。登录与原密码校验不套用新策略，已有密码及初始化 SQL 中的 `123456` 仍可验证；不重置现有账号、不修改初始化摘要。

普通用户资料 DTO 只包含 `id/username/display_name/role/is_super_admin/enabled` 及确有展示用途的时间。按字段显式投影，不将 `SELECT *` 结果直接序列化。列表按 `created_at,id` 稳定排序，有界分页（默认 20，最大 100），不为首版用户列表引入独立搜索服务。

### 4.2 超级管理员与管理员保护

- 权限判定：先确认有效登录态与启用用户，再判断 `is_super_admin || role === 'admin'`；超级管理员具备全部已定义权限，但不免除业务校验与凭证用途限制。
- `is_super_admin` 不是普通用户编辑 DTO 字段。未知输入字段直接拒绝，不能通过透传对象更新数据库。API 不提供授予/撤销标记的入口。允许按运维安全流程直接在数据库赋予其他用户该标记，不增加触发器、唯一标记约束或自动角色修正。
- 首次初始化 SQL 明确写入 `role=admin, is_super_admin=true, enabled=true`；默认用户名 `admin`，密码按用户要求为 `123456`，SQL 仅存预生成摘要，不另设初始凭据配置。
- 首版用户 API 没有 DELETE；禁止删除用户、审计只读等由服务端业务约束。单一应用数据库账号具备本库结构与读写权限，不再通过分离账号或逐表授权表达产品权限。后续若引入普通用户删除，必须仍显式拒绝超级管理员。人工数据库操作仍按安全规范审批。
- 最后管理员判断统计 `enabled AND (role='admin' OR is_super_admin)`，不能只看角色文本。带标记用户禁止通过 API 停用或从 admin 降为 user；无变化的原角色值不算降权。数据库赋标记后 role=user 的用户同样拥有全部管理权限，权限与保护不依赖用户名、固定 ID 或初始化来源。
- 管理员重置任意用户密码仍包括超级管理员；不能借本次标记新增“普通管理员不能重置超级管理员”的例外。

## 五、认证、凭证与并发

### 5.1 统一 Token 认证

2026-09-18 用户要求简化：后台和 Runtime 使用同一登录接口，仅提交 username/password，不再传 delivery。登录返回 center_id、user、token 和 llm_key；不含 session_id/session_token。普通用户可调用统一身份接口；后台页面按角色限制进入，管理 API 在服务端声明管理员权限，不能依赖页面限制授权。

每次登录生成两个独立 32 字节随机值：ct_ 身份 Token 与 cl_ LLM key。前者直接作为进程内 Map 的键对应 userId；后者仅关联本次 Token，不另建 Session 或凭据数据库。用途不可互换，me 不重复返回秘密。同一用户可有多个 Token，退出删除当前 Token 和关联 key，其他登录不受影响。改密/管理重置/停用/角色变更撤销目标用户全部凭据；后两类操作属于 M2。

没有 TTL、刷新令牌、Token 哈希或 Redis。Center 单实例运行，关闭/重启后全部 Token/key 失效，用户重新登录。用户、密码摘要、中心身份和审计仍持久化。不可用负载均衡把同一用户随机路由到多个实例，不宣称支持集群或跨实例恢复。

### 5.2 全局 HTTP 鉴权与秘密边界

- 全局入口位于 src/security.ts，通过 Nest 全局 Guard 执行，默认要求 Bearer Token；Controller 用 Access 显式声明公开、可选认证或管理员权限，不逐接口复制通用检查。
- /api/info、登录公开；退出允许缺失/无效 Token，保持幂等。公开或可选认证不跳过来源与 JSON 格式检查。Swagger UI/JSON 由 Fastify 注册，明确公开，生产可由代理限制文档访问。
- 只读取 Authorization: Bearer，不读取 Cookie 或 URL 参数。前端负责凭据保存与清除；后端不设置/清除 Cookie，不提供 Cookie 鉴权，也不拒绝与认证无关的普通 Cookie。
- 浏览器与 Host 使用相同契约；存在 Origin 时必须匹配 CENTER_PUBLIC_ORIGIN，Sec-Fetch-Site 为 cross-site 时拒绝；写接口要求 application/json，不开放任意 CORS。Bearer 不依赖浏览器自动携带的 Cookie，无 Cookie CSRF 分支。
- 生产仍使用 HTTPS；本机开发可显式允许 loopback HTTP。所有 API 响应 no-store；Token/key/请求体/密码不写日志。2026-09-20 用户确认 Admin 以会话 Cookie 保存后台 Token，bootstrap 恢复后查询本人身份，确认前遮蔽路由；网络失败保留凭据并允许重试，确认失效、退出成功或本人变更导致已确认撤销时清理。Cookie 为 host-only、Path=/admin/、SameSite=Strict，HTTPS 加 Secure，名称含端口避免开发实例覆盖（不构成安全隔离）；前端读写不能使用 HttpOnly，不承诺关闭浏览器后长期记住登录。Cookie 清理比对当前值，避免旧标签页清理新凭据；应用 dispose 仅清内存。后端仍不处理 Cookie，不增 Session、TTL 或刷新令牌。后台不保留 LLM key，用户投影与密码不落浏览器存储。显示内容以 React 文本渲染，不直接展开任意服务端错误或审计 JSON。

### 5.3 密码与入口资源限制

使用异步 `crypto.scrypt`，随机盐至少 16 字节，派生 32 字节，摘要编码同时携带算法和参数，比较使用恒定时间比较。建议首版参数 `N=131072,r=8,p=1,maxmem=192 MiB`，并将并行密码计算限制为 2；这是需要性能验证的初始预算，不宣称已经压测。不存在的账号使用固定假摘要执行同类验证，避免显著的认证时间差。

Node 提供异步 scrypt、随机盐及内存上限选项；同步密码计算不能放在 HTTP 热路径。[Node Crypto 文档](https://nodejs.org/docs/latest-v24.x/api/crypto.html#cryptoscryptpassword-salt-keylen-options-callback)。

M1 实现密码计算最多两个并行、八个等待者，满时返回 429 RATE_LIMITED；请求体上限 16 KiB。登录入口按真实 TCP 来源每分钟 20 次、最多 1024 个来源做有界内存限流，不为未认证账号写入无限限流记录，不增加 Redis 或永久锁号。trustProxy=false，不信任 X-Forwarded-For；经反向代理访问时按代理地址共享额度，可信代理策略仍需部署评估。限流与 Token 均为进程内状态，重启后清空。

### 5.4 两种密码操作

| 操作 | 输入与授权 | 成功事务 |
| --- | --- | --- |
| 本人改密 | 有效会话、原密码、新密码；目标取认证用户 ID | 更新密码摘要、撤销本人全部 Token、写 `self_password_changed` 审计 |
| 管理重置 | 管理权限、目标用户 ID、新密码；不收原密码 | 更新目标摘要、撤销目标全部 Token、写 `user_password_reset` 审计 |

管理员对自己执行管理重置仍走第二行，不依据 actor=target 自动切换功能。两条路径成功后都可能使当前操作者会话失效，事务提交后仍返回成功；后台据返回结果转到登录页。失败或原密码错误不修改密码、不撤销会话。

### 5.5 并发次序与事务边界

单实例下身份写入以一个进程内 Promise 链串行执行，覆盖数据库事务提交和紧随其后的内存 Token 变更；不再使用身份 PostgreSQL advisory lock。密码计算在串行段外完成，进入串行段后重新读取用户、校验 Token 与旧密码摘要，拒绝过时操作。初始化升级仍使用框架数据库锁，与身份 Token 无关。

顺序为：进入身份写入串行段 → 重验 → 数据变更与成功审计 → COMMIT → 同步签发/撤销内存凭据 → 允许下一写入。登录只有审计成功提交后才加入 Map；退出审计失败则保留 Token 并返回失败；改密与审计整体回滚时不撤销已有 Token。提交结果不明时清空内存凭据并失败，不自动重试。数据库与内存不是可持久化的同一事务；进程在两步之间崩溃会丢失全部 Token，重启必须重新登录。

同一业务事务只使用一个 TypeORM QueryRunner 的 EntityManager；失败回滚并释放连接。认证异步查询返回后重验 Token 仍在 Map，避免查询期间退出后继续使用旧结果。重复退出串行判断，只审计首次有效退出。M2 用户写入须复用同一串行边界和提交后撤销口径；不增加跨进程同步机制。

2026-09-18 用户确认转向 TypeORM，纳入 M2 调整，不提前进入 M3：

- 三张业务表各自映射 Entity，保留现有 SQL 表名、字段、默认值和约束；不新增 DDL、表或升级编号。DTO 不继承 Entity，密码摘要默认不查询，只有身份核验显式读取。
- 普通 CRUD 使用 Repository/QueryBuilder，用户与审计的数据访问分别收敛在对应模块 repository 文件，不建立通用 BaseRepository。列表的单语句分页/总数快照保留参数化 CTE，经 EntityManager 执行，避免改成两次查询改变并发语义。
- 启动先用维护 Pool 完成原有升级/准入并关闭，再初始化唯一业务 DataSource，随后监听；关闭顺序为 HTTP、DataSource。同一配置/账号，不增加长期并行连接池。
- TypeORM 固定 synchronize=false、migrationsRun=false、dropSchema=false，不注册升级文件；node-pg-migrate 仍是唯一升级工具。关闭原始 SQL/错误日志，连接和查询超时沿用现有界限。
- QueryRunner 负责业务事务，IdentityService 保留串行队列及提交后 Token 变更；所有业务和审计写入使用传入事务 Manager，不调用全局 Repository 绕过事务。COMMIT 结果不明清空凭据且不重试；回滚也失败时关闭业务池，须排查后重启。
- 复用 Nest 当前显式 provider 装配，不为此次切换新增框架自动重试或第二份 DataSource 生命周期。离线 OpenAPI 导出不初始化数据库。
- 回归身份、用户管理、审计、启动升级、回滚、提交结果不明、连接释放及 OpenAPI；真实数据库操作仅限重新核实的本机隔离环境。

只读请求以认证查询完成时点为授权边界；撤销不回滚已完成动作，活动代理取消归 C04。

### 6.2 错误与协议兼容

中心身份/管理 API 错误体统一为 `{error:{code,message,request_id}}`；message 用于展示，调用方按 code 分支，不依赖中文文案。建议固定：

- `400 INVALID_REQUEST`：格式、字段或值无效。
- `401 AUTH_FAILED / TOKEN_INVALID`：登录失败或身份凭据不可用；账号不存在/密码错误/停用共用 AUTH_FAILED。
- `403 ADMIN_REQUIRED / FORBIDDEN`：后台角色准入或操作权限拒绝。
- `404 USER_NOT_FOUND`：已获管理权限后查询不存在的目标。
- `409 USERNAME_EXISTS / LAST_ADMIN_REQUIRED / AUTH_STATE_CHANGED`：唯一性、最后管理员或计算期间身份状态变化。
- `429 RATE_LIMITED`，`503 SERVICE_UNAVAILABLE`：限流或无法可靠完成请求；不返回 SQL、栈和数据库地址。

超级管理员保护使用 409 SUPER_ADMIN_PROTECTED；最后一个启用管理员不能移除，使用 409 LAST_ADMIN_REQUIRED。以上仅适用 Center 自有 API；C04 的透明上游响应与固定配置过期错误独立细化，不强行套此错误外壳。

Center 软件版本、数据库迁移版本和企业协议版本各自承担已有不同职责：

- Center 包建议首个独立软件版本 `0.1.0`，不跟随 Runtime `0.27.0`；仅在实现/发布流程确认后写清单。
- 企业协议初始为 `1`，`GET /api/info` 声明当前及最低支持协议；Host C03 对照自己支持的协议判断，不比较双方软件版本相等，不依据账号配置变化升协议。
- 数据库版本由 SQL 文件及框架 pgmigrations 记录驱动；不维护第二份 manifest，不为每个实现循环或动态配置增加版本/revision。

C01 保存真实响应/错误的 JSON 契约夹具；C03 引入 Rust 消费时必须用相同夹具验证。2026-09-18 用户确认采用 Swagger/OpenAPI：后端 Controller 与 `src/contracts/` DTO 通过 Nest Swagger 装饰器单点描述接口，生成 OpenAPI JSON，替代原定自定义 TS 投影导出。前端从 OpenAPI 生成类型和请求方法，产物纳入版本管理且不可手改；不导入后端源码或安装整个后端作为依赖，不新增公共 SDK 或第三个协议包。

M0 接入 `/api/docs` Swagger UI、`/api/openapi.json`，并提供无需数据库或监听端口的 `openapi:export` / `openapi:check`。包根 `openapi.json` 为生成快照，接口变更后重新导出；前端按自身生成工具消费该文件或在线 JSON，日常构建不依赖运行中的后端。只描述已实现接口；显式固定 operationId、字段必填/可选、成功和错误结构，全局声明 tokenBearer，公开接口覆盖为空，退出声明可选认证。Swagger 注解不替代后端输入校验或权限检查。文档不包含真实凭据，关闭 Swagger UI 外部校验和凭据持久化；生产部署可由反向代理限制文档路径为内部可访问。

### 6.3 M2 管理接口交接

- createUser：POST /api/users，username/display_name/role/enabled/password 全部必填；201 返回 UserRecord。is_super_admin 不接受输入，使用数据库默认 false。账号 trim/lowercase 归一化，重复返回 409 USERNAME_EXISTS。
- updateUser：PATCH /api/users/{id}，只接受 display_name/role/enabled，至少一项；200 返回 UserRecord。账号和超级管理员标记不可通过此接口修改；无变化不更新 updated_at、不重复审计。超级管理员仅按标记保护；资料编辑不撤销 Token，角色/启用状态实际变化撤销目标全部 Token。
- resetUserPassword：POST /api/users/{id}/reset-password，仅 new_password；204 成功。目标可为自己、其他管理员或超级管理员；不收 old_password，不按 actor=target 切换语义。
- listUsers：GET /api/users，search 为账号或显示名的字面子串；role/enabled 可选；limit 默认 20、1—100，offset 默认 0、0—1000000；按 created_at,id 升序。返回 items/total/limit/offset，UserRecord 只含公开身份字段及 UTC created_at/updated_at。
- listManagementAudit：GET /api/audit，可选 from（含）、to（不含）、actor_user_id、action、success；时间须 UTC ISO 8601 Z 格式。分页规则同上，按 occurred_at,id 倒序，返回 items/total/limit/offset。详情只投影 before/after 的 display_name/role/enabled，不透传 JSON 任意字段。
- 两种列表都在同一 SQL 语句快照内取得总数和页面；空页仍有总数，连续翻页不承诺隔离并发新增。查询拒绝未知字段、重复键、非法布尔/日期/分页，不拼接客户端 SQL。
- 所有管理 API 由全局管理员 Guard 保护；写入在同一身份串行事务内重验操作者。失败审计记录已知操作者、固定动作/原因码；成功读取不额外写审计。无 DELETE、审计修改/删除或超级管理员赋权 API。
- 初始化默认账号名只存在于初始化 SQL；权限代码不比较用户名/固定 ID。用户状态与标记每次请求读取数据库，人工赋予标记不需服务重启。人工 SQL 不自动写产品操作审计，也不代替运维审计和数据库安全流程。

## 七、审计、数据库升级与运维入口

### 7.1 管理审计

2026-09-20 审计查询响应补充可空 actor_username/target_username（登录用户名）。在同一 SQL 中先分页，再 LEFT JOIN users 两次，只选择用户名，保留原 actor_user_id/target_user_id、总数、排序与无关联记录；不逐行查询、不新增数据库列或升级脚本。列表和详情共用此投影，前端不按当前用户分页拼接姓名。

成功用户变更、改密/重置与审计同事务提交；初始化由升级 SQL 同事务处理。登录/退出先提交成功审计，再改变内存 Token；失败不返回成功。拒绝动作在回滚后以独立短事务记录失败；失败审计不能令已拒绝动作重新执行。数据库不可用时仅输出脱敏诊断，不宣称数据库审计成功。

审计详情只允许普通字段变更前后值；密码和所有凭据只记录“发生过操作”，不记录摘要。客户端传入的 request ID 不直接作为日志内容；服务端生成关联 ID。失败登录不落原始请求体或任意输入账号，避免恶意输入与凭据混入日志。

### 7.2 数据库升级与自动开关

用户确认采用 node-pg-migrate，安装锁定稳定版 9.0.0，升级使用纯 SQL，不使用 TypeORM 升级器或自研升级执行器。仅配置一个 CENTER_DATABASE_URL，升级与业务共用本应用账号，预先授予专用库/schema 的建表、改表和读写权限；不切换账号、不临时提权，不要求数据库超级用户。

- CENTER_DATABASE_AUTO_UPGRADE 默认 true，只接受 true/false。开启时启动先完成升级 SQL（含首次初始化），再检查版本并监听；关闭时只读检查版本，空库或待升级库返回 UPGRADE_REQUIRED 并退出。
- 显式 db:upgrade 不受自动开关限制，使用同一账号完成升级和首次初始化；db:check 始终只读。删除未发布阶段旧 db:migrate/init-admin 入口设计，不保留别名。
- 纯 SQL 存在 src/database/migrations/；框架读取排序、取得数据库锁、执行并写入唯一 pgmigrations 记录。已发布文件不可改名/改内容，只追加需要的升级 SQL。
- 项目只补充未知/更高版本、记录顺序及无记录非空库准入，不逐字段、约束或索引比对，不自动认领现有业务库。初次失败后框架留下的空版本表可识别为尚未初始化。
- 所有待执行业务 SQL 与相应版本记录使用框架 singleTransaction；失败整体回滚并停止，不重试后续脚本或对外监听。框架先创建版本表，首次失败可能留下空 pgmigrations 及序列，不能宣称整库无对象。
- 框架的原始 SQL/错误日志不得直出，产品沿用固定原因码及脱敏异常；升级连接用完销毁，不把会话锁或 search_path 带回业务池。
- 只使用事务内 SQL，不开放 down/fake/no-lock 产品入口；不处理 PostgreSQL 大版本升级或未发布试验数据库格式兼容转换。

已有库升级前仍核对主机、端口、库、表和影响范围，并按项目安全规则停写、确认、独立 pg_dump 备份及实际恢复验证。自动开关不替代该流程。升级后在验收/运维环节核对受影响数据和接口，不在普通启动中扫描全部业务字段。

框架 API 与事务选项以锁定稳定版本为准：[node-pg-migrate 9 API](https://github.com/salsita/node-pg-migrate/blob/v9.0.0/docs/src/api.md)。备份方法见 [PostgreSQL 16 pg_dump](https://www.postgresql.org/docs/16/app-pgdump.html)。

### 7.3 首个管理员和运行配置

首次初始化直接写在 `src/database/migrations/001-initial.sql`，随自动升级或显式 db:upgrade 执行；不开放公网初始化接口，不另设初始化服务、命令或配置。默认凭据 admin / 123456，只存预生成的带盐 scrypt 摘要（16 字节盐、32 字节派生值，格式 scrypt$N$r$p$saltHex$keyHex）。公开默认密码应在正式使用前修改，不另增强制改密流程。

首个 SQL 在框架的同一升级事务中创建业务表、Center 身份、超级管理员及 center_initialized 审计，与对应版本记录一起提交或回滚。由框架账本保证只执行一次、框架锁避免并发执行，锁冲突明确失败；重启和后续升级不重置管理员，不另写数据存在判断或补建逻辑。关闭自动升级时空库不初始化，需显式 db:upgrade。

建议配置项保持少量：数据库连接秘密、监听地址/端口、public origin、受信代理范围、Center 数据目录。没有默认数据库密码。`start` 验证全部配置、数据库准入和构建资源后才开放业务监听；关闭时停止接纳请求、等待有界在途请求、关闭连接池。C01 不创建 LLM 内容快照目录或后台常驻任务。

Center 默认仅监听 loopback；企业外部访问由明确监听配置或现有 HTTPS 反向代理提供，服务端和前端同源。实际监听端口、测试端口和测试数据库必须在开发计划核对后锁定，不占用 Host 的默认 7240。
