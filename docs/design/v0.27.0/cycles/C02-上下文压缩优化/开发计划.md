1. 按 M0 → M1 → M2 顺序执行。每个里程碑完成“核查、实现、定向验证、汇报”后停止，

2. 本计划确认后只开始 M0，不因整体方向已确认而连续实现后续里程碑。
3. 实现事实与技术方案不一致，或出现新的公共协议、持久化、Provider 兼容取舍时，
   停止扩大修改并回到设计确认。
4. 不引入剪枝、多阶段摘要、新 token 账本、压缩表或后台 Worker；不改写完整原始产品历史。
5. C01 和 C02 并行期间，C02 不改写共享的 docs/开发进度.md、docs/版本管理.md、
   版本级总体设计和总台账。发现共享文件、依赖或验证环境冲突时，先协调冲突部分。
6. 测试和 Host 验证使用 TempDir 或显式隔离的 Runtime Home，不写入或清理用户

## 四、里程碑明细

### M0：压缩语义与自动主路（✅ 已完成）

**目标：** 关闭“压缩后仍整值使用旧 usage，导致立即再压缩”的已证实故障，并让自动摘要使用
Core 真实正常请求的完整前缀。

**交付范围：**

- Context Summary 的可选 usage 调整和程序化上下文字段可兼容序列化；Summary 只有一个模型可见渲染入口。
- 窗口评估实现已确认的 usage 减法、前一偏移继承、Unavailable 收敛和新 Assistant usage 接管；
  不改写原 usage，不影响 UI 累计。
- Rolling Summary 写入和验证 usage 调整；replacement 紧凑序列化后必须确实小于源 Conversation。
- Core 在阈值和 Provider overflow 路径交接精确 ModelRequest；handoff 只存在于进程内，
  AgentEvent、serde、Debug、SSE 和录制结果不暴露正文。
- Runtime 验证 Journal 是 live request Conversation 的有序原样子序列；不一致或 handoff 缺失时不提交压缩。
- 摘要请求保留 System、Conversation、Tools 顺序、采样、reasoning 和 Provider Options，
  只追加隐藏指令、设置 ToolChoice None 和 max_output_tokens = 4096。
- 父 Agent 覆盖 disclosure/shell request-only context，子 Agent 覆盖任务级 load_skill；
  两者在首次压缩后继续同一 Run，不重放工具。

**验证入口：**

- cargo test -p agent-types -p agent-context -p agent-core -p agent-testkit
- cargo test -p agent-openai-compatible -p assistant-runtime
- cargo fmt --all --check
- 对上述受影响包执行 cargo clippy --all-targets --all-features -- -D warnings

**完成判定：** 故障同构数据中，205421 >= 204800 不再被 replacement 原样整值采用；
阈值/overflow 与父/子 Agent 路径都使用 live request 完成单次摘要和续跑；旧 Summary 与
Provider 投影回归通过。

**Review 重点：** 近似 usage 不伪装成 Provider 真值；Core 只交接请求而不接管压缩；
Runtime 仍是候选、提交和续跑 owner；请求前缀不被重建或重排。

**实际结果（2026-09-18）：**

- Context Summary 已支持兼容的 usage adjustment 与统一模型可见渲染；窗口判断按减法近似，
  新 Assistant usage 到达后直接恢复 Provider 真值。replacement 中没有旧 Assistant usage 时不写
  adjustment，首次预检自然保持 usage unavailable，不制造无意义的旧引用。
- Core 已用仅进程内、正文脱敏的 handoff 交接阈值与 overflow 对应的精确 `ModelRequest`；Runtime
  校验 Journal 与 live Conversation 的有序原样关系后才允许生成候选。
- Rolling Summary 保留正常请求的 System、Conversation、Tools、采样、reasoning 与 Provider Options，
  仅追加隐藏摘要指令、禁用工具选择并将摘要输出上限设为 4096；无压缩收益的候选会被拒绝。
- 父 Agent 的 request-only disclosure/shell 上下文与子 Agent 的动态 `load_skill` 上下文均有自动压缩后
  续跑覆盖，没有重放既有工具副作用。
- 已通过 `cargo fmt --all --check`、受影响目标的严格 Clippy 以及 `cargo test --workspace`；依赖真实
  Provider、外部程序或人工环境的既有 ignored 测试未强制执行。M0 完成不要求发版、生成制品或提交 Git。

### M1：Runtime 记忆与生命周期（✅ 已完成）

**目标：** 将记忆净变化与压缩调整作为可持久化事实接入 Runtime 完整生命周期，使手动、重启、
改写和分叉行为与自动主路一致。

**交付范围：**

- Runtime 从完整产品历史重算成功且已闭合的 pin_memory、update_pinned_memory、
  unpin_memory 净变化；失败结果忽略，非法成功 JSON 拒绝整个候选。
- 程序化段使用 Runtime 私有、确定排序的 V1 JSON，复用 256 条、单条 16 KiB、整体
  128 KiB 限制；超限不截断且不提交半份状态。
- 手动压缩使用当前 Session 冻结 System、有效 Conversation、当前模型和无 Run 请求配置，
  不伪造上次 Run 的完整缓存前缀。
- Context Summary 新字段跟随现有 JSONL 与 generation 原子提交，重启不依赖 Run 内存状态，
  不新增 schema migration 或回填作业。
- 改写/分叉截掉被引用 Assistant 时，调整收敛为 Unavailable；Summary 也被截掉时不保留调整。
- NoOp、取消、snapshot race、存储失败和内存投影失败保持现有原子边界；完整产品历史继续保留
  原 usage 和原 Tool Result。

**验证入口：**

- cargo test -p assistant-runtime
- cargo test -p agent-context
- cargo fmt --all --check
- 对 assistant-runtime 和 agent-context 执行 cargo clippy --all-targets --all-features -- -D warnings

**完成判定：** 记忆新建、更新、删除、净零、旧 Summary 补建、限额、手动压缩、重启、
改写和分叉均有定向证据；成功时只提交一份有效新 generation，失败时无半提交、悬空引用或工具重放。

**Review 重点：** Pinned Memory 知识不泄漏到 Context 通用层；不读取当前 Memory Store 污染冻结
Session；手动 profile 不声称保持 Run 专属工具前缀；不为延续近似值而复活被截断消息。

### M2：集成验证与容量结论（✅ 已完成）

**目标：** 在正式 Host 代码路径上验证完整 C02 能力，并对 usage 修复后 protected tail 是否仍存在
容量问题作出有证据的结论。

**交付范围：**

- 在隔离 Runtime Home 中运行故障同构长任务，核对压缩次数、generation、新模型请求、
  首个新 Provider usage、工具不重放和最终 Run 状态。
- 对比摘要指令前的 System、Conversation 和 Tools 投影，证明本地未改写缓存前缀。
  如已有可用正式 Provider，同时记录真实 cached_input_tokens；零命中不单独判定实现失败。
- 构造同一 Run 多次模型/工具交换和大 Tool Result 的窗口边界样本。未复现真实 overflow 时明确
  C02 不实现轮内拆分/剪枝；复现时保存边界证据并回到设计，不在验证现场扩张实现。
- 执行 C02 跨模块回归与静态质量门禁，核对原始历史可回查、失败有界、无新协议/UI 变更。
- 同步修复 Desktop 可靠会话页的 owner、水位和连续边界校验，防止会话切换或并发刷新后把失配缓存
  与当前最新页合并；不新增协议字段，不改变 Runtime 持久化。

**验证入口：**

- cargo test -p agent-types -p agent-context -p agent-core -p agent-testkit
- cargo test -p agent-openai-compatible -p assistant-runtime -p assistant-runtime-host
- cargo fmt --all --check
- 对上述受影响包执行 cargo clippy --all-targets --all-features -- -D warnings

实际 Host 启动命令在 M2 开始时根据现有入口确定，不在计划中虚构脚本。如没有可用正式 Provider，
记录未执行项，但可用确定性的 fake/loopback Model 完成主路正确性验证；这不阻塞 C02 的实现完成。

**完成判定：** 已证实故障不再复现；自动、手动、父 Agent、子 Agent、重启、改写、分叉和失败路径
符合已确认设计；protected tail 样本形成“无需扩展”或“需重开设计”的明确结论。

**实际结果（2026-09-18）：**

- `256000` 窗口、`204800` 阈值和 `205421` 旧 usage 的故障同构样本只压缩一次；
  同一 Run 继续完成，新响应 `42000` 成为窗口判断的新权威 usage，工具未重放。
- 摘要请求的 System、Conversation、Tools、reasoning 与 Provider Options 前缀和 live 正常请求一致；
  正式 Host loopback 验收中也只出现一次摘要请求，工具定义不变且 `tool_choice=none`。
- 正式 Host 在隔离 Runtime Home 中完成“工具调用 → 自动压缩 → 同 Run 续跑 → 关闭重启”全链路；
  generation 2 与 Summary 可恢复。
- 30,000 字符受保护 Tool Result 在 `8192` 窗口中可复现真实容量上限；系统最多压缩两次后
  `ContextCompactionFailed`，原结果可追溯且工具只执行一次。未来如要求继续执行，需要另开轮内裁减、
  结果外置或引用协议设计；C02 不现场扩张。
- 无已授权真实 Provider，因此未执行外部 `cached_input_tokens` 命中验证；确定性请求投影和 loopback
  usage 已验证本地前缀与用量传递，真实缓存命中不作为实现门禁。
- Desktop 已复用现有 `ConversationOwner`、`ObservedSnapshot.observed_sequence` 与 generation 修复可靠
  投影：归属不匹配的响应被拒绝，倒序快照不再覆盖新状态，最新页与缓存无连续边界时以服务端页替换
  而不是取并集；新增交错响应、失配 owner、无交集替换和分页连续性回归。
- 详细证据与验证命令见 [M2 验证记录](M2验证记录.md)。
