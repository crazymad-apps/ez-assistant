# v0.27.0 C02 M2 验证记录

## 一、验证结论

- 日期：2026-09-18。
- 状态：M2 实现与验证已完成，并于 2026-09-18 获用户确认。
- 环境：确定性 Runtime fixture、loopback OpenAI-compatible Provider、临时 Runtime Home；
  未读写或清理用户 `~/.ez-assistant`。

现场故障的直接原因已经关闭：压缩后不会继续把 `205421` 作为新 generation 的完整占用，
下一次真实模型响应会接管 usage。C02 同时确认了另一条独立边界：如果最近受保护内容本身已经
超过窗口，现有完整 User Turn 保护规则不能释放它；系统会在最多两次自动压缩后有界失败，
不会重放工具或破坏原始历史。

因此 M2 的容量结论是：

1. 原现场问题不需要通过 Tool Result 剪枝修复，usage 减法已经使任务正常续跑。
2. 超大 protected tail 是可独立复现的真实容量上限，但它不影响本次故障修复的完整性。
3. 如产品以后要求“单个受保护 Tool Result 超窗时仍必须继续”，需要重新设计轮内裁减、结果外置
   或引用协议；C02 不在验证现场引入这类语义变更。

## 二、故障同构验证

定向测试 `fault_isomorphic_usage_is_subtracted_before_the_next_model_request` 使用与现场一致的
关键边界：模型窗口 `256000`、80% 阈值 `204800`、压缩前保留 Assistant usage `205421`。

验证结果：

- compressible head 的最后 usage 为 `150000`，新 Summary 持久化
  `Subtract(205421 - 150000)` 的调整事实；原 Assistant usage 与 Tool Result 仍保留在完整产品历史。
- 同一 Run 共发起四次模型请求：旧轮响应、工具调用响应、一次摘要请求、一次续跑请求。
- 只发生一次 generation 切换，generation 从 1 变为 2；工具只执行一次，Run 最终为 Completed。
- 摘要请求在追加隐藏指令前，System、Conversation、Tools、reasoning 与 Provider Options
  和 live 正常请求一致；只禁用工具选择并使用摘要输出上限。
- 续跑响应报告 `42000` 后，窗口评估的 `completed_tokens` 立即变为 `42000`、pending 为 0，
  不再应用旧减法，也没有发生第二次虚假压缩。

父 Agent 的 disclosure/shell request-only context、子 Agent 的任务级 `load_skill`、自动阈值、
Provider overflow、手动压缩、改写、分叉和重启路径由 C02 既有定向测试共同覆盖。

## 三、正式 Host 验证

新增正式进程验收 `v0_27_context_compaction`，使用 loopback Provider 和隔离 Runtime Home：

- 模型窗口 `8192`，80% 阈值约为 `6553`；旧轮 usage 为 `5000`。
- 同一 Run 的 `load_skill` 响应报告 `7000`，触发一次自动压缩；摘要请求报告
  `cached_input_tokens=6000`，用于验证 Host 能完整接收并持久化 Provider usage，而不是声称
  真实外部 Provider 已命中缓存。
- Provider 共收到四次请求；摘要请求只出现一次，工具定义与压缩前请求一致，
  `tool_choice=none`。
- `load_skill` 只执行一次；同一 Run 继续并以新响应 `total_tokens=1000` 完成。
- Session generation 为 2；关闭并重新启动正式 Host 后，generation 2 和 Context Summary
  均可恢复。

Host 存储测试还验证了 `usage_adjustment`、`programmatic_context` 与摘要 usage 随现有 JSONL 和
generation 原子提交并在 reopen 后保持一致。正式 Host 全套离线集成测试通过；需要真实凭证或
外部服务的既有 ignored 测试未执行。

本次没有可用且已授权的正式 Provider，因此没有把真实外部 Provider 的
`cached_input_tokens` 命中情况作为完成证据。本地证据能够证明 ez-assistant 没有主动改写
可复用请求前缀；上游最终是否命中缓存仍属于 Provider 行为。

## 四、protected tail 容量边界

定向测试 `oversized_protected_tool_tail_stops_after_two_automatic_compactions` 使用 `8192` 窗口和
单个 30,000 字符 Tool Result：

- Tool Result 属于当前受保护尾部，压缩策略不删除、不截断、不改写它。
- 系统成功提交两次 Summary generation，随后以
  `ContextCompactionFailed: context compaction recovery limit reached` 结束。
- 工具只执行一次；完整产品历史保留两次 Summary 和原始 30,000 字符结果。
- 下一次执行投影只从最新 Summary 开始，不形成多 Summary 叠加或无限压缩循环。

该样本证明 protected tail 确有硬上限，也证明当前失败路径是安全且有界的。它形成未来新设计的
输入，不构成 C02 未完成项。

## 五、Desktop 可靠投影同步修复

M2 待确认期间发现偶发的新会话页面混入其他会话可靠 Assistant Turn。只读核查得到以下证据：

- 新会话 `s_e8_Zr1LOThgC` 的 JSONL 从当前用户输入开始，不包含异常旧正文；异常正文只存在于旧会话
  `s_8CKBmDRdIhyg`，没有持久化串写。
- 异常块带复制、分叉、收起和完成时间，属于可靠 `AssistantTurn`，不是 SSE live tail。
- Desktop 最新页合并此前只比较 generation；新会话 generation 通常相同，且无连续交集时仍做并集，
  缺少 owner、快照返回顺序和页连续边界门禁。

同步修复后：

- 会话请求、Session/Child 快照和 `ConversationPage.owner` 必须一致，否则按协议错误拒绝；
- 同一 owner 迟到的较旧 `observed_sequence` 不再覆盖较新快照，也不触发 live reconcile；
- 同 generation 最新页与缓存无连续边界时以服务端页替换；存在连续边界时仍保留已加载的历史分页；
- 未增加协议字段、持久化、版本号或新的会话状态。

新增定向测试与完整 Desktop 验证均通过：2 个定向测试文件共 19 项、完整前端 56 个测试文件共
470 项，`npm run lint` 和 `npm run build` 通过。构建仅有既有的大 chunk 提示和 `ts-rs`
`deny_unknown_fields` 解析警告，没有新增错误。
