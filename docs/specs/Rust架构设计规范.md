# Rust 架构设计规范

本规范用于 Rust workspace 的 crate 划分、模块边界、依赖方向、状态所有权、异步任务、协议、
持久化和演进设计。它回答“代码应该放在哪里、谁拥有状态、边界怎样长期演进”；具体编码方式遵循
[`Rust 开发规范`](Rust编程规范.md)，领域架构遵循 `docs/modules/*.md`。

## 一、规范目标

架构设计必须让新参与者能够从文档和 crate graph 回答：

1. 系统有哪些进程、crate 和主要模块；
2. 每一层负责什么、明确不负责什么；
3. 依赖允许向哪里流动；
4. 每份权威状态由谁拥有和修改；
5. 请求、事件、取消、失败和恢复怎样穿过边界；
6. 哪些 API、协议、配置或数据格式是稳定边界；
7. 哪些不变量由类型、测试和构建检查持续保证。

架构文档不是目录清单，也不是把现有代码换一种语言复述。无法指导归属、依赖和变更 Review 的描述，
不算有效架构规则。

## 二、依据与方法

- Cargo workspace、feature 和兼容行为以 [Cargo Book](https://doc.rust-lang.org/cargo/reference/) 为准。
- 公共 Rust API 以 [Rust API Guidelines](https://rust-lang.github.io/api-guidelines/) 校准。
- 异步生命周期以 Tokio 的
  [Graceful Shutdown](https://tokio.rs/tokio/topics/shutdown) 和 cancellation safety 文档校准。
- 架构表达参考
  [rust-analyzer Architecture](https://rust-analyzer.github.io/book/contributing/architecture.html)：
  明确 API Boundary、Architecture Invariant、输入/派生状态和序列化边界。

成熟项目提供经过实践检验的方法，但没有适用于所有 Rust 项目的唯一分层。任何模式都必须根据本项目的
进程拓扑、发布方式、状态模型和实际替换需求做取舍。

## 三、架构设计的必备内容

新增 crate、跨层契约、进程、持久化机制或重要并发能力时，技术方案至少包含：

- 背景、问题、目标与非目标；
- 当前约束和已确认事实；
- 进程拓扑及生命周期；
- crate/module 职责和明确非职责；
- 依赖方向与禁止依赖；
- API、协议、配置、持久化和外部系统边界；
- 权威状态、不可变快照和派生状态的所有者；
- 关键请求、事件和数据流；
- 并发单位、串行化点、队列、背压、取消和关闭顺序；
- 错误分类、失败隔离、重试、恢复和幂等语义；
- secret、权限、审计和信任边界；
- 兼容策略、迁移路径和回滚方式；
- 测试边界、可观察性和验收方法；
- 被否决方案及理由。

只涉及单模块局部实现、且不改变上述任一边界时，可以不单独编写架构方案，但仍必须遵守现有规范。

## 四、职责与所有权优先

### 4.1 单一权威所有者

- 每类可变业务状态必须只有一个权威所有者。其他层只能持有不可变快照、缓存、句柄或投影。
- 写入权和生命周期必须一致：创建、修改、恢复和删除同一实体的逻辑不应分散到互不协调的层。
- UI、传输 Adapter 和 Demo 不得复制业务状态机；它们发送意图并展示权威层返回的事实。
- 缓存必须说明源、失效条件和重建方式；无法说明失效的缓存不是优化，而是第二事实源。

### 4.2 输入、派生状态与快照

- 区分外部输入、已校验领域状态、派生状态和展示投影，不能用一个可变结构贯穿所有层。
- 长任务读取配置或策略时，应在明确边界冻结不可变快照，避免执行中途读取到半新半旧状态。
- 派生状态应可由权威事实重建；若不能重建，就必须按权威状态设计其持久化与事务语义。

## 五、依赖方向

- crate graph 必须保持有向无环。高层装配和编排依赖低层能力契约，低层不得反向依赖应用、UI、
  具体进程或持久化实现。
- 领域类型应位于最接近其不变量的层；不能因“多个地方都想 import”就自动上提到公共 crate。
- 跨层共享 crate 只承载稳定、轻量、实现无关的契约；不得成为所有层都能倾倒类型的 `common`。
- 具体 Adapter 依赖抽象契约；应用入口负责选择实现和注入依赖。业务核心不得自行读取全局环境、
  创建具体 HTTP client 或定位用户目录。
- 测试工具可以向下依赖生产契约，生产 crate 禁止依赖测试宿主或 Demo。
- 依赖反转只用于真实替换、隔离副作用或测试边界。若一个 trait 只有一个调用者、一个实现且没有边界
  价值，优先使用具体类型。

本项目的具体依赖图以根 `AGENTS.md` 和 [`Agent 系统技术架构`](../modules/agent-system.md) 为准；
本规范不重复维护第二份项目依赖清单。

## 六、crate、module 与文件的拆分

### 6.1 何时建立 crate

满足以下一项或多项时才考虑独立 crate：

- 需要由 Cargo 强制执行依赖方向或禁止依赖；
- 有独立、稳定的 API 边界和两个以上真实消费者；
- 需要独立 feature、平台条件、发布/复用、编译缓存或测试边界；
- 需要把具体基础设施与 provider-neutral 契约隔离；
- 代码具有独立领域词汇和不变量，而不是主 crate 的几个 helper。

以下理由单独出现时不足以拆 crate：文件很长、测试很多、可能以后复用、想隐藏私有代码、目录看起来整齐。
crate 会增加编译、依赖、版本和 API 成本，应先尝试模块化。

### 6.2 何时建立 module

- 一组类型和函数共同维护一个可命名的不变量；
- 能明确写出该模块的职责和非职责；
- 主流程可以只依赖该模块暴露的少量入口；
- 该组代码因同一种原因变化，并能独立测试。

模块根负责展示主入口；transport、dispatch、validation、persistence 等边缘能力按职责下沉。
测试可独立成子模块，但不改变被测生产 API 的可见性。

### 6.3 不按行数设计

文件长度是 Review 信号，不是架构依据。一个较长但单一、连贯的状态机可能优于被随意切散的文件；
一个很短但同时泄漏 UI、I/O 和领域状态的模块仍然是坏边界。拆分后必须让：

- 主流程更容易顺序阅读；
- import 和可见性没有异常扩大；
- 同一不变量没有分散；
- 模块名能够预测内容；
- 循环依赖和跨模块往返没有增加。

## 七、边界类型与转换

- 每个边界使用该边界的语言：领域层使用领域类型，协议层使用 DTO，Provider Adapter 使用原生 wire
  类型，持久化层使用记录模型。它们可以结构相似，但不能默认是同一个类型。
- 转换集中在边界 Adapter，负责校验、默认值、兼容迁移、错误映射和脱敏。
- 可序列化类型意味着兼容承诺。参考 rust-analyzer 的做法，内部模型不因方便直接派生序列化；
  IPC 客户端定义面向自身的序列化 counterpart。
- 对外错误只暴露稳定 code、可安全展示的信息和必要结构；内部 source 链保留在边界以内。
- 协议不得携带进程内句柄、锁、trait object、数据库实体或只有某个具体实现理解的对象。

## 八、同步调用、命令与事件

- 普通方法用于进程内同步语义；Command 表示调用者意图；Event 表示已经发生的事实；Snapshot 表示
  某一时刻的权威投影。三者不能混用。
- 命令是否幂等、是否持久化、何时算成功必须明确。发送成功不等于业务完成，事件送达也不等于事实落盘。
- 事件不能默认作为恢复来源。若允许丢弃，必须能通过 Snapshot 恢复；若不能丢弃，就需要持久化、
  sequence、ack 或重放设计。
- 跨进程 API 必须有 correlation ID、稳定错误和版本/能力协商策略；传输私有细节不自动升级为应用协议。

## 九、异步架构与任务所有权

### 9.1 并发模型

设计必须写明：

- 并发单位是什么；
- 哪些操作可以并行；
- 哪些状态必须串行；
- 串行化由锁、队列、单所有者任务还是上层调度保证；
- 最大并发、队列容量和超载策略是什么。

不能只写“使用 Tokio 异步并发”。

### 9.2 任务树

- 每个后台任务必须属于某个 Runtime、Session、Run、连接或进程生命周期。
- 父级关闭时必须知道如何通知、等待和处理子任务失败；禁止把 `spawn` 当作隐式生命周期管理。
- 任务需要独立失败隔离时，仍必须有 supervisor 或 tracker 观察其结束，不能静默 detach。
- 连接生命周期与业务生命周期分离：网络断开是否取消业务必须由产品语义决定，不能由变量借用关系决定。

### 9.3 关闭顺序

受控关闭统一审查：

```text
停止接收新工作
  → 标记生命周期/拒绝新命令
  → 通知受管任务取消
  → 完成必要 flush、settle 或 rollback
  → 等待任务退出（有明确超时）
  → 释放进程拥有的端点和资源
```

强制 abort 只能作为超时后的明确兜底，并说明可能丢失的状态。

## 十、错误隔离、重试与恢复

- 在故障边界分类错误：配置、输入、授权、资源、网络、协议、业务冲突、取消和内部不变量不能只用
  一个字符串错误表示。
- 重试必须位于拥有幂等信息和生命周期的层。底层不得对已产生部分输出或副作用的操作偷偷重试。
- 重试策略包含最大次数、退避、Retry-After 上限、可重试错误、取消响应和可观察事件。
- 恢复必须基于权威持久事实；不能从可能丢失的 UI 事件或内存投影猜测业务状态。
- 跨多个资源的操作若不能原子提交，技术方案必须写清部分成功、补偿、幂等 key 和人工恢复路径。

## 十一、兼容与演进

分别识别以下边界：

- Rust 公共 API；
- Cargo feature 与 MSRV；
- 应用 IPC 协议；
- 用户配置 schema；
- 数据库/文件持久化格式；
- Provider 或第三方 API。

每种边界独立定义版本、兼容窗口和迁移策略。内部实现重构通常不需要升协议版本；兼容性扩展也不应
机械升 schema。破坏性变化必须通过显式迁移或兼容层归一化，读取旧格式和写回新格式是两个独立决策。

公共 enum 新增 variant、trait 新增必需方法、公开字段变化等 Rust API 影响按
[Cargo SemVer Compatibility](https://doc.rust-lang.org/cargo/reference/semver.html) 审查。

## 十二、安全与信任边界

- 架构图必须标出进程、用户输入、文件系统、Shell、网络 Provider、数据库和调试输出等信任边界。
- credential 的读取、驻留、复制、日志、序列化和销毁路径必须可追踪；secret 默认不进入协议、事件、
  Debug、Shell 环境或可导出配置。
- 路径校验、权限和应用授权不是 OS 沙盒，文档不得夸大安全保证。
- 高风险副作用在 Runtime/应用策略层授权和审计，底层 Adapter 只执行已决策的结构化请求。
- 安全失败默认 fail-closed；若允许降级，必须是用户可见且经过设计的产品语义。

## 十三、可观察性与测试架构

- 日志、metric、trace 和审计是不同用途。结构化关联 ID 可以跨层传播，敏感正文默认不能传播。
- 测试集中在稳定边界和架构不变量：依赖方向、序列化、状态转换、取消、背压、失败恢复和 secret
  不泄漏。
- 大多数行为在最内层可控边界测试，只保留少量真实 I/O 或跨进程端到端测试。rust-analyzer 也采用
  分层测试边界和可复现、无外部资源的测试原则。
- 架构不变量应尽可能由 Cargo 依赖、类型系统、lint 和测试强制，而不是只写在文档中。
- 性能优化必须先定义预算和测量方式；不能因推测性能提前破坏边界，也不能在无基准时引入复杂缓存。

## 十四、架构 Review 清单

### 归属

- 新能力属于哪个进程、crate 和模块？为什么不是相邻层？
- 谁拥有权威状态？是否产生第二事实源？
- 新 trait、crate 或共享类型是否至少有真实边界价值？

### 依赖与 API

- crate graph 是否仍单向、无环？
- 公共 API 是否最小？内部类型是否泄漏到协议或持久化边界？
- feature 是否 additive？兼容承诺和迁移路径是否明确？

### 并发与失败

- 任务由谁拥有、取消和等待？
- 队列容量、背压、丢弃和最大并发是什么？
- 部分成功、重试、超时、断连和 shutdown 后状态是什么？

### 安全与验证

- secret、权限和外部输入经过哪些边界？
- 哪些架构不变量由测试或构建强制？
- 是否存在更简单、依赖更少、恢复更清晰的方案？为什么没有采用？

## 十五、成熟项目参考结论

- **rust-analyzer**：最值得采用的是显式写出 API Boundary 和 Architecture Invariant，并让低层不知道
  高层协议或 I/O；不是照搬其众多 compiler crate。
- **Tokio / mini-redis**：最值得采用的是明确任务所有权、有界通道、CancellationToken 和三阶段
  graceful shutdown；不是把所有模块都改成 actor。
- **Serde**：最值得采用的是把核心契约、宏/派生实现和测试职责分开，保持核心依赖最小；不是为了
  “像 Serde”而制造 package。
- **ripgrep**：最值得采用的是库能力、CLI 装配和可选基础设施分离，以及对跨平台和 feature 成本的
  明确取舍；其搜索算法分层不适用于本项目领域。
- **Cargo / rustc**：最值得采用的是用 workspace、lint、feature 和稳定边界把架构约束变成可执行检查；
  大型编译器的内部复杂度不是本项目的目标。

参考项目的共同点不是“文件都很短”，而是边界有名字、依赖可检查、状态有所有者、失败可恢复、
兼容承诺受到控制。这也是本项目架构 Review 的判断核心。
