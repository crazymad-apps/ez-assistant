# 前端编程规范

本规范适用于 `apps/desktop` 的 WebView 前端。正式产品基线为 React、MobX、Sass、TypeScript
和 Vite；具体版本、迁移顺序与产品协议以当前版本技术方案为准。引入另一套框架、全局状态方案、
CSS-in-JS 或成套组件库属于架构变更，必须先记录决策。

## 一、总体原则

- **先搜后写**：新增组件、Hook、Store、样式工具或交互原语前，先搜索同 feature、
  `components/` 和 `styles/` 中的现有实现；已有语义一致的能力优先复用或小幅扩展。
- **按归属就近收敛**：页面或 feature 私有的组件、类型、Hook、Store、常量和样式放在 feature 内；
  测试代码统一放在应用级 `tests/`，按被测源码的业务语义组织；只有形成稳定跨 feature 语义后才上提。
- **不为形式提前抽象**：一个调用方、依赖大量业务字段或只能靠布尔参数适配单一页面的实现，
  仍是业务组件，不包装成“通用组件”。
- **组合优先于分支堆叠**：通过语义化子组件、`children` 或明确 slot 组合结构，避免一个组件依赖
  大量 `compact`、`simple`、`insideDialog` 等布尔参数承担互不相干的形态。
- **沿用既定设计语言**：组件封装不得借机改变视觉基准；相同交互状态应复用相同 Token、原语和
  可访问性语义，不在各页面重新创造近似实现。
- **保持简洁的信息层级**：一级设置页和管理列表只展示识别对象、核心状态与高频操作，不为完整而
  堆叠说明、副标题、能力字段或重复元数据；低频属性和诊断信息下沉到复用统一返回模式的二级详情页。
  Placeholder 可以清楚表达的短输入提示不额外占用一行可见 Label，但仍必须保留可访问名称。
- **改动必须可验证**：组件和样式变更至少通过类型检查/构建及相关测试；涉及浮层、滚动、焦点、
  缩放或窗口交互时补充真实页面和目标 WebView 验证。

## 二、职责边界

- UI 负责渲染、交互、Runtime 状态投影和短生命周期视图状态，不拥有会话、Run、调度、权限或
  Agent Loop 的权威状态。
- 所有 Agent 业务通过正式 Runtime Client 或窄 Tauri command/channel/event 接入，不从 WebView
  直接访问模型、数据库、Runtime Home、任意本地端口或本机文件。
- Tauri command 传递用户意图；Runtime event 表达事实。UI 不自行推断后端已成功。
- 文件选择、通知、窗口和系统权限由桌面层提供；不要用浏览器兼容方案绕过 Tauri 能力。

## 三、目录与组织

按业务能力垂直组织：

```text
src/
├── app/               # AppShell、RootStore 注入、顶层错误边界
├── runtime-client/    # HTTP/SSE、bootstrap 和错误映射
├── native-bridge/     # 唯一 Tauri invoke 包装
├── stores/            # RootStore 与跨 feature 协调
├── features/          # 按会话、消息、审批、设置等垂直组织
├── components/        # 已有两个以上稳定使用方的无业务原子组件
├── styles/            # Sass tokens、reset、全局布局和平台差异
└── generated/         # 从正式协议生成的只读类型
tests/
├── unit/              # Store、组件和协议投影单元测试
├── support/           # 测试环境初始化与跨测试复用夹具
└── e2e/               # Playwright 正式 Host 集成测试
```

- 先按 feature 就近放置组件、状态和样式，不提前建立庞大全局目录。
- feature 私有 Store 留在 feature 内；只有跨 feature 协调或应用生命周期 Store 才提升到
  `stores/`。
- 跨层协议应生成或映射自 `assistant-protocol`，不要在多个前端文件手写不同版本。
- `generated/`、`dist/` 和 `node_modules/` 不直接编辑。

### 3.1 Feature 内部结构

Feature 按实际复杂度逐步建立目录，不要求空目录占位。常见结构如下：

```text
features/conversation/
├── index.ts                    # 可选；只导出允许其他 feature 使用的公共入口
├── ConversationView/
│   ├── index.tsx               # 一个主要组件
│   ├── index.module.scss       # 与组件同生命周期的局部样式
│   ├── types.ts                # 仅该组件族使用的类型
│   └── useConversationView.ts  # 仅该组件族使用的 Hook
├── components/                 # feature 私有子组件
├── stores/                     # feature 私有 Store
├── constants.ts
└── utils.ts
```

- 无样式、无专用 Hook 的极小私有组件可以先保持单文件；需要配套样式或 Hook 的组件必须使用独立
  目录，以 `index.tsx`、`index.module.scss` 组织。不要在同一目录平铺
  `UserCard.tsx` 与 `UserCard.module.scss`，也不要把大量组件文件堆在 feature 根目录。
- 一个组件文件维护一个主要函数组件。具有独立状态、交互、样式块或测试价值的子组件必须拆到
  子目录；只用于当前 render 的极小无状态片段可以保留为私有函数，但不得逐步长成第二个组件。
- 与渲染无直接关系的映射、格式化、常量和类型从组件文件拆出；不要把组件文件变成同时承担协议
  转换、请求、状态机和 JSX 的综合模块。
- Feature 的 `index.ts` 只暴露稳定入口，不通配导出内部文件。跨 feature 依赖通过该入口，禁止
  深层路径引用对方私有组件、Store 或样式，也禁止形成 feature 循环依赖。

### 3.2 测试目录与命名

- `src/` 只存放生产源码，不放 `*.test.*`、`*.spec.*`、测试初始化、测试夹具或 mock；前端测试统一
  由应用根目录的 `tests/` 管理。
- Store、组件和协议投影测试放在 `tests/unit/`；公共初始化与确有多个测试使用的夹具放在
  `tests/support/`；Playwright 场景放在 `tests/e2e/`。生产源码不得反向导入 `tests/`。
- 单元测试文件使用可识别被测对象的语义名称和小写短横线，例如 `conversation-view.test.tsx`、
  `runtime-projection-store.test.ts`；禁止使用脱离源码目录后无法辨认对象的 `index.test.tsx`。
- 当前测试规模下 `tests/unit/` 保持单层语义文件；出现同一业务域的多份测试与专用夹具后，可以按
  `app`、`components`、`features`、`stores` 等源码业务域建立子目录，但不复制生产组件的 `index`
  文件结构。
- Vitest 的 `include` 和 `setupFiles` 必须显式指向 `tests/unit/` 与 `tests/support/`；TypeScript 和
  lint 范围必须覆盖测试目录，防止迁移后测试脱离静态检查。

### 3.3 组件层次与上提条件

- `app/` 组件只负责应用壳、全局 Provider、错误边界和路由/视图装配，不承载具体会话业务。
- `features/` 中的组件可以理解业务投影和用户意图，并在自身 feature 内组合 Store、Hook 与视图。
- `components/` 只放无业务归属、至少已有两个稳定使用方的交互原语或基础组件，例如 Button、
  Dialog、Menu、Listbox、Tooltip、Disclosure、RadioGroup 和 InlineEdit。
- 公共组件不得导入 feature、Root Store、Runtime Client 或 Native Bridge；它通过明确 Props、事件和
  `children` 工作。Feature 可以依赖公共组件，依赖方向不能反转。
- 上提公共组件前核对语义、交互状态、键盘行为和视觉 Token 是否真正相同。仅外观相似、业务规则
  不同的组件保留为各自 feature 组件，避免用条件分支制造伪复用。
- 扩展公共组件时先检查全部调用方。新增 API 应表达稳定能力，不接受只为一个页面存在的业务字段；
  无法保持公共语义时在 feature 层组合，而不是污染原语。

## 四、TypeScript

- 保持 `strict`，禁止用 `any` 绕过边界；未知外部输入使用 `unknown` 并显式收窄。
- Tauri invoke 的请求与响应必须有类型，不使用无约束对象。
- 状态枚举和事件分支应穷尽处理；运行时无法识别的新事件必须记录并触发相关快照恢复，不能继续
  用可能失真的投影运行，也不能导致界面崩溃。
- 命名表达业务语义，避免 `data`、`temp`、`foo` 等脱离上下文的名称。
- 不新增嵌套三目表达式；三目只用于简单二选一。条件或 JSX 需要换行阅读时，提前计算变量，或拆为
  `if/else`、语义函数、映射表或独立组件；不要为压缩行数把多分支业务逻辑塞进 JSX 属性和回调。
- 异步函数返回后必须重新核对其 owner 身份和版本，例如 `instance_id`、`session_id`、`run_id`、
  Conversation generation 或实体 revision；旧请求不得覆盖新导航状态。
- 组件和类型使用 PascalCase，Hook 使用 `useXxx`，Store 使用 `XxxStore`，用户意图方法使用动词开头；
  不用 `common`、`misc`、`helper` 等无法说明职责的目录或文件名汇集无关代码。
- Feature 目录使用小写短横线，组件目录使用 PascalCase，普通 TypeScript/Sass 文件按职责使用
  camelCase 或小写短横线；同一类别保持一致，不混用多套命名。
- 仅作为类型使用的导入使用 `import type`。共享类型放在最小稳定归属层，不因多个文件偶然使用就
  建立全局 `types.ts`。
- 不把 Runtime DTO 直接扩展成可写 UI 模型；界面草稿、选择和请求状态使用独立类型，避免修改投影
  时意外伪造 Runtime 事实。

## 五、React 组件

- React 组件负责组合视图和触发 Store action，不在 render、effect 或事件回调中复制 Runtime
  编排规则。
- 只有实际读取 observable 的组件使用 `observer`；优先在 feature 或叶级组件建立观察边界，
  不为方便把整个组件树无差别包成 `observer`。
- 单组件生命周期内的输入法状态、DOM 测量和临时开关可使用 React local state；需要跨组件协调、
  跨视图保留或由 Runtime 事件驱动的状态进入对应 Store。
- Effect 必须有明确依赖和清理函数。订阅、定时器、`ResizeObserver`、`AbortController` 和
  animation frame 不得遗留到组件或 Store 生命周期之外。
- 列表项使用稳定业务 ID 作为 key，禁止用数组下标承载可插入、删除或重排的消息、审批和队列。

### 5.1 组件职责与拆分

- Feature 入口组件负责取得 Store、选择投影并组合页面；子组件专注一段可描述的视图或交互。
  不强制机械区分 Container/Presentational，但单个组件不应同时承担请求、复杂状态编排、DOM 测量、
  多个浮层和大段列表渲染。
- 出现独立焦点管理、展开状态、键盘模型、滚动边界、错误边界或可单测交互时，应提取专用组件或
  Hook；不要只为了缩短文件行数拆出没有语义的 `Part1`、`Content`、`Wrapper`。
- 通用交互原语负责完整行为，而不只是画外观。例如 Dialog 同时负责 portal、focus trap、Escape、
  aria 关系和恢复焦点；调用方不应各自补一半行为。
- 组件不得直接查询 DOM 中其他 feature 的节点、依赖父页面的 class 名或修改全局样式来完成布局。
  跨区域协作通过 Store/协调组件的明确状态和意图完成。
- 不把完整 Root Store、巨型 Runtime 快照或无约束 `Record<string, unknown>` 作为 Props 传递。
  Feature 组件按需要选择实体和 action；公共组件只接收渲染与交互所需的最小语义数据。

### 5.2 Props 与组合 API

- Props 类型命名为 `XxxProps`，字段声明为只读；可选字段必须有清楚的缺省语义，不能让 `undefined`
  同时代表加载中、无权限和无数据。
- 公共组件、复杂 feature 组件和高频维护组件保留 `props` 参数，并在函数体内按需解构，以便阅读时
  区分外部输入和局部变量；参数极少且语义明确的简单组件可以直接解构，不作机械限制。
- 回调以用户意图命名，如 `onRename`、`onApprove`、`onOpenChange`，避免公共组件只暴露含义不明的
  `onAction`。事件参数传稳定业务标识或必要值，不泄露组件内部 DOM 结构。
- 同一状态只能选择受控或非受控的一种权威来源。支持两种模式的公共原语必须明确
  `value/defaultValue/onValueChange` 契约，禁止在 effect 中反复同步两份可写状态。
- 优先使用联合类型表达互斥形态，例如 `variant: "primary" | "danger"`；不要让多个布尔 Props
  形成无法解释的组合。只有真正正交的能力才使用独立布尔值。
- `className`、`style` 和 CSS Custom Property 只作为明确的外层布局/主题扩展口；调用方不得通过
  选择内部 class 或传任意样式覆盖组件结构。需要稳定变化时增加语义 Props 或组合 slot。
- `children` 和具名 slot 只承载结构组合，不用 render prop 隐藏业务状态机。需要复用的行为优先
  抽成 Hook 或无头原语，并为键盘与 aria 语义提供统一实现。

### 5.3 Hook、事件与渲染约束

- Feature 私有 Hook 与组件同目录；只有至少两个 feature 稳定复用且不依赖业务 Store 时才上提为
  公共 Hook。
- Hook 不建立 Runtime 权威状态的局部镜像。订阅或查询结果进入对应 Store；Hook 主要承担组件
  生命周期、DOM 能力、事件适配和组合选择。
- Render 保持纯函数，不在 render 中发请求、写 observable、调用 Tauri 或注册监听。事件处理器只
  发送一个明确意图，复杂流程进入 Store action 或 feature service。
- `useMemo`、`useCallback` 和 `memo` 只在引用稳定确实影响订阅、子组件更新或热点性能时使用，
  不作为默认样板。优化必须能够通过 Profiler、测试或明确依赖约束解释。
- Portal 浮层必须使用统一 overlay root 和层级 Token；定位更新、窗口缩放、滚动跟随和边界翻转由
  浮层原语统一处理，不由每个业务菜单重复实现。

## 六、MobX 状态管理

### 6.1 Store 装配与边界

- 使用显式 Root Store 装配 Store 依赖，并通过 React Context 注入；禁止导出可变全局 Store 单例。
- 至少区分 Runtime 连接、权威快照投影、活动流增量和纯 UI 状态，不把全部字段集中到一个巨型 Store。
- Runtime 快照是前端只读投影。Session、Run、Queue、Approval、ChildTask、Model 和 Permission 等
  业务事实只能通过 `applySnapshot`、`applyEvent` 或正式 Command 结果更新。
- 不允许为了即时反馈直接把投影改成成功态。业务 mutation 只能设置 pending/disabled，最终成功
  以 Runtime 响应或随后快照为准。
- 前端 Store 不持久化 Runtime 权威状态。`localStorage`、桌面偏好文件只保存明确的 UI 偏好，
  不能保存队列、审批、活动 Run 或模型配置副本。

### 6.2 Observable 与 Action

- 长生命周期 Store 使用 `makeObservable` 显式声明 observable、computed、action、flow 和 ref/shallow
  边界；不使用 `makeAutoObservable` 隐式扩大可观察面。短生命周期纯 UI 对象优先使用 React state，
  确需 Store 时也保持显式声明。
- 应开启 `configure({ enforceActions: "always" })`；同步修改放入 `action`，异步流程使用 `flow`
  或在每个 `await` 后用 `runInAction` 提交。
- 大型协议 DTO、Conversation Page 和工具输出优先使用 `observable.ref` 或
  `observable.shallow`，不要默认深度代理整个 JSON 树。
- `computed` 只做无副作用派生，不发起网络、Tauri 调用、写日志或修改其他 observable。
- Store 间调用通过构造时依赖或明确的协调 Store 完成，禁止形成相互 reaction 的隐式循环。
- 对外暴露表达用户意图的方法，不让组件直接取得并修改内部 observable collection。

### 6.3 查询、缓存与竞态

MobX 不自带服务端查询缓存能力，正式 Store 必须显式实现并测试：

- 相同 key 的进行中请求去重；
- 页面切换时取消不再需要的读取，但不得因此取消 Runtime Run；
- 实体的 loading、loaded、stale、error 和 revision/generation；
- 重试是否安全以及是否复用领域幂等键；
- Conversation 分页的数量或内存上限与淘汰策略；
- 命令结果、事件和重新查询之间的确定性覆盖顺序。

请求结果提交前必须核对当前 Runtime instance、owner ID 和 revision/generation。Stream gap、未知
事件、sequence 跳号或 instance 变化时，把相关投影标为 stale 并重新获取权威快照，不能继续拼接
旧增量。

### 6.4 流式更新与性能

- Text、Reasoning 和 Tool output 等高频 delta 先按 Run/Part/Call ID 缓冲，再在
  `requestAnimationFrame` 中用一次 action 批量提交；禁止每个 token 深度修改整份 Conversation。
- 活动流和已可靠提交的 Conversation 必须分层保存。Run/Child 终结并取得权威消息后，删除临时
  流投影，不能长期保留两份正文。
- 组件只读取需要的 observable；大型列表应分页、虚拟化或限制挂载数量，并使用稳定滚动锚点。
- 优化前先用 React Profiler、浏览器性能面板或可重复基准确认热点，不为假想性能提前拆 Store。

### 6.5 生命周期

- 持有 SSE、reaction、autorun、定时器、AbortController 或 animation frame 的 Store 必须实现
  幂等 `dispose()`。
- Root Store 负责按反向创建顺序释放子 Store；Session/Child 视图 Store 在导航离开时释放视图资源。
- reaction/autorun 必须保存 disposer；匿名注册后丢失 disposer 视为资源泄漏。

## 七、事件与状态

- 会话列表、历史消息以 Runtime 查询结果为准；前端缓存只是投影。
- 流式文本可以在内存聚合，但收到完成/失败事件后应以 Runtime 最终状态校准。
- 订阅必须在组件或页面销毁时解除，避免重复监听和重复追加 token。
- 每个事件携带并核对 `session_id`、`run_id`、`message_id`，禁止仅按“当前会话”接收异步结果。
- 启动时应先建立事件缓冲，再通过带观察水位的快照对齐；UI 刷新、窗口重建、断线和事件缺口都
  通过权威快照恢复，不能假设事件从不丢失。
- 事件 reducer 必须幂等。重复事件不得重复追加文本、工具、审批或消息；逆序和跳号按协议要求
  忽略或触发恢复。

## 八、安全与桌面体验

- Shell 确认必须显示完整原始脚本、工作目录、权限范围和风险提示。
- 不在 DOM、日志、localStorage 中保存 API Key、令牌或完整敏感文件内容。
- 外部 Markdown/HTML 默认不可信；渲染前清洗，链接和资源加载遵循明确策略。
- 长任务必须可停止，并展示运行、等待确认、失败和取消状态。
- 关闭窗口、隐藏窗口和退出应用的文案必须准确区分。

## 九、Sass、样式与可访问性

- 优先语义化 HTML，交互元素使用 `button`、`input` 等原生元素。
- 键盘操作、焦点、加载、错误和空状态必须可见。
- 使用 Dart Sass 的 `sass` 包，不使用 `node-sass`。SCSS 统一使用 `@use`/`@forward`，不使用
  已弃用的 `@import`。
- WKWebView 是 macOS 目标渲染环境；使用新 Web API/CSS 前确认最低 macOS 对应支持情况。

### 9.1 样式文件归属

`styles/` 按是否输出全局 CSS 区分职责，文件名可随实现调整，但不能混淆边界：

```text
styles/
├── index.scss       # 应用唯一全局入口
├── tokens.scss      # 输出 :root 下的 --ez-* 设计 Token
├── reset.scss       # reset 与基础元素规则
├── app-shell.scss   # 应用根布局和 overlay root
├── motion.scss      # 全局动效与 reduced-motion 基线
├── platform.scss    # 明确的平台根差异
└── _tools.scss      # 仅 Sass 函数/mixin，不输出选择器
```

- Feature/component 样式使用 `*.module.scss` 并与组件目录共存；组件删除时能同时定位并删除其样式。
  禁止为方便把业务组件 class 添加到 `styles/` 的全局文件。
- 全局样式只承担 reset、基础字体、设计 Token、AppShell 根布局、overlay root、motion/accessibility
  基线和明确的平台差异，并且只从应用入口导入一次。
- `styles/` 中只供 Sass 复用的变量、函数和 mixin 不应输出选择器，避免被多个 Module `@use` 后重复
  生成全局 CSS。会输出 CSS Custom Properties 或 reset 的入口必须与纯工具文件分离。
- 组件样式不跨目录导入其他组件的 Module。需要共同视觉能力时优先复用设计 Token、无输出 mixin
  或公共组件，而不是共享一组内部 class。
- 静态样式写入 SCSS Module；React `style` 只用于运行时计算值，并优先通过有名称的 CSS Custom
  Property 传入。禁止在 JSX 中长期维护颜色、间距、圆角、阴影和 z-index 等静态样式。

### 9.2 Token、命名与选择器

- Sass 变量用于构建期计算；需要被多个组件或运行时状态使用的颜色、间距、字号、圆角、阴影和层级
  输出为 `--ez-*` CSS Custom Properties。禁止在 TypeScript 和 SCSS 中各维护一份相同 Token 数值。
- 字号只允许使用三档设计 Token：`--ez-font-small`（12px，仅时间戳、徽章、辅助 meta 等非正文信息）、
  `--ez-font-base`（14px，正文与主要交互文字基准）、`--ez-font-large`（16px，页面与对话框标题）；
  禁止在组件样式中新增其他字号的字面量。
- 不是每个局部尺寸都必须成为全局 Token。只在单组件中表达结构的数值可留在 Module；同一语义在
  两处以上出现或属于设计语言基准时再提升，避免形成无语义的数字 Token 表。
- CSS Module 类名统一使用下划线格式，例如 `styles.message_row`、`styles.action_group`，使 JSX 中的
  样式引用与普通 TypeScript 标识符形成清楚区分。类名表达组件结构或语义，不使用颜色、坐标或
  `box1` 等表现型命名；CSS Modules 已提供作用域隔离，不再额外建设全局 BEM 体系。
- 交互状态优先使用原生伪类、`aria-*` 或 `data-state`/`data-variant`，不在 TypeScript 中拼接多个
  近义状态 class。状态属性值使用稳定的小写短横线格式。
- 选择器以本组件根节点为边界，嵌套通常不超过两层；禁止依赖 `div > div:nth-child(...)`、父页面
  class 或完整 DOM 路径。不要选择 CSS Module 生成后的哈希类名。
- `:global` 仅用于 reset、Tauri/WebView 根节点或明确的第三方内容接缝，并集中在有说明的适配文件；
  业务 Module 不用 `:global` 穿透其他组件。

### 9.3 盒模型与布局所有权

- 父布局决定子组件的位置、轨道、间距和可用宽度；组件根节点负责自身尺寸约束，不通过外边距偷偷
  推开周围元素。可复用组件根节点默认不设置场景相关 `margin`。
- Flex/Grid 中可能收缩的文本轨道显式使用 `min-width: 0`；滚动区必须有明确高度约束、滚动所有者和
  overscroll 行为，不能依靠父级 `overflow: hidden` 裁掉几像素来制造二级抽屉重叠。
- 文本、弹窗 Header、列表项和可本地化内容优先使用 `min-height` 与内容撑开，不用固定高度掩盖换行。
  只有图标按钮、头像、进度环等明确等宽高元素使用固定尺寸。
- 响应式布局优先 CSS Grid/Flex、container query 或 media query；如果 CSS 可以决定，不在 React
  中监听窗口宽度切换两套 DOM。平台差异由平台配置或根 `data-platform` 边界表达，不用 user-agent
  或零散 CSS 猜测。
- 共享层级使用语义 z-index Token，例如 base、sticky、popover、modal、toast；禁止新增 `9999`
  一类竞争数值。浮层被裁切时先检查 portal、stacking context 和滚动容器，不用提高 z-index 掩盖。

### 9.4 复用、覆盖与可访问状态

- 不滥用 `!important`、`@extend` 或全局选择器修补局部组件。需要覆盖时依次检查样式归属、Token、
  组件 Props/slot 和布局所有权；确有兼容覆盖时写明原因与删除条件。
- 公共组件不得要求调用方复制内部选择器才能完成 hover、selected、disabled、loading、invalid 和
  focus 状态。所有支持状态必须由组件 API 或标准属性驱动，并在同一 Module 内完整定义。
- Hover 不能是唯一反馈；键盘焦点使用可见的 `:focus-visible`，禁用状态保留可读对比度并同步原生
  `disabled`/`aria-disabled` 语义。图标按钮必须有可访问名称和足够命中区域。
- 动效使用统一 duration/easing Token，并遵守 `prefers-reduced-motion`。布局状态切换避免弹性过冲、
  大范围位移和持续动画；loading 状态也不得造成周围文本或按钮抖动。
- 修改样式时至少检查默认、hover、focus、disabled、loading、空、错误和内容超长状态；涉及浮层或
  密集布局时检查 100%、125%、150% 缩放、窄窗口、滚动边界和 Tooltip/Popover 裁切。

## 十、注释与可维护性

- 解释性注释默认使用中文；组件名、协议字段、浏览器/Tauri API、CSS 属性和外部库名称可保留英文。
- 组件、Hook、Store、协议投影和样式代码在存在非显然约束时必须补充必要中文注释，重点说明业务意图、
  权威状态来源、订阅与清理、竞态处理、滚动锚点、焦点恢复、Portal 层级、平台差异和兼容取舍。
- 公共组件或 Hook 的注释必须说明适用边界、受控状态和调用方责任；不能只复述 Props 或函数签名。
- CSS 中的特殊层级、负偏移、裁切规避和浏览器兼容规则必须说明原因与删除条件，不允许留下无法解释的
  魔法数修补。
- 禁止给显然的赋值、条件或 JSX 结构逐行加注释。缺失必要注释、注释过时或与实现不一致都视为缺陷，
  不能等到用户 Review 时再补。
