# 开发流程规范

本规范定义 `ez-assistant` 的需求输入、功能设计、开发、验证、归档和提交准备流程。处理需求、设计文档、版本台账、代码开发或版本归档时必须遵守本文件。

核心原则：项目以版本为主线，不以单个需求为独立流程单元；一个版本聚合一组方向一致的改动，统一完成设计、计划、实现验证和归档；根据改动范围选择必要文档；每一步和每个开发里程碑完成后暂停，等待用户确认再继续；每次进入新的版本阶段时同步修订 `docs/版本管理.md`；结论必须可验证。

## 一、文件与目录职责

- `docs/inputs/`：尚未归入版本的原始想法、需求和外部输入的长期记录池；随时可写，但不是独立开发流程的起点。
- `docs/design/`：规划、设计、开发或验证中的版本文档。
- `docs/specs/`：跨版本长期有效的开发规范与模板。
- `docs/modules/`：各应用和 crate 的长期职责、依赖与验证约束。
- `docs/resources/`：外部资料、截图、协议和样例。
- `docs/versions/`：已完成或暂停版本的只读归档。
- `docs/版本管理.md`：版本路线图、当前版本和历史版本的共享台账。
- `docs/重要决策与变更记录.md`：跨版本长期生效的架构与协作决策。
- `docs/specs/开发进度模板.md`：本地开发进度初始化模板。
- `docs/开发进度.md`：本地在途状态与开发过程记录，已被 Git 忽略，不提交；版本归档时本版本内容随版本移入归档目录一并提交。

## 二、版本主线

正式版本遵循：

```text
确定目标版本（待启动）
→ 功能设计（进入设计中）
→ 技术方案（按需，保持设计中）
→ 界面交互设计指导（按需，保持设计中）
→ 开发计划（计划中）
→ 分里程碑代码开发（开发中）
→ 版本验收（验证中）
→ 版本归档（已完成 / 已暂停）
→ 提交准备（用户明确要求时）
```

### 确定目标版本

启动版本前明确：

- 版本号和状态。
- 本版本目标与成功标准。
- 纳入范围和明确不做的内容。
- 主要模块和能力影响。
- 预计里程碑及风险。

版本号默认遵循语义化版本。`0.x` 阶段以能够独立验收的能力里程碑推进，不要求为每个细小变化递增版本。

版本是目标、范围、计划、验收和归档的唯一主键。单个需求点、缺陷或重构先判断是否属于当前版本，不为它机械创建一套独立流程文档；同一版本中的相关改动合并进版本文档，避免产生大量碎片化主题文档。

### 逐步确认规则

- 一次只推进当前被授权的步骤。
- 功能设计、技术方案、交互指导和开发计划分别形成可核验产物。
- 用户只要求某一类文档时，只完成该文档及保证其一致性所必需的索引或规范更新，不自行进入下一阶段。
- 开发计划得到确认后，只开始第一个未完成里程碑。
- 每个里程碑执行"核查 → 实现 → 最小有效验证 → 汇报实际结果 → 用户确认 → 进入下一里程碑"。
- 里程碑完成实现和验证后状态先改为 `🟨 待确认`；用户确认后才改为 `✅ 已完成`。
- 里程碑确认是强制门禁：
  - 汇报必须说明实际产出、执行的验证、未执行项、偏差、遗留和风险。
  - 用户明确确认前，不得开始下一里程碑的代码、依赖或协议改动。
  - 确认前可以修复当前里程碑的缺陷、补充验证和同步文档，但不能扩大到下一里程碑范围。
  - 用户要求调整当前里程碑时，完成调整和重新验证后再次等待确认。
  - 版本计划整体已确认、当前结果看似无风险或下一步有明显依赖，都不能替代里程碑确认。
- 实际实现与设计假设不符时停止扩大改动，先更新设计并重新确认。

### 从哪里切入

- 路线图主版本、跨模块能力或多阶段工程建设：走完整版本主线。
- 当前版本内的小修复和实现细节：直接纳入当前里程碑，不单独启动需求流程。
- 版本开发期间收到新事项时，先判断是否服务于当前版本目标：属于当前范围的，更新功能设计或计划后继续；明显扩大目标、改变关键架构或影响交付节奏的，放入后续版本或重新确认当前版本范围。
- 用户明确要求某种产物时，从对应步骤切入。

无论从哪里切入，代码修改前都必须读取根 `AGENTS.md`"动手前必读"要求的对应编程规范和模块约束。

### 版本状态同步

`docs/版本管理.md` 是版本状态的共享事实源。版本阶段发生变化时，状态修订是进入下一阶段的必要步骤，不能只更新版本文档或本地开发进度。

| 触发条件 | `docs/版本管理.md` 状态 | 必须同步的内容 |
| --- | --- | --- |
| 版本已列入路线图或被确定为当前目标，但尚未开始设计 | `待启动` | 当前目标版本、目标、关联输入和下一步 |
| 开始编写或实质讨论功能设计 | `设计中` | 当前版本状态、设计入口；已有功能设计时登记链接 |
| 功能设计及所需技术方案、交互指导均已确认，开始形成开发计划 | `计划中` | 当前版本状态、已确认设计链接和开发计划入口 |
| 开发计划已确认，准备开始第一个代码里程碑 | `开发中` | 当前版本状态、开发计划链接和当前开发重点 |
| 全部开发里程碑已确认，开始版本验收 | `验证中` | 当前版本状态和验收记录入口 |
| 用户确认验收通过，且文档移动、版本总结和链接修订全部完成 | `已完成` | 从路线图详细登记移入历史版本，记录完成日期、归档、结果、验证结论和总结 |
| 用户明确暂停版本，且暂停原因、恢复条件和现有文档已经归档 | `已暂停` | 从路线图详细登记移入历史版本，记录暂停日期、原因、恢复条件和归档 |

同步规则：

- 状态必须在进入对应阶段时更新；不得已经开始代码开发却仍标记为 `设计中` 或 `计划中`。
- 状态推进以用户确认和实际阶段为准，不能仅因文件已经创建就提前推进。
- 技术方案和界面交互设计指导仍属于 `设计中`，不额外增加版本状态。
- 等待功能设计、开发计划、里程碑或验收确认时，在对应文档和 `docs/开发进度.md` 中记录"待确认"，不为此新增版本状态。
- 当前版本因重大范围变化退回设计时，状态同步退回 `设计中`；恢复暂停版本时，根据实际续作阶段设置为 `设计中`、`计划中`、`开发中` 或 `验证中`。
- `已完成` 以用户验收通过和版本归档完成为条件，不以 Git commit、tag 或 push 为条件。
- 每次修订状态后都要核对路线图条目、"当前版本"、"历史版本"、在途文档链接和归档链接是否一致。
- 如果版本管理状态与实际阶段不一致，必须先修正状态，再继续下一阶段。

### 版本文档命名

- 在途文档统一使用目标版本号前缀：`docs/design/vX.Y.Z-<文档类型>.md`。
- 同一版本只有一份主功能设计和一份主开发计划。确需拆分专题时，专题文档仍以版本号为前缀，并在主文档中建立索引。
- 不要以 `YYMMDD-需求主题` 作为主要开发和归档单元；日期只用于输入文档记录时间，不代替版本号。

## 三、进度同步

`docs/开发进度.md` 用于长任务本地恢复，不作为共享事实源。不存在时从模板初始化：

```bash
cp docs/specs/开发进度模板.md docs/开发进度.md
```

推进规则：

- 确认当前版本后，填写版本、分支、当前阶段和当前里程碑。
- 开始里程碑时标记 `🔄 进行中`。
- 完成实现和验证后记录实际产出、命令、结论、偏差与遗留，标记 `🟨 待确认`。
- 用户确认后标记 `✅ 已完成`，再填写下一里程碑续作点；每个里程碑的用户确认结果同步到开发计划，本地进度在确认前保持"等待确认"。
- 切走前写清"下一步、续作点、等待/阻塞"。
- 共享范围、设计、里程碑和验收变化必须更新在途版本文档，不能只写本地进度。
- 版本阶段发生变化时，同时更新 `docs/版本管理.md`；`docs/开发进度.md` 不能替代版本台账。
- 版本归档时本版本进度内容随版本移入归档目录，归档后清理本地进度中的已归档内容。

## 四、需求输入

尚未确定版本归属的想法和需求存放为：

```text
docs/inputs/YYMMDD-<简述>.md
```

要求：

- 保留用户原始语义，不提前改写为技术方案；输入文档用于保留原始意图，不要求提前给出完整方案、验收标准或开发计划。
- 至少写清：记录日期；当前状态（待评估 / 已纳入版本 / 暂缓 / 不采纳）；原始想法或期望结果；必要的背景、约束和补充材料；已纳入版本时标明目标版本号。
- 不把未经确认的推断写成需求事实。
- 启动或调整版本时统一评估输入池：被选中的内容由功能设计吸收并建立引用，未选中的内容继续保留，不因版本启动而自动关闭或归档。
- 没有独立输入文档时，功能设计注明来源为路线图、已确认决策或用户会话结论。
- 输入数量不决定版本边界，版本目标决定纳入范围。

建议结构：

```markdown
# <主题>

- 记录日期：YYMMDD
- 状态：待评估 / 已纳入版本 / 暂缓 / 不采纳
- 来源：<用户、外部资料等>
- 目标版本：vX.Y.Z / 待定

## 原始内容

<保留原意的想法或期望结果>

## 背景与约束

<必要的背景、约束和补充材料>
```

## 五、功能设计

路径：

```text
docs/design/vX.Y.Z-功能设计.md
```

开始编写或实质讨论功能设计时，将 `docs/版本管理.md` 中当前版本状态更新为 `设计中`，并在创建功能设计文件后登记入口；状态和入口必须在同一步中保持一致。仅列入路线图、尚未开始设计的版本保持 `待启动`。

功能设计承担类似 PRD 的职责：说明版本最终要形成的系统能力和关键取舍，保持能力与使用视角。类型定义、包结构、接口签名和依赖版本等实现细节放入技术方案。

不涉及具体业务功能的版本（如纯引擎或基础设施版本），功能设计仍从能力视角描述版本要形成的能力闭环与验收标准，文档名称和结构保持一致。

必须包含：

- 版本、状态、影响模块和需求来源；
- 背景、目标和明确非目标；
- 功能范围和使用路径；
- 模块职责、依赖和契约影响；
- 关键取舍及理由；
- 可逐条验证的验收点；
- 风险、兼容性和待确认项。

开放问题应在设计确认前解决。确实无法在当前阶段确定的实现细节，必须说明归属到技术方案或具体里程碑，不能伪装成已确认结论。

建议结构：

```markdown
# vX.Y.Z 功能设计：<版本主题>

## 一、设计信息

- 版本：
- 状态：
- 影响模块：
- 需求来源：

## 二、背景与目标

## 三、非目标

## 四、功能范围与使用路径

## 五、模块边界与契约影响

## 六、关键取舍

## 七、验收标准

## 八、风险、兼容性与待确认项
```

功能设计完成后必须判断是否需要技术方案和界面交互设计指导。功能设计及所需设计文档全部获得确认、准备编写开发计划时，将 `docs/版本管理.md` 状态更新为 `计划中`。

## 六、技术方案

适用条件：

- 新建或重构 crate、应用或工程结构；
- 引入或更换核心依赖；
- 涉及协议、配置、持久化、文件格式或跨模块契约；
- 存在重要安全、兼容、性能或恢复取舍；
- 实现路径仅靠功能设计无法准确落地。

路径：

```text
docs/design/vX.Y.Z-技术方案.md
```

简单、低风险改动可不单独创建技术方案，但必须在开发计划中说明不需要的原因。

建议结构：

```markdown
# vX.Y.Z 技术方案：<版本主题>

## 一、方案信息

- 版本：
- 状态：
- 影响模块：
- 关联功能设计：

## 二、现状核查

## 三、目标架构与依赖

## 四、分模块实现方案

## 五、配置与运行约定

## 六、测试与验证

## 七、风险、兼容与排除项
```

技术方案必须基于真实仓库和依赖核查（实际代码路径、`cargo metadata`/`cargo tree` 等），不得只凭历史认知设计。涉及数据库时必须遵守根 `AGENTS.md` 的数据库操作安全规则。

## 七、界面交互设计指导

适用条件：

- 新增窗口、页面或应用壳层；
- 大幅调整页面结构、导航或状态流转；
- 复杂表单、可视化或多步骤交互；
- 视觉和交互验收无法仅靠功能设计表达。

路径：

```text
docs/design/vX.Y.Z-界面交互设计指导.md
```

纯 Rust crate 改动或极小界面调整时可以跳过。

建议结构：

```markdown
# vX.Y.Z 界面交互设计指导：<版本主题>

## 一、设计信息

- 版本：
- 状态：
- 影响模块：
- 关联设计：

## 二、页面与入口

## 三、布局与信息结构

## 四、交互流程

## 五、视觉与组件规范

## 六、状态与异常

## 七、验收口径
```

交互指导应说明真实窗口或页面入口、布局关系、状态、操作反馈、异常和视觉约束，并与 `docs/modules/desktop.md` 的模块约束一致。不得仅写"参考某项目"而缺少本项目落地口径。

## 八、开发计划

路径：

```text
docs/design/vX.Y.Z-开发计划.md
```

进入本阶段时，`docs/版本管理.md` 中当前版本状态必须为 `计划中`，并登记已经确认的设计文档和开发计划入口。

开发计划排在已需要的技术方案和交互指导之后。它是当前版本的**实施台账**，用于回答“分几步、
每步交付什么、如何确认、现在到哪里”，而不是第二份功能设计或技术方案。计划围绕版本能力闭环
拆分为可独立实现、验证和确认的里程碑，不按文件列表或零散需求清单机械拆分。

统一结构：

1. 计划信息与设计依据；
2. 台账原则；
3. 里程碑总览；
4. 各里程碑的目标、交付范围、验证入口、完成判定和 Review 重点；
5. 版本级完成条件。

开发计划不得重复展开已经存在于功能设计、技术方案或交互设计中的内容。以下内容原则上只放在
技术方案或其附件，并由计划链接引用：

- 类型定义、函数签名、模块树和依赖清单；
- 协议字段、状态转换、并发流程、算法和异常处理细节；
- UI 布局尺寸、完整快捷键表、组件内部状态和事件循环设计；
- 大段伪代码、调用链和测试夹具实现。

如果没有单独技术方案，确实影响排期与验收的最小实现约束可以写入计划，但仍应保持原则性，不把
开发计划扩展成混合设计文档。

里程碑使用 `M0`、`M1`、`M2` 顺序编号，状态统一为：

- `⬜ 未开始`
- `🔄 进行中`
- `🟨 待确认`
- `✅ 已完成`
- `⏸ 已暂停`

每个里程碑必须写清：

- 目标；
- 前置依赖；
- 交付范围；
- 验证入口及必要命令；
- 完成判定。

里程碑完成后在 `docs/开发进度.md` 对应里程碑小节记录"实际结果"，至少包含产出、验证、偏差、遗留和风险；开发计划只维护里程碑状态，不记录开发过程。

开发计划获得用户确认后，在开始第一个代码里程碑之前，将 `docs/版本管理.md` 状态更新为 `开发中`。计划确认本身不授权跳过里程碑确认规则。

## 九、代码开发

代码开发按已确认开发计划推进。

每个里程碑执行：

1. 核对 `docs/版本管理.md` 中当前版本状态为 `开发中`；不一致时先修订版本台账。
2. 核对工作树、当前版本、里程碑授权和涉及模块。
3. 读取对应编程规范与模块约束。
4. 核查现有实现和依赖，再新增模块、trait 或公共类型。
5. 实现当前里程碑范围，并同步补充或更新必要的中文注释。跨层边界、状态所有权、并发与取消、
   安全权限、兼容迁移、恢复策略、反直觉平台差异和非显然算法不得只靠代码自行解释。
6. 执行该里程碑最小有效验证。
7. 在 `docs/开发进度.md` 记录里程碑实际结果（产出、验证、偏差、遗留、风险）。
8. 将里程碑状态改为 `🟨 待确认`。
9. 汇报实际产出、验证、偏差、遗留和风险。
10. 等待用户确认。

注释属于实现质量的一部分，不能留到用户 Review 时再补。禁止用逐行翻译代码的低价值注释凑数；
缺失必要注释、注释与实现不一致或仍保留已失效说明，都视为当前里程碑未完成。

禁止：

- 未确认当前里程碑就开始下一里程碑；
- 把多个未验证阶段堆到版本末尾统一测试；
- 顺手实现后续版本业务；
- 覆盖用户已有改动；
- 未经明确要求执行 `git commit` 或 `git push`。

出现以下任一情况必须停止扩大改动并重新核对：

- 现有实现与功能设计假设不符。
- 关键协议、权限、持久化或架构取舍尚未确定。
- 测试或构建暴露非预期跨模块影响。
- 涉及破坏性文件、数据库或 Git 操作。
- 工作树存在与当前版本改动重叠的未知修改。

## 十、版本验收

全部开发里程碑获得用户确认后，先将 `docs/版本管理.md` 状态更新为 `验证中`，再创建验收记录并执行版本级验证。

进入验证阶段时创建：

```text
docs/design/vX.Y.Z-验收记录.md
```

验收记录至少包含：

- 实际环境与工具链版本；
- 实际执行命令；
- 自动测试、构建和运行结果；
- 人工核对结果；
- 未执行项及原因；
- 与设计相比的偏差；
- 遗留问题和风险；
- 是否达到版本完成门槛；
- 用户验收结论。

版本级验证使用各里程碑验证结果的合集（记录于 `docs/开发进度.md` 对应里程碑小节），加上验收阶段的实际执行结果。不能以"应该通过""命令已运行"代替实际结果；测试、构建、文件和接口展示状态必须按实际情况区分。

验收检查完成但尚未获得用户确认时，版本仍保持 `验证中`，不能提前标记为 `已完成`。

## 十一、版本归档

用户确认验收通过或明确暂停版本后，执行归档：

1. 创建 `docs/versions/vX.Y.Z/`。
2. 将本版本在途文档从 `docs/design/` 移入归档目录。
3. 去掉文件名中的版本前缀，统一为：
   - `功能设计.md`
   - `技术方案.md`
   - `界面交互设计指导.md`
   - `开发计划.md`
   - `验收记录.md`
   - 专题文档同样去掉版本前缀（如 `代码审查.md`）。
4. 不存在的可选文档不补空文件。
5. 新增简洁的 `版本总结.md`，记录实际完成范围、验证结论、偏差、遗留项和后续版本入口。
6. 修正归档内部引用。
7. 在 `docs/版本管理.md` 中将该版本从路线图详细登记移入历史版本，记录完成或暂停日期、归档目录、实际结果、验证结论和版本总结。
8. 将 `docs/开发进度.md` 中本版本的进度内容移入归档目录（命名 `开发进度.md`，随归档一并提交）；本地进度清理已归档内容，并登记下一个当前目标版本，尚未启动设计时状态为 `待启动`。

归档使用移动而不是复制；`docs/design/` 与归档目录不能同时保留同一版本副本。归档目录视为只读；后续纠错保留变更说明，不把新版本工作追加到旧归档。

暂停版本使用同样流程，并在版本总结和 `docs/版本管理.md` 中记录暂停原因和恢复条件。

## 十二、提交准备

归档与提交准备是两个独立步骤。版本开发中可以存在多个提交，归档不要求与 Git 提交一一对应；归档完成不代表自动暂存或提交。

未经用户明确要求：

- 不执行 `git add`；
- 不执行 `git commit`；
- 不执行 `git push`。

用户明确要求提交准备时：检查改动、暂存指定文件、为每个获授权范围草拟 commit message，并向用户报告暂存范围和未暂存改动。

commit message 使用：

```text
<type>: <message>
```

`type` 可取 `feat`、`fix`、`docs`、`style`、`refactor`、`perf`、`test`、`chore`。

## 十三、验证矩阵

按实际改动选择最小有效验证：

| 改动范围 | 最低验证 |
| --- | --- |
| 仅文档 | 相对链接、路径、命令和文档一致性检查 |
| Rust 格式或小型实现 | `cargo fmt --all --check` + 相关 crate 测试 |
| Rust 公共 trait、协议、并发或 Runtime | `cargo clippy --workspace --all-targets --all-features -- -D warnings` + `cargo test --workspace` |
| 前端 TypeScript/CSS | `cd apps/desktop && npm run build` |
| Tauri command、配置、capability | 前端构建 + `cargo test --workspace` + `npm run tauri -- build --no-bundle` |
| 窗口、托盘、快捷键、macOS 权限 | 构建 + 实机启动和交互验证 |
| 版本阶段转换 | `docs/版本管理.md` 的状态、当前版本、路线图/历史版本位置和文档链接与实际阶段一致 |

无法执行的验证必须记录原因、影响和替代证据。

## 十四、长期决策与范围变化

以下内容同步更新 `docs/重要决策与变更记录.md`：

- 架构、模块边界和目录结构；
- 核心技术栈、依赖方向和运行方式；
- 跨模块协议、权限、安全、持久化和部署策略；
- 版本、里程碑、归档和提交协作机制；
- 用户确认的重大范围调整和验收口径。

临时实现细节和单个里程碑进度不进入重要决策记录。
