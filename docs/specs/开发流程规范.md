# 开发流程规范

本规范定义 `ez-assistant` 的需求输入、设计、开发、验证、归档和提交准备流程。处理需求、设计文档、版本台账、代码开发或版本归档时必须遵守。

核心原则：

- 项目以对外发布版本为主线，不为内部开发阶段机械提升版本号。
- Feature 归属确定的目标版本，是版本内可独立设计、实现和验收的能力或问题；里程碑是 Feature 内的实施步骤。
- Feature 完成不等于版本验收或发布；Git 提交不作为进入下一 Feature 的前置条件。
- 每个里程碑和 Feature 完成后汇报并等待用户确认；结论必须可验证。
- 文档只为决策和恢复服务：同一事实只登记一处，其余位置链接引用。

### 全局最小新增原则

需求分析、功能设计、技术方案、代码实现、数据、协议、UI 交互和测试方案都必须优先复用、调整或组合现有事实与机制，不能把“新增一层”当作默认解法。

- 新增实体、状态、字段、DTO、enum variant、表、文件、缓存、队列、服务、Adapter、trait、模块、帮助类型或并行执行路径前，必须先搜索现有实现，并说明现有能力为什么不能直接承载需求。
- 同一业务事实已经存在时，展示、传输或命名差异不构成新实体。优先在现有聚合、投影、枚举或装配流程中内联表达；不得为同一事实创建包装实体、第二份状态或另一套生命周期。
- 只有新增对象具有独立身份、独立所有权、独立生命周期、不同事务边界或至少一个已存在的稳定替换／复用边界时，才允许引入新的实体或抽象；“以后可能需要”“看起来更完整”“便于扩展”不能单独作为理由。
- 若一个局部需求开始连带引入新的持久化、分页、恢复、迁移、全局计数或跨层状态同步，必须立即停止扩大实现，重新核对是否把简单展示或适配问题升级成了新的业务机制。
- 兼容层、旧字段别名、双读双写、迁移分支、旧命令转发和旧格式回退同样属于新增机制，不能以“更稳妥”为由默认加入：
  - 同一目标版本尚未正式发布时，版本内的临时命名、字段、协议或存储形态调整默认直接统一到最终设计，不为中间形态保留兼容代码、别名或迁移逻辑。
  - 跨已发布版本也不默认保留兼容。先评估受影响的协议、配置、持久化数据、文件格式、客户端和回滚路径，在实施兼容、迁移、拒绝旧格式或破坏性升级前取得用户确认。
  - 只有存在正式用户数据、已发布客户端、外部契约或已确认的滚动升级场景时，才把兼容机制列为候选；本地开发缓存和未发布的临时构建不构成长期兼容理由。
- 验证遵循最小有效范围：先执行直接覆盖改动的编译、静态检查或单项测试；只有失败证据、高风险边界或里程碑验收明确要求时才扩大，不用大量无关验证替代设计正确性。
- 验证是开发动作，不是文档交付物。不单独创建验证记录、测试报告或验证数据归档；命令输出、测试数量、数据库快照、逐表计数、临时制品和日志明细不写入设计、计划或进度。计划和进度只保留完成结论、用户确认、未完成项与必要风险；详细情况按需在会话中说明。数据库操作仍须遵守安全核对、备份与实际结果汇报要求。
- 设计与 Review 必须回答“删除本次新增机制后，现有事实是否已经足够”；答案为是时删除新增机制，而不是继续为其补充合理性。

## 二、版本主线

### 简单版本与复杂版本

版本启动时先判断目标范围，再决定需要几个 Feature。只有存在可独立验收的能力或问题边界时才拆成多个 Feature；不必在版本启动时确定后续 Feature 的内部方案。

| 情况 | 判断依据 | 实现方式 | 设计与验收 |
| --- | --- | --- | --- |
| 简单版本 | 目标集中、边界清楚，一次设计和验收即可收口 | 一个 Feature，可含多个里程碑 | 版本《功能设计》同时承担总体设计；Feature 验收与版本验收合并，不重复设置阶段验收 |
| 复杂版本 | 多个能力或问题各有验收边界 | 多个 Feature | 先确认唯一的《总体设计》；各 Feature 独立验收，最后做版本整体验收 |

Feature 围绕完整能力或明确问题，可以跨多个工程，也可以合并共同构成能力闭环的相关需求；不按页面、语言、代码目录或零散需求机械拆分。单 Feature 版本不重复创建《总体设计》或 Feature 级文档。

### 流程

```text
单 Feature：确定目标版本（待启动）→ 功能设计（设计中）→ 技术方案／交互指导（按需）
           → 开发计划（计划中）→ 分里程碑开发（开发中）→ 版本验收（验证中）
           → 版本归档（已完成／已暂停）→ 提交准备（用户明确要求时）

多 Feature：确定目标版本并确认《总体设计》
           → 逐个 Feature（设计 → 方案 → 计划 → 分里程碑实现 → Feature 验收 → 完成结论）
           → 跨 Feature 版本验收 → 版本归档与发布准备
```

Feature 不是软件版本，不产生新的 SemVer、兼容下限或发布标签。

### 确定目标版本

启动版本前明确：版本号和状态、目标与成功标准、纳入范围和明确不做的内容、主要模块和能力影响、预计里程碑及风险。

版本号默认遵循语义化版本。`0.x` 阶段以能够独立验收的能力里程碑推进，不为每个细小变化递增版本。版本是对外交付目标、总范围、最终验收和发布归档的唯一主键。单个需求点、缺陷或重构先判断是否属于当前版本；属于当前 Feature 的小修复直接纳入。只有能形成独立范围和验收结果时才建立新的 Feature，并同步版本目标和整体验收口径。

### 版本、Feature 与里程碑

| 层级 | 标识 | 承担的事实 | 不承担的事实 |
| --- | --- | --- | --- |
| 发布版本 | `vX.Y.Z` | 最终产品能力、总范围、兼容、发布产物和整体验收 | 内部阶段编号 |
| Feature | `F01`、`F02` | 所属版本内一项能力或问题的范围、设计、实现和验收结论 | SemVer、发布标签和对外完整版承诺 |
| 里程碑 | `M0`、`M1` | Feature 内部的实现、集成和定向验证步骤 | Feature 验收或版本验收 |

单 Feature 版本的唯一 Feature 无需编号。Feature 编号只在所属版本内有意义。

### 复杂版本的分批原则

按业务能力、状态所有权和稳定契约分批。每个 Feature 必须：

- 形成一个可独立说明、实现和验证的能力结果；
- 明确所属的权威状态、数据和失败恢复边界；
- 明确依赖哪些已完成 Feature，以及向后续 Feature 提供的稳定契约；
- 在实现和验证完整收口后标记完成，不把未验证代码留给版本末尾统一补测，也不以空实现或依赖后续重写的过渡结构冒充完成。

多 Feature 版本的《总体设计》在首个 Feature 进入实现前必须获得用户确认。Feature 设计引用《总体设计》的对应目标、边界和契约，不得自行改变版本方向。《总体设计》确需变更时，先记录原因、影响的 Feature 和重新验证范围，获得确认后更新；影响已完成 Feature 时按重开规则处理（见第九节）。

默认一次只有一个 Feature 处于开发或验证中。确需并行时，事先证明状态、文件、迁移、协议和验证环境无重叠，并取得用户确认。

### 逐步确认规则

- 一次只推进当前被授权的步骤。用户只要求某一类文档时，只完成该文档及保证一致性所必需的更新，不自行进入下一阶段。
- 设计文档可以分别确认，也可以一并确认；《总体设计》和 Feature 总台账确认不等于各 Feature 的设计、计划或实现自动获批。
- 开发计划确认后，只开始第一个未完成里程碑。当前 Feature 验收并记录结论后可开始下一 Feature。
- 每个里程碑执行“核查 → 实现 → 最小有效验证 → 汇报实际结果 → 用户确认 → 进入下一里程碑”。完成实现和验证后状态先记 `🟨 待确认`，用户确认后才记 `✅ 已完成`。
- 里程碑确认是强制门禁：
  - 汇报说明实际产出、执行的验证、未执行项、偏差、遗留和风险。
  - 确认前不得开始下一里程碑的代码、依赖或协议改动；可以修复当前里程碑的缺陷、补充验证和同步文档。
  - 用户要求调整时，完成调整和重新验证后再次等待确认。
  - 版本计划已确认、结果看似无风险或下一步有明显依赖，都不能替代里程碑确认。
- 实际实现与设计假设不符时停止扩大改动，先更新设计并重新确认。

### 从哪里切入

- 路线图主版本、跨模块能力或多阶段工程建设：走完整版本主线。
- 当前版本内的小修复和实现细节：直接纳入当前里程碑。
- 开发期间收到新事项：属于当前范围的，更新功能设计或计划后继续；明显扩大目标、改变关键架构或影响交付节奏的，放入后续版本或重新确认范围。
- 用户明确要求某种产物时，从对应步骤切入。

无论从哪里切入，代码修改前都必须读取根 `AGENTS.md`“动手前必读”要求的编程规范和模块约束。

### 版本状态同步

`docs/版本管理.md` 是版本状态的共享事实源。版本状态变化时，修订台账是进入下一阶段的必要步骤。

| 触发条件 | 状态 | 同步内容 |
| --- | --- | --- |
| 已列入路线图或确定为当前目标，尚未开始设计 | `待启动` | 目标、关联输入和下一步 |
| 开始编写或实质讨论版本《功能设计》或《总体设计》 | `设计中` | 设计入口 |
| 版本设计及所需技术方案、交互指导均已确认，开始形成开发计划 | `计划中` | 已确认设计链接和开发计划入口 |
| 开发计划已确认，准备开始第一个代码里程碑 | `开发中` | 开发计划链接和当前开发重点 |
| 全部里程碑（单 Feature）或全部 Feature（多 Feature）已确认，开始版本验收 | `验证中` | 开发计划中的验收状态 |
| 用户确认验收通过，且归档完成 | `已完成` | 移入历史版本，记录完成日期、归档、结果和总结 |
| 用户明确暂停，且原因、恢复条件和文档已归档 | `已暂停` | 移入历史版本，记录暂停日期、原因和恢复条件 |

- 状态推进以用户确认和实际阶段为准；不得已开始代码开发却仍标 `设计中`，也不因文件已创建就提前推进。发现不一致时先修正再继续。
- 多 Feature 版本进入第一个 Feature 实现后整体保持 `开发中`，不因后续 Feature 进入设计而回退。因重大范围变化退回设计时同步退回 `设计中`。
- `已完成` 以用户验收通过和归档完成为条件，不以 Git commit、tag 或 push 为条件。
- 每次修订后核对路线图条目、当前版本、历史版本和文档链接一致。

### 状态只登记一处

为避免一个决定要改多份文档，各类状态的唯一登记位置如下，其余文档只链接、不复述：

| 事实 | 唯一登记位置 |
| --- | --- |
| 版本状态 | `docs/版本管理.md`。只在上表的版本状态变化或某个 Feature 完成验收时更新，不记录 Feature 内部的设计修订和里程碑进展 |
| Feature 状态与用户确认 | 多 Feature 版本的版本级开发计划（Feature 台账） |
| 里程碑状态与用户确认 | 该 Feature 的开发计划 |
| 文档自身是否已确认 | 该文档头部的状态行 |

- 《总体设计》是方向基线，不记录各 Feature 的阶段进展。
- 输入文档被版本吸收后只标明目标版本和 Feature 链接，之后不再随设计变化更新。
- 设计处于讨论或待确认期间，只修改该 Feature 自己的文档；用户确认后再一次性同步受影响的上位文档。上位文档只在其自身内容（范围、契约、验收口径）确实改变时修改。

### 版本文档命名

- 单 Feature 版本：`docs/design/vX.Y.Z-<文档类型>.md`。
- 多 Feature 版本：

  ```text
  docs/design/vX.Y.Z/
  ├── 总体设计.md                  # 必须；版本方向与跨 Feature 基线
  ├── 技术方案.md                  # 跨 Feature 架构与契约，按需
  ├── 界面交互设计指导.md          # 跨 Feature 交互基线，按需
  ├── 开发计划.md                  # Feature 清单、依赖、顺序和版本门禁
  └── features/
      └── FNN-<主题>/
          ├── 功能设计.md
          ├── 技术方案.md              # 按需
          ├── 界面交互设计指导.md      # 按需
          ├── 开发计划.md
          └── 阶段总结.md            # 按需；完成结论也可记入开发计划
  ```

- 每个 Feature 只保留一份自己的功能设计和开发计划，完成后在原位记录结论。已归档版本中的 `cycles/CNN-.../` 是历史路径，保持原貌。
- 一个版本选定单文件或目录化形式后保持一致。不以 `YYMMDD-需求主题` 作为开发和归档单元。

## 三、进度同步

`docs/开发进度.md` 只用于长任务的本地恢复，不是共享事实源。不存在时从模板初始化：

```bash
cp docs/specs/开发进度模板.md docs/开发进度.md
```

- 头部的当前版本、当前 Feature、当前里程碑、下一步和等待／阻塞每次**覆盖重写**，始终反映此刻的状态；切走前必须更新。
- 过程记录只保留恢复所需的最近内容，被取代的设计中间形态直接删除，不做流水账。
- 里程碑完成后简要记录产出、完成结论与遗留，不附验证明细。
- 共享范围、设计、里程碑和验收变化必须写入在途版本文档，不能只写本地进度。
- 版本归档时本版本的进度内容随版本移入归档目录，本地进度清理已归档内容。

## 四、需求输入

尚未确定版本归属的想法和需求存放为 `docs/inputs/YYMMDD-<简述>.md`。

- 保留用户原始语义，不提前改写为技术方案，不要求给出完整方案、验收标准或开发计划；不把未经确认的推断写成需求事实。
- 至少写清：记录日期、当前状态（待评估／已纳入版本／暂缓／不采纳）、原始想法或期望结果、必要的背景与约束；已纳入版本时标明目标版本和 Feature 链接。
- 启动或调整版本时统一评估输入池：被选中的内容由功能设计吸收并建立引用，未选中的继续保留。输入数量不决定版本边界。
- 没有独立输入文档时，功能设计注明来源为路线图、已确认决策或用户会话结论。

建议结构：

```markdown
# <主题>

- 记录日期：YYMMDD
- 状态：待评估 / 已纳入版本 / 暂缓 / 不采纳
- 来源：<用户、外部资料等>
- 目标版本：vX.Y.Z / 待定

## 原始内容

## 背景与约束
```

## 五、总体设计与功能设计

路径：

```text
docs/design/vX.Y.Z-功能设计.md
docs/design/vX.Y.Z/总体设计.md                      # 多 Feature 版本，必须
docs/design/vX.Y.Z/features/FNN-<主题>/功能设计.md  # 多 Feature 版本
```

**先核查、先收敛，再成文**：凡是依赖现有机制的行为（队列、状态、协议、存储、界面规则等），先核对实际代码并列出已核对的现状，在会话中把方向谈定，再写入文档。不凭印象假设某条现有路径存在或可复用。

**功能设计**承担类似 PRD 的职责：说明对应范围最终要形成的系统能力和关键取舍，保持能力与使用视角；类型定义、包结构、接口签名和依赖版本等放入技术方案。纯引擎或基础设施版本同样从能力视角描述能力闭环与验收标准。必须包含：

- 版本、状态、影响模块和需求来源；
- 背景、目标和明确非目标；
- 功能范围和使用路径；
- 模块职责、依赖和契约影响；
- 关键取舍及理由；
- 可逐条验证的验收点；
- 风险、兼容性和待确认项。

开放问题应在设计确认前解决。确实无法在当前阶段确定的实现细节，说明归属到技术方案或具体里程碑，不能伪装成已确认结论。

**《总体设计》**是多 Feature 版本唯一的方向文件，必须包含：

- 版本背景、最终用户结果、成功标准与明确非目标；
- 产品边界、运行拓扑、系统责任和权威状态归属；
- 不得被各 Feature 局部优化破坏的架构原则和全局不变量；
- Feature 地图、每个 Feature 的能力边界、依赖顺序和稳定交付契约；
- 跨 Feature 的协议、数据、权限、兼容、部署和失败恢复约束；
- 版本级验收标准、发布门禁和已知风险；
- 总体设计变更的判定、影响分析和重新确认规则。

《总体设计》不展开某个 Feature 的类型、接口签名或文件级实现。

章节按上述必含内容顺序组织即可，不强制固定标题。设计完成后判断是否需要技术方案和交互指导。

## 六、技术方案

适用条件（简单、低风险改动可不单独创建，在开发计划中说明原因）：

- 新建或重构 crate、应用或工程结构；
- 引入或更换核心依赖；
- 涉及协议、配置、持久化、文件格式或跨模块契约；
- 存在重要安全、兼容、性能或恢复取舍；
- 实现路径仅靠功能设计无法准确落地。

路径：

```text
docs/design/vX.Y.Z-技术方案.md
docs/design/vX.Y.Z/技术方案.md                      # 多 Feature 跨域方案
docs/design/vX.Y.Z/features/FNN-<主题>/技术方案.md  # 多 Feature 版本
```

内容通常包括：方案信息、现状核查、目标架构与依赖、分模块实现方案、配置与运行约定、测试与验证、风险兼容与排除项。

- 必须基于真实仓库和依赖核查（实际代码路径、`cargo metadata`／`cargo tree` 等），不得只凭历史认知设计。涉及数据库时遵守根 `AGENTS.md` 的数据库操作安全规则。
- 只写功能设计没有回答的“如何实现”，不重复功能设计已有的行为描述；需要时链接引用。
- 若新增 `revision`、`version`、`generation`、`sequence`、ETag 或 CAS 字段，必须按 [`Rust 架构设计规范`第 4.3 节](Rust架构设计规范.md)逐项说明要解决的真实问题、CAS／纪元隔离／顺序消费者、不匹配语义、恢复与测试；不能以“以后可能并发”作为理由。单一 owner 串行、明确终态、相同状态 no-op 或幂等 key 已足够时，必须删除冗余版本字段。

## 七、界面交互设计指导

适用条件：

- 新增窗口、页面或应用壳层；
- 大幅调整页面结构、导航或状态流转；
- 复杂表单、可视化或多步骤交互；
- 视觉和交互验收无法仅靠功能设计表达。

纯 Rust crate 改动可以跳过。界面改动少的 Feature 不单独成文，把入口、状态与反馈写成功能设计的一节即可。

路径：

```text
docs/design/vX.Y.Z-界面交互设计指导.md
docs/design/vX.Y.Z/界面交互设计指导.md                      # 多 Feature 跨域指导
docs/design/vX.Y.Z/features/FNN-<主题>/界面交互设计指导.md  # 多 Feature 版本
```

内容通常包括：设计信息、页面与入口、布局与信息结构、交互流程、视觉与组件规范、状态与异常、验收口径。应说明真实窗口或页面入口、布局关系、状态、操作反馈、异常和视觉约束，并与 `docs/modules/desktop.md` 一致；不得仅写“参考某项目”而缺少本项目落地口径。

## 八、开发计划

路径：

```text
docs/design/vX.Y.Z-开发计划.md
docs/design/vX.Y.Z/开发计划.md                      # 多 Feature 版本总台账
docs/design/vX.Y.Z/features/FNN-<主题>/开发计划.md  # 多 Feature 版本
```

开发计划排在所需的技术方案和交互指导之后，是实施台账，只回答“分几步、每步交付什么、怎么算完成、现在到哪里”，不是第二份功能设计或技术方案。它不应随设计细节的修订而改动。

**Feature（或单 Feature 版本）开发计划**由三部分组成：

1. 计划信息：状态、设计依据链接、前置条件；
2. 里程碑总览表；
3. Feature 验收与完成结论。

里程碑总览表每行必须写清：

| 列 | 内容 |
| --- | --- |
| 交付结果 | 本里程碑完成后可验证的能力，一句话 |
| 完成判定 | 对应的功能设计验收点编号，或一句明确的判据 |
| 依据 | 技术方案或交互指导的章节链接 |
| 状态与用户确认 | 状态符号，以及确认日期和用户原话 |

表外只写确实影响排期与验收、且设计文档没有承载的说明（如顺序理由、开关时机、关键判据）。交付范围明细、验证入口、测试文件清单和 Review 重点不是必填项：已在技术方案中的不复述，需要时链接。没有单独技术方案时，可以写入影响排期的最小实现约束，但保持原则性。

里程碑按能力闭环拆分，每个都能独立验证，不按文件列表或零散需求清单机械拆分。Feature 验收是固定步骤（见第九节），不作为里程碑单列。里程碑使用 `M0`、`M1` 顺序编号，状态统一为 `⬜ 未开始`、`🔄 进行中`、`🟨 待确认`、`✅ 已完成`、`⏸ 已暂停`。

**多 Feature 版本的版本级开发计划**只管理 Feature 列表、依赖顺序、状态和最终门禁：

1. 计划信息与已确认《总体设计》基线；
2. Feature 拆分原则与跨 Feature 契约；
3. Feature 台账：依赖顺序、当前状态、用户确认和文档入口；
4. 每个 Feature 的能力结果、进入条件和独立验收条件，各用一两句话并链接到 Feature 文档；
5. 跨 Feature 版本验收和最终发布条件。

版本级计划不复述 Feature 的方案和流程，不保留设计修订的过程记录；已完成的 Feature 只留验收结论和向后交付的契约。

以下内容只放在技术方案或其附件，由计划链接引用：

- 类型定义、函数签名、模块树和依赖清单；
- 协议字段、状态转换、并发流程、算法和异常处理细节；
- UI 布局尺寸、完整快捷键表、组件内部状态和事件循环设计；
- 大段伪代码、调用链和测试夹具实现。

进入版本级计划阶段时，`docs/版本管理.md` 状态为 `计划中`。多 Feature 版本开始后续 Feature 的计划时，版本整体保持 `开发中`。

## 九、代码开发

按已确认的开发计划推进。每个里程碑执行：

1. 核对版本状态为 `开发中`、工作树、当前 Feature、设计基线、里程碑授权和涉及模块。
2. 读取对应编程规范与模块约束。
3. 核查现有实现和依赖，再新增模块、trait 或公共类型。
4. 实现当前里程碑范围，同步补充必要的中文注释。
5. 执行最小有效验证。
6. 把里程碑状态改为 `🟨 待确认`，更新本地进度。
7. 汇报实际产出、验证、偏差、遗留和风险，等待用户确认。

注释属于实现质量的一部分，不能留到用户 Review 时再补：

- 跨层边界、状态所有权、并发与取消、安全权限、兼容迁移、恢复策略、反直觉平台差异和非显然算法不得只靠代码自行解释。
- 跨持久化事实与内存投影、跨 owner／Session、事务提交与事件发布的内部函数属于强制注释范围：写清前置可靠事实、职责排除、幂等／失败恢复和 gate／锁顺序，不以“不是公共 API”为由省略。
- 禁止逐行翻译代码的低价值注释。缺失必要注释、注释与实现不一致或保留已失效说明，都视为当前里程碑未完成。

禁止：

- 未确认当前里程碑就开始下一里程碑；
- 把多个未验证阶段堆到版本末尾统一测试；
- 顺手实现后续版本业务；
- 覆盖用户已有改动；
- 未经明确要求执行 `git commit` 或 `git push`。

出现以下任一情况必须停止扩大改动并重新核对：

- 现有实现与功能设计假设不符；
- 关键协议、权限、持久化或架构取舍尚未确定；
- 测试或构建暴露非预期跨模块影响；
- 涉及破坏性文件、数据库或 Git 操作；
- 工作树存在与当前版本改动重叠的未知修改。

### Feature 验收与完成

多 Feature 版本的每个 Feature 独立验收，不把完成判定推迟到版本末尾：

1. 全部里程碑已获用户确认。
2. 执行该能力必要的核心回归、跨模块集成和适用平台验证。
3. 逐项核对功能设计验收点，以及对《总体设计》相关目标、边界、不变量和契约的符合性；核对数据和协议兼容、失败恢复、安全权限、未执行项、偏差和风险。
4. 用户确认后，在该 Feature 的开发计划记录实际范围、完成日期、未完成项与接受的限制，并更新版本级台账。确有独立总结价值时生成 `阶段总结.md`。

已完成 Feature 的设计、计划和验收结论在当前版本内视为稳定事实。后续 Feature 不得静默改写；整合时发现必须修改的，重新打开受影响 Feature，记录原因、影响和重新验证结果，再次经用户确认。

## 十、版本验收

单 Feature 版本的 Feature 验收确认后，或多 Feature 版本的全部必需 Feature 完成验收后，把 `docs/版本管理.md` 状态更新为 `验证中`，执行版本级验证。

- 结合已完成的核心验证与必要的跨 Feature 检查，覆盖升级、恢复、兼容、安全、分发和适用平台风险。不为归档重复已完成的验证，也不用单个 Feature 通过代替跨 Feature 验证。
- 验收结论维护在开发计划中：是否完成、用户是否确认、未完成项及必要风险。
- 不以“应该通过”“命令已运行”代替实际结果；测试、构建、文件和接口展示状态按实际情况区分。
- 验收检查完成但尚未获得用户确认时，版本保持 `验证中`。

### 用户向更新日志与操作手册

更新日志和操作手册使用仓库中的 Markdown，面向用户单独维护，不从版本总结、开发进度或 Git 提交自动生成。仓库保留权威静态内容；平台维护方式按内容职责区分，不把手册绑定安装版本。

- **位置**：日志按软件发布版本保存为 `docs/site/changelog/vX.Y.Z.md`；手册按主题保存在 `docs/site/manual/`。两者不随版本设计归档，不为 Feature 或里程碑创建用户日志。
- **日志发布**：在安装包版本详情直接编辑、预览并保存 Markdown 正文，复用现有更新说明字段，官网与客户端读取同一发布副本。通常从仓库复制正文；平台直接修订后，把同样的修改回存仓库，避免下次发布覆盖修正。不新增另一份官网日志字段、联合内容 ZIP 或自动双向同步。
- **手册发布**：与首页内容一起通过独立固定静态目录更新，不进入安装包上传／编辑界面，不跟随软件版本切换。内容校验和预览后独立部署，不要求重建平台或重新上传安装包。
- **更新时机**：版本验收时按实际交付范围整理日志，更新受影响的操作说明；发布前核对版本、日期和正文。归档不代表发布；未发布日志留在仓库或平台草稿版本，不提前公开，不虚填发布日期。
- **日志写法**：版本、发布日期和几条用户可感知的新增、改进、修复即可；必要时补升级提醒或已知限制。空分类省略，不写 Feature 编号、里程碑、内部架构、测试数量或开发流水账。
- **手册写法**：围绕“从哪里进入、如何操作、看到什么结果”简明说明；版本差异、前置条件和常见问题按需补充，沿用一套当前手册，不为每个版本复制全文。
- **核对**：确认用户能读懂、功能已交付、链接图片有效，删除内部信息和未实现承诺。其他发布渠道复用同一用户日志；不新增单独的开发计划、验收报告或审批流程。

## 十一、版本归档

用户确认验收通过或明确暂停版本后执行归档：

1. 多 Feature 版本把 `docs/design/vX.Y.Z/` 整体移动为 `docs/versions/vX.Y.Z/`。单 Feature 版本创建 `docs/versions/vX.Y.Z/`，把在途文档移入并去掉文件名中的版本前缀（`功能设计.md`、`技术方案.md`、`界面交互设计指导.md`、`开发计划.md`，专题文档同理）。
2. 不存在的可选文档不补空文件；不复制验证数据或临时产物，不为已完成 Feature 生成第二份汇总副本。
3. 新增简洁的 `版本总结.md`，记录实际完成范围、验证结论、偏差、遗留项和后续版本入口。
4. 修正归档内部引用。
5. 在 `docs/版本管理.md` 中把该版本从路线图移入历史版本，记录完成或暂停日期、归档目录、实际结果和版本总结。
6. 把 `docs/开发进度.md` 中本版本的内容移入归档目录（命名 `开发进度.md`）；本地进度清理已归档内容，登记下一个目标版本，尚未启动设计时状态为 `待启动`。
7. 删除该版本及各 Feature 的历史测试环境与测试数据，包括 `.runtime-test/` 下对应的 Runtime Home、测试数据库、附件、浏览器测试数据、日志、迁移测试备份和临时测试产物。已核实属于停用隔离测试环境的内容直接删除，无需备份；不以“以后可能复用”为由保留，也不转移到 `.local/` 等目录或压缩留档。清理前核对版本归属和进程占用，不能仅凭目录名判断；正式运行数据、共享用户数据、其他仍在使用的测试环境和最终交付文件不在清理范围，来源不明的数据按数据库安全规则处理。

归档使用移动而不是复制，`docs/design/` 与归档目录不同时保留同一版本副本。归档目录视为只读；后续纠错保留变更说明，不把新版本工作追加到旧归档。暂停版本使用同样流程，并记录暂停原因和恢复条件。

## 十二、提交准备

版本归档与提交准备是两个独立步骤。Feature 验收不触发 Git 操作，也不以提交作为完成条件；版本开发中可按用户授权多次提交，归档不要求与某一个提交对应。

未经用户明确要求，不执行 `git add`、`git commit` 或 `git push`。用户明确要求提交准备时：检查改动、暂存指定文件、为每个获授权范围草拟 commit message，并报告暂存范围和未暂存改动。

commit message 使用 `<type>: <message>`，`type` 可取 `feat`、`fix`、`docs`、`style`、`refactor`、`perf`、`test`、`chore`。

## 十三、验证矩阵

按实际改动选择最小有效验证：

| 改动范围 | 最低验证 |
| --- | --- |
| 仅文档 | 相对链接、路径、命令和文档一致性检查 |
| Rust 格式或小型实现 | `cargo fmt --all --check` + 相关 crate 测试 |
| Rust 公共 trait、协议、并发或 Runtime | `cargo clippy --workspace --all-targets --all-features -- -D warnings` + `cargo test --workspace` |
| 前端 TypeScript／CSS | `cd apps/desktop && npm run build` |
| Tauri command、配置、capability | 前端构建 + `cargo test --workspace` + `npm run tauri -- build --no-bundle` |
| 窗口、托盘、快捷键、macOS 权限 | 构建 + 实机启动和交互验证 |
| Feature 完成 | 验收点、里程碑完成结论、未完成项和版本台账一致 |
| 版本阶段转换 | `docs/版本管理.md` 的状态、路线图／历史版本位置和文档链接与实际阶段一致 |

无法执行且影响完成判定的验证，只简要记录阻塞原因及影响，不创建额外验证材料。

## 十四、长期决策与范围变化

以下内容同步更新 `docs/重要决策与变更记录.md`：

- 架构、模块边界和目录结构；
- 核心技术栈、依赖方向和运行方式；
- 跨模块协议、权限、安全、持久化和部署策略；
