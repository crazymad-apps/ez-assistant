# 开发流程规范

本规范定义 `ez-assistant` 的版本设计、开发计划、实现验证、归档与提交准备流程。项目当前处于早期密集研发阶段，开发活动以**目标版本**为组织主线，不以单个需求为独立流程单元。

核心原则：一个版本聚合一组方向一致的改动，统一完成设计、计划、实现验证和归档；结论必须可验证。

## 一、文档目录

- `docs/inputs/`：临时想法、需求和原始输入的长期记录池；随时可写，但不是独立开发流程的起点。
- `docs/design/`：当前版本的在途设计、技术方案、交互设计和开发计划。
- `docs/specs/`：全局开发规范与模板。
- `docs/modules/`：应用和 crate 的长期职责、依赖与验证约束。
- `docs/resources/`：外部资料、截图、协议和样例。
- `docs/versions/`：已完成或暂停版本的只读归档。
- `docs/开发进度.md`：本地在途状态，已忽略，不提交。
- `docs/版本管理.md`：当前版本和历史版本的共享台账。
- `docs/重要决策与变更记录.md`：跨版本长期生效的架构与协作决策。

## 二、版本主流程

每个正式开发版本遵循同一主链：

```text
确定目标版本与范围
→ 版本设计
→ 版本开发计划
→ 分阶段实现与验证
→ 版本归档
```

- 版本是目标、范围、计划、验收和归档的唯一主键。
- 单个需求点、缺陷或重构先判断是否属于当前版本，不为它机械创建一套独立流程文档。
- 同一版本中的相关改动应合并进版本设计和版本计划，避免产生大量碎片化主题文档。
- 用户只要求设计、计划或归档时，只完成对应阶段，不自行跨入下一阶段。
- 已确认版本计划只授权开始第一个未完成里程碑，不授权连续跨越里程碑。每个里程碑完成实现和验证后必须停止并等待用户明确确认，确认后才能进入下一里程碑。

### 2.1 输入记录与版本归属

尚未确定版本归属的想法和需求记录在：

```text
docs/inputs/YYMMDD-<简述>.md
```

输入文档保持轻量，至少写清：

- 记录日期。
- 当前状态：待评估 / 已纳入版本 / 暂缓 / 不采纳。
- 原始想法或期望结果。
- 必要的背景、约束和补充材料。
- 已纳入版本时标明目标版本号。

输入文档用于保留原始意图，不要求提前给出完整方案、验收标准或开发计划。启动或调整版本时统一评估输入池：被选中的内容由版本设计吸收并建立引用，未选中的内容继续保留。输入数量不决定版本边界，版本目标决定纳入范围。

### 2.2 确定目标版本

启动版本前明确：

- 版本号和状态。
- 本版本目标与成功标准。
- 纳入范围和明确不做的内容。
- 主要模块和能力影响。
- 预计里程碑及风险。

版本号默认遵循语义化版本。`0.x` 阶段以能够独立验收的能力里程碑推进，不要求为每个细小变化递增版本。

### 2.3 版本设计

版本设计描述本版本最终要形成的系统能力和关键取舍。跨模块、架构、协议、权限、持久化、后台调度或复杂 UI 变化必须写清技术方案；简单版本可合并在一份版本设计中。

设计至少包含：

- 版本目标和非目标。
- 当前实现核查结果。
- 功能范围和使用路径。
- 模块职责、依赖和契约影响。
- 关键技术选择及理由。
- 可逐条验证的验收点。
- 风险、兼容性和待确认项。

### 2.4 版本开发计划

开发计划把版本设计拆成可独立验收的里程碑。每个步骤应写清：

- 目标和影响范围。
- 前置条件与依赖。
- 具体产出。
- 最小有效验证。
- 完成判定。

计划围绕版本能力闭环组织，不按文件列表或零散需求清单机械拆分。

### 2.5 分阶段实现与验证

每个里程碑执行：

```text
核查 → 实现 → 最小有效验证 → 汇报实际结果 → 用户确认 → 进入下一里程碑
```

里程碑确认是强制门禁：

- 汇报必须说明实际产出、执行的验证、未执行项、偏差、遗留和风险。
- 用户明确确认前，不得开始下一里程碑的代码、依赖或协议改动。
- 确认前可以修复当前里程碑的缺陷、补充验证和同步文档，但不能扩大到下一里程碑范围。
- 用户要求调整当前里程碑时，完成调整和重新验证后再次等待确认。
- 版本计划整体已确认、当前结果看似无风险或下一步有明显依赖，都不能替代里程碑确认。

版本开发期间收到新事项时：

1. 先判断是否服务于当前版本目标。
2. 属于当前范围的，更新版本设计或计划后继续。
3. 明显扩大目标、改变关键架构或影响交付节奏的，放入后续版本或重新确认当前版本范围。
4. 小型修复和实现细节直接纳入当前里程碑，不单独启动需求流程。

出现以下任一情况必须停止扩大改动并重新核对：

- 现有实现与版本设计假设不符。
- 关键协议、权限、持久化或架构取舍尚未确定。
- 测试或构建暴露非预期跨模块影响。
- 涉及破坏性文件、数据库或 Git 操作。
- 工作树存在与当前版本改动重叠的未知修改。

## 三、版本文档命名

在途文档统一使用目标版本号：

```text
docs/design/v0.1.0-版本设计.md
docs/design/v0.1.0-技术方案.md          # 复杂技术版本可选
docs/design/v0.1.0-界面交互设计.md      # 新增/大改界面时可选
docs/design/v0.1.0-开发计划.md
```

同一版本只有一份主版本设计和一份主开发计划。确需拆分专题时，专题文档仍以版本号为前缀，并在主文档中建立索引。

不要以 `YYMMDD-需求主题` 作为主要开发和归档单元。日期只用于记录时间，不代替版本号。

## 四、验证矩阵

| 改动范围 | 最低验证 |
| --- | --- |
| Rust 格式或小型实现 | `cargo fmt --all --check` + 相关 crate 测试 |
| Rust 公共 trait、协议、并发或 Runtime | `cargo clippy --workspace --all-targets --all-features -- -D warnings` + `cargo test --workspace` |
| 前端 TypeScript/CSS | `cd apps/desktop && npm run build` |
| Tauri command、配置、capability | 前端构建 + `cargo test --workspace` + `npm run tauri -- build --no-bundle` |
| 窗口、托盘、快捷键、macOS 权限 | 构建 + 实机启动和交互验证 |
| 仅文档 | 链接、路径、命令和文档一致性检查 |

版本最终验收使用版本计划中所有里程碑验证结果的合集。无法执行的验证必须说明原因，不得以“应该可用”替代结论。

## 五、进度与范围管理

- `docs/版本管理.md` 记录当前目标版本、状态和历史版本索引，不展开实现细节。
- `docs/inputs/` 持续保留原始想法和需求状态；版本设计引用输入，不用技术结论覆盖原始记录。
- 长任务使用 `docs/开发进度.md` 恢复本地上下文，内容按当前版本和里程碑组织。
- 共享范围、里程碑和验收变化更新对应版本设计或开发计划。
- 跨版本长期生效的架构、模块边界、协议、权限或流程变化更新 `docs/重要决策与变更记录.md`。
- 完成一个里程碑后记录实际产出和验证结论；不要求记录每次代码编辑。
- 每个里程碑的用户确认结果同步到开发计划；本地进度在确认前保持“等待确认”。

## 六、版本归档

版本完成或明确暂停时归档：

1. 创建 `docs/versions/v<版本号>/`。
2. 将该版本在途文档从 `docs/design/` 移入归档目录。
3. 统一命名为 `版本设计.md`、`技术方案.md`、`界面交互设计.md`、`开发计划.md`；不存在的可选文档不补空文件。
4. 新增简洁的 `版本总结.md`，记录实际完成范围、验证结论、偏差和遗留项。
5. 修正归档内部引用并更新 `docs/版本管理.md`。
6. 归档目录视为只读；后续纠错保留变更说明，不把新版本工作追加到旧归档。

暂停版本也按相同方式归档，并在版本总结中说明暂停原因和恢复条件。

## 七、提交准备

提交准备与版本归档分开。版本开发中可以存在多个提交，归档不要求与 Git 提交一一对应。

未经用户明确要求，不执行 `git add`、`git commit` 或 `git push`。commit message 使用 `<type>: <message>`，type 取 `feat`、`fix`、`docs`、`style`、`refactor`、`perf`、`test`、`chore`。
