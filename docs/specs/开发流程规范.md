# 开发流程规范

本规范定义 `ez-assistant` 的需求输入、功能设计、开发、验证、归档和提交准备流程。处理需求、设计文档、版本台账、代码开发或版本归档时必须遵守本文件。

核心原则：项目以对外发布版本为主线，不为内部开发阶段机械提升版本号。简单版本默认使用一个完整实现循环；复杂版本按需要在同一版本号下拆成多个高内聚、低耦合的实现循环，逐个完成设计、实现、验证、提交和归档，最后统一完成版本验收与发布。每一步、每个开发里程碑和每个实现循环完成后都要暂停，等待用户确认再继续；版本阶段变化时同步修订 `docs/版本管理.md`；结论必须可验证。

### 全局最小新增原则

项目中的需求分析、功能设计、技术方案、代码实现、数据设计、协议设计、UI 交互和测试方案都必须
优先复用、调整或组合现有事实与机制，不能把“新增一层”当作默认解法。

- 新增实体、状态、字段、DTO、enum variant、表、文件、缓存、队列、服务、Adapter、trait、模块、
  帮助类型或并行执行路径前，必须先搜索现有实现，并明确说明现有能力为什么不能直接承载需求。
- 同一业务事实已经存在时，展示、传输或命名差异不构成新实体。优先在现有聚合、投影、枚举或
  装配流程中内联表达；不得为同一事实创建包装实体、第二份状态或另一套生命周期。
- 只有新增对象具有独立身份、独立所有权、独立生命周期、不同事务边界或至少一个已存在的稳定
  替换/复用边界时，才允许引入新的实体或抽象；“以后可能需要”“看起来更完整”“便于扩展”
  不能单独作为理由。
- 若一个局部需求开始连带引入新的持久化、分页、恢复、迁移、全局计数或跨层状态同步，必须立即
  停止扩大实现，重新核对是否误把简单展示或适配问题升级成了新的业务机制。
- 兼容层、旧字段别名、双读双写、迁移分支、旧命令转发和旧格式回退同样属于新增机制，不能以
  “更稳妥”为由默认加入：
  - 同一目标版本尚未正式发布时，版本内临时命名、字段、协议或存储形态发生调整，默认直接统一
    到最终设计；不得为开发过程中的中间形态保留兼容代码、别名或迁移逻辑。
  - 跨已发布版本也不能默认保留兼容。必须先评估受影响的协议、配置、持久化数据、文件格式、
    客户端和回滚路径，并在实施兼容、迁移、拒绝旧格式或破坏性升级前取得用户确认。
  - 只有存在正式用户数据、已发布客户端、外部契约或已确认的滚动升级场景时，才把兼容机制列为
    候选方案；本地开发缓存和尚未发布的临时构建不能单独构成长期兼容理由。
- 验证同样遵循最小有效范围：先执行直接覆盖改动的编译、静态检查或单项测试；只有失败证据、
  高风险边界或里程碑验收明确要求时才扩大测试，不得用大量无关验证替代设计正确性。
- 验证是开发动作，不是文档交付物。流程不要求单独创建验证记录、测试报告或验证数据归档；
  不将命令输出、测试数量、数据库快照、逐表计数、临时制品和日志明细写入设计、计划或进度。
  只在现有开发计划/进度中简要维护完成结论、用户确认、未完成项与必要风险；阶段总结沿用同一口径。
  详细验证情况按需在会话中说明。数据库操作仍必须遵守安全核对、备份与实际结果汇报要求，
  但不因此新增流程文档或要求把备份/验证数据纳入版本归档。
- 设计与 Review 必须把“删除本次新增机制后，现有事实是否已经足够”作为必答问题；答案为是时，
  应删除新增机制，而不是继续为其补充合理性。

## 一、文件与目录职责

- `docs/inputs/`：尚未归入版本的原始想法、需求和外部输入的长期记录池；随时可写，但不是独立开发流程的起点。
- `docs/design/`：规划、设计、开发或验证中的版本文档。
- `docs/specs/`：跨版本长期有效的开发规范与模板。
- `docs/modules/`：各应用和 crate 的长期职责、依赖与验证约束。
- `docs/resources/`：外部资料、截图、协议和样例。
- `docs/versions/`：已完成或暂停版本的只读归档。
- `docs/版本管理.md`：版本路线图、当前版本和历史版本的共享台账。
- `docs/重要决策与变更记录.md`：跨版本长期生效的架构与协作决策。
- `docs/specs/开发进度模板.md`：本地开发进度初始化模板。
- `docs/开发进度.md`：本地在途状态与开发过程记录，已被 Git 忽略，不提交；版本归档时本版本内容随版本移入归档目录一并提交。

## 二、版本主线

### 简单版本与复杂版本

版本启动时先判断复杂度，再选择实现循环数量，并在版本设计和开发计划中记录选择依据。复杂度与循环数量不是一一对应关系：简单版本默认一个循环；复杂版本只有在存在高内聚、低耦合且可独立验收的边界时，才拆成多个循环。

| 情况 | 判断依据 | 实现方式 | 设计与验收 |
| --- | --- | --- | --- |
| 简单版本 | 目标集中、边界清楚，能够在一次设计和验收中完整收口 | 一个实现循环，可包含多个里程碑 | 一份版本功能设计承担总体方向；循环验收与版本验收合并，统一提交与归档 |
| 复杂版本 | 多个能力或工程相互关联，一次展开全部细节会增加设计、集成与验证难度 | 评估后选择一个或多个实现循环 | 单循环沿用上述流程；多循环先确认总体设计，各循环独立验收、提交和阶段归档，最后进行版本整体验收 |

实现循环是包含设计、计划、实现、验证、提交和归档的完整工作单元。一个循环可以覆盖一个 Feature，也可以包含共同构成能力闭环的多个相关需求；不要求一个 Feature 对应一个循环，也不能仅因涉及多个工程就强制拆分。

所有版本都需要统一的方向依据。单循环版本由《功能设计》承担总体设计职责，不重复创建《总体设计》或循环级文档；多循环版本使用独立的《总体设计》，各循环再分别细化。

单循环中的循环验收、提交和归档与版本收尾共用完成结论，不再重复设置阶段验收、阶段总结或阶段归档。提交仍须取得用户明确授权。

### 单循环流程

单循环版本遵循：

```text
确定目标版本（待启动）
→ 功能设计（进入设计中）
→ 技术方案（按需，保持设计中）
→ 界面交互设计指导（按需，保持设计中）
→ 开发计划（计划中）
→ 分里程碑代码开发（开发中）
→ 版本验收（验证中）
→ 版本归档（已完成 / 已暂停）
→ 提交准备（用户明确要求时）
```

### 多循环流程

复杂版本需要分批推进时，在同一发布版本内使用多个实现循环：

```text
确定目标版本并确认《总体设计》
→ 实现循环 C01（设计 → 方案 → 计划 → 实现 → 实现循环验收 → 提交 → 阶段归档）
→ 实现循环 C02（设计 → 方案 → 计划 → 实现 → 实现循环验收 → 提交 → 阶段归档）
→ ……
→ 跨循环版本验收
→ 版本归档与发布准备
```

实现循环不是软件版本，不产生新的 SemVer、兼容下限或发布标签。

### 确定目标版本

启动版本前明确：

- 版本号和状态。
- 本版本目标与成功标准。
- 纳入范围和明确不做的内容。
- 主要模块和能力影响。
- 预计里程碑及风险。

版本号默认遵循语义化版本。`0.x` 阶段以能够独立验收的能力里程碑推进，不要求为每个细小变化递增版本。

版本是对外交付目标、总范围、最终验收和发布归档的唯一主键。单个需求点、缺陷或重构先判断是否属于当前版本，不为普通小事项机械创建实现循环。只有当某组能力需要独立设计、实现、验证和阶段提交，且可以形成清晰责任与依赖边界时，才在同一版本下建立实现循环。

### 发布版本、实现循环与里程碑

三层单元职责如下：

| 层级 | 标识 | 承担的事实 | 不承担的事实 |
| --- | --- | --- | --- |
| 发布版本 | `vX.Y.Z` | 最终产品能力、总范围、兼容、发布产物和整体验收 | 内部阶段编号 |
| 实现循环 | `C01`、`C02` | 一个高内聚能力的完整开发循环和完成结论 | SemVer、发布标签和对外完整版承诺 |
| 实现里程碑 | `M0`、`M1` | 某个实现循环内部的实现、集成和定向验证步骤 | 实现循环验收或版本验收 |

单循环版本的唯一实现循环无需额外编号，直接沿用一份版本设计和开发计划；
只有多循环版本需要使用 `C01`、`C02` 等编号和循环台账。

### 复杂版本的分批原则

选择多循环时，按业务能力、状态所有权和稳定契约分批，不按仓库、语言、前端、后端或文件列表机械切分。每个拆出的实现循环必须：

- 形成一个可独立说明、实现和验证的能力结果；
- 明确所属的权威状态、数据和失败恢复边界；
- 明确依赖哪些已完成实现循环，以及对后续实现循环提供的稳定契约；
- 包含自己的设计、计划、里程碑、验证、偏差、风险和阶段总结；
- 在实现和验证完整收口后才进入提交与阶段归档，不把未验证代码留给版本末尾统一补测；
- 即使暂时不对用户开放，也不能以空实现、无验证脚手架或依赖后续重写的过渡结构冒充完成。

多循环版本启动时必须先编制并确认唯一的版本级《总体设计》。它是整个发布版本的方向基线和各实现循环的上位依据，至少固定最终用户结果、总范围与非目标、系统边界、核心架构原则、权威状态和数据归属、实现循环列表及依赖顺序、跨循环契约、兼容与发布约束、最终验收门禁。

各实现循环的内部细节不必在版本启动时一次写完，而是在进入该实现循环时独立完成设计与确认。但实现循环设计必须明确引用《总体设计》的对应目标、边界和契约，不得自行改变版本方向。

《总体设计》在首个实现循环进入实现前必须获得用户确认。后续确需变更时，必须先记录变更原因、影响的实现循环和重新验证范围，获得用户确认后才能更新；如果影响已归档实现循环，必须按重开规则处理。

默认一次只有一个实现循环处于开发或验证中。确需并行时，必须事先证明状态、文件、迁移、协议和验证环境无重叠，并取得用户确认。

### 逐步确认规则

- 一次只推进当前被授权的步骤。
- 功能设计、技术方案、交互指导和开发计划分别形成可核验产物。
- 用户只要求某一类文档时，只完成该文档及保证其一致性所必需的索引或规范更新，不自行进入下一阶段。
- 开发计划得到确认后，只开始第一个未完成里程碑。
- 多循环版本的《总体设计》和实现循环总台账确认，不等于各实现循环设计、计划或实现自动
  获批；每个实现循环独立通过相应门禁。
- 当前实现循环未完成验收、获授权提交和阶段归档前，不开始下一实现循环；用户明确批准
  并行实现循环时例外。
- 每个里程碑执行"核查 → 实现 → 最小有效验证 → 汇报实际结果 → 用户确认 → 进入下一里程碑"。
- 里程碑完成实现和验证后状态先改为 `🟨 待确认`；用户确认后才改为 `✅ 已完成`。
- 里程碑确认是强制门禁：
  - 汇报必须说明实际产出、执行的验证、未执行项、偏差、遗留和风险。
  - 用户明确确认前，不得开始下一里程碑的代码、依赖或协议改动。
  - 确认前可以修复当前里程碑的缺陷、补充验证和同步文档，但不能扩大到下一里程碑范围。
  - 用户要求调整当前里程碑时，完成调整和重新验证后再次等待确认。
  - 版本计划整体已确认、当前结果看似无风险或下一步有明显依赖，都不能替代里程碑确认。
- 实际实现与设计假设不符时停止扩大改动，先更新设计并重新确认。

### 从哪里切入

- 路线图主版本、跨模块能力或多阶段工程建设：走完整版本主线。
- 当前版本内的小修复和实现细节：直接纳入当前里程碑，不单独启动需求流程。
- 版本开发期间收到新事项时，先判断是否服务于当前版本目标：属于当前范围的，更新功能设计或计划后继续；明显扩大目标、改变关键架构或影响交付节奏的，放入后续版本或重新确认当前版本范围。
- 用户明确要求某种产物时，从对应步骤切入。

无论从哪里切入，代码修改前都必须读取根 `AGENTS.md`"动手前必读"要求的对应编程规范和模块约束。

### 版本状态同步

`docs/版本管理.md` 是版本状态的共享事实源。版本阶段发生变化时，状态修订是进入下一阶段的必要步骤，不能只更新版本文档或本地开发进度。

| 触发条件 | `docs/版本管理.md` 状态 | 必须同步的内容 |
| --- | --- | --- |
| 版本已列入路线图或被确定为当前目标，但尚未开始设计 | `待启动` | 当前目标版本、目标、关联输入和下一步 |
| 开始编写或实质讨论单循环版本功能设计或多循环版本《总体设计》 | `设计中` | 当前版本状态和设计入口 |
| 版本设计及所需技术方案、交互指导均已确认，开始形成开发计划 | `计划中` | 当前版本状态、已确认设计链接和开发计划入口 |
| 开发计划已确认，准备开始第一个代码里程碑 | `开发中` | 当前版本状态、开发计划链接和当前开发重点 |
| 单循环版本的全部里程碑已确认，或多循环版本的全部实现循环已阶段归档，开始版本验收 | `验证中` | 当前版本状态和开发计划中的验收状态 |
| 用户确认验收通过，且文档移动、版本总结和链接修订全部完成 | `已完成` | 从路线图详细登记移入历史版本，记录完成日期、归档、结果、验证结论和总结 |
| 用户明确暂停版本，且暂停原因、恢复条件和现有文档已经归档 | `已暂停` | 从路线图详细登记移入历史版本，记录暂停日期、原因、恢复条件和归档 |

同步规则：

- 状态必须在进入对应阶段时更新；不得已经开始代码开发却仍标记为 `设计中` 或 `计划中`。
- 状态推进以用户确认和实际阶段为准，不能仅因文件已经创建就提前推进。
- 技术方案和界面交互设计指导仍属于 `设计中`，不额外增加版本状态。
- 多循环版本进入第一个实现循环实现后，版本整体保持 `开发中`；后续实现循环可以各自
  处于设计、计划、开发、验证、待提交或已归档，不因进入下一实现循环设计就将版本
  整体状态退回 `设计中`。
- 等待功能设计、开发计划、里程碑或验收确认时，在对应文档和 `docs/开发进度.md` 中记录"待确认"，不为此新增版本状态。
- 当前版本因重大范围变化退回设计时，状态同步退回 `设计中`；恢复暂停版本时，根据实际续作阶段设置为 `设计中`、`计划中`、`开发中` 或 `验证中`。
- `已完成` 以用户验收通过和版本归档完成为条件，不以 Git commit、tag 或 push 为条件。
- 每次修订状态后都要核对路线图条目、"当前版本"、"历史版本"、在途文档链接和归档链接是否一致。
- 如果版本管理状态与实际阶段不一致，必须先修正状态，再继续下一阶段。

### 版本文档命名

- 单循环版本的在途文档继续使用目标版本号前缀：
  `docs/design/vX.Y.Z-<文档类型>.md`。
- 使用多个实现循环的复杂版本改用目录化结构：

  ```text
  docs/design/vX.Y.Z/
  ├── 总体设计.md                  # 必须；版本方向与跨循环基线
  ├── 技术方案.md                  # 跨循环架构与契约，按需
  ├── 界面交互设计指导.md          # 跨循环交互基线，按需
  ├── 开发计划.md                  # 实现循环清单、依赖、顺序和版本门禁
  └── cycles/
      ├── C01-<循环短名>/
      │   ├── 功能设计.md
      │   ├── 技术方案.md              # 按需
      │   ├── 界面交互设计指导.md      # 按需
      │   ├── 开发计划.md
      │   └── 阶段总结.md
      └── C02-<循环短名>/
  ```

- 每个实现循环只保留一份自己的功能设计和开发计划。《总体设计》保留总目标、
  系统边界、跨循环约束、依赖和最终验收，不复制各实现循环内部实现细节。
- 一个版本选定单文件或目录化形式后，本版本内保持一致，不在两套结构间重复维护。
- 不要以 `YYMMDD-需求主题` 作为主要开发和归档单元；日期只用于输入文档记录时间，不代替版本号。

## 三、进度同步

`docs/开发进度.md` 用于长任务本地恢复，不作为共享事实源。不存在时从模板初始化：

```bash
cp docs/specs/开发进度模板.md docs/开发进度.md
```

推进规则：

- 确认当前版本后，填写版本、分支、版本复杂度、开发模式及选择依据；多循环版本同时填写当前实现循环、
  实现循环阶段和当前里程碑。
- 开始里程碑时标记 `🔄 进行中`。
- 完成实现和验证后简要记录产出、完成结论与遗留，标记 `🟨 待确认`，不附验证明细。
- 用户确认后标记 `✅ 已完成`，再填写下一里程碑续作点；每个里程碑的用户确认结果同步到开发计划，本地进度在确认前保持"等待确认"。
- 切走前写清"当前实现循环、下一步、续作点、等待/阻塞"。
- 共享范围、设计、里程碑和验收变化必须更新在途版本文档，不能只写本地进度。
- 版本阶段发生变化时，同时更新 `docs/版本管理.md`；`docs/开发进度.md` 不能替代版本台账。
- 实现循环完成阶段归档后，将完成结论收敛到该实现循环的开发计划和阶段总结，
  本地进度只保留后续续作所需的摘要。
- 版本归档时本版本全部进度内容随版本移入归档目录，归档后清理本地进度中的已归档内容。

## 四、需求输入

尚未确定版本归属的想法和需求存放为：

```text
docs/inputs/YYMMDD-<简述>.md
```

要求：

- 保留用户原始语义，不提前改写为技术方案；输入文档用于保留原始意图，不要求提前给出完整方案、验收标准或开发计划。
- 至少写清：记录日期；当前状态（待评估 / 已纳入版本 / 暂缓 / 不采纳）；原始想法或期望结果；必要的背景、约束和补充材料；已纳入版本时标明目标版本号。
- 不把未经确认的推断写成需求事实。
- 启动或调整版本时统一评估输入池：被选中的内容由功能设计吸收并建立引用，未选中的内容继续保留，不因版本启动而自动关闭或归档。
- 没有独立输入文档时，功能设计注明来源为路线图、已确认决策或用户会话结论。
- 输入数量不决定版本边界，版本目标决定纳入范围。

建议结构：

```markdown
# <主题>

- 记录日期：YYMMDD
- 状态：待评估 / 已纳入版本 / 暂缓 / 不采纳
- 来源：<用户、外部资料等>
- 目标版本：vX.Y.Z / 待定

## 原始内容

<保留原意的想法或期望结果>

## 背景与约束

<必要的背景、约束和补充材料>
```

## 五、总体设计与功能设计

路径：

```text
docs/design/vX.Y.Z-功能设计.md
docs/design/vX.Y.Z/总体设计.md                                  # 多循环版本，必须
docs/design/vX.Y.Z/cycles/CNN-<循环短名>/功能设计.md  # 多循环版本
```

开始编写或实质讨论单循环版本的功能设计，或多循环版本的《总体设计》时，将 `docs/版本管理.md` 中当前版本状态更新为 `设计中`，并在创建设计文件后登记入口；状态和入口必须在同一步中保持一致。仅列入路线图、尚未开始设计的版本保持 `待启动`。版本已进入 `开发中` 后开始后续实现循环设计时，只更新实现循环状态和版本级开发台账，不回退版本整体状态。

单循环版本和实现循环功能设计承担类似 PRD 的职责：说明对应范围最终要形成的系统能力和关键取舍，保持能力与使用视角。类型定义、包结构、接口签名和依赖版本等实现细节放入技术方案。

多循环版本的《总体设计》是唯一的版本方向文件，必须包含：

- 版本背景、最终用户结果、成功标准与明确非目标；
- 产品边界、运行拓扑、系统责任和权威状态归属；
- 不得被各实现循环局部优化破坏的架构原则和全局不变量；
- 实现循环地图、每个实现循环的能力边界、依赖顺序和稳定交付契约；
- 跨循环的协议、数据、权限、兼容、部署和失败恢复约束；
- 版本级验收标准、发布门禁和已知风险；
- 总体设计变更的判定、影响分析和重新确认规则。

《总体设计》不展开某个实现循环的类型、接口签名或文件级实现；这些细节由实现循环自己的功能设计和技术方案承担。
建议结构：

```markdown
# vX.Y.Z 总体设计：<版本主题>

## 一、设计信息与需求依据
## 二、版本背景、最终目标与成功标准
## 三、总范围与明确非目标
## 四、产品边界、运行拓扑与权威状态
## 五、架构原则与全局不变量
## 六、实现循环地图、边界与依赖
## 七、跨循环契约与兼容约束
## 八、版本级验收与发布门禁
## 九、风险、待确认项与总体设计变更规则
```

不涉及具体业务功能的版本（如纯引擎或基础设施版本），功能设计仍从能力视角描述版本要形成的能力闭环与验收标准，文档名称和结构保持一致。

单循环版本和实现循环功能设计必须包含：

- 版本、状态、影响模块和需求来源；
- 背景、目标和明确非目标；
- 功能范围和使用路径；
- 模块职责、依赖和契约影响；
- 关键取舍及理由；
- 可逐条验证的验收点；
- 风险、兼容性和待确认项。

开放问题应在设计确认前解决。确实无法在当前阶段确定的实现细节，必须说明归属到技术方案或具体里程碑，不能伪装成已确认结论。

功能设计建议结构：

```markdown
# vX.Y.Z 功能设计：<版本主题>

## 一、设计信息

- 版本：
- 状态：
- 影响模块：
- 需求来源：

## 二、背景与目标

## 三、非目标

## 四、功能范围与使用路径

## 五、模块边界与契约影响

## 六、关键取舍

## 七、验收标准

## 八、风险、兼容性与待确认项
```

对应设计完成后必须判断是否需要技术方案和界面交互设计指导。单循环版本的功能设计及所需设计文档全部获得确认、准备编写开发计划时，将 `docs/版本管理.md` 状态更新为 `计划中`。多循环版本在《总体设计》及所需版本级设计文档确认后进入 `计划中`，编制实现循环总台账；各实现循环内部仍按相同顺序独立确认。

## 六、技术方案

适用条件：

- 新建或重构 crate、应用或工程结构；
- 引入或更换核心依赖；
- 涉及协议、配置、持久化、文件格式或跨模块契约；
- 存在重要安全、兼容、性能或恢复取舍；
- 实现路径仅靠功能设计无法准确落地。

路径：

```text
docs/design/vX.Y.Z-技术方案.md
docs/design/vX.Y.Z/技术方案.md                                  # 多循环跨域方案
docs/design/vX.Y.Z/cycles/CNN-<循环短名>/技术方案.md  # 多循环版本
```

简单、低风险改动可不单独创建技术方案，但必须在开发计划中说明不需要的原因。

建议结构：

```markdown
# vX.Y.Z 技术方案：<版本主题>

## 一、方案信息

- 版本：
- 状态：
- 影响模块：
- 关联功能设计：

## 二、现状核查

## 三、目标架构与依赖

## 四、分模块实现方案

## 五、配置与运行约定

## 六、测试与验证

## 七、风险、兼容与排除项
```

技术方案必须基于真实仓库和依赖核查（实际代码路径、`cargo metadata`/`cargo tree` 等），不得只凭历史认知设计。涉及数据库时必须遵守根 `AGENTS.md` 的数据库操作安全规则。

技术方案若新增 `revision`、`version`、`generation`、`sequence`、ETag 或 CAS 字段，必须按
[`Rust 架构设计规范`第 4.3 节](Rust架构设计规范.md)逐项说明要解决的真实问题、
CAS/纪元隔离/顺序消费者、不匹配语义、恢复与测试；不能以“以后可能并发”作为理由。单一 owner
串行、明确终态、相同状态 no-op 或幂等 key 已足够时，必须删除冗余版本字段。

## 八、开发计划

路径：

```text
docs/design/vX.Y.Z-开发计划.md
docs/design/vX.Y.Z/开发计划.md                                  # 多循环版本总台账
docs/design/vX.Y.Z/cycles/CNN-<循环短名>/开发计划.md  # 多循环版本
```

进入版本级计划阶段时，`docs/版本管理.md` 中当前版本状态必须为 `计划中`，并登记已经确认的设计文档和开发计划入口。多循环版本开始后续循环的计划时，版本整体保持 `开发中`，只更新当前循环的阶段。

开发计划排在已需要的技术方案和交互指导之后。它是实施台账，用于回答“分几步、
每步交付什么、如何确认、现在到哪里”，而不是第二份功能设计或技术方案。单循环版本的开发计划直接围绕版本能力闭环拆分里程碑；多循环版本的版本级开发计划只管理实现循环列表、依赖顺序、状态和最终门禁，每个实现循环的开发计划再拆分该实现循环内部里程碑。两层计划都不按文件列表或零散需求清单机械拆分。

单循环版本和实现循环内部开发计划的统一结构：

1. 计划信息与设计依据；
2. 台账原则；
3. 里程碑总览；
4. 各里程碑的目标、交付范围、验证入口、完成判定和 Review 重点；
5. 对应版本或实现循环的完成条件。

多循环版本的版本级开发计划使用：

1. 计划信息与已确认《总体设计》基线；
2. 实现循环拆分原则与跨循环契约；
3. 实现循环列表、依赖顺序、当前状态和文档入口；
4. 每个实现循环的能力结果、进入条件和阶段归档条件；
5. 跨循环版本验收和最终发布条件。

开发计划不得重复展开已经存在于功能设计、技术方案或交互设计中的内容。以下内容原则上只放在
技术方案或其附件，并由计划链接引用：

- 类型定义、函数签名、模块树和依赖清单；
- 协议字段、状态转换、并发流程、算法和异常处理细节；
- UI 布局尺寸、完整快捷键表、组件内部状态和事件循环设计；
- 大段伪代码、调用链和测试夹具实现。

如果没有单独技术方案，确实影响排期与验收的最小实现约束可以写入计划，但仍应保持原则性，不把
开发计划扩展成混合设计文档。

里程碑使用 `M0`、`M1`、`M2` 顺序编号，状态统一为：

- `⬜ 未开始`
- `🔄 进行中`
- `🟨 待确认`
- `✅ 已完成`
- `⏸ 已暂停`

每个里程碑必须写清：

- 目标；
- 前置依赖；
- 交付范围；
- 验证入口及必要命令；
- 完成判定。

里程碑完成后在 `docs/开发进度.md` 对应里程碑小节简要记录产出、完成结论、遗留和必要风险；开发计划只维护里程碑状态和用户确认，不记录验证过程或数据。

单循环版本的开发计划获得用户确认后，在开始第一个代码里程碑之前，将 `docs/版本管理.md` 状态更新为 `开发中`。多循环版本在《总体设计》、实现循环总台账和首个实现循环开发计划都获得确认后，于首个实现循环代码里程碑开始前进入 `开发中`。计划确认本身不授权跳过里程碑或实现循环确认规则。

## 九、代码开发

代码开发按已确认开发计划推进。

每个里程碑执行：

1. 核对 `docs/版本管理.md` 中当前版本状态为 `开发中`；不一致时先修订版本台账。
2. 核对工作树、当前版本、当前实现循环、版本设计基线、里程碑授权和涉及模块。单循环版本
   以版本功能设计为基线，当前实现循环记为“唯一循环”；多循环版本以《总体设计》为共同基线。
3. 读取对应编程规范与模块约束。
4. 核查现有实现和依赖，再新增模块、trait 或公共类型。
5. 实现当前里程碑范围，并同步补充或更新必要的中文注释。跨层边界、状态所有权、并发与取消、
   安全权限、兼容迁移、恢复策略、反直觉平台差异和非显然算法不得只靠代码自行解释。
   跨持久化事实与内存投影、跨 owner/Session、事务提交与事件发布的内部函数同样属于强制注释范围；
   必须写清前置可靠事实、职责排除、幂等/失败恢复和 gate/锁顺序，不能以“不是公共 API”为由省略。
6. 执行该里程碑最小有效验证。
7. 在 `docs/开发进度.md` 简要记录里程碑产出、完成结论、遗留与必要风险。
8. 将里程碑状态改为 `🟨 待确认`。
9. 汇报实际产出、验证、偏差、遗留和风险。
10. 等待用户确认。

注释属于实现质量的一部分，不能留到用户 Review 时再补。禁止用逐行翻译代码的低价值注释凑数；
缺失必要注释、注释与实现不一致或仍保留已失效说明，都视为当前里程碑未完成。

禁止：

- 未确认当前里程碑就开始下一里程碑；
- 把多个未验证阶段堆到版本末尾统一测试；
- 顺手实现后续版本业务；
- 覆盖用户已有改动；
- 未经明确要求执行 `git commit` 或 `git push`。

出现以下任一情况必须停止扩大改动并重新核对：

- 现有实现与功能设计假设不符。
- 关键协议、权限、持久化或架构取舍尚未确定。
- 测试或构建暴露非预期跨模块影响。
- 涉及破坏性文件、数据库或 Git 操作。
- 工作树存在与当前版本改动重叠的未知修改。

### 实现循环验收、提交与阶段归档

多循环版本的每个实现循环都必须严格收口，不把完成判定推迟到总版本末尾。

1. 该实现循环的全部里程碑已获得用户确认。
2. 执行该能力必要的核心回归、跨模块集成和适用平台验证；不另建验收/验证记录文档。
3. 逐项核对该实现循环对《总体设计》中相关目标、边界、全局不变量和契约的符合性。
4. 核对功能设计验收点、数据和协议兼容、失败恢复、安全权限、未执行项、偏差和风险。
5. 用户确认实现循环验收通过后，进入 `待提交`；不得以里程碑通过代替实现循环级验收。
6. 同步实现循环文档、版本级开发台账和 `docs/开发进度.md`，生成 `阶段总结.md`。
7. 将实现循环设计、实现、验收、阶段总结和台账状态收敛为同一个可提交批次，执行
   提交准备并向用户报告精确变更和建议 commit message；阶段总结只保留完成结论和遗留，不归档验证数据。
8. Git commit 与 push 必须在当次获得用户明确授权；版本或实现循环计划确认不视为
   未来提交授权。未获得授权或提交失败时，实现循环保持 `待提交`，不开始下一实现循环。
9. 获得授权并完成提交后，该提交同时完成实现循环阶段归档，实现循环状态为 `已归档`。
10. 已归档实现循环的设计、计划、验收和总结在当前版本内视为稳定事实。后续实现循环
   不得静默改写；如整合发现必须修改，要重新打开受影响实现循环，记录原因、影响和重新
   验证结果，再次经用户确认。

实现循环阶段归档只证明该能力及其契约已完整收口，不表示总版本已可发布，
也不产生独立的版本号、tag 或兼容承诺。

## 十、版本验收

单循环版本的全部开发里程碑获得用户确认后，或多循环版本的全部实现循环
已完成验收、提交门禁与阶段归档后，先将 `docs/版本管理.md` 状态更新为 `验证中`，
执行跨循环的版本级验证，不另建验收记录或验证数据文档。

在现有开发计划中维护验收结论：是否完成、用户是否确认、未完成项及必要风险。命令、日志、
用例数量、数据库计数及快照不纳入流程文档；需要解释时在会话中按实际情况说明。

版本级验证结合已经完成的核心验证与必要的跨循环检查，覆盖升级、恢复、兼容、安全、分发和
适用平台风险。不为归档重复已完成验证，也不能用单个实现循环通过代替跨循环验证。
不能以"应该通过""命令已运行"代替实际结果；测试、构建、文件和接口展示状态必须按实际情况区分。

验收检查完成但尚未获得用户确认时，版本仍保持 `验证中`，不能提前标记为 `已完成`。

## 十一、版本归档

用户确认验收通过或明确暂停版本后，执行归档：

1. 单循环版本创建 `docs/versions/vX.Y.Z/`；多循环版本直接将
   `docs/design/vX.Y.Z/` 整体移动为 `docs/versions/vX.Y.Z/`。
2. 将本版本在途文档从 `docs/design/` 移入归档目录；多循环版本保留
   `cycles/CNN-<循环短名>/` 的设计、计划和阶段结论，不复制验证数据或临时产物。
3. 单循环版本去掉文件名中的版本前缀，统一为：
   - `功能设计.md`
   - `技术方案.md`
   - `界面交互设计指导.md`
   - `开发计划.md`
   - 专题文档同样去掉版本前缀（如 `代码审查.md`）。
   多循环版本的文件原本不含版本前缀，不需要重命名。
4. 不存在的可选文档不补空文件；不为已归档实现循环再生成第二份汇总副本。
5. 新增简洁的 `版本总结.md`，记录实际完成范围、验证结论、偏差、遗留项和后续版本入口。
6. 修正归档内部引用。
7. 在 `docs/版本管理.md` 中将该版本从路线图详细登记移入历史版本，记录完成或暂停日期、归档目录、实际结果、验证结论和版本总结。
8. 将 `docs/开发进度.md` 中本版本的进度内容移入归档目录（命名 `开发进度.md`，随归档一并提交）；本地进度清理已归档内容，并登记下一个当前目标版本，尚未启动设计时状态为 `待启动`。

归档使用移动而不是复制；`docs/design/` 与归档目录不能同时保留同一版本副本。归档目录视为只读；后续纠错保留变更说明，不把新版本工作追加到旧归档。

暂停版本使用同样流程，并在版本总结和 `docs/版本管理.md` 中记录暂停原因和恢复条件。

## 十二、提交准备

版本归档与提交准备是两个独立步骤。多循环版本在每个实现循环验收后设置提交门禁，
以使代码、完成结论和阶段归档保持对应；但仍不将归档动作视为 Git 授权。版本开发中
可以存在多个实现循环提交，最终版本归档不要求与某一个 Git 提交一一对应。

未经用户明确要求：

- 不执行 `git add`；
- 不执行 `git commit`；
- 不执行 `git push`。

用户明确要求提交准备时：检查改动、暂存指定文件、为每个获授权范围草拟 commit message，并向用户报告暂存范围和未暂存改动。

commit message 使用：

```text
<type>: <message>
```

`type` 可取 `feat`、`fix`、`docs`、`style`、`refactor`、`perf`、`test`、`chore`。

## 十三、验证矩阵

按实际改动选择最小有效验证：

| 改动范围 | 最低验证 |
| --- | --- |
| 仅文档 | 相对链接、路径、命令和文档一致性检查 |
| Rust 格式或小型实现 | `cargo fmt --all --check` + 相关 crate 测试 |
| Rust 公共 trait、协议、并发或 Runtime | `cargo clippy --workspace --all-targets --all-features -- -D warnings` + `cargo test --workspace` |
| 前端 TypeScript/CSS | `cd apps/desktop && npm run build` |
| Tauri command、配置、capability | 前端构建 + `cargo test --workspace` + `npm run tauri -- build --no-bundle` |
| 窗口、托盘、快捷键、macOS 权限 | 构建 + 实机启动和交互验证 |
| 实现循环阶段收口 | 实现循环设计验收点、里程碑完成结论、未完成项、阶段总结和提交状态一致 |
| 版本阶段转换 | `docs/版本管理.md` 的状态、当前版本、路线图/历史版本位置和文档链接与实际阶段一致 |

无法执行且影响完成判定的验证，只简要记录阻塞原因及影响，不创建额外验证材料。

## 十四、长期决策与范围变化

以下内容同步更新 `docs/重要决策与变更记录.md`：

- 架构、模块边界和目录结构；
- 核心技术栈、依赖方向和运行方式；
- 跨模块协议、权限、安全、持久化和部署策略；
- 版本、里程碑、归档和提交协作机制；
- 用户确认的重大范围调整和验收口径。

临时实现细节和单个里程碑进度不进入重要决策记录。
